FLY-2147 · runner 按「角色 + 项目」挂记忆目录

设计稿 · 2026-09-03 · 上游:FLY-1984 Epic PRD §B「runner 也要有记忆」+ §卡在哪 · 文档:engineering/doc/FLY-2147-runner-role-memory/(exploration / research / plan)· Codex 设计评审 8 轮后 APPROVED,期间 Tadashi 裁定 6 次(不加开关、fail-closed、目录编码证明式测试、设置探测收窄为「存在即冲突」等),都已写进 plan

一句话

以后每个 runner(干活的 AI 执行体)起来时,会被指到一个只由「哪个项目 + 哪个角色」决定的记忆文件夹——所有在 flywheel 做 QA 的共用一份,第十次来的 QA 读得到前九次学到的;文件夹不随 issue、不随工作目录、不随一次性编号变;而且 Flywheel 在起 runner 之前会先量一次那份索引,超长时在日志和 runner 的提示词里都说出来「从第几行起没进来」,不再悄悄丢。

范围只是 PRD 里她勾的 B0(「工程加上挂记忆目录的能力」)+ B1(「记忆挂在角色 + 项目上」)。备份到私有仓(A 线)、Codex 那边(C1)不在本单。

现状与三个实测(2026-09-03 本机)

runner 今天不是「没有记忆」,是「记忆不按角色分」

  • Claude runner 今天有一个记忆文件夹,由 Claude Code(Anthropic 的命令行工具,runner 就是它的一个会话)按「哪个 git 仓库」自动指定:~/.claude/projects/-Users-xiaorongli-Dev-flywheel/memory/,里面已有 573 个文件。
  • 所有角色(设计、实现、QA、PM …)和你本人在 ~/Dev/flywheel 里开的会话,写的都是这同一份。所以「qa 记得所有 qa 学到的」那一格今天确实不存在——但「什么都没有」也不对,PRD 事实底稿已经纠过这一句。
  • worktree(每个 issue 的临时工作目录)删掉不会丢:231 个 worktree 目录里 0 条记忆,全在主仓那一份。这与 PRD 的担心相反,是好消息。

实测 1:「挂目录」的能力 Claude Code 已经有

官方文档有一个设置键 autoMemoryDirectory。我用最小成本的模型跑了对照:不带这个键,模型报告的记忆目录是主仓那一份;带上这个键指向一个临时文件夹,模型报告的就是那个临时文件夹。所以缺的不是「能力」,是 Flywheel 在起 runner 时把它算出来、传进去、守住边界。

实测 2:「静默截断」在今天的版本里对模型不静默,但对人静默

造的索引模型看到了什么
218 行 / 12KB(行数超)第一条看得见,最后一条看不见;上下文里有一句 MEMORY.md is 218 lines (limit: 200). Only part of it was loaded.
153 行 / 32.7KB(字节超)同上;上下文里有一句 WARNING: MEMORY.md is 31.7KB (limit: 24.4KB) … Only part of it was loaded.
修正 PRD 一句话:Claude Code 2.1.259 超限时会给模型一条 WARNING,不是「不报错」。但三件事仍然成立,也正是本单要补的:① 这条 WARNING 只在模型脑子里,不进任何日志、事件、台账——Tadashi 的索引今天 152 行 / 32,998 字节已经超了 8.5KB,没有任何人被通知;② 没有东西阻止它发生,已超的存量每次开会话都丢后段;③ WARNING 不说丢了哪几条。

项定案为什么
根目录~/.flywheel/runner-memory/(隔离台架可用环境变量换根)Flywheel 自有、不分厂商;两级路径直接念出「项目 / 角色」;避开已被占名的 ~/.flywheel/memories/
角色 id 来源DAG 节点 id(qa / eng_design / implement …)或旧派工的 agent 名(generic / qa)不新造一套词;新旧两种派工的 qa 同名即同一份——正是「所有 QA 共用一份」
盘上目录名全小写的名字原样用(flywheel/qa 不变);含大写的名字用「小写 + -- + 大写位置掩码」(Sub → sub--1),可以一一还原Codex 评审两轮抓出来的:Mac 的磁盘不分大小写,配置里又允许 Sub 和 sub 同时存在,不编码就会把两个身份的记忆混成一份;第一版用哈希后缀又被抓到不是一一对应(合法小写名可能撞上它)。提示词和日志里仍显示原名
项目 id 来源Bridge 已归一的项目名(flywheel)缺了就不挂载,日志说明
索引形状MEMORY.md 一行一条指针 + 一事一文件(带 name / description / type 头)与 Lead 侧逐字同形;由 Claude Code 原生装载与写入,Flywheel 不再造一套
存量 573 条原样不动;runner 提示词里留一行「项目共享记忆在这里,需要时自己翻,不要往那里写」不迁移、不拆;有界(一行)、可见

有界且可见:超界要说出来,而且是两面说

图 3 · 起 runner 前的索引守卫时序:预算内也留痕,超预算时日志与提示词各说一遍

数字值出处
硬上限(Claude Code 装载侧事实)200 行 / 25,000 字节,先到先截官方文档 + 本机实测
软预算(本单守卫阈值,可配)160 行 / 20,000 字节留 20% 余量,让「这次写会超」的原生报错先于「装载时丢后段」发生
超预算时日志一行 OVER BUDGET … first_dropped_line=K + 提示词一行「约从第 K 行起没被加载,开工第一步先把索引压回预算内(搬正文,不删条目)」K 按两个维度算出更早的那个;文案写「约」,因为 Claude Code 没公开精确切法
没超时日志一行 mounted … over_budget=false「可见」不只在坏情况下可见
某份 Claude Code 设置文件(机器级、用户级或项目级)里出现了任何「自动记忆」相关的键——每次起 runner 时探测,存在即冲突,不去算谁赢按失败处理:不挂载、尽力关掉这次执行的自动记忆,日志与提示词带上那份文件的路径和键名,提示词明说「这次的有效状态未知,报 Lead」;由 Tadashi 去处理那台机器Tadashi 裁定:Codex 评审曾要求我们完整求解 Claude Code 的设置优先级(机器级 true/false、目录覆盖、目录合并、MDM…),那等于在 Flywheel 里再写一个设置引擎;收窄成「出现即冲突」既每次实测、又不长机制。探测不到的(MDM、服务器下发策略)明写为边界
挂载失败,或这次执行没有「项目 + 角色」身份关掉这次执行的自动记忆(fail-closed:什么都不装、写了也不留),日志 + 提示词 + 调度上下文三面可见,runner 照常起Tadashi 裁定。我原稿写「退回项目共享记忆」,Codex 评审指出那会让「共享份只留只读指针」这条规矩在失败时悄悄失效。代价:极少数没有项目名的旧式派工从此没有自动记忆(今天有),Tadashi 已接受
回退只有代码回滚,没有运行时开关;回滚后 runner 回到项目共享记忆,盘上已写的记忆不删Tadashi 转达你的直令「不加旋钮,写死」;我原本设计了一个 off 开关,按裁定删掉。「不挂载时提示词与改前逐字相同」由测试锁住,这就是回滚后的形状

关键取舍与否决的方案

方案处理理由
A · 用 Claude Code 自己的 autoMemoryDirectory 挂目录 + Flywheel 在起进程前做守卫采用代码最少(一个键 + 一段守卫);和 Lead 侧是同一套机制;runner 只有一个写入目标,不会被两套「记忆说明」搞糊涂;Claude Code 写入侧的格式指导免费拿到
B · Flywheel 自己读索引、自己截、自己塞进提示词,不动 Claude Code 的记忆否决runner 会同时有两个记忆目录、两套写法,「第十次来的 QA 到底写哪边」没有单一答案;还要自己重写一遍 Claude Code 已做好的格式与写入守卫;违背「一个真相源」
C · 给每个「项目-角色」造一份 agent 定义,起 runner 时用 --agent否决要往机器级 ~/.claude/agents/ 写文件(触碰全局配置,项目规则禁止);--agent 会整体替换提示词 / 工具 / 权限,与现有角色注入打架
D · 把记忆放进项目仓 .flywheel/memory/ 一起提交否决并行 runner 在各自分支写同一批文件 = 共享写点,合一个其余全冲突(里程碑表那次已实测 100%);内容含内部判断,不该进公开仓
根放在 ~/.claude/agent-memory/ 里蹭 A 线备份否决混进 Claude Code 自己管理的 Lead 目录树,「一个 Lead 一个文件夹」这句话被污染,名字还可能和 Lead id 撞;A 线备份多加一个根就够
写入时机写死进引擎(一个 issue 写一次)不写死按你的原话留给 Tadashi;本单只在提示词里建议「收工前写、一次 ≤5 条、只写可复用的判断」,引擎不做回执

怎么验收(PRD §B 四条逐条对上)

PRD 说怎么验
runner 起来能读到它这个角色 + 这个项目的记忆,不是空的第二次起同「项目 + 角色」的 runner,提示词里的索引含第一次写下的那一行
第二次跑读得到第一次写的同上(真命令行往返:第一次让模型把一个一次性随机码写进索引指针行,第二次在另一个目录里、提示词不含那个码,要它复述 ⇒ 必须逐字匹配)
换 issue、换工作目录,读到的还是同一份目录路径只由「项目 + 角色」决定,代码里不含 issue 号 / 执行号 / 工作目录;第二次往返在另一个临时目录里跑
工作目录清掉之后写下的东西还在删掉第一次的工作目录,在第三个目录再问一次,仍须逐字复述出那个码
(本单追加)超界要说出来四种日志形状各一条测试逐字 grep;超行数与超字节各一个样本算 K

诚实边界:这个设计做什么、不做什么

做

  • Claude runner 的记忆目录只由「项目 + 角色」决定;索引由 Claude Code 原生装载,与 Lead 同机制。
  • 起 runner 前的有界可见守卫:预算内留痕,超预算在日志与提示词两面说清起始行。
  • 默认对所有 Claude runner 生效,没有运行时开关(按你的「不加旋钮」直令);回退只能代码回滚,盘上已写的记忆不删。
  • 挂载失败或没有身份的 Claude runner,这次执行没有任何自动记忆(fail-closed),而且三面可见——这是 Tadashi 的裁定,也写进了 plan 防止以后被当 bug 改回去。
  • Codex runner 也拿到同一个目录的环境变量与说明段,至少能翻同角色的记忆。

不做 / 不能保证

  • 不改变 Claude Code 装载侧的截断本身,只让它在发生前被看见;K 是近似值(官方没公开精确切法)。
  • 同角色并行的几个 runner 同时往索引追加一行,有极小的丢行窗口(正文一事一文件不受影响);不加锁——加锁是长机制,先看会不会真发生。
  • 存量那 573 条不再自动进 runner 上下文,只留一行只读指针。如果你更想让 runner 两边都自动读,那就要换成被否决的方案 B,是另一份设计。
  • Codex runner 没有原生挂载(PRD 的 C1 你没勾)。注意:DAG 里「实现」节点默认走 Codex,所以 C1 之前「implement」这个角色的记忆主要由 Claude 系实现 runner 写、Codex runner 只能翻。
  • Codex runner 的说明段只说「目录在这、自己翻、自己写」,不声称任何自动装载(Codex 评审抓出来的:同一段文案发给 Codex 就是假合同)。antigravity / kimi 这两种 runner 本单什么都不给。
  • 守卫读索引最多读 64KB:字节数永远精确,行数在索引超过 64KB 时只报「至少 N 行」;这是为了一个坏掉的超大索引不能把调度进程拖死。
  • 不给角色名的三处配置加载器加文法校验(范围纪律,Tadashi 裁定):不合文法的角色会被可见地跳过并关掉记忆;「今天没有这样的角色」由一条测试证明,不是假设。以后要加校验另开 issue。
  • 不备份到远端(A 线);不做跨角色能不能互读的策略(PRD 明说没讨论过);不整理任何人的既有索引——包括 Tadashi 那份已超限的。
