FLY-1520 · DAG 派发引擎 — 设计稿

v2 上线批次 · 2026-07-28 · 设计已过 Codex 跨族评审 8 轮 APPROVED · 每个板块下方可留 comment,页底一键复制全部

1 · 一句话总结

给 v2 装上心脏:一个只认「图」的派活引擎——每张 issue 是一张节点图,节点自己带完成合同,全部完成后 ship 只做三条通用检查;没有它,v2 上线后一件活都派不出去。

「DAG」= 有向无环图,大白话就是「一张不绕圈的任务依赖图」:谁先做、谁等谁,全画在图里。三段式(设计→实现→QA)只是这张图最常见的一种形状,不再是特权。

2 · 为什么现在必须做

审计实证:数据库的表(任务/依赖/门/通行证)在 FLY-1497 已建好,设计在 FLY-1498 已过评审,但 main 上没有一行代码消费这些表——引擎零实现。派发、完成、ship 三件事现在都没人干。

本单与 FLY-1518(引擎外呼记账迁移)同批并行,两单都合完才进 FLY-1502 总切换。施工铁律:新代码全部进新包 packages/v2-dag,不碰 1518 正在改的文件、不加任何数据库迁移。

3 · 核心流程:一张活从建图到合入

派发器只看两件事:图的形状(上游节点是否全部完成)和节点状态(有没有人正在干)。它不认识「design / implement / qa」这些名字——1 个节点的纯文档单、2 个节点的小修单、N 个节点的大活,全走同一条查询,零特例。

4 · 节点完成合同:证据说了算,名字不算数

节点完成时,由它自己把「合同已满足」的证据和完成状态写进同一笔账(同一个数据库事务:一组写入要么全部成功、要么一条也不算)。这消灭了「先标完成、事后补记录」的老病。

  • 纯 PRD/文档单:实际 diff 里没有产品代码 → 全程零 code review 要求,一路畅通;
  • QA 单:合同就是一份 verdict(测试判定,且必须是 pass)→ 不会被错误索要 code review;
  • 改了产品代码:必须有「另一族 AI」(比如 Claude 写的代码由 Codex 审)对着真实 diff 做的逐字节评审——看的是真实作者集合,写过这段代码的家族不能自己审自己。

5 · 三层模型:任务 → 尝试 → 会话

返工不造新节点:同一个任务上开第 2 次尝试,旧套件收干净和新套件武装好在同一笔账里完成。会话断了续命(resume)= 换一个新的绑定和新的世代号,旧进程哪怕还活着,它的迟到写入会被账本整体拒绝——这就是「僵尸进程写坏账」的根治。

每个代码工作区同一时刻至多一个「活写手」,谁改过哪段代码有账可查,这正是上面「不能自己审自己」的依据。

6 · generic ship:三条检查,不多不少

ship 是一个动作,不是图上的节点。执行前只验三条通用检查:① 你的批准还绑着当前代码位置;② 图上节点全部成功;③ 代码位置没有漂移。ship 绝不重新过问「有没有 code review」——那是节点完成合同的事,节点没过合同根本到不了这一步。

每一次外呼(merge)都先在「黑匣子」(actions 表:只记「原本要做什么、最后成没成」的流水账)里记「准备做」,断电后靠去 GitHub 现场对账收口,绝不靠猜。

7 · 数据/结构模型:全在一本账里

落点装什么
tasks + 依赖表图本身:节点、连线、每节点的完成合同与「是否写代码」标记
attempts / activations每次尝试、每次会话绑定;「每任务至多一个活尝试」由数据库唯一约束硬保证
meta 键空间完成基线(span)、写手链、ship 门(每 issue 至多一扇当前门,值带单调版本号防旧进程重放)
actions 黑匣子外呼流水账(FLY-1500 已建,本单按已合形状消费,不改表)
capabilities一次性通行证:founder 批准时签发,ship 时消费一次即作废

零迁移:本单不改任何表结构。合同等字段承载在既有 payload/meta 里,不变量由「全库唯一写入口」强制——这是 Lead 在开工裁定拍的路线 A,后续可机械提升为正式列。

8 · 关键取舍与被否掉的方案

取舍点选了什么 / 否了什么
零迁移 vs 改表选零迁移映射(与 1518 并行不打架);否了「现在就重建表」——会把两单变串行,重演迁移链连环冲突
ship 记账方式直接编排账本的公开动词,保证「第 6 次失败 + 关门 + 通知 founder」同一笔账;否了复用现成薄壳——它做不到同事务
启动防重一次性启动通行证 + 操作系统级锁:同一个会话至多启动一次,收割和启动互斥;否了「只靠读一遍再确认」——读完到执行之间仍有缝
换人重试换执行者必须 founder 重新批准(新门);否了「系统悄悄换人」——授权不能被静默转移
每 issue 可 ship 的工作区本批限恰一个(想多个 → 1502 之后);否了现在就支持多个——门只有一个绑定位置,多写会含糊

9 · 评审与验收

APPROVEDCodex 跨族设计评审 8 轮,每轮都抓到真问题并全部采纳(共 30+ 项修订,含 3 处「按原文实现会构建不出来」的映射错误),第 8 轮零遗留通过。

  • 全链 E2E:一张三节点 issue 从建图 → 逐节点完成(合同+证据同一笔账)→ founder 批准 → 三条检查 → 合入落账;
  • 8 个断电点逐一「杀掉再重放」,不丢账不重账;
  • 纯 PRD 单零 code review 畅通、QA 单只认 verdict——各有专门测试;
  • 静态围栏:代码里出现「design/implement/qa」等节点名字面量直接测试红。

10 · 诚实边界:这个设计不做什么

  • 不做生产接线:常驻循环由谁托管、v2 merge 通道的激活探针(必须真实证明分支保护有效、执行者不是管理员)都归 FLY-1502 总切换单;
  • 不挡物理越权:执行 agent 真实持有 GitHub 钥匙,账本只能记账与对账,结构性约束靠 1502 的世界侧探针;
  • 账本外的直接改库不设防——这与 v2 前提一致:唯一写路径就是边界;
  • 超大图(超过上限,初值 500 节点)建图直接拒绝,而不是硬撑;
  • 老的引擎旁路建任务的口子仍在(1518 不关),本引擎只认自己建图时登记过的成员,合流归 1502。
