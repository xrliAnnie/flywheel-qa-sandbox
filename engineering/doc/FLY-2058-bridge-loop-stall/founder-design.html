FLY-2058 · Bridge 主循环卡死:根因取证与防护设计

Issue: FLY-2058 · 日期: 2026-08-28 · 设计文档: engineering/doc/FLY-2058-bridge-loop-stall/(exploration / research / plan)

① 一句话总结

Bridge 反复退出码 137(= 被 SIGKILL 强杀)的凶手已实锤:是它自己的「事件循环守卫」在自杀(EventLoopGuard:一个专门盯着主循环的看门狗线程,发现主循环 60 秒没心跳就把整个进程杀掉,让系统自动重启)。账本已有 15 次(写 issue 时 14 次,本设计当天又死 2 次)。账本形状把 15 次分成两个不同根因族,本设计的三条腿:给下一次死亡装上"行车记录仪"(归因取证)、让守卫别在机器整体假死后"补刀"(冻结止损)、把已锁定的头号嫌疑先行缓解(git 推送同步链)。

② 事实:15 条死亡账本,自己分成两族

守卫击杀前会把一行「取证记录」同步写进独立文件 ~/.flywheel/bridge-loop-guard.log —— 这就是全部 137 的账本。之前在主日志里搜不到痕迹,是因为主日志走的异步输出(写完内存缓冲就算完,进程被强杀时缓冲里的内容直接丢失),而这个账本是同步落盘(写到磁盘确认后才继续,强杀也丢不了)。

族次数卡死时长判据含义
Family A主线程独卡 11全部 60–65 秒 守卫线程按时(每 5 秒)在检查,60 秒阈值一到立即击杀 主线程真的被某个操作卡住 ≥60 秒,击杀是正确的;真问题是"是什么卡住了它"
Family B整进程冻结 4 + 1237 / 362 / 576 / 890 / 1008 秒 检测到的卡死时长远超阈值+检查间隔,唯一解释是守卫线程自己也被冻了同样久 整台机器/整个进程被内存风暴(swap 风暴)冻住,解冻后守卫醒来"补刀"——击杀是有害的(机器最难受时追加一次冷启动)

当天新增的两次(23:00 / 23:25 UTC)已实测验证:卡死窗口内整机系统日志正常流动(每 10 秒三五千条)⇒ 机器没冻,是 Bridge 独卡,属 Family A。另:15 条账目没有一条带归因字段 —— 已有的「同步操作标记」机制(sync-op marker:做慢操作前先写一个"我在做 X"的标记文件,守卫击杀时读它,就知道死时在干嘛)接线正确但生产覆盖率≈0,只包了 2 个冷门操作。

③ 核心流程:守卫怎么杀掉 Bridge 的

主线程每秒往一块共享内存(SharedArrayBuffer:两个线程都能读写的同一块内存)写一次当前时间当作心跳;独立的守卫线程每 5 秒来看一眼,发现心跳 60 秒没动,就写取证、开枪。系统的 launchd(macOS 的服务管家,负责把挂掉的服务拉起来)在约 5 秒后自动重启 Bridge。

这个机制本身是对的(它把"挂死"转成"可自动重启的崩溃")。问题在两处:它杀之前几乎不取证(死无对证),以及它分不清"主线程独卡"和"整机被冻"(后者不该杀)。

④ 设计:击杀前判族 + 取证 + 冻结不补刀

核心改动全部集中在守卫线程内部:检出卡死后,先看自己的检查间隔(tick gap)——守卫每 5 秒查一次,如果它发现自己"上一次检查"竟然是 60 多秒前,说明它自己也被冻结过 ⇒ 整进程冻结(Family B),给主线程 5 秒宽限窗证明自己活着;宽限后活了就只记账不杀。守卫一直健康的场景(Family A)行为与今天完全一致,60 秒照杀,只是杀前多花 ≤3 秒采一个「取证包」。

真死锁在 Family B 分支只多活 5 秒;而 8-15 那晚的"连环三杀"(机器 swap 风暴中被补刀 3 次、每次追加冷启动)在新设计下是 3 条"记账不杀"。

⑤ 头号嫌疑:git 推送的"同步三连"

静态盘点整个 Bridge 进程里所有可能阻塞主循环 ≥1 秒的同步操作,只有一处能解释"连续卡 60 秒以上":工作流文档推送(pushCommit)在一口气里连跑 3 个走网络的 git 命令,每个用 spawnSync(同步启动子进程:子进程跑完前,主循环整个停摆),单个超时上限 30 秒,之间零让出 ⇒ 网络挂起时最坏 90 秒连续阻塞 —— 与 Family A 全部落在 60–65 秒的击杀签名精确吻合;8-25 那次死亡前最后一行日志正是网络故障(fetch failed)。

缓解(两处小改,不动架构)

  • 网络类 git 操作超时 30 秒 → 10 秒:单链最坏 90 秒 → 30 秒,低于 60 秒击杀线;
  • 连续 git 调用之间插入一次事件循环让出(await yield:让主循环喘口气处理别的事,心跳恢复跳动):结构上消灭"单口气多连"。
⚠️ 诚实声明:这是「机制完全吻合 + 时间旁证」的头号嫌疑,还不是实证(15 次账目都没归因字段)。所以取证仪器照装 —— stall 频率 1–3 次/天,仪器上线后一两天内下一次死亡就会自带答案,证实或证伪它。

⑥ 数据模型:取证包字段(击杀前 ≤3 秒采齐)

字段是什么回答什么问题
tick_gap_ms守卫自己两次检查的实际间隔一个数判族:≈5 秒 ⇒ 主线程独卡;≈卡死时长 ⇒ 整进程冻结
childrenps 抓的 Bridge 子进程清单(≤10 条,每条 ≤200 字符)spawnSync 卡住时,卡住它的子进程命令行(如 git push …)直接躺在这里 —— 对头号嫌疑是决定性证据
last_sync_op同步操作标记(覆盖率从 2 处扩到全部 git/tmux 同步调用,在各自的唯一漏斗函数处一次收口)死时在做哪个已登记的慢操作
rss_mb / load进程内存占用与系统负载是否死于内存风暴之中

全部字段采集失败都写 null,取证失败绝不改变击杀语义(总预算 3 秒,超时带残缺包照杀)。曾评估用 macOS 的 sample 抓原生调用栈,当天实测被系统安全机制拦截(非 root 拿不到线程状态),已排除 —— 这也是为什么选上面这套组合。

⑦ 关键取舍与被否的方案

被否 / 缓议方案为什么不
用 sample/spindump 抓原生栈实测被 macOS 安全机制拦截(空栈);spindump 要 root
CDP/inspector 暂停主线程抓 JS 栈只覆盖纯 JS 自旋一族,对同步子进程/同步 SQL 全盲;复杂度与安全面不成比例。若归因后仍有"暗 stall"再立后续单
git 全链改异步(asyncify)18 个调用点大重构,在"嫌疑未实证"阶段不成比例;留给归因实证后的后续单
给每条 SQL 查询加标记成本/收益不匹配;靠"无标记 + 无子进程 + 守卫健康"的残缺包形状反向指认慢 SQL
无条件宽限复查(不分族)会让真死锁的 Family A 也多活 5 秒 —— 守卫健康时 60 秒已经等够了,不该再宽限
动 launchd ExitTimeOut(issue 原头号线索)已被账本证伪:15 次 137 全部来自守卫自杀,毫秒级对齐;launchd 线索留给 shuttle 成对重启(另一机制,另立单)

三条腿互相独立、各自单文件可回滚、零新子系统、零新配置项 —— 符合「只删不加」红线的精神:所有新逻辑都收在守卫 worker 一个字符串常量和 git 封装的唯一漏斗函数里。

⑧ 诚实边界:这个设计做什么、不做什么

做

  • 下一次 stall 自带归因(取证包),两族显式记账;
  • 整进程冻结不再被补刀(8-15 式连环杀清零);
  • 头号嫌疑的最坏阻塞压到击杀线以下;
  • 行为级验收:真进程被 SIGKILL / 被 SIGSTOP 冻结不杀,都有 harness 实测(issue 明确要求)。

不做 / 未知

  • 还没有任何一次 stall 的实证归因 —— pushCommit 是最强嫌疑,不是结论;若下一次取证指向别处(慢 SQL、纯 JS 自旋),按取证立后续单;
  • Family B 的机器级 swap 风暴"谁吃的内存"不在本单 —— 本单只保证 Bridge 在风暴里不自杀;
  • shuttle 班车时的成对重启(31 秒间隔)不在本单:账本里没有一条落在班车时刻,那是另一个机制(疑似 launchd 停服超时),只留观察线索;
  • 主日志无时间戳、每次重启清零的问题不在本单修(绕过:取证由守卫击杀前完成)。
