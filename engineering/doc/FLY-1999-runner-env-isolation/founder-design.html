FLY-1999 · 设计阶段交付 · 2026-08-23 · 工程 Runner(Tadashi 麾下)

●① 一句话总结

每个 AI 员工(runner)开工时拿到的"工作环境"不是按它自己的身份配的,而是碰巧继承了"谁先启动了共享终端服务器"谁的全套环境——8/22 晚它们继承的是 infra-bot 的:于是所有 runner 都在用 infra-bot 的 Codex 账号(跨号烧量)、还整包带着 30 多个机器人令牌和 API 密钥(其中一个被完整打进了工作记录,已报你建议轮换)。本设计把它改为:开工环境从零按白名单构造——不在名单上的东西一律不存在。

术语:runner = 干活的 AI 员工进程;infra-bot = 基础设施自愈机器人(另一个 AI 员工);Codex = OpenAI 的编程 AI,按账号计费/限流。

●② 病根:发生了什么

tmux(所有 AI 员工共用的终端服务器,你在 cmux 里看到的那些窗口就跑在它上面)有个规则:服务器重启后,谁第一个碰它,它就把谁的全套环境变量拍成快照,之后每个新窗口都默认继承这份快照。8/20 宿主机重启后,第一个碰它的是 infra-bot Lead 的启动脚本——它带着 infra-bot 的 Codex 账号路径,还把密钥文件(.env,175 行)整个灌进了自己的环境。从那天起,每个新开的 runner 都继承了这一整套。

当晚的代价链(全部可归因到这个病)

  • 误诊:「五个 Codex 账号同一时刻恢复额度 ⇒ 一定是机器级限流」——其实是同一个 infra-bot 账号被测了五遍(坏仪器给出的一致性假象),污染了当晚两条线的推理和给你的汇报;
  • 两具"一启动就死"的 Codex 尸体:用的都是 infra-bot 的已限流账号,你切到 personal 号对它们无效;
  • 跨号烧量:我们项目 runner 的 Codex 消耗一直记在 infra-bot 账上,费用和限流归属全错位;
  • 一次明文泄露:runner 自查环境时把 OPENAI_API_KEY 完整值打进了工作记录。

补充:「PATH 上的 codex 指向 mufasa 的安装」是第四个症状,但它是磁盘上的一个符号链接被 Codex 自动更新器改写所致(FLY-1955 已防再犯),和环境继承是两条支流——见图中紫色分支;复位那个链接是一条运维动作,不在本单代码里。

●③ 修法:三层收口

核心思想只有一句:从"继承全部、再删几个已知的坏名字"翻转为"从零开始、只给名单上的"。旧做法(FLY-1715)删 6 个名字,这次证明坏名字的清单永远追不上;新做法是白名单——哪怕明天出现新的污染,它也进不了 runner 的环境。三层各管一段:

  • 第一层(核心):每个 runner 窗口启动前,环境从零重建。这层是结构性的:不管共享服务器脏不脏,runner 拿到的永远是精确的白名单集合;
  • 第二层(防再犯):代码里三个可能"第一个碰 tmux"的位置,都改成用最小规范环境去启动服务器——以后重启竞赛谁赢都不再把自己的全套环境固化进去;
  • 第三层(治存量):现在的服务器已经脏了,又不能重启它(会杀掉你的 cmux 视图和所有活着的 runner)——所以 Bridge 每次开机时按名字逐个删掉服务器里的秘密名和身份名(只按名字删,值永远不读不打印)。

直接效果:CODEX_HOME(告诉 codex 用哪个账号目录的变量)从 runner 环境里消失 → codex 回到默认目录 ~/.codex → 你的切号器(codex-profile)写的账号文件重新被读到——这正是自动切号(1756 族)的前置条件。

●④ 结构模型:白名单怎么组成

白名单只有两段,都有单一权威来源,没有第三个口子:

  • 静态段(约 31 个名字):操作系统正常干活必需的——路径、家目录、语言、时区、终端类型等。与 Codex 后端已在用的同一份安全基底对齐(那边一年来运转正常,是现成的对照组);
  • 动态段(约 20 个名字):这一次启动时系统显式发给这个 runner 的协议变量(它的任务编号、通信数据库路径、进度账本路径等)。关键:名单直接来自"发放动作本身"——发了什么名字,名单里就是什么名字,不靠人工维护第二份清单;
  • 其余一切不存在:包括别人的账号路径、全部 API 密钥、30 个其他 AI 员工的身份残留。验收测试断言的是"环境集合精确等于白名单"(逐名相等),不是"没看到坏名字"。

●⑤ 关键取舍与被否方案

被否的方案为什么否
继续扩充"坏名字删除清单"(在 6 个名字上加)这次事故里 stale 变量有 30+ 个,下次会是另一批——删除清单结构性地慢一步,永远在追
重启共享终端服务器,一次洗净会杀掉你的 cmux 视图和所有活着的 runner,代价不成比例;所以选了"按名字逐个删 + 等自然换代"
给 Claude runner 也做每任务独立的 Codex 账号目录会改变现有"全体共享 ~/.codex、跟着你的切号器走"的语义,那是 FLY-1893 的领域,不混入本单
顺手修掉 PATH 上指向 mufasa 的符号链接那是磁盘态、属运维动作(FLY-513/1955 已有防再犯和告警);本单只留一行运维手册,不写代码
给洗法加个开关(feature flag)你定过铁律:不加新 flag;且这类安全修无条件生效才有意义(与 FLY-1715 同姿态)

独立评审(Codex)抓出并已折入设计的 5 个问题

  • 3 个阻塞级:shell 变量展开位置写错(会让洗法"形似而实哑")、遗漏一个既有协议变量(会断老式任务的完成通知)、服务器救援工具的控制环境不能整体洗(会破坏它自己的契约);
  • 2 个高/中级:开机清扫漏了 runner 会话层的存量、命令字节预算估计偏低(实测 955 字节)。5 项全部采纳,第 2 轮评审通过。

●⑥ 诚实边界:这个设计做什么、不做什么

做:身份确定性(runner 里的工具解析到的账号 = 它该用的账号,不再看运气)+ 事故卫生(环境自查/日志不再天然携带全量秘密)+ 可验证的最小默认视图。
不做(必须说清):这不是防恶意的安全围栏。runner 和 Lead 同一个 macOS 用户、没有沙箱——它想主动读密钥文件随时读得到。本设计防的是"顺手用错/顺手泄露",不是"故意作恶";后者要靠别的机制(如 Codex 侧的 read-deny 围栏)。
  • 存量带病的 runner:已经开着的窗口,环境改不了(操作系统没有这个能力)——它们带病到自然换代为止;新开的全部干净;
  • 你手动开的新窗口:以后默认拿到的是最小干净环境(不再默认带 infra-bot 身份)——如果你需要密钥,手动 source 一下 .env 即可,这是行为变化,提前告知;
  • 第三层清扫生效时点:随下一班定时部署(00:00/12:00)的 Bridge 重启后首跑——不为本单单独投重启票(FLY-1959 纪律);第一层不需要重启,合并后新开的 runner 即生效。
