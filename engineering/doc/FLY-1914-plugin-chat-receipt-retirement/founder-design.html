FLY-1914 · 让 Discord 插件停止调用已删除的命令

设计文档(founder 版) · 2026-08-19 · Issue FLY-1914 · 每个卡片下方都可以留批注,最底部一键汇总复制

一句话

告警噪音的修复早已写好、审过、独立测过(FLY-1730 留下的插件 PR #23),只是没走完最后一步;本单就是把它推过终点线:核对没过期 → 你批准合入 → 按既有受管流程装进生产 → 真机验证告警归零——外加把「删命令必须先查谁在用」写成一条永久规矩。

1 · 现在发生着什么

你在 #flywheel-engineer 反复看到的 ⚠️ Chat receipt settlement recovery has failed N times…,机制是:

8 月 12 日主仓 PR #808 按设计删掉了命令行工具里的 chat-receipt 子命令(子命令 = 命令行工具的一个功能开关,比如 git 的 push/pull)——「回执记账」这件事已经改由新的 mailbox 队列(消息的持久化收发账本)负责。但生产上的 Discord 插件还是旧版 0.0.4,每次 Lead 回复你的消息后,它仍按老习惯去调那个已经不存在的命令 → 永远失败 → 失败记录堆进 spool(重试等待区,一个存放待办文件的目录) → 每 3-4 分钟重试一次、永远不会成功 → 失败超过 5 次就往频道发一条 ⚠️ 告警。

43 + 4 条今晚仍在堆积的失败记录(两个 Lead)
26 次单条最高重试次数
0功能损失——每条回复本体都真实送达了

纯噪音坏的只是「记账」这个已被判死刑的动作,消息收发完全正常。你 8-19 归档的 14 条之后,新的又堆了 43 条——不修它就永远刷下去。

2 · 为什么又是它——修复其实已经存在

这不是新问题。8 月 12 日你亲撞过同一批告警(当时还 ×6 连发),立的单是 FLY-1730,它走完了完整流程:

时间发生了什么状态
08-12FLY-1730 立案,设计过 3 轮独立评审完成
08-12插件修复 PR #23 写好:删掉整套过时的记账代码 + 删掉它向频道发内部告警的全部通路已过代码评审 + 独立真机 QA
08-13主仓配套(部署校验器兼容新旧插件)合入上线完成
08-18你拍板关单:插件半没做完(执行的 runner 死了),症状还在就开新单→ FLY-1914 就是那张新单

本次设计节点逐项复核过(2026-08-20 当晚实测):那个 PR #23 至今干净可合(代码零冲突、内容零漂移,和当时 QA 通过的版本逐字一致),它要的版本号 0.0.5 也没被别人占。所以本单不需要写任何新修复代码——需要的是把它送到终点。

3 · 修好之后长什么样

插件升到 0.0.5 后:回复照常送达;「记账」动作物理上不存在了(不是关掉,是删掉);就算消息接收环节真出故障,插件也只会往自己的日志里记一条(stderr 日志 = 只有工程师排查时才看的后台记录),它没有任何代码路径可以再往你的频道发内部告警。

4 · 怎么交付(部署才算完,合入不算)

沿用 FLY-1730 已批准的受管部署流程,但本次审计发现一个没人做过的前置步骤:8-13 合入的部署校验器(checker = 每次重启前自动核对插件是否完好的脚本)只更新了代码仓库,生产机器上的那份副本从没同步过——它还在按旧规则查验。不先补这一步,新插件一装、整个重启流程会被它拦下。所以顺序被设计评审(3 轮,APPROVED)钉死为:先同步校验器、再合入插件;合入前一刻还要重跑一遍核对,并把两个代码仓库临时「冻结」(冻结 = 窗口期内除本单外任何改动不得合入,防止别的改动搭车溜进生产),验收通过才解冻。

验收标准(独立 QA,真机):你的频道连发两条消息各获回复,15 分钟观察窗内零 ⚠️、spool 零新增;并用今晚的 43 条活失败记录做对照组——同样操作,旧代码必产失败记录,新代码零产。

5 · 关键取舍与被拒绝的方案

方案判定为什么
① 删掉插件里的过时记账代码(采纳,即 PR #23)采纳记账机器已判死刑,插件不该假装它还活着;成品已过评审和真机 QA,零新代码、零新机制
② 插件启动时先探测命令还在不在,不在就静默停用拒绝给死代码续命,还新增一个「探测」故障面(探测误判会静默丢事或复活告警);且要新写新审新测,反而更贵
③ 只删告警、留着重试拒绝失败记录永久堆积 + 永续空转重试,「永败重试」本身就是 issue 点名不允许的现状
规矩用「写进 CLAUDE.md 的过程规矩」而非「通用自动检查器」采纳前者规矩内容:今后凡删除/改名 CLI 子命令的 PR,必须附「谁在用它」的排查证据(插件源码 + 生产插件缓存 + 主仓脚本)。自动检查器无法预知未来会删什么命令,通用化必然误报或漏报;针对具体命令族的自动门(receipt 那套)已经存在

本次已按新规矩做了一遍全量排查:插件总共调用 4 个子命令,只有 chat-receipt 一个是断掉的,不存在第二处同类问题。

6 · 诚实边界

本单做

  • 复核并采纳 PR #23(若窗口期内插件仓库动了,走「重测重审重 QA」路径,绝不带着失效的 QA 结论合入)
  • 主仓一个纯文档 PR:CLAUDE.md 新增「删命令先查消费者」规矩 + 本设计文档
  • 受管部署(先补校验器同步这块砖)+ 真机验收 + 最终把残留失败记录归档(沿用你已建立的归档先例)

  • 「同一告警 ×6 连发」的寄生进程问题 → FLY-1715(在途;部署时的进程清点会兜住旧进程)
