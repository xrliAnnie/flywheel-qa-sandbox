# Design Review — plan.md (Round 2)

Date: 2026-09-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

v2 的核心取舍是对的：删除旧线程上的模型交接 turn，改成有界、确定性的 rollout 读取，确实同时关闭了 R1 #1/#3 的工具权限、取消协议、`CodexTurnExecutor.run()` 不存在和 W1 重放副作用问题。pristine/turnless 对账、完整写点表、事件词表、跨运行时测试清单也让方案明显更接近可实施状态。

但当前版本仍不能交给 runner。最主要的新问题是把历史 user/assistant 原文提升为 `developerInstructions`：生成过程虽无模型和工具，但新线程的 full-access bootstrap turn 会把这些原文当作 developer 级指令消费，可能重放旧任务或提升嵌入内容的权限。除此之外，现有 `killTuiWindow()` 实际是无法证明成功的 fail-open `void`，Discord/router 也没有在二次检查前被 fence；`attemptedThisGeneration` 会令失败后的 6 小时重试永远不可达，若 pending 清理失败则又可能在重启后无界重放。结论为 **CHANGES REQUESTED**。

## What's Good (Keep)

- **保留删除模型交接 turn 的决定。** 这是正确的 simplicity trade：旧线程零 `turn/start`、无需取消协议、W1 可安全重读，比为一次周级交接再造受限 agent/session 更小、更可审计。
- `thread/start` 成功前不改 `thread-id`，成功后仍以 `thread-id` 为真相；W2/W3/W5 的恢复方向正确。
- 对 pristine、ledger 缺失/坏、pending stale/expired、非 pending turnless 的显式分类值得保留。
- ledger 采用 `O_NOFOLLOW`、regular-file/size/schema guard、`O_EXCL + rename` 和写后读回，符合项目已有 fail-closed 持久化风格。
- rotation rebuild 与普通 connection-loss rebuild 分开：前者主动 fence、首步无 backoff，后者保 pane、保 backoff；这个边界正确。
- C5 单独导出 `SAFE_ID`、补 headless atomic-write 回归，并把 demux started callback 拆成独立 chunk，实施顺序清楚。
- `rotated` 与 `rotation_ready` 分离、E2 把 eligibility 与 actual claim 分开，是正确的观测模型；只需修正下述证据语义。

## Issues & Recommendations (numbered: issue, why it matters, suggested fix; tag each HIGH/MED/LOW)

1. **[HIGH] raw excerpt 被提升成 developer 权限，删除模型交接并未消除执行风险。**

   **Issue:** §3.3 把旧 rollout 的 user/assistant 原文直接拼进 `thread/start.developerInstructions`，而 `HANDOFF_HEADER` 还要求模型“供你接续”。这些内容可能包含尚未执行或已经执行完的旧命令、跨部门 Discord 输入、assistant 转述的网页/工具内容，甚至伪造的角色或分隔符。`developerInstructions` 的权限高于普通 user 内容；新线程紧接着运行现有 full-access bootstrap turn（源码在 `codex-lead-tui-runtime.ts:846-887`），因此“摘录生成零模型/零工具”不等于“摘录不会触发模型行为”。截断还可能留下 user 命令而切掉 assistant 的“已完成/不要执行”回复。

   **Why it matters:** 这会把历史数据升级为新的高权限指令，并在无人确认的 bootstrap turn 中产生任务重放或工具调用风险；它是 v2 新增的 authority crossing，而不是 R1 已删除的旧 handoff turn。

   **Suggested fix:** 保留“无模型 handoff”的方向，但不要把动态对话插入 developer 层。最简单且安全的版本是 `developerInstructions` 只含固定、代码内置文本，不携带 raw excerpt；依赖 journal recovery 和稍后的 memory pipeline。若即时摘录是必需产品要求，计划必须先找到并验证一个保持原始低权限、不会在 bootstrap 中执行的结构化数据通道；在此之前宁可不带摘录，也不要用提示词/分隔符假装成权限 fence。加入包含“旧 user 要求执行写操作、assistant 表示已完成、恶意伪分隔符”的负面测试。

2. **[HIGH] 轮换前的输入 fence 仍然不是可证明的 fence。**

   **Issue:** 当前 `killTuiWindow()` 返回 `void`，内部忽略 `exec("tmux", ["kill-window", ...]).ok`，失败也会继续并打印 `killed`（`tui-window.ts:233-245`）；v2 却把它当作旧 pane 已关闭的承重证据。与此同时，在 kill 后二次检查与 `requestRebuild()` 真正停止 gateway 之间，Discord gateway 仍可调用 `router.submit()`；`submit()` 会同步 durable accept、入队并立即把 `processing` 置为 true（`LeadInputRouter.ts:199-210,266-274`），但检查已经结束。正常 connection-loss 后保留下来的 pane 还可能有一个在旧 generation 已开始的 founder turn，而新 generation 把 `founderTurnActive` 初始化为 false，未必会重放其 `turn/started`。

   **Why it matters:** pane kill 失败、二次检查后的 Discord 输入、或跨 generation 的 active founder turn，都允许旧线程在 excerpt/read 或新线程切换期间继续有 turn。这样 §1.2 的“不会并发”“旧线程不再有任何 turn”和 E1 的“`rotated.at` 后零新行”都不是事实；旧线程的 6 小时静置起点也会漂移。

   **Suggested fix:** 定义一个 rotation-only、可验证的 generation fence：先原子地暂停 router dispatch（新输入可 durable 保持 `accepted`，但不得进入 `dispatching`），停止/暂停旧 gateway ingress；让 `killTuiWindow` 返回并验证实际结果，pane 仍活或状态未知就清 pending/终止轮换；然后等待 router idle 和已知 founder turn 的终态，再调用 supervisor。对跨 generation 的 founder 状态要么查询权威 active-turn 状态，要么把未知视为 busy。增加 kill 返回 false、二次检查后 Discord submit、普通 loss 期间 founder turn 跨代三个竞态测试。若项目选择接受竞态，就必须删除绝对保证并让验收按旧线程实际最后更新时间计 6 小时，不能同时声称零并发。

3. **[HIGH] `attemptedThisGeneration` 让计划承诺的 6 小时后重试不可达，pending 写失败路径又会绕过 backoff。**

   **Issue:** due predicate 永久要求 `!attemptedThisGeneration`。在同一 generation 中，`rotation_skipped` 会把它置 true 且不重建；在新 generation 的 `thread/start`/`writeThreadId` 失败路径中它也置 true，而该 generation 随后继续服务旧线程。两种情况都不会在 6 小时后再尝试。反方向上，P2/P3/P4 若无法清 pending/写 backoff，下一 generation 会在 TTL 内直接消费 pending；它不会重新检查 founder/router idle，也不是表中所说的“再试一次”，而是每次 generation/launchd 重启都可再 `thread/start` 一次。

   **Why it matters:** 正常 skip 或瞬时 RPC 失败可能把轮换永久关闭，磁盘写故障时却可能产生相反的重试风暴和多条 turnless orphan；这同时违反“失败后 6h 内不重试”和“每次到期至多一次尝试”。P2 在 founder/router busy 后留下 armed pending，还会绕过 issue #2 的空闲保护。

   **Suggested fix:** 把 generation-local 字段改成仅覆盖正在执行 tick 的 `attemptInFlight`，终态后清除；由 durable `lastAttemptAt` 控制 6 小时 backoff。`thread/start` 前先持久化“本 pending 已开始一次不可重放 attempt”的状态/时间；重启看到 attempted pending 时进入 backoff，而不是再 start。busy skip 的 pending 清理若无法持久化，保持输入 fence 并 fail loud，不能重开 pane/gateway 后留下可消费的 armed pending。测试同一 generation 在 +6h 重试，以及 P2/P3/P4 连续三次重启都不会绕过 idle/backoff 或创建多个 orphan。

4. **[HIGH] 非法/不可读 `thread-id` 被当作 pristine，会静默遗弃有效线程。**

   **Issue:** 当前 `readThreadId()` 把文件缺失、读取失败和空文件全部折叠成 `undefined`（`codex-lead-runtime.ts:1155-1162`）。v2 又规定 saved 存在但不匹配 `SAFE_ID` 时“按缺失处理”，随后执行 pristine `startThread`。因此损坏、截断、软链/权限错误或超长但字符合法的 `thread-id` 都可能被当作首次启动。`SAFE_ID` 本身也没有长度上限，超长 id 可使 header 超过 6,000 字符并放大 tmux/ledger 输入。另与用户变更说明不符的是，实际 §3.1 只限制 `startedAt ≤ now+5min`，没有限制未来的 `lastAttemptAt`/`pending.requestedAt`；前者可永久阻止 due，后者可让未来 pending 永不过期并被立即消费。

   **Why it matters:** `thread-id` 是计划声明的唯一线程真相；把 corruption 当成 absence 是静默记忆切断，不是自愈。未来时间和无界 id 也能绕过 TTL/backoff/长度保证。

   **Suggested fix:** 将 reader 改成 tagged outcome：`missing` 才能走 pristine；`empty/unreadable/symlink/non-regular/oversize/unsafe` 必须 fail loud 或进入明确人工恢复态，禁止自动 start 新线程。给 id 加与实际 UUID 合同一致的长度/形状上限。所有参与运算的时间都要求 canonical ISO、finite 且不晚于同一 `now + skew`；`lastAttemptOutcome` 也按已声明词表校验。补每个 outcome 的测试。

5. **[MED] excerpt 文件绑定与“无摘录仍轮换”是 fail-open，且边界算法还有未闭合细节。**

   **Issue:** `findRolloutPathFor` 计划由现有 `rolloutExistsFor` 抽出，但现实现只是递归寻找 `e.name.includes(threadId)`（`codex-lead-tui-runtime.ts:421-438`）。如果直接返回该路径，会接受后缀伪装、多个匹配和文件软链；§3.3 的读取没有 `O_NOFOLLOW`/regular-file/identity recheck。文件缺失、不可读或 512 KiB 尾部没有合格 message 时，计划仍以 `HANDOFF_EMPTY` 启动新线程，造成最需要交接时静默丢失即时上下文。另“正文截到 800，超出再加 `…`”实际会得到 801 个 JS code units，和 ≤800 的合同不符。

   **Why it matters:** 错文件或被替换文件可污染新上下文；读取失败仍切换会让 founder-facing Lead 在 memory summary 尚未生成/重新注入的窗口里失去正在进行的工作。

   **Suggested fix:** 要求 basename 精确匹配规范 rollout 形状并绑定完整 thread id；多匹配视为 ambiguous；用 `open(O_NOFOLLOW) → fstat regular → snapshot size → bounded read`，读后确认同一 inode/size 策略。对一个有真实 rollout 的线程，missing/unreadable/无合格消息应成为唯一的 `rotation_failed:handoff_source_unavailable` 并留旧线程；只有可证明 turnless 才允许 empty。明确 800 包含 ellipsis，并做 surrogate-safe 截断或明确 code-unit 语义。

6. **[MED] `rotation_ready` 目前不能证明 pane ready，且 120 秒后静默不写会制造永久歧义。**

   **Issue:** 现有 `ensureTuiHealthy()` 内部知道 create 成败，但不返回该结果；`ensureTuiWindow` 本来就是 fail-open（`codex-lead-tui-runtime.ts:541-558,889-923`）。v2 只在 `startGateway` 完成后写 `rotation_ready`，因此 pane 创建失败时也可能误报 ready。反过来，若一切最终成功但超过 `ROTATION_READY_TIMEOUT_MS`，计划规定不写任何 ready 行；这无法区分“慢但成功”“gateway/pane 失败”“receipt append 失败”。E7 还引用“回执里 bootstrap 次数”，但事件结构没有 bootstrap outcome/count 字段。

   **Why it matters:** 这是 founder 可见性的主要 receipt；误报或无终态会让 E1、告警和一周观测不可判。

   **Suggested fix:** `rotation_ready` 必须同时绑定 gateway ready 与已验证的 pane health；无论快慢，实际 ready 时都写并带 `readyMs`/`late`/`bootstrapOutcome`。120 秒只用于产生一个明确的 `rotation_degraded`/timeout receipt 和告警，不能抑制后续真实 ready。把 bootstrap attempt/completion/timeout 作为结构化字段，供 E7 分母使用。同步收紧 §1.2：history/receipt 是 best-effort 时不能作为无条件保证。

7. **[MED] E7/E8 的统计仍不足以把空摘要归因给额度闸。**

   **Issue:** `journal state='completed'` 已包含 `source='founder-terminal'` 的观察行（`LeadJournal.recordObservation()` 直接以 completed 写入，`LeadJournal.ts:276-295`）；再加 founder-terminal 会双计，除非第一项显式排除它。bootstrap receipt 又尚不存在。更关键的是，`Q ≥ 0.9·S` 允许至少一个未被额度闸拦的 startup；若旧线程当时 eligible，该 startup 本应产生 claim，因而“无 memory_stage1”仍有未解释故障，不能归类为 `blocked_by_quota_gate`。三选一也缺少“已 rotated、未被 quota 全拦、但未 claim”的失败状态。E8 用 raw skip 行/天比较，不按 startup/turn 数归一化，使用量变化就会改变结果。

   **Why it matters:** 验收可能把 candidate/claim bug 错报成可接受的额度阻塞，正好掩盖本项目要证明的链路。

   **Suggested fix:** 给 S 一条可执行 SQL：按 source 去重、限定时间窗、明确 bootstrap 来源；证明 guard 一次 startup 恰好一行后要求 `Q === S`，或按 startup trace/timestamp 一一关联。新增第四结论 `rotated_but_unclaimed_unexplained` 并判失败。E8 比较 `guard skips / startup`（同时列 raw counts），而非只比每日绝对数。E4 也需可控 barrier：receipt append 后同一同步 tick 会继续 kill/rebuild，人工 tail 后 `kill` 不能保证命中“pending 后、rebuild 前”。

8. **[MED] 关联文档并未真正与 v2 对齐，runner 仍会读到相反合同。**

   **Issue:** `research.md` 仍写模型生成交接、旧线程 `resume`、不存在的 `CodexTurnExecutor.run()` 和待量 handoff token/cost（§4、§5、§8），但 plan 仍声明“基于 research.md”，C7 也没有列 research 更新。`qa-runbook.md` 首启仍期望 `reconciled:ledger_missing` 而 plan 定义为 `pristine`；E2 仍只有旧版 count SQL，没有 plan v2 的 source/preview/逐谓词输出；E1 用秒级 `stat -f %m` 与毫秒 ISO 比较，不能证明 rotated 后零追加。PRD 又说 Infra Bot“无 turn ⇒ 无 startup”，但默认轮换会创建新线程并运行 bootstrap turn，即使没有外部输入。

   **Why it matters:** 这是 DESIGN node；后续 runner 被要求先读这些文件。相互冲突的规范会直接造成错误实现或虚假的 QA 通过。

   **Suggested fix:** 把 research 的 handoff/runtime seam 改成 v2 真相并纳入 C7；让 QA 原样承载 plan E2/E7 的可执行查询，修正 pristine，使用 rollout 行数/末行时间或 hash/size 快照证明旧文件未追加；修正 PRD 对 idle Lead/bootstrap 的描述，或增加“无真实活动不轮换”的明确 gate。最后机械 diff plan、QA、PRD、research 的事件词表、时序和验收谓词。
