# Design Review — plan.md (Round 4)

Date: 2026-09-14
Author: Codex

## Summary

本轮严格按 round-cap，仅复核 Round 3 的 8 项。基于 v4 commit `96344b312` 的 `plan.md`、`research.md`、`qa-runbook.md` 与 `prd-supplement-FLY-2119.md`，8 项均已在规范、失败合同、测试清单和 QA 证据层得到实质解决；没有发现新的 HIGH，也没有仍使设计不安全或不可实施的旧阻塞。

最关键的三个 R3 HIGH 已闭环：unknown 不再形成循环门禁；`rotationFenceHeld` 明确阻止 20 秒 liveness cadence 在 fence 内重建 pane；E4 改为按 attempt/thread-id 的耐久 cut 分段，不再要求未知 RPC 结果下既 at-most-once 又必定成功。其余五项也已补齐 durable backoff、W5 readiness、E7 归因、legacy rollout 延迟前置量测和生产 SQLite store 文件边界。

结论：**APPROVED**。下方 follow-ups 都是非阻塞的 receipt/QA 精度或极端写失败收口，不改变本轮 verdict。

## What's Good (Keep)

- 继续保留“固定 developer note、零旧对话携带”的 authority 边界；这仍是最简单且最安全的 continuity trade。
- `thread/turns/list` 现在只接受三个显式 terminal status，空数组、未知 status、RPC 错误和超时全部 fail closed；参数与 Codex 0.154.0 合同一致。
- `rotationFenceHeld` 的生命周期、成功交棒、失败 unwind 和 fake-timer 测试都写得足够具体，runner 不需要临场推断 liveness 行为。
- W1/W2/W3 的 durable cut 与 at-most-once 代价被明确公开；W2 放弃一次轮换而不重放，是当前无 client-idempotent thread API 下正确的安全选择。
- `attempt_mark_failed`、`pending_busy` 现在都通过同一次 ledger transition 清 pending 并写 backoff；二次写失败则保留磁盘事实并禁用本代。
- `readinessPending` 把 thread 切换与 gateway/pane 就绪拆成可跨 generation 完成的状态；W5、late、degraded、superseded 都进入测试清单。
- E7 已把 job、非空 output、rollout slug 文件和 quota guard 分开，避免仅凭目录或单一计数判断成功。
- C0 是恰当的实施前置门：已知 legacy `thread/turns/list` 会重放整个 7.1 MB rollout，先在真实形状的只读拷贝上证明两次都低于 10 秒，再允许 C7。
- C3 已正确覆盖 `LeadJournal.ts` 的 interface/in-memory store 与 `SqliteJournalStore.ts` 的生产 SQL/index；首启失败与 post-start supervisor backoff 的责任层也已纠正。

## Issues & Recommendations (numbered: issue, why it matters, suggested fix; tag each HIGH/MED/LOW)

无阻塞问题。Round 3 项目逐项结论如下：

1. **[RESOLVED — R3 #1]** Due predicate 只拒绝明确 `true`；unknown 只能进入 preflight，不能直接写 pending，最终授权只来自显式 terminal 的 `thread/turns/list`。C1/C7 均有正反矩阵。
2. **[RESOLVED — R3 #2]** `rotationFenceHeld` 在 kill 前建立，fence 内 liveness 只 probe；所有可恢复 unwind 解冻并立即 ensure，一条 ≥3 cadence 的 fake-timer 测试覆盖原竞态。
3. **[RESOLVED — R3 #3]** W1/W2/W3 按 durable cut 分段，W2 明确允许零 `rotated` 并在 6h 后用 fresh pending 重试；不再与 at-most-once 合同冲突。
4. **[RESOLVED — R3 #4]** `attempt_mark_failed` 和 `pending_busy` 的成功清理都同时耐久化 `lastAttemptAt/outcome`；清理也失败时 pending 原样保留、本代禁用，不伪造 backoff。
5. **[RESOLVED — R3 #5]** Rotated transition 写入 `readinessPending`；W4/W5 后继 generation 能结清 ready/degraded，off 与 superseded 行为有明确边界和测试。
6. **[RESOLVED — R3 #6]** 独立 `rotation_bootstrap` receipt、窗口过滤、J/O 拆分、slug 绑定和六个有序 outcome 已覆盖原统计缺口。
7. **[RESOLVED — R3 #7]** `itemsView:"notLoaded"`、局部 10 秒 wrapper、迟到 promise 消费、C0/E0 真数据量测和失败返回设计共同关闭了 legacy full-replay 的可行性风险。
8. **[RESOLVED — R3 #8]** C3 文件与实现层已校正，compound index 和双 store 测试明确；launchd/supervisor 的失败层描述与当前代码一致。

## Follow-ups (non-blocking)

1. **[MED] 写不下 skip backoff 时应禁用本代，避免每分钟重复 kill/recreate pane。** §1.2/§6 说任何失败都由 durable `lastAttemptAt` backoff，但 §3.2 unwind 与 P1 在该 transition 失败时只 warn。若磁盘持续不可写，due 仍成立，下一 tick 可再次 fence。实施时建议在恢复 router/pane 后设置 `rotationDisabledThisGeneration="ledger_write_failed"`；这与 attempt-mark 二次写失败的 fail-closed 规则一致，不需要新增状态或配置。

2. **[MED] E4(c) 不能要求 history 必在，真机事后分段也应使用 pre-kill 快照与 outcome。** 写序是 `writeThreadId → history append → ledger → receipt`，所以 W3 的前半段以及 P5 都允许新 thread-id 已成为真相但 history 缺失。QA §4 还把 pending “已消费”归到 (a)，但 W2 reconcile 后 pending 也已清。建议先保存 `$OLD`，然后用 `thread-id` 是否变化、`lastAttemptOutcome=reconciled:pending_attempted`、reconcile receipt 和 ledger mismatch 组合判段；(c) 只要求新 id 为真相且无第二次 start，不要求 history。

3. **[MED] `rotation_bootstrap` 的“每个 to 至多一行”目前没有跨代耐久依据。** Step 5 写 receipt 后不改 ledger；若在 readiness 结清前重启，后继代仍看到 `readinessPending`，rollout 已存在时可再写一行 `skipped_rollout_exists`。这不影响线程安全，但与 C7/E7 的唯一性前提不符。最简单的收口是删除 at-most-one 运行时保证，并在 QA 按 `to`/outcome 去重；若必须保证 receipt 唯一，则需在 append 前检查已有 `to` 或给 readiness 状态增加 durable recorded marker。

4. **[LOW] readiness 写失败后的同代重试语义有一处文字冲突。** §3.1 说任何 reconcile 写失败都会设置 `rotationDisabledThisGeneration`，且本代“不结清 readiness”；P7 又说 readiness 结清写失败后“下一 tick 重试”。建议明确 readiness-only transition 失败不设置 generation-wide disable、仅保留 pending 供下一 tick；或保留 disable 并改成“下一 generation 重试”。两种都安全，选一种与测试对齐即可。

5. **[LOW] `blocked_by_quota_gate` 应要求 `S > 0`，并给 `Q > S` 一个测量异常出口。** 当前 `J` 空且 `Q === S === 0` 会被标成 quota blocked；额外手工 startup 或日志重复又可能出现 `Q > S`，不属于六个 outcome。建议条件改为 `S > 0 && Q === S`，并把 `Q > S`/无法归类记为 `measurement_inconsistent`，避免把“没有 startup”说成“每次都被 quota 拦”。
