# Design Review — plan.md (Round 1)

Date: 2026-09-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

方案的主方向成立：当前架构允许在 `CodexLeadRuntime.start()` 的 `ensureThread → wire → recover → startGateway` 窗口内完成线程切换，也允许通过 `DaemonConnectionSupervisor` 主动建立新 generation。7 天周期、单一 kill switch、旧线程不归档、失败留在旧线程，以及 ledger/thread-id 对账，都是合适的边界。

但 v1 还不能直接实施。最关键的问题是：交接 turn 没有工具权限隔离；重建期间旧 TUI pane 仍可提交 founder turn；180 秒超时也不会真正终止 daemon 中的 turn。这三点组合后，会产生重复副作用、旧线程并发 turn，以及“已回退继续服务、后台交接仍在跑”的状态。另有首次启动、持久化写失败和验收证据合同未闭合。结论为 **CHANGES REQUESTED**。

## What's Good (Keep)

- 根因与方案闭环清楚：轮换让旧线程不再是 `current_thread_id`，同时保持 `archived=0`、`memory_mode=enabled`，没有把额度闸或摘要成功错误地纳入 Flywheel 的保证。
- 保持了现有启动顺序。`CodexLeadRuntime.start()` 确实在 gateway 启动前调用 `ensureThread()`，因此新 generation 中执行对账和切换是可行的。
- W1–W4 把 `pending`、`thread-id` 与 ledger 的权威顺序写得较清楚；特别是 W3 以 `thread-id` 为准，可避免已经切换后重复交接。
- 失败转移坚持旧线程可用，且不归档、不改 `memory_mode`、不写 `CODEX_HOME`，范围控制正确。
- 单一 `off` 开关、固定常量、无管理台和额外巡逻，符合项目的简化原则。
- 测试矩阵覆盖了到期条件、turnless、自愈、崩溃窗与关闭路径；QA 也区分了“进入候选”和“真正产出摘要”。

## Issues & Recommendations (numbered: issue, why it matters, suggested fix; tag each HIGH/MED/LOW)

1. **[HIGH] 交接 turn 只有提示词约束，没有权限隔离。**

   **Issue:** 计划承认 `turn/start` 没有 per-turn 工具开关，却只把违规外发描述成可能调用 `discord_send`。实际交接发生在生产 Lead 的旧线程和既有 Codex 配置中，模型可触达的副作用面还包括文件、shell、git、网络及其它 MCP/Lead actions。W1 重放还允许同一 `requestedAt` 多跑一次交接 turn。

   **Why it matters:** “不调用工具”是模型指令，不是执行时 fence。一次自动、无人确认且可能重放的 turn 不应继承 founder-facing Lead 的写权限；否则这是新的自治 mutation 路径，且账本无法证明它没有产生外部副作用。

   **Suggested fix:** 在设计中选择并证明一个 fail-closed 方案：要么使用独立、只读且禁用全部 tools/MCP/network/workspace writes 的 summarizer session，并仅向它提供有界上下文；要么移除模型交接 turn，改为确定性生成可审计的交接材料。若当前协议无法提供该 fence，应明确把它列为实现前置，而不是接受为 Discord 单点风险。补充“尝试工具调用必须被拒绝、W1 重放无外部副作用”的测试与 QA 证据。

2. **[HIGH] “ensureThread 时无并发 turn”与现有 TUI 生命周期不符。**

   **Issue:** `buildTuiGeneration().stop()` 明确只停止 sidecar runtime，不杀 TUI window；这是为了让 pane 穿越普通 daemon WebSocket 重建。`LeadInputRouter.isIdle()` 也只能看到 Discord/router 的 `processing` 和 `queue`，看不到 founder 在 TUI 中已开始但尚未完成的 turn。当前 demux 只给 runtime 暴露 founder completion 观察点，计划也没有建立 founder-active fence。因此，长时间运行或沉默超过 30 分钟的 founder turn 可与 tick/交接重叠；写入 `pending` 后，旧 pane 在新 generation 的 `resumeThread`/交接期间仍可继续提交。

   **Why it matters:** 同一旧线程可能同时承载 founder turn 与自动交接 turn；交接内容会缺失正在进行的工作，甚至触发 daemon 的并发/忙碌错误。随后杀 pane 还可能让 founder 丢失正在生成的输出，而不只是未提交草稿。

   **Suggested fix:** 为“thread rotation”单独定义 TUI fence，不改变普通 connection-loss 的保 pane 语义：跟踪 founder turn started/completed 状态并把 `!founderTurnActive` 纳入 due 条件；`pending` 成功落盘后，在停止旧 generation/开始交接前禁止旧 pane 再接受输入并确认没有 active founder turn。明确 stop/fence 的所有权与次序。增加 founder turn 在 tick 前开始、触发边界开始、pending 后尝试输入等竞态测试。

3. **[HIGH] 交接 timeout 没有终止语义，且计划使用了不存在的 executor API。**

   **Issue:** 当前 `CodexTurnExecutor` 只有 `startTurn()`、`awaitCompletion()` 和 `reconcile()`，没有 `run()`。`wireDemuxedProcess.awaitTurnCompletion()` 的超时/`releaseTurn()` 只会停止本地等待并 tombstone 路由，不会取消 daemon 中的 turn；`CodexLeadProcess` 目前也没有 interrupt wrapper。按 v1 在 180 秒后返回 `saved` 并恢复服务，交接 turn 仍可能继续运行和产生迟到事件/副作用。

   **Why it matters:** “handoff_timeout 后旧线程继续服务”不是安全的失败转移；它可能把下一条 founder/Discord 输入送入一个仍在执行自动 turn 的线程。停止 WebSocket 连接也不是取消 daemon turn。

   **Suggested fix:** 把步骤改成当前真实 API 的 `startTurn → awaitCompletion`，并定义可验证的取消协议：超时后发送 upstream 支持的 interrupt/cancel RPC，等待该 turn 的终态确认，再允许旧线程恢复服务。若无法确认取消，则 fail closed，保持 gateway/pane fenced，并通过重建/状态查询确认 turn 已终止后再恢复。分别测试 request timeout、completion timeout、interrupt 失败、迟到 completion/tool event。

4. **[HIGH] ledger 初始化与非 pending 的 turnless 自愈没有定义。**

   **Issue:** §3.1 要求 `ensureThread` 入口先对账，但首次启动时 `readThreadId()` 可返回 `undefined`，无法构造 schema 要求的 `currentThreadId`。此外，正常启动（没有 rotation pending）也可能在 `resumeThread` 时命中既有 turnless 自愈并写入新 `thread-id`；v1 只说明了 pending 分支如何更新 ledger。

   **Why it matters:** pristine state 会在第一次启动就落入未定义分支；普通 turnless 自愈后，ledger 仍指向旧线程，下一次启动会被误判成 W3，并丢失真实的 `startedAt`/previous 信息。

   **Suggested fix:** 明确完整状态机：无 saved id 时先按既有路径 start/校验/原子写 `thread-id`，再初始化 ledger（`startedAt=now`）；任何路径只要改变 current thread——包括非 pending turnless——都必须更新 ledger/history 的对应字段。增加 pristine state、ledger 有而 thread-id 缺失、普通 turnless、pending turnless 四类测试。

5. **[HIGH] durable transition 的同步 I/O 失败合同不完整，ledger 校验也不足。**

   **Issue:** v1 只定义了触发前 pending 写失败和 `writeThreadId` 失败。没有定义以下同步失败：交接失败后清 pending/写 backoff 失败；`writeThreadId` 成功后 history 或 ledger 写失败；对账修复写失败；写后读回不一致。若清 pending 失败，下一代会立刻重放，违反 6 小时 backoff；若 `thread-id` 已成功而 ledger 写失败，当前 generation 仍需决定是否继续 wire 新线程。读取侧也只强制验证 `v` 和 `currentThreadId`，却会直接使用 `startedAt`、`lastAttemptAt`、`lastAttemptOutcome` 以及整个 `pending` 的日期、id 和枚举值。

   **Why it matters:** 磁盘满、权限变化、截断或恶意/意外 JSON 字段可绕过 due/backoff，造成轮换风暴、重复 handoff 或 NaN/无效日期语义。receipt/history 又是 best-effort，不能弥补权威状态不明确。

   **Suggested fix:** 为每一个 durable write 点写出“失败时 current thread、gateway/pane 是否开放、内存状态、下次启动恢复”的表；关键 ledger transition 失败应 fail closed，而非继续声称成功。读取时校验完整 schema：所有 ISO 时间可解析且有限、nullable 字段类型、`pending.fromThreadId`、`reason`/outcome 枚举及未知字段策略，并保留 O_NOFOLLOW/regular-file/size guard。补齐磁盘写失败与 malformed-field 测试。

6. **[MED] 事件、长度和证据合同内部不一致。**

   **Issue:** §3.3 对 `thread/start` 失败写“同 2 的失败处理”，会把它归为 `handoff_failed`，但事件词表和 §1.2 又承诺 `rotation_failed:*`；`disabled` 在 reason 词表中，却又承诺 `off` 时零回执。另一个冲突是先把正文截为 6,000 字符再加 `HANDOFF_HEADER`，使实际 `developerInstructions` 超过 §1.2 承诺的 6,000 字符。`handoffChars` 是原文、截断正文还是最终 payload 也未定义。成功后现有 `wire()` 还会对无 rollout 的新线程执行一次最长 90 秒 bootstrap turn；当前 `rotated.wallMs` 不清楚是否覆盖这段 founder 不可用时间。

   **Why it matters:** 实现者和 QA 会生成不同事件或计算方式；运维看见 `rotated` 也不能判断窗口是否已经 ready。

   **Suggested fix:** 给每个失败点指定唯一 event/reason，删除不可达枚举或说明用途；将 6,000 定义为最终 `developerInstructions` 总长并为 header 预留预算，或明确承诺仅限正文；定义 chars/truncated/wallMs 的精确计算。把“事务完成”和“新线程已 wire/gateway/TUI ready”分成明确证据，或将 end-to-end readiness 纳入 wall time/QA。

7. **[MED] 验收不能证明计划声称的全部候选条件与反向指标。**

   **Issue:** E2 只检查时间、archive 和 memory mode，未要求旧 id 的 `source` 属于 interactive whitelist、`preview <> ''`，也没有把实际 claim/watermark/retry 状态与“满足全部候选条件”区分。E7 的“窗口内每次 startup 都被额度闸拦”缺少 startup 分母和精确 SQL；仅有 quota skip 行不能证明没有其它未记录 startup。E8“告警次数不上升”没有基线窗口、统计口径或数据源。E4 的 `kill -STOP` 若发生在 `turn/start` 返回 turn id 之前，只验证 RPC timeout，不是 completion timeout，也没有验证 `CONT` 后迟到 turn 的处理。

   **Why it matters:** 这些检查可能在旧线程实际上不可 claim、没有发生 startup 或后台 turn 仍活跃时给出通过结论。

   **Suggested fix:** E2 按旧 id 精确输出所有候选谓词（source、preview、时间、archived、memory_mode），并把“candidate eligible”与“actual job claim”分开；E7 定义观察窗口、startup 总数和 quota-blocked 数的可复现查询；E8 固定上线前后等长窗口及告警类型。E4 明确在取得 turn id 后暂停 completion，并在恢复 daemon 后证明该 turn 已被取消/不会产生迟到副作用。

8. **[MED] 改动清单遗漏了必需文件和跨运行时回归面。**

   **Issue:** C1 路径写成 `teamlead/src/...`，实际根为 `packages/teamlead/src/...`。计划要求复用 `tui-window.ts` 的 `SAFE_ID`，但该常量当前是 private，C1–C4 没列 `tui-window.ts` 的导出/共享改动。`writeThreadId()` 位于 `codex-lead-runtime.ts`，被 headless 和 TUI 两条路径共用；C4 只列 TUI runtime 测试。`requestRebuild` 还必须保留普通 `onLoss()` 的“pane 不重建、带 backoff”语义，而 rotation 分支需要主动 fence pane 和首步无 backoff，两者需要显式分支测试。

   **Why it matters:** runner 按 chunk 清单执行会遇到不可导入的 validator，并可能改变 headless 写盘或普通 loss recovery 行为而没有回归覆盖。

   **Suggested fix:** 修正 C1 路径；把 shared id validator（或 `tui-window.ts` 的受控导出）及测试列入清单；加入 `codex-lead-runtime.test.ts` 的 atomic-write/headless 回归；在 supervisor/TUI 测试中分别覆盖 connection loss 与 rotation rebuild 的 pane、backoff、单循环和 stop 顺序。

## Verdict

CHANGES REQUESTED — address items above
