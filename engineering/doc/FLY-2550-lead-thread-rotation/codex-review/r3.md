# Design Review — plan.md (Round 3)

Date: 2026-09-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

v3 对 R2 最危险的问题采取了正确、足够简单的处理：彻底删除动态 handoff 内容，只给新线程一个代码内置的固定 developer note。这个取舍值得保留；它消除了历史 user/assistant 内容被提升到 developer authority 的路径，也不再需要旧线程上的模型 turn、取消协议、rollout 正文读取或新的受限-agent机制。

其余修订也明显改善了方案：`thread-id` 不再把损坏当 pristine，pending 在 `thread/start` 前有耐久 attempt 标记，活动门避免纯空白线程自动轮换，ready/degraded 开始区分 thread 切换与 founder 可见恢复。我还核对了 Codex `rust-v0.154.0`：`thread/turns/list`、`limit/sortDirection/itemsView` 和 `TurnStatus = completed|interrupted|failed|inProgress` 都确实存在。

但 v3 仍有三个实现/验收级阻塞。第一，`founderTurnActive` 代初为 `unknown` 且 unknown 等价 busy，而进入能够消除 unknown 的 fence 又先要求 `!founderTurnActive`，因此新代若未观察到 founder-terminal completion 就永远不会轮换，E1 的 Discord-only 步骤必然失败。第二，现有 20 秒 TUI liveness timer 在 fence 的 60 秒 idle wait 期间会把刚验证杀死的旧 pane 重建，计划没有冻结这条 timer。第三，E4 要求 daemon kill 落在任意位置都恰好一次 `rotated`，与 W2 “attempt 已落盘即永不重放 thread/start”直接冲突。结论为 **CHANGES REQUESTED**。

## What's Good (Keep)

- **保留固定 `ROTATION_DEVELOPER_NOTE`、不携带任何旧对话的决定。** 这是正确的 simplicity/authority trade；即时连续性的损失已在 founder 文案中如实披露，后续判断交给 Codex memory pipeline，而不是再造一轮无人确认的高权限执行。
- 保留 `thread-id` 为唯一真相，以及 `missing` 与 corruption 的严格区分；UUID 形状、canonical ISO、未来时钟上限和 outcome 词表使恢复分支可审计。
- 保留 `pending.attemptStartedAt` 先于 `thread/start` 的写序。它正确地把“最多一次 create RPC”与“最终一定轮换”区分开，也关闭了重启时重复创建 orphan 的主要窗口。
- 保留 router durable accept + pause、不丢新输入、由新代 journal recovery 重派的方向；这与现有 `accepted`/`dispatching` 恢复语义一致。
- 保留活动门 `countCompletedSince(startedAt) >= 1`。bootstrap 不计入 journal，因此不会仅因创建空页而自我续燃。
- 保留 `rotated`、`rotation_ready`、`rotation_degraded` 三层事实，以及 gateway/pane 双条件；这比把 thread-id 写成功误报为 founder 路径 ready 更准确。
- 保留普通 connection-loss 与 rotation rebuild 的行为分离：普通 loss 带 backoff、保 pane；rotation 由旧代显式建立输入 fence、首步不等待。
- research、QA 与 PRD 已删除 v1/v2 的 handoff/excerpt 旧合同，主方向已对齐。

## Issues & Recommendations (numbered: issue, why it matters, suggested fix; tag each HIGH/MED/LOW)

1. **[HIGH] `founderTurnActive = unknown` 与 due predicate 构成循环门禁，正常新代可能永远到不了权威查询。**

   **Issue:** plan §3.2 规定进入 fence 前必须满足 `!founderTurnActive`，同时规定代启动时状态为 `unknown`、unknown 等价 busy，只有观察到 founder `turn/completed` 或 fence 第 4 步 `thread/turns/list` 返回 terminal 才变成 false。第 4 步只有进入 fence 后才会执行，因此没有 founder-terminal turn 的 generation 永远无法消除 unknown。E1 只发送 Discord 输入；sidecar turn 不触发 founder observer，所以按当前规范 E1 在第一层 due check 就永久停住。C7 还把 “founder unknown”列作失败测试，反而会把这条不可达路径固化。

   **Why it matters:** 这是功能完全 inert 的确定性 bug，不是窄竞态。每次 daemon/Lead 重启都会把状态重新置 unknown；Mufasa 即使有大量 Discord journal completion，也可能永远不轮换。

   **Suggested fix:** 让 unknown 只能阻止“提交 pending”，不能阻止进入用于消除 unknown 的只读 preflight。最小改法是 due predicate 仅拒绝明确的 `true`，在 router pause + pane verified-dead 后以 `thread/turns/list` 为最终权威：只有明确的 terminal status (`completed|interrupted|failed`) 才设置 false 并继续，空数组、未知 status、错误、超时都 busy。相应测试必须证明“代初 unknown + Discord completed + terminal list ⇒ 可轮换”，以及 unknown/未知 response 本身绝不能直接授权 pending。

2. **[HIGH] 现有 TUI liveness cadence 会在 fence 尚未完成时重建刚杀掉的旧 pane。**

   **Issue:** 当前 `codex-lead-tui-runtime.ts:541-559,913-923` 每 20 秒调用 `ensureTuiHealthy()`，发现窗口死亡就重建；只有 generation `stop()` 才清 timer（`:959-969`）。v3 fence 最长会在 `router.whenIdle()` 等 60 秒，再等 `thread/turns/list` 10 秒，但步骤和 C7 测试都没有在 `attemptInFlight/fenceHeld` 时抑制 liveness。于是步骤 2 的 “kill ok 且 probe dead” 可以在步骤 3/4 中被旧代自己的 timer 推翻，founder 又获得旧线程输入入口。

   **Why it matters:** 这直接破坏 §1.2 “从 fence 建立起零 turn”、§3.6 “pane 已死所以 founder 无输入通道”和 E1 的旧 rollout 零追加证明；而且 race 窗不是毫秒级，是已知的 20–70 秒。

   **Suggested fix:** 增加明确的 generation-local `rotationFenceHeld`（可复用但不要混淆为 durable attempt）：`ensureTuiHealthy()`/liveness tick 在它为 true 时只能 probe/记录，不得 create。成功 handoff 给 supervisor 后由 generation stop 清理；任一 skip/clear-pending-success 路径先解除 fence，再立即调用一次 `ensureTuiHealthy()`（不要只等下一 tick）。C7 用 fake timers 跨过至少三个 20 秒 cadence，断言 pane 在 fence 内从不重建；再断言 unwind 后只重建一次。

3. **[HIGH] E4 的“任意 daemon kill 落点都恰一次 rotated”与 W2/P3 的 at-most-once 设计不可同时成立。**

   **Issue:** 若 kill 落在 `pending.attemptStartedAt` 已写、但 `thread/start` 尚未成功返回或 `thread-id` 尚未写入之间，下一代必须按 W2 清 pending、进入 backoff、**不再 start**。这可能得到零个 `rotated`（以及零或一个 orphan），正是 at-most-once 在未知 RPC 结果下的保守代价。若 kill/进程崩溃落在 thread-id 已写而 receipt 未 append 的 W3/W4，当前线程可以已经是新线程但仍没有 `rotated` receipt。QA §4 和 plan E4 却要求无论落点都恰一行 `rotated`、恰一条新线程；该判据会把设计规定的安全恢复误判成失败，也无法靠人工 `tail -f` 控制精确落点。

   **Why it matters:** 不可满足的验收会迫使 runner 在实现时偷偷放松 W2（重复 `thread/start`）或伪造 receipt，二者都比诚实区分 crash cut 更危险。

   **Suggested fix:** E4 按耐久 cut 分组验收：(a) attempt 标记前/W1：允许 pending 被同一或新代消费并最终一个 `rotated`；(b) attempt 标记后、thread-id 前/W2：要求零次重放、旧 thread-id 保持、`pending_attempted`、fresh pending 只能在 6h backoff 后再建；(c) thread-id 后/W3-W4：要求新 id 为真相、无第二次 start，receipt 可按既有 best-effort 合同缺失。用单元测试的 barrier 精确覆盖三段；真机随机 kill 只需先判定它实际落在哪段，再套对应判据。若产品硬要求每种落点最终同一 pending 都成功一次，则需要 Codex 提供 client-supplied/idempotent thread id；当前 API 无法证明。

4. **[MED] `attempt_mark_failed` 成功清 pending 的分支没有写 `lastAttemptAt/outcome`，会绕过承诺的 6 小时 backoff。**

   **Issue:** §3.3 步 2 只说 attempt 标记失败后“清 pending、回执、resume”，P2 也没有落 `lastAttemptAt`；而 §1.2、§3.2 和 §6 都承诺所有轮换失败由 durable `lastAttemptAt` 阻止 6 小时重试。如果标记写失败、随后的清 pending 写恰好成功，新代 wire 后只需重新满足 30 分钟 quiet 就会再次杀 pane/走 fence。

   **Why it matters:** 一次短暂的写后读回故障可以变成 founder-facing pane flapping，并违反本轮专门修订的 durable-backoff 合同。

   **Suggested fix:** 把成功清 pending 定义成一次原子 ledger transition：`pending=null, lastAttemptAt=now, lastAttemptOutcome="rotation_failed:attempt_mark_failed"`。若该 transition 也失败，就保留磁盘上的未 attempted pending、设置本代 rotation disabled；不要在内存中声称有 durable backoff。补“attempt mark fail + clear succeeds ⇒ +30m 不试、+6h 可试”和“clear 也失败 ⇒ 本代不消费”的测试。

5. **[MED] `rotation_ready/degraded` 状态在 W5 后不可恢复，实际可永久没有终态。**

   **Issue:** 成功切换后的 ledger 只保存 `current/previous/startedAt/lastAttemptOutcome=rotated`，没有 `requestedAt` 或待完成的 readiness 状态。若 generation 在 `writeThreadId`/rotated transition 后、gateway/pane ready 前崩溃，W5 下一代只走普通 resume；它无法知道应为哪个 rotation 写 `rotation_degraded`，也不能可靠恢复原 `requestedAt/readyMs/bootstrapOutcome`。120 秒 timer 也随旧 generation 消失。§3.3 的“超时必有 degraded、以后达到必有 ready”因此只在无 crash 的单代内成立。

   **Why it matters:** daemon 恰在 rotation bring-up 中波动时，最需要的诊断 receipt 反而缺失；E1/E4 无法区分“新线程有效但尚未 ready”“新代恢复成功”“receipt append 失败”。

   **Suggested fix:** 二选一并写死边界：(a) 在 ledger 中保留最小 `readinessPending {to, requestedAt}`，由任意后继 generation 在 gateway+pane 状态明确后结清，bootstrap outcome 可定义为本代 outcome；或 (b) 明确 ready/degraded 只是单-generation best effort，删除“无论多晚/120 秒必有”的绝对描述，并让 crash QA 只以 thread-id/history/ledger 为准。若保持 E1 对 ready 的强判据，建议选 (a)，并增加 W5 before/after-120s 重启测试。

6. **[MED] E7 的 S/Q/C 查询仍不能机械地产生所声明的四选一结论。**

   **Issue:** QA §7 的 `grep -c '"bootstrapOutcome":"completed"'` 实际没有按 `at` 过滤窗口；同一次 bootstrap 若先写 `rotation_degraded`、后写 `rotation_ready`，两行都会带 completed，S 被双计。`C` 只数 `$OLD` 的 job 行，不看 `status`/`stage1_outputs`；因此 `C>0` 但 job failed/pending 或输出为空时，不属于四个结果中的任何一个。`summaries_present` 也只看目录新文件，没有通过 `stage1_outputs.rollout_slug/thread_id=$OLD` 绑定旧线程，可能把别的候选摘要算成本单成功。

   **Why it matters:** `Q === S` 是 `blocked_by_quota_gate` 的核心归因条件；S 多计或跨窗会把未解释故障错误归因给 quota，C 的非 done 行又可能让观察结果没有 verdict。

   **Suggested fix:** 增加一条每个新线程最多一行的 canonical bootstrap receipt，或以 `to` 去重 ready/degraded 后再计；给出真正可执行的 `jq/sqlite` 窗口过滤命令。把 outcome 补全为至少：`summary_done_for_old`、`blocked_by_quota_gate`、`claimed_but_not_done`（失败，列 status/last_error）、`eligible_but_unclaimed`（失败）、`not_eligible`（回 E2）、`no_rotation`。摘要成功必须由 `$OLD` 的 done job + 非空 stage1 output + 对应 rollout slug 文件共同证明。

7. **[MED] `thread/turns/list` 在 0.154.0 的 legacy 路径每次都会重放完整 rollout，10 秒 fence 对首条 7.1 MB 线程尚未做可行性验证。**

   **Issue:** 官方 tag 的 handler 明确写着 legacy `thread/turns/list` “still replays the entire rollout on every request”，即使 `limit:1` 也先 load 全历史；v3 在旧代和新代各调用一次，且参数未指定 `itemsView`（默认 `summary`）。生产首目标正是 plan 已知的 97 天/7.1 MB 线程。另一方面，本仓 `CodexLeadProcess.request()` 只有 process-wide 60 秒 timeout（`CodexLeadProcess.ts:100-104,329-346`）；plan 的 10 秒需要额外 wrapper，不能靠现有签名直接表达。

   **Why it matters:** 这是 fail-closed，所以不会错切线程，但若解析超过 10 秒，生产会每 6 小时杀一次 pane、随后 `turns_list_busy`，永远不完成首轮换；小 rollout 的 529 E1 无法发现它。

   **Suggested fix:** 请求显式加 `itemsView:"notLoaded"`，并在实施前/529 验收加入对 Mufasa **只读拷贝的同一 7.1 MB rollout** 的两次 latency 测量，证明 p99/连续多次都低于 10 秒且记录 wallMs。10 秒用局部 bounded wrapper 实现，不能把 `CodexLeadProcess` 全局 timeout 改成 10 秒；外层 timeout 后底层 read-only promise 的 late settlement 要被消费。若真实数据过不了 10 秒，先回设计选择另一条权威 active-turn seam，不能调成不设上限。

8. **[MED] C3 的文件清单与当前实现位置不符，runner 按表实施会漏掉 SQLite store。**

   **Issue:** plan C3 的文件列只有 `LeadJournal.ts`，但实际 `JournalStore` interface / in-memory store 在 `LeadJournal.ts`，生产 SQLite 实现在独立的 `SqliteJournalStore.ts:78-324`。给 interface 新增 `countCompletedSince` 后，若不同时改后者会直接类型错误；若 runner 只在 journal facade 绕过 store，则活动门可能只在测试 store 生效。现有 SQLite 表确有 `created_at`/`updated_at`，实现位置和索引策略也应进入计划。另 §3.1 说初始 strict-read 失败由 supervisor backoff，实际 `DaemonConnectionSupervisor.start()` 首启失败会抛给 launchd（`:92-121`），只有已成功启动后的 loss 才走 supervisor rebuild backoff。

   **Why it matters:** 这是 DESIGN node 的派工边界；错误文件表会造成未实现生产路径或 runner 临场猜测，启动恢复文案也会误导 QA 看错重试层。

   **Suggested fix:** C3 明列 `LeadJournal.ts`、`SqliteJournalStore.ts`，要求 interface、in-memory、SQLite 三处实现，并分别测试；SQLite 可加 `(state, created_at)` 索引或用真实 journal 规模证明现有扫描足够。把 §3.1 改成“初始 bring-up fail-loud 交给 launchd；已成功启动后的 generation/rebuild 失败由 supervisor backoff”。
