先看结论

  • Codex 体确实远比 Claude 体容易出事。近 14 天 Codex 执行体 694 个，出事 477 个（69%），涉及 102 张单； Claude 执行体 330 个，出事 25 个（8%）。只看实现节点：Codex 70% 对 Claude 10%。
  • 浪费主要花在「等人手」上，不在死本身。Codex 出事合计浪费 507 单×节点小时，其中 422 小时（83%）是 run 已经被打成 held、等 Lead 手工 resume 或重派。

窗口：执行体创建时间在 2026-09-11T22:00:00Z 到 2026-09-25T22:00:00Z（14 天）。数据冻结于 2026-09-25T22:57:33Z （事件 id 上限 run_event ≤ 193059、session_event ≤ 10864431），重跑结果逐字节相同。全程只读。

前三类修法建议（由 Lead 决定开单）

① 账号额度墙 usageLimited — 234 次 · 71 张单 · 30 批 · 浪费 207.8 h（其中等人手 185.9 h）

根因：额度打满时所有在飞体同时死掉。引擎不看死因，照样盲换 3 具替身，替身起跑即死（本类 140 具），用尽后 run 被打成 held。额度回来以后没有自动重新派发，只能人手 resume（FLY-2371）。自动切号子系统又没在宿主上真正部署（FLY-2521）。

最小修法：① 替身派发前读前任死因：同一 vendor、同一 home 刚以 usageLimited 死过，就不盲换，直接进 hold，并把 resume_after 设成额度重置时刻；② 订阅额度恢复事件（同一 home 重新有 token 消耗，或 quota-monitor 切号完成），自动重新派发。

预计节省：下限是额度已回来、还在等人手的那段，本窗口 39.1 h，外加起跑即死的 140 具盲换。另外，下游由额度墙死体留下脏 worktree 引出的 K6 有 21 次、108 h，会随盲换消失而减少。 其余时间是额度真的没了；要省这部分，得让自动切号真正落地（FLY-2521），并且当时有别的号还有余量。上限约为本类全部 207.8 h。

风险：如果恢复信号误判，可能在额度仍满的时候重新派发。所以自动重臂最多一次，失败后保持 held 并告警，不能退回盲换循环。

② worktree 接管失败 — 40 次 · 30 张单 · 浪费 137.8 h（其中等人手 133.3 h）

根因：前任死前在共享 branch-B worktree 里留了未提交的改动。替身接管时检查到 clean=false，拒绝原地复用 → unlaunched_admission_rolled_back → run 被打成 held。要 Lead 手工 stash 再 hold resume 才能继续（FLY-2510）。 前任死因以额度墙居多（21/40）。Claude 替身也会撞上（5 次），所以这一类跟载体无关。

最小修法：接管时如果前任已被证明死亡，而 worktree 里有未提交改动，先由引擎把这些改动存档到一个带名字的救援引用（例如 refs/flywheel/rescue/<dead-exec>，stash 并推送），让 worktree 回到干净状态再接管。交接文案里写明救援引用，替身自己决定要不要取回。

预计节省：本类等人手的时间基本全部可省，约 133.3 h；只剩几分钟的自动处理时间。

风险：存档只能在「前任已被证明死亡」之后做（和现有判死条件相同），否则可能跟一个还活着的体抢 worktree（参见 FLY-2572 死而复生的形状）。救援引用必须推送到远端，不能只留在本地。

③ Codex 凭据与身份 — 27 次 · 23 张单 · 6 批 · 浪费 77.4 h（其中等人手 72.5 h）

根因：见上一节。全局 ~/.codex 既是人工重登或换号的操作面，又是 runner 起跑时的凭据种子源。操作期间文件缺失或身份不一致，新起的体必死，并且会被当成普通死亡去盲换。

最小修法：① 换号或重登改成原子替换：先写临时文件再 rename，任何时刻都不删 auth.json；重登也在独立目录里完成，成功后再原子换入；② runner 起跑时如果凭据缺失或身份未知，按「凭据暂不可用」退避重试几分钟，不判死、不计入盲换次数；③ 长期方向是 FLY-2404（全机一份凭据真身，原地刷新）。

预计节省：本类几乎都能省，约 77.4 h，外加今天这类 companion 评审停摆。

风险：②的退避要有上限，否则真正的账号失效会被拖延暴露。超过上限仍按现状判死并告警。

第四名以后：重启后 reown 失败（64 次 / 48 张单，涉及单数第二多，但多数 1–2 分钟就换体接上，合计 56.4 h，对应 FLY-2586 / FLY-2505 / FLY-2558）； 体自报 blocked（28 次，Codex 独有：三轮等不到外部条件就自报 blocked，然后被当作死亡换体）； 「关了没关死」在额度上最亏（见额度视角，FLY-2892 / FLY-2814）。

局限与复算方法

  • Bridge 日志只保留约 8 小时，FLY-2814 复活的直接日志证据拿不到。改用「终态后 rollout 仍有 token」间接判断，只能说明终态后仍在消耗，分不清是自动复活还是没杀掉。
  • 有 81 个 Codex 执行体找不到 rollout（多为起跑失败），token 记 0。
  • 浪费时长包含 Lead / founder 的反应时间。这是出事造成的真实损失，但它依赖人什么时候在线，所以预计节省写成区间。
  • 额度折算基于本机可见的 rollout，其他机器上用同一账号的消耗看不到，所以百分比可能偏高。
  • 复算：cd evidence/scripts && python3 collect.py && python3 usage.py && python3 classify.py && python3 switches.py && python3 build_report.py。 raw/freeze.json 固定了冻结点，重跑得到的每个 CSV 都逐字节相同（已验证）。抽查 10 条出事记录与生产原始事件和 transcript 的对照，见 derived/spotcheck.md。
