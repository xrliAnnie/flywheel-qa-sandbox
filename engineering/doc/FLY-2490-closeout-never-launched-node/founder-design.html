一句话结论

一具在 worktree 接管阶段就失败、从来没起过窗口和进程的 Codex 实现体，被收尾流程当成「需要留着给人看的崩溃现场」永久保护；而收尾自己的「独立验尸」又因为把「根本没有 daemon 记录」和「daemon 状态查不清」混成同一个「不确定」，永远拿不到死亡证明。本单只补这一格证据判断，不动保护崩溃现场的那道门。

你在 issue 里写的方向本设计怎么落
「无东西可保留」的体应视为 already gone采纳精神 但不用「没有 CommDB 行 / 没有 tmux 记录」这种表面判断（它们在收尾后都会被删，不是证据），改为让既有的三重缺席探针说话
或传 forcePreserved 走 issue 终态权威否决 那会让有窗口的崩溃体在 shipped 收尾时被杀窗，破坏 FLY-116
⛔ 不要「failed 一律直接杀」遵守 门不动；只对「Bridge 进程内写下的失败回执（receipt）说这具体从未进入适配器（目前只有 worktree 接管失败；HTTP 通道伪造不了）+ launch claim 已 closed + 状态 failed/blocked + 当前 root 无任何 daemon 痕迹」放行到既有探针，三重缺席才判死，判死后再复核一次
把 lifecycle_conflict 换成可诊断的 token新增 nodes_not_confirmed_gone，与审计事件里的 reason 同一个词

发生了什么（FLY-2351 / PR #1133 实况）

  • 9-9 07:24：实现体 c070fce7… 在 worktree 接管时失败，状态 failed，适配器 codex-tmux。它没有 tmux 窗口、没有 daemon、没有 CommDB 行，磁盘上也没有 session.json 和 socket 文件。
  • 9-9 19:00：PR 合入，issue 级收尾开始。收尾逐个节点确认「已消失」，轮到这具体：closeRunner 见状态是 failed 就按 FLY-116 规则返回「保留取证」；收尾再做独立验尸，Codex 分支先问 daemon 探针，探针因为没有 daemonPgid 返回「不确定」，收尾就此停手。
  • 随后每小时一轮：18 轮 closeout_report outcome=blocked，每轮一条 closeout_issue_items_blocked，阻塞项恒为这一个节点（confirmed_gone_false, communications_finalized_false）。
  • land 操作把 cause 标成 lifecycle_conflict（其实没有任何冲突：founder 停手意图 0 行、Linear 取消观测 0 行），重试 9 次后进入 held；Lead 9-10 05:20 手动 resume 一次，再 9 次，09:20 再次 held。
founder 可见影响为 0（thread 已手动归档、Linear 已 Done）。同形的还有 FLY-2382（PR #1107），同样 held 在 lifecycle_conflict；今天新出现的两次 blocked（FLY-2509 / FLY-1949）是正常完成体的例行收尾，不属本族。

核心流程：收尾如何确认一个节点「已消失」

图 1 · 橙色：FLY-116 的保护门，不改；绿色菱形：本单新增的四道门与终复核；蓝色：既有的三重缺席探针；红色：仍然 fail-closed 的分支
  1. 节点状态是 failed/blocked ⇒ closeRunner 返回「保留取证」。这是对的：有窗口的崩溃体要留给人看。
  2. 收尾做独立验尸（FLY-2313 加的路径，已被测试证明「探针说 dead + 定位不到窗口 ⇒ 收尾完成」）。
  3. Codex 体先看 daemon 证据。新增：证据分三种——活着、已死、不确定；「不确定」时再过四道门（图 1 绿色菱形）。
  4. 四道门：① 状态已是 failed/blocked；② StateStore 里有一张只由 Bridge 进程内部写的失败回执（receipt），说这具体的失败类别属于「从未进入适配器」白名单（目前只有 worktree 接管失败——Blueprint 在调用适配器之前就返回了，所以这具体在任何目录下都不可能起过 daemon）；③ 它的 launch claim 已 closed；④ 当前目录下也没有任何 daemon 痕迹（无 session.json、无 spawn lock、socket 无人）。四道门全过才把问题交给既有的 generic 探针；三重缺席才判死，判死后再读一次证据做终复核。
  5. 承重的是第 ② 道门，而且必须是 Bridge 自己写的回执——评审第 3 轮指出「文件不在」在目录漂移、daemon 自己删文件、复核后才起进程这三种情况下都不算证据；第 4 轮又指出 Runner 拿着 /events 的 token 可以伪造一条「我是 worktree 接管失败」的事件。所以回执单独建表、只有进程内的 DirectEventSink 能写，/events 见到这类失败直接拒绝并留审计。
  6. 判死后走既有路径：通信账本收尾（无行 = 0 改动、成功）、thread 归档、Linear 一致性。

证据模型：哪些东西算证据，哪些不算

图 2 · 标 [新] 的是本单新增的证据字段和 cause 词；标 [白名单] 的是承重证据；其余都是既有数据
不算证据StateStore 的 tmux_session 列（快照里 592 个 failed/blocked 行绝大多数为空，包括曾经有窗口的）；CommDB 行（收尾时被删）。所以不能用「没有行」推「从未起过」。 承重证据新表 pre_adapter_failure_receipts 里的一行回执：只由 Bridge 进程内的 DirectEventSink 在「Blueprint 在调用适配器之前失败」时写下，Runner 可见的 HTTP 通道写不了（对这类失败直接 400）。回执说 worktree_takeover_failed 就意味着这具体在任何目录下都没起过 daemon。加上 launch claim 已 closed（快照里这一族 57 具全部 closed）。 一致性核对当前目录下 session.json 的四态（不存在 / 有文件无 pgid / 有合法 pgid / 不可读）、spawn lock 的四态（不存在 / 持有者已死 / 持有者活着 / 不可读）、socket 有没有人监听。只有「不存在 + 不存在 + 无人」这一种组合算「无痕迹」；「有文件无 pgid」和「持有者已死」都可能是 Bridge 在起进程途中被杀的形状，一律不放行。 状态门只对 StateStore 已判 failed/blocked 的行放行；除了 issue 收尾这条线，其它 5 个探针调用者不接「数据库事实」钩子，行为一个字节不变。 新 cause 词nodes_not_confirmed_gone：从收尾报告里节点的 confirmedGone / communicationsFinalized 推出；lifecycle_conflict 只留给真正的冲突（Linear 被取消、founder 停手、权威中途变更）。

取舍与被否决的方案

方案结论为什么
A · 在 closeRunner 里把「无 CommDB target ⇒ already gone」提到保护门之前否决CommDB 行被删过的崩溃体也会被判死，正是 FLY-2313 刚修掉的假死；而且 closeRunner 是 Lead/founder 的保留动作入口，不该在这里放宽
B · shipped 收尾对 failed 节点传 forcePreserved否决会真的去杀窗：有窗口的崩溃现场在 shipped 收尾时被清掉，违背 FLY-116；对本体也没必要，问题不在门在证据
C · 探针区分「零 daemon 证据」与「daemon 不确定」采纳改动最小；既有救援路径和测试已经证明后半段是通的；closeRunner 零改动
只看文件系统痕迹（无 session.json / 无 lock / socket 无人）就放行否决（评审第 2、3 轮）持有者已死的 lock 不能证明 detached daemon 已死；目录漂移、daemon 自己删文件、复核后才起进程都能让「无痕迹」与活 daemon 共存。改为以 StateStore 的结构化失败类别为承重证据
把「有 session.json 但无 pgid」也算无痕迹否决它与「Bridge 在起进程途中被杀」同形，fail-closed
从 session_failed 事件里读失败类别当承重证据否决（评审第 4 轮）Runner 持有 /events 的 token，事件表里任何一行都能伪造。改为单独的回执表，只有 Bridge 进程内能写
放行条件用全部终态而不只 failed/blocked不做正常完成的 Codex 体必然写过 daemonPgid；其它终态由正常关窗路径处理。保持最窄
自动扫所有 held 的 land 操作并 resume不做held 是有意的停手信号；清单只有两条，Lead 手动 resume 更可控

诚实边界：这个设计做什么、不做什么

  • 做：Bridge 回执证明「从未进入适配器」（目前只有 worktree 接管失败）、claim 已 closed、状态 failed/blocked、当前目录无痕迹的 Codex 空体，从此可被三重缺席探针判死；/events 拒绝伪造这类失败；land 的 cause 标签如实反映「有节点没被证明消失」。
  • 不做：不改 FLY-116 保护门；不改 daemon 探针对「有记录但查不清」的 fail-closed；不改 Codex 恢复（revive）那条线的探针；不加环境变量、不加开关；唯一的表变更是新增一张回执表（只增不改），不自动回填历史数据。
  • 不承诺：held 的 land 操作自动恢复——而且 FLY-2351 / FLY-2382 这两具体是修复之前失败的，没有回执，合入后 resume 仍会阻塞；要么由 Lead 决定跑一次随 PR 附带、默认不执行的补写回执脚本，要么按 FLY-2486 的形状人工收尾；claude-tmux 体的任何行为变化（路径字节不变）。
  • 不顺带修：run 级的静默判定（hold / terminate / 死体清扫）与另外 4 个探针调用者不接「数据库事实」钩子，行为一个字节不变；Bridge 在起进程途中被杀留下的 Codex 体（有 session.json 无 pgid、lock 持有者已死）仍永远「不确定」，作为后续单处理。
  • 回滚：纯代码，revert 一个 PR；回滚后行为回到「不确定」，不会产生新的误判死。
