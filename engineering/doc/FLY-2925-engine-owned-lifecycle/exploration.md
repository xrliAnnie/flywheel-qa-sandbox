## 1. Founder 要解决的问题

让每个 Codex 工程师像独立终端中的 Claude 一样，不因调度服务重启丢掉正在做的事；是否终结只由工作流引擎决定。goal 是 Codex 自己记录的工作目标，它的暂停、卡住、完成不等于 Flywheel 执行体死亡。

原始修复范围为重启恢复、goal 结果分类、禁止终态自续三至四处。2026-09-26 13:14 PDT 的追问要求首先评估独立终端路线，不能把“已存在 app-server”当成保留现状的理由。

本阶段只设计、取证、评审和交付 HTML。没有运行真实 Codex 验收、没有重启 Bridge、没有申请 529 房、没有改生产配置或实现代码。

## 2. 现状中容易混淆的三个概念

1. **终端窗口**：founder 能看到并操作的 `runner-*` TUI；当前已经有。TUI 是文字交互界面，并不代表控制逻辑也在这个窗口内。
2. **后台推理进程**：每个执行体的 Codex app-server。app-server 是让程序控制同一 Codex 会话的接口；当前 detached 子进程可以活过 Bridge 重启。
3. **运行控制者**：驱动 goal、处理回合边界、收信和恢复的 TypeScript 逻辑。当前位于 Bridge 进程内，重启后它消失，随后 reowner 重建它。

所以“多开一个窗口”不能消除旧恢复路径；真正的独立终端必须让第 3 项也与 Bridge 分离。当前窗口是 remote TUI，不能据此宣称 founder 的方案已经实现。

## 3. 优先评估的三个方案

| 方案 | 重启时发生什么 | 能力与代价 | 初步判断 |
|---|---|---|---|
| A. 原生独立 `codex` 终端 | 原进程继续，Bridge 按精确会话找回 | 原生 goal 与精确 resume 可保留；现有机器信件回执、回合边界、自动账号动作需要可靠接入点，不能用粘贴和读屏冒充 | founder 首选的最简形态；尚无证据证明当前发行版能保持全部自动化语义 |
| B. 独立 runner 宿主 + 真实 Codex TUI | 独立宿主继续驱动原 daemon；Bridge 只重新订阅 | 保留现有 app-server 协议，但把所有执行控制放到每个 runner 的独立程序内；增加一个窄宿主入口和可重连事件通道 | **建议方向**：达到独立终端的使用效果，并保住已有通信、隔离、goal 能力 |
| C. Bridge 继续驱动 app-server，修 reown | Bridge 起来后按原 thread 重建控制者 | 改动较小，仍需重建控制状态；跨重启消息、回合身份、终态判据继续容易分叉 | 可作为迁移旧体的兼容路径；不应是最终产品形态 |

B 不是“把旧 reown 藏到新进程”：存活宿主的重连不提交恢复、不重置 goal、不注入 kick、不改变执行体或 thread。只有宿主也确证死亡，才按同一身份恢复；恢复失败保留诊断，不自动创建新对话冒充成功。

选择 B 的最终前提：Lead 对超出原三至四处的载体包装范围没有冲突指令，且设计评审通过。待答问题 `8221ee32-6265-4da8-b341-7e100b14926a` 已说明该取舍，并请求 FLY-2902 最新约束。本文件不是架构批准凭证。

## 7. 实施前必须关掉的风险

- 独立宿主不能继承只在 Bridge 堆内存在的闭包作为恢复 authority；恢复、关闭、邮箱路由需要可持久核对的身份。
- 工作流节点、执行体、原生会话、账号绑定、进程代数分开；窗口标题只是显示，不能用来选中待杀或待接的体。
- engine 已关闭、身份不符或权限状态读不到时拒绝恢复；普通 Bridge 断连不直接终结体。
- 原会话恢复不等于原进程恢复；若只有 TUI 丢失只修显示，不能重启仍活着的 daemon。
- 启用 FLY-2808 会影响两 vendor 的新 admission，不能把全局开关误当 Codex 专用；必须明确旧体迁移和回滚。
- 真实进程、账号切换、模型消费、Bridge 重启的行为证据要在 529 房取得，静态文档与模拟测试不能替代。
