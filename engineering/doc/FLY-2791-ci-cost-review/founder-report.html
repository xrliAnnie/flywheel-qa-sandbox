CI 迁 Ubicloud 之后，钱花得对不对？

FLY-2791 · 2026-09-23 · 数据来自 GitHub Actions 的真实作业记录（1,500+ 个 job 的实际起止时间）。账单本身没拿到，页面里每个金额都标了是怎么算出来的。
一句话

省了，而且省了一大截。同样的 CI 活、机器跑的分钟数几乎一模一样，月成本从约 $1,400–1,600 降到 $291（便宜档）或 $468（贵档）—— 降 79% 或 67%。
「用 Ubicloud 比以前还贵」这件事没有发生，也不会发生，除非 GitHub 把一条已经撤回的收费重新开征。
至于「是不是跑了很多没必要的 CI」：没有重复跑的测试，但有一个已经做好、却一直没打开的省钱开关——它值每月 $114–196，是剩下唯一的大钱。

一、省没省，省多少

用另一个口径交叉验证过：按 9 月 1–22 日实际发生的 1,659 次 CI 算，这 22 天是 $1,106，折全月 $1,538；8 月同法是 $1,617。两个口径都落在 $1,400–1,620，互相印证。

为什么省的是钱、不是时间

我拿同名的 17 个 CI 作业，把它们在两家机器上跑的时间逐个比了一遍：Ubicloud 的机器其实还快约 16%（原本担心它更慢，实测不是）。但把一次完整 CI 的所有作业加起来、按计费规则向上取整之后，两边消耗的分钟数几乎完全相同：每次都是约 112 分钟。

所以这笔钱省下来的原因很干脆：同样的机器时间，单价便宜了 4.8 倍。跟跑得快不快基本无关。

有一件事只有你能确认，它值 $177/月需要你看一眼

Ubicloud 有个叫 Premium Runners 的开关，藏在控制台的 Settings 页。它不换标签、不换写法，只是把同一批活分到更快的机器上，然后按贵一档收费（$0.002 而不是 $0.00125 一分钟）。

我们 9 月 18 日在你的控制台实测过一次：新装完成后这个开关是「开着」的（和看源码推断的默认值相反）。但之后有没有被改过，我这边看不到。

要你做的：打开 Ubicloud 控制台 → Settings → 看一眼 Premium Runners 是不是 Enabled，截个图给我。开着 = $468/月，关着 = $291/月。

你说的「本月已花 800+」，我对不上，如实告诉你未收口

我算出来 9 月 1–22 日应该是 $1,106，和你说的 800+ 差约 28%。这个差我没有查清楚，原因是：

  • 账单页我读不到。这台机器的 GitHub 令牌权限不够（缺 user 权限），账单接口直接返回「权限不足」。本单的边界不允许我去改令牌权限。
  • 不是被额度上限挡掉的。我把窗口内全部 903 次 CI 都查了一遍，没有一次是「余额耗尽被拒跑」，抽查的 368 次里最小的也花了 2 分钟，没有 0 分钟的。所以差额不是来自「有些活根本没跑」。
  • 剩下的可能（都没验证，不当结论）：你的 GitHub 计划含的免费分钟可能多于 3,000；800+ 可能不是当期精确值；或者 9 月上半月的活比我抽样的那两周轻。

要你做的：GitHub → Settings → Billing → Actions 用量页截个图。有了它，这 28% 五分钟就能收口。

二、是不是跑了很多没必要的 CI

好消息：没有一条测试被重复跑已核实

CI 里有 290 个 shell 测试套件 + 85 个 Node 套件，分散在 15 个作业里。仓库里有一道硬闸专门防重复：它把「仓库里所有测试文件」「CI 里写明要跑的」「人工标记为不在 CI 跑的」三份名单对比，重了或漏了就直接红。我实测过：一条重复都没有。

所以「跑了很多重复 CI」这个猜想，在测试粒度上不成立。浪费在别的地方。

真正的浪费：一个 PR 平均跑 17.5 次完整 CI根因

我用仓库自带的成本工具跑了 9 月 20 日一整天：72 次 CI、8,677 计费分钟、68 个不同的代码版本，最后只合进去 4 个 PR。换算下来，一个 PR 从开到合，平均要跑 17.5 次完整测试矩阵。

另一面：两周内 962 次 CI 里 321 次（33%）被「有新提交了，取消旧的」打断——但每次被打断前，平均已经烧掉了约 80 分钟机器时间，相当于一次完整 CI 的六成。

这不是 CI 配置写坏了，是「一个 PR 被推了十几次中间提交，每一次都触发全套测试」。

好消息的另一半：解药早就做好了，只是没打开一个变量

9 月 17 日上线的 FLY-2681 已经把机制建好了：打开之后，开发过程中的普通提交只跑 5 分钟的快速检查，全套重活留给「真正要合进去的那个版本」。

但它的总开关 CI_SCOPED_MODE 到今天还是 off（9 月 18 日设的，至今没打开）。

打开它安全吗？安全。「能合进 main 的东西」受到的保护一条都没少——要合入必须拿到 CI OK 这个凭据，而只跑了快速检查的版本拿不到它，根本合不进去。少跑的全是那些「反正也不会拿来当合入凭据」的中间版本。代价是：开发过程中发现问题会晚一点。

值多少钱：每月 $114–196（按 FLY-2681 自己做的重放，降幅 39%–67%）。回滚就是把变量改回 off，一步，不动代码。

三、Ubicloud Canary 流程能不能删

能删。但我要先说清楚：删它省不到钱清洁工作

它已经完全不需要了，三条证据：

  • 迁移已经在 9 月 22 日做完了。它当初要回答的三个问题（Ubicloud 上跑得起来吗、容量够吗、并发作业会不会互相踩），已经被生产上两周、1,000 多个真实作业回答了——比 canary 那 2 次试跑强得多。
  • 它全历史只跑过 2 次，都在 9 月 18 日，之后再没动过。
  • 它的授权开关变量 UBICLOUD_CANARY_AUTHORIZED 已经被删掉了——现在就算有人手动点它，第一步就会被拒。它已经是一具跑不起来的空壳。

删掉丢什么：一条「不动生产 CI、单独拿任意机器跑一轮试验」的通道。将来要评估第三家供应商时得重写。不过它在 git 历史里完整留着，随时能取回来。

省多少：现金 $0/月。它已经零运行了，不产生任何费用。省的是维护：这个 32KB 的文件现在每次 CI 都要被语法校验扫一遍，任何 CI 结构改动都要同步改它。

我按边界没有动它。请你说一声，我让后续的实现单去删。

四、那些 payload 发布流程，迁不迁

建议：留在 GitHub按你自己的口径

你说过「如果这些只是一些 release 的流程，那放在 GitHub 上倒也可以」。我查了：这六个确实全都是发布/分发流程（beta 班车、过期清理、一次性激活、客户版候选、manifest 提交、客户版执行器）。三条理由支持留着不动：

  • 迁过去省不到钱。六个加起来约 2,100 分钟/月，完全在 GitHub 的免费额度里（每月含 2,000–3,000 分钟）。迁过去省 $0–6/月。
  • 迁过去要付一次安全评审的代价。其中四个握着真凭据（Cloudflare 令牌、npm 发布令牌）。当初把凭据放进 CI 是一次特意做的、评审过的决定，而那次评审的前提就是「跑在 GitHub 自己的机器上」。交给第三方的虚拟机是换了信任边界，得重走一遍评审。为省 $0 去动它不划算。
  • 它们本来就不怎么跑。其中四个近 60 天一次都没跑过。

但有件事该做（不是清理，是体检）：正因为四个 60 天没跑过，我们没有任何证据说明它们今天还能跑通。建议单开一张单，在非生产目标上把整条发布链走一遍。防的是「真要发版那天，发现四个流程全坏了」。

实话的另一半：能省的钱几乎全在第 2 条上，其余加起来不到 $45/月。迁 Ubicloud 这一步已经把 $1,400 打到 $291，剩下能再挤的空间本来就不大了。

两件「看着浪费、其实不花钱」的事，别去动

  • 每条评论都会触发一次 ship 流程：两周 501 次，其中 345 次（69%）在第一步就被跳过。被跳过的作业不占机器、不计费。GitHub 不支持按评论内容提前过滤，这已经是最省的写法。真正的 ship 每次只花 0.6 分钟。
  • 纯文档 PR 也会跑一遍快速检查：约 4 分钟。但那个检查里有一批专门校验文档和目录结构的脚本，纯文档 PR 恰恰需要它们。整条文档 CI 才 6 分钟，占全月不到 0.1%。不值得为它加复杂度。
