FLY-2134 · 监控者的监控:给每个自动机制登记「该产出什么」,由独立进程只看产出物年龄

设计稿 · Codex 四轮评审(11→9→4→1 条)+ Lead acceptance 收口 2026-09-08 日期 2026-09-08 · 文档 engineering/doc/FLY-2134-monitor-the-monitors/ · 上游 FLY-2146(它把「看者本身没人看」明写交给本单)

① 一句话

建一张登记表,写清全舰每个自动机制「应该产出什么文件 / 数据 / 远端提交、多久必须更新一次」;再加一个每小时跑的独立小程序,只看这些产出物的年龄——过期就响、根本不存在也响——完全不看那个机制自己的日志、退出码、或它有没有被 launchd 关掉。最后让这个小程序、Bridge、已有的 Bridge 探针三方互看成一个环,任何一方死了都有另一方出声。

「launchd」= macOS 的定时任务系统。「产出物」= 一个机制干完活留下的东西:一个文件、数据库里的一行、GitHub 上的一次提交。「Bridge」= Flywheel 的主进程。「探针 probe」= 已经在跑的每分钟检查 Bridge 是否活着的小脚本。

③ 两种失效形状,一个修法

issue 里最该带走的一格:A「报成功地死」骗的是监控——机制在,但停了,日志和状态还说正常;B「假设存在而从未存在」骗的是假设——从来没人建过。两种都不会响,但一张「期望产出物」登记表能同时抓住:A 由「产出物过期(stale)」抓,B 由「产出物根本不存在(missing)」抓。

「stale」= 产出物在,但比登记的最大年龄还老。「missing」= 登记说应该有,机器上根本没有。「undetermined」= 这一轮读不到(网络断、数据库被锁),判不出——判不出时不动「过期/缺失」那本账(不误报也不误清);但连续两轮都判不出会走另一本账响一声——「看不见」本身不能再沉默(Codex 评审第 1 条)。

④ 核心流程:看者每小时的一轮

看者 = 新脚本 artifact-freshness-check.sh,由 launchd 每小时第 50 分钟拉起(排在 FLY-2146 的记忆看者 :40 之后,这样它每轮看到的都是本小时的台账)。三种探针全部只读:看文件修改时间、看 sqlite 数据库指定表指定列里最新一天的日期(登记表里只写表名和列名,不写 SQL——脚本自己拼一句固定的取最大值查询,杜绝有副作用的语句)、看 git 仓本地 HEAD 与 GitHub 远端的祖先关系。

判词file_mtime(文件年龄)sqlite_max(数据库最新日期)git_remote_head(远端是否跟上)
fresh普通文件、非空、够新最新日期够新远端 == 本地;或远端领先(本地没有独有内容);或本地领先但最早没推的提交还够新
stale太老,或零字节最新日期太老最早没推的提交太老(两边分叉也按此判,台账标 diverged)
missing路径不存在 / 是快捷方式 / 是目录数据库不存在;或表里一行都没有不是 git 仓;或没配远端(没有远端 = 假设不成立)
undetermined存在但读不了被锁 / 损坏 / 表或列不存在 / 超时 120 秒联不上 GitHub / 超时 / 远端那次提交本地没有(不 fetch,只报判不出)

每轮开跑先体检自己的三个状态文件(是不是普通文件、台账表头对不对、账本形状对不对),不对就退出、什么都不碰——先确认自己没坏,再去看别人。告警节奏抄 FLY-2146:进入异常发一条;持续每 24 小时重提一条;恢复发一条;发成功才记时,恢复帖发成功才清账。每个产出物两本账:「过期/缺失」一本,「连续判不出」一本,各响各的。登记表里任何一行写坏了 ⇒ 整表拒绝、这一轮零发帖、也不写心跳——这样「登记表坏了」本身 3 小时后会被 Bridge 的 W-4 抓出来。心跳文件只在一整轮全部写完时才写,是「这一轮真做完了」的印章,不是「跑过」。

⑤ 谁监控监控者:三方成环

再加一个看者去看看者,是无穷回归。答案是让已经存在的三个进程互看:看者每轮写一个心跳文件 last-run.json;Bridge 的 /health(它自报健康的页面)新增一条 W-4 记录(第一步可选、第二步必有)读这个心跳的年龄,超 3 小时算 stale;已有的每分钟探针读 /health,看到 W-4 stale 连续 3 分钟就折进它已有的「Bridge 退化」告警;而看者的登记表里有一行就是探针自己的状态文件——超 15 分钟没更新就 stale。看者 → 探针 → Bridge → 看者,三方任何一方死掉,另一方出声。

「W-1 / W-2 / W-3」是 Bridge /health 里已有的三条自检记录;W-4 是新加的第四条,分两步上线:第一步可选(老探针读不到就当没有,升级顺序前后都不误报;但探针先学会认「第 3 版清单必须带 W-4」),第二步必有(Bridge 切到第 3 版清单,从此 W-4 不见了 = 清单不合法 = 告警)。Bridge 读心跳文件时逐字段严格校验:文件是快捷方式、超 4KB、时间在未来、计数对不上、字段非法——任何一项都判 invalid 并告警,不会「坏着报健康」(Codex 评审第 3、4 条)。

⑧ 诚实边界:这个设计做什么、不做什么

  • 只让沉默的东西出声,不修它们。首轮三条告警(用量库、chezmoi、runner-memory)是预期阳性;救回单元归 FLY-1814 审批清单,修 chezmoi 推送、建 runner-memory 远端各需另开单。
  • 环只到「进程级」。看者、探针、Bridge 都在这台机器同一个 launchd 域里;整机死或 launchd 坏时三方同死,只剩人的眼睛。第二台机器是 FLY-2146 记录的 founder follow-up。
  • 「远端有」只证到 GitHub 报出的那一行提交编号和它与本地的祖先关系。远端内容能否恢复、有没有被覆盖,不在本单。
  • W-4 第一步期间是可选行,且「心跳文件还不存在」在第一步不响:这段时间「W-4 从未接上」「看者从未跑过」都只能靠上线后的检查清单人眼看到;第二步(第 3 版清单)合并后,心跳缺失立即由探针机器抓,不依赖 Bridge 开机时长(Bridge 反复重启也重置不掉)。开第二步的前提是一组只有新探针才能通过的正/负对照证据。本单的完成定义包含第二步。
  • 检测延迟:普通产出物最坏「最大年龄 + 1 小时」;看者自己死 ≈ 3 小时 5 分;探针死 ≈ 1 小时 15 分。
  • 崩溃窗口:发帖成功与记账之间被杀,下一轮最多重发一帖;记账后、台账前被杀,这一轮没有台账也没有心跳,但不重发;台账写到一半失败,留半轮(同一 run_id 可辨),没有心跳;心跳写失败 ⇒ W-4 最终变 stale ⇒ 环出声。
  • 故意不登记:每日 standup 的日志、配额守护进程的日志——「日志新鲜」只说明「跑过」,登记它们会违反本单第一原则。
  • 不读任何机制自己的日志、退出码、launchd 状态——用测试锁死(脚本文本不得含 launchctl / chezmoi / git fetch / .log)。
