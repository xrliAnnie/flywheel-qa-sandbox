## 目标与边界

让常驻 Lead 用更少真实模型请求和更小上下文完成同样职责。保留 founder 消息到达、及时响应、精确授权与未完成义务。仅设计；不改运行时代码、不调生产配置、不重启、不代 successor 执行 QA。

## 最先校准的问题：40 亿是什么

已直接读取 Tadashi 的 Claude Code transcript（会话逐条记录），完整复现 9 月 14 日 UTC 的原数：6,668 条 assistant usage 记录、3,974,850,298 缓存读、41,373,447 缓存写、11,274,047 输出。相同 requestId 的 usage 在多个内容块上重复；去重后是 **2,662 个非合成模型请求（另1条零usage合成记录）、1,553,141,091 缓存读**。首条/末条/最大 usage 三种取法完全一致。

这不是节省成果。仍有约 15.53 亿实际请求口径的缓存读、58.70 万平均输入上下文；省账本误差和省模型工作必须分开。不能用缓存读直接推算订阅配额或美元。

## 已审计的假说

| 假说 | 当前判断 | 设计方向 |
|---|---|---|
| 同 batch 重投是主因 | 9/14本日2,002个batch各一次；9/15 Cass独立样本确认一个输入夹带9份相同batch，ACK已持久但消费延迟。零同batch重复不能证明零逻辑重投 | 修ACK消费/租约边界；Cass同attempt重复继续查carrier，未证实因果量不计收益 |
| Bootstrap 只应含未答问题 | 当前查询已排除持久 response。实际 5 份 bootstrap 列出 876 个 ASK 条目，其中 843 条正文以 DONE 开头；当前仍可查的 399 个唯一问题里 397 个是结构化 report | 按持久 kind 分出单向报告；保留全部未答义务，摘要+分页，不按正文 DONE 猜测或删旧问题 |
| 事件都应降噪 | 423 次 stage_changed、18 次恢复监控事件真实入上下文；EventFilter 目前只标优先级，全投递 | 精确例行事件只进审计；founder、门禁、失败、unknown 默认照常送 |
| 规则包太大 | 当前 active manifest 确认 18 个源文件，合为一个 234,795-byte / 215,011-char bundle。不是 18 次 API 请求；静态 token 占比没有原生分项 usage | 去重复、把低频 SQL 配方移到按需 runbook；权限和路由核心常驻 |
| 提前压缩可行 | 官方原生 auto-compact window 可配；本机 CLI --help 也有 --autocompact。事故版本 2.1.270、本机 2.1.272，尚无本项目灰度实测 | 先限制恢复量并瘦身规则；测底线F后，满足余量硬门才对这个Lead试窗口（首候选400k）；不改模型、不禁用自动压缩 |

## 四条之外的浪费

- 412 个只调用 ACK 工具的请求消耗 241,327,898 缓存读，占 15.54%；2,007 次 ACK 工具调用不等于 2,007 次模型请求。
- 452 个含 FOLLOWUPS.md Bash 操作的请求关联 282,716,461 缓存读。包括写入、检查，不能全部算重读浪费。
- 自建两小时 wakeup 加 cron backstop：20 次输入关联 53 个请求 / 29,307,942 缓存读；与 Bridge summary_due 是不同调度源。
- 普通 runner ASK 处理关联 503,649,810 缓存读；大量单向报告误呈现为 ASK 是更值得优先处理的原因之一，不能把所有 ASK 都静默。

## 候选比较

1. **选：先减恢复清单和例行通知，再用原生压缩窗口。** 小改动覆盖请求频率与上下文两个乘数。
2. **选：删规则重复、同轮批量 ACK、增量维护跟进记录。** 不建新的调度器或摘要模型。
3. **不选：先换便宜模型。** 未解决无效工作，且不是 founder 目标。
4. **不选：低优先级全丢、问题超时即删、取消 ACK/重试。** 会丢义务、恢复或 founder 消息。
5. **不选：全舰消息新总线、自动 LLM 降噪分类器。** 现有队列和类型足够，新增模型调用反而耗量。
