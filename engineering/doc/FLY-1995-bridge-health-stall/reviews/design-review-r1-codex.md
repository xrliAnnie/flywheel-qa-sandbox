# Design Review — plan.md (FLY-1995) (Round 1)

Date: 2026-08-22
Author: Codex
Status: CHANGES REQUESTED

## Summary

The overall direction is sound: instrument first, keep FLY-1971 on hold, bound the orphan loop, and make destructive cleanup operator-gated. The in-process V8 profiler is feasible on the production Node 25 runtime, but the plan has blocking correctness gaps around the existing FLY-1328/FLY-161 question-retirement boundary, profiler persistence during the guard's kill window, fail-closed API auth, and the residue surgery's evidence-preserving sequence.

## What's Good (Keep)

- Treating FLY-1995 as a symptom and making stack attribution—not a presumed database cause—the primary acceptance criterion.
- Using both `monitorEventLoopDelay` and ELU. Together they distinguish scheduler delay from a merely slow request path and give FLY-1986 a useful measurement surface.
- Keeping the profiler behind one default-on kill switch while leaving the low-cost detector available when profiling is disabled.
- Making `/health` additive and reserving the richer, potentially sensitive data for an authenticated diagnostics endpoint.
- Preserving review-gate questions and keeping FLY-1971 threshold work explicitly out of scope.
- Defaulting the data surgery to dry-run, requiring a backup, exact counts, integrity checks, an immutable receipt, and an operator-controlled maintenance window.
- Adding producer-side suppression as well as deleting historical residue; cleanup without stopping recurrence would be incomplete.
- The proposed test matrix is stronger than usual, especially the real inspector integration test, guarded disposal race tests, dry-run byte-safety check, and profiler-on/off overhead comparison.

## Issues & Recommendations

1. **Fix B duplicates and weakens the existing FLY-1328 orphan-retirement authority.** `GatePoller.zombieGateHygienePass()` already runs `runZombieGateHygiene()` at the 60-second cadence and retires eligible checkpoint-less asks through `CommDB.retireQuestionGuarded()`. That path contains the load-bearing FLY-161 protections: a completed runner's question survives while its CommDB registration still exists, a live StateStore session survives, non-UUID/non-runner senders fail closed, chronology is checked, and a concurrent response wins. The proposed `getSession() === null && age > 24h` rule bypasses those protections and could silently dispose a legitimate question from a non-session-backed actor; the current `voice-*` residue is exactly such a non-UUID actor. **Revise Fix B to extend/reconcile the existing hygiene path rather than create a parallel terminal authority.** Define authoritative provenance for the voice producer (an explicit actor kind/allowlist or durable tombstone), keep the existing runner UUID/CommDB/StateStore/chronology guards, and reuse `retireQuestionGuarded({ expectedFromAgent, requireUnanswered: true, resolvedVia: ... })`. A small in-memory cache may throttle the 3-second relay scan, but it must not decide disposal. Extend the existing FLY-1328 test matrix, including “completed but still CommDB-registered,” response race, reopened question, non-UUID fail-closed, review gate, and the exact voice-orphan provenance case.

2. **The proposed SQL targets a read-only view, and the new narrow API is weaker than the primitive already present.** `mailbox_message_projection` is declared as a read-only compatibility `VIEW`; existing terminal writes update the base `mailbox` table. `resolveGate()` is intentionally broad and unconditional, while `retireQuestionGuarded()` already checks the exact id, expected sender, unanswered state, and nonterminal state before setting `relay_state='terminal_disposed'`. **Do not implement the pseudo-`UPDATE mailbox_message_projection`.** Prefer the existing guarded primitive; if a wrapper is still useful, implement it over `mailbox`, require `expectedFromAgent`, retain the `NOT EXISTS(response)` condition, and return a result that distinguishes `retired`, `response_won`, `already_terminal`, and `missing` rather than a lossy boolean. `terminal_disposed` is the correct terminal state only when reached through those guards.

3. **The profiler lifecycle and units are underspecified, and the “previous window survives a guard kill” claim is incorrect.** A local Node 25.6.1 spike confirmed that a 10,000 µs in-process CPU profile captures both a named busy loop and a named `Atomics.wait`, so the approach is feasible. However, inspector requires `Session.connect()` → `Profiler.enable` → `Profiler.setSamplingInterval` (before profiling) → `Profiler.start`; omitting `Profiler.enable` fails. `monitorEventLoopDelay` values are nanoseconds, so comparing `histogram.max` directly with a 1,000 ms threshold is wrong without division by `1e6`. Most importantly, the 30-second boundary callback runs on the stalled event loop: if a stall continues past the guard's 60-second threshold, the worker sends `SIGKILL` before the main thread can call `Profiler.stop()` or serialize the in-flight profile. The prior window does not contain that stall. **Document this as a known attribution gap or use an out-of-process/continuously persisted profiler if >60-second stalls must be captured.** For the in-process design, add explicit lifecycle/error states, unit conversion, actual window start/end timestamps, `stop()`/disconnect wiring in Bridge `close()`, and tests for initialization failure, the 999/1000 ms boundary after conversion, a boundary-spanning stall, and the expected guard-kill limitation.

4. **Profile persistence and retention need crash-safe operational semantics.** A process restart currently resets the in-memory keep count, so `PROFILE_KEEP=20` is not a durable cap. Stop/serialize/write also creates an unprofiled interval and can itself stall the loop; a partial `.cpuprofile` can be mistaken for evidence after a crash. **On startup, inventory only strictly owned profile filenames and prune oldest files across restarts; write with mode `0600` to a `0700` directory via temp-file + atomic rename; never follow or delete unrelated paths.** Start the next profiling interval before expensive serialization where the inspector protocol permits it, and expose the measured rollover gap plus a degraded/error status in `snapshot()`. Use the repository's state-directory seam (including `FLYWHEEL_HOME` where applicable), and use the existing `appendRotatedLogSync` discipline for the JSONL ledger rather than reimplementing rotation. Keep `/health` on an in-memory, nonthrowing cached summary—no filesystem enumeration in the health request path.

5. **The “long-task ledger” does not provide deterministic event-loop attribution as written, and the proposed coverage is incomplete.** Timing a whole async promise measures wall time, including harmless network, SQLite-worker, or Discord waits; overlapping fire-and-forget riders can all appear “long” without occupying the event loop. In addition, `gate-poller.ts:695-772` is only part of the periodic surface: reconciliation, quota, flag scan, issue supersede, workflow materialization, landing, health, zombie hygiene, founder passes, and the awaited per-question loop enter elsewhere. Wrapping only the named range and `HeartbeatService.check()` would create misleadingly selective evidence. **Rename this signal to a rider wall-span correlation ledger and store start/end timestamps, or instrument only known synchronous sections using the existing sync-operation marker seam.** Enumerate all poller/heartbeat entry points, distinguish synchronous duration from awaited wall time, and state clearly that the CPU profile—not the ledger—is the stack-attribution authority.

6. **The diagnostics route is not fail-closed under the current `/api` convention.** `apiAuthWithRunnerTierDelegation()` delegates to `tokenAuthMiddleware()`, and that middleware deliberately no-ops when `TEAMLEAD_API_TOKEN` is absent. Merely placing the route under `/api` therefore violates the plan's “never naked” promise. Profile names, stack-derived function names, and absolute filesystem paths are also sensitive operational data. **Mount the route with explicit sensitive-surface behavior used elsewhere: no configured master token → 503; missing/wrong bearer → 401; Gemini-scoped token → 403; master token → 200.** Return profile IDs/basenames rather than absolute paths and do not add profile-file download unless separately designed. Test all four auth states and make the `/health` first-window/profiler-disabled/degraded shapes stable and purely additive.

7. **Fix C does not yet define a reproducible deletion cohort or a usable dry-run/apply handshake.** The plan reports several overlapping counts but never gives the exact `DELETE` predicate. “Recheck equals dry-run baseline” is unenforceable unless apply consumes a durable baseline, and treating a zero count as `already_applied` can falsely bless a wrong, empty, or newly created database. A read-only query against a live WAL database can also change `-shm` read marks, so testing only the main DB file's bytes is not a physical-read-only proof. **Specify one exact, half-open cohort predicate** (event type, source, timestamp bounds, and any intended execution/project restrictions), plus breakdowns and min/max identity evidence. Dry-run should query a copied main/WAL/SHM snapshot and emit a signed/hashed baseline receipt containing the database realpath/identity, schema version, predicate, counts, script SHA, and timestamp. `--apply` must require that receipt, open with `fileMustExist`, acquire `BEGIN IMMEDIATE` while Bridge is demonstrably stopped, and revalidate inside the transaction. Only a prior applied receipt bound to that database/cohort may produce `already_applied`; otherwise zero rows is a fail-closed `target_missing` result.

8. **The surgery needs explicit WAL, disk, and failure-recovery handling.** Deleting ~2.64 million rows in one transaction can create a large WAL in addition to the 1.77 GB backup. Checking only that the backup is nonempty does not prove restorability, and an `integrity_check` performed after commit cannot roll back a corrupt result. **Preflight free space for the backup plus worst-case WAL, validate the backup with `quick_check`/cohort counts, run integrity/foreign-key checks before commit where possible, and define restore/failed-receipt behavior for any post-commit failure.** After a successful commit, explicitly checkpoint/truncate the WAL while still avoiding `VACUUM`. Resolve `better-sqlite3` through a package-owned maintenance seam such as `StateStore.openForMaintenance`/`backupTo` or an anchored `createRequire`; do not rely on root hoisting. Test with a real WAL fixture including sidecars and ensure a typo/missing DB path never creates a database.

9. **The implementation sequence can destroy the evidence required by acceptance criterion 1.** Applying Fix C first may remove the strongest current CPU/stall candidate and make the quasi-periodic episode disappear before a flame graph is captured. That could improve production while leaving FLY-1995's attribution acceptance unmet and weaken the before/after causal record. **Sequence the rollout explicitly:** ship Fix A (plus safe producer suppression and the corrected Fix B), validate profiler health/overhead, capture at least one production episode or reproduce it against a faithful database clone, preserve the profile and baseline metrics, then run the operator surgery and compare the same surface afterward. Keep the surgery artifact deliverable independent, but gate production `--apply` on that evidence checkpoint.

10. **The notifier limiter's key, memory bound, and “total conservation” promise are not correct yet.** `(executionId, reason)` can merge distinct projects, issues, and notification kinds; the Map grows without bound across unique keys. A process restart—or simply no later event for that key—loses the accumulated count, so an in-memory “emit on next event” design cannot guarantee conservation. No semantic reader of `issue_thread_infra_notify_skipped` exists today, so aggregation is safe, but dynamic event-query APIs still expose these rows. **Limit suppression to the skipped event type, key by at least `(projectName, executionId, issueId, kind, reason)`, and add TTL/LRU bounds.** Either call `suppressed_count` best-effort sampling and remove the conservation claim, or add periodic/shutdown flushing if exact conservation is required. Re-run the zero-reader check immediately before implementation and keep `notified`/`failed` audit events byte-compatible.

11. **The flag declaration and runtime test matrix need to match this repository.** `FeatureFlagSpec` has no `owner` field; it requires category/source/scope/polarity/value kind/default/description/read sites/toggleability. The repository's `.node-version` is 22 while production is Node 25.6.1, so a single local inspector test does not establish both CI compatibility and production behavior. **Register `FLYWHEEL_LOOP_PROFILER` as a default-on `kill_switch`, `env`/`bridge_global`/`bool`, with `bridge_boot` or `object_construction` read timing and the correct non-direct toggleability, and update the registry drift/truth tests.** Run unit/integration coverage on the repository's Node 22 baseline and repeat the real inspector/busy-loop, `Atomics.wait`, overhead, and shutdown lifecycle checks on Node 25 in the production-like QA environment.

## Verdict
