FLY-2919 提供统一进程证据：它说明准确的执行代次是否还有能写文件或重启工作的进程。本单消费该结果，保留现有身份校验和清理收据。FLY-2754 已并入：即使任务曾失败或阻塞，只要能证明进程已停止，也应继续正常收尾；失败记录仍保留。启动之前就失败的情形，使用系统留下的可信凭证，不能只凭一段报错判定。

操作记录固定目标目录与分支；短期证据确认当前进程；效果收据分别记录目录、通信和归档结果。预览清单只表达选择，执行时必须重新验证。

存量清理：先列清单，再重新检查

只列出已合入或已关闭、没有活体或未知体、目录干净、提交已在远端保全、身份一致的候选。执行使用 Git 自带的安全工作树删除，不强制删除。任何进程仍以候选目录为当前目录，都保留该项；存量清理绝不终止进程。被忽略的嵌套仓库也必须检查，避免外层干净却删掉内层未提交文件。

明确保留：FLY-2688 / 2751 复现样本，有未提交或未推送改动的目录，仍开放或没有 PR 的目录，以及数据库取证件。PR 是代码评审请求，用它确认分支的处理状态。

已关闭但未合入的候选还须有可信的取消权威和最新任务状态，只回收目录，不伪造合入状态或归档授权。整单记录已完成但目录仍在的项，单独记录目录回收，不把重复请求的空操作当作清理成功。重复执行时，已不存在的准确目录记作已清理；同名新目录绝不能被误删。

取舍与不采用的办法

  • 复用现有清理、告警和恢复入口，避免再造一套任务系统。
  • 复用 FLY-2919 的进程判断，避免两处说法冲突。
  • 不靠增加重试次数遮住探针超时。
  • 不因窗口消失、账面完成或缺少进程记录就宣告安全。
  • 宁可明确留下缺证的旧样本，也不凭名字或操作备注删除。

怎样证明真的修好

  1. 在隔离环境走真实合入路径：目录消失、讨论串远端已归档、整单完成，而且没有收尾不完整。
  2. 重现“节点无法确认消失”和“心跳租约过期”，恢复旧缺陷时对应测试必须失败。
  3. 生产只读清单与逐目录复核结果一致，脏目录作为不能删除的对照。
  4. 告警重试、重启和响应丢失之后，同一失败仍只产生一条逻辑消息。
  5. 新的节点工作流收据中出现准确目标的 worktree_cleanup_done，即目录清理成功事件。
