3 · 核心流程:声音怎么走一圈

一个常驻的轻量 brain 文字触发器,加上一次语音模式期间才运行的 raya-voice 会话进程。voice 启动后维持两条 20 毫秒一帧的常开流,三条「腿」(Discord 连接 / Codex 子进程 / 实时语音会话)各自被盯着,一个「协调器」决定现在该说什么、该不该退出。

{{SVG1}}
realtime 会话 v2
Codex 自带的实时语音通道第二代:WebSocket 同时带声音和控制,所以它「想空闲也空闲不了」—— 这是你 8 月 20 日拍板选 v2 换来的稳定性(代价是没有「先应一声」和打断)
app-server
Codex 的后台程序,我们用一问一答的消息协议(JSON-RPC)和它说话;voice 与 brain 各跑一个进程,但共享 Raya 的订阅认证 CODEX_HOME。单独空 home 只带语音 key 时,后台任务实测 401,所以本单不偷偷切到另一套计费账本
Opus / PCM / 24k
Opus 是 Discord 用的音频压缩格式;PCM 是未压缩的原始样本;Codex 这边要 24 kHz 单声道,Discord 那边是 48 kHz 立体声,中间要换算一次(1911 已证明卡顿的元凶不是换算,是节拍不准)
抖动缓冲
网络来的包时快时慢,先攒 3 帧再放,免得把你一句话中间剪进空白(1911 实测会让 ASR 听错)

5 · 断了怎么办

先说一件事。你 2026-08-20 那晚定过:「否掉我们自己做掉线重连,不许写成待办,也不许写成候选方案」(写在 B、C 两份 PRD 和 1911 的记录里)。Codex 评审第一轮就抓到本单标题里的「断流重连」和这条决定相撞。Tadashi 核实后回复:标题里那四个字是他拆单时的措辞,不是你的原话,你的决定继续有效,标题会改成「断流语义」。所以下面这套是保守版:
  • 做:三条腿断了都能被看见;在文字频道发「⚠️ 语音断线:哪条腿」(有投递回执);把会话证据编号落盘;然后以非 0 退出。
  • 不做:进程内任何「自己重连」的循环 —— 不重新进房、不重起会话、不重起子进程。
  • 回来靠 launchd 在 voice-mode.requested 仍存在时重启这个进程 → 它重新进房 → 新开一段对话 → 发「✅ 已回来(记得:否)」。多久回来不承诺:由守护节流决定。voice 使用 RunAtLoad=false + SuccessfulExit=false;正常 stop 先清 marker 再 exit0,所以不会回来。
{{SVG3}}
这里最重要的一句:断流后回来,但不记得。Tadashi 采用的边界是:你 8-20 否掉的是进程内自己 rejoin / 重起会话的循环;launchd 把退出的进程重新拉起是既有基线。但 P2 已证明旧实时线程没有可恢复记录,所以回来后一定是 fresh thread,不能写成「还记得」。
