# Design Review — FLY-1232 plan.md (Round 3)
Date: 2026-07-13
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 3 incorporates all five Round 2 findings and is substantially closer to an implementable design: spawn ownership, composite atomicity, UID namespacing, honest partial backfill, and T9 repair now have coherent owners and tests. Four correctness gaps remain in the revised evidence/replay contract—two of them are direct contradictions with the current `RunDispatcher`/Codex adapter behavior—so implementation should wait for one more bounded plan revision.

## What's Good (Keep)

- Keep `RunDispatcher.start()` as the sole physical-spawn owner and `StartRequest.shadowContext` as Bridge-internal metadata only. Writing lifecycle events, projections, and `intent_recorded` in one pre-launch `applyWorkflowShadowBatch` transaction fixes the Round 2 ownership and tear problems.
- Keep run/node/attempt-namespaced lifecycle UIDs, run-scoped kickback IDs, T3b as a separately named wake moment, and T6's single ownership of only `loop_iteration`.
- Keep the semantic distinction between launch history and current liveness. A runner that started and later exited must never be rewritten to `abandoned`, and `checkStartedEvidence`'s live-window probe should not define historical ledger state.
- Keep T8's explicit declaration that wake moments are not fully reconstructible in sub-issue A. This is more accurate than claiming full T1–T9 recovery and respects the Lead-ruled boundary around CommDB source-event projection.
- Keep T9's best-effort in-process hook plus durable `post_ship_finalization_claim` repair. It provides a fast path without making shadow success a production prerequisite.
- Keep the expanded B3/B4/B6/B7/B10 tests. They target the right crash, collision, rollback, and dual-finalization-path risks.

## Issues & Recommendations

1. **A non-pending CommDB row is not, by itself, durable started evidence on the Codex path.** `CodexTmuxAdapter.execute()` calls `registerCommDbSession()` before constructing/running the goal runtime, before `onThreadReady` opens the window, and before `onGoalActive` writes the commit marker. The row is adapter-created—not runner self-registration—and it is retained with a terminal status even when setup or goal execution fails. Research §F.3 and plan item 14 therefore overstate what that row proves. **Suggested fix:** define the `started` transition as `current ledger state == launch_committed` (so the marker has already been proven) **and** a durable non-pending CommDB row. Never allow a row-only `intent_recorded → started` shortcut. Add a negative Codex case where the row exists but the marker was never written; it must remain intent/unknown, not started. Keep marker+row convergence tests for both adapter orderings, and describe the conservative Codex pre-goal-failure case honestly if it cannot reach `abandoned`. Also remove `started-evidence` from plan item 10's ledger-backfill list, since §F.3 now correctly says its live probe answers a different question.

2. **The pre-commit replay rule assumes same-execution re-drive, but every fresh `start()` call allocates a new UUID.** Current `RunDispatcher.start()` has no execution-id input or reservation handshake. If the Bridge crashes after the shadow batch but before CommDB pre-registration/marker creation, the production startup reconcile can re-enter the handoff and call `start()` again with a new execution id. T1/T2 currently hard-code ordinal 1 and the same dispatch UID/key, so the new launch would idempotently retain the old row's execution id and become unrepresented. This is exactly a crash/replay window the outbox is meant to describe. **Suggested fix:** make `launch_ordinal` advance for every distinct execution id within the same `(run,node,attempt)`, regardless of whether the previous physical launch reached started; only an actual same-execution re-drive converges on the existing row. Allocate the ordinal transactionally in the writer (do not trust a precomputed orchestrator ordinal), and make T1/T2 dispatch UIDs use that returned ordinal. Alternatively have the batch return an existing uncommitted execution id and make `start()` adopt it before any production side effect. Add a crash test: batch committed, crash before pre-registration, restart allocates a different execution id, and the second physical launch gets a distinct ledger row while the logical edge remains deduplicated.

3. **T3b still omits the forward edge traversal for a wake handoff.** An Implement → QA handoff traverses the same DAG edge whether QA is newly spawned or an already-alive QA is woken for retest. T2 records `edge_traversed` only for the spawn branch, while T3b currently writes only `node_dispatched` and the QA run-node projection. The keep-alive loop therefore loses the Implement → QA edge for every retest round, and B2 would bless the incomplete table. **Suggested fix:** make the `handoff()` target-wake seam atomically append both a run/attempt-namespaced Implement→QA `edge_traversed` event and the T3b wake `node_dispatched` event, with no side-effect row. Add lifecycle-sequence assertions for both spawn and wake handoffs.

4. **T4's declared backfill source is a mutable projection, not a durable identity for repeated keep-alive completions.** A “phase session completion state” can prove the latest boundary, but the same Implement execution can complete in multiple logical attempts. Its current session row cannot uniquely reconstruct every `node_completed` fact or map each one to an attempt after later rounds proceed. This leaves T8/B4 overclaiming T4 recovery despite correctly admitting the wake gaps. **Suggested fix:** name an append-only production event id as T4's durable source (for example the persisted `session_completed`/phase-completion event) and define how it maps to the logical attempt, or explicitly mark repeated keep-alive T4 moments as another partial backfill gap. Add a two-round crash test where the first completion's shadow write is missing but the second round has already progressed. If source identity must be threaded into `onPhaseComplete`, update the affected sink/route files in §3.

5. **The API wording is still internally inconsistent.** Plan item 8 says the two separate APIs are gone and `applyWorkflowShadowBatch` handles optional side-effect transitions, while item 13 still specifies `applyWorkflowSideEffectTransition`; research §F.2 still describes separate lifecycle and side-effect transaction APIs. **Suggested fix:** choose one normative surface. If reconcile keeps a side-effect-only convenience method, state that it delegates to the same batch transaction and is never used for T1/T2/T7 creation; otherwise remove the stale method references. Align plan, research, file comments, and B6 before implementation.
