# Design Review — FLY-1232 plan.md (Round 2)
Date: 2026-07-13
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 2 substantially improves the plan: all seven Round 1 findings are represented, and the corrected fresh/retry evidence audit, attempt/launch-ordinal split, transaction rollback tests, composition seam, substrate hardening, and docs-first sequencing are sound directions. The plan is not implementation-ready yet because the normative transition table still conflicts with the current dispatch call graph and keep-alive behavior, and its `started`/`abandoned` and startup-replay contracts can record false history or miss required history.

## What's Good (Keep)

- Keep the corrected fresh/retry evidence model: `RunDispatcher.start()` does not use `LaunchClaimStore`, `recordWindow` has no production caller, and neither the pending CommDB row nor the early `session_started` event is accepted as started evidence.
- Keep the default-off construction boundary: `plugin.ts` decides whether to construct the writer, `run-infra.ts` is the real production injection surface, and an absent optional seam preserves the existing path. The externally injected `startDispatcher` exclusion is now explicit and testable.
- Keep `attempt` as the logical decision round and `launch_ordinal` as the physical-launch ordinal within that round, including immutable committed `execution_id` values and no side-effect row for a wake.
- Keep the partial unique index for one active `(project_name, issue_id)` run and the requirement to finalize that run before a later workflow on the same issue.
- Keep transaction-level fault injection, total-rollback assertions, idempotent replay assertions, loud best-effort shadow failure handling, and the real-machine flag-ON acceptance. These materially improve the safety case for touching production paths.
- Keep the four substrate-hardening items and A13. They close real fail-open API-boundary and identity-consistency gaps in the starter commit.
- Keep the corrected commit order: carrying the umbrella documents pinned to `9ed7ea69e` before cherry-picking the sentinel test makes the intermediate history buildable and bisectable.

## Issues & Recommendations

1. **T2/T7 cannot record dispatch intent at their declared owners before the side effect, and the two named StateStore APIs do not provide the composite atomicity the table requires.** `RunDispatcher.start()` allocates `executionId`, pre-registers CommDB, grants TURN when applicable, invokes `Blueprint.run()`, and then returns. `dispatchNextPhase()` therefore learns `newExecId` only after launch has already been initiated. `reconcileQaLoss()` does not itself spawn either; it re-enters `onPhaseComplete()` → `handoff()` → `dispatchNextPhase()`. Consequently T2 and T7 cannot write `intent_recorded` before launch at their proposed hook points. In addition, calling `applyWorkflowLifecycleTransition` and `applyWorkflowSideEffectTransition` separately cannot atomically create T1/T2's lifecycle events, projections, and side-effect intent, while B6 explicitly forbids that tear. **Suggested fix:** make the production `RunDispatcher` pre-launch seam the sole physical-spawn owner for T1, T2, and T7. Pass Bridge-internal shadow transition context into `start()` (including run/node/attempt/ordinal and any preceding edge), allocate the execution id, then invoke one batch/composite StateStore transaction that writes all required lifecycle event(s), projections, and intent before CommDB pre-registration/`Blueprint.run()`. Alternatively expose an execution-id reservation API that gives the orchestrator a true pre-launch transaction boundary. Update the transition table, T7 owner description, API shape, and B6 tests accordingly.

2. **The deterministic event IDs collapse valid keep-alive rounds, and the table omits the QA retest wake.** The starter schema makes `workflow_run_event.event_uid` globally unique. With keep-alive, the same Implement and QA executions participate in multiple attempts, so `complete:{executionId}`, `complete:{qaExecId}`, and `edge:{fromExecId}:{toNode}` deduplicate later legitimate completions/edges. `kickback:{issueId}:{round}` also collides when a later workflow run reuses the same issue and round. Separately, T3 covers the QA-FAIL → Implement wake in `runFailFlowKeepAlive`, but not the subsequent Implement → already-alive QA retest wake in `handoff()`; that is another `node_dispatched` lifecycle moment with no side-effect row. **Suggested fix:** namespace every lifecycle UID by `run_id` and logical attempt (and use the durable source event id, such as the QA verdict `eventId`, where available), for example `run:{runId}:complete:{node}:{attempt}:{executionId}`. Add a distinct transition row for the `handoff()` target-wake branch, define which attempt rows T6 creates, and add acceptance cases for two rounds reusing the same executions plus two separate runs of the same issue.

3. **The revised `abandoned` evidence can still turn a successful start into false history, and no adapter-neutral live observation point is specified.** `checkStartedEvidence` proves only “non-pending CommDB row plus a window that is live now.” Its own contract says a non-pending dead row proves a runner once existed. Therefore `commit marker + tmux_dead` is not positive evidence that launch was abandoned; it can be a runner that started and exited before reconciliation observed it. Likewise a generic `Blueprint.run()` failure can occur after the runner started. This is especially important because `started` is terminal. There is also an adapter ordering gap: `TmuxAdapter` invokes `onTmuxWindowCreated` after writing the marker and registering CommDB, while `CodexTmuxAdapter` opens the window/calls that callback before `onGoalActive` writes the marker. A one-shot callback reconcile can therefore miss Codex, and startup-only reconciliation may run after the window is gone. **Suggested fix:** restrict `abandoned` to explicit pre-start/pre-commit failure evidence; keep commit+dead as `launch_committed`/unknown unless a durable historical-start fact exists. Specify an adapter-neutral mechanism that observes the live state after the marker (for example a bounded best-effort post-callback poll, or an explicit committed callback). If that requires adapter/Blueprint changes, update the approved file scope first. Add tests for both adapter orderings, a post-start `Blueprint.run()` failure that must not abandon, and a runner that exits before a later reconcile.

4. **T8 promises full lifecycle backfill but does not define durable sources for most T1–T9 facts.** Step 4 says every row includes a persistent source identity and reconciliation evidence, but the table has neither column. The evidence named in item 10—CommDB row, commit marker, and started evidence—can reconcile dispatch state, not `node_completed`, `edge_traversed`, QA PASS, `loop_iteration`, or finalization. Replaying formulas alone is insufficient, especially across multiple keep-alive rounds where current session state loses intermediate history. **Suggested fix:** add explicit durable-source identity and reconcile-precedence columns for every transition. Map existing same-database facts where available (for example QA verdict `eventId`, persisted fix-round/belt records, phase session/event records, and `post_ship_finalization_claim`) without pulling the Lead-ruled CommDB source-event projection from sub-issue B into A. For any transition that cannot be reconstructed from an existing durable source, state that limitation rather than claiming T1–T9 backfill, or add the minimal A-owned durable observation required. Extend B4 with a crash-after-production-source/before-shadow-write test for each reconstructible transition.

5. **T9 has no concrete owner in the proposed file changes.** The plan assigns T9 to a finalization `onFinalized` seam and lists `phase-orchestrator.ts` as carrying T2–T9, but finalization lives in `post-ship-finalization.ts`, and `makeFinalizeThreeStagePhases` is constructed from more than one composition surface. Neither `post-ship-finalization.ts` nor the affected construction sites appear in the file list. A hook on only the plugin's shared closure would not cover every production finalization route. **Suggested fix:** choose one authoritative T9 design and name it precisely: either derive T9 in the dedicated shadow reconciler from the durable `post_ship_finalization_claim`, or add a best-effort optional hook to the single serialized `runPostShipFinalization` path and retain claim-based startup repair. Update the transition owner, failure/replay behavior, file list, and B10 to test external-merge and in-process finalization paths.
