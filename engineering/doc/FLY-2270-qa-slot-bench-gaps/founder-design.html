FLY-2270 · 529 房台架缺口:报告链隔离发布 + Bridge 临时目录固定

设计交付 · 2026-09-03 · 来源:FLY-2215 QA 在 529 隔离房做真机验收时发现的两处台架缺口
文档:engineering/doc/FLY-2270-qa-slot-bench-gaps/{exploration, research, plan}.md · 本页只讲结论与取舍,细节在 plan。

一句话结论

给每个测试房配一个只在本机跑的「假 Vercel」,让报告发布链在隔离房里真的走通;同时把测试 Bridge 的临时目录钉死在房间自己的文件夹里,不再看谁来启动它。生产 Bridge 一行行为都不变。

名词一次讲清:529 房(529 是 Linear 单号,指用 test-deploy.sh 临时搭起来、跑完就拆的隔离测试环境;一个这样的环境叫一个 slot,每个 slot 有自己的 Discord 频道、端口和文件夹);Bridge(Flywheel 的中枢进程,负责接 Discord、派 runner、托管报告);runner(Bridge 派出去干活的 AI 会话);台架(test harness,指搭测试环境的那套脚本,它本身不是被测对象)。

缺口今天本设计
报告链在隔离房验不了测试 Bridge 没有发布凭证,publish-report 直接回 501「不可用」;而且只要给它凭证,它会把报告写进生产的报告目录并重部署生产站点slot 自带一个只听 127.0.0.1 的「假 Vercel」,Bridge 用 slot 自己随机铸的凭证往它上面发布;报告目录、截图目录全部落在 slot 文件夹里;链接能打开、能截图、能投到 529 频道
从 runner 环境起不来 Bridgerunner 的临时目录路径 89 个字符,Bridge 启动器 tsx 在它下面建通信管道,路径超过 macOS 的 104 字节上限 → 报 EINVAL测试 Bridge 的临时目录固定为 /tmp/flywheel-test-slot-N/tmp(约 30 字节,加上管道文件名也只有 51 字节),三种启动模式同一来源,与谁来启动无关

不动的:publish-report 命令本身、报告保留/过期规则、Discord 投递、生产 Bridge 的任何默认行为。生产代码只多了「一个带默认值的可选参数 + 两个只在开关设了才走的分支」;拆房脚本零改动。

核心流程:报告在隔离房里怎么发出去

图 1 · 黄框是 slot 自己的文件夹;六步都在本机;红框是生产资源,与 slot Bridge 之间只有一条「零写入」的虚线。

  • 假 Vercel(stub,指用最小代码模仿一个外部服务的替身):一个小 Node 进程,只实现 Bridge 真正会调用的两个 Vercel(报告托管服务商)接口——「上传一组文件」和「查部署状态」——并把上传的页面按原路径静态托管出来。它只认 slot 自己铸的那把 token(访问凭证),拿别的 token 来一律 401。
  • 它的寿命就是 Bridge 的寿命:Bridge 的启动命令前面套一个 30 行的包装脚本——先起假 Vercel、等它报「就绪」、把地址放进环境变量,然后在同一个进程号里变身成 Bridge。假 Vercel 每半秒看一眼自己的父进程,Bridge 一死它就自退。所以不需要任何 pid 文件、所有权核对、拆房步骤:既有的「拆房杀 Bridge」和「房内重启 Bridge」自动把它一起带走。假 Vercel 起不来,包装脚本就报错退出、Bridge 根本不启动,原因写在 bridge.log(本机已实测:父进程退出后子进程 250 毫秒内感知并退出)。
  • Bridge 侧的开关:一个新环境变量 FLYWHEEL_REPORT_HOST_OVERRIDE_URL。不设 = 今天的生产路径,一字节不变;设了就把「上传去哪」和「链接长什么样」都指到假 Vercel。它只接受一种写法 http://127.0.0.1:端口(回环地址,即只有本机自己能访问的地址;连 localhost 都不收),写成别的 Bridge 在启动的第一步就拒绝——所以这个开关不可能被用来把生产凭证送到任何远端。开关生效时,另一条老的「通用 HTML 发布」接口(/api/publish-html)会明确关闭并回 503,文案直接告诉调用方改走 publish-report;这个关闭不是旋钮,只由启动时有没有这个变量决定,拆房即解除。
  • 报告目录:测试 Bridge 与测试 Lead 都拿到 FLYWHEEL_REPORTS_DIR=slot/state/reports,注册表、页面文件、截图(previews,投 Discord 前的截图暂存目录)全部落在 slot 里;这一条对所有启动模式都注入,不只是开了报告链的那种。
  • QA 怎么验:test-deploy.sh 输出里直接给出假 Vercel 地址、token 路径和一条可复制的验收命令;跑完后 529 slot 频道收到一条消息,链接 curl 得到 200,生产报告目录的修改时间与截图数量前后不变。

图 2 · 从操作者视角的时间线:1–8 步是装房(其中 4–6 是包装脚本起假 Vercel 再变身 Bridge),9–16 步是发一份报告,17 步是负向对照,18–19 步是拆房时假 Vercel 自退。

第二个缺口:为什么从 runner 环境起不来,怎么修

图 3 · 左边是今天的故障链,右边是修法。

  • TMPDIR(临时目录环境变量,程序放临时文件的地方)在 runner 环境里是 ~/.flywheel/runner-state/<36 位 id>/browser-tmp,恒为 89 个字符——这是另一张单(FLY-766)为了给每个 runner 的浏览器归属所用的契约,不能改。
  • tsx(启动 TypeScript 程序的工具,测试 Bridge 用它起)会在 TMPDIR 下建一个 IPC socket(进程间通信用的本地管道文件):TMPDIR/tsx-501/<pid>.pipe,合计 108 字符;macOS 规定这类路径最长 104 字节,于是 EINVAL(参数无效),Bridge 没起来。
  • 今天只有 --generalized 模式有一个「太长就退回 /tmp」的启发式,而且它按 tmux 的路径长度判,tsx 的路径碰巧比它短 1 个字符才没事;另外两种模式什么都没做。FLY-2215 QA 撞的就是这个洞。
  • 修法:不再猜长度,直接把测试 Bridge 的 TMPDIR 固定为 slot/tmp,放进三种模式共用的那个环境数组里,一处改三处生效;启发式函数和它的测试一起删掉(单一真源)。顺手修正了「Bridge 用 runner 的浏览器临时目录当自己临时目录」这个错位。

关键取舍与放弃的方案

方案结论为什么
报告链:给 slot 一个独立的真 Vercel token + 独立项目放弃① 注册表每次新建都会随机起一个新项目名,一房一个新 Vercel 项目,账号被污染;② 吃全局每日 100 次部署配额(FLY-2283 已经因为配额耗尽拿到过 402);③ 要往 .env 再放一个真秘密;④ 同一个 api 域名只靠 token 不同,拿不出「slot 绝不碰生产项目」的结构性证据;⑤ 依赖外网
报告链:本地假 Vercel采用零外部依赖、零配额、零真秘密;链接真能打开、真能截图;生产路径开关未设时字节不变;开关只认回环地址
报告链:只桩掉「上传」,链接仍指向 vercel.app放弃链接打不开、截图必失败,只能验「发了一条消息」,不算端到端
假 Vercel 的生命周期:独立守护进程 + 三份所有权文件(pid / 身份 / 端口)+ 拆房专用步骤(评审第 1–3 轮的形态)放弃Codex 每一轮都在这一处抓出新的阻塞项:房里有 11 条「删锁就退出」的路径会让它活过锁、启动瞬间没有任何元数据、拆房脚本的「全部」模式会吞掉失败……这是「一个与 Bridge 不同步的进程」天然带来的,补不完。Lead 裁定改向:删机制而不是加机制
假 Vercel 的生命周期:绑在 Bridge 进程上(包装脚本 + 看父进程自退)采用零新增清理步骤、零锁交互、零元数据核对;拆房和房内重启的既有路径自动覆盖;起不来就 fail-loud
报告链:让 Bridge 自己托管页面放弃Bridge 是被测对象;往生产代码里塞只为 QA 存在的 HTTP 面,与「生产路径不变」冲突。假 Vercel 放在 scripts/lib/,与既有的 runner stub 是同一类台架代码
临时目录:把「太长就退回 /tmp」的启发式推广到三种模式放弃仍依赖调用方环境;判据是 tmux 的长度,tsx 靠巧合;/tmp 全机共享,slot 之间不隔离
临时目录:固定 slot/tmp采用恒短、不看调用方、拆房时顺手清掉、一处改三处生效
临时目录:先编译再用 node 起,不用 tsx放弃改变了被测字节形态,与 529 房「用当前仓字节装房」的原则冲突;tsx 本身也没有关闭管道的开关
一个刻意的「不起」:假 Vercel 只在 slot 有 API token 的模式(--generalized 或 TEST_REPLY_BY_ISSUE=1)才起。默认模式下 Bridge 的报告接口本来就按设计回 503(没有 API token 就不开这个面),起了也没用;默认 slot 保持原字节路径是台架一贯的原则。
评审过程本身也是一次「只删不加」的练习:方案从第 1 轮的 12 条意见收敛到第 4 轮,中间第 3 轮改向,把一整套所有权机制删掉后问题才真正收口。

诚实边界:这个设计做什么、不做什么

做

  • 让「发布 → 托管 → 截图 → 投 Discord」整条链在 529 房可以端到端验,并给出可复制的验收配方与负向对照。
  • 让从 runner 环境不改任何环境变量直接跑 test-deploy.sh 能起测试 Bridge。
  • 把生产凭证挡在 slot 之外:三条启动边界先清掉 VERCEL_TOKEN 再注入 slot 自己的;开关只认回环地址;假 Vercel 只认 slot token。

不做

  • 不改生产 Bridge 的任何默认行为,不加定时器、不加 feature flag、不加新抽象层、不加任何新的可调开关(端口 0 和就绪文件都是实现细节)。
  • 不改拆房脚本 test-teardown.sh:假 Vercel 随 Bridge 进程生灭,不需要它知道。
  • 不动 runner 那个 89 字符的临时目录(FLY-766 的浏览器归属契约)。
  • 不改默认模式下报告接口的 503。
  • 本页是设计,不是验收:真机 529 验收由 QA 节点执行,截图在 runner 沙箱可能因浏览器权限降级为纯链接投递——判据是「消息到达 + 链接 200」,截图是加分项。
  • runner 会话不继承 slot 的报告目录变量(评审第 1 轮核实:runner 的环境是白名单构造的)。这是有意的:runner 只有「ingest」级凭证,命令行工具已强制它只能 --publish-only 拿链接;真正投递到 Discord 的是 Lead 或 QA 操作者(master 凭证)。将来若要 runner 自己截图投递,必须显式改 runner 的环境合同,不在本单。

回滚

无数据迁移、无 schema 变化;revert PR 即回到今天的「501 + 继承调用方临时目录」。部署走普通 merge,等 00:00/12:00 班车,不需要手动重启。
