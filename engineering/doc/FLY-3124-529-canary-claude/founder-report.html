1 · 为什么现在不写 marker

金丝雀（canary）是一项很小、隔离运行的探针，用来确认一条传输链路真的把消息送到正确的执行体。

TURN是服务器授予某个工作流节点的独占写入权。当前结果是 yours，所以 design 文档可以写，但 TURN 本身不包含 marker 内容。

执行体（execution）是一次有独立身份的 agent 运行。当前执行体是 Codex design；输入没有 exact marker，root probe.txt 也不存在。

结论：承认真实 TURN，拒绝伪造另一条 Claude execution 的收件证据。

2 · 核心流程

phase（阶段）是工作流中职责固定的一段。Design 只交付文档和审查；downstream 节点先取得自己的 TURN，再判断当前原生输入是否真的包含 exact marker。

图中所有红色出口都是“停止写入并报告”，不是失败后猜一个 marker。

3 · 数据与证据模型

provenance（来源证据）说明一条 marker 是谁、在什么 execution、通过什么指令送来的。它必须和 TURN、exact line、local commit SHA 相互印证。

身份execution id、vendor 与 phase 防止拿别人的回执充数。
授权TURN 只回答“谁能写”；原生 instruction 才回答“写什么”。
内容marker 逐字保留，只允许明确 grammar 和 printable ASCII。
审计complete-line count、staged diff、commit tree 与 structured receipt 相互校验。

4 · 关键取舍与拒绝方案

  1. 采用：TURN + exact instruction + 条件式 append。 没有 literal 就不写；收到后只追加缺失的完整行。
  2. 拒绝：从 issue title 推导 Claude BOOT / R4 marker。 那些文字绑定外部 driver 创建的另一条 Claude execution。
  3. 拒绝：自定义 owner + 时间戳 marker。 可读但没有发送方，不满足“requested marker”的逐字合同。
  4. 拒绝：让 design 直接写 probe。 会混淆阶段职责，让设计审查绑定到已经发生的实现。

5 · 诚实边界

DAG（有向无环工作流）把 design、implement、QA 等步骤按依赖连接起来；节点不能替 orchestrator 派发后继或扩大权限。

本设计会做到：三份设计文档、两张本地渲染图、设计审查、Founder HTML，以及一份可执行的 downstream append 合同。

本设计不会做到：创建或修改 probe.txt、声称收到 Claude native mail、改产品代码、创建 PR、请求 ship、merge 或部署。

若下游没有 exact marker，它只能报告 TURN 并等待；若收到 marker，commit 必须只含 probe.txt，且保持 local-only。
