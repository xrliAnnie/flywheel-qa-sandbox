一句话总结

QA（测试员 agent）交判决时必须附一份判据清单：每条验收项都要标明「过了 / 没过 / 没测（写原因）/ 沿用上一轮」。清单不合格，命令行和服务端都直接拒收；下一轮复验开局，系统自动把上一轮清单发给 QA，没被改动碰到的通过项直接沿用，不重跑。

另外新增一条：529 流程演练（在隔离的测试房间里把「设计 → 实现 → 测试 → 审批」整条流程真跑一遍）按「改没改流程」判，不按「改没改 Discord」判。交 PASS 必须带「跑了」或「豁免 + 理由」。

你提的要求机制怎么保证
一轮测全，别碰到第一个问题就打回交 FAIL 时只要有一项既没测又没写原因，拒收
复验只验改动部分系统把上一轮清单发给 QA；通过项用「沿用」引用上一轮编号即可
实现体修问题要补相邻路径写进实现体的修复指令和角色说明；交卷时列出补了哪些
别再因为「没改 Discord」跳过 529豁免理由里提到 Discord 或为空，拒收

核心流程图

下图是一次「FAIL → 修复 → 复验 PASS」的完整过程。名词解释：Bridge 是 Flywheel 的调度服务，负责在各个 agent 之间传话和记账；账本是一张只能追加、不能改的表，记录每一条被系统真正采纳的 QA 判决；ref 是每条判决的编号，下一轮引用它。

关键点：检查做三遍，用的是同一份规则代码——命令行先查（最快给反馈）、Bridge 收到时再查、登记进账本的那一刻最后查一次（防止两条判决同时到达时互相踩）。

数据结构

清单是一个 JSON 文件（一种通用的结构化文本格式）。每条判据有五种状态之一。

状态含义必须附带
pass这轮测了，通过—
fail这轮测了，没通过证据（预期 vs 实际）
not_run这轮没测具体原因（写「无」「略」「TBD」这类占位词会被拒）
carried上一轮已通过，这轮改动没碰到，沿用上一轮判决的编号 + 证据；只能引用紧邻的上一轮
merged这条判据并进了另一条并入哪一条；没通过的项不能并进通过的项来「洗白」

529 流程门

根因：原来的规则写的是「改了 Discord 才跑 529」，QA 照字面执行，于是「没改 Discord 所以没跑」。现在改成：改到流程就跑；是否改到流程由 QA 自己判断，拿不准就跑。

豁免类别含义
docs_only只改了文档
ci_config_only只改了 CI（自动化检查）配置
tests_only只改了测试文件
no_flow_changeQA 判断没改到流程——必须写明改了什么、为什么运行中的流程不受影响

这道门按项目开关（配置键 qa.e2e_529_flow_gate），读的是项目主干上的配置，被测的 PR 改不了它；配置写坏时按「开着」处理。

关键取舍与否决的方案

问题选了什么否决了什么，为什么
「上一轮」怎么认定新建账本，按被采纳的先后顺序排沿用现有的「判决事件编号」字段：重新指派 QA 或重开时它会被清空，上一轮就丢了
规则放哪一份共享代码，三处调用命令行和服务端各写一份：迟早不一致
要不要加开关慢慢放量不加，上线即强制灰度开关：你要的是「必须做成机制」，开关等于留了后门。回滚有分步顺序
豁免理由谁来判机器只拒空理由和 Discord 理由，其余信 QA机器判断理由是否充分：做不准，而且你明确说 QA 可以自己判断
Discord 理由怎么识别理由里出现 Discord 一词就拒识别否定句式（如「没改 Discord」）：换个说法就漏，宁可严一点
529 门的开关放哪项目主干配置QA 角色说明文件里的标记：系统读它的时机晚于会话创建，会有先后竞争
豁免转实跑「跑了」和「豁免」视为同一个槽位的两种形态，可互换按普通判据处理：上一轮豁免后这轮想实跑会被规则卡死（Codex 评审第 5 轮发现）

诚实边界：做什么、不做什么

做不做 / 做不到
拒收「没测又没写原因」的 FAIL不判断 QA 写的原因是否合理——原因原样显示给 Lead（负责管理 agent 的主管 agent），由人复核
复验时自动发上一轮清单系统不看代码改动；「这项真没被改动碰到」靠 QA 判断
PASS 必须带 529「跑了」或「豁免」本仓库是测试沙箱，没有 529 房间命令，也没有演练记录存储：房间号和记录号只校验格式，填假的机器发现不了。账本和 Lead 通知会标「未核对记录」
拒收提到 Discord 的豁免理由会误伤正当理由（如「只改了 Discord 渲染的单测」），QA 需换个不提 Discord 的说法
上线即对新判决生效上线时已在运行的 QA，第一次交卷会被拒一次（拒收信息里带示例）
—房间超时上限提到 3 小时、真 runner 负控：依赖房间基础设施，本仓库没有，不在本设计内
—判决已采纳但叫醒实现体失败时不会自动重发：这是已有缺口，本次不修
