# Design Review — FLY-1281 plan.md (Round 1)

Date: 2026-07-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

The proposed architecture is feasible and the plan preserves several important decisions from the approved brainstorm, especially the v1/v2 split, typed enrollment, separate output credentials, and the standalone D2 acceptance group. It is not implementation-ready yet: the current code cannot admit generic executions through the described API, the node-id write point is incorrect, completion replay can permanently swallow a pre-output completion, and review/product handoff behavior crosses contracts intentionally deferred to sub-issue D.

## What's Good (Keep)

- Keep the schema-version dispatcher with the v1 validator body and existing three engineering seeds unchanged; this is the strongest foundation for the required default-off byte compatibility.
- Keep D2 as its own acceptance group, including the no-QA `qa_exempt` policy claim and explicit negative matrices.
- Keep the typed-enrollment discipline (`claims_read_enrolled` plus immutable execution binding) and the face-by-face legacy/enrolled test pairing. Do not infer enrollment from a nullable session column.
- Keep output capabilities separate from `workflow_submission_credential`; its existing family CHECK is correctly limited to `qa_verdict` and `review_verdict` and must not be rebuilt.
- Keep strict, snapshot-pinned `agent_file` content, capability-gated Blueprint construction, fail-closed unknown node IDs, and the S11–S16 tests.
- Keep selection facts on the run row rather than changing the append-only `workflow_template_audit.action` CHECK.
- Keep the three new seeds default-off and non-dispatchable until their downstream capability owners are available.

## Issues & Recommendations

1. **There is no generalized execution-admission contract.** `StateStore.admitWorkflowExecution` currently requires a decision `family`, only accepts `qa_verdict`/`review_verdict`, updates stale-attempt authority only for the literal node ID `qa`, and always mints a submission credential. `RunDispatcher.start` calls it only for `shareParentBranch && role === "qa"`; `RetryDispatcher.dispatch` does not call it. Consequently, a generic node with no output cannot be admitted, an output-only generic node would need a fake verdict family, and retry can spawn without a new binding/credential. Replace Step 4b's separate output-admission call with one atomic generalized pre-spawn API that validates the v2 flag, typed run, snapshot membership, node type/capabilities, and current per-node attempt; writes `workflow_run_node` plus immutable `workflow_execution_binding`; revokes superseded tickets; and conditionally returns zero, decision, output, or both credentials. Invoke it before CommDB registration/Blueprint launch on both fresh and retry paths. Resolve vendor/model/effort before this call, pin the resolved values in the snapshot/execution projection, and apply `manifestReviewFamilyOk` to the actual resolved producer/reviewer families—not manifest vendor intent. Thread the separate output secret through `BlueprintContext`, `packages/core/src/adapter-types.ts`, `TmuxAdapter`, and `CodexTmuxAdapter`, with OFF/non-output tests proving no new env entry.

2. **The proposed `sessions.workflow_node_id` write point does not exist at the required time.** `RunDispatcher` does not own `StateStore`, and the session row is created later by `DirectEventSink.emitStarted` or the HTTP `session_started` branch. Persist the node ID at those two authoritative sinks by resolving it server-side from the already-committed execution binding; never accept it from the runner event payload. Add it to `SessionUpsert`, `Session`, the fresh DDL/add-column migration, both INSERT lists, and `rowToSession`, make it set-once, and have the enrolled resolver verify session value = binding value = a node in the pinned snapshot. The face matrix should also name the new enrolled-only StateStore queries, the `issue-display`/refresher derivations and plugin fallback, completed and failed sink mappings, `actions.ts` retry request construction, post-ship collection by binding, and startup collectors. Existing phase SQL, `normalizeChatThreadRole`, and three-stage display/finalization helpers should remain untouched for legacy rows.

3. **The v2 output contract and storage invariants are under-specified.** Step 1 never adds `produces_output` to the v2 node exact-key/type contract, and no per-node payload schema, schema version, canonical serialization, or byte limit is defined even though Step 4 promises schema/size validation. Add an explicit generic-node output contract to the manifest and resolved snapshot, reject output submissions for non-producing nodes, and define digest canonicalization. `workflow_node_outputs` should have the same composite FK to `workflow_execution_binding` as the credential. A mutable `promoted` bit is also at odds with the stated append-only pattern and is not protected by a uniqueness constraint; moreover, `workflow_run` only has `current_qa_attempt`, so “read workflow_run.current” cannot authorize generic attempts. Prefer immutable output rows plus a new `(run_id,node_id) -> current attempt/output` promotion table (or specify an equally strong transactional alternative), with one-current-output uniqueness and explicit per-node attempt authority. Spell out durable request ID/submission digest receipts, old-live-ticket revocation, exact replay, and same-key/different-digest rejection.

4. **The completion guard is ordered too late for replay safety.** The HTTP `/events` route calls `insertEvent` before any `session_completed` validation and immediately returns success for the same event ID; `DirectEventSink.emitCompleted` also inserts first. If the new output check rejects after insertion, submitting the output later and replaying the complete marker will be treated as a duplicate forever. Introduce one shared enrolled-completion authorizer and call it before `insertEvent`, metadata writes, FSM changes, or orchestration in both sinks. Missing output must produce a retryable failure that leaves the complete marker intact. If event insertion and status/handoff cannot be committed atomically, add a durable pending-completion receipt/outbox so a crash after event insertion is replayable. Test at least: complete-before-output then output then same-ID replay; crash after output commit; crash after completion receipt but before session transition; and Bridge restart through the marker reconciler.

5. **The review node's executable semantics do not match the existing decision substrate.** `workflow-decision-routes.ts` currently requires durable QA roles, hardcodes producer node `implement`, resolves a git head, emits `qa_result`, and calls `PhaseOrchestrator`. The existing `review_verdict` family contains approval predicates only; there is no failure predicate that can represent `review_fail`. Product review additionally requires the trusted materialized docs head, which the approved scope assigns to D. In C, keep review schema/registry/prompt representation but make review execution admission explicitly fail closed until the D materializer/subject resolver is present. If C is intended to own a reusable review outcome substrate, define a credential-authenticated PASS path to `design_review_approved` and a replay-safe FAIL receipt/run event that consumes the ticket without adding a fake claim or changing the existing claims CHECK, plus a concrete CLI command. Do not route review through the QA-only endpoint or orchestrator. Cross-family checks must use server-resolved families at admission and submission.

6. **D2 is not consistently capability-driven, and `qa_exempt` is not made atomic/idempotent.** Step 1 describes all combinations of `design/generic/review/gate` as no-code, while the approved rule says omission of QA is legal only when every node has write capabilities off. The registry is also supposed to mirror today's behavior, where Design writes/commits on the shared branch. Define `nodeTypeWritesCode` solely from the approved capability predicate and test at least one non-`implement` writer without QA; do not maintain a parallel type allowlist. For an eligible no-QA run, write exactly one `bridge_policy/qa_exempt` claim in the same transaction that inserts the run and final snapshot, using the digest of the snapshot including loaded agent content, a deterministic authority ID, and actor/reason evidence. The existing `appendWorkflowSystemClaim` is a separate transaction and does not deduplicate `authorityId`, so merely calling it after materialization leaves a crash gap and duplicate-replay path.

7. **Template selection is neither callable as specified nor connected to launch.** The proposed resolver signature lacks `runId`, `issueId`, override, canonical project root, and enrollment inputs, yet says it calls `materializeWorkflowRun`; `/api/runs/start` currently accepts no task category/template/reason and goes straight into three-stage entry resolution. Define the authoritative caller and request contract, validate Lead and founder-override authority server-side, run selection before legacy three-stage routing, atomically materialize a matched run, and carry `{runId,nodeId,attempt}` through `StartRequest`. Reconcile this with the existing `WorkflowShadowWriter`: a matched materialized run must be reused rather than shadow-duplicated, while the promised null/naked path must either suppress shadow-run creation or explicitly revise “does not create a run” to “does not create an enrolled/template run.” Add combination tests with claims shadow write ON.

8. **The default-off flag is aimed at the wrong mutation surfaces and lacks a flag-combination policy.** `workflow-template-routes.ts` is read-only; the real authoring mutations are `StateStore.createWorkflowTemplateRevision`, `publishWorkflowTemplate`, `importWorkflowTemplateSeed`, and `materializeWorkflowRun`. Boot currently calls `importBundledWorkflowSeeds(store)` unconditionally, and seed insertion hardcodes `schema_version = 1`. Name the exact env variable/helper and inject the resolved flag into these authoritative seams; publish must inspect the target revision's stored schema version. Define its relationship to `FLYWHEEL_WORKFLOW_CLAIMS_WRITE`, `FLYWHEEL_WORKFLOW_CLAIMS_READ`, and `FLYWHEEL_WORKFLOW_FORCE_LEGACY`: v2 admission should fail unless all required claims paths are available, and an already-enrolled v2 run must pause/fail closed when generalized support is disabled—never fall into legacy normalization. OFF sentinels should exercise these real methods and both launch paths, not a nonexistent mutation route.

9. **Strict agent loading and snapshot versioning need an owning service boundary.** `StateStore.materializeWorkflowRun` currently has no project-root input, while the canonical root lives in `ProjectEntry`; filesystem reads “inside a SQLite transaction” do not by themselves solve TOCTOU. Resolve the trusted project root in the Bridge/service layer, use the extracted realpath/symlink-containment helper, read and truncate once, compute a content digest, and pass the verified content into the transaction that pins the final snapshot. Preserve the old Blueprint caller's null-warning fallback while the new admission caller throws. Also update the current hardcoded snapshot `schema_version: 1`, `LoadedWorkflowSeed` types, and `importWorkflowTemplateSeed`'s hardcoded revision schema version so v2 is actually stored and reloaded as v2. Add digest tests proving file changes after materialization do not affect dispatch and frontmatter remains inert text.

10. **Step 3/8 crosses the explicit C→D sequencing boundary.** “Startup reconciliation replays stranded nodes from the snapshot” and an E2E that advances handoff require snapshot-driven orchestration, which the scope assigns to D; product review also requires D's docs materializer. In C, deliver the node-ID/query/retry/output/completion substrate and a startup collector that can identify and loudly hold generalized stranded work without dispatching a successor. Narrow the C E2E to selection → materialization → direct generic-node admission → output submission → completion authorization → restart/read/replay, and assert that automatic successor/review dispatch remains unreachable. D should own edge interpretation, successor spawning, review subject materialization, and full-chain handoff E2E.

## Verdict

CHANGES REQUESTED — address items above
