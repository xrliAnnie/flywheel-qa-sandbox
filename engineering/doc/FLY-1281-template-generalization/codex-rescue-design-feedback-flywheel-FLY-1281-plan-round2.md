# Design Review — FLY-1281 plan.md (Round 2)

Date: 2026-07-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

Draft v2 materially addresses all ten Round 1 findings and is much closer to an implementable C/D boundary. The remaining blockers are concentrated in the new generalized completion state machine, trusted dispatch identity/runtime persistence, output-current invariants, and `/api/runs/start` authority; as written, these gaps can still corrupt an enrolled run or make a valid generic completion unrecoverable.

## What's Good (Keep)

- The unified pre-spawn admission direction is correct: one transaction owns the run-node projection, immutable execution binding, ticket revocation, and conditional credential issuance, and both fresh and retry launches are intended to pass it before CommDB/Blueprint side effects.
- D2 is now capability-driven rather than keyed only to `implement`; explicitly treating `design` as a writer and testing `design` without QA closes an important policy hole. Writing the deterministic `qa_exempt` claim in the snapshot-pinning transaction is also the right atomicity boundary.
- The C→D split is now honest. C represents and validates `review`, but refuses review execution and successor interpretation instead of fabricating verdicts or routing them through QA infrastructure.
- The output design correctly separates output submission from completion, uses hash-only one-time credentials, binds submissions to the immutable execution binding, records durable replay receipts, and retains output across Bridge restart.
- Resolving `workflow_node_id` from the server-owned execution binding rather than runner payload is the right trust boundary. The explicit eight-face touchpoint matrix and per-face legacy/unknown-node tests should remain.
- The strict agent-file read belongs in the Bridge/service layer. Reading, truncating, hashing, and then passing verified content once into materialization removes the earlier filesystem/transaction and TOCTOU ambiguity while preserving Blueprint's legacy fallback behavior.
- The flag is now aimed at real authoring/materialization and launch seams, the later-disable behavior is fail-closed, and the E2E is appropriately narrowed to C's responsibilities with an explicit no-successor-dispatch assertion.

## Issues & Recommendations

1. **Generalized completion still has two competing terminal authorities and no atomic node-completion commit.** A no-write generic runner is told to call `complete --route no_code`, but current `Blueprint.runInner` still derives success from Git/DecisionLayer (`commitCount > 0` in the fallback) and `emitTerminal` subsequently sends a DirectEventSink completion/failure. That later zero-commit result can overwrite or conflict with the HTTP completion. In addition, Step 4e only checks output presence: it does not validate that the submitted route equals the snapshot capability's `completion_route`, and it never marks `workflow_run_node` completed or appends a deterministic `node_completed` run event. Consequently the stranded collector cannot reliably distinguish completed from stranded nodes. Make the explicit generalized `complete` call the server-owned terminal authority: atomically record a deterministic completion receipt/run event, transition the bound run-node attempt, and apply the session projection without dispatching a successor. The later Blueprint terminal emission must consult that receipt and no-op; if no receipt exists, it must hold/fail closed rather than translate zero Git commits into a legacy decision. Suppress legacy whole-issue “completed” side effects for an intermediate generalized node. Add collision tests for HTTP-complete followed by Blueprint success/failure, route mismatch, missing receipt on process exit, and exactly-once node completion.

2. **The replay fix stops before `insertEvent`, but the existing post-insert crash remains unrecoverable.** In `event-route.ts`, `insertEvent` commits before the session mutation and a repeated `event_id` returns immediately as a duplicate. A crash or exception after that insert therefore cannot be repaired by replaying the marker; Step 4e's claim that the existing sink semantics introduce no relevant half-write window is incorrect. Add a transaction/receipt-outbox boundary for generalized completion, or make duplicate receipt handling re-drive the idempotent session/run-node projection instead of returning early. The acceptance group must include “event/receipt committed, crash before session/run-node projection, same-ID replay converges,” not only “authorization passed, crash before insertEvent.” Direct and HTTP sinks should exercise the same repair primitive.

3. **The dispatch contract does not yet carry a trusted generalized identity or a defined runtime projection.** `/api/runs/start` selection materializes a run, but the proposed public `StartRequest` fields do not provide an internal `{runId, nodeId, attempt, snapshotDigest}` handoff. Today `RunDispatcher.start` synthesizes the shadow node from `sessionRole` and defaults it to `main`, so merely “reusing” the materialized run would write the wrong node into that run. The retry hook is also placed at `actions.ts`, while the final execution ID and resolved `runnerSpawn` vendor/model/effort are created inside `RetryDispatcher.dispatch`; admission cannot correctly bind or pin them one layer earlier. Finally, neither `workflow_run_node` nor `workflow_execution_binding` has columns for the promised resolved runtime projection, and the storage summary defines no new object for it. Define a Bridge-internal generalized execution context returned by selection and thread it through RunDispatcher/RetryDispatcher, Blueprint, and WorkflowShadowWriter; never accept it from the HTTP body. Put retry admission inside `RetryDispatcher.dispatch` after ID/runtime resolution and before CommDB. Specify a new immutable runtime-projection table (or another no-existing-table-change design) for vendor/model/effort/family/capability digest. Admission must require attempt 1 on the unique graph start for fresh dispatch, exactly max+1 (or exact same-execution replay) for a retry of that same node, and must reject graph-successor admission in C. Add a shadow-ON assertion that no `main` node is created. Also remove the required “both credentials” production shape or define a test-only registry seam: under the proposed closed registry, only `generic` may produce output and it is not a QA verdict emitter, so that shape is currently unreachable.

4. **The output-current schema permits ambiguous or stale authorization.** `workflow_node_outputs` lacks `UNIQUE(run_id,node_id,attempt)`, so multiple immutable outputs can exist for one attempt. The current table is described as both immutable and CAS-advanced, although a `(run_id,node_id)` pointer must be mutable (or replaced by an append-only promotion ledger). The `attempt >= current` rule also permits a different output to replace the pointer at the same attempt, and the pointer does not state an FK/consistency rule proving that `output_id` belongs to the same run/node/attempt. Make output identity unique per run/node/attempt; choose either a mutable CAS pointer with no append-only trigger or an append-only promotion ledger; require a strict attempt increase except exact same-output replay; and enforce pointer-to-output consistency. `authorizeEnrolledCompletion` must require the promoted output's attempt and execution to equal the completing execution binding, not merely find any current output left by an older attempt. Add the corresponding stale-attempt, equal-attempt replacement, and cross-node pointer tests.

5. **The resolved v2 snapshot has no formal schema or fail-closed parser.** Current `workflow_run.snapshot_json` is opaque JSON, while draft v2 proposes adding agent content/digest, output contracts, resolved capabilities, and dispatch inputs. Injecting these fields directly into strict manifest nodes would violate manifest exact-key validation; leaving their shape implicit invites each of the eight consumers to cast JSON differently. Define a typed `WorkflowRunSnapshotV2` with a strict shared parser and canonical digest verification. Keep the validated manifest separate from resolved immutable node data (agent content/digest, pinned capabilities and output/completion contract), and make every lifecycle, admission, output, and Blueprint consumer use that parser. Missing/unknown fields, capability drift, digest mismatch, or an unknown node must all hold fail-closed. Add corrupted-snapshot, digest-mismatch, missing-agent-content, and unknown-capability tests.

6. **`/api/runs/start` cannot establish the Lead/founder authority claimed by selection.** The existing middleware proves only possession of a bearer value; it permits the Gemini scoped token to POST this route and deliberately no-ops when the master API token is unset. `leadId` is a body field, not an authenticated principal. Therefore accepting `founderOverrideTemplateId` on this public body under the “existing auth posture” lets a scoped caller assert founder authority, and `selected_by`/actor evidence can be spoofed. Remove founder override from the public DTO and expose it only through a founder-authenticated/internal path, or require a founder capability/challenge bound to issue, template, and reason. Derive `selected_by` from server-authenticated identity, validate Lead selection against the resolved owning Lead, and require a reason for founder override as well. Cover master-token, scoped-token, missing-token-configuration, wrong-Lead, and founder-capability cases.

7. **Flag/claims ordering and session identity recovery still allow partial or permanently unidentifiable state.** For a no-QA v2 chain, Step 6b materializes the run and writes `qa_exempt` before Step 4a checks `workflow_claims_write`; with claims-write disabled, selection can therefore create an enrolled run/claim and only fail later at execution admission. Check the full flag combination before the materialization transaction so a rejected start has zero v2 side effects, then recheck at execution admission. Separately, writing `workflow_node_id` only in the two `session_started` branches does not cover the existing recovery path where a lost fire-and-forget start allows `session_completed` or `session_failed` to create the session. Resolve and set-once the binding-owned node identity before any enrolled lifecycle event that can insert/upsert a session, and perform conflict/missing-binding validation before `insertEvent`; otherwise the bad event is durable and same-ID HTTP replay is swallowed. Add no-side-effect claims-write-OFF tests plus lost-start completion/failure and pre-insert set-once-conflict tests.
