# Design Review — FLY-1281 plan.md (Round 3)

Date: 2026-07-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

Draft v3 incorporates all seven Round 2 requests and now has the right major components: server-owned completion receipts, trusted execution context, immutable runtime records, strict output promotion, typed snapshots, narrowed authority, and complete session identity recovery. Six remaining contradictions still need resolution before implementation, chiefly because the current flag ordering would break the legacy OFF path and the completion section assigns receipt creation to the same teardown sink that is forbidden from creating a receipt.

## What's Good (Keep)

- The completion receipt is the correct durable authority, and committing it with the run-node transition and deterministic run event is a much stronger model than treating `session_events` as the workflow ledger.
- Output promotion is now well-shaped: immutable per-attempt output rows, a deliberately mutable CAS pointer, strict attempt advancement, exact-replay semantics, and completion authorization bound to the same execution and attempt.
- The internal `GeneralizedExecutionContext` closes the public-node spoofing and shadow-`main` problems. Moving retry admission into `RetryDispatcher.dispatch` also matches where the final execution ID and runtime are actually available.
- The C→D boundary remains disciplined: only the graph start can launch in C, retries stay on that node, review and successor admission fail closed, and startup reconciliation reports rather than interprets edges.
- `WorkflowRunSnapshotV2` separates the validated manifest from resolved execution data and gives every lifecycle consumer one strict parser. That is the right antidote to ad hoc `JSON.parse` casts across the eight faces.
- Founder override is correctly removed from the public surface, and the plan now recognizes scoped-token, tokenless, and wrong-Lead cases as authority tests rather than assuming the existing bearer middleware proves an actor.
- D2 remains a separate capability-driven acceptance group, including the previously missed `design` writer case and atomic, deterministic `qa_exempt` issuance.

## Issues & Recommendations

1. **The generalized flag/claims check is ordered before knowing whether the request selected v2, which breaks the required OFF legacy path.** Step 6b says `assertGeneralizedRunAdmissible` runs before the lead/binding/default/null resolution. Because Step 6c invokes selection before legacy three-stage routing, an ordinary request with no matching template would be rejected whenever generalized templates or claims-write is off instead of reaching the null/legacy path. It would also incorrectly gate a v1 candidate with the v2 flag. Resolve the candidate and stored revision schema read-only first; return null unchanged when there is no candidate; route v1 through its existing contract; and only then check the v2 flag combination immediately before the v2 materialization transaction. Keep the same predicate inside `materializeWorkflowRun` and execution admission as defense in depth. Add explicit tests for OFF + no candidate → byte-identical legacy, OFF + v1 candidate → existing v1 behavior, and OFF/claims-write-OFF + explicit/bound/default v2 candidate → reject with no run or claim.

2. **Step 4e still gives DirectEventSink two mutually exclusive roles, and its stated crash case cannot occur under the stated transaction.** In production, `DirectEventSink.emitCompleted/emitFailed` is Blueprint's process-teardown emission; it is not the runner's explicit `flywheel-comm complete`. If DirectEventSink calls `authorizeAndCommitEnrolledCompletion` when no receipt exists, a zero-commit Blueprint result can create the receipt—the exact behavior the next bullet forbids. The HTTP `/events` branch also receives both explicit `source="flywheel-comm"` completions and `TeamLeadClient` teardown events, so “HTTP sink” alone is not a terminal-authority discriminator. Split the API into an explicit-complete commit primitive and a teardown-observer primitive: only the authenticated explicit-complete/marker-replay path may create a receipt; DirectEventSink and HTTP Blueprint teardown may only re-drive an existing receipt or hold/escalate when absent. Then early-return from legacy session-completion side effects after the generalized audit event. Also, if receipt + run-node + run-event + session projection truly commit in one StateStore transaction, “receipt committed, crash before projection” is impossible—the transaction rolls back. Test the real remaining boundary instead: core completion transaction committed, crash before the separate `session_events` audit insert, replay converges and inserts the audit once. If any projection is intentionally outside that transaction, introduce an outbox rather than calling the operation atomic. Use the existing run-node terminal vocabulary `done` (not the draft's `completed`) and pin the deterministic event-UID formula. Add the HTTP `TeamLeadClient` teardown-without-receipt case to the collision matrix.

3. **The `/api/runs/start` authority and unknown-key guarantees still lack an implementable boundary contract.** Today `tokenAuthMiddleware` only calls `next()`; it does not attach a master/scoped principal, the Gemini token is expressly allowed to reach `/api/runs/start`, and the router is mounted without middleware when no master token is configured. Therefore “derive `selected_by` from auth context” and “scoped must not select v2” require a new, explicit request auth-kind handoff. Define it: master-authenticated requests may request/trigger v2 selection; scoped and tokenless requests must not materialize v2 (state whether they reject a v2 candidate or fall through), while requests with no v2 candidate keep their existing legacy behavior. Derive the recorded actor and owning Lead separately so a global master token is not mislabeled as a Lead identity. Likewise, extending the TypeScript `StartRequest` interface does not reject unknown JSON keys; the current route reads many body fields without an exact-key parser. Add a runtime `RunsStartBody` parser covering all existing public fields, or an explicit forbidden-field check for `founderOverrideTemplateId` that does not accidentally reject legacy callers' established fields. Specify expected statuses for master/scoped/tokenless/wrong-Lead and test both explicit template selection and an implicit v2 binding/default.

4. **The typed snapshot currently risks making the live registry a runtime authority again.** Step 4h says “capability drift” causes every consumer to hold, but the umbrella contract says the registry hash is for audit/drift detection and not a runtime basis; the materialized snapshot must keep running after canonical config changes. At materialization, validate against the live registry and pin normalized capabilities plus their digest. Afterward, the parser should validate the snapshot's own schema/digest and reject unknown capability vocabulary, but it must not require equality with a later live registry version. Clarify the two dispatch records as well: the snapshot's per-node dispatch triple is the pinned effective input used on retries, while `workflow_execution_runtime` records the actual adapter/model/effort/family chosen for one physical execution. Generalized dispatch must bypass refreshed issue-label selection and prove the actual runtime matches the pinned node contract; author/reviewer inversion should compare the actual author family with the snapshot-pinned reviewer family and be rechecked when D eventually admits the reviewer. Add a test that registry/config/labels change after materialization yet the existing run parses and retries with its pinned behavior; malformed or unknown snapshot capabilities must still fail closed.

5. **The new DDL descriptions are not yet sufficient to enforce the claimed binding integrity.** `workflow_execution_runtime` says it has an `execution_id` plus a composite FK to `workflow_execution_binding`, but it does not list the child `run_id/node_id/attempt` columns required for that FK; either add them or use a simple FK to the binding's primary-key `execution_id` and verify the joined tuple. `workflow_node_completion` likewise needs a composite binding FK, `event_uid` uniqueness, NOT NULL fields, and exact-replay conflict checks proving execution, route, and event identity agree with the stored receipt. Its deterministic run event must converge with any shadow writer event rather than merely dedupe an unrelated payload under the same UID. Spell out these constraints and add foreign-key/conflicting-receipt tests. This keeps the new tables consistent with the existing immutable execution-binding and append-only ledger patterns instead of relying solely on caller discipline.

6. **Selection/shadow reconciliation still covers only the post-materialization happy path.** `materializeWorkflowRun` currently inserts a new run while the database enforces one active run per `(project, issue)`. With claims-write required, an active legacy shadow run may already exist when generalized templates are enabled; the new insert will conflict before the new context can be threaded. In addition, `WorkflowShadowWriter` currently locates an active run by project/issue, swallows failures as observation-only, and its explicit-`runId` StateStore mode rejects lifecycle ops—so merely adding `runId` to the context does not yet make dispatch target that exact authoritative run. Define the issue-lock/reconciliation rule before materialization: exact replay of the same v2 run may reuse it; a pre-existing legacy/nonmatching active run must be loudly held or explicitly retired under a safe policy, never grafted with a generalized snapshot. Add a generalized, fail-closed run-targeted dispatch method (or extend the batch API under typed-enrollment checks) rather than relying on the observation-only `safe()` path. Test pre-existing empty and nonempty shadow runs, wrong active run IDs, and exact materialization/start replay.

## Verdict

CHANGES REQUESTED — address items above
