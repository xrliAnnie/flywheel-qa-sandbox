### 🔴 P-1 = **FLY-1996**(已由 Tadashi 立单)— 堵住快车道的安全洞

> **这不是省钱单,是修 bug,必须最先做。**
> 单号:**FLY-1996** —
> <https://linear.app/geoforge3d/issue/FLY-1996/cibug-classify-快车道把-docmd-全判惰性但-shell-守卫测试断言-doc-内-runbook>
> 本单(FLY-1987)只出方案、不改代码;下面这段是交给 FLY-1996 的输入,不是本单要做的事。

- **问题**(research §2.4,已实读源码确认):
  `scripts/__tests__/launchd-units-manifest.test.sh:836` 把
  `doc/engineer/implementation/FLY-222-a0-a10-runbook.md` 当作断言对象(grep 陈旧 plist 路径,
  命中即 FAIL),而该测试由 `ci.yml:367`(Script Tests 2/2)执行。
  但 `doc/` 前缀 + `.md` 后缀**正好在 classify 白名单里**。
  ⇒ **一个只改这份 runbook 的 PR 会走快车道,跳过那条守卫,`CI OK` 判绿,直接合并。**
- **同类第二例**(今天不触发,但证伪了「doc 路径都惰性」这个前提):
  `scripts/__tests__/test-fly1609-design-compare.test.sh`(`ci.yml:475`)执行
  `engineering/doc/FLY-1458-abc-prompt-three-arm-analysis/scripts/design_compare.py`。
- **要做的**:
  1. **穷举**:列出 `ci.yml` 里每个 `run:` 实际执行/读取的、位于四个 doc 前缀下的路径。
     不能只靠 grep 关键字 —— 变量拼接的路径要人工过一遍。
  2. **三选一收口**(每个 CI 输入各自定):
     (a) 把它挪出 doc 前缀(移到 fixture / 代码路径);
     (b) 在 classify 里加**显式非惰性排除**(白名单开洞的反向清单);
     (c) 把它的合同检查搬到常开的 Quick Gate 里。
  3. **加守卫(lane-aware,不是「CI 不许碰 doc」)**。
     上一版我把不变量写成「CI 不消费任何 doc 前缀下的文件」——**太粗**,因为方案 (c)
     恰恰允许一份白名单内的文档被**常开车道**消费,那是安全的。正确的不变量是:

     > **每一个被 CI 消费、且本身满足惰性白名单的文件,要么被 classifier 显式排除,
     > 要么它的全部必需合同都在常开车道执行。**

     落法:维护一份**有主的清单**(路径/模式 → 消费它的 job → `always-on` | `classifier-excluded`),
     Quick Gate 同时校验**这份清单**和**classifier 的排除表**两边一致。
     ⚠️ **静态扫描扫不全动态拼接的路径**,所以人工过一遍 `run:` 调用图这一步**保留为 review 证据**,
     不要声称守卫能自动发现所有消费者。
- **验收**:红先行 —— 构造一个只改 `FLY-222-a0-a10-runbook.md` 的 diff,
  断言修复前 `no_code=true`(洞在)、修复后 `no_code=false` 或该守卫在常开车道跑到。
- **风险**:低(只会让更多 run 跑全量,不会少跑)。
- **顺带**:研究里的快车道命中率(严格口径 **34.7%**)在 P-1 之后会**再下降一点**,这是对的。

#### P1-a(必须先做)— 基线标记的可行性 spike

research §4.5 的实测结论:**运行时的 base 环境事后拿不回来。**
对 open PR 的历史 workflow run 逐条查:
- 顶层 `head_sha` 是历史值 ✅;
- 但 `pull_requests[0].head.sha` / `.base.sha` 在**每一个历史 run 上都已变成 PR 的当前值** ❌;
- check-suite 查询的 `before_sha` / `after_sha` 返回 `null`。

⇒ **run 里内嵌的 PR 关联对象是活指针,不是快照。**
所以 P1 **不能**建立在「事后从 API 恢复当时的 base」上 —— 那要么查不到(白做),
要么信了可变元数据(重新打开假绿的门)。**必须在全绿那一刻自己写下持久标记。**

spike 要定死的东西(不定完不许进 P1-b):

| 项 | 要求 |
|---|---|
| **何时写** | **只在该 run 的全量 `CI OK` 校验通过之后**才写。快车道 run **绝不**写标记 |
| **写什么** | ① workflow `run_id` + `run_attempt`;② PR 号 + **历史 head SHA**;③ **实际用于构造被测 merge commit 的 base 分支 SHA**(取被检出的 merge commit 的第一个父提交,**不要**用语义含糊的 API 字段);④ 被测 merge SHA;⑤ `ci.yml` 的 **blob hash**;⑥ 期望的重 job 清单及其各自结论 |
| **写在哪** | 由 spike 定(候选:artifact / check-run output / 仓库外存储)。必须能被**下一次 run 读到**,且不可被 PR 作者伪造 |
| **怎么认证** | 标记必须能**绑回产出它的那次 run**(run_id + attempt),不能只凭内容自证 |
| **保留 / 过期** | 明确保留期与过期语义。**过期 = 跑全量**,不是「就当还有效」 |
| **怎么读** | 分页必须读完;读不全 = 跑全量 |

**任何一项:缺失 / 过期 / 格式错 / 对不上 → 跑全量。**

spike 的输出只有两种,都是合格产出:
「标记方案可行,规格如上」 或 「本平台上做不出可信标记,P1 放弃」。
**在 spike 出结论前,不许把 $116 当成可实现的优化对外报。**

#### P1-b(spike 通过后才做)— 实现

在现有「merge-base 全量 diff 惰性」通道之外加第二条通道。

🔴 **合格基线的定义(这条特性唯一真正的风险所在)**
第一版 plan 写「基线 = `CI OK` 成功的 run」——**错的**,design review R1 抓出来了:
`ci.yml` 的 `ci-ok` job **显式接受 `no_code=true` 时重 job 为 `skipped`**,
所以**一次快车道 run 也会产出成功的 `CI OK`**。照那个定义,文档-only 的快车道 A 可以给
文档-only 的快车道 B 当基线,**两次都没跑过重测试** —— 正是本条声称要防的自举漏洞。

合格基线必须**同时**满足:
1. 是本 PR 的一次 `pull_request` workflow run,**且带有 P1-a 定义的、能绑回该 run 的标记**;
2. **同一个 run 的同一次 attempt 内**,**恰好** 5 个 Unit 矩阵 job + **恰好** 2 个 Script Tests job
   + **恰好** 1 个 payload-distribution,**全部 `success`,且无一 `skipped`**
   ——「恰好」不能省:只检查「已有的重 job 都成功」会让**清单不完整的 run** 蒙混过关;
3. 该 run 的 `CI OK` 成功
   ——**这一条也不能省**:`ci-ok` 在 `no_code=true` 时接受 skipped,所以快车道 run 也是 `CI OK` 成功;
   反过来,重 job 全绿但 Quick Gate 挂掉的 run,`CI OK` 是 failure,**它不是合格基线**。
   research §4.0 里那 124 条错误引用就是漏了这一条造成的;
4. 标记里的历史 head 是当前 head 的**祖先**;
5. 基线 head → 当前 head 的 raw diff 通过现有惰性文件 + mode 检查;
6. 标记里的 **base 分支 SHA** 与 **`ci.yml` blob hash** 与现在**一致**。
   若 main 或 `ci.yml` 变过,那次全绿验证的不是当前的合并结果。

**必须 fail-closed 的点**(任一不确定 → 跑全量):
标记缺失/过期/畸形/绑不回 run;API 报错;分页不完整;schema 变化;job 名漂移;
基线 commit 已被 GC;祖先关系不成立(force-push、rebase);找不到合格基线。

**验收(全部红先行)**:

| # | 场景 | 期望 |
|---|---|---|
| 1 | 快车道 run 当基线 | **不得**被接受 |
| 2 | 真全绿 → 连续多个文档提交 | 全部走快车道 |
| 3 | 真全绿 → 一个代码提交(未绿)→ 文档提交 | **跑全量** |
| 4 | 代码提交 failed/cancelled → 文档提交 | **跑全量** |
| 5 | 基线之后 base SHA 变了 | **跑全量** |
| 6 | 基线之后 `ci.yml` blob 变了 | **跑全量** |
| 7 | force-push 改写历史 | **跑全量** |
| 8 | **run 的 PR 关联元数据在事后漂移了**(§4.5 的真实行为) | 判定**只认标记**,不受影响 |
| 9 | **同一 run 的 re-run attempt** | 标记按 `run_attempt` 精确匹配,不串 |
| 10 | runs API 报错 / 分页截断 / job 名对不上 / 标记读不全 | **跑全量** |

**还要一并改的合同**(要在 PR 里显式说明,不能夹带):
现行 `ci-classify.test.sh` 有断言**禁止** classify 调用 runs API / `gh` / `jq`(v2 简化时加的);
P1 需要外部读取,这些断言必须更新。`ci-structure.test.sh` 的 skip 语义也要同步。

- **风险**:中—高,**是本轮分类器风险最高的一条**(错误跳过本该跑的测试)。
  但**不是唯一能造成假绿的改动**(P0、P3 各有自己的路径,见 research §4.4)。
  必须在 job summary 打印用了哪个基线标记、以及拒绝原因,否则出事后无法回溯。
- **与 P0 的关系**:两者救的是不同 run(research §4 台账 ②③ 互斥),但都改同一个脚本,
  **P0 先合、P1-b 后合**,让 P1-b 的 diff 只含增量逻辑。

### P3 — 构建一次,artifact 跨 job 复用

- **省**:≈ 28,230 分钟/月 ≈ **$169/月**(作用在仍需跑全量的 337 个尝试上)。**量级最大的一条**,排在 P1 前面。
  🔴 **它不是上限,是推算**(research §4.3):
  `dup_build_sec`(重复构建秒数)是**量出来的**;`p3_billed_min`(省下的计费分钟)是**建模出来的**
  —— GitHub 按 job 向上取整,从 61 秒的 job 去掉 2 秒构建省的是整整 1 分钟,
  所以「秒数 ÷ 60」方向都不定。上一版把它写成上限、还说「按 job 取整只会让它更小」,**那是错的**。
  ⚠️ 它**没有**减去新增生产者 job 自己的 checkout/setup/install 和 artifact 传输(这两项往下拉),
  而且**随所选设计变**,必须各自单算。
  ⚠️ 而且**随所选设计变**:Quick Gate 保留本地 build 与拆独立常开 job 两套方案,
  剩下的 build 次数和传输次数都不同,**必须各自单算,不能共用这一个 $169**。
  这是 provisional 值,在下面那步「先量」做完之前**不得对外当成可实现额度**。
- **先量再改(硬性)**:第一步在 CI 里量一次完整 `pnpm build` 后的 `dist` 总体积、
  artifact 一次上传 + 七次下载的实测耗时,以及**新增 build job 自身**的
  checkout + setup + install 开销。
  GitHub 按 **job** 向上取整到分钟计费,新 job 至少多算 1 分钟。
  **量完不划算就地放弃,不要硬做。**
- 🔴 **不要给 `quick-gate` 加 `needs: [build]`**(上一版 plan 写了,是错的):
  `build` 失败时 GitHub 会 skip 依赖它的 job,`ci-structure.test.sh` 等治理守卫就不跑了,
  直接违反 research §8 第 2 条和现行结构守卫「Quick Gate 必须独立启动」。
  两个可选设计,**二选一,在 PR 里写明选了哪个**:
  - (甲)Quick Gate 保持独立、保留自己的本地 build(省得少一点);
  - (乙)把常开的治理检查拆成一个独立的常开 job,只让真正消费构建产物的 job 依赖 artifact job。
  无论哪种,**要求的结果是:`build` 失败时 `CI OK` 必须失败**(消费者 job 本身是 skip 还是 fail 无所谓)。
- **防假绿断言(这条改动唯一真正的风险)**:
  artifact 里必须带一个由**源码树摘要**算出的指纹;每个消费 job 使用前重算并比对,
  不一致 fail-closed。没有这条,artifact 陈旧会表现为「测的不是这次的代码」。
- **风险**:中 —— artifact 身份/内容错了就会「测的不是这次的代码」,是本轮第二条能造成假绿的改动
  (research §4.4)。
- **前置**:P-1(治理守卫要先在位)。与 P0/P1 正交;**建议排在 P1 之前**,
  但理由**不是额度更大**(两个数口径不同不能比,见 §2 开头),而是它不碰分类器语义、
  且 P1 有一个未解决的可行性前提。

### P4 —(观察项,不立即做)进度账本的推送策略

- research §1.5:`chore(progress)` 占 **14.1%** 的 CI 开销。
- **P1 落地后先重新量一次**。如果 P1 已把它压下去,这条不用做。
- 若仍高,再考虑改推送策略。⚠️ **前置阅读 FLY-945**(progress push 会自动重绑 PR head),
  **不能直接关掉 push**。

### 不排期 — 自托管 runner

research §5 的结论:**不要挂到 founder 的生产机上**,理由是信任边界
(PR 代码在一台有生产凭据、非一次性的机器上执行)+ 资源争抢,
**不是**上一版写的「测试直接操作生产 tmux/launchd」——那条已实读源码撤回。

   `teamlead.db` 的 `design_review_manifest` 表,否则会多铸一份、引来多份 gate 指令。)
2. **`.flywheel/runs/<exec>/codex/design-review.json` 我没有写,这是故意的。**
   那个文件的 schema 要求 `status:"APPROVED"`。**没有 APPROVED 的评审就写这个文件 = 伪造批准。**
   等真评审拿到 APPROVED 再写,`rounds` **按 §4.1 台账里的实际轮数**填,不要写死一个数。

## 5. 风险与我的自警

1. **最大的风险是这份调研被当成账单读。** 我算的分钟没能被 GitHub 自己的接口证实
   (`/timing` 返回全 0)。比例拆分不受影响(同一把尺子量的相对值),
   但**绝对美元数必须当估算读**。这句话要在所有交付物的第一屏。
2. **外部评审一共抓出我十几类硬伤**(逐轮台账见 §4.1),值得逐类记下来,因为它们不是笔误:
   - 找到一个支持性来源就停了(自托管定价:漏了置顶的推迟更新)—— *结论靠惯性活着*;
   - 把两个不同实现的时间段当成一个「现状」(classifier v1/v2);
   - 两张表用了不同窗口却放在一起(18,759 vs 21,981);
   - **把「required check 通过」当成「重测试跑过」**(`CI OK` 在 no_code 下接受 skipped)
     —— *用一个近似指标冒充了它要证明的属性*,而那正是这条特性的全部风险所在;
   - **拿不满的窗口按满窗折月**(2 天 16 小时当 3 天),折出来的月量偏低;
   - **把毛额标成「可省」**,没有扣掉改走快车道后仍要付的钱 —— P0 因此从「$4」变成「0」;
   - **把「均匀分布」当成已知**(那 46 个缺失 run)—— 实测后发现它们是零-job 取消,是真零;
   - **把提交标签当成文件事实**(`docs(...)` ≠ 没有代码);
   - **分档判据漏了作用域闸** —— P0/P1 是 PR 作用域的,我却让一个 `push: main` 的 run 落进了 P1 档,
     而「分钟守恒」校验对它完全无感:**加得上不等于标得对**;
   - **两处百分比用了错的分母**(命中率拿全 workflow 的 614 当分母、CI 提交标签表除以 12,180 而不是 12,144);
   - **把抽样说成全量,而且说了两次** —— 第一次是「46 个均匀分布」(纯推断),
     R2 之后我只抽查 8 个就写成「逐个查了」,R3 又抓一次,现在才是真的 46/46 全查。
     **同一个错误形状能连犯两轮,说明它不是手滑。**
   - **采集方法本身有缺陷,而我从没验证过采集层** —— 6 路并发 `>>` 同一个文件会交错损坏,
     且 `/jobs` 默认只给最新一次尝试而 GitHub 每次重跑都计费。两项合计让总额偏低 4.8%。
     R4 是**重放 API** 才发现的,所以现在原始快照入库了(research §0.1.0);
   - **判据只写了「合法」没写「被救」** —— P0 判的是「加了后缀之后仍然合法」,
     不是「靠新增后缀才被救」;38 个样本因此全是假的,修正后归零;
   - **合格性判据漏了最关键的那一项** —— P1 基线只看重 job 成功,**没看 `CI OK`**,
     于是 124 条引用了 `CI OK=failure` 的失败 run 当「之前绿过」。

     一次是把 `CI OK` 看得太重,一次是根本没看它。
