## Issues & Recommendations

1. **(a) BLOCKING — #5 把来源明确排除的“接班首回合”重新写成 40.5 亿重读收益。**

   位置：`plan.md:46,62`；`research.md:68-71`。
   FLY-2893 当前分支的 `evidence/scripts/build_report.py:150-155` 明确说明：goal 首回合含大量实际工作，无法可靠分离接班重建成本，q2 仅留 CSV 参考，不进入结论。这里将其称为“替身首轮重读”，再与残留相加成“最多约 52 亿 / 5 个号周”，超出了引用依据。该报告的前三类建议是 K1 额度墙、K6 worktree 接管、K3 凭据（同文件 171-195 行）；终态残留另涉及 FLY-2892 / FLY-2814，也不能全部归给这三项修法。

   建议：删除 40.5 亿的“重读可省”归因和 52 亿排序值，保留接班首回合总消耗作为未分离参考；把已核实约 12.1 亿残留对应到实际处理残留的建议。固定引用 SHA，保持来源报告的证据限制。“最多”不能消除工作内容和措施覆盖范围不匹配的问题。

2. **(a) BLOCKING — #4 的 poll 分类会把写代码、运行测试和复合工作命令计成纯等待，44.1 亿不是所称的纯轮询请求量。**

   位置：`evidence/scripts/census.py:175-204,350,467`；`analyze.py:483-496`；`plan.md:45,61`。
   `cmd_class` 在整段命令字符串中先匹配 flywheel 子命令，再匹配 `sleep` / `until` / `while`；它没有区分 shell 指令、heredoc 内的代码/注释或同一调用中的其它工作。`trigger` 无 `+` 只证明归类后剩一种标签，不证明只有等待。

   [verified by reading code / verified by executing] 实际 CSV `file_id=745`，session `6ab081b3-29b7-4cec-8a85-30f59133928a`，`2026-09-23T00:25:24Z` 的 **253,006 token** 请求被标为 `bash:sleep/poll-loop`。前一个工具实际追加测试并执行 Vitest；命中的是测试注释中的英文 `while`，没有 sleep 轮询。`2026-09-22T19:21:57Z` 的 **162,844 token** 被标为仅 inbox，实际同一 Bash 还读取 CI、Git HEAD 和工作区状态。

   建议：对无法证明是纯等待的复合调用标为 mixed/unknown，排除文字内容命中；识别无变化的重复轮询及每段必须保留的返回，再估算减少量。修正前只能发布“启发式命中等待相关调用的消耗”，不能以它推出 30–40 亿可省。

3. **(a) BLOCKING — #6 把所有上下文增量分给工具输出，44.0 亿“大输出超额重读”有实际错误归因。**

   位置：`census.py:224-247`；`analyze.py:520-532`；`plan.md:47,63`；`research.md:96-98`。
   `grow = ctx[i] - ctx[i-1] - prev_output` 没有扣除其间外部输入、工具定义注入或模型切换等变化，却把 grow 全部分给工具返回。避免按字符估计截断，并不证明这部分增长全来自返回内容。

   [verified by reading code / verified by executing] `claude_tool_outputs.csv` 中 `file_id=11`、`2026-09-16T21:20:49Z` 的 `bash:read/search` 返回只有 **151 字符**，却分到 **47,833 token**，又乘 **358** 次，单行向“超过 5,000 token”贡献 **15,334,214 token**。对应 session `007b4857-b3ef-4c8c-8233-24f6315fb379` 的 transcript 确认该返回为 151 字符；下一计费响应前还有其它用户输入，最早一条长 **22,433 字符**。这不是应被 5,000-token 输出上限裁掉的大返回。

   建议：只把可归属增量算入工具输出；有并发输入、上下文重建或工具定义变化时保留 unknown，必要时给有依据的边界。复算 W10 和 #6；仅给现有 44 亿乘 35–55% 无法修复错误分母。

4. **(a) BLOCKING — #8 用通知条数占比推 token 上限，实际 Monitor 归因只有 5.04 亿。**

   344/817 是通知条数占比，不是 21 亿请求 token 的占比；817 条通知也不等于有计费请求的 701 回合。

   [verified by executing] 沿用 census 的外部输入分类及 `turn_seq` 规则，从原 transcript 给 CSV 中 701 个回合关联 Monitor 标签，结果完全闭合：**317 个 Monitor 回合 = 504,402,520 token**；**384 个其它/后台回合 = 1,593,730,851**；合计 **2,098,133,371**。Monitor 的 token 占比是 **24.04%**，不是 42%。现有乘法给出的约 **8.83 亿**甚至超过该分类中 Monitor 的全部回合消耗。

6. **(a) BLOCKING — #1 遗漏现有旋钮的生效前提，“只配 40 万然后重启”不会应用。**

7. **(a) BLOCKING — §2 承诺证据下限，§3 实际给的是主观折扣情景；尤其 ack 的触发标签不能证明请求可删除。**

   位置：`plan.md:29-30,58-69`；`census.py:307-350`；`analyze.py:545-553`。
   2/3、75%、70–90%、30–50% 等没有对应的已验证删除请求集合或效果测量。作为明示假设的情景估算可以使用；作为“有直接证据可以不发生”的下限则不成立。FLY-2749 原分类器报告本身也明确限制：文本类别不是 proven removable savings（`measure-usage.py:283-285`）。

   [verified by executing] 6,815 个 ack 标签请求及 **3,295,046,833 token**可精确匹配回 transcript，但其中 **1,358 个 / 712,580,046 token**的响应继续调用工具，不能仅凭平均输出 233 token 推断只做结束语。更直接地，工具结果与外部输入没有独立排他标志：其中 2 个请求同时有新外部输入，共 **1,186,410 token**。例为 `file_id=11`、`2026-09-16T23:14:36Z`，以及 `file_id=20`、`2026-09-15T19:03:19Z`。这些数是“收到 ack 返回后的消耗”，不是已证明可消除的额外请求；后续有工具动作也不等于一定不能合并，仍需区分可合并情况。

   建议：统一分开“观测类别消耗”“假设减少比例”“情景节省”，把目前正数下界称为情景低值，明确不是保底或实测下限；无法分离的部分写未知。若坚持证据下限，就只纳入逐请求核实可删/可合并的集合。无需为了本研究强行开展生产 A/B。

8. **(a) BLOCKING — 清单顺序不符合声明的排序公式，含上限条目也没有可计算中值。**

   位置：`plan.md:38-54`。
   按现表计算，#9 为 **13.5 × 1 = 13.5**，#8 为 **6.5 × 1 = 6.5**，却把 #8 放在前面；#11 为 **25 × 0.5 = 12.5**，#10 为 **17.5 × 0.5 = 8.75**，顺序同样相反。风险只用于并列，不能解释这些逆序。S–M、M–L 没有确定系数；#5/#13 没有下界，也没有区间中值。

   建议：更正数字后，给每条明确系数和排序政策，计算并展示分数；上限/未知项单列或明示主观优先级。若实际是综合判断排序，就删除“按该公式排序”的声明并说明额外考虑。保留“不相加”的约束。

9. **(b) implementation detail — 压缩模拟需统一 raw-token 计量，避免把 909 次读成实际执行预测。**

   `simulate_compaction.py:48` 的重建费用用了 `floor * 1.25`，而 observed 与其余 simulated 使用原始 token；这是原始量与相对价混算，方向是保守低估节省，不是放大 90.4 亿的证据。部分模拟状态低于设定 floor；只在普通增量处补 floor 下界的敏感性重放，把 40 万节省从 **9,035,271,562** 改为 **9,030,626,896**，差 **4,644,666（约 0.05%）**，不构成此次独立阻塞项。建议统一费用单位，说明会话最小上下文、增长回放及压缩次数均为模型假设；不要将这个敏感性版本当成已经验证的生产模型。

10. **(b) implementation detail — 报告构建应列全输入与证据文件，保留可追踪性。**

    `plan.md:12,86` 的脚本列表/验收只覆盖四个脚本与 summary，但正文依赖 compaction JSON、Monitor 拆分及未合的 FLY-2893。Monitor 脚本在评审开始时未跟踪，派生 JSON 在评审过程中出现，均未由本评审写入或修改。实现时把实际采用的拆分脚本、关联 token 聚合、比例假设、来源 SHA 一并纳入 docs PR，让页面从这些输入生成。无需建设新平台；现有小型构建脚本足够。W10 的后续重读计数还应限定 `[T0,T1)`：当前 `attribute_outputs` 遍历整段 transcript，而调用处只过滤工具输出发生时间。
