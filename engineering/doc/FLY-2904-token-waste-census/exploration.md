## 问题

要交付的是**决策材料**,不是修复:一页 HTML,列出每一类浪费机制的量、证据、省法、代价,按「省得多 × 好做」排序,founder 在页上勾选/评论。

## 「浪费」的定义(先钉死,避免把「用得多」写成「浪费」)

一笔 token 算浪费,当且仅当存在一个**不降低交付质量**的替代跑法,可以不花这笔 token。三种形状:

1. **重复读**:同样的内容被再读一遍,而下游没有因此多得到信息(整段重读上下文去看一条纯通知;替身重读 onboarding;每个请求都重读庞大的系统提示)。
2. **无产出的消耗**:消耗发生在交付物已定型之后或必然作废之前(终态后残留;额度墙前起跑即死;被作废的评审轮)。
3. **放大器**:一次性的大输出被后续每个请求重读(整包测试日志、整份 diff 放进上下文后,再跑 N 个请求)。

「设计评审 5 轮」本身不一定是浪费:第 2 轮以后如果每轮都抓出真问题,那是质量成本。报告里对这一类只给量和「可省上限」,不直接计入浪费。

## 已知边界

- 只覆盖**本机**。其它机器 / claude.ai 网页端 / 手机端用量不在内。
- 订阅没有逐 token 单价。Claude 的 cache_read 在 API 计价里是 input 的 1/10,订阅额度怎么折算官方未公布;报告同时给「原始 token」和「按 API 相对价加权」两列,后者只作相对比较。
- Codex 只有累计 token 和账号周额度百分比;额度折算沿用 FLY-2889 的 fingerprint 方法,是情景估算。
