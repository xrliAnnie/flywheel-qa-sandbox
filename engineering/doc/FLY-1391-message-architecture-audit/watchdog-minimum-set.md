# FLY-1391 必须保留的 watchdog — 最小清单与逐条论证

Issue: FLY-1391 (https://linear.app/geoforge3d/issue/FLY-1391/audit消息全貌-message通知架构全图-谁发给谁哪些送-lead哪些送-runner哪些根本没送annie-直令不打地鼠先看全貌)
日期: 2026-07-20
基于: architecture-target.md · architecture-current.md

> 目标是 **watchdog 面最小化**,不是归零。本文逐条论证**为什么消息语义覆盖不了它**,
> 并给出「不用它会发生什么」。凡是消息语义能覆盖的,一律列进 §3 的**该消失清单**。

## 0. 判据(整份清单只用这一条)

> **一条消息只能由「活着且还能干活」的进程发出。
> 凡是失败模式本身会让进程发不出消息的,消息语义永远覆盖不了它。**

推论,也是本文的核心论点:

**watchdog 是这套系统里唯一不依赖被观察方配合的信号。**
收据机制再好,也建立在「对方还能产生副作用」之上;而 watchdog 是**从外部探测**的。
这两者不是同一层的替代关系 —— 收据管**做没做**,watchdog 管**还在不在**。

⇒ 所以正确的收缩方向不是「少留几个 watchdog」,而是:
**把「做没做」全部交给收据,watchdog 只留「还在不在」和「外部世界变了没有」。**

## 1. 必须保留(逐条)

### W-1 · 进程存活探测(Runner / Lead)—— **不可消,第一条**

| 项 | 内容 |
|----|------|
| **它检测什么** | 进程**死了**(不是慢、不是闲):tmux 会话没了、pane 死了、PID 不在 |
| **为什么消息覆盖不了** | **死进程发不出任何消息,也发不出「我没处理」的信号。**收据机制对死亡**天然失明** —— 它只能观察到「没有收据」,而「没有收据」在语义上无法区分「死了」「在忙」「模型卡住」。**这个歧义只能由外部探测消解。** |
| **现状实现** | 底层原语 `probeRunnerProcessLiveness`(`bridge/tmux-lookup.ts:371-400`),跑 `tmux list-panes -F "#{pane_dead}"`,返回**四态**:`alive` / `dead_pin`(窗口在、进程是尸体)/ `absent`(证实没了)/ `indeterminate`(探测本身失败 → fail-closed 永不回收)。上层 `HeartbeatService.probeSessionLiveness`(`:1217-1236`)扩成五态。消费者至少 13 处(crash-reaper / phase-orchestrator / terminal-thread-archive / done-thread-reconcile / LeadWatchdog / …) |
| **🔑 代码库自己就在论证这一点** | `bridge/liveness-evidence.ts:10-17` 原文:活动证据是「**给人看的证据,永不作为判定输入** —— `decideDestructive` 刻意不接收它。一个会因『过去 10 分钟有没有流量』而摇摆的判定是不可复现的,而且会重新引入 FLY-1319 那类 bug:因为一个弱信号看起来像死亡而销毁了一个活会话。」<br/>⇒ **「用消息流量判断死活」在这个仓库里是被明文否决过的方案,不是我在这里新提的顾虑。** |
| **`indeterminate` 这一态尤其无法用消息表达** | 它编码的是「**观察者失败了**」。消息协议里没有任何东西能表示「我没能看清楚」—— 只有外部观察者才需要、也才能表示这个状态。 |
| **不用它会发生什么** | 已有实证:**founder 已批准 ship、runner 已死**,系统靠 `reWake` 试着叫醒、叫不醒后走 `alertDead`(`gate-poller.ts:3844-3866`)。**没有这条探测,这个分支根本不会被触发** —— 那次批准会无限期挂着,Annie 以为在跑,实际没有任何东西在跑。 |
| **注意** | 这条**恰恰是本单最重的发现里被关掉的那批之一**(`RunnerIdleWatchdog.ts:257` 在 legacy flag 下)。目标态必须把它**明确移出**任何「投递看门狗」的关停半径 —— 它不是投递机制,是存活机制,两者被同一个 flag 管本身就是分类错误。 |

### W-2 · 投递循环自身的心跳 —— **不可消,且不能由它自己报**

| 项 | 内容 |
|----|------|
| **它检测什么** | `LeadInboxLoop` / GatePoller 这类**承载消息的机制自己**停了 |
| **为什么消息覆盖不了** | **自指问题**:如果消息系统本身死了,任何「基于消息的告警」都发不出去。要报告消息系统死亡的那个东西,不能建立在消息系统之上。 |
| **现状实现** | FLY-1373 已经保留了**唯一一条新报警**:per-Lead `loop_heartbeat` → `inbox_loop_stalled`。**这个决策是对的,目标态原样保留。** |
| **不用它会发生什么** | 消息全部安静地停在队列里。所有收据都不满足,但**没有任何东西会因此出声** —— 因为出声本身要走那条死掉的路。表现为「系统很安静」,而安静看起来像「没事发生」。 |
| **⚠️ 现状实现没解决自指** | 复核指出:投递循环的健康检查**跑在 Bridge 自己的 heartbeat tick 里** ⇒ **Bridge 整体死亡时它不会告警**。⇒ 目标态必须把这条放进**独立 failure domain**(独立进程/独立通道),否则它只是看起来解决了自指。 |
| **⚠️ 检测 ≠ 缓解** | W-1/W-2 只能**告诉你枢纽死了**,**不能把 founder→Runner 的路接回去**。要真正兜住 `architecture-target.md §1.3` 的单点,还需要 supervisor + break-glass 路径,**那是另一类东西,不是 watchdog**。 |
| **注意** | 这条必须**独立于主消息路径**(独立进程/独立通道)。现状 shell 侧 `scripts/lead-alert.sh` 的存在理由正是这个(Bridge 死了它还能发),但它**不认统一告警频道**(`plan.md` G-13),所以最需要被看见的信号反而不在 Annie 盯的频道 —— 目标态必须修掉。 |

### W-3 · 外部世界的状态漂移 —— **不可消(它们根本不是我们的组件)**

| 项 | 内容 |
|----|------|
| **它检测什么** | Discord thread 被归档 / PR head 变了 / CI 状态 / 账号 auth 过期 / 配额耗尽 |
| **为什么消息覆盖不了** | **这些系统不给我们发消息。**Discord 不会通知我们「你要发的那个 thread 归档了」,GitHub 不会主动说「head 漂了,你那条 review 记录作废了」。**没有对端可以给我们发收据。** |
| **现状实现** | 分散在多处:`isArchivedThreadError`(50083,`ChatThreadCreator.ts:80-85`,且**只管改名不管发言**)· `verify-approval` 的 `pr_head_sha` 校验 · `gh pr checks` 探针 · 配额监控 |
| **不用它会发生什么** | 本单**当场撞到过两次**:① bot 往归档 thread 发言把它弹回活跃且永不再归档(`plan.md` G-16);② 我自己在写完 code review 后差点被 `progress` 自动 commit 推走 head,那会让刚挣到的 review 记录和 Annie 还没点的批准一起作废。**这类失败的共同点是:我们这边一切正常,是外面变了。** |

### W-4 · 「活着但干不了活」—— **建议保留,但这是唯一一条建议交给 founder 拍的**

| 项 | 内容 |
|----|------|
| **它检测什么** | 进程没死,但无法推进:模型额度用尽、auth 过期、OOM/swap 打满、卡在交互式确认框 |
| **为什么消息覆盖不了** | 进程「活着」到不会被 W-1 判死,但**它的模型调用全失败** —— 它想报也报不出来。这是 W-1 和收据之间的**盲区带**。 |
| **现状实现** | `LeadWatchdog` 的 blocked-keyword 巷(**注意:FLY-1373 明确把它留在圈外,没关**) |
| **不用它会发生什么** | Lead 静默瘫痪。所有消息投递「成功」(文件写进去了),没有一条被处理,而 §4 的升级要等 30 分钟窗口 —— 期间 Annie 完全不知道。 |
| **⚠️ 但这条是历史上刷屏的重灾区** | FLY-193(pane_hash_stuck 误报)、FLY-218(529 限流被误判成额度用尽)、FLY-220(告警回声自放大 276+ 条)全在这条上。**保留它 = 同时继承它的误报史。** |
| **目标态必须附带的三条硬约束** | ① **每个 episode 只报一次**,恢复前静音(FLY-220 的 episode-latch 已实现,复用)② **去重键不能被内容搅动**(FLY-218/220 根因:内容变→eventId 变→绕过去重)③ **必须免疫自己的告警回声**(FLY-220 的 `ownStateRegion` 已实现,复用) |
| **⚖️ 这一条建议交 founder 拍** | 其余三条(W-1/2/3)是**结构性必需**,没有取舍空间。W-4 不同:它是**误报成本 vs 漏报成本**的权衡,而两边的代价 Annie 比我清楚。<br>**砍掉的后果**:Lead 静默瘫痪时,要等 §4 的 30 分钟窗口过完才会经「无收据」升级 —— **不是永远发现不了,是慢 30 分钟**。<br>⇒ 若她选「宁可漏也不要吵」,**这是一条可接受的取舍**,不是安全事故。 |

### ~~W-5~~ · 崩溃恢复对账 —— **被复核击穿,已降为「不单列」**

| 项 | 内容 |
|----|------|
| **它检测什么** | Bridge 崩溃/重启那一刻**正在途中**的消息与状态:未销账的批次、孤儿 marker、状态机停在中间态的 session |
| **为什么消息覆盖不了** | 崩溃时没有任何一方有完整视图 —— 发送方以为发了、接收方没收到、账本停在半路。**需要一次外部的、全局的对账**,而对账本身不能是消息。 |
| **现状实现** | `complete-marker-reconciler`(loopback 重放 `/events`,`:19-23`;**关键安全性质**:marker 删除**不看 HTTP 2xx**,而是重读 session 状态验证,含糊的进 quarantine `:25-31, 70-76`)· boot drain of orphaned markers(FLY-172) |
| **不用它会发生什么** | 已有实证(FLY-172 记录的 GEO-374 事故形态):runner 真的干完了,但完成上报卡在崩溃窗口 → session 停在 `running` → tmux 窗口死掉后被孤儿回收判成 **false `failed`**。**一次成功的工作被记成失败。** |

> ⚠️ **这一条被 Codex 复核击穿了,我接受。**
> 我在 §5 写过「欢迎删掉任何一条,前提是能回答消息语义怎么覆盖它」—— 复核**回答上来了**:
> **持久 claim + lease + 幂等重放 + boot recovery 本来就是标准 MQ 的崩溃语义**。
> `complete-marker-reconciler` 之所以现在必须存在,是因为**现状没有这些语义**,它是**旁路补偿**,
> 不是「消息语义天然覆盖不了」的东西。
>
> ⇒ **目标态若真按 §5 实现了 MQ 崩溃语义,W-5 就应当被吸收进去,不单列为 watchdog。**
> **保留的前提**只有一个:能举出**具体的非消息状态**(例如 tmux 窗口与 DB 状态的一致性)
> 必须独立对账 —— **那一部分才计数,且应当写清是哪一部分**。本文目前**举不出**,所以不计。
>
> **最小集合因此是 4 条,不是 5 条。**

## 3. 该消失的(不是关掉,是不再需要存在)

| 现状 watchdog | 为什么在目标态里不需要 |
|--------------|---------------------|
| misroute 捞回 | **入队时拒绝未知收件人** → 黑洞不可能存在(现状 `SendMessage to:"team-lead"` 之所以是黑洞,是因为 stock 工具不校验收件人且自动建文件) |
| lead-pending 催办 + 升级 | `processed_at` 超时是队列的一等属性,不需要外部巡逻 |
| checkpoint-park 巡检 | 同上 |
| 陈旧门驱逐 | 门被答 → 判据满足 → 自动销账 |
| AlertChannelHub T2 **按年龄**升级 | 改为**按收据状态**升级;「催已过的门」**结构性不可能** —— ⚠️ **前提是 `architecture-target.md §2.4` 的原子性三条成立**,否则「有收据」本身不可信 |
| delivery-ack / redeliver / dead-letter 巡检腿 | 队列内建(`architecture-target.md §3`) |
| 检测缺口扫描(gap-scan) | 缺口 = 无收据,队列自己看得见 |

⇒ **不轰炸是结构性的**(**前提**:`architecture-target.md §2.4` 的原子性三条成立):
目标态里没有「按时间催办」的组件,只有「按状态升级」的组件。
在那个前提下,一个已被处理的事项**不可能**产生催办 —— 因为催办的前提是收据缺失。
**前提不成立时,「收据」本身就不可信,这个性质随之失效** —— 所以原子性不是实现细节,是这套设计的**承重墙**。

## 3.5 一个必须澄清的反直觉点:heartbeat **是消息,但基于 heartbeat 的死亡检测是巡检**

有人会问:runner 不是在主动发 heartbeat 吗?那存活不就是消息语义能覆盖的吗?**不是。**

**heartbeat 确实是 runner 主动推的消息**(独立复核链路):
`Blueprint.ts:2154-2156` 的 `onHeartbeat` → `ExecutionEventEmitter.emitHeartbeat`
(`:210-214`,专用轻量路由)→ HTTP POST → `DirectEventSink.emitHeartbeat`(`:1259-1261`)
→ `UPDATE sessions SET heartbeat_at`(`StateStore.ts:4602-4605`)。

**但死亡是靠「这条消息在阈值内没来」判定的,而「没来」不是一条消息。**
任何协议都无法传递「我什么都没发」—— 只有外部轮询者能观察到缺席。

**还有一个坑,设计时必须知道**:`heartbeat_at` 这一列**被两方写**——
runner 推的 beat,**以及 Bridge 自己探测成功后代写**(`HeartbeatService.ts:1286`、`:1608`)。
⇒ **单看 `heartbeat_at` 区分不出「runner 说话了」和「我们探了一下它还活着」。**
现状对此有刻意的守卫:只有**肯定的 `alive`** 才允许刷新 heartbeat,
探测失败**只许告警、不许刷新**(`:1240-1249`),`indeterminate` 可以抑制回收但
「永不庆祝、也永不刷新 heartbeat」(`:165-171`)。目标态**必须保留这条守卫**,
否则「探测失败」会被误记成「它还活着」。

## 4. 一条必须写进设计的分类纠正

现状把**存活检测**和**投递看门狗**放在同一个 flag(`FLYWHEEL_LEGACY_DELIVERY_WATCHDOGS`)下,
于是 FLY-1373 退役投递看门狗时,**把 W-1(存活)一起关掉了**
(`RunnerIdleWatchdog.ts:257`、`HeartbeatService.ts:701` 等,见 `research.md §1.2`)。

**这是分类错误,不是决策错误。**投递机制可以被新的收据机制取代;**存活探测不可以** ——
它和投递根本不在一个层面。

⇒ 目标态的硬要求:**每一条都必须有自己独立的开关,且不得与任何「投递层」flag 耦合。**
(**这与 W-4 可由 founder 选择关闭并不矛盾** —— 恰恰相反:**那个独立开关就是她行使选择的方式**。
要禁止的是「关投递层顺手关掉存活探测」那种**耦合**,不是「不许关」。)
这条如果不做,下一次投递层重构会再一次顺手关掉存活探测,而且**同样不会有人发现**
—— 因为存活探测关掉之后的表现,恰恰是「很安静」。

## 5. 边界

- 本文是**论证**,不是实施计划:没有拆任务、没有 schema 定稿、没有排期。
- W-3 的「收口」具体怎么做(统一到一个外部状态巡检,还是各自保留)**本文不裁定**,留给实施 owner。
- W-4 的三条硬约束引用的是**已实现**的机制(FLY-218/220),但**是否足以覆盖目标态的新触发形态,未验证**。
- 四条是否**恰好**是最小集合 —— 这是我的判断,不是证明。欢迎继续删,前提是能回答「消息语义怎么覆盖它」。
  (W-5 已经这样被删掉一条,见 §1 末尾。)
