01 · 先看结论

这次修好了吗？

修好了。以前只要你改的文档不是 md/html/图片这几种，CI 就当成改了代码，整套重跑。这次把 txt、csv、log、jsonl、mp4、mp3、字幕等 13 种纯数据/媒体后缀也认成「文档」。我用 131 个对照用例逐项验过：这 13 种在四个文档目录里全部正确走快车道，目录外、以及没获批的后缀（json、yaml、tsv、脚本等）一个都没被放行。更重要的是，我抓到并确认这次顺手补上了一个原来就存在的漏洞——有 17 份文档其实被 CI 的测试读取，以前改它们会被当成普通文档放行、把该跑的检查悄悄跳掉，现在会强制跑全量。

原来会怎样

改一份 evidence.txt / run.jsonl / demo.mp4 → CI 判成代码改动 → 5 个单测分片 + 2 个 shell 分片 + 打包发布全跑，约 50 分钟以上 runner 时间。另有 17 份实际被测试读取的文档，改它们反而被当成普通文档放行，该跑的检查被悄悄跳过。

现在会怎样

同样的文档改动 → 走快车道，只跑 classify 和 quick-gate。那 17 份被测试读取的文档改动 → 强制跑全量。目录外、未获批后缀、大小写不符、混着代码改的，一律照旧跑全量。

QA 判断： PASS

02 · 怎么修

病根和修法

CI 里有一份「哪些文件算惰性文档」的清单。这份清单原来只写了 13 种后缀，纯数据和媒体类的后缀漏了。漏了的后果不是报错，而是安静地多花钱：改一份 evidence.txt 或一段 demo.mp4，CI 照样把 5 个单测分片、2 个 shell 分片和打包发布全跑一遍。

真正的病根

判断逻辑是「路径要落在四个 doc/ 目录内，且后缀要在清单里」，两个条件必须同时满足，任何拿不准的情况一律按「跑全量」处理（fail-closed）。所以漏后缀不会出错，只会浪费。清单从 13 项补到 26 项后，判断结构一行没改。

修复原则

只加清单，不动判断结构；拿不准一律跑全量；新增的宽松必须配一道自己的围栏。

具体改了什么

  • 把 FLY-1987 账本里认定的 13 个纯数据/媒体后缀（txt、csv、log、out、jsonl、wav、mp3、m4a、ogg、mp4、webm、vtt、srt）补进惰性清单。我把生产脚本、账本、测试三处逐项比对过，26 = 13 旧 + 13 新，不多不少。
  • 新增 17 条「确切文档路径」围栏：这些文档虽然是 .md，但真的会被 CI 的测试读取，改它们必须跑全量。这是本次新增宽松带来的自我约束，也顺手补上了原来就存在的漏洞。
  • 把清单和围栏钉进一个「永远都会跑」的检查里（quick-gate）。任何人日后改动清单、改动围栏、改名或删掉被围栏保护的文档、甚至改动那两个真实读取者，CI 都会立刻变红并点名说缺了哪一项。

06 · 诚实边界

什么没测，为什么

没有藏起来的空白

「快车道在真 GitHub Actions 上确实让四条 lane 变成 skipped、而 CI OK 仍然绿」这一句，我没有实测。

原因： 要实测就得专门推一个牺牲性的纯文档 PR 上去。本次改动没有碰 CI 的流程图和聚合逻辑，快车道这条腿是几个月前就在生产上跑着的既有路径，所以风险低——但这句话我只能靠推理，不能靠实测背书，就照实写出来。建议合入后第一个碰到新后缀的纯文档 PR 顺手确认一次。另外两条边界：一是围栏的完整性我只能覆盖静态查得到的三种写法，目录和文件名两端都是变量的完全动态拼接谁都查不到（缓解是那道 always-on 的活体检查，而且这条残余风险在本次改动之前就存在，本次反而净减少了 16 个已知漏洞）；二是省钱额度按账本口径为 0，本报告不从这次改动推算任何金额。

风险与补测时间： 可回滚：删掉 13 个后缀和 17 条围栏就回到改前行为，没有数据库、没有状态、没有部署动作。Follow-up 两项：① 合入后在第一个纯文档 PR 上确认快车道真的跳过了 lane；② 实现方的行为 suite 每个新后缀只测一个目录，我的台架测的是 4 个目录 × 13 个后缀全矩阵，建议后续把矩阵补齐。
