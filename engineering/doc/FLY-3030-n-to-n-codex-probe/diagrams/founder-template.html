FLY-2919 换体续干探针：一行 README，写成「随时可杀、随时可续」的合同

● 一句话总结
下游执行体只需在沙箱仓 README.md 末尾加一行 FLY-2919 N-to-N codex-body probe 并交卷；本设计把每一步都写成幂等的 （幂等 = 同一步做一次和做十次结果一样，已经做过的会自动跳过）， 所以不管执行体在哪一步被杀、换成新体从头重跑，最后都只会有 1 行字、1 个提交、1 个 PR，正好配合 FLY-2919 去检验「死体换体、同一对话续干」。
● 背景：FLY-2919 要验什么

执行体（body）——真正在干活的那个 AI 进程（这里是 Codex）。FLY-2919 在隔离测试房里故意折腾它，验收四件事：

验收点谁负责本设计怎么配合
死体当场终结并换体引擎新体从任意中间状态都能安全接着干
活体丢窗口不判死引擎计划里没有任何一步看「窗口还在不在」
同一 thread 续干（thread = 与 Codex 的同一段对话记录）引擎进度只认 git 与 GitHub，谁接手都读得出来
交卷回 thread引擎 + 执行体只用系统注入的回执命令交卷
● 核心流程图：执行体走的状态机

状态机——把任务切成几个可检查的状态，每步先看「现在处在哪个状态」再决定做什么。每个状态都有 git 上看得见的判据；被杀后新体从「Task 0 预检」重新判断即可。

{{D1}}

冻结——里程碑文件（milestone，交卷前的最后一份说明）一旦提交，分支就不再写任何东西，只剩对这个最终提交做代码评审、等 CI、交卷。这保证 milestone 永远是最后一个提交，代码评审也只针对这个冻结后的最终提交，批准不会因为之后又有提交而失效。

● 换体续干：一次「杀掉 → 换体」的时序
{{D2}}

新体 B 不需要旧体 A 告诉它做到哪了——它自己去看 git 与 GitHub（唯一真相：只有一个地方说了算，避免两份记录对不上），发现已做过的就跳过。

● 数据 / 结构模型：状态存在哪里、怎么判
{{D3}}
  • README.md：现在 44 字节 3 行，末尾已有换行；追加后应为 77 字节 4 行。
  • progress.md 账本（进度记事本，方便重启后看做到哪）：只作提示，是否跳过某一步只看 git 判据。
  • PR（Pull Request，请求把改动合进主分支的申请单）：同一分支只允许 1 个 OPEN 的。
  • 精确头 CI（CI = 自动跑的构建与测试；精确头 = 就是 PR 最新那个提交）：全量测试证据只认它。
● 关键取舍与否决方案
方案结论理由
A. 幂等状态机采用任意时刻被杀都收敛到同一终态；设计阶段在临时仓演练 17 个场景全部符合预期
B. 直接「追加 → 提交 → 推送」顺序跑否决换体重跑会追加第二行、第二个提交，正好污染 FLY-2919 要看的「续干」证据
C. 重写整个 README否决改动面变大、diff 不止一行，没有收益
E. 先评审、后写 milestone否决评审批准绑定的是「当时的最新提交」；之后再提交 milestone 会让批准失效（Codex 设计评审第 1 轮指出）
D. 用账本文字决定跳过哪步否决账本本身也会在半路被杀时停在旧值；git 状态才可靠

演练中抓到并修掉的真问题：完工后换体重跑时，中间步骤的账本更新会在 milestone 之后再落提交 → 加了「冻结后账本更新自动跳过」。独立的 Codex 设计评审（gpt-6-astra，最高推理强度）跑了 4 轮才批准：先后指出「评审后又提交导致批准失效」「CI 失败仍交卷」「越界文件先推送后才发现」「跨步骤变量丢失」「受限沙箱里临时文件失败会让守卫静默放行」等问题，全部改掉，并在临时仓演练 17 个场景验证。

● 诚实边界：做什么、不做什么

这份设计做到的：

  • 给下游执行体一套可逐字照抄的 POSIX sh 命令，每步带判据、断言和「异常就停下问 Lead」的出口。
  • 保证换体重跑不会重复写行、重复提交、重复开 PR，也不会破坏「milestone 最后一个提交」。

这份设计不做 / 不保证的：

  • 不负责「死体判定、换体、丢窗口不判死、同 thread 续干」本身——那是引擎的行为，由 FLY-2919 QA 按驱动器回执判定。
  • 设计阶段的演练用的是替身命令（假的 flywheel-comm / gh），真实推送、真实 PR、真实 CI 要到实现节点才发生。
  • 不跑任何本地全量测试；这是纯文档改动，全量证据只认 PR 精确头 CI。
  • 不合并、不上线、不碰生产。
