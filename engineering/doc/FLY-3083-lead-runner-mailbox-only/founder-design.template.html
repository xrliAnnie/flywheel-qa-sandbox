FLY-3083:Lead 给 Runner 发消息只走一条路

工程设计说明 · 2026-09-29 · 分支 project-slot-3-FLY-3083 · __REVIEW_META__ · 每个卡片下方都可以留意见,页底一键汇总复制

1. 一句话总结

给 Lead 装一个「护栏」:它想用 Claude 自带的 SendMessage(Claude Code 内建的队友私信工具)给 Runner 发消息——不管是点名发还是「群发给所有队友」——都当场被拦下并拿到一条可直接运行的正确命令;所有能带 Runner 的 Lead(部门 Lead 和 CoS,Claude 和 Codex 后端)共用一份「Runner 通道契约」:给 Runner 发消息只有 flywheel-comm send(Flywheel 自己的信箱投递命令)这一条路;投递命令把「写没写进去」说清楚,通道卡住时有明确的发现和升级动作,不再靠旁路。

回答你 9-29 的两个问题:① 规矩还要,但只剩一句正向指引「给 Runner 发消息用 flywheel-comm send / respond」;② 机制现在能兜住——护栏拦住之后,规矩只是省一个回合的提示,不再是正确性的依赖。

2. 现状:两条路,一条留底一条不留

Lead 现在有两种办法给 Runner 发消息。走 flywheel-comm send 的,先在 CommDB(Flywheel 的通信账本数据库)写一行、拿到编号,再投到 Runner 的收件箱并叫醒它;走 SendMessage 的,只写收件箱文件——消息能到,但 Flywheel 完全不知道这封信存在:没编号、没送达记录、丢了没人报。9-29 实测:SendMessage 发的十几条一条都没留底;flywheel-comm 发的 249 条全部有账。

__SVG_D1__

为什么会这样:5 月 FLY-142 时,Flywheel 的信箱就是 Claude 自带的队友收件箱文件,所以规矩写「日常聊天用 SendMessage」。5 月底 FLY-168 让 flywheel-comm send 变成「账本 + 收件箱」双写,7 月 FLY-1547 又升级成有编号、有状态的 v2 信箱——机制一路进化,规矩没跟上。而且代码里自己也打架:启动脚本的注释说「必须教 Lead 用 SendMessage」,另一处系统提示又说「用 flywheel-comm send(不是 SendMessage)」。这份规矩所有部门 Lead(Tadashi、Aunt Cass、Mufasa 等,含 Codex Lead)都装同一份。

3. 核心流程:护栏拦下 → 给命令 → 走账本投递

护栏是一个 PreToolUse hook(Claude Code 在每次调用工具之前先跑的一段小程序,可以否决这次调用)。它只盯 SendMessage,收件人是 Runner 的队名(形如 runner-xxxxxxxx,由 Flywheel 唯一生成)就拒绝,并把正确命令原样喂回给 Lead;收件人是别人(其他 Lead、founder)照常放行。

__SVG_D2__
  • 拒绝时 Lead 看到什么:一段可直接复制的命令,例如 flywheel-comm send --from tadashi --to runner-42afa86c "…";答 gate(Runner 停下来等 Lead 拍板的问题)仍用 flywheel-comm respond。
  • 也拦「群发」:SendMessage 的收件人写 * 会发给团队里所有人,Runner 也在其中——同样不留底。在 Flywheel Lead 的会话里群发一律拦(第二轮评审证明「先看名单再放行」有竞态:看名单时没 Runner,下一秒新 Runner 登记进来,群发照样写进它的收件箱);要联系非 Runner 队友就逐个点名,零功能损失。
  • 命令是安全的、完整的:正文里的 $变量、反引号、引号、换行都原样保留(用 shell 引用规则整体转义),不截断;协议类消息不给命令。
  • 只拦不代发:护栏不替 Lead 把消息发出去(见第 6 节的取舍),Lead 下一回合自己跑命令,拿到编号。
  • CoS 与 Codex Lead 也覆盖:新写一份很短的「Runner 通道契约」,同时注入部门 Lead 和 CoS(CoS 也可能自己带 Runner——这是设计评审抓出来的原规矩漏洞),Claude 和 Codex 两种后端都装。Codex Lead 没有 SendMessage 工具;它直接操控 Codex Runner 的旁路(codex queue --remote)本单只在契约里明令禁止,机制拦截留后续单——不假装已经封死。
  • 装在每个 Lead 自己的工作区:护栏写进 Lead 工作区的本地设置文件;Lead 启动脚本、运维手动安装/卸载全部走同一把工作区锁(不会互相覆盖,不和其他全局护栏抢同一个文件,也不会因为 Claude 配置目录切换而装错地方)。评审已从 Claude Code 源码确认:这种本地设置里的护栏在 Lead 的「跳过权限确认」模式下照样生效。一个环境变量开关可关(QA / 回滚用)。

4. 数据 / 结构模型

三样东西各只有一个来源:Runner 的队名由一个函数生成(执行 id 前 8 位);账本里每封信一行(编号 + 送达时间);flywheel-comm send 是唯一往账本写信的入口。本单给 send 加两处小改动:接受 Runner 队名当收件人(以前必须给 36 位的全长执行 id,护栏拿到的只有队名),以及把「传输层写没写成功」放进返回结果(诚实地讲:写成功 ≠ Runner 已读,后者要看回执)。

__SVG_D3__

队名 → 全长 id 的解析「宁缺毋滥」:只有精确的 runner-xxxxxxxx 形状才去查,找不到或找到不止一个都直接报错、不写账本——没有确定收件人的信不留底;其他任何写法(全长 id、老测试用的自定义 id)原样放行,现有行为一字不变。

5. 只走一条路之后,通道自己卡住了怎么办(Tadashi 的补充)

9-29 Lead 之所以改用 SendMessage,是因为 FLY-3071 让信箱通道长时间卡住。只走一条路后,不能再靠旁路兜底,所以要回答「怎么发现、怎么办」:

__SVG_D4__
  • 发现:send 的返回结果带 transport_write = ok / skipped / error(以前失败只在错误输出里打一行 WARN)。ok 只表示写进了传输层;「写进去了但 Runner 十分钟没回执、而且 Bridge 报它空转」只算疑似停滞——是调查触发器,不是确诊(Runner 也可能已读但在等外部条件)。skipped 有两种正常情况(回滚模式、无传输后端的 Runner),不当故障处理。
  • 兜底:账本那一行已经写了(信没丢)。Lead 收集证据(编号、写入时间、最后一次终端截屏、Bridge 空转事件),照契约里的完整命令模板报一个新的告警类型 mailbox_channel_fault(区分「即时写失败」和「疑似停滞」;以「Runner + 情况 + 这次故障的第一条消息编号」为一个事件,同一次故障重试自动去重、恢复后再犯算新事件;告警脚本路径由 Lead 启动时显式注入——评审发现原先假设的环境变量其实进不了 Lead 进程;「重复」只说明有人报过、不证明送到,Lead 没有送达凭据时必须改在 issue thread 明文报告)——不凭空重启 Runner,不套「卡住 Runner」处置阶梯,更不换旁路。这条分支表同时写进契约和护栏的拒绝文案。
  • 边界:本沙箱的 Bridge 没有投递进度探针(它的健康接口只能证明进程活着,不能排除信箱故障),设计里如实写明;生产的 v2 信箱若有排队状态查询(FLY-1547),就用「排队超过十分钟」作直接证据。Bridge 投递循环本身停滞(真 FLY-3071 形态)在沙箱无法注入,归 FLY-3071 / v2 验收。信箱到 Runner 的最后一段怎么投由 FLY-2127 定,本单不重复。

6. 关键取舍与被拒方案

方案判定原因
护栏拦下后自动替 Lead 发进信箱先不做Lead 的记录里显示「被拒」但信其实发出去了,审计混淆;AI 一重试就重复投递;护栏里带副作用要另设记账;Codex Lead 没这条路,不对称。观察生产被拦频率,高了再做。
Bridge 事后巡检收件箱、把 SendMessage 的信补录进账本拒等于把第二条路合法化,不是「一条路」;分辨来源靠前缀,脆。
只改规矩,不加机制拒你明确要机制兜住;9-29 证明规矩挡不住临时兜底的冲动。
拆掉 Runner 在 Lead 团队里的登记,让 SendMessage 根本发不到拒flywheel-comm send 自己叫醒 Runner 也靠这个收件箱,拆了等于拆信箱。
护栏装进全局 Claude 设置(第一版方案)拒(评审改)Lead 可能用另一个 Claude 配置目录启动,全局装法会装错地方却报成功;而且和另外两个全局护栏抢同一个文件、没有共享锁。改为 Lead 工作区本地设置 + 既有工作区锁。
群发按团队名单豁免(第二版方案)拒(评审改)看名单和真正发送之间有「新 Runner 刚登记」的竞态,评审用原生群发代码复现了;改为 Flywheel Lead 会话一律拦。
把「写成功」当通道健康拒(评审改)写成功只是写进传输层;消费停滞要用「没回执 + Bridge 报空转」判定。
护栏自己查数据库把队名换成全长 id拒会出现第二份读账本的逻辑;改成 send 命令直接接受队名,只有一个真相。

7. 诚实边界:这个设计做什么、不做什么

  • 做:Lead 侧护栏(拦点名与群发 + 给安全完整的命令)、send 接受队名并外露传输结果、一份所有 Runner-capable Lead 共用的通道契约 + 四份规矩与启动脚本注释统一、一个新告警类型、回归测试(喂 SendMessage 给 Runner / 群发,断言被拦,且文案里的命令经 stub 命令行 round-trip 后参数逐字节正确)、一键卸载 / 环境变量开关回滚。
  • 不做:Runner 回报 Lead 的方向(FLY-208 已有黑洞巡检);信箱到 Runner 的最后一段(FLY-2127);信箱排队状态查询(FLY-1547 / FLY-3071);用机制拦 Codex Lead 的 codex queue --remote 旁路(契约禁止,机制记为后续单);顺带发现的 FLY-913 护栏装错配置目录的老问题(另开单)。
  • 已知残余:AI 可能连续两次撞护栏,多花一个回合;Flywheel Lead 会话里群发这一种用法被整体禁用(逐个点名替代);「疑似停滞」用的是十分钟无回执 + Bridge 空转信号,只触发调查,不是确诊。
  • 沙箱说明:本设计在测试沙箱(v1.55.0,没有 v2 信箱)上审计;对 send 的改动只有「解析队名 + 外露结果」,与 v1/v2 信箱无关,实现时以生产分支为准合并。
