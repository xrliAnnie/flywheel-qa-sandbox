## ① 为什么重做 — 回溯

抄 Claude Code 起家没有错。Flywheel 的现实多出四件事：DAG（一个 issue 拆多 session）、
7×24 无人值守、跨厂商（Codex 耳朵不同）、Founder gate（ship 需要 Founder 批准）。

v1 的病根是每碰到一样就自创一块流程机器，再让机器看管机器：watchdog 看 watchdog、收据追收据。
结果是 watchdog 噪音刷屏、接力棒三次挡 ship、假 blocked 作废批准、retest 凭据连环死结、重启不换真身。

## ② 三条设计原则

### 抄作业

机制全抄 Claude Code：1 秒轮询、忙时排队、喝干循环、无 watchdog、无门铃。
只在完全不能照抄处偏离：

- 存储进入 SQLite，保证不丢；
- 处理完才销账，Claude Code 是读到即标已读。

### Agent-first（方案乙）

能让模型做的绝不写专用代码。Agent 亲手做一切，工具薄壳只自动记账。
没有派发器、执行者注册或认领。

### 真实复杂性必须接，但用最小数据接

DAG、无人值守、跨厂商、Founder gate 各以几张表和一条规则接住，不发明流程机器。

## ③ 数据层 — 一个 SQLite 文件，六类表

| 表 | 存什么 | 为什么必须有 | 谁写谁读 |
|---|---|---|---|
| `mailbox` | 发给任何人的所有话，按 `to_agent` 分 | 五个信箱合一；信先落库，永不丢 | 采集器/任何 agent 写；收件人自己读 |
| `processing_attempts` | 每封信每次处理的成/败/崩记录 | 崩溃账目精确；死在第 50 条，51–100 无损 | 收件人的薄壳自动写 |
| `tasks` + 依赖边 + attempts | DAG 节点、依赖、每次尝试及证据 | phase/state 必须落成数据；重启后能查工作进度 | Lead 建；runner 更新 |
| `gates` | ship 门状态 + 批准绑定的 head | review 后才能 ship；批准不依赖会话活着 | 完成事务开门；Founder ship 落批准 |
| `actions` | 对外动作的待做与结果流水 | 断电后回答哪些做了；由工具薄壳自动写 | 工具薄壳写读 |
| `config` | 全部数值参数 | 不许写死第二个数 | 人改；所有件读 |

一致性由三件套保证：

- 所有表在同一文件，跨表写进一笔事务；
- `UNIQUE`、`CHECK` 与 append-only trigger 由数据库执法；
- 崩在任何一步，整笔回滚。

## ④ 消息生命周期 — 拉为主，处理完才销账

- 收：每个 agent 的壳每 1 秒查询一次自己名字。50 agent 的估算负载是单核 0.25%；闲 agent
  后续可直接下线（FLY-1510）。
- 处理：喝干循环是代码 `while`，不是记性。取 1 条，处理（即转化；小时级工作登记为 task 交 runner），
  销账与产物同一事务，再取；空了才睡。
- 丢失防线：“看了”这个动作不存在。每条消息唯一出口是自己的事务 commit。
- 死信：第 N 次失败，N 来自 config；管理者必须收到告警。源稿写“业务信改投 Lead”，本单后续由
  Lead 明确收敛为“原信 dead、不重路由，追加一次性 dead event，由消费方按 DAG 现查通知对象”。
- 公平：Founder 信走 VIP 道，使用有界优先与超龄晋升，参数进入 config。

## ⑤ 会话生命周期 — 醒、睡、死、接班

- agent 结构：厂商 CLI + 我们的壳 + 各家耳朵垫片。垫片是唯一 per-vendor 代码，新厂商只加一个小垫片。
- 睡：进程活着但 LLM 不烧 token；轮询照跑，来信即醒。
- 下线：进程退出，信留库无损；冷启动目标 1–2 分钟（FLY-1510）。
- 死（假活）：轮询捎带心跳；有 pending 且心跳停止时自动重启，反复失败才告警 Founder。
  进程级死亡仍由 launchd 管。
- 接班：先杀干净是第一道；世代号是保险丝，数据库拒绝僵尸旧会话的迟到写入。它替代 TURN 的另一半。

## ⑥ DAG 与工作 — 图是数据，返工原子换装

- 模板是 tasks 行和依赖边；三段式、单 session、并行分支都是数据形状，引擎不特判。
- 每节点恰好一个 active attempt，由唯一索引约束；并行工作使用多个节点。
- 返工/retest 是同一节点的新 attempt，在一笔事务内让新尝试装备齐全并收干净旧尝试。

## ⑦ 对外动作与 ship — 方案乙

- Agent 亲手调用工具，薄壳自动记录 actions 黑匣子。
- 查询与写入使用不同动词，防止读操作误触批准。
- ship 是最后节点（通常是 ship 报告节点）完成事务的一部分：事务内查询图上是否还有未 done 节点；
  没有则开启带报告的 gate。没有扫描者，“最后”是查询结果而不是固定身份。
- Founder 批准写入 `gates` 并绑定当前 head，不依赖任何会话活着。
- 活着的 agent 亲手执行；若没有活 agent，由调度唤醒一个。

## ⑧ 调度进程 — 系统唯一常驻小件

一个几十 MB、零 token 的常驻进程只做“看库后拉起进程”：

1. 节点 ready，拉起对应 runner；
2. 收件人有 pending 且不在线，拉起；
3. 有信且心跳停，重启；
4. 对反复重启做风暴刹车。

它自己死亡由 launchd 拉起。它不读消息内容、不做路由、不执行动作，不成为 v1 Bridge 式中枢。

## ⑨ 删除清单与事故对照

| 删除 | 对应事故 | 替代 |
|---|---|---|
| watchdog 全家 | 大量噪音；误报已归档 thread | 心跳 + 自动重启 |
| TURN 接力棒 | 多次阻挡 ship | 每节点唯一索引 + 世代号 |
| 五个信箱 | respond 写错通道后石沉大海 | 一张 mailbox |
| 门铃/30 秒投递扫描 | 1 秒轮询使其多余 | 轮询即唤醒 |
| 病历卡 obligations | 收到卡也无可执行动作 | 删除，不留后门 |
| 派发器/执行者注册/认领 | Agent-first 裁决 | 方案乙 |
| 独立死数字 | 时间窗作废批准 | 参数全进 config，同源 |
| 幽灵重派发 | 重启误派多个 implement | 派发只查库条件，重启后条件不满足就不派 |

## ⑩ 改变主意的轨迹与裁决台

四次改向及原因：

| 改向 | 原因 |
|---|---|
| 执行者（甲）→ Agent 亲手（乙） | 专用执行者维护成本过高；薄壳足以保住收据增量 |
| 门铃 → 纯 1 秒轮询 | Claude Code 本身无门铃；门铃是从省查询出发的过度设计 |
| 病历卡 → 心跳 + 自动重启 | 病历卡只产通知，唯一有用动作是重启 |
| phase wake “被吸收”的表述拆开 | 唤醒指针与阶段状态被混为一句；两半应各归其位 |
