调查发现:引擎自动合入后的收尾链其实已经存在并且当天全自动跑通了(你看到的"没收尾"另有原因,下面讲清);本单要做的是把收尾链在边角形态下焊死——让 generic 类型的工人体享受和 implement 一样的四层收网、把停驻台账的三处硬伤补上、让诊断和提示不再说误导人的话。

① 8-24 当天到底发生了什么(账本还原)

当天 FLY-2000 和 FLY-2015 两单由 generalized 引擎(Flywheel 的自动流水线:把一张 issue 拆成 设计→实现→QA→合入 的自动流程)走 land(流水线最后一步:引擎亲自执行合并代码)合入。事后的印象是"工人体没收、thread 没归档"。我们把数据库账本逐条对了一遍,真实时间线是:

时刻 (UTC)发生了什么快慢
05:57 / 06:09两单的实现工人交付 PR,进入停驻(ship_parked:交完活先不关,等你批准,万一打回还能返工)—
07:44 / 08:20QA 通过,批准卡片发给你—
17:12 / 17:13你点了批准 → 引擎立即合入—
17:13-17:16停驻的工人体被收掉合入后 35~63 秒
17:14 / 17:16issue thread 自动归档成功合入后 ~2 分钟

那"没收尾"的印象从哪来?三个来源,都不是收尾链坏了:

  1. 批准前的正常等待被看成了"合入后没收"。工人 6 点交活、你 17 点批准,中间 11 个小时它一直停驻着——这是等你批准的设计行为,不是合入后的滞留。
  2. 你在归档后的 thread 里发了话。FLY-2015 的 thread 17:16 归档成功后,你在里面发言(Discord 会自动把它重新打开),系统按 FLY-1709 的保护规则不再自动收起你正在用的 thread——所以它看起来"一直没归档"。这个保护是你之前拍板要的,本单原样保留。
  3. Tadashi 手动扫的那两轮(17:24 / 17:32,对应你的两条消息)扫出来的结果大多是"早已归档"。

立单时的判断("generalized land 缺收尾链")经 Tadashi 确认是误读,他会改 issue 标题防后人再误读。8-24 两单从"待修对象"改判为"链条已通的证明"。

② 核心流程:收尾链与本单要补的位置

你批准之后,引擎自动做完下面五步——这条链和老的 🆒 自助合入路径用的是同一份代码。本单要补的是第①步里 generic 体的"收网层数":

"generic 节点"= 流水线里的通用单步工人(比如写文档、做调研的单步任务),对比"implement 节点"= 标准三段流水线里的实现工人。两种工人干完活的收法目前不对等。

③ 数据模型:停驻的"两本账"与结算

工人停驻时,系统同时记两本账:状态账(这个体现在是什么状态)和停驻台账(park ledger:只增不删的流水账,记录"谁为什么停驻、停驻何时解除")。合入完成后由结算器把两本账一起收口。本单在结算器上补三处硬化:

④ 本单做什么 — 四刀

刀 1generic 体收网对等(先做)

implement 工人的体有四层收网:优雅关闭 → 卡死强收 → 批量收编 → 兜底;generic 工人的体只有两层(直接杀 + 兜底)。当 generic 体的窗口卡死时,没有强收兜底,合入收尾会反复重试直到卡死等人工。本单把三个"只认 implement/design/qa"的判断点加性扩展,让所有流水线管理的体(含 generic、review)进入完整收网;普通老路径的体一行不动。

刀 2generic 也能停驻等返工(后做)

现在只有 implement 工人交付后会停驻等你批准;generic 工人交完就关,你打回时没有体可返工。本单把"谁能停驻"从写死的节点名改成按能力判断(能交 PR + 声明保活的节点)。诚实说明:停驻给的是"可返工的持久地址",不保证进程还活着——死体返工会自动重新派工(已有机制),这点和 implement 现状完全一样。

刀 3停驻台账结算硬化

三处:①另一种停驻理由(runner_ship_gate_wait)过去永远没人清账,补上;②9 个会触发结算的调用方逐个限定"允许清哪种理由",防止活体被误清;③结算器静默跳过的情况改为留审计痕迹。

刀 4诊断与提示说真话

①收尾失败时报的"原因:unknown"是因为失败细节在传递中被丢掉了——修传导链,让重试原因变准;②"thread 未归档"的豁免提示原文是"原因解除后会自动重试",但你发过言的 thread 其实永远不会再自动归档——改成真话:"你在这条 thread 发过言,它会保持打开;需要收起时由 Lead 手动处理"。

实施顺序是硬约束:刀 1 先落地并测试全绿,刀 2 才允许打开——先有收网能力,再制造停驻体。

⑥ 诚实边界 — 这个设计做什么、不做什么

做

  • generic/review 等流水线体获得与 implement 对等的四层收网(含卡死强收),合入收尾不再因 generic 卡窗而挂起等人工。
  • generic 交付后停驻,打回返工有持久地址(死体自动重派)。
  • 停驻台账三处硬化;失败原因传导变准;归档豁免提示改真话。
  • 验收:一单 generic 经你批准 + 引擎合入后,无人工介入体全收、thread 自动归档;你发过言的 thread 不强收;老 🆒 路径逐字节不回归。

不做(留 follow-up 单)

  • 不修"工人被提示立即退出、账上却记停驻"的语义矛盾(D3)——本单如实继承并用测试兜住,根修另立单。
  • 不接线停驻凭证的唤醒消费者(FLY-1448 遗留死代码)——与本单验收无关。
  • 不动 FLY-1709 归档保护、老 🆒 路径行为、合入重试预算(FLY-1940)、held 恢复(FLY-1861)。
  • 不承诺停驻体"活着等返工"——只承诺可达、可自动重派。
