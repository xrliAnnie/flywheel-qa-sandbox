FLY-2127 · Codex runner 叫不醒 / 停着空转 — 根治设计

Issue FLY-2127（合并 7 张同类病根单） · 设计节点 · 2026-09-30 · 作者 eng_design runner

1一句话总结

以后 Lead 发给 Codex runner 的每一条话，都直接打进 runner 自己的「控制口」（codex app-server 的 socket），忙时插话、闲时排队、停着时顺手把它叫醒；runner 看到那句话才算送达；连送 3 次都送不进去就报警给 Lead，再由带审计的 tmux 按键兜底。

术语解释：runner = 干活的 AI 工人进程；Codex = OpenAI 的编码 agent（我们的 runner 有 Claude 和 Codex 两种）；app-server = 每个 Codex runner 旁边常驻的一个小服务，Bridge 通过它下指令、收进度，就像遥控器；Bridge = Flywheel 的调度中枢进程；Lead = 管 runner 的 AI 主管（Discord 里那位）。

病根现在 Lead 的话被写进一个 JSON 文件，指望 runner 自己来读；Codex runner 一「停车」（做完 goal、自判卡住、阶段结束）就永远不来读，唯一能叫醒它的是人工在终端敲 /goal 和回车。 覆盖的病根单FLY-2127 主单 + FLY-2464 / 2480 / 2502 / 2569 / 2905 / 2953（详见第 5 节） 依据founder 2026-09-29 批「可以被取代的直接取代」；FLY-3064 已验证 Codex 原生能力 queue/add、turn/steer、goal/set active 可用 预估2–3 人日；改动集中在 Bridge 内的 Codex 适配层与 flywheel-comm 的投递入口；Claude runner 路径零改动

2核心流程：一条消息怎么送到 runner 手里

CommDB = Flywheel 自己的 SQLite 小数据库，所有 Lead↔runner 消息的持久记录；lane = 本单新增的「投递员」，常驻在 Bridge 里、每个 Codex runner 一个；turn = Codex 的一轮思考+行动；goal = Codex 里的长期目标对象，有 active / paused / blocked / complete 四种状态；RPC = 远程过程调用，也就是通过 socket 发一条命令。

runner 当时在干嘛用哪条原生命令效果

3数据与结构模型

不建新表。复用 CommDB 里已有的 runner_phase_wakes 队列表（每条待送消息一行，按 execution + message id 唯一去重），只加三列：attempts（送了几次）、last_error（最后一次失败原因）、exhausted_at（何时放弃）。

4关键取舍与否决的方案

方案结论为什么
A · Bridge 内常驻 lane，CommDB 是唯一入口（选定）采用Bridge 已经握着每个 runner 的控制口连接；CommDB 本来就是共享的持久记录；Bridge 重启后 runner 重新接管时队列还在，能补送。不引入新进程、不引入两个进程抢同一个 socket。
B · Lead 的命令行工具自己连 runner socket否决包依赖会成环（flywheel-comm ↔ claude-runner）；两个进程同时控制一条 thread，runner 里的「goal 被外人换掉」守卫会误判；Bridge 挂了照样送不到。
C · 不换通道，只在 wake 用尽时通知 Lead + tmux 敲键（issue 原修法）否决，降为最后一级兜底founder 已批「可被取代的直接取代」；tmux 按键本身不可靠（菜单挡键盘、TUI 没开、cmux 断连）。

几个小决定（默认值，Lead 可改）

  • 升级阈值：3 次失败，退避 2s / 8s / 30s，总计不到 1 分钟就升级——远早于 FLY-2096 那口 60 分钟的 stall 钟。
  • 先排队再激活：停驻时先 queue/add 再 goal/set active，保证叫醒时嘴里已经有话；M0 探针若证明排队本身就能自起，激活只当幂等补刀。
  • 旧文件：lane 启动时若发现旧 JSON inbox 里还有没读的消息，一次性并入队列再删文件，下个版本删这段过渡代码。
  • 回滚开关：FLYWHEEL_CODEX_NATIVE_DELIVERY=0 回到旧路（默认开）。

5诚实边界：这份设计做什么、不做什么

做到

  • Lead / 引擎 / 批准流 / 三段式 rework 发给 Codex runner 的消息，全部走原生 RPC，runner 真读到才算送达。
  • 停驻三态（paused / blocked / complete）收到消息自动续跑，不需要任何人碰终端。
  • 送不进去有限升级：事件 + Discord 告警 + 带审计的 tmux 兜底，不再静默。
  • 七张病根单的落点：主单与 2502 / 2569 / 2905 / 2464（投递与停驻）直接根治；2480（完工 drain 的 digest 匹配）因回执改为「看到 userMessage」而不再依赖 digest；2953（等 CI 无人唤醒）只保证「一旦有人写入就一定送到」。
  • Claude runner 的收信路径零改动，QA 只做回归。

不做

  • 不做 CI 完成后自动写一条唤醒（FLY-2953 自己的写点，另单）。
  • 不做 instant_interrupt（Codex 尚在开发，FLY-3066 周更再决定是否灰度）。
  • 不做 Bridge 进程整个崩掉后自动重建 runner 适配器（FLY-1269 已列 follow-up）；本单只保证队列持久、重新接管后补送。
  • 不动 Codex Lead 后端（Mufasa 那条线）。

已知风险

  • 原生命令的参数名与「看到 userMessage」的通知名要在本机 Codex 0.159 上用 M0 探针实测再定，plan 已留备用回执方案。
  • blocked 有可能是真卡（沙箱拒绝等）；进 hold 时会写一条 Lead 可见事件，stall 钟照常管。
