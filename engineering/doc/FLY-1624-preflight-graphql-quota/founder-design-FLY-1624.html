FLY-1624 · GitHub 配额燃烧根源修复 — 设计稿

2026-08-03 · 设计节点交付 · Codex 设计评审 15 轮通过 · 每个卡片下方都可以留评论,页面底部一键汇总复制

① 一句话总结

找到了每小时烧光 GitHub 5000 次查询额度的真凶 —— 发货巡检程序对三个 PR 每秒问一次 GitHub、且对已经合并的 PR 永远不罢休;本设计给它装上「问过就记账、记过就闭嘴」的纪律:确定的结论写进持久账本,之后一次都不再问。

② 出了什么事(实测数字)

GitHub 给每个账号两条独立的查询额度,各 5000 次/小时:GraphQL(gh 命令如 gh pr view 默认走的通道)和 REST(gh api 走的另一条通道)。今天全舰队实测烧 5,640 点/小时,超过 GraphQL 预算,导致 529 测试房的检查误报「沙箱仓库不存在」还附了一条跑不通的修复指令。

  • 生产 Bridge 自己在近乎连续地跑 gh pr view 762 / 765 / 766,单个 PR 采样占空比约 50%(每 1~2 秒一发);
  • PR #762 早上 07:05 就合并了,合并后 9 小时还在被连续追问;#765 同样;
  • 根因 a:程序观察到「已合并但代码指纹对不上」这种死胡同结论后,只写一行日志就丢掉,没有任何记录 —— 下一秒又原样再问一遍,永动;
  • 根因 b:这条巡检是全系统五个同类探测器里唯一没装纪律的(没有缓存、没有频率上限、失败不退避)。

③ 核心流程:修复前 vs 修复后

修复后三条铁律:确定的结论(已合并 / 死胡同)只问一次,写进持久账本,重启也不会忘;还没有结论的活 PR 按纪律问(每分钟最多 6 次、答案缓存 60 秒、失败按 30 秒→5 分钟逐级放缓);每个死胡同发一次告警让人看见,而不是无声地烧钱。

④ 数据与结构模型

持久账本不建新表 —— 复用数据库里现成的「事件表」(天生带去重能力)。死胡同标记的钥匙由「登记状态 + 代码指纹 + 仓库 + PR 号」四样东西拼成:任何一样后来变了(比如你批准了发货),钥匙对不上,程序会自动恢复处理,不会把活单误杀。「已合并」记录则保证 Bridge 重启后也不用再问 GitHub 一次。

安全底线:所有写入都带事务级二次核验(写之前在同一笔数据库事务里把候选身份重新验一遍,验不过就一个字都不写)—— 防止「查的时候是 A、写的时候世界已经变成 B」的竞态错账。

⑤ 关键取舍与被否掉的方案

候选方案结论为什么
把引擎 1 秒巡检节奏整体放慢否1 秒节奏服务的是任务派发的响应速度,放慢会伤及无辜;病根在这个探测器自己没纪律,不在节奏。
探测到「已合并但指纹对不上」就自动替它收尾否指纹对不上意味着「合并的代码不是走批准流程的那份」,自动收尾等于替你签字 —— 安全红线不动,只停表 + 告警一次。
无法证明仓库身份的老单(legacy)继续允许自动收尾收紧为不允许评审发现一个真实漏洞:换过仓库指向的目录下,可能拿 A 仓库的合并记录去收 B 仓库的单。收紧后这类单改为告警请人确认(现役生产单都有仓库身份,不受影响)。
加一个开关(环境变量)控制新行为否这是正确性修复不是可选功能;且全项目正在做开关收敛。回退方式 = 代码回滚 + 重启。
顺带把全仓 17 处同类 GraphQL 用法一次迁完 + 上守卫拆出去与本次燃烧修复没有原子依赖,合在一起只放大风险;已列为独立后续单。

本设计经 Codex(另一个 AI 工程评审员)15 轮逐层评审后通过,期间修掉了竞态错账、跨仓库串号、重启后复燃、账本自相矛盾等十余个真实设计洞。

⑥ 诚实边界 — 这个设计做什么、不做什么

  • 做:燃烧归零的机器保证 —— 已合并/死胡同的 PR 一次结论后零 GraphQL(跨重启);活 PR 每分钟最多 1 次;死胡同各发恰一次告警;顺带吸收 529 检查的一行修复(改走 REST 通道 + 「查不成 ≠ 不存在」的三态报错)。
  • 验收数字(硬承诺):修前采样三个 PR 各 ~50% 占空比;修后死胡同 PR 0 命中、无活跃发货时全体 ≈0、单个活跃 PR ≤ 每分钟 1 次。
  • 不做:不自动收尾任何指纹对不上的合并(告警请人看);不清理今天 Tadashi 手工止血的两条历史死数据(物理清理另开运维单,但本单顺手修掉了还会读到它们的最后一条代码路径);不承诺秒级收敛(批准后引擎收尾是分钟级,与现状一致)。
  • 已知代价(如实):无仓库身份的老单每次 Bridge 重启后会多花 1 次查询;由账本记录驱动收尾动作前会花 1 次便宜的 REST 复核(防极端情况下拿旧记录办新事)。
  • 部署:随正常发布走全舰队重启;修复效果由独立 QA 用与 Tadashi 相同的采样法出前后对比数字。
