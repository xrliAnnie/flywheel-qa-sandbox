# Design Review — prd.md (Round 2)

Date: 2026-07-08
Author: Codex
Status: CHANGES REQUESTED

## Summary

R2 materially fixes the R1 direction problems: MVP is now bounded to built-in `design/implement/qa`, arbitrary node types are correctly deferred, the lifecycle workstream is named, and the loop/skip scope is no longer an open-ended DSL. I would approve the architectural direction, but not the PRD as a build blueprint yet: the durable snapshot and Auto-QA/ship-gate sections still have correctness holes that will surface in implementation.

## What's Good (Keep)

- MVP scope split is now right: §3 keeps arbitrary `research/generate_video`-style node IDs out of Phase 1 and explicitly lists the storage/display/retry/finalizer workstream needed before Stage 2 (`engineering/doc/FLY-1020-workflow-templates/prd.md:77`).
- R1's factual correction for `three-stage-phases.ts` is reflected: the PRD now treats phase role, sequence, completion-role preservation, next resolver, and display metadata as part of the registry surface, not just `DEFAULT_PHASE_TIER` (`engineering/doc/FLY-1020-workflow-templates/prd.md:38`, `engineering/doc/FLY-1020-workflow-templates/prd.md:126`).
- The loop scope is much safer: §5.1 now limits MVP to configuring the existing QA-fail loop and calls out max iterations, durable intent, head capture, wake/spawn, TURN, ghost guard, startup replay, and fail-closed wake failures (`engineering/doc/FLY-1020-workflow-templates/prd.md:166`).
- The lifecycle workstream is no longer hidden inside “orchestrator generalized”; §13 names DirectEventSink, event-route, startup reconcile, complete-marker drain, terminal rejected paths, TURN recovery, display refresh, and post-ship finalization (`engineering/doc/FLY-1020-workflow-templates/prd.md:304`).
- Red-line guardrails are much better: core-shipped templates only, no arbitrary user nodes in MVP, bounded condition domains, and naked single session as an always-available exit (`engineering/doc/FLY-1020-workflow-templates/prd.md:262`).

## Issues & Recommendations

1. **Snapshot is still specified as a reference, not a replayable workflow snapshot.**  
   §6 says persist `workflow_template_id`, `workflow_template_version/hash`, `current_node_id`, and `node_index / edge_state` (`engineering/doc/FLY-1020-workflow-templates/prd.md:203`). That is not enough to satisfy the next line's contract that handoff/retry/startup/post-ship “一律读快照” and never re-resolve live label/config shape (`engineering/doc/FLY-1020-workflow-templates/prd.md:210`). If the canonical YAML changes, disappears, or the registry changes after entry, an id+hash tells you drift happened but does not give the orchestrator enough material to continue. Also, `session_params` is per execution row (`packages/teamlead/src/StateStore.ts:3168`, `packages/teamlead/src/StateStore.ts:3202`), while handoff starts new executions (`packages/teamlead/src/bridge/phase-orchestrator.ts:1426`) and retry dispatches a successor execution (`packages/teamlead/src/bridge/actions.ts:840`); the PRD does not say the snapshot is copied to every phase/retry session or where issue-level truth lives.
   **Suggested fix:** Define a materialized `workflow_snapshot` payload, not just id/hash: normalized node list, resolved edges, skip decisions or skip inputs, effective per-node model/capability/badge metadata, loop edge ids and counters, selected overrides, template/registry content hash for audit, and current node/edge state. Require copy-forward on every phase handoff, QA loop wake/spawn, and retry successor. If you want to avoid storing full prompt text, store immutable core template version plus enough normalized graph/capability data to run without re-reading project YAML.

2. **Auto-QA precedence still does not match the current per-execution ship gate.**  
   §7 says templated internal QA sets `qa_required=1`, and product skip-QA uses `onMainAwaitingReview` to write `qa_required=0` (`engineering/doc/FLY-1020-workflow-templates/prd.md:223`, `engineering/doc/FLY-1020-workflow-templates/prd.md:224`). Current code does not support that as written. `onMainAwaitingReview` returns unless the row is `session_role=main` (`packages/teamlead/src/bridge/auto-qa-coordinator.ts:306`, `packages/teamlead/src/bridge/auto-qa-coordinator.ts:323`), and both event sinks only call it for main rows (`packages/teamlead/src/DirectEventSink.ts:755`, `packages/teamlead/src/bridge/event-route.ts:2015`). A templated product run's reviewable phase is `implement`, not `main`. Separately, `evaluateQaShipGate` treats `qa_required=1` as “there must be a passed `auto_qa_record` for this exact execution/head” (`packages/flywheel-comm/src/ship-eligibility.ts:114`, `packages/flywheel-comm/src/ship-eligibility.ts:185`), but the three-stage internal QA PASS currently records `three_stage_verdict` and opens the QA phase's own ship path; it does not create a passed `auto_qa_record` (`packages/teamlead/src/bridge/phase-orchestrator.ts:929`).  
   **Suggested fix:** Split the concepts. Keep `qa_required` as the existing independent Auto-QA gate unless you also extend `evaluateQaShipGate` to understand internal workflow QA evidence. For templated internal QA, either write a new `workflow_qa_required/workflow_qa_passed` evidence path that `evaluateShipEligibility` understands, or deliberately set the Auto-QA snapshot to exempt and rely on the workflow state machine to ensure QA happened before the QA phase can open the ship gate. For skip-QA product, specify exactly which execution row gets `qa_required=0` and which sink writes it, since the current main-only coordinator will never see an implement-phase review completion.

3. **`FLYWHEEL_AUTO_QA=0` / `no-qa` precedence over template QA is ambiguous and likely conflates two gates.**  
   §7 says the Auto-QA kill-switch and `no-qa` label “仍最高优先,可覆盖模板” (`engineering/doc/FLY-1020-workflow-templates/prd.md:226`). Today `FLYWHEEL_AUTO_QA=0` is the independent Auto-QA spawn policy kill-switch (`packages/teamlead/src/bridge/auto-qa-policy.ts:8`), while three-stage has its own workflow kill-switch (`packages/teamlead/src/bridge/three-stage-policy.ts:11`) and ship eligibility has a separate QA-done gate (`packages/flywheel-comm/src/ship-eligibility.ts:15`, `packages/flywheel-comm/src/ship-eligibility.ts:36`). If `FLYWHEEL_AUTO_QA=0` also skips internal template QA, it changes workflow shape under a flag that currently only controls separate QA runners. If it does not skip internal QA, then “覆盖模板” is misleading.  
   **Suggested fix:** Define three independent control planes: workflow-template enable/kill switch controls the template layer; `FLYWHEEL_AUTO_QA=0` controls only independent spawned Auto-QA; `FLYWHEEL_QA_DONE_GATE=0` controls ship-gate enforcement. If `no-qa` is intended to skip an internal QA node, call it a per-run workflow override and require the same snapshot + ship-gate evidence write as `skip qa`.

4. **The loop spec still omits FLY-939 founder-feedback kickback as an explicit loop trigger.**  
   §5.1 says the condition source is only the existing verdict event `qa_fail` (`engineering/doc/FLY-1020-workflow-templates/prd.md:174`). The current implementation has a narrow but important second shape: after QA PASS opens its approve gate, founder/Lead feedback is accepted as a FAIL kickback only under keep-alive, with the QA session in `awaiting_review`, runner-driven review evidence present, and a gate response already recorded (`packages/teamlead/src/bridge/phase-orchestrator.ts:804`, `packages/teamlead/src/bridge/phase-orchestrator.ts:817`). It then bypasses the “prior PASS already recorded” guard and routes back to implement (`packages/teamlead/src/bridge/phase-orchestrator.ts:860`). Blueprint also prompts QA to emit this kickback explicitly (`packages/edge-worker/src/Blueprint.ts:1020`).  
   **Suggested fix:** Add `founder_feedback_kickback` as an allowed source of the configured QA loop, or define `qa_fail` to include that exact guarded case. Preserve the same guard conditions in the loop interpreter; otherwise a configured loop may regress the current founder-feedback fix path.

5. **The build sequence should move ship-gate evidence design before Auto-QA migration.**  
   §13 currently puts entry+snapshot, registry, orchestrator, then Auto-QA/ship-gate boundary (`engineering/doc/FLY-1020-workflow-templates/prd.md:299`). Given issue #2, the Auto-QA/ship-gate decision is not just a later integration detail; it determines what snapshot fields and state-store writes are needed and how product skip-QA can ship.  
   **Suggested fix:** Add a small “ship-gate evidence model” step before orchestrator migration: decide whether internal QA uses existing `qa_required/auto_qa_record`, a new workflow-QA evidence field, or an Auto-QA exemption plus workflow-state guard. Then implement orchestrator and Auto-QA boundary against that settled contract.

## Verdict

CHANGES REQUESTED — R2 is close, but the snapshot and Auto-QA/ship-gate contracts need one more pass before this is safe to hand to implementation.
