FLY-1863:拆掉测试里的定时炸弹(main 红告警已裁出)

设计文档 · 2026-08-17 · Codex 设计评审 R4 APPROVED · founder 后续裁决:修法 B 移交独立问题
1 · 一句话结论

那两条"时好时坏"的测试其实是一枚定时炸弹:测试里写死了一个"租约到期时间 = 2026-08-18 凌晨 01:00:01(UTC)",而被测代码是拿真实的当前时间去核对这个租约的 —— 所以在那个时刻之前跑必然绿,之后跑必然红。它不是随机抽风,也和测试怎么分组、和谁一起跑毫无关系。本单只把测试时间从"写死的日期"改成"相对当下推算",再补一道守卫;"main 红了没人知道"经 founder 裁决移交独立问题。

2 · 出了什么事(机制与证据)

PR #869 新增的两条测试要走一段"合入代码后的收尾流程"。这段流程里有个租约(lease)—— 一种"这项工作归我、限时有效"的占用凭证,过了到期时间就作废,防止两个执行者同时动同一件事。测试给自己造的租约把到期时间写死在了 2026-08-18 01:00:01,离 #869 合入只有 46 分钟。之后的每一次执行,收尾步骤都因"租约过期"被拒,测试就红了:

之前看起来"时好时坏",是因为大家把引信两侧的样本混在一起看。把每个样本按实际执行时刻排开,零反例:

样本执行时刻(UTC)引信前/后租约写的年份结果
main 的 CI(#869 合入触发)— 整轮虽被后续合入顶掉取消,相关检查组已跑完00:14–00:2x前2026绿(238 项全过)
main 的 CI(下一次合入触发,完整跑完)00:29–00:35前2026绿
PR #868 那轮00:38前2026绿
PR #871(排队 64 分钟后才真正开跑)01:49–01:55后2026红
PR #874 / #876 / #87701:34+后2026红
本地在干净 main 上单独跑这份文件 ×1002:50–02:51后202610/10 红,零方差
PR #875(它的分支恰好把年份改成了 2099)01:56–02:24后2099全绿
本地实验:只把年份改成 2099,别的一字不动02:5x后209940/40 全绿

也就是说:引信前全绿、引信后写 2026 的全红、引信后写 2099 的全绿 —— 一个日期解释了全部现象。之前怀疑的"测试分组不同导致互相影响""运行环境差异"等假说,全部被这张表判死。

3 · 修法 A:拆引信 + 上守卫(数据/结构模型)

核心改动只有一处:测试种子里的时间不再写死,而是以"跑测试那一刻"为基准推算 —— 创建时刻 = 现在减 1 秒,租约到期 = 现在加 1 小时。这样无论哪年哪月、单独跑还是混在任何组合里跑,租约永远有效,测试彻底自包含。

光修还不够,要防复发:再加一条守卫测试,把程序的时钟临时"冻结"在一个假想时刻,然后逐字核对种子产出的每个时间字段是否精确等于"冻结时刻 ± 规定偏移"。只要有人再把绝对日期写回去 —— 不管写 2026 还是 2099 —— 这条守卫当场红,不用等真实引信烧完才发现。验收里还包含一次反向实证:临时把日期改回绝对值,确认守卫真的会红,再还原。

被检查的数据字段(全部在测试文件内,产品代码零字节改动):

字段原来(写死)改后(相对推算)
created(创建时刻)2026-08-17 00:00:00现在 − 1 秒
claimed(领取时刻)2026-08-17 00:00:01现在
leaseExpiresAt(租约到期)2026-08-18 01:00:01 ← 引信现在 + 1 小时
4 · 修法 B【founder 已裁出 → 独立问题】

范围裁决(2026-08-17):这一节不在 FLY-1863 实现。本 PR 不改 CI workflow、不新增 webhook 或 secret;以下内容保留为历史设计和后续独立问题输入。

这次事故里更深的病灶是:main(主干)自己的 CI(每次代码变动自动跑的检查流水线)其实一直在跑,红了也没人知道 —— 信号存在、无人接。等发现时,红已经顺着流程"传染"到每一条待合入的 PR 上,引发了一整晚的逐条错误归因。设计:在 CI 里加一个只在"main 上有检查失败"时才运行的报警任务,把失败清单直接投进 #flywheel-alerts(告警频道,已有值班 bot 盯守处置):

几个关键讲究:投递时要求 Discord 确认消息真的落了盘才算成功(平台默认"发出去就当成功",消息可能悄悄丢);提交说明里的文字按不可信内容处理,不允许触发任何 @全体;webhook(频道的投递地址,属于密钥)必须在合入之前就配好并真投一条验证 —— 因为合入本身触发的那次 main 检查,恰恰是第一条需要保护的;密钥没配时报警任务自己转红、页面可见,绝不静默。这个任务不进 PR 的检查门,对每条 PR 的通过判定零影响。

5 · 关键取舍与放弃的方案
  • 放弃「给产品代码注入假时钟」:产品代码按真实时间判租约过期是正当语义,为了迁就测试去改产品,是把病往更深处推。
  • 放弃「冻结整个测试文件的时钟」:文件后半已有另一组用假时钟的用例,再叠一层容易互相污染;"相对当下推算"是最无聊、最不会出错的修法。
  • 放弃「调整测试分组 / 跳过这两条」:Lead 明令禁止,而且治不了病 —— 单独跑也红。
  • 历史方案(已裁出):放弃「由本机 Bridge 轮询 GitHub 来发现 main 红」:main 红常与本机繁忙同时发生,报警器不能依赖病人自己活着;放在 GitHub 侧自报,独立于本机。
  • 历史方案(已裁出):放弃「为防人工重跑造成重复报警而建去重账本」:人工重跑本来就说明有人在看,重复一条无害;为它建持久状态是过度工程。
  • 顺手发现但不顺手修:仓库里还有几处同形状的"未来日期"写法(最远写到 2999),本单只做一次有边界的排查、逐项定性列表上报,发现真引信另立 issue,不在本单扩大修改面。
6 · 诚实边界:这个设计做什么、不做什么

本单做:拆掉这枚引信(两条测试从此任何时刻都绿);上守卫防同类复发;实现侧只动 1 个测试文件,产品代码零改动。

已裁出:main 红告警、CI workflow、webhook 与 secret 整体移交独立问题。

不做 / 已声明接受的边界:

  • 以下告警语义均属已裁出的历史方案,不构成本 PR 的实现或验收承诺。
  • PR #875 的分支里恰好带着一个"把年份改成 2099"的临时缓解,和本修复会在同一行撞车;已约定无论谁先合入,最终以本单的"相对推算"版本为准(2099 仍是绝对日期,只是引信更长,守卫测试也会当场抓红它)。
