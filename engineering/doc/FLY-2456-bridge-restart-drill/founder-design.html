FLY-2456 · 529 房真机重启演练:修前/修后各一次,看 Codex 体能不能被认回

设计稿 · 2026-09-10 · 服务于 FLY-2352(PR #1128)的 founder 前置 · 文档:engineering/doc/FLY-2456-bridge-restart-drill/(exploration / research / plan)· Codex 设计评审 4 轮后 APPROVED(R1 9 条 → R2 7 条 → R3 7 条 → R4 0 HIGH,3 条 MEDIUM 实施残留入 plan §3.5c)· Lead 三项裁定已写入 plan §3.5/§3.5a

一句话

由 Lead 在宿主机按一份「每步一条可复制命令 + 期望输出」的路书,在专门的测试房(529 房:一套与生产完全隔离的 Bridge、数据库、tmux 和 Codex 进程)里起三具真 Codex 体,只重启那间房的 Bridge,看每具体是不是被「认回」(reown:Bridge 重启后重新接管还活着的 runner 进程,而不是判它死、换一具新的)。修前(现在的 main)预期「被返工唤醒过的体」必败被换掉,修后(#1128)预期全部认回;同时交出九项「生产一根毫毛没碰」的证据。我这边交付的是路书本身和一套不连真库、可自测的判定工具。

审计发现:演练不能照 issue 字面直接跑

写设计前把房、脚本、被测代码都翻了一遍,三件事会让「直接跑」得出假结果或伤到生产:

  1. 测试房里 reown 被整体关掉了。FLY-2211 给 Bridge 加了一条排除规则:只要房间目录里有 room-info.json(装房脚本写的「这是一间测试房」标记)且标记说这是 generalized 房,Bridge 就对房内所有 Codex 体跳过认回。而真 Codex 房型(--codex-runner)必须是 generalized 房。⇒ 直接跑,修前修后都是「什么都没发生」。Lead 已裁定(aa0f4fe9):本次用夹具——体就位后、重启前把这个标记文件改名藏起来,重启完再改回;两轮用同一夹具,报告里明说。产品侧的正式豁免另立 FLY-2487。
  2. #1128 的分支头不含 FLY-2454 的隔离修复。从它起房 = 用没修隔离的脚本起房 = issue 依赖段警告的「击杀生产 Codex 舰队」。⇒ 修后轮用「当前 main + #1128」的本地临时合并头(已验证能干净合并,不推到远端),或等 #1128 合入后直接用 main。
  3. 「生产 comm.db 前后逐字相同」做不到。comm.db 是生产 Lead 和 runner 的活信箱,5 秒内就在写。⇒ 改成:前后各做一次只读快照,快照里凡是带测试房标识的行必须是 0 行,加上 Codex 进程 / tmux 窗口清单的 diff 为空。Lead 已接受。

核心流程(每轮一遍;修前 slot 4,修后 slot 1)

图 1 · 一轮演练的时序:起房 → 三具体 → 造出「多 activation」靶体 → 给 B1/B2 挂上 gate → 形状与资格硬门 → 正对照重启 → 藏标记 → 被测重启 → 读事件判定 → 拆房 → 三组零影响对照。宿主机命令全部由 Lead 执行,工具只读文件。

三具体各是什么形状

  • B1(靶体,多 activation):activation 是「这具进程被授权去做某个 run 的某个节点的第几次尝试」的一条记录。B1 先做完 implement 第 1 次(停驻等待),再被返工唤醒去做第 2 次——同一具进程挂了两条记录。这就是生产里 15 具必败体的共同形状,也是 #1128 修的那一种。
  • B2(正对照,单 activation):刚出生、正在做第 1 次,只有一条记录。B1 与 B2 只差「有没有第二条记录」,是单变量对照。
  • B3(阴性对照,停驻、非 TURN holder):做完第 1 次停驻等待,TURN(「现在轮到谁说话」的令牌)已经交给 QA 体。Bridge 对这种体的正确行为是「跳过、不认回」(reown_skipped_not_turn_holder),它证明认回机制没有乱抢;不进成功率分母。

为什么 B1/B2 要先「挂一个 gate」

Codex 评审指出:Bridge 只对「daemon 还活着、但手里握着一个未答问题(open gate),或者停驻中」的体做认回;一具活着、正常干活、没问题在手的体,Bridge 只会登记「继续观察」,根本不进恢复流程。生产里那 15 具必败体在第一次尝试时都是「活着 + 握着 gate」。所以路书让 B1/B2 用它们自己的身份各发一个不阻塞的问题(gate question --no-block),房里没有 Lead 应答,它永远悬着——正好复刻生产形状。这是本演练的第二个夹具,报告里会写明。

为什么要先做一次「正对照重启」

藏标记之前先重启一次,预期三具体都是 0 条认回事件——这证明「排除规则确实在起作用」;然后藏标记再重启,事件才出现。少了这一步,「没事件」既可能是排除生效,也可能是体本身不合格,分不开。

数据与判定:看哪几张表、认哪几个词

图 2 · 房间数据库里与认回相关的五张表。判定只认表里的行,不认日志里的叙述。
  • 认回成功:事件表出现 reown_revive_succeeded;修后的 B1 还会多一条 codex_recovery_capabilities_prepared 且 attempt=2(修前这条对 B1 永远是 0 条——这是最锋利的对照)。
  • 2352 的病复现:两条 reown_revive_failed,原因以 workflow capability drift 开头;接着预算(每具体只给 2 次机会)耗尽 episode_exhausted,体被标 failed,引擎另铸一具替换体。
  • B3 的预期:reown_skipped_not_turn_holder——被正确跳过。
  • 夹具没生效 / 体不合格:0 条事件,或只有「继续观察」(reown_watch_started,说明 gate 没挂上)。靠正对照区分,不猜。

事件按数据库的自增 id 和序号划界(每次重启前记下「此刻最大 id」),不按秒级时间戳,否则两次重启和 5 分钟一次的例行巡检会把事件串在一起。

图 3 · 每具体的终局怎么归类,两轮各自的通过条件,以及不符合时怎么办(报可证伪的障碍,不写 PASS)。

生产零影响:九项证据,三组对照

每轮取四次快照:开始前、体还活着时、拆房前一刻、拆房后。三组对照各回答一个问题:「起房到重启期间生产少了什么」(开始前 → 活着时)、「整轮下来生产回到原样没有」(开始前 → 拆房后)、「拆房本身有没有杀错」(拆房前一刻 → 拆房后,这是 Lead 在 FLY-2455 C4 用过的严格基线)。

  1. 生产 Codex 进程的 socket 清单 + 生产默认 tmux 的窗口清单:活着时只允许多出事先登记的测试房 socket、不允许少任何一行;拆房后 diff 为空。演练前先在生产 tmux 放一个 fly2454-decoy 假窗口,每份快照里都得在(证明「diff 为空」不是因为什么都没看到)。
  2. 全量进程表按 PID 归属:消失或新增的每个进程标成「测试房的」还是「不是测试房的」;「不是测试房的」若消失,必须逐个用生产数据库事件解释(比如某个生产 runner 自己干完了)。
  3. 生产 comm.db(Lead 与 runner 的活信箱)只读快照:对所有表、所有文本列扫测试房标识,前后都必须是 0 行;它是活库,5 秒内就在写,所以「逐字相同」做不到,改用这条(Lead 已接受)。
  4. 生产 ~/.flywheel/state/launch-commits/:这是路书明写的「测试房也会写进去」的唯一位置,所以判据不是「没新增」,而是「新增的每一项都属于本轮登记过的体,没有一项来路不明」。
  5. 生产 StateStore 只读副本:测试房那几具体的 execution id 在生产库里零条认回事件、零条 session。
  6. 生产告警目录(meta-alert / alert-deadletter):新增或变更的文件按内容里的 leadId 归属,测试房 Lead 名下的算污染、交 Lead 隔离;生产 Lead 名下的按真告警留着。
  7. 生产 runner-flywheel 窗口数前后相等,或差异被生产事件解释。
  8. 生产 Bridge 的 /health uptime 单调递增、buildSha 不变——证明生产 Bridge 没被重启。
  9. 测试房自己的「拒杀账本」(kill-ledger)里零条越界拒绝记录;有的话逐条解释。

另外:路书 §7 规定演练前先按原样做一次硬前置——先放 decoy、起空房、起一具一次性体并终止它、等至少两个巡检周期、拆房、核对 diff 为空与归档可读;它只证明房不伤生产,不代替 2352 的验收。

取舍与被否掉的做法

  • 采用只重启房内 Bridge 的原语(FLY-2237 的 cycle 脚本):只给 Bridge 那条进程链发 TERM,按同一份启动合同重启;Codex daemon 是独立进程组,活过重启——这正是生产事故里「daemon 还活着却被判死」的形状。否掉拆房重装:会把体一起杀掉,测不到认回。
  • 采用simple_code 菜单(implement 直接打头):Codex 体在 run 开始后立刻出生。否掉code 菜单:第一节点是 Claude 设计体,要走完文档流和 founder HTML 门,一具几十分钟且不可控。
  • 采用代 runner 推进(FLY-2182 实证配方):用体自己的环境替它提交完工 / 判 QA FAIL,几分钟内造出靶体形状。否掉等真跑手自己干完:时间不可控,且体可能先把活干完退出。
  • 采用QA 判 FAIL 触发唤醒为主(FLY-1768 真房走通过),备选operator 返工接口(POST /api/runs/:id/rework,不用起 QA 体,但房里没跑过)。
  • 采用藏 room-info 夹具(Lead 裁定)。否掉改产品 predicate:同一文件正是 #1128 在改的,本单边界不碰,另立 FLY-2487。
  • 采用「挂 gate」夹具让 B1/B2 进入认回资格。否掉把 daemon 杀掉来制造「死体」资格:那会变成另一种事故形状(daemon 已死),不是生产里那 15 具「活着但被判死」的形状。
  • 采用每轮一份 manifest:所有会产生副作用的命令先「认领」——已有回执就只重放输出,不再执行;幂等键、请求 id、分支/PR 号都提前生成并落盘。否掉现场手敲 uuid:「服务器收到了、客户端没拿到回应」那几秒里重试就会重复起体。
  • 采用路书 dry-run 直接调用部署护栏(FLY-913)的真判定函数逐条检查命令。否掉数「敏感词」:护栏是组合语义,数词会误报证据文件名、也会漏掉经 shell 包装的真危险命令。
  • 采用两轮用不同 slot、串行跑:修后轮不依赖修前轮拆房成功(拆房撞 cmux 租约是老坑);串行让生产零影响能单变量归因。

诚实边界:这个设计做什么、不做什么

做

  • 一份宿主机路书(Lead 逐条复制执行)+ 一套只读文件、不连真库、可自测的判定工具 + 两轮证据 + 一份零表格的 ship report 骨架报告,由 Lead 投到 FLY-2352 thread。
  • 修前:B1 复现「drift → 耗尽 → 换体」、B2 认回、B3 被正确跳过;修后:B1/B2 全认回。这是 founder 决定按不按 #1128 的材料。

不做 / 证明不了

  • 不改任何产品代码,不碰 #1128 分支,不重启生产任何东西,不跑 restart-services / request-restart;不用会终止整个 run 的 run 级 terminate。
  • 测试房需要两个夹具(藏 room-info、挂 gate)才能观察认回——所以「529 房能开箱测 reown」这句话本设计不成立,要等 FLY-2487。
  • 拆房后有几样东西会留下:生产的 launch-commits 回执(每具体一个,这是已登记的写点)、qa-evidence 归档、沙箱仓的分支与已关闭 PR、可能漏出的测试房死信。报告会逐一披露,它们不是「零影响」的反例。
  • 修后轮跑的是「main + #1128」的本地合并字节,不是 CI 验过的那一份;报告会附 diff 统计。若 #1128 先合入,就直接用 main。
  • 房里心跳固定 5 分钟,修前的第 2 次尝试与换体最迟要等 5–15 分钟;QA 体被唤醒后的行为不在观察范围,重启必须在唤醒后 5 分钟内做(否则 run 可能被 FLY-2208 的跑道问题挂起,靶体会被判「已被取代」而不是 drift)。
  • 不覆盖 2352 计划里「生产首次重启窗口的形状对照」和已知限制 L1(恢复后凭据未投影到 CommDB);房里的 Codex 节点和生产一样不带产出凭据,撞到 credential_revoked 要单独归因。
