Confound 清单(不许拿脏数直接比)

  • ①【最大】任务规模不对等:各臂样本是不同 issue。历史臂 implement 产出差 ~4×(A≈4.3×C)。workflow_run.tier / task_category 系统难度标签全 NULL,无客观难度分级。
  • ②【Annie 已知】B 中途注入第 6 修复面(1385 design 阶段 scope 被扩)。
  • ③【新发现】C(1393)implement 被 blocked + 过夜 11h 重派(两个 implement session 拼接)。
  • ④ wall-clock ≈ founder 在线时机,非计算时间(approve 等待 A 11h47m / B 9h41m / C 39m)。
  • ⑤ C 的 design N=4 实为 2 个不同 issue(1150 同任务 ×3 pass 相关)。
  • ⑥ 1374 / 1150 有前置 main 研究被取代 → design first-pass 可能低估。
  • ⑦ 1457 是 generic 单段 ops 任务,执行模型 + 任务类型都不同,不可与三段并列。

✅ 数据能说什么(方向感,N 小)

  • Design 阶段 duration:matt(19-21m,最紧)与 bare(11-31m)偏低;superpowers 有 1 个大异常(1392,1h),但其余样本(13-19m)与其他臂同区间 → 加样本后没看到 superpowers 系统性更慢。
  • 历史 implement first-pass:A(2h44m)>B(2h12m)>C(1h08m)——但与任务规模同序。
  • review churn:A(11)>C(7)>B(5),A 迭代最多(可能因任务最大)。

🚫 数据不能说什么(诚实边界,不估算冒充实测)

  • 哪个 prompt 更快 / 更好 —— 无法定论。 N=1~4、任务体量差 ~4×、多个 confound、token 不可得、主指标(扣等待的 active)只能部分测。
  • 每臂 token 消耗:不可得。 token-usage.db 只有 2026-06-28~30 数据,07-21~24 全空;GPT(implement)侧 token 也不在 Claude 账本。仅有行数/文件数作产出规模的部分代理。
  • 跨轮 fix 的总 active 工作时间:不可干净分离。 QA/design session 停在 active 标签阶段(如 test)时其实在等 implementer —— 从时间戳无法把「真在算」和「在等别的 role」分开。这正是等待态无法从时间戳区分的盲区。只有 first-pass active 可干净测。
  • 今晚的 implement / QA 阶段尚不可用(1448/1456 implement 仍 running;1150 implement 是 65s stub / 1s failed)。
