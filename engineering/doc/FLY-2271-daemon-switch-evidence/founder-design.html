FLY-2271 · 自动切号失败为什么「零证据」,以及怎么修

Issue: FLY-2271 · 文档类型: 设计一页(founder 版) · 日期: 2026-09-02 · 设计节点: eng_design · 分支 flywheel-FLY-2271

结论一句话总结

9-02 两次自动切号失败,不是 issue 猜的「token 轮转把账号标记判成过期」,而是切号 daemon 这个常驻进程还跑着 FLY-2240 之前的旧代码——新版切号脚本要求它出示一个「原子切号许可」,旧进程不会出示,脚本在写审计记录之前就拒绝退出,daemon 又把所有这类拒绝一律记成「标记漂移」,于是失败发生了、却什么证据都没留下。

本设计做五件事:A 每次失败必留证据(退出码、错误标记、原因写进日志、告警和审计);B 把「daemon 版本落后」单独分类,不再冒充标记漂移;C daemon 对真正的标记漂移采用与人工路径同一套严格修复并重试一次;D 部署时把跑旧码的 daemon 重启掉;E 用隔离台架把三种场景修前修后跑一遍,包括「daemon 是旧码」这一幕。

名词:切号 = 把机器上正在用的 Claude 账号换成另一个;daemon = 后台常驻的自动程序,这里指盯着额度、到 90% 就自动切号的 quota-monitor;审计日志 = 每次切号动作的流水账文件。

证据发生了什么(时间线,UTC)

时刻事件证据来自

09-02 06:16daemon 自动切到 business 成功,审计记录完整审计日志
09-02 06:51自动更新器把新代码拉到磁盘;daemon 进程没有被重启git reflog、进程启动时间不变
09-02 12:46personal 到 90% → daemon 切号 → 失败,告警只写「reason=active_marker_drift」;审计日志一行都没有daemon 日志第 1406 行、审计日志

09-02 18:46business 到 90% → daemon 再次同样失败;18:47 Lead 再次手动兜底daemon 日志第 1427 行、审计日志

为什么能断定是「旧 daemon」而不是「标记漂移」

  • 审计零记录只可能来自「脚本在写记录之前就退出」。切号脚本的顺序是:拿锁 → 写审计 entry → 检查标记。所有「标记漂移」的失败都发生在写 entry 之后,一定会留两行记录。委托模式下,写 entry 之前唯一的退出点,就是「缺原子切号许可」。
  • 「标记是否漂移」比的是账号身份(账号 id 和邮箱),不是 token 的字节。token 轮转不改身份,走的是正常的「保鲜」分支,委托模式同样允许。
  • daemon 每个周期本来就会检查「机器上的 token 是否和池里的副本一致」,不一致就自动修复并留审计;9-02 全天零条这类修复记录,说明当天根本没发生 issue 假设的分歧。
  • daemon 自 06:51 之后再没有任何一条审计记录,而它明明在 12:46 和 18:46 各试了一次。

名词:标记(marker) = 池目录里一个叫 .active 的小文件,记着「当前用的是哪个账号」;委托模式 = daemon 先拿到全局锁,再把「真正改钥匙串」这一步委托给切号脚本执行,脚本不自己拿锁。

流程修后:一次自动切号会经历什么

图 2 · 修后流程。绿色 = 成功;红色 = 失败但带证据;蓝色 = 新增的自动修复段。关键约束:修复(reconcile)只做一次,重试只做一次,绝不循环;修复动作用的是人工路径同一条严格流程(先用 token 向 Anthropic 查身份、再在池里找唯一匹配的账号、再把 token 保鲜进池、同步台账、最后原子改标记)。

名词:reconcile(对账) = 让「标记说的账号」与「钥匙串里 token 真实属于的账号」重新一致;executor = daemon 里负责持锁、挑候选、调脚本、写台账的那段 Node 代码;snapshot = 切号前读一次「现在是谁在用、台账第几代」的快照。

结构证据从哪里产生、流到哪里

图 3 · 类图:左列是「证据链」——bash 退出码/标记 → Node 的类型化错误 → 切号结果 → 日志 / 告警 / 状态文件;右列是「部署层」——daemon 启动时自算的代码树哈希,部署波次拿它和磁盘上新构建的哈希比对。标「新」的是本单新增,其余已有。

退出码 48
新分配给「缺原子切号许可」。46/47 回归 FLY-1201 原义(46 = 标记无法证明、零改动;47 = 修复中途失败)。
reasonCode
新增 apply_contract_mismatch,告警文案直接说「daemon 运行的构建早于切号脚本,需要重启」。
证据载体
一个统一的小结构 ApplyChildEvidence(退出码、子进程是否启动、脱敏后的 detail),从「调脚本的那层」一路原样传到 daemon;daemon 永不从错误文本里反推证据(Codex 第 1 轮抓出的漏洞:二次清洗会把证据洗空)。
detail
只保留 stderr 里以 FLYWHEEL_ 开头的标记行和第一行 Error:,去掉控制字符,再把 sk-ant-…、Bearer …、accessToken/refreshToken 字段、token=… 这类形态一律替换成 <redacted>,按 UTF-8 字节截到 600,永不含 token(bash 从不把 token 写 stderr,新增测试锁住;清洗函数可重复调用、结果不变)。「修复后仍漂移」这类由代码自己加的前缀走另一个拼接函数,不再经过白名单——否则前缀会被整段丢掉(Codex 第 2 轮抓出)。人工路径打印到终端和写入兜底审计的文本也过同一套脱敏。
状态文件
只加三个可选键 applyExitCode、childStarted、detail,不升版本;旧文件照常解析。告警「是否算同一起事故」只看退出码/子进程状态等稳定字段,detail 变化只就地更新、不重置再告警计时。
健康标记
daemon 已经在写 quota-monitor.health.json(进程号、启动时间、自己代码树的哈希);部署层第一次真正用它——三项同时与活进程和磁盘构建一致才算「最新」,缺标记或任一项不符都重启。

台架三场景(修前 / 修后)

  • token 轮转(同账号、新字节):修前修后都成功——这是对 issue 假设的诚实否定,会写进证据。
  • 真漂移(标记说 personal,钥匙串里其实是 business 的 token):修前 daemon 失败、人工成功;修后两路径都成功,daemon 日志里能看到「对账:personal → business」。
  • 旧 daemon(用独立的临时 git worktree 真实构建 FLY-2240 之前的 daemon,配当前脚本;每个场景 × 版本 × 入口都用独立的 scratch 数据,互不污染):修前 46 + 零审计;修后审计有 48 的 entry/exit,再由部署 lib 检测到标记与磁盘构建不一致而重启 daemon,新 daemon 下一周期切号成功。证据文件用「命中任何一个假 token 即失败」的检查守住。

取舍关键取舍,以及被否决的做法

选择为什么
daemon 的漂移修复放在锁外调用现有 reconcile 命令,再重读快照重试一次与人工路径完全同一套校验(身份探测 + 唯一匹配 + 严格保鲜 + 台账同步 + 原子改标记),不加开关;不碰 FLY-1201 定下的「委托子进程零修改」安全边界
契约错配给独立退出码 48 + 独立标记行数字和文字互为备份(有些失败形态只带信号名不带数字);46/47 恢复单一含义
部署层按「健康标记三项 + 磁盘哈希」比对决定是否重启,不是每次都重启,也不用「进程很年轻就当作最新」这种猜测同版本的部署波次零动作,不打断在飞周期;重启理由自动写进证据;一个刚重启但仍是旧码的进程不会被漏掉
证据用结构化载体贯穿三层,不靠解析错误文本Codex 第 1 轮指出:把摘要再喂给摘要器会得到空串;载体避免任何一层重建证据
告警只带标记行 + 首行 Error,全文进日志Discord 不适合长文;stderr 全文可能含路径;token 从不出现在 stderr(测试锁住)

否决的替代方案

  • 让 bash 在委托模式下直接修标记/台账 — FLY-1201 评审明确否决:daemon 持锁期间的台账事实会被后续提交覆盖;锁外 reconcile 已能达到同样效果。
  • daemon 自己发现代码树变了就自杀让 launchd 重拉 — 等于 daemon 自行决定部署时机,违反「合入与部署分离、只有更新器在窗口部署」;还可能采用到构建到一半的产物。
  • 每次部署无条件重启 daemon — 同版本波次白白打断;哈希比对更省且自带解释。
  • 每次切号前都先跑一次网络对账 — 委托分支本来每次切号就做一次身份探测和保鲜,再加一次是双倍网络与双倍审计行;反应式修复零常态开销。
  • 保留 46 只靠文字区分 — daemon 先按数字分类,两处都要改;不如独立码。

边界这个设计做什么、不做什么

做

  • 失败必留证据:日志、告警、审计三处都有退出码与原因;再告警时沿用同一份 detail。
  • 「daemon 落后」与「标记漂移」分开分类,告警文案直接指向正确动作。
  • daemon 对真漂移自动修复一次并重试一次,与人工路径同一套校验。
  • 部署波次重启跑旧码的 daemon(Task 4,可摘除)。
  • 隔离台架给出三场景修前修后对照,证据文件不含任何 token。

不做 / 需要知道

  • 不改 FLY-1201 的安全边界:委托子进程仍零修改;修复永远由持锁的非委托 reconcile 完成。
  • 不扩 FLY-2265(手动入口 spawn ENOENT,已到 ship 卡)的范围;只消费它已放进结果里的诊断字符串。
  • 现在还在跑的那个旧 daemon(pid 45051)在本单合入后、下一次部署波次之前仍是旧码;需要一次部署波次或人工 launchctl kickstart -k gui/$UID/com.flywheel.quota-monitor。这一步不在本单自动完成。
  • account_switch_failed 这类告警目前的路由是不 @ 人、非严重,本单不改路由(范围外);所以修后失败仍不会主动 @ 你,但点开就能看到原因。
  • 「模型额度上限」触发的切号失败(和「账号额度」触发是两条路)仍是即时告警、不进持久的事故记录——这是现状,本单只保证它的日志和告警同样带退出码与原因,明确不扩。
  • 你 9-1 定的轮换规则「剩下所有能用的号里选 reset 最早的」不在本单实现,也没有被改动:它已由 FLY-2240 实现(候选选择器先做 live 验证,再按 weekly reset 最早排序,并优先 5 小时额度还没到线的账号)。本单的 daemon 与人工路径都沿用那个顺序;自动修复后的重试只是从同一批已排好序的候选里剔除刚确认的当前账号,不重排、不新增规则。规则要改的话另立单改选择器。
  • 部署 lib 在 --dry-run 下只读不动,需要重启时报 planned,不会假装「已是最新」。
  • issue 里「token 轮转 → 必失败」的假设被三条独立证据否定;PR 会如实写明。
  • Task 4 与并行的 FLY-2280 都改 restart-services.sh,已按 Lead 要求做成独立 lib + 一处调用;谁后合谁 rebase。
