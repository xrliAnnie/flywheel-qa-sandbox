核心流程

Execution 是一次独立 runner 运行身份；历史 execution 收到的 marker 不能自动转授给当前 execution。Delivery receipt 是 message-status 返回的只读投递凭证；它配合 mailbox lane 对当前 execution 的结构绑定，无需 runner 没有的管理员 credential。Park 唤醒时先定位唯一 lead-instruction sentinel，丢弃其前面的 phase-wake / standby transport prelude；随后用只读 CommDB API 把 exact row.content 直接写进 private source file，parser 不从页面文字重抄。

数据与结构模型

Exact marker 是不做 trim（删首尾字符）或 normalize（改写字符形式）的原始标记字节。Native instruction 是系统直接投递给同一 execution 的原生指令。Marker file 是 parser 生成的单行临时文件：它把可打印字符安全地作为数据传给 grep -F -f 与 cat，即使内容含引号、反引号或 $() 也不会被 shell 执行。

Mailbox 分支直接解析 sentinel 后的 row.content；direct-kick 分支从受限候选路径读取 immutable session.json 并直接解析 kickText。两者都不会从对话显示文本重抄 marker。

关键取舍与拒绝方案

采用：runner 可执行的 provenanceMailbox instruction 用 exact-id message-status receipt + trusted lane binding；direct kick 从 env、CODEX_HOME state root 或默认 home 的受限候选定位 immutable session.json。任一步不匹配都拒绝。
采用：明确 byte source短生命周期 read-only process 把 row.content 或 launchSnapshot.kickText 直接写进 mode-0600 source file；phase-wake / standby 前缀、terminal 输出和模型转述都不进入 marker bytes。
采用：file-backed shell bindingParser 先写 exact bytes + LF 临时文件，再用 grep -F -f 计数、cat 追加；printable ASCII 永远只是数据。
采用：owner handoff没有 marker 或 tpl_code route 与 local-only/no-PR 边界冲突时，runner 结构化报告并 park，由 workflow owner close、cancel 或 retemplate。
拒绝：从 owner 与 driver 模板推导能生成“看起来正确”的 `${owner}-native-BOOT`，却不能证明当前 execution 收到了它。
拒绝：模糊 driver grammar 或冲突回执DAG phase 的 injected contract 高于历史 driver 文本；direct fixture 只接受绑定同一 execution 的 kick。无法证明优先级时不做“聪明修正”，而是请求重发。
