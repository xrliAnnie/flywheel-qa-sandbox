## A. 代码审计事实

### A.1 准入闸门(FLY-1971 要改的那个东西)

`packages/teamlead/src/bridge/runner-admission.ts`

| 事实 | 位置 |
|---|---|
| 判据 = `loadavg()[0] / cpuCount > loadPerCore`,默认 `loadPerCore = 8.0` | `RunnerAdmissionController.tryAdmit()` |
| 本机 `hw.logicalcpu = 18` ⇒ 整机 load **144** 才开始拒 | sysctl 实测 2026-08-22 |
| 内存腿 `minFreeMemBytes` 默认 **0 = 关闭** | 构造函数 + 文件头注释 |
| **没有迟滞**:单次比较,过线就拒、跌回就放,不存在「跌到更低的线才恢复」 | `tryAdmit()` |
| 判据只读 **loadavg[0]**(1 分钟平滑值),不读 Bridge 自身状态 | 同上 |
| 显式手刹 `pressure_hold`(FLY-1082)/ `admission_paused`(FLY-1638)排在资源判据之前 | 同上 |

> ⇒ 最后两行是本单最关键的两条审计事实:**闸门读的是机器的 load,而不是「Bridge 还能不能服务」**。B 节的实测给出了**一个二者不同步的时段**。
> ⚠ 「不同步」≠「完全脱钩」 —— 一个时间窗的观测不足以支持「脱钩」这种全称断言;它只说明**至少存在**闸门读不出服务状态的情形。这已经足以要求先做 plan 的阶段 0。

### A.2 `/health` 远不是免费探针(⚠ 本节经 Codex R1 复核后**上修**)

`packages/teamlead/src/bridge/plugin.ts:1784` 的处理函数每次调用做的同步工作:

1. `store.getActiveSessions()` —— SQLite 查询(`StateStore.ts:7316`,`SELECT * FROM sessions WHERE status IN (...)`);
2. `store.getAdmissionPause()` —— 又一次 SQLite;
3. `livenessHealthProvider.current()` → `buildLivenessManifest()` —— 其中 `liveness-manifest.ts:142` 对 **每一个 Lead** 调一次 `queue.getHeartbeat(leadId)`。

> ⚠ **实测第 3 条不是「一次」而是「每 Lead 一次」**:生产 `/health` 响应体里 `liveness.components.w2_delivery_loop.leads` 有 **16** 条。
> ⇒ **一次 `/health` ≈ 2 + 16 = 18 次同步 SQLite 查询**,不是 3 次。

均在**单线程事件循环上同步执行**。所以「最便宜的探针」这个说法要大打折扣:它和别的请求抢的是**同一个线程**,而且它自己就有 18 次 DB 往返。

> 这条同时是对 **B 节实测的一个自我限定**:我的采样器每 0.5 秒打一次 `/health`,等于给事件循环额外加了约 **36 次查询/秒**。见 B.5。

- 缓解事实:`sessions` 表上有 `idx_sessions_status`(实测 `sqlite_master`),这条查询走索引,不是全表扫。
- 加重事实:`teamlead.db` 实测 **1.6 GB**(`PRAGMA page_count = 432198` × `page_size = 4096`),WAL 模式,另有 4 MB WAL。DB 大不直接让这条索引查询变慢,但它决定了 page cache 的压力面。

### A.3 单线程 + 同步工作面

- Bridge 是**单进程 Node**。进程树:`npm exec tsx`(45497)→ `tsx cli`(45928)→ **真正的 worker `node`(45953)**。
  > ⚠ 方法论坑:`ps` 查 45497 得到 `%CPU 0.0`。**量错 PID 会得到「Bridge 很闲」的假结论**。FLY-1971 里那个「84.4% CPU」没有写明取自哪个 PID、用什么工具,因此只能算低成色锚点。
- `packages/teamlead/src` 非测试代码里的同步子进程调用 —— ⚠ **本条经 Codex R1 指出后下修并复核**:
  - **56** 是「提到这三个标识符的行数」(含 import),**不是调用点**;
  - 按调用表达式实测:**36 个调用点**,其中 `src/bridge/` 下 **18 个**。
  - 且其中若干在 CLI / 冷路由上,**不是周期性 rider**。
  - ⇒ 「存在同步 fork」这个风险是真的;**「热路径上有 56 处」是我原来夸大了**。作为 M2 的证据,只能用「周期性且可达」的那个子集,完整清单只当库存。
- SSE 广播器 `SseBroadcaster.startPolling()`(`plugin.ts:1183`)**每 2000 ms** 调一次 `buildDashboardPayload()`,后者一次做 **5 个** StateStore 查询(`getActiveSessions` / `getTerminalSessionsSince` / `getRecentOutcomeSessions` / `getStuckSessions` / `getDeliveryStats`)再 `JSON.stringify`。
  - ✅ 它是**有门的**:`addClient()` 里 `if (this.clients.size === 1) this.startPolling()`,`removeClient()` 里降到 0 就停。
  - ⇒ **只要有人在浏览器里开着 dashboard / fleet console,Bridge 就每 2 秒做一轮重活,直到那个页面关掉。** 这是一条「与机器负载无关、与人的行为有关」的周期性开销 —— 正好是 B 节观测到的那种「负载没动但 Bridge 忙起来了」的形状。**列为候选,未证实**(见 §C)。

### A.4 一个只增不减的积压面(候选,未证实为病因)

生产 Bridge 日志 `/tmp/flywheel-bridge.log`(实测 54 MB):

```
[GatePoller] orphan question — no session for from_agent=... (qid=..., lead=...)
```

- 该行累计 **286,531** 条;
- 涉及的**不同 qid 只有 46 个** —— 同一批 46 条被无休止地反复扫描、反复打日志;
- 最近 20000 行里有 19534 条是它,仍是同样 46 个 qid ⇒ 约 **425 个完整轮次**;
- 日志增速实测 ≈ 1.1 KB/s(30 秒 33,516 字节)。

⇒ 事实层面:存在一个**永不清理、只增不减**的 orphan question 集合,每轮 poll 全量重扫。
⚠ 成色:**我没有证据说它就是烧 CPU 的那个**。1.1 KB/s 的日志量本身很小。它是一个真实的浪费面和长期增长风险,不是已证实的病因。

## B. ★ 生产机只读实测(2026-08-22 17:0X–17:2X UTC)

### B.1 原始数据(已随文档提交,可复核)

- 原始 CSV:`evidence/baseline-health-20260822.csv`(600 行样本)
- 采集脚本:`evidence/sample-health.sh`
- 独立客户端复核脚本:`evidence/probe-indep.mjs`

**采集方式(逐字)**:`curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 60 http://localhost:9876/health`,**串行**、每次完成后 `sleep 0.5`,时间戳取自请求**完成**时刻;`load1` 取自同一轮的 `sysctl -n vm.loadavg` 第二列,在 curl **之前**取。

| 统计量 | 值 |
|---|---|
| 采集时长 | 1032 秒 |
| 样本数 | 600 |
| 中位数 | **2.7 毫秒** |
| p90 | 0.509 秒 |
| p95 | **11.96 秒** |
| p99 | 18.59 秒 |
| 最大 | **30.31 秒** |
| ≥ 1 秒的样本 | 54 / 600 = 9.0% |
| **「事务时间占用率」**(见下方命名说明) | **656 秒 / 1053 秒 = 62.3%** |
| 同期机器 load1 | min 5.28,**p50 7.33**,max 11.17 |

**精确算法(便于复核 / 反驳)** —— ⚠ 这里有过一次自我更正,两个数都留着:

- 分子(两版相同):`Σ(latency_i where latency_i ≥ 1s)` = **655.95 秒**。
- 分母 v1(**原估计,已弃用**):`last_ts − first_ts` = 1032 秒 ⇒ **63.56%**。
  > ⚠ **它是错的**:CSV 的时间戳取自请求**完成**时刻,所以第一条样本的 20.95 秒被算进了分子,但分母却从它**完成**的那一刻才开始起算。分子分母的边界没对齐。(Codex R2 MEDIUM-7 指出,已复核。)
- 分母 v2(**现用**):`last_ts − (first_ts − first_latency)` = 1052.95 秒 ⇒ **62.30%**。
- ⚠ 时间戳精度是 **1 秒**(`date +%s`),所以这个比例本身的精度约 ±0.1 个百分点级别以上,不应报到小数点后两位以上。

**结论的成色不因这次更正而改变** —— 62.3% 与 63.6% 都指向同一件事。但报出去的数字应当是 **62.3%**,而且我在更正前已经把 63.6% 报给过 Tadashi 两次(见 §B.6)。

因为采样是**串行**的,每个样本的耗时就是它独占的墙钟,所以这个比例是**墙钟占比**,不是样本占比 —— 两者差别很大(样本占比只有 9.0%)。

### ⚠ 这个数叫「事务时间占用率」,它**不是** plan 的判据量(Codex R2 MEDIUM-9 / R3 MEDIUM-9)

- **本数**:这次**串行**探测的墙钟里,花在「单次耗时 ≥ **1 秒**」的请求内部的比例。
- **plan 的判据量 `b`**:按**固定调度的 tick**计的 `P(latency > **500 毫秒**)`(plan §2.2)。
- 三处不同:**阈值不同**(1 秒 vs 500 毫秒)、**分母不同**(墙钟 vs 调度 tick 数)、**采样方式不同**(串行、慢期欠采样 vs 截止取消、无欠采样)。
- ⇒ **不能拿 62.3% 去对照 plan §3 的结局判据。** 本数只是**动机**;阶段 0 必须用 `b` 的定义**重新量**。

发作是**成段**的,不是零星的:退化段约 130–155 秒,健康段约 50–65 秒,交替出现,粗略周期约 190 秒。健康段 1–3 毫秒,退化段 5–30 秒。

### B.2 发作中 vs 恢复后的对照(同一台机器,负载几乎相同)

⚠ **本节经 Codex R2 MEDIUM-7 更正,原来的表述超出了证据**。下面是更正后的版本。

| | 机器 load1 | Bridge worker **进程** CPU(top 瞬时) | 同(ps 一分钟衰减均值) | `/health` |
|---|---|---|---|---|
| **发作中** | 8.6 – 11.2 | **78.3 %** | **97.9 %** | 10.7 / 14.1 / 19.0 秒 |
| **恢复后** | 7.9 – 8.1(更低) | **29.1 %** | **24.9 %** | 1 – 50 毫秒 |

工具语义(两条都已核):
- `ps` 的 `%cpu`(`man ps`):**「a decaying average over up to a minute of previous (real) time」** —— 近一分钟的衰减均值,不是生命周期均值。
- `top` 报的是**整个进程**的 CPU,**可能包含 native 线程与 worker pool**,**不是**主线程 / 事件循环的占用。

**我原来写、现在撤回的三句话**:
1. ~~「机器 18 个核只有 8–9 个在忙」~~ —— **错**。load average **不是**「在忙的核数」,它是运行队列长度的平滑值(在 macOS 上还包含不可中断等待的线程)。load 8–11 不能翻译成「8–11 个核在忙」。
2. ~~「Bridge 不是被机器抢 CPU 抢死的」~~ —— 由上一句推出的,跟着一起撤。
3. ~~「它把自己那一个线程烧满了」~~ —— 进程外的 `top` **区分不出**是主线程还是别的线程。能说的只有「**这个进程**在烧 CPU」。

### B.3 更正后能说的话,以及各自的成色

| 说法 | 成色 |
|---|---|
| **① 在 load ≈ 9 时观测到的退化,与 FLY-1971 在 load 48.77 记录的那次在数值上接近**(12.9 秒 vs 我量到的 10–19 秒;84.4% vs 78.3%/97.9%) | ⚠ **成色下修(Codex R6 MEDIUM-9)**:这是**两次不受控 episode 之间的数值相似**,**不是「强关联」** —— 无共同测量协议、无重复、无对照,而且在一个重尾分布里数值相近本身并不稀奇。能说的只有:它提供了一个**不需要负载参与的候选解释**,值得用阶段 0 去检验 |
| **② 退化期间该进程的 CPU 明显高于恢复期,而同期机器 load 没有相应变化** | **直接观测**,但 n = 1 个 episode,且 CPU 与延迟读数**不是同一瞬间**取的。这是**机制线索**,不是「找到了控制变量」 |
| **③ 因此把准入闸值从 144 降到 30–40 可能拦不住这类发作** | 由 ① ② 推出的**可证伪预测**,不是结论。**⚠ 能削弱它的观测(有界表述,Codex R5 指出)**:在**零附加负载**的多窗口基线里,低负载自发发作**不再出现**。⚠ 但**有限次观测推翻不了它** —— 三个干净窗口能反驳「发作当前很频繁」,**不能**推翻那次历史观测,也**不能**排除更稀疏的复发。⇒ 阶段 0 估的是**给定运行情境下发作频率 / 占空比的上界**;`spec-baseline.md` 必须**预注册本次曝光意在排除的最小发作率**,否则**非复现只能报 inconclusive**。<br>我原来写的「发作率随施加负载单调上升」**同样不构成反驳**(Codex R4 指出):「高负载下更容易坏」与「低负载下也会自发坏」可以同时为真。 |

### B.4 对现有锚点的重新解读(不推翻,只是限定)

FLY-1971 的每一档都是**单次采样**。在一个中位数 **2.7 毫秒**、p95 **11.96 秒**的分布里(§B.1 的 600 样本):

> 单次采样无法区分「这一档确实变慢了」和「这一次恰好落在尾巴上」。

- load 15 → 2.40 秒:在上表分布里落在 p90 与 p95 之间。**完全可能是尾部样本,也完全可能是真实典型值。现有数据不能分辨。**
- load 48 → 12.9 秒:**落在我在 load ≈ 9 量到的 p95(11.96 秒)附近**。
- ⇒ 这不是说 FLY-1971 错了。是说**它掌握的数据不足以支撑「延迟是 load 的函数」这个读法**,而整张单的修法建立在这个读法上。

### B.5 ★ 这批实测自身的四个已知缺陷(Codex R1 指出,全部成立,不许在转述中抹掉)

1. **观察者效应未排除**。`/health` 每次 ≈ 18 次同步 SQLite(见 A.2),我每 0.5 秒打一次 ≈ **给事件循环加了 36 次查询/秒**。36 次索引查询/秒**不太可能**吃掉 80% 的一个核,但我**没有做 A/A 对照**(稀疏探针 vs 密集探针),所以**不能排除**探针本身参与了它所测量的现象。
2. **响应依赖的采样偏差**。采样是串行的:一个请求慢,期间就采不到别的样本 ⇒ **慢期被采样得更少**。这让上表的**分位数偏乐观**(真实的 p95 只会更差,不会更好)。墙钟占比不受此影响,样本分位数受。
3. **单一时间窗**。1032 秒、一个窗口、而且就在一次舰队重启(本地 09:28)之后不到一小时。**不能**排除这是重启后的暂态或某个周期性任务的一段。
4. **「零施压」≠「零负载」**。它只意味着**没有本实验施加的处理**,机器上仍有 9 个 session、16 个 Lead、以及一切日常工作。

⇒ 这四条合起来的意思是:**B 节是一个足以威胁 FLY-1971 前提的假设,不是一个可以取代它的因果模型。** plan.md 的阶段 0 就是为把它做扎实而设的。

## C. 机制候选清单(⚠ **不是本方案要回答的问题**)

⚠ **经 Codex R1 HIGH-1 / R2 更正**:原来这一节写的是「方案必须能区分下列机制」。**做不到** —— 进程外的观测量无法把 M1 / M2 / M4 / M6 分开(理由见 plan §2.4)。

⇒ 本节现在的用途只有两个:**(a)** 给另案(plan 的 Q6)一份候选清单;**(b)** 指出哪些**便宜的协变量**值得在压测中顺带记下来,**用于排除,不用于证实**。

> ⚠ **数据来源已变**(Tadashi 裁定,2026-08-23):这些协变量**不再由 Phase-0 探针采集**。探针只产判据量 `b`;对照数据取自 **Bridge 本体内建仪表(FLY-1995)** 与 **`machine-watermark.ts` 现有传感器**,分析时按时间戳对齐。见 plan §2.2(c)。下表读作「分析时该看哪些量」,不是「探针要采哪些量」。

| # | 机制(候选) | 便宜的协变量(**只用于削弱,不用于证实**) | 真要归因需要什么 |
|---|---|---|---|
| M1 | 机器 CPU 竞争 | 若发作期该进程 CPU **低**,与 M1 相容。⚠ **高不等于削弱 M1** —— 进程 CPU 接近一个核**并不排除**宿主调度竞争(它可以既在烧又在等) | 剂量-反应实验(= plan 的 Q2) |
| M2 | 事件循环被自身同步工作占满 | 该进程 CPU 高 —— ⚠ **与 M2 相容,但也与「某个 native/worker 线程在烧」相容**,进程外分不开 | `monitorEventLoopDelay()` / `eventLoopUtilization()` + 嫌疑工作的开关对照 |

1. **`pressure_hold` 会卡死全部准入**。FLY-1082 的 hold 是 StateStore 里一条 durable 行,`tryAdmit()` 见到就对**每个** runner 返回拒绝(`/api/runs/start` 走同一条)。FLY-1142 探索文档记载过它卡死 **8 小时**的真实事故。⇒ 压测前必须记录 hold 状态,压测后必须**验证已清**。

## F. 明确未验证 / 未做的事

- ❌ 没有识别出烧 CPU 的具体代码路径(`sample` 走不出 JIT 帧)。
- ❌ 没有在**发作期**采到 `lsof` 连接数,所以 M6 既没被证实也没被排除。
- ❌ 没有做任何施压 —— 全部数据来自机器的自然状态。
- ❌ 只观测到 **1 次**发作,没有发作频率、持续时间分布、间隔分布。
- ❌ 没有验证 529 隔离房里的 Bridge 是否表现出同样的发作(隔离房 Bridge 没有生产的 9 个 session 和 1.6 GB DB)。
- ⚠ 所有 CPU 数字来自 `ps` / `top`,**不是** Node 内部的事件循环延迟。`top` 报的是**整个进程**的 CPU(可能包含 native / worker-pool 线程),不是主线程事件循环占用。⇒ **从进程外无法证实「事件循环被占满」这个机制**,只能拿到与之相容的线索。要真证实,需要在一个**可改代码的** Bridge 上用 `perf_hooks.monitorEventLoopDelay()` / `eventLoopUtilization()`,那是另一件事(plan §2.4)。
- ⚠ 端点契约的四处修正(Codex R1 HIGH-7,已逐条复核):
  - `/health` **不暴露** `pressure_hold`(只有 `admissionPause`);
  - `/health` 的 `sessions_count` 是 `getActiveSessions()` 的行数,**含 parked / awaiting_review / approved_to_ship**,不是「正在跑的 runner 数」;
  - `/api/sessions` 与 `/api/linear/issues` **需要 master Bearer token**(实测无 token 返 **401**);
  - `lsof` 只能数 TCP 连接,**分不出哪条是 `/sse`** ⇒ 它对 M6 只是**弱代理**,不是 `SseBroadcaster` 的客户端数。
