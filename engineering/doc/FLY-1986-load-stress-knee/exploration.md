## 2. ★ 本单新增实测:同一负载下延迟跨度已超 1000 倍

2026-08-22 17:04Z 起,本 runner 在生产机做**只读**采样(只 curl `/health`,与 `scripts/bridge-liveness-probe.sh` 每分钟做的事同类,零写入):

```
20 次连续采样,load 稳定在 9.20 – 10.43
health 200  0.003379s     health 200  0.002424s
health 200  0.137380s     health 200  0.001615s
health 200  0.004829s     health 200  0.004043s
health 200  0.002924s     health 200  0.001973s
health 200  0.002218s     health 200  0.003920s
health 200  0.026047s     health 200  0.002363s
health 200  0.005151s     health 200  0.001615s
health 200  0.014850s     health 200  0.000974s
health 200  0.111517s     health 200  1.435094s   ← 最大值
health 200  0.001960s     health 200  0.001751s
```

- p50 ≈ **3 毫秒**,最大 **1.435 秒**,**跨度 ≈ 1470 倍,而 load 全程只在 9.2–10.4 之间动**。
- 分布是重尾的:20 个样本里 3 个 ≥ 0.1s,其余都在毫秒级。

### 2.1 这条观测为什么会改变方案的形状

**它不推翻任何已有锚点**——load 15 那次 2.4 秒完全可能是真实的典型值。但它推翻了一种读法:

> ⚠ 已有锚点每档只有一次采样。在一个同档内跨度 1000 倍的分布里,**单次采样无法区分「这一档确实变慢了」和「这一次恰好落在尾巴上」**。

⇒ 所以压测方案的第一个问题**不是**「拐点在哪」,而是:

> **load average 到底能不能预测 Bridge 的延迟?**

如果每一档内部的方差远大于档与档之间的差异,那么 FLY-1971 想做的事(把闸门从 144 降到某个数)**不管选哪个数都是弱修法**——因为闸门读的那个变量本身就不携带足够信息。这是必须先证伪/证实的前置问题,而且它可以用同一批数据顺带回答(方差分解),不额外增加成本。

### 2.2 ⚠ 本条观测自身的成色

- n = 20,单一时间窗(约 20 秒),单一端点,只在一个负载点(≈9.5)。
- 只能支持「**在 load ≈ 9.5 这一点上,/health 的分布是重尾的**」。
- **不能**支持「所有负载点都重尾」、「尾巴的成因是 X」、或任何关于拐点位置的话。
- 一个 5 分钟的后台采样正在跑,会把 n 提到 ~600,用来把这条观测从「20 个样本的印象」升级成「一个可报区间的分布」。区间而非点估计。

## 3. 机制候选(压测必须能区分它们,因为修法完全不同)

「曲线还是开关」只是表象层面的问法。真正决定 FLY-1971 怎么修的是**哪一种机制在起作用**:

| # | 机制 | 表象 | 迟滞 | 若成立,正确修法 |
|---|---|---|---|---|
| M1 | **CPU 竞争**:Bridge 与 N 个 runner 抢 18 核,可用 CPU 份额 → 0 时延迟 ∝ 1/(1−ρ) | 平滑但超线性的曲线 | 无 | 闸值放拐点下,FLY-1971 的修法成立 |
| M2 | **事件循环被同步工作堵头**:Bridge 是单进程 Node;周期性 rider 做同步 SQLite 查询与同步子进程(tmux/ps)探测,高负载下每次同步调用本身变慢几十倍,事件循环整段停住,HTTP 排队 | 阶跃状,平时毫秒偶尔秒级(**与 §2 观测一致**) | 有 | 闸值有用但不够;真修是把同步工作挪下事件循环 |
| M3 | **超时—重投正反馈**:send 45–50 秒超时 → 调用方重发 → 负载更高 → 更多超时 | 真·双稳态,一旦进去不靠降载出不来 | 强 | 闸值单独无效;需重试预算/熔断(FLY-1974 / FLY-1963) |
| M4 | **内存 / page cache**:`teamlead.db` **1.6 GB**(实测 `page_count 432198 × 4096`)。工作集在 page cache 里时查询是微秒级;一旦内存压力把它挤出去,每次查询变成真实磁盘 IO,而且是**同步地**发生在事件循环上 | 阶跃 + 需重新预热才恢复 | 强 | 与 load **无关**;降 load 闸值治不了,要么控内存要么缩 DB |
| M5 | **外部依赖**(Linear / Discord / GitHub 限流或抖动) | 只有依赖外部的端点变慢,/health 不受影响 | 无 | 与本机负载无关,阈值方向整个错 |

### 3.1 已有证据对各机制的倾向(仅倾向,非结论)

> ⚠ **本节写于 research.md 之前,其中几条倾向后来被 Codex R1/R2 复核推翻或下修。以 research.md §B / §C 为准。** 保留原文以留痕。

- **削弱 M1(不等于支持 M2)**:§2 的尖峰发生在 **load 平的时候**,单纯的机器 CPU 竞争解释不了。⚠ 但这只**削弱** M1,**不指认**任何一个替代机制。
- **支持 M4 的额外事实**:`teamlead.db` 1.6 GB;`/health` 处理函数(`plugin.ts:1784`)里 `store.getActiveSessions()` 是**同步** SQLite 查询,`getAdmissionPause()` 再一次,liveness manifest provider 再一次。所谓「最便宜的探针」其实每次都要在事件循环上打三次本地 DB。
- **削弱 M4 的一点**:`sessions` 表上 `idx_sessions_status` 存在,`/health` 那条 `WHERE status IN (...)` 是走索引的,不是全表扫。所以如果 M4 成立,代价更可能来自**别的 rider 扫的大表**而不是 /health 自己。
- ~~**支持 M2 的额外事实**:非测试代码里有 **56 处** 同步子进程调用~~ —— ⚠ **已更正**:56 是「提到这三个标识符的行数」(含 import),按调用表达式实测是 **36 个调用点**(`src/bridge/` 下 18 个),且部分在 CLI / 冷路由而非周期性 rider 上。见 research.md §A.3。
- **FLY-1971 记录的「延迟按请求成本递增(health < linear < send)」**同时兼容 M1 与 M2,**不能**用来区分它们——它只能排除 M5(单路故障)。这一点 FLY-1971 已经正确地用了,但不能再往前推。

### 3.2 ⇒ 对方案的直接要求

只测「外部 HTTP 延迟 vs load」这一组曲线,**无法区分 M1/M2/M4**,而这三者的修法互相不能替代。所以每个档位必须同时记录协变量:

- 机器侧:load1/5/15、run queue、free%、swapout delta(复用 FLY-1142 已经定好的真实内存压力口径)、page cache 状态代理。
- Bridge 进程侧:瞬时 CPU%(**必须标明取值语义**——FLY-1971 里那个「84.4% CPU」没有说明是 `ps` 的生命周期均值还是 `top` 的瞬时值,两者含义完全不同,这条锚点因此只能算低成色)。
- 端点侧:四条成本阶梯的**分布**(p50/p95/p99/max),不是单值。

## 4. 「曲线还是开关」的可操作定义

「曲线」和「开关」在单次上行扫描里长得可以很像(一条足够陡的曲线看起来就是台阶)。能把两者分开的是**迟滞**:

- **上行扫描**找 trip point T:第一次越过服务判据的档位。
- **下行扫描**找 recovery point R:从 T 之上一档一档降下来,服务重新回到判据之内的档位。
- **R ≈ T** ⇒ 是曲线(无记忆),阈值可以放在 T 之下留余量。
- **R ≪ T** ⇒ 是开关/双稳态(系统进去了就出不来),**阈值必须放在 R 之下,不是 T 之下**——因为放在 T 和 R 之间的任何值,系统一旦进去就永远不会自己出来。

这条正好也是 FLY-1971 提出的「配向下回滞」在实验上的依据:**当前 `runner-admission.ts` 根本没有迟滞**(单次比较),如果 R ≪ T,那么「加迟滞」不是锦上添花而是必需项。

## 5. 施压方式的取舍

issue 明确要求「真实负载形状,不是人造 CPU burn」。理由成立(人造 burn 只造 run queue,不造 fork 风暴、不造 IO、不造内存压力),但纯真实负载不可复现、不可调、且贵。

- **A 档(标定/可复现)**:用仓库自己的东西造压——并发的 `vitest` 跑真实测试套件。它同时产生 CPU、fork、文件 IO 和内存占用,形状接近真实评审/QA job,而且**并发度是一个干净的旋钮**。
- **B 档(有效性校验)**:在少数几个档位用**真 runner**(QA 房 slot)复现同一个 load 数,看 Bridge 的响应是否与 A 档在同一 load 下一致。
- **A 与 B 在同一 load 下不一致 ⇒ load average 不是正确的自变量**,这本身就是最有价值的输出之一(直接决定 FLY-1971 该不该继续用 loadavg 当闸门)。

## 6. 安全护栏(必须在方案里写死)

压测会人为把生产机打到高负载,以下每一条都是真实可触发的伤害:

1. **`pressure_hold` 会被自己的压测触发并卡死后续准入**。FLY-1082 的 hold 是 durable 一行,`tryAdmit()` 见到就拒**所有** runner(FLY-1142 探索文档记载过一次卡死 8 小时)。压测必须在开跑前记录 hold 状态、结束后**验证 hold 已清**,不清就显式上报。
2. **告警风暴会 page founder**。高负载会同时踩到 LeadWatchdog / 内存 ARC / Bridge liveness probe。要么在隔离房跑(告警镜像),要么提前让 founder 知道该窗口的告警是预期的。
3. **绝不重启 Bridge**。FLY-1959 之后重启只走班车或 founder 紧急票;压测窗口内任何形式的重启都不在授权范围。
4. **不碰生产数据写路径**。`send` 是写路径(真发 Discord),必须指向专用测试频道或隔离房。
5. **单档位熔断**:任一档位出现预设的危险信号(端点超时超过 N 次 / 内存进 danger / 有真 runner 在跑)立即降档并中止。
6. **不先上生产**。先在隔离房把 harness 与大致拐点标定出来,生产只做少数几档的短窗确认。
