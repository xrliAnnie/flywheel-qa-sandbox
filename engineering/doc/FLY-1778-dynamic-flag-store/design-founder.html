② 为什么是重做,不是复活旧 PR

旧实现 FLY-1150(PR #698)长到 19,833 行被清理令关闭。考古发现:58% 是一个 1 万行的盘点 JSON 文件,真正的产品代码约 5,400 行——超重的不是界面,而是三台「批量迁移基础设施」:per-flag 迁移状态机、.env(存开关值的文本配置文件)与数据库之间的双向镜像同步器、60 秒一次的值变更扫描器。

本单的解法不是做小一号的同款,而是抽掉三台机器存在的理由:每个 flag 的权威(值以谁为准)在代码里静态声明——要么归 store 管,要么留老路——没有运行时切换,就不需要状态机;单一权威,就不需要镜像;store 是纳管 flag 唯一的写入口,时钟在写入的同一笔事务(要么全成、要么全不成的数据库操作)里直接落账,就不需要扫描器。

③ 核心流程:翻一个开关的全程

入口是一条 CLI(命令行工具)命令,必须写明原因;Bridge 先「预检」并发一个一次性确认令牌,确认后在一笔事务里写值、比较新旧生效值(值真的变了才拨 value_last_changed,同值重写不误拨)、并在同一笔里写变更流水账。读的那头「用时现读」(read-on-use):每次代码要用这个开关时都去数据库里读当下的值——所以翻完立即生效,全程不碰 git、不重启任何进程。

④ 数据模型:三张表

flag_values 是值的唯一真相源,每行带版本号(每次写必加一,两人同时改会有一人被拒绝重试,防互相覆盖);flag_value_changelog 是只增不改的流水账,「原因」一栏数据库层面强制必填;flag_store_meta 是一行的应急围栏标记(见 ⑤)。

关键语义value_last_changed 只在生效值真的变了时更新;初次纳管收编现值时不算变(留空 = 「纳管以来没变过」);代码里默认值被 PR 改掉的情况,由启动时的一次对账补记(标注为「观测到的时刻」,与「翻动发生的时刻」明确区分——上游 PRD 要求两口钟必须点名)。

⑤ 应急逃生口:出问题时怎么退

万一 store 本身出故障,运维可以改一行 .env 并重启,进入旁路模式:所有纳管开关退回老的 .env 语义,系统照常跑。代价是诚实标注的:旁路期间禁止翻这些开关(值冻结)、它们的时钟标记为「不可信」;退出旁路时做一次全有或全无的恢复对账,每个开关保守地拨一次钟(旁路窗口发生过什么无法回放,时钟不假装覆盖它)。进出旁路只能通过「改 .env + 重启」——不给运行时开关,否则权威可以被悄悄切走,时钟就撒谎了。

⑦ 诚实边界:这个设计做什么、不做什么

  • 做:四件套——一张值表(带 value_last_changed)、读点接现有解析层、一个带审计的 CLI 翻转入口、安全白名单留老路。开工前先做 M0 读点盘点(硬门,Tadashi 复审后才写实现代码;首批 5 个只可缩不可扩)。
  • 不做(越界即停,开新单):灰度/百分比发布、开关依赖图、历史回滚、可视化大盘、跨进程读取、数值型开关纳管、项目级开关纳管。
  • 时钟契约只覆盖纳管开关:没纳管的开关(安全白名单、CLI 读的、数值型)和今天一样没有翻转时钟;每周退役扫描(已上线的快照法)继续用快照对比,不退化。扫描消费这口新钟 = 明确的后续单,本单只产出契约。
  • 两处对 issue 原文的显式收窄(将在 M0 复审时报 Tadashi 确认):6 处「重启才生效」读点的手术拆出去(那些开关今天无人能翻,手术对使用者不可见);扫描消费拆出去。
  • 已知双重故障角:store 整库坏掉期间进旁路,围栏可能写不进——恢复靠修它的那个 PR 显式带时钟失效步骤,不为这个角落造更重的机器。
