FLY-1718 设计:重新派工不再丢已拍板成果

Issue FLY-1718 · 设计节点交付 · 2026-08-12 · Codex 设计评审 5 轮通过(xhigh)· 实证来源:FLY-1704 现场

① 一句话总结

给「同一个 issue 第二次派工」装四道结构护栏:派工前先问云端「上一轮的成果还在不在」,在就接着做、探不清就不派;再把「强推覆盖」「审查指令指向废文件」「秒死循环重生」三个同族窟窿一起堵上——全部是机制兜底,不再靠嘱咐 runner 自觉。

② 出了什么事(FLY-1704 实证)

一个 issue 的第一轮 runner 已经把成果推上了云端分支、开了 PR、方案你也拍板了。后来这个 runner 被关闭清理,同一个 issue 第二次派工时,系统只在本地找「上一轮的痕迹」——但本地已经被清干净了,于是它判定「全新开始」,从主干新开了一条同名分支。

结果:新 runner 花了 22 分钟、烧了 7 万 token,把你已经拍板的东西重新造了一遍,靠人肉盯梢才发现。更险的是:如果它执行强推(force-push——git 的覆盖式上传,会把云端分支整个改写成本地的样子,别人的成果直接蒸发),拍板件就没了。当前唯一的防线是一句口头禁令。

③ 修后的派工流程

核心哲学一句话:重生必须先对账存量。派工入口按下面的顺序过闸:

  • 在 → 新工作目录直接从云端成果顶端起步(先把成果完整取回本地并核实,不是只看一眼名字),runner 的任务说明里写明「有 open PR #N,先读它」。
  • 确认不在 → 真·全新开始,行为和今天完全一样(不影响正常新 issue)。
  • 探不清(断网、超时)→ 拒绝派发,宁可晚一会儿,不许瞎分叉——这一刀是整个设计的底色:探不清存量就不动手。

④ 四个工作包(结构模型)

这次事故牵出同一哲学下的四个窟窿,拆成四个互不依赖的工作包,各自独立上线,P1 最先:

包堵什么窟窿机制要点
P1 延续性预检fresh 派工无视云端成果,从主干分叉派工前问云端同名分支;在 → 取回核实后续接;探不清 → 拒发。另:本地被清理后,原有的「进度账本续跑」也补上从云端找回的能力
P2 push 护栏强推覆盖拍板件只有口头禁令每个 runner 工作目录建好时自动装 pre-push hook(git 在上传前自动运行的本地检查脚本):覆盖式上传一律拦下并记审计账;确需强推要先问 Lead 拿确认、设一次性放行码
P3 指令路径快照自动审查指令指到改道后的废文件,下一个 runner 会为废文件过审查门Bridge 侧存对账单:「这次审查审的是哪个文件的哪个版本」;过门时三方核对(对账单 = 审查结果 = 当前文件),对不上不放行
P4 秒死断路器上一轮出生即死,系统 1 秒后又派一个,继续秒死上一轮活了不到 60 秒就死 → 冷却 1/2/4/8 分钟再试;连续 5 代秒死 → 停止自动重派,叫 Lead 来看

⑤ 关键取舍与否决的备选

拍板的方向

  • 探不清就拒发,不是「警告一下照旧」 —— 警告+照旧等于把 FLY-1704 再演一遍;拒发可重试、不留残留。
  • 默认永远续接,重做必须显式说 —— 续接错了大不了 runner 在旧基础上重整(可恢复);分叉错了会覆盖拍板件(不可恢复)。真要推倒重来,由 Lead/你显式下令并留审计痕。
  • 护栏装在机制层,嘱咐退役 —— 「先读已有成果」的嘱咐在 FLY-1704 里根本没法执行:成果不在盘上。结构给不到的东西,嘱咐给不了。

否决的备选(为什么不)

  • 只靠提示词嘱咐 → 已实证不可执行。
  • 把预检塞进底层建目录的代码 → 底层看不到 issue/PR 上下文,分层被污染。
  • 在 GitHub 服务端配强推保护 → 平台级改造、多仓配置漂移;本地护栏当天可达,服务端留后续单。
  • 断路器顺带做「自动诊断死因」 → 体量是另一个单;这里只做止血(冷却+叫人)。

评审锤炼(Codex 5 轮,共 18 项发现全采纳)

几个有代表性的:云端查到的成果编号必须真正下载核实后才能用(光看编号会建目录时报错);「续接」不能借用三阶段流水线的内部开关(会误触接管逻辑);断路器的「放行」要做成有租约的预订,不然一次网络抖动会把它永久烧断;审查对账单的权威存在 Bridge 数据库里,runner 改不了。

⑥ 诚实边界:这个设计不做什么

  • 不防故意使坏的 runner:护栏是防事故不防对抗——技术上 runner 能绕过本地 hook(git 有跳过检查的开关)。绕过会留审计账、且合同明文禁止;真要防对抗得做服务端保护,那是后续单。
  • 不改「close done=true 把没合并的活也标成完成」的老语义:那牵扯整个终态机;本设计绕开它——预检不看会话状态,只看云端存量,所以照样兜得住。
  • 不做死因自动归因:秒死断路器只负责「停下来、叫人」,不负责「猜为什么死」。
  • 不覆盖人类自己建的工作目录:只管系统派工建的 runner 工作目录。
  • 姊妹单 FLY-1712(重生时对账「信箱里还没送到的批准」)独立推进,两单互不阻塞。
