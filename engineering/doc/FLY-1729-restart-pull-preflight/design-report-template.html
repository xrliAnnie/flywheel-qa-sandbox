重启脚本:起步先拉最新 main

FLY-1729 · 设计方案 · 2026-08-12 · Codex 设计评审 6 轮通过
一句话总结

给全舰重启脚本加一段「起飞前检查」(preflight,即正式动手前的一串安全核验):先确认代码目录状态正常,再把它拉到 GitHub 上最新的 main(主干分支,所有已合入代码的唯一权威版本),任何一步不对就响亮报警并停下,绝不带着旧代码或可疑状态起舰。零新开关、零新机制——就是把你 8-12 那天看到 Lead 手动干的「拉代码 → 重编译 → 重启」机械化进脚本本身。

事故回放:8-12 差点发生什么

重启脚本一直有个盲区:它部署的永远是「本机代码目录里当下是什么就是什么」,从来不去 GitHub 拉最新代码。自动更新器那条路(系统定时任务)会先拉再调它,所以没事;但 Lead 或人手动直接跑重启脚本时,没有任何人拉代码。

8-12 当天,生产代码目录落后 main 6 个提交。如果直接重启,当晚要上线的两张卡(#807 / #814)根本不会生效——舰队会在旧代码上原地起舰,而且不会有任何报错。是重启前的一次演练模式(dry-run,只打印计划、不真执行的试跑)露了馅,Lead 手动补拉了代码才救回来。

修法核心:七步起飞前检查

重启脚本抢到互斥锁之后、做任何真动作之前,插入这段检查。图里红色 = 直接停下并报警(需要人来处理),黄色 = 报警停下但等网络恢复重跑即可,蓝色 = 现有机器,一行不改:

「快进合并」(fast-forward merge):本地没有任何多余提交时,直接把本地指针推到最新 main,不产生新的合并痕迹——这是唯一允许的合并方式,保证部署的每个字节都来自 main 本身。演练模式跑同样的检查并打印「将要拉到哪个版本号」,但不真的动代码。

修完后的格局:两条路径,一条不变量

自动更新器那条路完全不用改(它已经先拉后调);新检查对它只是几秒钟的幂等复核(重复执行也不改变结果的操作)。从此不管谁、从哪条路触发重启,都共享同一条铁律:重启起步那一刻,代码目录必然等于最新 main。

关键取舍与被拒方案 第 1 条请你过目
决策取舍理由 / 被拒的方案
① build 失败后的行为:沿用既有「回滚重启旧版」,偏离 issue 字面「不重启」 你的原话是「build(把源码编译成可运行产物)失败同样 fail-loud 不重启」。但现有机器的真实顺序是:先停掉 Bridge、再 build——build 失败时 Bridge 已经停了,字面上的「不重启」= 舰队保持死机。既有机制会自动回滚到旧版本、重启旧版恢复服务、响亮报警、且绝不把失败版本记成「已部署」。本设计保留这个既有行为(精神上满足:不在坏状态上完成部署、必须响亮;字面上偏离:它会用旧版重启)。要改成字面语义得把 build 挪到停机之前,那是对部署链的真实重排、另有风险,建议不塞进这张卡。你若不同意,评论区说一声,我们另立 issue 做重排。
② 断网时,重启会被拒绝 拉不到 GitHub = 不知道 main 最新是什么,继续跑就是「可能又在旧码上起舰」——正是本次事故。所以拉取失败一律报警停下(等网络恢复重跑即可)。真正的崩溃恢复不靠这个脚本:Bridge 挂了由 macOS 的系统服务管家 launchd 自动拉起,不受影响。被拒方案:加个「跳过拉取」的开关——违背你「零新 flag」红线,且开关一定会被误用。
③ 拉代码放在锁内,接受「重启逻辑本身晚一代」 手动直调时,本次运行使用的是启动那一刻的旧版重启脚本去部署新代码(下次重启自愈)。被拒方案:拉完代码后让脚本「重新执行自己的新版本」——会撞上自己持有的锁造成自锁死,属于真实新机制 + 真实死锁风险。另一个被拒方案:在抢锁之前拉代码——会和正在进行中的另一场重启的 build 抢代码目录,可能编译出损坏产物。
④ 本地有多余提交/分叉时,只报警不清理 绝不 reset --hard(git 的强制还原,会永久丢弃本地未上传的东西)——它会吞掉未知的本地状态。留给人裁决。
⑤ 顺手修掉一个既有隐患 评审中发现:现有「特殊切换流程安全闸」里,git 读取失败会被误当成「不需要切换」放行(fail-open)。本设计把它改成读取失败 = 报警停下(fail-closed),自动更新器那边的可观察行为保持逐字不变。
诚实边界:这个设计不做什么
  • 不改自动更新器的拉取流程——它本来就是对的;更新器在重启锁之外拉代码的既有小窗口也不在本单修(单列观察)。
  • 不消除直调路径「重启逻辑晚一代」(见取舍③,下次重启自愈)。
  • 不加任何跳过开关、不加可调参数——拉取限时 120 秒是写死的常量。
  • 不代替人清理本地脏改动或分叉,也不动其它项目仓的检测逻辑。
  • 不重排 build/停机顺序(见取舍①,你若要,另立 issue)。

你的三条验收标准逐条映射:

  1. 制造「落后 N 个提交」→ 重启 → 起舰后运行版本 == 最新 main ✅(函数级 + 顶层 + 真机各一层)
  2. 本地脏改动 → 响亮拒绝,信息指明原因 ✅
  3. 演练模式输出「将要拉到哪个版本号」✅
