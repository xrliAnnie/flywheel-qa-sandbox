01 · 先看结论

这次修好了吗？

你 8-12 撞到的那件事——重启完，刚合进去的两张卡还是没上线——原因是重启脚本从来没有「先把最新代码拉下来」这一步。它只是拿最新 main 的编号来做个对比，然后照旧用本机那份老代码去构建、去起舰。这次把那一步补上了：重启一开始就先拉，拉不干净就宁可不重启也不乱动你机器上的东西。

原来会怎样

重启脚本里没有任何 fetch / merge。它读一下 origin/main 的编号只为比较，构建用的仍是本机 checkout 里那份代码。8-12 那次生产落后 6 个 commit，如果直接重启，E1.5 的两张卡（#807 / #814）根本不会上线——当时是 Tadashi 手动 pull + build 才把新码带上的。

现在会怎样

重启一开始（已经拿到重启锁、还没碰任何服务之前）先 fetch，再确认三件事：在 main 上、被跟踪的文件没有本地改动、能够直接快进。三件都成立才 merge，然后才构建、才起舰。任何一件不成立就大声停下并报警，绝不 reset、绝不 stash。

QA 判断： PASS

02 · 怎么修

病根和修法

「知道有新代码」和「把新代码拿过来」是两件事，脚本只做了前一件。

真正的病根

restart-services.sh 里只有一处读 origin/main，用途是和已部署编号做比较；整条链路上没有 fetch，也没有 merge。所以只要本机 checkout 落后，构建就必然发生在旧代码上，而且看起来一切正常——日志、健康检查、告警全是绿的。

修复原则

只补一步机械化动作，不引入新机制、不加新开关；宁可停下，也不替你决定丢掉本地状态。

具体改了什么

  • 重启锁内、任何构建与服务动作之前，先 fetch 最新 main 并冻结目标 SHA。
  • 只接受「能直接快进」这一种情况；脏、分叉、本地超前、拉不到，一律停下并具名报警。
  • dry-run 也真去 fetch，并把「会拉到哪个 SHA」完整打出来，但一个字节都不改。
