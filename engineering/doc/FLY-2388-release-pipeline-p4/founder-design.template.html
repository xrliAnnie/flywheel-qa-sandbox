FLY-2388 · 发布流水线 B1:把候选版本安全地交给客户

Issue FLY-2388 · 设计节点 · 2026-09-08 · Codex 设计评审 3 轮后 APPROVED · 文档:engineering/doc/FLY-2388-release-pipeline-p4/

一句话

发布机器的零件(打包、上传、验 hash、切指针)其实早就造好了;这单做的是把它们接成一条真正能跑的线:先修好死了 52 天没人发现的 beta 线,再补上「把版本交给客户」那一步的按钮,并把薄壳(客户装的那个小安装器)的 npm 发布改成不用长期密码的方式。

名词解释:payload = 真正的产品代码包;薄壳 = 客户 npx @flywheel-ai/onboard 装的那个小安装器,它不含产品代码,只负责去拉 payload;manifest = 一份放在 Cloudflare 上的「版本目录」,里面两个指针分别指着内部 beta 和客户正式版;CAS = 「先看清目录现在长什么样,再原子地改」,两个人同时改只有一个能成。

审计发现的两件现场事实(设计前必须知道)

事实 A:beta 线自 7 月 18 日激活起,210 次全部失败

每 6 小时自动发一个内部 beta 的流程,从激活那天起一次都没成功过,每次都死在同一句「目录改写冲突,重试 8 次仍失败」。没有任何告警接线,52 天无人发现。

根因(证据链已核,待一次带凭据的探针最终确认):Cloudflare 边缘(Cloudflare 在 Worker 前面那层 CDN)对返回的 JSON 做了压缩,按它的规则把「强 ETag」改成了「弱 ETag」(ETag = 目录的版本指纹;弱 ETag 就是前面多了 W/);我们的服务端只会剥引号、不认 W/,于是每次比对都失败。本机测试环境没有 Cloudflare 那一层,所以永远测不出来。

图 1 · beta 线失败的根因:边缘把强 ETag 改弱,服务端不认(时序图)

事实 B:GitHub 上的凭据面是空的,且套餐做不出「Annie 点一下」的门

  • GitHub 的 release 环境(environment = GitHub 里一个只有 main 分支上的任务才能读到密钥的隔离区)里一个密钥都没有;7 月首发时用的 Cloudflare 与 npm 密钥都已不在。所以今天既不能重新部署 Worker,也不能再发薄壳。
  • 本仓库的 GitHub 套餐不支持「required reviewers」(让指定的人点一下批准才继续的功能;已实测,GitHub 直接回「套餐不支持」)。
  • 本机所有 runner 都用 Annie 的 GitHub 登录,所以「谁点了按钮」在 GitHub 层无法证明是 Annie 本人。

核心流程:PRD 的六步里,B1 补齐第 ②④⑥ 步

绿色 = 已经造好、本单只修 bug;蓝色 = 本单新建;灰色 = 未来的 B3/B5。关键设计:上传(② 窗口前)和切指针(④ 窗口后)刻意分开,中间那一步「授权」在 B1 期间 = Annie 在 Discord 说一声 go、Lead 核实是她本人后再按按钮;将来 B4 落地后 = 否决窗口里她没喊停就自动 go。

图 2 · 六步流程与三条 GitHub 工作流的分工(流程图)

零构建:第 ④ 步的按钮按下去之后不再编译、不再打包,只核对「要发的那个文件的指纹(sha256)」是否与审批时一模一样,对上才切指针。所以 Annie 批准的就是最终交付物,不存在「批了 A 发了 B」。

凭据与授权边界:哪把钥匙在哪、能开什么门

图 3 · 四条工作流各持哪把钥匙;三把 capability token 的 sha256 存在 Worker 里(结构图)
  • customer-release token(能切客户指针的钥匙)= 由 runner 一次性随机生成、直接写进 GitHub 的 release 环境,过程中不显示、不落盘;只有 main 分支上声明了 environment: release 的任务才能读到。
  • 它能做的最坏的事 = 提前把一个「已经从 main 代码打包、已证明与 beta 逐字节相同、指纹已绑定」的候选发给客户,或把当前客户版本撤回到另一个正式版。它做不到把任意代码推给客户——那需要另一把 beta 钥匙的明文,而 runner 读不到 GitHub 密钥。
  • Cloudflare 的 API token 本来就能改 Worker 里任何一把钥匙的指纹,所以把 customer-release token 放进同一个环境,没有让边界比今天更松。

manifest 的格式一个字段都不改(schemaVersion 仍是 1)。每个发布候选在目录里有一条记录,状态只能单向前进:

图 4 · 候选状态机;本单新增的是三条「abandoned(放弃)」的进入路径与清理策略(状态图)

staging 清理策略(PRD 让工程定的那条)

情况谁、什么时候把它标成 abandoned
同一个正式版本号有多个候选赢家 commit 的那一次 CAS 里,顺手把其余候选标掉(原子)
beta 候选被更新的 beta 取代 / 搁浅每 6 小时的 beta 任务在预约新版本号的那一次 CAS 里,把其它未完成的 beta 候选标掉
被 Annie 否决 / 主动放弃按钮工作流的 action=abandon;将来 B4 自动按
搁浅超过 14 天的正式版候选runbook 手动跑 abandon --stale-days 14 --apply(默认只列出不动)
物理删除对象沿用已有的三步清理(expire → tombstone → delete),不新造清理系统;不做定时化,因为那把运维钥匙同时能签发客户 license key,不该进 CI

薄壳 npm 发布:改成 trusted publishing,发的是「那一个文件」

trusted publishing(OIDC) = npm 与 GitHub 之间的信任关系:GitHub 上指定的那条工作流在 main 上跑时,npm 临时发一张几分钟就过期的通行证,不再需要保存任何长期 npm 密码(旧密码 90 天到期、还绕过双重验证)。

图 5 · 薄壳发布:先打出一个确切的 .tgz,门检查和发布用的都是同一个文件;registry 已有同版本时按指纹判断是「重跑」还是「事故」(流程图)
  • dist-tag 规则:版本号带 -beta/-rc 这类后缀 → 打 next 标签;干净版本号 → latest。客户默认装的是 latest,预发布版不会误伤客户。
  • 发布后回读:从 npm 把刚发的包下载回来,本地重新算 sha256,必须与发前一模一样;不信 npm 自报的校验值。
  • provenance(npm 的「来源证明」徽章)对私有仓库不生成,PRD 已明确不承诺;工作流显式关闭,避免歧义。

关键取舍与否决的方案

问题选了否决了什么、为什么
「切客户指针」的按钮放哪选GitHub 工作流 + release 环境 + 只允许 main否Bridge 进程直接持钥匙跑脚本 —— 同一台机器上的 runner 能读到 Bridge 的环境变量,等于把钥匙放在公共抽屉;当年为此造的 broker 已被删除。
否GitHub required reviewers 人门 —— 套餐不支持(实测)。
否人手工跑脚本 —— 违反「发布全自动、不依赖 Annie 本机」直令,且无审计。
customer-release 钥匙怎么保管选持久放在 release 环境,一次生成否每次运行现造一把并写进 Worker —— 每次 commit 都得动用 Cloudflare 总钥匙,还每次改 Worker 配置;原本的理由(省一把 admin token)并不成立。
薄壳发布凭据选trusted publishing(OIDC)否继续用长期 npm token —— 90 天到期、绕过 2FA、PRD 明令改 OIDC。
清理定时化缓手动 runbook否定时工作流持运维钥匙 —— 那把钥匙还能签发/吊销客户 key,爆炸半径太大;拆钥匙是另一单。
beta 线的 bug 另开事故单?Lead 裁不另开,作 B1 第 0 块52 天静默失败记到 FLY-2134(「无人看的监视器」目录单);本节点无 Linear 写权限,评论文本已交 Lead 代贴。

诚实边界:这单做什么、不做什么

做

  • 修活 beta 线(客户端 + 服务端 + 清理脚本三处都认弱 ETag,并加能复现生产失败的测试)。
  • 新建「切客户指针」工作流(commit / abandon / withdraw 三个动作),零构建、指纹绑定、只在 main + release 环境跑;withdraw 必须是撤当前版本。
  • 薄壳发布改 OIDC、发确切文件、打对 dist-tag、发布后回读;重跑安全。
  • 清理策略定稿;合同文档加署名日期的修订附录,把过时的句子逐条替换。

不做

  • 不做 B3(判断这版稳不稳)、B4(否决窗口与自动放行)、B5(客户端自动更新、止血到「暂停更新」态)。
  • 不改 manifest 格式,不改客户端安装器的任何字节,不加 Worker 新能力。
  • 不在本单里真的发任何东西:真发薄壳、真把版本交给客户,只在 QA 段、经你 go 之后发生。
  • 不代替你操作任何凭据。
最重要的一条诚实:B1 交付的是一个「可以被机器按下去」的按钮,不是一个「只有你能按」的门。在这台机器上,能按它的主体 = 任何有仓库写权限的 runner。它能造成的最坏结果是「提前发一个本来就会发的版本」,不是「发任意东西」。真正的机器门(否决窗口 + 送达回执 + 你的 Discord 身份核验)是 B4 的活。
