① 一句话：这张票在做什么

这张票不是在做功能，而是让一台真 Runner 把 Flywheel 的整条流水线 （设计 → 实现 → QA → QA 打回后再修）在隔离的 QA 房间里完整跑一遍，交付物只是一个两行的 markdown 文件。

名词解释：Runner 是 Flywheel 派出去干活的 AI 执行单元；529 QA 房间是 FLY-529 搭的隔离测试环境， 有自己的 Discord 频道和数据库，跑什么都碰不到生产；DAG 流水线是把一张票按"设计、实现、QA"等节点串成有向图、 由编排器逐节点派发的工作流。

② 核心流程：演练怎么跑

下面是演练的时序。重点是第 6 到第 11 步：QA 第一轮故意判失败，看实现节点能否拿着 QA 给的 claim id 回来修，再被 QA 精确放行。

名词解释：hand-in 指实现节点提交并推送代码、交给下一节点验收；claim id 是 QA 打回时给这次判定的唯一编号， 像一张"退货单号"；CI 是代码推上去后自动跑的检查流水线，README 要求它必须跑在"这次提交的精确版本"上。

Mermaid 源文件：diagram-1-flow.mmd（与本页同目录，本地 mmdc 渲染，页面零外部请求）。

③ 数据与结构：一个文件、三条准则、一个 id

交付物只有一个文件，但它和三条 QA 准则、一个 claim id、三条禁区之间的关系要写清楚，QA 才能机械判定。

──────────────────────────────
QA-SBX FLY-2167 drill
FIXED-FOR-CLAIM <id>   ← 第 2 次 hand-in，<id> 来自 QA 打回

④ 关键取舍与否决的方案

取舍点选了什么否决了什么、为什么
设计节点要不要顺手把两行文件建好不建，留给实现节点否决"顺手建好"：那样演练就测不到实现节点真实落盘，演练目的落空
文档三件套（探索/调研/计划）只写探索 + 计划否决"凑齐 research.md"：README 明说不要调研文档，任务指令要求逐字遵守 README
claim id 怎么比对逐字精确匹配否决"正则宽松匹配"：宽松会掩盖 id 传递链的 bug，而那正是演练要抓的
提交信息风格普通信息，不带任何 skip 标记否决"照抄仓库历史里的 [skip ci]"：README 明说历史不是风格指南，hand-in 必须跑 CI
修复轮的自检替换第一轮的"第 2 行 = AWAITING-QA"检查Codex 第 1 轮抓到：若"追加"而非"替换"，正确修复也过不了自检，QA 修复回路会被卡死
CI 证据记录每次 hand-in 的精确 head，核对 CI run 的 SHACodex 第 1 轮抓到：只禁 skip 标记不等于 CI 真跑了；修复轮的新提交不能拿旧提交的 CI 顶替

⑤ 诚实边界：做了什么、没做什么

这份设计做了什么

  • 把 README 的每条规则翻成实现节点和 QA 节点可机械执行的步骤，含负向守卫（第一轮即使第 2 行碰巧写对也判 fail；id 大小写、多余空格都算不匹配）。
  • 给出 claim id 解析失败时的失败路径：不猜，按协议报 blocked。
  • 回滚边界：revert 一个提交或删一个文件，无迁移、无状态。

这份设计没做、也不该做的

  • 没有创建那个两行文件，没有碰 Linear issue，没有部署任何 529 房间。
  • 没有代码、测试、CI 配置改动。整张票没有可运行的东西。
  • 没有等创始人审完本页再推进。按协议，本页发出后实现节点即可开始；创始人意见到了由当时持有 TURN 的节点记 design-correction.md 增量修正。
  • Codex 评审是静态审阅：它核了 README、分支名、目录现状，但没有跑 CI 或真实演练。真实 hand-in 的 CI 证据要由实现节点取得。

名词解释：TURN 是 Flywheel 给共享工作区上的"接力棒"，同一时刻只有一个节点能改文件，防止两个节点互相覆盖。
