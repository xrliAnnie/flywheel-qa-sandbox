4 · 本轮特殊情况：同名分支分叉与处置

审计发现上一轮运行的痕迹还在：main 上已经有这个 drill 文件（第 2 行是上一轮的 FIXED-FOR-CLAIM 1）， 而且远端同名分支 origin/project-slot-5-FLY-3150 仍带着上一轮的提交，和本次新建的工作区 （worktree：同一个仓库的独立工作目录）分叉了。直接推送会被拒绝（non-fast-forward ：远端有本地没有的提交，git 拒绝覆盖）。

  • 处置：把远端分支和 origin/main 都 merge 进本地（纯技术同步），之后推送变成 fast-forward。没有 force-push。
  • 对实现节点的影响：第一次交付不是"新建文件"，而是把第 2 行从 FIXED-FOR-CLAIM 1 覆写成 AWAITING-QA。
  • 负向守卫：旧 id 1 对本轮无效。QA 第一轮即便看到 FIXED-FOR-CLAIM 也必须 fail；第二次修复必须用本轮 QA 给的新 id，禁止偷懒复用旧 id。
  • Codex R1 补的一刀：若再遇推送被拒，恢复步骤必须先 git fetch origin 再 merge，否则 merge 的还是旧引用，推送仍会被拒、无人值守节点就卡死。

5 · 关键取舍与被否决的替代方案

替代方案结论原因
force-push 重置远端分支否决FORCE-PUSH GUARD 要求 Lead 显式确认；房间无人类 Lead，而 merge 同步已能解决。
设计节点顺手把第 2 行改成 AWAITING-QA否决README 把它归为实现节点产物；设计越界会让演练测不到实现节点真实落盘。
写 research.md 凑齐三件套否决README 明示"No research document"，任务要求逐字遵守。
claim id 用正则宽松匹配 / 复用旧 id否决QA 只认精确匹配；宽松匹配会掩盖 id 传递链的 bug，而那正是演练要抓的。
merge 同步 + 覆写第 2 行（本方案）采纳零破坏、可机械执行、与 README 每条规则逐字对齐。

6 · 诚实边界：这个设计做了什么、没做什么

做了

  • 读 sandbox main 上的 README 并逐条落成实现节点、QA 节点可机械执行的步骤（plan.md §2–§4）。
  • 审计并以非破坏方式解决了同名远端分支分叉；给出推送被拒时的 5 步恢复流程。
  • Codex 设计评审 2 轮（gpt-6-astra / xhigh）：R1 一项 MEDIUM 已采纳修订，R2 APPROVED。

没做（也不该做）

  • 没有改 drill 文件本身，没有建 PR，没有合并，没有部署任何 529 房间。
  • 没有碰 Linear issue（不改状态、不评论、不打标签；本会话 Linear 连接本就不可用）。
  • 没有写 research.md、没有写代码或测试——README 明确这是纯文档演练。
  • 没有向 Lead 提问：README 规定这个房间没有人类 Lead，一切答案都在 README。

剩余风险

  • CI 必须跑在实现节点每次交付的精确 head 上；仓库历史里大量 [skip ci] 提交是反例，不得模仿。
  • 若驱动器在本轮再次移动 main 或远端分支，实现节点需按 plan §5 先 fetch 再 merge，不得 force-push。
