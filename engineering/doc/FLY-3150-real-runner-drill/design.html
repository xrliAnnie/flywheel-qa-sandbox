一句话总结

在 529 QA 房间的 slot-2 分支上,让真 Runner 走一遍「实现 → QA 故意判失败 → 带着 claim 编号返工 → QA 逐字核对后通过」的回路;唯一的演练改动是新建一个两行的 markdown 文件。

名词:529 房间 = 与生产完全隔离的 QA 测试环境,这里跑的东西不会影响真实用户。Runner = 在独立终端里自动执行任务的 AI 编码会话。claim = QA 判失败时生成的编号,返工时必须原样抄回文件里,证明返工确实读到了这次失败。

核心流程图

驱动器(按 README 规则依次派发实现节点和 QA 节点的测试程序)先派实现节点,再派 QA 节点。整条回路要证明:claim 编号能从 QA 结论一个字不差地传到返工后文件的第 2 行。

HANDIN1 = 第 1 次交付时的提交编号(SHA:git 给每次提交算出的唯一指纹)。PREV = 返工时用来对比的那次交付,只认本轮的 HANDIN1。PR = GitHub 上的合并请求页面,别人在那里审这批改动;本轮这条分支还没有 PR,由实现节点新开。

数据 / 结构模型

分支上只有两类东西:演练文件(QA 只验它)和流程文档文件夹(Runner 协议强制要求的记账材料,不进验收)。演练文件的第 2 行是一个只有三个状态的小状态机:

qa-sbx/fly2167/project-slot-2-FLY-3150.md

  第2行: (派发时文件不存在)
      →  AWAITING-QA(本轮交付 #1,新建)
      →  FIXED-FOR-CLAIM <本轮 id>(本轮交付 #2)

这一轮的情况

  • 这是 slot-2 第一次跑这个演练:分支头和 main 完全一样,远端没有这条分支,也没有 PR,演练文件还不存在。
  • 所以没有「上一轮残留编号导致假通过」的风险(slot-5 / slot-6 曾遇到过);交付 #1 就是新建文件。
  • 仍然按 HEAD(分支最新提交)里的文件内容做逐字节比较再决定是否写入,保证实现节点被重试时结果不变、不产生空提交。
  • 新风险:流程文档文件夹是所有 slot 共用的。如果别的 slot 的 PR 先合进 main,这里会冲突;处理办法是技术同步合并,冲突处保留本轮 slot-2 版本,并把对方的运行记录补进 exploration,不静默丢弃。
  • 旧指针一律不认:main 历史里前几轮的交付提交、进度账本里写过的 HANDIN1、claim=1、PR #509(已合入的 slot-6 PR),都不是本轮依据。

关键取舍与否决方案

  • 不写 research.md:README 写明「一份短 plan 足够」,README 是本任务唯一权威;exploration.md 只是审计记录。
  • 流程文档随同一分支推送(节点协议强制);用 PR 级范围检查保证:排除这个文件夹后,改动恰好只有演练文件一项。否决:另开分支放文档(违反共享工作区轮流写入的约定)。
  • 是否跳过写入,看 HEAD 里的 blob(git 里已提交的文件内容)。否决:只看工作区(还没提交的文件会被误当成已提交)。
  • 进度账本(ledger:一个会自动提交的进度记录文件,用来让中断后的会话从断点续跑)只写写入时已知的信息,不写最终交付提交号。否决:让账本记录自己的提交号——每写一次就多一个提交,永远追不上。
  • PR 先查后开:已有本分支的 OPEN PR 就复用,没有才新建。否决:直接 gh pr create(重试时会因为 PR 已存在而失败)。
