529 房间:一套与生产完全隔离的 Flywheel 测试环境(自己的 Bridge、自己的频道、自己的数据库),专门用来在上线前演练"要重启或上线才看得到"的流程。本演练不碰任何代码、不碰 Linear issue、不部署房间。

2. 核心流程

下图是四个角色之间的消息顺序(序列图:时间从上往下,箭头代表谁对谁说了什么)。关键在第 5 步:QA 第 1 轮按规则必定判失败,这不是缺陷,而是故意埋下的触发器,用来逼出第 6–10 步的返工回路。本轮新增的是第 2 步:先把上一轮残留的第 2 行覆盖回 AWAITING-QA,并在第 3 步把本轮交付号写进交付摘要,返工只认这个号。

名词:claim id = QA 判定失败时生成的一个编号,返工提示词、文件第 2 行、重验提示词三处都必须原样带着它。HANDIN1 / HANDIN2 = 两次交付时固定下来的 git 提交号(SHA,一串唯一标识提交的字符),CI(自动检查流水线)必须在这个号上跑。

3. 数据与结构模型

整个演练只有一个数据对象:一个两行的文本文件 qa-sbx/fly2167/project-slot-1-FLY-3150.md。第 1 行是永远不变的"身份行",第 2 行是一个小状态机(状态图:圆角框是状态,箭头是触发状态变化的事件)。本轮的起点不是"文件不存在",而是上一轮留下的 FIXED-FOR-CLAIM 1。

5. 诚实边界:做了什么、不做什么

这份设计做了什么

  • 把 README 的规则翻译成实现节点、QA 节点能逐步执行的合同:两行内容、固定验收编号、claim id 提取与回填、字节级自检、固定 SHA 的改动面核验、禁用跳过 CI 的标记。
  • 明确两套要求(README 演练内容 vs 派发提示词要求的文档产物)的路径边界,避免后续节点为了"diff 干净"误删设计材料。
  • 处理"第二次运行"的两个陷阱:上一轮残留的 claim 行、上一轮残留的基准提交号。

这份设计不做什么

  • 不写任何代码,不改 README,不改 Linear issue(状态/评论/标签),不部署或拆除 529 房间。
  • 不改目标文件 —— 重置和返工都是实现节点的工作;设计节点结束时它仍是上一轮的 FIXED-FOR-CLAIM 1。
  • 技术性合并只为消除与 main 的冲突,不改变任何演练语义;main 带进来的 slot-5 同名演练文件(project-slot-5-FLY-3150.md、FLY-3150-design.html 等)原样保留、不动。
  • 不验证生产环境里 FLY-2167 的实现本身;演练只证明 529 房间内真 Runner 的 fail → fix → re-verify 回路能贯通。
  • Codex 的 APPROVED 只代表计划文本自洽,不代表 CI 或演练已跑通。

若后续节点收到的提示词格式与 README 不符,以 README 为准;取不到 claim id 时停下走失败通道,而不是猜。
