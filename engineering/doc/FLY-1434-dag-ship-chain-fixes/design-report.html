十项修复清单（现象 → 修法）

①主项
所有 DAG 单都显示「PR 未绑定」
开发完成开了 PR，但流程没记下 PR 号——昨晚 6 个单全中招，1423 靠手工改数据库救急。
修：完成时把 PR 号和代码版本一起登记进台账（按轮次记，返工自动换新账），后面每一环都从台账读。
⑤self-ship 最后一环
你在 thread 回 ship，引擎纹丝不动
批准识别只认旧流程的登记处；DAG 单的批准门根本没开出来，你的话无处落笔（1423 实测 10 分钟零反应）。
修：新工程单统一切到带「自动合并尾巴」的流程模板——批准门、识别、合并全是已建好的链路，一个协议都不用新造。存量卡死的单走 ③ 的返工通道救。
②
「启动」按钮假成功
对已完成的单再点启动，返回成功但什么都没发生 → Lead 误报你「已开工」。
修：不能启动就诚实报错并写明原因，指路到正确入口。
③
完成/卡死的单没有返工入口
只能开接替新单绕路（1435/1436 就是这么来的）。
修：新增正规返工入口（走你的授权面 + 全程留痕），重开、补位、唤醒执行者全自动接手。另给 Lead 一个只读诊断面：一眼看清卡死单的全部状态，不用再手工拼数据库（Tadashi 点名要求）。
④你的直令
重启分好几档，有的档不发通告
修：删掉所有分档，只留一个全量重启脚本；每次重启（含改配置）自动向 #flywheel-notify 发起止通告 + 原因。
⑥
两个 PR 的单，合了一个就被当「完成」
1426 半部署上线净负（收据风暴），第二个 PR 无人接。
修：先登记「这单几个 PR」再逐个封口对账，最后一个合完才收口；中途每合一个都提醒「部分交付，先关功能开关」。
⑦高频误报
一晚 17 条「唤醒失败」全是假警报
给干活中的执行者发正常消息也被当「唤醒失败」，30 分钟后升级页你——Lead 越尽责误报越多。
修：给每条唤醒标注用途：正常聊天不进失败判定；只有「叫醒睡着的」和「送批准结论」才走催办阶梯。
⑧
评审结论写好了，执行者干等 15 分钟
结论只投一次、丢了没人管，最后靠 Lead 手工转发。
修：结论写入和催办登记绑成一笔账，90 秒起自动重投直到真正取走为止。
⑨
代码在子仓库时，评审绑错对象
修：评审请求可声明子仓库为被审对象（服务端校验真伪），评审记录带仓库身份。边界：只管「审得对」；子仓库 PR 的自动合并不在本单（见下）。
⑩
评审通过了，换个经手人查账查不到 → 合并卡死
通过记录绑在写代码的人身上，合并时按持钥匙的人查——必然查空（1435 实测）。
修：查账改按「单 + 代码版本 + 仓库身份」，不看经手人是谁。

数据/结构模型（新增 4 张台账）

台账记什么解决谁
PR 绑定台账每个单每轮开发产出的 PR 号 + 代码版本 + 仓库身份①⑤⑩ 的取数源头
PR 清单封口账这单计划交付几个 PR、封口版本、逐个的合并对账⑥ 的「全齐才收口」
ship 对象绑定账你批准的那一刻，批的到底是哪个仓库哪个版本⑤⑩ 的批准↔合并对齐
收口终审账每单每版本只允许收口一次，崩溃自动续⑥ 防重复收口/漏收口

关键取舍（和被否掉的方案）

  • ⑤ 选「换模板」不选「给运行中的单动手术」——快照手术要造一整套迁移机器，风险大收益小（评审第 2 轮否掉）。代价：只有新单受益，存量卡死单改走 ③ 返工通道；Tadashi 批复条件：两条都要真机演给你看（新单全链 + 1437/1423 存量标本救援）。
  • ③ 返工只开你的授权面，不开旁路——返工/重启单属于本窗口你保留的动作类；QA 侧已有可信通道，不重复开口。
  • 子仓库收口为「只管审对，不管自动合」——issue 原文只要求评审对象声明；自动合并子仓库 PR 是评审过程长出来的范围，砍掉后少一半复杂度。子仓库 PR 由 Lead 按手册人工收尾（手册已写成一键脚本，防呆：没全合完就物理按不下终止键）。
  • 4 个 PR、固定部署顺序——可靠性底座（⑦⑧⑨⑩）先上，ship 链闭环（①⑤⑥）踩着它上，入口修复（②③）与重启改造（④）独立。

诚实边界（这单不做什么）

  • 产品线（无代码交付）流程模板的批准门 → 后续单独立项。
  • 子仓库 PR 的自动合并、以及人工合并后的自动收口 → 后续单；本单内该场景 = 明确拒绝 + Lead 按手册收尾，不假装是闭环。
  • 存量卡死单不能原地升级到新模板（技术上做不到），只能返工或关单重开。
  • QA 递归豁免归 FLY-1261；NPM 分发版的重启面不动。
  • 本单自己的 4 个 PR 也要「全合完才算完」——但 ⑥ 上线前只能靠 Lead 流程纪律保证，机制管不了自己的出生。

验收（逐项真机）

  • ⑤（你亲测）：新开一个真工程单，你在 thread 回 ship → 引擎自动合并全链走通；再用 1437/1423 标本演一次存量救援。
  • ⑦：复现昨晚的正常对话流量，零误报；真睡着的执行者叫不醒仍会升级（阳性对照）。
  • ④：--bridge-only 不存在；改配置重启也自动出通告。
  • 其余各项按 plan §14 逐条复现→修→复验；三段式老流程、单 PR 单行为全程不变（回归护栏）。
