目标是零白起浏览器,不是禁 Playwright

你的原话:「思考的不是说开了之后怎么关,而是我们为什么需要开它?如果不需要开的话,一开始就不应该打开呀。」

二次审计确认:Chrome 本来就等第一次 browser tool 才启动,所以 19 个空挂 server 不是可见窗口根因。 真正要修的是用过一次后不回收(P0);普通会话默认不带 MCP(P-1)同时消掉空挂 server,但不再冒充主因。

1 · 答案先说:不调用就 0 Chrome;调用过就必须能关

现在

全机 Playwright 插件是开启的。每个 Runner、Lead、你自己开的 Claude 会话都先起一个 playwright-mcp server,不管用不用。

修正后

普通会话默认不启动。只有 QA、带 playwright / full-mcp 标签的任务,或人明确要求的会话才打开。

这不是把 browser 能力删掉。Chrome 的 first-tool lazy 保留;P0 给 teardown 足够时间关掉已经启动的 Chrome。默认不带 MCP 另行减少 19 个空挂 server 与误触入口。

2 · 为什么它一直无差别启动:正确设计写了,但现机没执行

证据读到的事实
当前机器配置playwright@claude-plugins-official = true
切换脚本留下的 backup0 份 —— 说明从没跑过
仓库里已有的默认策略machine default-off
仓库里已有的打开入口QA / playwright label / full-mcp label
新机 provisioning已经接了 default-off 脚本
现场 server census23 个:15 Lead + 6 Runner + reviewer + 你的 Terminal
从未启动 Chrome21 / 23 —— server 常驻不等于 browser 正在用
严格 14 天 Playwright全部 98 次;Lead 只有 32 次 / 4 个短 QA sessions / 2 个身份
严格 14 天 Claude-in-Chrome2335 次;它是独立工具,不再混进 Playwright 白名单

第一次「4 个 Lead 真用户」结论作废:它按文件 mtime 选样本却没按每条事件 timestamp 过滤,也混入了另一套 browser。 重审计只认实际 Playwright tool name;Lead 只有 Eng 与 Flywheel Product 的四次短 HTML/report QA。

浏览器本身其实已经是懒启动

我重新读了本机实际运行的 @playwright/mcp@0.0.79:server 会随 enabled plugin 先启动; 但 Chrome 要等第一次 browser tool 调用才创建。也就是说,不用再造一层 supervisor 或 lazy launcher; 应该在更前面把「不需要的 server」挡掉,需要时沿用上游已有的 first-tool lazy。

当前 0.0.79 没有 idle-close:可信关闭边界只有手动 close 与会话结束。resident Lead 一次低频调用后也可能长期留住 Chrome, 所以不建立常驻 Lead 白名单。

3 · 修正后的整条链:P-1 先决定要不要开

否 → 到此结束

Playwright MCP 与 Claude-in-Chrome 是两套独立能力。这一单只关掉普通会话里的 playwright-mcp,不顺手改另一套 browser 的全舰合同。

4 · 当前 Lead allowlist 为空,日常 browser 继续走 CiC

严格窗口里只有 Eng 与 Flywheel Product 在四个短 QA sessions 调过 Playwright;CoS 与 Tidal Content 是 0。 四次短任务不值得让 resident Lead 永久持有插件与没有 idle-close 的 Chrome。当前 production 与 example 的 playwrightMcp: true 名单都是空集。

Lead 平常的 browser 路径是 Claude-in-Chrome。Playwright visual QA 改走 QA / labeled Runner 或一次性会话;未来有明确持续需求时,才用精确身份字段 opt-in。

你的 Terminal 会发生什么

默认也会关掉 Playwright MCP。切换前我们会先在现有 thread 告诉你;临时需要时明确运行 claude --settings '{"enabledPlugins":{"playwright@claude-plugins-official":true}}'。 它只影响这一次 Claude 会话,不会恢复全机常开。

5 · 为什么 P0–P3 还保留:它们只管真需要开的残余场景

P0 · 需要开时,给它完整的关机时间

Flywheel 现在 3 秒就强杀,而上游给 graceful close 最多 15 秒。改成轮询:一消失就继续,真顽固才强杀。

P1 · 需要开时,也不画窗口

同一个安全 writer 写 default-off 与 HEADLESS=true;回滚有 receipt,不覆盖别人后来加的 hooks / plugins。

P2 · 只量残量,不杀、不告警

P-1 + P0 上线后看两周。只有读数持续满足数字门,才单开 follow-up 讨论自动回收。

P3 · cutover 前的旧 profile 一次性隔离

人工复核清单 → 只改名搬进 quarantine → 观察至少 7 天 → 人再下命令真删。归因不到的一律不动。

原来砍掉的 supervisor、受管插件 fork、Chrome 启动 shim、六相 activation 与自动 kill 一个都不恢复。P-1 让它们更没必要,不是把旧大方案换个名字装回来。

6 · 这次怎么证明不是又写了一条「以后会执行」的规则

验收必须看到的事实
普通新会话playwright-mcp server = 0,不是「有 server 但 Chrome=0」
Lead allowlistproduction 与 example 均为空;fixture 只证明未来 exact-identity opt-in 不会越界
明确 opt-in 会话server 存在;第一次 tool 前 Chrome=0;第一次 tool 后 Chrome 才出现
桌面目标 Chrome 的 on-screen window = 0,同时用你自己的 Chrome 做阳性对照
功能GPU/WebGL 截图走预注册阈值与独立 validation shots,不看完结果再放宽
存量收敛Runner / Lead 受控重启,你的 Terminal 由你重开;不能拿「配置文件改了」冒充进程已经换代
泄漏根因close 前后按 pid + lstart + profile 精确身份证明 MCP 与 Chrome 都消失
