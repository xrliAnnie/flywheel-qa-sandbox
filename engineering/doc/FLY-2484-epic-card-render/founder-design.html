一句话结论

今天那份自己会刷新的机器页,把 36 张子单当 36 张同款卡平铺、不分 Epic(Linear 里带子单的大任务);本单只改「怎么画」这一层,把它重排成一 Epic 一张卡:卡头的状态徽标(状态标签)一字不改照抄 Linear,旁边写「N 在跑 · N 等依赖 · N 未开始 · 共 N」;卡默认收起,点开是它的子单,在跑的在上、还没开始的在下,被挡住的写「等 FLY-XXXX」而不是「未开始」;全做完的 Epic 不出现。数据一格不动、顺序是数据的纯函数(同样的数据永远同样的顺序)。

核心流程:数据怎么变成这一页

图 1 · 蓝色是本单新增的步骤;灰色是「不出现」;绿色是既有的发布闸门
  1. 输入只有 E1 已合入的文档:每张子单一格「我挂在哪个 Epic」、每个 Epic 一格「六种状态各几张」。
  2. 一个纯函数(只看输入、不看时钟)把文档排成「Epic → 子单」的树,并决定顺序、徽标、整块在等、等谁在哪。
  3. 没有未做完子单的 Epic 直接不出现;其余每个一张收起的卡。
  4. 卡里只列未终态子单;已完成 / 已取消只剩一行计数。
  5. 每行折叠着它的 15 格出处与时间;页面自己推出的结论各带一条「页面展示规则号 + 读了哪些格 + 输入最新观测时间」。
  6. 发布前仍过既有闸门:HTML 超过 512KB 不发布,固定页停在上一版。

数据与结构模型:页面中间多了一层「视图」

图 2 · 左上是 E1 的文档(不改);中间是本单新增的视图模型(只在内存里,不落库);右下是每条页面结论的出处
EpicPage(不改)E1 的文档合同原样;本单不加字段、不升版本、不动回执与摘要。 FounderView(新,内存)「页面怎么排」的中间结果:已排序的 Epic、每个 Epic 已排序的未终态子单、全做完的个数、没挂 Epic 的子单。它是展示规则,不是事实,所以不进文档。 ViewProvenance(新)页面自己推出来的每条结论(顺序、隐藏数、整块在等、等谁在哪、进度行)各带:规则号 view.*.v1、读了文档里哪些格、输入里最新的观测时间。这样 PRD §12「不许有只存在于页面里的事实」在页面层也守住:它不是事实,但它能说清自己是怎么来的。 classifyItem(从 E1 抽出)「这张子单算在跑 / 等依赖 / 可起跑 / 未开始 / 已完成 / 已取消」这一段逻辑今天埋在计数函数里;本单把它抽成一个函数,计数与徽标都调它,计数输出逐字节不变(有测试锁)。

徽标与顺序怎么定(全部可测)

什么怎么定
Epic 徽标Linear 状态名原话(今天都是「In Progress」);颜色只按 Linear 的状态类型分
Epic 旁的计数「N 在跑 · N 等依赖 · N 可起跑 · N 未开始 · 共 N」;为 0 的段省略,「在跑」与「共」永远显示
Epic 顺序先按 Linear 状态类型分组(在做 → 还没开始 → 其余);组内按单号数值序(FLY-999 在 FLY-1000 前)。工程 Lead 已裁定:不用计数排序,不造第二个状态。今天范围内全是 In Progress,所以只有一组
子单顺序在跑 → 等依赖 → 可起跑 → 未开始;组内按单号数值序;已完成 / 已取消不列
「等 FLY-XXXX」它的前置里还有没做完的(已取消也算没做完,与「可以开始」的既有规则一致);多于 3 个写「等 FLY-A / FLY-B / FLY-C 等 N 张」
「整块在等 XXX」这个 Epic 所有没做完的子单都在等 ⇒ 卡头一行,收起也看得见;XXX 是它们在等的单的并集
跨 Epic挡它的单在别的 Epic ⇒「(在 FLY-ROOT)」;在范围外(不在任何在做的 Epic 下)⇒「(范围外)」。比 issue 原文多标了前一种,因为 E1 之后「范围内」指整份文档,不指本 Epic
同样数据 = 同样页面顺序键只看单号与状态,不看时钟、不看数据到达顺序;测试会把同一份数据打乱两次输入,断言顺序逐字相同

关键取舍与被否掉的方案

问题选了否掉了,为什么
Epic 按什么分组Linear 状态类型「按 0 在跑的沉底」—— 那就是用计数造第二个状态,你已裁定状态只有一个来源
徽标的判据从哪来从 E1 的计数函数里抽出同一个分类函数「页面自己再判一次」—— 两套判据,迟早一边说 1 等依赖一边列 2 张
已完成的子单怎么放不出行,卡尾一行数「折叠着列出来」—— 字节不省(今天一半字节是它们),清爽的目的落空;「完全不提」—— 你抽查时分不清是没做完还是没取到
给 Lead 看的几块诊断整体收进页尾折叠面板,内容不动「删掉」—— 固定页是唯一 hosted 形态,Lead 也会看;「留在顶部」—— 违背首屏只看 Epic
页面推出的结论要不要出处要:页面展示规则号 + 读了哪些格 + 时间「进文档合同」—— 那是把展示规则当事实存,E1 已裁定不加第二个状态;「不给」—— 违背 §12
体积怎么保证终态子单不出行 + 出处格瘦身(同一张单的链接只写一次),容量在实现期真渲染实测「先承诺一个张数」—— 评审两轮都证明估算不可信;「超限就删出处」—— 违背 §12,评审否决
和另两张并行单怎么合等它们先合入,本单在合入后的代码上动手,留三个固定插槽「三张同时改同一个函数」—— 后合的必然手工解冲突;工程 Lead 已裁定顺序

诚实边界:本单做什么、不做什么、等什么

图 3 · 蓝色是本单改的;橙色是等两张并行单(#1147「现在要你看」、#1148 Lead 判断)合入后接进来的插槽;灰色不动
  • 等 #1147 与 #1148 先合入。它们和本单改同一个渲染函数;工程 Lead 已裁定本单的实现在它们合入后才动手。设计里为「现在要你看」(页面最前)和「Lead 判断」(Epic 卡顶、子单机器行紧后)各留了固定位置,并写清输入字段 / 位置 / 没内容时什么都不画(不伪造判断)。
  • 不做留言层。PRD 里「每个 Epic 留言 + 一键复制」不在这张单,FLY-2481 名下也没有它;结构给它留位。
  • 不做 Discord 跳转、不做 Lead 判断格(分别是 #1147、#1148 的事)。
  • Markdown 形态不动。Lead 每小时巡检读的那份仍是今天的平铺样子;要把它也排成 Epic 树是另一张单。
  • 已完成 / 已取消子单的 15 格出处不再出现在 HTML 里(只在 JSON / Markdown)。页面是文档的子集,不是全集。
  • 容量不承诺具体张数。实现期在合入两张并行单后的最终页上真渲染实测:门槛是至少容下 60 张未做完的子单(今天 18 张);并且这个数是「每张单最多一条 Lead 判断」条件下的数 —— #1148 没有给判断条数设上限,超出时页面走既有的「不发布、停上一版」,不截断、不发坏页。
  • Epic 分组今天恒为一组。若将来你要「没人动的 Epic 沉底」,那是 §6.2 之外的新裁定。

体积与风险

  • 今天的真页(本地按 E1 的冻结 Linear 数据重放,与 E1 证据逐字节相同):469,843 字节,36 张卡,每张约 10.7KB,其中 76% 是每格出处的样板字,18 张已完成 / 已取消占了一半。上限 512KB,只剩 45 张卡的余量。
  • 设计后:终态子单不出行(今天 −18 张)、出处格瘦身(同一张单的 Linear 链接只写一次、验收原文只出预览);估今天真数据约 165KB。这是估算,实现期真渲染实测后写实数。
  • 风险 1 · 三张单改同一个函数。已用「先等合入 + 固定插槽」化解;实现开工前核两个合入记录,没合就等。
  • 风险 2 · 计数函数重构回归。E1 的 37 条合同测试与逐根 golden 一字不改全绿,错误优先级与文案逐条断言。
  • 风险 3 · 页面结论没出处。每条结论带页面展示规则号与输入格路径,测试逐条核每条路径确实指向文档里的一格。
  • 零迁移、零表改动;回滚 = revert 一个 PR,下一次刷新回旧样子。

验收怎么看(QA 当天,报告零表格)

  1. 页面上的 Epic 集合 == Linear 里 In Progress 且有没做完子单的父单;全做完的个数 == 页尾那个数,且它们没有卡。
  2. 任取一个 Epic:列出的子单 + 尾行的已完成 / 已取消数 == 它在 Linear 的全部子单;每张徽标与 Linear 状态、前置状态对得上。
  3. 同一份数据渲染两次逐字节相同;Epic 顺序 == 单号数值序。
  4. 被挡的子单徽标「等 FLY-XXXX」、全被挡的 Epic「整块在等」、跨 Epic 与范围外后缀 —— 生产没有这种数据就用测试数据截图为证。
  5. 首屏零展开;「现在要你看」(若已上线)在最前。
  6. HTML 字节数 ≤ 512KB,并写出实测容量与它的条件。
  7. 固定页版本号前进;手机宽度截图两张(收起 / 展开一张)由 QA 出。
  8. 零人名:剥掉 Linear 数据串后 grep,页面自己的文案零命中。
  9. E1 的计数输出与合入前逐字段相同;两张并行单的测试在本单头上全绿。
