FLY-2901 · 替身接不了前任的工作目录时，自动保全再接上，不再 held 等人

分支 flywheel-FLY-2901 · 文档 engineering/doc/FLY-2901-worktree-takeover-rebuild/{exploration, research, plan}.md · 评审记录见最后一节

一句话结论

替身（接班的新执行体）发现共享工作目录不干净或提交点对不上时，不再直接失败等人；而是先确认前任不会再写，再把前任留下的东西一字不丢地存到远端的救援分支，然后把目录清干净接着干——任何一步证明不了「零丢失」，就停手告警，和今天一样。

issue 要求本设计怎么落
按失败原因分类，每类定自动处置做 七类（未提交改动 / 嵌套仓 / 提交点落后 / 前任已推送的分叉 / 未推送的分叉 / 目录没了 / 路径没登记），一张表定处置和停手条件
保全现场：未推提交推备份分支、未提交改动存档记 SHA做 不用 git stash（它在所有工作目录间共享，别的会话可能把它弹走），改用带名字的引用 + 推到远端 flywheel-rescue/… 分支，推完再从远端读回核对
会丢工作的情况停手并告警做 写成代码里的「零丢失不变式」断言；停手时目录一个字节不动，告警里列出具体脏路径
证据写进进度账本给替身读换个方式做 Bridge 直接改账本会移动提交点（和第 3 条冲突），所以证据先放在 git 看不见的文件 + 替身提示词里，替身第一次写账本时带上 rescue 指针
重建后能继续 complete / 复审，不撞 head做 首选「原地清理」：路径、身份标记都不变，替身完成时读到的提交点就是清理后的那个

发生了什么（为什么要做）

  • FLY-2893 普查：「工作目录接管失败」Codex 40 次 + Claude 5 次，浪费约 150 单×节点小时，其中 133 小时是在等人手。
  • 45 次里 34 次只是「脏」：提交点是对的，只是多了没提交的改动——大多是被额度墙同时杀死的实现体写到一半的代码（FLY-2510）。
  • 9 次同时提交点对不上，典型是 FLY-2463：返工体合法地把分支 rebase 到新 main 并推了上去，然后死了；替身还拿着旧的起点去比，于是拒绝。
  • 2 次是目录本身坏了 / 没了。另有一支 worktree_not_found（前任的路径没登记）在派发前就失败，而且没有任何告警，每分钟静默重试。
  • 今天的处置全靠 Lead 手工：git stash 记下死体编号 → 恢复被暂停的 run → 替身起来后再把改动取回。
今天机器上还留着的工作目录里，脏的内容全是真实工作（未提交的代码、文档、报告）。所以「直接清掉」绝对不行，必须先保全。

核心流程

图 1 · 蓝：今天就能走通的路径，不变；绿：本单新增的自动处置；红：停手（和今天一样失败 + 告警，但信息更全）
  1. 先证明前任不会再写：前任已经正常交卷停驻（它按规矩不碰目录），或已被判死且进程探针证实它的窗口和进程都不在了；被判死但进程还活着的「僵尸」、探针说不清的、以及还在跑的前任，一律停手。这张判断叫许可证。
  2. 两次采样：隔 5 秒对目录拍两次「指纹」（提交点 + 改动清单 + 每个改动文件的内容哈希），不一样说明还有人在写，停手。
  3. 保全：没提交的改动用临时索引做成提交（不碰真实目录）；不在目标里的提交推到远端救援分支（名字带前任、替身编号和时间），再从远端读回核对。
  4. 先落盘再动手：证据文件和一条持久运行事件写成功之后，才允许任何破坏性动作；写不进就停手。这样中途崩溃也不会出现「目录已清、却没人知道东西存在哪」。
  5. 清理：嵌套仓整目录挪到 Flywheel 状态目录；目录还在就原地清理（忽略文件如 node_modules 不动）；已登记但目录没了才重建。
  6. 交给替身：提示词一节列出救援清单。同一节点的替身会被明确要求先把死体写到一半的改动恢复回来再干活（对齐 Lead 今天的手工配方）。

清理后停在哪个提交点

图 2 · H = 目录原来的提交点；S = 引擎期望的起点；R = 远端分支头

原则：远端分支是已发布的真相，清理后的提交点必须包含它；本地多出来又不在目标里的东西，一律先推救援分支。FLY-2463 那种「前任 rebase 后已经推送」的情况，直接采纳前任的提交点，不再拒绝。

数据与结构

图 3 · 一次自动处置留下的所有记录，以及它们的关系（清单先写、事件带清单哈希、清理完再追加回执）
救援引用本地一份（refs/flywheel/rescue/…，带完整的前任和替身编号）+ 远端一份（flywheel-rescue/<单号>/… 分支，GitHub 上能看到）。只新建、不改写、不删除。 generation原地清理时不变。目录没了必须重建时，沿用旧号——否则同一张单里其他执行体的绑定对不上，之后合并会卡住。这是本设计最需要评审盯的一点。 救援清单（manifest）每次处置都有一份，先写在 Flywheel 状态目录（目录没了、或根本不需要推救援分支时也有），事件里记着它的哈希；清理完再复制一份到目录里 git 看不见的 .flywheel/runs/takeover/，不影响替身启动前的「目录必须干净」检查，也不移动提交点。 一把锁跑完从检查到清理全程持有这个仓库的变更锁，中间不给别的流程插进来删建同一个目录的机会；中途崩溃后，下次派发先读回「已保全但没清理完」的事件，核对 manifest 哈希后只接着把剩下的做完，对不上就停手。 运行事件worktree_takeover_rescued，只能由 Bridge 进程内部写，外部 HTTP 通道写不进（防伪造）。

取舍与被否决的方案

方案结论为什么
原地清理（保全后 reset --hard + clean -fd）采纳路径、身份号不变；不会把停驻前任的进程一起杀掉；替身完成时的提交点校验天然一致
issue 字面的「删目录，从远端重建」只用于目录已经没了删目录会换身份号（合并会卡 worktree_generation_mismatch），还会把停驻前任的进程收割掉
在新路径旁建一个目录否决路径是按单号算出来的，十几处代码依赖；绑定关系只能设一次
用 git stash否决stash 在所有工作目录间共享，别的会话可能弹走；也推不到远端
只留本地引用，不推远端否决本机出事仍会丢；普查明确要求救援引用必须上远端。推送失败就停手
Bridge 把证据直接写进 progress.md 并提交否决会移动提交点，QA 测的和评审过的就不是同一个了
Bridge 启动前自动把死体的改动放回去否决启动前「目录必须干净」是防止把别人的改动算到替身头上的硬门；冲突处理也不该变成无人值守的静默决定。改为替身启动后按提示词自己恢复

诚实边界：做什么、不做什么

  • 做：七类失败的自动保全 + 清理 + 接管；停手时告警列出具体脏路径；worktree_not_found 这支改为从分支尖回退找提交点，找不到时告警（今天完全静默）；一个总开关（kill switch），关掉即回到今天的行为（下面「关不掉的防线」除外）。
  • 不做：不修前任为什么会死（额度墙是 FLY-2521 等）；不修 FLY-2528（宿主 tmux 消失被记成「完成」）、FLY-2329（回滚后不重新派发）；不把评审目标 checkout 挪出共享目录（那是 FLY-2122 的根治）；不自动回收救援分支和救援目录（至少保留到本单 ship 之后，回收另起单）。
  • 已与 Lead 定案（FLY-2122）：「脏」的判断一字不改。前任不能证明已停时，往共享目录放未跟踪目录 → 接管仍失败并列出路径；能证明时 → 嵌套仓整目录零损失挪走、列出路径、再接管。同时做根治：跨仓评审的嵌套 checkout 固定放在树内 .flywheel/review-targets/，并被 git 精确排除（不能放到树外——「评审目标必须在工作树内」是防伪造的安全边界）。
  • 不改变的老路：「从没登记过、目录也不在」的首次创建照旧，只补一步：本地分支上有未推提交时先推救援分支。登记探针出错、目录在但读不出提交点、目录在却没登记——这三种一律停手，不再像今天那样直接删目录。
  • 不承诺：真 Codex 替身演练——要等 Codex 服务恢复后由 QA 另做；本机只跑相关测试。
  • 关不掉的防线：总开关只管「要不要自动保全 + 清理」。「登记状态查不清 / 目录在却读不出提交点 / 目录在却没登记 / 本地分支有未推提交却要被删」这四种今天会静默丢数据的情况，开关关着也一律停手。
  • 回滚：关开关即可；已经推上去的救援分支、救援目录都保留，不需要清理。
  • 2026-09-26 新增（v5.2）· 被忽略文件的保全门：.gitignore（仓库里一份「这些文件 git 不管」的名单，例如依赖包目录）列出的文件，git 平时看不见，所以既不进快照、也不进救援分支。重派时的新一轮评审用真实 git 复现出：如果清理要切到的提交点改了这份名单，或者开始管同名文件，清理就会把这些「看不见」的文件删掉或覆盖，而系统还报「零丢失成功」。现在清理前先逐条核对「这次清理会写哪些路径」：那些位置上只要有没被保全的东西、或这次清理会改动任何一份忽略名单，就停手告警并列出路径，和今天一样等人处理。代价：这类情况不再自动接上；常见的「只有未提交改动」和「只落后几个普通提交」不受影响。

测试与验收（实现节点要交的证据）

层要证明的事
真 git 集成测试（每类一次）临时目录里建远端 + 主仓 + 共享目录，构造每一类失败；处置后从远端救援分支取出内容，与处置前逐字节比对，提交集合完整；嵌套仓按挪走后的目录比对
