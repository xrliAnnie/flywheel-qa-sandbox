● 2. 核心流程图（实施节点要做的四步）

下图是 实施节点（流程里真正动手改文件的那个自动化环节）拿到本设计后要走的路。四个 chunk（分块：把任务切成可独立验收的小步）严格顺序执行，验证不过就退回重做，不会带着错误往前走。

  • C1 追加：用 printf '%s\n' '…' >> README.md。>> 是「只在文件末尾追加」的 shell 写法，天然不会碰到已有内容。
  • C2 窄验证：只允许读 README 的命令（看末行、数行数、看 diff）。issue 明令禁止跑测试套件，计划里把禁令写成了硬规则。
  • C3 提交：提交后立刻记下这个提交的 SHA（Git 给每次提交的唯一指纹）写进进度账本，供回滚定位。
  • C4 开 PR：base 是 main，PR 正文带 Linear 链接和「未跑测试套件」的诚实声明。到此为止，不 merge。

● 4. 设计评审是怎么把关的

计划在实施前经过了 3 轮 Codex 设计评审（由另一家模型 gpt-6-astra 做独立审查，Bridge 即协调服务指定模型与力度，防止自审自批）。每轮结果都回写给 Bridge，最后由一个 fail-closed 门（默认拒绝、只有证据齐全才放行的检查点）核对 requestId、已提交 plan 的内容指纹、工作树干净等条件后才放行。

● 5. 关键取舍与被否掉的方案
方案做法结论
A（选定）printf … >> README.md 追加最小、字节可控、不触碰既有内容
B用编辑器 / Edit 工具把整个文件重写成 4 行结果等价，但多一次「读全文再写回」的风险面（容易顺手规范化空行），无收益
Cecho … >>不同 shell 对 echo 的转义行为不一致，printf 更确定
D顺手删掉前导空行、加个标题越权 issue 明确禁止改其它内容

验证范围的取舍：只做只读 README 验证而不跑测试套件，不是偷懒，是 issue 的硬性要求；research 已实测提交 / 推送钩子（push-guard 的 pre-push、lint-staged 只管 js/ts/json）都不会「背着我们」跑测试，所以这条边界守得住。

回滚的取舍：不用 reset，用 revert（新建一条「撤销提交」而不是抹掉历史）。原因是账本提交会插在中间，且沙箱有 force-push 守卫，抹历史既不可靠也不被允许。

● 6. 诚实边界：这个设计做什么、不做什么
做
  • README 末尾追加恰好一行、逐字等于 marker、文件仍以换行结尾
  • 只读验证：tail -n 1、grep -cxF、wc -l、git diff --numstat
  • 提交、push、开 PR 到 main，PR 正文带 Linear 链接
  • 三份过程文档 + 进度账本随分支进 PR
不做
  • 不改任何其它产品文件（含 doc/VERSION，synthetic 任务不发版）
  • 不跑 pnpm test / vitest / lint / build
  • 不 merge、不 deploy、不重启服务、不请求 ship 批准——merge 走 founder-gated 的 ship 流程
  • 不清理 README 前导空行、不加标题

已知限制：本设计只证明「流程能跑通」，不对 README 内容本身有任何产品意义；marker 行未来由后续 QA 轮次按同样方式追加或清理。
