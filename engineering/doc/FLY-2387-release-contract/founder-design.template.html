FLY-2387 · 先锁发布合同:版本 / 通道 / 发布清单

设计稿 · 2026-09-06 · 上游:PRD FLY-1098 §6 / §7.2 / §7.3 / §14 B0 · Epic FLY-1143 · 文档:engineering/doc/FLY-2387-release-contract/(exploration / research / plan)· Codex 设计评审 4 轮后 APPROVED(8 → 4 → 2 → 0 项,全部采纳)

一句话

给 Flywheel 对外发布这件事立一份「合同」:版本号怎么起、发布走哪条通道、发布清单里有什么字段、什么情况下绝不允许把东西推给客户——全部写成机器能自动核对的规则,放在一个地方;后面五张单(发布流水线、托管、健康判据、自动发布、客户更新器)都只认这一份,不再各抄一份。

审计发现:这份合同的大半已经是运行中的代码(FLY-1062 / FLY-1323 落地并在 CI 里强制)。所以本单不是从零发明,而是把散在三份不互相引用的实现和一份 54KB 计划里的规则收成一份,顺手补上 9 个缺口和 1 条评审时发现的真漏洞。本单不做任何真实发布动作。

现状:哪些已经有了,哪些是本单要补的

先解释几个词。manifest = 发布清单,一个 JSON 文件,记录「现在内部测试版指向哪个版本、客户正式版指向哪个版本、每个版本的内容指纹」;sha256 = 内容指纹,文件内容变一个字节指纹就变;CAS = 「先比对再写」,写清单前先确认它没被别人改过,改过就重来,保证不会两个人互相覆盖;beta = 内部先用的版本,写法 1.56.0-beta.3;clean = 去掉 beta 后缀给客户的正式版 1.56.0。

PRD 要求现状本单
§6.1 版本只有一个真相(doc/VERSION 存 base,beta / clean 由它派生)已落地但派生规则有 三份互不引用的实现(bash 打包脚本、端点、发布脚本),且实测都放过了 beta.0、beta.01 这类不该出现的写法一份真相 + 一组正反例向量同时锁三份实现
§6.2 两个身份(beta 产物 / 正式产物)+ 否决窗口绑真产物已落地提交时必须报指纹、零重新构建;但没有具名的「候选 / 产物 / 绑定」类型给自动发布用定义 VetoBinding 等三个类型和派生函数,全部从清单读,不另存副本
§7.2 一个通道真相(internal-beta / customer-release)已落地但通道名硬编码在 8 处常量出口 + 结构检查禁止再硬编码
§7.3 七条发布不变量已落地六条半;「同一正式版本号绝不换内容重发」没有具名负例逐条写成表:谓词 / 现有测试 / 新增负例 / 谁负责
manifest 字段合同(给 B1 切指针、B4 否决窗口、B5 更新器)缺只有代码和计划散文,没有机器可读的 schema(字段与类型的正式定义)和示例JSON Schema + 6 个合法示例 + 两层坏例
§8.2 「无可用版本,更新暂停」状态缺清单校验规则不允许「客户指针为空但有被隔离的版本」,所以「第一个正式版就坏」这种情况根本表达不了放宽一条规则(C-1b),定义 paused 态和它的对外回应

核心流程 ②:一个版本从起号到给客户的身份链

__SVG_D2__

图 2 · 版本身份链与 C-6b 围栏(Mermaid 本地渲染)

重点在菱形那一步。Codex 评审第一轮用现有代码真的构造出一条漏洞路径:先把一个候选 beta 隔离掉(标记为坏版),再提交由它派生的正式版——现有的所有检查都放行。这就是 TOCTOU(检查时和使用时之间被人改了状态)。本单把「提交那一刻 beta 必须仍是好的」写进服务端规则 C-6b:不满足就拒绝,指针不动,本周期取消且不重开否决窗口。

合同要点(细则见 plan §1)

  • 版本:doc/VERSION 只存 vX.Y.Z;清单和包里的版本号不带 v;beta 序号 N ≥ 1、不许前导零;N 只能由清单里的计数器分配,脚本不许自己算;正式版本号一旦切进清单永不换内容重发。
  • 通道:客户端只认指针,不许自己在版本列表里挑最大的(撤版时指针会往回退);npm 上的标签只描述薄壳安装器,永远不表达 payload 通道;不用 GitHub Release。
  • paused 态:某通道指针为空 ⇔ 该通道没有 active 版本。从未启用和「有版本但都被隔离/过期」两种子态,对客户都是 503,但回应体分别是 not activated / no-release-available;这期间不给该通道签发新 key。
  • 身份:自动发布(B4)绑定的是 VetoBinding = beta 身份 + 正式产物身份 + 同一个 sourceCommit,六个字段全部逐字来自清单;提交接口保持现有的「releaseId + 预期指纹」两个参数不变。
  • REQ-0(两扇独立门):上线门的授权是 Discord 🆒;对外发布门的授权是否决窗口沉默或 founder 明确说发,不是 🆒、不是 merge、不读上线账本。三个发布 workflow 都只由定时或手动触发,merge 不会连带发布——这条也写成结构断言 S13 进 CI。

关键取舍与否决的方案

决定选了什么否决了什么,为什么
合同放哪新建一个零依赖的小包 packages/release-contract/,端点和发布脚本改为引用它否决只写文档不改代码:三份实现照旧漂移,「示例通过 schema 校验」没有对象可校验。否决把真相留在端点包里让别人引用:Bridge 侧要反向依赖一个 Cloudflare Worker 包,方向反了。
schema 怎么执行JSON Schema 作为对外的机器可读文档;运行时不装校验库,由合同包内置的零依赖「键集合逐字相等」检查执行同一规则;测试断言两者对同一组例子判定一致否决在 Worker 运行时引入 ajv / zod:端点包坚持零依赖,且现有手写校验器已经覆盖 schema 表达不了的跨字段关系。
paused 态放哪放本单(合同层放宽 C-1b),撤版进 paused 的命令行归 B5否决留给 B5:B5 会被合同堵死,验收第三种情况「第一个正式版就坏」在合同层不可表达。
提交时的 TOCTOU 围栏服务端 transition 层做(C-6b),客户端提交回调再核一次;提交接口两个参数不变;已提交的重跑只核 releaseId + 指纹即幂等成功否决只在否决窗口关闭前预检一次:Codex 证明窗口和最终提交之间可被改状态。否决写成静态不变量:beta 14 天后合法过期而正式版还活 28 天,静态规则会误杀。
bash 打包脚本保留 bash 实现,由共享向量文件锁一致否决让 bash 调 node:打包环境可能没有 node 依赖。
清单版本号schemaVersion 保持 1,所有改动向后兼容,零数据迁移否决借机升 2:没有不兼容字段,升了只会让 B1/B2 多一件事。

怎么验收(对 issue 的三条验收)

  • B1 / B2 能只依赖本合同并行开工:合同文档、类型、schema、校验器全在一个包里自包含;B1 落最后一步「切客户指针」时唯一要重谈的旧断言(S4b)已在表里写明。
  • manifest 示例通过 schema 校验:6 个合法示例过 schema 和关系校验;形状坏例被 schema 和运行时检查一致拒绝;关系坏例过 schema、被校验器按编号拒绝——全部在 CI。
  • REQ-0 对照表无违反项:表在 plan §1.6;结构断言 S1 / S4 / S13 在 CI 绿。

另有:版本向量在 node 和 bash 两边跑同一份文件;类型声明用 tsc --noEmit 夹具锁;Worker 打包 dry-run 证明合同代码真的进了产物;既有六套发布层测试全部保留、不改断言。

诚实边界:这份设计做什么、不做什么

  • 做一份合同 + 一个合同包 + 消费者改引用 + 两条合同层加固(C-1b 放宽、C-6b 收紧)+ 断言测试 + CI 接线。
  • 不做任何真实发布:不碰 npm、不碰 R2、不碰凭据、不新增 workflow、不动 broker、不改 FLY-1323 的凭据姿态。
  • 不做B1 的薄壳 next 标签断言、B5 的撤版进 paused 命令与客户端话术、B4 的决策账本、/v2/manifest。
  • 不改发到 npm 的薄壳安装器任何一个字节。
  • 假设生产清单目前为空(FLY-1323 中间态);即便有内容,本单的规则放宽向后兼容,收紧只影响新写入。B1 启用前会用合同包对生产清单快照跑一次校验。
  • 已问 Lead、按默认继续两个非阻塞问题:合同包是否独立成包(默认是)、C-1b 放宽是否放本单(默认是)。Lead 若改主意,implement 节点按 design-correction 增量改。
  • 本 worktree 限制没有 node_modules,bash 的版本注入测试在这里没跑过;implement 节点先 pnpm install 再跑,不得把「没跑」记成绿。
