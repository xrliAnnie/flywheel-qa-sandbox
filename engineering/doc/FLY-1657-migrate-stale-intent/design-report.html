FLY-1657 · 迁移工具修复设计

run5 迁移窗的硬前置 · 设计阶段报告(Codex design review 4 轮 APPROVED) · 2026-08-07 · Issue: FLY-1657

1 · 一句话总结

run4 迁移窗炸掉的真凶不是"库形状",而是上一次窗口留下的一张过期便签(swap-intent:迁移工具写在库旁边的断点续跑进度文件)——工具无条件相信它、跳过全部工作,最后在检查步上撞死;本设计让工具在信便签之前先核对现实:证据链闭合的过期便签自动归档后重新迁移(run5 不需要人工干预),其余任何对不上的情况一律大声报错停下,同时封死了比 run4 更危险的三条"静默丢数据"暗道。

2 · 出了什么事(run4,8月7日 01:17)

迁移窗按计划先迁 root 库——成功;紧接着处理 comm/flywheel 库时,工具报 no such table: mailbox_migration_meta(意思是:库里找不到"迁移已完成"的标记表),整窗判 FAILED 自动回滚。

关键在橙色那步:8月6日那次窗口,comm/flywheel 其实完整迁移成功过,便签写下了"done"。后来窗口整体失败,恢复用的是"把旧数据快照直接拷回去"的文件级操作——数据回去了,便签没人清。run4 的工具一进门看到"done",就把备份、迁移、换库全跳过了,直落最后的检查步撞死。root 能过,只因为它没有残留便签。

3 · 根因证据:四个实验,推翻"库形状"假设

issue 原本怀疑是两个库的表结构形状不同导致。设计阶段做了四个实验(全部在临时副本上,没碰任何生产库):

实验输入结果
复现(阳性对照)极小合成库(连"多出来的表"都没有)+ 一张 done 便签原样炸出同一个错误 —— 形状无关,便签就是触发器
负对照 A同款小库 + 故意加上那些"多出来的表",不带便签迁移成功
负对照 B(根库幂等)生产 root 库副本(已迁移)+ done 便签副本通过,数据无损 —— run5 重跑不会误伤 root
全量彩排r4 快照里真实的 comm/flywheel 数据(5.3 万行),不带便签16.6 秒全量迁完,"多出来的表"原样保留

结论:现行迁移代码对这个库的形状和全部真实内容都能正确处理;唯一的雷就是过期便签。重跑必死、root 能过 flywheel 必炸——全部由此解释。

4 · 比 run4 更危险:三条"静默丢数据"暗道

run4 撞上的便签是"done",结局是大声失败——这其实是运气好。同一张过期便签如果停在更早的进度上,工具会把8月6日的旧备份或旧暂存副本直接盖到今天的库上,然后报"成功":一天的新数据无声消失。

便签停在工具会做什么后果
done 等后段进度全跳过 → 最后检查撞死大声失败(run4 实况)
staging_verified(暂存副本已就绪)把旧暂存副本直接改名换入正式位置静默丢数据
backed_up 等前段进度发现旧备份已存在就直接复用,拿旧数据走完全程静默丢数据

所以修复不能只补 run4 那一条路,必须把"信便签之前先核现实"做成整套闸门。Codex 评审还追出了同一根源的第四条暗道:回滚命令(rollback)同样无条件信便签——对着被恢复过的库执行回滚,会把旧备份盖上去并"验证成功"。本设计一并封死。

5 · 修复方案:先核现实,再信便签

三个要点:

  • 自愈只开一扇窄门:便签说"换库完成过"、但库现在明明是旧格式——这只有一种解释(数据被带外恢复过)。再验两道证据(暂存副本确已消费、隔离区无残留)后,工具把旧便签归档留证,从当前数据重新迁移。这正是 run5 需要的:comm/flywheel 不用任何人工清理。
  • 其余一律大声停:任何对不上的情况(格式坏、路径不符、指纹不匹配、证据矛盾)都拒绝动库,把该归档什么讲清楚。宁可窗口失败重开,不静默丢数据。
  • 断点续跑要凭内容指纹:光看文件"只读属性"不够(已打开的写句柄不受它约束,Codex 实测证实)。新便签(v2)记下每个环节的 sha256 内容指纹(文件内容的唯一数字摘要,内容变一个字节指纹就变),续跑前逐环核对。

6 · 数据/结构模型:v2 便签的凭据链

迁移流程是"正式库 → 备份 → 暂存副本迁移 → 原子换回"。v2 便签把链上每个文件都用指纹钉死;续跑或回滚要动谁,先验谁:

  • sourceBinding:上锁那一刻正式库(和它的 WAL ——数据库的"待写入流水账"文件)长什么样;
  • backupSha256 / refsManifestSha256:备份产物落定的同一笔账里记下它们的指纹——防止有人把"另一份看起来合法的备份"塞进来被误采纳;
  • stagingSha256:暂存副本验证通过时的指纹——换库前最后一道核对;
  • 旧格式(v1)便签只允许走"库确实已迁移"的收尾路径,断点续跑一律拒绝(生产现存的两张 v1 便签都是 done,不受影响)。

7 · 关键取舍与被否掉的方案

决策点选了否掉了为什么
过期便签怎么处理证据链闭合 → 自动归档重迁;其余大声停"一律人工归档后重跑"run5 窗口是全自动脚本,窗口里插人工步骤正是 r4 类事故的温床;自愈只开在证据无歧义的场景,且旧便签归档不删、可复盘
内容核对用什么文件字节 sha256 指纹"全库逻辑摘要"(逐表逐行算)要证明的是"上锁之后没人动过",字节指纹恰好足够,还复用现有工具函数;逻辑摘要是过度工程(Codex 也认可)
备份发布与记账之间的空窗发现"有备份文件但账上没指纹"→ 大声停,绝不采纳加一套"备份准备中"子状态机自动收养那个空窗极窄,自动收养换来的收益抵不过引入的复杂度;牺牲这一点自动恢复,换零数据损失
只修 run4 那条路?正向 + 回滚两侧全部装闸只补最后检查步的报错同一根源有四条暗道,三条是静默丢数据,比 run4 的大声失败更毒

8 · 诚实边界:这个设计做什么、不做什么

做

  • 迁移工具(库层 + 命令行清单输出)对便签的全部信任路径加现实核对;回滚命令同侧加闸;
  • run5 所需的两件事有实测背书:comm/flywheel 自动自愈重迁 ✅(彩排 16.6 秒)、root 幂等跳过不误伤 ✅(副本实测);
  • 清单命令(inventory)顺带显示每个库旁边有没有便签、停在哪一步——run5 预检一眼可见。

不做(留给别的单/运维)

  • 不碰生产现场的任何清理:旧备份、旧暂存目录、root 那张 done 便签全部原位保留(root 的备份+便签定位为取证证据,root 铁律不许回滚);
  • 不改窗口脚本本体(~/.flywheel/r4 是生产资产;模板回灌在任务 #192);runbook 修订条目随 PR 文档交付:废止"看到便签就执行回滚"的旧经验法则;
  • 不重新设计迁移映射逻辑——彩排证明它没病,不该动的不动;
  • run5 当天活库若新增了工具没见过的数据形态,工具会按既有守卫大声拒绝——那是正确行为,不是本单要"修"的东西(验收会用新鲜副本预扫一次尽早暴露)。

9 · 验收计划与 run5 对接

  1. 先复现用生产 comm/flywheel 的新鲜副本 + 便签副本,在未修代码上先炸出同一个错误(阳性对照,设计期已用合成库和快照库各证一次);
  2. 再修复同一副本在修后代码上:自愈日志 → 便签归档 → 全量迁移 → 验证通过;
  3. 根库幂等root 副本(连便签一起)实测跳过路径与库层收尾路径;
  4. 全库清点生产全部 9 个库(root + 8 个项目分库)逐一副本化跑 inventory:状态干净、便签期望逐库对上;
  5. 全仓门禁lint + 全量 build + 全包测试 + 脚本 bash 测试;Codex code review 循环到 APPROVED;
  6. 合入后报新 target SHA,Annie 重新授权,run5 才开窗。
