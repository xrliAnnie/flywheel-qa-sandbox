- Keep EngineDriver as the sole settlement owner and keep CLI settlement writes prohibited.
- Keep the explicit runner delivery path separate from the existing Lead Converter semantics.
- Keep the two named founder decisions, structural hold, full evidence revalidation, and atomic 8b release.

- Keep the explicit checkpoint/rename/fsync/marker crash seams once their executable order is corrected.

## Issues & Recommendations

1. **[BLOCKER] The host IPC can acknowledge a proposal that disappears before EngineDriver settles it, and its claimed authentication mechanism is not actually frozen.** The plan says duplicate submission returns an existing “accepted receipt” and the CLI retries only across host crash (`plan.md:48-56`). If the host accepts and replies, then crashes before the waiting Converter returns/EngineDriver commits `mailbox.applied`, the proposal exists only in host memory; the CLI has already succeeded and need not retry. After restart, the recorded delivery action may replay without physically reinjecting, leaving the running processing attempt with no proposal. Batch 2 has no durable proposal row; `submitProposal()` is the settlement itself (`packages/v2-engine/src/settlement.ts:98-134`). Also, “FLY-245 broker pattern” does not by itself authenticate an agent: the existing secret broker accepts any successful socket connection and relies on sandbox connect denial (`packages/teamlead/src/lead-backends/codex/secret-broker.ts:82-101`), while this CLI must be allowed to connect; mode 0600 only distinguishes Unix users, not co-resident agents. **Recommendation:** choose one crash-safe acknowledgement boundary. Either persist `{attempt_uid, message_uid, agent/generation, proposal_digest, payload, status}` before returning an accepted receipt, or hold the IPC response until EngineDriver settlement commits; in the latter design, a retry queries a durable settlement receipt keyed by attempt/message/digest, returns success for the same digest, and rejects a different digest. Specify how the IPC proves the caller is the bound agent/generation/attempt—e.g. a per-activation non-replayable capability or verified peer PID/process ancestry—not merely caller-supplied identity fields. Add real tests for crash after receive, after receipt creation, after settlement/before response, concurrent same/different-payload duplicates, and cross-agent impersonation.

2. **[BLOCKER] The proposed same-instance/same-generation Lead reattach cannot be fenced from the current durable schema.** The plan requires session evidence plus a new reattach API (`plan.md:70-74`), but the `agents` table persists only agent id, kind, generation, heartbeat and state—no Lead `instance_id` (`packages/v2-kernel/src/migrations/0005-agents-config-mailbox-rebuild.ts:3-9`). `processing_attempts.instance_id` exists only when a message attempt exists (`0003-activations-processing-attempts.ts:11-23`), so an idle Lead after host crash has no durable value against which “same instance” can be checked. A PID/socket liveness observation alone cannot prove the database generation belongs to that exact session, especially under PID/socket reuse. **Recommendation:** persist an immutable current consumer binding (agent, instance id, generation, host epoch/session identity) in the same registration transaction and make reattach CAS that exact binding plus fresh process/session evidence; alternatively decline reattach and define a safe generation transition that does not falsely declare a live session dead. Include idle-Lead recovery, wrong instance with correct generation, stale PID/start-time, reused socket, stale host epoch, and concurrent reattach-vs-reregister tests.

3. **[BLOCKER] Authority/T1 still has no valid state transition for the interval after 8b but before the first external effect.** Step 8b changes authority `cutover→live` (`plan.md:258-260`), while rollback only accepts `cutover AND zero effect intents` and authority rollback is specified only as `cutover→pre` (`plan.md:157-164,241-243,258-260`). The locked T1 boundary is the first external effect, so a `live` database with zero effect intents must still be reversible; the current predicate rejects it. Conversely, the armed sentinel is never deleted and unauthorized state regression must fail closed, so a legitimate T1 projection back to `pre` needs durable rollback proof that readers can distinguish from tampering. Finally, `plan.md:269` still says authority-file absence is byte-compatible without conditioning that statement on “unarmed,” contradicting `plan.md:252-260`. **Recommendation:** make the atomic rollback predicate accept `{cutover, live} + zero effect intents + rollback_state=clear`, transition to `rollback_started` under the same fence, and publish `pre` only with a monotonic revision/window plus a durable rollback receipt/digest. Readers with an armed sentinel may accept `pre` only when that receipt validates; every other live/cutover→pre regression fails closed. Correct the unconditional missing-file sentence and add live-zero rollback, live-with-intent rejection, forged-pre projection, and stale rollback-receipt tests.

4. **[BLOCKER] The “complete” migration table still has uncovered/overlapping states and does not preserve canonical Discord dedupe.** A JSON main entry contains only `{from,text,timestamp,read,...}`—no message type, expiry, or business/notice class (`packages/agent-team-transport/src/claude/ClaudeMailboxCodec.ts:46-54`). Therefore the row “JSON with flywheelId but no comm row → classify by messages rules” (`plan.md:208-210`) is not executable unless another authoritative envelope supplies those fields. The table also omits a non-expired model `lead_inbox` row whose Lead is absent/terminal, overlaps protocol+expired rows despite promising “exactly one cell,” and places every `carrier='external'` row outside the domain even though undelivered external rows are active delivery obligations (`packages/flywheel-comm/src/lead-inbox-queue.ts:711-767`) that must drain/block rather than be silently archived. Finally, migrated `lead_inbox` rows use `(legacy-comm,<project>/inbox/<id>)` and keep a Discord key only in payload metadata (`plan.md:191-193`); a post-cutover replay enqueued as `(discord,<canonical Discord key>)` will not hit mailbox `UNIQUE(source_kind,source_id)` and can deliver twice. The vendor “content hash” is also underspecified and can collapse two legitimate identical texts unless it includes occurrence identity. **Recommendation:** make the table mutually exclusive with precedence and cover every recipient/deadline/terminal combination. Treat JSON-only rows without class metadata as a defined tombstone/manual class, or name the authoritative metadata source used to reconstruct the class. Require pending external receipts to drain to zero or become a blocking manual item; archive only terminal external rows. For Discord/founder rows, use the same actual `(discord, canonical message key)` as future enqueue, derived and verified from `source/ref_message_id/content`; unknown provenance is manual. Define the JSON key as a canonical tuple including team, recipient path, from, timestamp, text (and collision ordinal/evidence where needed), then add replay-dedupe and identical-text/distinct-occurrence fixtures.

5. **[BLOCKER] The cutover inventory still omits each Codex Lead’s durable `journal.db`, which can contain accepted but unfinished Discord/mailbox inputs when those runtimes are disabled.** Codex TUI/headless construct `SqliteJournalStore(config.journalDbPath)`, one WAL database per Lead under `…/codex-lead/<id>/journal.db` (`packages/teamlead/src/lead-backends/codex/SqliteJournalStore.ts:1-17,78-114`). Its nonterminal states are explicitly recovered by `listUnfinished()` and include accepted, dispatching, dispatched, model-completed and output-pending work (`LeadJournal.ts:88-121,333-357`). Round 3 disables those independent gateways but step 2 enumerates only comm.db and JSON, and neither plan nor research mentions journal paths. Stopping a Lead with unfinished rows can lose an accepted founder message, duplicate a turn, or strand a completed-but-unsent output. This does not require changing the locked two-source migration architecture: it requires proving this separate runtime journal is drained. **Recommendation:** add all per-Lead journal DB/WAL/SHM paths to the target manifest and stop-new-ingress sequence; before step 3, run their native recovery and require `listUnfinished()==0`, with any ambiguous/dead-letter rows reported separately. Nonzero unfinished rows must block the window (or be explicitly mapped if the design chooses migration). Include WAL-safe snapshot/archive evidence and a Go/No-Go query/fixture for each nonterminal journal state.

6. **[HIGH] The WAL promotion sequence is still mechanically impossible in its stated order.** `plan.md:166-174` says close all staging handles/readers and then issue `wal_checkpoint(TRUNCATE)`, but the PRAGMA is connection-scoped and requires an open SQLite connection. The correct check also needs the checkpoint result’s busy/log/checkpointed values, not only filesystem sidecar size. **Recommendation:** close every other reader/writer, retain or open one sole promotion connection, execute blocking `wal_checkpoint(TRUNCATE)` and require `busy=0` with all frames checkpointed; close that final connection; then verify no open fds and absent/empty WAL/SHM, fsync the main file and directory, rename, fsync again, validate the promoted DB, and durably publish/fsync the marker. Update the four crash-boundary tests to exercise this exact order.
