# Design Review — FLY-1502 plan.md (Round 2)

Date: 2026-07-28
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 2 substantially improves the operational design: the locked nine-step ledger, full-control-plane rehearsal, machine-wide writer inventory, staging/open-existing sequence, lsof/path fencing evidence, and primitive rollback ledger are all materially stronger. It is still not ready to implement because several newly introduced contracts conflict with the batch-2 transaction/API boundaries, the authority and T1 predicates are not monotonic/atomic, and `research.md` still contains normative legacy rules that contradict the corrected plan.

## What's Good (Keep)

- Keep the restored locked step numbering and the explicit rule that live-fire/checker evidence is not a replacement tenth or eleventh step.
- Keep the target-manifest rehearsal model, production-label/path/socket rejection, real namespaced services, and production control-plane zero-delta proof.
- Keep production host/scheduler/CLI as open-existing-only and move every fresh migration/bootstrap operation into cutover/rehearsal tooling.
- Keep the expanded writer matrix; it now reflects the real independent Codex Lead ingress and old-DB openings rather than treating `plugin.ts` as the whole machine.
- Keep lsof evidence, realpath ancestor/descendant/symlink checks, the explicit ban on fencing `~/.flywheel`, and the post-8b zero-old-write acceptance response.
- Keep per-primitive intent/apply/verify/complete records, crash injection, rollback credentials, and exact filesystem/service-state comparison as the basis of T1.

## Issues & Recommendations

1. **[BLOCKER] The proposed sessionRef mapping cannot be written by the current spawn port “in the same kernel transaction.”** The plan says the spawn port writes `injection_ref:<activation_id>` while the activation is created (`plan.md:55-59`). In batch 2, activation/attempt/session identity is created inside the synchronous `prepareCandidate` Kernel transaction (`packages/v2-dag/src/dispatch.ts:269-333`), while `SpawnPort.spawn()` is asynchronous and is invoked only after a separate launch-receipt transaction has committed (`dispatch.ts:436-481`; `types.ts:44-57`). `Kernel.write()` also rejects async/thenable callbacks (`packages/v2-kernel/src/kernel.ts:273-309`). Calling an async external spawn port inside that transaction would violate the kernel lifecycle; letting the port open its own write would no longer be the same transaction. **Recommendation:** freeze a feasible seam: add a pure synchronous `InjectionRefBuilder` (or equivalent) that derives the exact shim JSON from the IDs created during prepare; v2-dag-owned code inserts that value into meta in the same activation transaction. Keep `SpawnPort.spawn()` outside the transaction and make it consume the already persisted mapping. Define recovery reads for `requestForSession()` and negative tests for missing/mismatched mapping. Do not give a port a raw `WriteTx` or let it perform nested writes.

2. **[BLOCKER] The process-external proposal/settlement and restart protocol is still not a closed executable contract.** Today `EngineDriver` awaits the registered Lead `Converter`, then itself calls `submitProposal()` or `reportConversionFailure()` from the returned `ConversionResult` (`packages/v2-engine/src/driver.ts:378-450`). The package-level `submitProposal()` immediately settles the mailbox/attempt in SQLite; there is no durable proposal queue/table (`packages/v2-engine/src/settlement.ts:98-157`). Therefore a CLI that directly settles will leave the host Converter waiting and make the driver attempt a second settlement; a CLI that merely “submits to host” needs a specified authenticated IPC/durable handoff that the plan does not define. Runner handling is also different: `attachRunner()` has no Converter, and `poll()` starts the automatic handler only when a Converter exists (`driver.ts:134-188`). Finally, host restart is not an idempotent registration replay as claimed at `plan.md:60-61`: replacing any existing generation requires matching death evidence and advances generation (`packages/v2-engine/src/registration.ts:91-162`). **Recommendation:** choose and freeze one settlement owner. The clean shape is an authenticated host IPC: CLI submits an attempt-bound, idempotent proposal; the waiting host Converter returns it and EngineDriver remains the sole settler. Specify IPC durability/retry after host crash, exact handle/agent fencing, proposal-size validation, stable delivery action `invocationUid`, and duplicate behavior. Define a separate runner delivery loop or change the driver API explicitly. For host recovery, either obtain exact absence evidence and register a new generation or add/test a narrowly fenced idempotent reattach API; do not describe current registration as idempotent.

3. **[BLOCKER] The machine authority is called fail-closed but deletion/missing state fails open, and its state transitions are absent from the nine-step ledger.** `plan.md:186-190,198` defines missing authority as `pre`, so deleting/corrupting the only authority file after freeze or after cutover re-enables every old entrypoint’s byte-compatible path. The document also never says which primitive performs `pre→cutover`, `cutover→live`, or rollback, even though those transitions determine when new legacy CLI invocations are rejected and must match the DB window/epoch. **Recommendation:** seed an explicit `pre` file as part of deployment and distinguish never-armed compatibility from an armed machine. Once a valid authority/window has ever been armed, missing, malformed, stale-window, wrong-epoch, or regressed state must fail closed; use a separate durable armed sentinel or equivalent monotonic evidence so absence cannot mean both “never cut over” and “authority disappeared.” Put CAS-like transitions in the primitive ledger: step 2 establishes `pre→cutover` before allowing the freeze to proceed, 8b establishes `cutover→live`, and T1 may establish `cutover→pre` only through the atomic rollback gate. Every reader must validate the same window/epoch and tests must cover deletion, truncation, stale rename, and state regression.

4. **[BLOCKER] The migration mapping is still promised rather than specified, and `research.md` retains the exact rejected rules as its “core specification.”** `plan.md:149-154` lists the Cartesian state dimensions and says a normative mapping table will later go into the runbook, but it does not state which concrete combinations map to pending/dead/tombstone/archive/manual; implementation is scheduled before runbook finalization (`plan.md:228-234`). More critically, current `research.md:147-162` still says `relay_state='open'`, all `consumed_at IS NULL`, universal sidecar flywheelId alignment, and the old raw-source conservation equation. Its step table also still says fresh DB creation at step 5 and only three process checks (`research.md:129-141`), while `research.md:125-127` still makes a per-project config key the switch. These conflict with the corrected facts at `research.md:59-90` and with the plan, leaving two normative answers in the same design packet. **Recommendation:** place the complete per-combination mapping table in plan/research now, before implementation—not in a later W6 artifact—including the canonical-key rule for vendor-only/surrogate/sidecar-less entries and exact handling of protected+expired, external, processed, disposed, and pending-sidecar cases. Delete or rewrite the stale §2.4 tail, §3 table, §4 rules, and §5 mechanics so there is one authority. Add an explicit assertion/test that every enumerated row receives exactly one mapping and that the table itself, not implementation judgment, drives fixtures.

5. **[HIGH] The step 7→8 authorization sequence is internally impossible as written.** `plan.md:132-133` says live-fire plus the complete Go/No-Go evidence set is green before founder GO and step 8, but `plan.md:134-137,170-175` says item ② can only be obtained after step 8a has started the held endpoint. Both cannot be true, and an implementer will have to invent which founder confirmation authorizes 8a. **Recommendation:** write one explicit sequence in both ledger and runbook: (a) after step 7, run live-fire and every pre-start check except item ②; (b) founder authorizes the reversible/effect-held 8a start; (c) start 8a with admission/effects structurally held; (d) execute item ② and revalidate all evidence; (e) founder gives final GO; (f) 8b atomically releases the hold. Name the two founder decisions and state that 8a cannot create the external-effect watermark.

6. **[BLOCKER] T1 still lacks the atomic exclusion required by “before the first external effect,” and its signed launchd baseline is captured too late.** Step 3 bootouts mutate the loaded/running service state, but the signed service manifest is not captured until step 4 (`plan.md:117-123`); that snapshot cannot reconstruct which jobs were loaded/running before step 3 unless each bootout intent durably stores its preimage. Separately, `rollback-t1` merely checks `watermark==0` and then restores (`plan.md:138-140,178-182`). After that read, a concurrent injection/spawn/Discord/GitHub/scheduler actor can record/perform the first effect while rollback restores the old stack—a classic TOCTOU split-brain. **Recommendation:** capture the service baseline before the first step-3 mutation, either as a signed step-2 artifact or as a complete preimage in every primitive intent. Serialize rollback and all external-effect intents through one durable CAS/fence: rollback atomically changes `cutover/live-with-zero-effects → rollback_started` only if no effect intent exists; every effect atomically records the non-clearable first-effect watermark/action intent under the same predicate and is rejected after `rollback_started`. The watermark must be written before the external call, never after it, including v2-dag spawn’s launch-claim path. Add a real concurrent race test (`rollback-t1` versus each effect family), not only crash-before/after tests.

7. **[HIGH] Atomic promotion of the staging database is not yet WAL-safe.** Every writable kernel connection enables WAL (`packages/v2-kernel/src/connection.ts:20-28,47-79`), but the frozen sequence only says “fsync → rename” the main staging path (`plan.md:142-146`). If committed frames remain in `.staging-<window>-wal`, renaming only the main file can promote an incomplete database or strand its WAL under the old basename. **Recommendation:** require all staging handles/readers closed, a successful blocking checkpoint (and verified empty/removed WAL/SHM), then fsync the main DB and containing directory before/after same-directory promotion; alternatively produce the promoted file with SQLite backup into a fresh final-name temp and validate that copy. Define crash reconciliation at checkpoint, main rename, directory fsync, and marker publication boundaries, and assert the final DB has no mismatched staging sidecars/open fds before writing the completion marker.
