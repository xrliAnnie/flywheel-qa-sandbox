# Design Review — FLY-1502 plan.md (Round 4)

Date: 2026-07-28
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 4 correctly moves the IPC success boundary behind the EngineDriver settlement commit, recognizes the Codex Lead journal as a third durable account, and fixes the WAL checkpoint ordering. It is not yet executable as written: migration 0009 is bypassed by the frozen creation/startup checks, the proposal receipt and capability have no complete durable representation or Lead binding, and several Round-3 corrections remain contradicted by normative migration/T1 text.

## What's Good (Keep)

- Keep `hold-until-settlement`: the host must not reply successfully until mailbox application and processing-attempt settlement commit.
- Keep same-digest success, different-digest rejection, single-use proposal authority, and EngineDriver as the sole settler.
- Keep the requirement for exact process/session evidence before reattach and exact absence evidence before generation replacement.
- Keep the primary step-9 predicate admitting both `cutover` and `live` before the first effect, plus the durable rollback receipt for authorized `pre` republication.
- Keep the first-match migration-table direction, blocking treatment of unfinished external delivery obligations, Discord replay-dedupe goal, and distinct-occurrence fixture.
- Keep the explicit Codex Lead journal drain-to-zero requirement and per-state negative fixtures.
- Keep the corrected promotion order: one final connection checkpoints, then closes, then fd/sidecar/fsync/rename/marker checks run.

## Issues & Recommendations

1. **[BLOCKER] Migration 0009 is not part of the database creation or launch-acceptance contract, so the new reattach fence can be absent while every gate passes.** The plan introduces 0009 at `plan.md:78-86`, but the host accepts exactly eight migration-ledger rows (`plan.md:38-41`), step 5 verifies `20 表+8 ledger` (`plan.md:155-158`), and staging runs only 0001-0008 (`plan.md:187-199`). Research repeats the eight-ledger requirement in Go/No-Go item ⑦ (`research.md:165-176`). The current repository really does contain only 0001-0008 (`packages/v2-kernel/src/migrations/index.ts:16-64`), so 0009 is a proposed FLY-1502 artifact, not something implicitly covered by the current migrator. Following §4.3 literally produces and promotes a database without the consumer-binding columns, after which the host is explicitly allowed to start. **Recommendation:** make the expected migration manifest an exact ordered ID+checksum set ending in 0009 everywhere that creates, promotes, backs up, or opens the DB; avoid independent hard-coded “8” checks. Keep “20 tables” only if 0009 is a column-only rebuild. Add a fixture proving an otherwise valid 0001-0008 database is rejected by host, scheduler, CLI, promotion validation, and Go/No-Go.

2. **[BLOCKER] The durable proposal receipt and proposal capability are not frozen to a concrete persisted record, and the stated capability binding is not total for Leads.** The plan calls `mailbox applied + processing_attempt settled` the receipt and says it is queried by `(attempt_uid,message_uid,proposal_digest)` (`plan.md:48-61`), but `processing_attempts` has no digest (`packages/v2-kernel/src/migrations/0003-activations-processing-attempts.ts:11-22`) and the current `mailbox.applied` event payload stores only `message_uid` and `attempt_uid` (`packages/v2-engine/src/settlement.ts:111-134`). No planned migration/API change says where `proposal_digest`, the receipt status, or capability consumption lives. The CLI verb table also omits the capability token from required proposal inputs (`plan.md:91-105`). Finally, binding the token to `activation+message_uid+generation` is not valid for Lead attempts, whose durable `activation_id` is null; it also omits `attempt_uid`, permitting a token from an older processing attempt to be presented against a later attempt unless another unstated predicate saves it. **Recommendation:** name the exact existing/new row and typed API. Have the host canonically compute the proposal digest, and in the EngineDriver settlement transaction atomically (a) validate a running exact attempt/agent binding, (b) validate and consume a capability hash, (c) write an immutable receipt containing attempt UID, message UID, digest, and settlement result, and (d) apply effects/mailbox/attempt settlement. Bind Lead tokens to `{agent_id,instance_id,generation,attempt_uid,message_uid}` and additionally bind runner tokens to activation; never use caller-provided digest or identity as authority. State where the token hash, raw deliverable token, and consumed state survive host restart, then add the token to the CLI verb table.

3. **[BLOCKER] A host crash after delivery intent commit can still strand the message forever; “recover from the recorded-action ledger” is not a recovery algorithm.** The plan records delivery as `intent → external effect → outcome` and says in-flight delivery recovers from the action ledger (`plan.md:65-70,78-86`). In the merged implementation, a replayed action immediately returns the prior row and does not call `perform()` (`packages/v2-actions/src/index.ts:49-60`), matching the locked rule that an `intended` action must not be guessed and re-executed (`doc/engineer/plan/v2/design-FINAL-v2.md:34,43-48`). Therefore a crash after intent but before injection and a crash after injection but before outcome both recover as the same `replayed+intended`; in the first case no agent can ever submit the awaited proposal. The newly minted raw token can also be lost before it reaches the injection envelope unless its recovery representation is specified. **Recommendation:** freeze a backend-specific intended-delivery reconciliation path consistent with the locked actions model. Confirmed acceptance waits for the same capability; confirmed non-delivery may create an evidenced successor with a new invocation UID and `supersedes_action_id+retry_basis`; unknown remains typed/manual and must not auto-redeliver. Define the evidence available for both Claude and Codex, token recovery across each boundary, and tests for crash after intent-before-effect and effect-after-before-outcome on both backends.

4. **[BLOCKER] “Immutable binding columns on `agents`” conflicts with generation replacement and with the held-start registration order.** The existing durable agent row is never deleted and registration advances it in place (`packages/v2-kernel/src/migrations/0005-agents-config-mailbox-rebuild.ts:3-20`; `packages/v2-engine/src/registration.ts:113-162`; `packages/v2-engine/src/sql.ts:11-15`). If the added instance/host/session columns are literally immutable, generation+1 cannot install the new binding; if they are freely mutable, they do not fence reattach. The plan also says host boot registers Leads directly from fleet config (`plan.md:36-43`), while 8a starts the host in held mode before Leads return at 8b (`plan.md:165-173`), so no live PID/start-time/session evidence exists for that registration. **Recommendation:** define binding immutability as generation-scoped: generation 0 may be provisioned with no binding; registration atomically installs a non-null exact binding; same-generation updates cannot change it; a CAS generation advance must replace the entire binding while proving old-session absence. Alternatively use a generation-keyed binding table and update the table-count contract. In 8a, provision addresses only; register/reattach only after the actual Lead session exists and its evidence is captured. Specify exact persisted columns and 0009 rebuild/backfill behavior, including malformed existing online rows.

5. **[BLOCKER] The normative migration specification still makes the unfinished-external blocking row unreachable and has inconsistent canonical-key precedence.** The enumeration domain includes only `lead_inbox carrier='inbox'` and declares `carrier='external'` archive-only (`plan.md:203-210`), yet first-match row 2 says unfinished external rows must drain/block (`plan.md:226-242`); the fixture list again calls external carrier “excluded” (`plan.md:252-254`). An implementation following the domain filter never evaluates row 2 and can silently archive an unfinished external delivery obligation. Separately, a traceable Discord `messages` row receives a `(discord, canonical Discord key)`, while its JSON copy with `flywheelId` is assigned `(legacy-comm,<project>/<flywheelId>)` (`plan.md:212-224`); without an explicit “linked JSON inherits the comm row’s resolved canonical key” rule, the copies do not overlap and post-cutover Discord replay can double-deliver. First-match row 1’s unqualified “unknown provenance” can also consume vendor-only rows before row 13. **Recommendation:** define three disjoint enumerations: canonical unread migration input, unfinished external obligations that must reach zero, and terminal/archive-only rows. Make the external-zero account a mandatory conservation/precondition report rather than an unreachable migration row. Define canonical-key resolution order so a linked JSON copy inherits the comm row’s final key, distinguish failed claimed-Discord provenance from legitimate vendor-only provenance, and define the collision ordinal from immutable snapshot evidence (for example relative path plus stable array occurrence). Add external-nonterminal blocking and Discord-comm-plus-JSON-plus-post-cutover-replay fixtures.

6. **[HIGH] The T1 section still restates the old cutover-only predicate and therefore contradicts the corrected step-9 authority.** Step 9 correctly permits rollback in `{cutover,live}` with zero effect intents (`plan.md:174-185`), and W4 also describes `{cutover,live}→pre` (`plan.md:289-294`), but the normative T1 subsection still requires only `cutover 且零 effect intent` (`plan.md:269-276`). An implementer can reasonably build `rollback-t1` from §4.7 and reintroduce the exact post-8b/pre-first-effect failure Round 3 identified. **Recommendation:** state the predicate once as a named kernel primitive and have §4.2, §4.7, W4, tests, and runbook reference it verbatim: `state IN ('cutover','live') AND effect_intent_count=0 AND rollback_state='clear' → rollback_started`.

7. **[HIGH] The Codex Lead journal is inventoried in step 2 but is not mechanically carried through snapshot/archive and Go/No-Go evidence.** Step 2 says journal DB/WAL/SHM are drained and WAL-safely archived (`plan.md:140-147`), but step 4 snapshots only comm.db and JSON (`plan.md:152-156`), and the research Go/No-Go table has no `listUnfinished()==0` or journal integrity/snapshot assertion (`research.md:165-180`) despite `research.md:94-99` promising one. Test fixtures alone (`plan.md:314-318`) do not make the production checker enforce the condition. **Recommendation:** explicitly include every journal DB in step-3 fd checks, step-4 WAL-safe snapshot/integrity evidence, step-6 archive/fence actions as applicable, and a mandatory pre-start Go/No-Go evidence row (or named subcheck of an existing item) requiring native `listUnfinished()==0` plus separate ambiguous/dead-letter counts. Add a failure fixture showing 8a cannot be authorized when any manifest journal is absent from evidence or has a nonterminal row.

## Verdict

CHANGES REQUESTED — address items above
