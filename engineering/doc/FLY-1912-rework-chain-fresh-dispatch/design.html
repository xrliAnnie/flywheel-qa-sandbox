FLY-1912 · 引擎 rework · 设计稿 · 2026-08-20 · Codex design review 3 轮 APPROVED

返工后交棒撞上"没人跑过"的环节，引擎不再报 500 死循环

一句话：一个 issue 被返工（rework，指 founder 或 operator 把做过的环节打回去重做）之后，工程师 AI 做完 implement 交棒时，引擎要把"验证链"推到下一站 qa；如果这条 run 的 qa 以前从没人跑过，引擎找不到"上一任 QA"可唤醒，就直接抛错、回 HTTP 500，工程师 AI 重试 4 次全败、Bridge 重启后又撞同一个错 —— 纯死锁。本设计让引擎在这种情况下像第一次一样派一个新的 QA，并把"抛错 500"改成"说清原因的 409 + 一次 Lead 告警"，再给失败存根的重放装上刹车。

共同点：都是"有返工史、返工指向 implement、而 qa 从未跑过"的 run。队列里还有 FLY-1847 / FLY-1859 / FLY-1814 三个同类 run 等着交棒，大概率同撞 —— 修复要赶在它们之前合入。

名词：runner = 干活的 AI 工程师会话；Bridge = 调度中枢服务；marker = 交棒失败时写在磁盘上的存根文件，Bridge 重启后会拿它重放一次交棒，保证"做完的活不会丢"。

2. 核心流程：为什么会撞，修完怎么走

验证链 = 返工后必须重新走一遍的环节清单（这里是 implement → qa → founder 审批）

图 1：上方蓝色是原有做法（qa 跑过 → 唤醒上一任 QA），保持不变；中间红色是修复前的死循环；下方绿色是修复后的新分支。

引擎原来只有一条路：验证链下一站必须"唤醒上一任执行者"。这个前提在"qa 从未跑过"时不成立 —— 但这恰恰是一种合法状态（run 还没走到 qa 就被打回 implement 重做）。修复 = 补上缺失的那条路：没有上一任，就按第一次的方式派个新人；验证链本身不断开，只是原地前进一格。

3. 三层防线（issue 要求的三件事，各管一层）

图 2：① 把已知的合法状态修对；② 以后再有没预料到的状态，不再是 500 盲重试；③ 任何未知 500 都不再无限重放。

层修什么防什么
①引擎验证链下一站没有上一任 → 全新派发，链原地前进（commitWorkflowTransitionTx 加一个分支 + 一个事件）这次事故的直接原因
②边界引擎内部其余 8 处"不该发生"的自检失败（CAS = 先比较再写、防并发互踩的检查）改成结构化拒绝 engine_invariant:<名字>，由同一个函数自己接住 → HTTP 409 + 原因码；拒绝记录和 Lead 告警在同一个事务里落盘（要么都在、要么都不在）runner 只拿到 "internal error" 四个字、Lead 不知情
③回放明确的 409 拒绝 → 存根"持有"：每小时慢探一次、不删、不隔离、不重复告警；未知 500 → 指数退避 1m→2m→4m…→1h 封顶，第 3 次告警 Lead 一次Bridge 重启/心跳无限重放同一个错，把会话冻在"运行中"还没人知道

4. 数据与结构：改了哪些账本、怎么改

4.1 引擎侧：零新表、零新状态，只让一张表"原地前进"

表（账本）原有链式做法（qa 跑过）新分支（qa 没跑过）
workflow_rework_request
返工请求		再铸一条新请求，指向 qa不铸（与第一次跑 qa 一样，没有"返工请求"）
workflow_rework_route_revision
返工路线（不可改）		新请求的路线：唤醒上一任 QA不动；原路线仍写 implement（这是刻意保留的痕迹，不是损坏）
workflow_rework_verification_path
验证链当前位置		老链置 completed，新链从 qa 开始老链原地前进：当前位置 implement → qa，状态仍 active
workflow_rework_delivery
投递状态		老投递置 completed保持 wake_delivered；等 qa 过了、到 founder 审批卡时，由现成的收口逻辑一并结清
派发预留给上一任 QA（等它被唤醒）走第一次派发同一段代码：分配新的执行者 id、写 node_dispatched 意图、dispatcher 起一个新 QA

为什么保持投递 open 很重要：系统里有"同一 run 同时只能有一条返工在途"的守卫（rework_already_open）。临时治法把投递提前结清，QA 还没跑完就能再开一条返工；新分支保留这层守卫。

4.2 回放侧：失败存根自带一份小账本

存根文件（marker）里多一个 replay_ledger 字段：模式（退避中 / 持有）、连续失败次数、下次探针时间、告警是否已确认送达。写法是"先写临时文件再原子改名"，同一存根同一时刻只允许一个回放在跑（boot 与心跳不会互踩）。

图 3：回放的四种去向。橙色两种都有界（最坏每小时一次）、都保留证据；"规则 0"保证 Lead 告警一定先送达，才允许任何回放或结清。

其它取舍

  • 不按"响应内容相同 N 次"判定死锁（Codex 第 1 轮否决了我的初版）：Bridge 对所有未处理异常都回同一句 "internal error"，内容相同不能证明是同一个 bug；那样会把 3 次普通抖动判成永久死锁、只能靠重新部署解锁。改成有界退避 + 自动恢复。
  • 把"转成 409"放在引擎转移函数自己的边界，而不是只在交棒接口补一刀：qa→审批卡的交棒走的是另一条接口（决策路由），只修一处会漏。下沉一层后 6 个调用方全部自动受益、调用方代码零改动。
  • 不加任何新开关（flag）、不加新定时器、不加新表。

6. 诚实边界：这个设计做什么、不做什么

做：修引擎这条缺失的分支；把引擎内部 9 处自检失败变成有原因码的 409 并告警 Lead 一次；给存根回放加刹车。有上一任 QA 的返工、qa 不通过的回环、founder 打回、合并冲突返工 —— 这些路径逐字不动。
不做：不改 runner 侧 flywheel-comm complete 的重试与落盘方式；不改 operator 发起返工时"目标必须有历史"的合同（那是对的）；不在回放器里改 run 的状态（回放器管文件，引擎管状态，不越权）；不给 QA 决策失败的存根（qa-result-failed，目前整个仓库没有读者）补读者 —— 这是既有缺口，归 FLY-1898 对账器族，本单如实指出、不假装能重放。
未知 500 的诚实处理：因为响应体证明不了"一定是死锁"，设计选择最坏每小时探一次、告警一次，根因修好后自动恢复 —— 而不是"N 次后永久停手"。代价是日志里每小时多一行；好处是不需要人去删文件或重新部署。

什么时候能看到效果、怎么验

  • 单元测试首次覆盖"返工链下一跳"这段代码（此前 0 条测试走到过它，这也是 bug 能溜进生产的原因）；现有 fixture 只差一步就能复现 FLY-1330。
  • 独立 QA 在 529 隔离房真机复现：模拟"implement 完成 → 不跑 qa 就返工 → 再交棒"，期望 200、新 QA 自动起；再人为制造一次引擎自检失败，期望 409 带原因码、告警恰 1 条、存根保留且每小时慢探。
  • 合入后生产观察：FLY-1847 / FLY-1859 / FLY-1814 到达交棒时零 500、qa 自动起。
