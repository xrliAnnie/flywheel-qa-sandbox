Belle 完整 Lead 席位 — 设计方案

FLY-2034 · 2026-08-24 · 设计节点产出(实施前的方案,不是完工报告)

① 一句话总结

给 Belle 建一个她自己的仓库(belle-workspace),她做的每件事都归档在里面、每周有台账可查;同时把她的席位从"只能聊天的陪伴角色"升级成"能像 Tadashi 他们一样派 AI 工人干活的完整 Lead"——升级本身只是"翻一处配置 + 改一行名册描述",不动 Flywheel 任何机制代码。

名词解释:「Lead」= 一个常驻的 AI 主管,在 Discord 频道里和你对话并管理手下的 AI 工人;「派工」= Lead 把一个任务(Linear issue)交给一个临时 AI 工人(Runner)去完成,产出以 PR(代码仓的变更提案,须你批准才合入)形式交付。

② 核心流程:从"只聊天"到"派工归档"

现在的 Belle 是「companion(陪伴型)」席位:能陪你聊、帮你记,但系统层面禁止她派工人。翻转后,你在 Linear 建一张带 life 标签的任务(比如"生成本周菜单"),Belle 接到后派一个 AI 工人去做,工人把产出(菜单文件 + 台账一行)写进她的仓库并提 PR,你批准后正式归档——从此"她每天做了什么"永远查得到。

名词解释:「Linear」= 我们的任务看板系统;「label(标签)」= 任务上的分类贴纸,系统靠它决定这张任务归哪个 Lead 管。

③ 数据/结构模型:她的仓库长什么样

  • skills — 每个任务的"做法说明书"(菜单怎么排、买菜怎么挑)。说明书的正式存放位置是仓里系统能自动识别的 .claude/skills/ 目录(这样 Belle 和派出去的工人都能直接调用),仓库顶层的 skills 是指向它的入口链接,方便你直接翻看——两处是同一份内容,不会出现两个版本。以后定时任务逐个写成 skill 存这里(本单先立规矩 + 放一个菜单样例)。
  • archive/ — 产出归档:每次产出一个文件(如 2026-08-24-menu.md);archive/weekly/ 每周一份台账,一行记一件"这天做了什么",随手就能搜。
  • MEMORY.md + memory/ — 她的长期记忆:索引一行一条,细节进主题文件(和 Flywheel 全队同款记忆结构)。
  • tasks/(存量) — 她现有的三个任务(备餐/买菜/监控)原样保留,以后随用随迁进 skills/,不推倒重来。

关键决定:仓库不搬家。她现在的工作目录原地变成 git 仓库(远端叫 belle-workspace),目录名和项目名都不动——因为她的记忆和会话都锚在这个路径上,搬家 = 冒记忆断代的风险,不值得。

名词解释:「git 仓库」= 带完整历史记录的文件夹,每次变更都留档可回溯;「远端」= GitHub 上的私有备份与协作副本。

④ 上线步骤:谁做什么

工程侧(1–3)由本单的 AI 工人独立完成,全程不碰 Belle 正在运行的目录和配置。她侧的翻转(4–9)是一份逐字命令清单,安排在一个短维护窗里一口气做完:配置开关(删 companion: true、打开 canSpawnRunners 即允许派工)在临时文件上改好、用真实校验器验过才替换正式文件;同时把她的"身份说明书"里"不派工"那段按升级稿合并掉(先备份、看着 diff 改)——否则会出现"系统给了她权限、她自己的说明书还禁止她用"的自相矛盾。翻完立即重启中枢(Bridge),不等班车——中枢只在启动时读一次配置,拖到半天后的班车会出现"她已升级、中枢还当她是旧角色"的错乱期。每一步都有对应的回滚命令,失败就原路退回。

名词解释:「cutover(切换上线)」= 从旧形态切到新形态的那一步;「Bridge」= Flywheel 的中枢服务;「紧急票」= 你本人授权的一次性立即重启通道(平时部署只走每天两班的定时班车,这次维护窗是它的合法使用场景)。

⑤ 关键取舍与被否掉的路

决定为什么 / 否掉了什么
选原地 git 化,目录不搬否新建 ~/Dev/belle-workspace 再迁移:记忆锚点会断,她的"家"和"工作仓"分裂两地,是我们明令避免的形态。仓名(belle-workspace)与目录名(personal-assistant)不一致是纯认知成本,README 首行写明即可。
选配置翻转 + 一行名册文案,零机制代码逐行核过启动脚本与配置校验:companion 标志是唯一开关,rafiki/reflection 两个"非工程但能派工"的 Lead 就是现成同款。唯一例外:全队规则里有一处名册把 Belle 写死为"不派工的陪伴角色",这行描述必须同步改掉(独立评审抓出的,已折入)。否为 Belle 写任何专属代码路径。
选复用 LEARN 看板 + 现有 life 标签growth 先例:不建新 Linear team。否新建 team/标签(按你的规矩,新标签要先问你点头——这条路我们直接不走,零新标签)。
选私人文件入不入库由你们定工程侧只推"新写的通用骨架";BELLE.md、她的记忆等存量私人内容是否提交,留在清单里由你/Belle 决定。否工人替你决定隐私边界。
选做法说明书放系统识别位置,顶层放入口链接系统只从 .claude/skills/ 识别 skill——把正本放这里,调用零风险;顶层 skills 链接只是给你翻看的入口。否正本放顶层再链接回去:那要先赌"系统识别跟得上链接",不值得。
选工人不做要登录态的浏览器活买菜类任务依赖你本机 Chrome 的登录状态,派出去的工人碰不到也不该碰。工人只做生成/整理/归档;要真开浏览器的环节仍是 Belle 本体的活。

⑥ 诚实边界:这个设计做什么、不做什么

做

  • 建仓 + 立结构(skills/archive/台账/记忆)+ 派工配置 + 逐字上线清单;
  • 上线后真派一个工人生成一周菜单并归档,作为端到端验收。

不做(明确留白)

  • 存量定时任务的 skill 化迁移 — 你定的节奏是"随用随做",本单只放一个菜单样例立规矩;
  • 动她的启动器/身份配置 — 全部进清单,由你们侧执行,工程侧一个字节都不碰;
  • 她的三个 launchd 定时器(日/夜模式等)原样保留在机器上,不入仓(里面有机器路径,仓里只放"做法",触发器留在机器);
  • 合并权仍在你手里 — 工人产出的每个 PR 照旧要你批准才落库,这条全队铁律不因 Belle 而松动。

已知风险(都有对策)

  • 配置文件写坏会把整个项目踢出系统(踩过的坑)→ 派工配置用真实加载器先验;全局配置在临时文件上改、真实校验器全量验过才原子替换,防一处笔误拖垮其他项目;
  • 验收"真派一个工人"的证据按可证伪标准收:要看到 Belle 自己发起派工的记录、工人真调用了菜单 skill、合入提交里真有归档文件——不收"文件长得像"当证据;
  • 翻转后她人设"变味"(管理规则压过生活助理)→ 身份升级稿保留她 persona 全文只做叠加,且上线验证含"真回话 + 记得之前的事";
  • 验收②要等你执行清单后才能跑 → 工程件完成即报,不空等。
