02 · 怎么修

病根和修法

不是有什么东西坏了,是 Belle 从一开始就是按"陪伴型"设计的:她没有仓,所以做过的菜单、买菜结果落不下来;席位上明确写着不能开 Runner;连 Flywheel 给所有 Lead 看的那张名册上都写着"Belle 不开 Runner、不碰代码"。这三样是一整套,只改其中一样会自相矛盾——比如给了她权限但她自己的说明书还写着"你不干这个",她照样不会干。

真正的病根

Belle 的能力边界由三处独立事实共同约束,缺一处就会出现"有权限但不行动"或"行动但产出丢失"的错配:(1) 无版本化工作区,产出没有 durable 落点,archive/weekly 台账无处可写;(2) ~/.flywheel/projects.json 中 belle-lead 为 companion:true / canSpawnRunners:false,Bridge 层面直接拒绝为她起 Runner,且该文件只在 Bridge boot 时读取;(3) 她自己的 identity.md 与全队共用的 cross-dept-channel-rules.md 名册都把她描述成不开 Runner 的 companion,即使配置放开,提示词层面仍会自我禁止。本单只动 (1) 与 (3) 中的名册那一处;(2) 与 identity 合并是 founder 维护窗的显式步骤,已写成逐字清单。

修复原则

把"能不能做"和"知不知道自己能做"分开处理,且都不在实现节点上偷跑 live。实现节点只产出可审计的工程件;所有会改变生产行为的动作一律留给 founder 维护窗,并配对称回滚。判断"清单是否真能执行"不靠读,靠在副本上真跑它的每条命令。

具体改了什么

  • 建 private 仓 xrliAnnie/belle-workspace(main=726c5204):skills 约定 + 样例 meal-menu skill、archive/ 与 archive/weekly 台账约定、MEMORY 结构、以及 generic 派工所需的 life-executor + ic-roster + adoption。
  • 写一份 11 节的接入清单(onboarding.md):admission 硬门、逐路径归档矩阵(禁 git add -A)、identity 单独 commit、projects.json 同目录 0600 原子替换 + 三道硬门、重启前 live 终验、对称回滚,外加一张"会过期的结论"表。
  • 把 Flywheel 名册里 Belle 从 companion 改成 life dept Lead,companion 注记收窄为只剩 Mufasa;并用行为测试钉死这两句,改回旧文案即变红。
