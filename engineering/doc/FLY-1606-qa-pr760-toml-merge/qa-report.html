Codex 全舰队趴窝 — 怎么修的 · 怎么测的

独立 QA 报告 结论:PASS 合并仍需你拍板 2026-08-02

一句话总结

8 月 1 日 Codex 桌面端自己往它的全局配置文件里写了一张表,而我们注入 GitHub 令牌也正好要写同一张表。配置文件的格式规定同名表不能出现两次,于是我们的代码宁可停下也不写坏配置 —— 结果所有 Codex 干活的机器人都开不了工(1602/1603/1604/1605 四个单子同时趴)。

修法是:不再"另起一张表",而是认出已有的那张表,把令牌折进去,Codex 自己写的东西原样不动。

我是独立验证方(不是写这段代码的人)。我把所有验证自己重跑了一遍,不采信实现方的自测记录。结论:通过。

出了什么事

每个 Codex 机器人开工前,系统要给它准备一份专属配置,把 GitHub 令牌安全地传进去(不走命令行,避免被别的进程看见)。做法是:读一份全局配置当底子,再把令牌加进去。

令牌要写进的位置,叫 [shell_environment_policy.set]。8 月 1 日之前,全局配置里没有这张表,所以我们直接追加一张新的,没问题。

8 月 1 日,Codex 桌面端自己往全局配置里写了这张表(它用来存浏览器后端、Node 相关的几个设置)。于是我们再追加一张,文件里就会出现两张同名表 —— 配置格式明令禁止,Codex 读到会直接拒绝加载。

写这段代码的人当初留了一道守卫:发现这张表已存在就停下来报错,绝不写出坏配置。所以真实结果不是"配置坏了",而是机器人根本起不来 —— 四个单子实证全趴。

为什么这是好事(虽然它让舰队停了)如果当初没这道守卫,我们会安静地写出一份坏配置,Codex 起不来的原因会藏得很深,排查要多花几小时。守卫让故障立刻、明确地暴露出来。

三个关键问题

① 那道守卫当初是对的吗? 是对的。在它写下的时候,全局配置确实没有这张表,而且当时没有能力做"表内合并"。守卫的判断是:遇到没见过的形状,宁可停也不写坏。这在当时是正确的保守选择。

② 前提是怎么过期的? 守卫依赖一个前提 —— "全局配置不会声明这张表"。这个前提不由我们掌握:那份文件是 Codex 桌面端的地盘,它随时可能改。8 月 1 日它就改了。(我做 QA 期间它又改写了一次,见"还剩什么风险")

③ 现在怎么合并? 新做法是先真正读懂整份配置(用标准解析器,而不是靠文本匹配猜),据此判断能不能安全合并:

  • 已有那张表 → 把令牌那一行插进这张表里,Codex 自己的键一个不动;
  • 没有那张表 → 和以前完全一样,追加一张新表;
  • 形状怪异、或它自己已经设了同名令牌 → 照旧停下来报错,绝不覆盖别人的东西。

写出来之前还会再解析一遍成品自检:令牌确实在、Codex 原有的键一个没变、数量对得上 —— 任何一条不满足就拒绝写。

代码改动要点

改动说明
引入标准 TOML 解析器新增一个小依赖(smol-toml),用"真读懂"代替原来的正则文本匹配。原来的匹配会误判(把别的表下的同名键当成冲突),也会漏判(带引号的表头认不出来)。
外科式插入只在那一行表头之后插入令牌行,文件其余部分一个字节不动。
令牌永不进解析器自检时用一个假占位符跑解析,真令牌最后才落进去 —— 因为解析器报错会把出错那一行原文抄进错误信息里,那一行可能正是令牌。
错误信息脱敏所有失败信息都不带令牌、不带配置原文、不带行号。
可反复执行重复准备同一个机器人,结果逐字一致;不带令牌再跑一次,能把文件逐字还原成原样(轮换令牌时不留旧的)。

改动集中在一个文件(codex-home.ts),外加测试文件与依赖声明。

还剩什么风险

这三条都不阻挡合并,但值得记下来。

a) 这个修法是"认形状"的,不是万能的

现在认的是 Codex 当前写法的那个形状。如果将来它换一种写法,我们的代码会再次停下来报错 —— 好消息是它仍然不会写坏配置、报错也清楚,但机器人还是会趴,需要再修一次。彻底的做法是"整份配置重新生成",工程量更大。这是有意识的保守取舍。

这条风险在我做 QA 期间当场应验了一次就在我验证的这几个小时里,Codex 桌面端又把那份全局配置重写了一遍(文件被整体替换,内容指纹变了)。这次它没改我们关心的那张表,所以无害。但它实锤了这份文件是"活的" —— 有个我们管不着的程序随时会改它。我已把当前版本存档,以后再变可以直接比对。
(顺带澄清:那次改写不是我造成的 —— 我的代码对这个文件只读不写;你的文件里没有出现任何令牌。)

b) 新依赖进了关键路径

现在每次准备机器人,都要靠这个新的解析器成功读懂你的全局配置。万一它和 Codex 自己的解析器对某种写法理解不一致,又会全舰队趴。今天这份 911 行的真实配置,实测能正常读懂。

c) 一个边角行为变了

令牌传空字符串时,以前是"安静地不注入",现在是"直接报错"。我查过:实际调用它的地方本来就先拒绝空字符串,所以生产行为没有变化。

合并部署之后,建议这样验

  1. 重派 1602 和 1603(就是这次趴掉的两个单子)。这是最直接的行为验收 —— 机器人真的开工了,就说明修复在真实链路上生效。
  2. 看第一个机器人的准备日志:不该再出现 "already declares the shell_environment_policy namespace" 这句话。
  3. 抽查一个机器人的专属配置:那张表里应该同时有我们的令牌和 Codex 自己的 3 个键,而且表头只有一个。
  4. 留意 a) 那条风险:如果哪天 Codex 又改了写法,症状会是"机器人集体起不来 + 报错说形状没法合并"。看到这个症状就知道是同一类问题,直接找我们。

前三条都是看现象,不需要动手做实验。

这个改动我验过了,可以合并 —— 但合并这一步按规矩仍然是你拍板。

  • 问题的根因清楚,修法对症,而且保留了"宁可停也不写坏"的安全性格。

  • 最终确认仍建议合并后重派 1602/1603 看一眼 —— 那是最直接的现场验收。
