FLY-2102 · 九个启动期开关的固化删除

Issue: FLY-2102 · 日期: 2026-08-27 · 设计文档: engineering/doc/FLY-2102-flag-b2-startup-freeze/(exploration / research / plan)

一句话总结

按你 8-27 的裁定,把 9 个只在启动时读一次的 env 开关连根删掉:6 个把默认值写死进代码、2 个整段删除(publish broker 连代码带 CI 一起删)、1 个语音测试用的挪进豁免账;实测生产环境这 9 个开关全都没设置过,所以这次改动对线上行为是零变化 —— 删掉的只是「未来想拧」的旋钮,而这正是裁定要的效果。

env flag = 写在环境变量文件(.env)里的功能开关。「启动时读一次」意味着改了值也要重启进程才生效 —— 这类开关既不能实时拧,又常年没人拧,就成了纯负债。

核心流程:9 个开关的三种去向

三条路的共同点:registry(登记册)里这 9 个名字全部注销,今后 .env 里再出现旧名字,校验器会直接报「已退役,删这行」,不会静默生效。

删得最深的一处:flag store 的 env 逃生旁路

这是 9 个里唯一牵动数据库逻辑的:FLYWHEEL_FLAG_STORE=0 不只是个开关,它背后有一台三层「逃生+恢复」机器。裁定 store 常开后,这台机器整体失去存在理由:

  • 删:旁路入口、双模式运行时、管理接口的「旁路中禁改」分支、数据库里的栅栏标记读写、下次启动的恢复重播逻辑。
  • 留:数据库表结构本身(留着无害,删表反而要迁移);历史变更日志(append-only 史料,不许动)。
  • 安全性核验:生产 .env 从未设过这个变量 ⇒ 旁路在生产从未走过,不存在「删掉恢复逻辑把谁卡在半路」的窗口。

数据/结构模型:四本账怎么动

Flywheel 的 flag 治理有四本账:登记册(registry,所有 flag 的唯一出生地)、墓碑账(tombstone,退役名字的黑名单)、豁免账(exemptions,「不算 flag 但允许存在」的名单)、以及两本「只许减不许增」的冻结上限账本。

需要你知道的一处账本修订:豁免账的上限账本(LEGACY_FLAG_EXEMPTION_BASELINE)设计上是冻结的 —— 新名字进不去。voice 这条要进豁免账,就必须给上限账本 +1。这不是开后门:是把一个已登记的名字从登记册挪到豁免账(总治理面 −9 +1),授权来源就是本单裁定,PR 里会显式声明。

三个关键取舍(以及被拒掉的方案)

① broker 的 token 擦除随 broker 一起删

publish broker 挂载时有个与开关无关的副作用:无条件从 Bridge 进程环境里删掉两个发布 token(防止子进程继承)。broker 删了,这个擦除也就没了。被拒方案:留 5 行「孤儿擦除」代码 —— 拒因:它保护的注入路径(为 broker 往 Bridge 环境放 token)随 broker 一起消失了,而且违背「只删不加」;token 的正身一直在 GitHub Actions secrets 和校验服务端,实测 Bridge 机器环境里也从来没有。代价与守卫写在诚实边界 ③。

② lead_lease_bypass 只删「生产者」,不删「史料读者」

旁路被用过会在耐久数据库里留审计行。删除范围只到「不再可能产生新的旁路」;把历史审计行渲染成告警的那条链保留 —— append-only(只追加不改写)的史料不能因为生产者死了就变不可读。被拒方案:连告警种类一起删 —— 拒因:历史行会变成没人认识的孤儿数据。

③ voice 开关不删读点,走豁免

它本来就不是运行时功能开关,是测试治具的接缝(QA seam):FLY-1353 无头语音端到端测试还在每次运行时置位它。被拒方案:连读点删掉 —— 拒因:治具还活着,删了测试就瞎了;裁定原文也写明「治具仍在用 → 进豁免账」。守卫不降级:带 loopback 白名单(连生产 Bridge 直接拒启)+ 持久 .env 出现即报错。

④(顺带)验收判据的一个词面冲突,先量了再裁

验收写「rg 九个 env 名零命中」,但墓碑账和豁免账机制上必须保留名字才能拦住旧配置回流。字面零命中 vs 退役机制是词面冲突不是实质冲突 —— 处理:零命中判据精确化为「排除墓碑账、豁免账、voice 治具、断言测试自身、历史文档后全仓零命中」,并做成带逐条自检的常驻守卫测试,不是跑一次就完的人肉检查。

验收与守卫

  • 反旋钮断言(每条删除路一条):全部是「把旧值真实设回去,断言行为不再变」—— 例:设 FLYWHEEL_LEAD_LEASE_BYPASS=1 仍拒绝写入;设 FLYWHEEL_CMUX_VIEW_HELPER=0 仍产出 helper 命令。不是「grep 不到字符串」这种弱检查。
  • 常驻残留守卫:新增 fly2102 残留测试(沿用 fly1674 模式):9 个名字全仓扫描 + 精确豁免清单 + 每条豁免的存活自检(防死豁免悄悄放宽)。
  • 发布路径无损:payload-activation 的 preflight 本地 dry-run 一次;CI 删的只有 broker 结构测试那一步。
  • 启动日志:隔离环境起一次 Bridge,确认无 [publish-broker]、无 flag-store 旁路输出。
  • 全仓门:lint + 全包构建 + 全部包测试 + 触及的 shell 测试。

诚实边界:这个设计不做什么、代价是什么

  1. 不碰另外 13 个运行时读的 flag(B1 批)、不碰 config.yaml(C 批)、不新增任何旋钮。
  2. 「未来想关」从此要改代码走 PR。这 9 个开关删了就没有 env 级后悔药 —— 这正是裁定的本意,但值得写明:万一哪天想暂停 cmux 收敛/node 面板,路径是改代码,不是改配置。
  3. token 擦除消失后的残余风险:如果将来有人违规把 FW 发布 token 放进 Bridge 机器环境,不再有兜底擦除,子进程可能继承。守卫 = runbook 退役横幅写死红线「FW token 永不进 Bridge env」+ 实测当前环境本来就没有。这是一个「守卫从代码降级为文字」的点,如实标出。
  4. 最大实现期不确定性:cmux 的 1.1 万行测试套件全局跑在「node 层关闭」态,写死开以后受影响的节数只有跑起来才知道。计划把它排为第一步,若重工量超预算(约 15 节)先报量再继续,不静默扩 scope。
  5. 老库残留:生产主库已实测确认没有 bypass 栅栏标记(2026-08-27 只读核验),PR 验收会再查一次作为部署前置;非生产的隔离测试库不逐一保证 —— 对它们的行为定义是「数据库里的 store 行原样即权威」,不迁移、不清理。
  6. 本页只是设计:代码一行未改;实现、QA、ship 都在后续节点。
