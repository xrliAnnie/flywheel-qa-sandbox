## What's Good (Keep)

- R3 修订现在同时定义成功、估计失败和 QA 门槛；不再将有限缓冲等同于保证不丢句首，也不再把网络安静等同于房间已经安静。
- 新 T5c 所针对的问题有实证。`F2866:research-v3.md:49–52` 的四次追加虚构汇报和一次无声，与原始记录一致：`evidence/v3/runs/fly2866-v3-run/{spruce-3,sol-3}/session.jsonl:18`、`fly2866-v3-run-b/{spruce-1,vale-1}/session.jsonl:18` 各有长篇虚构追加；`fly2866-v3-run/vale-3/session.jsonl:16–21` 则是 appendSpeech 成功后约 60 s 仍无声。
- 在完整转写可用且按字到达的离线模型中，四个既有越界样本都会在规范化第 56 字触发规则：期望为 49 字，再多 7 字。这个正例值得保留为固定夹具。录音器没有采集数据通道消息和逐条 transcript delta（`F2866:evidence/v3/record-v3-voice.mjs:135–139,161`），所以它们尚不能证明实时检测时间或 ≤1 s 停声。
- 只给绑定朗读加守卫、失败回执沿用现有 frontend 映射、限制重试次数和保留 thread 文字，范围合理。无需扩展为自由对话的事实审查器。

## Issues & Recommendations

1. **HIGH — [Scope: T5c] 轻微改字后追加虚构内容可同时绕过两条越界条件。**

   **问题与证据：** `plan.md:169–170` 必须先满足全文等价／期望字符全部按序出现，才按后续新增 >6 字截断；否则仅在总长度超过 `1.5 × expected + 12` 时处理。FLY-2866 同时发现了常见的 1–6 字改写（`F2866:research-v3.md:52`），它与虚构追加可以出现在同一块中。

   **已执行的离线反例：** 期望为“目前，需求文档已经整理完成，测试环境准备就绪，还有接口方案等待你确认，我会按顺序说明。”；实际只把“目前”改成“现在”，然后追加“另外生产环境已经部署完成，可以对外宣布上线。”。按现有规范化所涉及的标点／全半角规则，期望 **38 字**、实际 **58 字**。期望首部“目前”没有出现，coverage 始终为假；58 又没有超过 **69** 字上限。逐字执行计划规则，**从头到尾不触发越界**，虽然已经增加了 20 字虚构上线陈述。现有等价判定最终会失败，但那不等于 T5c 已 cut、审计并阻止镜像发布；`V:codex/CodexVoiceBackend.ts:455–468,505–546` 的现有路径仍把 final 原文交给持久化／发布。

   **为什么重要：** 这不要求辨别事实真伪；新增内容就在已知朗读文本之外。它属于 T5c 的任务，并会漏过 QA-7“所有自编越界都被检测”的要求。仅测“原句完全不变 + 长尾”不足以覆盖实际模型行为。

   **建议：** 对允许的小幅改写与超出原文的追加统一计量，不能让一次替换把检测永久切换到宽松的总长度阈值。可以用有界文本对齐或更保守的额外字符预算，保持明确的 1–6 字容差；加入上述“2 字替换 + 20 字追加”固定用例，并对最终全文再次检查后才持久化／镜像。

   同时把检测输入补成可执行契约：从 admission/send 起暂存增量，绑定后纳入 created 之前的前缀；明确双路采用整轮单一来源还是可证明的去重。`C156:codex-api/src/endpoint/realtime_websocket/protocol_frameless_bidi.rs:48–55` 只把 item.text 转成 delta，没有共同的 turn/chunk 标识可直接逐条配对；`plan.md:86` 目前还会丢弃数据通道 output_transcript.added，与 `:168` 的使用不一致。测试需覆盖早于 created 的增量、两路重复／不同分块、缺增量但 final 完整的情况，避免完整输入的正例在实际通知路径中失效。

2. **HIGH — [Scope: T5c] “丢弃本回合”没有独立的有界收尾；turn.done 也不能单独充当媒体排空屏障。**

   **问题与证据：** `plan.md:171–172` 检测后立即失败结算，却只在同 id turn.done 到达时退出静音。如果该事件缺失，连接仍正常且一直有 RTP，T2 的断线规则不会触发（`:87`）；T5 的 WaitGap 期限也不适用于这个新状态。原 30 s 朗读定时器不能隐式承担此职责：当前 speaker 在 settle 时就清 timer 和 pending（`V:codex/CodexProofSpeaker.ts:383–388`）。结果是本次朗读已经返回 unconfirmed，而后续正常回答可能一直被消音。

   反方向也未定义：若 turn.done 先到、旧音频 RTP 因抖动稍后到，按正文立刻恢复正常播放会重新漏出已判越界的尾音。计划本身已承认音频和通知不同步（`:121`），而 `onDownlink({payload, voiced, rms})` 并没有 turn id（`:85`），不能仅凭 done 给迟到音频逐包定归属。

   **为什么重要：** 守卫可能把一次内容错误升级成整场永久无声，也可能在报告“已截断”后继续播放同一段虚构内容。它必须有独立于朗读 Promise 的状态生命周期。

   **建议：** 明确 overrun 丢弃状态的拥有者、期限、与 T5 mute／新用户输入的优先级，以及换代／关闭时的清理。same-id done 可作为控制面证据，恢复播放还需明确媒体尾部的处理；无法确认时可复用 T7 的关闭屏障结束／换代，不能无期限等，也不能直接放过旧尾包。已判 overrun 的转写处理结果应保留到对应 final 通知处理完，防止 receipt 已结算后迟到的 app-server final 走回普通镜像路径。补 done 缺失、done 早于尾部 RTP、done 后迟到 final、用户插话／换代与 overrun 同时发生的测试。

3. **HIGH — [Scope: T5c] 没有绑定事件不等于无声，自动重试会重复已经播出的朗读。**

   **问题与证据：** `plan.md:173` 将“30 s 内无可绑定回合”直接判作 speech_silent 并重试；但 `:159` 原本将它定义为 speech_binding_unavailable。数据通道事件与 RTP 是独立观察，`:86,313` 也明确允许事件缺失。

   **允许的具体时序：** 第一次 appendSpeech 已被播放器消费 100 个有声包，即 **2 s** 音频，随后安静；其 assistant created 缺失。到 30 s 时，T5c 仍会走“无声重试”。此时 audible 已假超过 600 ms，没有已知 open assistant，也没有 pending user，重新准入并不能阻止同一句再念一次。若第一次的 created 在重试发送后才迟到，还可能被错绑为第二次。这个反例不需要网络掉线或其他用户抢占。

   另外，摘要说“消费过的包”，磁盘 `:173` 写的是“推出过的包”，而 T5b `:157–158` 已改用消费口径；done 到达时尚在排队的音频也不能被直接判为无声。

   **为什么重要：** 守卫把“关联不明”错误地改成“确定未播”，丢掉了 R3 刚收紧的诚实失败边界。次数限制只能把重复限制为一次，不能证明重试安全。

   **建议：** 分开“已确认无声”与“绑定／完成状态未知”。从发送开始记录实际消费和待消费音频；已经出声或无法确认旧尝试终止时，沿用 binding_unavailable 等结果，不自动按 silent 重试。只有零有声消费、无有声积压且旧尝试已明确结束／隔离时，才执行一次重新准入的重试；明确迟到事件不能结算给新尝试。统一 pushed/consumed 术语，并列出已播但 created 缺失、done 先于队列消费、第一次事件在重试后迟到、确认零声后重试成功／再次零声的测试。

4. **MEDIUM — [Scope: T5c] audioAfterDetectMs 的名称与正文定义测的是不同时间段，QA-7 目前无法一致判定。**

   **问题与证据：** `plan.md:172` 记录 detectedAtMs/audioAfterDetectMs；`:174` 却把后者定义为“检测到越界时，该回合在期望文本之后已经播出的时长”，即检测之前的越界暴露。用户本轮摘要使用的是检测之后停止播放的 ≤1.0 s 指标，`:299` 又只引用字段名，未明确起止点。

   **为什么重要：** “检测后立即停”可以得 0 ms，同时检测前已播数秒虚构汇报；这两项不能互相替代。现有能量包和 turn 时间也不能自动定位“期望文本最后一个字”的音频边界。

   **建议：** 明确区分两项：检测时间到最后一个越界声音可听时间的停止延迟，以及虚构内容首次可听到最终停止的总暴露时长。给每项写清起止点、时钟及采集方式；涉及词边界的值用 QA 录音人工／离线标注，不能从字符数或 turn.done 伪造对齐。统一正文、证据字段和 QA-7 的 ≤1.0 s 究竟约束哪项，并补“转写明显迟到但 cut 很快”的验证样例。
