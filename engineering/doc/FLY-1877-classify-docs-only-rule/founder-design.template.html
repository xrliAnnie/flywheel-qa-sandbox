FLY-1877 · CI 简化:一条规则替换整套历史机制

设计阶段净删除 工程 Runner 产出 · 依据你 08-18 的直令「就把这个东西简单化,不要把东西复杂化」

1 · 一句话总结

把「docs PR 要不要跳过重测试」的判定,从一套要翻查 CI 历史记录的机制(六步),换成一条不看历史的规则:

整个 PR 的全部改动只碰文档目录 → 什么重活都不跑(约 3 分钟出绿)
其余任何情况(包括判不出)→ 全跑(约 30 分钟,和现在一样)

PR = 一次待合入的代码/文档提交包;CI = 每个 PR 自动跑的检查流水线。这单是简化单,不是省钱单:钱上净省约 $6/月,真正的收益是删掉一整套会出毛病的机制(见 §3)。

2 · 新规则怎么判

每次 PR 推送,CI 里有个叫 classify(分类器,一个几十行的小脚本)的步骤先跑。它只做一件事:找到这个 PR 和主干代码的分叉点(git 术语叫 merge-base,即两条开发线最后一个共同版本),看从分叉点到 PR 最新提交之间,改过的每一个文件是不是都落在文档白名单里。

所有「判不出」的情况(输入不合法、分叉点找不到或不唯一、改动清单读不出来)一律走全跑——这个「拿不准就全跑」的原则叫 fail-closed(宁可多跑不可漏跑),和现在一样,一条不放松。

3 · 删掉了什么(净删除)

旧机制(FLY-1861 上周落地)要先去 GitHub 翻这个 PR 的 CI 历史,找到「最近一次跑绿的记录」,再做四道校验,才敢对比文件。整套全部删除,脚本从 145 行缩到约 70 行:

随它一起消失的问题(这才是本单真正买到的东西):

  • 不再依赖 CI 历史 —— 旧机制在「新提交把旧 CI 顶掉」时会退化成全跑(我们的流水线恰恰经常这样);新规则不看历史,不存在退化。
  • 「历史查不全」「哪次算最新」「重跑后顺序乱了」「主干悄悄前进了」这一族问题整体蒸发——不是修好了,是没有了。
  • 不再调用 GitHub 查询接口(旧机制最多翻 12 页记录)——省下的接口额度和排查成本一并归零。
  • 后来的维护者不用再学那套六步机制,也不用再重演 08-18 晚上那轮诊断。

4 · 判定明细(结构模型)

文档白名单(沿用现行,一字未改)

维度内容
目录前缀(四个)doc/ · product/doc/ · engineering/doc/ · content/doc/
文件后缀(13 种).md .markdown .mmd .html .htm .svg .png .jpg .jpeg .gif .webp .avif .pdf
永远算「非文档」机器要读的文件:doc/VERSION(无后缀)、doc/**/*.mjs(脚本)——碰了就全跑;改名、软链接、子仓库指针也一律全跑

每个判不出的分支都有名字(排查时一眼见因)

诊断名什么情况结果
invalid_input输入的版本号格式不对(比如主干直推场景)全跑
head_commit_missing / base_commit_missing对应版本在本地仓库里找不到全跑
merge_base_unresolvable找不到分叉点全跑
merge_base_ambiguous分叉点不唯一(两条线互相合并过会出现;任选一个可能漏看代码改动——设计评审抓出的真漏洞,已堵上)全跑
diff_not_inert任何一个文件出了白名单全跑
(无)全部改动都在白名单内跳过重活

跳过 ≠ 裸奔:Quick Gate(编译 + 类型检查 + 代码规范 + 一批守卫测试)任何情况下都全量跑,不受这个开关影响。

5 · 关键取舍与被否方案

方案结论为什么
两套机制并存(历史 + 新规则)你已否复杂度翻倍,和「简单化」直令相反;删旧机制正是这个决定的直接结果
更聪明的「按改动猜要跑哪些测试」明令禁止猜错就是漏测;「不猜耦合、不做分析」写进了规则本身
一条不看历史的规则(本方案)采纳判定只依赖 PR 自己,结果可复现、可解释、不会被历史状态坑

新旧规则判法不同的地方(全部是有意为之)

  • 纯文档 PR 首次推送/主干已前进/上次 CI 被顶掉 —— 旧机制全跑,新规则跳过(这就是跳过轮数从 64 涨到 101 的来源)。安全底:文档合入不带任何可执行内容;主干自己的改动由主干自己的 CI 跑。
  • PR 里先改过代码、后来全是文档 —— 新规则看累计改动,含代码就全跑(比旧机制更保守的一侧)。

6 · 诚实边界

这个设计做什么

  • 重写那个分类脚本(145 → 约 70 行)+ 换掉整套测试向量(两侧都测,含「故意造个坏的看它响不响」的阳性对照);
  • 顺手清掉三处会误导后来人的残留:CI 配置里描述旧机制的注释、共享测试数据里没人再用的一列、脚本里已无用的三个环境变量。

这个设计不做什么

  • 不碰 CI 的任务图、依赖关系、汇总门 —— 三处守卫测试零改动(这是你在 FLY-1861 已拍过的门,不需要重新拍);
  • 不碰合入/发布(ship)那一侧的任何逻辑;
  • 不加任何开关或配置项 —— 规则无条件生效,拿不准就全跑。

要诚实说的两点

  • 钱:净省约 $6/月,不是 $59。旧机制本来就在跳一部分(≈$53/月),新规则跳得更多(≈$59/月),差额才是增量。写这么细是防止日后有人按「才 $6」判定不值、想把历史机制加回来 —— 价值在删机制,不在省钱。
  • 一个无害残留:分类步骤保留一个已用不上的只读权限(actions: read),因为守卫测试把它钉死了,收窄它就得改守卫 —— 超出本单授权,留给未来某次合法守卫修订顺手做。
