# Design Review — plan.md (FLY-1655) (Round 2)

Date: 2026-08-08
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 2 resolves the intent-level concerns from Round 1 and is substantially closer: the authorization proof is narrow, post-materialization recovery now creates a new founder interaction, failure classes are separated, and deployment truth is closed through FLY-270. Source verification still found two implementation-blocking model mismatches in E1b and F2, plus several smaller contracts that need to be made explicit before this production self-hosting path is safe to build.

## What's Good (Keep)

- Keep A1's full-tuple, fail-closed reconciliation shape, separate boot entry point, exact failed-condition diagnostics, and commit-scoped audit event. This directly addresses the Round 1 authorization-weakening concern.
- Keep the decision not to change `recordWorkflowShipTargetBindingTx.matches()`. The plan now respects the `approve_question_id` primary-key model.
- Keep the conceptual split between pre-materialization carrier rebind and post-materialization **new-card** recovery. Never transferring an existing founder card is the correct founder-only-authority boundary.
- Keep permanent lifetime propagation into the derived QA claim, the complete issuance/migration inventory, and explicit revocation hooks. These are necessary to make I6 an end-to-end invariant rather than a credential-only exception.
- Keep C2's deterministic/infrastructure/output lanes and the “StateStore terminal/hold first, marker move second” ordering.
- Keep D1's use of the conflict-free observation projection and D2's durable death observation before holding.
- Keep C4 at all snapshot construction/publication boundaries, E2's established discriminated single-reason response, and run events as E4's idempotency receipts.
- Keep B2's narrow correlation and dedupe, B3 in the same issue, G's use of the existing updater/restart chain, and the revised layered sequence. No new flags, RESERVED changes, workflow_v2 revival, or founder-authority bypass are introduced.

## Issues & Recommendations

1. **E1b cannot create the proposed `attempt+1` holder through `createWorkflowGateHolderTx` with the current ledger schema.** `createWorkflowGateHolderTx` recomputes and inserts every gate-evidence row (`StateStore.ts:30087-30230`), but `workflow_gate_holder_evidence.claim_id` is globally `UNIQUE` and the table has no-update/no-delete triggers (`StateStore.ts:15449-15480`). A reissue over the same head/prerequisite claims will therefore fail on duplicate `claim_id`. It also creates no `workflow_run_node` row for the new gate attempt; founder transition loads the exact `(run,node,attempt)` row and returns `node_attempt_not_current` when it is absent (`StateStore.ts:27617-27657`). Choose and specify one coherent identity model. The smaller option is to treat reissue as rotation of the **transport identity** on the same logical holder/attempt: exact-CAS the holder from the old qid/card/stage to a newly derived qid, preserve its immutable evidence, supersede the old ship-target row, and audit the complete before/after tuple. If reissue must be a true gate attempt, then create/retire the corresponding `workflow_run_node` attempts and explicitly redesign how evidence is safely re-attested or referenced without violating claim single-use. Do not claim reuse of the existing creation primitive until this is resolved.

2. **E1b still describes an impossible cross-database transaction and omits the carrier-state handoff.** `workflow_gate_holder` and ship-target mutations live in teamlead.db, while `retireShipGate` opens comm.db; they cannot commit atomically. `retireShipGate` also intentionally updates only unanswered, non-terminal questions and returns false when a response child already exists (`flywheel-comm/src/db.ts:1095-1120`), yet consumed questions are an explicit E1b input. Define a durable saga: atomically record the reissue intent, invalidate old teamlead authority, rotate/detach the old live carrier session, bind the candidate session, and establish the new qid; after that commit, converge old-question retirement and new-card materialization with retryable durable stages. A false retire result must be classified as already answered/terminal, missing, or a real failure—not reported as “retired.” The authoritative old binding must stay superseded in every case, so a founder response racing onto the old card cannot regain head authority. The idempotency event should distinguish `accepted/intent_committed` from `externals_converged`; a replay must resume unfinished comm.db/card work rather than returning a false completed result. Add crash tests after each cross-DB boundary and tests that exactly one carrier session owns the new qid.

3. **F2's `expires_at=NULL` representation is incompatible with three current contracts.** `workflow_submission_credential.expires_at` is `TEXT NOT NULL` (`StateStore.ts:15909-15932`), its row interface and reader return `string` (`:26923-26955`, interface near `:36747`), and both decision routes pass that string as `claimExpiresAt` (`workflow-decision-routes.ts:449,560`). The submission method validates it as a finite timestamp and includes it in the replay digest (`StateStore.ts:26977-27008`). It also copies the value into `workflow_decision_capability.expires_at`, which is independently `NOT NULL` (`:15640-15660`, insert at `:27120-27137`). The plan's listed `ADD COLUMN permanent` migration does not relax any of these constraints. Prefer the smaller representation: retain the credential's original non-null deadline as audit data, have `permanent=1` bypass it, pass an explicit lifetime union such as `{kind:'permanent'}` into submission, mint only the derived claim with `expires_at=NULL, permanent=1`, and keep the same-transaction internal capability bounded/non-null. Include the normalized lifetime in the replay digest. If nullable credential expiry is required instead, specify the SQLite table rebuild, nullable reader/API types, capability expiry policy, and compatibility for every old caller.

4. **The F2 replay acceptance criterion is currently backwards.** The plan says “已消费 replay → 全拒,” but the method deliberately resolves an exact consumed replay before expiry/revocation so response-loss recovery survives Bridge restarts (`StateStore.ts:26971-26975,27025-27043`). Removing that behavior would regress a durable receipt guarantee. Test three distinct cases: an exact replay with the same `client_request_id` and canonical digest returns the prior claim with `idempotentReplay=true`; reuse with a changed request id or payload returns `replay_payload_mismatch`; and an **unconsumed** credential revoked by canceled/terminal/reworked/dead/replaced state returns `credential_revoked`. Revocation should not erase the receipt semantics of a decision already committed.

5. **A1 still needs an explicit carrier lifecycle condition, and its boot status contract contradicts itself.** Condition 6 binds execution/qid/head but does not require a valid carrier status. A terminal session can retain those fields, so the repair proof should require the exact lifecycle states in which the gate can legitimately be awaiting or holding approval—normally `awaiting_review` or `approved_to_ship`—and test terminal/dead states negatively. The boot section says conditions 1–5 are unchanged, including `run.status='active'`, but then sweeps runs in `('active','held')`; every held row necessarily fails condition 1 and may create misleading aggregate alerts. Either sweep only active runs, or define a separate held-run materialization rule while ensuring `/head-authority` still refuses authority until resume. Also rename the A fixture's “摘掉 A4” reference to the actual boot-reconcile item.

6. **C2 leaves `missing_output` outside I3's visibility guarantee.** Keeping it retryable is correct, but “unchanged” can still mean an indefinitely retained marker and active workflow with no deduped signal if output never becomes visible. Give this lane durable backoff/age bookkeeping and one alert after a generous threshold while retaining the marker and continuing retries; do not apply the deterministic strike/quarantine policy. This preserves eventual output arrival while satisfying the invariant that no completion failure remains silently active forever.

7. **D1 must separate external no-code observation from the StateStore CAS.** The merged projection can be proved wholly inside StateStore, but recomputing a no-code baseline/current repository digest requires filesystem/git observation. `proveDeliveredWithoutReceipt(runId,nodeId)` has no input carrying that observation, and holding a SQLite transaction open across repository I/O would enlarge a hot lock and still leave an unclear freshness boundary. Compute the no-code candidate outside the transaction using the existing authority path, then pass its baseline/current digests, repository identity, and binding generation into the StateStore method; inside the transaction revalidate the current run/node/attempt/binding and compare the supplied proof before holding. Add a mutation test where the binding/head changes between observation and CAS.

8. **G must define build identity and ancestry in the safe direction.** Runtime `git rev-parse HEAD` proves the checkout at Bridge startup, not necessarily the commit from which a prebuilt `dist` artifact was produced. Prefer a build-time embedded SHA for built deployments, with runtime git identity used only for an explicitly source-run mode and `unknown` for unprovable packages. If newer running code may satisfy an older intended deploy, the only safe ancestry test is `git merge-base --is-ancestor <intended> <reported-build>`—the intended commit must be an ancestor of the running build. Never accept a reported build merely because it is an ancestor of the intended commit; that is exactly the stale-Bridge condition this fix is meant to prevent. Add tests for equal, running-descendant, stale-running-ancestor, divergent, malformed, and `unknown` identities before `restart-services.sh:1989-1991` writes the receipt.
