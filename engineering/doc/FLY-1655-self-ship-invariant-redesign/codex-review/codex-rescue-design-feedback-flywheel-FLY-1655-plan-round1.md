# Design Review — plan.md (FLY-1655) (Round 1)

Date: 2026-08-08
Author: Codex
Status: CHANGES REQUESTED

## Summary

The invariant framing is the right direction and most anchors in the research and plan match the implementation, but the plan is not safe to implement as written. Three blocking gaps must be redesigned first: A1 lacks a sufficiently narrow proof for repairing authority material, E1 is both incompatible with the current binding/CommDB data model and unsafe after card materialization, and F2 makes only the credential permanent while leaving its derived QA claim expiring.

## What's Good (Keep)

- Keep I1–I6 as the organizing model. They describe durable system obligations instead of adding another incident-signature detector, which is consistent with FLY-1466.
- Keep the explicit red lines: no new runtime flags, no RESERVED-flag changes, no workflow_v2 revival, and no change to founder-only approval authority. The proposed surface is otherwise compatible with the current architecture.
- Keep read-time repair plus boot backfill as the recovery shape for reconstructible materialized state, provided both use the same strict derivation proof and transactional compare-and-set behavior.
- Keep typed completion errors, explicit founder feedback, audited operator actions, bounded recovery, and production-shaped positive and negative fixtures.
- Keep B1's relay change. The identified `approval_failed` path really does omit the Discord reaction while its sibling failure paths add one.
- Keep the idea of long-lived QA submission capability. It is a better fit for delayed human QA than repeatedly extending timers, but permanence has to propagate through the whole authorization artifact chain.
- Keep the existing FLY-270 updater as the deployment foundation and strengthen its acknowledgement semantics rather than creating a second deployment-truth mechanism.

## Issues & Recommendations

1. **A1's reconciliation proof is too weak to guarantee that repair cannot enlarge authority.** The existing `/head-authority` request contains both `execution_id` and `approve_question_id`, but the proposed `reconcileShipTargetBindingForQuestion(questionId)` throws away the execution identity. The stated proof also accepts a unique head binding without requiring that it belong to the holder's exact carrier node and current attempt. Since an already-approved CommDB question plus a newly repaired binding can enable merge, this is authorization-relevant even though the repair does not itself mint founder approval. Require one transactional, compare-and-set proof over the exact tuple: active run and current gate node; current, non-superseded runner-ship holder; holder `source_execution_id`; holder authority snapshot carrier node; latest/current carrier attempt; that node attempt's unique PR binding and head; and, on the request path, the supplied execution's session/qid/head relationship. Reject ambiguity, old attempts, wrong-node same-head bindings, advanced runs, superseded/approved-old holders, and mismatched executions. The boot path has no caller identity, so give it a separately named stricter entry point rather than silently weakening the request proof. Add negative tests for every rejected relation and emit a stable audit event only after the transaction commits.

2. **A2 and E1 conflict with the physical binding model, and E1 is unsafe after question materialization.** `workflow_ship_target_binding` is keyed by `approve_question_id`. `recordWorkflowShipTargetBindingTx` reads that row and either returns a match or throws a conflict; adding `superseded_at IS NULL` to `matches` means a superseded row will now throw, not permit another insert, and a second row with the same question ID cannot be inserted because of the primary key. More importantly, after `question_written`, `gate-materializer.ts` has written the CommDB question with `from_agent = holder.source_execution_id`, and `verifyApproval` requires `question.from_agent === execId`. Changing only the holder/session to a new carrier creates split authority: the new carrier cannot verify the old question, while the old carrier may retain the qid. Preserve the existing pre-materialization rebind path. For post-materialization recovery, supersede the old holder/question/binding and create a new gate question/card bound to the new carrier; do not transfer an existing founder card between executions. If an in-place repair of one binding row is still needed, specify an exact-value CAS `UPDATE` with before/after audit, not “supersede + insert.” Tests must prove the old execution and old qid can never verify after recovery.

3. **F2 does not make the full QA authorization chain permanent.** `/decision` passes the credential's `expires_at` into `submitWorkflowDecisionByCredential`, which inserts a `workflow_claims` row with `permanent=0` in the same transaction. `resolveWorkflowDecisionClaim` still rejects that derived claim after expiry. Thus an expired “permanent” credential can produce an already-expired claim and have the transition refused or rolled back. Model lifetime explicitly at the API boundary and propagate it: a permanent QA credential must create the QA verdict claim with `expires_at = NULL, permanent = 1`, while the review verdict/output semantics remain unchanged. Include lifetime in the binding/digest where relevant. Cover all schema paths, not only an `ALTER`: base table creation, idempotent migration, `rebuildWorkflowActivationChildren`, row types/readers, initial issuance, prelaunch rotation, generalized admission, and repair issuance. Preserve anti-stale checks for consumed token, current binding, current attempt/head, and active/current run, and revoke or render unusable credentials for canceled, terminal, reworked, dead, or replaced QA executions. Permanence intentionally removes theft containment by time, so add explicit negative tests for those states and exact replay.

4. **The proposed F2 expiry test would not test expiry after F1.** F1 changes legacy QA credentials to the manifest-derived window; the default QA window is 360 minutes with a 24-hour absolute deadline, and manifests can override it. Advancing only three hours is therefore not reliably expired. Construct a credential whose `expires_at` is already in the past, or advance beyond both the selected submission window and absolute deadline. Assert that `permanent=0` still returns `credential_expired`, while `permanent=1` is accepted and its resulting permanent claim remains valid through transition evaluation. Avoid stating that all QA windows are 360 minutes when manifest overrides exist.

5. **C2 counts failure classes that are not evidence corruption.** `complete-marker-reconciler` currently groups network/abort failures, Bridge 5xx, 429, and retryable `missing_output` into `transient_failed`. Five heartbeat/boot attempts during an outage or delayed output can therefore quarantine a valid marker and fail the session. Split deterministic, same-context completion rejection from transport, rate-limit, and not-yet-visible-output conditions. Quarantine immediately for the new typed incoherence 409s; use durable backoff/age and alert/hold for infrastructure failures; apply a same-digest strike budget only to a clearly enumerated stable failure class. Define whether strike exhaustion atomically holds the workflow in StateStore before moving the marker, so I3 does not degrade into “delete the retry input, then mark the session failed.”

6. **D1 and D2 need durable, conflict-free proofs rather than event presence.** A `runner_ship_merged_observed` event can represent a base observation, a mismatch, or a projection that was later quarantined/conflicted; its existence alone is not merge proof. The dispatcher should call one StateStore transaction that proves the current run/node/attempt/head binding and a current conflict-free merged observation projection, then compare-and-sets the hold. The proposed `no_code` case is also incomplete: the attestation is currently Bridge-derived during completion and may roll back with a failed transaction, so the plan must either persist a server-derived attestation before the risky step or recompute the exact baseline/current proof at hold time. For D2, persist every death observation before holding. Today the dead-execution watch is written as part of replacement; if death #2 holds without recording it, resume can repeatedly rediscover the same death and the cap cannot progress deterministically. Specify resume behavior and an idempotent death receipt/event.

7. **Several validation and operator contracts are attached to the wrong or unspecified boundary.** C4's coherence rule belongs at every template publication/seed-import or immutable-snapshot construction boundary after capabilities resolve, not only in `workflow-menu.ts`; otherwise a custom/founder template can still publish an incoherent runner-ship snapshot. Existing frozen incoherent snapshots should fail with the typed hold path, not be silently rewritten. E2 also does not actually copy a `/re-qa` `failed[]` precedent: the current endpoint returns one discriminated `reason`. Either preserve that established shape with precise per-condition reasons or explicitly introduce and test a new multi-failure contract. E4 must name its idempotency store: there is no existing re-QA receipt table, while the plan simultaneously says no new table is needed. A uniquely keyed run event can be the canonical receipt if replay lookup and response reconstruction are specified. Finally, do not emit `ship_target_binding_skipped:not_required` for every ordinary non-runner gate; expected absence is not an invariant failure and will create audit noise.

8. **B2 needs exact founder-reply correlation, and B3 should not be deferred.** The relay scans live threads and classifies approval-intent text by prefix. Alerting whenever such text coexists with any consumed ship question in the thread can misattribute a later reply to an old gate. Require a Discord reply/reference to the exact card, or a single unambiguous current/recent consumed qid tied to the active holder, head, and carrier; persist a dedupe key and define outbox/retry behavior for the reaction and alert. The recovery instruction must invoke the safe new-gate flow from issue 2, not the unsafe same-qid rebind. The stale SHIP-VERDICT guidance contributed to this incident and the founder requested one coherent fix, so update or remove it in this issue rather than leaving it as an optional follow-up.

9. **Fix G duplicates detection instead of closing deployment truth.** `scripts/update-flywheel.sh` already fetches `origin/main` and deploys drift under FLY-270, while `restart-services.sh` writes `~/.flywheel/deployed-sha` after Bridge health succeeds. A daily standup detector introduces a second clock plus git-history, path-diff, dedupe, and packaged-install edge cases, yet still allows a stale Bridge for 24 hours. Expose a startup build SHA where the build has one, and make the existing updater/restart/marker acknowledgement verify that `/health.buildSha` is the intended deployed commit (or an explicitly accepted ancestor) before writing the deployment receipt. Keep packaged builds explicit rather than inferring a repository commit. This is a smaller structural closure and aligns with the “fix structure, do not add detectors” rule.

10. **Re-sequence around the corrected authority model and add rollback checkpoints.** Suggested order: (a) F1 plus complete credential-and-claim permanence with migration tests; (b) B1's founder feedback as immediate containment; (c) strict A reconciliation and boot backfill; (d) C typed failures and safe retry classification; (e) D proof-backed holds; (f) a post-materialization **new-gate** recovery operation with audited idempotency; then (g) deployment acknowledgement hardening and diagnostics. A and the current E proposal should not land together until the carrier-transfer model is replaced. Keep the no-flag constraint, but make each layer independently deployable and reversible through data-compatible commits, with production-shaped mutation tests proving that removal of each structural fix recreates its failure.

## Verdict
