# Design Review — plan.md (FLY-1655) (Round 3)

Date: 2026-08-08
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 3 removes the previous holder/evidence schema conflict and makes the permanent credential representation physically compatible with the existing tables. The design is close, but the gate-reissue saga can still discard a real founder response and its carrier predicates are contradictory; F2 also needs a valid internal-capability lifetime and backward-compatible receipt digest before this can be approved.

## What's Good (Keep)

- Keep reissue as transport-identity rotation on the same logical holder/attempt. It preserves immutable evidence and the current workflow node model while still producing a genuinely new qid/card.
- Keep the separate `intent_committed` and `converged` receipts, crash-boundary tests, exact holder CAS, full before/after audit tuple, and use of the existing gate materializer.
- Keep A1's carrier lifecycle restriction, active-only boot sweep, terminal negative tests, and A1-boot fixture.
- Keep F2's non-null credential expiry as audit data, explicit permanent claim representation, exact-replay receipt behavior, and unconsumed-credential revocation hooks.
- Keep durable age/alert handling for `missing_output`, D1's observation-outside/CAS-inside split, and the drift mutation test.
- Keep G's build/source/unknown identity modes and the safe ancestry direction. The six logical identity cases are correct.
- The plan remains consistent with the no-new-flags rule, RESERVED/workflow_v2 red lines, and founder-only merge authority in its intended end state.

## Issues & Recommendations

1. **E1b uses one carrier proof/update shape for two mutually incompatible session states.** A1 condition 6 proves the **current holder owner** by requiring the old qid plus `awaiting_review|approved_to_ship`. A replacement carrier must instead be the latest/current carrier-node attempt with a valid activation/PR binding, `status ∈ {running,ship_parked}`, and no review qid—the creation/rebind shape visible at `StateStore.ts:30141-30161` and `:32347-32375`. Conversely, when the candidate is the original live carrier, the creation-path update cannot bind it because it is already `awaiting_review` with the old qid. Specify two exact branches in the Phase-1 transaction: same carrier performs `review_question_id old→new` while remaining `awaiting_review`; replacement carrier detaches the old eligible session and moves the new `running|ship_parked,NULL` session to `awaiting_review,new`. Both branches must revalidate the latest carrier attempt/head and end with exactly one session owning the new qid. Refuse reissue when the holder is already `approved`, the carrier is `approved_to_ship`, or a valid founder claim already exists—reissue must not discard a completed founder decision. Also insert the **new** `workflow_ship_target_binding` row in this transaction after superseding the old one; do not deliberately leave the new qid dependent on A1 read repair.

2. **The current saga linearization can lose a founder response that won before authority rotation.** Phase 1 rotates teamlead authority first, then Phase 2 treats any `retireShipGate=false` caused by an existing response as expected. `retireShipGate` is intentionally a guarded “unanswered only” CAS (`flywheel-comm/src/db.ts:1095-1120`), so false may mean the invalid Lead response from instance B, but it may also mean a trusted structured founder approval landed just before the teamlead transaction and has not yet been projected. Treating both alike revokes real founder intent and asks for approval again. Add a durable pre-rotation fence: record a request receipt without changing authority, then atomically retire the unanswered CommDB gate or inspect the response that won. A trusted founder approval must abort reissue and drive/await canonical approval convergence; an invalid or non-founder response, already-terminal invalid gate, or missing row may proceed to the teamlead qid rotation. The durable request receipt must let a crash after CommDB retirement but before teamlead rotation resume safely. Test founder response before the fence, concurrent with the fence, and after successful rotation; the first two preserve the old approval when trusted, while only the last is rejected as stale.

3. **F2's internal capability is born expired in the required permanent test.** The plan deliberately tests a permanent credential whose audit `expires_at` is already in the past, then copies that value into the newly issued `workflow_decision_capability`. Although the current direct path inserts and consumes the capability without invoking the normal capability-expiry check, this produces an authority row that was invalid at its own `issued_at` and weakens the ledger's forensic meaning. Mint the unexposed same-transaction capability with a fresh, short, server-owned bounded window (and matching non-null absolute deadline), consume it immediately, and leave the past credential deadline only on the credential row as audit history. Derive the lifetime union **inside** `submitWorkflowDecisionByCredential` after loading the credential in its transaction, rather than accepting a route-computed value as authoritative; then compute the replay digest from that persisted lifetime.

4. **The new lifetime digest must preserve exact replay for credentials consumed before migration.** Existing rows store `consumed_submission_digest` using the current object containing `claimExpiresAt` (`StateStore.ts:26998-27008`). If bounded lifetime is normalized into a new object shape, an exact replay after deployment recomputes a different digest and returns `replay_payload_mismatch`, despite no client change. Make bounded lifetime serialization byte-compatible with the legacy digest and add only a stable permanent marker for newly issued permanent credentials, or persist/version the digest algorithm and verify with the recorded version. Add a migration fixture containing an already-consumed bounded credential and assert exact replay still returns its prior claim after upgrade. This is required by the plan's data-compatible, independently revertible sequencing claim.

5. **G's built-mode proof conflicts with the existing `SKIP_BUILD` paths.** `restart-services.sh` skips `pnpm build` when the deployed SHA already matches or when changes are classified as non-build-relevant (`:920-1005`, build gate at `:1879-1897`). In built mode, the embedded SHA then remains the previous commit while `CURRENT_HEAD` advances; the new safe ancestry check correctly classifies that running build as stale, so the receipt can never advance and the updater will repeatedly alert even for doc-only changes. Define mode-aware behavior: either refresh/rebuild the build stamp whenever a built deployment's intended commit changes, regardless of ordinary build classification, or define and persist a separate intended runtime-artifact commit while keeping checkout/deployment receipts honest. Add tests for built-mode `SKIP_BUILD`, source-mode doc-only changes, and an updater retry after the rejected receipt.

6. **The plan's E acceptance text still contradicts the same-holder design and could drive the implementation back to the rejected model.** The E fixture says “旧 holder superseded” even though the holder row must remain the same, and it says “旧 execution 永拒” although the original execution is explicitly allowed to be the candidate and must then verify successfully with the new qid. The invariant should be: old **qid/card** always rejects; the old execution rejects only when it is not the selected carrier. E3 still refers to nonexistent “A4” instead of A1-boot, and the document header still labels the plan R2. Finally, name the component that appends `gate_reissue_converged:<requestId>` when the asynchronous existing materializer reaches `completed`, and require replay to compare the receipt's canonical before/candidate tuple so request-id reuse with different inputs returns a conflict. Correct these before implementation so the tests encode the chosen model rather than the superseded attempt+1 model.

## Verdict

CHANGES REQUESTED — address items above
