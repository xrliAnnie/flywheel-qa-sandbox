FLY-1833 合库冲突:从「卡死要手术」到「常规自动流程」

设计方案 · 2026-08-17 · 独立设计评审 6 轮通过后交付

一句话

以后合库(把你批准的 PR 真正合进 main)撞上代码冲突、时序竞速或 GitHub 故障时,引擎自己认出是哪种情况、自己修、自己重新发车;只有当代码内容真的变了,才回到你手上 —— 而且只需要在一张新卡上点一次 ✅。全程零重启、零终止会话、零数据库手术。

名词:land = 引擎里负责合库收尾的最后一步;head = PR 当下指向的那份代码版本;held = 引擎把一件事「判死停摆」的状态。

那一晚发生了什么(2026-08-16/17,一夜四撞)

事件现象人工代价
FLY-1806 ×2你批准后发车,同一分钟另一单先合入 → 撞冲突 → 引擎双判死终止会话 + 重开新执行体 + 手动改底座 + 你重批,一夜点了 3 次
FLY-1809批准与代码版本对齐差了 5 分钟 → 判死;5 分钟后条件已消失,引擎仍永不复查数据库手术(手改引擎账本)
FLY-1781GitHub 自己故障(503)→ 引擎把死掉的发车当「已发」,重试预算被故障吃光;人工合入后引擎不认账人工重发口令 + 手动踢引擎收尾

共同形状:一次纯机械的失败,烧掉的却是你的手指和工程师的手术刀。你已定性:并发跑项目,冲突是常见场景,不是异常。

为什么现在会卡死

  • 信息丢失:发车失败只剩一个比特(「失败了」)。代码冲突、测试挂了、GitHub 故障,引擎完全分不清 —— 分不清就只能一律判死。
  • 判死无门:held 状态没有自动出口,返工门的白名单也不放行这类失败。
  • 批准不跨版本:解冲突必然产生新 head,而你的批准精确绑定旧 head(这是对的,不能放宽)—— 但现在连「证明内容没变」的机制都没有,只能整轮重来。

新流程:四条路,各有各的自动出口

  • Tier-1 机器合并:冲突但底座能干净自动合并时,引擎自己把 main 合并进 PR 分支,并用数学证明「内容一个字没变」→ 你的批准自动延续,不打扰你(只在讨论串里留一句通告)。
  • Tier-2 真冲突:机器合不了 → 引擎原地唤醒写代码的那个执行体(不杀会话、不重开),给它冲突文件清单让它解;解完重走 QA,自动出一张新批准卡(卡上写清「差异只是解冲突」),你点一次 ✅ 即走。
  • GitHub 故障:单独识别,暂停等待,不烧重试预算,恢复后自动续;人工在 GitHub 上合入的,引擎也能自己认账收尾。
  • CI 真挂了:这是代码问题,停下告警 Lead —— 但从此所有 held 都有返工门,Lead 一个动作就能重开,永远不需要手术。
  • 预防:同一仓库一次只发一趟车(排队不赛跑),发车前先探一次「能不能合」,不再白烧 30 分钟 CI。

你的批准如何被保护(安全设计的两条铁律)

  • 铁律一:批准延续只认机器证明。新版本必须同时满足:父提交恰好是「你批的版本 + main 顶点」,且内容树逐字节等于机器干净合并的结果 —— 任何人手夹带的改动(哪怕一行)都会让证明失败,自动降级为「出新卡请你确认」。现有的「批准绑定精确版本」比较逻辑一个字不改,延续是加出来的独立留痕通道,链条永远能查回你的原始批准。
  • 铁律二:内容变了必回你手。人手解过冲突 = 内容变了 = 重走 QA + 新卡一次 ✅。自动化消灭的是终止/重开/手术这些无谓消耗,不是你对内容的最终决定权。
  • 极端窗口诚实处理:如果你的打回恰好晚于「发车授权」那一毫秒,引擎不假装能追回已经发出去的 GitHub 动作 —— 它会大声告警,交人裁定,绝不产生「本地说拦住了、远端却合进去了」的两面账。

关键取舍与否掉的方案

决定为什么
采用解冲突后重走 QA安全合同要求新内容持有自己的测试凭证。评审确认「跳过 QA 直接发卡」会打穿凭证链 —— 已否掉;若以后想给小改动开快道,单独立项由你拍板。
采用「合并 main 进来」而非 rebaserebase 需要强推(force-push),会切断批准的血缘链、撞上推送保护;合并方式让你批的版本永远是新版本的祖先,内容可证明。
采用同仓库排队发车慢几分钟,换来不再同分钟撞车 —— 那正是那晚两次事故的起点。
否掉放宽「批准绑定精确版本」底线,评审全程反复确认一根手指都没碰。
否掉自动解语义冲突机器只做可证明的机械合并;真正的语义冲突永远交给人 + 执行体判断。
否掉把发车改造成「可撤销」的分布式事务过度工程 —— 30 分钟 CI 无法可靠撤回,与其假装能,不如诚实告警。

诚实边界:这个设计做什么、不做什么

做:冲突/竞速/外部故障的自动识别与分流;干净合并自动延续批准;真冲突自动唤人解、QA 重验、自动出新卡;所有判死状态都有免手术的返工门;全程不需要重启任何服务。

不做:不放宽 founder-only 合库授权;不自动解语义冲突;不覆盖老式(legacy)ship 路径;QA 快道不在本单;打回晚于发车授权的窗口只承诺「诚实告警 + 人工裁定」,不承诺拦截。

打磨过程:方案经独立设计评审 6 轮(累计 28 项修订意见,全部采纳),第 6 轮零阻断通过;最重的一刀(批准延续)带有明确的安全回退 —— 若实现期发现覆盖不全,退回「都出新卡」,你多点一次 ✅,其余自动化全保留。
