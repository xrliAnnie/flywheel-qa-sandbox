FLY-108

Session 状态不翻转 — 修复设计报告

工程设计节点交付 · 2026-09-01 · Codex 设计评审通过后成稿

1 · 一句话总结

AI 工人干完活以后，系统账本上它的状态经常没有翻成"已完成"，导致后续的完工通知、终端回收、聊天归档全部卡住；本设计让工人在收工时主动上交一份带凭证的"完工报告"，并给服务器加上严格的把关和兜底，让状态可靠地走到终点。

涉及的两个具体故障（GEO-362 / GEO-363）症状相同、病根不同，下一节分别解释。

2 · 问题是什么：同一症状，两个病根

先解释几个词：Runner（跑在终端里干活的 AI 工人）、Bridge（中枢服务器，记录每个工人的状态）、session status（账本上工人任务的状态字段，比如"进行中 running"、"待审核 awaiting_review"、"已完成 completed"）、session_completed 事件（工人完工时应该发给服务器的那条"我干完了"的消息）。

  • Bug A（GEO-362）：完工消息发了，但内容是空的——像交了一张白卷。服务器猜不出该怎么记账，走了一条兜底逻辑去硬改状态，被状态规则拒绝，最后卡死在"待审核"，而且无声无息。
  • Bug B（GEO-363）：某类精简流水线里，从来没有任何组件发过完工消息——工人只上报了"阶段变化"（一种仅供展示的信号，设计上不改账本）。状态永远停在"进行中"，终端变成僵尸窗口。

3 · 修复后的核心流程

修复分四层，源头一层 + 服务器三层：

  • D1 · 源头上报：给工人新增一条 flywheel-comm complete 命令（flywheel-comm 是工人和服务器之间的通讯工具），收工时必须调用，带上完整凭证：走哪条路线（route，比如"已批准并合并"还是"待人审核"）、PR 编号（PR = 代码合入请求）、合并证明。这是 Bug B 的唯一正解——消息从没人发，就让该发的人发。
  • D4 · 严格把关：服务器收到完工消息时，route 缺失或不认识 → 大声告警并拒绝，绝不再静默硬改状态。这治 Bug A 的"白卷被瞎猜"。
  • 授权闸：合并了但没走批准流程的，拦停并告警，不自动记"完成"——防止绕过创始人审批。
  • 可靠投递：发送失败自动重试 4 次；全失败就在磁盘写一个"待补发"标记，服务器重启时扫到会自动补账。

4 · 状态模型与数据契约

状态机（FSM，即"什么状态可以走向什么状态"的规则表）只新开一条窄边：从"待审核"直达"已完成"，且仅当三个条件同时成立——此前已有一次真实的完工上报、握有合并凭证、授权闸放行。其余路径一律维持原语义，审批流程不被绕过。

关键数据契约（不可随意变更项）

标识含义谁在消费
session_completed / stage_changed两种事件类型：前者改账本，后者仅展示服务器两个接收面、事件表、重启补账器
route 枚举完工路线（已批准/待审核/失败等 6 种）命令行校验、服务器把关、状态映射
待补发标记文件~/.flywheel/state/complete-failed/发送端写、服务器重启时读
合并凭证键名完工事件里叫 landingStatus，阶段事件里叫 landing_status（历史既成契约，两边各自钉死，不强行统一）状态映射、兜底守卫

5 · 关键取舍与被否方案

方案结论与理由
采用工人源头上报（Option 1）+ 服务器窄面兜底（Option 2 收窄版）源头修 Bug B、把关修 Bug A；兜底只救"此前上报过、后来才合并"的一类掉队者，绝不给"从没上报过"的任务开后门（有专门的回归测试钉死这条底线）
否决Option 3：靠 GitHub 合并通知（webhook）另起一条独立记账通道合并证据已随现有信号上行，无需再引入一个外部依赖和一条新链路
否决Option 4：放宽状态规则，允许"待审核"随意跳"已完成"破坏审批语义——等于告诉系统"没批准也能算完成"
否决把"阶段变化"信号升格为通用记账驱动展示信号和账本必须分离，否则任何展示噪音都能改账
刻意不做为"服务器收到但没记完账就崩溃"的极端缝隙加应用级回执协议用重启对账 + 隔离暴露兜住，把交付语义诚实声明为"至少送达一次 + 可对账"，不虚标"绝对必达"；回执协议另立 issue

6 · 评审与验收

本设计经 Codex（另一家的代码评审 AI，作为独立第二双眼睛）4 轮设计评审通过，评审意见逐轮收敛（7 → 6 → 4 → 0），共 17 项全部吸收，零项拒绝。核心纠偏包括：兜底逻辑的适用范围曾被写得过宽、与代码里钉死的安全边界相反；部署清单漏了两个必须重新构建的组件；若干风险描述与真实故障时序不符——全部对照代码逐条修正后才获批准。

  • 验收 = 三个代码包的定向测试全绿 + 两类 bug 的重放实验（白卷重放 → 大声告警不卡死；精简流水线重放 → 状态正确到达"已完成"并触发收尾）。
  • 回归哨兵：正常审批路径、失败路径、"从没上报过"的任务不被误终态化——全部保持原行为。

7 · 诚实边界：这个设计做什么、不做什么

做

  • 让"带 PR 的正常流水线"完工后状态可靠翻转，完工通知、终端回收、聊天归档恢复触发。
  • 把"白卷式"坏消息从静默卡死变成大声告警、可排查。
  • 失败时留痕（标记文件 + 重启补账），不静默丢失。

不做

  • 不救"从来没上报过完工、又没有 PR"的任务——它们交给心跳巡检暴露给人工，这是刻意的保守设计（宁可人来看一眼，不可系统瞎记账）。
  • 不保证百分之百"必达"：服务器在"收到消息"和"记完账"之间崩溃的极窄缝隙依然存在，靠对账机制暴露而非本设计根除。
  • 不动数据库结构、不动审批语义、不引入新外部依赖。
  • 本沙箱节点只交付设计文档，不改运行时代码；生产上线顺序（先服务器后工人、必须重新构建产物）已写入计划。
