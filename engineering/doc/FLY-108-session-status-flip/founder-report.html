FLY-108 · Runner 完工后状态不翻转 — 设计报告

Issue: FLY-108 · 日期: 2026-08-31 · 节点: eng_design(QA slot-3 设计重放)· 代码快照 1855f7a1
设计评审: Codex 4 轮收敛(6→4→1→0)· 最终判定 APPROVED

① 一句话总结

Runner 干完活以后,系统账本上它却永远显示「还在干」——修法是给 Runner 一个正式的「完工上报」命令,并让中枢对不合格的上报大声拒绝而不是瞎猜。

审计结论:这套修复已随 PR #155 在主干落地并经受两年多迭代检验;本设计节点在 QA 沙箱重放完整设计链(探索→调研→计划→评审),并如实补齐了原设计与今日系统之间的差异记录。

② 问题现场:同一个症状,两个不同的病根

「session status」(会话状态:中枢 Bridge 数据库里记录每个 Runner 干到哪一步的字段)应该在 Runner 完工后翻转成 completed(已完成),但它不翻。后果连环:关不掉 Runner、完工通知 🏁 不发、收尾清理不跑、tmux(Runner 干活所在的终端窗口)变僵尸。

Bug A(GEO-362)Bug B(GEO-363)
完工事件发了吗发了,但内容是空的根本没人发
卡在哪awaiting_review(等审)running(进行中)
病根发射器 bug + 中枢遇到空内容就瞎猜,猜的结果又被状态机拒绝 → 死锁架构缺口:这条产线上压根没有「完工上报」这个动作

Bug B 更普遍:所有「只改文档、不合并代码」的轻量流程都中招,不只一例。

③ 修复后的核心流程

核心动作:给 Runner 的命令行工具新增 flywheel-comm complete 子命令(「完工上报」:Runner 在收尾全部做完后,把完成方式、PR 编号、代码指纹等完整证据打包发给中枢)。发送失败自动重试 4 次,还不行就写下 marker 文件(存底的凭证文件,中枢重启时会自动补投),绝不静默丢失。

  • 发射侧管住 Bug A:完成方式(route)是必填项、只认白名单取值——这条产线物理上发不出空上报。
  • 中枢管住兜底陷阱:收到空/野路子上报时,从「瞎猜成 completed」改为大声警告并拒收,bug 变得可见而不是变形。
  • 时机合同管住误杀:上报必须是收尾的最后一步——因为中枢收到上报后的第一个破坏性动作就是关 tmux。

④ 数据与状态模型

整个生命周期由一个状态机(FSM:预先声明哪些状态之间允许跳转的规则表,防止非法捷径)把守。修复没有为了省事放宽状态机——「等审 → 已完成」的直跳依旧被拒,审批语义完好。

关键标识(保证不重、不乱):每个事件有唯一 event_id(重试复用同一个,天然幂等——同一事件收到多次效果也只算一次);收尾编排用 post-ship-finalization-<执行ID> 原子认领(数据库唯一键抢锁,三个入口谁先到谁跑,保证恰好一次)。展示层一律从 status 派生,不另建第二本账。

⑤ 关键取舍与被否掉的方案

方案判定为什么
1. Runner 侧补「完工上报」命令✅ 主修谁完成、怎么完成,Runner 自己最清楚——单一事实源正确;证据全是现场真数据
2. 中枢侧兜底合成完工事件⚠️ 只留有限形态Issue 原本推荐它,但「中枢替 Runner 猜完成」正是 Bug A 病根的制度化;只保留两条窄守卫通道(merge 后补终态 / 无 PR 的轻量 Runner 兜底),都不无中生有造数据
3. 靠 PR 合并 webhook 翻状态❌ 否「代码合并了」≠「Runner 收尾完了」——提前翻状态会误杀还在收尾的 Runner
4. 放宽状态机(等审→完成直跳)❌ 否绕过创始人审批闸,语义破坏不可接受

  • 两类 bug 的根治设计:完工上报命令 + 严格闸门 + 时机/可靠性合同(§③)
  • 对照今日代码的 as-built 核对:六项改动全部在位,并逐条标注后续迭代叠加的差异

  • 本节点是设计重放:零代码改动、零生产动作,交付物 = 设计文档三件套 + 本页
