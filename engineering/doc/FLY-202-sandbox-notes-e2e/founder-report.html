01 · WHY

为什么需要这个 fixture

Fixture（测试夹具）就是为了反复触发同一条测试路径而保留的稳定任务。这里的稳定任务是 FLY-202，它让 QA 不必伪造 issue。

PreHydrator（启动 Runner 前读取 Linear issue 的准备步骤）需要一个真实存在的 issue。于是 test-slot Bridge 可以启动真实 Runner，观察 TURN、阶段、review gate、Git push 和 PR，而不是只验证 mock。

02 · CORE FLOW

核心流程

Mermaid 是用文本描述流程图的格式；源文件保存在 HTML 旁边，用本机 Mermaid CLI 在构建时渲染成 SVG（一种可缩放的矢量图片格式）后内联，托管页面不加载任何外部脚本或图片。

03 · DATA MODEL

数据 / 结构模型

这里没有数据库模型。结构模型是三个当前事实来源，汇入一个稳定 Markdown 路径；稳定路径让每轮 PR 的差异可直接比较。

03b · RE-DISPATCH

重新派发时先对账，不重做

这条分支已经带着上一轮的成果：notes 已刷新、PR #267 已打开且可合并、main 没有前进。所以 implement 节点的默认路径是验证型无改动：先跑四项验证（目录集合、10 条摘要、目录树逐字、格式检查），全过就不碰 notes，只把进度提交推上去并确认同一个 PR。只有 main 前进或某项验证失败，才进入内容刷新。

04 · TRADEOFFS

关键取舍

选择：原位刷新稳定路径。
重复运行不产生 run-stamped 垃圾文件，Git 历史仍保留每轮差异。
拒绝：只追加新章节。
它会留下重复、互相矛盾的目录表和 tree snapshot。
拒绝：新增生成脚本。
纯文档 fixture 不值得扩大为生产代码和测试维护面。
05 · EVIDENCE

如何证明做完

  • 用途说明为 2–3 段。
  • 目录表集合等于当前 17 个顶层目录；未来变化时以现场集合为准。
  • README 摘要为 10 条，并覆盖架构、五步协议、slot 脚本和模式边界。
  • 内嵌 tree 与指定命令 stdout 完全一致。
  • PR 为 open，base 是 main，head 是 project-slot-6-FLY-202，且 PR head SHA 等于分支最终 HEAD（push 之后才校验，校验之后不再产生 commit）。
  • 用途说明第二段保留「alert queue / claims DB 仅在 --alerts 部署时隔离」的条件说法；这是机械验证覆盖不到的语义点，QA 单独核对。
06 · HONEST BOUNDARY

诚实边界

这个设计会做：指导 implement 节点先在 exact head 重跑四项验证；验证全过且 main 未前进就不改 notes，只把 progress commit 推上去并复用 PR #267；否则才刷新失败区块、docs-only commit、fast-forward push，并复用或（仅当被外部关闭时）重建 PR。

这个设计不会做：不会改生产代码、不会访问生产频道或数据库、不会 merge PR、不会请求 ship authority，也不会把这个 fixture 交给生产 Lead / Runner。

本轮相对上一轮的变化：上一轮 Mermaid CLI 无法启动 Chromium，只能放占位；本轮本地渲染成功，三张图都是真实 SVG。设计评审由 Codex（gpt-6-astra / xhigh）跑了两轮：第一轮提出 3 medium + 1 low（无改动路径漏 push、PR 被关闭时到不了重建、刷新指令会回退 --alerts 条件说法、scope 白名单漏 milestone），全部采纳后第二轮 APPROVED。

当前已知限制：同一 issue 还有 slot-3 的并行 PR #203 与多个 529 fixture 分支，本设计不处理它们；PR #267 是否 merge 由下游 QA 与 founder gate 决定。
