01 · WHY

为什么需要这个 fixture

Fixture（测试夹具）就是为了反复触发同一条测试路径而保留的稳定任务。这里的稳定任务是 FLY-202，它让 QA 不必伪造 issue。

PreHydrator（启动 Runner 前读取 Linear issue 的准备步骤）需要一个真实存在的 issue。于是 test-slot Bridge 可以启动真实 Runner，观察 TURN、阶段、review gate、Git push 和 PR，而不是只验证 mock。

04 · TRADEOFFS

关键取舍

选择：原位刷新稳定路径。
重复运行不产生 run-stamped 垃圾文件，Git 历史仍保留每轮差异。
拒绝：只追加新章节。
它会留下重复、互相矛盾的目录表和 tree snapshot。
拒绝：新增生成脚本。
纯文档 fixture 不值得扩大为生产代码和测试维护面。
05 · EVIDENCE

如何证明做完

  • 用途说明为 2–3 段。
  • 目录表集合等于当前 17 个顶层目录；未来变化时以现场集合为准。
  • README 摘要为 10 条，并覆盖架构、五步协议、slot 脚本和模式边界。
  • 内嵌 tree 与指定命令 stdout 完全一致。
  • PR 为 open，base 是 main，head 是 project-slot-6-FLY-202。
06 · HONEST BOUNDARY

诚实边界

这个设计会做：指导 implement 节点刷新同一份 sandbox notes，做 docs-only commit，push 当前 feature branch，并创建 sandbox PR。

这个设计不会做：不会改生产代码、不会访问生产频道或数据库、不会 merge PR、不会请求 ship authority，也不会把这个 fixture 交给生产 Lead / Runner。

当前已知限制：本机 Mermaid CLI 因 sandbox 权限无法启动 Chromium，所以这份 HTML 清楚标注两张图仍待本地渲染；源文件已保留，发布失败或渲染失败都会如实报告。
