FLY-202 · QA 沙箱说明夹具设计

eng_design · 2026-09-26 · sandbox slot-1 · 现有 PR #196

1 · 一句话总结

用一个真实但低风险的文档任务，让隔离测试环境里的真实 Runner 从当前证据核验稳定文件，只在不一致时修复，并把现有分支推到 PR #196，供 QA 观察而不触碰生产资源。

Runner 是实际执行工程任务的 AI 会话；test slot 是与生产隔离的一套临时测试环境。

2 · 核心流程

QA harness 是启动测试环境的编排器。它把真实 Linear issue FLY-202 交给 slot Bridge；Bridge 是负责创建和跟踪 Runner 的本地服务。PreHydrator 是启动前读取 issue 并把任务内容交给 Runner 的步骤。

DIAGRAM PENDING LOCAL RENDER Mermaid 源文件：core-flow.mmd。mmdc 两次均因 sandbox 内 Chromium 权限失败。
  1. Harness 注入真实存在的 FLY-202。
  2. Runner 从当前 checkout 读取目录树、QA framework README、live listing 和目标文件。
  3. Bounded validator 是只检查这个文档合同的小型验证器：全部一致时保持目标字节不变；不一致时只修对应段落。
  4. Runner 把当前分支 fast-forward push；PR（Pull Request，供审阅的分支变更集合）#196 保持 open，供后续 QA 观察。

3 · 数据与结构模型

设计坚持一个 source of truth，也就是每项事实只从一个权威来源读取：目录表来自 tracked tree，过滤 Git-ignored 项后的 live checkout 只做异常诊断；框架说明来自当前 README，命令证据来自现场执行结果。

4 · 关键取舍与被否方案

  • 选定审计优先的幂等复核：幂等表示重复执行会收敛到同一正确结果；证据一致时不制造 diff，不一致时才最小修复。
  • 选定复用 PR #196：动态任务明确要求 branch continuity，也就是沿用现有分支历史，不另开平行 PR。
  • 否决无条件重写同一个文件：source facts 没变化时只制造 churn，还可能改坏已经审核过的措辞。
  • 否决重建 branch 或另开 PR：破坏 branch continuity，也让 harness 丢失正在观察的 carrier。
  • 否决用 synthetic fixture：synthetic fixture 是伪造的测试输入；它会绕开本任务真正要验证的 Linear、Runner、Git 与 PR 链路。
  • 否决顺手改产品代码：扩大风险和验证范围，也违反“sandbox documentation only”的任务边界。

5 · 诚实边界

这个设计会做：提供探索、调研和逐步实施计划；用当前仓库事实验证 Markdown；只在 mismatch 时修改；fast-forward push sandbox branch；复用 open PR。

这个设计不会做：

  • 不修改任何 runtime code、package、数据库、生产配置或生产 Discord 资源；
  • 不删除继承的 FLY-2456 drill marker，也不改写已经发布的 branch 历史；
  • 不 merge PR、不请求 ship 权限、不部署；
  • 不承诺每次 run 都有新的 target diff——当前内容已经正确时，no-op 是诚实结果；
  • 不保证目录表永久不变——每次 fixture run 都必须重新读取当前 checkout；
