# Design Review — plan.md (FLY-1224, Round 1)

Date: 2026-07-13
Author: Codex
Status: CHANGES REQUESTED

## Summary

The core design is feasible with the current architecture: the existing dispatcher/resolver seam, Codex adapter, shared-branch machinery, and cross-family review contract can support the requested per-phase vendor table without a new framework. I am requesting changes because the plan misses one phase-capable successor lane, leaves phase retry without its shared-branch identity, does not fully fix pending display truthfulness, and treats one non-authoritative `absent` probe result as permission to spawn.

## What's Good (Keep)

- The fixed `DEFAULT_PHASE_DISPATCH` table is the right scope. It preserves phase-table sovereignty, keeps vendor/effort off the public HTTP body, reuses `VENDOR_TO_EXECUTOR`, and leaves all dispatch-model-only callers on the legacy Claude branch.
- The three orchestrator starts cover legacy QA-FAIL respawn, keep-alive QA-FAIL spawn fallback, normal handoff, startup reconcile, and FLY-1050 QA respawn because the reconcile paths re-enter `onPhaseComplete`/`dispatchNextPhase`. Keeping FLY-579 auto-QA unchanged is correct.
- C8 targets the two and only two production `wakePhaseRunner` call sites. The evidence chain is real process liveness, not StateStore status: `probePhaseAlive` resolves the tmux target and `probeRunnerProcessLiveness` reads `#{pane_dead}` with `tmux list-panes`.
- The Lead's mutation requirement is well aimed: the QA-FAIL regression test will distinguish a corpse wake (`fixExecId` bound to the old execution) from a fresh fix spawn. Keep both dead variants and the alive/indeterminate controls.
- The Codex effort mechanism is correct. The installed Codex CLI accepts app-server `-c key=value`, parses the value as TOML, advertises `gpt-5.6-sol` with `xhigh`, and accepts the exact separate argv value `model_reasoning_effort="xhigh"`. Daemon-level configuration is appropriate for this one-thread-per-runner runtime and will be reapplied on daemon rotation.
- The existing FLY-1188 executor-based prompt variants, Codex worktree guard, CommDB transport registration, and `review-family.ts` cross-family invariant already provide the required execution and review semantics. The plan correctly avoids duplicating them.
- The three-commit split is useful for review and audit, and the restart-services rider is correctly isolated from the vendor work.

## Issues & Recommendations

1. **The phase dispatch inventory is incomplete, and the documented retry lane still drops the phase's shared-branch contract.** `plugin.ts:6708-6729` is a sixth phase-capable feed: FLY-871 login-expired rescue calls `RunDispatcher.start()` to obtain FLY-795 progress-resume behavior, but only forwards `s.dispatch_model`. Orchestrator-created phase rows normally have no persisted `dispatch_model`, and even a persisted GPT model without a vendor would resolve to `claude-tmux`. Separately, `actions.ts:854-859` deliberately omits `shareParentBranch`; C5 would therefore retry an Implement row on Codex while Blueprint treats it as a non-phase run, persists `chat_thread_role=main`, and can rebuild a role-specific branch instead of shared branch B. This also makes the proposed quota kill-switch/manual-retry recovery unsafe. Extend the plan's inventory to the FLY-871 successor and derive the full spec from durable `chat_thread_role`: model/vendor/effort, `ignoreRunnerLabelSelection: true`, and `shareParentBranch: true`. Do the same shared-branch propagation for phase-row actions retry (the request type and dispatcher already support it), or explicitly resolve the existing FLY-840 dependency before claiming retry/rollback coverage. Add tests for a running Implement rescue with null `dispatch_model`, a progress-resume successor, and a phase-row retry retaining shared branch/phase identity. Non-phase rescue/retry must remain unchanged.

2. **C8's `absent` decision is not fully fail-closed and can change a live Claude path.** `probePhaseAlive` uses `getTmuxTargetFromCommDb`, while `tmux-lookup.ts:198-212` explicitly collapses both `gone` and a CommDB read `error` to `undefined`; plugin wiring then returns `absent`. Treating every `absent` as permission to fall into spawn can therefore duplicate a live runner during a CommDB lock/corruption error. The later ghost guard helps only when `StateStore.tmux_session` was successfully persisted; that callback is best-effort, so it is not a proof in every case. Preserve the Lead's “only two wake sites” scope by authorizing fallback on `dead_pin` unconditionally, but on `absent` only when the row has a persisted `tmux_session`, after which the existing ghost guard directly probes that target and blocks `alive`/`indeterminate`. With no persisted target, retain the current wake/reconcile path. Alternatively, obtain explicit scope approval to make `probePhaseAlive` use the existing discriminated `lookupTmuxTarget` and map lookup errors to `indeterminate`. Add negative controls for `absent + no persisted target` and `absent + direct ghost probe alive`; also assert dead paths perform no worktree assertion, TURN grant, or wake before spawning.

3. **The proposed display change fixes active GPT rows but still lies for pending/fallback rows.** `issue-display-refresher.ts:287-300` and `:719-733` compute pending `plannedModel` from unchanged `DEFAULT_PHASE_TIER`, and call `phaseMessageTag(role)` with no runner model. `phaseMessageTag` itself also falls back to that tier, so pending Implement remains `[实现·Fable]` / planned Fable. Adding GPT recognition to `modelDisplayName` only helps when `gpt-5.6-sol` is actually supplied. Make the phase display fallback derive `resolvePhaseDispatch(role).model` (including the kill switch), using `runner_model` when present and the legacy tier only as a last unknown fallback. Test pending Implement under both default Codex and kill-switch Claude modes in both issue-display paths, not only `phaseMessageTag("implement", "gpt-5.6-sol")`.

4. **T12 is a false-green test strategy and the operator-facing restart contract is incomplete.** Normal-mode dry-run exits at `restart-services.sh:589-594` before the normal idle gate, and bridge-only dry-run exits at `:1341-1345` before its gate, so dry-run text cannot prove either runtime branch. Extend the existing hermetic top-level suite in `scripts/test-restart-services.sh`: with a busy `/health` shim, prove default normal and bridge-only runs do not call `wait_for_idle`; prove `--wait-idle` and `FLYWHEEL_RESTART_WAIT_IDLE=1` do; and prove `--force --wait-idle` skips it. Update the existing bridge-only busy test to opt in with `--wait-idle`. Also update the script's usage header/dry-run narration and `scripts/hooks/flywheel-restart-guard.py:109-119` plus its tests—the current guidance says `--force` skips a wait that will no longer be the default, and the legal `--wait-idle` forms should be covered.

5. **The kill switch and Codex-quota failure mode need an accurate runbook.** Editing `~/.flywheel/.env` does not mutate an already-running Node process; the bridge wrapper sources it only at process start. “No deployment” is fair, but activation requires the sanctioned `restart-services.sh --bridge-only` path, and after C9 that restart skips idle wait unless the operator opts in. The plan must also state that an in-flight Codex failure does not automatically fall back to Claude: the operator sets the switch, restarts Bridge, and safely re-drives the failed phase after issue 1's phase-retry continuity is fixed. Keep commits 1 and 2 separate for audit, but declare them one deployment/revert unit—reverting C8 while Codex Implement remains default knowingly restores the deterministic QA-FAIL stall.

6. **Cross-package verification and types should be tightened.** `flywheel-config` is consumed through `dist`, while root `pnpm test` does not build; tests can therefore exercise stale config output after C1. Require a fresh topological `pnpm build` before cross-package tests, plus `pnpm typecheck`, `pnpm test`, `pnpm lint`, the restart shell suite, and the restart-guard test. Use the existing `RoleEffort` type for `PhaseDispatchSpec.effort` and `dispatchEffort` instead of `string`, while retaining the daemon-boundary whitelist. Update the touched-file/test inventory to include the rescue wiring, both issue-display paths, `scripts/test-restart-services.sh`, and restart-guard guidance/tests.

7. **Document the remaining observability boundary rather than expanding this ticket.** Internal phase dispatch bypasses `normalizeDispatchModel` only after the HTTP boundary, so the GPT id is not blocked; StateStore stores `runner_model` as an opaque string; and `modelShortCode` returning undefined for GPT is intentionally non-breaking. However, `packages/token-usage` scans Claude Code JSONL and its built-in pricing is Claude-only, so default Codex Implement usage/cost will be absent (or zero if an unknown model record arrives). That should be an explicit accepted limitation with a follow-up/telemetry owner, not silently presented as complete per-phase model observability. Also record the pre-existing FLY-840 manual-retry limitation if it is not pulled into issue 1.

## Verdict

CHANGES REQUESTED — address items above
