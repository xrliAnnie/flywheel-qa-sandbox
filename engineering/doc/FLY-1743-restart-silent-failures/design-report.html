FLY-1743 · 重启部署两处静默失效 — 设计方案

Issue: FLY-1743 · 2026-08-13 · 设计节点交付 · Codex design review 2 轮 APPROVED · 改动面: 仅 scripts/restart-services.sh + shell 测试
🎯一句话总结

给「全舰重启」补上两道安全底线:部署做到一半死掉时,系统必须大声说「源码和正在运行的东西已经对不上了」;回滚时如果连工作区状态都读不出来,就绝不执行破坏性重置。

背景:FLY-1729(昨天已上线)让每次全舰重启前自动把源码更新到最新版。它的收尾审查发现了两处「坏了但不出声」的隐患,这单就是修这两处。

🕳两处静默失效是什么

缺陷 ①部署做一半死掉,没人知道「源码已前进、产物没跟上」。

重启脚本先把源码更新到最新(这一步叫 fast-forward merge,即快进合并:把本机代码指针直接移到最新版本,不产生新改动),然后要经过十多个步骤(编译、停旧服务、健康检查、换代所有 Lead……)才最终把 deployed-sha(部署账本:一个记录「当前正在运行的是哪个版本」的小文件)推进。中间任何一步失败,就留下「源码是新的、实际跑的还是旧的」——失败那一步自己可能有报警,但报的是那一步失败,没有任何声音说出这个残留状态本身。

审计还发现更糟的一层:合并之后、部署主体开始之前有三个检查点,失败退出时连兜底的「重启异常终止」告警都不会响(那个告警只在部署主体开跑后才生效)——这是最彻底的静默。

缺陷 ②回滚时读不出工作区状态,却照样执行破坏性重置。

回滚前脚本会问 git「工作区干净吗」。但如果 git 这个命令本身失败了(仓库损坏、锁冲突、磁盘问题),旧代码会把「读不出来」误当成「干净」,然后继续执行 reset --hard(硬重置:把代码强行退回某个版本,未保存的改动会被永久丢弃)。这叫 fail-open(出错时放行——安全领域的大忌;正确姿势是 fail-closed:出错时停手)。而且它只在「已经出事、正在补救」的时刻触发——那正是最不该再丢东西的时刻。

🧭核心流程图:缺陷 ① 的修法 — 退出收口的「结果对账」

不在每个失败点各补一句告警(失败点有 10+ 个还在增加,总会漏),而是在所有退出路径的必经收口(EXIT trap,即脚本退出时必然执行的钩子,不管是正常结束、报错死掉还是被人按 Ctrl-C)做一次「结果对账」:重新读源码版本和部署账本,两者不一致就发严重告警 + 保证非零退出码。判据锚在「结果状态」上,不锚在「哪一步失败」上——这正是 issue 点名要求的。

「布防」(arming)决定何时开始要求这条铁律:在合并之前布防(防信号打断的空窗),preflight 成功后再布防一次(接手上次没收敛的烂账)。没布防的退出(比如 dry-run,演练模式,只看不改、或还没走到合并就被响亮拒绝)不检查,避免误报。

🔒缺陷 ② 的修法 — 回滚改为「状态未知就停手」

修法就一个动作:把「读状态」和「做重置」这两个命令的返回码都显式检查。读不出状态 → 拒绝重置 + 严重告警;重置本身失败 → 停止后续重建 + 严重告警。同文件里 FLY-1729 自己写的前置检查已经有完全正确的写法,直接镜像过来,不发明新东西。

两个修互相配合:② 保证补救动作不把状态弄得更坏;① 保证「没修完」这件事必然有人听到——回滚被拒后脚本退出,①的对账发现源码和账本不一致,状态告警自动补位。

🗂数据 / 结构模型

本单零新增存储、配置开关、定时器和外部机制(遵守「不加新 flag」铁律)。涉及的既有数据只有两样,新增的只是四个告警名字:

东西是什么本单怎么用
HEAD源码当前版本指针(git 自带)退出时重新读一次(不用运行早期的缓存值——回滚成功会把它挪回去)
~/.flywheel/deployed-sha部署账本:记录正在运行的版本退出时重新读一次;和 HEAD 相等 = 部署收敛
布防标志(脚本内变量)本次运行是否拥有部署事务合并前 + preflight 成功后置真;dry-run 永不置
4 个新告警名restart-source-deployed-mismatch(不一致)/ …-unverifiable(读不出)/ rollback-blocked-state-unreadable / rollback-reset-failed全部走既有 severe 告警通道(会 @ 你);命名刻意中性——两个版本号不相等只能证明「不一致」,证不了谁新谁旧,文案只说可证的事实

告警通道本身是「尽力送达」(送不到也不能卡死重启),所以「非零退出码」是并列的第二根支柱:即使 Discord 消息丢了,调用方也能从退出码知道失败。

⚖️关键取舍与被否掉的方案
决策点选了否掉了 · 为什么
缺陷①检测位置 退出收口一处对账(结果不变量) 逐失败点补告警——失败点 10+ 且持续演进,总会漏新路径;issue 逐字反对按步骤判。下次运行时再检测——issue 要求 abort 当下就响。
何时开始要求不变量 合并前 + preflight 成功后两点布防 每次退出都查——演练模式、锁竞争失败、响亮拒绝这些路径没碰源码,查了纯误报(每次追赶式部署开场都会冤枉响一发)。只在合并成功后布防——Codex 复现了一个真空窗:终止信号恰好在合并返回的边界到达时,源码已动而标志未立,告警会静默丢失。
双告警噪声 接受「步骤告警 + 状态告警」各响一条 做跨条去重——两者回答不同问题(哪断的 / 留下了什么);去重逻辑本身就是一个新的静默面。
回滚新硬闸的严格度 读不出状态一律拒绝重置 保持宽松——旧行为里「侥幸继续」的多是锁冲突类瞬时失败,已用更稳的读取方式(不抢锁)消掉大半;剩下的真失败本来就不该在状态未知时继续。
自动修复残留? 只检测 + 响亮,不自动修 自动重跑/自动回滚——在「已经出过一次事」的状态上再叠自动动作,风险大于收益;下一次人工发起的重启天然会收敛残留。

🧪验收与测试(可证伪)
  1. 构造「合并成功但后续失败」 ⇒ 必须出现「源码与部署账本不一致」的显式告警,且退出码非零。(对应测试 T5/T6/T13/T14,含一个真实终止信号的边界用例)
  2. 构造「git status 命令本身失败」 ⇒ 必须拒绝 reset --hard 并响亮报警;先在未修复代码上跑出「照常执行了重置」的红灯,证明缺陷真实存在,再修绿。(T1/T2)
  3. 回归:正常部署、正常回滚、演练模式行为逐字不变。(T3/T4/T7/T8/T9)

测试完全复用 FLY-1729 已验证的沙箱基建(假仓库 + 告警捕获文件 + 假 HOME),并写死一条红线:任何整脚本沙箱用例必须把 Bridge 地址指到空闲端口——此前有过沙箱测试误杀生产 Bridge 的真实事故。基线诚实化:现机器上既有重启测试是 124/132(8 个环境项),不沿用旧的「131/131」口径,以 CI 为权威。

🧱诚实边界 — 这个设计做什么、不做什么

做:abort 残留必被宣告(告警+非零退出码);回滚在状态未知时绝不破坏;全部只改一个脚本,零新开关、零新机制。

不做:

  • 不自动修复残留——只响,不修;修复留给下一次人工重启。
  • 告警只说「两个版本不一致」,不判断谁新谁旧、哪边在跑——那超出可证明的范围。
  • 还没走到「布防点」就退出的路径(锁竞争失败、preflight 响亮拒绝等)不做对账——它们没碰源码,里面若有更早遗留的旧残留,本单不负责发现。
  • 每个项目仓库自己的部署小账本(project-deployed-sha)是另一本账,本单不碰。
  • 本单不阻塞已上线的 FLY-1729;真正的风险窗口是下一次真部署——目前自动部署链未加载,且已约定配好 TEAMLEAD_INGEST_TOKEN 之前不做任何部署/重启。
