cmux 稳态修复包 — 设计方案

FLY-1446 · 2026-07-24 · design 阶段 · Codex design review APPROVED(4 轮,findings 8→5→3→0)· 上游:07-23 cmux 事故 Retro
一句话:让「你在 cmux 侧栏永远看得见全队」变成被系统保证的事——修好部署腐化、多实例互踩、丢窗沉默、双 tab、坏账本罢工五个根因,任何一环坏了都报警而不是沉默。

为什么要修(07-23 事故 30 秒回放)

侧栏 tab 数一天内 18→8→7 乱跳、13 个 Lead 没有 tab、名字错挂——你完全失去了对机群的可视。根因链:

① 部署腐化:repo 里修好的同步代码 7 天没进生产,旧版没有单实例保护 → 7 个进程互踩。
② 丢窗即沉默:同步器只认「看得见的窗」,没有「应该有谁」的名册——窗丢了它不找、不报、不建。
③ tmux 地基塌了:托管 runner 窗的 tmux server 整体退出,凶手至今没钉死。
当晚又实锤两个新 bug:同一个窗被收养两次出双 tab;一个坏账本文件让同步器每轮全跳过、零报警(就是那次「tab 一直缺」的真因)。

核心流程:五层防线怎么协同

C · 部署层
合并即部署
PR merge 到 main→ 生产脚本 = symlink 指向主 checkout(git pull 即新代码,无 cp 环节)→ 巡检发现有人换成了副本 → 自动换回 + 报警(三个既有巡检点,零新定时器)
B · 启动层
唯一启动者
launchd 是唯一启动者(KeepAlive 自愈)→ .zshrc / 手动路径降级为「只确保 launchd 在位」,永不再自己拉起实例→ 重启唯一手势:launchctl kickstart -k
A · 对账层
roster 点名
从 launchd Lead 清单自动派生名册(零手工维护)→ 每 60s 点名:该有窗的有没有窗、该有 tab 的有没有 tab→ 缺 tab 且窗还在 → 自动补建 连窗都没了 → 报警(每次故障恰好报一次,恢复后再坏再报)
E · 账本层
收养纪律
收养建 tab 前先查账:这个「槽位」已有归属 → 不再重复建(根治双 tab)→ 坏账本文件 → 隔离进 quarantine + 报警 + 其余照常干活(不再全局罢工)
D · 地基层
tmux 保底
先保全易失证据、出死因报告(不预设结论)→ 给 server 挂保底哨兵会话 + 关掉「最后一个会话没了就退出」→ 批量清理再也带不走整台 server
绿 = 自动修复路径 · 橙 = 报警路径(核心原则:看不见 ≠ 没事,看不见 = 报警)

数据与结构模型(三个关键机制)

机制是什么为什么这样设计
Lead 名册派生 launchd 的 com.flywheel.lead.* 清单 → 期望窗名(逐字一致)→ 按「载具类型」闭集分类:Claude(tmux 窗)/ Codex TUI(精确白名单)/ 其余一律按违规报警 launchd 清单本来就是「谁存在」的唯一真相,零手工维护;分类是闭集——认不出的形态宁可报警也不静默豁免
账本唯一键 收养账本按「代际 + 标题」= 一个可视槽位,唯一约束写进账本写事务内部;改名卡住留下的半成品行由专用守卫安全收尸 07-23 双 tab 就是「按标题找 tab」被改名延迟骗过;唯一键放事务里才没有竞态窗口
报警 episode 每个对象一条持久状态:坏了→报一次;恢复→自动解锁;再坏→再报一次。读取失败(≠真的空)只报「对账盲区」,绝不批量误报 既不刷屏(FLY-1220 的教训)也不哑火(旧去重是永久的,恢复后再坏就再也报不出来)

关键取舍(与被否掉的方案)

  • 否issue 原文的「发版自动 cp + md5 对账」 → 改为强制 symlink 形态。cp 副本模式本身就是这病的宿主(漏跑一次就腐化);安装器的设计终态本来就是 symlink,「合并即部署」天然成立,md5 对账退化为 symlink 健康检查。目标保留,手段替换——Codex review 明确认可这个偏离。
  • 否手工维护 Lead 名册 → launchd 清单自动派生。手工名册第一天就会过期。
  • 否同步器代管 Lead 生命周期(窗没了帮忙重建 Lead)→ 越权。窗的生死归 launchd/Lead 启动器;同步器只管「可视 + 报警」。
  • 切单孤儿 runner 的只读观察窗 → 移入 follow-up 单。四个安全启用前提(日志轮转契约、窗口所有权凭据、不可逆终态白名单、真机场景矩阵)尚未齐备,硬塞进来会带进一个能误关别人窗口的半成品;本单先交付「孤儿 runner 检测 + 报警」,启用契约已在计划里逐字钉死。
  • 守住fail-closed 骨架一律不动:坏账本隔离只处理「纯语法坏」;一切说不清的失败仍然整轮停手——宁可这轮不干活,不可在证据不足时乱动你的窗口。

验收(issue 六条,逐条可测)

#能力修复项
①杀掉任一 Lead 的 tab/窗 → ≤2 分钟自动重建或报警,绝不沉默A
②同时从 3 个路径触发同步器 → 始终单实例B
③改 repo 脚本合并 → 部署自动同步,对账绿C
④server 死因报告 + 防复发措施落地D
⑤改名延迟下反复扫描 → 永不双收养E1
⑥人为塞坏账本 → 报警 + 隔离 + 继续建 tabE2

诚实边界(这个设计不做什么)

  • Bridge 内部的 sessions 状态真相、Discord 渲染 —— 归并行单 FLY-1374(两单不同代码区,可并行)。
  • Lead 进程本身死活的看护 —— 归 LeadWatchdog;本单只管可视层。
  • cmux 应用(Electron)自身的 bug —— 只做同步器侧防御。
  • Codex TUI Lead 的 v1 覆盖 = 存在性检查 + 报警(不代建 TUI);孤儿 runner v1 = 检测 + 报警(观察窗 follow-up)。
  • keepalive 开关只「停止继续执行」,不自动还原已生效的 server 设置(真回滚是显式运维动作,写进 runbook)。
