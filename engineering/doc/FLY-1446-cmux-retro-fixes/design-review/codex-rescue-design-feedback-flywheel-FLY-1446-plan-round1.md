# Design Review — plan.md FLY-1446 (Round 1)

Date: 2026-07-24
Author: Codex
Status: CHANGES REQUESTED

## Summary

总体方向成立：WP-C 回到安装器既定的 symlink 终态、WP-B 把 launchd 固化为唯一稳态启动者，均比新增 copy/md5 发布管道更贴合现有架构；WAL 隔离、rename-lag 去重和 tmux server 防复发也都击中了真实故障面。但当前计划把若干尚不存在的能力当成既有能力：Lead/Runner roster 的身份与状态口径不符合当前源码，E1/E2 的 ledger/WAL guard 不足以执行计划中的收尸/继续语义，D 的证据保全和 keepalive 挂载也未闭环，因此还不能直接实施。

## What's Good (Keep)

- **保留 WP-C 的 symlink 方案偏离。** 安装器本来就以 symlink 作为“repo 更新立即生效”的终态（`scripts/flywheel-cmux-install.sh:40-42`），而 converge 目前只检查已经是 symlink 的路径（`scripts/converge-flywheel-bin.sh:178-193`）。把普通副本判为 shape drift 并恢复 symlink，既解决根因，也避免另造一条 copy/md5 发布链。
- **保留 WP-B 的 launchd 唯一启动者方向。** 当前 wrapper 确实同时服务 `.zshrc` 和 launchd（`scripts/flywheel-cmux-autostart.sh:56-76`），而真正的 mutation lease 已下沉到所有 `--watch` 入口（`scripts/flywheel-cmux-sync.sh:5770-5807`）。把非 supervised 路径降级成 job guard，是小而正确的收口。
- **保留 syntactically malformed WAL 的隔离原则。** WAL 文件名由 view identity 的 hash 决定（`scripts/flywheel-cmux-sync.sh:2728-2749`）；先完成纯语法/文件名校验，再把坏文件移出 `*.wal` 授权集合，能够同时做到零 mutation 与保留取证。
- **保留“不预设 server 死因”、所有新 gate 登记 registry、按 WP 拆 commit、使用 Bash 3.2 与独立 tmux socket 做测试的纪律。** 这些与项目的 fail-loud、可回滚和 source-first 惯例一致。

## Issues & Recommendations

1. **[BLOCKING — A-Lead 正确性] 仅凭 `ProgramArguments` 过滤 `flywheel-lead-wrapper.sh`，并 blanket 豁免 Codex Lead，会漏掉当前生产要求必须可见的 Lead。** 标准 launchd plist 对所有 backend 都写入同一个 `flywheel-lead-wrapper.sh` 和 manifest 路径（`scripts/flywheel-daemon.sh:223-239,303-309`）；真正的 backend 是 wrapper 从 manifest 读取并在运行时 dispatch（`scripts/flywheel-lead-wrapper.sh:92-110,170-200`）。反过来，两个现有 windowed Codex TUI plist 使用专用 `flywheel-codex-lead-wrapper-*`，却正是应纳入 roster 的形态（`packages/teamlead/scripts/templates/com.flywheel.lead.flywheel-codex-infra-bot-lead.tui.plist:10-15`、`com.flywheel.lead.growth-mufasa-lead.tui.plist:9-14`）。更重要的是项目硬规则明确要求所有 production Codex Lead/Runner 都必须是 founder 可见的 windowed TUI（`CLAUDE.md:271-278`）。**建议：**把 roster 派生写成明确的 carrier matrix：标准 wrapper 必须继续读取 canonical manifest 并按 backend/carrier 决定期望窗口；专用 TUI wrapper 必须入册；发现 production headless carrier 应报配置漂移，而不是静默豁免。对任一已加载 plist 的解析/manifest 读取失败应使本轮 Lead roster fail-loud、零局部结论，测试覆盖标准 Claude、标准 Codex、专用 Codex TUI、真正非生产 headless、坏 manifest 和部分 plist 解析失败。

2. **[BLOCKING — A-Runner 可行性/正确性] Runner roster 的窗口键、状态集和 HTTP 契约三者均与当前源码不符，且 launchd watcher 当前拿不到 API token。** Runner 窗名不是 Linear identifier，而是 `<issueId>-<runner>-<title>`（`packages/core/src/tmux-naming.ts:31-42`；`packages/teamlead/src/bridge/tmux-lookup.ts:29-52`）；按 identifier 精确匹配会把正常 runner 全部误报为 orphan。当前 HEAD 已有更强的执行身份：窗口上的 `@flywheel_exec_id`，并已有按 execution id 枚举、合并 cmux alias、对多 window id fail-closed 的实现（`tmux-lookup.ts:67-123`）。状态方面不存在 `parked`：`getActiveSessions()` 是 `running|ship_parked|awaiting_review|approved_to_ship`，readopt 才额外含 `design_done`（`StateStore.ts:4436-4453`）；`GET /api/sessions?mode=active` 也不接受任意状态集（`bridge/tools.ts:134-217`）。认证要求 `Authorization: Bearer $TEAMLEAD_API_TOKEN`（`bridge/plugin.ts:1017-1046`），但 watcher plist 只注入 `FLYWHEEL_CMUX_SUPERVISED=1`（`scripts/com.flywheel.cmux-watcher.plist.template:17-23`），autostart 也只从 `.env` 提取三个 cmux bool（`flywheel-cmux-autostart.sh:15-49`）。**建议：**锁定一个真实契约：优先用 `/api/sessions?mode=active` 返回的 `execution_id` 对 `@flywheel_exec_id`，明确这版精确覆盖的状态；若必须覆盖 `design_done`，应先提供一个有界、鉴权、schema 固定的 Bridge read endpoint，而不是假定现有 endpoint 可参数化。计划还必须写清 `TEAMLEAD_API_TOKEN` 的最小化安全载入、Bearer header、JSON/schema/重复 execution id 校验以及 401/403/timeout 的 episode 行为；做不到时应把 A-Runner 从本 PR 降为 alert-contract follow-up，而不是带着错误默认值上线。

3. **[BLOCKING — A-Runner observer 的 destructive ownership] “实现期再核实日志文件”加上 title-only viewer，不足以安全创建和回收观察窗。** sessions 允许同一 identifier 存在多个 execution，`[orphan] <identifier>` 不是唯一身份；计划也没有给出稳定 transcript 文件、tmux window id/generation receipt 或可证明“这个窗由 roster 创建”的 marker。后续按标题关闭可能撞上同名 observer 或 founder 手工窗口，而现有源码已经记录同名 sibling 是生产现实（`scripts/flywheel-cmux-sync.sh:4024-4029`）。**建议：**要么 v1 只报警、暂不创建 observer；要么在计划阶段先钉死日志来源，并以 execution id 为键创建窗口，写 `@flywheel_orphan_exec_id`/owner marker，持久化 exact `window_id + tmux generation` receipt，关闭前最后一步重验 marker、exec id、generation 和 session 终态。标题可以人读，但不得成为 mutation authority；测试必须含同 identifier 双 execution、同名人工窗、重启后 recovery、真窗回归与终态并发。

4. **[BLOCKING — A 报警 episode/维护语义] 计划声称的“恢复后清 latch、下次再丢再报”并不存在。** `_alert_cmux_cleanup` 的进程内 latch 只在 cmux generation 改变时清空，且最多容纳 64 个 signature（`scripts/flywheel-cmux-sync.sh:130-166`）；下游 event id 又永久由 `project|lead|kind|signature` 决定并写入 claims.db（`scripts/lead-alert.sh:348-419`）。因此稳定的 `lead-window-missing|name` signature 恢复后仍会被 durable dedup，不能形成第二个 episode。另外 maintenance marker 只在 watcher 启动/入 lease 时检查（`flywheel-cmux-sync.sh:5671-5687,5822-5831`）；一个已经运行的 supervised watcher 在维护期间仍会执行 roster。**建议：**像现有 cmux flag transition latch（`flywheel-cmux-sync.sh:4236-4279`）一样设计 durable per-subject 状态与单调 episode counter，恢复时原子写回 healthy，signature 带 episode；Bridge blind、derive failed、Lead missing、Runner orphan 都写明 re-arm 规则。`reconcile_roster()` 顶部每轮检查 maintenance marker，存在时零派生、零 observer mutation、零报警，并明确是否保留还是清理现有 unhealthy episode。还要明确这些报警复用合法的 `cmux_cleanup` kind，或同步扩展 shell/TS kind contract，不能只发明 signature 名。

5. **[BLOCKING — E1 不可按文实施] 三个关键假设与现有 ledger API 相反。** 第一，`ledger_refs_for_title` 只返回 `committed`，完全看不到 rename-lag 留下的 `prepared`（`scripts/flywheel-cmux-sync.sh:3213-3218`），所以照计划加 create 闸仍会复现事故。第二，所谓“既有 close guard 收尸”要求 exact row 已是 `committed`（`flywheel-cmux-sync.sh:3224-3268`），不能关闭 prepared 输家；现有 unreceipted rollback 又只授权 unnamed/provisional title（`:3271-3334`），也不能直接处理已经被补 rename 的 prepared ref。第三，历史双 committed 行不会被 step 3 看见（reconcile 只遍历 prepared，`:3336-3396`），而 `dedup_workspaces_by_title` 在 ledger/invariant 模式下明确直接返回（`:754-769`）。**建议：**新增能够返回 `prepared|committed` 的严格解析 helper；把 `(generation,title)` 不同 ref 的唯一性检查放进持有 inner lock 的 `_ledger_transaction` 写事务中（当前真正写点在 `:3100-3187`），而不只在外层 `_ledger_upsert` 先读后写。为 prepared loser 单独设计 last-operation guard：必须同时证明 current generation、exact prepared row、另一个 exact committed owner、loser exact ref 及允许的 observed title，之后才能 close + remove。历史双 committed 必须另设检测和保守处置；若不能从 exact attachment/source evidence 证明 winner，就 alert/manual，不得声称现有 title dedup 会收敛。并把 `(generation,title)` 表述为“一个逻辑 visual slot”的唯一键，而不是物理 tmux window 身份，因为当前系统允许同名 sibling，并已有 highest-live-window winner 规则（`:4402-4409`）。

6. **[BLOCKING — E2 fail-closed 回归] `recover_view_construction` 的 rc=1 远不止 canonical collision，统一 `continue` 会把不确定的授权失败降级成可继续 mutation。** rc=1 还覆盖 tmux generation 读取失败、WAL 读失败、guard/rename/cleanup 失败等（`scripts/flywheel-cmux-sync.sh:2990-3081`）。当前上游之所以中止，是因为 `prepare_linked_view_state` 随后还会跑 ledger reconcile 和 invariant repair（`:3591-3597`），`refresh_linked_sessions` 再继续执行 mutation（`:4411-4417`）；一个未恢复 WAL 对应的 view 若仍进入这些阶段，会破坏“该记录授权零 mutation”的边界。**建议：**把结果分型，而不是复用单一 rc=1：至少区分 `recovered`、`known_collision_preserved`、`indeterminate_abort`。纯语法/filename malformed 可 quarantine 后继续；已完整证明的 collision 可保留并把该 view/title 放进本轮 blocked set，使后续 ledger/invariant/create 对它零 mutation但允许其他 view 前进；任何 IO、generation、snapshot、guard 或 cleanup 不确定性仍中止本轮。测试除四类 malformed/collision 外，还必须注入 generation read、WAL read、rename guard、stage cleanup 失败，并断言相应 view 及下游 mutation 全为零。

7. **[HIGH — D 挂载/回滚/顺序] server forensics 应先于代码工作保全，keepalive postcondition 也没有可实施的单一挂载点。** 当前顺序把 D 取证放到后段，但 unified log、shell history 和 launchd 记录都可能轮转；FLY-1117 先例使用 raw evidence、derived slice、命令和 hash 的 chain-of-custody，而本计划只承诺一份结论文档。代码侧 `_tmux_socket_ensure_locked` 在 verified/created/rescued 多处分支直接返回成功（`scripts/lib/tmux-server-rescue.sh:540-590,593-659`）；“ensure 成功后顺手校验”必须覆盖每个成功出口并仍处于同一个 socket lock，不能只加在函数尾。watcher 当前 bootstrap 也不调用 rescue（`scripts/flywheel-cmux-sync.sh:5073-5123`）。最后，`FLYWHEEL_TMUX_KEEPALIVE=0` 只能停止未来 enforcement；它不会自动把已经持久化在 server 上的 `exit-empty off` 改回 on，也不会删除 sentinel，所以“旁路后旧行为/server 退出”不是对同一 server 的真实回滚。**建议：**把只读证据保全升为 W0，先保存原始输入/时间区间/时区/命令/sha256，再动代码。提取一个在 rescue lock 内执行、并对同一 reachable PID 做前后验证的 policy postcondition，所有 success action 统一经它返回；失败应产生明确 hold/fail-loud action。为 watcher 定义同一 locked API（或说明为什么只依赖下一次 Lead/Runner ensure 足够），不要在锁外另写 tmux。把 flag 文案改成“停止 enforcement，非状态回滚”，on/off 测试使用两个全新独立 socket；若需要真回滚，另写带 exact sentinel ownership 与空载检查的显式 operator 动作。

8. **[HIGH — flag 传播、WP-C 原子性与 rollout] registry 登记不等于运行进程能读到 flag，rollout 还包含一次不必要且有副作用的 installer 重跑。** supervised watcher 只继承 plist 的一个变量，autostart 只读取三个旧 bool，因此 `CMUX_ROSTER`、`ORPHAN_VIEWER`、`RUNNER_ROSTER_STATES`、`WAL_QUARANTINE`、`TMUX_KEEPALIVE` 和 `AUTOSTART_EXEC` 若只写入 `.env` 都不会按计划生效；D 的 flag 还跨 watcher、Lead launcher 和 Runner launcher 三种进程边界。C 项同时未规定备份失败/并发行为：若为了留档先 `mv` 普通文件，会在 temp symlink rename 前制造真实缺口；仅用 epoch 的备份名也会在三个 converge mount 并发时碰撞。另一方面 `.zshrc` integration 内容始终调用同一个 installed autostart 路径（`scripts/flywheel-cmux-install.sh:52-69`），symlink 恢复后行为已经更新；重跑完整 installer 会额外改偏好、bootout/bootstrap watcher（`:72-156`），无需新增 `--shell-only`。**建议：**给每个 flag 列出 process owner、读取点、`.env`/plist/inherited precedence、非法值 fallback 与生效边界；autostart 继续只做 key-specific parser、绝不 source 整个 `.env`，并为 value/token 分开校验。C 的 archive 先用 no-clobber 的 unique path 做 hard-link/copy，备份失败则零替换；随后在同目录创建 unique temp symlink 并原子 rename 覆盖 canonical path，测试并发 converge、备份失败和 canonical path 全程可执行。删除 rollout 第 4 步和 `--shell-only` 设想，只需 converge + 一次受控 kickstart，并用日志/进程/实际 flag 值验收新 watcher。
