FLY-1604 · Codex 配置合并修复 — 设计方案

FLY-1604P0 阻塞Codex 设计评审 3 轮通过
2026-08-02 · 设计节点交付 · 文档与评审记录随分支入库

① 一句话总结

Codex 昨天往自己的全局配置文件里写了一张表，恰好和 Flywheel 要写的是同一张 —— 旧代码遇到重名只会拒绝开工（于是所有 Codex 施工节点全趴下）；本设计教会它「把我们那一行安全地并进对方已有的表里」，对方的内容一个字节不动，并不动产线上任何其他东西。

② 出了什么事（事故还原）

Flywheel 每次启动一个 Codex 工人（执行代码任务的 AI 实例），都会给它生成一份专属配置文件：把全局配置整份抄过来，再在末尾追加一小块 Flywheel 的内容——里面装的是 GH_TOKEN（GitHub 访问凭证，工人提交代码用的钥匙）。

这块内容要写进一张叫 [shell_environment_policy.set] 的表（TOML 配置格式里的一个小节；TOML 是 Codex 配置文件用的文本格式，规矩是同一张表不许定义两次）。旧代码的安全守卫发现「全局配置里已经有这张表了」就直接报错拒绝 —— 这个守卫本身没错，错的是它赖以成立的前提：「全局配置永远不会有这张表」在 8 月 1 日被 Codex 自己打破了（Codex 升级后自己写入了 3 个键）。

后果：所有走三段式流水线的 Codex 施工节点全部起不来（FLY-1603 已实证失败，FLY-1602 等着撞同一堵墙），所以是 P0。

③ 核心流程 — 修复前后怎么走

修复的核心：报错的死路上开一条合法的合并岔路。先用 TOML 解析器（能真正读懂配置文件结构的程序，而不是靠猜文本）看懂全局配置长什么样，能安全合并就合并，不能就照旧大声报错。

④ 数据与结构模型 — 合并后的文件长什么样

合并后的关键三行（紫色 = Flywheel 新插入，蓝色 = Codex 原有、逐字节保留）：

[shell_environment_policy.set]            ← Codex 原有表头，不动
# >>> flywheel-managed credential — do not edit >>>
GH_TOKEN = "●●●（真实凭证）"
# <<< flywheel-managed credential <<<
BROWSER_USE_AVAILABLE_BACKENDS = "chrome,iab"   ← Codex 的三个键
NODE_REPL_TRUSTED_BROWSER_CLIENT_SHA256S = "…"
NODE_REPL_TRUSTED_CODE_PATHS = "…"

前后两行「标记注释」是这套设计的老机制：下次重新生成时先按标记剥掉旧的再插新的，所以重复渲染永不堆积、需要时可干净移除（术语叫幂等（同一操作做多少遍结果都一样））。妙处在于：插入的这一小块不带表头，紧贴在 Codex 已有表头下面 —— TOML 规则里它天然归属那张表，而旧的剥离逻辑对它原样适用，一行不用改。

⑤ 关键取舍与被否掉的方案

方案结论为什么
文本手术 + 解析器验证（选定）：只在已有表头下插三行，解析器负责「看懂结构」和「验收产物」，不重写文件✅ 采用全局配置 900 多行原文（含注释、格式）逐字节保留；改动面最小；无冲突时输出和现在完全一样
整文件「解析 → 合并 → 重新生成」✕ 否决重新生成会丢光注释、打乱格式，违反「底稿逐字保留」的既有合同；900 行全量重写的故障面大得不成比例
换通道：凭证改回命令行参数传递✕ 否决命令行参数在系统进程列表里人人可见 —— 当初正是为了堵这个泄漏点才改成写配置文件的，不能开倒车
删掉 Codex 写的那三个键✕ 否决治标不治本（Codex 会再写回来），且 issue 明令不许删改

评审里磨出来的三个安全细节（Codex 评审 3 轮、前 2 轮共 9 项意见全采纳）

  • 凭证绝不进解析器：结构验证全程用一个固定占位符代替真凭证，验证通过后再用同一台「构建器」以真值重新生成 —— 因为解析器报错时会把出错行附近的原文带进错误信息，若那里正躺着真凭证，就等于把钥匙写进了日志。
  • 不做全局替换：第 2 轮评审抓到一个真隐患 —— 若配置里恰好本来就含占位符字样，「全文替换占位符」会把不相干的字节也改掉。改为确定性构建器两次生成，底稿字节零替换。
  • 看结构不看长相：旧守卫按「文本长得像」判冲突，会把其他小节里碰巧同名的无害配置误杀。新设计以解析器读出的真实结构为准，正则只用来定位插入点。

⑥ 诚实边界 — 这个设计做什么、不做什么

做

  • 让 GH_TOKEN 并进已存在的 [shell_environment_policy.set] 表（当前生产事故形态），Codex 三键逐字保留；
  • 顺手治好同一守卫的另一半：skills 命名空间（Codex 未来若写入技能配置会撞的下一堵墙），并修掉一个潜伏洞 —— 某种带引号的表头写法旧代码会静默生成坏文件，新设计在写盘前就拦下；
  • 幂等、可撤销、错误信息脱敏（不带凭证、不带配置原文）；无冲突路径输出字节不变。

不做

  • 不碰全局 ~/.codex/config.toml 本身（那是 Codex 的家）；
  • 无法安全合并的怪形态（内联写法、带引号表头、表里已自带 GH_TOKEN、同名技能重复等）不赌、照旧大声报错 —— 尤其「同名技能在 Codex 里谁生效」官方语义未验证，宁可拒绝也不写一份效果不确定的配置；
  • 本设计批准不等于上线授权：合并 PR、重启 Bridge（Flywheel 的常驻调度进程，改动要它重启后才生效）都要等 founder 批准后按自托管上线纪律走。

⑦ 验收路径（两段制）

第一段 · PR 前（不碰生产）：用当前真实的全局配置 + 假凭证跑一遍渲染，验证产物合法且 4 个键共存；全仓 lint / 构建 / 测试门禁；执行「变异判据」—— 把合并逻辑退回旧样子，对应的 8 个新测试必须变红（证明测试真的在测这件事，不是空转的绿灯）。

第二段 · founder 批准合并后：构建 → 重启 Bridge（核对进程加载的确实是合并后的代码）→ 重试 FLY-1602 / FLY-1603 的 implement 节点 —— 工人真的起来了才算数（行为验收，不是测试绿就算）。失败回滚 = 撤销 PR 再重启，无状态迁移。
