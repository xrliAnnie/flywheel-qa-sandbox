① 一句话总结

按你拍板的 Option 2 v2 落成可实施方案:建单一注册表 .flywheel/agents/registry.yaml(nodes 层=每段工作的执行者说明书,graphs 层=流水线),名字一处定义、处处引用、加载时校验;工程设计节点改名 eng_design(显示「设计(工程)」)、产品设计节点 product_design、产品设计流水线 product_design_flow;派工菜单不再自立词表(菜单项=流水线名);迁移零改史——模板发新版本只管新 run,跑过的 run 一个字不动,旧名显示层翻译;顺手删掉 11 个零使用模板和三个残留文件。

② 两层注册表(核心结构)

今天名字散落在 5 个地方互不引用(派工菜单、模板库、模板里的节点、config 注册键、真正的 md 文件),所以一个 design 能同时指三件事。注册表把定义收成一处:nodes 层登记每个执行者(名字、说明书文件、展示名、行为类),graphs 层登记每条流水线(只许引用已登记的名字)。加载器(loader = Bridge 启动时读配置的程序)三道硬校验,写错名字直接拒绝启动,不会带病运行。

增量修订六条流水线全部展开:工程开发、轻量开发、产品需求、产品设计、原型验证、通用。PM、产品设计执行者、Prototype 三个单节点业务 DAG 已在注册表中,现在不再被图里的省略号藏住。

②A 项目身份边界(增量裁定)

节点 id 不加项目前缀。运行时身份不是裸 nodeName,而是 (project, nodeName);统一 IC markdown 来自 bundled registry,项目差异由 project overlay 提供,记忆按 (project, identity) 分桶,因此跨项目同名不会调用错执行者或串记忆。展示名需要时可以带项目。personal-assistant 的 companion 转换由 Tadashi 在激活阶段作为 operator 执行;目标 registry 不存在或 bundled/project 两入口校验失败时,系统拒绝激活并保留旧 loader。

③ 菜单收编 + 展示名(前端零编名)

派工菜单不再有自己的词表:Lead 派活时选的就是流水线名(code、product_design_flow……),一份词表两处共用,这是你要求的 A+B 融合。每个名字都带 label(label = 给人看的展示名),两个前端接口(派工菜单、DAG 管理视图)都返回 label;前端只显示后端给的 label,不再出现裸 id,更不自己编——「后端叫什么我们就显示什么」。

现状实证:管理视图代码里 name: node.id、标题直接拼分类裸词——都在这次一并改为 label。

④ 零改史迁移(沿用你同意的原则)

模板发新版本(版本+1 = 同一个模板追加一个新版本,旧版本原样保留),只有新 run 用新名;跑着/跑完的 run 连同它的历史记录一个字不改。旧 run 的旧名由显示层翻译成新展示名(如 design → 「设计(工程)」;同名 produce 按所属模板区分翻译)。需要认识旧名的代码分两类管:A 类是历史解码(读旧快照、旧分类词、显示翻译)——历史 run 永远存在,这几处永久保留,保证多年后的旧 run 依然打得开;B 类是活跃旧 run 的执行分支——打 FLY-2121-legacy 标记,「收场哨」脚本定期数还有多少旧名 run 在跑,归零那天开收尾 issue 只删 B 类,双名执行彻底退场。founder 中文说「设计要返工」这类指令,系统按每个 run 自己的图纸解析到该 run 的实际节点名,旧 run 新 run 都指得准。零停机、每步可回退。

审计里揪出的一个隐形炸弹已拆:快照解析器会拿旧 run 里存的分类词对照现行词表校验,词表一换,所有旧的产品设计 run 会「读取即报错」——五处兼容里专门有一处就是给它的放行。

⑥ 关键取舍 + 与简报的差异标注(按你的授权)

你说过设计时发现问题可以改、但要标明差异和理由。本方案与简报的差异共五处,全部只是落地精化,不改你拍的架构:

差异1模板的内部存储编号(tpl_code 之类)不换新号:「版本+1」按字面执行=同一行追加版本;这些编号降级为无人念的内部键,所有人看到的名字全是流水线名和 label。换新号会让新旧 run 分家,三处要写双行逻辑,复杂度不划算。

差异2prd/prototype 的节点一并改名 pm/proto:它们和产品设计节点原来都叫 produce——同一个词指三段不同工作,和 design 同病;注册表「名字全局唯一」的规则下重名根本注册不进去,属于架构的必然结果。

差异3nodes 层带一个行为类字段:引擎判断「这节点能不能开 PR、走哪条完成路线」的内部分类词冻在历史快照里,改它=改史,违反零改史;所以行为类作为注册表里的声明字段保留原词。

差异4「旧名删干净」的语义按简报修订:issue 原文禁双名层;你后拍的零改史要求过渡双名。取后者,但把双名压缩到五个显式标记处+可执行收场判据,守卫对其余全仓照旧零容忍——两个决定的交集,不是弃守。

差异5config 引用形态定稿:「config 不再重复定义」落成 node: 注册名 引用;执行者归属哪个部门也改为注册表里的显式字段(今天靠文件放在哪个目录来猜,搬家就会猜错);标签路由专用的 engineer / product_designer 也进 nodes 层注册(不进任何流水线)。

差异6派工接口的字段名不改:「词表消失」落成合法值收编(只认流水线名),但接口/存储里那个字段的名字保留——改字段名要全量排查所有外部消费者(FLY-1914 级),纯代价零收益。

否决role 改名 product_designer(与既有 product-designer 只差一个符号=制造新撞名)· 运行时旧名改写(改史)· 只改展示名不改 id(把病藏进皮下)。
