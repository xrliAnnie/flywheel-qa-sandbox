只做设计marker 必须有出处不 PR / 不 ship / 不部署

一句话：当前节点只确认自己拿到了写入权并设计后续合同；只有收到明确文字的下游执行体，才可以把那段文字逐字追加到 probe.txt 并在本地提交。

1 · 为什么现在不写 marker

金丝雀（canary）是一项很小、隔离运行的探针，用来确认一条传输链路真的把消息送到正确的人。

TURN是服务器授予某个工作流节点的独占写入权；当前返回了 yours，所以 design 文档可以写，但 TURN 本身不包含 marker 内容。

执行体（execution）是一次有独立身份的 agent 运行。当前执行体是 Codex design，不是外部 driver 启动的 Claude fixture；它的 inbox 也明确返回 No instructions.

结论：记录真实的 TURN 回执，拒绝伪造另一条 Claude 链路的完成证据。Lead 已确认这条边界。

2 · 核心流程

phase（阶段）是工作流中职责固定的一段。Design 只交付文档和审查；后续 implement 阶段也必须先拿到自己的 TURN，再检查是否真的收到 exact marker。

橙色菱形是授权或内容门；红色节点表示必须停下，不能自行补值。

3 · 数据与证据模型

provenance（出处链）说明一段文字是谁发给谁、为什么允许落盘。它把 TURN、Lead instruction、文件和 commit 连成可核查的证据，而不是只看文件里“像不像”成功。

commit（提交）是 Git 中不可变的一次本地快照。Probe commit 只能包含 probe.txt，并且明确不 push。

身份execution id + vendor + phase，防止拿别人的回执充数。
授权TURN 只回答“谁现在能写”，Lead instruction 才回答“写什么”。
落盘每条 raw literal 完整行出现一次，已有内容全部保留。
审计本地 SHA、路径清单和带 instruction id 的结构化回报互相印证。

4 · 关键取舍与拒绝方案

  1. 采用：TURN + 条件式 marker。 真实性最高；没有 literal 就不写，稍慢但不会误报。
  2. 拒绝：从 issue title 推导 Claude BOOT / R4。 外部 driver 会同时检查原生消息、ACK 和 Claude 身份；只抄文字会制造假阳性。
  3. 拒绝：自定义 owner + 时间戳 marker。 可读但没有发送方，也不满足“requested marker”的逐字合同。
  4. 拒绝：让 design 直接写 probe。 会混淆阶段职责，让设计审查绑定到已经发生的实现。

5 · 诚实边界

DAG（有向无环工作流）把 design、implement、QA 等步骤按依赖串起来；节点不能替 orchestrator 派发后继或扩大权限。

这份设计会做到：完成三份设计文档、设计审查、Founder HTML；为后续 exact marker append 给出可执行合同。

这份设计不会做到：创建或修改 probe.txt、声称收到 Claude native mail、改产品代码、创建 PR、push probe、请求 ship、merge 或部署。

如果后续执行体仍没有收到 exact marker，它必须报告 TURN 已确认但 marker 缺失，然后等待；“没有值”不是可以猜值的许可。
