1. 一句话

你每在一张 ship 卡上批准或打回一次,系统就在同一笔账里顺手记下「如果自动道开着,这张卡会不会被机器直接合掉」;两周后一条只读 SQL 把这些记录算成三个数(N1 / N2 / N3)和四条线各自的覆盖率。你的动作一点不变,规矩一条不改,一次都不真的合并。

来源PR #1063 build-issues.md §B4;PRD §4.2「四条记录线」、§5.1「一张表三个数」、§5.2「N1 = 0 才放手」
你已定的判据纯文档类错判率(你本人口径)为 0 才放手;不为 0 连它也不开。任一记录线覆盖率不到 100%,这张表不作数。
今天的现状B2 的判决台账已在跑(库里 19 条判决);B1 的全仓分类器已上线;B3 的强度二台账刚上线、还是 0 行。但判决和「机器当时判的类」之间没有绳子:19 条里只有 12 条还能找回当时的分类快照 —— 照今天直接算,第一天覆盖率就不到 100%。
这单做什么① 判决落库的同一事务里冻结一行「影子观察」;② 给 Lead 一条用自己 Discord 身份声明「这单属于哪一类」的通路(四选一,没有自由文本);③ 一份只读 SQL + 脚本,任何人拿库副本都能复算。

名词:ship 卡 = Bridge 发到 Discord 让你批准/打回的那张卡;影子跑 = 规则照旧由你把关,系统只在旁边记「如果自动道开着会怎样」;纯文档类 = 改动全部落在 6 个文档目录里且 ≤ 50 个文件,机器今天已能判;强度二 = B3 定义的两半——在真环境跑过 + 留下别人能查能重跑的记录;Bridge = Flywheel 的调度服务进程;Lead = 管 runner 的 AI 组长(Tadashi 这一类)。

2. 核心流程

三条线并行:你照常过卡;Lead 在自己的频道用 bot 身份发一句「这单属于哪一类」并跑一条命令;两周后任何人拿库副本跑一份 SQL。

四条记录线各自落在哪

#记什么落在哪什么时候写
①机器判的类(纯文档 / 含代码 / 判不了)影子观察行(新表)你批准/打回落库的同一事务里,用 B1 的判定核算一次并冻结
②人判的类(Lead 四选一)类别声明行(新表)Lead 看到卡后任何时候;晚于你的判决也收,但单列「声明晚于判决」
③强度二两半(真环境跑过 / 外部记录可取)影子观察行(同一行)同 ①,只看判决时刻之前 B3 台账里的行
④你有没有打回、是不是你本人B2 的判决台账(不动)已在跑

为什么一定要在「同一事务里冻结」:分类快照是一张会被覆盖、会被清理的当前态表(gate 会话结束后就删),等两周后再去查已经没了;而判决台账是只追加、不可改删的。把观察行和判决行绑在同一笔写入里,它们就同生同灭,覆盖率才能真正 100%。事务 = 数据库里「要么全部写进去、要么全部不写」的一组操作。

3. 数据模型

只加两张表,都只追加、不可改删(数据库触发器直接拒绝 UPDATE / DELETE);不改 B1/B2/B3 的任何表。

影子观察 auto_merge_shadow_observation

  • 主键 = 判决 id,一条判决恰有零或一条观察。
  • 机器判的类三态 + 原因;强度二两半各自状态 + 原因 + 依据行。
  • 冻结输入事实(每个候选 PR 的仓、号、期望 head、快照 head、快照年龄),≤ 16 KB,由编码器保证上限。
  • 观察写失败 ⇒ 只回滚观察、判决照常提交;代价是两周表作废。宁可作废表,不碰你的批准路径。

类别声明 auto_merge_shadow_declaration

  • 四选一枚举:纯文档类 / 配置类 / 单点修改类 / 其它代码。没有任何自由文本字段(有了两周后就没法统计)。
  • 声明属于一张卡,不跨卡、不跨单回填;再声明 = 新行,最新一条生效。
  • 声明人由 Bridge 从项目名册派生,不信请求方自填。
  • 每条声明绑一条 Lead 自己 bot 发的 Discord 消息,一条消息只能用一次。

名词:head = 被评审代码的精确 40 位提交号;bot 身份 = 每个 Lead 在 Discord 里的机器人账号,它的 token 只有 Lead 自己有,runner 拿不到 —— 这是本机上唯一 runner 冒充不了的 Lead 身份,所以「这单属于哪一类」只认它发的消息。

4. 两周后那张表怎么算

先算「这两周你在 ship 卡上一共动了多少次」(批准 ∪ 打回 ∪ 进了死信的动作,不依赖四条线里任何一条),再看四条线各自是不是 100% 覆盖;不到 100% 表就作废,但数字照样全部打印。

数定义(PRD 原文口径)怎么读
N1机器判纯文档、Lead 已声明类别、到过你门前的单里,你本人打回的单 / 这类单总数放手判据本身。分子分母都打印,分母为 0 时只打「0 / 0」不打比率
N2同上,分子放宽到「以 founder 权限打回」(含 Lead 引你原话提交的)上界。另单列「全部打回(含 Lead / operator)」作最宽上界,不冒充 N2
N3N1 分子那几条的逐条原话(你说了什么、哪张卡、哪个 head)「率」会掩盖「这一条有多严重」,你要看的是具体哪几条

报出来的还有

  • 四条线各自的覆盖率 covered / 全集(死信动作算在分母里,所以会显示 10 / 11 而不是 10 / 10 外加一行)。
  • 「未声明」的卡(按 PRD 不进分子分母,单列);「声明晚于判决」的卡数;机器判不了的卡数与原因分布。
  • 强度二:无台账行的卡数(起跑期预计几乎全是,因为 B3 台账刚上线)、exact head 无行但同单别的 head 有行(「绑定失败」)、判决后补账。
  • 两个从 B1 带过来的代理指标:「声明 PR 快照年龄 > 30s 的纯文档卡数 / 纯文档卡总数」——不等价于误判单数,精确数需 PR head 变更事件台账(Lead 已接受此口径);「判决后新增的 nested 评审 (仓, head)」——上界。
  • 每一个 0 都带全集:「30 个里 0 条」才是结论,单独一个 0 不是。

名词:死信 = 你在 Discord 上的动作因为绑不到 head 等原因没能落成判决,被系统放进「处理失败」的桶里;它是一次真实动作,所以算在全集里、四条线都记为未覆盖。只读 SQL = 一份查询脚本,先把库备份一份再以只读方式打开,永不碰生产库。

5. 关键取舍与被拒的方案

问题选了拒了为什么
机器判的类在报表时刻已经不在了选判决落库的同一事务里冻结一行拒两周后 join 现状表;拒给分类快照表加历史表前者实测 19 条里只有 12 条能找回;后者要改刚过四轮评审的 B1 写路径,还得把 60 秒时效判定再写一遍
Lead 声明谁来认选Lead 用自己 bot 身份发一条 Discord 消息,Bridge 取回核对作者、正文、时间、频道拒只靠 Bridge 通用 token 加一个 declared_by 字段那个 token runner 也有,本机同用户什么秘密都读得到;唯一 runner 拿不到的是 Lead 的 bot token(B2 核实你的消息用的就是这一手)
声明属于卡还是属于单选属于卡拒属于单、最新一条覆盖全单否则返工后第二张卡的声明会追溯套到第一张卡上,把「未声明」洗成「已覆盖」
观察写失败怎么办选只回滚观察,判决照常;表作废拒观察失败让批准也失败;拒加开关 / 重试 / 补写PRD 定的 fail 方向就是「表不作数」,而不是动你的批准路径;不加旋钮是你 9-6 定的
未声明的单算不算选照 PRD:不进分子分母,单列;同时线②覆盖率不到 100% 表也作废—两条都是 PRD 原话,同时成立;这意味着 Lead 一张卡不声明整张表就不作数 —— 这是 PRD 定的,不是这单放宽或收紧的
两周从哪天起算待你拍报表窗口做成必填参数,库里有一个「观察表上线时刻」作最早下界拒写死在代码里你 9-6 未定(PRD Q1);Lead 9-8 裁「按默认写,起点可配置」。建议:观察表上线后首个 UTC 零点起算两周

6. 诚实边界 —— 这单做什么、不做什么

做

  • 每条判决同事务冻结一行影子观察(线①③)。
  • Lead 身份可核实的四选一类别声明(线②)。
  • 一份只读 SQL + 包装脚本,四线覆盖率、N1 / N2 / N3、卫生指标,每个 0 带全集。
  • 两层隔离测试证明这两张表不进任何合并判定。

不做

  • 不写任何合并执行代码;不动 merge 授权契约。
  • 不改你的卡文案、不改你的任何动作、不改 Lead 的任何规矩。
  • 不改 B1/B2/B3 的表、判定核、review-hold。
  • 不补历史:观察表上线前的判决永远没有观察行,窗口外报条数。
  • 不做配置类 / 单点修改类的机器判定;不做 B5。

已知限制(实现不许悄悄声称覆盖)

  • 「33 秒窗口误判」算不出真实命中数,报的是代理指标(快照年龄 > 30s),Lead 已接受此口径;精确数需 PR head 变更事件台账,那是 B5 时再看。
  • 强度二起跑时几乎全是「无台账行」——B3 台账 9-8 才上线,今天 0 行;这是事实,作为数报出,不折进「不满足」;对 N1 / N2 没有影响。
  • 「你本人」= B2 的绑定事实(你在该卡 thread 里、卡发出之后、经 Bridge 核实为你所发的消息),不是意图判断。
  • N2 的「founder 权限」在今天的库里不含 operator 重开(那条写的是 lead 权限);另报最宽上界,改口径要改 PRD。
  • 声明依赖 Discord 可达:Discord 长期不可达 ⇒ 线②覆盖率掉 ⇒ 表作废,照实。
  • 一个 flaky 的端到端测试偶然全绿照样进台账、照样判满足;B3 无新解法,B4 亦无。
  • 只覆盖 land / git_head 这类 founder 门(B2 只记这类判决)。
