01 · 先看结论

这次修好了吗？

修好了，而且实际情况比工单里写的更险。工单说缓冲还有 1.3 分钟；我去量最近一次 main 上的真实跑批，它已经跑到 19 分 21 秒 —— 上限 20 分钟，只剩 39 秒。拆分之后两条车道分别是 10 分 39 秒和 10 分 14 秒，各占上限的 53% 和 51%。

原来会怎样

50 个测试排成一条队串行跑，占满上限的 97%。任何人再加一个测试、或者机器当天慢一点，就会被系统在 20 分钟处掐断。掐断后的报错长得跟 flaky 一模一样：时好时坏、重跑有时能过 —— 于是下一个人会当成偶发问题从零重查一遍。

现在会怎样

同样这 50 个测试被分到两条并行车道，各占上限的一半左右，加起来的墙钟时间反而从 19.4 分钟降到 10.7 分钟。另外每条车道跑完会自己量一次用时，一旦超过上限的 85%（17 分钟）就把这条车道判红、连带把 PR 的必过检查 CI OK 判红，错误信息第一句就写着「这不是 flaky」。

QA 判断： PASS。工单的三条验收全部达成，而且不是靠推算 —— 时长是从真实 CI 跑批的接口里逐步骤取回来的；「测试一个没少」是拿真实执行过的步骤名做集合比对（不是只读 YAML）；报警会不会真的响，是用 9 个人为破坏实验逐个验过的。

02 · 怎么修

病根和修法

这不是某段代码写错了，是一条车道装太满。测试套件这两年一直在加，车道容量没动过，于是余量被慢慢吃到只剩 39 秒。

真正的病根

Script Tests 是一条串行车道：50 个 shell 测试步骤一个接一个跑，总时长 19 分 21 秒，上限 20 分钟。其中 4 个测试就吃掉 55%（647 秒），而它们慢是因为在等真实的东西 —— 真 tmux 服务、真重启闸门的 36 秒空转、真 15 秒超时证明 —— 把这些等待缩短就等于不再测真实行为。所以病根不在这 4 个测试，在「只有一条车道」。

修复原则

不缩短任何一个测试，不降低任何覆盖，也不靠单纯把上限调高来买时间。做法是把同一批测试分到两条互不依赖的并行车道上，再给每条车道装一个自己量自己的报警 —— 报警的落点选在「会挡住合并」的地方，而不是一个没人看的告警频道。

具体改了什么

  • 把原来的 Script Tests 拆成两条并行 job：车道 1（cmux / session，13 个测试步骤）和车道 2（fleet / setup / packaging，38 个测试步骤）。步骤是整块搬家，连注释一起，没有改动任何测试内部。
  • 每条车道开跑第一步记下时间、最后一步量一次用时；超过上限的 85% 就判红，并打印一段明确写着「这不是 flaky，是快撞上限了」的处置说明。没超线的轮次也会打印一行观测数字，方便日后看趋势。
  • 给这套结构加了机器守卫：两条车道各自的测试清单、顺序、超时上限、报警参数、以及 CI OK 必须同时依赖两条车道 —— 任何一项被改动或漏掉，守卫会先变红。这是防止「以后有人顺手删掉一个测试，CI 却还是绿的」。

单测 / 集成

40 项契约断言全通过：报警脚本自身的 36 项（含参数校验、时钟异常、以及 1019 秒放行 / 1020 秒判红的边界），加上 CI 工作流守卫的 4 项。另外 10 项是我自己做的破坏实验：先确认守卫在未改动状态下是绿的（防止它是个永远绿的空壳），再逐个注入 9 种破坏 —— 删掉一个测试步骤、删掉报警步骤、删掉计时起点、把 CI OK 的依赖砍掉一条车道、把报警阈值偷偷调松、把上限和报警参数改得不一致、把上限压到 20 分钟以下 —— 9 次全部被守卫抓红。

真机验证

真机 = 真实的 GitHub Actions 跑批，不是本地模拟。在最终 commit 上的那一轮：车道 1 用时 639 秒（53%），车道 2 用时 614 秒（51%），报警步骤本身也在真实日志里打印了 usage=52% 和 usage=50%。同时我取回拆分前 main 上最近一次成功跑批做对照：1161 秒 = 上限的 97%。最关键的一项是拿三轮跑批里「真实执行过的测试步骤名」做集合比对：拆分前 50 个，拆分后 13 + 38 = 51 个，少的 0 个、重复的 0 个，多出来的 1 个正是新增的报警自测。

最终验证 commit： 92f31f49da1199b3f5e88d972d79dafef5f3b278 · 结果： CI 全绿（Quick Gate 构建/类型/lint、Unit 五个分片、两条 Script Tests 车道、payload 分发、CI OK 汇总）。分支保护接口确认 CI OK 是 main 上唯一的必过检查，且它的判定是「所有依赖 job 都必须 success」。

06 · 诚实边界

什么没测，为什么

没有藏起来的空白

三件事没测到，都不是漏做，是这次的能力边界：① 真正撞上限的那一轮，报警本身发不出声 —— job 连同它的步骤会被系统一起杀掉；② 拆分后只积累了 2 轮跑批，两轮都绿，所以「两条车道之间没有隐藏的先后依赖」是经验支持、不是压力验证；③ 这次没有任何 Discord / 聊天链路可测。

原因： ① 是这个做法的固有边界：任何跑在 job 里的报警，都无法在 job 被杀掉之后再说话，它的价值在 85%～100% 这段「还来得及」的区间；② CI 跑批需要真实推送才能积累，两轮是本次窗口内能拿到的全部；③ 这次改动只碰 CI 配置、一个报警脚本、几个测试文件和文档，代码里没有任何发消息 / 转发 / 渲染 / founder 交互的面 —— 所以按规矩明说：本单没有 N-to-N 面，改用真实 GitHub Actions 跑批 + 9 个破坏实验来验。

风险与补测时间： ① 的残余风险是「一步跨过 85%」：现在离报警线还有约 6 分钟增长空间，要一次性多出 6 分钟才会毫无预警翻崖，可能性低但不为零；真发生了，症状仍然是超时，只是少了提前一轮的提醒。② 会在接下来几轮 main 跑批里自然消解，不需要额外动作。另有一条设计上的软点值得知道：把上限和报警参数同步调高（比如都从 20 改成 40）是能通过全部守卫的 —— 这是有意留的最后手段，但它意味着「提高上限」这条路除了代码评审之外没有额外阻力。
