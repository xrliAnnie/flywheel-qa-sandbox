FLY-2076 Claw 值守上岗:每条告警都有人先看一眼,并且只有三种去向

0一句话

Claw 今天每条告警都签收、几乎每条都「Standing by」——近 7 天签收 5,034 批、说了 208 次「我在待命」、0 次提到 runbook。PRD 说「没有第四种去向」,第四种去向正是它现在的常态。本单把它改成 alerts 频道唯一的值守席位:每条告警它都先看,看完必须落到「① 自己解决 / ② 查册子找人 / ③ 兜底给 Tadashi」之一,并在那条告警的 thread 里留一帖。

术语先解释一次:Claw = claude-infra-bot-lead,Claude 侧的基础设施机器人;签收 = 它的会话「收到了」一批消息(不等于处理);runbook = 「这类问题怎么解决」的手册;contact book = 「这类问题该找谁」的册子;thread = Discord 里挂在一条告警下面的讨论串,是这条告警的公共记录。

1今天怎么回事:它执行得很准确,是合同错了

Claw 的角色文件写着三条:「只响应显式 @ 我的工单」「没被 @ 的工单不动手」「修不掉才 @Annie」。它照做了——而且做得很准。近 7 天的会话记录里,它签收了每一批,然后:

它说的话次数意思
「Standing by」208签收后不动
「no action needed」65判定「不归我」
「outside my toolset」22判定「我没工具」——然后也没转给任何人
提到「runbook」0没有任何沉淀
原话(会话记录):「Acked and triaged. Summary: cmux_watcher_stalled (severe, …) is a host-daemon watchdog issue outside my toolset … Standing by.」—— 一条 severe 级告警,它判定「不是我的」,然后就没有然后了。

另一个事实它在告警频道有发言权:近 7 天发过 64 帖。所以「留痕」不需要新权限。

CassPRD 担心 Cass 和 Claw 「都有点负责 = 都不负责」。查下来 Cass 事实上已经不在值守位上:她的角色文件对「alert」零命中,她的 Discord 配置根本没订阅告警频道,自动修复的执行者是 Bridge 里的一段代码不是她。所以本单只需把「席位唯一 = Claw」写成字,不用「移交」什么。

2核心流程:每条告警,三个去向,没有第四种

这张图是 Claw 新角色文件里的动作序列。关键是中间那个菱形:「runbook 有这一类,且动作在授权范围内」两个条件缺一个,就不许动手——只许看和查(读日志、看状态),然后转出去。这就是「宁转勿吞」:不确定时把一个还能诊断的现场原样交给能诊断的人,比试探性乱修更有价值。

图 1 · 值守初审的动作序列(绿 = ① 自己解决;蓝 = ② 找到人;紫 = ③ 兜底)

每条工单一帖,格式固定,这样验收能机器核对。这帖由 Claw 用它现有的 Discord 回帖工具发;规矩写在角色文件里:先发帖、再记账(记账 = 这条处置完成;重启后只重做没记账的,所以处置不会丢)、发帖前先看 thread 里有没有自己的 🧭(看不了就不发)、@ 只允许一个人(转给谁 @ 谁;自己解决或归 Codex 机器人的一个都不 @)、已经被系统自动修好的只记账不发帖。反面「发了帖、还没记账」那一瞬间它重启,会多发一帖——见 §8 交你判的缺口 G1。

🧭 值守初审 · <kind> · 去向 ① 自己解决 / ② 转 @X / ③ 兜底 @Tadashi
看到:<现象,一两句>
查了:<只读动作清单>
依据:<runbook 命中 | contact book 命中 X | 册上没有(③)>
根因线:<代码/配置问题 → 已开 FLY-xxxx | 判不清,已知到 <步>>
落账:待执行 ack | handoff --to <leadId>(发帖之后调;这里写 Lead 的 id,不再 @)

永不 @Annie值守自己永远不 @ 你。兜底是 Tadashi;要不要惊动你,是接手的人判断的事,或者你自己翻「没解决」的 thread(PRD R6)。这与今天「修不掉就 @Annie」的合同相反——是按 PRD 主线改的。

压力自述「压不过来必须主动说」:Claw 自己看得见的堆积信号只有「上一批还没落完去向,下一批已经到了」和「启动补扫发现一堆没人看过的」。任一出现,它在频道发一帖 @Tadashi 说明积压形状;同一积压期只喊一次(账本里记一个「已喊过」的标记,重启也不会重复喊,欠账清零时自动解除)。没有阈值、没有 SLA、没有考核——它是一个行为,不是一个指标。

3它怎么「看到每条消息」:翻一个已经存在的开关

Claw 的 Discord 插件(它连接 Discord 的那个程序)对每个频道有一组「门控」设置。告警频道那一组现在写着 requireMention: true——「没 @ 我的一律丢掉」。本单把它翻成 false。翻了之后走的路,就是 8 月 14 日之前每天在跑的那条路:插件放行 → 写进 Claw 的信箱 → 唤醒会话。不新增任何一层。

图 2 · 接入管道(橙 = 本单翻的那个开关;红 = 现状被丢掉的消息;绿 = 既有管道;虚线 = 启动时的补扫)
选项做法为什么不选
A · 翻插件门控(选它)改一个布尔值,启动时用脚本幂等落地—— 反面:它会看见一切,所以角色文件必须写死「只在工单 thread 里回、一条工单一帖」,否则会重演 FLY-220 的刷屏回环
B · Bridge 再造一个频道轮询器投它信箱新代码第二条 Discord 入口 = 新增一层;且与 2075「撤信箱腿」方向相反
C · Claw 自己定时拉最近 100 条用插件的 fetch_messages要外部唤醒、上限 100 条、爆发期会漏、空转烧 token。保留为启动时的补扫,不做主路
D · 保持现在的信箱腿不改接入与你 07:12Z「不双发,只发 Discord」的裁定相反,2075 正在拆;且信箱里的一行没有 thread 可留痕。若你改口,只换这一节:落账改按 event id 查,角色文件不变

翻开关的脚本仿照 FLY-898 那个(原子写、先备份、幂等、坏 JSON 就拒绝、绝不创建新组),每次 Claw 启动都跑一遍,所以重装 / 重建后不会悄悄回到 true。它还做一项预检:发告警的那个 dispatcher 机器人必须在 Claw 的「允许机器人」名单里——插件在门控之前就先按这份名单过滤机器人作者,名单里没有它,开关翻了也白翻(今天名单里恰好有它,但那是巧合不是保证,脚本把它变成保证)。启动日志固定打印一行 [alert-duty] seat=… gate=… dispatcher=… token=…,失败原因不吞。

4账本模型:认领和去向记在哪本账上

PRD 数出「0/497 从未认领」用的是 alert_threads(告警工单账本,一条告警一行,记它开了哪个 thread、谁认领、什么状态)。今天只有一条路能往这本账写「ACK」,而且那条路只服务两种登录过期告警,值守用不上。本单不加表、不加列(Tadashi 的「只删不加」):值守「处置完成」= 写这本账里两个月从没被写过的那个 acked_at;转给谁 = 写既有的 owner_ref + 状态 ESCALATED;解决 = 走既有的解决路径。一条新路由 + 一个命令行,就这些。唯一的删除:今天还有另一条路会往 acked_at 写(Codex 机器人做账号救援时「顺手认领」,救援一开始就盖章、不管结果)——它两个月一次都没触发,但留着会让「已认领」和「值守处置完了」混成一个字段;删掉它,这个字段只剩一个意思。

认领与状态分开2075 保留了 Bridge 的自动修复:一条告警开 thread 的同时,Bridge 可能已经在修(REPAIRING)或在观察(MONITORING),甚至已经自动修好(RESOLVED)。值守的「看过了」只盖 acked_at,不去改动 Bridge 正在推进的状态;已经自动修好的,值守只记账、不发帖。

第二把钥匙写账本的路由挂在一个独立入口上,只认一把专用钥匙(只交给 Claw 的进程),不认所有 Lead 共用的那把;两把钥匙相同时 Bridge 拒绝启动。诚实地说:所有 Lead 跑在同一个系统用户下、配置文件对谁都可读,这把钥匙防的是误用,不是能挡住一个存心作恶的 Lead——那需要换一种凭据,另开单。

断掉了怎么办Claw 重启后按账本列出「还没看过」的工单(一条查询,没有上限),逐条从头走。

不是第四层告警这几条路由只是值守对既有工单动手的「手」:盖时间戳、改球在谁手上、改状态、同步根消息那行 🎫。它们不发任何告警、不 @ 任何人、不给你发任何东西;要 @ 谁,是 Claw 自己在 thread 里发的那一帖。

ESCALATED 这个状态原来的意思是「无人认领超时」(PRD §1.3 那 425 条);2075 删掉了自动产生它的路径之后,本单把它复用为「值守已转出,球在 owner_ref」——不加新枚举。这是工程裁定,Tadashi 拍。

这本账的两个天生缺口(本单不封,交你判,见 §8)(G2) 同一类问题连续发生两次,第一次还没初审、第二次就到了:这本账只记最新的那次,第一次的行被覆盖、thread 被归档,于是第一次没有自己的去向——与 PRD「每条都要落到 ①/②/③」冲突;封它要按「每次发生」另立账本,Tadashi 的「只删不加」不允许。(G3) 根消息发出去了但 thread 没建成的工单,这本账里没有它,值守认领时找不到行——那是 Bridge 开 thread 那段代码的事,归 2075 / Epic。

5关键取舍与被否掉的方案
取舍选了什么反面(不藏)
「不许装懂」按什么切按动作会不会改变系统状态切,不按告警种类切。只读永远允许;改状态只在「runbook 有这一类 且 动作在既有授权范围内」时允许前期 runbook 几乎是空的 ⇒ 前期几乎全部走 ②/③,Tadashi 兜底压力先高后低(PRD §6.3 说的沉淀期净增负担,本单没有解法,只有「压力自述」这个补救)
解决后「立刻写 runbook」怎么落Claw 立刻写成完整条目:贴在 ✅ 帖里 + 写到 state 目录的草稿文件;进仓库由 2077 定义的收割 PR 完成两步走,草稿可能堆积。另一条路(让 bot 直接在生产检出上 git 提交)踩 FLY-2048 那类 worktree 事故与「不碰产品代码」两条线,所以没选;Tadashi 若要 Claw 自己开 PR,那是新的授权面,另开单
根因线(R8)怎么做每帖带一行;判定代码/配置问题 → 用 Linear 建单(先搜同类未关闭的单,不重开);判不清 → 只写「已知到哪一步」2075 删掉了「同类升级 3 次自动建单」;本单用人工判断接替——差别是带着「为什么」而不是只数次数
「值守席位是谁」写在哪代码里一个常量(claude-infra-bot-lead),启动脚本、路由鉴权、日志三处共用不做配置面:席位唯一,没有第二个候选,配置面只会制造漂移
Claw 帖子的 @ 谁兜底 @Tadashi;永不 @Annie被 @ 的 Lead 今天收不到告警频道里的 @(他们的插件根本没订阅那个频道)——这是 FLY-2078 的活。本单落地后 ②/③ 先是「留痕」,「必达」等 2078

部署顺序(写死)2075 的设计页把「席位就位前频道里没有自动读者」列为你的拍板点 2。本单的接入机制正是那个读者,所以顺序是:先部署本单(Bridge 路由 + Claw 重启)→ 两条证据都到齐:① 第一条真实的 dispatcher 根消息(信箱死信通报每天都有,是天然探针)证明 Claw 确实收到了;② Claw 的启动日志显示钥匙已到位、且用它查一次账本能写得了 → 再让 2075 在同一窗口切频道单腿。缺任一条不切;钥匙没配时 Claw 的门控根本不翻——听得见却写不了账的席位不该上岗。反过来的顺序 = 把 2075 自己列的「无读者窗口」制造出来。

和 2075 的四条共同约定① Bridge 的自动修复保留,值守认领不覆盖它的状态;② 转出时根消息上的 owner 一起改;③ thread 里那句「🔧 Cass 收到」改成中性措辞(Cass 早已不在这条线上);④ 根消息 @ 的是 Codex 机器人的那些工单(账号 / 登录类,「谁都不救自己」),值守只记「② 归它」,不再 @ 一次。

7怎么算做完:一条真实告警走完 ①/②/③ 之一,并在 thread 留痕

不注入假告警。触发点 = 2075 和本单都部署后的第一条真实告警(基线每天几十到三百条);6 小时没事件记「暂无结论」继续等,不算失败。六处取证点标在图里。另加两条硬项:(a) 部署后 24 小时观察,Claw 在根频道的帖子 = 0(除压力自述),同一工单只有一帖 🧭——防 FLY-220 刷屏回环;(b) 让 Claw 正常重启一次(班车即可),它按账本补齐欠账,且没有重复的 🧭 帖——验恢复协议。

8诚实边界:这个设计做什么、不做什么

做Claw 角色文件改成值守席位(看全部、三去向、不装懂、压力自述、根因线、启动补扫);告警频道门控翻转 + 启动幂等落地;一条 Bridge 路由 + 一个命令行让值守把认领 / 转出 / 解决写进账本并同步 🎫 行;spec 守卫段。

  • 不做被 @ 的 Lead 必达、接手进展、「没解决」清单 —— FLY-2078。
  • 不做两本册子的格式、落位、收割 PR —— FLY-2077。
  • 不做频道单腿、砍自动 @ 你 —— FLY-2075。
  • 不做任何指标、考核、hard limit、噪音判定、日量控制、限速调参 —— PRD §5。
  • 不做给 Claw git / gh 写权;Cass 角色文件改字(归 2078)。
  • 不能证明Claw 不会被压垮。前期 runbook 空、几乎全部走 ②/③,Tadashi 的兜底负担先高后低——PRD §6.3 自己也说这一段没有解法。本单能保证的只是:压垮时它会说出来,不会默默堆。
  • 已知边界写账本的路由靠一把专用钥匙认人——它防误用,不防同一系统用户下存心作恶的 Lead(配置文件对谁都可读)。更强的身份归另一张单;Tadashi 拍板时要明确接受这一条。
  • 明确切出信箱死信通报那类「旁路」根消息(没有 thread、没有账本行、按合同本来就是直接给人看的):Claw 看,但不回帖、不记账——没有 thread 可留痕,回根频道会撞回环护栏。它是 Epic 已知缺口(PRD §1.4 里占 22%),把它变成有 thread 的工单是 2075 / Epic 的事。本页不假装它被三去向覆盖了。
  • 不承诺「severe 优先处理」——账本里没有严重度,承诺了也验不了;按到达顺序处理。
  • 交你判的三个缺口(「只删不加」的代价)G1 偶尔多一帖(至少一次,不会丢):顺序是先发帖再记账,Claw 在「发了帖、还没记账」的一瞬间重启,或者 Discord 工具对结果不明的发送自行重试,或者看不到 thread 里较早的旧帖,会再发一次 🧭;但没记账的一定会重做,处置不会静默丢失——封掉「多一帖」要 Bridge 代发 + 一本待发帖账 + 每分钟对账(这正是设计评审 3 轮里越加越多、被 Tadashi 叫停的那套机制)。G2 连续发生两次时第一次没有去向(§4)。G3 thread 没建成的工单账本里没有(§4,归 2075 / Epic)。三条都写在工程合同里,不假装为零;要不要为它们另开单,是你的决定。另:压力自述「同一积压期只喊一次」没有跨重启记忆,Claw 重启后若积压仍在可能再喊一次。

一句自我修正:开单时说「让它看到每条消息」是主要工作;查完发现它已经在信箱里看到了每一条(只是信箱那条腿正在被拆),真正缺的是「看到之后必须落去向」这个合同,以及一条把去向写进账本的路。
