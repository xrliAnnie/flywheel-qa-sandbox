📌 第四条路:专用 barge-in / backchannel 分类器

它既不是通用 VAD(路 2),也不是「等转写再调文本 LLM」(路 3),而是一个低延迟的音频域小模型,直接判「这是真插话还是附和」。它正对着你关心的那个问题。

  • 方向上最对 —— 四条里唯一对「附和」有判别力、又不用等转写的。
  • 今天接不上 —— adaptive 明文要求「支持 aligned transcripts 的 STT」。Raya 的 STT 在 Codex 内部,我们只拿得到转写片段,拿不到对齐时间戳。除非自建 STT 或换 voice 栈。
  • 时延 / 许可 / 能否离线部署:官方文档均未公开(我排除它的理由只有上面那一条,与时延无关)。
  • 同族的开权重替代 Pipecat smart-turn 训练目标是轮次结束,不是 barge-in 判别 ⇒ 不能直接改用。

⇒ 列为路线图选项,不是本轮候选。若将来 Raya 自建 STT 或换栈,它应该是首选检测层。⛔ 不能拿它当「不做路 2」的理由 —— 它今天不可用。

修正后仍然成立的两条

① 语义层不进硬实时停口路径 —— LiveKit 的 min_interruption_words 要 STT,只用来决定这次打断要不要继续;smart-turn / semantic_vad 都在轮次结束侧。
② 假打断靠「原位续念」兜底 —— 三个栈一致,且是 LiveKit 的默认开。检测器允许错,错的代价被恢复语义吃掉。这是本单结论里最稳的一块。

对照我们现在的 BargeGate:sustainMs 350 + 密度 7/10 + 犹豫窗 800ms + 连续段 80ms + 锚段 240ms + 「≥2 段且 ≥1 段 ≥240ms」的形态判定 —— 六组常数,没有一组来自外部基准。

R4不做 快模型判意图不进停口路径。理由不是「已证实 ≥1.2s」(我没量过),而是把串行 ASR + 网络 LLM 放进硬实时路径,引入一个没有时限保证的外部依赖。仲裁继续用转写;附和词先用词表兜。
R5必做 假打断走「原位续念」—— 但范围比我上一版写的窄。Raya 的这套机制只认 inbox: 开头的任务,续接位置来自此前投递的转写覆盖度,是近似续接不是精确原位。
✅ 能说的:你那次 3 分 19 秒灾难(5 条念读被打死 3 条)正好落在它覆盖的范围内,它对那个问题是最强的一招。
⛔ 不能说的:「误掐的风险已被兜住」—— 普通对话轮次被误掐就是没了,既无可重注源文本,也无恢复句柄。那一半目前无解。
R6-1上游 暴露 server_vad.threshold。无前置保持自动取消开着、把门槛调高,直接降低平台误触率。
⚠️ 上一版我说这是「风险最低、白捡」—— 不准确。调高门槛是拿漏检 / 对轻声的灵敏度换误触抑制;每次调完必须同时重测误触率和漏检率。
⚠️ 另外:我之前把 prefix_padding_ms 也列进来,那是错的 —— 它只决定"检测到语音之后往前多带几毫秒音频",不参与"是否检测到语音"的判决,拦不住呼吸。
R6-2上游 透传 response.cancel。无前置让本地层能主动停生成。
⚠️ 上一版我说它必须和 interrupt_response 捆着要 —— 只证明了一个方向。官方合同下单独拿 cancel 不拆任何现有机制(没有可取消的 response 时只返回 error)。它可以独立交付。
平台信号不可用时它独立有价值;服务端根本不取消时它是必需。
R6-3要先有 R6-2 interrupt_response 可配 / 可关。只有想让本地检测器真正当判官时才需要。
⛔ 没有 R6-2 就拿 R6-3,等于拆掉唯一现成的停口机制而没有替代 —— Codex 的出站消息里根本没有 response.cancel,而关掉自动取消后正在进行的 response 会继续跑完。

建议的探针(排期归 Lead,不在本单执行)

统一尺子(三路共用):speechOnset → audibleStop。speechOnset 用离线标注的音频真值,不是任何检测器的输出 —— 否则每条路都在给自己打分。

  • P1(决定性):真房重叠场景,裸录 app-server 全部通知流。五个判据:
    (a) itemAdded{speech_started} 到不到、相对 speechOnset 的时延; (b) 服务端 outputAudio 是否真的随之停止(验证「平台已经是判官」); (c) 用 FLY-2178 已有的 1-breath-overlap.wav 重放 —— 呼吸是否也触发平台 VAD; (d) 同轮记录本地 gate 的触发时刻,裁决「谁先」(我初稿的断言是错的); (e) 是否出现 conversation.item.truncate(证伪我的静态推断)。
  • P2:量「平台喊停 → 本地最后一帧可听音频」,得出播放队列积压的真实上界。
  • P3(只在你想保留路 3 时才做):量首个 user 转写片段何时到达。那是路 3 唯一的真实下界,现在没有人量过。

判据设计的要害:(c) 是唯一能证伪「平台 VAD 比我们准」的一条;(b) 是唯一能证实/证伪「平台已经是判官」的一条 —— 而后者若成立,FLY-2178 检测层的定位就不由它自己的质量决定。

边界与诚实声明

  • 本单没有跑任何真房探针。所有关于「服务端实际行为」的量化(150–217ms 停口)都来自旧版本观测(n=2),必须重测。
  • 「平台 VAD 对呼吸更鲁棒」是推断,不是观测。我核到的是配置已开,不是它对呼吸的反应。P1 的 (c) 就是为证伪这条设的。
  • 「平台在链路上更早」是我初稿写错的。它其实更靠后;可能因为门槛更短而绝对时刻更早,那是 P1 (d) 要测的。
  • 路 3 的「≥1.2s」是推断,不是实测。我只有 user final 1–3s 的旧观测,没量过首个 partial;final 不是 partial 的下界。
  • 验收尺子有缺陷。FLY-2178 的判据排除了判决耗时,三路横向比要换成 speechOnset → audibleStop。
  • truncate 结论是静态证据(源码 + 官方 schema),未在运行时观测。P1 (e) 可证伪。
  • semantic_vad 不可达基于源码 + 装机二进制(0 命中),不是运行时观测;而「它下面 speech_started 不再发」只有社区报告,是待验证假设,不是排除理由。
  • 路 4 的时延、许可、能否离线部署官方均未公开。我排除它的理由只有一条(拿不到 aligned transcript),与时延无关。
  • 「服务端确实取消了生成」是官方合同 + 旧探针推出来的,不是我在真实链路上看到的。整份建议的分叉点就在这里 —— 这也是为什么探针是唯一的阻塞项。
  • 恢复语义的覆盖面(只管念读条目)是我读源码确认的,但没跑过。假触发重排后的实际续接位置取决于此前投递的转写覆盖度,我没实测过它有多准。
  • 本单未触碰 FLY-2178 attempt-18 的传输层帧膨胀修复(你划定的边界外)。
