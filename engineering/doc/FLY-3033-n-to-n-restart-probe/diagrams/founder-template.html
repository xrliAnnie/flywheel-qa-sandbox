● 数据 / 结构模型：分支最终长什么样

唯一的「数据」就是 git 分支上的提交序列。最后一个提交是 milestone（里程碑说明文件，记录交付了什么），它就是冻结头（冻结 = 交卷前最后一次提交，之后分支不再写任何东西，复审批准绑定这个提交）。

● 复审时序：为什么「先冻结、后复审」

复审门会核对「批准的提交 = 当前 HEAD」。如果复审之后再落任何提交（哪怕只是账本），批准就作废。所以所有写入在复审前完成，冻结后只读。

● 关键取舍与被否决的方案
方案结论理由
一次性脚本，不做幂等否决提交后、推送前被杀，新体会重复加行或重复提交——演练单必然出错
靠驱动器 / 引擎兜底去重否决把责任推给外层，QA 证据会混进节点自己的错误
分块幂等 + 冻结后复审（复用 FLY-3030 已批准结构）采用同房兄弟单已经过 3 轮 Codex 评审定型；本单只去掉无关的第 1 轮行和 13 分钟睡眠
孤儿锁（进程被杀后残留的 git 锁文件，会挡住后续所有写操作）直接删否决前体的 git 子进程可能还活着；必须「持有写权 + 锁够旧 + lsof 实查无活 git」三条同时成立才删
账本每次都写否决（演练中发现）重放时游标会从 2/3 倒回 1/3；改为只看已提交的账本游标，只前进不后退
进度记录工具中途被杀的残留（锁 / 临时文件 / 没提交完的改写）一律拒绝否决（Codex 第 1 轮发现）会让新体永远卡在预检；改为「持有写权 + 残留够旧 + 进程表里没有活的写者」时清理并还原到上次提交
共享的 git 锁也按「本工作区没活进程」就删否决（Codex 第 2 轮发现）这些锁放在整个仓库共享的目录里，隔壁工作区（同一个仓库的另一份检出）可能正在用；改为检查全仓所有工作区，配置锁一律不碰，推送也不再写配置
复审被打断就重新开一次复审否决（Codex 第 1 轮发现）每次都会生成新的复审编号，与 FLY-2920「沿用原编号恢复」的规则冲突；改为先把编号记到本地文件再发请求，重启后沿用原编号，开门途中被杀则停下请 Lead 核对
● 演练证据

设计阶段在临时仓里把计划里的每个代码块逐字抽出来跑了 31 个场景：完工后重放、加行 / 暂存 / milestone / 开 PR 后被杀、推送失败、越界文件、各种残留锁（包括「隔壁工作区有活的 git 正拿着共享锁」时必须不动它）、进度记录工具在 4 个内部时刻被真实杀掉、复审登记在 5 个时刻被打断、写权不在自己手上、CI 失败、交卷时有未读消息、冻结后读取失败、无临时目录——全部收敛到正确终态或按预期停下求助。

设计评审：Codex（gpt-6-astra，最高推理强度）评审 3 轮后批准——第 1 轮抓出进度记录工具被杀后的残留会卡死重启、复审重放会换编号；第 2 轮抓出共享锁可能误删隔壁工作区正在用的锁；全部修复并加进演练后第 3 轮零问题通过。三轮意见原文见同目录 design-review-round1/2/3.md。

诚实说明：GitHub 与复审门在演练里是模拟的；真实推送、PR、CI、复审只在实现节点发生。

● 诚实边界：做什么、不做什么

做：给 Codex 实现体一份可逐字照抄、任意步被杀都能安全重跑的合同；README 只加一行；复审、CI、交卷走正常流程。
