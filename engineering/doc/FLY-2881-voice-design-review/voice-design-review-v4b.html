先答你的问题
  • Codex CLI 的语音，前台和后台是怎么分的？前台是一个实时语音模型（默认 gpt-live-1-codex），声音在你和它之间直接来回。它觉得要干活时发出一个「委托」，Codex 就在同一个对话里开一轮普通回合（用这个对话自己的模型和工具，也就是你平时在 CLI 里用的那个）。做完后把最终答案交回，前台用自己的话说出来。这就是「Codex 自带的后台 agent」：它不是另起的程序，就是同一个对话里的一轮回合。
  • 是只有前台语音那一半不能用订阅，还是两半都不行？后台那一半在订阅登录下永远不需要 API key（今天实验也证实了：后台回合走的是 ChatGPT · Pro）。前台语音要看连接方式：
    • WebRTC（CLI 自己的 /voice 固定走这个）：订阅就能跑。唯一没被证实的一环是，一条控制通道用订阅凭据去连 api.openai.com，服务端接不接受，源码里看不出来。
    • WebSocket（我们 B 现在用的）：只有前台语音这一半必须要 API key，否则一启动就报「realtime conversation requires API key auth」。
  • Codex App 的代码公开吗？不公开。开源的是 CLI 和它底下的 app-server；桌面 App 是闭源的。OpenAI 维护者 2026-04-02 原话：「The Codex desktop app is not open source. If you want to write your own client, you're welcome to do so.」（discussion #16538）；请求开源的 issue 已关闭为 not planned（#10733）。仓库许可证 Apache-2.0 只覆盖 CLI 和 app-server。

对我们的意思
  • 后台 agent 用订阅：已证实，照实验的配置做就行。
  • 前台语音也想用订阅：要改走 CLI 那条 WebRTC 路。我们的房间是 Discord，不是本机麦克风，所以要在房间进程里做一个 WebRTC 端点，把 Discord 的声音接进去。工作量大，而且「控制通道带订阅凭据」这一环还要实测。
  • 所以建议不变：先让前台语音用 API key、后台用订阅，改动小；WebRTC 放第二步。
