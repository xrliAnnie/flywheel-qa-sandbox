结论
  • 行，实测跑通了。在同一个 Codex 会话里：实时语音那一路用 API key；后台 agent 那一路用你的 ChatGPT 订阅（school 号，Pro）。模型自己决定把「读一个文件」交给后台；后台在只读沙盒里读完，0.3 秒后前台就用口语说出了结果。从提问到说出结论约 7 秒。
  • 你的直觉是对的：Codex CLI 自己就能语音，而且用订阅就行。它的 /voice（F8）走的是 WebRTC 这种连接方式，用 ChatGPT 登录就能跑。只有我们 B 现在用的 WebSocket 连接才非得要 API key。第三版里「实时语音只能用 API key」这句话说得太死，这里更正。
  • 方案②（另开一个专用文字 agent）可以不要了。Codex 自带的后台 agent 就是你说的 sub-agent：同一个对话，走订阅，结果会自动交回，前台用口语讲出来。
  • Codex App（桌面）的语音叫 ChatGPT Voice，用订阅就能语音操作电脑、指挥 Codex。但它没有公开给第三方用的接口。

A实验：一半用 API key，一半用订阅

做法：建了一个临时的 Codex 配置目录，登录文件用软链指向你现有的 ChatGPT 登录（没有复制，没有跑任何登录命令）；API key 只放在进程的环境变量里。会话设成只读沙盒、不联网、不需要审批。实时会话用文字输出（不出声音，省钱），发一句「请读取 hello.txt 的第一行」进去。

D「Codex 自带后台 agent + 订阅」能替代方案② 吗？还差什么

能替代。第三版的做法①（让语音会话里 Codex 自带的后台 agent 去查）之所以当时判不行，是因为 2799 的容器被特意设成了「只认 API key、后台回合一开就掐掉、没有任何工具」。这些都是我们自己加的限制，不是 Codex 做不到。还差的是：

#还差什么多大
12799 的容器改成：登录用订阅，API key 只给语音那一路；「客户端自己管交接」关掉；不再掐后台回合。实验里的配置就是这个样子小（改配置和几处代码）
2把 Lead 的身份和记忆装进这个对话（2799 已经有这一步），让后台 agent 也带着它们小
3后台 agent 的只读工具：读代码（实验已证可行）；查 Linear、Bridge 状态需要只读的连接或只读的 MCP（现在沙盒不联网，未测）中
4「动手」的边界：后台 agent 只读；派活、批准、改东西要有一个「交给 Lead 本体」的出口（走 Bridge）中
5额度：后台回合走当前活跃的订阅号（今天只有 school 可用，其余号本周已满），和所有 Lead 共用风险，不是代码
6如果连语音那一路也要走订阅：改用 WebRTC 连接（CLI 的 /voice 就是这条路），需要在我们的 Discord 房间进程里接一个 WebRTC 端点。服务端是否接受我们这种接法，未验证大，可以放到后面
7真声音、真房间里测一次（这次是文字）QA

要你拍板的只有一条：语音那一路先继续用 API key（改动小，今天就能按实验的配置做），WebRTC + 订阅作为之后的第二步。可以吗？
