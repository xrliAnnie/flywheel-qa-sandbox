结论
  • 通了，而且两半都走你的 ChatGPT 订阅。我们用自己的 Node 程序（纯 TypeScript 的 WebRTC 库 werift，不用编译任何东西），照 Codex CLI /voice 的同一条路连上了实时语音：真的发出一段中文语音，真的收回了声音；模型自己把「读文件」交给了后台，后台读完，前台用声音说出了结果。
  • 服务端没有拒绝我们这种客户端，全程没有任何报错。第四版里唯一没证实的那一环（控制通道带着订阅凭据去连 OpenAI，服务端接不接受）现在也证实了：接受。
  • 快：连接 1.65 秒建立；说完 1.2 秒前台就开口「我来读一下，稍等」；后台 7.9 秒读完；交回后 0.9 秒开始说结果。从说完话到听到结果共约 9.8 秒，其中大部分是后台干活的时间。
  • 前台开口那一句「我来读一下，稍等」是模型自己说的，不是我们写死的，正好就是你定的「我去看一下」那种说法。

3这对 B 意味着什么

  • 可以不再需要 API key。前台语音和后台 agent 都走订阅。代价是额度和所有 Lead 共用：今天只有 school 这一个 Codex 号可用。
  • 方案②（另开专用文字 agent）确定不需要。Codex 自带的后台回合就是 sub-agent。
  • 接到 Discord 上：这次的「说话的一方」是本机合成语音。换成 Discord 房间时，要把 Discord 收到的声音送进这条 WebRTC 连接，再把收回的声音放进 Discord。Discord 的语音本来就是 Opus 48k，和这条连接用的格式相同，理论上可以直接转交、不用重新编码（未验证）。
  • 还需要补的：用 Lead 的声线（开会话时可以指定 voice，这次用的是默认）；装入 Lead 的身份和记忆；后台 agent 的只读工具（Linear、Bridge）；「动手」交 Lead 本体的出口。这些都是第三版改法清单里的项，不因为换成 WebRTC 而增加。

4这次没证明的

  • 真人、真房间：输入是合成语音，不是你在 Discord 里说话；没有环境噪声、没有插话。
  • 声音清不清楚：只做了客观检查（不削波、不断音），要人耳确认。
  • 只跑了一次：数字是单次的，不是平均值。
  • 长时间稳定性和额度消耗：31 秒一场，看不出一小时的表现和订阅额度的消耗速度。

  • 实时会话 1 次（上限 3）、31 秒（上限 60）；后台回合 1 次（上限 1，脚本里加了「第二次回合立即中断」的保险，没有触发）；没有运行任何 login/logout；环境变量里明确去掉了 OPENAI_API_KEY。
