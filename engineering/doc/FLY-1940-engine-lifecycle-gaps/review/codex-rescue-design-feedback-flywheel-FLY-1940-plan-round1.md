# Design Review — plan.md FLY-1940 (Round 1)

Date: 2026-08-21
Author: Codex
Status: CHANGES REQUESTED

## Summary

The plan identifies the right six failure surfaces and most of the proposed primitives exist, but it is not yet safe to implement as written. The ACK handoff, daemon reap/quiescence proof, founder-gate retirement, stale-TURN convergence, and finalization convergence each contain at least one load-bearing assumption contradicted by the current code, so the stated acceptance criteria are not closed yet.

## What's Good (Keep)

- Keep the root-cause framing: immutable workflow authority, physical liveness, delivery acknowledgement, and finalization convergence are the correct ownership boundaries.
- Keep Fix 1-A's exact-head gate-entry assertion. The gap is real: `resolveWorkflowGateEvidenceTx` derives `proof.subjectDigest` from the current unrevoked claims and `createWorkflowGateHolderTx` never compares it with `input.runnerShipHeadSha`.
- Keep the session-status writer fence as a concept. `assertCurrentWorkflowWriterTx` currently proves run/node/activation currency but never checks the backing session status; `ship_parked`, `awaiting_review`, and `approved_to_ship` are not in `OPERATIONAL_TERMINAL_STATUSES`, so they can remain legitimate writers.
- Keep ACK—not a successful file write—as the semantic delivery boundary. CommDB already has durable TURN-wake ACKs, unprojected-receipt replay, and an `onReceipt` projection seam; that is the right architecture to reuse.
- Keep the four-way orphan-gate predicate, especially treating both `active` and `held` runs as alive and making “no workflow card exists” immediately visible to the Lead.
- Keep `deleteTurnIfCurrent(issue, holder, epoch)` as the only stale-TURN deletion primitive. Exact-epoch CAS is what makes a boot sweep race-safe against `grantTurn`.
- Keep Fix 4d-A and delete the two copies in the same PR. The two worktree assertions are exact-equality copies today, and accepting `base === HEAD || merge-base --is-ancestor base HEAD` is the correct fast-forward-only rule.
- Keep the same-PR coupling of process reaping and `allowMissingTargetHostAbsence`; enabling absence-based death judgment before the detached daemon is actually reaped would be unsafe.
- Keep the no-new-alert-layer and no-per-row-alert decisions. Existing workflow alert/outbox and patrol riders are sufficient if the state transitions are corrected.

## Issues & Recommendations

1. **Fix 2-A does not yet define an implementable ACK projection or a real timeout path.** The existing `onReceipt` path only projects `workflow_ship_carrier`, and `recordWorkflowCarrierWakeReceipt` requires state `wake_delivered` before it moves to `receipt_started`. If coordinators stop at `turn_granted`, every carrier receipt returns `carrier_wake_receipt_not_ready`; rework has no equivalent receipt projection at all. Also, `claimWorkflowReworkDelivery` updates `updated_at` on every lease takeover, while the 30/60-minute stall scan uses `delivery.updated_at` for `turn_granted`, so continuous reconciliation resets the alleged stall clock. Missing ACKs also do not increment `hold_count`; the five-strike path only runs after explicit delivery failures. **Suggested fix:** drive both flows from the existing TURN-wake `onReceipt` seam, with idempotent StateStore methods keyed by activation/execution/epoch. For carriers, atomically preserve the current semantic chain (`turn_granted` acknowledgement and `receipt_started`) rather than calling the existing method against an impossible precondition. For rework, project ACK to `wake_delivered`, release ownership, and preserve the current stall-recovery/event effects. Base ACK age on stable `grant_started_at`/`turn_granted_at`, and explicitly select one failure owner: bounded ACK-timeout strikes or the 30/60-minute stall hold. Do not claim both happen automatically.

2. **The proposed TURN-wake rearm is underspecified and needlessly changes a hot schema constraint.** `turn_wake_outbox` currently enforces `push_count BETWEEN 0 AND 2`; due-claim logic is built around attempts 0/1 and a second verified push. Resetting `push_count` on each coordinator pass has no defined episode boundary, can replay indefinitely, and changing a SQLite `CHECK` requires a table-rebuild migration, not a simple widening. **Suggested fix:** keep the existing two-push bound unless production evidence requires more. Use the first durable write, the existing second verified push, then a stable ACK timeout/stall disposition. If more attempts are required, specify an immutable delivery-episode/generation, total cap, `next_attempt_at`, migration, and idempotency tests before implementation.

3. **Fix 2-B is feasible at the plugin call site, but `mode: "wake_pointer"` currently points to the wrong command.** The Bridge has the required lead resolution, session fingerprint, tmux discovery/capture, and CommDB dependencies. However, the existing phrase says to run `flywheel-comm inbox`; a TURN handoff must run `flywheel-comm turn`, and the nudge's liveness/status/pending-gate guards must still pass for the actual goal-achieved carrier statuses. **Suggested fix:** add a typed TURN-pointer purpose/phrase (or a separate mode) rather than silently changing the instruction-lane pointer, wire it on the second unacknowledged TURN push, and test the real target statuses plus the exact `turn` command. Delete the old receipt-triggered wake only after this path is live in the same PR.

4. **Fix 5-A's primary process-identity assumption is false, which also makes Fix 4a-A unsafe.** The Codex daemon receives `FLYWHEEL_EXEC_ID` in its environment, not its argv; `pgrep -f` searches the command line. The daemon socket name is a hash, and the rotation-shim/app-server argv does not reliably contain the execution ID. Moreover, `daemonPid` is only persisted from `onThreadReady`; a terminate between spawn and thread readiness leaves no persisted PID, and pane descendants cannot find the detached Bridge child. Reusing only `createDefaultKillGroup`'s guard does not prove a stale PID owns this execution. **Suggested fix:** export one claude-runner-owned `reapCodexDaemonForExecution` primitive that uses the deterministic socket plus the existing two-fact proof (socket holder PID from `lsof` belongs to the persisted process group), persists/replaces `daemonPid` immediately in `onDaemonPid`, sends group TERM then KILL with bounded socket-death verification, and is called by every canonical teardown path before CommDB deletion. The Bridge can read `codexSessionStateDir(execId)/session.json`, but it should not duplicate weaker ownership logic. Only after that proof is in the same PR should quiescence permit missing-target host absence.

5. **Fix 4a-A is conceptually correct but is not literally a one-line call change.** `RunExecutionLivenessProbe` is a two-argument type and `collectRunQuiescenceEvidence` invokes the injected probe with two arguments; several routes explicitly pass `probeGeneralizedLaunchLiveness`. **Suggested fix:** either make the default probe a wrapper that supplies `{ allowMissingTargetHostAbsence: true }` and stop explicitly passing the raw probe at production call sites, or extend the probe seam with a typed optional policy argument while keeping two-argument test doubles assignable. Add a regression where CommDB and tmux are absent but a live detached daemon keeps the verdict non-dead, followed by a successful reap that makes it dead.

6. **Fix 3-A is neither just filter widening nor safe blanket retirement.** Adding `founder_review` to the three CommDB checkpoint lists is necessary, but `issueFor` maps through session rows or Codex review jobs; a pruned founder-review source remains `unmapped`. `TerminalGateRetirement` enumerates sessions and calls `getPendingGatesByRunner`, whose `expires_at > now` filter misses relay-open expired questions. Removing `checkpoint !== "approve_to_ship"` would also retire every non-ship checkpoint, not only founder review. Finally, a terminal source session does not by itself prove a founder review is obsolete: an active/held workflow may still own that review while the founder is looking at it. **Suggested fix:** add an explicit `{approve_to_ship, founder_review}` allowlist; derive founder-review issue/run identity from validated immutable gate content/holder binding rather than a possibly-pruned session; enumerate canonical unanswered, unsuperseded, relay-open questions independent of TTL; and retire founder review only when a newer same-family gate exists, external issue/PR terminal authority is freshly revalidated, or its exact workflow activation/holder is no longer current. Preserve concurrent-response-wins behavior. If primitives are unified, extend `retireQuestionGuarded` to accept caller time and `resolved_via` and return `retired/already_retired/response_won/missing`; it does not currently provide the full terminal-retirement semantics claimed by the plan.

7. **Fix 3-C's predicate cannot satisfy the “158 stale TURNs converge to zero” acceptance criterion.** “Holder is irreversibly terminal and current activation does not reference it” only covers rows with a terminal StateStore session. The incident census was based on dead host probes; rows with missing/pruned sessions or stale nonterminal status remain skipped forever. The current reconciler interface also exposes non-CAS `deleteTurn`, and its engine-ownership lookup is historical, not an exact current active-or-held activation proof. **Suggested fix:** first classify the production set into bounded, provable categories. At minimum support (a) irreversible terminal holder plus no current active/held activation and (b) missing holder beyond grant grace plus no current active/held activation and positive host/tmux absence; leave ambiguous rows fail-closed and report the remaining count. Carry run/node/attempt/activation identity from `three_stage_turn`, query exact current activation including held runs, replace the interface with `deleteTurnIfCurrent(issue, holder, epoch)`, and test both race orders with a concurrent `grantTurn`. If those predicates cannot safely cover all 158, explicitly prioritize the residual instead of promising zero.

8. **Fixes 1-A/1-B need exact error and revocation contracts.** FLY-1912's reusable 409 machinery catches `WorkflowEngineInvariantError` inside the transition transaction and surfaces `engine_invariant:<reason>`; a plain `Error("runner_ship_qa_head_stale")` escapes as a server error. The nearby `design_review_approved` revocation runs specifically in materialization push confirmation for a review node, not at every PR-binding head change, so copying it is not a complete QA revocation hook. `assertCurrentWorkflowWriterTx` returns only boolean, and its callers map false to several existing reasons, so simply adding a session join cannot uniformly emit `writer_session_terminal`. **Suggested fix:** compare normalized `proof.subjectDigest` to `runnerShipHeadSha` before holder/carrier side effects and throw `new WorkflowEngineInvariantError("runner_ship_qa_head_stale")`; revoke stale `qa_passed` at every authoritative current-head mutation using the exact producer/run/node binding. Refactor the writer check to return a structured classification (with a bool wrapper if needed), fail closed on a missing session, and retain idempotent-completion replay checks before the fence. Add focused tests for completed-session replay/final reporting, `ship_parked` carriers, awaiting-review authority, and terminal-session new submissions.

9. **Fix 4b duplicates an existing safer recovery transaction, while Fix 4c risks breaking active-run classification.** `POST /api/runs/:runId/rework` plus `openOperatorRework` already recognizes held `needs_lead`, applies strict quiescence, revokes unused credentials, supersedes the exhausted attempt, and creates a fresh attempt. Re-arming the same request/delivery can wake the same terminal actor or preserve a `retain_ambiguous_grant` TURN. Separately, `getWorkflowStartReservationForRun` is used to classify and recover active engine runs; making that generic accessor hide terminal executions can turn a recognized run into `*_RUN_STATE_CORRUPT`. **Suggested fix:** make the requested `/rework/:requestId/resume` endpoint a thin, idempotent wrapper over the existing operator-replacement transaction, or define explicit branches for pre-grant cleanup versus ambiguous grant, including stale TURN/outbox cancellation—do not blindly reset the exhausted row. For start replay, add terminal-session classification to `inspectWorkflowStartReplay` (or a dedicated `getReplayable...` accessor) and return a machine-readable terminal-execution reason while preserving the generic reservation accessor. Reconcile this with FLY-1638's already-merged lease/tombstone base and its still-diverged follow-up branch before coding.

10. **Facet 6 is not closed, and the plan's dependency record is stale.** Commit `f09a3f19b` (`FLY-1770: make land closeout self-healing (#845)`) is already an ancestor of this branch. Its retry budget is intentionally per progress epoch: `releaseLandOperationWithRetryAccounting` derives the epoch from `COUNT(land_operation_step)` and `current_step`. Fix 6-A creates additional `notification:<stage+reason>` step receipts, so changing reasons increments the step count/current step and can reset the retry budget more often. FLY-1770 therefore cannot later supply the claimed cross-epoch convergence. **Suggested fix:** make cross-epoch convergence part of FLY-1940: add a durable total closeout-attempt/horizon that notification receipts cannot reset, or exclude notification steps from the progress epoch and add a separate bounded global budget. Base Fix 6-B's 1/4/8 visibility buckets on that durable total. Test an alternating `issue_closeout_incomplete`/other-partial sequence through thread archive, Linear disposition, local cleanup, and terminal escalation. Do not ship 6-A ahead of this correction.

11. **Refresh the dependency table and PR gates before implementation.** In this checkout FLY-1759 (`e4ae3893e`), FLY-1628 (`acbf39bee` squash merge), FLY-1770 (`f09a3f19b`), and FLY-1912 (`f4d789396` squash merge containing the invariant machinery) are all in HEAD; the named feature branch tips may be absent because of squash merges. FLY-1638 has a merged base (`f02ecbc87`, #779) plus a diverged follow-up branch, so treating the whole item as merely “in flight” is also too coarse. **Suggested fix:** update exploration/research/plan with merge-ancestry evidence and rebase the division of labor on code actually present. Preserve PR-1's 5-A↔4a-A atomic coupling; gate PR-2 on the explicit receipt projection/stable timeout design, PR-4 on exact current-activation and CAS APIs plus a production TURN classification, and the final PR on the new cross-epoch finalization test. Add one acceptance matrix mapping every appended criterion to a code owner and test; today wake verification, all-158 TURN convergence, safe needs-lead resume, and finalization convergence have no complete path.
