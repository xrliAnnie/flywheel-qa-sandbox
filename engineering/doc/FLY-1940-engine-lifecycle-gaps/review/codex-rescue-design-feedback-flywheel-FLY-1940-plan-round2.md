# Design Review — plan.md FLY-1940 (Round 2)

Date: 2026-08-21
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 2 is a substantial improvement: the revised plan correctly resolves the Round-1 schema, ACK ownership, gate-retirement, TURN-CAS, typed-invariant, dependency-baseline, and cross-epoch scope errors. The architecture is now feasible, but four implementation-defining contracts remain open—one can still falsely certify a live detached daemon as dead—so the plan is not yet safe to implement as written.

## What's Good (Keep)

- Keep TURN-wake `onReceipt` as the sole semantic delivery boundary, keyed by activation/execution/epoch. The stable `grant_started_at`/`turn_granted_at` clock, single 30/60-minute stall owner, unchanged two-push constraint, and retirement of the unused `wake_failed` episode path are coherent with the current stores.
- Keep the typed TURN-pointer doorbell and exact `flywheel-comm turn` phrase. The plugin has the dependencies needed to wire it without changing the instruction/inbox lane.
- Keep the claude-runner-owned two-fact daemon reap, immediate `onDaemonPid` persistence, process-group TERM/KILL, socket-death verification, and same-PR coupling with quiescence. This matches the actual rotation-shim/app-server process shape and avoids duplicating destructive ownership logic in the Bridge.
- Keep the exact QA-head invariant and structured writer classification. `WorkflowEngineInvariantError("runner_ship_qa_head_stale")`, authoritative PR-binding revocation, fail-closed missing sessions, and replay-before-fence ordering fit the merged FLY-1912 machinery.
- Keep Fix 3-A's explicit checkpoint allowlists, immutable founder-gate identity, TTL-independent enumeration, three-condition founder retirement, and response-wins result contract. These changes remove the unsafe blanket-retirement interpretation from Round 1.
- Keep Fix 3-C's two provable release classes, residual reporting, exact active/held activation test, identity-carrying TURN rows, and `deleteTurnIfCurrent`-only reconciler. Both grant/delete race orders are the right concurrency tests; not promising zero for ambiguous production rows is appropriately fail-closed.
- Keep the narrow Fix 4c replay accessor, fast-forward worktree rule, and the corrected merge-ancestry baseline. The five named merged commits are all ancestors of this checkout's HEAD.
- Keep Facet 6 in FLY-1940 and keep 6-A gated on 6-C. The plan now correctly recognizes that notification steps participate in FLY-1770's current `COUNT(land_operation_step)` epoch and can reset the per-epoch retry budget.
- Keep the net-deletion table, no-new-alert-layer constraint, PR-1 `5-A ↔ 4a-A` coupling, and acceptance-to-owner matrix.

## Issues & Recommendations

1. **Fix 4a-A still has no production-grade way to observe a live Codex daemon after CommDB deletion.** `probeGeneralizedLaunchLiveness` falls back to `hasHostProcessByExecutionId` when CommDB and tmux discovery are absent (`generalized-launch-recovery.ts:58-75`), and that helper is still only `pgrep -f <executionId>` (`:25-41`). The plan correctly states that the daemon does not carry the execution ID in argv, yet its proposed wrapper adds only `allowMissingTargetHostAbsence`. Because Fix 5-A deliberately allows teardown and CommDB deletion to continue when reap proof or killing fails, the resulting state can be “live socket + no CommDB + no tmux + pgrep no-match,” which the declared wrapper would incorrectly return as `dead`. The required live-detached-daemon regression can pass only with an injected fake `hasHostProcess`, not through the production default. **Suggested fix:** export a non-destructive claude-runner-owned daemon liveness primitive alongside the reaper and compose it into the production 4a wrapper. A positively live execution socket must yield non-dead; an inconclusive socket/group probe must yield `unknown`; only proven socket absence plus the existing tmux/host absence evidence may yield `dead`. Alternatively, a failed reap must retain a durable veto that strict quiescence reads. Require the regression to invoke the real production wrapper, including the failed-reap-then-CommDB-delete case.

2. **Fix 2-A does not specify the carrier's “sent but awaiting ACK” replay behavior, leaving a second false-delivery path live.** The carrier currently promotes on both immediate send success (`workflow-ship-carrier-coordinator.ts:486-502`) and the next reconcile's `wake_already_sent` result (`:435-453`). Deleting only the direct file-write transition is insufficient; deleting both without adding a neutral outcome makes `wake_already_sent` fall into retry/hold accounting. **Suggested fix:** explicitly replace both branches with an idempotent `awaiting_receipt` outcome that remains `turn_granted`, preserves the original epoch/wake identity, and consumes neither hold budget nor a delivery failure. Define whether ownership is released or merely lease-refreshed while waiting. Add crash/restart coverage for “wake-send ledger committed, ACK not yet received,” repeated coordinator passes, a late valid ACK, and a stale/wrong-epoch ACK; only the valid `onReceipt` projection may advance the carrier chain.

3. **Fix 4b-A is not yet an exact, crash-convergent wrapper over `openOperatorRework`.** The existing transaction accepts no old request ID (`StateStore.ts:30374-30388`) and selects the latest `needs_lead` request by run (`:30533-30546`), so the route's `:requestId` currently cannot be proven to name the delivery being replaced. TURN/outbox cleanup is also in CommDB, outside the StateStore replacement transaction; the plan does not choose an order or a replay owner. A crash after StateStore replacement but before cleanup can leave the stale TURN, while an idempotent `openOperatorRework` replay returns from its prior event before re-performing external cleanup. **Suggested fix:** bind an `expectedNeedsLeadRequestId` into the transaction's precondition and idempotency payload, and return/persist the exact old cleanup identity (issue, holder, epoch, wake ID). Commit the StateStore replacement first, then cancel only that wake ID and call `deleteTurnIfCurrent` for the old holder/epoch. Make endpoint replay or an existing patrol redrive the cleanup obligation until settled; the existing turn-wake `canDeliver` guard can remain the outbox crash backstop. Test wrong/stale path IDs, crash after StateStore commit, idempotent replay, and a concurrent new `grantTurn`.

4. **Fix 6-C still presents alternatives rather than a bounded convergence contract.** The plan leaves “total counter or wall-clock horizon,” “exclude notification steps or add a column,” the increment boundary, the reset boundary, and the terminal threshold undecided. This matters because `releaseLandOperationWithRetryAccounting` is shared by all retryable land stages (`StateStore.ts:49344-49430`), while the closeout attempt occurs specifically after `finalize()` returns incomplete (`land-executor.ts:1822-1849`); incrementing a global counter at every release can exhaust the operation before closeout, while incrementing it too late preserves the infinite loop. The 1/4/8 alert buckets also cannot be specified without a canonical post-increment value. **Suggested fix:** choose one mechanism now. The simplest fit is an independent monotonic `closeout_attempt_count` (optionally paired with `first_closeout_attempt_at`) incremented atomically only when finalization returns incomplete, with an explicit hard cap/horizon and explicit resume/supersession semantics. Notification and other step receipts must never mutate it; 6-B and the held transition must consume the same post-increment value. Make the alternating-reason test assert the exact terminal attempt/horizon, not merely monotonicity.
