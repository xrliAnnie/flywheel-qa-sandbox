一句话说明

Codex 只在「同一个家的下一次开机」才整理上一次的日记,而且日记必须凉满 1 小时;我们的 runner 过去每次换新家,所以从没整理过。本单让下一次派到同一个家的 runner 在开工前先按一次「整理」按钮,并留一张回执。

家(CODEX_HOME) 是 Codex 保存个人文件的目录;日记(rollout) 是一次任务的完整对话记录;蒸馏 指 Codex 把日记压成几段可复用经验的后台步骤。

734 / 879旧家只有 1 条线程,永远没有「下一次开机」
10 篇FLY-2358 持久家 implement 岗已自然蒸馏出的真实摘要
95 秒实验里同家再开机后从触发到真记忆落盘

为什么从不触发(源码级根因)

逐条读了 Codex 0.153.2 源码(与本机生产二进制同版),四道门叠加我们的家布局:

门它规定了什么对我们的影响
A 工具模型看得见的「记忆工具」默认关闭(dedicated_tools=false);记忆的写入路径本来就是后台蒸馏,不是模型手写。QA 看到「0 个工具名」是 Codex 默认形态,不是故障。
B 触发点后台蒸馏只在 app-server 收到一条真正的对话请求(turn/start)时启动;codex debug prompt-input 这类调试命令永不触发。只有真会话才会触发。
C 候选只蒸馏「别的」线程,且必须闲置 ≥1 小时(配置钳死在 1–48 小时)、≤10 天、来源为交互式;每次最多几条。一家一线程 ⇒ 这条线程永远是「当前线程」,永远不合格。
D 整理真正写出模型开工读的那页纸(phase2)每 6 小时最多成功一次,且在 Codex 进程里跑,进程一关就中断。runner 一收工,整理常常被打断(生产里已实证)。

FLY-2358 的持久家(同项目同岗位共用一个家)已经让 implement 岗在生产里自然蒸馏出 10 篇真实摘要;eng_design 岗的持久家却 0 条任务,原因 Codex 不写日志,我们至今看不见——这也是本单要补「回执」的理由。

实验(生产旧家零写入):把一个旧家整目录拷到临时目录,同家再开机并覆盖阈值,34 秒后 stage1 完成,再 61 秒 phase2 写出 FLY-2142 的真实交接经验,不是模板。

核心流程:下一次开工前先整理

触发线程 是我们在同一个 Codex 进程里额外开的一条只回一个字「ok」的对话,它的唯一作用是让 Codex 启动后台蒸馏;它自己被标成「不生成记忆」,不会留下关于触发本身的痕迹。预算 最多 5 分钟,到点就让 runner 开工,绝不阻塞;没有候选时零成本。

数据与结构模型

保存什么有什么用
候选(hints)我们自己从家里数据库算出的「应该被整理」的旧线程清单,只用来决定要不要触发。
Codex 真做的(claimed)只认由本次触发线程认领的任务行,这是唯一的成功权威。
输出行 + 入选标记摘要必须真的非空落库,且被 phase2 选进那页纸,才敢说「下一轮能读到」。
回执每次执行一张 JSON:到了哪一步、耗时、触发线程 token 总数;不含记忆正文与凭据。

承诺的精确边界与成本

回执状态意思
readable_ready上一批摘要已落库,且 6 小时冷却已过、本次整理完成并把它们选进了那页纸 ⇒ 这一次第一轮就能读到上一任经验。
stage1_done摘要已落库,但整理受 6 小时冷却或未入选 ⇒ 下一次开工时读到。
partial有候选没被认领、或认领了却没产出、或整理出错;如实列出。
skipped:…没有候选 / 数据库读不到 / 限额守卫拦下 / 超过 5 分钟 / 进程被叫停;每种原因单独可统计。

成本:触发线程本身只是一句「ok」;stage1 每条约 40 秒、phase2 约 90 秒,都由 Codex 用 founder 账号额度完成,Codex 自带的「剩余额度 <25% 就不跑」守卫原样保留。回执记录墙钟与触发线程 token 总数(Codex 只把 stage1/phase2 的 token 记在自己的指标里,不落库,我们如实标「不可得」)。

关键取舍与否决的方案

方案结论原因
什么都不加,靠持久家自然蒸馏基线保留,不够滞后且不可见;phase2 常被收工打断;间隔 <6h 永远等下一次。
收工时当场蒸馏本次线程(v1)否决Codex 把闲置门槛钳死在 ≥1 小时,刚结束的线程不可能被认领;想靠「唯一租约」保并发也只是瞬时观察。
下一次开工前整理上一次(v2–v4,采用)采用唯一能让「下一任第一轮读到」成立的位置;无候选零成本;不改 Codex、不改任何家的配置文件,全部用按线程覆盖。
让模型自己拿记忆工具随手记不开(Lead 裁定)每轮多 4 个工具、笔记无审阅、与后台蒸馏形成两套真相。
一次性回填 288 个旧家不做(Lead 裁定)≈8 小时串行、≈3–4 千万 token,吃 founder 额度,且必须赶在 FLY-2359 首次种回之前才有意义。
Bridge 加巡逻处理「某岗位最后一次执行」不做(Lead 裁定)多一套机制;它等该岗位下一次派发即可。
另起 codex exec 子进程当触发器否决实验可行,但要靠人为拖延保活才等得到整理,是 hack。

怎样证明它真的有用(529 房)

529 房 是与生产隔离的真机测试房。验收由 QA 节点执行,用真实 Codex 任务:

  1. 真实任务 T1 结束 ⇒ 回执 skipped:no_candidates(家里还没有旧线程)。
  2. ≥1 小时后派真实任务 T2 到同一家 ⇒ 回执列出 T1 被认领并 done_with_output;数据库里 T1 的摘要非空、不是模板文字、含 T1 的任务关键词。
  3. 若该家上次整理已过 6 小时 ⇒ readable_ready,T2 第一轮的模型回执能复述 T1 的经验(prompt 只给主题不给答案),且用无副作用的调试命令导出的开工提示里能找到它;否则在 ≥6 小时后的 T3 上验证。
  4. 阴性:关闭开关 FLYWHEEL_CODEX_MEMORY_DISTILL=off 重跑,零回执、零触发;RED 变异必须真的改变被测字节。
  5. 成本与延迟:回执墙钟 ≤ 预算,派发到第一轮的延迟差等于墙钟,原任务的超时上限不变。

诚实的边界:本设计做什么、不做什么

做:让同一个持久家的下一次执行在开工前把上一批日记蒸馏进库;冷却已过时当场整理并让第一轮可读;每次留下可核对、可统计的回执。

不做:不能让「刚结束的线程」当场被蒸馏(Codex 硬钳 1 小时);不保证每一次第一轮都读到(受 Codex 6 小时冷却);不回填旧家、不加巡逻、不开模型记忆工具、不改 Codex 二进制、不改 FLY-2359 的运输逻辑。

验收口径已按 Lead 裁定改写:FLY-2358 之后有身份的新任务全部进持久家,「旧家 retire → 下一个家 seed」那条链对新任务没有自然人口,本单不证明它;它的真实人口只有 288 个旧家(回填已裁定不做)。

接受的风险:一条闲置超过 1 小时但仍活着的线程(例如卡在审批门)会被蒸馏「到目前为止」的内容,恢复后会再蒸馏一次——这是 Codex 原生语义,短暂窗口里其他任务可能读到过时但非伪造的摘要。

副产品:Claude Code 驱动的 codex exec 评审会话不在 Codex 的交互来源白名单里,永远不会被蒸馏;不在本单范围。
