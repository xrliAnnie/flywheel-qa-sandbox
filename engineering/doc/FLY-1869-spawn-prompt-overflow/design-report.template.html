FLY-1869 · Runner 起不来:任务说明太长,撞了 tmux 的命令上限

设计方案 · 2026-08-18 · 工程执行节点 → Tadashi → Annie
1一句话总结

给每个 AI 工程师(runner)开工时,系统把整份任务说明原文塞进了一条启动命令里;说明一长(约 16KB 以上)命令就被拒收,工程师根本没法上岗 —— 修法是把任务说明先存成文件、命令里只递一张"文件地址条",并加一道在撞墙前就大声报警的检查。

这个 bug 有个恶性反转:我们习惯把复盘、分析都追加进任务说明,于是一张单被分析得越透,它的 runner 越必然起不来 —— 最重要、最难的单最先失去执行能力。8/18 凌晨挡住所有 PR 的 P0 单 FLY-1863 正是第一个撞线的。

2出了什么事(实测证据)

先解释两个词:tmux(一个在服务器上开很多虚拟终端窗口的工具,每个 AI 工程师就住在一个这样的窗口里干活)、runner(领一张任务单独立干活的 AI 工程师会话)。

开工命令的结构是:"打开一个新 tmux 窗口,在里面启动 Claude,并把任务说明全文作为启动参数一起带上"。tmux 自己有一条内部限制:一条命令太长就直接拒绝。实测边界:

命令长度结果
2,000 / 4,000 / 8,000 / 16,000 字节✅ 成功
20,000 / 24,000 / 32,000 / 65,000 字节❌ command too long(拒绝执行)

FLY-1863 的 QA 环节 05:52 就这样起不来;06:07 有人手工压缩了任务说明,06:34 重试才成功。更糟的是这条错误在系统表里静躺了 40 分钟,没有任何人被通知,最后是 Annie 用嘴报的障。

3修法:任务说明改走文件,命令里只递地址条
__SVG_D1__

关键点:窗口里有一个本来就存在的启动小脚本(它原来的职责是等系统确认"这次启动已记账"再放行),现在让它多做一步 —— 把文件内容原样读回来交给 Claude。所以 Claude 收到的任务原文一个字都不变,变的只是"怎么送到它手上"。

这不是新发明:系统里另外三种 AI 工程师后端(Codex / Antigravity / Kimi)早已各自绕开了这面墙,只有生产默认的 Claude 通道还在裸奔;而且 Claude 通道自己在 FLY-154 时就撞过一次同一面墙(当时只修了另一个参数,没修任务说明本体)。本单是把欠的那一半补上。

4数据去向 + 第二道防线:撞墙前大声报警

修复后,一条启动命令里各部分的去向:

内容今天修复后大小
任务说明全文(prompt)命令行内联0600 权限私有文件可到 120KB
系统提示词(system prompt)已是文件(FLY-154)不变—
环境变量、启动开关、各类路径命令行命令行(不变)~3-5KB,恒定

即便如此,还要防"未来有人又往命令里塞新的大块内容"。所以在真正调用 tmux 之前加一道双重检查:

__SVG_D2__

超限时不悄悄截断、不静默降级 —— 直接抛一个写明"实测多长、超了哪条预算、最大的三块是什么"的具名错误,顺着既有的失败上报链路走,Lead 会被告知。这正对应验收标准第 3 条:"必须有一条会失败的检查"。

5关键取舍与被否掉的方案
方案判定理由
A. 文件 + 窗口内读回(选定)✅ 采用Claude 收到的内容逐字不变(零行为风险);命令长度与任务说明彻底解耦;改动只集中在一个文件
B. 学 Kimi:只递"请先读某文件"的短指令❌ 否会改变 AI 的第一步行为(先去读文件),对生产默认通道是无必要的行为回归风险;A 用零变化达成同一目标
C. 太长就截断 + 告警❌ 否丢信息,且正面违背本单动机 —— "分析越透越必须起得来"
D. 改用环境变量传递❌ 否环境变量走的是同一条 tmux 命令通道,一样撞墙,不解决问题

预算取值:命令总长红线 12KB(实测成功下限 16KB 再留 25% 余量);任务文件红线 120KB —— 取所有平台都能兑现承诺的最小上限(Linux 对单个启动参数有 128KB 硬限制,生产 Mac 虽能到更大,但红线必须在测试环境也为真),验收要求的 100KB 之上留 20% 余量。这个数字是独立交叉评审揪出来改的:原稿写 512KB,在 Linux 上会出现"检查放行、执行时黑箱死"的假合同 —— 恰是本单要消灭的失败类。

6诚实边界:这个设计不做什么
  • 不修"起不来变成永拒重试"的次生 bug(rollback 悬挂指针)—— Tadashi 已另立单;本单保证 spawn 这一步要么成功、要么大声具名失败。
  • 不新建告警通道 —— "有人被告知"复用既有两条失败上报链路;本单的贡献是让错误变得具名、自述、且发生在撞 tmux 之前。
  • 任务说明超过 120KB 依然会失败(但是大声的失败,不是静默的)—— 红线取自跨平台都能兑现的操作系统限制;真出现更大的需求时另立单换形态。
  • 其他三种后端(Codex/Antigravity/Kimi)行为字节不变,用回归测试钉死。
  • 已知微小变化:文件读回会剥掉任务说明末尾的连续空行(shell 的固有行为),语义无害,已在测试口径中声明。
  • 验收口径:QA 判断 runner 活着必须用进程探测(ps),不得用 sessions 表的 tmux_session 字段(活 runner 该字段也可能为空 —— issue 里点名的坑)。
