# Independent Design Review — FLY-1869 plan.md (Round 1)
Status: CHANGES REQUESTED

## Summary
The plan's mechanism is sound and every load-bearing source claim checked out against the worktree: the overflow chain, the always-gated claude-tmux invariant, the gate-script shape, and the typed-failure plumbing are all real, and I reproduced the tmux 3.5a limit and validated the proposed v2 gate script (including the `|| exit 78` semantics) with real /bin/sh and real-tmux experiments. Remaining defects are one MEDIUM (the 512KB prompt budget is justified by macOS-only reasoning — on Linux a single argv string caps at 128KB, so the plan's "≤512KB succeeds, >512KB fails loud" contract silently breaks in the 128KB–512KB band on any Linux host/CI) plus several cheap hardening/consistency folds. Nothing requires a redesign.

## Verified Claims
- **Overflow chain**: `Blueprint.ts:1794-1809` composes prompt as template + full `hydrated.issueDescription` (no truncation); `TmuxAdapter.ts:1115` `args.push(ctx.prompt)`; `execute()` passes `...windowCommand` as separate argv elements to `execFileFn("tmux", ["new-window", ...])` at `TmuxAdapter.ts:682-695`.
- **tmux limit, empirically**: on this host (tmux 3.5a), `new-window` with a single big arg succeeds at 16,300B and fails "command too long" at 16,384B (fixed overhead ~34B), i.e. total packed size ~16,384B — consistent with the plan's "success 16,000 / fail 20,000" black-box numbers and the imsg 16,384B claim. `getconf ARG_MAX` = 1,048,576 — confirms it is not ARG_MAX.
- **Multi-arg direct exec (probe #1)**: verified on a private tmux 3.5a socket that a multi-arg window command is exec'd directly — an arg containing `; $(danger) and spaces` arrived as ONE literal argv element. No shell-join, no quoting inflation, so `Σ byteLength(arg)+1` is a sound proxy (probe #2) with ~4KB headroom at the 12,288B guard.
- **claude-tmux is ALWAYS gated**: `TmuxAdapter.ts:656-666` — `generationGated = this.type === "claude-tmux"` forces `launchToken` (658-661) and `gateFile = commitFile ?? directGateFile` (662-666); both branches defined. Base class `type` at 203; only Antigravity/Kimi subclasses override `type`/`buildCliArgs` (no other subclass in repo).
- **Gated kimi/agy share the script**: when `ctx.launchCommitPath` is set (all generalized runs — `run-dispatcher.ts:1641` sets it unconditionally for `generalizedExecution`), kimi/agy launches flow through the same `sh -c` gate script at `TmuxAdapter.ts:118`. The plan's "pass empty `pf` for them" handling is therefore *necessary* and I verified the empty-`pf` → `exec "$@"` branch is behavior-equivalent in a real /bin/sh run.
- **`p="$(cat -- "$pf")" || exit 78` semantics (requested experiment)**: on macOS `/bin/sh` (bash 3.2), an assignment-only command takes the exit status of the last command substitution — missing file → exit 78, empty file → exit 78, gate loop + `unlink` cleanup + prompt-append-as-last-arg all behaved exactly as the plan describes. Prompt content with `$( )`, backticks, quotes, multibyte, emoji passed through verbatim (only trailing newlines stripped — the plan's declared delta).
- **512KB single arg works on macOS**: the exact v2 script exec'd a 524,288-byte last arg successfully (production platform is Darwin).
- **FLY-154 precedent**: `TmuxAdapter.ts:1028-1053` is the `--append-system-prompt-file` hotfix with the same dir (0700)/file (0600) scheme; agy (`AntigravityTmuxAdapter.ts:98-125`) and kimi (`KimiTmuxAdapter.ts:256-281`) already use file+short-pointer; codex prompt rides `buildGoalKickText` → app-server turn (`CodexTmuxAdapter.ts:486`), not tmux argv. Backend matrix in §1.3 is accurate.
- **Typed-failure plumbing**: `LaunchPrecommitFailure` union at `adapter-types.ts:419-446`; `Blueprint.ts:162-179` `isLaunchPrecommitFailure` accepts any `LAUNCH_*` code structurally, so the new variant flows through the catch at `Blueprint.ts:2953-2979` → `run-dispatcher.ts:124-143` `observeResult` → dispatcher `workflow-engine-dispatcher.ts:2815-2831` releases the launch owner when `physicalEvidence !== "unknown"` ("absent" qualifies). `runs-route.ts:3209-3224` degrades unknown codes to 500/non-retryable — semantically right for a deterministic oversize. Direct path: plain throw → `session_failed` → `[Failed] ... Error: last_error` at `event-route.ts:238-239`. All verified.
- **No hidden consumers break (probes #4, #5)**: the gate-script string exists only in `src/TmuxAdapter.ts:118` and `test/TmuxAdapter.test.ts` (assertions at 352-353/447/467 check substrings `grep -qF` / `exec "$@"` — both still present in the v2 script); `launchFingerprint` = sha256(execId:generation:token) (`run-dispatcher.ts:1652-1658`), independent of the window command; `pruneScaffoldWindow` matches window *name* only (`TmuxAdapter.ts:1885-1915`); cmux-sync keys on `window_name|window_id`; `LeadWindowLocator`'s `pane_start_command` probe targets v2 Lead private-socket panes (`lead-body.sh`), not runner windows; no ps/pane probe parses the prompt from argv — and note the claude *process* argv still contains the full prompt after the gate shell's exec, so `ps ... | grep "claude --agent-id runner-"` liveness (acceptance 4) is unchanged either way.
- **Replay/stale-prompt race (probe #3) is structurally closed on the workflow path**: a stale gated shell can only `cat` prompt.md after its own token is committed, and once any commit file exists the dispatcher adopts instead of re-driving — so a re-drive (which overwrites prompt.md) only happens when no stale shell can ever pass the gate. Residual exposure requires two concurrent `execute()` calls for the same execId, which the launch-owner lease exists to prevent. (Still recommend the cheap hardening in issue 4.)
- **Test precedent**: `scaffold-prune.real-tmux.test.ts` exists; `TmuxAdapter.test.ts:74-116` already spawns the real gate script via `spawnSync` — the plan's "real sh execution, not grep-the-string" test approach has in-file precedent.

## Issues & Recommendations
1. **MEDIUM — 512KB prompt budget is justified with macOS-only reasoning; on Linux it reintroduces the exact "guard passes, opaque downstream failure" class this issue exists to kill.** §3.3/§8.3 derive 524,288B from "ARG_MAX 1MB 的一半" and promise ">512KB fails loud". But Linux caps a *single argv string* at MAX_ARG_STRLEN = 128KB regardless of ARG_MAX — a 129KB–512KB prompt would pass the guard, then the gate shell's `exec "$@" "$p"` fails E2BIG → untyped corpse pane. Production is Darwin (I verified 512KB works there), and the plan's own tests stay at 100KB (< 128KB, so nothing in the plan breaks on Ubuntu CI), but the *contract* as written is false on Linux and this repo runs script/vitest suites on Ubuntu CI. Fix: either lower the prompt budget to a portable number (e.g., 120,000B — still 20% above the 100KB acceptance) or keep 512KB and add an explicit "Darwin-only validity; Linux band 128KB–512KB fails at exec, not at the guard" caveat to §3.3/§8.3 plus a platform note in the integration tests. Evidence: `getconf ARG_MAX`=1048576 + successful 512KB single-arg exec on this host; Linux MAX_ARG_STRLEN = 32×PAGE_SIZE = 131,072.
2. **LOW — whitespace-only prompt flips from "launches" to "untyped corpse pane".** Plan special-cases `ctx.prompt === ""` (inline) but a prompt of `"\n"` is non-empty → file written (1 byte, non-empty on disk) → `$()` strips it to empty → `[ -n "$p" ]` fails → exit 78 corpse. Today claude launches with that prompt. Unreachable via Blueprint composition (always prefixed text) but reachable on the direct path. Fix: treat `ctx.prompt.trim() === ""` like the empty-string inline case in `buildCliArgs` (TS-side, one line), so the shell's fail-closed check only ever fires for genuine file corruption.
3. **LOW — exit 78 is fail-closed but not fail-*loud*.** The corpse pane produced by a missing/empty prompt file surfaces only through the generic pane-death path; nothing maps exit code 78 to a cause. Cheap fix: `printf 'FLYWHEEL_PROMPT_FILE_UNREADABLE %s\n' "$pf" >&2` before each `exit 78` so pane capture forensics (and any human at the pane) see the cause. The plan's acceptance-3 story ("typed error before opaque error") deserves this breadcrumb for the one new opaque mode it introduces.
4. **LOW — prompt.md is execId-deterministic + non-atomic overwrite; make it per-launch for free.** The token gate closes the race on the workflow path (see Verified Claims), but naming the file `prompt-<launchToken>.md` (launchToken always exists on claude-tmux, `TmuxAdapter.ts:658-661`) — or writeFileSync-to-temp + `renameSync` — removes the entire cross-attempt aliasing class (including "attempt-2 content read by a theoretically-leaked attempt-1 shell") instead of relying on the lease invariant. Same lifecycle/no-cleanup posture as today; the gate script already receives the path as an arg, so uniqueness costs nothing.
5. **LOW — §5.2-3's "把 guard 预算临时调到 200B" contradicts §3.3's "阈值为硬编码常量".** To adjust the budget in a test you need an injection seam (constructor option with the constant as default — fine, that is not a runtime flag), OR better: trip the *production* 12,288B threshold naturally by building a ctx with huge `allowedTools`/env values, which tests the real constant instead of a knob. Pick one and say so in the plan; as written the test plan and the design contradict each other.
6. **LOW — "Top-3 最大 args 的名字与长度": argv elements have no names.** A flag's *value* is a separate element from its flag; the error-message builder needs a stated heuristic (e.g., report the preceding element when the big one doesn't start with `-`, else a positional index). Minor, but specify it so the "actionable last_error" promise is implementable as described.

## Verdict
CHANGES REQUESTED

The design is correct and all critical invariants verified (always-gated claude-tmux, shared gate script for gated kimi/agy, direct-argv exec in tmux 3.5a, sound byte-sum proxy, `|| exit 78` propagation confirmed by experiment, typed-failure plumbing end-to-end, no hidden script/argv consumers). Required before approval: fix or explicitly scope the 512KB budget claim against Linux's 128KB per-arg cap (issue 1), and resolve the hardcoded-constant vs test-knob contradiction (issue 5). Issues 2-4 and 6 are cheap folds I'd expect incorporated in the same revision.
