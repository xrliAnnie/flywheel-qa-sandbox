FLY-2101 · 13 个运行时 env flag 全部固化删 — 设计方案

Issue: FLY-2101 · Batch 1(无依赖;D 依赖本单)· 2026-08-27 · 依据:founder 8-27 v4 裁定
文档:engineering/doc/FLY-2101-flag-batch1-hardcode/(exploration / research / plan)

① 一句话总结

把 13 个从来没人动过的运行时开关(env flag)按现值写死成常量,连读点、名册条目和 mailbox / merge 门的旧回退路径一起删掉 —— 行为逐字节不变,治理账本少 13 行。

env flag = 通过环境变量文件(.env)控制的功能开关;「运行时读」指程序运行中每次用到才去读,理论上改了立即生效 —— 但这 13 个从上线起就没有任何人改过。

② 核心流程:固化前后

现状:每个 flag 背后是一条完整「供应链」—— 环境变量、代码读点、名册(registry,所有 flag 的登记表)、真值守卫(truth,核对 .env 里每一行是不是合法开关的检查器)、drift 扫描(自动对账:代码里的读点和名册是否一致)、每周退役巡检。改后只剩一行常量。

②b 删除半径最大的一个:mailbox_queue

它的「=0 回切路」不只是几个 if:整个 deploy barrier(部署就绪闸 —— 每次部署时先把这个 flag 压成 0、等全舰队就绪再恢复的保护机制)存在的唯一目的就是伺候这个 flag。flag 固化后它不但没用,还会继续往 .env 里写这个 key,和「全仓零残名」目标直接冲突,所以连根删。

④ 关键取舍与被否方案

裁决选了没选(为什么)代价
D1 墓碑 vs 零命中 不加墓碑,达成 rg 全仓零命中(验收原文「含 dist 外全部源」) 按惯例加 RETIRED_FLAGS 墓碑 —— 墓碑字符串本身就是一个 rg 命中,与验收冲突 你删 .env 行之前,检查器报的是通用的「unknown 环境变量」而不是定制的「已退役,删这行」;仍然响,只是话糙
D2 空保护名单去留 连集合带分支整删(两个成员都在删除名单里,空集守不住任何东西) 留一个空集合「以防将来」—— 死代码,且「只删不加」原则不许留壳 无
D3 deploy barrier 子系统整删(TS 模块 + CLI + shell 库 + 部署脚本编排段 + 两套测试) 只删 flag 留 barrier —— barrier 会继续往 .env 写这个 key,零命中永远达不成 未来若真要「部署窗口暂停某投递协议」,得重新设计(见诚实边界)

实施顺序(TDD):先立三条旧路的「已删」回归测试(mailbox / merge 门 / supersede 各一条,红),再逐 flag 删读点写常量(绿),最后名册守卫同步 + 全仓 lint / build / test + 逐名词界扫描(\b 词界,因为有 4 组同前缀的幸存邻居,比如 FLYWHEEL_ISSUE_GATE_SUPERSEDE_MAX_MUTATIONS 要留)。

⑤ 诚实边界:这个设计做什么、不做什么

做

  • 13 个 flag 的读点、名册条目、守卫账、旧回退路径全删;行为逐字节不变(固化值 = 现默认值,已逐条核对)。
  • 三条旧路各一条回归测试,证明「旧路已不存在」而不只是「没走」。
  • 部署说明(由 Lead 执行):删生产 .env 的 FLYWHEEL_MAILBOX_QUEUE=1 行;顺检并删可能残留的 barrier marker 文件。不投重启票,随 00:00/12:00 班车。

不做 / 做不到

  • 不回答「以后要不要能关」:merge 门、supersede 巡检从此没有全局阀。若未来出现真实操作者需求,走新 issue 重新登记(登记闸会强制走 SQLite 托管路径),本单不留后门。
  • 代码替不了人删生产文件:.env 那行要 Lead 手动删;删之前检查器会持续报 unknown(可见、无害,但会响)。
  • 测试改造面大于代码改造面:约 30 个测试文件要动,最重的是一批拿 MERGE_APPROVAL_GATE=0 当捷径绕过 merge 门的测试,要改成构造真审批 fixture。工作量风险,不是行为风险。
  • 死代码只在零引用时删:flywheel-comm 的旧单条投递方法等,删除前逐个 rg 复核,清单列进 PR body,不顺手扩权。
  • B2(9 个启动/CLI 时读的)、C(config.yaml)、任何新旋钮/告警层:不在本单。
