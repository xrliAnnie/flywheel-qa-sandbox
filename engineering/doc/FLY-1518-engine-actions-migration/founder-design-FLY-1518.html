FLY-1518 · 引擎外发迁到「动作黑匣子」+ 删三张退役表

v2 上线前置 · 设计方案(已过 5 轮 Codex 独立评审,APPROVED)· 2026-07-28
设计阶段交付Codex 评审通过实施尚未开始

1. 一句话总结

把引擎里一条"写了没人收"的旧外发路径,改成你凌晨拍板的「动作黑匣子」方式;然后把三张已经退役的旧表从数据库里删掉;最后把总设计文档更新成真正的终稿——这单做完,v2 才能安全上线。

背景:总设计有两层——旧终稿(R13)+ 你凌晨的修正案(动作黑匣子整包替换旧机制)。修正案下发时只传到了其中一个施工单,另一个单(FLY-1499 引擎)照旧文档施工,于是留下了这道缝。

2. 出了什么事:一个"没有发件员的待办箱"

引擎处理每条消息时,会把要对外发的东西(回复、通知)写进一张叫 commands 的表——这是旧设计里的「外发待办箱」(术语叫 outbox:先把"稍后要对外做什么"记在数据库里,再由专门的"发件员"程序去真正发出)。

但修正案已经把那个"发件员"(dispatcher,负责取待办并执行的常驻程序)整个删掉了。审计证实:现在整个代码库里没有任何代码会去读这张表。也就是说——引擎每写一条待办,它就永远躺在那里。如果就这样上线:所有走这条路的回复和通知会静默丢失,账面却显示"处理完成"。

3. 新做法:动作黑匣子的四步流程

按你批准的黑匣子哲学:不再有发件员。Agent 在处理消息的过程中亲手做对外动作,黑匣子只负责在动作前后自动记账:

  • 防重复:每个动作有一个跨重试稳定的"身份编号"(由消息编号 + 动作名派生;同一条消息重新处理时,同一个动作会撞上"已记过"的账,只读回结果、绝不做第二次)。评审补了一条硬要求:一条消息里有两个动作时,各自的编号互不干扰——已写进必测清单。
  • 防丢失:动作做完才算"消息处理完成";消息没销账就会重新投递,活儿不会凭空消失。
  • 防抢跑(评审 5 轮里最重要的加固):结算前必须等所有动作落账——引擎里加了一道"屏障",谁想在动作还悬着时就把消息销账,会被直接拦下;连停机、换班这些边角路径也一并上闸。
  • 诚实"未知":断电断在"记了意图、还没动手"的窗口,账上会留一条"意图"状态——它老老实实表示"做没做成不知道",由 Agent 查外部现实后拿着证据显式重做,系统绝不自作主张重发。这是你已拍板接受的残余风险,不是 bug。

4. 数据与结构:删三张退役表

引擎改完后,三张旧表(commands 外发待办 / command_dependencies 待办依赖 / obligations 旧"病历卡"义务账)就一个引用者都不剩了。用一条新的数据库升级脚本(迁移 0008:给数据库动结构的一次性脚本,跑过一次就登记在案)把它们删掉:

  • 删表前先把"被丢弃了多少行"写成一条永久回执留在账上——即便表是空的也写(全零),绝不静默。
  • 历史升级脚本一个字节不改(每个脚本有校验指纹,改了历史指纹对不上,整个升级链就废了);只往后追加。
  • 全新数据库从头到尾跑一遍升级链、带着旧数据升级、升级中途失败回滚,三种路径都有测试;评审时 Codex 还真拿一个塞了数据的库把这条删除脚本完整跑通了。

5. 关键取舍与被否掉的方案

怎么删表最稳先删挂在别的表上的两个触发器,再按依赖顺序删三张表;用"先关外键检查、删完全面复查"的模式❌ 直接裸删——其中一张表自己引用自己,裸删时行的删除顺序没保证,可能中途报错

6. 诚实边界:这单做什么 / 不做什么

做

  • 引擎外发路径迁到黑匣子语义 + 上面那道结算屏障;
  • 删三张退役表(带永久弃行回执);
  • 顺手修一批上轮评审留下的黑匣子小缺口(比如:重做必须换新编号、结果没法存档时也要诚实收尾、时间戳格式校验);
  • 把总设计文档 design-FINAL-v2 更新成含修正案的真终稿——消灭"设计散在对话里"。

不做

  • 不做 DAG 派发引擎(FLY-1520 并行在做)、不做切换上线(FLY-1502)、不删 v1 告警(FLY-1503);
  • 不给黑匣子加自动重试/探测/清理——修正案明确杀掉的东西,一样都不复活;
  • "记了意图、还没动手就断电"的账会停在"意图"状态等人拿证据处置——系统不猜、不自动重发,这是你已接受的设计,不是缺陷。
