# Workflow-Orchestration Patterns for a Multi-Agent Coding System

## Bottom line

Across the systems you named, the stable production pattern is surprisingly consistent. Author the workflow in code when the runtime semantics are complex, long-running, or demand deterministic replay; serialize either the execution state or a normalized graph representation for the control plane, UI, version pinning, portability, and historical inspection. When a system does make the workflow itself into data, it almost always does so to gain editorability, portability, change history, and stronger client/server separation—not because dynamic data representations are inherently better execution engines. Airflow is the clearest example: Python-authored DAGs remain the source of truth, but DAG serialization and DAG bundles buy stateless UI components, lower startup/memory costs, and per-run version pinning. AutoGen Studio, n8n, Dify, and CrewAI lean further toward declarative artifacts because those products optimize for configuration-driven editing, sharing, and operational snapshots. citeturn37view0turn37view1turn12search1turn12search4turn31search1turn31search0turn9search6turn10search4turn10search7turn13search0turn13search6

For your shape of system, the best-fit answer is: keep the executable workflow as **declarative manifest data** at the orchestration layer, but keep step implementations as **server-known node types** with server-enforced contracts. Do **not** hand the whole graph to any model. Instead, hand each model only the local node contract, current state slice, and allowed next actions. Bind every “QA passed” or “approval granted” fact to the **exact commit SHA** being shipped; verify that binding server-side at gate time; and auto-invalidate it when the branch head moves, exactly the way GitHub required checks and stale-review dismissal invalidate earlier approval facts when new commits arrive. For high-trust shipping evidence, the closest industry analog is an attestation model: subject digest or commit SHA, builder/reviewer identity, short validity window, and verification at use time. citeturn36search6turn8search1turn8search6turn7search4turn7search21turn35view1turn35view2turn33search1turn33search6turn33search15

## Graph representation and serialization

The major orchestration runtimes in your survey are still mostly **graph-as-code**. **LangGraph** has a Graph API and Functional API, and its standard authoring pattern is to create a `StateGraph`, add nodes and edges, then `compile()` it; its durable layer is the checkpoint, not a first-class declarative workflow artifact. **Temporal** workflows are code backed by event history and replay. **Airflow** DAGs are Python definitions even though the platform serializes them into JSON for control-plane use. **Prefect 3** describes itself as orchestration for workflows “written in plain Python,” and it dynamically constructs task dependency graphs at runtime. **Dagster** asset and op definitions are code, with declarative automation attached through `AutomationCondition`s rather than through a pure-data executable graph. **OpenAI Agents SDK** is also code-first: an `Agent` is a dataclass configured with instructions, tools, guardrails, and handoffs. **Anthropic’s** guidance is even more explicit: the successful agent implementations they observed favored simple, composable patterns over elaborate framework machinery. citeturn11search7turn11search2turn29view2turn17search15turn39search9turn37view0turn24search0turn24search16turn22search8turn22search4turn14search0turn15search2

The systems that treat workflows more directly as **data** do so for very specific reasons. **AutoGen v0.4** still supports programmatic GraphFlow construction, but it also supports component serialization and an AutoGen Studio interface where teams, agents, tools, models, and termination conditions are represented declaratively in JSON; Microsoft explicitly frames serialization as useful for debugging, visualization, and sharing. **CrewAI** is now “JSON-first” for new crews, with `crew.jsonc` plus `agents/*.jsonc`, while still allowing code-based definitions. **n8n** workflows are JSON artifacts with draft/published states, version history, and export/import. **Dify** exports and imports apps as YAML in its DSL, including workflow orchestration and node settings. Those are all concrete gains from making the workflow a serializable artifact: editor compatibility, portability across environments, version comparison, and better machine tooling around the workflow object itself. citeturn12search0turn12search1turn12search4turn12search8turn13search0turn13search2turn13search6turn13search24turn31search1turn31search0turn9search0turn9search4turn10search4turn10search1turn10search7turn10search11

The clearest evidence for what serialization buys comes from **Airflow**. DAG serialization made the webserver stateless, decoupled the webserver from DAG parsing, let the scheduler make decisions from serialized DAGs, and reduced webserver startup time and memory by loading DAGs on demand from the metadata database. Airflow 3.1 then extended this into a versioned serialization contract between Task SDKs and server components, explicitly aiming at client/server decoupling, independent upgrades, security isolation, and even multi-language SDK support. DAG bundles push that idea further by versioning “everything the DAG needs to run,” so a DAG run can keep using the same code for the whole run even if the DAG changes midway. **AutoGen** says component serialization is for debugging, visualizing, and sharing. **n8n** ties publication to a specific version and lets operators compare historical versions visually. **Dify** says DSL export/import is for versioning, backup, and portability; importantly, its CLI distinguishes exporting the current draft from exporting a specific published workflow version. citeturn37view0turn26view0turn23search6turn37view1turn12search4turn9search4turn31search0turn31search1turn31search3turn31search9turn10search4turn10search1turn10search7

For your architecture, that suggests a clean split: make the **orchestration graph declarative data**, because you want manifest review, reproducible execution, selective disclosure to models, and per-run pinning. But keep the **node implementation semantics server-known and code-backed**, because your nodes are long-running, non-idempotent AI coding sessions whose lifecycle, retry rules, evidence policies, and vendor-diversity rules should not be left to model-generated graph text. That is closer to “Airflow bundles plus GitHub-style policy enforcement” than to “let the model invent the graph at runtime.” citeturn37view1turn37view0turn36search6turn7search0turn7search4

## Handoff contracts and claim invalidation

The strongest production pattern for “step X completed with result Y” is not a vague database flag; it is an **authorized, bounded claim** with a clear writer, server-side verification path, and explicit invalidation rule. **Temporal** is the most mature example. An Activity Task has a **Task Token**, which Temporal defines as a unique identifier for an Activity Task Execution; asynchronous activity completion works by handing identifying information to an external system, returning the special “result pending” state, and then using a Temporal client to heartbeat and complete the activity with that token or with workflow/activity identifiers. Temporal also splits lifetime control by failure mode: **Schedule-To-Close** bounds the overall activity execution across retries, **Start-To-Close** bounds a single attempt, and **Heartbeat Timeout** bounds the gap between heartbeats. That means the completion capability is implicitly short-lived because it becomes invalid once the matching activity execution times out, completes, or is replaced by retry state. citeturn17search1turn17search0turn17search4turn17search6turn39search0turn39search1turn39search2turn17search3

**Restate awakeables** are a similar but slightly looser pattern. Restate’s docs describe awakeables as durable promises for coordinating with external systems: the service creates an awakeable, gets a unique ID, sends that ID to an approver or external actor, suspends, and later resumes when the promise is resolved via HTTP. Restate’s broader model is also explicitly durable and journaled: it records steps and results in a journal and replays completed steps on recovery. What the public docs make clear is that the write capability is the awakeable ID plus the Restate resolution endpoint; what they do **not** emphasize as strongly as Temporal is fine-grained per-claim cryptographic binding to content. In practice, the expiration semantics come from the surrounding workflow logic and timers, not from the awakeable itself. citeturn18search0turn18search16turn18search13

**Inngest** shows why shared secrets are weaker than per-claim capabilities. Inngest signs requests with a pre-shared environment signing key and embeds a timestamp to prevent replay; the SDK verifies signatures server-side, and Inngest warns that if the signing key is exposed, endpoint security is at risk. More importantly for your use case, Inngest’s branch environments intentionally **share Event Keys and Signing Keys**, which is operationally convenient but increases blast radius: any holder of that environment key can authenticate requests for every branch environment that shares it. That is a perfectly reasonable product choice for webhook authenticity, but it is a weaker fit for “QA evidence for exactly this commit and only this commit” than a one-time, content-bound claim or a task-scoped capability. citeturn19search0turn19search1turn19search6turn19search9

**Dagster** and **LangGraph** are instructive because they model progress as trusted runtime state, not as externally signed claims. In Dagster, code changes and output changes are tracked with `code_version` and `data_version`; “Unsynced” is a logical freshness/staleness judgment, and Dagster explicitly notes that “Unsynced” status is **not transitive** until an upstream version change actually affects the downstream asset’s last materialization. In LangGraph checkpoints, state is represented with `channel_values`, `channel_versions`, and `versions_seen`; runtime logic uses those versions to decide whether an interrupt should trigger because a channel has changed since the last seen version. In both cases, the fact is written by the trusted runtime or by the user code running under that runtime, then compared by the orchestrator later. There is no built-in cryptographic verifier; the trust base is the orchestrator’s storage and execution authority. citeturn21search0turn25search5turn29view0turn29view1

The broader industry pattern is the one you should copy for ship gates. **GitHub required status checks** are evaluated against the **latest commit SHA**, and checks from an earlier SHA do not satisfy the requirement. GitHub can also **dismiss stale approvals** when new commits are pushed, and CODEOWNERS can make approval path-scoped and role-scoped. At the supply-chain layer, **in-toto Statements** bind attestations to subjects by **digest**, while **SLSA provenance** makes `builder.id` explicit and requires consumers to accept specific signer–builder pairs; **Sigstore Fulcio** issues **short-lived** certificates, and Rekor/timestamps let verifiers prove the signing happened while the certificate was valid. Those are all versions of the same lesson: the only trustworthy handoff contract is one that is **authorized, content-bound, and invalidated automatically when the subject changes**. citeturn36search6turn8search1turn8search6turn7search4turn7search21turn35view1turn35view2turn35view0turn33search1turn33search6turn33search12turn33search15turn33search17

## Static graphs with runtime dynamism

Production orchestrators overwhelmingly support **runtime fan-out and conditional routing**, but they do so inside a graph whose **node vocabulary and execution semantics are fixed for the run**. **Airflow Dynamic Task Mapping** lets a workflow create a variable number of tasks at runtime based on current data. **Dagster DynamicOut** does the same by yielding dynamic outputs that clone downstream ops per mapping key. **LangGraph’s `Send`** lets a routing function return a list of per-node invocations, which is effectively dynamic fan-out over already-defined nodes. None of these are “give the model permission to invent a brand-new operator type halfway through execution”; they are “instantiate more copies of nodes that the engine already knows how to run.” citeturn23search0turn25search0turn25search1turn29view2

When definitions change during execution, production systems generally **pin the run** rather than mutate it in place. **Airflow 3** says a DAG run goes to completion based on the version at start, and DAG bundles let a run keep using the same versioned bundle even if the DAG is updated mid-run. **n8n** separates draft from published state, says publication creates an active version from the current draft, supports restoring previous versions, and keeps old node versions usable in workflows even after a newer node version is published. **Restate** is explicit that deployments are immutable and that every execution continues on the version it started with; retries, resumptions, and callbacks all route back to that same version. **Temporal Worker Versioning** says pinned workflows run entirely on the worker deployment version where they started, while auto-upgrade workflows must remain replay-safe and otherwise use patching. citeturn23search6turn37view1turn31search1turn31search3turn9search6turn18search2turn18search3turn18search10turn16search0turn16search7turn16search10

That leads to the practical answer to your “new node types in a running graph” question. In the surveyed production systems, I did **not** find evidence of a general, supported mechanism for inserting arbitrary new node types into an already-running execution and having the runtime treat that as a first-class graph edit. What I did find was: dynamic creation of **more instances** of predeclared nodes; conditional routing among known branches; or version-transition mechanisms that preserve replay safety by pinning the run to a definition version or by using explicit compatibility constructs like Temporal patching. That is an inference from the surveyed docs rather than a single explicit statement, but it is a strong one. citeturn23search0turn25search0turn29view2turn37view1turn18search2turn16search0turn16search10

For your system, that is the right tradeoff. Let the manifest support **conditional edges**, **runtime fan-out**, and **per-node configuration** such as vendor/model/effort. But keep the **set of node types closed** for a run: `design`, `implement`, `qa`, `human_approval`, `ship_gate`, and so on. If you need a new node type, publish a new manifest version and start a new run or a new pipeline stage on top of the new definition. That mirrors the path taken by systems that have lived longest under replay, audit, and operational-pressure constraints. citeturn16search0turn18search2turn37view1turn23search6

## Retries, semantic loops, and human approval

The cleanest retry discipline in your survey is to separate **environmental failure** from **semantic failure**. **Temporal** defaults to retrying failed Activities because Activities are where failure-prone, non-deterministic work belongs, while workflows themselves are deterministic orchestration logic. That gives you a natural place to put OS/network/vendor/API errors. By contrast, semantic problems such as “the patch compiles but violates style or requirement X” should usually not ride on the same retry policy as infrastructure faults. **CrewAI** makes that distinction visible: task guardrails validate or transform task outputs, and `guardrail_max_retries` explicitly bounds retries when a guardrail fails. **OpenAI Agents SDK** guardrails likewise run as checks on input or output and can block execution early. The common pattern is: infrastructure retry policies for transient execution failures; bounded validation/review loops for semantic defects. citeturn39search6turn17search15turn38search1turn13search5turn38search15

The human-approval mechanisms differ mostly in who owns the timeout semantics. **Airflow 3.1+ HITL** pauses in a dedicated waiting state, and `ApprovalOperator` is just a fixed-option HITL node. `response_timeout` is optional; if set, the task resumes via human response or scheduler timeout handling, and the implementation distinguishes timeout from human rejection. Airflow also supports defaults, so timeout can resolve to a default selection rather than always raising a hard failure. **Prefect** exposes `pause_flow_run` and `suspend_flow_run`, plus typed `wait_for_input` that can be a built-in type, Pydantic model, or `RunInput` subclass. In Prefect’s API, pausing has a timeout that defaults to **one hour** before failing, while suspend has **no timeout by default**. **Temporal** does not have a built-in “approval operator”; the standard pattern is to wait for a **Signal** and combine it with **durable timers**, which survive outages and can wait for hours, days, or indefinitely. **Inngest `step.waitForEvent()`** pauses until a matching event arrives or the timeout is reached, returning the event or `null`; matching can be keyed by a field or by a CEL predicate. **OpenAI Agents SDK** pauses a run when a tool or tool-agent `needs_approval`, surfaces the interruption, then resumes when the application approves or rejects it; the public docs emphasize pause/resume and revalidation, not a built-in approval timeout. citeturn26view2turn27view0turn28view1turn28view3turn37view2turn24search5turn16search6turn16search12turn16search19turn20search0turn20search1turn20search4turn14search1turn14search4turn14search10turn14search16

If you ask which of these are **fail-closed on timeout by default**, the answer is “fewer than teams often assume.” **Prefect pause** fails on timeout unless you choose otherwise; **Airflow HITL** can fail on timeout, but it also supports timeout defaults, so it is not inherently fail-closed; **Temporal** and **Inngest** leave timeout behavior to workflow code, meaning they are policy-neutral until you implement the timeout branch; **OpenAI Agents SDK** exposes an interruption model without an opinionated built-in timeout default in the docs cited here. The right conclusion for your ship gate is therefore not “pick the framework default,” but “encode fail-closed in your own gate node.” citeturn24search5turn27view0turn28view1turn16search19turn20search1turn14search1

## Recommended design for your system

The consensus answer to the four design questions is straightforward. For **graph representation**, use a **declarative manifest** for the control plane, not graph-as-freeform-code inside the model. That matches the operational advantages seen in Airflow bundles, n8n, Dify, AutoGen Studio, and CrewAI’s JSON-first mode: reviewability, versionable execution plans, portability, and the ability to pin in-flight runs to a known snapshot. For **handoff contracts**, use **authorized, expiring, content-bound claims**, not plain booleans in a database. For **runtime change**, allow dynamic fan-out and routing only among already-defined node types, and pin every run to a manifest version. For **retries and approvals**, separate environmental retries from bounded semantic correction loops, and make ship/approval gates fail closed unless there is a documented reason not to. citeturn37view1turn31search1turn10search7turn12search1turn13search0turn36search6turn35view1turn33search15turn23search0turn25search0turn29view2turn39search6turn38search1turn24search5

Concretely, the mechanisms that transfer best to your setup are these. Represent each pending node completion as a **server-issued completion capability** that names: run ID, node ID, manifest version, expected input/output schema version, and the **git SHA** the claim is about. Make that capability one-time and short-lived, closer to a Temporal task token than to an Inngest environment signing key. When a QA node reports success, store the evidence payload and its metadata as an attestation-like object whose subject is the commit SHA (or a tree digest if you want stronger Git object binding), whose producer identity records the node type plus runtime identity, and whose policy fields include the model/vendor used. Then make the **ship gate** recalculate validity at use time: the gate only passes if the current branch head still equals the attested SHA, the evidence is from the required QA node, the manifest version still matches the run, and any vendor-diversity policy is satisfied. If the head moved, the evidence auto-invalidates the same way GitHub invalidates stale approvals and outdated required checks. citeturn17search1turn17search0turn36search6turn8search1turn8search6turn35view1turn35view2turn33search6

Your vendor-diversity rule should be enforced exactly where SLSA enforces signer–builder compatibility: in **server-side policy evaluation**, not in prompts. Each node manifest should specify an allowed provider set, a selected provider, and a role such as `author`, `reviewer`, or `qa`. The engine should reject a transition if the reviewing node’s vendor equals the authoring node’s vendor for the artifact under review. That is the same class of guarantee as “specific signer–builder pairs only,” adapted from build provenance to model/provider provenance. Because different providers can still share the same underlying model family or infrastructure, I would record both **vendor** and **model identifier** in the handoff evidence and make the policy operate over whichever independence boundary you actually trust. That is a design inference, but it follows directly from how provenance systems separate the artifact subject from the specific trusted producer identity. citeturn35view2turn35view0turn33search6

For long-running AI coding sessions, the practical node contract should look more like **“suspendable activity with explicit completion semantics”** than like a short RPC. Give every node: start policy, cancellation policy, heartbeat/progress channel, evidence schema, timeout budget, and compatibility envelope. Environmental failures—tmux session died, vendor API timed out, CI worker vanished—should use Temporal-style or Airflow/Prefect-style retry controls. Semantic failures—design incomplete, implementation rejected by QA, tests insufficient—should go through a bounded correction loop with an explicit maximum, CrewAI-style, so the system cannot grind forever in self-critique. Human founder approval should be its own typed gate node with explicit timeout behavior and a documented default of **fail closed** for shipping. citeturn39search6turn37view2turn26view2turn38search1

## Anti-patterns to avoid

The first anti-pattern is **mutable unbound approvals**: storing “QA passed” or “founder approved” as a branch-level fact with no SHA binding and no automatic invalidation. GitHub’s required-check and stale-review model exists precisely because approvals that survive a head move are unsafe. If your QA gate is not keyed to the exact commit being shipped, you will eventually ship an unreviewed delta. citeturn36search6turn8search6turn8search1

The second is **shared-secret completion authority**: using one environment-wide signing key or broad API credential as the proof that any node has completed. Inngest’s docs are candid that a signing key is a pre-shared environment secret and that branch environments may share the same keys; that is convenient, but it is the wrong shape for per-step completion claims with strict blast-radius requirements. Prefer per-step, one-time capabilities or attestation verification over shared symmetric authority. citeturn19search1turn19search6turn19search0

The third is **mid-run graph mutation**: editing a live execution’s node types or semantics instead of pinning it to a manifest version. The surveyed production systems overwhelmingly avoid this. Airflow, Restate, Temporal, and n8n all solve the problem with version pinning, immutable deployments, or published snapshots rather than with arbitrary mutation of in-flight graphs. citeturn37view1turn18search2turn18search3turn16search0turn31search1

The fourth is **retry conflation**: treating semantic disagreement the same way you treat network flakiness. Temporal’s default retry story is for Activities that fail transiently; CrewAI’s guardrails show the better pattern for semantic correction, which is a bounded validation loop. If you use infrastructure retries for semantic problems, you get opaque loops, bad observability, and no principled stopping rule. citeturn39search6turn38search1

The fifth is **policy-in-prompt instead of policy-in-engine**. Rules like “the reviewing node’s vendor must differ from the authoring node’s vendor,” “ship only if QA evidence matches current SHA,” and “human approval times out closed” are orchestration invariants. They belong in deterministic engine checks, in the same way GitHub, SLSA verifiers, and Kubernetes admission controls evaluate policy at enforcement time rather than trusting the workload to self-report compliance. And because Kubernetes webhooks default `failurePolicy` to `Fail`, but best practices for mutating webhooks sometimes recommend fail-open plus later validation, you should make an explicit per-gate decision rather than inheriting convenience defaults unconsciously. For a ship gate, the right choice is fail closed. citeturn32search4turn32search6turn32search1turn36search6turn35view2
