同型 2-core GitHub runner 证据与相同被测 blob 排除了 #1219/#1221 的算法回归：失败只出现在 drain 后 WAL auto-checkpoint 落入单个 tail 写事务时，异常窗口 wall/CPU 分离且带 11–26 次 voluntary context switches。测试 fixture 现在在 backlog、tail、modeTick 三组计时前显式执行 `wal_checkpoint(TRUNCATE)`，将 wall/CPU、context switches、WAL before/after 与 SQLite receipt 单列报告；170 万事件、500 holders、功能断言及原 50/100ms CI 硬门全部保留。

红侧先用缺失的三相 checkpoint receipt 确定性失败，绿侧目标文件在原实现头、替身接手头及同步当前 main 后均 1/1 通过；最终一次 backlog/steady/tail max 为 23.22/0.45/10.08ms，两个 modeTick max 为 10.66/19.26ms，三条 checkpoint 均 `busy=0` 且 WAL after bytes 为 0。宿主全量套件按 Lead 与 QA 的并发假红禁令未重跑；effective code review 与同一精确头连续三次 GitHub CI green 仍由结构化回执判定。本实现未放宽其它测试，未改 production 路径、CI workflow、部署或运行态，也未 dispatch QA、merge 或请求 ship。
