# FLY-2681 — CI 按需全量矩阵

**Status**: ⏳ Pending exact-head review and CI
**PR**: [#1249](https://github.com/xrliAnnie/flywheel/pull/1249)
**Date**: 2026-09-17

CI workflow 现在具备默认关闭的 `CI_SCOPED_MODE` 分层开关。关闭时保持原有每头全量行为；打开后，普通 PR 头只运行 Classify、Quick Gate 与动态命名的 `CI Scope OK`，纯文档头保持 `CI OK`，被请求的冻结头运行清单钉死的 16 个 required jobs 并产出 `CI OK`。全量聚合逐项要求 job `result == success`，classify 误判导致全 skipped 会红；required check 名 `CI OK`、ship-await-ci、land exactGreenCi 与 approve-to-ship 的精确头守卫均未放松，因此 scoped-only 头自动 fail closed。

新增 `flywheel-comm ci-full ensure`：以 PR、精确 HEAD、attempt epoch、锁与 durable receipt 幂等地管理 `ci:full` label；同头重复请求不产生第二次全量。QA 协议把它设为取得 TURN 和 reviewed HEAD 后的第一步，并在 pass verdict 前要求同一 HEAD exit 0；approve-to-ship 前置也会在缺少全量时补请求后照旧拒绝。implement 普通修订不花全量，只有明确冻结当前头的 handoff 才能提前请求。`ensure` 在报告 `full_green` 前先调用与立卡相同的 `probeShipCiGreen`，因此不会出现 CLI 说绿、立卡守卫却拒绝的分叉。

QA 在 throwaway PR #1250 捕获了 run `35296884034` 被后续全量 run 取消时的真实 GitHub 形状：聚合 job 尚未来得及求值，check-run `105451287579` 的名字是 `jobs.ci-ok.name` 的原始表达式文本。W3 修订只把**精确头 `ci.yml` 中实际读取出的那一个原始名字**视为受限例外，并且要求它早于后来成功的 `CI OK`、属于同仓另一 run、而成功 run 的 16 个 required jobs 全部逐项为 success；普通 failed/pending/cancelled 以及任意伪造的相似名字继续拒绝。

第二轮 code review 发现 `ci-full ensure` 被共享协议注入后会让没有 Flywheel manifest 的其他仓库永久拒绝出卡。修订后仅当 Git tree 明确证明 `.github/ci-required-jobs.json` 不存在时才退回旧的精确头 CI 判定：全绿返回成功、运行中返回可重试状态、失败继续拒绝，且不写 label；manifest 存在但损坏或读取失败仍 fail closed。新增兼容测试覆盖三种旧 CI 结论及“树中存在但读取失败”反例。

main push 可按 tested tree SHA 复用证据；复用前回验仓库、workflow、成功结论、全量模式、16-job 多重集与当前 tree，任一不符即重跑。PR-head 内容复用未实现，保留 follow-up。workflow 和 CLI 的 mutation paths 有开关、事件、HEAD、label、锁内重读及最新 attempt 顺序守卫；开关关闭即回到当前全量语义。生产仓库变量未修改；合入并部署新 flywheel-comm dist 后，仅 Lead 可在 canary/readback 完成后打开，回滚为关闭变量。

职责边界保持不重叠：FLY-2681 只负责让 GitHub CI 少跑；主机本地 package gate 的排队/信号量由 FLY-2702 负责，本 PR 不实现第二套并发守卫。
