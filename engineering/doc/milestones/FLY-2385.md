## 交付

- 既有 updater 的 00:00/12:00 scheduled cycle 现在在 Flywheel 更新后执行 Raya pass：在独立锁内
  `fetch origin main`，仅允许 main 分支，并只对可快进的 checkout 执行 `pull --ff-only`。
  没有安装 brain launchd job 的非 Raya 主机会可见地跳过该段；urgent/unknown wake 不会触发
  Raya，也没有新增 launchd、cron 或其他调度器。
- Raya 发生变更时按生产语义执行 `pnpm install --frozen-lockfile`、`pnpm build`、kickstart
  `com.xrli.raya.brain`；install/build 均有 600 秒上限，voice 按需重启。成功后原子写入
  `~/.flywheel/raya/deployed-sha` 与部署收据，供巡检判断「合入是否真正上线」。
- install、build、restart 或 ready preflight 任一步失败时，部署器回到旧 ref，重装、重建并恢复旧
  brain；失败原因及 rollback 结果通过 updater 的既有告警出口上报。若无法证明安全快进、checkout
  dirty、分支错误或锁冲突则 fail closed，不会覆盖生产工作树。
- Bridge patrol STEP 5 增加单行 Raya 事实，包含 checkout/head/origin_main/branch/behind、部署
  收据年龄、checkout drift、deploy drift、shuttle stale 与 overdue。behind 或 deployed-sha 漂移
  超过一个班车窗口后进入 warning，发往既有 `#flywheel-engineer` 通道；事实采集只读且不隐式 fetch。
- Raya issue 的 Done 判据与 `summary-inflow.md` / founder authority rule 已明确要求生产 checkout
  到达目标 sha、brain 完成重启、preflight ready 且有 deploy receipt，从流程上落实「合入 ≠ 上线」。

## 边界与 QA handoff

- 本实现没有修改 Raya 代码、没有新增调度器，也没有操作生产 checkout、重启生产服务或伪造
  `deployed-sha`。生产验收由独立 QA 在下一次班车完成。
- QA 应确认 scheduled updater 日志出现 Raya pass，`deployed-sha == origin/main`、brain preflight
  ready；随后在隔离演练中将 checkout 安全退后一 commit，确认 STEP 5 报出 `behind=1`，并在超过
  一个班车窗口后产生 `overdue=yes` warning，再恢复 checkout。
- 本 implement 节点没有 dispatch QA、请求 ship approval、merge、deploy 或重启 Bridge/Lead。
