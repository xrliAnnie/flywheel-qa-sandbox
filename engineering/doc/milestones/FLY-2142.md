## 交付结果

Linear 现在是 dependency ledger 的唯一事实源。任意 Lead 可用
`flywheel-comm dependency add|remove|discover|note|log|show` 记录拆 Epic 时的初始先后关系，
并在执行中明确处理漏掉的、不需要做的和新发现的三类变化。每次动作带 UUID v4 operation ID、
理由与可回读评论；写边成功但评论失败时返回可复制的补记命令，幂等重放不会重复记账。

「不需要做的」不是取消 issue 或隐式放行，而是显式 `remove`。Epic 页面新增
`dependency_review`，每次完整生成都会确定性列出已取消 blocker、范围内依赖环，以及仍有活但
0 件可开始时的前沿边；空态也明确提醒机器看不见“blocker 仍活着、但 Lead 已知不用再等”的边。

Bridge 写路由为 master-token only，并对 active-root 子树做 scope 校验；Backlog 后代可在拆 Epic
与 discover 阶段写账，真正范围外的 blocked 端仍 fail-closed。Linear 三种写调用均有 20 秒 deadline，
不会永久堵死同 project 的串行队列。账本日志并列展示载荷自述时间与 Linear 观测时间，comment
与 relation ID 不一致时不再静默吞掉调用方证据。

- config → teamlead → flywheel-comm 逐 package typecheck 与 build 全部 exit 0；
- 真 Linear 演练完成 add → show → remove → note replay → log 闭环，确认历史删边码 `rb`、
  评论纯文本结构与探针归档清理；
- code review R1 在旧头指出 1 HIGH、3 MEDIUM、2 LOW；本提交前已按 Lead 裁定全部修复或登记；
  每个交付头的 fresh request-driven cross-family review 结果以 PR body 为准。

本实现没有创建 StateStore 副本，没有从正文推断依赖，没有自动删边/自动释放，没有修改
`ready.v1`、`dependents.v1`、`scope.v1` 或 `CLAUDE.md`，也没有 dispatch QA、请求 ship、merge、
deploy 或重启服务。
