# FLY-2606 — 工作流模板与 Lead 参数热生效

**Status**: ⏳ Pending ship
**PR**: 当前 FLY-2606 分支 PR
**Date**: 2026-09-16

新增受管的 `flywheel-comm workflow-template publish|rollback|status` 路径：发布使用 revision/digest CAS，写入 actor、reason、来源、前后 digest 与运行时 build 审计；新派工即时读取新 revision，已有 run 保留原快照。Bridge 重开时，已受管发布的手工版本不会被仓库种子回滚。

新增受管的 `lead-config set|rollback|status` 路径与常驻 Codex Lead 的签名 runtime-config 通道。每代配置绑定项目、Lead、thread、carrier、owner、runtime/build 与模型注册表版本；只有能力、容量、来源和应用回执完整匹配才会标记 applied，下一 turn 的实际观测单独记账。未知模型容量按设计 fail closed，effort 热改不依赖重启；操作和状态转换均有不可变审计记录。

隔离 CLI/HTTP/StateStore 的 publish、rollback、reopen 验收通过；lint、全仓 build、模板/模型矩阵、相关 shell 守卫与包门禁通过，其中 TeamLead 使用零断言失败、仅 `onTaskUpdate` RPC 超时的结构化 PACKAGE_GATE_RECEIPT。QA attempt 1 已用真 `codex app-server` 证明 effort 变更 applied、下一真实 turn observed 与 rollback；同时发现同值 set 因原生不发 settings 通知而停在 pending。本轮有界返工改为在显式 generation 下用匹配的 native readback 直接形成带证据的 applied receipt，不发送多余 update，并保留 readback 不可用时的原更新路径。该同值修复仍待 QA attempt 2 真机复核；生产模型热切换和浏览器视觉不在本轮已验证范围。没有修改生产模板、生产注册表、生产数据库或服务；本 PR 不执行 QA、合并或部署。

代码评审补强了两条生产降级路径：注册表显式 effort 但沿用 Codex 默认 model 时仍可启动；native 热配置能力探测失败时继续使用已验证的 bootstrap 参数，不把能力缺失误判为 owner 丢失。严格 package audit allowlist 同步绑定了更新后的 fleet console 渲染行。
