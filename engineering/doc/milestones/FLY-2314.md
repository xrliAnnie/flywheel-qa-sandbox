## 交付

- `packages/core/test/tmux-viewer.macos.test.ts` 不再用 `which osascript` 代替 Terminal.app
  能力判断；守卫会向 Terminal.app 发出最小 AppleEvent，并且只有当前进程确实能解析、驱动应用时才运行两条
  真实 GUI 测试。
- 首次探针允许 60 秒唤醒冷态应用，成功后必须再通过一次 5 秒热态验证；后者与生产关闭路径最严格的调用预算一致。
  普通解析/驱动错误会携带明确原因 skip；首轮 timeout 会重试，第二轮 timeout、冷成功后热 timeout 与外部 signal
  都会显式失败，不会被误报成环境 skip。
- 探针在真实 GUI suite 的 hook 中惰性执行并 memoize；测试文件 import/collection 不会启动 Terminal，纯守卫单测也不受影响。
  cleanup 只在能力验证成功后武装。两条真实 GUI 测试的行为断言没有被修改，也没有通过隐藏 `osascript` 绕过信号。

## A/B 验收与变异

- **A（能驱动 Terminal.app）**：精确 reviewed code head
  `11613487d4ee4a5d70afe9ad5074059c2c85b310` 上，Lead 的可用进程探针 `rc=0`、输出 `[2]`；目标文件
  15/15 pass、0 skip。两条真实 GUI 用例实际运行并通过：custom-title close 8679ms，`not_found` 517ms。
  这是热宿主上的真实 Terminal.app/AppleEvent 证据，不声称为真实冷启动验证。
- **B（不能解析 Terminal.app）**：本 resident 进程即使 `launchctl managername` 为 `Aqua`，60 秒探针仍快速返回
  `rc=1`，并给出 HiServices/XPC `Connection Invalid` 与 `Can’t get application "Terminal" (-1728)`。
  目标文件为 13 pass / 2 skip，两条 GUI 测试都带原因
  `Terminal.app cannot be resolved by osascript in this process context`。因此判据是当前进程能否经
  LaunchServices/AppleEvents 解析与驱动 Terminal，而不是是否有 Aqua manager 或 `osascript` 二进制。
- **退回旧判据的变异**：把能力判断改回 `which osascript` 后，B 侧目标测试 6 fail；守卫断言以
  `expected true to be false` 变红，两条真实 GUI 测试也都会错误运行并失败。reviewer 另行杀死了
  accept-first-success、10 秒热预算、诊断与 application-name 变异。
- 早期原始冷态观察解释了 60 秒首次预算：同一探针外套 20 秒 timeout 时 `rc=124`；外套 60 秒时
  `rc=0`、输出 `2`；后续调用变快。冷重试、双 timeout、冷成功/热 timeout 和外部 signal 由注入单测覆盖，
  没有把这些单测写成真实冷启动证据。
