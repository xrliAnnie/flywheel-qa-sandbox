## 交付

TeamLead 与 CommDB 现在把超过固定 7 天窗口、且已证明终态的热行分批搬到 immutable cold archive。
维护任务复用现有 tick，每次最多处理 100 行，并在 candidate SELECT、逐页归档与 identity 事务边界检查
25ms/page wall-clock deadline；TeamLead 每次调用另受 2 pages/call 与 50ms/call 约束。没有新 timer、
runtime knob、sharding 或云端数据库实现。

TeamLead 覆盖 `session_events`、`workflow_run_event`、`lead_events`，同时保留 CommDB running lineage
防误归档；Comm 覆盖 ACKED/DEAD mailbox family、log 与 identity，失败 identity 独立回滚且 keyset cursor
可越过坏行。所有候选查询使用固定时间窗口与 allowlist partial index，查询计划测试拒绝全表 scan 和
temp B-tree。所有会写入三张热表的生产入口均完成 census：session/lead/workflow event 写入使用
hot-first/cold-second exact lookup；workflow 新事件 seq 取 hot/cold indexed max，归档后重放与恢复仍保持
原幂等、内容冲突及 `UNIQUE(run_id,seq)` 语义。

一次性 operator 脚本默认 dry-run，`--apply` 要求 source-bound baseline，归档后才允许显式 `--vacuum`；
TeamLead 与 Comm 两类 archive 都提供逐行 hash 校验的 restore。脚本拒绝缺库、schema drift、baseline
drift、活跃 lineage 与重复/冲突恢复。没有触碰 guard 阈值或 `CLAUDE.md`。

## 隔离演练

529 验证只写 `/tmp` online-backup 副本，源 TeamLead/CommDB 只读且 SHA-256 固定。129 分钟 checkpoint
归档 TeamLead 53,772 行、Comm 116,482 行；page-bounded rehearsal head 在两份新的 630MB TeamLead
副本上执行 15 个真实 maintenance tick，均达到 100 rows/tick，单 tick 7.5–34.7ms，合计 1,500 行 /
205.4ms。R8 后调用上限只会减少单次页数，不扩大同步工作。两库停止时
`quick_check=ok`。详情与 source hashes 见 `engineering/doc/FLY-2341-db-retention-hygiene/rehearsal.md`。

首次迁移会在 `StateStore.runMigrations` 启动 preflight 创建并校验 7 个 archive index，其中 4 个为
`json_extract` expression index；这不是首个 maintenance tick 的成本。现有 1.28–2.94s 只量到原 3 个
keyset index，rollout 必须重新量完整启动成本。

同库 cold evidence 会令 VACUUM 前文件增大，因此本实现只承诺 hot-path 行数收缩，不虚报文件已缩小。
生产库 apply/VACUUM、前后维护 pass、连续两小时零 loop-guard stall，以及 7 天稳定曲线仍属于 rollout/QA
观察，本 implement 节点未写生产数据库。
