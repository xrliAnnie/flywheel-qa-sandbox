# FLY-2876 — 同一 slot 重新部署后，孤儿语音房锁让 start 永远 already_owned

**Status**: ⏳ Pending ship
**PR**: #1332
**Date**: 2026-09-25

**范围。** FLY-2867（PR #1323）已覆盖本单 QA 判据 2（别的 slot 的锁仍拒绝）与判据 3（teardown Step 6b 释放本 slot 的锁）。
本 PR 只补剩下的事故本体：同一 slot 被拆后重新部署，`/tmp/flywheel-voice-room-<guild>-<channel>.lock` 的 `owner.slotDir`
仍等于本 slot，回执随旧 slot 目录删掉、也没有存活进程 —— `acquireVoiceRoomLease` 对同 slotDir 返回 `created:false`，
`start` 报 `voice_room_lease_already_owned`，正规路径只剩「再拆一次」能清。

**修复（只动 `scripts/qa/fly2655-voice-room.mjs` 的租约函数）。** 同 slot 租约只有在三者都不活时才经 #1323 的墓碑流程回收并重建：
新增的 `owner.holder`（执行 start 的 CLI 进程，覆盖 daemon/回执尚未写出的窗口，并发 start 仍被挡）、
`owner.daemon`（#1323 的判定，函数体抽成 `recordedProcessAlive` 复用，行为不变）、
`<slot>/voice-run-receipt.json` 未到 `STOPPED`（**daemon 死活不论**）。回执读不了 / 软链接 / 越界 / 字段畸形一律按「活」处理，宁可不回收。
**范围变化（Lead 裁定）**：会话自然结束（daemon 退出、回执仍 `STARTED`）不由 `start` 回收，而由正常 `stop` 收尾
（Bridge stop 对已结束会话幂等返回 200），之后 `start` 可用。
异 slot 规则、teardown、voice-codex 均未改。

**代码评审 R1（Codex gpt-5.6-sol xhigh）HIGH，已修。** 回收打开了 ABA：旧 run 的 `stop` 读完回执后，新 `start` 回收重建同一把锁，
旧 `stop` 只比 slotDir 就会删掉新锁、并用自己的 `STOPPED` 回执覆盖新 run 的回执。修法：每把新建的锁带 `leaseId` 代次
（写进 owner.json、由 `acquire` 返回、`start` 写进回执）；`releaseVoiceRoomLease` 只释放同代次的锁（旧锁与旧回执都无代次，照旧配对）；
`stop` 收尾抽成 `settleStoppedVoiceRun`，只有磁盘上的回执仍是本 run（`sessionId` + `leaseId`）时才写 `STOPPED`。

**代码评审 R2 HIGH → Lead 裁定选项 A（减法）。** R2 指出代次比较与删除/写回不是原子操作，微秒级交错仍可命中新代次。
根因是初版把「`STARTED` 回执 + daemon 已死」当孤儿，而进行中的 `stop` 恰好处在这个状态。改为未 `STOPPED` 的回执一律算活：
`start` 再也不会在进行中的 `stop` 底下回收，竞态在结构上消失；代次与回执归属检查保留作纵深防御。
