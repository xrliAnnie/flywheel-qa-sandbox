# FLY-2359 — `(agent, project)` 记忆历史种回新家

**Status**: ✅ Implementation 与 focused verification 完成；final-head review/CI 与真实 529 RED/GREEN 待后续门禁
**PR**: https://github.com/xrliAnnie/flywheel/pull/1131
**Date**: 2026-09-09

Flywheel 现在会在同一 `(agent, project)` 首次建立 B1 持久 Codex home 时，从该身份历史上的一次性
home 收集原生蒸馏记忆，按确定性规则发布到新 home 的 `.flywheel-memory-seed/`。后续任务从同一
持久 home 开场即可读取历史；不同 agent 或不同项目不会成为候选来源。B1 已经选择共享持久家，因此
本单没有新增任务结束回流路径、home 删除、公共家改动或节流闸改动。

## 交付内容

- `codex-memory-seed` 只归档白名单内的 Markdown 记忆，使用内容/树 SHA-256 去重；同路径不同内容
  以不同 snapshot 保留，不靠 Codex Phase 2 或模型判断解决冲突。
- 发布采用私有 staging、边界上限、二次源扫描与原子 rename；已有完成 archive 会在复用前验证，
  首建失败保持 fail closed，崩溃重试不会发布半成品。
- TeamLead 从精确项目 session 集合中按 project、agent role、Codex adapter 与 legacy home 条件选源；
  Edge Worker 只为解析成功的 keyed Codex identity 注入 lazy loader。
- runner contract 只要求按需读取固定 index/catalog 与匹配 snapshots；当前任务指令优先，archive
  中的脚本不得执行，Codex 原生记忆仍继续写入持久 home。
- QA harness 使用真实 build 后的 StateStore、loader、home admission/provision/retire 与真实
  `codex exec` 路径，并提供 `backflow-disabled`、`seed-disabled`、`role-leak`、`project-leak`
  四个受 exact binary diff 约束的 mutation RED 模式。

## 四条验收映射

1. 同一 `(implement, flywheel)` 的 F1 fixture 写入原生蒸馏 marker；retire 后，归档/种回路径必须
   在 F2 开场可见该 marker。
2. F2 必须复用 keyed home，并由真实 Codex session 同时读到当前原生记忆和 catalog-only 历史。
3. `(qa, flywheel)` 使用独立 positive control，且不得出现 implement marker。
4. `(implement, joycon-typeless)` 使用独立 positive control，且不得出现在 flywheel implement home。

本节点已交付可执行的真机 runbook 与 mutation verifier，但没有把本地 fixture 结果冒充真实 529
产品验收。QA 节点仍须在 529 房、部署的 exact build SHA 上给出未接路径时 1/2 失败的 RED，以及
接入后的 GREEN，并同时证明两条反向隔离指标。
