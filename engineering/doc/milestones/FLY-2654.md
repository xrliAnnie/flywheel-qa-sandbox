本单把 founder 两次明确要求“不再逐次授权”的方向落成两个窄 standing carve-out，同时
保留 merge/ship、R2 停体、R5、正常身份修复和其他生产权限的原边界。

## 交付结果

### Raya 随 main 的标准载体切换

`raya-carrier-follow-main/v1` 激活后，既有 00:00/12:00 updater 班车会读取正常审批合入
后的 `xrliAnnie/raya` fresh `origin/main`，把完整 SHA 固定为本轮目标并走原标准 Lead
生命周期。P2 停旧体前若 main 前进，必须开新 revision、重建 quiet15m 和相关证据；一旦
进入停机/逐条对账窗口，本轮目标冻结，新头留给下一班。Flywheel 自身没有新 commit 时，
班车仍会执行一次独立 Raya pass。

这条 standing authority 不把 merge 变成 deploy trigger，不增加 scheduler、wrapper、
relay 或第二数据源，也不授权 merge/ship、停体、身份修复或紧急重启。旧 founder 逐 SHA
授权保留为历史，不能再充当新目标批准；既有账本通过 revision/digest CAS 原位迁移，
保留 owner、activation、cursor、未决消息和旧运行身份。

### Lead 收尾类紧急重启

`lead-closeout-restart/v1` 激活后，Lead 只有在三项前置全部成立时才能发 schema-v3
`lead-closeout-restart`：

1. founder 在权威本地当日发过固定 full-match 语法的“收尾后重启/重启电脑”意图；它被
   标记为 precondition，不冒充 AUTH-CANON(A) 单次授权。四个正例、十四个反例以及
   prefix/suffix/newline/quote 性质例均由代码锁定。
2. StateStore 的全部 nonterminal session 与所有项目 CommDB、最新 activation、精确
   review/QA receipt、park、`active_turn_id`、phase/turn wake、tmux、recovery digest、
   Git clean/pushed head 完整一致；或 founder 的精确 waiver 仅覆盖列明损失。任一单边
   孤儿、活跃 turn、新 wake、未 push 或恢复证据漂移都拒绝。
3. 发票前工程频道真实播报绑定 decision/revision、intent ref、scope digest、target、
   目的、会打断的 execution 和恢复预期。

操作顺序不可交换：先显式 `scope-snapshot` 物化固定 `current.json` 与四类 receipt，
再播报，回读真实消息后才 `request-restart.sh --request <absolute-private-json>`；播报后
重新物化 scope 会使绑定失效。withdrawal census 覆盖项目配置频道、active issue/phase
thread 和 CommDB 历史已知 DM/route；任何后续 founder 消息或摄取缺口都使当前 decision
失效。

producer、updater 和 final guard 均从 active、独立确认的不可变执行包运行。caller 伪造
package-active 环境、包篡改或包外脚本均 fail closed。updater claim 时仍不写 `started`；
第一次停服务前会从旧已确认包重枚举并复核全部 a/b/c、manifest、from/target、公告和
clean checkout，全部通过后才原子 `prepared→started`。此前拒绝写
`consumed-no-deploy`；started/unknown 永不自动重发，同一 intent 只有可证零服务副作用的
同 wave 才能增加 revision。

原 bare v1 direct-founder 路径保持 AUTH-CANON(A) 兼容；显式 `--request` 不再签发 v2。
未 started 的历史 v2 原字节审计为 `retired-conditional-authority`，started v2 只完成既有
恢复。坏 v3 永不自动降级为 v1/v2；v3 拒绝后 30 分钟内的 bare v1 会被记录为
`possible-closeout-fallback`，但该异常审计本身不授予权限。

## 激活合同

AUTH-CANON(B) 现要求每条 standing carve-out 具有独立 activation manifest：精确 entry
文本/digest、批准引用、实现 commit、不可变执行包 root/digest、Claude 与 Codex 实际加载
receipt、部署/回滚证据、状态和 revision 必须属于同一 manifest。实现者不能自证激活；
CoS confirmer 必须与 author/implementer 不同。pending、混摘要、自签、revoked、假的部署
或加载证据全部拒绝。

本 PR 只实现 schema、verifier、自动 confirmer 消费和两个 backend 的真实加载 receipt；
没有写 active production pointer。独立 confirmer 的生产 activation 与 host 观察仍由后续
授权节点完成，PR green 或本地 package proof 都不等于已经激活。

复审 R7（同家族 Claude 复审门 `7ebf7507`）判定本地文件自洽不构成独立确认，与 plan §4
第 73 行“确认证据必须由确认者身份的认证通道写入权威回执、producer/consumer 独立回读”
一致。现在 Bridge 的 `/api/standing-authority/confirm` 在写任何激活文件之前，先把确认行
（receiptId、entry、revision、manifest/evidence-body/package digest、确认者身份 digest 与
carrier claim）写入 StateStore 表 `standing_authority_confirmation`；`loadVerifiedStandingAuthority`
只读回读该行并逐项比对，且从 manifest 重建 evidence body 逐字节比对。只有本地文件而无
Bridge 行、账本缺失、行 digest 漂移、body 被改写，全部拒绝；同一行重复记录幂等，不同内容
同 receiptId 视为冲突。

## 权限与副作用边界

本实现没有创建真实紧急票、使用真实凭证、激活条目、deploy、restart、停体、dispatch
QA、请求 ship 或把 PR merge/push 到 main。普通 merge 仍只等待班车；成功发票也只代表受理，
不证明重启完成。最终完成仍需本 literal-last head 的 effective code review、QA-owned CI、
独立 QA 和结构化 handoff。
