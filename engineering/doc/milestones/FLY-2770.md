# FLY-2770 — cmux 同步器失控：占位标题堵死 title migration → 关掉重建的空壳圈

**Status**: ✅ Implementation + QA@1 criterion-5 rework complete; frozen-head full CI remains QA-owned
**Date**: 2026-09-23

cmux（0.61.0）给新建 surface 的初始标题是它自己的占位符 `Terminal N`，只有
`tmux attach` 真正画出画面之后 tmux 才用 OSC 把它改成 window name。
`complete_title_migration` 却要求观察到的 surface 必须等于出生命令的某个变体
（FLY-1605 的「别改 founder 命名的 tab」护栏），于是 attach 没画出来时 tab 改名
永远 defer、receipt 永远停在 `prepared`。真机取证：`workspace:451` 的 workspace 面
已是 `flywheel-codex-infra-bot-lead`，surface 面仍是 `Terminal 65`，ledger 行
`prepared|…|10A91D8B-…`；watcher 日志里 `title migration surface drift` 4231 行。

真正把 workspace 关掉的不是 prepared-stall 计数器，而是 W1p restored-adoption：
`_restored_candidate_probe` 的 W1p 判据**字面就是** `surface != title`，所以它恰恰
因为 tab 还是 `Terminal N` 而通过；铸出 marker 后 `complete_title_migration` 在
`restored_inflight_state` 处硬阻断，决策行 `13|advance` 造一张丢了 UUID 的合成
committed receipt，接着 `recovery-close` 关掉 workspace，下一轮 additive 再建一个，
如此循环 —— 9/21 03:50Z 三分钟刷出 29 个空壳，9/22 全舰重启后 14 个 Lead 面板死 9 个。

改法：

* **C1** `complete_title_migration` 接受 cmux 自带占位符，但只在 receipt 是 UUID 绑定时
  （只可能来自本 watcher 的 create、birth 记录收编、或 birth 证明过的 legacy 升级；
  `authorize_stock_candidate` 给 founder stock 写的是四字段 legacy 行，永远拿不到），
  并把**观察到的精确字节**钉进变体表 —— 与 FLY-1884 `__DEFAULT__` 分支同形，守卫在真正
  `rename-tab` 前重读，占位符若被换成另一个（`Terminal 65` → `Terminal 66`）仍然拒绝。
  这不是新授权等级：`adopt_birth_candidate` / `_v2_lead_prepare_and_name` 本来就在只有
  birth 证据、没有命令面证明时对不匹配的 surface 发 `rename-tab`。
* **C1b** `_restored_migration_pending`：UUID 绑定的 prepared 行 + 占位 tab = 「迁移待完成」，
  不是「被 restore 的半截事务」，probe 返回 rc=1。落在 probe 本体上顺带拿到一个更好的
  性质 —— `recover_restored_transactions` 因此把**既有** marker 判成 `evidence=drift`，
  走 `14|marker-delete` 而不是 `13|advance`：**部署后一轮收敛，零 close，零重建**。
  代价是 `--rebuild-views` 的 W1p 分支也会被波及（`resolve_rebuild_targets` 只看 receipt
  状态和活源窗口、不看 surface，真机 dry-run 确认 `flywheel-codex-infra-bot-lead` 正是
  W1p），所以给那一臂加了一条收敛出口：迁移待完成时直接完成 title migration 而不是收编。
  legacy 四字段行的 W1p 行为一字未动。
* **卡死升级**：永久失败的行现在既不回收也不静默 —— 新增 `migration` stall 计数器，
  到阈值经 `_alert_cmux_cleanup` 以 `cmux_cleanup|title-migration-stuck` 升级一次。
* **C2** 四条 title-migration WARN 改走既有 episode 抑制，三个新 kind
  （`title-surface-drift` / `title-rename-deferred` / `prepared-migration-deferred`）
  **两份** allowlist 都登记（`_cmux_log_episode_state_valid` 的校验器和 `log_cmux_episode`
  的分发门 —— 只改一份会让整个 episode 文件被判 malformed，反而给所有既有 kind 关掉抑制）。
* **C3** 维护标记的语义收窄成「暂停住场 watcher」，不再是「冻结一切修复」：
  `--refresh` 新开独立分支、`--rebuild-views` 摘掉 marker 项（互斥体本来就是 mutator
  lease，park 的 watcher 已经释放了它）；`once` / `reaper` / `qa_teardown` / `watch`
  一律不变；`--converge-runners`（脚本里最具破坏性的入口）通过 `allow-parked` 显式
  opt-in 保持冻结。`restart-services.sh` 的自动 `trigger_cmux_refresh` 在 marker 在时
  整体跳过（两步都跳），否则每次 Lead 重启都会悄悄重塑一个被刻意冻结的舰队。
  三处「tmux-only / safe from anywhere」的过时注释一并订正 —— `--refresh` 会关 workspace、
  会改名提交，不是只读。
* **C4**（2655 QA 留账）`CMUX_QA_TEARDOWN_CLAIM` 在 `flywheel-cmux-sync.sh` 与
  `test-teardown.sh` 两处都取独立 env `FLYWHEEL_CMUX_QA_TEARDOWN_CLAIM`，派生值仍是默认，
  生产默认行为不变；`test-teardown.sh` 读 marker 的**拒绝闸**是安全特性，未动。QA@1 证明
  「两边有同名 env」本身不是跨进程握手：只给 teardown 设置 override 时，sync 会看错路径并
  fail-open。返工在 teardown 活跃时把同一份 owner-bound claim 同时发布到 configured path 与
  marker 派生的 canonical rendezvous，sync 两处都查；单边、双边配置都 fail-closed，无 teardown
  时仍保持原 admission。release / stale reap 只删除内容完全匹配的双路径。

R1 判 CHANGES REQUESTED，2 HIGH / 1 MEDIUM / 1 LOW，全部同头修掉：

* HIGH — 延迟执行的自动 refresh 能越过在延迟期间才出现的 marker。`trigger_cmux_refresh`
  只在函数入口查一次 marker，然后把 `--refresh` 排到 5 秒后、`refresh-surfaces` 排到 10 秒后；
  而 `refresh` 的准入分支**刻意忽略 marker**，于是在延迟中被 park 的舰队照样被改。两个后台体
  现在都在真正调用前重查一次，测试的 sleep 接缝改成「在延迟期间创建 marker」而不是调用前就有。
* HIGH — `_restored_migration_pending` 把「读不到」塌缩成「不是迁移待完成」，等于把一次瞬时
  cmux IPC 失败交还给它本要解除的 W1p 破坏性路径。改成三态（0 待完成 / 1 确定不是 / 2 不确定），
  并复用 probe 已经读过的 surface，所以在 probe 路径上不再引入第二种失败方式。rc=2 会传播：
  adoption 跳过、recovery 因 `evidence=inconclusive` 短路到决策行 0 quarantine、最终 close 守卫
  拒绝、`--rebuild-views` 停在该目标而不是落回「收编→关闭→重建」。
* MEDIUM — 新的 `migration` stall 计数器只在成功时清除，非连续的 defer 会累加到升级阈值，
  且 receipt 被 GC 后会留孤儿行。第一轮修法只在 `reconcile_prepared_ledger` 的分支里清，
  R2 指出这不够：同一轮里 `reconcile_workspace_titles` 可能把同一 receipt commit 掉，
  而 committed 行此后不再被 prepared 枚举，prepared-loser 与陈旧 generation 清理也会直接
  删 receipt。最终改成绑到 **receipt 生命周期**：`complete_title_migration` 的两个
  prepared→committed 成功点各清一次，`_ledger_remove` 之后按 generation+ref 整体 purge
  （`_prepared_stall_purge_ref`；purge 失败只告警，绝不假装 ledger 事务回滚了）。
* LOW — 两处注释仍称 `--refresh` 只动 tmux。

R3 再指出清理仍绑在**调用方**而非状态本身（birth 收编、V2 Lead 命名、restored recovery、
stock 收编、rebind 都直接写 committed，绕过了 per-caller 清除），且 ledger 与 stall 是两个文件、
中间崩溃会留永久孤儿。最终改成：commit 时的退役下沉进 `_ledger_upsert` 这一个 upsert 原语，
per-caller 清除随即删除；再加 `_prepared_stall_sweep_orphans`，每轮 reconcile 跑一次，丢掉
「本生命周期拥有的 kind 里、其精确 prepared receipt 已不存在」的行以及一切陈旧 generation 行，
这就是两文件边界的恢复手段（崩溃、`_restored_ledger_cas delete`、rebind 的 ref 级替换都自愈）；
不属于本生命周期的 stall kind 原样保留。

R4 再抓到清扫自身输入边界两头都错：ledger 缺失时 `reconcile_prepared_ledger` 提前返回，
清扫根本跑不到（而「有证据、没 ledger」正是它要收的残留）；awk 的 `getline` 读错误返回 -1 被
当成 EOF，活体集合变空会把**活的**证据全删掉。改成显式三态：确定不存在 → `/dev/null`；
存在但不是可读普通文件 → 返回 1 保全；awk 内捕获 `getline` 结果，负值 `exit 2`。

R2 确认两个 HIGH 与 LOW 修复成立、静态调用链确认 `rc=2` 无法到达任何 close，并留下上面那条
MEDIUM 的补完要求（含「删掉任一分支清除仍然全绿」的测试盲区）。补完后做了 negative control：
删掉 `__ABSENT__` 那条清除 → 红（617/1）；删掉清扫调用 → 红（617/2）；把 ledger 缺失的提前返回
放回清扫之前 → 红（617/1）。还原后全绿。诚实说明：「不可读 ledger」那条子用例**不能**区分
`-f/-r` 前置检查与 `getline < 0 → exit 2` 守卫 —— macOS awk 对目录输入自己就 exit 2，
`awk || return 1` 已经满足了合同；两道守卫保留是给「只用 getline 的 -1 报错」的 awk 的防线。
