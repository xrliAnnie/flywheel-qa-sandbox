# FLY-2547 — 评审体回合生命周期：后台跑测试 + 结束回合 → no_verdict 的病根修复

**Status**: ⏳ Pending effective code review and exact-head CI
**PR**: #1284
**Date**: 2026-09-22

跨家族 Claude 评审契约只规定了**输出形状**（"your very last line must be that JSON
object"），对**回合生命周期**只字未提。遇到长测试套件时，评审体把它放到后台、然后
结束回合去「等完成通知」。但 `claude -p` 是一次性 headless 会话 —— 回合结束即会话
结束，通知永远不会到达；进程退出码 0、没超时（预算 30min），只是 stdout 里没有判决
JSON，于是 `claude-review-runner.ts:553` 的 `parseClaudeReviewOutput` 返回 null，
job 落成 `failure_reason=no_verdict`，评审门保持关闭，告警要求 Lead 令实现体用同一
requestId 重放。FLY-2770 PR #1283 同头 4/4 复现，每次 6–8 分钟、$5–7；class_key 自
2026-09-14 起累计 5 次。

修法只动 `review-request-coordinator.ts` `buildPrompt` 的 `legacyContract`（四个
return 分支共享的前缀，因此 round / resume / head_move / fresh-re-review 与
policy-on / policy-off 全部自动继承），加三句：

* **前台同步** —— every command in the FOREGROUND, wait for it before judging；
* **禁止后台 + 结束回合**，并**给出理由**（single headless session，回合结束即会话
  结束，通知永不到达）—— 光下禁令会让评审体在慢套件上无路可走；
* **保判决的出路** —— 单套件超过 5 分钟就停止等待，**仍然出判决**，并加一条
  `{"severity": "LOW", "title": "tests_incomplete", ...}` 说明哪些套件没跑完。

第三条是关键：只有前两条的话，评审体只是换一种卡法。5 分钟是软阈值，硬上限仍是
runner 原有的 30 分钟超时（未改）。新文本刻意不含 `"findings": [{"severity":
"HIGH|MEDIUM|LOW",` —— severity-policy 分支拿它做 `String.replace` 的锚点。

判决解析、`no_verdict` 重试状态机（`review-request-coordinator.ts:2110`）、
`StateStore.ts:20234` 的连续失败计数、request payload、feature flag 和任何其它
prompt 都未改。净改动 2 个文件。

测试：新增 `FLY-2547` 用例，三层语义各以字面子串断言，policy-off / policy-on 两条
