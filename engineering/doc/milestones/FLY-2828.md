# FLY-2828 — 返工回执投影解卡与可观测性修复

**Status**: ⏳ Pending exact-head re-review, PR scope CI, and QA
**PR**: #1310
**Date**: 2026-09-24

根因已落到事务与巡检的具体控制流。`recordWorkflowReworkWakeReceipt` 原先只接受
`admitted -> running`，但同一个 wake 中的通用完成逻辑可以先把该节点推进到终态；随后
回执投影把这种「完成已证明投递」误判成永久失败并抛出
`workflow_rework_activation_not_admitted_on_receipt`。巡检又让单条异常逃出行循环，外层
GatePoller 只吞掉整轮异常、不带 wake ID，因此队首两条留下 held 日志后，窗口内其余行
既未处理也无日志；固定按最老 `acked_at` 取 LIMIT 20，进一步让窗口外行永久饥饿。

修复把完成事实作为回执结算依据：同事务里先结算当前返工 delivery，再推进工作流；已经
完成的不可逆 obligation 会取消尚未 ACK 的穷尽 wake，仍在途的 wake 不会被提前取消。
Lead 与 founder 两条 `rework_already_open` 门现在共用同一谓词，同时检查 delivery 和
`workflow_rework_verification_path`，所以 delivery 清掉而 verification path 仍 pending/active
时两边都会继续拒绝，不再出现 founder 能过、Lead 被挡的不对称。

`turn-wake` 巡检现在逐行隔离异常，每个 `retry` 都打印 wake ID、分类和原因；未投影行记录
attempt、最后错误与下次尝试时间，并用 attempt 优先级和退避时间让永久失败行退出热窗口。
超过预算的永久失败行进入 quarantine 并触发可见告警，`turn-wake-no-receipt` episode 会写入
`alerted_at`。时间型未投影告警只扫描至少真正尝试过一次的行，避免窗口外尚未访问的 backlog
部署即误报；quarantine 明确点名的 wake 仍会立即告警。`markTurnWakeReceiptProjected` 的 CAS
结果被检查，丢失/竞争不再静默；可重试、需 Lead、replacement pending、过期 revision 等分类
也都保留到事件路由。

回归覆盖了 backlog 大于窗口、队首永久失败、所有无日志 retry 分支、投影 CAS miss、告警
episode、完成与 wake 同轮竞态、已完成 obligation 的安全取消边界，以及两道返工门在
verification path 未清时的一致行为。部署辅助 SQL 冻结候选 cohort，并以 `acked_at` 边界、
范围外哨兵和精确计数验证修复，不会把今晚手工结算之外的历史残骸混入自动处理。

本机证据：teamlead 点名 8 文件 360/360 tests；flywheel-comm 点名文件 35/35；
`workflow-rework.e2e` 9/9；`pnpm lint` 0 error（保留 26 个既有 warning）；受影响包与依赖
build 通过；`flywheel-comm` 和 `flywheel-teamlead` 自身 typecheck 通过；
`...flywheel-comm` 的 8 个依赖/消费者 typecheck 全部通过。`vitest related` 因

规则终止；其暴露的两个并行负载敏感失败均在精确隔离重跑通过，未把该尝试写成全量绿。
