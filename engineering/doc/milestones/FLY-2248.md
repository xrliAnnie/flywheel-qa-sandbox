# FLY-2248 — 通用投递欠条与超时升级

**Status**: ⏳ QA rework complete; pending fresh review
**PR**: [#1040](https://github.com/xrliAnnie/flywheel/pull/1040)
**Date**: 2026-09-02

Flywheel 现在把跨节点交接统一投影为 delivery obligation，不绑定节点类型或某一对 DAG 边。`mailbox`、
`phase_wake`、`turn_wake`、`rework`、`carrier`、`launch`、`land` 和 `gate_holder` 八个物理家族共用
append-only attempt 谱系与 set-once 的 minted/granted/sent/received/consumed 时钟；Bridge 的 legacy
baseline 和 CommDB projector 在重启、重放及迁移窗口中补齐可证明的阶段事实，迁移前没有 attempt 的
物理行继续按兼容路径推进，不会阻断原事务。

r6/r7 review 后，CommDB projector 只接纳仍可投递的当前物理交接；blocked/timeout recipient 的未决交接
仍可观察，DEAD/cancelled/superseded 与已完成历史行不会被重铸。在 2026-09-02 的只读生产库快照上，
首 tick 候选从 2,772 条历史行收敛到 11 条当前行，避免部署时向 Lead 灌入告警。已经铸出后才终结的
mailbox/phase-wake/turn-wake 会按精确物理主键核销并在同一维护 tick 关闭 episode；物理行缺失仍保留为
可告警的 crash-window 证据。`land` attempt 的身份在 live ensure 与 boot baseline 中统一为 `{table, pk}`，
因此同一 operation 可先建仓、后回填 run binding 或重启 baseline，而不会触发持久 identity conflict。

r8 review 后，同一 terminal sweep 也会从 `rework`、`carrier`、`launch`、`land`、`gate_holder` 的精确
物理源解析 owning run。只有 run 明确进入 `completed` 或 `terminated` 时才以 `run_terminal` 核销；
`active`/`held` run 与物理源缺失的 crash-window 证据保持未核销。由此 launch 等原生欠条不会在所属
run 已终结后永久保留 warning/severe episode，而活跃欠条仍继续受超时合同监控。

QA attempt 1 的真 Discord 双臂回放发现：没有当前 `workflow_run` 的欠条若伪造
`delivery:<root_id>` 归属，会在外部发送成功后的 run-event 核销处回滚，继而重复发送。attempt 2 改为按
真实 active run 分流：有 run 时保持既有 `workflow_alert_outbox` 与 `workflow_engine_alert_posted` 审计；
无 run 时不再生成 synthetic id，而是以确定性 event id 同步写入 `LeadInboxRuntime.enqueueInfraAlert` 的
durable CommDB 队列，episode 以 `run_id=NULL` 记录该非 run 绑定路径，且不创建 workflow outbox 行。
该路径先用同 issue 的 session 标签解析 owner；没有标签 owner 时使用欠条所属 project 的默认 Lead，
不会落到 fleet 全局默认 Lead 或逐 tick 打 fallback 日志。`workflow_delivery_contract_episode` 是本 PR
首次新增且尚未部署的表，因此 `run_id` 可空直接由首次建表生效，不为未存在的生产旧表追加迁移。
同轮 QA 还复现了墙钟回退后，同一 episode 被误判为 `advanced` 并在时钟恢复时重插相同主键；现在同
attempt、阶段和进入时刻完全一致的开放 episode 会保持开放，不会重复插入或阻断后续扫描。Watch 同时
按 attempt 隔离异常，一份坏账不会阻断同轮后续欠条。

QA attempt 2 在 exact head `799f4f6f8` 上把机制五条判据全部跑通，但发现已批准计划承诺的事故回放床
没有随实现期收口同步更新。Lead Tadashi 于 2026-09-02 将 M2 转移/改派与 M4 冻结正门正式移交
FLY-2278，并把本 PR 的回放床从 6 起收口为 #1/#4/#6 三起；#2/#5/#7 随 M2/M4 移交。pinned
`plan.md` 保持设计审查时原文不变，范围更正正式记录在同目录 `design-correction.md`、
`implementation-notes.md` 与 PR body。本轮返工新增
`phase_wake` 双臂回放（未 push 的 minted 欠条按时告警，刚完成 push 的 sent 欠条未超期不告警），以及
runner-ship carrier completion 的五个集成用例：`superseded_by_completion`、`carrier_delivery_settled`、
缺行 fail-closed + 事务回滚，并证明该 runner-ship invariant 不会套到 `land` / `engine_terminal` authority。
该轮 QA 返工没有改动生产机制。随后 exact-head code review 发现 `launch` 欠条在两条合法 abandon
路径上没有核销：普通 side-effect abandon 与 fenced unlaunched rollback 都会留下永久可扫描的 granted
欠条。最终修复在两个 authoritative 事务内以 `source_terminal` set-once 核销；pre-contract attempt 缺行
保持 additive-rollout no-op。两条回归均先 RED、后 GREEN。

现有维护 tick 会逐份检查活跃 attempt。阶段超过固定期限时，以确定性 episode/alert UID 升级给 owning
project Lead；run 绑定欠条经既有 `workflow_alert_outbox`，无 run 欠条经 durable Lead inbox。三倍期限后
同一 episode 只追加一次 severe 升级，阶段推进或终结会关闭旧 episode。StateStore 迁移只新增三张
delivery 表，CommDB 只给
`runner_phase_wakes` 增加 `first_push_at`，没有新增 CommDB 表、feature flag、env 旋钮或节点对硬编码。
