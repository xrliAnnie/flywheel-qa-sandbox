founder 9-28 直问「每一个节点用哪些模型、effort、比例……为什么不能 follow 那个去走」。根因不是 `opus` 绑定变成了 Codex:`resolveAutomaticModelSplit` 先按当前 modelSplit 算出选择，再用同一张 issue 所有历史 run 的 weighted assignment 覆写它(不比较策略版本、连已终止的 run 也算);`pinMenuReceiptsToRun` 又只换括号里的 exact、保留当前别名，拼出 `opus (= gpt-6-astra)`。新单没有历史，所以 FLY-3017 正常。

1. **选择。** 删掉跨 run 历史覆写分支;新 start(包括老 issue 换新 key)只读当前 models.json 的节点 arm、权重、bindings 与 arm effort。同一 reservation 的重放、同 run 接力/恢复仍读本 run 冻结记录(`resolveFrozenModelSplit` 不变),确定性分桶不变。`StateStore.listWorkflowModelAssignmentEventsForIssue` 只是不再被新 start 调用，未删除。
2. **回执。** 回执从本 run 冻结记录重建:有本 run assignment 用它自己的 alias;没有时菜单 alias 只在同一注册表模型家族(`modelFamilyCode`,FLY-2775 的 Opus 升代窗口)时保留，否则用具体模型 ID 自标;effort 走与 launch 相同的 `narrowEffort`,被收窄掉就不写。
3. **预准入校验。** runs-route 在准入之前对每条 start 路径(新派单、同 key 重放、keyless 恢复)用 `readFrozenRunModelAssignments` 校验本 run 冻结 assignment;自损 run 在准入前拒绝，run/reservation 原样保留，同 key 重试得到同一个 409;缓存响应原样重放，准入后不再改判。
4. **已知影响(不扩大实现)。** 同 issue 跨 run 出现不同 arm/policy 后,`workflow-scorecard-report.ts` 会把它标为 mixed 并退出按 arm 分组，样本数可能下降;统计增强另开 follow-up。存量错跑的 run 不自动换模型，老单需要 Lead 按既有授权路径重派。
