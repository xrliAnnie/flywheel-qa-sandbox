# FLY-2152 — 判决层投递与巡检闭环

**Status**: ⏳ Pending ship
**PR**: #988
**Date**: 2026-08-30

把 workflow verdict 从「等 Runner 自觉发消息」改成库内事实驱动的双保险：
credential-backed claim 落库时同事务写入 `workflow_claim_recorded` Lead event，
Bridge 立即投递并在 Lead inbox admission 时按 Lead + project 重驱；巡检 Step 4
增加第六维度「判决层」，对 active run 的新合同 claim 检查缺失、待投递、错投和归属异常，
且单条异常不会压掉同项目其它判决或既有 mailbox / wake 事实。QA 与 generalized
workflow prompt 同时要求 `qa-result && ask --report`，历史缺少 `leadId` 的 dispatch
继续只提交 verdict。

QA 发现并关闭了一条 P0 split-brain：route 即时 enqueue 与 admission redrive 曾用
不同 priority 重建同一 delivery id，可能触发 `mailbox identity conflict` 并卡住整个
Lead tick。两条 redrivable claim/replacement 路径现在共享 priority 常量；claim redrive
按行隔离失败并保留 `delivered_at=NULL` 供重试，replacement 的异常仍上抛给既有
loop-stale detector。新增回归测试同时钉住 identity 稳定性和 poison-row 不饿死后续
健康 claim。

边界与 FLY-2134 保持清晰：`delivered_at` 只证明事件已投递，不证明 Lead 已处置；
engine 判决与 legacy 消息的处置判断不强行合并。普通 `ask --report` 仍属于 `[ASK]`
family，Lead 回复仍产生既有 `ask_answered` wake。本单不新增 `CLAIM_UNACTIONED`
状态机，也不新增 report family。

验证：`pnpm lint`、`pnpm -r build`、Edge Worker 全量 1285 tests、巡检 shell
199 tests 和本改动相关 Teamlead suites 均通过；Teamlead 全量在并发压力下出现的
5 个旧用例失败均已逐文件复跑通过。代码审查在本轮以 `APPROVED` 通过，无 blocking
finding；非阻塞 advisories 已回报 Lead。分支随后 rebase 到最新 `main`，唯一测试文件
冲突保留了两侧用例；目标 Biome 与受影响的 49 tests 重新通过。
