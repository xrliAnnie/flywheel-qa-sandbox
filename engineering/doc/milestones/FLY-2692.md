## 交付

- `flywheel-comm shadow-declare` 不再要求 Lead 先往 Discord 发一条哈希文本。CLI 只向 loopback Bridge 提交声明；有 carrier 时走本地 carrier proof，没有 carrier 时用当前 Lead lease 与 Lead bot secret 生成 HMAC。Bridge 以 master API token 接入，重新校验项目、Lead、identity digest、卡片、类别、proof method 与当前授权，再用服务端时间落账。
- 两种 proof 是严格互斥的 tagged union：`lead_hmac` 必须且只能携带 lease claim/HMAC，`carrier_passthrough` 必须且只能携带 carrier claim；CLI 与 Bridge 都拒绝混合、缺失、未知字段及非 loopback 目标。缺少本地授权环境与 Bridge 拒绝 HMAC 也有不同诊断。
- 影子声明表升级为 typed v2 proof，同时保留四条记录线与既有 `decision_source` 语义。迁移在事务前后比较本次涉及表的 scoped foreign-key baseline，因此既不掩盖新增 FK 破坏，也不会因数据库里既有无关残留误报。
- prompt 明确禁止在 founder 主频道或 issue thread 发布、转发 `shadow-declare`；历史 Discord 凭证字段仅以 nullable 兼容列保留，不再参与新声明。FLY-2453 的 auto 模式 founder 消息校验与任何 merge/ship 授权语义均未放松。

## 凭证强度与边界

新记录继续可审计“谁、何时、哪张卡、哪个类别”：身份来自当前 Lead lease/carrier，声明内容绑定 declaration/question/class/lead/project，时间由 Bridge 在卡片创建之后生成，账本 append-only，调用方不能回填或编辑时间。HMAC secret、carrier claim 与 bearer token 均不写入声明表或日志。

本机信任边界仍是 OS 用户：同一 macOS UID 下的另一个进程在部分宿主条件下可能观察进程环境。Lead HMAC 恢复了原 Discord 路径具备的身份与内容绑定强度，但不构成同 UID 进程隔离；这项残余风险不扩张到远程调用，因为两条 proof 路径都要求精确 loopback，Bridge 仍重验当前 lease/carrier 与 identity digest。
