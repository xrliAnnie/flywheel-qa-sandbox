# FLY-2885 — 语音引擎 B 改走 WebRTC + ChatGPT 订阅

**Status**: ⏳ Pending review and QA retest (founder readback rework)
**PR**: #1353
**Date**: 2026-09-26

引擎 B（voice-codex）从 Realtime WebSocket + `OPENAI_API_KEY` 改为 Codex app-server 0.156.1 的 v3 realtime：音频走 WebRTC，计费走 ChatGPT 订阅，模型 `gpt-live-1-codex`。FLY-2799 的回环排除、首帧即播和句子预滚全部保留。

1. **连接与订阅。** 新增 `WebRtcLeg`（werift 0.24.4），音频只走 RTP，sideband 只传朗读和交接。container 的临时 `CODEX_HOME` 强制 `chatgpt` 登录，`auth.json` 以符号链接指向钉死的凭据（从不复制），`account/read` 必须回 `chatgpt`。wrapper 和 daemon 都清掉 `OPENAI_API_KEY` / `CODEX_API_KEY`，没有任何代码路径读取它们。
2. **Discord 直通 Opus。** WebRTC 下行的 48 kHz Opus 包直接交给 Discord（`StreamType.Opus`），不转码；上行 24 kHz 编码。
3. **打断与误触发。** 本地打断在 1.0 s 内停掉旧回复且不说完旧句；越界内容丢弃，朗读有准入和截断标记；上行起声峰值门（默认 −30 dBFS）挡住远处人声误触发。
4. **重连与收尾。** 单一故障入口，≤3 次重连（0/2/5 s 退避，每次 20 s），关闭屏障（stop + closed ≤5 s）；进程退出即终止；启动时按 `lsof -d cwd` 清理上一代 daemon 留下的 container 目录，从不杀进程。
5. **每个 Lead 的音色。** `ProjectConfig` 新增 `liveVoice`（9 个 v3 音色，默认 `cove`），投影到语音房间。生产 `projects.json` 的写入有锁、前像校验、备份和逐字节回读，记录见 `live-voice-config-change.md`。
6. **上下文（T8 + plan §12）。** v2 快照 = 完整 base instructions + realtime prompt + developer 角色的 `initialItems`（记忆分段），两侧用同一份摘要合同。实测发现服务端在约 8,192 个真实 o200k token 以上会**静默丢掉全部** items，所以 items 另按 `Σtok + 8·条数 ≤ 7,600` 限额：分段 ≤2,000 token 且 ≤8,000 字节，只在行边界切，放不下的按原顺序回填 prompt；prompt 仍超限就整场不开并说明原因。container 用自己的 js-tiktoken 1.0.21 逐条复算。Bridge 路由返回 503 + 白名单 details，前端在 Lead 的语音 thread 里明示原因。§12 由 Lead 按裁定 `0ee0c065` 单独做外部复核（gpt-6-astra xhigh），4 轮后 APPROVED，设计门按新 blob 重绑。

代码评审 R1（gpt-5.6-sol xhigh）提出 1 HIGH、1 MEDIUM，均已修复并补了回归测试：朗读块等到 app-server final 才结算（v3 里 `turn.done` 比 final 早约 12 ms，原先会漏检只有 final 越界的情况）；container 复算整份上下文，不再只核 items 合计。R2 又提出 1 HIGH，已修复：final 晚于等待时限到达时仍按原朗读块检查并截断，期间不发下一块；一出现新回合，这个检查就作废，不会误判别的回答。R3（按 Lead 裁定为最后一轮）指出这个检查在几种事件顺序下归属不准（3 HIGH、2 MEDIUM）。已改为按发出顺序排队的待收 final，每条问题都有复现用例和负对照。残余边界：新回合开始后仍未到的旧 final 不再检查，宁可漏截断也不误伤 founder 的回答。

QA@1 返工：QA 的唯一阻塞项是一场会话之后 daemon 退不出。根因是 werift 在 BUNDLE 协商后漏关了被替换 transport 的两个 UDP socket。现在 WebRTC 腿改用 `max-bundle`，真实会话验证关闭后 0 个 UDP 句柄；按 Lead 裁定 `c8e10764` 补齐两点：一是关闭时显式停止每一个底层 transport，不只依赖 `pc.close()`；二是空闲退出和 SIGTERM 都必定退出：清理一完成就立即退出；只有清理真正卡住时才强制退出：idle 路径的期限是 60 s（长于所有有界清理步骤之和）；收到信号时期限提前到 4 s，赶在 launchd 5 s 的 SIGKILL 之前。强制退出前会先按进程组杀掉告警进程；告警发送进程被停掉时，就算 shell 先退出，也会整组 SIGKILL；下次启动时清扫残留的根目录。在途的 lead 告警最多等 8 s，到时按进程组整组终止。werift 没有可升级的版本。
