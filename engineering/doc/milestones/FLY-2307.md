## 交付

本单没有再写一套生产收口逻辑。当前分支的祖先 `069013b25`（FLY-2278）已经让
`DeliveryProjector` 在 launch source row 不存在时依次用 durable
`contract_ref_json.runId` 和既有 episode attribution 找 owning run，并在 run 终态时以
`run_terminal` settle attempt、同步关闭 open episode。继续加 terminal guard、迁移或新告警层都会重复实现。

实现仅把缺失边界固化进现有 projector recovery suite：

- A 从 production-like 的 granted/sent/received launch attempt 出发，先建后清 session，保持 execution
  binding 从未创建，把 run/node 置为 completed/done；terminal-run watch 自然创建 `run_id=NULL` 的
  received episode，随后 projector 通过 durable ref 收口为
  `terminal:settled:run_terminal`，下一轮 watch 不再观测或告警；同时证明同 attempt 没有任何 run-bound
  episode 可污染 fallback。
- B 通过真实 `admitWorkflowExecution` producer 建 active launch attempt，断言 producer 写入 exact
  `contract_ref_json.runId`；在 30/90 分钟边界仍分别发 warning/severe，episode 保持 open，run 保持
  active。没有把真实 stall 一起吞掉。

设计审后的实现修正没有回写已 pin 的 `plan.md`：当前 schema 用 trigger 保证
`workflow_execution_binding` immutable，因此 A 表示 dispatch-intent 已 mint、但 admission/binding 从未创建，
不是 binding 后来被清理。`exploration.md`、`research.md`、测试名和本里程碑已记录该区别，避免维护者以后给
A 加 admission，反而让 authoritative binding lookup 掩盖 `ref.runId` fallback。
