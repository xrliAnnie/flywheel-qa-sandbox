3根因与已落地的修复（PR #1381）

根因不是「opus 这个名字指向了 Codex」，而是两层叠加：

  • 选择层：系统先按当前配置算好选择，然后回头去查这张 issue 所有历史 run（run：一次完整的派单执行）的模型分配，并用历史结果覆盖当前结果。老单沿用了旧配置年代的 astra / sol；新单没有历史，所以正确。
  • 显示层：回执只替换括号里的精确名、保留前面的别名，于是拼出 opus (= gpt-6-astra) 这种自相矛盾的字样。

PR #1381 的修复：新 run 只读当前 models.json；同一个 run 内部把选择「冻结」下来供恢复与重放；回执只从本 run 的冻结记录重建，别名只在能证明它确实指向该模型（同一家厂商、同一型号或同一家族升代）时保留，否则直接写精确名。跨厂商拼接在结构上不可能再出现。

5核心流程：本轮两个节点各做什么

{{D1}}
图 1 · implement 零改动交卷 → QA 四步验收 → 判定与提交
  • implement 节点：核对本地、远端、PR 三处头一致且树干净 → 不改文件、不 merge、不重跑 CI → 直接交卷。任一不一致就停下问 Lead。
  • 前置检查（评审第一轮补上的）：派单命令打的是「管理 Bridge」而不是房内 Bridge。生产 Bridge 还在旧代码上，根本不认「不带覆盖」这个参数。Lead 裁定：QA 节点只挂测试槽的 Bridge（localhost:19873），且它的两个版本号字段都必须等于 7e28dd51c；不满足就停下问 Lead，不许自己部署、不许偷偷去掉参数。
  • QA 节点：先自己起房（房的所有权规则只让 owner 操作，Lead 起的房 QA 碰不了，所以改成 Lead 给参数、QA 自起）；① 精确头 CI 全绿；② 单测一次一个文件；③ 先按哈希算好每张单会落到哪个模型，再用 room drill --real --no-overrides 跑矩阵；④ 用服务生成的重放规格记录强度二证据，并检查回执三项都 satisfied。

房：一套隔离的测试环境（独立 Bridge、独立数据库、独立 Discord 频道），由 Lead 起，参数改动也由 Lead 做。Bridge：Flywheel 的中枢服务，负责派单、记录状态、跟 Lead 通话。

6数据与结构模型（本轮不新增，只沿用）

{{D2}}
图 2 · 从预留到会话的一条记录链；回执只从本 run 的记录投影

判定顺序固定：先断言 回执精确名 = 运行时模型 = 同一次执行的 sessions.runner_model（数据库里记录该会话实际用了哪个模型的字段），再核对实际载体（Claude 的终端界面或 Codex 的会话头）。

一个重要事实：房进程继承宿主的 HOME，所以「房内的 models.json」其实就是生产那份 ~/.flywheel/models.json。任何人改它就是改生产。因此本轮所有节点对该文件只读，QA 在矩阵前后各记一次文件哈希，两次必须一致。

idempotency key：同一次派单的唯一凭证，重试时凭它拿回同一个 run 而不是新开一个。arm：配置里的一个选项，比如 impl_opus；分桶：按 issue 编号与节点名做确定性哈希，同配置下同一张单每次落到同一个 arm。

7QA 验收矩阵（每例都不带覆盖）

先算再跑：分桶是按 issue 编号做确定性哈希，同配置下可以预先算出每张单会落到哪个 arm。QA 在 drill 之前把预期写进报告，「碰运气看落到哪」不算证据。

例输入证明什么
N1 新单 · Opus 桶预先算出必落 impl_opus 的 issue，drill 一次每个节点的 arm 来自当前 modelSplit；回执 opus (= claude-opus-5-5)；回执 = 运行时 = 会话记录
N2 新单 · Codex 桶预先算出必落 impl_sol56 的 issue仍合法选 Codex，修复不是「全量强制 Opus」
O1 老单 · 同配置对 N1 的 issue 再 drill 一次（房内已有 N1 历史）选择与 N1 一致，依据字段里的规则版本是当前版本
O2-seed 老单 · 不同配置历史（强证明）Lead 条件授权：只在房内隔离的 QA 数据库植入一条明确标注 synthetic 的终态历史记录（旧配置的 astra 分配），再 drill 同一 issue修复前会得到 opus (= gpt-6-astra)，修复后应得到 opus (= claude-opus-5-5)。这是「历史不再牵引」在真房里的直接证据。若证明不了房数据库隔离且可写，就不植入，PASS 范围明确缩小为单测 + 源码守卫 + 同配置矩阵

诚实的缺口：驱动脚本把任务类别写死成 code，而 founder 的事故是 simple_code。房内没有现成的、被授权的 simple_code 派单入口（加参数属于产品改动，超出本轮）。simple_code 只有单测覆盖，报告单列，是否算 PASS 阻断由 Lead 定。

每例保留：请求 key、issue UUID、预期 arm、run id、节点 id、执行 id、宿主 models.json 哈希、回执原文（从房数据库取原件 response.resolved.nodeModels，不用重建值冒充）、本 run 冻结分配、运行时的 vendor/model/effort、sessions.runner_model、实际会话证据。

负向守卫：回执出现跨厂商拼接（如 opus (= gpt-*)）直接 FAIL；房参数不可复现（被拒 drill_config_not_reproducible）问 Lead 改房而不是改命令绕过；房头 ≠ 7e28dd51c 停下问 Lead；PASS 被主 PR 身份缺失拒绝时按恢复路径显式交 FAIL 并写明原因，不绕过、不伪造；强度二记录命令返回 0 不等于通过，必须看回执里 verdict / ran / record 三项都 satisfied，不确定时用同一个记录 id 原样重试。

9诚实边界：本设计做什么、不做什么

做：审计头差异并拿到 Lead 裁定；给 implement 节点零改动交卷的边界；给 QA 节点可执行、可判定的矩阵与命令；把上一轮 FAIL 的两处流程缺口封死。

不做：不改代码、不起房、不派单、不判定 QA 结果；不重派生产老单（FLY-2405 / FLY-2909 由 Lead 按既有授权处置）；不处理统计口径（记分卡 mixed 分组是已知的后续项）。

回滚：本 run 无代码改动，配置也不写（生产 models.json 只读哈希），所以没有代码或配置回滚对象；若做了 O2-seed，回滚对象是房数据库里那几行 synthetic 记录，随房拆除一并消失。产品代码若回退会恢复历史继承缺陷，且新旧配置并存后旧代码可能报「历史分配含糊」。

合并 ≠ 生效：merge 与部署是两步，只有独立更新器在它的窗口部署。
