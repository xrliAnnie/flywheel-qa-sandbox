3根因与已落地的修复（PR #1381）

根因不是「opus 这个名字指向了 Codex」，而是两层叠加：

  • 选择层：系统先按当前配置算好选择，然后回头去查这张 issue 所有历史 run（run：一次完整的派单执行）的模型分配，并用历史结果覆盖当前结果。老单沿用了旧配置年代的 astra / sol；新单没有历史，所以正确。
  • 显示层：回执只替换括号里的精确名、保留前面的别名，于是拼出 opus (= gpt-6-astra) 这种自相矛盾的字样。

PR #1381 的修复：新 run 只读当前 models.json；同一个 run 内部把选择「冻结」下来供恢复与重放；回执只从本 run 的冻结记录重建，别名只在能证明它确实指向该模型（同一家厂商、同一型号或同一家族升代）时保留，否则直接写精确名。跨厂商拼接在结构上不可能再出现。

6数据与结构模型（本轮不新增，只沿用）

图 2 · 从预留到会话的一条记录链；回执只从本 run 的记录投影

判定顺序固定：先断言 回执精确名 = 运行时模型 = 同一次执行的 sessions.runner_model（数据库里记录该会话实际用了哪个模型的字段），再核对实际载体（Claude 的终端界面或 Codex 的会话头）。

一个重要事实：房进程继承宿主的 HOME，所以「房内的 models.json」其实就是生产那份 ~/.flywheel/models.json。任何人改它就是改生产。因此本轮所有节点对该文件只读，QA 在矩阵前后各记一次文件哈希，两次必须一致。

idempotency key：同一次派单的唯一凭证，重试时凭它拿回同一个 run 而不是新开一个。arm：配置里的一个选项，比如 impl_opus；分桶：按 issue 编号与节点名做确定性哈希，同配置下同一张单每次落到同一个 arm。

7QA 验收矩阵（每例都不带覆盖）

先算再跑：分桶是按 issue 编号做确定性哈希，同配置下可以预先算出每张单会落到哪个 arm。QA 用配置包已导出的只读函数（不新增产品代码）在 drill 之前把预期写进报告，「碰运气看落到哪」不算证据。

诚实的缺口：驱动脚本把任务类别写死成 code，而 founder 的事故是 simple_code。房内没有现成的、被授权的 simple_code 派单入口（加参数属于产品改动，超出本轮）。simple_code 只有单测覆盖，报告单列，是否算 PASS 阻断由 Lead 定。

每例保留：请求 key、issue UUID、预期 arm、run id、节点 id、执行 id、宿主 models.json 哈希、回执原文（从房数据库取原件 response.resolved.nodeModels，不用重建值冒充）、本 run 冻结分配、运行时的 vendor/model/effort、sessions.runner_model、实际会话证据。

负向守卫：回执出现跨厂商拼接（如 opus (= gpt-*)）直接 FAIL；房参数不可复现（被拒 drill_config_not_reproducible）问 Lead 改房而不是改命令绕过；房头 ≠ 6c091c4fd 停下问 Lead；房服务返回 room_service_disabled 或槽 4 slot_unavailable 都停下问 Lead，不改 --slot auto、不用 1–3 号死房、不改 Bridge 环境；重放规格里「不带覆盖」这个键必须存在且为 true（新头上不带旗子的演练不再写 false，而是没有这个键），键缺失就重跑，不手改规格；PASS 被主 PR 身份缺失拒绝时按恢复路径显式交 FAIL 并写明原因，不绕过、不伪造；强度二记录命令返回 0 不等于通过，必须看回执里 verdict / ran / record 三项都 satisfied，不确定时用同一个记录 id 原样重试。

9诚实边界：本设计做什么、不做什么
