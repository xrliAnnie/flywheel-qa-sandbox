01 / 这次修什么

每次新派单按当前配置选模型、思考投入与比例；同一次运行的重试保留原选择，回执准确说明实际模型。

问题出在历史分配覆盖了新选择。系统已经算出 Opus，随后又拿老单过去用过的 Codex 覆盖它；回执却把新的名字和旧的具体模型拼到了一起。

不是把所有任务强制改成 Opus。当前配置中合法的 Codex 候选仍会按比例被选中。

02 / 核心流程

run 是一次独立派单。同一请求再次到达称为重放；它只能沿用该次运行，不能重新抽取模型。

新请求读取当前模型配置，按节点比例选择候选，再冻结具体模型与投入程度。重放直接读取这次运行的冻结记录。启动与回执共同核对这份记录。

05 / 取舍与验收

  • 采用：新 run 读当前配置；同 run 的恢复、替身与后继节点保留冻结选择。
  • 不采用：给每张老单手工加覆盖。它只能绕开问题，无法让正常派单遵守配置。
  • 不采用：每次节点启动都重新选模型。这样一次运行会随着配置变化而改口，无法可靠重试。
  • 不采用：只修回执文字。模型选择错误也必须修。

验收同时覆盖两张历史老单、新单、合法 Codex 候选、仅修改投入程度、配置换代，以及同一 run 恢复。每例用同一执行标识核对回执、启动记录、会话模型和真实窗口；尚未启动就不能算通过。

本机只跑相关测试。完整检查由下游在固定提交上运行；设计阶段没有启动测试 Runner。

06 / 诚实边界

现在完成的是根因调查与实施方案，尚未修复或上线。既有运行不会自动换模，历史数据与旧回执不重写；配额不足时已有的明确降级机制保持不变。

权重控制确定性分桶，不保证少量派单恰好呈现 3:1。历史统计包含重复起体与显式覆盖，不能把所有偏差都归因于这一个缺陷。
