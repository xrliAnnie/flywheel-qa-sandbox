QA@4：stub 只推动演练，房外 owner 才能判 PASS

stub 是按预设脚本返回 FAIL/PASS 的测试替身。它可以推动受测流程经过 rework，却不能判断生产 PR 是否合格。

  1. 房外 QA 先受控快照并终止错误递归 driver，用 owner teardown 清空 slots 2/3。
  2. Lead 授权安全 fixture issue；明确 QA_FIXTURE_ISSUE != FLY-2922。
  3. 房外 QA 从已安装/构建依赖的隔离 source clone 选择两个显式空槽，禁止 auto。
  4. 真实 Claude 完成 design review；QA-only shim 只能截获 QA execution。
  5. driver Steps 1–9 全过，并证明 FAIL 后出现新的 execution、launch ordinal、dispatch ledger/receipt 与 sandbox PR head。
  6. driver 每步等待预算显式为一小时；超时归类基础设施未决，不冒充产品 FAIL。
  7. 外层 owner 同时核验 StateStore/CommDB 原始行和 driver/Bridge artifact，并证明生产 PR、branch、checkout、push audit 前后不变，再先快照后用 raw test-teardown.sh 拆 owner slot。

诚实边界：这份设计做什么、不做什么

做：定义可信 execution 身份、生产 DAG、房外 QA、房内 sandbox 的 repo、issue、evidence、递归房清场与 teardown 合同。
不做：不在当前 design 节点合 main、改代码、起房、杀 driver 或跑 QA；不授权当前 sandbox 触达生产 PR；不把 CI 绿或 stub PASS 冒充最终 QA；不请求 ship 或 merge。

如果 orchestrator 没有分别绑定 Production Implement 和 Host QA Controller，本计划应 fail closed，而不是让当前房内 actor 临时换 cwd 补位。
