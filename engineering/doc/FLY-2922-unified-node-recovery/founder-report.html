卡住之后，有一个可靠的出口

一句话结论

卡住后重派当前节点；放行必须写出新的派发凭据，关掉死体不再顺带终结整条任务链。

run 是一条完整任务链；Runner 是其中干活的执行体；held 表示任务链暂时停住。恢复后仍是同一条任务链、同一分支。

人工暂停与等待审批仍从同一入口恢复原工作，不强行换体；已完成节点上的业务决定保留原语义。只有执行故障的重派才必须给出新派发凭据。

  1. 确认当前节点和旧执行体，拿到旧体已经退出的证据。
  2. 一次保存新身份、派发账本、前序工作关系和可运行状态；任何一步失败都不算放行。前序工作关系记录新体应从哪次工作取得版本与返工意见。
  3. 调度器读账本启动新体；落地节点继续原操作中未完成的步骤。
  4. 再次失败仍回到同一个恢复入口。

派发账本 是系统承诺启动某个执行身份的持久记录。写入派发与实际启动分开显示；只有启动证据齐全才显示已启动。非首个节点还必须实际读到正确的上游版本与返工意见，不能只有一条无人能接的派发。

恢复回执 是一次放行的固定凭据。故障重派回执包含新执行身份与账本行号；人工暂停或审批探测的回执只证明原工作已恢复，不虚报新派发。同一个请求重复提交，只返回原回执，不多起一具执行体。

为什么选这个方案

选择同一任务链内恢复。 终结后重开会丢失上下文与仍有效的批准，且把“修一次故障”变成“放弃整条链”。

选择一次写齐凭据。 只改状态、以后再补派发，会重新制造看起来恢复但没人干活的空档。

保留安全检查。 旧体仍活着、身份不明或审批内容已变，都不能硬放行。旧故障名字只说明原因，不再各自拥有一套恢复代码。

根据新证据修正盘点。 当前完成提交已经具备原子顺序；当前落地恢复外层也有恢复任务链的逻辑。本方案补真实缺口与回归，不机械重复旧结论。land 是合并及收尾的引擎节点，不是一个新 Runner。

这份设计承诺到哪里

本次交付是实施计划与设计审阅。只修改文档，没有实现、重启、部署或操作线上任务链。

恢复不批准新内容，不补造成功回执，不重复已做的合并，也不清空其他执行体的额度记录。已真正结束的任务链不靠恢复复活。仍活着的返工执行体只重新投递原任务，不强制换体；已被真实恢复收据取代的旧暂停记录保留审计，但不再阻塞新恢复。

本机只跑相关验证；实现后须逐张复现、贯通公共入口与调度器。生产是否可用要由后续真实验收证明。
