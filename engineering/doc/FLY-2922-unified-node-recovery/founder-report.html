FLY-2922 · Engineering Design

只让 QA 走测试替身，真实评审不再被截胡

一句话：把“所有 Claude 都是假人”改成“只有身份确凿的 QA 是测试替身”，设计评审和其它执行仍走真实模型。

一句话结论

QA stub 是质量验证节点使用的可控测试替身，它会按外层脚本的指令给出确定结果。当前故障不是产品恢复链，而是测试替身装得太宽：它覆盖了 Bridge 里所有名为 claude 的调用。

方案是把 raw stub 换成一个身份选择器——身份选择器是一道小门，只在证明调用属于当前 QA 节点时放去替身；没有 Runner 身份的设计评审、版本探测和其它节点全部原参数转给真实 Claude。

验收一句话：同一间房里，设计/实现是真 Codex，跨家族评审是真 Claude，只有 QA 是 stub；外层 driver 仍必须完整跑完并产出最终证据。

故障为什么发生

  1. 测试房把 stub-bin 放到 Bridge 的搜索路径最前面。
  2. 设计评审也执行 bare claude，所以先找到 QA stub。
  3. 评审不是 workflow Runner，没有 FLYWHEEL_EXEC_ID。
  4. stub 正确地拒绝缺身份调用，真实 Claude 评审从未启动，设计节点一直等。

旧行为：全局截获目标：评审真实目标：仅 QA 替身

不能通过“让 stub 接受缺身份”来修；那会抹掉安全边界。缺身份调用应进入真实 Claude。

StateStore 是这间测试房的持久状态数据库。选择器只读查询现有 binding，不写新状态，不改变生产恢复规则。

安全护栏与验收

风险护栏证据
选择器又找到自己，死循环装房前钉死真实 Claude 的绝对路径；拒绝 symlink、hardlink 和带 marker 的 copyalias 负控
qa-extra 被当成 QAnode 必须逐字等于 qa，attempt 必须为正整数近似名称负控
外来 activation 冒充activation 的 execution 必须与环境里的 execution 相同cross-execution 负控
QA 原体恢复没有 activation用 slot DB 的 distinct node binding；唯一 QA 才放行standby QA 正例
Codex producer 被替身化QA-only 目录不得存在 codex文件边界断言

本地只跑一个相关 shell 测试文件、lint 和受影响 build。最终强证据来自 QA@3：真实 Claude 完成设计评审，driver 全链完成，并看到 held → 统一恢复口 → 新派发账本。

取舍与拒绝方案

选择：测试房内的身份选择器

优点是改动集中在 harness，production 默认行为零变化；也能覆盖没有 activation 的 QA standby。代价是 shell 选择器必须认真防自引用和身份歧义。

拒绝：给生产 runner adapter 加 per-node binary override

边界更纯，但要修改 Blueprint、adapter context 和多个执行后端，只为测试房加产品级 seam，回归面不值。

拒绝：只把 review binary 钉死，或直接去掉 QA stub

前者只救评审，仍会误伤版本探测和 Claude fallback；后者会回到房内 QA 等外层最终回执的递归死锁。

诚实边界

这份设计只解决 QA harness 的进程选择，不重新打开 FLY-2922 的产品状态机设计，也不宣称产品修复已经通过真房。

  • 它不会让 inner QA stub 生成 PASS 或最终 529 证据。
  • 它不会修改真实 QA 的角色规则、review coordinator、StateStore 事务或 evidence judge。
  • 它不会把上次两小时卡死的房追认为成功。
  • 完成仍要求 exact-head CI、可合并状态、两个真实 Lead 和完整 held → recovery → dispatch 场景。

本页是设计交付，不是上线或验收收据。
