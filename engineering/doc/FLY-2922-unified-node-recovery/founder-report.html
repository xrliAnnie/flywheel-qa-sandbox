FLY-2922 · Engineering Design

让测试房看见自己的活进程

一句话：把 driver 的探活查询固定到当前测试房的 tmux server，避免把正在等待返工的实现体误判为死亡，同时不碰产品恢复逻辑。

一句话结论

tmux server 是承载终端窗口和 pane 的后台进程；每个隔离测试房都有自己的 server。QA@3 卡住，不是产品没有派出 QA，而是外层 driver 去宿主 server 查房内 pane，得到“找不到”，再把活实现体误写成 dead。

设计决定：所有 driver pane 探活只走一个 probeRoomPaneAlive 入口。它使用当前房间的绝对目录选择 tmux server，再校验 pane 身份、存活位和 execution 身份。

旧：查宿主 server新：查当前房间产品状态机不改

QA@3 为什么停在 step 4

  1. slot 4 已走完 step 0–3；实现体已经 ship_parked，QA 也已经派出。
  2. 实现 pane @5 活在房间专属的 tmux server 上。
  3. driver 删除了 TMUX 和 TMUX_PANE，却沿用了宿主的 TMUX_TMPDIR。
  4. TMUX_TMPDIR 是 tmux 找 socket 的根目录；它选错，就等于拨错房间。
  5. classifyImplementPark 是 step 4 的分类函数。它要求 liveness=alive，因此一直拒绝通过。

这不是放宽分类规则的问题。状态证据本来是对的，driver 只是从错误的位置读取活性。

关键取舍与拒绝方案

选择：library 内的单一 room-scoped helper

优点是 driver 所有探活消费者共用同一 socket 选择和身份校验，且可以注入 spawn 做确定性测试。代价是 helper 显式知道 slotDir，但这个目录本来就是装房的权威坐标。

拒绝：直接拼 -S /tmp/.../tmux-<uid>/default

虽然更显式，但会复制 uid 子目录和默认 socket 名，形成第二套房间布局合同。用 TMUX_TMPDIR=slotDir 能复用 tmux 自己的标准解析。

拒绝：全局修改 driver 或 Bridge 的 tmux 环境

作用域太宽，会让 teardown、宿主诊断或未来新增调用意外进入房间 server。探活边界应局部、可审计。

main 冲突取舍

scripts/test-deploy.sh 同时保留本单的 --qa-stub-runner 和 main 的 --codex-source-home。两项分别控制 QA 替身与 Codex source-home fixture，不互相吞并。

诚实边界

这份设计只修 529 QA harness 的观测坐标，不修改 FLY-2922 产品恢复代码，也不重新判定先前 QA@3 为成功。

  • 不改变统一恢复口、派发账本、complete 顺序或 carrier-close 行为。
  • 不放松 step 4 的状态条件；只让它看到正确 server 的真实 liveness。
  • 不把 unit test、lint、build 或 CI 当作 held → new dispatch 的真房证据。
  • 最终仍需 QA@4 在 exact head、full CI 绿且 PR mergeable 后跑完整 driver。

本页是设计交付，不是产品验收、ship 授权或上线收据。
