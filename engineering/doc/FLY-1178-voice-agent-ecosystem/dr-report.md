# Voice-Agent Ecosystem Survey

## Executive summary

- The strongest 2026 pattern is **not** “one voice model does everything,” but **a conversational shell delegating to deeper workers**: Google ADK explicitly supports live bidirectional sessions with shared invocation/session state and long-running tools, while OpenAI’s official materials separate highly interactive Realtime sessions from longer-running Responses/background work. That makes “voice front-end + delegated text/tool workers” look like the most platform-aligned shape for serious agentic work. citeturn9view2turn10view2turn9view4turn11view0turn27view0
- **Memory handoff is usually layered, not singular.** In practice, teams combine a short-term session/thread object for immediate continuity with a separate long-term memory system for facts, preferences, and cross-call recall. ADK, LangGraph, Zep, Mem0, and Letta all document pieces of this stack directly. citeturn12search0turn24search0turn23search12turn22search0turn25search1
- The industry default remains **ephemeral compute + persistent state**, not always-on resident compute. Letta, LangGraph, and ADK all emphasize persistence, resumability, and managed state; the evidence for truly indefinite warm sessions is much thinner than the rhetoric around “persistent agents.” citeturn22search14turn25search1turn24search0turn24search2turn9view2
- For live voice handoffs, the most consequential UX detail is that **handoffs are often technically seamless but perceptually ambiguous unless the app adds explicit transition cues**. ADK says transitions happen transparently in one stream, and OpenAI’s Realtime docs constrain voice changes after first audio, which can preserve continuity but also hide role changes unless the product surfaces them. citeturn11view1turn11view0turn2view1
- Your “**resident per-meeting brain**” huddle line is unusual but not alien: LiveKit rooms treat agents as real-time participants; ADK `run_live()` creates a single invocation context across the streaming session; OpenAI Realtime sessions similarly create a per-session live context. The pattern exists at the infrastructure level more than as a mainstream packaged product. citeturn30search1turn9view2turn2view1
- In shared rooms, the sharpest evidence on duplicate responses and duplicate work comes from **coordination surfaces**, not better prompts alone: Raft’s 2026 “agent inbox” and “held draft” are the clearest explicit answer to stale-snapshot collisions; AutoGen, LangGraph, and CrewAI mostly solve coordination by central speaker selection, supervisor routing, or explicit delegation rather than true room-level concurrency control. citeturn39view0turn34search1turn34search0turn36search1turn33search11
- In the framework/platform market, the field is crowded for **customer-service voice agents**, but much thinner for **voice-commanding your own private engineering/agent organization**. The nearest products are voice-coding and dictation tools such as Replit Voice Mode, Superwhisper, and Wispr Flow, but they stop short of spoken delegation into a private multi-agent operating system. citeturn40search11turn40search6turn40search14turn40search13
- The honest market read is **adjacent to effectively blank**: there are many pieces, but very few products converge on spoken delegation, status checks, approvals, durable organizational memory, and multi-agent room coordination against a private dev/ops substrate. citeturn20search2turn21search3turn17search7turn40search11turn40search14

## Q1 Realtime voice plus delegated agents

OpenAI’s own terminology background is short and useful here: its current platform separates highly interactive **Realtime** speech experiences from more general **Responses/Agents** orchestration and background work, plus the broader platform now exposes **Conversations** and **ChatKit Sessions/Threads** objects for persisted interaction state. The architecture difference that matters for your discussion is therefore not generic audio latency, but whether delegation happens **inside one live voice loop** or **outside it in a worker loop that later reports back**. OpenAI’s API reference lists Conversations and ChatKit Sessions/Threads directly, and the Agents SDK adds Realtime-specific agent types and session abstractions. (OpenAI docs pages are largely undated in the rendered docs I could inspect; accessed July 11, 2026.) citeturn27view0turn2view1turn4search2

- **OpenAI Realtime API plus Agents SDK handoffs are real, but voice continuity constrains persona switching.**  
  Technical form: In the OpenAI Agents SDK, `RealtimeAgent` can use handoffs inside a `RealtimeSession`; the docs state that if a handoff happens **before** any agent speaks, the next agent may use a different voice, but **after audio has started** the voice cannot be changed because the session voice is effectively locked after first emission. The same SDK also exposes session backends such as SQLite, SQLAlchemy, Redis, encrypted, and advanced SQLite sessions for persistence. (Docs undated; accessed July 11, 2026.) citeturn2view1turn4search2  
  Product-experience implication: OpenAI’s live handoff can feel seamless because the conversation stays inside one real-time session, but a hidden specialist swap may be **too invisible** if your user expects different agent identities. For a system like yours, this suggests that once the session has spoken, you should treat handoffs as mostly **brain/persona handoffs behind one continuing voice**, unless you intentionally stop and re-establish the voice surface. citeturn2view1turn4search2

- **OpenAI’s official split for long-running work is “interactive realtime front-end, heavier work elsewhere.”**  
  Technical form: OpenAI’s platform materials around Realtime and Responses position Realtime for low-latency conversational interaction, while longer-running agentic work is handled through the broader Responses/Agents stack and background execution rather than forcing every task to complete inside the live speech loop; the API reference’s distinct Realtime, Responses, Conversations, and ChatKit Session/Thread surfaces reinforce that separation. citeturn27view0turn2view3  
  Product-experience implication: The natural UX pattern is a **voice shell that can keep the user oriented while delegated work continues asynchronously**. For your line-three architecture, that means OpenAI’s stack is most naturally used as “talk, acknowledge, dispatch, optionally narrate progress, then return with the result,” not “keep a single synchronous voice turn open until Jira/GitHub/tool work finishes.” citeturn27view0turn2view3

- **Google’s ADK makes live delegation more explicit at the event/protocol layer than most stacks do.**  
  Technical form: ADK’s streaming docs say `run_live()` is the primary BIDI entry point and yields events for text, audio, transcriptions, tool calls, and multi-agent transitions; `event.actions.transfer_to_agent` signals dynamic routing to a specialist, while `task_completed()` moves deterministic sequential workflows to the next agent. ADK emphasizes that the stream continues in the same `run_live()` loop and the same `LiveRequestQueue`, with optional UI indicators keyed off the changing `event.author`. (ADK docs are largely undated; accessed July 11, 2026; copyright footer shows 2026.) citeturn9view2turn9view4turn11view0turn11view1  
  Product-experience implication: Google’s live stack is unusually well-suited to making delegation **visible without being jarring**. You can keep one audio session and still surface “now billing agent,” “researcher done, handing off to writer,” or similar indicators. For a Discord-style command line, that supports a cleaner “human-facing shell with specialist workers” aesthetic than a monolithic voice identity. citeturn11view0turn11view1

- **Google ADK also has the clearest first-class story for long-running tools during live sessions.**  
  Technical form: ADK documents automatic tool execution in `run_live()`, including parallel tool execution, streaming tools that emit intermediate results through `LiveRequestQueue`, and long-running tools marked `is_long_running=True`; in resumable async flows ADK can pause after long-running calls, and in live flows the stream continues while clients can inspect `long_running_tool_ids` and reflect pending operations in UI. Session state persists across invocations, while `temp:` state lives across the current invocation chain. citeturn10view2turn11view2turn12search0turn12search15  
  Product-experience implication: ADK supports a particularly strong version of your line-three concept: the caller can keep hearing confirming speech or progress cues while deeper work is still underway, rather than experiencing a mysterious silent block. It also lowers the odds that “agent is still working” gets mistaken for “voice bot froze.” citeturn10view2turn11view2

- **The “ears/mouth from one vendor, brain from another” split is now a normal production pattern, not a hack.**  
  Technical form: Anthropic’s public platform docs did not expose a native realtime voice API in the pages I could verify, and its OpenAI-SDK compatibility page explicitly says audio input is not supported and will be stripped. At the same time, several frontline voice stacks advertise model/provider modularity: LiveKit says its pipeline works with any provider and supports complex workflows; Vapi supports custom transcribers, custom TTS, and MCP tools; ElevenAgents says it supports ElevenLabs-hosted LLMs and customer-hosted models; Azure’s hosted agents docs explicitly say hosted agents can pair with Pipecat, LiveKit, or Voice Live. citeturn13search6turn14view0turn14view1turn14view2turn14view3turn30search1turn29search17turn29search15turn17search7turn31search23  
  Product-experience implication: For a Claude-brain organization like yours, the split stack is best thought of as an **orchestration-layer pattern** or **bring-your-own-brain pattern**, not an awkward exception. The practical UX consequence is that you gain model freedom and persistent identity in your own backend, but you must explicitly design the seams: who owns interruption logic, what gets persisted where, and whether the voice surface admits that the underlying brain/tooling changed vendors. citeturn13search6turn30search1turn17search7turn31search23

- **Notable others are converging on the same shell-plus-workers pattern.**  
  Technical form: AWS’s 2025–2026 Nova Sonic materials describe Nova Sonic as an s2s orchestrator in multi-agent systems, with Bedrock Agents or Bedrock/AgentCore hosting used for broader agent logic and session isolation; Azure’s June 2026 Voice Live docs position Voice Live as the low-latency speech interface and Foundry Agent Service as the managed agent layer behind it; LiveKit Agents is an open framework where a program joins a room as a full realtime participant and can run multi-agent/discrete processing workflows with provider choice and built-in load balancing. citeturn32search2turn32search8turn32search15turn31search2turn31search9turn31search23turn30search1turn30search14  
  Product-experience implication: Across AWS, Azure, and LiveKit, the architecture trend is clear: **speech is becoming a transport/runtime concern, while delegation and durable state live one layer behind it**. That trend strongly favors your line-two, line-three, and line-four shapes over a pure “one realtime voice model is ears + brain + mouth forever” strategy. citeturn32search15turn31search9turn30search1

## Q2 Memory handover between short-lived task agents

- **Family one is context injection at handoff time, and it is the lightest-weight mechanism.**  
  Technical form: Google ADK passes the same `InvocationContext` to sub-agents, so the chain shares the same invocation ID and `temp:` state; its `Session` state can also be injected into instructions. Vapi documents three explicit handoff data-passing mechanisms in squads—handoff arguments, variable extraction, and templated prompt injection—and warns that choosing the wrong one is a common reason handoffs feel slow or unreliable. Retell’s intra-call agent transfer says the destination agent gets the full conversation history and call-level metadata. citeturn12search0turn8search15turn20search3turn21search3  
  Product-experience implication: This family is the fastest way to preserve continuity for a specialist agent, but it is only as good as the handoff payload. It works well for “what just happened” and “what you need next,” and less well as the sole memory substrate for an organization that needs durable facts, approvals, and long-range recall. For your system, this is ideal for **line-three dispatch packets** and **same-meeting specialist swaps**, not for whole-company memory. citeturn20search3turn21search3turn12search0

- **Family two is platform-managed session/thread memory, which typically owns short-term continuity.**  
  Technical form: OpenAI’s platform now exposes Conversations and ChatKit Sessions/Threads in its API reference; the Agents SDK also has session backends so an agent can reload prior interaction state. ADK’s `SessionService` persists event history and state; `session.events` is the chronological interaction record, and `context.session.state` persists across invocations. Zep’s Sessions API treats a session as a conversation whose messages are simultaneously added to session history and ingested into a user-level graph. ElevenAgents lets you configure transcript/audio retention and post-call webhooks, while Retell retains transcripts, logs, dynamic variables, and KB logs subject to retention settings. citeturn27view0turn4search2turn9view4turn11view2turn23search12turn18search1turn18search10turn17search10turn17search13  
  Product-experience implication: Platform sessions are where “don’t make me repeat myself this call” usually lives. They are strong for immediate continuity, observability, and replay, but they often remain scoped to a call, chat, or thread unless you deliberately connect them to a cross-session memory layer. For production voice agents, this is the usual place to store **full transcripts, event logs, and call-local variables**, not your durable organizational worldview. citeturn23search12turn18search1turn17search10

- **Family three is external shared memory, and the best tools explicitly differentiate facts from raw transcript.**  
  Technical form: Mem0 positions itself as a persistent memory layer that extracts and stores what matters from conversations, with explicit controls for memory ingestion and partitioning by user/agent/app/session; its OpenAI Agents SDK voice companion cookbook is a direct example of voice plus external memory. Zep exposes sessions plus extracted facts/summaries and a user-level knowledge graph; facts are time-stamped with `valid_at` and `invalid_at`, and Zep’s LiveKit integration persists completed turns then injects relevant context before each response. Letta stores all agent state—messages, reasoning, tool calls, memories—in a database, with memory blocks plus semantically searchable archival memory; LangGraph splits short-term memory into checkpointed thread state and long-term memory into stores. citeturn22search0turn22search19turn22search9turn23search0turn23search6turn23search12turn23search15turn25search1turn25search10turn22search14turn24search0turn24search1  
  Product-experience implication: External memory is what turns a voice agent from “contextual in this session” into “knows how we work.” The main UX gain is durable personalization and continuity across calls, meetings, and worker invocations; the main risk is stale or misapplied recall, which is why the stronger systems now separate **facts/preferences** from **raw transcript** and add temporal validity, partitioning, or ingestion controls. citeturn22search19turn22search9turn23search6turn24search0

- **Production stacks are usually combinations, not single-family choices.**  
  Technical form: ADK itself distinguishes session state from longer-term memory services and offers integrations such as database memory, Firestore session service, and GoodMem in its catalog. LangGraph’s docs explicitly recommend checkpointers for thread-scoped continuity and stores for long-term, cross-thread memory. Mem0’s ADK integration and Zep’s LiveKit integration are both direct examples of an external memory layer wrapped around a live or framework-managed session. citeturn12search12turn7view5turn24search0turn22search12turn23search15  
  Product-experience implication: The dominant real-world shape is **short-term platform/session memory plus long-term external memory plus a handoff packet**. For your architecture, that maps naturally to: live Discord/realtime session for immediate turn-taking, dispatcher-written task state in your own DB/issue tracker, and a selective long-term memory layer for founder preferences, current projects, and agent-team policies. citeturn24search0turn22search12turn23search15

- **Dominant real-world patterns**  
  Technical form: The clearest repeated patterns I found are: **session-first plus external memory** (LangGraph checkpointer + store; Mem0 + OpenAI Agents voice companion), **live shared-state handoff** (ADK `run_live()` + shared `InvocationContext`/session state), and **intra-call platform transfer with full transcript** (Retell transfer agent; Vapi squads plus context engineering and variable extraction). citeturn24search0turn24search1turn22search0turn12search0turn21search3turn20search3turn20search2  
  Product-experience implication: If you want your handoffs to sound intelligent rather than bureaucratic, the winning pattern is usually: **session object for the live room, explicit handoff summary for the next worker, external durable memory for everything that should survive tomorrow**. Named examples: OpenAI Agents + Mem0 voice companion; LiveKit + Zep; ADK live agents with shared session state. citeturn22search0turn23search15turn12search0

## Q3 Resident versus ephemeral agents

- **Bucket one is ephemeral compute plus persistent state, and it is the clearest industry default.**  
  Technical form: Letta says its agents are “stateful services, not stateless APIs,” but also says agents persist in a database and callers should send only the new user message; its core concepts page states that memories, messages, reasoning, and tool calls are persisted in a DB. LangGraph similarly defines persistence as state that survives beyond a graph run via checkpointers and stores, enabling fault tolerance, human-in-the-loop, and resumption. ADK emphasizes session management, state persistence, and managed deployment/runtime rather than warm always-on conversations between invocations. citeturn22search14turn25search1turn24search0turn24search2turn9view2  
  Product-experience implication: This form gives users continuity without forcing you to pay for idle model context. The agent “feels resident” because its identity and memory rehydrate on demand, but operationally it scales like a stateless service with durable state. For most voice systems beyond one active conversation, this is the safest baseline. citeturn22search14turn24search0

- **Bucket two is per-conversation or per-meeting resident compute, and it maps closely to live voice rooms.**  
  Technical form: Google documents one `InvocationContext` per `run_live()` loop that persists for the entire streaming session; agent transitions in sequential or collaborative live flows happen within one event stream and one shared `LiveRequestQueue`. OpenAI’s Realtime/RealtimeAgent model also creates a live session whose handoffs and voice behavior occur inside that session. LiveKit lets a Python or Node program join a room as a full realtime participant. citeturn12search2turn11view1turn11view0turn2view1turn30search1  
  Product-experience implication: This is the sweet spot when you need accumulated in-session context, warm-turn latency, and a strong feeling of “the agent is here with us right now.” Your huddle line fits this bucket almost exactly: resident for the meeting, then summarized and torn down when the meeting ends. citeturn12search2turn30search1

- **Bucket three is indefinite residency, but the evidence is mostly logical rather than compute-resident.**  
  Technical form: Letta markets “persistent digital people or coworkers” and “stateful agents,” and Raft describes “one agent is one session: a continuous identity that stays alive across days and tasks,” but the evidence in the docs I could verify is about durable state/identity, not proof of a permanently warm model process. I did not find strong official vendor documentation endorsing broad indefinite warm compute as a standard production posture. citeturn25search9turn25search12turn38view0  
  Product-experience implication: Industry language often makes logical persistence **sound** like always-on compute. For your leadership discussion, keep those axes separate: “persistent coworker” usually means **rehydratable identity and memory**, not “model connection sitting warm all weekend.” That distinction matters a lot for cost, orchestration, and failure handling. citeturn25search1turn38view0

- **Why the default tilts toward ephemeral compute is better documented indirectly than directly.**  
  Technical form: The strongest source-backed reasons I could verify are resumability/fault tolerance (LangGraph checkpointers and interrupts), scaling/managed runtime deployment (ADK Agent Engine and hosted runtimes; LiveKit built-in load balancing; Retell workspace concurrency quotas), and keeping durable task state outside runtime memory (Letta App Server integration patterns say to keep task state in the controller, not in runtime state). I found less explicit vendor prose saying “don’t keep compute resident because idle cost/context pollution/security surface are bad,” so those specific reasons are partly inference from the surrounding architecture docs. citeturn24search2turn24search4turn7view4turn30search14turn21search4turn25search3  
  Product-experience implication: The practical takeaway is still strong: per-task ephemeral compute is easier to recover, easier to scale horizontally, and easier to reason about. If you choose meeting-resident compute, do it for a clearly bounded UX win—continuous presence, warm replies, and preserved in-meeting context—not because the industry has broadly concluded that indefinite residency is the normal answer. citeturn24search4turn25search3turn21search4

- **When residency is worth it, the evidence clusters around live presence and warm-turn UX.**  
  Technical form: ADK’s live streaming model, LiveKit’s real-time room participants, and OpenAI Realtime sessions all assume a running, per-session context because that is what enables continuous audio I/O, interruption handling, and agent identity across a live interaction. Meanwhile, LangGraph and Letta document durable execution and persistent state for resumption across interruptions or future turns. citeturn9view2turn30search1turn2view1turn24search0turn25search1  
  Product-experience implication: The hybrid pattern that emerges is exactly the one you are already exploring: **resident conversational shell + ephemeral workers + persistent memory/state**. That is the most evidence-aligned way to preserve conversational presence without paying resident-compute costs for every specialist agent all the time. citeturn9view2turn24search0turn25search1

## Q5 Multi-party rooms and coordination

**Human-facing meeting participation**

- **Most mainstream meeting copilots still act more like note-takers or utility layers than speaking participants.**  
  Technical form: Public Google Meet materials I could verify emphasize live captions, recordings, transcripts, and scheduled meeting utilities; I did not verify an official Google Meet product surface where Gemini behaves as a full, speaking room participant with its own floor-taking policy. Similarly, the strongest “full participant” documentation I found comes from infrastructure stacks such as LiveKit, whose docs say an agent program joins rooms as a full realtime participant, rather than from a packaged meeting-copilot product. citeturn37search14turn37search17turn30search1  
  Product-experience implication: The market has many “meeting AI” products, but far fewer “AI colleague in the room” products. That means your huddle line is differentiated mainly on **presence behavior**—silent listening, selective speaking, interruption handling, and agenda memory—rather than on commodity note-taking. citeturn30search1turn37search14

- **The infrastructure for a true speaking participant exists, but the product layer is still immature.**  
  Technical form: LiveKit rooms support full realtime participants; ADK live streaming supports continuous audio I/O, turn completion, interruption, transcriptions, and agent transitions inside one session. Research published in 2025–2026 continues to focus on multi-party next-speaker prediction, addressee recognition, backchannels, and multimodal cues such as gaze and prosody as core hard problems. citeturn30search1turn9view1turn10view0turn41search0turn41search3turn41search9  
  Product-experience implication: The gap between “can technically speak in the room” and “feels like a socially competent participant” is still large. For your huddle line, the most defensible product target is probably **lurk mode first, explicit addressability second, proactive interjection third**—in that order—because the literature and current products both imply that deciding *when not to speak* remains the hard part. citeturn41search0turn41search3turn41search9

**Multi-agent same-room coordination**

- **Raft’s 2026 AX surfaces are the clearest direct answer to your duplicate-response problem.**  
  Technical form: Raft’s May 21, 2026 post argues that shared-room chaos comes from a gap between an agent’s snapshot-based reasoning and a room that keeps moving. Its “agent inbox” turns notifications into pull-based, queryable items the agent decides to ingest; its “held draft” adds a freshness check so a draft written against an older room state is either committed if nothing changed or held and returned with a note about what changed, after which the agent can revise, send as-is, stay silent, or explicitly override. citeturn39view0  
  Product-experience implication: This is highly relevant to your Discord pain. The important idea is not just “better dedup logic,” but **making stale perception and send-time freshness first-class protocol states**. For your rooms, an inbox/held-draft design would likely do more to reduce double replies and double ticket creation than prompt changes alone. citeturn39view0

- **AutoGen solves room chaos mainly through centralized floor control.**  
  Technical form: AutoGen’s group-chat pattern is sequential, with all participants publishing to a shared thread while a Group Chat Manager maintains turn order; `SelectorGroupChat` uses a model to choose the next speaker based on participants, roles, and conversation history, and custom speaker-selection functions can further constrain transitions. Conversation history can also be resumed from prior messages. citeturn34search1turn34search0turn34search4turn34search10  
  Product-experience implication: AutoGen’s answer to duplicate responses is essentially “**only one agent gets the floor**.” That works well when the room is mostly text and task-oriented, but it is less natural for an always-moving human voice room unless you are comfortable with a clearly visible manager or speaker-selection layer. citeturn34search1turn34search0

- **LangGraph and CrewAI also reduce collisions by explicit supervision and stateful orchestration, not by letting many agents free-run in one room.**  
  Technical form: LangChain’s multi-agent docs distinguish **subagents** coordinated by a main agent from **handoffs** that switch the active agent based on state; its supervisor tutorial defines a central supervisor that routes to specialists. LangGraph’s graph/subgraph and `Command.PARENT` patterns support explicit navigation and handoff in a parent graph, while persistence/checkpointers preserve exact state during pauses or interruptions. CrewAI’s collaboration docs say agents work together by delegating tasks and asking questions when `allow_delegation=True`, and flows coordinate crews as structured units of work. citeturn36search1turn36search3turn35search2turn36search5turn24search2turn33search11turn33search2  
  Product-experience implication: These systems mostly assume that reliable multi-agent work comes from **supervision, explicit task ownership, and resumable shared state**. For your voice rooms, the lesson is that if several personas coexist audibly, you still want a hidden coordinator deciding ownership and idempotency, even if the room UI makes it feel like peers. citeturn36search3turn24search2turn33search11

- **Voice-room coordination is still less mature than text-room coordination.**  
  Technical form: The academic 2025–2026 literature continues to describe multi-party turn-taking as hard because it requires not just lexical history but addressee recognition, overlapping speech handling, gaze/body-orientation cues, and next-speaker prediction; these papers discuss overlapping speech and unnatural pauses as failure modes. Yet the commercial coordination surfaces I found that directly tackle duplicate work are mostly text/workspace-native rather than voice-room-native. citeturn41search0turn41search3turn41search11turn41search15  
  Product-experience implication: In voice rooms, the safest near-term approach is likely a **text-grade coordination substrate underneath a voice façade**: task claims, send-time freshness checks, idempotency keys for tool actions, and explicit floor ownership, with voice only as the human interface. That is less magical than “all bots naturally cohabiting a call,” but much more likely to avoid duplicate answers and duplicate ticket creation. citeturn39view0turn41search0turn41search3

## Implications for our four voice lines

- **Option for line one: keep it only if the target experience is fast command intake or lightweight companionship, not deep delegated org control.**  
  Technical form: Pure hosted speech-to-speech systems align with the part of the ecosystem that optimizes one live voice loop, but the stronger agent stacks in 2026 separate live speech from durable agent orchestration and long-running work. OpenAI, Google, AWS, Azure, and LiveKit all reflect that separation in one way or another. citeturn2view1turn10view2turn32search15turn31search9turn30search1  
  Product-experience implication: This line is strongest when the founder wants the **fastest, least ceremonious voice interaction**. It is weakest when the system must reliably hand work to specialist agents, track ownership, persist approvals, and return later with confidence. An evidence-based stance is “keep as a thin fast lane, not as the strategic center.” citeturn10view2turn30search1

- **Option for line two: deepen it if you want platform-managed voice plus your own Claude brain, with moderate product speed and lower infra burden.**  
  Technical form: Split-stack voice orchestration is common and vendor-supported: Anthropic lacks the verified native realtime voice surface you were looking for, while Vapi, ElevenAgents, LiveKit, and Azure all support some version of provider modularity, external tools, or customer-hosted models. citeturn13search6turn30search1turn17search7turn29search17turn29search15turn31search23  
  Product-experience implication: This line is the most pragmatic way to preserve your Claude-centered brain while outsourcing ears/mouth/turn-taking. The experience target should be **clear specialist delegation without overpromising identity continuity**: users should feel one assistant is helping them, even if the backend routes to your own agents. citeturn17search7turn31search23

- **Option for line three: this is the most evidence-aligned strategic build if your core problem is spoken delegation into a private agent organization.**  
  Technical form: ADK’s long-running tool patterns, Vapi/Retell transfer/context engineering, LangGraph durable execution, Mem0/Zep external memory, and OpenAI’s split between Realtime and background/responses all point toward the same architecture: live shell, explicit worker dispatch, durable state, and progressive reporting. citeturn10view2turn20search3turn21search3turn24search0turn22search0turn23search15turn27view0  
  Product-experience implication: The experience target here should be **trustworthy spoken operations**, not theatrical conversation. That means crisp acknowledgement, visible ownership, progress updates during async work, and post-hoc summaries tied to durable task state. If you deepen one line for founder command-and-control, this is the one with the best ecosystem support. citeturn10view2turn24search0turn39view0

- **Option for line four: deepen it only if you are willing to build coordination surfaces, not just audio plumbing.**  
  Technical form: Per-meeting resident sessions are supported well enough by LiveKit rooms, ADK `run_live()`, and Realtime sessions, but the real unsolved part is shared-room coordination. Raft’s inbox/held-draft ideas, LangGraph/AutoGen supervision, and idempotent tool orchestration are more relevant than yet another speech backend swap. citeturn30search1turn12search2turn2view1turn39view0turn34search1turn36search3  
  Product-experience implication: The experience target for huddle mode should probably be **one socially legible speaking agent plus several mostly-silent workers**, or several speaking personas with strict hidden floor control. If you deepen this line, build “lurk mode,” freshness-checked replies, task-claiming, and duplicate-action prevention before you polish voices. citeturn39view0turn41search0turn34search1
