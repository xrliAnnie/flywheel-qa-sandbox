CI 装包步骤两波全仓卡死 — 根因与修复设计

FLY-1905 · 2026-08-19 · 设计阶段(未实施)· 每个板块下方都可以留评论,页尾一键汇总复制

一句话总结

卡死的导火索在 GitHub 那边(Azure 的 Ubuntu 软件源当天两次故障),但「一次故障 = 烧掉 11 个 job × 15~20 分钟」是我们自己的 CI 结构放大出来的——修法是「先验证、再跳过」:每次开工先花几秒真实验证工具在不在、跑不跑得动、版本够不够,全过才跳过安装(时间照省);任何一项不过就明确报错并自动补装,补装走「带秒表的加固通道」,故障时几分钟内明确报错,而不是静默挂满。

名词:CI = 每次提交代码后自动跑的测试流水线;job = 流水线里的一台临时测试机的任务;apt = Ubuntu 系统的软件安装器;软件源(镜像)= apt 下载软件的服务器。

铁证(从 GitHub 原始日志逐行取的):卡死的每台机器都停在同一处——apt-get update(刷新软件目录)向 azure.archive.ubuntu.com(GitHub 测试机内置的 Azure 软件源)拉索引时,连接半死不活;同一步骤里微软和谷歌自家的源都是毫秒级返回。最狠的一条:一次 CI 的 7 台机器在同一分钟内全部卡死——7 台互不相干的机器同时出事,只可能是共享的外部源坏了,不是某台机器自己的问题。

另一个关键实测:apt 自己带的超时机制没有救场——最后一行输出之后 14~18 分钟零动静、不自己退出,直到撞上 job 的 15/20 分钟上限被杀。所以修复必须外挂「强制秒表」,不能指望 apt 自己。

② 「是我们这里有什么问题吗?」— 分两层回答

导火索在外部:Azure 的 Ubuntu 软件源当天两个故障窗。这是 GitHub 官方社区多年反复出现的已知毛病(有一串历史工单),我们控制不了,必须假设它还会再犯。

放大器在我们侧(三条,全部可修):

  1. 装了根本不需要装的东西:实测当前测试机镜像里 tmux、lsof、sqlite3 全部预装,真正缺的只有 ripgrep 一个 1.5MB 的小工具。可 CI 每次跑 7 遍安装步骤,其中 5 遍是 100% 无用功;
  2. 每遍都先跑最脆弱的 apt-get update:为下载 1 个小文件,先向故障源拉 4 份大索引 × 7 遍——把暴露面放大了几十倍;
  3. 零超时、零重试、零快速失败:唯一的止损就是 job 的 15/20 分钟上限,所以一次源故障 = 每台中招机器满额烧完。

③ 修复设计:一个统一的「聪明安装」小脚本

三处 CI 安装步骤全部改为调用同一个小脚本 scripts/ci-apt-install.sh,逻辑如下:

  • 先验证再跳过(不是「预装就信」):每个工具做三重验证——在不在、真实跑一下动不动、版本是否 ≥ 写死在脚本里的最低要求(白纸黑字可审计)——全过才跳过安装 → 5/7 台机器常态下零安装零联网,对软件源故障彻底免疫;验证不过(缺了/坏了/版本不对)就明确报出原因并自动补装;
  • 跳过 update 的快路:剩下 2 台只下载 ripgrep 一个包,不再拉索引(用镜像自带的目录),暴露面缩到原来的几十分之一;
  • 双层强制秒表:每条 apt 命令外挂 2 分钟硬闸(timeout 命令),整个步骤再加 8 分钟上限——最坏情况 ~6 分钟明确报错,错误写清卡在哪一步,不再静默烧 20 分钟;
  • 换源重试:快路失败就切到 Ubuntu 官方全球源(绕开出故障的 Azure 源)再试一次——按今天的故障形态,这一步大概率能让 CI 保持绿灯;
  • 防回归门闩:CI 结构守卫测试从「必须有 apt-get update」翻转成「禁止任何人再写裸 apt 命令」,以后谁想加回老写法,CI 直接拦下;
  • 防假成功:装完再复查工具真的能用,apt 说成功但没装上也会报错(不给「假绿灯」留门)。

⑥ 诚实边界:这个设计做什么、不做什么

  • 做:治「放大器」——源再故障时,5/7 台机器无感,2 台大概率换源保绿,最坏 ~6 分钟具名失败;
  • 不做:治不了「导火索」——Azure 软件源还会坏;也不承诺「全网源都挂时 CI 仍是绿灯」(那需要上面被延后的彻底零安装方案);
  • 如实标注:issue 里怀疑的「dpkg 锁竞争」(两个安装程序抢同一把锁)这次没有发生——日志证明卡在联网拉索引阶段,根本没走到装包环节。锁超时参数照加,但它是防御措施,不是这次的病因;
  • 「万一装的有问题/版本不对呢?」(你在 thread 里的质疑,已折入设计):跳过安装的前提不是「它预装了」,而是每次都真实跑通探针命令 + 版本 ≥ 最低要求;装了但坏了、版本漂移、哪天 GitHub 换镜像把预装拿掉——三种情况都会被当场抓住、报出原因、自动补装,补装完还要用同一把尺复查。省时间只发生在验证通过之后;
  • 验证的边界:探针验「存在 + 跑得动 + 版本达标」,不是全功能体检——工具若以更隐蔽的方式坏掉,由真正使用它的测试兜住(那些测试本来就是硬失败设计);
  • 评审来源说明:常规的 Codex 设计评审当天额度耗尽(5 个账号全部实测被拒,当晚 11 点后才恢复),Gemini CLI 免费层已停服;本设计改由一个独立上下文的 Claude 评审员(与作者无共享记忆)做了对抗性评审。如需 Codex 复评,额度恢复后可随时补跑。

⑦ 验收标准与下一步

  • 模拟故障验收(issue 要求④):测试里人为注入「源挂死」和「锁被占」两种模拟,安装脚本必须在秒级预算内明确报错,绝不挂死——这两条写成常驻自动化测试,以后每次 CI 都跑;
  • 真机自证:合并后每次 CI 都真实走一遍「缺 ripgrep → 快路安装」,修复主路不是死代码;PR 自己的 CI 就是第一次真机验收;
  • 下一步:本页是设计交付;接下来由实施节点按计划落地(先写测试再写脚本)。改动范围 = CI 流水线 + 它的四处守卫测试,零生产运行时代码;出问题一个 revert 即可整体回滚。
