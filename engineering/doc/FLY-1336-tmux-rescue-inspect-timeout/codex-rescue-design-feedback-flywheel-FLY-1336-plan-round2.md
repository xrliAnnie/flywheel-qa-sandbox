# Design Review — FLY-1336 plan.md (Round 2)

Date: 2026-07-17
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 2 substantively addresses all eight Round 1 findings: the new bounded-inner design, narrowed pending scope, end-to-end `success:true` contract, parked-safe cleanup, test seam, and atomic sequencing are all materially better. Two new implementation blockers remain in the canonical plan: the stated budget initialization permits nested recovery to start a second 60-second clock, and the proposed pending-response write violates the current durable-response contract. A few smaller contract clarifications are also needed so implementation does not reintroduce false failures or overstate process-tree containment.

## What's Good (Keep)

- Commit 1 is now correctly atomic across the rescue script and both TS callers; this avoids shipping a larger inner latency envelope behind the old 10-second outer cap.
- A static total inner budget is the right way to make runtime independent of candidate count and orphan-recovery iterations. The default arithmetic `20s lock + 60s inner budget + 5s startup <= 90s`, with a 210-second deadline for two attempts, is coherent once the budget is truly shared.
- Moving numeric parsing and arithmetic to `awk` is Bash 3.2-compatible and preserves the existing positive-fraction timeout contract. The explicit `rc=3` timeout propagation for `ps`/`lsof` closes the Round 1 observability hole without weakening fail-closed verdicts.
- Pending semantics are now correctly restricted to generalized launch delivery, where durable launch-owner evidence exists. Keeping both `waitForSession` failure contracts unchanged and preserving workflow-engine fence/hold behavior is the right scope boundary.
- `HTTP 202 + success:true + pending:true` matches the real gateway contract: `mapHttpDispatchOutcome` maps 2xx plus explicit `success:true` to dispatched, while the old code strings have no additional runtime consumers in this worktree.
- The guarded `RunDispatcher` catch is consistent with the existing commit-refusal paths: an already-cleaned entry is not touched again, a replacement entry is protected, and `LifecycleParkedError` does not trigger `onSpawnFailed`. The proposed three-part tests cover the meaningful branches.
- The exported `ensureSessionWithRetry` helper is a feasible hermetic seam while retaining `deps.ensureSession` as the full-replacement seam. Keeping process status as the sole verdict avoids coupling correctness to logging output.
- Sentinel-matrix work is now out of PR scope, the symlink operation is correctly described as a deployment prerequisite, and the real-hold byte-stability tests preserve the split-brain/saturated/ambiguous fail-closed boundary.

## Issues & Recommendations

1. **BLOCKER — The plan currently gives nested orphan recovery a fresh total budget instead of one shared 60-second clock.** Plan §2.1 says `_tmux_socket_ensure_locked` and `_tmux_socket_recover_locked` each record their entry time (`plan.md:42-45`), but the real ensure path invokes recovery inside command substitution at `scripts/lib/tmux-server-rescue.sh:364-366`. If recovery initializes its own start time there, ensure can spend nearly 60 seconds before that call and another 60 seconds inside it, invalidating both the 90-second attempt proof and the “independent of recovery shape” acceptance criterion. A `/bin/bash` probe also confirmed that a command-substitution child inherits the outer `SECONDS` progression, but resetting its own clock does not reset the parent; the outer call simply blocks while the second clock runs. **Fix:** define one normal-variable budget anchor initialized only if absent by the top-level locked dispatch; nested `_tmux_socket_recover_locked`, `tmux_socket_inspect`, and all helper command substitutions must inherit that anchor. Direct `recover` may initialize it because no anchor exists. Sample/cache the load factor before entering command substitutions for the same reason—cache mutations made only inside `$(...)` do not propagate to the parent. Add a full `ensure -> pre-recovery work -> nested recovery` wall-clock test that spends budget on both sides of line 365 and still stays within one `TOTAL_BUDGET + tolerance`; standalone N/recovery tests do not prove this composition.

2. **BLOCKER — `recordWorkflowStartResponse` cannot record the proposed pending response, and making it do so would break replay semantics.** Plan §4.3 explicitly says to record the pending body (`plan.md:126-130`). The current method rejects unless the reservation is already `launch_committed/responded` *and* the owner generation is committed with `delivery_state === "delivered"` (`packages/teamlead/src/StateStore.ts:13193-13220`), which is exactly the evidence missing on the 202 branch; the write would throw and turn the semantic fix back into a 5xx/false failure. Moreover, the response table stores only JSON and is append-only (`StateStore.ts:12277-12309`), while replay returns cached JSON via bare `res.json(...)` (`runs-route.ts:721-727`): if the guard were relaxed, a cached pending response would replay as HTTP 200 and could never upgrade to delivered success. **Fix:** do not call `recordWorkflowStartResponse` on the pending branch. Cache only the existing delivered 200 response. Add a same-idempotency-key route test: first call returns uncached 202; delivery then converges; replay returns and records the normal 200 without dispatching a second runner. A separate mutable/status-aware pending store is possible but is unnecessary scope expansion for this fix.

3. **HIGH — The claim that outer SIGKILL releases all lock state is contradicted by the lock implementation.** Plan §2.1 says the flock/lockf fd is released when the rescue process exits (`plan.md:45`), but the source deliberately makes the fd inheritable and states that bounded children retain it so the lock is *not* released while a previously started critical action completes (`tmux-server-rescue.sh:568-574`). Node’s `execFile` timeout sends SIGKILL only to its direct child (`TmuxAdapter.ts:1644-1657`), not an independently managed descendant process group. The inner budget should make this backstop rare, but it does not prove descendant termination or immediate lock release. **Fix:** keep the inner-budget rationale, but describe outer SIGKILL as an existing last-resort process-tree risk rather than “同时化解.” If containment is a required invariant, explicitly design and test process-group termination; otherwise avoid expanding this narrow PR and add a regression proving an outer kill cannot allow a critical child to outlive its own bounded timeout or release the lock early.

4. **HIGH — Moving retry lineage/WAL writes before the delivery wait must preserve the existing post-dispatch exception shield.** Today the wait is outside the post-dispatch `try`, while `setRetrySuccessor` and `markRetryDispatchDispatched` are inside the best-effort block (`actions.ts:1165-1188`); the surrounding contract explicitly says any error after `dispatch()` returns must still report success because the runner may already be starting (`actions.ts:1069-1077`, `1251-1257`). A literal move above the wait would put those calls outside that shield and permit a StateStore throw to become another post-commit error response. **Fix:** specify the control-flow shape: attempt both bookkeeping writes under post-dispatch error handling before waiting, then return 200/202 according to the terminal delivery check regardless of bookkeeping exceptions. Add injected-throw tests for both methods, asserting no clean failure/no redrive; do not claim lineage/WAL is unconditionally complete when the store itself rejects a write.

5. **MEDIUM — The outer-budget proof is a default-configuration proof, but the plan currently presents it as an unconditional invariant.** `LOAD_FACTOR_MAX`, lock base, `TOTAL_BUDGET`, attempt cap, and deadline are all independently configurable; for example `LOAD_FACTOR_MAX=8`, a larger lock base, or the documented rollback advice “TOTAL_BUDGET 可设大” can make `90 >= lock + total + margin` false. This configurability is acceptable, just not self-coherent automatically. **Fix:** state the operator invariant explicitly: `attempt >= lock_base * factor_max + total_budget + startup_margin` and `deadline >= 2 * attempt + retry_delay/overhead`; say the 90/210 proof covers defaults. Update rollback guidance to list the paired attempt/deadline changes, and cover one coherent non-default tuple in tests.

6. **MEDIUM — Invalid explicit load-factor behavior is internally inconsistent.** The normative rule says `FLYWHEEL_TMUX_RESCUE_LOAD_FACTOR=0` or negative is ignored and falls through to live sampling (`plan.md:49-55`), while the test matrix requires `factor 0/负 -> clamp 1` (`plan.md:174-177`). On a loaded host these produce different factors. **Fix:** choose one contract and make implementation/tests match it. Given the stated precedence, the smallest correction is to assert “invalid override ignored; valid sampled factor is used,” with a separate malformed-sample case asserting fallback 1.

## Verdict

CHANGES REQUESTED — address items above
