在 codex-runner-contract.md 这份文件的最后面，恰好追加一行 - Sandbox note: runners run only the tests related to their change.，再补一条自动化断言证明这行真的到位了；不改任何程序行为。

这是 QA 沙箱（沙箱：一个和生产完全隔离的测试用仓库和环境，怎么折腾都不会影响真实系统）里的合成任务（人为设计的、刻意简单的任务，目的是让整条自动化流水线真跑一遍而不是测这行字本身）。所以真正被检验的是流程：设计 → 实施 → 开 PR → 评审 → QA 复核，每一步都要留下机器可查的证据。

3数据与结构模型：这份文件是谁在用

被改的文件叫「Codex runner 契约」。Runner 是 Flywheel 派出去干活的 AI 执行体；Codex 是 OpenAI 的编程 AI，Flywheel 支持用它当 Runner。这份契约文件在每次启动 Codex Runner 时，会被逐字复制进它的 AGENTS.md（Codex 每次启动都会读的「行为守则」文件），所以改这份源文件 = 改所有沙箱 Codex Runner 读到的守则。

4实施步骤与「冻结点」

实施节点按 TDD（Test-Driven Development，先写一条会失败的测试，再改代码让它通过，用「红→绿」证明测试真的在管事）走。下图特别标出一个冻结点：进度账本（progress.md，记录做到第几步、崩溃后能续跑的小文件）每次更新都会自动产生一次提交，而每次新提交都会让 CI 重跑并取消上一轮，所以账本必须写在 push 之前，push 之后只读不写。

5关键取舍与否决的方案

决定选了什么为什么
新行放哪文件最末尾，紧跟上一条项目符号，不加空行issue 原文 "at the end"，且 "exactly one line" 意味着 diff 只能是 +1
要不要加测试加一条断言（默认执行，Lead 一句话可退回不加）issue 的完成定义要求「相关测试」；一条断言成本几乎为零，却让 QA 能用机器复核「这行真进了每个 Runner 的守则且在末尾」
本机跑哪些测试只跑那一个相关测试文件，完整套件交给 PR CI本 issue 的本机测试政策明文禁止裸跑全套 pnpm test；巧合的是，新加的这行字说的正是这条政策
要不要改契约版本号不改注释性内容不改变契约语义，而且会违反「只改一行」

否决的备选：

  • 否决 只改文档、不加测试 —— 满足字面但不满足完成定义第 2 条；保留为 Lead 可选的退路。
  • 否决 新开一个「Sandbox」小节 —— 至少 +3 行，违反「恰好一行」。
  • 否决 写到别的角色文件 —— 文件名是 issue 硬指定的。
  • 否决 不改源文件、改在运行时动态注入 —— 过度设计，issue 明说改源文件。
