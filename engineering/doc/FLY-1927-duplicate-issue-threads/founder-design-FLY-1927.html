一条 issue，只留一条工作 thread

FLY-1927 · 2026-08-20 · 设计阶段（未实施，Codex 设计评审 9 轮通过）· 每个板块下方都可留评论，评论只保存在当前浏览器

一句话总结

系统会在真正开 thread 前先记住同一条根消息；之后无论网络超时、进程重启还是两个入口同时开工，都只恢复这条消息对应的同一条 thread，不再另起一条。

根消息是 Discord 里用来启动 thread 的那条频道消息。登记正主是系统认定为这个 issue 唯一工作落点的 thread。两者编号天然相同，这是本设计能把重试锁回同一条的关键。

① 这次到底坏在哪里

现状先发一条频道消息，再从它开 thread；两次请求共用一个 5 秒计时。计时一到，本机只知道“我没等到答案”，但 Discord 可能已经建好了 thread。系统却把“结果未知”当成“创建失败”，下次从头再建，于是产生没人登记的野 thread。

5 / 108 月 20 日新建尝试超时
4 条取证时仍活跃的登记外 thread
62 条7 月以来已归档的同类残留
4 个月缺陷至少自 4 月 13 日存在

这不是最近两天代码改出来的新回归。最近改动没有碰建 thread 路径；昨晚连续新建很多 issue，加上主机繁忙，让一个长期存在的超时缺口集中暴露。

② 修完后的核心流程

先发根消息，拿到编号 p
把 p 写进耐久锚点，再开 thread
超时后保留 p，并探测真实状态
只提升或重试 p，绝不另发根消息

耐久锚点是一条先写进本地数据库的恢复记录，进程重启后仍在。三态探针会把 Discord 的回答分成“确认存在、明确不存在、暂时无法判断”；暂时无法判断时保留锚点并明确报错，不再冒险重建。

结构保存什么谁能看到何时删除
chat_threads已经确认的唯一正主现有事件、发送、归档等全部读者沿用既有生命周期

两张表使用同一个“issue + 频道”唯一键。提升时在一笔本地事务中同时重读正主和锚点：如果别人已经赢了，后来者只清理自己的空根消息，绝不会从它再开 thread。

④ 两个入口撞在一起时，谁赢都只能有一条

  • Lead 通报与开工事件同时来：两边都可能先发出根消息，但只有一个能拿到锚点；败者绝不执行“开 thread”这一步。
  • 登记接口抢先装上正主：锚点认领会在同一笔事务里看到正主，后来者直接复用它。
  • Discord 已建好、本机却超时：下一次用相同编号探测并认领，不重新发消息。
  • Discord 暂时 429、5xx 或拒绝访问：保留恢复钥匙并响亮失败，绝不把未知当不存在。
  • 旧正主已被 Discord 删除：带“已删除”标记的墓碑可在同一事务中替换，保留既有自动重建能力。
  • 根消息被人手工删掉：系统不再猜。把对应登记标记为“已失踪”、保留恢复记录并明确报错；由人确认放弃后，下一次才从头干净重建。绝不自动另起一条。
  • 手工登记接口不再允许顶替：一个 issue 已有活着的正主时，再登记另一条会被直接拒绝（而不是把旧正主顶成无人认领的孤儿）；也不能把别的 issue 的恢复记录抢注成自己的。

⑤ 关键取舍与被拒绝方案

方案判断原因
耐久锚点 + 同一根消息重放 + 事务提升采纳直接保证“重试多少次都只能对应同一条 thread”
只把 5 秒改成 15 秒拒绝只降低概率；机器忙时本地仍可能错过已经成功的结果
按 thread 标题搜索和认领拒绝标题可变且可能重名；已有确定编号，不该靠猜
常驻孤儿巡检或新告警拒绝会增加长期复杂度，却没有堵住重复创建入口
重试若干次后丢弃锚点拒绝丢掉恢复钥匙正会重新制造同一个 bug
根消息消失后自动换一条重来拒绝Discord 未承诺相关的时序保证，自动重来可能弄丢唯一的恢复钥匙；改为明确报错、由人确认
Discord nonce 去重另议会改健康请求形状，并有作者身份与重锚限制，需要独立真 API 验证

⑥ 诚实边界：这个设计做什么、不做什么

  • 做：阻止部署后的新重复 thread；让超时、重启和跨进程并发都收敛到一条登记正主；保持现有对外接口形状不变。
  • 做：把“Founder 对话、开工事件、Lead 通报”都落到同一个正主；独立 QA 会在 529 隔离房跑一次真实 Discord 全流程与超时注入。
  • 不做：本次不清理已有的 4 条活跃、62 条归档孤儿记录；存量清理另开 issue，不搭车生产修复。
  • 不做：不顺手修另一条 resolvedIssueId 回落隐患，也不追查昨晚主机为何突然更慢。
  • 残余：如果进程恰好在 Discord 接受根消息后、拿到编号前崩溃，频道可能多一条没有 thread 的普通消息；它不会变成第二条 thread。
  • 残余：极罕见情况下（有人手工删掉了那条根消息），这个 issue 的自动建 thread 会停在明确报错上，需要人工确认放弃一次才恢复；系统宁可停下来问，也不冒着再造重复的风险自动继续。
