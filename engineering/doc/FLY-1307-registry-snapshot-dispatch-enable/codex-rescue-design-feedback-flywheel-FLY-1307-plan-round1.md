# Design Review — FLY-1307 plan.md (Round 1)

Date: 2026-07-16
Author: Codex
Status: CHANGES REQUESTED

## Summary

该切片在范围、三 PR 顺序、默认关闭策略和 loop 语义上忠实于已批准的伞单，而且 #578、#593、#613 的 substrate 与计划列出的主要接缝都确实存在，因此总体方向可行。当前仍不能直接交给实现者：推进事务、引擎接管标记、review 决策通道、v1 snapshot、materializer 格式，以及 enrolled ship gate 尚有会导致半推进、双驱或绕过门禁的未决契约；其中数项 research.md 审计事实也与当前源码不符。

## What's Good (Keep)

- PR-7 → PR-7.5 → PR-8 的依赖关系正确，且明确坚持 PR-7.5 独立、三片全部落地才关 D，符合 Lead 裁定（`plan.md:20-37`）。
- registry 真相方向审计准确：当前 `node-type-registry.ts:1` 的确反向依赖 `three-stage-phases.ts` 的 badge，而 phase-role、badge、completion-role 仍在 legacy 文件中；保留 `resolvePhaseDispatch` / vendor-model-effort 默认值在 legacy dispatch 层也是正确边界（`plan.md:41-54`）。
- 四要素 loop、`max_iterations`、`on_limit: escalate` 没有扩写或缩减；非法边 fail-closed、并发 advance barrier、crash-point replay 的验收方向正确（`plan.md:68-80,102-110`）。
- default-off、legacy byte-compat、事后关 flag 后 hold、不回落 legacy 的目标，以及 source-outbox 作为 PR-8 硬 gate，都是控制 live 三段式爆炸半径所必需的（`plan.md:138-169`）。
- scope discipline 良好：没有把 FLY-1306、UI、高层编排、node-inject/fork 或任意具名节点类型带入本切片（`plan.md:187-191`）。
- 已落地前提可验证：#578、#593、#613 的 merge commits 都是当前 HEAD 的祖先；六个 seed、v2 selection/admission/output/completion、CommDB source outbox、projector、launch-owner fence 与 Blueprint generalized gating 均存在。

## Issues & Recommendations

1. **[HIGH] `advanceWorkflowRun` 仍留下 claim/completion 与选边之间的非原子窗口，且与伞单的单事务契约冲突。** `plan.md:64-67,179-180` 说 B 的 `/workflow/decision` 提交事务“已按 snapshot 选边”，但当前 `submitWorkflowDecisionByCredential` 只写 claim、核销票并追加 `claim_written`（`StateStore.ts:14752-14931`），没有 edge、loop 计数、run/node 投影或 dispatch intent；`commitEnrolledCompletion` 同样只在一个事务中写 completion、node projection 与 `node_completed`（`StateStore.ts:14491-14587`）。若随后由 `advanceWorkflowRun` 再选边，崩溃或两个 driver 并发时会出现“事实已提交但没边”、重复选边或同一节点走两条边，而伞单明确要求 decision 的 claim→选边→核销→event→loop→projection 在一个 StateStore 事务内（伞单 `plan.md:88-91`），合法转移/event/projection 也必须同事务（伞单 `plan.md:149-154`）。**建议修复：** 在 PR-7 明确定义一个共享的事务原语（例如 `commitWorkflowTransitionTx`）：以稳定 transition/event UID 做 CAS，在同一事务内验证当前 node/attempt + snapshot、写 completion 或 claim、选择唯一合法 edge、更新 loop/attempt/run projection，并写 durable dispatch intent；外部 launch 只消费已持久化 intent。`advanceWorkflowRun` 与启动 reconcile 只能重放这条已定 transition/outbox，不能重新决定边。补 decision/completion 各 crash 点和双提交 barrier，断言恰一 edge、恰一 successor intent。

2. **[HIGH] research/plan 把现有 `/workflow/decision` 当作可直接复用的 review seam，但该路由实际上硬编码为 QA。** 路由要求 reporting session 的两个 role 都是 `qa`（`workflow-decision-routes.ts:183-197`），subject 由 PR head authority 得到（`:199-218`），producer 固定查 `implement`（`:220-238`），predicate 固定映射 `qa_passed/qa_failed`（`:245-264`），成功后还直接调用 legacy `phaseOrchestrator.onQaResult`（`:272-299`）。因此 review session 会在写 claim 前被拒，且即使放开 role，也会绑定错误的 producer/head 并再次驱动 legacy belt；这与 `plan.md:85-89` 的“只接线不新写”不成立。**建议修复：** PR-7 应列出通用 decision canonicalization seam：从 credential→execution binding→pinned node 推导 family/predicate；QA 使用服务端 PR head + 实际 code producer，review 使用 PR-7.5 ledger 中当前 accepted output 对应的 materialized head + output producer；两者进入问题 1 的同一事务原语。engine-owned 决策成功后不得再调用 `onQaResult`，legacy QA 分支和响应保持字节兼容。补 review pass/fail、同厂商拒绝、伪造 client head、旧 materialized head、response-loss replay 测试。

3. **[HIGH] “enrolled” 判别会把 claims-read 迁移状态与新引擎 ownership 混为一谈，现有 v1 snapshot 也不能被 generalized runtime 消费。** `plan.md:58-59,177-182` 用 `claims_read_enrolled / v2 typed snapshot` 描述 engine 接管，并计划 `enrolled ⇒ belt early-return`。但现有 legacy `admitWorkflowExecution` 也会把 `claims_read_enrolled=1`（`StateStore.ts:13829-13835`），legacy shadow run 可以没有 snapshot（`:16253-16270`）；当前 `generalizedExecutionContext` 只承认 schema v2（`:13907-13948`），`parseWorkflowRunSnapshot` 更明确拒绝任何非 v2 snapshot（`workflow-run-snapshot.ts:188-213`）。按现文字 early-return 会搁浅已切 claims reader、仍由 legacy belt 驱动的三段式 run，而所谓“复用 v2 结构给 v1”也没有版本化 parser/admission/dispatch 合同。**建议修复：** 增加独立且显式的 engine-dispatch ownership marker（或给出现有字段组合中唯一、事务性写入且不会命中 legacy run 的精确定义），只能与 start reservation + typed snapshot 一起落库；`claims_read_enrolled` 继续只表示 claims reader。定义真正的 typed snapshot union/versioned parser，使 v1 pin 住 registry capabilities、dispatch 三元组、edge/loop/gate 语义并能走 admission/context/completion；同时说明 successor `StartRequest` 如何保留 legacy 三段式的 `sessionRole`、shared branch、startPoint、TURN/park-wake 与 label bypass。belt 的所有入口和三个 startup reconciler 只对 engine-owned marker early-return。补 design/implement/qa 三种在飞 legacy + claims-read-only + engine v1/v2 的部署分类测试。

4. **[HIGH] 新 `TEMPLATE_DISPATCH` 杆若只按本计划接在 eng-v1 entry，现有 v2 template start 会绕过它和 `claims_read` 前置。** 当前 `/api/runs/start` 在 three-stage entry 之前无条件调用 `resolveWorkflowTemplateSelection`（`runs-route.ts:682-720`）；v2 candidate 会物化并进入 generalized dispatch（`:729-944`）。该链只由 `workflow_generalized_templates ∧ claims_write` 防守（`workflow-template-selection.ts:62-165`; `StateStore.ts:12832-12842,13963-13969`），不读计划新增 flag 或 claims-read。因此 `FLYWHEEL_WORKFLOW_TEMPLATE_DISPATCH=0` 仍可能派发模板，`claims_read=0` 也不会传递性阻断 production enable，违反 `plan.md:138-148` 的总开关语义。**建议修复：** 明确所有 start-time template dispatch（v1 和 v2）共同要求 `template_dispatch ∧ claims_write ∧ claims_read`；v2 再额外要求 `generalized_templates`。在 candidate selection、materialize、admission、successor consume 四个 mutation seam 复检，并把已有 v2 route/readSites 纳入 registry drift。矩阵覆盖 v1/v2 × 每根 flag OFF，逐格断言零 run/reservation/claim/dispatch side effect；已 engine-enrolled run 事后关任一必需 flag 时只 hold，不回落 belt。

5. **[HIGH] PR-7.5 尚未给出可实现的 materializer 输入语法，且 research 对 side-effect ledger 的落地状态不准确。** 当前 `json_v1` 只约束“payload 是可解析 JSON + 大小上限”；代码/文档没有定义 files/path/content/delete 等结构，因而 `plan.md:117-121` 的 path allowlist、canonical serialization 和 git 写入无法从 payload 得到确定行为。另 `workflow_side_effect_ledger.kind` 的 CHECK 已包含 `materialize`（`StateStore.ts:15975-15995`），不是 `research.md:38-40` 所写“kind 待 D 落地”；真正缺的是 materialize API，而且现有 state CHECK/API 是 `intent_recorded→launch_committed→started|abandoned`、并硬编码 `kind='dispatch'`（`StateStore.ts:16443-16533`），与计划的 `intent_recorded→committed→done` 不同。**建议修复：** 在 PR-7.5 写死 versioned docs-output JSON schema、允许的操作/相对路径/编码/总文件数与大小、允许 roots、重复路径和删除语义，以及 canonical bytes→digest→commit/head 的映射；禁止 runner 指定 repo/branch。再选定 ledger 方案：复用现有状态词并给 materialize 定义对应证据，或给出保留全部 dispatch rows/index/trigger 的生产 SQLite CHECK/table rebuild migration 与 rollback；列出 materialize 专用 allocate/transition/reconcile API、fence identity 和每一状态的 crash 证据。否则四类 fault test 没有稳定 oracle。

6. **[HIGH] source-outbox 硬 gate 目前只能证明有 TURN source receipt，不能证明 enrolled run 得到了权威 TURN 历史。** `grantTurn` 虽与 TURN 写同事务插入 source event/history，但把 `target_run_id` 固定为 null，replay 也要求 null（`flywheel-comm/src/db.ts:1700-1793`）；projector 明确拒绝 non-null target，并只写 `workflow_source_receipt`，不追加 run event（`StateStore.ts:15651-15669`）。`plan.md:94-98` 又说“不改 grantTurn 语义”，而 PR-8 只检查 source/history/cursor（`:161-169`），这不足以满足伞单“append-only TURN 源历史投影为权威 run event”的要求（伞单 `plan.md:155-170`）。**建议修复：** 为 engine-owned TURN 定义可验证的 run 归属：优先在 source payload/history 写 `target_run_id`，projector 校验 project/issue/run 与 new-holder execution binding 后，在 receipt 同一事务追加稳定 UID 的 run TURN event；或明确给出等价的、不可歧义的 server-side binding 推导。legacy `grantTurn` 的 null payload 保持原字节。硬 gate 同时断言 CommDB authority/history、payload run binding、StateStore receipt/cursor 和对应 run event，且 poison/deadletter 不得被算作成功。

7. **[HIGH] pinned manifest 的 `ship_claims` 目前没有 enrolled-only 的完整 USE-time 执行点，计划也未指定新增位置。** 生产代码中 `ship_claims` 除 validation/snapshot 不被消费；`evaluateShipEligibility` 只组合 founder merge approval 与 QA（`flywheel-comm/src/ship-eligibility.ts:399-451`），其 claims reader 也只查询当前 QA attempt 的 `qa_verdict`（`:170-259`）。因此 product v1 的 `design_review_approved` 可能在 gate 打开后被 rematerialization 吊销，却没有一个终局 seam 重新验证 snapshot 所列全部 claims；`plan.md:90-93,125-127` 的 gate/吊销顺序不足以单独关闭这一孔。**建议修复：** 在 PR-7 明确一个只服务 engine-owned run 的 terminal/ship precondition：从 pinned snapshot 逐项解释 `ship_claims`，对当前 attempt/current exact subject 做 USE-time resolution，并要求 founder claim 与 materialized/PR head 一致；缺失、fail、conflict、revoked、stale head 全部 hold。把它加在任何 completed/Done/merge 状态变更之前，作为现有 legacy `evaluateShipEligibility` 之外的加法式门，legacy 字节不变。补 product v1 无 QA、review revocation/rematerialization、founder stale head，以及 eng v1 QA/founder 组合矩阵。
