FLY-2694 把 Raya 的「业务大脑」搬进 Flywheel — S1 设计

Issue FLY-2694 · 2026-09-17 · Epic FLY-2679 的第一张子单 · 只设计,不改代码 · plan v3,Codex 三轮评审 7 → 4 → APPROVED,全部采纳无驳回

第一屏一句话

把 Raya 仓里那个零依赖的包 packages/cos(她的业务大脑,即处理日报、summary、目标跟踪等业务逻辑的代码)原样复制进 Flywheel 仓,改名 flywheel-raya-cos,接上 Flywheel 自己的测试与 CI;除此之外不改任何既有文件,不部署,Raya 今天怎么跑明天还怎么跑。

搬什么
120 个文件,一个字节不改
来源钉死在 Raya 仓的一个精确版本(90e433e8)。搬家时逐文件对照指纹,多一个、少一个、改一个字节都会被拦下。
怎么接
零改动自动接入
Flywheel 认包只看两件事:目录在 packages/ 下、包里有 test:run 这个脚本名。补上这一行,workspace、CI、package-gate 三个地方就都自动认得它。
守卫
两份测试锁住合同
「零运行时依赖」「只放松一个编译开关」「不进客户打包闭包」「三条命令行行为不变」——都变成会红的测试,不靠约定。
你要按几次
1 张 ship 卡
就是合并这一个 PR。没有任何授权动作:不停旧壳、不迁数据、不换人设、不碰 launchd。那些都在后面的子单里。

名词:ship 卡= 你在 Discord 上按的合并按钮。workspace= pnpm 管理的「这个仓里有哪些包」清单。package-gate= Flywheel 本地/CI 逐包跑测试并出回执的脚本。CI light shard= CI 里跑「轻量包」测试的那条车道。

怎么做核心流程:六步施工,三个 commit

来源施工步骤commit证据 / 门

  • C1 落盘:临时克隆 Raya 仓(不碰生产机器上的 Raya checkout),按钉死的版本复制;脚本自己算每个文件的指纹跟来源对照,对不上就停。
  • C2 / C3:写两份很小的配置文件(包名、脚本、编译选项)和 README 里的来源说明。
  • C4 守卫:一份在包内(合同不变量),一份在仓根跑构建出来的命令行(三条行为)。CI 里只在既有的一个 step 末尾追加一行,不新增 step——因为 Flywheel 有一个「CI 结构守卫」会拒绝任何新 step(Codex 第一轮抓到的)。
  • C5 lockfile:pnpm 的依赖锁文件必须多一段(否则 CI 的 --frozen-lockfile 直接拒绝);我实测它只多 12 行、零新依赖解析。
  • 三个 commit:①搬运、②守卫(这是「被测版本」)、③证据。顺序是先推 ② 等 CI 跑完记下链接,再推 ③——因为 CI 对同一个 PR 会「新的取消旧的」,一起推就拿不到 ② 的证据(Codex 第二轮抓到的)。

全部变更就这些。设计里有一段脚本把这张表变成机器检查:任何删除、改名、第三个被修改的文件、包目录里多塞的文件,都会让它输出 FAIL。这就是工单判据「全程未触碰任何 raya / updater 脚本」的证据形式。

取舍一件上游方案没核到的事,以及我怎么选的

上游方案(FLY-2680)说「编译配置改成继承 Flywheel 的公共配置就行」。我真的把包放进去试编译了一次:报 170 个类型错误,分布在 26 个文件里。原因只有一个——Flywheel 的公共配置开了一个 Raya 仓没开的严格开关(noUncheckedIndexedAccess,意思是「数组取元素时编译器强迫你先考虑取不到的情况」)。把这一个开关在本包关掉,170 → 0;其它所有严格开关这个包本来就全过。

选项结论理由
A. 包级只关这一个开关,源码不动采用这是 Raya 那边原本的编译语义,不是放松;120 个文件保持字节不改,来源可核;后续子单 S3 删 Raya 仓副本时还能逐文件对照。Flywheel 里此前没有包这么做过,所以用测试把「只关这一个」锁死,并在 README 写明原因。
B. 改 26 个文件 170 处让它满足全部开关不采用破坏「原样搬运」;S3 时两边对不上;而且这是纯类型加固,与「搬家」无关——如果要做,应在 S3 之后单开一张单。
C. 不继承公共配置,自带一份完整编译配置不采用能编过,但会让这个包在 Flywheel 里成为唯一一个「不跟公共配置走」的包,以后公共配置的任何调整都漏掉它。

Codex 评审时用等价的编译参数独立复现了 170 / 0 这条分界。

诚实边界这张单做什么、不做什么

做

  • 把包搬进来、接上测试与 CI、提交依赖锁文件、留下来源与证据。
  • 工单五条判据每条都有对应的机器证据(测试全绿、package-gate 回执含包名、CI 车道日志含包名、全仓 build/typecheck/lint 绿、边界脚本 OK)。

不做

  • 不让 Raya 用上它。调用入口(宿主转接脚本)是 S2;人设投影是 S4;Raya 仓删旧包是 S3。搬完之后 Raya 的行为零变化。

  • 不改搬来的任何测试文件;原来 Raya 仓校验脚本里「空工作区 status 返回空列表」这一条没被现有测试覆盖,由新加的命令行测试补上。
