FLY-2268:工人随时能收信、完成前把信读完、返工唤醒 30 分钟内叫得醒

工程设计说明 · 2026-09-03 · 分支 flywheel-FLY-2268 · 母单 FLY-2248 拆出的工人层(M3) · Codex 设计评审 4 轮已闭合,第 5 轮复审待 Lead 裁定账号(见第 8 节) · 每个卡片下方都可以留意见,页底一键汇总复制

1. 一句话总结

09-01 三起事故(判决秒变死信、三道指令没人读、返工叫不醒只能换人)的共同病根是:工人只在「阶段结束停下来等」的那一小段时间里才有人收信。本单把收信员的工作时间改成「工人从派活到终结的全程」,把「工人正在干活时来的信」记进持久账本、在下一个工作回合边界必读,把「完成」改成「先把信读完才算完成」,再让 loop 入边节点(模板里有返工边指回来的节点)的工人完成后常驻 30 分钟等返工唤醒——原地再派活,不换人。全部机制来自母单 FLY-2248 已定稿并合入的设计,本单只减不增:没有新告警面、没有开关旋钮、没有节点名硬编码。

2. 核心流程:一个工人从派活到终结,信是怎么被收、被读、被清的

三个关键改动串成一条线。① 收信员(Bridge 进程里替 Codex 工人盯信箱文件的小组件;Claude 工人自带轮询,不需要它)在派活提交成功那一刻就武装,而不是等工人停下来;Bridge 重启后由现有的「重新认领在飞工人」流程重新武装。② 工人正在一个turn(AI 的一个工作回合,从收到输入到给出结果)里时来的信,记为「回合中到件」,当前回合不打扰,回合一结束就变成「排队待读」,下一回合开始前必读——这就是「入队 + 下一回合边界必读 + 欠条超时兜底」,不是实时打断(我们查到 Codex 协议里有打断接口,但没有阳性对照证明模型真会读到,所以本单不写成实时)。③ 工人说「我完成了」时,Bridge 先查信箱:还有没读的信,就退回一张「清信挑战」,工人读完再带回执提交,才算完成。

图 1 · 工人一生:武装收信 → 回合中来信延后 → 边界必读 → 完成前清信 → loop 入边节点常驻 30 分钟 → 唤醒原地再派 / 到期关停

3. 数据 / 结构模型:两张新小表、三个新列、一张表换主键

母单已经铺好的东西全部复用:saga 表(把一个跨账本的动作拆成几步、每步都能崩溃后重驱的记账表)早就预留了「常驻到期」这一种动作,本单直接用。真正新增的持久化只有:「常驻宽限表」(每个工人一行,记着第几轮常驻、什么时候到期)、「清信挑战表」(记着哪次完成被暂缓、要读完哪些信)。三个新列都加在现有表上:TURN 传送带(记录「这张 issue 现在谁持棒、可以改代码」的表)加「当前活动回合 id」与「回合代数」,信箱唤醒表加「回合代数」。唯一一处表重建:工人关停请求表的主键从「一个工人一行」改成「一个工人一次请求一行」——这是母单 Codex 评审明确要求的,否则到期关停可能永远等不到自己的回执。

图 2 · 数据模型:实线框为现有表加列或换主键,`workflow_resident_hold` 与 `workflow_completion_drain_challenge` 为本单新表
对象人话为什么不能塞进现有表
常驻宽限表工人完成后「等返工」的第几轮、到期时间、当前状态(常驻 / 已唤醒 / 已到期 / 已收口)现有工人会话表已经有另一套「版本号锁」保护重启认领;再放一套「常驻版本号」会互相误判。一行一工人的小表把两套锁隔开。
清信挑战表「完成被暂缓」那一刻的快照:要读完哪些信、业务提交的摘要、挑战是否已消费那一刻「完成记录」本身还不存在(它就是被暂缓的那条),没有可挂列的行;同业务重试复用同一挑战要靠一条部分唯一索引,宿主表上表达不了。
关停请求表换主键同一个工人可以同时有多张关停请求(合入清理一张、常驻到期一张),各自成行、各看各的回执旧主键「一个工人一行」让第二张请求被静默忽略,到期关停就会等错行。工人退出时一次性确认全部待处理请求。

4. 常驻宽限与到期关停:30 分钟怎么算、到期谁负责、崩溃了怎么办

只有模板里有返工边指回来的节点才常驻(按模板结构判断,不看节点叫什么名字;Codex 与 Claude 工人一视同仁)。工人完成时先向 Bridge 登记一行「常驻 r=1」,拿到到期时间才本地进入等待;返工唤醒来了,Bridge 先把行改成「已唤醒」再叫人,赢了就原地再派活,再次完成就变成「常驻 r=2」;30 分钟没人叫,由 Bridge 的维护 tick(每几分钟跑一次的例行巡检)把行标为「已到期」,再走 saga 四步:铸关停请求 → 等工人回执 → 收口。每一步都能崩溃后重驱,旧版本号的迟到唤醒或到期一律无效。

图 3 · 常驻状态流转与到期 saga(revision 递增;expired 之后的四段 barrier 每个维护 tick 重驱直到回执)

5. 完成前清信:「我完成了」要先把信读完

Bridge 的完成路由是唯一读信箱账本的地方:读不到账本就拒绝完成(宁可晚一点,不能漏信)。有未读信就发一张清信挑战(一次性回执凭证,同一次业务提交重试拿到的是同一张),工人读完带回执再提交;Bridge 再核一遍信件确实已签收,然后把「挑战消费」和「完成记录」放进同一个数据库事务——要么一起成功,要么一起不发生,不会出现「回执烧掉了、完成却没记上」。回执本身不参与业务摘要计算,所以带不带回执的同一次提交不会被当成两次。

6. 关键取舍与被否决的替代方案

取舍选了什么否决了什么、为什么
收信员放哪保留Bridge 进程内 + 重启后重新认领时重武装否决「体外」独立进程:真正的单点是 Codex 守护进程的 socket,socket 死等于守护进程死,母单 FLY-2211 已有同线程复活;独立进程还要一整套启动/收敛闭包,FLY-2216 证明很重。接口不变,将来要换宿主只换宿主。
回合中来信怎么处理保留入队 + 下一回合边界必读 + 欠条超时兜底否决写成「实时打断」:协议里有 turn/steer 接口(本机 0.153.2 已验证 schema 存在),但没有阳性对照证明模型会读到注入内容。实现节点若要做,必须单独提交并附真实守护进程上的阳性对照测试。
回合状态记哪保留复用 TURN 传送带表加两列(Lead 裁定)否决另造一张「每个工人一行」的回合状态表:多一本账就多一处不一致。
到期关停记哪保留复用母单 saga 表的预留 kind否决第二张 saga 表 / 新告警前缀:机制只减不增。
回合写账失败怎么办评审后改fail-closed:写不进去就不推进(不推信、不开下一回合),60 秒内重试,仍失败则工人以「setup 失败」终态退出,交给母单欠条超时兜底否决初稿的「写失败就当边界信、继续跑」:Codex 评审指出这会让当前回合看见本该延后的信,等于机制失效。
关停表换主键怎么保证能回滚评审后改Bridge 启动时先做在线备份 + 前后哈希一致性证明 + 写 receipt;重建门放在打开数据库的第一条语句里复验备份、源库哈希、schema,全部相符才重建,否则一个字节不写否决初稿的「启动时既有备份机制会留快照」(代码里根本没有)与「部署窗口所有写者都停机」(部署脚本实际只停 Bridge)。改成靠精确绑定而不是靠停机。

7. 诚实边界:这份设计做什么、不做什么

做

  • Codex 工人全程收信(不只是 loop 入边节点的工人);Bridge 重启后一个维护节拍内重武装。
  • 回合中来信持久落账、边界必读;回合状态记在 TURN 传送带表,Bridge 重启后靠守护进程回读对账。
  • loop 入边节点的工人(Codex 与 Claude)完成后常驻 30 分钟;唤醒原地再派,到期由 Bridge 权威关停。
  • 完成前清信,挑战消费与完成记录同事务。
  • 关停请求表换主键并给出可回滚的受控重建;母单 Codex 评审留给本单的两项(#3 exact 读法、#5 首次代数=1)全部闭合。

不做

  • 不做实时打断(turn/steer)——没有阳性对照。
  • 不新增告警面、开关、环境变量;30 分钟是写死的常量。
  • 不改信箱的关系/新鲜度模型(FLY-1792)、不改重启认领的判死规则(FLY-2211)、不改「该唤醒还是换人」的判定枚举。
  • 不写反向迁移代码;回滚靠迁移前备份 + 记录好的恢复步骤。

还没被证明的

  • 真机验收(QA 节点做):一个 loop 入边节点的工人完成后,30 分钟内收到返工欠条并被再派活,零人工唤醒;对照臂:不发唤醒,30 分钟后行变「已到期」、关停请求被回执、saga 走到 projected。
