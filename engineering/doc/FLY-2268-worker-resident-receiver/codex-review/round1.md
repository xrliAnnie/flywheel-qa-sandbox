# FLY-2268 Plan Review — Round 1

## Summary

该方案遵守父单 M3 与 Engineering Lead 的既定裁定，核心组件、schema 数量、shutdown exact-request 迁移和 resident-expiry saga 总体可落地。当前仍不能进入实现：receiver 候选集、turn fail-open/restart、drain 原子性、launch snapshot 双向兼容和 CommDB 回滚备份五处会直接破坏硬验收，另有三个应在实施前钉死的 consumer/identity/guard 合同。

## What's Good (Keep)

- §M3 的机制骨架与父单 `0dac08247` 的 M3 文本一致，且扩展仍复用现有 `three_stage_turn`、`workflow_delivery_operation(kind='resident_expiry')` 和既有告警通路，没有重开已裁定的架构选择。
- R5 #3 已被具体化成 exact-request 读取、runtime 多 pending 退出时全量 ACK、caller sweep 和 requested/acked/failed 三态回放；这能避免 expiry saga 等错 shutdown 行。现有单行假设确实分布在 `packages/flywheel-comm/src/db.ts:4962-5028`、`packages/claude-runner/src/codex-phase-lifecycle.ts:287-295,493-519`、`packages/teamlead/src/bridge/codex-phase-shutdown.ts:207-241` 和 `packages/teamlead/src/bridge/land-cleanup-opportunity.ts:33-48`，计划覆盖面基本完整。
- R5 #5 已明确两处 INSERT 首次写 `turn_generation=1`、冲突分支 `+1` 并在同一 upsert 清 `active_turn_id`；该 SQLite upsert 形状可执行，legacy 默认 0 与首次真实 grant 1 也可区分。迁移本身位于现有 `BEGIN IMMEDIATE` 外层事务内，见 `packages/flywheel-comm/src/db.ts:1075-1085,1118-1162`。
- resident hold 的 revision、enter-before-local-hold barrier、旧 revision no-op、expiry 四段 saga 和“deadline 只缩短轮询、只有 shutdown 行才退出”形成了可重驱闭环；Claude/Codex 两家 ACK 证据也分别落到 pane liveness 与 exact shutdown 行。
- 测试矩阵覆盖了 turn 交错、mid-grace 重启、三种旧 shutdown 状态、drain 七个负例和通用节点名守卫，方向正确，应保留。

## Issues & Recommendations

1. **[BLOCKER] `ResidentReceiverSupervisor` 的候选集把“全生命周期收信”错误地绑定到了 loop hold 标志。** 计划目标要求所有 Codex 工人从 admission 到 terminal 全程有 receiver，但 research 把候选集再与 CommDB `sessions.phase_keep_alive=1` 相交；与此同时本单又把该列改成只有 loop target 才写 1。于是所有非 loop Codex 工人都不会被 supervisor 武装，A3(a)/(b) 无法成立。初次武装点也写在 `startDispatcher.start()` 返回后，但该返回只带一个尚未完成的 `launchOutcome`，真正 launch commit 之后还要等待该 promise，过早 arm 会与 CommDB session registration 竞态。建议：receiver 资格只由非终态 StateStore session/binding + Codex `external-watcher` capability 决定，`phase_keep_alive` 只继续服务 hold/doorbell；初次 arm 绑定既有 launch-commit receipt，或让 pending arm 持续重试至 registration 可见。增加“非 loop Codex admission 后立即武装、Bridge 重启后重武装、延迟 CommDB registration 不漏武装”的测试。证据：`engineering/doc/FLY-2268-worker-resident-receiver/plan.md:10-16,144`；`engineering/doc/FLY-2268-worker-resident-receiver/research.md:21-33`；`packages/flywheel-comm/src/db.ts:6580-6602`；`packages/claude-runner/src/CodexTmuxAdapter.ts:2264-2300`；`packages/teamlead/src/bridge/retry-dispatcher.ts:307-315`；`packages/teamlead/src/bridge/workflow-engine-dispatcher.ts:2742-2751,2816-2831`。

2. **[BLOCKER] durable turn 写入被定义成 fail-open，且 Bridge 重启后没有恢复丢失的 turn notification，不能保证“下一 turn 边界必读”。** research 明确说 `onTurnStarted/onTurnCompleted` 抛错只记 diagnostic、不中断 goal；started 写失败时 supervisor 会把 mid-turn 到件当 `queued`，当前 turn 可见，completed 写失败时 `deferred_midturn` 又可能在下一边界仍不可见。更严重的是当前 `ownedTurnIds` 纯内存，重启后为空，只有属于该集合的 `turn/completed` 才被处理；若 Bridge 在 `turn/start` 已成功但 CommDB 未写、或在停机期间漏掉 completion，计划没有 reconciliation owner。建议：把两个回调改成真正 await 的边界 barrier；不能确认 CommDB 状态时禁止 push/开启下一 turn，而不是退化为 queued。reown 时复用现成 `thread/read(includeTurns:true)` 对 `active_turn_id` 做确定性 reconcile，再武装投递；补“外部 turn 已开始、mark 前崩溃”“completion 在 Bridge 停机期间发生”“两回调 CommDB 暂不可写”的回放。证据：`engineering/doc/FLY-2268-worker-resident-receiver/research.md:50-66`；`packages/claude-runner/src/codex-daemon-client.ts:461-468,743-816,840-856,1243-1268`。

3. **[BLOCKER] drain challenge 的一次性消费与 completion commit 不原子，而且 `drainReceipt` 仍会进入现有 completion digest。** 计划步骤是先 `consumeDrainChallengeTx(issued→consumed)`，再调用原 `commitEnrolledCompletion`；两者之间崩溃会留下“receipt 已烧掉、completion 未提交”，重试既不能再次消费，也没有已提交 completion 可幂等返回。当前 `commitEnrolledCompletion` 的权威事务从 `this.db.transaction` 才开始，且在事务前对完整 `completionSubmission` 求 digest；若 event route 原样传递 payload，`drainReceipt` 会污染 `workflow_node_completion.completion_submission_digest`，同一业务提交带/不带 receipt 的重放会冲突。建议：把已验证的 challenge identity 传入 `commitEnrolledCompletion`，在插入 completion、推进 DAG、写 disposition 的同一个 StateStore 事务内 CAS challenge；权威 completion digest 必须使用去掉 `drainReceipt` 的业务 payload。增加“challenge 验证后、completion transaction 前崩溃”“事务提交后 HTTP 响应丢失”“同业务 payload 带/不带同一 receipt 重放”测试。证据：`engineering/doc/FLY-2268-worker-resident-receiver/research.md:212-241`；`packages/teamlead/src/bridge/event-route.ts:987-1049`；`packages/teamlead/src/StateStore.ts:44763-44782,45017-45026,45109-45126,45194-45236`。

4. **[BLOCKER] launch snapshot 的 `<legacy>` sentinel 与 capability digest 迁移不能实现计划声称的双向升级/回滚兼容。** research 规定把 digest 对象里的 `phaseRole` 键替换为 `loopTargetNodeId`，这会改变所有旧 snapshot 的 digest；但 sentinel 只覆盖“旧 `phaseRole != null`”，旧 snapshot 中 `phaseRole=null` 的真实 loop target 仍会因 digest 不同而 reown 失败。反方向也一样：新 snapshot 写 `phaseRole=null`、新算法 digest，回滚后的旧二进制虽然忽略额外字段，却会用旧 `phaseRole` 算法得到不同 digest，在到达计划所称“按现状 terminal”之前就拒绝恢复。此外，旧 `phaseRole != null` 不等价于 loop target，把 `'<legacy>'` 当实际 nodeId 会让非 loop 旧 phase 进入 resident hold，违反 loop-target-only。建议：sentinel 只能表示解析版本，不能作为业务 nodeId/loop 判据；从 StateStore binding + pinned workflow snapshot 还原真实 nodeId 并重新跑 `isLoopTargetNode`。为 digest 保留 legacy verifier 或明确版本化算法，并对 old-null、old-nonnull、new→old rollback 三条真实 snapshot 做双向测试。证据：`engineering/doc/FLY-2268-worker-resident-receiver/plan.md:44,81,108-112`；`engineering/doc/FLY-2268-worker-resident-receiver/research.md:84-99,265-270`；`packages/claude-runner/src/CodexTmuxAdapter.ts:198-227,251-378,413-426,920-937,954-978`；`packages/teamlead/src/bridge/codex-session-reown.ts:165-222`。

5. **[BLOCKER] M3-1 回滚依赖的“Bridge 启动时既有 CommDB 备份”在当前代码中不存在。** 计划正确地服从 Lead 的“受控重建后按备份/恢复边界回滚”，但当前 `CommDB` 构造器直接执行 schema 与 `BEGIN IMMEDIATE` migrations，没有迁移前 backup；仓内 WAL-safe `backupCommDb` 是 FLY-1572 专项函数，并未接入普通 Bridge/CommDB 启动。主键重建一旦发生，回滚旧 schema 不能靠一个并不存在的快照。建议：在 M3-1 部署顺序中明确一个实际可执行的一次性 preflight：对每个目标 project 的 comm.db 调现有 online backup、验证 quick/integrity 与产物路径后才允许首个新二进制打开数据库；记录精确 restore 命令和冻结窗口。测试必须证明“检测到旧 shutdown PK → 先得到已校验 backup → 才重建”，不要求反向迁移。证据：`engineering/doc/FLY-2268-worker-resident-receiver/plan.md:100-111`；`packages/flywheel-comm/src/db.ts:1034-1089`；`packages/flywheel-comm/src/mailbox-migration.ts:1283-1317`。

6. **[HIGH] `phaseKeepAlive` 改形状的 consumer sweep 不完整，按计划直接实施会编译失败或产生错误 prompt。** 计划列了 Blueprint 的计算段、adapter type、snapshot/reown 和 `run-infra`，但当前 Blueprint 还在 prompt 中读取 `${phaseKeepAlive.role}`，Codex adapter 也把 `.role` 传给 phase lifecycle factory；A4 只扫描计算段，抓不到这些遗留消费者。对任意命名 loop target，现有文案还会输出 `DAG workflow undefined parked`。建议：在 §3.1 明列所有直接消费者：prompt 的角色文案从 `ctx.sessionRole` 获取，resident/hold 判定只看 `{loopTarget,nodeId}`；phase lifecycle factory 去掉 role 运行时依赖，role 字面量仅保留在 v1 parser 白名单。加 TypeScript 编译守卫及一个非三阶段名称的 loop target prompt 测试。证据：`engineering/doc/FLY-2268-worker-resident-receiver/research.md:84-99,265-268`；`packages/edge-worker/src/Blueprint.ts:1640-1649,2490-2509,2519-2525,2855`；`packages/core/src/adapter-types.ts:205-210`；`packages/claude-runner/src/CodexTmuxAdapter.ts:1025-1050`；`packages/claude-runner/src/codex-phase-lifecycle.ts:20-39,181-188,349-366`。

7. **[MEDIUM] expiry operation 没有定义既有 saga 表要求的 canonical identity。** `expireResidentHoldsTx` 只规定写 `kind/client_request_id/state`，但已合入的 `workflow_delivery_operation` 要求 `run_id` 与 `canonical_digest` 非空；若实现者自行拼接或只用 `INSERT OR IGNORE`，重复 `operation_id/client_request_id` 无法验证是不是同一 execution/revision/activation 的重放。建议在稳定标识中固定 canonical payload/digest（至少绑定 run、execution、activation、node、revision、expiry kind），并要求命中既有行时逐字段校验、冲突 fail-loud；增加 poison collision 负例。证据：`engineering/doc/FLY-2268-worker-resident-receiver/research.md:100-133,146-156`；`packages/teamlead/src/StateStore.ts:20754-20771`。

8. **[MEDIUM] A7(d) 的“全仓仍恰好三个告警前缀”目前不是一个可执行的守卫定义。** 现有父单机制测试只扫描 `bridge/delivery-contract/**` 的节点名，并在整个 `StateStore.ts` 中只匹配 `delivery_contract_stalled` 这一种构造式；它既没有枚举三个前缀，也不可能按字面证明全仓只有三个 alert UID 前缀。建议把 guard 改成明确的 production construction-site allowlist：本单新增/修改文件只能产生父单允许的三个前缀，receiver/expiry 分别断言落入 `delivery_operation_stalled`；同时保留父单原测试不变。证据：`engineering/doc/FLY-2268-worker-resident-receiver/plan.md:26-27,49,120,124-125`；`packages/teamlead/src/__tests__/fly2248-mechanism-guards.test.ts:25-52`。
