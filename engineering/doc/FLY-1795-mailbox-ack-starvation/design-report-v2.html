FLY-1795 极简方案:两条 SQL 治楔死

Issue: FLY-1795 · 重设计 v2(净删除)· 2026-08-20 · 前版复杂设计已整层作废

① 一句话总结

给 runner(干活的 AI 工人)发的消息投递成功、活也干了,但销账要等它自己想起来跑一条命令——不跑,3 个在途名额被占死,后面的指令每 10-30 分钟才漏一条。修法是删掉「等回执」这个状态本身:投递成功的那一笔更新直接销账。两处小改,各一条 SQL,其余全部不做。

② 最小改动(两处)与流程对比

  • 改动 1:投递成功即销账。消息内容写进 runner 的对话是一次可靠投递(内容必达,下一轮工作必然出现在它眼前)。现在这笔更新之后行还要停着等自愿回执;改后这同一笔更新直接把行销账。「等回执」状态从系统里删除——楔死这个类别不是被守住了,是没了。
  • 改动 2:主动来取也记账。runner 自己来取消息(另一条合法投递路,今晚已有物证)时的销账,同一条 SQL 顺手记下「送出时刻」。此前这条路不记账,账上和「消息被吞」长得一模一样,是今晚三个 Lead 反复取证的根源。

名词解释:销账(ACK)= 告诉系统「这条处理完了,名额可以释放」;在途名额 = 同时允许「已送出、未销账」的消息份数(每工人 3 份)。

③ 你的问题:不需要 AI 销账的话,怎么知道它读没读?

直接回答:旧机制也从来不知道——「读没读」这个信号在旧设计里就不存在,旧销账是个假证人。今晚的两份物证正好是它的双向反例:

  • 账上「已销」但从没被读:5 条消息被自动拉取后调用方把正文弄丢,runner 从没看到内容——账上却是已销账。
  • 真读了但账上「未销」:runner 逐字引用消息编号交了完工报告(= 铁证读过),那几行却挂着未销账好几个小时——就是这次楔死本身。

所以这次改动没有放弃任何真实存在过的「读回执」,它把账本上那个名不副实的字段换成了两个诚实的东西:

  • 「送到了」有了更实的定义:正文已写进 runner 的对话,下一轮工作必然渲染在它眼前——这比「等它自愿跑一条命令」离「读」更近一层,而且不依赖它的自觉。
  • 「真读了」的判据不变、也不动:唯一硬证据从来都是远端产物——runner 的完工报告逐字引用消息编号,和账对得上。这个对账判据我们已经在用,新设计原样保留。

真实的取舍是什么

放弃的是「没销账就自动重发」。而重发对「没在看」实测无效:今晚 22 分钟到 176 分钟的硬卡里,同样的内容一遍遍重发,没有一次唤起阅读——对没在看的人重发 N 次等于 0。真正解卡的从来是换工人或人工介入,那条救济路本来就有、继续在。

④ 新设计的赌注(如实说)

这个方案把一切押在「投递成功」那一笔的严格性上:它的定义必须是「正文确实进了 runner 的会话」,不能有一点松动。如果投递路径谎报成功(说送到了其实没送到),新设计会把那条消息销账——它就真丢了。

  • 所以那一笔写入要有测试钉死:投递返回「成功」的语义测试(成功 = 正文已 durable 写入会话,不是「发出去了」),以及「假报成功」的负向测试。
  • 剩余边界:消息送到后 runner 会话恰好死了、没来得及读——旧机制的重发同样救不了死会话(重发给死人还是死人),救济一直是换新工人,这点新旧无差,只是账面从「死信」变「已销」。

⑤ 改后的消息生命周期

正文永不因销账消失:消息本体在库里存活 72 小时,归档后仍完整保留——runner 取走后自己把正文弄丢的场景,内容随时找得回(要不要加一条只读找回命令,单独小题另议,不捆绑本修)。

⑥ 不做什么(净删除清单)

砍掉为什么
自动收尾钩子替 runner 销账你点名的错签风险;而且改动 1 之后它没有存在理由——没有「等回执」就没有要替签的账
整个告警层(占槽超时告警等)watchdog 洪水的教训;且「占槽超时」这个告警对象在改后不复存在
迁移日志新表 / 告警管道 / 状态机 / 新列前版复杂度的主体,全部不做

验收(三条):构造一个永不主动销账的工人连发多批 → 全部按投递节奏销账,零楔死零饿死;Lead 通道与 Codex 工人行为逐字节不变;任一销账行,账上一条查询讲清经哪条路送出。
