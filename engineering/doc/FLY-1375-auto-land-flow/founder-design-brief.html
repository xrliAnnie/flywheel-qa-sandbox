说完 ship,系统自己收尾

FLY-1375 · 设计定稿 · 2026-07-21

① 这单是什么

你的原话:「我说可以 ship 之后,应该进入全自动流程,但基本没成功实行过。」深诊查清了原因:收尾这套动作本身是好的(那晚人肉走过一遍全套),坏在没有扳机 — 「你批准了」在系统里不是一个事件,合并之后该不该收尾、谁去收,全靠 Tadashi 记性。再加上四个小断口:该关的会话因状态特殊被拒关、工作目录清理只建了一半、一单三个会话要逐个关容易漏、会话被关之前没人给它收拾的机会。

② 怎么解

给流水线补上最后一个自动节点 land:你点 ✅ 之后,引擎(不是任何 AI 的记性)接手把剩下的全部跑完:

你点 ✅→ 验明正身(批的就是这个版本)→ 走 :cool: 安检合并→ 给每个会话 30 秒收拾→ 一键关这单全部会话→ 删工作目录→ Linear 标 Done→ 归档 thread

每一步都留凭据:哪怕中途断电重启,接着上次的位置继续跑,绝不会做了一半却显示「已完成」 — 这正是深诊点名的老病根(系统只信「事件发出那一瞬间」,从不回头核对真相)。

③ 关键取舍

  • 合并仍走 :cool: 安检流程,一字不改(你定的「不许裸合并」红线);只是按下 :cool: 的手从 Runner 换成引擎 — Runner 中途死掉,链条不再断。
  • 你的批准凭据从会话身上摘出来单独保存:以前批准「记在某个会话头上」,会话一关批准就悬空;现在批准独立存在,会话关了照样有效。
  • 宁可重复触发,绝不重复合并:触发允许多来一次(有安检兜住),合并只认准你批的那个版本。
  • 只在新流水线(DAG)上生效:现有在飞单一律不受影响,过渡期 Tadashi 按成文清单人肉收尾 — 清单和自动链用的是同一套动作。

④ 风险边界

  • 分三步交付(骨架 → 能力 → 上线),每步都带「旧路一字不变」的哨兵测试;总开关先关着做安全脚手架,最终交付默认打开(不开就等于没做 — 若有理由不开,会显式来问你)。
  • land 若中途卡住:告警升级给人,恢复有两条路(修好后接着原进度跑 / 止血期间按清单人肉),不会卡死也不会瞒着。
  • 一种特殊会话(还活着但心跳异常的 Codex)不硬杀 — 硬杀会留孤儿进程,这种转人工,其余全自动收。
  • 方案经 Codex 设计评审五轮打磨通过,每轮都抓出真问题并已全部吸收进设计。

⑤ 验收(真机,能力级)

  • 你点 ✅ 后零人工:合并完成 → 工作目录消失 → 这单全部会话关闭 → Linear Done → thread 归档。
  • 故意留一个卡死的会话 → land 照样收掉。
  • 收完之后,同一分支再派新任务能干净启动。
  • 全程 thread 里有播报,每一步看得见。
