FLY-2146 · 记忆定时真同步:以「远端上有没有」为准 + 连续多日新鲜度验证

设计稿 · Codex 四轮 + Lead acceptance 收口 日期 2026-09-04 · 依据 FLY-1984 Epic PRD §A「定时 update」段 · 上游 FLY-2145(A1,仓已建、首搬已推)· 文档 engineering/doc/FLY-2146-memory-remote-sync/

① 一句话

给 A1 建好的记忆仓配两个互不商量的小程序:一个写者每小时把各 Lead 新写的记忆按规矩提交并推到 GitHub,推完只认「GitHub 上那一行 sha 是不是我刚推的」;一个看者每小时跟在后面只看 GitHub 和本地有没有超过一天没送到的东西,有就发告警,并把每一次观察记成一行事后还能拿远端复核的台账。判断「到没到」的证据永远来自远端,不来自本地日志;「连续多日」的证据也放在远端自己身上:记忆仓里一个每天定时跑的 GitHub Actions 任务(GitHub 提供的自动化任务,带服务端时间戳)记下当时 main 的 sha,本机零参与。

「sha」= git 给每次提交算出的唯一编号,远端上的那个编号和本地一致,就是「到了」。「远端」= GitHub 上那个私有仓 xrliAnnie/lead-memory。

③ 核心流程:写者每小时做什么

写者 = com.flywheel.lead-memory-sync,launchd 每小时第 17 分钟触发一次(合盖睡觉错过的,开盖时补跑一次)。它严格按 A1 定下的提交合同走:一个 Lead 夹一次提交、带归属标记、经过 A1 的钩子(钩子 = git 在提交/推送前自动跑的检查,这里是「只准一夹」+ 密钥扫描)。

几条硬规矩

  • 「到了」只有一个来源:推完之后再问一次远端 git ls-remote(= 只读远端当前的 sha),等于刚才本地的 sha 才写 arrived=true。push 命令的退出码、任何日志行,都不参与这个判断。这条是 Lead 的硬要求。
  • 某个夹被密钥扫描拦住:那个夹原样退回不提交,其他夹照常提交推送;整次以非零退出,回执里点名夹与规则编号,绝不记录命中的值。
  • 远端比本地新(另一台机器推过):先把本地各夹提交完,工作树干净才 rebase(= 把本地提交接到远端最新之后);冲突就中止、退回原样、非零退出,不自动解。
  • 只在有新提交时 push,避免每小时空跑远端 CI。
  • 没有任何开关:没有 --dry-run、没有跳过扫描的参数或环境变量(继承 A1 你定的规矩)。

台账每行长什么样(固定表头,远端两列只来自远端)

观察时刻 · 远端sha · 远端提交时间 · 本地未推提交数 · 脏文件数 · 删除项数 · 最老待送内容年龄(小时) · 写者回执年龄(小时) · 标签集合 · 发帖结果。标签 ∈ stale | writer_silent | remote_unreachable | unfetched,空集合就是 fresh。读不到的列写 undetermined,不用 0 冒充;台账、回执、状态文件任一写不进,脚本以专门的退出码收场,不会「远端变了却没证据」。这份台账只是运维心跳和告警依据,不是验收证据:它是本地文件,评审证明事后拿它去远端核祖先关系,证明不了「记录那一刻已在远端」。

写者回执里 arrived 只有一个赋值点:每次结束前重新问一遍远端;push 命令自己的退出码另记一列。「到了但 push 命令报错」和「push 说成功但远端没变」是两种不同的结局,各有各的退出码。

⑤ 看者每小时怎么判、什么时候吵你

看者是另一个进程、另一份代码,它不信写者说的「到了」;它自己去远端读一遍,再看本地有没有东西该送而没送。它只读,不 fetch、不写记忆仓。

结论意思会不会发到 #flywheel-alerts
fresh(无标签)本地待送的东西都在 26 小时内;写者 3 小时内跑过不发
unfetched远端读到了一个本机对象库里还没有的提交(另一台机器刚推、写者还没 fetch)——本地领先多少算不出来,记 undetermined,不当 0;连续两次观察才成立发(独立一本账)
stale本地有内容超过 26 小时没到远端(= PRD 的「第二天」加 2 小时容错)发,点名夹与小时数;持续每 24h 再提一次;恢复时发一条恢复
writer_silent写者 3 小时没留回执,而且连续两次观察都这样(避免整夜合盖、开盖那一刻写者还没轮到就误报)—— 哪怕远端是最新的也报,这正是「日志说完成但根本没人跑」那一类发
remote_unreachable看者自己读不到远端(网络 / 凭据 / GitHub)发

Lead 三天没写记忆不是故障:没有待送内容就不报 stale。删除也算待送:看者第一次看到某个删除时记下时间,之后按它算年龄,不会永远没年龄。

四本告警账各自独立:进入才发一条,发成功才记时;持续每 24 小时再提一条;观察到恢复并且恢复帖发成功才清账;读不到远端的那次不清任何账。检测延迟如实说:stale 最坏在超阈值后 1 小时内报(变化后 27 小时),writer_silent / unfetched 最坏 5 小时。

⑥ 关键取舍与否决掉的方案

取舍选了为什么
写者频率每小时「第二天看得到」留足余量;launchd 日历型任务睡眠错过会补跑,间隔型不会
写者与看者两个独立单元;看者每小时跟在写者后面chezmoi 的病就是「自己推、自己说完成」;分开之后,写者挂了看者会报,看者读不到远端也会报。看者原本设计成每天一次,评审指出那会让 26 小时的阈值最坏 50 小时才发现,改为每小时
「连续多日」的证据远端自己每天记一笔(remote-observe.yml)+ --check-visibleGitHub 只保存提交自带的日期,不保存「这条什么时候到的」;先在本地提交、几天后才推的内容,远端显示的还是旧日期。本地台账事后拿去核祖先关系也证明不了「记录那一刻已在远端」(评审第二轮否掉了这个方案)。唯一本机伪造不了的证据是 GitHub 自己在每天固定时刻记下的 main sha,再拿前一天写的文件去那棵树里比对
到达阈值26 小时PRD「第二天」= 24h + 2h 容错
告警去向#flywheel-alerts,沿用 Bridge 探针那套发帖与去重已有值班流程(claw),不新开渠道

否决的备选

  • 把记忆夹加进 chezmoi 管的 46 项:它六个月没送到过东西、包体 9.76 GiB、要 TTY;而且它是把文件拷到另一个仓再推,A1 的钩子在那个仓里根本不会跑。
  • 一个单元推完自己核实:部件最少,但写者自评,它没装上 / 凭据失效时没人知道 —— 正是现状的形状。
  • 让 GitHub 那边定时检查:远端只知道「多久没来提交」,不知道本地有没有东西该来;Lead 没写会误报,东西卡在本地只能等到期。可作为 FLY-2134 一类的补充,本单不做。
  • 给写者加 --dry-run / 跳过扫描:违反你在 A1 定的「不加任何开关」。
  • 用 git pull --rebase --autostash 应付脏工作树:会把被密钥扫描拦住的内容暂存再弹回,弹回失败留残骸;改为工作树脏就不 rebase、不推、留证据。
  • 拿提交自带的日期当「到达日」做报告:评审证明它会把 4 号才到的内容算到 1 号。
  • 拿本地台账 + 事后祖先检查当多日证据:先把一个只在本地的 sha 写进台账、第二天才推、第三天核,照样能过;改为远端每日观察。
  • 只比「今天远端有没有这个文件」:评审第三轮证明拿一个几个月前就同步过、从没变过的老文件每天 touch 一下,也能连绿三天;改为必须证明「昨天的树里没有或不同、今天的树里一样」这一次真实变化。
  • 测试夹具用 git 的 insteadOf 重定向到本地假远端:评审证明同样的重定向在生产上能把 push 和到达核实一起指到错误仓而假绿,所以生产预检必须拒绝它,测试改用「把脚本拷一份、只替换那一个常量」。

⑧ 诚实边界:这个设计做什么、不做什么

  • 「连续若干天」是关单硬门,不是合并部署的前置,一次 QA 会话验不完:QA 能证明「无人值守连跑两次且远端到达」与「看者能报错」;三天证据来自远端每日观察,齐之前 issue 由 Lead 的「观察中」说明守着,不齐则重开。远端观察任务和 README 一样是仓顶层文件,由 Lead 在 QA 通过后按计划里的逐条清单(命令 + 判据)用管理员身份发布。
  • 远端历史不保存「哪天到的」:报告只能按提交自带的日期分组;所以才需要远端自己每天记一笔。本地台账只做运维心跳。
  • 真第二台机器仍是你的 follow-up;本机 fresh clone 只证明「拉下来 == 远端最新」。
  • launchd 下能不能拿到 GitHub 凭据(存在 macOS 钥匙串里)设计阶段没验;实施时第一次真跑就能看出来,失败形态已写明,失败即上报,不自己改凭据配置。
  • 看者本身没人看:它每小时留一行台账,这是 FLY-2134(「没人监控监控者」那类)可以消费的心跳;本单不做元监控。
  • 另一台机器推了、本机还没 fetch 的那一小时里,看者报 unfetched 而不是假装 0;两台机器同时写同一个 Lead 夹会撞,撞了就中止 + 告警,不自动合并。
  • launchd 单元的配置文件改了不会自动刷新:部署脚本只在缺失时安装,已装的与仓里不同只记「漂移」,要走既有的人工修复路径。回滚也不是删一行就完:部署脚本会把任何还在目录里、没被标记 disabled 的单元重新拉起;仓里也没有现成的命令能卸这两个单元,所以本单附一条最小退役命令(先标记 disabled,再卸载,再把配置文件归档而不是裸删,最后撤代码)。
  • 本单对 A1 的改动只限模板闭包:铺模板脚本、首搬脚本的精确文件集合、以及对应测试各加一行(把远端观察任务铺进私仓);护栏与钩子本身不动。手动补跑与人工重跑的远端观察永不计入验收;三个观察日证明的是两次连续的次日可见,不是三次。
  • 机上那套 chezmoi 同步仍是坏的:它管的 46 项 .claude 条目与本单无关,建议另开单。
  • 告警靠 Discord bot 发帖,token 或频道缺失时看者只能在台账记 post_status=failed;这层与 Bridge 探针共用同一套配置。
  • 设计评审怎么收的口:Codex(OpenAI 的代码评审模型)四轮评审 12→8→8→8 条,后两轮的问题都出在上一轮新写出来的验收清单上;Lead 裁定不再跑第五轮,由 Lead 出面收口:第四轮的 8 条已全部按修法改进计划,并在计划末尾逐条列出处置位置,实现阶段起手再对着最终版本复核一遍当作第五轮。
