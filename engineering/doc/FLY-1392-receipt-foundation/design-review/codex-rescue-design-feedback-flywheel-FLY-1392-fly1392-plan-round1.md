# Design Review — FLY-1392 plan.md (Round 1)

Date: 2026-07-20
Author: Codex
Status: CHANGES REQUESTED

## Summary

总体方向可行：以 `lead_inbox` 承载 Lead-scoped hub、只把可观察业务副作用当 processed evidence，并把 wake 与未处理升级做成持久闭环，符合 FLY-1391 蓝图和 D-1/D-6/D-7 裁定。但 v1.5x.0 仍把“同一个 comm.db”误当成“同一个事务”，且删掉了 FLY-1339 wake 设计中若干防误收据、防风暴和 crash-recovery 的承重合同；按当前计划实现会出现假 processed、重复/卡死重发，以及 kill-Lead 场景永远无法 page founder。以下均是实施前需要写回 plan 的 blocking 项。

## What's Good (Keep)

- 保留 D-1 的协议层 hub / 窄枚举模型巷、D-6 的 `read_at` 零接线，以及 D-7 的保守 `no_route_needed` 方向；没有用弱 ACK 冒充 processed。
- evidence 合同采取“新类型默认不催”、P2/P3 诚实降级，并把蓝图 §2.4 三条原子性要求列为 blocking，原则正确。
- founder 归因、trusted founder writer、FLY-1099 游标/死信纪律、FLY-605 ship wake 反压、FLY-1373 `consumed_at` 语义均明确要求保留，scope 控制合理。
- causal key、持久退避、重发带轮次、一次性升级、kill Lead / kill pane / adversarial fixture / flag-off mutation 等验收目标很有价值。
- 对死分支 `06c6dfa07` / PR #648 的 provenance 标注正确，也明确不继承旧批准。

## Issues & Recommendations

1. **[Blocking — Correctness / Atomicity] 当前 API 形状无法兑现“同 comm.db 事务”。** `LeadInboxQueue` 自己创建私有 `better-sqlite3` connection（`lead-inbox-queue.ts:114-125`）；`CommDB.insertResponse` 与 `insertFounderApprovalResponseWithSource` 又各自在自己的 transaction 内提交（`db.ts:1077-1145,1276-1338`）。`send.ts` 也是先提交 instruction，再调用 wake（`:47-102`）；“caller 持 db 句柄”不等于业务写仍处于一个开放事务。尤其 plan §4 还说 trusted writer “不动”，这与 §0.1、S2/S3 的同事务承诺直接矛盾。**建议：**在 `CommDB` 上定义 connection-bound composite transaction API，逐入口原子提交：`response + founder_msg processed + wake intent`、`trusted founder response + workflow_source_event + founder receipt + wake intent`、`instruction + wake intent`、`route response + 原/模型两行 receipt + wake intent`。trusted writer 的授权/业务语义可以不动，但 transaction body 必须扩展；禁止在这些 unit-of-work 中调用另一个 `LeadInboxQueue` connection。为每个复合 API 写 commit 前、各 INSERT 间、commit 后的 crash-injection。

2. **[Blocking — Correctness / Evidence contract] `deriveProcessedFromResponses(toLead, now)` 不能事后制造可信的 actor+epoch。** response 行有 `from_agent` 和可选的 `sender_generation`/holder provenance（`types.ts:44-66`），但 Bridge/founder 写入者不天然拥有 LeadInboxLoop 的 `loop_owner.owner_epoch`；若在巡检时读取“当前 epoch”，owner takeover 后会把旧副作用错误归给新 owner。plan 的 `{actor: responder, epoch}` 也没有说明 null provenance、founder trusted source 和 `bridge-protocol` 各自如何排除其他 actor。**建议：**把 evidence JSON 做成逐 producer 的 typed contract，并在副作用发生时冻结 fence：Lead CLI 用已验证 lease generation/provenance；trusted founder 写用同事务 `workflow_source_event`/authority source；Bridge protocol 用当时通过 fence check 的 loop owner epoch。推导只能复制这份既存 provenance，缺失或不匹配时不得填 processed。增加 owner takeover、reserved attribution、null provenance、另一 actor 先造成 response 的负测。`route-founder-reply` 成功时还必须同时标记原 `founder_msg` 和 `founder_route` 行 processed；“只 consume 模型巷行”不满足 S4 对 `founder_reply_ambiguous` 的合同。

3. **[Blocking — Feasibility / Lifecycle] `founder_msg` 不能按计划作为普通未消费 protocol 行落库。** 现 `enqueue` 不接受 `delivered_at`（`lead-inbox-queue.ts:127-180`）；所有 `msg_class='protocol' AND consumed_at IS NULL` 行都会被 `LeadInboxLoop` claim（`:328-340`; `lead-inbox-loop.ts:142-179`），而 `ProtocolIngress` 只接受 `ack_receipt`，否则抛 `unsupported protocol message type`（`protocol-ingress.ts:85-88`）。结果是 founder root 被重试/隔离，而不是静候 processed。**建议：**在 plan 写死 hub-root 生命周期。最小做法可以是 admission 事务内同时写 `delivered_at=consumed_at=now, disposition='hub_recorded'`，把“未 processed”完全交给新列；或者增加明确的 `hub_only`/purpose 并让 claim、pending health、batch、quarantine 查询全部排除。无论选哪种，都要新增测试证明 root 永不被 ProtocolIngress/Lead adapter 投递，同时 processed patrol 仍能选中它。

4. **[Blocking — Correctness / Spam & deadlock] S4 没有定义唯一 retry owner，现形状既可能永远卡在 r1，也可能每 tick 连发并逐 resend 升级。** root 的 `resend_round` 是 NULL；若巡检始终看 root，会反复 `INSERT OR IGNORE #r1` 而不进入 r2/cap；若巡检 resend 行，会产生嵌套 id/多 episode。重发后也没有新的 due time，所以一个 30 分钟老 root 可在连续 tick 中立刻 r1→r2→升级。另有 `idx_lead_inbox_ref` 对 `ref_message_id` 全局唯一（`lead-inbox-queue.ts:82-83`），resend 无法复制 question reference，response 后容易只收口 root、留下 resend 继续催。**建议：**只有 canonical root（`resend_of IS NULL`）拥有状态机；同事务计算/插入下一轮并推进 root 的 `next_unprocessed_at`，增加 `UNIQUE(resend_of,resend_round)`，每轮重新等待完整窗口。resend 是 root 的投递 attempt，不是独立 processed/escalation episode；response/route evidence 一次性收口整个 family 并取消未决 attempt。测试重复 tick、重启、并发 patrol、r1 后收到 response、cap 边界、无嵌套 id、root-only once escalation。

5. **[Blocking — Risk / Wake durability] S3 的“零 schema 改动 + metadata”不足以承载 absorbed wake 安全合同。** `runner_phase_wakes` 当前只是 pending/started/finished，且已被 Codex lifecycle 精确逐 message 使用；`finalizeSession` 和 issue-terminal cleanup 会直接删行（`db.ts:2456-2464,2502-2513`），正好会在 dead runner 需要 T3 时抹掉证据。plan 也未定义 initial push 与 T1 如何共享总预算、并发 tick 如何 CAS、push 后完成如何按 ordinal 合并、DB admission 失败由谁持久恢复、`writeVerified` 如何从行重建稳定 envelope/flywheelId，以及 T3 在外部 outbox accepted 前后的 crash settlement。**建议：**不必照搬 FLY-1339 v14 的所有字段，但必须保留最小 durable state machine：事务内 `queued|duplicate|suppressed/ledger_unavailable` admission；initial/T1 共用的 claim-before-write + attempt ordinal/token/lease + completion；T2 durable claim-before-act；T3 deterministic outbox 两阶段；stable envelope；terminal/started stand-down；teardown 保留未决/episode 行并只 TTL-prune 已终态证据。ledger unavailable 时必须零 push，并有且只有一个独立 durable recovery owner/告警，不能靠下次调用碰运气。

6. **[Blocking — Evidence / Safety] `inbox`/`turn` 循环 mark 全部 pending 会产生假 started，T2 也不能新造裸 terminal 注键路径。** 现 `markRunnerPhaseWakeStarted(execId,messageId,now)` 只按两个 caller 参数更新（`db.ts:1780-1792`）；`turnStatus` 本身只是纯读 helper（`turn.ts:36-53`）。若 intent 在命令开始后、ack 循环前入队，该命令并未因它醒来却会将其标 started；任意拿到 `--exec-id` 的进程也能代写。死分支已经给出必要边界：入口捕获 `observedAtMs`、只 ack `queued_at <= observedAtMs`、本职成功后写、Codex 保持逐 message 精确 ack/不同 `ack_scope`。此外现有 `runner-recovery-nudge.ts` 明确把 fresh capture+fingerprint、idle input、pending-gate probe、scope、audit-before-send 作为唯一 sanctioned terminal primitive（`:1-18,144-274`），且当前只允许 `continue`；S3 的短指针不能绕过它。**建议：**恢复上述 observedAt/identity/vendor 合同，并给 exec-level 与 exact-message ack 分 scope；生产优先信任 launcher env/session binding，`--exec-id` 仅 debug override。T2 应扩展同一 audited helper 的 `wake_pointer` mode，写出 awaiting_review 的完整真值表：causal question 已有 terminal response、无其他 unanswered gate、live binding 一致、fresh capture/fingerprint/input box、adapter/target 合法；任一不确定均 fail-closed，claim 已消费后进入 T3。

7. **[Blocking — Feasibility / Escalation] 现有 detection-escalation production wiring 无法完成计划的 Lead-keyed kill-Lead 验收。** `notifyLeadFirst` 接口虽允许 `<project>:<leadId>`，但 plugin 的 owner resolver只做 `store.getSession(input.targetKey)`（`plugin.ts:6446-6470`）；founder pager 的 production resolver明确对 lead-keyed target 返回 null（`detection-escalation-sinks.ts:86-117`），fleet project resolver同样查 session。更关键的是 `onDetectionReconcileTick` 仍在 default-false `legacyDeliveryWatchdogsOn` 下才接线（`plugin.ts:7039-7051`; flag registry `:104-126`），所以新 row 可停在 LEAD_NOTIFIED 永不 page founder。`notifyLeadFirst` 返回 `no_owner/target_clearing` 时若仍写 `escalated_at`，还会永久压掉重试。**建议：**为 receipt/wake 单独装配、不打开旧 detector 的 reconcile callback；补 Lead-keyed owner、thread/founder-page、fleet-project resolver，或对 runner 可定位的 episode继续使用 execId target。只有 outcome=`notified|already_notified` 且 durable escalation row 可核实时才写本地 anchor；`no_owner/clearing` 保持可重试。明确 `escalated_at` 是 Lead-first started 还是 founder page confirmed，必要时拆成两个字段，并测试 restart 两个 crash window。

8. **[Blocking — Completeness / Cursor discipline] “从非终态 session 构建 byThread”还不能扫描零 pending thread，且缺少 cutover watermark。** deliverer 当前 `questions.length===0` 立即 noop，并以最早 question 时间构造初始 `after`（`founder-reply-deliverer.ts:267-275`）；当前 matching=0 直接推进 cursor（`:345-360`）。只改 GatePoller 的 byThread 来源仍不会入账 F-1，也没有回答旧活跃 thread 无 cursor 时是回放全部历史、bounded backfill，还是从当前 Discord head 建 baseline；错误选择会把历史聊天瞬间灌入模型巷/升级链。S2 也没有指定谁在 `REBIND_WINDOW_MIN` 后把 F-4 原子晋升模型巷，且把 F-3 已有 durable deferred-rebind 与 F-4 unbound 混在一起。**建议：**写出 per-thread bootstrap contract、空问题 maturity、同 thread 多 session 去重与 cursor pin/waterline规则；flag cutover 用明确 watermark（若只保证启用后的消息，就先持久写当前 head；若要 backfill，限定范围并审计）。F-3 继续由现有 deferred rebind owner 收口，F-4 另存 durable due/promotion state，与 late binding 做 CAS。测试无 cursor 老 thread、初始化并发新消息、已有 cursor、空 pending、多个 session、promotion/late-rebind race。

9. **[Blocking — Authorization / D-1 & D-7] route CLI 的候选边界和 no-route whitelist 仍然过宽。** 计划只拒 `GATED_CHECKPOINTS`，未要求 `qid` 属于该 `founder_route` 冻结候选、同 Lead/project/issue/thread、仍 pending、非 report/review/superseded；持有 Lead lease 的调用者因此可把 founder 原文路由到任意 runner question，违背“窄且枚举”。同时“纯 emoji”是开放类别，`🛑/🚢/❌` 等明显可能表达动作/否决，不是保守 whitelist。**建议：**模型巷行持久存结构化 frozen candidate set 与 scope（不要只藏在自然语言 content）；CLI 在同事务重新校验 row current、candidate membership、scope、question state/type，并定义 response race/idempotent outcome。emoji 只枚举被批准的 ACK token（如确需 `👍` 就只列 `👍`），evidence.basis 记录具体 token/rule；加入 stop/ship/cross/reply emoji 对抗 fixture。

10. **[Blocking — Completeness / Undelivered axis] model max-attempt dead-letter 不是对现有 `quarantineModelBatch` 改一个 disposition 就成立。** 现方法只处理 immutable-membership conflict，并在同一 `lead_inbox` model lane 插入 `model_batch_quarantined` 行（`lead-inbox-queue.ts:475-558`）；把耗尽告警再放回故障 model lane 会自我堵塞，直接跨库调用 `LeadAlertNotifier` 又有“先死信后崩导致无告警 / 先告警后崩导致重复”的窗口。现 `claimModelBatch` 的 existing-batch discovery/read（`:365-383`）也不看 `next_retry_at`，只改新 batch selector会让失败 batch立刻重试。**建议：**新增语义独立的 batch dead-letter transaction：冻结整个 batch、稳定 alert/outbox id、一次提交；由 Bridge 单独投递该 outbox并确定性去重。existing batch 与 fresh batch 两条 claim 路径都必须尊重同一个 persisted due time，且不改变 immutable membership。测试 dead-letter/outbox 双 crash window、Bridge restart、alert sink failure、同 batch 并发 tick、两次 reopen 与告警恰一次。

11. **[Blocking — Sequencing / Reverse compatibility] 单一 kill-switch 当前不能实现宣称的 byte-compatible rollback。** S5 的 `=0` 只短路 S2/S3/S4，但 S1 的 claim backoff、model max attempts、dead-letter/alert 仍改变现有运行时；sentinel 也没覆盖这些差异。flag 到 S5 才注册/接线，使前面 default-ON commit 缺少完整逃生口。**建议：**S1 首先落 registry/read helper 和 flag-off sentinel；schema additive migration可常驻，但所有 S1-S4 行为变化都受同一开关控制，或明确拆出不承诺 byte-compat 的独立安全变更。`=0` 测试必须覆盖 model adapter 连败、protocol/model claim cadence、founder 六分支、wake writers、patrol/detection callback和零新 outbox；registry `readSites` 列出所有真实读取点及 boot/live timing，再做 mutation proof。
