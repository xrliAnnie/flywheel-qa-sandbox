最重要你要亲手做什么

别只记住"7 次卡"这个数。 7 只是合并 PR 的次数;真正需要你判断的是下面那 3 次授权,尤其是第 2 次。

动作次数它到底授权了什么
Flywheel ship 卡7合并 7 个 PR:这份设计文档、搬包、装调用入口、人设投影、迁移工具、拆旧机制、改规则+巡检。合并代码,不等于在生产上执行任何东西。
Raya 仓 merge 授权1Raya 仓改人设路径 + 删包的那个 PR。Raya 仓的 main 没有任何服务端保护,所以这一步只有你的授权在挡。
割接窗口授权 🔴1这是唯一不可逆的一次。 它授权:停掉旧 Raya → 对数据库做一次历史数据迁移 → 换人设 → 重启 → 确认无误后放行。数据迁移一旦做完就回不去了(人设文件能回滚,数据不能)。
宿主收尾授权1删掉两个旧 launchd 任务和残留文件。这一步之后旧壳永久起不来了。

为什么"割接窗口"必须单独授权,不能被 ship 卡覆盖

因为 ship 卡授权的是"把这段代码合进 main",而那一次要做的是"对当前这个生产数据库执行一次不可逆的历史数据分类迁移"。这两件事的风险完全不同。所以它要绑定当时那一刻的数据库状态、工具版本和回执,是一次性的、针对那一次的授权。

如果流程能把"割接窗口"和"钉住人设版本"这两件事合并成一条同时满足两边条件的指令,对你来说就是一次交互 —— 但它们在计划里必须分别写明,不能糊成一句。

现状此刻有两个 Raya 同时连着 Discord

我在调查时做了只读取证,发现的现场比工单描述的更紧张:

  • 旧壳还活着,而且还连着 Discord。 进程 PID 1671,今天 10:23 被系统自动拉回(宿主今早 08:55 重启过)。它持有两条 Discord 长连接,但从 9 月 4 日起就没往日志里写过一个字 —— 连着,但不出声。
  • 标准 Lead 也活着,而且它才是在干活的那个。 进程 PID 17271,今天 12:04 起,今天还在写工作区状态、界面线程 13:38 仍活跃。今天在回你的是它。
  • 那个"业务大脑"从来没在生产上跑起来过。 它需要工作区里有一个叫 business/current 的入口才会被调用,而生产工作区里根本没有这个目录 —— 因为唯一会创建它的就是这套一直在失败回滚的旧机制。而且当前活着的那份人设里,连"去跑这个业务大脑"的指令段都没有。

这对你意味着两件好事:① 搬家本身不会让 Raya 掉线,因为今天在回你的能力来自人设,不来自那个包;② 真正需要小心的是"换人设"和"停旧壳"这两步,不是"搬包"。

纠正工单里有两处说法不成立

工单原话核实结果
「packages/cos import 了 Flywheel 内部模块,并仓后要改成 workspace 依赖」不成立。 我逐文件查了全部 120 个源文件:它一个 Flywheel 模块都没 import,连 dependencies 字段都没有。所以"解耦依赖"这项工作不存在,搬家比想的简单。
「今晚 FLY-2657 切换(旧机制最后一次使用)」"今晚"查无实据。 FLY-2657 不是一次切换,是对旧机制两个故障点的修复,而且它自己还在实现中(6 步走到 4 步),连 PR 都还没开,它的计划里明确写着"不运行班车、不更新生产、不重启"。所以本方案按"它何时落地、是否落地都不确定"来设计 —— 不等它,也不挡它。

另有一项工单列进拆除清单的东西(FLY-2654 Part B)在主干上根本不存在:它在一个没合入的分支上,而且已经自己关闭了,被这个 Epic 取代。

怎么做割接分三段,只有中间那段有风险

🟢 阶段 A — 纯增量,生产 Raya 一点感觉都没有

搬包、装调用入口、部署人设投影器(但先不启用)、部署迁移工具(但先不执行)。这一段结束时,生产上的 Raya 与今天完全一样。 每一步都能直接撤销。

🔴 阶段 B — 割接窗口,一口气走完,不能停在半路
  1. 冻结 Raya 仓那个 PR 的内容指纹 → 你授权 → 合并 → 复核合进去的内容没变 → 钉住这个精确版本
  2. 停掉旧 Raya,并证明它的进程与占位都真的消失了
  3. 在停机状态下执行那次不可逆的数据迁移,并留下回执
  4. 换人设 → 启动 → 在打开收件箱之前先验证"我加载的确实是你授权的那份人设",不对就拒绝启动
  5. 确认无误,放行

窗口期间你在 #raya 说的话不会丢(有游标记位,重启后接着读),但会延迟到放行之后才被处理。

⚪ 阶段 C — 拆旧机制、清理宿主

逐个 PR 拆掉班车、迁移工具、巡检里的 Raya 事实行、规则文件里"合入≠上线"那一段,最后清理宿主上的旧任务与残留文件。

一件我特意查清楚的事

割接窗口里不能顺手把"生成 summary 的那个后台服务"也停掉 —— 直觉上停了更干净,但实际上停它反而危险:那个服务每次只回看很窄的一个时间窗,停的时间点如果卡在窗口上,那段时间的 summary 记录就永久补不回来了。而且它不只管 Raya,它给全舰队的 Lead 排 summary。正确做法是让它照常跑,只把 Raya 这一个"读的人"围起来。

备注一个我没自作主张改的边界

工单规定"人设文件留在 Raya 仓",本方案照办了。但调查中发现一件值得你知道的事:

Raya 仓的 main 没有任何服务端保护(我实际查了 GitHub,分支保护返回"未保护",规则集为空),而人设是直接进 Raya 的最高权限系统提示的。也就是说,任何改到那个仓 main 的内容,下次她启动时就会成为她的行为准则。

方案里已经用"必须钉住一个经你授权的精确版本,不能跟着 main 走"把这个洞堵上了。但更彻底的做法是把人设也搬进 Flywheel —— 那样它会受 main 保护 + CI 覆盖。我没有这么做,因为那会改掉你定的边界,而且要重做本方案的一半。

👉 如果你想换这个口径,那是一张独立的后续单,现在不做。 这里只是让你知道有这个选项,以及它的代价。

拆单建议拆成 7 张子单

子单能不能并行一句话
S1 搬包✅ 最先,无依赖把那 120 个文件落进 Flywheel,接上 CI
S2 调用入口依赖 S1装一个小转接脚本,让 Raya 能调到它。这单的核心风险是要实测她的沙箱允许不允许
S4 人设投影✅ 可并行让人设能从 Raya 仓自动送到她工作区,并在启动时验证版本对不对
M0 迁移工具✅ 可并行包一层受权外壳 + 回执 + 崩溃恢复。合并它 ≠ 执行它
S3 Raya 仓改造依赖 S2 已部署改人设里的调用路径 + 删掉那个包。合并后仍然不生效,生效点在割接窗口
T1–T3 拆机制依赖割接完成拆班车、迁移账本、相关工具与测试
T4–T5 巡检+规则依赖 T1–T3拆巡检的 Raya 事实行,改规则文件里"合入≠上线"那段
