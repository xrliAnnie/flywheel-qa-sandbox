术语:head 就是「某个 PR 在某一刻的最新 commit 号」;holder(gate holder)是系统为每一次开卡记的一行,里面本来就存着 head 和卡片消息 id——只是判决行没有指向它。

核心流程:判决怎么被写下来

两条入口(你直接在卡上判 / Lead 经 operator 通道打回)最后汇到同一个「解析绑定 → 写判决快照」步骤。解析失败就整笔回滚,连判决本身都不落库,所以新数据按构造 100% 能绑到 (repo, pr_number, head_sha)。

「是不是她本人」怎么定:只认事实,不读文字

新字段 founder_authored(0 / 1)与 authority(权限)完全分开。它的值只来自三种可核验的事实:你直接在卡上写的(作者 id 相等)、Lead 附了一条你在这张卡 thread 里、卡片发出之后说的消息(Bridge 去 Discord 核过作者)、或者什么都没附(记 0)。文本前缀、正则、语气判断一律不用。

spec 的 5 条对照按这个规则分开:c8f001a6 / 3f9f9f1c(Lead 转述你的 thread 原话,可附引用)→ 是;5ae599c6(引的是另一张单 2074 的话,不在这张卡 thread)→ 不是;54f0d683(Lead 自己的打回)/ f5bd6f2b(机械换头)→ 不是。

数据结构:一张新表,不改旧表

新表 workflow_founder_gate_verdict 是不可变的(数据库触发器禁止改和删),过卡 / 打回各写一行;它指向已有的 holder、claim(过卡凭证)、rework_request(打回原行),并把 repo / PR 号 / head 快照下来——因为 PR 绑定行以后可能被清理,事后再 join 不可靠。

遗留 63 条怎么报,验收拿什么

回溯脚本只做等值 join(holder 按 run + attempt 唯一),不猜时间窗;在 SQLite online backup 快照上跑(不是 cp,cp 会漏掉未落盘的已提交写入)。

诚实边界:这个设计做什么、不做什么

  • 不动merge 授权契约:authority 列、放行谓词一行不改;新字段没有任何读者拿它当放行条件(有 repo 级守卫测试)。
  • 不修operator 通道把 authority 硬编码成 founder 的问题(它参与返工授权契约);真相记在新表的 0 / operator 证据里。
  • 不猜遗留 63 条的作者;只有 5 条人工 attestation,58 条永远「未判定」。
  • 语义「她本人」= 判决绑到了一条经核实为你所发、在该卡 thread、卡片发出之后的消息。Lead 不附引用的转述记 0;Lead 附了你在该 thread 的无关消息,也会记 1——记的是绑定事实,不是意图判断。
  • 依赖Discord 接口不可用时,带引用的打回会被 503 拒(可重试);不带引用照常。
  • 未查插件 fork 源仓库的调用方 sweep(本机无 checkout);新字段是可选的,旧调用不受影响。
