## 关键发现(影响判定方法)

1. **病根单本身从不出现在修复提交里**。main 482 个提交里,166 张待判单的单号**零命中** ——
   巡检开的 `[病根]` 单是「记账单」,修复都开在独立的机制单上(如 FLY-2083 的修复单是 FLY-2478)。
   所以「已修未关」只能沿着「病根单描述/评论 → 引用的机制单 → 该机制单在 main 的合入提交 → 合入后是否再复发」这条链去核。
   166 张里有 141 张引用了至少一个在 main 有合入提交的单,但**引用 ≠ 修复**,需逐张看范围与合入后复发。
2. **出现次数的真源是评论**。巡检每复发一次就在单下追加一条「本次实例」评论并把标题 `· ×N` +1;
   描述里的 `occurrences: N` 常常落后(如 FLY-2114 标题 ×289 被截成 ×28 显示,描述 289)。次数取标题/描述/评论 ×N 的最大值。
3. **近 7 天仍在冒的只有少数**:最后一条评论落在 9-19 之后的 37 张;近 7 天巡检报告点名的 34 张。
   其余单「近 7 天没再出现」只能说明安静,不等于修好 —— 巡检只在有体撞上时才会记账。
4. Epic 下还有 2 张「⚠️测试用」夹具单(FLY-2081 / FLY-2089),是巡检查重功能的 QA 产物,不是真实缺陷。

## 方法

1. 机械层(脚本,可复跑):每张单抽 次数 / 最后评论时间 / class_key / 近 7 天巡检命中 / 引用单状态与其 main 合入提交 / 在飞 PR。
2. 判定层:166 张按单号切 8 批,由 8 个只读子代理并行逐张读完整描述与评论后按统一口径判定
   (口径见 research.md),每张同时打 Epic 四病根标签 + 统一的 family 词表 + 具体缺口 slug。
3. 归并层(本人):按「具体缺口 slug」去重合并成类,每类汇总单号、合计次数、最近一次、删状态/删路径式修法方向、改动面,按合计次数排序。
4. 机械核对:结论 JSON 的 id 集合 == 166 张待判集合(N/N),写进 research.md。
