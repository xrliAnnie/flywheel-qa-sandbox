# Design Review — plan.md (Round 1)

Date: 2026-07-10
Author: Codex
Status: CHANGES REQUESTED

## Summary

常驻 `claude -p --input-format stream-json` 的核心方向可行，已有 spike 足以证明多轮、in-band interrupt、轮间 `--resume` 与 EOF 回收这几块承重能力；daemon 单一 owner、只读脑、orchestrator 落 Linear 的边界也正确。但当前 plan 仍包含一个已被本项目真机证据否定的 /glaw TEXT 模态假设，并且 resident 协议、barge-in/crash 状态机、BrainPort 运行边界及 /eleven 收尾合同尚未闭合，因此不能按现稿安全实现。

## What's Good (Keep)

- Scope 收得正确：仅 /glaw + /eleven，明确不动 /gemini(-advanced)，避免把没有 Claude 对话脑的链路硬套进本架构。
- Phase A 先把 `ResidentClaudeBrain`/manager 落 main，再让 545/1006 各自接线的总体拆法合理；它避免两个在飞分支各造一套持久脑。
- spike 对「首条 user 前没有 init」「中断轮以 `error_during_execution` 收束」「进程存活」「轮间 crash 后 `--resume` 记忆保留」「stdin EOF 干净退出」给了直接证据，且 plan 没有超卖 1–2 秒延迟。
- daemon-only process ownership、全局 session 上限、默认非零 watchdog、有限重生、fail-loud TIV、会后零孤儿这些目标与项目的事故教训和 fail-loud 文化一致。
- 安全方向正确：Claude 只有 `Read,Grep,Glob` + `--strict-mcp-config`，Linear 写操作仍由 orchestrator 执行；BrainPort 默认关闭且不开放远程 spawn。
- QA 同时覆盖 PID 不变、kill/recover、Gemini 断连、纪要落地和孤儿检查，结构性验收比只测延迟可靠。

## Issues & Recommendations

1. **[BLOCKER] /glaw 的 `Modality.TEXT` 主路径在当前生产模型上物理不可用。** Plan `plan.md:44-47,153-156` 要求 Gemini Live 使用 TEXT 模态，但 FLY-545 一手 spike 明确记录 `gemini-3.1-flash-live-preview` 以及当时所有可用 Live 模型均拒绝 TEXT（`FLY-545-huddle-mode/evidence/s1-gemini-text-modality.md:8-36`），545 当前回归测试也钉死 `responseModalities === ["AUDIO"]`（`packages/voice-core/src/__tests__/genai-config.test.ts:121-124`）。这会让 /glaw 在连接时直接被服务端关闭，Phase B 无法启动。**建议修复：**把合同改为保留 `Modality.AUDIO` + `inputAudioTranscription`，丢弃 Gemini 的 response audio/output transcript，不让它进入嘴；用最短 system instruction 降低被丢弃的生成成本。新增回归测试证明 AUDIO 模态不变、输入转写仍提交给 resident Claude、Gemini audio 永不进入 speaker。若坚持 TEXT，必须先对一个明确 pin 的新模型补真机 PASS 证据，再改计划，不能以 seam 代替可行性证明。

2. **[BLOCKER] Phase A 复用现有 parser/ProcessRunner 会产生重复口播，并且不足以可靠承载常驻 stdin。** Plan `plan.md:83-86,141-142` 要求把 `parseStreamLine` 原样抽共享；但它既返回 partial `text_delta`，也返回最终完整 assistant message（`HeadlessClaudeBrain.ts:294-310`）。FLY-1006 shim 已用真机证据记录这会把完整回答再说一遍，并专门加了 `dedupeFinalEcho`（`shim-core.mjs:138-156`）；当前 FLY-1160 spike 只累计 `text_delta`，没有覆盖这个真实事件序列。此外 `ProcessHandle` 只有 `write(): void`/`onExit()`，没有 child `error`、stdin write error 或 backpressure/drain 合同（`process.ts:39-83`）；对长期可写子进程，ENOENT/EPIPE 和写队列失控都可能变成 daemon crash 或静默丢 turn。**建议修复：**让共享解析结果携带 event kind，Resident 只向消费者 yield delta（或显式去掉 final echo），并用真实 init/delta/final/result 序列测试。将 `ProcessHandle` 扩成可观察 spawn/error、可确认 write/backpressure、可 await close 的 seam，同步升级 fake；测试 ENOENT、EPIPE、分片 JSON、无尾换行、stderr 上限和 write-after-exit。不要只把现有 one-shot seam 直接用于 resident。

3. **[BLOCKER] interrupt/watchdog/crash replay 还不是一个可实现且无竞态的状态机。** API 写成 `interrupt(): void`，同时又规定仅允许一个 in-flight、barge-in 后立刻开新轮（`plan.md:75-99`）；调用方无法知道旧轮何时收到 `control_response`/terminal `result`，新 `respond()` 要么被并发拒绝，要么进入 CLI 内部队列。watchdog 的 interrupt→kill 等待时间也未定义。更关键的是 spike 只验证了“轮与轮之间 kill 后 resume”，没有验证 plan `:88-90` 声称的“生成中 crash 后自动重放”；此时可能尚无 sessionId，或已经向 TTS 发出半句，盲目 replay 会重复用户 turn 和已播内容。`maxLifetimeMs` 又声称会触发“正常收尾”，但 voice-core 并不拥有 landing。**建议修复：**写出显式状态/时序合同：每轮唯一 id；`interrupt()` 返回 Promise 并以 terminal result 为 barrier；新轮必须等待旧轮收束；timeout 的 interrupt grace 与 kill grace 固定且有界；close 与 in-flight 的优先级明确。定义 crash-before-sessionId 的 fresh+journal/history fallback，以及 crash-after-delta 时先通知消费者 flush、再 resume/replay 的可见语义。补一个真实 mid-turn SIGKILL spike，以及 abort→立即下一轮、timeout→kill→resume、close-while-thinking、respawn-limit、lifetime-expiry 的测试。把 lifetime-expiry 暴露为 orchestrator 事件，由 /glaw 或 /eleven 决定 degraded landing，不能由 core 宣称“正常收尾”。

4. **[BLOCKER] /glaw 合同漏掉现有多 Lead 的静默上下文同步，而且指定的 mouth 类型与 edge-tts 数据格式不兼容。** 当前 FeedPipeline 是一等合同：非 addressed Lead 必须通过 `injectContext()` 收到其他人的发言，否则会自信编造（`FeedPipeline.ts:1-24,38-40,121-149`；`wireMeeting.ts:260-279`）。计划中的 resident API 只有 `respond/interrupt/dispose/health`，没有 silent context 面，按 `plan.md:157-159` 只调用 addressed brain 会让其余 persona 丢失会议事实。另一方面 `GeminiTurnMouth.feed()` 接受 24k PCM 并上采样，而 `EdgeTts.synthesize()` 返回完整 MP3；“GeminiTurnMouth 改喂 edge-tts 合成流”不是现有接口可支持的接线。**建议修复：**给 resident/line 增加明确的 `appendContext()`（推荐只缓存，下一次真实 `respond` 时作为标记 context 与 founder turn 一起送入，避免无声 context 自己触发模型回答），并保持 FeedPipeline cursor/retry/replay 语义。嘴侧明确替换为现有 `LeadSpeaker` 的 text queue（或新增专门 TextTurnMouth），写清 sentence buffer、final flush、TTS 串行顺序、失败/TIV 和 barge-in `stop()`；不要复用 PCM-only 的 GeminiTurnMouth 名字和 `flush()` 合同。补 multi-lead handoff/feed/recovery 以及 barge-in during TTS 的端到端单测。

5. **[BLOCKER] BrainPort 目前只是端点草图，配置、鉴权、daemon 装配和 abort 传播没有形成安全边界。** `plan.md:121-131` 没说明 Phase A 在 `voice-bridge/src/cli.ts` 哪里构造唯一 manager、启动/回滚 server、关闭 port 并 `closeAll()`；实施顺序也只有“新增 BrainPort”。配置表同时写 `huddle.brain.portToken / port` 来自 projects.json+env，而正文写固定 `BRAIN_PORT_TOKEN env`，shim 配置却只有 `FLY980_BRAIN_URL`（`plan.md:187-195`），因此 token 如何安全传给 shim、是否会误把 token 值写入 projects.json 都不清楚。也未定义所有端点（尤其 health）是否鉴权、body/read timeout、413/409/503 映射、client disconnect 如何中断、health 是否泄露 active keys。**建议修复：**定义并实现一个 fail-loud resolver：projects.json 只存 `port` 与 `tokenEnv` 名称，secret value 只从 env 取；shim 明确读取同一 token env（绝不放 URL/query/日志）。所有 `/brain/*` 端点鉴权，loopback bind，constant-time token 比较，有限 body/text、Content-Type、read/turn timeout、稳定错误码，health 不回传 issue/key。把 singleton manager + BrainPort 的启动、后续 Discord 启动失败回滚、SIGTERM/SIGINT/slot release teardown 写进 `cli.ts` 任务和测试。BrainPort client 断开或同 key supersede 时必须 interrupt 并等待第 3 项的 barrier；shim `/health` 在 resident 档还应验证 downstream port/token 可达，否则现有 /eleven preflight 会在脑口已坏时假绿。

6. **[BLOCKER] /eleven 的 kickoff→brain bind→终轮纪要→landing 生命周期不足以从现有代码落地。** daemon 已经在 `ElevenCommand` 生成 UUID，并将它作为 `custom_llm_extra_body.conversation_id` 传给 ElevenWs；计划却等 `conversation_initiation_metadata` 才 open（`plan.md:169-174`），给第一笔 custom-LLM 请求留下 404 race，也没有校验平台回传 id 与本地 id 一致。“选定 Lead”没有配置来源；当前 `/eleven` 没有 lead 参数。现有 `ElevenSession.stop()` 只是停 WS/离开 VC/释放 slot，不区分手动 stop、WS 异常、start failure、daemon shutdown 或 no-show；`onEnded` 也是不可 await 的同步回调。AssistantLanding 接受 `recapText + timestamped quotes`，而 resident 每轮只收到纯文本，计划没有说明 /eleven journal 如何进入同一 session 的终轮，也没有说明 summary 失败后 issue/brain 如何保留以供重试。**建议修复：**规定 `huddle.eleven.leadId`（启动时验证存在）或给命令增加明确选择；严格按 `slot acquire → kickoff issue → manager.open/warm using daemon UUID → WS connect` 排序，并把 metadata 只当一致性 gate。将 `issueId/sessionId/brainKey` 贯穿 ElevenCommand/Session。把 `stop(reason)` 设计成 exactly-once async finalizer：冻结并落盘 timestamped journal → 同一 resident 终轮生成 minutes → 复用/小幅泛化 AssistantLanding 的 receipt/comment/close → 无论 landing 成败都按定义关闭 brain 和释放 slot。逐一定义 manual stop、remote close、start failure、brain failed、daemon shutdown 的 issue 状态和 degraded 标记；启动失败沿 GeminiCommand 的 abort comment/close 形态。为每条退出路径和重复 stop 写测试。

7. **[HIGH] “安全边界不变”和“默认字节兼容”还没有被配置/API 设计结构性保证。** `extraArgs?: string[]` 位于安全 flags 之后（`plan.md:63-65`），调用方可再次传 `--tools`、`--mcp-config`、permission/prompt/input/output/resume flags，从而覆盖只读或破坏协议；`toolArgs` 本身也允许完全替换安全基线。`huddle.brain.mode` 同一个键却声明 /glaw 默认 `gemini`、shim 默认 `per-turn`，而 shim 根本不读取 projects.json（`plan.md:191-195`），这个默认模型不可实现。容量超限用 `VoiceError("unsupported")` 也不符合现有 code 对“backend 不支持能力”的语义。**建议修复：**把安全 flags 做成不可覆盖的内部常量，只给 `model/effort/settings` 等经过 allowlist 的 typed options；拒绝 reserved flags，voiceContext/preamble 仍只走 stdin/0600 file。拆清 daemon 的 `huddle.brain`、/glaw mode 与 shim env 三个解析面，列出每个 resolver/类型/测试的准确文件；token 只用 `tokenEnv`。为容量增加准确的 `resource-exhausted`（或项目认可的等价）VoiceError code。byte-compat sentinel 应比较未配置时的 health JSON、监听端口、已注册命令、Claude argv、shim SSE/error 行为，而不只断言“不监听 BrainPort”。

8. **[HIGH] Phase A/B/C 的交付顺序有方向但没有可审计的 completion gate，且分支漂移会直接碰共享文件。** FLY-545 已修改 `HeadlessClaudeBrain.ts`（增加 cwd）、`types.ts`（injectContext/connection error）和 Gemini connector；FLY-1006 则与当前 main 在 voice-core transcript 类型和 voice-bridge chassis 上存在较大漂移。`plan.md:180-185,230-237` 只说“A 合入后 Lead 调度”，没有规定 rebase 基点、冲突必须保留的合同、各分支的 build/test/byte sentinel，也容易在 Phase A PR 合入后误把 FLY-1160 标成完成。**建议修复：**在计划中记录 Phase A 的精确导出/config/cli 文件清单；A 合并后分别把 545、1006 rebase 到包含 A 的明确 main commit，再做 B/C，列出共享冲突必须保留的内容（545 cwd/injectContext/reconnect；1006 当前 transcript/room chassis）。每个消费者独立跑 voice-core + voice-bridge typecheck/test 与未启用模式的 reverse-compat sentinel。FLY-1160 的完成条件必须是 A/B/C 三个 landed commit/PR 均可追踪、两条真机 QA 均 PASS、最后一次跨分支整体验证完成；Phase A 单独合入只能记为组件 milestone，不能结单。
