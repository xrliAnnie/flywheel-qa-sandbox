# FLY-2008 plan.md — Codex Design Review (Round 1)

Date: 2026-08-23
Author: Codex
Status: CHANGES REQUESTED

## Summary

The A-disease remediation is well grounded and implementable: its query rewrites preserve behavior, the proposed indexes match SQLite's planner rules, and the gate-poller budget/yield work is appropriately scoped. The event-loop acceptance semantics also match the shipped attribution thresholds. Changes are required because the B-disease forensic taxonomy cannot be observed at `HeartbeatService.probeSessionLiveness` as written, and the plan does not yet specify the production path that exposes those counters through `/health`.

## What's Good (Keep)

- A1 is semantically correct. `QUEUED` and reclaimable `LEASED` are mutually exclusive sets; `priority` is non-null and `seq` is the unique integer primary key, so taking each branch's top row by `(priority, seq)` and then the minimum of those two is exactly the original union's global `ORDER BY priority, seq LIMIT 1`. Keeping the fenced `UPDATE` unchanged preserves the lost-race behavior.
- The three partial indexes are correctly shaped. In particular, the adoption `UPDATE` contains state inside an OR expression, and SQLite's limited partial-index implication rules cannot prove that expression implies a state-bearing index predicate. Omitting state leaves predicates that occur as matching AND terms and makes `mailbox_legacy_adopt` eligible. The question and queued-deliverable indexes likewise match their hot-path predicates; `ORDER BY +seq` is a valid semantic no-op that avoids the rowid-order full-scan choice.
- The bound-parameter EQP discipline and full-chain regression guard are important. The plan correctly avoids treating literal-value plans as evidence for prepared production statements and includes positive controls and behavior-equivalence tests.
- B1 preserves the important product behavior: every question-bound thread remains eligible each pass, while only pure ingress scans consume the independent rotating budget. Resetting the rotation cursor on restart is safe because it only causes redundant scans; the per-thread delivery cursor is persistent in production and delivery remains idempotent.
- B2 attacks the actual per-thread synchronous cost—the writer `CommDB` construction, schema/migration work, and purge—not just the smaller read-only open. Pass-level ownership with `finally` cleanup and explicit event-loop yields is consistent with the existing serial poller model.
- The plan introduces no environment variable or runtime feature flag. The scan budget remains a named constant with an internal test seam; implementation must keep that seam out of environment/config loading.
- Acceptance uses the actual episode-minting rule from `event-loop-attribution.ts`: a 30-second window mints an episode when max loop delay is at least 1,000 ms. `LONG_SPAN_MS = 500` controls attribution evidence only, so the plan correctly does not use span presence as the success criterion.

## Issues & Recommendations

1. **BLOCKER — the mandatory heartbeat source taxonomy is not observable at the proposed layer.** `probeRunnerProcessLiveness` catches normal tmux failures itself and converts both timeout/throw failures and empty or unparseable output to the same string, `"indeterminate"`. Consequently, the outer catch in `HeartbeatService.probeSessionLiveness` does not see a production timeout and cannot populate `probe_throw`, `errorType`, or `timedOut`; the proposed test using a mocked rejection would prove only a mock-only path. In addition, the `:pending` early return cited by the plan belongs to `probeTmuxWindowLiveness`, while HeartbeatService calls `probeRunnerProcessLiveness`, which has no pending special case. Adding one in HeartbeatService would change the current likely `absent` → `dead` result to `indeterminate`, contradicting the promised byte-for-byte behavior preservation. **Suggested fix:** revise the plan to add a structured observation/result seam at the tmux-probe layer (for example, a detailed sibling API whose legacy wrapper still returns the existing four-state verdict), and have HeartbeatService consume that detail without changing its `SessionLiveness` result. Explicitly rule whether `pending_sentinel` is an orthogonal target classification recorded alongside the unchanged verdict or an intentional behavior change; it cannot simultaneously be a new indeterminate source and be zero-behavior-change. Test real lower-layer timeout, unclear output, absence, and pending behavior rather than relying only on HeartbeatService mocks.

2. **MAJOR — `/health` exposure is not wired in the plan.** The existing liveness manifest is built in `bridge/plugin.ts` through a `livenessHealthProvider` closure that receives tracker and inbox-loop data only; `buildLivenessManifest` has no HeartbeatService diagnostic input, and the HeartbeatService is constructed later. A private process-local Map therefore cannot satisfy the proposed “inject N times, observe N through `/health`” test without additional production composition work. **Suggested fix:** name and design the missing surfaces: a read-only HeartbeatService snapshot API, a late-bound holder in `plugin.ts`, an additive typed field in `buildLivenessManifest`, and route/manifest tests proving the live service's counters reach `/health`. Define the exact JSON shape and zero-value behavior for all four taxonomy keys; extend the manifest validator if this is intended to be a contractual field.

3. **MEDIUM — B2's borrowed-connection ownership needs a type-safe contract.** Today `commDbFactory` returns the concrete `CommDB` class and the deliverer unconditionally calls `db.close()` in its `finally`. A plain no-op-close wrapper is not structurally assignable to a class with private members without a cast or proxy, leaving the central ownership rule underspecified. **Suggested fix:** narrow the dependency to an explicit interface containing only `getPendingQuestions`, `ingestDiscordChat`, and `close`, or introduce a lease object with separate per-call release and pass-owner close. Keep the pass's real per-project connection in an outer `try/finally`, and test success, per-thread failure, and multi-project isolation.

4. **MEDIUM — define rotation behavior when the saved thread disappears.** “Continue after the cursor” is unambiguous only while the cursor ID remains in the next sorted task set. Falling back to index zero after deletion can repeatedly favor the head under thread churn and weaken the no-starvation claim. **Suggested fix:** specify an upper-bound search for the first sorted `threadId` greater than the saved cursor, wrapping only when none exists; advance the cursor after each attempted pure-scan task, and do not advance or charge it for question-bound work. Add insertion/deletion and restart cases to the budget tests.

5. **MINOR — describe the founder pass as scan-bounded, not absolutely wall-bounded.** The independent budget caps pure ingress scans, but question-bound threads are intentionally unlimited to preserve the ≤60-second delivery contract. The plan acknowledges this later, while its goals and effect summary still promise a bounded pass and a roughly 15-second wall time. **Suggested fix:** change those claims to “bounded background scan lane; question lane intentionally unbounded,” retain the current-volume estimate as an estimate, and report questioned-thread count and pass duration during acceptance so a question-volume regression is visible without changing behavior.
