# Design Review — plan.md (Round 3)

Date: 2026-09-03
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 3 incorporates all nine Round 2 corrections and now gives mechanically testable answers for the original six defects: the liveness classifier is single-sourced, false freeze predicates are write-free, reroutes are generation- and target-fenced, successful operations terminate at `projected`, and over-cap recovery uses the existing confirmed hold door. The plan is nevertheless not implementation-ready because startup baselining can recreate versionless attempts after the one-time upgrade, the proposed frozen episode conflicts with the ledger's one-open-episode invariant, and operator cancellation does not cancel the authoritative delivery. These are integration gaps in the existing mechanism; closing them does not require a new table, column, knob, endpoint, or alert layer.

## What's Good (Keep)

- Keep the single `classifyRecipientLiveness` path, the format-total `founder-notify-utils.parseSqliteUtcMs`, and fresh liveness collection at both rework warning and severe boundaries. A1/A6/A10 now make false-positive holds and alerts mechanically visible.
- Keep the four-table byte-for-byte assertion when `shouldFreeze` is false. It cleanly enforces the founder's rule that a failed hold predicate has no side effects.
- Keep State-native reroutes atomic and terminal at `projected`, with the cross-store saga limited to the three CommDB families and only `staged`/`applied` eligible for stall detection.
- Keep the in-transaction current-activation/live-session target fence for both reroute paths. The terminal and replacement barriers are the correct proof that stale targets consume neither lineage nor reroute capacity.
- Keep the projector's consumption-only settlement rule and the explicit seven-caller settlement matrix. Together they make terminal-unread delivery observable while ensuring every legitimate settlement closes its episode in the same transaction.
- Keep `run`/`delivery`/`run-derived` registry scope, per-instance counting of `runHeld:true`, and last-run-hold carrier revival. This resolves the prior mismatch between run state and delivery-level recovery.
- Keep the same list/stage/apply confirmation door for the over-cap decision. No second operator authority path is needed.
- Keep the M0 CHECK migration and JSON data upgrade ahead of maintenance, plus the no-new-schema mechanism budget.

## Issues & Recommendations

1. **[BLOCKER] Startup baselining can mint a new versionless legacy attempt after the version upgrader has finished.** M0 runs `upgradeWorkflowDeliveryAttemptVersionsTx` before the first maintenance tick, but the first tick subsequently calls `baselineWorkflowDeliveryContracts`. That baseline discovers open rework/carrier physical rows which have no attempt and sends them through the generic `mintWorkflowStateDeliveryAttemptTx`; its query does not select `route_revision`/`generation`, and the generic minter serializes only `{table, pk, runId}`. The plan updates only the two normal family-specific minters, while making versions mandatory in every rework/carrier selector. A legacy physical row without a pre-existing attempt therefore becomes a versionless live attempt after the upgrader and cannot advance or settle until a later process restart happens to upgrade it. **Recommendation:** make the baseline query and generic minter version-aware for rework/carrier, or run a second atomic upgrade immediately after baseline before any projector/watch work. Prefer minting the correct ref once. Extend A7 with the missing boundary: start from an authoritative legacy rework/carrier row with no attempt, run the real startup baseline, and prove the resulting attempt is versioned, accepts the current physical version, and rejects a stale one in that same process lifetime. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:62-64,78,84`, `packages/teamlead/src/bridge/plugin.ts:7407-7419`, `packages/teamlead/src/StateStore.ts:35203-35273,35474-35521`.

2. **[BLOCKER] Opening a `frozen` episode is incompatible with the current one-open-episode-per-family/root invariant unless the prior stage episode is transitioned first.** The schema's partial unique index permits only one open episode for `(family, root_id)`. A turn-wake attempt becomes overdue at the existing `sent` deadline of 15 minutes, while `three_stage_turn_stuck` freezes at 20 minutes; in the real maintenance stream, the normal observer can therefore have an open `sent` episode before `freezeRunTx` tries to insert a distinct `frozen` episode. The plan does not close or transition that episode, so the positive freeze can fail with a uniqueness error. The same transition must be explicit when opening `undeliverable`; the deleted implementation handled that case by closing the prior episode before insertion. There is a related rework boundary: if an old stage episode exists and the first post-receipt observation finds the worker alive, unconditional “zero writes” leaves the obsolete stage episode open even though the delivery advanced. **Recommendation:** define one complete episode-transition rule. Once the freeze predicate is true, close any different open episode and insert the frozen episode in the same transaction; keep the required false-predicate path at zero writes. Likewise, close-before-open for undeliverable. For liveness-suppressed rework receipt, distinguish “zero new received episode/alert” from closing an obsolete prior-stage episode. Add sequential real-stream controls: sent episode opens at 15 minutes, freeze at 20 minutes closes/replaces it and holds; terminal-unread replaces a prior stage episode; receipt advancement with alive liveness leaves no stale earlier-stage episode. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:43-45,52,91`, `packages/teamlead/src/StateStore.ts:19989-20010`, `packages/teamlead/src/bridge/delivery-contract/policy.ts:3-8`, deleted reference `37dc5bd63^:packages/teamlead/src/StateStore.ts:37963-37999`.

3. **[BLOCKER] `resume_undeliverable(... cancel)` settles only the observational ledger, not the authoritative physical delivery.** The shape covers all five reroutable families, but the specified cancel action only sets `workflow_delivery_attempt.settlement_reason` and closes its episode. For rework and carrier, the authoritative StateStore row remains in `awaiting_receipt`/`replacement_pending`; the existing dispatchers continue reconciling those states, and carrier failure handling can retry or move the delivery to `needs_lead` and emit another alert. CommDB wake rows can likewise remain deliverable. The door would report a successful cancellation while the underlying delivery is still capable of side effects, breaking the promise that `contract_ref` names the authority and making the attempt ledger disagree with it. **Recommendation:** make cancellation terminalize the exact physical row before settling the attempt: in the same StateStore transaction for rework/carrier, and through the existing operation saga for CommDB families. If a family has no truthful existing cancellation state and adding one is out of scope, do not offer `cancel` for that family; require confirmed reroute or an existing run-termination authority instead. Add family-complete positive and crash-barrier tests proving physical state, attempt settlement, and episode closure cannot diverge. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:47,50,97`, `packages/teamlead/src/bridge/workflow-engine-dispatcher.ts:818-836`, `packages/teamlead/src/bridge/workflow-rework-coordinator.ts:362-428`, `packages/teamlead/src/StateStore.ts:49471-49542,49627-49715`, deleted reference `37dc5bd63^:packages/teamlead/src/StateStore.ts:37520-37560`.

4. **[HIGH] The two producer modes for one operator-required episode have no defined transition when successor availability changes.** A cap-exhausted episode with a live successor emits its exactly-once event as `runHeld:false`. If that successor terminates before the operator acts, the next post-grace pass satisfies the no-successor hold predicate and wants the same episode to become `runHeld:true`. Run events are content-addressed and immutable: replaying one UID with a changed payload conflicts, while emitting another event contradicts the per-episode exactly-once/list identity unless explicit supersession and deduplication are defined. The reverse transition can also make run-hold counting disagree with the actionable item. **Recommendation:** define a monotonic per-episode state rule. The smallest rule is that, after the cap path emits an actionable `runHeld:false` event, that episode never promotes to a run hold; subsequent `holdUndeliverableTx` calls detect the existing operator-required event and write nothing, while the same door remains actionable. If promotion is required, specify distinct deterministic event identities, supersession, list deduplication, and run-hold counting. Add a cap-event -> successor-disappears transition test and the reverse availability change. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:24,50-51,92,138`, `packages/teamlead/src/StateStore.ts:43112-43173`.

5. **[HIGH] A turn-wake freeze that clears naturally can strand the run because the restored resume primitive rejects the now-acked source.** The plan closes an open frozen episode when the shape disappears but does not reactivate the run automatically, so the operator door must still release it. The restored `resumeTurnWakeHold` is specified “unchanged”; that implementation only resets a source in `pending` or `sent` and throws for `acked`/`cancelled`. A recipient can ACK after the run was frozen, causing the next watch pass to clear the shape and then making the official resume action fail permanently against the already-acked source. **Recommendation:** define an already-consumed exact source as a successful no-op physical recovery and still project the confirmed hold resume, or explicitly auto-resolve this cleared shape while respecting all remaining run-scoped holds. Add freeze -> recipient ACK -> list/stage/apply -> run active coverage, plus a variant where another run hold remains and the run stays held. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:91,97,99`, deleted reference `37dc5bd63^:packages/flywheel-comm/src/db.ts:3068-3102`.

6. **[MEDIUM] The written JSON rollback does not use the exact pre-upgrade bytes already recorded by the upgrade event.** `json_remove` parses and reserializes JSON; for example, whitespace in `{ "table" : ... }` is normalized. The schema has no canonical-JSON constraint, so the SQL cannot guarantee A7's byte-identical rollback for every valid pre-upgrade row even though each `delivery_attempt_version_upgraded` event stores `before`. **Recommendation:** restore `contract_ref_json` directly from the matching event's `payload.before`, fenced by both attempt ID and the event's recorded `after` value so rollback refuses rows changed after upgrade. Test a non-canonical-but-valid JSON fixture as well as current minified writer output. This keeps the rollback idempotent and uses no new mechanism. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:64,120,124`, `packages/teamlead/src/StateStore.ts:19965-19980`.
