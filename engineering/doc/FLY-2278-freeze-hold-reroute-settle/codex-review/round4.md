# Design Review — plan.md (Round 4)

Date: 2026-09-03
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 4 correctly incorporates all six Round 3 changes: every minter is version-aware, episode replacement is explicit, cancellation is family-specific, operator-required state is monotonic, consumed-source recovery is replayable, and JSON rollback restores recorded bytes. Two blocking integration defects remain, however: the proposed mailbox cancellation does not actually make the mailbox row nondeliverable, and a late successor can close the only episode that makes a `runHeld:true` hold resumable while leaving the run held. Both can be corrected with existing states, tables, and the existing confirmation door.

## What's Good (Keep)

- Keep version-at-mint across the two family minters and the startup baseline. A7 now covers the exact legacy-authority/no-attempt boundary that previously escaped the one-time upgrade.
- Keep the single episode-transition table and the sequential A4b controls. Closing the previous episode before opening `frozen` or `undeliverable` respects `idx_wdce_open_by_root` without changing the schema.
- Keep the false-freeze four-table zero-write contract. The transition table correctly delays prior-episode replacement until the freeze predicate is true.
- Keep family-specific cancel availability and the refusal for `phase_wake`; `finished` is a business result, not a truthful cancellation state.
- Keep one immutable `delivery_reroute_operator_required:<episode_id>` event and the no-promotion rule for `runHeld:false`. That is the simplest replay-safe model for the cap path.
- Keep consumed CommDB sources as idempotent no-op recovery, followed by normal projection and remaining-run-hold evaluation.
- Keep event-backed byte-exact rollback with both attempt-ID and recorded-`after` fences, including the noncanonical JSON control and dry-run script.
- Keep the zero-new-schema/knob/endpoint budget and the M2+M3 atomic deployment boundary.

## Issues & Recommendations

1. **[BLOCKER] Setting only `mailbox.superseded_by` does not terminalize or cancel the authoritative mailbox delivery.** The plan calls `superseded_by='cancelled:<operation_id>'` a real cancel state, but `superseded_by` is provenance metadata, while the mailbox state machine remains `QUEUED | LEASED | ACKED | DEAD`. The active queue paths select, claim, renew, and deliver rows by `state`/`batch_id` without filtering `superseded_by`; a QUEUED row can still be claimed after “cancel,” and a LEASED row can still be recorded as delivered. This violates the newly stated physical-first ordering and can settle the attempt while its physical row remains actionable. The plan also names no durable encoding/owner for replaying the mailbox/turn cancel decision from a staged `hold_resume` operation; the current operation row stores only a digest unless the existing `family`, `source_attempt_id`, and `target_activation_id` fields are deliberately populated. **Recommendation:** add explicit idempotent CommDB cancellation primitives. For mailbox, CAS the exact row to the existing terminal `DEAD` state, set deterministic `dead_reason`/`dead_at` plus `superseded_by`, and clear lease/batch retry ownership before projecting attempt settlement; an already `DEAD` row with the same marker is replay success, and an already `ACKED` row is consumed/no-op success. Persist `family` and `source_attempt_id` in the existing operation row (with null target denoting cancel), and make `delivery-operations.runPass` the named owner for both the pre-CommDB and post-CommDB crash windows. Add barriers for staged-before-physical and physical-before-StateStore projection, plus an assertion that cancelled mailbox rows are absent from the real runner claim/delivery stream. No new state or column is needed. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:47,51,56,101,105,142`, `packages/flywheel-comm/src/mailbox-schema.ts:99-107,125-145`, `packages/flywheel-comm/src/mailbox-queue.ts:1131-1219,1241-1304,1496-1521`, `packages/flywheel-comm/src/db.ts:3478-3494`, `packages/teamlead/src/StateStore.ts:20013-20030`.

2. **[BLOCKER] A successor appearing after a `runHeld:true` event makes the run lose its only usable resume item.** The monotonic rule says delivery operations should normally reroute and close the undeliverable episode when a successor later appears, while the run remains held for the official door. But this shape's authoritative precondition is that the episode is still open. Once reroute closes it, `GET holds` marks the event changed/non-resumable (or omits it under the revised scope rules), yet the unmatched `runHeld:true` event continues to count as a run-level hold. The operator can no longer stage/apply the action needed to reactivate the run. **Recommendation:** make the post-event rule monotonic in both modes. Once an episode has emitted `runHeld:true`, automatic delivery operations must not reroute it; leave the episode open and require the existing confirmed `reroute_to` or family-supported `cancel` action to perform the physical mutation, close the episode, write `hold_resumed`, and evaluate remaining run holds. A successor that wins before `holdUndeliverableTx` commits is still handled by the existing in-transaction fence and automatic reroute. Add a real transition control: `runHeld:true` -> successor admitted -> maintenance pass leaves episode/run unchanged and door resumable -> confirmed reroute closes it and activates only when no other run hold remains. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:10,51-52,96`, deleted reference `37dc5bd63^:packages/teamlead/src/StateStore.ts:36874-36890`, deleted reference `37dc5bd63^:packages/teamlead/src/bridge/delivery-operations.ts:68-118,175-180`.

3. **[MEDIUM] The rework liveness row still contradicts the new episode-transition table.** The stable rework rule says `overdue && alive` causes “zero writes,” while A4b, the transition table, M2, and the negative guards require an existing `sent` episode to be closed as `advanced` in exactly that case. Those cannot both be implemented literally. **Recommendation:** narrow the statement to “no new received episode and no alert”; specify zero writes only when no previous stage episode exists, and otherwise allow the sole `advanced` closure. Keep A10's alert/episode-creation assertions and A4b's prior-episode closure assertion separate. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:27,33,46,54,95,147`.

4. **[LOW] The operator copy advertises an invalid `cancel` command for `phase_wake`.** The family table and dynamic `requiredDecision` correctly prohibit phase-wake cancellation, but the `runHeld:true` message always prints `reroute_to <exec>|cancel`; only the cap copy is conditional. **Recommendation:** render allowed decisions from the same per-family `requiredDecision` value used by list/stage/apply, so the alert cannot suggest an action the door will reject. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:51,155`.

## Verdict

CHANGES REQUESTED — address the two blockers above before implementation
