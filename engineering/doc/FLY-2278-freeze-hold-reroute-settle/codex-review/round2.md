# Design Review — plan.md (Round 2)

Date: 2026-09-03
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 2 materially resolves all twelve Round 1 findings: the terminal-unread path is now reachable, the two hold decisions are transaction-owned predicates, State-native reroutes are atomic, migration is correctly front-loaded, and the tests are tied to real producers. The plan is still not ready to implement because the replacement rework detector is not liveness-gated and the mandated timestamp parser can discard valid activity, while several operation, upgrade, and recovery states remain internally inconsistent. The required corrections can reuse the existing attempt/episode/operation ledger and hold door; none requires a new table, column, feature flag, or alert layer.

## What's Good (Keep)

- Keep the projector rule that settles only consumed or explicitly superseded physical rows. The projector-first positive control in A2(a) now makes the terminal-unread defect mechanically verifiable through the real event stream.
- Keep `freezeRunTx` and `holdUndeliverableTx` as the only new run-hold writers, with the session re-read, one injected decision time, successor barrier, and atomically matched event/alert payload. The `alive -> absent` reclassification test correctly avoids a permanent liveness latch.
- Keep State-native rework/carrier reroute in one StateStore transaction and reserve the cross-store saga for mailbox/phase-wake/turn-wake. This removes the most dangerous physical-row/ledger crash window from Round 1.
- Keep real physical primary keys plus generation metadata in `contract_ref`; the stale-old-generation receipt tests are the right proof for defect 4 once upgrade compatibility is added.
- Keep `scope`, remaining-run-hold checks, the two-simultaneous-hold test, and the fully mounted auth test. These are substantial improvements over the deleted registry implementation.
- Keep the M0 CHECK-constraint prerequisite, including a non-empty legacy table and second-start byte-for-byte test. Removing `deferred_alive_at` also makes the schema delta smaller and the post-grace behavior more correct.
- Keep settlement in `settleWorkflowDeliveryAttemptTx`, with exact attempt resolution, the caller-supplied timestamp, same-transaction episode closure, and rollback injection.

## Issues & Recommendations

1. **[BLOCKER] The replacement for the retired rework scanner still violates the founder's threshold-plus-liveness rule.** Adding `rework` to `RECEIPT_CONSUMPTION_DEADLINE_FAMILIES` feeds `wake_delivered` attempts into the existing pure age classifier; neither `classifyDeliveryAttempt` nor `observeWorkflowDeliveryContract` reads heartbeat, activity, or outbound evidence. A healthy rework session that legitimately works for 30 minutes after its wake receipt will therefore receive `delivery_contract_stalled`, and the existing severe tier will fire at 90 minutes if the episode remains open. That is not the liveness-gated replacement requested in Round 1, and it is not equivalent to the plan's claimed “exactly one warning.” **Recommendation:** gate rework's received-stage warning inside the existing contract watch with `classifyRecipientLiveness`, re-evaluate it every tick, and perform zero alert/episode writes while the recipient is alive. Specify whether the existing severe tier remains; if it does, it must use a fresh liveness verdict too. Add real `recordWorkflowReworkWakeReceipt` controls for alive-at-30m/90m (zero alerts), absent-at-30m (one warning), and the chosen 90m behavior. This changes an existing classifier path rather than adding a detector. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:15-18,41,98,151`, `packages/teamlead/src/bridge/delivery-contract/policy.ts:3-15`, `packages/teamlead/src/bridge/delivery-contract/classify.ts:42-56`, `packages/teamlead/src/StateStore.ts:35873-35985`, `packages/teamlead/src/StateStore.ts:28870-28902`.

2. **[BLOCKER] The selected timestamp parser can turn valid recent activity into `unknown` and permit a live-recipient hold.** `stale-blocker-guard.parseSqliteUtcMs` unconditionally appends `Z`; an already-ISO value such as `2026-09-03T12:00:00.000Z` becomes invalid and returns `NaN`. StateStore's session APIs persist caller-provided `last_activity_at` values without a format-normalization contract, and this repository already has a tested parser whose comment explicitly warns against the second-`Z` failure. If heartbeat/activity are dropped and no recent outbound row exists, `classifyRecipientLiveness` returns `unknown`, which is a positive hold verdict. **Recommendation:** use or extract the format-total parser from `founder-notify-utils` (SQLite UTC, ISO-Z, and ISO-offset; invalid/null fail safely), rather than mandating the stale-blocker helper. Expand A6 with those format cases and add a `freezeRunTx` barrier using a recent ISO-Z `last_activity_at` that must refuse the hold. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:22,36,74`, `packages/teamlead/src/bridge/stale-blocker-guard.ts:54-58`, `packages/teamlead/src/bridge/founder-notify-utils.ts:7-23`, `packages/teamlead/src/StateStore.ts:7282-7351,8585-8598,8623-8624`.

3. **[HIGH] A completed State-native reroute is left in a nonterminal operation state, and the CommDB operation transitions have no concrete owner.** `rerouteWorkflowStateDeliveryTx` performs the physical mutation, lineage update, episode close, event, and outcome alert, but A4 requires its operation to remain `applied`. The restored stall scan treats `applied` as unfinished, so every successful State-native reroute will eventually emit a false `delivery_operation_stalled`. For the three CommDB families, the plan says “existing outbox -> sent,” but the deleted operation loop moved directly from deterministic CommDB application to projection and contains no owner for `applied -> sent`; the shipped code documents `workflow_delivery_operation` as reserved and currently mounts no such writer. **Recommendation:** either omit the operation row for same-store reroutes or insert it directly as `projected`; if retained for idempotency/audit, `projected` is the accurate terminal state. For CommDB, name the exact physical outbox evidence and method that advances each state, or remove the unused `sent` hop and project idempotently from `applied`. Change A4 to assert the terminal state and add a post-timeout negative control proving no stall alert after a successful State-native reroute. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:25,58-59,84`, `packages/teamlead/src/StateStore.ts:20013-20030`, `doc/engineer/implementation/delivery-contract.md:12`, deleted reference `37dc5bd63^:packages/teamlead/src/bridge/delivery-operations.ts:137-181`, deleted reference `37dc5bd63^:packages/teamlead/src/StateStore.ts:36635-36664`.

4. **[HIGH] Version-aware selectors will strand live attempts created by the currently shipped minters.** Existing rework and carrier attempt refs contain `{table, pk, runId}` but no `routeRevision` or `redriveGeneration`. After deployment, every versioned clock/settle call will add a `json_extract(...)=?` condition that cannot match these live legacy rows, so an in-flight pre-upgrade delivery can stop advancing or settling indefinitely. A7 rebuilds only `workflow_delivery_operation` and does not test this data-compatibility boundary. **Recommendation:** update both initial minters and add an idempotent M0/M1 data upgrade for unsuperseded, unsettled rework/carrier attempts, deriving the current version from their authoritative physical row. A narrowly fenced legacy fallback that atomically upgrades the ref on first safe write is also viable. Add an upgraded-snapshot test with one versionless live row from each family and prove current-version progress/settlement plus stale-version rejection. This is a JSON data migration, not a schema addition. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:28,56-57,75`, `packages/teamlead/src/StateStore.ts:35351-35382,35402-35428,35542-35575`.

5. **[HIGH] `carrier_run_inactive` is a derived run hold, not an independently resumable delivery hold.** The producer moves a carrier to `held` only because its run is already non-active, and its alert explicitly instructs the operator to recover the run first because run recovery automatically revives the carrier. The revised registry instead makes `carrier_run_inactive` resumable without a held run. With another run-scoped hold still present, `revive_carrier` can therefore put the carrier back to `pending` while the run remains held; it will either be paused again or expose an impossible run/delivery combination. **Recommendation:** keep `carrier_needs_lead` as the independent delivery-scoped hold, but model `carrier_run_inactive` as derived/non-independent: list it with the underlying run hold and let the last run-scoped resume call `reviveHeldWorkflowCarrierDeliveriesTx`. If it stays in the 19-entry registry, its door should resolve the run hold rather than redrive the delivery directly. Add a negative control where another run hold remains and direct carrier revival is refused, followed by a positive control proving final run resume auto-revives it. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:45-46,89`, `packages/teamlead/src/StateStore.ts:32571-32613,49543-49624`, deleted reference `37dc5bd63^:packages/teamlead/src/StateStore.ts:37185-37235`.

6. **[HIGH] The alert-only reroute-cap branch has no reachable operator action.** On the third automatic reroute the plan leaves the episode open and the run active, then tells the operator to use `hold list`. But the existing registry recognizes `delivery_undeliverable_no_recipient` from a `delivery_reroute_operator_required` hold event, while this branch emits only an outcome alert and deliberately does not create that hold. The only `allowOverCap:true` entry is `resume_undeliverable`, which requires the very hold event that the cap branch does not produce. The result is a permanent open episode with a known live successor and no way to approve the bounded override or cancel it. **Recommendation:** expose the open undeliverable episode as an actionable, delivery-scoped item through the same list/stage/apply endpoint without changing `run.status`, and let that confirmed action perform one over-cap reroute or cancel. Alternatively, name a different existing recovery owner and remove the false `hold list` instruction. Add a real control: cap alert -> action appears -> confirm-token apply -> reroute/cancel completes -> run was never held. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:23,84,91,127-129,138`, deleted reference `37dc5bd63^:packages/teamlead/src/bridge/hold-shape-registry.ts:165-169`, deleted reference `37dc5bd63^:packages/teamlead/src/StateStore.ts:36943-37006`.

7. **[HIGH] The reroute transaction does not explicitly revalidate that its target is still the current live successor.** `delivery-operations.ts` resolves a target before calling either reroute path, but the enumerated steps of `rerouteWorkflowStateDeliveryTx` validate only the physical source CAS and lineage. A successor can terminate or be replaced between resolution and transaction entry; State-native reroute would then atomically bind to the wrong corpse, and the CommDB saga can stage the same stale target. The deleted State-native apply method at least re-read target session/run status, so omitting that fence is a regression. **Recommendation:** inside the State-native transaction and the CommDB staging transaction, re-resolve/fence the current activation and require the exact `targetExecutionId` to remain in `CMUX_LIVE_SESSION_STATUSES` for the same run/issue. If it changed, leave the episode open and retry resolution; do not consume reroute capacity. Add barriers for target-terminal and target-replaced between scan and stage. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:23,39,57-59,84`, deleted reference `37dc5bd63^:packages/teamlead/src/bridge/delivery-operations.ts:99-118`, deleted reference `37dc5bd63^:packages/teamlead/src/StateStore.ts:36241-36253`.

8. **[MEDIUM] The freeze writer's no-op contract contradicts its alert contract.** The stable signature says any failed condition produces zero rows, but M2 and the display copy require the same transaction to write “not frozen: recipient still moving/terminal.” A1 checks only that `workflow_run` is unchanged in ten cells, so either implementation could pass while episode and alert behavior diverge. **Recommendation:** choose one rule and make A1 assert episode/event/alert counts in all twelve cells. The smaller and founder-aligned rule is zero writes when the three-condition predicate is false, with the “not frozen” variants removed; if an informational alert is required, specify it as a separate non-hold observation with deterministic deduplication. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:22,40,83,126,137`.

9. **[MEDIUM] The settlement caller map still mislabels and therefore does not mechanically cover every caller.** `StateStore.ts:56229` is launch side-effect abandonment, not a second land caller, while `:26580` is launch rollback only. The current source has one land call at `:55216`. Calling the tests “land x2” can leave launch abandonment untested even though A5 claims one test per concrete caller. **Recommendation:** enumerate the actual logical callers explicitly: baseline, launch rollback, launch side-effect abandon, carrier completion, gate-holder completion, land completion, and projector settlement. Keep a distinct rollback test for every transaction owner. **Evidence:** `engineering/doc/FLY-2278-freeze-hold-reroute-settle/plan.md:26,75,78`, `packages/teamlead/src/StateStore.ts:26580-26585,35320-35329,35696-35701,35800-35813,47670-47684,55215-55221,56213-56234`.
