已结束的 Codex 体，必须真正关掉

FLY-2903 · 设计稿 · 2026-09-25 · 基于代码审计与 FLY-2893 普查数据；本单只读取证，没有碰生产进程

一句话结论

Bridge 以后要关一个 Codex 体时，先让它自己停下，再动手杀进程；另外加一个每 5 分钟跑一轮的「收尸巡检」，保证每个已结束的 Codex 体都有一句查实过的「确实关了」。关不掉、或者结束后还在烧 token 的，会发告警，也会显示在额度页上。

为什么要做：FLY-2893 算出，已经标成「结束」的 Codex 体又多烧了约 12.07 亿 token，差不多是一个 Codex 号一周额度的 112%。其中 92% 来自两具体：FLY-2766（结束后又跑约 15 小时）和 FLY-2873（约 10 小时）。

病根为什么「关了」的体还在跑

先说几个词：

  • daemon：Codex 在后台常驻的进程，真正调模型、真正花 token 的就是它。
  • goal runtime：Bridge 进程里的一个小管家，负责连上 daemon、推着任务一轮一轮往下做。
  • transport death：管家和 daemon 之间的连接突然断了。

管家有一个自救本能：连接一断，它就认定「daemon 崩了」，于是重启一个新的 daemon，接着同一个任务继续做，最多重来 5 次。可是 Bridge 自己「关」一个体时（Lead 终结、收尾、引擎退役），做法是越过管家，直接把 daemon 杀掉。管家不知道这是我们有意杀的，照样把它当成崩溃救回来。新 daemon 用的是当时的登录凭据，所以常常已经换成了另一个号，这就是 FLY-2814 看到的「换号继续干 ×5」。

第二个洞是没人收尸：杀的结果如果是「证不出这进程是不是它的」，调用方直接不管了；而现有的两道兜底，一道只看数据库里还标着 running 的行，另一道只收跑了 2 小时以上的孤儿进程，FLY-2873 这种形状两道都漏掉。

修法 1先请它自己停，再动手

Bridge 里本来就有一张「谁在跑哪个体」的登记表（所有权登记：记录某个 Codex 体此刻由 Bridge 里哪个管家负责）。这次给它加一个「请停」按钮：

  1. 所有要关体的路径（Lead 终结、收尾、引擎退役、关窗口），动手前都先按一下「请停」。
  2. 管家收到后自己叫停：它先把自己标记为「已叫停」，然后亲手关掉 daemon，确认 daemon 退出后再交还登记。
  3. 管家的自救本能多了一道闸：只要这个体已经被请停，或者引擎已经批准它退役，连接断了也不再复活。这道闸自己如果出错，同样按「不复活」处理。
  4. 然后 Bridge 照旧对进程组补一刀（兜底），再探测一次，把结果记进「收尸账本」。

真正的中途崩溃（上游断线、daemon 自己挂掉）不受影响，照样会被救回来，因为那种情况下没有人按过「请停」。

修法 2每 5 分钟一轮的收尸巡检

巡检挂在 Bridge 现有的 5 分钟维护节拍上，不新增定时器。每一轮它会挑出两类体：近 48 小时内结束的 Codex 体；以及不管结束多久、只要现在还有活进程的已结束体（专门抓 FLY-2766 这种跑了十几个小时的）。挑出来的逐个探测：

  • 「确实关了」要测两次：第一次看到进程组没了、socket（daemon 接收连接的那个本机通道）不再有人监听、进程列表里也找不到它，先记「待确认」；下一轮再测一次，而且它的 token 计数没再涨，才记「已关」。测两次，是为了防「旧进程死了，其实换了个新身体接着跑」这种假象。
  • 还在 Bridge 里跑（FLY-2766 的形状）：连续两轮都看到，就按「请停」，同时告警。
  • 没人管、但能证明是它的 daemon：杀掉（先礼后兵：SIGTERM 不退再 SIGKILL）。每次发信号前再同步复查一遍：仍是结束状态、仍然没人管、没有被停驻。
  • 证不出是它的：一个信号都不发，只告警，交给 Lead 处理。本单不新增任何「凭猜测杀进程」的路径。
  • 进程列表里还能看到它的任何 Codex 进程（不管跑在哪个账号目录下）：就绝不算「已关」。哪怕证不出是它的、不能动手，也会告警。

token 从哪来：每个 Codex 体都有一份逐轮记录文件（rollout：Codex 把每一轮用了多少 token 都写在里面）。巡检记下「结束那一刻」的累计数，之后每轮只读新写进去的部分；只要结束后还在涨，就是在烧额度。算法和 FLY-2893 普查用的是同一个。

数据记在哪里、你在哪里看得到

新建一张表 codex_terminal_close（收尸账本：每个结束的 Codex 体一行，记录它现在是「待确认 / 已关 / 还在跑 / 收不掉」中的哪一种、结束后又烧了多少 token、最后一次的证据）。账本每换一次状态，另写一条不可改的审计事件。

  • 告警：新增一种告警 codex_terminal_body_alive，内容包括单号、体、结束时间、结束后 token、处置结果。同一个体同一种状态只告一次；结束后的 token 每涨一个数量级（比如从百万级涨到千万级），再告一次。
  • 额度页：顶部加一条横幅「⚠ 终态 Codex 体仍在用额度（N）」，逐行列出近 24 小时里没关干净、或者结束后还烧了 token 的体；没有这样的体就不显示。
  • 总开关：新增 codex_terminal_reap_enabled，默认开。关掉以后巡检只看、只记账、只告警，不请停也不杀进程。

取舍考虑过、没选的做法

做法为什么不选
干脆关掉自动复活（重启次数设成 0）真崩溃也救不回来了，退回到一年前那种一断就死的脆弱状态。
只让管家在复活前去查一下数据库状态单靠这个不够：有的关闭路径是先杀进程、后改状态，比如引擎退役时体还标着 running。这一条保留成第二道闸，但主修法是「先请停」。
在磁盘上写一个「已死」标记文件多一个要写、要清理的地方。登记表就在同一个进程里，Bridge 一重启管家也跟着没了，用不着落盘。
把 FLY-2555 的收尸扩大，或者放宽 2 小时孤儿收割器的门槛前者只看数据库里还标着 running 的行，FLY-2873 正是从这里漏掉的；后者 FLY-2830 评审时已经否决。
按进程环境变量认出是谁，直接杀这等于新增一条「凭推断杀进程」的路径，误杀的风险太高。证不出是谁的，一律只告警。
同时在巡检快照（Lead 巡检脚本）里加一项额度页和告警已经能看到；再改 shell 脚本会撞上一整套清册守卫。放到以后做。

边界这个设计做什么、不做什么

做：关体时先让它自己停；已经请停或已批准退役的体不会再复活；近 48 小时结束的每个 Codex 体都会有一个测过两次的「已关」结论；能证明身份的活 daemon 会被收掉；证不出身份的、或者结束后还在涨 token 的，会告警并显示在额度页上。在默认节奏下，一个「已结束但 daemon 还活着」的体从被发现到关闭确认，最多三轮巡检，约 15 分钟。

不做：

  • 不凭推断杀进程。证不出身份的只告警，这类体仍需要人来处理。
  • 不改现有两道兜底（FLY-2169 孤儿收割、FLY-2555 终态收割）的规则。
  • 不回头处理 48 小时以前结束、现在也没有活进程的历史体（它们已经不再烧额度）。
  • 不单独处理 founder 可见的 Codex 窗口客户端：它不烧 token，daemon 一死它就自己断开，窗口由现有流程关闭。
  • 这是设计，不是生产结果。本机只跑相关的单元测试；用真 Codex 的演练要等 Codex 服务恢复后由 QA 来做；上线后的实际效果由 QA 和部署后的核验确认。
