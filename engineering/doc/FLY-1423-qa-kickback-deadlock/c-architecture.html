2 技术附图：六块组件怎样把规则落下来

依赖关系不倒流；每次打回向账本追加新 attempt，再把一次性的写权交给原 actor。

3A Data flow：QA fail 打回 implement

QA 给出有权限的 FAIL 和问题上下文；原 implement 不换 exec，只换新 epoch，完成后自动回 QA 重验。

3B Data flow：founder 打回 design / implement（FLY-1364 类）

Founder 指定“哪里不对”；状态机先算影响范围，再唤醒目标节点原 actor，最后只重验真正受影响的下游。

4 Session 生命周期：完成节点不等于下线

写权短命，actor 长活；真正的 terminal 只发生在 issue 收口。

完成节点后

写 output、交 TURN、进入 park；不再碰 worktree。

收到打回后

同 exec 带新反馈和新 epoch 被唤醒，继续原上下文。

5 C 解决两类打回：机制相同，只换四个参数

引擎只实现一次 re-entry；QA 与 founder 不再各自维护一套脆弱的人肉协议。

明确回答：C 同时解决两类打回

两条路都先追加 node#attemptN，再给原 actor 一个新的 TURN epoch 和本轮 context；actor 保持同一 exec，完成后按 verification policy 继续。不同的只是上表四个参数，不是调度机制。

不在 DAG 上画回边 不把活进程改绑新 exec 不覆盖旧 attempt 不让旧 epoch 继续写 进程死亡才 fresh spawn
