FLY-1423 · Founder decision brief · 2026-07-22

节点做完以后，是下线，还是能被叫回来重做？

QA fail 与 founder correction 暴露的是同一个根问题：single-pass DAG 不足以承载随时打回的 LLM 工程流程。DAG 继续做依赖模板，runtime 升级为可重入 workflow state machine；健康 phase actor 保留身份和上下文继续做。

形式 · DAG 模板 + 可重入状态机 C · 正常路径：同 runner / 同 exec A · 死亡兜底：fresh exec B · 淘汰：活进程换 exec

1 先回答形式：这还算 DAG 吗？

只做底层纯 DAG + task retry

适合失败重试和单轮依赖；要表达“1、2、3 完成后重做 2”，只能靠 clear/rerun 运维动作，correction 语义太弱。

推荐 runtime可重入 workflow state machine

correction 是显式 event；追加 node attempt、计算下游失效范围、授权 actor、增量复验，全部 durable。

设计参照Temporal 式长活 workflow

open workflow 接 Signal/Update；worker cache 可粘滞也可驱逐。借它的语义，不要求直接换引擎。

静态依赖图仍是 DAG： design → implement → QA → founder gate
design#1→implement#1→QA#1→founder correction→design#2→增量 review / affected nodes

没有在静态图里画 3 → 2 回边；event history 只向前追加，所以历史仍然无环。“回去”是业务语义上的 re-entry，不是覆盖旧结果。

Session 生命周期： 节点完成后立即释放 TURN 并 park；issue 还在 QA / founder / landing 的 correction horizon 内，phase actor 保持可唤醒。只有 ship、取消、founder close 才逻辑 terminal；容量压力可物理 eviction，但必须能从 durable state 恢复。

一句话裁决： QA rework 与 founder correction 是同一个 first-class correction loop 的两个触发源；同 runner 唤醒是首选执行策略，不是 loop 本身。

4 六个成熟引擎的共同答案

Airflow

clear 已成功 task，可选 upstream/downstream 后重跑并保留历史；worker 不保活。

Temporal

open workflow 接 Signal/Update；closed 后 reset 或 with-start；sticky cache 可驱逐并 replay。

Dagster

可 re-execute / op selection 选择目标、祖先或后代；step 默认独立进程。

Argo Workflows

可 restart-successful + node selector 重启成功节点；同 Workflow object，新 pod 承载。

GitHub Actions

成功 run 也能 rerun all / specific job；RUN_ATTEMPT 递增，hosted runner 是 fresh VM。

AWS Step Functions

redrive 只接受未成功 execution；SUCCEEDED correction 要新 execution 或定义内显式 loop。

成熟引擎并不认为“成功后永远不可重做”：Airflow clear、Dagster subset、Argo restart-successful、GitHub rerun 都提供 correction 手段。共同底线仍是 attempt / event durable、worker 不是真相源。Flywheel 的特殊点：correction 是业务常态且 LLM 上下文昂贵，所以要把 operator action 提升为 first-class event，并优先复用健康 actor。

为什么 B 最差？

它让一个活进程中途“换工牌”。但 exec 身份已经进入环境变量、CommDB session、凭证、workflow binding、watchdog、Lead 指令路由、completion ownership 和 TURN holder。任何一处未原子切换，就会同时出现旧身份和新身份；收益却只是绕着 C 的稳定 actor 模型走了一圈。

6 正确的身份拆分

1逻辑工作(run, node, attempt=2)
DAG durable truth
2Resident phase actoractor_exec_id = impl-1
身份稳定，可服务多轮
3一次激活权(attempt=2, epoch=4)
append-only lease / capability
4本地进程alive / dead / replaced
可丢失，不是真相源

现有 schema 把 execution_id 一对一绑定某个 attempt，且禁止 update/delete。终态不应放松历史不可变性，而应新增 stable actor → per-attempt activation 这一层。

7 C 不双写的十条底线

  • 每次 QA fail 都创建新的 logical attempt，绝不覆盖上一轮。
  • actor execution_id 稳定；禁止活进程重绑身份。
  • activation 记录 append-only，历史不可改、不可删。
  • 同 worktree 同时只有一个 active TURN lease。
  • 所有写入带 TURN epoch；迟到的旧 epoch 被 fence。
  • completion 权限绑定 attempt + actor + epoch，而非“exec 一生只能交一次”。
  • 同 attempt 同 digest 重放 200；不同 digest 仍 409。
  • 相同 round/epoch 的重复 wake 不重复 worktree 或外部副作用。
  • 只有 proven dead 才走 A；replacement launch 成功后才 admit。
  • 每轮仍写 docs、progress、commit、receipt，确保随时可恢复。

8 对 PR #674 的裁决建议

暂停现形态 ship；保留基建，替换主路径

  • 不能原样 ship：正常 QA kickback 不应 evict 一个健康、掌握上下文的 implement actor。
  • 保留：launch 成功后才 admit、ghost cancellation fence、卡住 tripwire、相同 completion 幂等、真冲突 409。
  • 重做：runtime 采用 first-class correction event；健康 actor 走同 exec + 新 TURN epoch；A 只在 proven-dead 后启动。
  • 统一：QA fail 与 founder correction 共用 attempt / activation / TURN / wake 基建，差别只在目标、权限、失效范围和复验 policy。
  • 已有先例：FLY-752 的 QA retest 同 exec；FLY-887 PhaseOrchestrator 已实现 QA fail 后唤醒原 implement、死亡才 spawn。

需要 Annie 拍板：批准 “C 主路径 + A failover + B 淘汰” 后，再进入代码重构与真机 E2E；拍板前不改代码、不推进 ship。
