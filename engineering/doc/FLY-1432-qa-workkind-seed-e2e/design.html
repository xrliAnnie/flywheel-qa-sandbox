FLY-1432 · 「新工作类型模板」的独立验收方案

被验对象:PR #678(FLY-1380,版本指纹 6a0576bd)· 2026-07-22 · QA 设计阶段
一句话:FLY-1380 往系统里「预装」了一批按工作类型分的新派工模板,但按设计它们应该装好了却先不启用;本方案在一间与生产完全隔离的「测试房」里,用真实系统实跑三件事——① 模板真的装进去了 ② 真的没被启用 ③ 现在的派工没被弄坏——并留下可查证据。

「真启动」= 跑的是和生产一模一样的启动代码,不是模拟;房间用完即拆,生产零感知。

2. 三项体检分别怎么证

体检项怎么证(全部真机)
① 模板真落库 房间里全新启动一次 → 数据库里应出现恰好 6 个新旧模板身份、且都处于「已发布」状态;被淘汰的 2 个旧模板不再被安装。再热重启一次 → 不重复安装(幂等)。
② 装而未启用 重启前后,「哪个项目用哪个模板」的绑定表一行不多一行不少;正常派工照旧选到老模板;有人想手动直选新模板 → 系统按开关拒绝(409)。开关只在房间里打开试一下:手动直选可以过(这是设计允许的),自动路由仍然不会选到新模板。
③ 老派工没坏 原样跑 PR 自带的两条「从派工到完工」全链路真机测试(真终端、真调度、真文档落盘)+ PR 触到的全部单测。任何红项须用主干版本对照,证明是环境噪音而不是这次改动弄坏的。

「没启用」的判定完全落在绑定账本上:只要它零变化,新模板就不可能被自动派到——这正是 FLY-1380 设计里 dormant 的定义。

4. 关键取舍(为什么这么设计)

  • 复用 PR 自带的两条全链路测试,而不是重写一套 —— 它们本来就是真机全链路,且这次 PR 恰好改写过它们;原样跑绿一举两得:老链路没坏 + PR 对这两个脚本的迁移不是纸上谈兵。(弃案:全部重写——重复劳动且引入自己的 bug 面)
  • 隔离房实跑,而不是直接在生产库上核对 —— 生产验收属于上线窗口(ship note 已有专门口径);QA 阶段在生产上做启动实验风险不对等。(弃案:读生产库——只能看现状,无法做「重启两次对比」这种关键实验)
  • 验收脚本连同证据一起存档进仓库,而不是用完即删 —— 谁都能复跑复查,证据留到 Annie 验收完。
  • 被测版本指纹开跑前后各核一次 —— 防「测的和合的不是同一份代码」。

5. 诚实边界(这次验收不覆盖什么)

  • 不验真正「启用」新模板的切换动作(绑定迁移、开关翻转)——那是后续 cutover 单的事,本 PR 本来就不含。
  • 不验设计师/原型两个新模板的完整创始人闭环(试用投递、「不能做」终态)——系统能力尚未建成,FLY-1380 计划里已明文登记为后续项。
  • 不重跑codex 代码审查——那是合并时的独立关卡。
  • 覆盖本次上线唯一会发生的行为变化:重启后模板一次性预装 + 一切照旧运转。

6. 判定纪律

PASS 的唯一条件:三项体检全绿、每条结论都指向一份存档证据文件;任何红项要么当场判 FAIL、要么用主干对照证明与本 PR 无关。不允许「工具说成功了」当证据。
