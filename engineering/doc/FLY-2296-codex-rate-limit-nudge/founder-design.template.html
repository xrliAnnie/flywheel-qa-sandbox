FLY-2296:Codex 额度换模菜单,让停驻体出生就关掉它

工程设计说明 · 2026-09-03 · 分支 flywheel-FLY-2296 · __REVIEW_META__ · 每个卡片下方都可以留意见,页底一键汇总复制

一句话总结

9 月 3 日早上,7 个 Codex 停驻体同时被同一个弹窗钉住:「额度快用完了,要不要换成 luna?」。这个弹窗是 Codex 自带的,默认焦点停在「换」上;而 Flywheel 的模型是你定的,所以它对无人值守的体只有「卡住等人」和「误按换模」两种结果。修法只有一件事:体出生时,把 Codex 自己那个「以后别再提醒我」的开关预先写进它的配置文件。不换模、不加旋钮、不改巡检。

名词:停驻体 = 常驻在后台、一直追着一个目标干活的 AI 工人进程;Codex TUI = 你在 cmux 窗口里看到的那个 Codex 文字界面;luna = OpenAI 的低成本模型 gpt-5.6-luna;config.toml = Codex 的配置文件,每个体有自己独立的一份。

病根:弹窗从哪来、为什么必撞

我读了 Codex 的源码和本机那份二进制:当账号的 5 小时窗或周窗(OpenAI 按这两个时间窗计额度)用量到 90%,Codex 界面就记一个「待弹」状态,等体做完下一个 turn(一次问答回合)就弹出来。它只看一个开关:配置文件里 notice.hide_rate_limit_model_nudge 是不是 true。Flywheel 给每个体生成配置文件时,从来没写过这个开关,所以每个体都会撞上。

__SVG_D1__

图 1 · 修复前后的分叉。左边是今天发生的事:弹窗盖住画面 → 巡检人手按三下选「以后别提醒」→ Codex 把开关写进配置,但写在了 Flywheel 自己管理的区块里面,下次重新生成配置时会被一起删掉。右边是修复后:开关已在,弹窗状态直接归零,只留一行「Heads up」提示。

还有一件比卡住更危险的事:弹窗里的「换」不是只改画面,它会把整条线程的模型换成 luna——后台驱动这个体干活的进程用的也是同一条线程,所以任何一次误按 Enter,这个体接下来就一直用 luna 干活。

修法:配置生成链上加一道钉子

体的配置文件是一条流水线生成的:从你自己的 Codex 配置做种子 → 钉死沙箱与审批策略(已有)→ 追加 Flywheel 管理的几个区块(已有)。本单在「钉死策略」旁边再加一道同样形状的钉子:[notice] hide_rate_limit_model_nudge = true。这与 Codex 自己在你按「以后别提醒」时写的内容一字不差,只是提前写好。

__SVG_D2__

图 2 · 配置文件的生成链与两类 home。pin / 钉 = 不管种子里写了什么,输出里这一项一定是我们要的值;managed 块 = 被 Flywheel 用标记包起来、每次重新生成都会整段替换的配置片段;Lead home = 三个 Codex Lead(mufasa、honeylemon、infra-bot)各自的配置目录,它们用同一个 TUI,同样会撞弹窗,Lead 裁定一起钉,但只钉这一个键。

种子配置可能长几种样子:完全没有 notice 段、只有 notice 的子表、已经有 notice 表头、或者用了不能安全改写的写法。前三种各有一条确定的处理;最后一种直接报错拒绝生成——宁可这个体派不出去,也不写出一份坏配置。生成之后还会把文件重新解析一遍,确认开关真的是 true,否则同样报错。

证明它真的有效:假服务器接真界面

Tadashi 提了一条硬要求:守卫必须能变红——要能证明「没有这个键就会弹、有了就不弹」,不能写一条永远绿的检查。弹窗要真实账号用量到 90% 才出现,不能拿生产等。我写了一个假 app-server(Codex 界面背后那个提供数据的服务的替身,只会按剧本回答),接上真的 Codex 界面,让它相信「用量 95%」,然后看弹不弹。

上面是「没有键」那一组抓到的真实画面,与巡检当天在 7 个体上看到的一字不差。实现时这个探针会固化成仓库脚本,QA 用它打真生成出来的配置:先期望不弹,再把键删掉期望弹;两条都过才算修复有判别力。

关键取舍与被拒方案

  • 选体出生时写进配置文件——与 Codex 自己保存这个偏好的位置、键名、语义完全一致,一处真相,重新生成也幂等。
  • 拒在启动命令行上加参数——同一件事两处写(命令行与配置文件互为镜像);Lead 侧早已把配置文件定为唯一被校验的来源。
  • 拒预先把体设成 luna(设成 luna 就不弹)——直接违反你的模型决定权。
  • 拒让巡检自动按「以后别提醒」——把病根留给巡检;而且按下去写的键会在下次生成配置时被剥掉,治标不治本。
  • 拒额度到 90% 自动切账号——那是 FLY-2109 的题,先把弹窗去掉,切不切号是另一个决定。
  • 拒给在飞的 17 个体回填配置——界面只在启动时读一次开关,回填不改变生效时刻;等下一次重新生成配置并重开界面(Bridge 重启的恢复路径)自然生效。

诚实边界:这个设计做什么、不做什么

做

  • runner 的配置生成链加一道钉子;三个 Codex Lead 的配置脚本加同一个键(只这一个键)。
  • 一个可以变红的探针脚本进仓库,QA 用它证明有键不弹、无键会弹。

不做

  • 没有证明弹窗会导致 goal 暂停。代码里让 goal 暂停的只有 Bridge 自己(阶段交接、等门时的有意停顿),弹窗是界面本地状态,不会向后台发暂停。巡检当天对两个体手工 /goal resume,有越过 Bridge 有意停顿的风险——这一点 Tadashi 已认领另行处置,本单不为它改代码。
  • 「poller 不读信」在 Codex 体上的准确含义是「体的 turn 没推进」;本单只能证明弹窗盖住了画面并带来误按换模的风险,不能把 turn 停滞归因于弹窗。
  • 修复对修复前已启动的界面不生效,要等下一次重新生成配置并重开界面;在那之前巡检的手工处置照旧。
  • 不改巡检脚本(它现在就能识别这个弹窗);不做额度切号;不加环境变量、开关或告警层。
