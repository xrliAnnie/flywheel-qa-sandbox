DAG 断点继续与恢复 — E5 设计

FLY-1707 · 设计已过 Codex 独立评审 14 轮(终局 APPROVED)· 2026-08-15 · 附:FLY-1416 / FLY-1711 / FLY-1668 三单并入

① 一句话

崩溃重启后,单子从『当前该做的那一步』接着跑,不再从头重来 —— 做法是:平时每走一步都留一份可验证的『恢复凭据』,重新进场时先验凭据(代码没变、输入没变、旧执行者已围住),验过就接着跑,验不过就明确拒绝并给出路,绝不悄悄退回第一步。同一张设计里把 run(一次任务的完整执行记录)的『关不掉』『死不透』『救不活』三个邻接死角一并修掉。

② 问题:为什么只能从头重跑

DAG(把一个单拆成设计→实现→检验等有先后顺序的多步流程)引擎其实一直记着『现在该做哪一步』,但没有任何证据能回答『凭什么现在还能接着做』。2026-08-11 系统崩溃后,五个单全部退回设计步重跑,单日白烧 4.1 小时(全部在最贵的模型档位)。

③ 核心流程:恢复凭据怎么用

四条已锁语义(Annie 8-11 拍板):恢复到当前那一步(不做逐步缓存)/ 半成品先封存再从该步重跑(不算『代码变了』)/ 验收口径 = 1 单进 qa + 3 单进 implement + 设计步零重跑 / 『省 4.1 小时』必须与『历史那批要靠凭据重建才能重放』的说明绑在一起讲。

两个关键细节(不做就白修)

  • 比对用『是不是同一条线往前走』,不用『完全相等』 —— 跑到一半的步骤只要提交过东西,严格相等就会误判『代码变了』,又退回第一步。
  • 重建工作目录时必须显式指定起点 —— 否则现有代码会把存着设计稿和成果的分支(git 里一条独立的改动线)删掉、从主干重建,东西就没了。代码锚点存两份(本地受保护引用 + Bridge 自有备份仓),连换机器/删仓都能找回。

④ 数据与结构模型

不新建『第二本进度账』—— 凭据直接挂在引擎已有的权威进度上,每次进度变动(共 10 类写入点,逐一盘点 + 防漏守卫)都同步写/继承凭据。新增 8 张表,全部沿用项目现成模式(只增不改的账本 + 带校验的状态机):

组表干什么
断点继续workflow_resume_attachment恢复凭据本体:代码锚点 + 输入快照指纹 + 语义指纹,绑死『当前那一步』
…_attachment_state凭据的异步补全状态机(锚点落备份仓、输入正文盖章),崩在任何一步都能续

五道验证(V1–V5)里最容易做错的一道是 V5『旧执行者已围住』:不能只在受理时看一眼活没活,必须在每个写入口装闸 —— 晚回来的旧执行者提交任何东西(产物/完成报文/评审结论/PR 证据)都会被拒。

⑤ run 的生死闭环(三张并入单)

  • FLY-1416 force-cancel:审计发现 issue 里描述的『拒绝关闭』那半边其实已是死代码,真缺口是『关了 run 却不收执行体』。设计成一步原子操作 + 崩溃可续的收据。
  • FLY-1711 close 级联:今天运维关掉最后一个执行体,run 反而会被误标成异常并报假警。设计成:只有运维显式操作才级联判终(自动化清理一律不级联),多执行体的 run 绝不误杀。
  • FLY-1668 救援路径:主路径定为『重派认领』(不复活已完结的旧执行者 —— 终态免疫是红线);具体派发机制归在飞的 FLY-1772,本单只做路径定案 + 一条真卡单的端到端实证 + 死角文档化。

⑥ 关键取舍与被否掉的方案

选了否了为什么
恢复当前那一步(整体验证)逐步增量缓存(build cache)引擎不知道执行者实际读过什么,缓存会错误复用过期结论 —— 宁可多跑一点,不能跑错
续同一个 run + 独立受理(路A)新 run 顶掉旧 run(路B)Tadashi 有活体证据:被顶掉的僵尸 run 清理负担大、还有双活风险;路B 留后续单
验不过 → 明确拒绝 + 落账 + 三条出路『自然回落』到第一步静默回落正是本单要消灭的行为;每次拒绝可查账是 Tadashi 硬要求
级联终态写 terminatedissue 原文的『done→completed』completed 在引擎里的含义是『流程真走完了』,伪造它会污染完成账(与 FLY-1655/1770 的不变量冲突)
恰好一个注册开关,默认关;观察模式先行多开关 / 无开关直接上这个功能压在每一次 DAG 派单上,先只观察出数据、再手动打开;与『不加新 flag』纪律取最小交集

⑦ 诚实边界:这个设计不做什么

  • 不做步骤内断点续传(Annie 明确不需要)、逐步缓存、自动恢复(引擎自己发现自己重派)—— 本单只保证『重新派单时不退回起点』。
  • 不复用你的批准、上线动作、以及任何『检验不合格』的结论;不放开已完结执行者的复活。
  • 历史单救不回:存量完成记录物理上无法补写凭据(账本只增不改),新机制从上线后的下一步生效。『省 4.1 小时』的验证靠事故重放:在生产库只读副本上重建当时的凭据来证明『判据当时能判对』—— 它不等于『机制当时就在跑』,这两句话必须绑在一起讲(锁定语义④)。
  • 排期依赖:与在飞的 FLY-1770 / FLY-1772 划清了辖区(对账表在计划 §9),两个撞文件的切片排在它们合入之后。
