# Design Review — plan.md (FLY-1707 E5) (Round 11)

Date: 2026-08-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 11 closes the six Round 10 findings in direction: the T2 constraint is now real SQL, frozen replay has a durable-body design, baseline writes are launch-fenced, marker adoption has an authenticated-source concept, executable shadow probes wait for current proof, and V2/invalidation are discriminated. The architecture remains feasible, but the normative T3 DDL, physical-launch preparation seam, reconciler fencing, state-only shadow branch, collector adoption semantics, and flag-off launch contract still contain implementability or concurrency gaps on paths with fleet-wide blast radius.

## What's Good (Keep)

- The T2 invalid-state invariant is now an actual bidirectional SQLite CHECK; an executed negative insert rejects `invalid` with a NULL reason.
- The frozen-replay design correctly recognizes that a digest cannot reconstruct prompt bytes and binds replay to admission-frozen S3 input instead of re-fetching Linear.
- Baseline-slot writes now share the physical launch owner/generation/delivery-attempt fence, preventing stale launches from poisoning the whole run.
- The executable shadow gate now waits for both committed delivery evidence and a recovery-relevant writer state, closing the stale `attachment:ready` verdict identified in Round 10.
- The selected-action V2 tail and discriminated invalidation authority preserve the legitimate no-execution gate path.
- The plan continues to honor the locked product boundaries: current-step rerun only, quarantine of half-done work, no silent template-head fallback, no approval/land/fail-verdict reuse, and no `completed -> running` reopening.
- Source assumptions around the strict four-key marker parser, marker-first commit ordering, recovery adoption path, neutralized quiescence helper, GatePoller rider cadence, worktree deletion, and launch-owner generation all match the current branch.

## Issues & Recommendations

1. **The normative T3 action CHECK still does not make `frozen_s3_body` part of the redispatch union.** Section 2.1 says the DDL is authoritative, but its CHECK only constrains result attachment, attempt/execution, and redrive generation. Executing that DDL permits a `redispatch_execution` row with `frozen_s3_body IS NULL`, permits a state-only admission to carry arbitrary body bytes, and imposes no 256 KB limit. Such a schema-valid redispatch cannot satisfy the promised crash replay. Add the body clauses to the same action-discriminated CHECK: redispatch requires non-NULL UTF-8 bytes with `length(CAST(frozen_s3_body AS BLOB)) <= 262144`; state-only requires NULL. Keep the transaction-local digest comparison to the authoritative baseline, add a canonical `frozen_input_too_large` reason (the current closed union has none), and execute negative inserts for NULL redispatch, non-NULL state-only, and byte-over-limit multibyte input.

2. **The prepared-candidate/marker protocol is not yet represented in either the normative persistence model or the current launch call graph, and marker v2 is rollback-incompatible.** The plan has one prose reference to a “durable prepared-candidate record,” but no event kind/UID/payload, table, retention rule, or slice owner. In source, the candidate is learned after `Blueprint.hydrate()`, while all three TeamLead launch surfaces build a zero-argument `commitWorkflowLaunch` closure earlier and the adapters invoke that closure later; there is no named post-hydration callback that can persist and validate the candidate before prompt continuation. Also, the current `readWorkflowLaunchMarker` rejects every extra key, so a previous binary cannot read a new v2 marker after rollback; the stated dual-read contract only covers new code reading old markers. Use the simpler existing primitive: append a checked immutable run event such as `issue_delivery_prepared:<execution>:<generation>:<deliveryAttempt>` with the complete candidate projection, and add an explicit `prepareWorkflowIssueDelivery(candidate)`/opaque prepared-token seam from Blueprint through core/adapter context to the three launch surfaces. Keep the four-field marker byte-compatible; new adoption can authenticate it by looking up the exact prepared event, while absence means legacy adoption with no resume evidence. If marker v2 is retained, specify reverse-read/rollback behavior. Put this work explicitly in S2 and test runs-route, actions/retry, and engine-dispatcher initial plus repair paths.

3. **`attachment_reconciler{riderEpoch}` is not a durable authority and can terminally invalidate a successfully readied attachment.** T2 stores no rider epoch/owner generation, and GatePoller has only process-local tick/cadence state. Because the helper currently allows every authority kind to change any non-invalid state including `ready`, a stale fifth retry can race a successful store/S3 stamp, win afterward, and make the absorbing result permanently `invalid`. Do not add another lease machine: make reconciler invalidation an exact CAS on attachment ID + current V0 target/receipt + expected retryable T2 state + attempt count/next-attempt (and store generation where applicable), and allow it only from `intent/ref_prepared/store_pushed` after the current retry budget is exhausted. Reserve ready-to-invalid transitions for current launch-delivery or gate authority. Add the interleaving test “old retry exhausts after another actor commits ready” and require ready to survive.

4. **The new shadow opportunity predicate excludes every state-only/gate target.** Section 2.6 now says the query admits only an executable target with committed `issue_delivery` and a dead/terminal writer. By design, a gate has neither an execution nor a delivery receipt, so A10/reconcile-state-only can never produce a shadow T5 verdict before enforcement. Make opportunity eligibility a discriminated union: executable targets require committed delivery plus recovery-relevant writer state; state-only/gate targets require `ready`, the exact current transition/holder/source receipt, and current gate authority, with no death or delivery requirement. Add a ready current gate case that produces exactly one `proposed` verdict and negative cases for superseded holder/source receipt.

5. **The advertised sweep-first T7 alias race is unreachable under the stated run-status transaction.** The sweep only creates a receipt for an already terminal run. If the terminate Phase-A transaction wins first, it creates the open receipt and the sweep merely adopts it; if the sweep has already inserted, the run was terminal before Phase A, so the current `active|held` terminate CAS cannot run. The plan nevertheless requires “sweep pre-creates -> later request aliases” without defining a terminal-run collect-only branch, while same-key false-to-true must still conflict. Specify the ordering explicitly: first replay/conflict-check the operator event and T7b alias; active/held runs use the existing atomic terminate+receipt path; an already terminal run may only attach a new true request to an existing open sweep receipt through a named collect-only adoption branch (or remove this promised API behavior). That branch must not rewrite run state, must preserve same-key false-to-true rejection, and needs tests for terminal-by-cascade/different-key versus terminal-by-same-key false request.

6. **Flag-OFF compatibility covers the rider/request path but not the new unconditional launch write path.** `workflow_resume` controls enforcement only, while W1-W10, baseline preparation, prepared-candidate persistence, marker handling, and the `issue_delivery` co-write run on every new DAG launch. A new checked-append conflict or evidence-preparation throw inside `fencedCommitWorkflowLaunch`/delivery repair can therefore change launch acknowledgement and HTTP/error ordering even with the flag off; O1 currently injects only rider failures. Define a compatibility failure contract for the write-only/shadow phase: resume-evidence failures must make that target explicitly non-recoverable and preserve the legacy launch outcome wherever the existing launch-owner/marker operation itself remains healthy. Add fault injection at baseline ensure, candidate preparation, delivery-event append, and initial/repair adoption across all three launch surfaces, asserting legacy session/owner/HTTP behavior under flag OFF. If any of those failures intentionally block legacy launch, narrow A17/O1 and rollout claims and justify the availability cost before implementation.
