# Design Review — plan.md (FLY-1707 E5) (Round 8)

Date: 2026-08-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 8 closes the conceptual per-writer-input hole and materially improves quarantine and takeover coverage, but the new V2 evidence path is not yet a complete crash-safe protocol. In particular, terminal fallback invalidation is inconsistent with the resolver contract, baseline and unavailable-sentinel outcomes are not mutually exclusive, and `issue_delivery` is not bound to the physical launch commit that could actually produce work.

## What's Good (Keep)

- The split between a run-level immutable baseline and writer-specific delivery evidence is the right model; it directly addresses the prior counterexample without weakening locked V2 semantics.
- `ensureWorkflowIssueBaselineTx` correctly adopts an existing well-formed winner without comparing later candidates, takes `runId` from trusted generalized execution context, and keeps ordinary launch compatibility explicit.
- The rename/copy distinction is now correct: `R*` deletes the source while `C*` retains it, and unknown type-2 prefixes fail closed.
- Restricting gitlink support to clean/staged pointer changes and refusing dirty submodule contents before teardown is an appropriately simple boundary.
- The close-runner takeover tests now protect both safety and observability: stale collectors must perform no destructive/success effects while still emitting exactly one authority-loss diagnostic.
- The broader design remains feasible with the current architecture: append-only run events, StateStore transactions, existing launch fences, CAS state machines, and GatePoller riders provide the needed primitives.

## Issues & Recommendations

1. **`input_fallback` is terminal in prose but retryable or unknown in the normative resolver contract.** Section 2.3 says fallback synchronously changes T2 to `invalid(input_fallback)`, while §2.2 and V1 say every non-`ready` state returns retryable `anchor_pending`; the canonical short-code union also omits `input_fallback`. The T2 state diagram does not define `ready -> invalid`, so a concurrent rider stamp can also race the new negative evidence. This can turn a terminally ineligible target into an endless retry or, depending on CAS ordering, resurrect it as ready. Add one exact-writer transaction helper that CASes any non-invalid state (including `ready`) to terminal `invalid`, make all stamp/progress CAS operations reject `invalid`, and bind the mutation to attachment/run/node/attempt/execution/activation. Resolver ordering must return stored `invalid_reason` for `invalid` and reserve `anchor_pending` for `intent/ref_prepared/store_pushed`; add `input_fallback` to the canonical registry (or deliberately map it to an existing canonical envelope code). Test fallback racing the rider from every T2 state and assert the result is never `ready` or `anchor_pending`.

2. **The run-level baseline and `issue_baseline_unavailable` sentinel are not schema- or transaction-mutually-exclusive.** They use different event UIDs, and the current `workflow_run_event` uniqueness plus `appendWorkflowRunEventCheckedTx` only arbitrates one identical `event_uid` (`StateStore.ts:16425-16436,31193-31231`). The plan requires `ensureWorkflowIssueBaselineTx` to notice a sentinel, but does not require the fallback writer to arbitrate against a concurrently committed baseline in the same transaction; both immutable events can therefore exist and different consumers can reach opposite conclusions. Model these outcomes as one logical slot, preferably one deterministic UID such as `issue_input_baseline:<runId>` with a discriminated `authoritative | unavailable` payload, and use a single transaction-local primitive for both writers. If the baseline wins, fallback invalidates only its target; if unavailable wins, later authoritative observations adopt the terminal outcome and cannot add a baseline. Add both concurrent commit orders, replay after restart, and malformed-existing-event tests.

3. **`issue_delivery` is keyed to a logical execution, not the physical launch that actually received authority to run.** The proposed payload has only node/attempt/execution and no event UID or selection rule. Current launch authority is finer-grained: `workflow_launch_owner` carries `owner_generation` and `delivery_attempt` (`StateStore.ts:17274-17290`), its token includes both (`:19286-19295`), and delivery repair can launch the same execution again with a higher attempt (`:21190-21216`). Prompt materialization also occurs before the adapter calls `commitWorkflowLaunch`, so a precommit-failed launch can leave a receipt even though its runner never started. Conversely, an older authoritative receipt can mask a later same-execution delivery with changed authoritative input; only fallback currently forces invalidation. Define a commit-bound delivery protocol: carry `{updatedAt, bodyDigest, sourceKind}` from hydration, prepare/check it before prompt continuation, then append the immutable receipt inside `fencedCommitWorkflowLaunch` or `commitWorkflowLaunchDeliveryRepair` under the exact activation + generation + delivery-attempt fence. Give it a deterministic per-physical-launch UID and define how V2 selects the committed receipt. Any non-frozen delivery that is fallback **or differs from the frozen baseline version/digest** must terminally invalidate the attachment before the prompt proceeds. Represent W10 explicitly as a `frozen_replay` kind bound to admission/source attachment rather than leaving an undefined exemption from the stated `kind=authoritative` predicate. Test an authoritative A launch followed by same-execution repair with B, receipt-written/precommit-failed repair, reverted Linear content, and consecutive frozen resumes.

4. **The normative T1 DDL still does not encode the claimed W1-only NULL-anchor form.** The carrier CHECK at §2.1 permits `anchor_commit IS NULL` for every `git_checkpoint` receipt kind, although the comment says only W1/start-reservation may use that form. This preserves the exact DDL/prose drift the normative rewrite was intended to eliminate and allows another W path to acquire an anchor later through T2. Restrict a NULL `anchor_commit` to the W1 `start_reservation` case in the CHECK, constrain `T2.resolved_anchor_commit` to a valid commit shape, and make the stamp helper reject every non-W1 attachment. Add schema-negative tests for a W2/W3 NULL anchor and positive tests for W1 pending and W1 resolved forms.

5. **Three smaller normative/test declarations remain internally inconsistent.** The quarantine matrix says “fifteen” and lists 15 cases, but the newly required clean-gitlink and dirty-submodule cases make 17 and are not in that list. T5's DDL comment says `opportunity_key` includes a generation, while §2.6 defines only `attachmentId:T2.state` and T2 has no such generation column. Finally, T5 says `verdict` comes from the canonical failure-code union but does not define the success value needed for shadow hit-rate reporting. Update the count/list, choose one opportunity-key projection, and define T5 verdict as an explicit success literal plus the canonical failure union.
