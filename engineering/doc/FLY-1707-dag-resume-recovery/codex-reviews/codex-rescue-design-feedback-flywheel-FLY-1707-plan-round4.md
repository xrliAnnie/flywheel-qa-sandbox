# Design Review — plan.md (FLY-1707 E5) (Round 4)

Date: 2026-08-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 4 closes most of the substantive direction from Round 3, and the design is now much closer to the project's authority, crash-recovery, and simplicity patterns. It is not yet implementation-ready because several accepted fixes are present only in later prose while the normative schema/state machine still says the opposite, and a few remaining races would break V0, A6/A10, A13, T7 request replay, or staged-work preservation.

## What's Good (Keep)

- Keep the typed-receipt approach and W10 option (a): sharing an already-validated immutable ref avoids introducing another SQLite×Git protocol during admission.
- Keep `runtime_semantics_digest` as a versioned identity-free projection and replay the frozen projection without calling the live dispatch resolver.
- Keep the full state-only predicate, including S3 and the gate-form V5 authority check, and keep the rule that no gate execution is minted.
- Keep create-only store push with same-value adoption, dual-carrier recovery ordering, and the expanded crash/race matrix.
- Keep mutation fences immediately adjacent to irreversible land effects and the await-boundary mutation tests.
- Keep the intended two-snapshot quarantine chain, untracked-file expansion, bounded capture, and post-GC reachability tests.
- Keep T7's partial unique index plus collector owner/generation/lease, transaction-local live-session target set, and the explicit distinction between in-progress and responded replay.
- Keep shadow entirely off the request path, the single registered enforcement flag, explicit operator-only cascade authority, T6 TTL convergence, `held` precedence, and rebase sequencing after FLY-1772.

## Issues & Recommendations

1. **[BLOCKER] The normative SQL and resolver contract still contain the Round 3 forms that the later prose says were replaced.** T3's displayed SQL has no per-action `CHECK` and is followed by an explicit “application-layer CHECK” comment; T4 is still documented as universally requiring launch evidence; the carrier invariant still rejects W1's NULL T1 anchor; V3 still compares the old whole-row `runtime_digest`; and §2.6's claimed closed reason list still omits the newly added codes. An implementer following §2.1/§2.3 would therefore build a different protocol from §2.5/§7. **Fix:** make the displayed DDL authoritative: add the SQL action-union CHECK, model the discriminated T4 proof, encode the effective-anchor union, and define `effectiveRuntimeSemanticsDigest = T1.runtime_semantics_digest ?? T2.runtime_semantics_stamped` with the exact versioned projection. Replace the old V3 text and update the single canonical reason union in §2.6 rather than appending corrections only in acceptance prose. Also either add the claimed W10 parent FK to T2 or state explicitly that T3's source/result pair is the sole parent relation.

2. **[BLOCKER] V0's typed receipt union still does not cover every authority-changing W path and does not bind mutable receipt payloads.** The union enumerates W1/W2/W3/W4/W5/W7/W10 but omits W8 and W9 even though their inventory rows can change `current_node_id`. The source already gives W8 an immutable-identity `execution_admitted` event, while W9 has operation-specific ledger events; the plan must either map those or prove/remove the exempt paths. In addition, current `workflow_rework_request` and `workflow_rework_route_revision` tables have no no-update/no-delete triggers, so calling their rows “immutable receipts” is stronger than the schema. **Fix:** give every attachment an explicit `receipt_kind` and frozen `receipt_digest`, define W8/W9 UIDs and canonical receipt projections (or delete W9 after proving engine-owned batches cannot move the frontier), and make V0 compare both identity and digest. Add append-only triggers to the reused authority rows where jurisdiction permits, or rely on an immutable run-event receipt instead. The inventory mutation test must fail separately for missing receipt mapping, changed receipt payload, and missing attachment co-write.

3. **[BLOCKER] The state-only S3/redrive lifecycle has no coherent durable state model or fresh enforcement observation.** W6 and the T2 diagram still say a state-only attachment is `ready` immediately, while V2 says it may become ready only after the rider fetches and stamps S3. `resolveWorkflowResumeTarget(store, {runId, requestedEntry?, env})` also has no Linear observation/client input, so it cannot compare the frozen issue digest with a fresh issue body at enforcement time; stamping once is not enough to detect A6. Finally, the “redrive request with generation” and its ack are not represented in T3/T4 or another named receipt. The existing `workflow_carrier_redrive_receipt` applies to approved carrier delivery, not an unapproved founder gate waiting in A10. **Fix:** let state-only attachments start in an explicit pending state and transition to `ready` only after all S1–S3 stamps. Define an async, fail-closed fresh-envelope observation passed into the resolver/admission (with the DB sources rechecked transaction-locally). Persist the gate redrive generation in T3 or a named existing ledger, define the tick's immutable ack event/row and its CAS, and make T4 reference that exact ack. Add tests for Linear unavailable/changed between stamp and admission, crash before/after stamp, and crash before/after redrive ack.

4. **[HIGH] The carrier loss and retention text remains internally contradictory, and literal reference counting never frees a normal ref.** After correctly stating that every ready local miss adopts from the store first, §2.2 still says a ready ref that disappears is terminal invalid. It also alternates between “no attachment row references the ref,” “no current attachment references it,” and “ready refs are never cleared.” Because T1 is append-only, every valid ref remains referenced by at least one historical attachment forever, so the advertised 90-day cleanup cannot reclaim checkpoint-store objects. **Fix:** retain the adopt-first rule as the only loss rule and remove the stale terminal sentence. Define liveness for retention (for example current attachment or non-retired T2 reference), add a durable release/tombstone or a transactionally derived terminal/non-current criterion, and delete local/store refs only with expected-old CAS after 90 days. W10 shared refs must remain while any live child/source reference exists. Test a completed run, an active run with a superseded attachment, a W10 shared chain, and cleanup racing admission.

5. **[BLOCKER] The land-effect predicate is at the right call sites but still binds too little authority to make the A16 test pass.** Section 2.3bis defines the land predicate as only “current land operation + claim generation.” A holder can be superseded or a resume admitted while that operation row and generation remain unchanged, so rechecking only those fields immediately before `triggerCool`/finalize still permits the stale effect. The current executor's early authorization checks the holder/head, but that is exactly the check invalidated across later awaits. **Fix:** define the effect-time predicate as the conjunction of current run/target, current gate holder/question/head/source receipt, approved PR binding/claims, and land-operation owner/generation/lease. Re-evaluate that complete projection immediately before each irreversible call after the preceding await. Mutation tests should prove that changing each constituent independently prevents the external call, not merely causes the later receipt write to fail.

6. **[BLOCKER] The quarantine prose still applies worktree deltas before writing the index snapshot.** Its numbered order copies staged blobs, then hashes/applies unstaged files, and only afterward says to `write-tree` the index-state commit. At that point a staged/worktree-divergent path has already been overwritten, so the first commit is not the staged snapshot despite the intended two-commit chain. **Fix:** specify two explicit phases: seed from `suffixHead`, apply only staged deltas/deletions, write `indexTree` and `indexCommit`; then seed a second temporary index from `indexTree`, apply only unstaged/untracked deltas/deletions, and write `worktreeCommit` parented by `indexCommit`. Point the quarantine ref to the latter. Count staged blob sizes with `cat-file` as well as worktree bytes, and include staged-delete-plus-worktree-recreate in the post-GC content assertions.

7. **[BLOCKER] T7 still has no stable request-to-receipt identity when the sweep wins, and lease expiry alone can overlap destructive collectors.** The request receipt key is `<runId>:<clientRequestId>`, but the sweep uses `sweep:<runId>:<epoch>`. If the sweep inserts immediately before Phase A, the partial unique index prevents the request row; merely “adopting” the sweep row does not persist the client's request digest/key. After the sweep row responds, the same client key can no longer replay that exact response and may create a new collect-only receipt. Also, a slow but live collector can lose its lease while inside `closeRunner`, allowing takeover and concurrent closure before the stale outcome CAS is rejected. **Fix:** use one canonical receipt identity per terminal run episode and durably map every client request/digest to it (the existing operator event can carry this mapping), or add an explicit immutable alias relation. Define lease renewal before each close, a lease duration exceeding the bounded close operation, and takeover fencing that prevents overlapping live owners; exact `closeRunner` idempotency remains the crash-after-effect safeguard. Extend the sweep-preinsert test through first response, responded replay with the original client key, process restart, and a deliberately slow close crossing the nominal lease.

8. **[HIGH] The marker-free shadow rider has no durable opportunity key, dedupe, or fair cursor, and one claimed source does not exist.** T5 stores run/node/attempt but not attachment ID, transition UID, T2 generation/state, or a unique opportunity key. A `LIMIT 3` scan can therefore reprobe the same three active runs forever, starve the rest, or fail to reprobe an attachment that moves from pending to ready. The current `runs-route.ts` emits 409 HTTP responses but does not append the claimed durable “start-route 409 events.” **Fix:** drive shadow from real attachment/T2 identities only (or explicitly add a durable route event), persist `opportunity_key = attachmentId + state/generation` in T5 with a uniqueness constraint, and query unprobed current opportunities by keyset order. Add restart, pending-to-ready, more-than-three-run fairness, T5-retention, and mutation tests proving rider failures cannot affect runs/start.
