# Design Review — plan.md (FLY-1707 E5) (Round 12)

Date: 2026-08-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

The rewrite remains feasible in the current architecture, and all six Round 11 corrections are present in the normative plan; the T3 action-union constraints also behave correctly under representative SQLite inserts. Four remaining crash/concurrency contracts are still ambiguous or incorrect, however, and two can manufacture evidence for an uncommitted repair or roll back a healthy legacy launch, so this is not implementation-ready yet.

## What's Good (Keep)

- T3 now makes `frozen_s3_body` part of the actual SQL action union, measures the UTF-8 byte size through the BLOB cast, and has the right negative-schema-test contract. The canonical reason union includes `frozen_input_too_large`.
- Keeping the launch marker byte-compatible is the simpler migration. A checked `issue_delivery_prepared` event at the post-hydration seam is a credible way to bridge Blueprint's late candidate discovery to marker-first recovery without expanding the filesystem protocol.
- The invalidation authority is now discriminated and the reconciler can no longer invalidate `ready`; launch/gate authority retains the only legitimate `ready -> invalid` paths.
- Shadow eligibility is correctly discriminated: executable targets wait for physical delivery plus writer death, while gate targets use current holder/source authority and do not invent a runner or death prerequisite.
- The terminal-run collect-only branch is the right architectural correction, and replay/conflict checking before run-status dispatch preserves false-to-true rejection.
- The plan now treats baseline/prepared/delivery writes as always-on fleet-wide launch changes and assigns fault injection across all three launch surfaces. That is the right blast-radius lens even though the transaction behavior needs one more specification pass.
- The broader design still aligns well with house patterns: append-only receipts, checked event replay, CAS ownership, GatePoller riders rather than new timers, one registered opt-in flag, fail-closed V0-V5 resolution, and no fallback to template head.

## Issues & Recommendations

1. **The prepared-event adoption contract does not disambiguate an old marker from the currently claimed repair attempt.** Current `recoverOrAcquireWorkflowLaunch` explicitly accepts `marker.deliveryAttempt === owner.delivery_attempt - 1` while the owner is `repairing` (`StateStore.ts:20338-20351`), then returns the current owner's attempt/token. Counterexample: repair attempt N appends `issue_delivery_prepared:N`, crashes before writing marker N, and leaves marker N-1 on disk. If the new adoption code keys from the current owner/result rather than the four marker fields, it can mint `issue_delivery:N` even though physical attempt N never crossed the marker boundary. **Fix:** make the normative lookup key the tuple read from the accepted marker, not the current owner tuple. In the `markerIsExpectedPriorRepair` branch, only dedupe/repair evidence for N-1 and never consume the prepared event for N; the repair remains eligible for the existing re-drive flow. Add an initial/repair matrix case that prepares N while marker N-1 remains and asserts zero receipt for N, followed by a case where marker N is present and exactly N is committed. Also state that the frozen-replay receipt's admission/source binding is reconstructed and verified from the marker execution's immutable T3 row before append.

2. **R11-6 states the flag-OFF compatibility result but not the transaction rule needed to achieve it.** Both launch commit functions write the filesystem marker inside an SQLite transaction before the owner update (`StateStore.ts:21259-21292`, `21317-21370`). `appendWorkflowRunEventCheckedTx` throws on an event UID/payload conflict (`:31193-31230`); if the new delivery append is allowed to escape, SQLite rolls back the owner mutation while the marker remains, and marker adoption can repeat the same conflict. That directly violates the new promise that an evidence-only conflict cannot change a healthy legacy launch. **Fix:** define a non-throwing evidence outcome inside initial commit, repair commit, and marker adoption: exact event replay/appending yields evidence; an evidence-domain conflict atomically commits the legacy owner transition while marking the target non-recoverable with a distinct durable receipt/T2 invalidation; only failures that also make the underlying StateStore/marker operation unhealthy retain legacy failure behavior. Preserve the receipt-if-and-only-if-physical-commit invariant for successful evidence. Add a real pre-existing conflicting `issue_delivery:<tuple>` test (not only a mocked throw) for all three surfaces and both initial/repair/adoption paths, asserting owner/session/HTTP compatibility and no false delivery receipt. Expand S2's slice row to name this preparation/commit/adoption protocol explicitly before S3 consumes it.

3. **The reconciler's “exact CAS” still does not fence partial T2 progress.** Its expected tuple is only `(state, attempt_count, next_attempt_at)`, while `resolved_anchor_commit`, `store_locator`, `envelope_stamped_json`, and `runtime_semantics_stamped` can change without necessarily changing those three values or reaching `ready`. For example, a stale exhausted worker can snapshot an `intent` row, the launch side can stamp the W1 resolved anchor while leaving it `intent`, and the stale invalidation still matches and destroys useful progress. The existing “other actor commits ready” test misses this case. **Fix:** add a monotonic T2 `revision` (or an equivalently collision-proof full-row CAS token), increment it on every T2 mutation, and require `expectedRevision` in reconciler invalidation in addition to the current predicates and a transaction-local readiness recheck. Test stale invalidation after each partial stamp—W1 anchor, store locator/generation, S3, and runtime—not only after the terminal `ready` transition.

4. **The terminal collect-only episode rule excludes the first episode and stale text still contradicts the new status split.** Section 4 says a terminal request may create a receipt only when there is no open receipt and “the previous one responded.” A run terminated by cascade before the first sweep tick has neither an open nor a previous receipt, so the literal branch cannot serve the advertised `terminal-by-cascade + new key` case. The preceding Phase A/Phase B bullets also still say an active/held terminate transaction may adopt a sweep-created open receipt, despite the new text correctly proving that state combination unreachable. **Fix:** normalize the single rule: active/held Phase A always creates episode 0/current N atomically; terminal collect-only adopts an open receipt, otherwise creates N when no receipt exists or the latest receipt is `responded`. Remove the unreachable sweep-adoption claims from Phase A/Phase B and add an explicit terminal-by-cascade-before-first-sweep test plus no-history/concurrent-first-request coverage.
