# Design Review — plan.md (FLY-1707 E5) (Round 2)

Date: 2026-08-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 2 materially addresses all eight Round 1 findings and the design remains feasible on the current architecture, but it is not yet implementable without correctness gaps. The remaining blockers are concentrated in the core recovery contract: the resume operation itself is absent from the attachment lineage, state-only/gate recovery does not fit the execution-replacement admission, V1/V3 are still incomplete, the authority fence omits real non-execution consumers, and T7 does not actually provide run-level collector exclusion.

## What's Good (Keep)

- Preserves every founder-locked semantic: recover only the current step, quarantine and rerun half-done work, no template-head fallback, no per-node cache, no `completed → running`, and no inflated savings claim.
- The new `commitAuthoritativeTargetChangeTx` direction, W7/W8 audit, explicit non-recoverable receipt, mutation guard, and CAS upgrade are the right way to keep attachments subordinate to the existing frontier.
- T2 now has durable pending/ready/invalid stages and a GatePoller forward reconciler; pending is correctly distinguished from terminal invalid, with no new timer.
- The route-key ordering is now correct: explicit resume is parsed before the original-start key guard, has a separate idempotency namespace, and freezes resume fields into authority digests.
- T6 makes close cascade explicit opt-in, keeps automated `closeRunner` callers byte-compatible, rechecks all cascade predicates in one StateStore transaction, and correctly lets `held` win.
- T7's frozen/collecting/collected/responded direction, per-execution outcomes, response cache, observe-before-act rollout, and crash matrix are the right durability shape even though the ownership key still needs correction.
- Quarantine now uses temporary-index plumbing, no filters, safe config, bounds, create-only refs, and adversarial tests; the corrected active template IDs, one registered flag, and rebase-after-FLY-1772 sequencing should remain.

## Issues & Recommendations

1. **BLOCKER — `admitWorkflowResume` is itself an unlisted authoritative target change, so a successful first resume makes a second resume diverge.** T1 binds an attachment to one `target_attempt` and T3 explicitly records that attachment as the superseded old attempt while minting `new_attempt`/`new_execution_id` (`plan.md:74-89,114-127`). Section 2.5 then advances the current attempt, but W1-W9 contain no resume-admission writer and no child attachment (`plan.md:149-163,227-229`). After admission, V0 sees the new max attempt while the cited attachment still names the old one; W8's admission-time consistency assertion will either reject the new launch or the next crash will return `attachment_frontier_divergence`. **Fix:** add resume admission itself as W10 and co-write a child/current attachment in the admission transaction, with a deterministic `resume_replacement:<admissionKey>` lineage that inherits the validated anchor/envelope but binds the new attempt/writer. T3 should distinguish `source_attachment_id` from `result_attachment_id`; test two and three consecutive crashes/resumes, including response loss after each co-write.

2. **BLOCKER — the carrier union is not carried through admission: executable initial nodes are mislabeled state-only, while gate targets cannot use the mandatory replacement shape.** W1 marks every fresh start `state_only_checkpoint` merely because no Git product exists yet (`plan.md:153`), but the locked V4 contract reserves state-only for nodes that do not need a worktree. `materializeWorkflowRun` has no start-point/runtime input (`StateStore.ts:18448-18496`); those facts are resolved later, so an executable first node cannot be ready-on-write and cannot rebuild half-done work. At the other end, a gate target is stored as `workflow_run_node.state='review'` with no execution (`StateStore.ts:30831-30847`), and `admitGeneralizedWorkflowExecution` explicitly rejects `node.type === 'gate'` (`:23813-23819`), while T3 and §2.5 always require a new attempt/execution/dispatch. That makes A10's “continue waiting at the unapproved gate” impossible. **Fix:** make resume admission a strict action union: `redispatch_execution` mints an attempt/execution only after a Git attachment has been completed from the original continuity start point, while `reconcile_state_only` keeps the same gate attempt, mints no execution, and re-drives the exact current holder/delivery. Add a post-continuity attachment writer/stage for W1 instead of marking executable roots ready state-only; update T3 CHECKs and A10 to prove zero QA rerun and zero synthetic gate runner.

3. **BLOCKER — V3 still omits two founder-approved validity fields and can silently change the resumed model.** The PRD requires the actual dispatch/runtime digest and rework authority-context digest in addition to the pinned snapshot and resolved node. T1/V3 currently store/check only `snapshot_digest` and `resolved_node_digest` (`plan.md:84-86,192`). This is not equivalent on this branch: `resolveNodeDispatchAtLaunch` intentionally reads the current published template for unpinned nodes (`workflow-dispatch-resolution.ts:48-107`), and admission persists that live choice in `workflow_execution_runtime` (`StateStore.ts:23982-24014`). A resumed attempt can therefore use a different vendor/model/effort while V3 still passes; rework context can likewise change without a bound digest. **Fix:** bind a canonical digest of the original immutable runtime row and the applicable `workflow_rework_request.authority_context_digest` (or an explicit `none`) into the ready attachment. Resume dispatch must replay the frozen runtime rather than call the live resolver; facts unavailable before original admission keep the attachment pending/non-recoverable until stamped. Add mutations for live template/config and authority context that prove same-run semantics stay frozen without comparing against the current published template.

4. **BLOCKER — the protected ref is durable only inside one repository, so A4's “new clone” case cannot pass.** T2 creates `refs/flywheel/checkpoints/...` with local `git update-ref` and a ready ref that later disappears is terminal invalid (`plan.md:168-179`). That ref survives `git gc` in the same object database, but a different clone does not receive local custom refs or an unpushed half-done object. `WorktreeManager.create` resolves `startPoint` only in the selected main repository (`WorktreeManager.ts:535-575`), and the cited CAS precedent is likewise a local ref (`workflow-docs-git.ts:87,176-189`). **Fix:** choose one real durable carrier allowed by V1—e.g. an allowlisted remote checkpoint ref with exact push/fetch CAS and refspec, or a Bridge-owned portable bare checkpoint store—and persist its locator plus generation. On a fresh clone, materialize/adopt the local ref from that carrier before `ready`; test an unpushed commit with the original repository removed, not merely a second worktree sharing its object database.

5. **BLOCKER — the universal execution-writer predicate is neither valid for gate authority nor exhaustive for A16.** `assertCurrentWorkflowWriterTx` requires an execution-bound row in `{pending,admitted,running}` (`plan.md:202`), but legitimate gate transitions use the `review` row plus an exact `workflow_gate_holder` and deliberately bypass `current.execution_id` (`StateStore.ts:30223-30253`). Applying the proposed predicate literally breaks founder approval/kickback. Conversely, the six listed receivers omit `applyWorkflowSourceEvent`, which writes the permanent founder claim and receipt, marks the holder approved, and can complete the run or create a carrier delivery without calling the execution decision receiver (`StateStore.ts:31797-31844,32202-32378`). A16 mutation tests state the desired result but provide no fence for these consumers or for land-operation effects. **Fix:** use a discriminated transaction-local authority predicate: execution writers bind run/node/attempt/execution/activation/generation; gate authority binds current run/gate attempt/question/head/holder state and source receipt; land effects bind the current land operation and claim generation. Wire the latter predicates before any claim/holder/carrier/terminal/land mutation, retain the six execution surfaces, and mutate every real approval/land consumer—not only attachment fields.

6. **BLOCKER — T7's “same-row CAS” does not exclude request and sweep collectors, and its frozen set assumption is false against the cited API.** Request receipts use `<runId>:<clientRequestId>`, sweep receipts use `sweep:<runId>:<epoch>`, and collect-only calls may create later keys (`plan.md:264-266`); CAS on different rows offers no mutual exclusion, so a sweep can mint one row while a request owns another. Also `listRunAttributedExecutions` returns every historical ID from run nodes, side-effect ledger, and bindings with no session-status filter (`StateStore.ts:24613-24627`), not the asserted live set, and the existing operator replay receipt does not freeze `collectExecutions`. **Fix:** enforce one open collector per run with a partial unique index (or a separate run-level claim row); the sweep must adopt that open receipt rather than mint a competing key. Freeze an explicit ordered target list/digest from a transaction-local live-session query, include `collectExecutions` and the frozen digest in request conflict/replay semantics, and make later residue create a new receipt only after the prior one is terminal. Add the race where sweep inserts immediately before Phase A, plus false→true replay of the same client request ID.

7. **HIGH — the quarantine plumbing still does not specify how the promised staged-only and symlink cases are preserved safely.** A temporary `GIT_INDEX_FILE` plus `hash-object --no-filters` does not itself construct a tree (`plan.md:219-222`): a staged-only blob may differ from the working-tree file, deletions and modes must be represented, and hashing a symlink path as a normal file can follow the target rather than store mode `120000` plus link text. The existing precedent first `read-tree`s the base into the temporary index before explicit updates and `write-tree` (`workflow-docs-git.ts:95-104`). **Fix:** specify the complete mode-aware algorithm: seed from `suffixHead`, parse a NUL-delimited staged/worktree delta, copy staged blobs from the live index without modifying it, hash only selected worktree bytes, handle deletions and symlink text explicitly, then `write-tree` and parent the commit. Add staged-vs-worktree divergence and staged deletion to the existing eight-case contract.

8. **HIGH — O1 asks an inline DB/Git shadow probe to have byte-identical launch latency, which is not a testable or achievable compatibility contract.** The probe is inserted at the runs/start block entry and writes T5 (`plan.md:233`), yet O1 injects a Git timeout/DB failure there and demands byte-identical launch latency (`:294`). Exception isolation can preserve HTTP bytes and error order, but awaited or synchronous I/O necessarily changes latency and a timeout changes it materially. **Fix:** move flag-OFF shadow work entirely off the request path—prefer a GatePoller rider over another scheduler—or define a structural contract of zero awaited/external I/O before response plus a measured latency budget. Keep the fault injection for HTTP bytes/error ordering and add a sentinel proving the legacy launch is committed before any shadow failure can run.

## Verdict

CHANGES REQUESTED — address items above
