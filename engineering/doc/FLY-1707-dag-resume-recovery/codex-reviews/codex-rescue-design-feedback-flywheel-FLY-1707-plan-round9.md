# Design Review — plan.md (FLY-1707 E5) (Round 9)

Date: 2026-08-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 9 correctly lands the single baseline slot, W1-only NULL-anchor DDL, T5 projection, and most of the absorbing-invalid model. However, the reviewed file still contains the old execution-level `issue_delivery` contract rather than the accepted physical-launch protocol, and source tracing exposes unhandled marker-recovery, stale-launch, and state-only branches. The design remains feasible, but these are authority and crash-consistency gaps on the core recovery predicate.

## What's Good (Keep)

- `issue_input_baseline:<runId>` is now one discriminated immutable slot, so authoritative and unavailable outcomes are physically mutually exclusive under the existing global `event_uid` uniqueness.
- `invalidateResumeAttachmentTx` establishes the right absorbing-state direction: a terminal negative result can invalidate `ready`, and ordinary progress CAS operations cannot resurrect it.
- The T1 CHECK now rejects NULL anchors for non-W1 git attachments, while T2 constrains the resolved W1 anchor and assigns stamping to a W1-only helper.
- T5 now has one unambiguous opportunity-key projection and an explicit success literal, which makes shadow cursor behavior and reporting implementable.
- The quarantine contract now explicitly accounts for clean gitlinks and dirty submodules while preserving the fail-closed/no-destruction boundary.
- The existing launch-owner generation, delivery-attempt token, marker recovery, append-only event, and gate-authority primitives are sufficient to implement the remaining fixes without adding another timer or broad subsystem.

## Issues & Recommendations

1. **The accepted physical-launch `issue_delivery` rewrite is not present in the review subject.** Section 2.3(②) still says to append `issue_delivery{node,attempt,execution,kind,bodyDigest}` at prompt materialization, requires only `kind=authoritative`, and describes W10 as a “constructive exemption.” The file contains no `sourceKind`, `frozen_replay`, deterministic `issue_delivery:<executionId>:<generation>:<deliveryAttempt>` UID, activation/generation/delivery-attempt binding, latest-committed selection rule, or co-write in `fencedCommitWorkflowLaunch` / `commitWorkflowLaunchDeliveryRepair`; its tests are also the old three cases. Therefore R8-3—the central Round 8 blocker—has not actually been folded into the normative plan. Replace the old paragraph with the complete physical-launch protocol from the Round 9 change description, including `{updatedAt, bodyDigest}` comparison, explicit `frozen_replay` admission/source binding, deterministic UID, exact selection rule, both commit functions, and the full stated negative/crash test matrix.

2. **Appending the delivery receipt only in the two commit functions does not close the existing marker-first crash path.** Both launch commit functions write/read back the filesystem marker before their SQLite transaction is durably committed (`StateStore.ts:21259-21292,21317-21371`). A crash after marker rename but before DB commit leaves the marker while rolling back owner state and any event append. On restart, `recoverOrAcquireWorkflowLaunch` recognizes that marker and repairs/returns `status:'committed'` directly (`:20328-20377`), bypassing both commit functions; the marker currently contains only execution/generation/deliveryAttempt/token, so it cannot reconstruct the proposed input receipt. Persist a content-addressed delivery candidate before the marker boundary, or version the marker to carry an authenticated candidate digest/source tuple, then require marker adoption to validate it and co-write the exact `issue_delivery` receipt while repairing owner state. Cover initial launch and delivery repair at: candidate prepared, marker written, SQLite owner/event commit, and response return. Every recovery must produce either no acknowledged launch or one matching committed receipt—never an acknowledged launch with missing/ambiguous V2 evidence.

3. **The terminal-invalid resolver correction is only partially propagated.** The new §2.1 text gives the correct ordering, but the later §2.2 carrier rule still says every state not yet `ready` becomes `anchor_pending`, and the V1 table likewise maps all “未 ready” states to `anchor_pending`. More concretely, the canonical short-code union still omits the newly introduced `input_fallback`, despite the Round 9 claim that it was added. This leaves two competing normative implementations and violates the single-registry requirement. Update both stale passages to distinguish `invalid` from the three retryable states, add `input_fallback` to the union (or intentionally map it to a listed envelope code), and make resolver parsing fail closed if an invalid row has a NULL or unregistered reason. Prefer a T2 CHECK tying `state='invalid'` to a non-NULL `invalid_reason`, plus negative schema/resolver tests.

4. **Delivery-triggered invalidation is fenced to the logical writer but not to the physical launch producing the observation.** `invalidateResumeAttachmentTx` binds execution and activation, while the accepted delivery protocol recognizes that the same execution/activation can have multiple owner generations or delivery attempts. A stale precommit launch can therefore observe fallback or changed input and terminally poison T2 even after a newer physical launch has acquired authority; its later launch commit would be rejected, but `invalid` is already absorbing. For delivery-caused reasons, extend the invalidation authority with owner identity/generation/deliveryAttempt (or the exact launch token) and verify the live launch-owner lease/cancellation fence in the same transaction. Test an old generation reporting fallback after takeover: it must perform zero T2 mutation, while the current physical launch must still be able to invalidate.

5. **V2 and invalidation still lack a state-only/gate authority branch.** Gate targets are materialized as `workflow_run_node(state='review')` with no execution (`StateStore.ts:30831-30837`), and generalized admission deliberately rejects gate nodes (`:23813-23818`). Such a target can neither possess the target-writer physical `issue_delivery` demanded by §2.3 nor call an invalidation helper that requires execution/activation, so `reconcile_state_only` cannot satisfy its advertised full V2 contract or converge retry exhaustion to `invalid`. Define a discriminated proof/authority union: executable targets use the latest committed physical-launch receipt; state-only gates use the immutable baseline + fresh observation + exact transition/source-holder receipt and gate authority, with no synthetic runner or target delivery. Likewise provide a target/gate-authority invalidation form for reconciler failures. For a true state-only W1 root, either bind an authoritative start observation at W1 or mark it explicitly non-recoverable—do not let the rider invent a historical baseline. Add A10 tests for an ordinary entered gate, a gate invalidation, and the root state-only policy.
