# Design Review — plan.md (FLY-1707 E5) (Round 1)

Date: 2026-08-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

The plan has the right product semantics and is broadly feasible on the current architecture, but it is not yet safe to implement. The blocking gaps are the absence of a mutation-time writer fence, incomplete attachment/ref crash recovery, an unreachable resume-key route, and non-durable force-cancel/close-cascade protocols; as written, A10, A11, and A13 cannot be proven.

## What's Good (Keep)

- Keeps the founder-locked shape: resume only the current authoritative step, quarantine half-done work, never silently fall back to template head, and preserve the 4.1h caveat.
- Correctly chooses Path A (same run plus a separate resume admission), keeps `workflow_start_reservation` immutable, and does not reopen `completed → running`.
- Attaches recovery evidence to the existing run target instead of inventing a second frontier, preserves pinned-snapshot semantics, and treats unknown probes as fail-closed.
- Explicitly rejects reuse of founder approvals, land effects, and fail verdicts; preserves gate-wait as a recoverable target without equating that with approval reuse.
- Uses one registered opt-in flag, existing GatePoller riders instead of new timers, normalized short reasons plus structured detail, and an observable ledger.
- The FLY-1770/FLY-1772 jurisdiction table and rebase-after-1772 sequencing are directionally correct.

## Issues & Recommendations

1. **BLOCKER — V5 is still admission-time prose, not a mutation-time writer fence.** The plan marks the old attempt `superseded`, but current completion admission only checks that the old `(run,node,attempt)` row still names the old execution (`StateStore.ts:29084-29090`), and `commitWorkflowTransitionTx` rejects only `state === 'done'`, not `superseded`, while checking only `current_node_id`, not the current attempt/generation (`:30248-30255`). For a same-node resume, a delayed old actor can therefore submit the first completion for the superseded attempt after the new actor starts; the dispatcher also checks only latest ordinal + row execution (`workflow-engine-dispatcher.ts:316-341`), and `admitGeneralizedWorkflowExecution` can rewrite `current_node_id` without an exact-target CAS (`StateStore.ts:24073-24079`). **Fix:** define one transaction-local `isCurrentWorkflowWriterTx` predicate/fencing token bound to exact run/node/attempt/execution/activation (and resume admission/generation), use it at every authority-bearing mutation receiver—output, completion, decision, transition, PR/gate binding, launch/dispatch—and atomically revoke old TURN/launch/credentials when admitting the replacement. Add negative tests in which the old actor submits output, completion, verdict, push/PR evidence, and launch commit after the new admission; every one must fail without writing authority.

2. **BLOCKER — W1–W6 do not cover all real frontier/writer changes, so the attachment can diverge immediately.** `appendWorkflowReworkRouteRevision` supersedes the prior reservation and changes `workflow_run.current_node_id` in one transaction (`StateStore.ts:23525-23552`); the founder-feedback path calls it after `commitWorkflowTransitionTx` (`:32134-32156`). W2 would attach to the preliminary transition target, then this second writer can move the frontier with no co-written attachment. Dead-exec and rework replacement also change the current writer while often retaining the same node/attempt, but T1 does not bind execution/activation/generation and the plan does not define their synthetic transition identities precisely. **Fix:** inventory every production write to `current_node_id`, target reservation, preferred actor, and launch owner, then route all authoritative target/writer changes through one transaction helper that either co-writes an exact attachment or an explicit non-recoverable receipt. Include `appendWorkflowReworkRouteRevision`, `openOperatorRework`, both replacement paths, generalized admission, and any engine-owned `applyWorkflowLedgerBatch` path; mutation tests must fail when any one co-write is removed.

3. **BLOCKER — the SQLite×git/envelope protocol has no durable forward reconciler and does not cover gate/wake targets.** Section 2.2 commits the attachment first, prepares the ref later in the dispatcher, declares a missing ref permanently invalid (“not later auto-fill”), and only reconciles stale-ref deletion. A crash after SQLite commit but before `update-ref` strands the target; moreover gate W6 has no dispatcher launch, and a rework wake can bypass fresh dispatch, so their issue-envelope stamp/ref producer may never run. In particular, a gate attachment remains unstamped and A10 fails, while the stated A13 crash replay has no stage/owner that can finish it. **Fix:** add a single durable prepare/adopt state machine (prefer reusing the side-effect ledger/event machinery) covering attachment intent → ref create/adopt+verify → envelope stamp → writer fence → worktree rebuild → launch committed → response recorded. Its reconciler must service fresh dispatch, wake, and state-only gate targets, adopt either side of every SQLite/git crash, and distinguish retryable pending from terminal invalid. Specify response-loss replay and ref-orphan cleanup for every crash point, not only ref deletion.

4. **BLOCKER — the proposed `resume` request cannot reach the new admission branch with its required new key.** The current route rejects any explicit key different from the original `workflow_start_reservation.idempotency_key` at `runs-route.ts:1715-1732`, before the successor-session 409 at `:1734-1751`. Section 2.6 only says to insert resume handling before the successor 409, while also requiring a new mandatory admission key, so every legitimate resume request is rejected as `WORKFLOW_RUN_KEY_MISMATCH`. **Fix:** parse and authenticate explicit `resume:true` before the original-start key guard; route its key exclusively to `workflow_resume_admission`, while preserving the existing key guard byte-for-byte for non-resume replay. Also freeze the resume fields into the route/admission digest so the normal route-decision layer cannot claim or reinterpret the new key.

5. **BLOCKER — force-cancel has no durable collection idempotency or response receipt.** Existing terminate idempotency records only the Phase-A run-state request and replays `{status,idempotentReplay}` (`StateStore.ts:24831-24861`; HTTP response `runs-route.ts:504-509`). The plan promises cached per-execution Phase-B results and a new-key “collect-only” mode, but defines no request stage, target-set digest, per-execution claim/result, or response cache. A crash after freezing the run (or midway through closes) can therefore replay with different/unknown results while the sweep races the request. **Fix:** define a durable `frozen → collecting → collected/responded` receipt, with a frozen attributed-execution-set digest (or explicitly monotonic remaining-set semantics), idempotent per-execution outcomes, claim fencing shared with the sweep, and byte-identical response replay. Test crash before Phase B, between every execution, after collection before response, concurrent same/different keys, and repeated collect-only calls.

6. **BLOCKER — the close cascade is neither scoped nor atomic and conflicts with the FLY-1770 held contract.** `closeRunner` is a shared teardown primitive used by explicit endpoints, stale-terminal cleanup, parked-phase reclaim (`plugin.ts:6403-6459`), rework supersession (`:8448-8458`), post-ship finalization, and other automation. Unconditionally writing an “operator close intent” and cascading from this chokepoint can turn routine cleanup into run termination; an append-only intent written before FSM/kill with no completion stage also becomes a permanent dead-exec veto if the process crashes. Finally, the three “last carrier” reads occur outside the run-state CAS, so a dispatch/rework can appear between the check and terminate, and the plan explicitly continues from `held` even though current terminate accepts `active|held` (`StateStore.ts:24867-24872`) and FLY-1770 defines held as a human terminal state. **Fix:** require an explicit run-close authority option at selected callers (default no cascade), record prepared/committed/failed close-effect stages, and perform one StateStore transaction that rechecks exact current execution/lifecycle evidence, other live carriers, pending dispatch/rework, and `status='active'` before terminating. If held wins, stop—do not overwrite it. Add crash tests around intent/FSM/kill/CommDB/finalization and race tests that insert a second carrier, dispatch intent, rework delivery, or held transition at every boundary.

7. **HIGH — quarantine currently mutates the live index and can persist unbounded or sensitive data.** `git add -A && git write-tree` changes the worktree index, may invoke repository filter configuration, and indiscriminately writes untracked files into the object database before any file/byte/path policy. This is riskier than the existing `workflow-docs-git.ts` pattern, which uses a temporary `GIT_INDEX_FILE`, `hash-object --no-filters`, explicit paths, and a parented `commit-tree`. **Fix:** reuse that plumbing with a temporary index, safe git config, `commit-tree -p <suffixHead>`, ref-name validation, symlink/path checks, and bounded file/count/byte limits; overflow should produce a diagnostic/quarantine manifest and hold rather than silently capture secrets or exhaust disk. Prove dirty, staged-only, untracked, descendant-commit, filter, symlink, oversized, and create-only-ref race cases.

8. **HIGH — rollout/acceptance details still contain false greens and avoidable new machinery.** Flag-OFF shadow performs DB/git/issue probes on every start but the plan does not say that probe timeout/write failure is isolated from legacy admission; O1 must inject all of those failures and prove unchanged HTTP/error ordering and no launch delay/failure. A16 needs actual mutation tests of approval/land-effect consumers, not merely the observation that attachment fields omit them. A18 is stale against this branch: `WORKFLOW_MENU_BINDINGS` currently uses `tpl_generic_menu`/`tpl_prd`, while `tpl_generic`/`tpl_product_v1` are in `RETIRED_BUNDLED_TEMPLATE_IDS`; the plan currently names `tpl_generic`/`tpl_prd` as the active pair. Also reconcile the “3 new tables” claim with the five tables actually described (attachment, stamp, admission, response, probe) plus the close-intent table; prefer existing run events/side-effect receipts where they satisfy the same queryability contract.

## Verdict

CHANGES REQUESTED — address items above
