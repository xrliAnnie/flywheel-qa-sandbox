# Design Review — plan.md (FLY-1707 E5) (Round 3)

Date: 2026-08-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 3 materially improves the design: the resume lineage, action union, durable carrier, authority fence, force-cancel receipt, quarantine plumbing, and off-path shadow are all moving in the right direction. However, the updated contracts still contain several implementation-level contradictions that would make consecutive resume, state-only recovery, A4/A10/A13/A16, staged-work preservation, or concurrent collection fail even if implemented literally; these need to be resolved before implementation.

## What's Good (Keep)

- Keep W10 and the explicit `source_attachment_id` / `result_attachment_id` split. Treating resume admission itself as a frontier change is the correct closure for repeated crash/resume cycles.
- Keep the `redispatch_execution | reconcile_state_only` action union. It correctly recognizes that a gate holder is not an execution and must not mint a synthetic gate runner.
- Keep V3's frozen runtime and rework-authority concepts, and the rule that resume must not call the live `resolveNodeDispatchAtLaunch` path.
- Keep the Bridge-owned checkpoint store. A second object database is necessary to satisfy A4 after deletion of the original repository.
- Keep the discriminated execution/gate/land authority fence and the addition of `applyWorkflowSourceEvent`; the source confirms that this receiver can write permanent claims, approve holders, create carrier delivery, and complete a run without passing through an execution receiver.
- Keep T7's transaction-local live-session target query and the partial unique index limiting each run to one open receipt.
- Keep the mode-aware Git plumbing, bounded quarantine policy, `GIT_SAFE_CONFIG`, and symlink-specific handling.
- Keep explicit cascade authority at only the two operator endpoints, the T6 staged intent with TTL reconciliation, the single-transaction cascade recheck, `held` precedence, the one registered opt-in flag, and the rebase-after-FLY-1772 sequencing.

## Issues & Recommendations

1. **[BLOCKER] W10 produces a child attachment that V0 and T2 still cannot validate on the next crash.** The plan's V0 accepts only an `edge_traversed` receipt whose payload carries `targetAttempt`, but W1/W3/W4/W5/W7/W10 deliberately use synthetic transition UIDs; in particular, `resume_replacement:<admissionKey>` has no `edge_traversed` receipt. Separately, W10 says the child “inherits” anchor/envelope but does not define whether its T2 row is atomically `ready`, whether it shares the source ref/store locator, or starts a new Git protocol. A new attachment-specific ref cannot be created inside the SQLite admission transaction. **Fix:** define an immutable target-authority receipt union for every W1–W10 UID kind and make V0 verify that typed receipt rather than require `edge_traversed`. For W10, explicitly co-write a child T1/T2 row that either (a) references the already-validated immutable source ref/store locator with reference-counted cleanup, or (b) starts `intent` and blocks dispatch until its own ref reaches `ready`; add an explicit parent/source link and SQL-enforced per-action T3 constraints. Run the advertised 2- and 3-cycle tests through V0 after every response-loss replay. Also update §2.7, S2, and R5 from W1–W9 to W1–W10.

2. **[BLOCKER] `runtime_digest` is not a stable semantic digest, and most executable attachments have no defined stamp point.** The current `workflow_execution_runtime` row includes `execution_id`, `run_id`, `node_id`, `attempt`, and `created_at` in addition to vendor/model/effort (`StateStore.ts:17080-17093`); hashing the whole row cannot match a new resume execution even when its runtime semantics are identical. W2 creates the successor attachment before `admitGeneralizedWorkflowExecution` creates that runtime row, while T2 and the write-point text only explicitly assign `runtime_digest_stamped` for W1. **Fix:** define a versioned `runtime_semantics_digest` over the exact replayable projection (for example vendor, model, effort, resolved family, and capabilities digest), excluding execution identity and timestamps. In the same SQLite admission transaction that inserts `workflow_execution_runtime`, stamp the current executable attachment for every relevant W path, then create resume runtimes from that frozen projection without calling the live resolver. Test every executable carrier, identity-only changes, each semantic-field mutation, live-template mutation, and authority-context mutation. Add `runtime_mismatch` and `authority_context_mismatch` to the canonical short-code registry.

3. **[BLOCKER] The `reconcile_state_only` branch is not a complete V1–V5 or idempotent-response protocol.** Section 2.5 validates only V0/V2/V3, omitting V4's carrier-union check and the gate form of V5. Section 2.3 also exempts gates from S3 issue-body stamping even though the locked V2 contract names the issue body as an input source. T4 then requires the same positive launch-owner evidence as `recordWorkflowStartResponse`, but a state-only action intentionally creates no execution or launch, so it can never satisfy that precondition. Finally, §2.5 re-drives holder/delivery state and §2.3bis writes holder state while §9 says E5 does not touch the gate-holder table. **Fix:** specify the full carrier-specific V1–V5 predicate for state-only recovery, including a current gate-authority V5 check and the locked V2 sources (or obtain an explicit PRD deviation rather than silently omitting S3). Make the admission transaction durably request a holder/delivery redrive generation that the existing rider consumes, and give T4 a discriminated proof: launch delivery for redispatch, durable redrive receipt/ack for state-only. Enforce the T3 NULL union in SQL, test response loss before/after the redrive receipt, and reconcile §9 with the actual read/write jurisdiction after rebasing FLY-1772.

4. **[BLOCKER] The checkpoint-store protocol is not yet an actual immutable CAS and has contradictory validity/cleanup rules.** `git push <store> <anchor>:<ref>` is not create-only CAS: it can fast-forward an existing ref, so “exact refspec” alone does not freeze an attachment. The application invariant says every `git_checkpoint` has non-NULL T1 `anchor_commit`, contradicting W1's deliberate NULL plus T2 `resolved_anchor_commit`. The recovery text says a missing local ready ref is adopted from the store before invalidation, but the next bullet declares any missing ready ref terminal invalid. Cleanup likewise says old non-current refs are removed after 90 days and that ready refs are never removed, without distinguishing local and store refs. **Fix:** define a tested create-only store-ref operation with expected-old=zero and same-value adoption (plus different-value/fast-forward conflict), and persist/verify the expected generation. Define one effective-anchor schema union that permits only the W1 pending form until its T2 stamp exists. On every ready local miss, adopt from the store first and invalidate only when both carriers fail. Apply reference-aware retention to both local and store refs, never deleting a currently referenced ref. Add crash/race cases for push-before-DB, DB-before-push, existing-same, existing-different, attempted fast-forward, local-only loss, store-only loss, and both-lost.

5. **[BLOCKER] The land fence is placed at receipt writes, not at the irreversible effects that A16 protects.** `executeLandOperation` authorizes once, then crosses several awaits before `triggerCool`, cleanup, and finalization; `triggerCool` can initiate the merge before `recordLandOperationStep` checks owner/generation (`land-executor.ts:303-466`, `StateStore.ts:39101-39191`). A stale operation can therefore perform the external effect and only then discover that its receipt write is fenced. **Fix:** re-check the complete land authority (current run/gate/head/holder plus operation owner and generation) immediately before every irreversible external effect and again after any intervening await; pair each effect with its existing head-bound idempotency key/receipt. Add A16 mutations that admit resume or supersede the holder at every await boundary and assert that `triggerCool`, merge/finalize, cleanup, and terminal writes are never invoked by the stale generation.

6. **[BLOCKER] The quarantine algorithm cannot satisfy its own staged-vs-worktree preservation test.** Applying the staged blob and then the unstaged blob to one temporary index leaves only the worktree version at that path; a single Git tree cannot preserve both versions. More directly, the plan creates a quarantine commit and then updates `refs/flywheel/quarantine/...` to `<suffixHead>`, making the newly created commit unreachable. Default `status --porcelain=v2 -z` can also collapse an untracked directory unless `--untracked-files=all` is requested. **Fix:** materialize two reachable snapshots when index and worktree differ: an index-state commit parented by `suffixHead`, followed by a worktree-state commit parented by the index commit, and point the quarantine ref to the latter. Parse `--untracked-files=all`, size staged blobs by object size as well as worktree bytes, retain the explicit validated path list, and make the nine-case tests assert both commit contents and ref reachability after GC.

7. **[BLOCKER] T7 excludes a second open row but does not fence two collectors adopting the same row, and the route can still fail before force-cancel begins.** T7 has no collector owner/generation/lease or row version. The HTTP request and sweep can both adopt the same `collecting` receipt, concurrently call `closeRunner`, and lose or duplicate `outcomes_json` updates; the partial unique index does not prevent that. Returning a changing “current receipt snapshot” while collecting also contradicts the stated byte-identical replay contract. In the current route, `collectRunQuiescenceEvidence` is awaited before `terminateWorkflowRunByOperator` and an unavailable probe returns 503 (`runs-route.ts:404-520`), even though the StateStore quiescence validator is neutralized; `collectExecutions:true` would therefore remain blocked in the exact failure mode it is meant to recover. **Fix:** add a crash-recoverable collector claim (`owner_id`, `generation`, `lease_expires_at`) and fence every outcome/state mutation by it, or use an equivalently versioned normalized outcome ledger. Keep `target_list_json` immutable and derive remaining work from fenced outcomes. Define whether the first in-progress response is cached byte-for-byte or whether polling is explicitly a different endpoint/contract. Parse the new flag before the liveness probe and make the new force-cancel path rely on the transaction-local live-session query, with probe data best-effort only; preserve the old path byte-for-byte when the flag is absent. Test request/sweep same-row adoption, claimant crash/lease takeover, stale late outcome, and replay before/after `responded`.

8. **[HIGH] O1 still claims zero request-path external I/O while adding a durable WAL write to every DAG start.** StateStore uses synchronous better-sqlite3 WAL durability per mutation (`StateStore.ts:1925-1931`), so the T5 marker INSERT is external disk I/O even though it has no `await`. A structural “no await” test would therefore prove a weaker property than the text claims and would miss lock/fsync latency on the highest-blast-radius path. **Fix:** preferably use the already-written W1 attachment/start ledger as the GatePoller rider's opportunity cursor, making shadow add no new request-path mutation at all. If a separate marker is retained, state the truthful contract (“one bounded synchronous DB write after launch commit; no awaited Git/network I/O”), add a write-budget/lock-contention test, and remove “zero external I/O” from §2.6/O1. While normalizing the rollout ledger, add the currently omitted short codes (`anchor_pending`, `runtime_mismatch`, `authority_context_mismatch`, `quarantine_overflow`) so observability tests target the same closed union the resolver emits.
