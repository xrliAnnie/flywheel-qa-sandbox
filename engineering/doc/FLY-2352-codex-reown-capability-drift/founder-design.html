Bridge 重启后,被返工唤醒过的 Codex 体不再「必死换体」

FLY-2352 · 设计稿 2026-09-08 · Codex 设计评审 2 轮 APPROVED · Bridge design gate 已过 · 实现节点待派

一句话

Bridge(总机:管所有 runner 的那个常驻进程)每次重启,只要一个 Codex runner(runner:领了一张 issue 在干活的 AI 工人,下文叫「体」)之前被 QA 打回过一次(返工),它就必定救不回来,被判死、换一个新体从头读交接。原因不是它真的坏了,而是「救援程序」找它的档案时用了一把只认单条记录的旧钥匙,返工过的体有两条记录,旧钥匙一看两条就说「查无此人」。换成早就写好的那把精确钥匙,同一个体就能按原样接着干。

修改范围:一个函数换一把钥匙 + 两个新的失败原因词 + 一句更清楚的报错。不动数据库结构,不加开关,回滚就是撤回 PR。

核心流程:出事的路(红)与修后的路(绿)

名词:activation(激活记录)= 「这个体在这张 issue 的第几轮里被授权干活」的一条档案;正常派工留一条,QA 打回后引擎不换人、直接「唤醒」同一个体再干一轮,就会再挂一条。snapshot(启动快照)= 体出生时冻结下来的一份参数,救援时拿它重建现场。drift(漂移)= 快照里的参数和现在重新算出来的参数对不上。

重点看菱形分叉:同一份快照、同一个体,只是换了一把找档案的钥匙,结果从「判死换体」变成「原体续命」。绿线上的 runtime.resume 就是 issue 里说的「同 socket 重拉 daemon」——这条路本来就在,只是从来没跑到过。

两把钥匙的差别

左边这把旧钥匙不是 bug,它是 FLY-1423 有意做成「多条就报空」的保险丝,源码注释原话:「this legacy getter is only well-defined for a single activation. Callers that can observe re-entry must use an exact activation API」。问题是救援程序没听这句话。右边这把精确钥匙在同一次救援里已经被另一行代码用着(拿它取 activation id 传给 runner),两把钥匙在同一次救援里给出了矛盾答案:精确钥匙说「你是第 3 轮的返工体」,旧钥匙说「查无此人」。

数据结构:谁记着什么

关键就一句:WORKFLOW_EXECUTION_BINDING 允许同一个 execution_id 有多行(attempt 2 和 attempt 3 同时挂着),而救援程序假设它只有一行。RECOVERY_CLAIM 是救援次数账本,每个 episode(一轮救援周期)最多 2 次,第 3 次来就判死。LAUNCH_SNAPSHOT_FILE 里那两个布尔值是出生时冻结的,不会变;这次出事不是它们变了,是「现在重新算」那一侧根本没算出来。

改什么、怎么验

改动(最小交付)

  • 改prepareCodexRecoveryCapabilities:找档案的那一行从旧钥匙换成精确钥匙 resolveCurrentWorkflowActivation;后面发能力、轮换凭据的代码一行不动。
  • 加两个失败原因词:activation_ambiguous(精确钥匙也找不到唯一的一条,例如替身已经铸好)、activation_invalid(档案本身损坏)。都走既有的「本次尝试作废」分支,不再让异常炸掉整轮巡检。
  • 改drift 报错句子带上两边的值,巡检不用再猜是哪个布尔、哪一侧。

验收

  • 先红后绿:用内存数据库复现生产的「原始 + 唤醒」两条档案形状,改前返回「非 workflow 体」(红),改后返回正确能力且新凭据挂在返工那条档案上(绿)。设计阶段已用一次性探针验证过红侧。
  • 三份既有测试文件基线 54/54 绿,改后继续绿;CI 以 PR 的确切 head 为准。
  • QA 上线后盯下一次 Bridge 重启:若窗口内有 2 条档案的 Codex 在飞体,期望看到 reown_revive_succeeded 而不是 drift;窗口内没有这类体就如实写「未观测到目标形状」。

取舍与被否掉的方案

方案结论为什么
A. 救援程序换精确钥匙采用一处改动,和同一次救援里已在用的那把钥匙统一成一个来源;生产两例的救援日志证明精确钥匙当时能唯一解析。
B. issue 提的「漂移了就重算覆盖,别抛错」否快照里的布尔已经烘进了体的启动指令和环境变量;若真对不上,覆盖只是把矛盾藏到运行期。修好 A 之后合法返工不再触发这个守卫,它剩下的职责就是抓「真的对不上」,那正该 fail-closed(宁可停下也不猜)。只把报错句子写清楚。
C. 把检查挪到「杀旧进程」之前 / 失败不扣次数不做,记为已知限制失败不扣次数会让一个确定救不回的体永远悬着,比换体更糟;A 修好后这个场景不再出现。
D. 直接改旧钥匙本身否FLY-1423 有意把它做成保险丝,还有 9 处调用方各有自己的合同;改语义是另一张单。
issue 提的「失败后先试同 socket 重拉 daemon」不需要新路绿线上的 runtime.resume 就是这条路,它只是从来没被跑到。

诚实边界:这单做什么、不做什么

做

  • 返工唤醒过的 Codex 体在 Bridge 重启后能按原体救回。
  • 档案找不到唯一一条、或档案损坏时,给出可辨认的失败原因,不炸整轮巡检。

不做

  • L1(Codex 评审抓到的另一个洞,FLY-2211 就有,本单不修):救援时轮换出的新凭据只放进了体的环境变量,而体在提交结果时读的是另一张表里的旧凭据。这只影响「带输出/裁决凭据」的 Codex 体;今天生产里没有这种体——314 条救援能力事件里带凭据的 0 条,54 个救回的体全是 implement,所有在飞 workflow 模板里 Codex 节点只有 implement / eng_design,都不带凭据;QA 节点全是 Claude。已建议 Tadashi 另开一张单;ship 前会再核一次模板没变。
  • 不改旧钥匙和它的其他 9 处调用方。
  • 不改救援的次数上限、先杀后救的顺序、判死后换体的引擎行为。
  • 不回填已经被换体的 14 个 session(替身已在跑或已完成)。
  • FLY-2403 里另一种判死(recovery owner failed before commit)不是这个病,不在本单。
