# FLY-1500 外发执行与对账 — 设计修正

Issue: FLY-1500
日期: 2026-07-27
基于: plan.md

## Founder 原话与本轮修正目标

> “图太简单没用，要一份详细 Technical Architecture Graph。”

本轮不改机制，只升级表达，专门修正一个已发生的误读：v2 不是在 v1 已有的五套机制上再加第六套。v1 的问题正是 5 本以上零散账互不相认；v2 用 1 本统一账替掉它们，批次 4 删除旧账，净减至少 4 本。

新版 founder HTML 必须让人一眼看见：

1. before 是收据表、唤醒指针、进程内去重缓存、stage 进度文件、CommDB、Bridge 状态机等 5 本以上零散账；after 是 v2 kernel 的 1 本统一账。
2. `messages → 同一事务完成处理、销账、登记 command → commands → 每 kind 唯一执行者 → 外呼 → 回执 → 探针对账`。同一事务内崩在任何一步，整笔回滚。
3. 人不读数据库，只看有行动意义的告警；旧明细按保留策略归档；过载时 notice 可以丢，business 永不丢。
4. 对标 etcd、银行核心和 transactional outbox（待办账本）工业模式；Claude Code 单进程、有人盯着，所以通常不需要这套机器。
5. 对照 Annie 的 99% 原则：本设计只治已经咬过她的 1% 崩溃窗口——重启双发与 ship 丢失；手段不是堆保护，而是净减至少 4 本账。

## Before：v1 的 5+ 本账为什么会双发或丢失

| 零散账 | 它知道什么 | 它不知道什么 | 已枚举的失败 |
|---|---|---|---|
| 外发收据表 | 某一步曾记录成功 | 消息消费是否已结清、Bridge 是否推进 | 收据有了，状态机仍重放，造成双发 |
| 唤醒指针 | 应从哪里继续读 | 上一次读到后是否真的完成外发 | 指针前移但效果未落地，造成丢失 |
| 进程内去重缓存 | 本进程刚刚发过什么 | 重启前发生过什么 | 重启清空，重复通知 |
| stage 进度文件 | runner 自报走到哪一步 | 外部系统实际是否成功 | 文件写了“完成”，真实外发可能失败 |
| CommDB | 问题、回复、指令 | GitHub、Discord、Linear、进程的真实效果 | 问题已答但外发状态未同步 |
| Bridge 状态机 | UI/工作流当前状态 | 其他五本账的原子提交结果 | Bridge 重启后只能猜该补发还是跳过 |

这些账各自有局部价值，但不存在一笔共同提交：一本写成功时，另一本可能还没写或已经崩溃。补更多读取规则不能根治，因为没有一个权威提交点。

## After：1 本统一账如何替掉 5+ 本旧账

“事务”首次出现时的白话定义：一组数据库写入要么全部成功，要么一条也不算成功。

“待办账本（transactional outbox）”的白话定义：业务处理只把“稍后要对外做什么”记进同一本数据库；唯一发件员稍后真正外发。

固定顺序：

1. `messages` 收到一件事。
2. 同一事务内：处理它、把消息销账、登记一条 `pending command`。
3. 事务提交后，`commands` 成为唯一待办来源。
4. 每种 `command.kind` 恰好一个 dispatcher（唯一发件员）认领。
5. 外呼前先记 intent（“准备做”）；外呼不放进数据库事务。
6. 外呼成功或失败后写 receipt（结果证据）。
7. 若在外呼和 receipt 之间崩溃，probe（事后到现场查询）比较 desired（应有）与 observed（实际）。
8. 批次 4 删除 v1 零散账；迁移完成后不长期双写。

## 对账与崩溃窗口

“探针（probe）”首次出现时的白话定义：不猜，而是去 GitHub、Linear、Discord 或 tmux 现场查动作到底有没有发生。

- `present`：查到了，补写 receipt，不重发。
- `absent`：查询成功且明确不存在；只有安全的 kind 才允许重做。
- `unknown`：查询本身失败或证据不完整；连续 3 次且跨度至少 5 分钟才升级给人。
- Discord 消息不可可靠探测：接受极罕见重复，以 effect key（同一动作的身份证）和更正帖收口，不造一台不可靠的历史扫描器。
- `github_merge` 与 `destructive_delete` 不进入自动补偿；不可逆动作宁可停下来叫人。

## 防超载三闸

1. **人机闸**：人不读账本行，只收到需要行动的聚合告警；普通成功记录留给机器对账。
2. **保留闸**：热数据保留当前处理窗口，过期明细归档；不会把审计历史永远塞在热表。
3. **优先级闸**：notice 是加速提示，过载可丢，周期扫描会补；business 是业务事实，必须落账，永不以丢弃换吞吐。

## 为什么别的系统看起来不需要

| 系统 | 实际做法 | 为什么看起来更简单 |
|---|---|---|
| etcd / Kubernetes | desired 与 observed 分开存，控制器持续对账 | 它们从一开始就把“一本权威状态 + 对账”当基础设施 |
| 银行核心 | 分录先落账，再由清算执行，差异进入对账 | 钱不能靠内存和日志猜，所以账本是产品本体 |
| transactional outbox 工业模式 | 业务事务只写待办，独立 worker 外发并记结果 | 和 FLY-1500 同型，不把跨系统网络调用伪装成数据库事务 |
| Claude Code 单进程 | 一个进程、人在旁边、失败直接重试 | 生命周期短且有人盯着，重启双发和无人值守 ship 丢失不是主要场景 |
| Flywheel v1 | 5+ 本局部账拼在一起 | 怪不在“有账”，而在“账互不相认”；所以 v2 是 1 本换 5+ 本 |

## Annie 99% 原则：只治已经发生过的 1%

99% 的普通外发一次就成功，不需要人看账本，也不需要额外告警。本设计只覆盖已经发生并咬过 Annie 的 1%：

- 重启落在“外呼已成功、receipt 未写”窗口，导致双发。
- ship 或通知落在“业务已结清、外发未成功”窗口，导致丢失。
- 探针坏时把“查不到”误判成“不存在”，导致过度重派。

根治动作是建立一个权威提交点并删除旧账，净减至少 4 本。租约、三态探针和有界升级只服务这些已枚举窗口，不扩展成通用工作流平台。

## 保护性机制单列，供 Founder 砍

| 机制 | 哪个已枚举场景需要 | 根治为何不够 | 砍掉的影响 |
|---|---|---|---|
| claim SQL 第二道通知前置硬门 | 内部代码绕过 admission，出现先斩后奏 | 类型入口能早失败，但裸写仍可能绕过 | 内部 bug 时双保险变零保险 |
| 可丢门铃 | 正常 command 希望秒级唤醒 | 60 秒周期扫描已保活，只是不够快 | 不丢业务，最坏慢 60 秒 |
| unknown 的次数 + 时间双条件 | 短暂探针风暴与长期不可见要区分 | 三态只表达事实，不决定何时叫人 | 只留次数会噪声升级；只留时间会升级太慢 |
| 5 分钟 observed 心跳 | 需要知道探针最近一次仍健康 | 状态不变时不写也能维持正确性 | 时间戳变旧，排障证据变弱 |
| 查询计划变体断言 | SQLite 统计变化曾让公平索引退化 | 代码正确不保证优化器永远选同一路 | 性能退化可能静默发生 |
