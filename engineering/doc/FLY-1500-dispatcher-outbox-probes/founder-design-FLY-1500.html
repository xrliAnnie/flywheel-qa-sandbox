双发案例
外呼已经成功，receipt 还没写，Bridge 重启。旧系统看不到共同提交点，只能再发一次。
丢失案例
业务状态先标完成，外呼随后失败。另一套账以为事情结束，ship 或通知静默消失。
Architecture graph 02

从 messages 到现场对账：每一步按固定顺序

事务一组数据库写入要么全成功，要么一条也不算成功。
待办账本 / outbox业务只登记“稍后要做什么”，不在事务里直接上网。
唯一发件员 / dispatcher每种动作只有一个执行者负责认领和外发。
结果证据 / receipt外部系统返回的 ID、URL 或状态，写回统一账。

蓝色是数据库内，橙色是真实外呼，绿色是证据与对账。最关键的原子边界是第 ② 步。

为什么“崩任何一步整笔回滚”只写在第 ② 步？

GitHub、Discord、Linear 和 tmux 不参加 SQLite 的事务；把网络调用塞进事务只会让锁更长，仍然不能让两个系统一起回滚。所以根治方式不是假装跨系统能做一笔事务，而是：同一事务只负责处理消息、销账、登记 command；真实外呼放在事务外，用 intent + receipt + probe 对账。

Architecture graph 03

崩在外呼前可以重做；崩在外呼后必须先查现场

“探针 / probe”是事后去 GitHub、Linear 或 tmux 查动作到底有没有发生。它只回答三种事实：在、不在、查不清。

结果机器看到的事实自动动作为什么不更激进
present / 在查询成功，效果已存在补写 receipt，绝不重发外呼已成功，只缺本地证据
absent / 不在查询成功，明确不存在仅安全动作按预算重做merge / 删除不可逆，仍停下来叫人
unknown / 查不清查询超时、5xx、限流或证据不全连续 3 次且跨 5 分钟才升级“探不到”不等于“死了”，避免误重派
Discord 不可可靠探测历史扫描受权限、分页、归档干扰罕见重复 + 动作身份证 + 更正帖不为毫秒级窗口造一台更不可靠的扫描器

Architecture graph 04

防超载三闸：人不读库、旧账归档、notice 可丢

business 永不丢

消息、command、receipt 是业务事实，必须先落统一账。过载也不能靠丢业务换吞吐。

notice 可以丢

门铃只是“快点来看”的提示；丢了以后，60 秒周期扫描仍会发现同一条 business。

人不读数据库

正常成功静默结清。只有重试耗尽或长期 unknown 才聚合成需要行动的告警。

保留策略归档

热表只留当前处理窗口；旧明细归档，审计可查但不拖慢日常执行。

Annie principle

Founder 99% 原则：99% 正常路径保持安静，只治咬过我们的 1%

本设计不是为了让每次外发更“隆重”。99% 的动作一次成功，机器自行结清，人完全不用看。它只在已经发生过的崩溃窗口里接管：重启双发、ship / 通知丢失、把“查不到”误判成“死了”。

Honest boundaries

这批造机器，不接生产电源

  • 本批新增 kernel command 生命周期与独立 dispatcher 包，但不接 daemon / launchd；生产行为零变化。
  • 消息消费归 FLY-1499；gate 与 task 派发归 FLY-1498；告警聚合归 FLY-1501；批次 3 才切换，批次 4 才删旧账。
  • Discord 普通消息仍接受极罕见重复；这比假装历史扫描可靠更诚实。
  • github_merge 与破坏性删除不自动补偿，卡住时需要人。
  • notice 可丢，不代表 business 可丢；二者在结构上分开。
