FLY-2096:返工换体超过一小时不再被打成 held,已收工的体不再被当成卡住

工程设计说明 · 2026-09-03 · 分支 flywheel-FLY-2096 · __REVIEW_META__ · 每个卡片下方都可以留意见,页底一键汇总复制

一句话总结

这张单点名的病根——「返工换了一个新的工人之后,只要这一轮干活超过 60 分钟,系统就把整条 run 冻住,工人做完了也交不了工」——已经在今天下午合入的 FLY-2278 里被整体拆掉了;但生产还没换到新版本(今天 19:02Z 又发生了一次同样的冻结)。本单要做的是三件收尾:把「不会再冻」钉成一组能在旧代码上变红、在新代码上变绿的回归测试;顺手删掉拆机制时留下的死参数;补一个 FLY-2278 漏掉的口子——工人做完之后系统仍把它当成「还没收到交接的人」,过 30 分钟就发一条假的「投递卡住」告警。

名词:run = 一张 issue 在自动流水线里的一次完整执行;rework / 返工 = QA 或 founder 打回后,把活重新交给一个工人再做一轮;换体 = 原来的工人已经不在了,系统另起一个新工人接这轮返工;held / 冻结 = 系统把一条 run 暂停、等人来决定;delivery / 交接 = 系统对「这份返工任务必须送到工人手里」的一条记录。

发生了什么:生产里的 69 次

从生产数据库的只读副本(2026-09-03 20:08Z)里数:系统一共 69 次因为「返工交接卡住」把 run 打成 held。其中 49 次(71%)的理由本质上是「工人活着、只是时间到了」——包括 6 次理由字段本身就写着「工人在收到交接后还活着」。issue 里的 FLY-2074 案例逐字对得上:19:28 换体上岗,20:28 被冻结。

冻结理由(系统原话)次数大白话
delivery_wake_delivered30交接已经送到工人手里,只是这一轮干得久
delivery_awaiting_receipt13还在等工人回一个「收到」;换体的工人从不回这个
actor_alive_after_receipt6系统自己每 3 分钟写一次「工人还活着」,然后把这句话当成冻结理由
worktree_not_ready / holder_activation_failed / 其他20真有问题的那部分,不是本单

为什么会这样:旧的巡检只看一件事——「交接记录最后一次更新是多久以前」。30 分钟发告警,60 分钟冻结。它不看工人的窗口是不是还在动、任务是不是已经交到手、甚至不看这个节点是不是已经做完了(8-31 的新证据:节点已完成、下一步 QA 已经在跑,照样冻)。

核心流程:旧机制 vs 新机制

左边是生产此刻仍在跑的旧机制;右边是 FLY-2278 之后 main 上的新机制。新机制的关键差别:超时之后先问「收件的工人活着吗」(看它的 heartbeat——只要工人的终端窗口还在,系统每个周期都会刷新这个心跳——或者 10 分钟内有没有发过消息);活着就什么都不写,不活着也只告警不冻结。整个新路径里根本没有「把 run 打成 held」这一步。

图 1:旧机制按「交接记录的年龄」冻结;新机制按「工人活性」决定是否告警,且永远不冻结。

新发现:做完了却被当成「投递卡住」

核对 FLY-2278 之后的代码时发现一个漏掉的口子。系统给每条交接记一张 delivery attempt(投递账本上的一行,记着「什么时候送出、什么时候收到、什么时候结清」)。另一种交接(carrier,把 founder 的问题带给工人的那种)在工人做完的同一笔事务里就把这一行结清了;返工这种没有。结果是:工人做完、终端窗口关掉、心跳停了,系统 10 分钟后判它「不活」,再对照那张没结清的账——「30 分钟前就该收到,还没结清,人又不在」——于是给一个已经做完的节点发「投递卡住」告警,90 分钟后再升级一次。今晚 founder 频道里 FLY-2291 / FLY-2278 那几条 warning / severe 就是这个。

__SVG_D3__

图 2:修前与修后的时间线。修法只有一处——工人做完的那笔事务里,顺手把返工的这一行账结清(复用 carrier 已经在用的同一个函数),不加任何新机制。

Lead 已裁决把这一处纳入本单,并明写这是推翻 FLY-2278 计划里「不为返工补写点」那一条:那条的前提「活性门会挡住误报」只对还在岗的工人成立,对做完的工人正好反过来;而且同一张账本、同一个结清函数,两种交接两套结果,本身就是缺陷。

怎么证明:先红后绿

Lead 的硬要求:回归测试必须先在旧代码上跑一遍并且变红,再在新代码上变绿——否则写出来的只是一条永远不会响的警报。做法是同一个测试文件拷进旧代码的临时副本里跑一次。测试脚本按 issue 里的真实时间线走:换体上岗 → 61 分钟 → 95 分钟 → 交工 → 3 小时后再巡检。

取舍与被否掉的方案

方案结论为什么
再修一次旧时钟(让它看 turn 已授、任务已投、窗口活跃)否旧时钟已经被 FLY-2278 整个删掉,再修等于复活它;而且新活性门已经做了更强的形式(活着连告警都不发)。
冻结改成只告警已由 FLY-2278 完成新路径里没有 hold 写点;本单用测试钉死这一点。
给返工补一个「消费时刻」时钟否那是再造一个阶段时钟;本单只结清账本行,不造时钟(与 FLY-2278 的零预算一致)。
返工做完时结清投递账本行做复用 carrier 已在用的同一个函数,零新机制;Lead 裁决并写明推翻 FLY-2278 那一条的理由。
顺手清掉每 3 分钟一次的「工人还活着」重探噪音另开单它不再驱动任何冻结,是独立的噪音问题;已向 Lead 点出。
把生产里那条还冻着的 FLY-2241 解开本单不碰数据处置权在 Lead / founder;而且现成的「解冻门」会把返工重新投给一个已经做完的节点,不是它需要的动作。本单只写一段可核对的处置建议。

诚实边界:这个设计做什么、不做什么

做

  • 一个测试文件,钉死本单精确形状:换体上岗超过 60 / 95 分钟且工人活着 → run 保持 active、零告警、交工被接受;对照组工人不活 → 只告警,仍不冻结,交工仍被接受。
  • 同一文件在退役前代码上跑出红,两次输出贴进 PR。
  • 删掉一个只有旧时钟在用的死参数(includeDeferred)。
  • 返工做完时结清投递账本行(先红后绿,带对照组)。

不做

  • 不部署、不重启。生产 Bridge 此刻仍是 FLY-2278 之前的版本(buildSha 31da17817),修复只会随 00:00 PT 的自动更新班车生效;在那之前这类冻结还会发生,巡检照旧手工拨回。
  • 不碰任何生产数据:FLY-2241 那条冻着的 run、以及 3 条已完成但账本行未结清的返工,都留给 Lead 处置或由引擎在 run 结束时自然结清。
  • 不动 FLY-2278 定下的阈值(30 / 90 分钟、10 分钟活性窗),不加表、列、开关、告警层、冻结形状、事件种类。
  • 不处理「工人还活着」3 分钟重探的事件噪音——另开单。
