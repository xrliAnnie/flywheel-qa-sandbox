Claude 传输探针：只回执 TURN,不伪造 marker

[529 canary] FLY2127-CANARY-7b7c4e0e-f5ee-4fc2-ac0a-544468dfb145 claude · 设计阶段(eng_design)· 2026-10-01
● 一句话结论

这一步只证明“轮到我写了”并如实回报，不往 probe.txt 里写任何一行——因为没有任何人把要写的那一行真正发给这个执行实例。

几个词先说清楚：

  • execution(执行实例):一次具体的 AI 工作进程，有唯一编号。本次是 d27c7945-…(前两个实例 2cd673b2-…、f0635f3b-… 写好了草稿并做过一轮评审修订，但都没收尾，这次接着做)。
  • TURN(写入令牌):同一个工作目录同一时刻只允许一个执行实例改文件，拿到令牌才能写。本次查询结果是 yours,即“轮到我”。
  • marker(标记行):canary 测试要求写进 probe.txt 的一行精确文字，用来证明“消息送到了”。
  • canary(金丝雀测试):用一个极小、无害的任务去试探整条传输链路是否通畅。
  • native instruction / 原生邮件:Lead 通过 Flywheel 邮箱直接送到某个执行实例的指令，数据库里能查到收件人和发件人。

● 核心流程

上半部分是本设计阶段实际走的路；虚线之后是下游实现阶段(另一个执行实例，称为 writer)在“收到发给它自己的指令”时才会走的路。design review(设计评审)指另一个模型(Codex)独立审这份方案，批准后才能收尾。

中途断掉也不会出错：写之前同时看“工作区里有没有这一行”和“这一行有没有真正提交进 Git”。已写未提交就补提交；已提交就不重复写，只找出原来那次提交并核对。

● 数据与结构模型

三份证据彼此独立:TURN 回答“谁可以写”,LeadInstruction 回答“写什么”,DeliveryReceipt(投递收据) 证明“消息确实送达了这个执行实例”。provenance(来源证据)就是把这三者串起来的可核验链条。真正写入的字节只能来自数据库里那条指令的原文 row.content,不能从聊天画面里重新抄。如果这条指令的正文被存成“外部文件引用”(content_ref,大消息才会这样存),一律拒绝并请对方直接把原文发过来——不去跟着路径读文件。

QA(质检)是另一个独立的执行实例：它拿 writer 的回执去核对“指令确实发给了 writer、内容哈希一致、提交只改了 probe.txt”。指令即使已经被归档，也能从归档快照里核对；查不到证据只能判“无法验证”,不能判通过。

● 关键取舍与被拒方案
采用A. 只回执 TURN;下游只追加“发给它自己的原生精确指令”

优点：每一行 marker 都能追溯到一条具体指令，不会制造“测试通过”的假象。代价：如果一直没人发指令,probe.txt 就一直不存在——这是诚实结果，不是失败掩盖。

拒绝B. 照着测试脚本模板自己写出 …-CLAUDE-BOOT / …-R4-CLAUDE

这两行确实是测试脚本期待的字符串，但它们属于脚本自己另起的那个 Claude 执行实例(不同编号、不同目录)。在这里抄一遍只证明“会抄模板”,不证明“收到了邮件”。除非 Lead 明确指示，否则不做。

拒绝C. 自己写一行“诊断信息”(早期 FLY-3121 的做法)

TURN 事实已经由系统命令原生给出并会正式回执；再往文件里塞一行近似证据，只会让 probe.txt 混进不是被请求的内容。后来的 FLY-3122 / FLY-3125 已经纠正了这一点。

待 owner 决定工作流路由不匹配

“实现”节点的标准完成方式需要开 PR(合并请求),而本 issue 明确禁止 PR / push / 上线。设计规定：下游不发明“无代码完成”出口、不造空提交，而是如实报告“结果 + 不匹配”后停靠(park),由工作流负责人选择关闭、取消或换模板。Lead 已书面确认这一做法。

● 诚实边界
这份设计做什么
  • 记录本执行实例的身份与 TURN,并正式回执
  • 定义下游追加合同：来源核验、两种允许的指令句式、同一条 marker 不许出现两次、重复检查、只提交 probe.txt、仅本地

  • 定义 QA 按 writer 身份做只读审计；结果只写进回报，不走“需要 PR、可能推送”的通用质检收尾

  • 把设计文档推送到功能分支(设计合同要求)

  • 不往 probe.txt 写任何内容
  • 不声称本实例收到了原生 Claude 邮件(它没有收到)
  • 不替代测试脚本自己的 R4-claude 用例

  • 不改任何产品代码，不跑测试套件
