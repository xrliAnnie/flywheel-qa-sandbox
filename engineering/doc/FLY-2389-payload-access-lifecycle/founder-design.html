让客户拿到对的版本，

从授权码到产品包

端点检查授权码后发出最多 60 秒有效的下载链接；私有文件库直接传输，安装器校验文件一致后才安装。

R2 是存放产品包的私有文件库。presigned GET 是只能下载一个指定文件、到时失效的临时链接。链接是凭证，请勿转发。

一份目录，两种授权

manifest 是版本目录，决定当前内部测试版与客户正式版。entitlement 是授权档位，决定能看和下载的版本集合。

记录唯一真相保持什么
内部授权internal → internal-beta可下载允许的测试版和正式版
客户授权customer → customer-release只可下载允许的正式版
文件身份版本号 + SHA-256同一身份的内容不能被替换
授权码记录授权码的摘要 → 档位、吊销状态不存明文，不覆盖已吊销授权码

SHA-256 是文件内容的校验值，用来检查下载的字节是否与发布目录一致。机器版本号不带 v；人看的标签可以带 v。公开安装器的 npm 标签不决定产品包版本。

最新的一直留；旧的才开始计时

内部测试版被替换后保留 14 天，客户正式版保留 28 天。当前版本即使一年没更新也不能被按年龄删除。旧版到期前重新启用，会清零历史时钟；再被替换时重新起算。

到期后端点立即停止新下载授权。后台计划任务按小时尝试清理；任务延迟或失败会推迟物理删除，后续任务继续重试。

吊销与密钥：明确生效边界

吊销授权码、隔离坏版后，端点不再发新链接。已发出的链接仍可能在剩余 60 秒内开始下载；已经开始或完成的下载不能召回。Engineering Lead 已确认接受这个边界。

quarantine 是隔离坏版本，禁止再取得它的新下载授权。缺文件、超出授权、到期、已隔离的请求都不会得到下载链接。

用途放在哪里权限边界
文件签名凭据GitHub 的 release 受管环境 → Worker 密钥只读指定文件库，不交给客户
自动清理凭据同一受管环境 → 清理任务只能标记到期、标记删除和删除已标记文件
运营授权码工具运营进程环境变量签发、吊销；不把这项权限给清理任务
客户授权码签发时私密交付；客户本地受限文件库里只保留摘要，不出现在文档或日志

Worker 是运行验权端点的小型云程序。GitHub release 受管环境 是现有发布流程专用的配置与密钥存放位置。

为什么采用这个最小方案

采用没有采用理由
复用现有版本目录和清理协议按上传年龄删文件上传日不等于被替换日；会误删还在服务的最新版本
原生规则只清理未完成分段上传搬迁 current/history 或每个文件一条规则避免多份状态、复制与恢复竞态
短效链接直接下载每次文件传输都代理验权满足本单分级直连下载，接受 60 秒剩余窗口
随机授权码 + 摘要记录新账户、签名 license 或支付系统现有基础已足够签发、验证和吊销

CAS 是先检查目录没有被别人改过，再原子提交自己的修改。删除前通过它提交永久删除标记，避免与重新启用旧版竞争。

审计发现上传收尾可能误删刚刚发布的当前版本。设计只修这处收尾检查，并把实际删除收归既有删除标记协议。

怎样证明它真的可用

  1. 授权正反例：客户可下正式版、不能下测试版；内部授权可下测试版。无效或已吊销授权不能换链接。
  2. 保留期夹具：模拟 365 天、14/28 天边界前后、旧版重新启用、清理失败与并发上传，断言当前文件一直存在。
  3. 联合真实验证：B1 发布 → 端点给短效链接 → 私有 R2 下载 → 安装器校验值一致。改签名、改文件、过期链接必须失败。
  4. 自动化证据：确认清理任务只有清理权限，真实运行成功，原生规则不删除完整产品包。

已有 28 个端点与生命周期基线测试通过。新增短效链接、自动清理和真实 R2 联合验证尚未实施；不能把基线通过写成整单上线成功。

这份设计交付到哪里

覆盖私有托管、分级下载、授权码签发/验证/吊销、14/28 天保留与自动清理，以及 B1 联合验收方案。

不做计费、账号、席位、计量，也不在这次设计中实现自动发布决策或客户自动更新器。ship 是内部合并/部署流程；release 是对外发产品包的流程，两者保持独立授权。
