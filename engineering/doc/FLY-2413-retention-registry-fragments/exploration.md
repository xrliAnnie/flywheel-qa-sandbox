## 问题与成功标准

2026-09-07 的 FLY-2397 / FLY-2396 合并冲突是本单给定背景。当前 checkout 为 `579c79ed6`，本次没有重新取证历史 PR 冲突，也没有接触生产数据库。

新增表必须有人决定保留分类；目前同一事实重复写入 registry、大型测试中的数量/表名断言、JSON 总清单。不同表也争抢相同文件。解决目标是：两个独立新增保护表的 PR 在 retention 分类面仅追加各自文件；合并后统一守卫无需编辑；漏登记、重复登记、缺表及摘要漂移仍能报错。

## 方案比较

| 方向 | 收益 | 代价 / 判定 |
|---|---|---|
| 从实际 schema 自动生成期望分类 | 新表零登记 | 数据库知道表存在，不知道其授权语义；期待与观测同源会放过遗漏。不选。 |
| 每个 owner 一个片段 | 跨 owner 冲突减少 | StateStore 是大 owner，同 owner 并发仍碰撞；还会出现集中 import 清单。不选。 |
| 每个数据库+表一个 JSON 片段，目录发现 | 不同表写不同路径；分类仍是人工审查的独立事实 | 一次性拆分文件较多；需严格加载器和完整证据摘要。推荐。 |

## 推荐合同

- 唯一稳定身份是 `(database, table)`；每个身份占一个文件。分类是既有枚举，不从表名前缀推断，中文标签仅用于说明。
- 通用测试检查目录格式、身份唯一、真实建库表均有分类、删除目标与既有执行策略一致；不维护全局数量或第二份当前期望列表。
- runtime 的 `assertClassifiedSchema` 继续严格拒绝未知和非 optional 缺失；`assertNoUnclassifiedSchema` 保留原来的单向检查职责。
- schema 观测来自实际 StateStore / MailboxQueue 初始化；不能把片段表名拿去建一套假 schema 再宣布覆盖生产。
- 最低变异体验收：临时数据库新增未登记表必红；去掉一个必需表必红；禁用未知表断言时，该负向测试本身必须失败。
- 分类片段不带 SQL、执行模块或“默认受保护”兜底；新增删除目标仍需要专属删除策略与评审。
- 数据驱动也必须受证据保护：新增、删除、修改片段要使旧激活凭证与 inventory 失效，不能只继续散列原来的 mjs 文件。

## 边界

保留 14 天策略、现有删除 SQL、authority/current 分类语义与 optional-retired 例外。本单不新增清理目标、不迁移数据库、不执行清理、不重新激活 janitor、不扩展 schema 指纹算法、不重构所有迁移代码。不能承诺 StateStore 同文件 DDL 的并发冲突也消失。

当前阶段只交设计、研究、实施计划和 HTML；评审由注入的显式 request-review 流程完成。排期仍由 founder 决定，当前 design dispatch 不代表提高优先级。
