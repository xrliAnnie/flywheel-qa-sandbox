v2 退役与整批清理 — 设计方案

FLY-1631 · 2026-08-04 · 设计节点交付 · Codex 设计评审 2 轮 APPROVED · 完整计划:engineering/doc/FLY-1631-v2-retirement-cleanup/plan.md

① 一句话总结

把已废弃的 v2 系统从生产机上彻底清干净:先停掉还在跑的 engine,再把 3GB 数据目录整体归档,然后一个 PR 把 9 个包共约 6.3 万行代码全部删掉,最后把 14 个 v2 旧单逐一分诊 —— 每一步都留备份、都能一键回滚,现役系统一根汗毛不动。

你 8-4 的裁定:「原来那个 V2 我们是打算完全不要了,甚至之后那一整批代码都要全部清理掉。」本方案就是这句话的完整执行图纸。昨晚杀 eng-lead 的 v2-scheduler 已在第①步拔牙;这是第②步,把剩下的尸体全部清走。

需要你拍板的 5 件事(全文细节见对应小节):
1. 在裸终端贴一行命令,停掉还在跑的 engine(②节);
2. 批准代码删除 PR 的合入与部署(④节);
3. 批准旧单分诊清单 —— 关 10 单、改 2 单、收 3 个旧 PR(⑤节);
4. 旧 PR #741(v2 观察记录文档)是留档合入还是直接关(⑤节);
5. 归档目录里几把明文钥匙(Discord bot token 等)要不要换新(⑥节)。

② 现场取证:尸体在干什么

engine(v2 的总调度进程,由 launchd(macOS 的开机自启管家)拉起并保活)此刻仍在跑。它现在唯一做的事:每秒钟对着一个 7-31 就已删除的工作目录尝试 git 操作 → 失败 → 报错 → 下一秒再来。启动至今已刷了 437,442 条一模一样的错误日志(44MB),除此之外零输出。

③ 五阶段执行图

  • 阶段 A · engine 下线(今天可做):先把它的自启配置文件挪进「退休区」(防下次登录复活),然后你在裸终端贴一行:launchctl bootout gui/$(id -u)/com.flywheel.v2-engine。系统护栏不允许 agent 代跑这类命令(这是对的),所以和第①步一样由你亲手执行。顺手把从未安装过的 ingress 配置也挪进退休区。
  • 阶段 B · 数据归档:mv ~/.flywheel/v2 → ~/.flywheel/v2.retired-20260804,一次改名,3GB 原样保留当证据,随时可改回来。7 天后要不要压缩/删除,到时你再拍。
  • 阶段 C · 代码整批删除:单个 PR 一次删干净(为什么必须一个 PR,见④节),照旧走你批准后合入 + 受控重启部署。
  • 阶段 D · 旧单分诊:与前面并行,清单在⑤节,你批准后由 Tadashi 逐单执行。
  • 阶段 E · 7 天观察:观察钟从「代码 PR 部署完成 + 首次全舰队重启成功」起算 —— 那次重启才是最大考验点。每天巡一次:无 v2 自启任务、无 v2 相关报错、无进程重建 v2 目录。

顺序上唯一的硬规矩:A 必须在 C 部署之前完成。否则代码删了、自启管家还拿着旧配置永远保活地拉一个已不存在的程序,机器上会多一个每 15 秒失败重启一次的幽灵。

④ 代码删多少、为什么敢删、为什么必须一刀切

删多少

  • 9 个 v2 专属包,约 6.3 万行代码(引擎、调度器、账本内核、信箱、切换工具等)—— 相互抱团、外界无人使用,整体移除;
  • 寄生在现役包里的 v2 文件约 4,800 行(6 个源文件 + 7 个测试);
  • 3 个安装脚本 + 5 个专属测试脚本 + 9 个 v2 派工说明书文件;
  • 15 处现役文件里的 v2 引用点要在同一个 PR 里一并改掉(这是评审 2 轮抠出来的完整清单,含 3 处一旦漏删就会让 Bridge 或全部 Lead 起不来的点)。

为什么敢删 —— 唯一的真连接点已查明是「空转的安检门」

v2 当年在 5 个现役程序的启动第一句装了一道「切换期安检」(术语叫 guard,作用是:如果 v2 正式接管,就不许旧系统再写数据)。实测:这道安检要找的「接管令牌文件」在生产机的默认位置从来不存在,所以它每次都只是看一眼、放行 —— 删掉它 = 行为零变化。

为什么必须一刀切(单 PR)

如果先删 v2 的包、下一批才删这 5 处安检调用,那 5 个程序启动时会因为「找不到被删的模块」直接崩 —— Bridge、全部 Lead、命令行工具一锅端。同一个 PR 里包和调用点一起消失,就不存在中间危险态;万一出事,整个 PR 一键撤销。

红线:同名不同物,严禁误伤

Bridge 内部的派工引擎名字里也带 "v2"(workflow_v2 等)—— 那是现役系统,与废弃 v2 无关。方案里列了逐字节不许变的红线文件清单,PR 验收时机器自动比对,防手滑。

数据怎么办整目录改名归档,3GB 原样保留直接删(丢证据、断回滚);压缩(多一步出错面,7 天后再议)

历史文档全部保留在 git 里连文档一起删(「尸体」的定义是会跑的代码;文档是病历,留档)
engine 何时停你贴一行命令,今天即停等下次重启自然消失(可行,但它每天再刷 2 万条错误日志,且多活一天多一天风险)

钥匙处置门(关单前必须了结)

归档目录里有几把明文钥匙:ingress 配置里内嵌的 Discord bot token、一份 Claude 凭据、两份 GitHub 凭据、一把 v2 内部握手密钥。归档只是换了住址,不等于钥匙作废。方案:逐把按「凭据指纹」与现役钥匙比对 —— v2 专用的直接吊销;与现役共享的不动(换新需另做波及面计划)。比对结论留档、钥匙原文与指纹都不进报告,最终处置你拍板。

⑦ 诚实边界 — 这个方案不做什么、哪里有不确定

  • 不做任何功能迁移:你已裁定 v2 整批不要,所以没有「把 v2 的某能力搬到 v1」的动作;个别有价值的诉求(如投递健康报警)若还要,由消息层重构那条线重新立项。
  • 不碰消息层重构(1569-1576)与 Bridge 派工引擎:那是 v1.5 现役,红线保护。
  • 7 天观察是每日抽查,不是持续监控;最大考验点(部署后首次全舰队重启)已单独列为观察钟起点。
  • 回滚不是一个按钮:代码 PR 撤销后还需要重装依赖 + 重新构建 + 一次受控重启,这一点如实写进部署报告。
  • 一个流程瑕疵如实报告:本设计 runner 的执行记录在 Bridge 里被误标为「已失败」(实际一直在正常干活,疑与昨晚 FLY-1627 事故的连锁有关)。不影响本方案内容,但说明 Bridge 对 runner 状态的判定还有毛边 —— 已一并报给 Tadashi。
