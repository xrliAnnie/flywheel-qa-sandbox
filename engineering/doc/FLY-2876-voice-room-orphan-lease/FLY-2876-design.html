FLY-2876 · 病根 529 语音房 · 同 slot 孤儿语音房锁让 start 永远失败 · 2026-09-26 · 设计评审 待裁定

一句话总结

测试房被拆掉再重新部署后，它自己上一轮留下的语音房锁会把新一轮 start 永远挡住；这个设计让 start 在确认“锁后面没有任何活着的东西”之后自己回收这把锁，而属于别的测试房的锁一律不碰。

推荐方向方案 A：start 自愈同 slot 孤儿锁 + 锁代次 + 回执围栏（只改一个脚本的租约函数）。

  • slot（测试房）：一台机器上互相隔离的 QA 测试环境，编号 1–6，目录在 /tmp/flywheel-test-slot-N。
  • 语音房锁（lease，租约）：/tmp 下一个以 Discord 语音频道命名的目录，谁建了它谁就独占那个语音频道；目录里的 owner.json 记着是哪个 slot 建的。
  • 运行回执（run receipt）：start 成功后写在 slot 目录里的一份 JSON，记着这次语音会话的编号、进程和状态（STARTED 或 STOPPED）。
  • 孤儿锁：锁还在，但建它的 slot 已经被拆掉重建、回执也随目录消失、进程也不在了 —— 没有人还能用正规命令释放它。
  • teardown（拆房）：scripts/test-teardown.sh，把一个 slot 的进程停掉、目录删掉。

核心流程：start 怎么决定回收还是拒绝

只有“三样东西都不活”才算孤儿：建锁的那个 start 进程（holder）、锁里记录的语音 daemon（后台常驻进程），以及本 slot 的运行回执（只要它还不是 STOPPED 就算活）。任何一样活着，行为和今天一样：拒绝。别的 slot 的锁沿用 #1323 的规则，本设计不改。

回收用的是 #1323 已有的“墓碑”流程：先把锁目录改名挪开，再复核一次仍是孤儿，才真正删除；复核不过就放回去并按原样拒绝。这样两个同时想回收的进程不会都得手。

数据与结构模型

没有新数据库。全部状态就是两份 JSON 文件：锁目录里的 owner.json，和 slot 目录里的运行回执。本设计给它们各加一个字段：leaseId（锁代次），每次新建锁随机生成一个编号，回执里记同一个编号，stop 只释放编号相同的锁 —— 旧一轮的 stop 永远删不掉新一轮的锁。

最难的一点：start 和进行中的 stop 撞车

三轮 Codex 代码评审（Codex 是 OpenAI 的代码评审模型，这里作为独立第二双眼睛）都盯着同一个问题：旧一轮的 stop 还在收尾时，新一轮的 start 会不会把锁抢走、又被旧 stop 误删。最终答案是做减法：回执只要还不是 STOPPED 就算活。进行中的 stop 必然对应一份 STARTED 回执，所以 start 在结构上不可能在它底下回收，而不只是“窗口变小”。

评审轮次发现处置
R1（HIGH）回收引入 ABA（同一把锁被换了主人，旧 stop 认不出来）：旧 stop 只比 slotDir 会删掉新锁、覆盖新回执加 leaseId 代次；stop 收尾前重读回执，确认还是自己的才写 STOPPED
R2（HIGH）比较代次和删除不是原子操作，微秒级交错仍可能命中Lead 裁定减法：STARTED 回执一律算活 ⇒ 竞态在结构上消失；代次保留作纵深防御
R3（MEDIUM）stop 先释放锁、后写 STOPPED，空档里 start 走普通建锁分支不看回执建锁前也先看本 slot 回执，未 STOPPED 不建锁；不改成“先写回执再释放”（会重开 R2）

关键取舍与放弃方案

方案结论理由
A：start 自愈同 slot 孤儿锁 + 代次 + 回执围栏采用唯一同时满足三条 QA 判据的方案；只改一个文件的租约函数；异 slot 规则和拆房脚本不动。
B：不改 start，等下一次拆房清锁放弃事故第二例就是“新 slot 已部署好却被挡”，再拆一次等于把 founder 实测再推迟一轮。
C：让语音 daemon 退出时自己删锁放弃把 QA 脚本的锁格式泄漏进产品包；daemon 被强杀或机器重启时钩子不跑，事故照样发生。自然结束改由幂等的 stop 收尾。
D：再加一把互斥锁消除回收竞态放弃互斥锁自己也会变孤儿，问题递归；R2 的减法已让竞态在结构上消失。
start 直接回收“daemon 已死但回执 STARTED”的锁（初版）放弃这正是进行中的 stop 所处的状态，会撞车（R2）。

诚实边界

这个设计会做

  • 同 slot 的孤儿锁在 start 时自动回收重建
  • 会话自然结束后，跑一次 stop 即可释放，然后 start 可用
  • 每把锁带代次，旧一轮的 stop 删不掉新一轮的锁
  • 回执读不了、是软链接、字段畸形时一律不回收

这个设计不会做

  • 不改拆房脚本、不改异 slot 回收规则、不改 voice-codex 产品包
  • 不在 start 里回收“daemon 已死但回执仍 STARTED”的锁
  • stop 因 Bridge 不可用或会话 404 失败时，锁要等下一次拆房才释放
  • 合入前遗留、没有任何进程记录、回执也没了的锁，若旧 daemon 其实还在跑，识别不出（与 #1323 拆房规则一致）
  • 本节点不改代码、不开 PR、不 merge、不派后继节点
