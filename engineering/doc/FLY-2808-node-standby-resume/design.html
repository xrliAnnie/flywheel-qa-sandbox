FLY-2808 · 节点生命周期 N1 · 工程设计

做完退下，需要时接着原对话

一句话：每个节点做完自己那段就真正把进程放掉，被打回时用原来的对话、原来的模型、原来的目录接着干；拉不起来会讲清原因，并用单独记账的兜底让单子继续。

Issue FLY-2808 · 日期 2026-09-24 · 文档 engineering/doc/FLY-2808-node-standby-resume/ · 本页只是设计说明，不是上线验收

01 · 核心流程

三个事实分开：阶段做完、退下待命、整单结束

今天系统只有一个「completed」和一个「进程还在不在」来推断一切，所以一个节点主动退下会被当成死了。定稿把它拆成三个各自独立的事实：阶段完成（这一段的结果已被接受，会像今天一样推进一次）、退下待命（这个节点现在没有进程，但随时能接着干）、整单结束（ship、取消或关闭，之后一切都不能再恢复）。退下和拉起本身绝不推进也不回滚整单。

设计、实现、QA 以及未来新增的节点统一执行；Claude 和 Codex 用同一份合同。不设空转缓冲，阶段结束就开始释放。

图 1 · 节点生命周期：从在干活到退下，再到核对后拉起；释放 60 秒未确认或恢复失败进入「出问题」，迟到的同代退出回执可自动转回待命，否则走明确的重新开始。

02 · 主动退下 vs 意外死亡

「我在等」只是自报，不能单独证明退下是安全的

现在 Runner 可以通过 declare-state park 自报一个 parked（Runner 说「我暂时不干活了」）状态，落在 runner_declared_states 表里。它只说明进程还活着在等，不能证明阶段已完成、会话能恢复、进程真的放掉了。定稿保留这条自报作为输入，另加一份由控制器（Bridge 里负责裁决的一方，不是 Runner 自己）确认的进程体记录。

要判定为「正常退下」，四件事同时成立只要缺一件
Runner 自报 parked仍按今天的死亡证据与故障额度处理；批准后进程才死、但还没发停机指令的情况，按停机请求的持久步骤重放，不把未知死因改成成功
这一段的阶段完成回执已被接受，且对应当前激活
会话身份已持久保存并核验过（对话编号、模型、目录、分支）
控制器批准了释放意图，并在 60 秒内确认专属进程、后台守护进程、监听端口都不在了

状态机是 active → retiring → standby → resuming → active / resume_failed → closed，每次拉起代数（generation，一个只增不减的整数，用来区分「上一具身体」和「这一具身体」）加一，旧代数的任何回调、停机指令、探活结果都不能改新代数。

退下失败也不是死胡同。60 秒内没确认释放会标成「出问题」，但后面每种观察都有唯一的合法去向：迟到的同代退出回执或探活证明进程都没了 → 自动补写待命，不用人管；进程还活着但已停止接活 → 保持隔离，Lead 可以重发停机或安全接管；探活说不清（PID 被复用、权限不够）→ 只挂起，不杀、不换、不拉；Lead 决定不退下 → 审计后回到在干活；这期间来的需求只排队。每一步都带请求编号、代数比较和审计回执。

03 · 六个会把退下当死亡的打断点

逐个改，且六处不是消费者全集

#今天发生什么定稿改法负例（必须测到）
1进程退出时 adapter 的收尾逻辑直接把会话写成 completed / timeout返回专门的 standby 结果，保持非终态；带代数的停机回执不发 session_completed旧代数的收尾不能终结新进程；没有退出回执不能显示待命
2探活发现进程不在，就判死、走替换先查控制器的进程体记录；确认待命则按原会话恢复；探活四态保留，不把待命冒充「活着」只有 parked 自报或注册缺席，不算可恢复
3TURN（共享工作目录的写权限令牌）巡检发现持有人不活，就转授或删除逻辑持有人与物理进程分开；只因退下不回收；合法阶段交接照常；恢复者必须重新查 TURN旧快照里的 TURN 不能复活；同目录两个需求不能双写
4收件人处于终态就拒投；新消息到达会清掉 parked 自报待命不是终态，可收 QUEUED 消息；清自报不清控制器真源；先排队后按需拉起投递 ACK 不等于模型消费了消息
5心跳巡检只在进程活着时接管 parked 节点，否则告警「监控丢失」没有需求的已确认待命没有进程是正常；有需求才拉起；Bridge 重启只重建监视身份不明不能冒充「无进程」；重启不能拉起全员
6把 dispatch 次数当成故障替换额度launchOrdinal 只排序；所有额度按目的分账：首次启动 / 故障换人 / 恢复兜底3 次兜底不能吃掉 3 次故障额度；回放不能双扣

还必须一起改：泛化完成事务只在特定情形保留非终态、终态时间戳写入边界、CommDB 的「证明已消失」清理、done-running 对账、会话裁剪、pane 丢失巡检、worktree / 分支清理。研究文档列了全部消费者及一条覆盖全部 packages 的普查命令。

04 · 数据 / 结构模型

节点与对话保留，进程可以换

图 2 · 一个节点管理一具可停止的进程体；进程体恢复同一份对话；每次拉起都留一条记录。

数据放在哪作用
进程体状态（一行 / 执行）StateStore 新表，字段含代数、状态、完成回执、清单摘要、当前需求、持有人、原因码物理进程生命周期的唯一真源；用「期望代数 + 期望状态」比较更新
恢复清单（resume manifest）Codex 扩充现有 ~/.flywheel/state/codex-sessions/<execId>/session.json；Claude 新建同级 claude-sessions/<execId>/session.json会话建立时由 adapter 原子写入：非空会话编号、解析后的模型与推理力度、账号绑定、目录 realpath、git 身份、分支、最后看到的 HEAD
退下时工作区基线与进程体记录同一事务、同一代数冻结：git status 规范化摘要、index tree、每个已暂存 / 未暂存 / 未跟踪条目的路径 + 权限 + 内容 digest（只存指纹，不存正文）拉起前逐条比对「未提交改动还在不在」的机械依据；被外部 reset / clean / 重建 worktree 都能查出来
需求 episode（一行 / 需求）需求来源、authority_mode（这条需求有没有写工作目录的权限：writer 或 conversation_only）、要求的激活与 TURN 版本、过期 / 取消身份、待投递的首条输入恢复、回放、兜底只看这条记录决定权限，不看消息文字；普通聊天消息永远不会变成写者
拉起记录现有 workflow_run_event，带唯一事件号请求 / 开始 / 核验 / 结束、结果与原因、排队耗时 / 启动耗时 / 总耗时、期望与实际的会话与模型
dispatch 账本现有表加 purpose 列：initial / fault_replacement / resume_fallback，两阶段迁移（先加可空列并回填历史行，再把它纳入不可改写触发器）purpose 只由服务端按动作派生，调用方不能自报；混跑期读到空值一律按故障换人保守计数；所有额度消费者共用同一条计数查询
park 事件流版本号现有 park outbox 每行加 schema_version；旧读取端遇到不认识的版本只挂起、游标不前移先部署认识新版本的读取端，全部就位后才允许写新版本；回滚时保留新读取端直到事件流排空
park 自报与投影现有 runner_declared_states 与 CommDB 投影加代数 / 状态引用仍是输入与显示，不是权威

不改 append-only 的 workflow_execution_runtime 配置绑定；不复制第二套 Codex 会话真源；摘要用于发现漂移，不当凭证。

05 · 拉起：身份 / 模型 / 工作目录逐项核对

先核再启动，启动后再核一次才发活

图 3 · 拉起路径：整单未结束 → 旧进程确认不在 → 拉起前核对 → 启动 → 拉起后核对 → 重新查写权限 → 首轮消费回执。

核对项拉起前拉起后
会话身份清单里的会话编号非空、格式合法、有可读 transcript（对话记录文件）Codex：resumeThread 返回的编号必须来自响应且等于清单，不再用请求编号兜底（空编号会静默新开一个会话）；Claude：交互式 --resume <精确编号>，不带 fork，由 SessionStart 钩子回报实际编号并比对
模型配置解析后的模型标识（含窗口变体）与推理力度必须与原会话完全一致；改了默认值也不能替换原模型；解析不到就 model_unverified，不一致就 model_mismatch实际生效模型不一致则不发任何业务输入
工作目录与分支目录 realpath、git 公共目录、worktree 登记、分支引用一致；共享分支 HEAD 允许因后续节点合法提交前移，不要求相等，也绝不自动 reset / checkout记下当前 HEAD 与未提交改动摘要；把「上次看到的 HEAD → 现在的 HEAD」差异作为首条输入的前置内容，防止模型用退下时的旧文件内容作答
未提交改动把退下时的工作区基线逐条比对：每个条目要么还在且指纹相同，要么已进入合法的后继提交，要么被后继提交改过；解释不了的（被清掉、被外部 reset、worktree 被重建）判 workspace_baseline_mismatch 挂起并列出路径。退下时的 HEAD 必须是现在 HEAD 的祖先，被 rebase / 重写判 head_rewritten 挂起基线到现在的差异先存进待投递信封，不在核验前进模型
写权限不从旧清单复活 TURN顺序固定：① 身份 / 模型 / 目录 / 进程核验通过才算 resume_verified → ② 重建可见终端 → ③ 只有 writer 需求才去申请当前 TURN 与激活 → ④ 申请成功后，信封与原需求一次性投递为首条业务输入。TURN 申请失败时信封保留、不投递

Claude 今天在交互 tmux 模式下明确不 resume（TmuxAdapter.ts 注释「previousSession intentionally ignored」），所以要在会话建立时保存实际会话编号，而不是等进程退出再存。每次拉起都记录排队耗时、启动到身份确认的耗时、需求到首条输入被消费的总耗时；单次启动 180 秒超时，两个厂商同值。

06 · 拉不起来怎么办 · 兜底与故障分开记账

允许继续，也如实承认丢了上下文

图 4 · 两本账互不相通：恢复额度按每次需求算（2 次原会话 + 1 次兜底），故障额度按每个节点尝试算（最多 3 次换人）。

情况自动动作记在哪本账 · founder 看到什么
瞬态启动 / 通信超时确认清理后 10 秒再试一次，总计最多 2 次恢复额度 · 「重试中」，标明超时阶段
会话编号空 / 错、transcript 不可读不再试坏的编号；只有 writer 需求（既有权威的返工 / 阶段唤醒）允许一次明确的新执行兜底；普通聊天消息遇到坏编号只挂起、消息保留，不会因此产生新的写者恢复额度 · 「原对话恢复失败，已重新开始」；兜底只继承原需求的权限，不放大
模型 / 目录 / 分支 / 账号不符、持有人冲突不自动兜底；挂起并给出修复入口不扣任何额度 · 显示期望 vs 实际（脱敏）
清理不明（cleanup_unconfirmed）闩住：不重试、不兜底；founder 面 canResume=false不扣故障额度 · 只能由 Lead 审计重开（留 actor / 时间 / 原因，旧尝试保留，额度从重开点重算）
兜底本身也启动失败不在原需求下继续循环挂起等 Lead；修复后审计重开
成功运行后意外死亡原有死亡证据 + 故障换人故障额度 · 最多 3 次，与恢复额度隔离

兜底是让单子继续的路径：分配新的执行编号、保留节点身份与完成 / 返工历史、重新绑定当前激活与未消费需求，UI 必须明示「原对话已丢失」，不能显示「原会话已恢复」。目录丢失时没有已验证的检查点就不能凭空保证未提交内容，由 Lead 选择可审核的工作副本或重做范围，单子保留可恢复，绝不判「重试耗尽」死单。

07 · founder 面状态

三种状态一眼可分，退下不推进整单进度

在干活
可细分为排队 / 拉起中 / 等授权，都带原因与开始时间。
退下待命
只在确认释放后出现：显示已完成哪一段、退下时间、是否可拉起。长时间待命不报死亡。
出问题
可读原因、重试情况、兜底进展；挂起或未知不会被染成「在干活」的成功色。

列表、项目页、issue 标题（含 💤 待命徽标）、状态 API、Lead 工具和窗口列表共用一个 DTO（页面用的数据结构）：activityState = working | standby | problem，附阶段、退下时间、canResume、原因、上次拉起耗时、是否丢过上下文、观测时间。整单终态是单独的结局，不映射成「出问题」。所有来自源码 / issue 的文本先 HTML 转义，运行时只用 textContent 写页面。

08 · 开放项默认值（Lead 已确认）

整单未结束就保留恢复机会；同目录排队，跨目录最多两个并行

退下后多久内允许拉起直到整单终态（ship / 取消 / 关闭）；不设按小时过期的墙钟 TTL。理由：真实等待可达 55 小时以上，24 小时上限会误伤
多节点同时打回同一工作目录串行（一次只一个恢复、一个写者）；不同目录全机最多同时恢复 2 个，第三个 FIFO 排队；排队超过 5 分钟显示原因但不计失败；容量不足只等待，不换账号、不静默换模型
空转缓冲不设；阶段完成立即开始释放
原会话尝试次数每次需求最多 2 次原会话 + 1 次明确丢上下文的新执行兜底；真实故障仍独立最多 3 次换人
超时退下释放确认 60 秒；单次拉起 180 秒；重试间隔 10 秒。均为设计默认值，统一配置，run 启动时冻结；N5 实测后可调，不能静默换模型绕过
Bridge 重启无需求时只重建监视，不自动拉起所有待命节点

09 · 关键取舍与被否决的方案

复用现有机制，只加必要的核验

候选为什么不选 / 为什么选
否决只把 parked 自报当「不是死了」的标记改动最少，但任意 park、消息清标记、崩溃时序都会误判；自报不能证明安全释放
否决新建一套完整的节点调度系统能统一，但会复制现有工作流、TURN、投递与重试权威，制造第二真源
否决内存 checkpoint（把整个进程内存冻结保存）与「释放进程」目标相悖，且跨厂商不可行
否决15 分钟空转缓冲、只做 Codex 实现段产品决定已作废这些旧路线；全部节点、两个厂商一致
选定在现有工作流执行状态上增加可审计的进程体生命周期，park 只作输入保留原工作流推进、消息、会话、所有权机制；代价是要逐个修消费者，所以研究文档列了全部消费者与普查命令

接受的代价：频繁打回要多付本地重建时间；保留 transcript 到整单结束要占磁盘（空间不足显式挂起，不静默删）；不承诺模型永远逐字记忆，用原会话编号 + 实际上下文问答验收连续性。

11 · 诚实边界

这是工程设计，不是上线验收

本单做了：源码审计（六处打断点重新定位 + 全部额外消费者）、退下协议、拉起核对、失败分账、founder 三态、开放项默认值、分期建议，以及这份说明；文档在设计评审门通过后才交卷。
