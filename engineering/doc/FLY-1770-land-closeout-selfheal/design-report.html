FLY-1770 · land 收尾自愈设计

Issue: FLY-1770 · 设计文档(已过 4 轮 Codex design review, APPROVED)· 2026-08-14 · 文中「land 收尾」= PR 合并之后系统自动做的一串清理:关掉干活的 runner、归档 Discord 讨论串、把 Linear 工单翻成 Done、给这单记上「完成」。
●一句话总结

合并成功后的自动清理,以前只要撞上一次 Linear 打嗝(哪怕只是一次读失败)就会永久卡死、没人知道;这个设计让它自己重试着走完,只有真正需要人的情况才停下并大声喊 Lead。

背景实证:FLY-1751(2026-08-14)。merge 本身成功,但收尾撞上一次 Linear 瞬时读失败,被标成 held(挂起)——reason 字面写着 retryable(可重试),但系统里没有任何东西会重试 held,于是清理级联全断,founder 一小时后自己发现。讽刺的是:那次失败的只是「读一下 Linear」,而 Linear 那边其实一分钟前就已经被 GitHub 集成自动翻好 Done 了。

●出了什么事:FLY-1751 事故链

根因(读代码确认,非推测)

  • 收尾开头有一道「预仲裁」检查(preArbitrate:动手清理前,先确认这单没有被 founder 取消或搁置)。它去 Linear 现读一次状态,读失败时代码注释明确写着「可重试,下一次会重新仲裁」。
  • 但消费这个结果的代码把一切仲裁失败统一记成 held(挂起等人)——held 在整个系统里是死路:重试清单永久排除它,执行入口见到它直接短路返回。「下一次」永远不会来。
  • 另两处隐患一并确认:partial(部分完成,稍后再试)的重试没有退避也没有上限,每 30 秒裸重试、永不收敛也永不告警;Linear Done 写失败会让 run 永远无法记完成。
●修复后的核心流程:失败分三类,retryable 不再是装饰词

三类失败,三种命运

类别例子处理
等待类等 CI 跑完、等 founder 给评审结论不计数、不退避 —— 每 30 秒照常看一眼(合并就是靠它被及时发现的)
可重试类Linear 打嗝、网络抖动、未知失败(未知一律先当可重试,防止静默卡死)按 1/2/4/8 分钟退避重试;只有「连续 5 次毫无实际前进」才转真 held + 大声告警 Lead(附重试历史)
真终态PR 被人关掉、CI 明确失败held 停下等人 + 告警(和今天一样)

「有没有实际前进」不看失败文案变没变,看有没有新落账的步骤收据(每一步清理完成都会写一条不可篡改的记录)——文案换来换去但步骤不前进,照样 5 次封顶。这堵死了「两种失败交替出现、计数永远清零」的漏洞(评审第 1 轮抓出来的)。

●Linear 依赖降级 + 数据模型:本地清理不再被外部服务扣为人质

为什么降级放行是安全的

  • 这一步发生在 merge 之后 —— 不可逆的动作早已完成,剩下的全是清理。
  • 关 runner、清工作目录:就算这单真被取消了,取消处置也要做同样的动作,做了不亏。
  • 唯一真正危险的外部写(把 Linear 翻成 Done)有独立的双重现读守卫:发现已取消就绝不覆写;这次设计又给重试队列加了每次动手前的权限重查。
  • Discord 讨论串归档是可逆的:founder 在里面说一句话就会自动重开(既有机制)。

数据模型:land_operation 表加 7 个新列(存量数据全部不受影响)

列作用
retry_count / retry_epoch_key重试计数 + 「实际前进」指纹(指纹变了才清零)
next_attempt_at退避闸:没到点谁都不许重试(闸设在最底层的领取环节,两条重试路径都绕不过)
linear_done_dispositionDone 义务三态:done(翻成了)/ canceled_refused(founder 已取消,拒绝覆写)/ deferred(Linear 够不着,进队列慢慢试)。三态之一落了账,run 才许记完成 —— 义务不会凭空消失,报告也不再谎报
linear_done_deferred_at / settled_at / last_reason队列的入队 / 出列时刻与最近失败原因(审计用)

工程细节(评审逐轮钉死的合同):重试记账收进一个数据库原子方法(读指纹、判定、写账一个事务);对 Linear 的读写都有硬超时 —— 且超时后保证「不再发出任何新的写请求」+「调用方一定能返回」双不变量,不会出现"超时 16 秒后一条迟到的写把 founder 刚按的取消覆掉"。

●关键取舍与被否掉的方案
选项思路结论
A. 修结构(选定)held 语义纯化为「真的需要人」;可重试失败一律走既有 partial 重试通道 + 有界退避;Linear 依赖降级采纳三条交付一一对应;不新增巡检器
B. 给 held 建「复活器」保留现有逻辑,加一个巡检扫 held 里带 retryable 字样的复活否靠字符串猜语义;held 从此说不清是不是终态;是「加报警器」不是「修结构」
C. 只修一行映射把 retryable 失败改记 partial,其余不动不足FLY-1751 这一种能自愈,但持续故障仍旧 30 秒裸重试永不收敛、Linear 长时间不可达仍卡本地清理 —— issue 三条交付明确要全套

另有两笔显式裁定:存量已 held 的旧账不自动迁移(FLY-1751 那笔按 issue 原文保留为证据;实现时附一份只读盘点贴进 PR,发现意外卡账报 Lead 人工裁定,绝不写通用复活代码);不加任何新开关(founder 既定铁律)—— 这是 bug 修复,行为由回归测试守护。

●诚实边界:这个设计不做什么
  • 不改合并判定、QA 结论、审批闸门的任何逻辑 —— 只治「合并之后的清理」这一段。
  • 不处理 FLY-1715 那个「PR 在系统外被人合并」变体家族的其它成员。
  • 不建全系统通用的「所有 held 自动重试框架」,也不建通用的 Linear 写队列 —— 只治 land 收尾这一族,避免过度工程。
  • 已知边界:一条在超时之前、权限检查通过时已经发出去的 Linear 写请求,理论上可能在超时后才到达 —— 这和今天主路径的固有竞态一致,且被「动手前双重现读」尽力收窄;设计保证的是超时后零新请求。
  • 真机验收(注入 Linear 故障、断网重连、founder 中途取消)属于实现与 QA 节点,不在本设计节点内完成。
