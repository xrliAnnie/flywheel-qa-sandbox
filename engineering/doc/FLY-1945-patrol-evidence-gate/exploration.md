## 目标与已批准范围

修复巡检仪器将有提交推进的 runner 判为停滞，并让机制缺陷必须留下可追踪去向后才允许报告完成。合并原 FLY-1952；本节点仅设计、评审、交付文档。

用户给定的两个验收反例：%7 / PR #891 在 21:16 推进；%8 / PR #892 在 20:11 推进；两行仪器 last_change 都冻结在 17:51:06Z。最终实现必须用固定历史输入将两行判活跃；不得以删除断言或只延长阈值过关。上述时间目前是 issue 提供的证据，不冒充已恢复的原始 push 日志。

机制缺陷 finding 必须三选一：链接已有修复单／新建含根因和验收反例的修复单（先在 Linear 去重）／写明不立原因。账落 Linear，不用 memory 代替；立单不是派工。

## 方案选择

| 方案 | 判断 |
|---|---|
| 延长 60 分钟或对 parked 全部豁免 | 拒绝：不能解决仪器语义，也会掩盖真实卡住 |
| 改为完整终端文本 hash | 拒绝：时钟/动画也能变化，仍把渲染当工作进展 |
| 状态跃迁计时，并用准确绑定的远端提交证据否定停滞 | 采用：分别记录观测新鲜度、状态变化、提交活动；失败显式未知 |
| 机制缺陷只加自然语言提示 | 拒绝：没有去向仍能通过现有 gate |
| 在现有 FINDING 门扩展类别与去向，保留病根账 | 采用：一个完成门组合旧约束与新约束，不新建巡检调度系统 |

## 验收边界

任何 STALLED 必须有同一 runner、同一观察区间的提交交叉核对；有正证据必须撤销该区间的 STALLED，缺证据不得当成“没有 push”。明确等待状态不能自动发“继续工作”误唤醒；状态合法性仍由独立交接/等待巡检检查。
