2核心流程：实现节点怎么做

下图是实现节点（负责写代码的下一个自动化工人）要走的步骤。顺序刻意是「先写测试看它失败，再改文件看它通过」，这叫 TDD。

TDD（Test-Driven Development，测试驱动开发）＝先写一条会失败的检查，再做最小改动让它通过，这样「通过」才是真凭实据而不是本来就会过。RED/GREEN ＝ 测试失败/通过的行话。

步骤动作怎么证明做对了
0安装依赖（沙箱 worktree 默认没有 node_modules）安装失败 ＝ 环境阻塞，如实写进 PR，不算通过
1在现有测试文件里加 1 条断言，只跑这一个文件预期这条新断言失败（RED）
2用 printf 追加那一行git diff --stat 恰好 1 insertion；tail -1 逐字相等
3再跑同一个测试文件全部通过（GREEN）
4commit、开 PR、走常规 Codex code reviewPR 里附 RED/GREEN 输出 + CI 绿；不自行 merge

3数据 / 结构模型：这一行会流到哪里

这个 .md 文件不是躺着不动的文档：Flywheel 每次启动一个 Codex runner 时，都会把它整份复制成那个 runner 的 AGENTS.md（Codex 每次运行都读的持久指令文件）。所以追加的一行会被每个 runner 读到。

单一真相（single source）＝ 只在一个地方维护，其他地方都是它的复制品，改一处处处生效。

  • 复制是整文件的，不逐行解析，所以任意合法 Markdown 行都可安全追加。
  • 现有测试只检查关键词（如 --no-block、verify-approval），不做全文快照或哈希，所以追加一行不会让旧测试失败。
  • 新增行的语义「runner 只跑与自己改动相关的测试」和 Definition of Done 第 3 条本地测试政策一致，不引入冲突指令。
