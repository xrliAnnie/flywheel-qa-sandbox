Mufasa 的回复改走 Bridge,顺手把「信箱 → 壳」的接口写成一页合同

FLY-2442 · Epic FLY-2441 通路① · 设计稿 2026-09-08 · Codex 设计评审 4 轮已 APPROVED · Lead 裁定已落地

一句话

今天 Mufasa(跑在 Codex 上的那位 Lead)回你话时是拿自己的钥匙直接发到 Discord,绕过了 Bridge(所有 Lead 共用的那台「总机」);代码里早就有一条经总机代发的路,只是启动脚本没打开。本单打开它,并把中间挡路的一道门改对;同时把「信先进信箱、再按壳投递」这个形状写成一页合同,以后任何壳都照它接。

这单要解决什么

现状(2026-09-08 逐行核过):Mufasa 的启动脚本(launcher,就是 launchd 每次拉起 Mufasa 时跑的那个 shell 文件)默认 outbound=direct,注释原话是「bypasses Bridge outbound authorization」——绕过总机的出站授权。生产日志三次启动都印着 outbound=direct。

已经存在的那条路:Codex Lead 有一个「经 Bridge」的发送器 CodexOutboundSender,它把回复先写进本地一张持久小表(outbox,发件箱),再 POST 给总机的 /api/lead-outbound/send;总机核对身份与频道、按幂等键(idempotency key,一条回复唯一的编号,重复送达只发一次)去重、用服务端保管的钥匙代发。这条路两端代码都在,总机那张去重表今天是 0 行——生产从没用过。

真障碍:Codex 的运行时里有一道硬门——「经 Bridge 出站」和「跨部门频道」不能同时开,开了就直接报错退出。原因是总机今天只授权 Lead 自己的两个频道,而 Mufasa 配了 #leads-roundtable(圆桌,跨部门共用频道),往圆桌回话会被总机 403(拒绝)。所以不改这道门,Mufasa 根本切不过去;丢掉圆桌又是回归。这单的核心就是把这道门改对。

核心流程:现状 vs 本单之后

左:今天两种 Lead 都是自己直发,Claude 只是发之前先问一声总机的 reply-guard(回复守卫,一个「允不允许」的检查)。右:本单之后 Mufasa 的回复由总机代发;Claude 那边不动(那是 Epic 的 ②)。

一条回复经总机的完整路径(含启动期的自检)

启动期 Mufasa 先向总机「探测」(probe,只问「这几个频道我能发吗」,不真的发):总机说不行(403)、或者总机版本太旧/钥匙不对/路由不存在(400/401/404),Mufasa 一律当场报错退出,绝不悄悄退回直发;只有总机暂时打不通才有限重试、然后继续启动。每条回复:本地先记账 → 总机授权 → 去重 → 代发 → 两边都记「已发」。

数据与结构

新东西在哪做什么
roundtableChannel~/.flywheel/projects.json 里 Mufasa 这一行声明「这位 Lead 可以往哪一个圆桌频道回话」。总机只认这里声明的,不认全局配置、不通配;没声明的 Lead 往圆桌发 → 403。圆桌下面的话题线程按「父频道在不在授权集」继承。
probe: true总机 /api/lead-outbound/send 的请求体只走到授权那一步就返回 authorized,不去重、不发送。启动期自检用它。
[lead-outbound] 日志行总机日志 /tmp/flywheel-bridge.log每次响应一行:项目、Lead、频道、结果、消息 id、幂等键。永远不含正文。这是验收「日志可证」的读取点。
启动脚本默认 bridgerun-codex-lead-mufasa-tui-fullaccess.shdirect 只作显式回滚,启动时大写警告。总机的钥匙名从 TEAMLEAD_API_TOKEN 别名过来,不新增配置。

合同页:「信箱 → 壳」的五段接口

你在 FLY-2439 说的形状——「信件先投到 Mailbox,然后再 batch 投到 Claude Code 或 Codex,只是投递过程中因为 Harness 不同会有一些区别」——今天 Claude Lead 和 Codex Lead 就是这么跑的。合同页(仓库里 mailbox-adapter-contract.md)把它写成五段,每段给接口、不变量、两边实现、新壳要提供什么。

段谁拥有ClaudeCodex新壳要提供
① ingest(取信)各壳自带Discord 插件 → 子进程写库3 秒轮询 → 写库一个会调 ingestDiscordChat 的取信器
② mailbox(信箱)共用同一张 mailbox 表;权威一直在这里,直到拿到持久回执无,不许绕过
③ 投递泵共用(Bridge)活跃 1 秒 / 空闲 30 秒轮询;每批最多 10 条;同时最多 3 批在飞;30 分钟内没 ack 就重投,3 次到期进死信无,不许自己写泵
④ 最后一跳各壳一个适配器两阶段写 JSON 文件 + 边车;Claude 二进制自带 poller 自己读签名的 unix socket 交给 TUI 进程,由它入 journal(日记账)一个 LeadDeliveryAdapter + 一个 ack 通道
⑤ 回程总机授权;发送按壳问 reply-guard,再自己直发总机代发(本单起)必须经总机授权;推荐直接复用总机代发

为什么 Codex 的第④段砍不掉(原注释)

agent-team-transport/src/types.ts:308 — builtin-receiver: vendor binary polls mailbox itself (claude-code). external-watcher: needs IMailboxWatcher + tmux send-keys (codex).
Codex 二进制不会自己读文件,必须有人把包好的一轮推进去。
CodexLeadInboxSocket.ts:4-7 — The Codex Lead router lives in the windowed TUI sidecar process. The Bridge therefore cannot mutate journal.db directly: doing so would durably accept a row without waking the router's in-memory pump.
journal 属于 TUI 那个进程;总机是另一个进程,所以要一条 socket 把批交过去,由拥有它的进程自己入账。
LeadJournal.ts:5-9 — a Codex app-server thread can execute arbitrary shell/MCP side-effects (gh merge, flywheel-comm). On a crash, naively replaying an input could double-fire those side-effects.
journal 存的是「这条输入走到哪一步了」,让崩溃恢复能证明该不该重跑,而不是猜。Claude 侧对应物是 jsonl 边车,只是不是 sqlite。

一个前提修正:Claude Lead 其实不是「经 Bridge 出站」

issue 原文写「改为经 Bridge 出站(与 Claude Lead 一致)」。审计发现 Claude Lead 的回复其实是:插件先 POST 总机的 /api/discord/reply-guard 问一声允不允许,允许后自己 ch.send 直发(插件 server.ts:375 与 :1342);总机打不通时按内容分类 fail-open(放行)或 fail-closed(拦下)——这正是 Epic ② 要收紧的东西。而 Codex 的 bridge 模式是总机代发:钥匙只在总机、持久去重、403 硬拦,比 Claude 那条更强。

所以「与 Claude 一致」的准确说法是:两边都必须经总机授权。Tadashi 已裁定按这个理解做,不给 Codex 另造一套 reply-guard,并会据此向你更正昨晚的说法。

Claude Lead(今天)Codex Lead(本单后)
谁发Lead 自己总机代发
钥匙在哪Lead 进程里只在总机
总机打不通按内容 fail-open / fail-closed(②)发不出去,记 ambiguous,不会绕过总机
跨重启去重无有(持久表 + 永不盲重发)
授权粒度只判「顶层是否含 issue 号」按(项目、Lead、频道)判归属

关键取舍与被否决的方案

方案结论为什么
A · 翻 launcher,顺手把 Mufasa 的圆桌配置删掉否决零代码,但你在用圆桌;把 Mufasa 踢出圆桌是回归,不是「一致」。
B · 总机授权集加上「该 Lead 声明的圆桌 + 其线程」,运行时那道硬门改成「启动时问总机」选中不动 journal、不动 Claude、不动 Raya;改动集中在总机授权与一处启动自检。Tadashi 加了三条约束:只认 projects.json 里为该 Lead 声明的圆桌(不通配)、必须有「未声明 → 403」的阴性测试、探测遇 403 必须报错退出、绝不静默退回直发。
C · 把「Lead 能发哪些共享频道」搬进 projects.json 做唯一真源,launcher 也从那里读以后最干净,但要动 launcher 的频道来源和 Claude 侧同名配置的消费者,超出「launcher 配置选择」的范围。现在两处各声明,漂移靠启动探测 403 抓出来。
D · 让 Codex 也做成「问一声 reply-guard 再自己直发」(字面上和 Claude 一样)否决那是退化:放弃已有的持久去重和服务端钥匙。Epic 的方向是各壳都收敛到总机授权,② 是把 Claude 收紧,不是把 Codex 放松。

几个具体的小取舍

  • 探测在进程起来之后做:Codex 进程只有 start() 之后才接管那条 WebSocket;探测失败要能把它关干净,所以顺序是先起进程、再探测、失败就自己关掉再报错(Codex 评审第 3 轮抓到的资源泄漏点)。
  • 探测有总时长上限:每轮对所有频道并发问、单次 5 秒超时、最多 4 轮、间隔 10 秒 → 最坏 50 秒,与频道数无关。
  • 总机打不通 ≠ 报错退出:总机在更新窗口会停几秒再起;这时 Mufasa 若恰好重启,应该等一等再继续,而不是像 FLY-1597 那样崩 205 次。

上线顺序与回滚

  1. 合并前(你或 Tadashi 做):在 ~/.flywheel/projects.json 给 mufasa-lead 加一行 "roundtableChannel": "1512578695468941333"。今天的总机会忽略这个未知键,零影响。有一条 jq -e 检查当门,现在是 false。
  2. PR 合入 main → updater 窗口自动重启总机,带上新授权与探测分支。
  3. Mufasa 不会自动重启(启动脚本改动不在「重启全体 Lead」的名单里),它继续直发,直到下一次重启。
  4. 你的窗口重启 Mufasa → 读到新脚本 → 走总机 → 启动自检通过。

回滚:只想退出站 → .env 加 FLYWHEEL_CODEX_LEAD_OUTBOUND=direct 重启 Mufasa,记忆线程不受影响。想整单回滚 → 先把 Mufasa 切回直发并重启,再 revert 总机;反过来做会让在跑的 Mufasa 往圆桌回话被 403。

顺序错了会怎样:Mufasa 若先于新总机重启,探测会拿到旧总机的 400(不是 403),同样报错退出、日志明示「总机比 FLY-2442 旧」;等总机更新后再重启即可。

验收怎么证明「这条回复真的经了总机」

三处证据必须按同一个幂等键串起来,不能各取「最新一行」:

  1. 在 #mufasa 发一句带唯一标记的话,等回复。
  2. 总机日志里找这条回复的 [lead-outbound] … status=sent 行,记下频道、消息 id、幂等键。
  3. 总机去重表按这个键查 → sent + 同一个消息 id。
  4. Mufasa 本地发件箱按这个键查 → sent + 同一个频道。
  5. 用 Discord REST 按频道 + 消息 id 查 → 200,内容就是那条回复。
  6. 圆桌再来一遍;另外对一个没声明的频道发探测 → 必须 403。

诚实边界:做什么、不做什么

做 Mufasa 启动脚本默认走总机;总机授权集加「该 Lead 声明的圆桌 + 其线程」;运行时硬门改成启动探测(403/400/401/404 一律报错退出,绝不退回直发);总机出站审计日志;合同页一页;本页。

不做

  • 不动 journal、不动 socket、不动 Claude 侧的 reply-guard 与 fail-open(②)、不动 Raya(④)。
  • 另一位 Codex Lead codex-infra-bot-lead(Claw 的席位,跨部门频道是 Alerts)保持直发——机制通用,但翻它是另一张单。
  • Mufasa 的主动发言 lead_actions.discord_send(FLY-350)保持直发,有自己的审计;本单只改「回复」。
  • Mufasa 的实际重启由你或 Tadashi 在窗口做;implement 与 QA 节点不自作。
  • Epic FLY-2441 里引用合同页:本机 Linear 凭据 401,由 Tadashi 补链接。

没验证过的:总机拿 Mufasa 的钥匙查圆桌线程的父频道是否总有权限(理论上有,QA 实测一次);Bridge 崩溃空窗的「恰好一次」仍靠去重表,既有限制不动。
