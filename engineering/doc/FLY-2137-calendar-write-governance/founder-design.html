FLY-2137 · 给你的 Google Calendar 上锁

Issue: FLY-2137 · 设计节点交付 · 2026-08-31 · 配套文档: engineering/doc/FLY-2137-calendar-write-governance/

① 一句话总结

给你的日历立规矩:只有 Raya 排会模块被授权自动写你的真日历;Claude agent 会话里的日历写命令由守卫拦截(先只记账,你批了才真拦),每日只读清扫兜底。

如实说明:这套守卫是行为护栏,不是牢不可破的安全边界——只要机器上的 Google 凭据没隔离,绕开守卫的技术路径仍然存在(⑧ 有细账)。根治方案(凭据隔离)将另立专项,并作为本治理目标真正关闭的前置。

agent = 在你机器上干活的 AI 会话(各 Lead、各 runner、QA 都是);守卫 = 装在每个 AI 会话命令入口的检查程序,命令执行前先过它;凭据 = 登录你 Google 账号的钥匙文件。

② 出了什么事(为什么要定这个规矩)

2026-08-29 凌晨,FLY-2130 的 QA 在测试期间实测发现:另一个 agent 看到测试消息后,自作主张往你的真日历建了一个假会议(「FLY-2130 日历同步验收 — 与 Tadashi」),还带 10 分钟邮件提醒。QA 及时删掉了,否则你会收到一封假会议提醒邮件。

  • 根源:登录你 Google 账号的命令行工具(gog 和 gws,两个能读写你 Gmail/日历的终端工具)在这台机器上全局可用——任何拿到 shell 的 agent 都能直接建、改、删你的日程;
  • FLY-2130 的正路写入带隐形标记、有回执、可审计;这次的野路写入零标记零审计,事后无法归因;
  • 你的日历是个人高敏面:假会议、假提醒直接打扰到你本人。

③ 治理后的写入格局(核心流程图)

读图要点:

  • 唯一授权的自动写入方:Raya 排会模块是独立后台程序,每个事件带 raya_meeting_id 隐形标记(写在事件的扩展属性里,你在日历界面上看不到,但程序能查),不经过守卫——因为它根本不在 agent 会话里;
  • agent 会话里的日历写命令按命令语法精确识别(建、改、删、回复邀请、专注时间、转移日历所有权、改共享权限等全部写形态,gog 和 gws 两个工具都覆盖);不认识的新写法一律先当成写来拦(宁可误拦让 agent 来问,不放过);读日历不受任何限制,gws 里与日历无关的服务也不会被误伤;
  • QA 测试日历:QA 需要练手时写专用测试日历(和你的真日历完全隔离);守卫逐字核对目标日历号,命令里不写目标(默认=你的真日历)不算豁免;放行也记账;
  • 没有特批旁路:评审明确否决了「agent 带特批标记就放行」的设计——标记是 agent 自己就能加的,证明不了你授权过。确需给某链路写权限时,走 ⑤ 的名单公开加名,由你批准;你自己加日程用 Google 界面或自己的终端即可(守卫不装在那里);
  • 每日清扫:只读扫一遍你的真日历,汇总「无标记 + 新出现 + 内容像机器建的」可疑事件 + 守卫账本摘要 + 模式一致性检查(一天最多一条,零发现完全安静,绝不删任何东西)。

④ 上线路线 + 你要做的决定

待你决定守卫合入后先以 audit(只记账)模式运行:所有本该拦的命令照常放行,但记一笔账,每日清扫会汇总给你看。真正开拦(enforce)必须由你批准,二选一:

选项含义适合
audit(只记账)不拦任何命令,只记录 + 每日汇总。想先观察一段,确认不会误伤
enforce(开拦)agent 会话里的日历写命令被真实拦截(QA 日历与特批除外)。确认规矩后的常态

你批 enforce 后:Lead 写入一份永久批准回执(记你的批准消息编号)+ 模式文件,即刻生效(零重启)。此后模式文件若丢失或损坏,守卫宁拦不放(fail-closed)——不存在「误删文件就静默不拦了」。回滚到 audit 也必须你授权后显式写回(同样留痕),不是删文件。QA 随后回归验证:Raya 排会仍正常写 ✅、野路演练确实被拦(用替身命令,绝不碰你的真日历)❌、QA 日历确实放行 ✅、模式文件故障时确实拦 ✅。

⑧ 诚实边界:这套规矩管什么、不管什么

管得住

  • 所有 Claude agent 会话里的 gog/gws 日历写命令——这次实测事件的路径正是这一类,含各种包裹写法(转一层 shell、加 env 前缀等);
  • 事后归因:每次命中都有账,谁在什么会话里试图写、被怎么处理,查得到。

管不住(如实说明)

  • Codex / Gemini 等非 Claude 跑道的 agent 直接执行 shell——守卫装在 Claude 会话入口,它们不经过;
  • agent 把写命令藏进脚本文件再运行——守卫只看得见「运行了某脚本」;
  • 直接拿机器上的 Google 凭据调 API——凭据仍是机器全局可读的;
  • 清扫对以上绕过形态只有启发式发现能力:Google 不告诉我们事件是谁的程序建的,只能靠「无标记 + 新出现 + 内容特征」圈嫌疑——内容不含特征词的绕过写入可能完全发现不了,所以清扫只报告、由你目视裁决,不能当保证。

因此本单的定性是「规矩 + 行为护栏 + 检测」,不是「机器强制的唯一写入方」。根治 = 凭据隔离(Raya 持独立写钥匙,agent 环境读不到你的钥匙)。实现节点开工时会开出独立专项 issue 并挂在 FLY-2137 上;该专项落地前,「唯一写入方」这个治理目标不算真正关闭。
