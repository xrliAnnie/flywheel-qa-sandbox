# Design Review — plan.md (Round 1)

Date: 2026-09-02
Author: Codex
Status: CHANGES REQUESTED

## Summary

方案的主方向正确：把 8 个既有事实源投影为统一阶段、复用现有 Lead inbox 告警链、并以注册表统一冻结正门，符合 founder 要求的通用对象边界。但当前计划在 loop 入边判定与上下文持久化、30 分钟驻留到期、receiver 单一所有权、完成前清信以及跨 StateStore/CommDB 恢复事务上仍有不可实现或会失真的契约；第 2 起事故也只覆盖了“看见死信”的半边，尚未保证改派。以上问题会使 A1/A2/A3/A6 在测试表面通过时仍重现原事故，因此本轮请求修改。

## What's Good (Keep)

- 保留“合同是只读投影、只持久化 episode”的方向；它避免给 8 个家族再造一份会漂移的镜像账本。
- 固定 `STAGE_DEADLINES_MS`、`SEVERE_MULTIPLIER` 与 `RESIDENT_GRACE_MS`，不引入 env/flag，并复用 `workflow_engine_escalation` → Lead inbox → issue thread，准确落实了 Lead 的红线。
- M0 先建 8 起事故回放床、source 状态映射穷举、负向零写守卫与 exact-head CI 的验收框架是合适的。
- 判死引入 delivery evidence、移除 `rework_activation_stalled_held` 新写入、以及让真实节点完成不再被 `awaiting_receipt` CAS 拒绝，直接击中了事故 #4/#5/#6 的共同根因。
- 正门沿用 carrier-redrive 的 loopback、master token、canonical digest 与一次性 confirmToken 模式，没有扩张权限模型。
- 复用 FLY-2211 的 reown 入口和 FLY-2216 的心跳/分类/episode 模式是正确的架构落点；多数文件路径和所引函数存在，但需要补齐下面列出的相邻消费者。

## Issues & Recommendations

1. **[BLOCKER] loop 常驻判据与硬约束相反，而且通用上下文没有穿透现有 dispatch/reown 链。** Lead 明确要求“只在有 loop 入边的节点”park，plan §0 也如此写，但 M3 用 `loops[].to|from`，会把仅有 loop 出边的源节点也常驻；research 的通用性段落反而正确地写成“loop 类型边的目标节点”。更关键的是，当前 dispatcher 只给 `isWorkflowPhaseRole(node.type)` 设置 `shareParentBranch`，Blueprint 又以 `shareParentBranch` 为 `phaseKeepAlive` 前提，所以名为 `general` 的任意 loop 目标不会拿到常驻标记；重启恢复仍只从 `launch.phaseRole` 重建 `{role}`。建议把谓词唯一化为 pinned run snapshot 上的 `snapshot.manifest.loops.some(loop => loop.to === nodeId)`，并把冻结后的 `{loopCapable: true, nodeId}` 显式贯穿 `StartRequest`/`RunDispatcher`/`BlueprintContext`/`AdapterExecutionContext`/Codex immutable launch snapshot/session state/FLY-2211 reown/Claude completion；不要借用控制共享 worktree 的 `shareParentBranch`。增加“任意名称的 loop target 正例、仅 loop source 负例、两家 vendor、Bridge 重启后不丢字段”测试。证据：`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:13,44,100`；`engineering/doc/FLY-2248-generic-delivery-contract/research.md:96,127`；`packages/teamlead/src/bridge/workflow-engine-dispatcher.ts:2774-2785`；`packages/edge-worker/src/Blueprint.ts:1622-1634`；`packages/core/src/adapter-types.ts:206-210`；`packages/teamlead/src/bridge/codex-session-reown.ts:139-148`；`packages/claude-runner/src/CodexTmuxAdapter.ts:912-935`。

2. **[BLOCKER] 30 分钟 resident grace 没有实际会执行的到期路径。** 计划只在 `classifyTerminalStatus` 上加分类，但当前 terminal 被消费一次后，`enterPhaseHold()` 会清掉 `terminalSeen`；随后 `held` 分支明确“不做 budget check”，只等 wake 或 transport close，因此 30 分钟后不会再次调用分类器，也不会自然 terminal。现有 durable `phaseHold` 只保存 `enteredAt` 与剩余 budget，没有 grace deadline；Bridge/adapter 重启后的到期重建、到期与 wake 同时发生时的胜者、Claude `loop_park` 到期的确切 owner 也未定义。建议把 `graceStartedAt/graceExpiresAt/nodeId` 纳入版本化 durable hold state，在 held loop 中以 deadline 驱动一次有 fence 的 terminal transition，并为 Claude 指定同一语义的 durable park receipt/cleanup owner；补 crash/restart mid-grace、到期前后 wake、wake-vs-expiry race、重复 cleanup 测试。证据：`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:102-105`；`packages/claude-runner/src/codex-daemon-client.ts:981-1006,1292-1300,1486-1500`；`packages/claude-runner/src/codex-phase-lifecycle.ts:32-39,71-91,342-370`。

3. **[BLOCKER] `ResidentReceiverSupervisor` 与 phase lifecycle 的单一所有权、边界状态和 admission vocabulary 尚未定义。** 当前 `CodexPhaseLifecycleController.confirmHoldPaused()` 会覆盖 `watcher.onDelivered` 并启动 watcher，`leaveHold()`/`stopIntake()` 会停止它；若按计划把同一 watcher “注入” lifecycle，receiver 仍会在每次离开 hold 时被拆掉，违反“工人整个生命周期武装”，还可能出现 double-start/callback 覆盖。Supervisor 也没有现成接口获知 `boundary`，`IMailboxWatcher.health()` 只返回 `ok/lastEventTs/pendingCount`，不足以产生计划中的 `lastPollAt/running`；此外计划写入 `admission_state='boundary'`，但稳定标识只新增 `deferred_midturn`，现有类型只认 `queued|duplicate|suppressed_cap|skipped_no_transport|null`，多条 push/ack/escalation SQL 只处理 `queued`。建议规定 supervisor 是 `start/stop/onDelivered` 的唯一 owner，phase lifecycle 只暴露 durable boundary observation 和 wake-activity signal，不得停止 receiver；边界到件继续用既有 `queued`，仅 mid-turn 使用 `deferred_midturn`，并列出所有 admission-state reader 的迁移矩阵。扩展 health 接口前先定义可观测字段语义，并以 ownership 测试断言一个 execution 只有一个 callback、一次 start、仅 terminal disarm。证据：`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:94-101,141`；`packages/agent-team-transport/src/types.ts:199-214,302-308`；`packages/claude-runner/src/codex-phase-lifecycle.ts:247-280,372-426,441-452`；`packages/claude-runner/src/CodexTmuxAdapter.ts:982-1007`；`packages/flywheel-comm/src/db.ts:531-547,3509-3512,3578-3588,3690-3708`。

4. **[BLOCKER] `consume_pending_mail` 的 digest 不是“已读”证明，且 StateStore/CommDB 之间存在无法忽略的 TOCTOU。** `session_completed` 的权威事务现在完全在 StateStore 内完成，mailbox 与 phase wake 则位于独立 CommDB；plan 把 `listPendingMailForExecution` 放进 StateStore 入口，却没有给它 CommDB 读取/失败契约，也无法把“检查无未读”和写 completion receipt 原子提交。第一次响应还会把 ids 与 sha256 直接交给 runner，runner 无需 ACK/started 即可立即原样重试，因而 digest 只证明拿到了挑战值，不证明读过信；research 又说匹配旧 digest 时即使出现新信也放行，而 plan 文案看起来要求匹配当前 ids，两种选择分别造成漏交付或持续来信下饿死。建议引入 StateStore 内 durable、一次性 drain challenge receipt（绑定 execution、activation、completion submission digest、精确 mail set/watermark），由 event route fail-closed 读取 CommDB；二次请求必须核验 challenge 尚未消费，并验证覆盖的 mailbox 已 ACKED、phase wake 已 started/finished，而非只比较 caller 提供的 hash。明确 challenge 后新到件进入下一 generation 还是触发有界 park/escalation，并覆盖“发 challenge 后崩溃、清信时新信到达、重复 event_id、错误/旧 digest、CommDB 不可读”测试。证据：`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:104,108,159-160`；`engineering/doc/FLY-2248-generic-delivery-contract/research.md:101-105`；`packages/teamlead/src/bridge/event-route.ts:986-1057`；`packages/teamlead/src/StateStore.ts:38925-38950,39363-39584`；`packages/flywheel-comm/src/commands/complete.ts:377-424,446-470`；`packages/flywheel-comm/src/mailbox-schema.ts:79-124`；`packages/flywheel-comm/src/db.ts:175-199`。

5. **[BLOCKER] M4 的“所有 resume 在同一 `db.transaction`”无法覆盖 CommDB 与外部 send。** `releaseMailboxSlotsTx` 操作 CommDB mailbox，`turnHandoffTx` 操作 CommDB `three_stage_turn` 且还要求配对 `send`；`hold_resumed/hold_resume_refused` 则是 StateStore run event。两个 SQLite 文件和外部发送不可能处在同一个本地 transaction 中，所以按当前文字实现要么先解冻后发信失败，要么发信成功后审计/StateStore 回滚，重放还可能重复 side effect。建议让每个 shape 声明 authoritative store 与 effect boundary：StateStore 先持久化带 canonical digest/clientRequestId 的 resume operation/outbox，CommDB handler 在自己的 transaction 内 CAS 并写 receipt，外部 send 从 durable outbox 投递，最后幂等投影 `hold_resumed`；拒绝事件使用独立短事务，不能依赖将要回滚的动作事务。为两个跨库 shape 增加每个 commit barrier 后崩溃的重启回放测试；不要再声称跨库原子。证据：`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:113-118,125,160`；`engineering/doc/FLY-2248-generic-delivery-contract/research.md:160-167`；`packages/flywheel-comm/src/db.ts:91-100,114-140`；`packages/flywheel-comm/src/mailbox-schema.ts:79-124`；`packages/teamlead/src/bridge/workflow-carrier-redrive-routes.ts:110-145,204-228`。

6. **[BLOCKER] 事故 #2 只做了 undeliverable 告警，没有实现或验收通用改派。** research 的 incident→test 明确要求“合同告警且 land 家族把清理令改派给存活收件人”；M1 测试却明确只把它列为“undeliverable 半边”，M2/M3/M4 也没有 undeliverable 的 mutation owner 或 resume shape。这样系统只会更快告诉 Lead “信死了”，并不会满足“欠条必达”；§6 文案写“已改派/需要正门处理”还会在未改派时制造错误事实。建议增加与节点名无关的 `undeliverable` disposition owner：在 mutation time 重新解析 pinned run/transition 的当前接收 authority，以 generation/activation fence 铸新 delivery；没有可证明接收者时生成明确可 resumable 的 hold shape。replay #2 必须断言新 recipient 的 durable delivery/settlement（或可操作 hold），而不只断言 alert；文案按实际 outcome 分成 `rerouted` 与 `operator_required`。证据：`engineering/doc/FLY-2248-generic-delivery-contract/research.md:175-180`；`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:65-76,113-123,168`；`engineering/doc/FLY-2248-generic-delivery-contract/exploration.md:73-80`。

7. **[HIGH] `superseded_by_completion` 的选择范围过宽，且终态语义没有区分“正常结清”和“完成抢先”。** 当前两处 CAS 都绑定唯一的 `activePath.request_id`；计划改成按 `runId/nodeId/attempt` 扫所有 route revision，并允许 `pending` 到 `needs_lead` 的 7 种状态、0..n 行，这可能把同一 attempt 上另一个 revision/并发 founder obligation 或需要决策的 debt 静默核销。把正常 `wake_delivered` 也一律改成 `superseded_by_completion` 还会丢失“已送达后正常 settled”和“未获 receipt 但工作事实已完成”的诊断差异。建议仍从 active verification path/当前 carrier question 得到精确 contract id，并在事务内复核 route revision、target execution/activation 与 completion receipt；仅对完成确实越过的 pre-settlement 状态使用 `superseded_by_completion`，已 `wake_delivered` 的正常路径保留 `completed/settled`（若确要统一，必须把该语义写进 canonical mapping 与运维文档）。0 行只在同一 completion receipt 的幂等 replay 时成功，否则继续报 invariant。增加 stale revision、同 node/attempt 两张债、wrong execution、policy-held、重复 completion 测试。证据：`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:22,84-87`；`packages/teamlead/src/StateStore.ts:41536-41579,41616-41647`；`packages/teamlead/src/StateStore.ts:20755-20770`。

8. **[HIGH] 迁移与旧二进制兼容结论不成立；在当前约 454 MiB StateStore 上风险不足以由“行数/主键相等”覆盖。** 旧代码并非都使用显式 open 集：`listOpenReworkDeliveries` 与 `listOpenGateAuthorities` 使用 `state != 'completed'`，所以旧二进制会把 `superseded_by_completion` 当作 open；carrier redrive 更会以同一谓词把该终态重置成 `pending`。计划只列了部分 consumer sweep，却据此断言 rollback 无需数据迁移。重建表还必须保存/重建所有 index、trigger 与 FK 行为，并在外键关闭期间验证 `foreign_key_check`；carrier redrive receipt 本身引用 carrier 表。建议先把所有消费者改成正向 open-state allowlist 并列完整 sweep（含 row unions、diagnostic/patrol、carrier-redrive），把旧二进制兼容改为“不支持跨 schema downgrade”或提供真实兼容证据；迁移验收增加 pre/post `sqlite_master` 对象集合、`foreign_key_check`、`integrity_check`、全列值 digest、重复启动，并在生产大小副本上测启动时间、峰值磁盘与内存。证据：`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:85-90,133-150`；`packages/teamlead/src/StateStore.ts:8890-8915,8940-8950,47351-47368`；`packages/teamlead/src/StateStore.ts:2484-2543,2545-2613`；`packages/teamlead/src/StateStore.ts:20044-20057`；`packages/teamlead/src/StateStore.ts:56204-56254`。

9. **[HIGH] episode 的“阶段时钟”和 progress token 会被维护性 churn 重置，唯一 open 索引的换代规则也缺失。** research 让 rework/carrier 用 `generation` 作 progress token、`updated_at` 作 `stageEnteredAt`；但 generation 会在同一阶段每次 claim 时增加，pending/turn_granted 的 release 也会改 `updated_at`，这不是业务投递进展。结果是一直重试但永远没送达的合同可以不断换 token/刷新时钟而永不超期；若旧 episode 仍 open，新 `<stage>:<progressToken>` 主键又会撞上 `(family, contract_id) WHERE closed_at IS NULL`。计划还没有定义 source 行消失、terminal/frozen、阶段倒退或 token 变化时怎样原子 close/reopen。建议为每个 source 明确只随 canonical stage 前进的 immutable `stageEpoch/stageEnteredAt`（必要时从状态事件推导或在源表加专用时间列），把 lease owner、retry generation 排除在“进展”之外；写出 watch 的完整 transition table和 mutation-time CAS，包括 disappeared/terminal/recovered/severe alert retry。另需落实 research 已要求的 turn_wake 20 分钟既有 question 与新 15 分钟 episode 共用 identity/去重，否则会给 Lead 双告警。证据：`engineering/doc/FLY-2248-generic-delivery-contract/research.md:28-36,40-47,62-73`；`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:33-34,63-76`；`packages/teamlead/src/StateStore.ts:29760-29863,29905-29938,30492-30518,47450-47548`；`packages/flywheel-comm/src/db.ts:5564-5624`；`packages/teamlead/src/bridge/turn-wake-patrol.ts:34-35`。

10. **[HIGH] hold inventory 的静态守卫不能证明 21 个 shape 都被覆盖。** M0 只 grep 两个文件里两种精确拼写的 `status = 'held'`，但 registry 同时声称覆盖 run、rework delivery、carrier、land、mailbox slot 和 CommDB TURN；后 7 类并不都写 `workflow_run.status`，而通过 helper/dynamic SQL/其他文件新增的 held writer 也能绕过该 grep。14 个 run 写点的 golden 与 21 个 shape id 做集合相等，本身不是同一维度。建议把守卫拆成两份：`hold-mutation-inventory` 记录 `{store/table, file, symbol, mutationKind, shapeIds}`，`hold-shape-manifest` 记录每个 shape 的 detect/resume owner；测试验证每个权威 held/frozen/undeliverable mutation 都映射至少一个 shape、每个 shape 都有 fixture，并将新增写入集中到少数 audited helper（或用 AST/导出符号 allowlist 扫描），而不是依赖字符串空格。理由前缀迁移也要做 consumer sweep，避免现有代码按旧 `last_error` 字符串分支时失效。证据：`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:41,53-56,113-125,160-163`；`engineering/doc/FLY-2248-generic-delivery-contract/research.md:137-169`；`packages/teamlead/src/StateStore.ts:26371-26416,34232-34370,48221-48287,52146-52238`；`packages/flywheel-comm/src/mailbox-queue.ts:1192-1232`。

11. **[MEDIUM] 验收词汇与 revert 单元互相矛盾，会产生“测试绿但契约含义不同”的空间。** research 规则表把阶段 `< received` 的结果称为 `hold`，plan 的负向守卫却要求任何路径不得 `held`，而 M2 又说“hold 已不存在”；当前 `PhaseActorReentryDecision.kind='hold'` 只是 coordinator 的 defer/release 决策，并不等于写 `workflow_run.status='held'`。应把返回值改名为 `defer` 或把验收明确成“允许 transient decision=hold，但不得写 run/delivery held 状态和对应 event”。此外 §4 先说每个 milestone 可独立 revert，紧接着又说 M1 必须与 M2 一起 revert；应把 M1+M2 声明为一个 deploy/revert 原子组，或保留旧 clock 到 M2 的最终 cutover。M0 也应使用真正失败的 `it`，不能以 `it.todo`/skip 充当 8 个 RED，并逐事故保存能证明失败原因的输出。证据：`engineering/doc/FLY-2248-generic-delivery-contract/research.md:109-122`；`engineering/doc/FLY-2248-generic-delivery-contract/plan.md:50-58,81-90,146-160`；`packages/teamlead/src/bridge/phase-actor-reentry.ts:7-22,30-67`；`packages/teamlead/src/bridge/workflow-rework-coordinator.ts:488-511`。
