01 · 生死怎么判

本机图形进程被权限策略拒绝，标准参数重试仍失败。Mermaid 源码已随设计保存；这里暂未显示图，不代表已完成视觉验证。

流程内容：按执行身份读进程证据。活着保留工作；未知保留现场；已死核对当前代次与回执，批准退下进入待命，意外退出终结后再按需要恢复。

daemon 是在终端窗口之外持续工作的后台进程；窗口关掉不等于它退出。进程代次是同一个执行身份第几次实际启动，用来防止旧退出消息伤到新进程。

控制器是负责启动和恢复工作进程的程序。它正常重启后台进程时，短暂空窗只能标为无法确认；结束任务后必须留下对应代次的退出记录，旧控制器不能偷偷重启。

可靠证死的当次处理就结束物理体，不再等缺窗次数、停驻期限或人工改账。探测失败则明确说无法确认，不能判死，也不能再造一个写代码的体。

02 · 一份判据，两处记录

结构内容：执行身份和进程代次绑定物理证据；工作流主账记录结果，再由可重放的结账义务更新通信记录。窗口状态单独展示。

进程证据
核对真实进程、启动时间、所属会话与代次；窗口和自报停驻不作判据。
StateStore
工作流主账：记录体的结局、阶段交卷和谁能继续工作。
CommDB
通信记录：跟随主账结束 running（正在运行）投影，清掉失效停驻声明。
结账义务
跨库更新中途崩溃，重启后从同一条记录继续；重复执行不多造替身、不丢意见。

TURN 是共享工作树的写入权。转交必须核对原持有者与版本；尚未处理的 founder 意见保留来源；旧体无法接收时明确报告失败，需要继续时再发给合法接手者，不假装已读。

03 · 删掉哪些错误分支

  • 删除“缺窗就是死”和“窗在就是活”。
  • 删除停驻、等审标签对意外死体的豁免。
  • 删除“必须先人工改成终态，系统才肯换体”。
  • 删除“通信账仍在跑，所以不探测或不结账”。
  • 删除“没交卷的进程退出也算正常完成”。
  • 删除 run 终止时按 completed 标签漏掉仍活着的体。

run 是一张任务单的一轮工作流；completed 是账上的完成标签，不能单独证明进程已经退出。窗口恢复与清理仍保留，但不能再决定体的生死。

05 · 保留的边界与取舍

保留正常退下：FLY-2808 已定义由控制器批准进程退下、之后恢复同一会话。这种有精确回执的待命不能误当故障；仅自报 parked（停驻）没有这个特权。

保留真实交卷：完成回执已经被接受时，体后来死亡不能抹掉成果或重跑该阶段。没有交卷回执的异常退出不能冒充完成。

不选多等几次缺窗：只是延后同一种误判。不选“账面终态就直接换”：旧进程可能还在写代码。不选全删等待状态：会破坏等审、返工和批准待命。

旧体若缺少可信进程绑定，必须显示无法确认并列入迁移清单，不能靠猜测补死亡证明。FLY-2903 的收体改动已合并；实现时先同步并复用，合并记录不能当成已上线或本单已验收的证明。
