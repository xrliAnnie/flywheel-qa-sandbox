FLY-2919 进程生死单一真源 — 设计说明

Issue: FLY-2919 · 日期 2026-09-28 · 设计节点 eng_design · 基线：本房 checkout（沙箱 main 1855f7a1a）· 文档：engineering/doc/FLY-2919-process-liveness/

一句话：一个「体」（替某张 issue 干活的 Claude / Codex 进程）是死是活，只问它自己的进程；tmux 窗口只是看它的入口，parked / awaiting_review 这类「停驻」只是工作安排——两者都不再有权决定生死。死体当场终结、结清通信账；活体窗口丢了只报「窗口缺失」，不判死、不铸替身。

1病根：体的生死有两份账

今天判「体死没死」有两套互相打架的依据：

  • 账一：tmux 窗口/pane 探针。tmux（终端多路复用器，Bridge 用它给每个 Runner 开一个窗口）。名为「进程探针」的 probeRunnerProcessLiveness 实际只读 pane 有没有死、窗口在不在；没有任何死亡路径真正看进程。所以「窗口没建出来、进程活着」被判死（FLY-2618，9-26 凌晨 FLY-2910/2911/2901 三具 Codex 实现体就是这样被 force-failed 的）。
  • 账二：账面状态。死亡候选只查 status='running'，停在 awaiting_review / approved_to_ship / design_done 的死体永远不进候选；换体前置又要求「没有 active 会话」，死在 awaiting_review 的体就把替身堵死（FLY-2083 ×25、FLY-2537 ×16）。

盘点：9 张单、合计 68 次；近 7 天仍在出 3 张。涉及 FLY-2083 / 2537 / 2474 / 2193 / 2690 / 2512 / 2618 / 2528 / 2529。

2核心流程：每轮巡检怎么判

巡检（Bridge 每 5 分钟跑一轮的 HeartbeatService 检查）改为先按「执行身份」读进程证据，再做三分支处理。完成 marker（Runner 交卷时写下的回执文件）优先于死亡：有待处理 marker 的执行先对账完成，绝不当场记 failed。

  • alive：保留体与写入资格；窗口缺失只发一条「window_missing」告警，是要修的展示缺陷，不是死。
  • unknown（超时 / 权限 / 身份不符 / 没绑定）：零副作用，只进「待收体清单」告警。不判死、不铸替身。
  • dead：先查 marker → 核对 lifecycle_revision（会话状态的版本号，用来防旧证据盖新状态）→ StateStore 记 failed（或保留原终态）→ CommDB 清 parked 声明、结束 running 投影。整个过程在同一轮完成。

延迟上界：进程退出 → 判死 ≤ 一个巡检周期（默认 300 s）+ 5 s 探测窗口；529 真机把周期调到 30 s 验证 ≤ 35 s。

3谁在判生死：从多份判据收敛到一个真源

审计到 16 个文件在调窗口探针，其中 12 处会据此写 failed / terminated、删通信记录或铸替身（致死消费者）。修后它们全部改读同一个 observeBody；窗口探针只提供展示字段 windowState，不再进入任何写路径的判断条件。

4数据 / 结构模型

新增一个「进程绑定」记录和一个「死亡义务」事件，只记身份，不存 alive/dead——生死每次都现探，不靠旗标。

  • Claude / Kimi / Antigravity 的身份：启动瞬间 tmux 窗口的 pane_pid（窗口里第一个进程的进程号，两条启动路径下都恰好是 worker 本身）+ 进程开始时间 + 主机开机标识 + 可执行文件路径。核验只比这三样，不看命令行参数、不看进程标题（Claude Code 会改写它们）。登记失败 = 启动失败，不许「窗口有了但没绑定」算成功。
  • Codex 的身份：复用已有的 daemon socket + 进程组核验（socket 活且持有者属于登记的进程组 → 活）。Codex 自动重启（最多 5 次换号）期间返回 unknown，不误判。
  • 证据有效期 10 s，进事务前重核版本号；崩溃重放时先按幂等键找回执、再看过期（重放不撞过期）。
  • 运行时开关 FLYWHEEL_BODY_DEATH_AUTHORITY（登记在 feature registry，默认开）：置 0 时所有致死消费者只观察、报 unknown，是不改代码的紧急止血。

B. 账面终态 / 停驻直接视为死在活进程旁造替身、写入冲突否决

7诚实边界：这个设计做什么、不做什么

做

  • 一个进程证据契约、两载体探针、启动绑定登记、致死消费者全部收敛、死亡义务两库收敛、marker-before-death 不变式、运行时开关、九单 fixture、性质测试（窗口状态任意变化不改 verdict，旧实现必须出反例）。

不做

  • 不铸替身（归 FLY-2921 协调器，本单只提供可靠死亡真值与「换体前置消失」）。
  • 不改 Bridge 崩溃根因、不重构调度、不重写全部告警、不清生产库、不自动关九张 Linear 单、不部署。
  • 设计阶段未跑任何测试（本树没装依赖）、未做故障注入、未改活库。
