# Design Review — FLY-1278 plan.md (Round 1)

Date: 2026-07-15
Author: Codex
Status: CHANGES REQUESTED

## Summary

The A+B+C+D design is feasible in the current Bridge/StateStore architecture and preserves the settled governance direction: default-on severity policy, issue-scoped Lead rulings (including HIGH), and unchanged downstream founder/approval gates. The plan is not yet implementation-ready because several runtime assumptions are false or underspecified, most importantly production alert/thread wiring, mixed issue identity, kill-switch behavior, and the exact ordering needed to preserve head-echo and outbox protections. Addressing the items below should not require changing the approved product policy.

## What's Good (Keep)

- The three convergence layers are complementary: the mechanical whitelist resolves the observed MEDIUM-only deadlock, the ruling table provides a durable governance channel, and the prompt change reduces unnecessary rerounds without treating prose from the runner as authority.

- The severity classification is correctly fail-closed: only normalized MEDIUM/LOW are advisory; missing and unknown values remain blocking. APPROVED is not tightened, matching the stated one-way policy.

- Keeping `codex_review_job.verdict` as the effective verdict is compatible with the existing authority and gate consumers. Leaving `verify-approval`, `isCodexGateSatisfied`, family inversion, and the legacy Claude-author lane unchanged is the right blast-radius boundary.

- Freezing reviewer/effective verdict data before delivery recognizes the existing byte-identical response ownership and boot-redrive invariants in `review-request-coordinator.ts`.

- Validating rulings only against findings from delivered jobs is a strong, architecture-compatible guard against pre-authorized exemptions. Additive SQLite migrations and a revocable audit record fit existing StateStore patterns.

- The real FLY-1251 replay, the HIGH/missing-severity matrix, downgraded head-echo tests, migration idempotency, and policy-off sentinel are the right acceptance surfaces.

## Issues & Recommendations

1. **The `=0` rollback contract is internally inconsistent.** The plan calls `FLYWHEEL_REVIEW_SEVERITY_POLICY=0` a complete return to old behavior, but Slice 3 always changes the reviewer prompt to approve MEDIUM/LOW findings, and Slice 1 always describes a new response shape. A mocked `CHANGES_REQUESTED` result does not prove reverse compatibility because it bypasses the prompt behavior that produces the verdict. Define the switch boundary explicitly and make it match the approved reverse-compat promise. If `=0` means full rollback, gate the new severity/governance prompt sections and emit the legacy canonical payload as well as bypassing effective-verdict computation; if it is intentionally mechanical-policy-only, narrow the compatibility claim. Add an end-to-end sentinel that asserts prompt, stored verdict, delivered bytes, authority write, and alert behavior with the switch off.

2. **The proposed computation point does not mechanically guarantee the downgraded head-echo rule.** Current code branches on `outcome.verdict` before persistence (`review-request-coordinator.ts:666`), so a reviewer `CHANGES_REQUESTED` with no echo is tolerated. The plan says to compute effective verdict after the “head recheck,” which can leave that branch unchanged and allow a downgraded APPROVED authority record without an exact echo. Specify and test the exact order: revalidate the gate; load the verdict-time ruling snapshot and compute the effective verdict; re-derive and compare current versus frozen head; require an exact `reviewedHeadSha` whenever the *effective* code verdict is APPROVED (otherwise retain the existing mismatch-only CHANGES rule); then persist, deliver, and commit authority.

3. **The production notification/audit wiring assumed by the plan does not exist.** `ReviewCoordinatorDeps.alertLead` exists (`review-request-coordinator.ts:94-95`) and tests inject it, but the production constructor in `plugin.ts:6080` does not; `plugin.ts:6072-6076` explicitly says failures currently only reach console plus the durable row. Therefore advisory and dispute alerts in the plan would be console-only. The Discord ruling post is also named as a side effect without specifying a production dependency or failure/redrive behavior. Add the concrete plugin wiring: either introduce review-specific alert kinds through `ALERT_EVENT_TYPES`, `kind-contract`, routing, and exhaustive tests, or inject a dedicated structured sink. Inject a result-bearing issue-thread poster (the existing `AutoQaEffects.postThreadResult` pattern at `auto-qa-effects.ts:146` is reusable), and define whether a ruling is activated only after delivery or whether a durable notification outbox/status is redriven. Add production-wiring and Discord-failure tests; a mocked coordinator seam is insufficient for the promised dispute alert and visible audit.

4. **Issue-scoped rulings need alias-aware identity resolution.** The CLI accepts `FLY-XXXX`, while the table and lookups are specified against `issue_id` only. The repository explicitly documents the mixed UUID/Linear-identifier reality (`StateStore.ts:3704` and `StateStore.ts:5445`), and dispatch persists `node.id` separately from `issueIdentifier` (`PreHydrator.ts:35-40`). Resolve the supplied issue reference, scoped by project, against both `sessions.issue_id` and `sessions.issue_identifier`; store a canonical identity (and identifier for audit), and make job/ruling lookups alias-aware across executions. Ambiguous or cross-project resolution must fail closed. Add a regression where one execution stores the UUID and another stores `FLY-XXXX`, and prove one ruling applies to both.

5. **The ruling schema permits ambiguous active authority and incomplete revocation audit.** “Any active row” plus multiple allowed active rows means retrying a create can leave duplicate active rulings; revoking one may still leave the finding settled. A nullable `review_type` also lets a short model-generated id accidentally settle a different finding in the other review lane. Derive `review_type`, finding snapshot, source request id, and finding index from the matched delivered job rather than trusting optional CLI fields; transactionally reject or idempotently return an existing overlapping active ruling, backed by an appropriate uniqueness invariant. Record `revoked_by`, `revoke_reason`, and revoke time (or use a separate append-only event row), because the proposed `revoked_at` update does not substantiate the claimed full audit. Treat any re-raised HIGH finding that matches a ruling by id or fingerprint as a dispute alert even if the model omits `disputesRuling`; otherwise the optional field creates a silent HIGH-dispute path. Cover duplicate create, concurrent create, partial revoke, cross-review-type collision, and HIGH-without-`disputesRuling`.

6. **Canonical response construction and upgrade ownership need one versioned source of truth.** The current live path manually builds a payload near `review-request-coordinator.ts:697`, while `deliverStoredResponse()` independently rebuilds it at line 438; adding four conditional fields increases the chance of key-order or omission drift under byte comparison (`isOurResponse`, line 951). The plan also promises a frozen `policyNote` without storing it. Persist either the exact canonical `response_json` plus a payload version, or all inputs including a stable note token, and make live delivery and redrive use the same builder/string. Accept the old canonical shape only for identifiable migrated legacy rows, not every new job; add the inverse test that an old-shape response for a new-shape job remains FOREIGN. Preserve the delivery nonce and the deliver-before-authority sequence.

7. **The ruling API/prompt boundary needs bounded, usable finding identities.** `rationale`, `ruledBy`, titles, and follow-up values are injected into a privileged reviewer prompt, but the plan only requires a non-empty rationale and sets no length/control-character or active-ruling-count limits. Add field length/character validation, a total prompt budget, deterministic structured serialization, and explicit data delimiters. Also expose the server-derived `findingKey` in the delivered finding/advisory data (or allow `requestId + finding index` in the CLI); otherwise the fingerprint fallback is not operable by a Lead when the reviewer omits `id`. Use one shared fingerprint helper in endpoint validation, policy matching, payload rendering, and tests.

8. **The machine-replay fixture provenance and execution model are not yet reproducible.** `research.md:51` summarizes R6-R9 and quotes fragments, but it does not contain the verbatim `findings_json` claimed by `plan.md:179`. Capture the four raw production JSON values into a committed fixture with request id, round, frozen head, and a provenance/hash note; do not reconstruct them from the prose summary. Run R6-R9 as table-driven policy replays, run R6 as the policy-on coordinator convergence test, and run the sequential policy-off requests through R9 to reproduce the old closed-gate shape. Under policy ON, a natural coordinator flow ends at R6, so a single test cannot both converge at R6 and then continue the same gate through R7-R9.

## Verdict

CHANGES REQUESTED — address items above
