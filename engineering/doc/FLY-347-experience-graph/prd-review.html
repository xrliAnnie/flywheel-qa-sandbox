1建出来是什么样(核心)

  
一句话:在现有 markdown 记忆层之上,加一层「run 教训图」+ 两条自动管道(抽 / 查)。
  不建新数据库,复用「markdown 页 + frontmatter + [[链接]] + index」。


  
① 数据模型:图长什么样

  
节点 = 一个 markdown 文件(放 knowledge/lessons/),三类:lesson(教训)/
  root_cause(失败根因)/ signal(信号)。边 = frontmatter 里的 ref + body 的
  [[链接]](不建图数据库):from_run(溯源)/ subsystem
  (查的时候按这个匹配)/ failure_type / caused_by / relates_to。


  
② 一个真实节点长这样(拿我们真踩过的 FLY-176 那个坑举例)

  
---
type: lesson
id: bridge-restart-pid-unquoted
from_run: FLY-176
subsystem: [bridge, restart]
failure_type: process-kill
severity: high
signals: ["multi-line PID", "kill 静默失败", "restart-services.sh"]
caused_by: [[rc-restart-services-523-unquoted-pid]]
relates_to: [[lesson-config-before-kill-bridge]]
---
改 Bridge 重启逻辑时:restart-services.sh:523 的 multi-line PID 变量没加引号
→ kill 静默失败 → 得手动重启。避坑:PID 变量加引号,或 pgrep -f run-bridge | xargs kill -9。

  
index = knowledge/lessons/index.md:按 subsystem/failure_type 归类的目录,
  查询先读它定位再钻页(中小规模够用,不需要向量库)。


  
③ 自动抽:教训怎么自动进图(不靠人写)

  

    run 到终态→
    收集 transcript/CI/review/QA/retro→
    LLM 抽取 pass(固定 schema)→
    写节点+index+边(幂等)
  

  
fail-closed:抽不确定就不写(宁缺毋滥)。现在教训靠人事后记得手写、大量蒸发;这条让它
  每次 run 完自动沉一次。


  
④ 起活时查出来长啥样(注入 Runner 的「相关历史教训」块)

  
[相关历史教训 · 子系统=bridge/restart]
· bridge-restart-pid-unquoted (FLY-176): restart-services.sh:523 PID 没加引号→kill 静默失败
· config-before-kill-bridge (FLY-193): 改 config 要在 kill Bridge 之前(KeepAlive 会 respawn 用旧 config)
· bootout-wrong-pid: launchd job PID ≠ 真 Bridge PID,bootout 会杀错进程

  
何时查:Runner/Lead 起活时(onboard)自动做,不用人想起来。怎么用:开工前先读这块,
  不把老坑重踩一遍 —— 这就是产出价值。


  
⑤ 闭环

  
run 到终态 ──①自动抽──▶ 抽取 pass ──▶ 经验图(markdown+frontmatter+links)
                                              │
下一个 Runner 起活 ◀──②按 subsystem/task 查──┘
        └──注入相关教训──▶ 避坑开工 ──(完成后又抽)──▶ …

  
  





  
2MVP 范围(先做骨干,别做花的)

  
做:① 自动抽(run 终态触发,fail-closed)② 存(markdown 图)③ targeted 查(起活按 subsystem/task 拉 top-N 注入)。

  

    
先砍的为什么先不做

    
图可视化 UI纯 agent-facing,没人看图

    
向量/语义搜索(pgvector)MVP 规模 index+subsystem 过滤够用,要了再上

    
自动 merge/去重/lint那是另一片(agent-wiki 的 Lint MVP),别混

    
因果推理引擎边先靠抽取显式写,不做自动推断

    
跨项目图先单项目跑通

  

  
  





  
3跟现状差距 + 为什么值得

  
现状:教训靠人事后手写进 MEMORY(已有 123 feedback + 31 qa);MEMORY.md 整份注入;
  mem0 MemoryService 代码在但 pgvector 基本没接、主力人工 markdown。

  
差距(不在有没有教训,在怎么进/怎么出):进 —— 没 run 完自动抽;结构 —— 零散文件不能按维度查;
  出 —— 整份索引注入靠运气,不是 targeted。为什么值得:真教训会蒸发,起活时自动摆到面前,省的是
  重复 debug 的真实时间。诚实:这是增量(补「自动进 + 按需出」),不是从零。

  
  





  
4常规 PRD 段(浓缩)

  
    
    
  • Problem:每次 run 产生宝贵教训,但只有一部分靠人写进 MEMORY、大量蒸发;即使写了起活也只能整份注入靠运气 → 同类坑反复重踩。
    • 
    
  • Users:Runner(起活避坑 + 完成后自动沉淀)、Lead(派活看已知坑);人不直接看图。
    • 
    
  • Goals:run 完自动沉教训 / 起活 targeted 拿到 / 复用现有 markdown 不建新存储。
    • 
    
  • Non-goals:不做人类 UI / 不上向量库 / 不做 merge 去重 / 不重写 MEMORY / 不跨项目 / 不自动删。
    • 
    
  • Success:run 终态稳定产结构化节点(fail-closed)· 起活能捞到相关 top-N(拿 Bridge/Discord 两场景验收)· 同类坑重踩率降 · 不拖慢现有流程。
    • 
    
  • Open questions:抽取挂哪(hook vs skill)· subsystem 怎么推断 · 放新目录还是并进 memory · 注入量级 · 抽取质量把关。
    • 
  

  
  





  
5拆给 Tadashi 的活(draft,现在不建 issue)

  
    
    
  • EG-1 数据模型 + 图约定:定节点 schema/边约定/index 格式。
    • 
    
  • EG-2 抽取 pipeline:run 终态触发 → 抽取 pass(fail-closed)→ 写节点+index+边(幂等)。
    • 
    
  • EG-3 targeted 查 + 注入:起活按 subsystem/task 查 → top-N → 注入「相关历史教训」块。
    • 
    
  • EG-4 回填种子 + 验收:用现有 feedback/qa 回填种子;两个真实场景端到端验收。
    • 
  

  
顺序:EG-1 → EG-2/EG-3 → EG-4。等你确认样子 OK,才由 Lead/Tadashi 正式建。
