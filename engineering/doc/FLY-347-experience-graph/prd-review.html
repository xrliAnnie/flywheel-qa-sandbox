3⭐ lint 定义(写死 —— 你 v3 要讲清的)


  
① 多久 lint 一次:就每周一次(+ 可手动)

  
cadence 很简单:就每周一次(低频定时)+ 随时可手动:

  

    · 就每周一次(一个低频定时活动)
      + 随时可手动触发(Lead 想清理时跑一次)。
    
config 键如 lesson_lint.cron: weekly;不配用默认。Annie 定稿:去掉了「攒到 N 条」双触发,cadence 就是周频。
  


  
② lint 时做什么(4 件,写死)

  
一个 pass 扫整库,做:

  
    
    
  1. 去重 / 合并近似 lesson:讲同一个坑的多条并成一条(保留全部要点 + 各自来源 issue/from_run)。
    2. 
    
  2. 退役过时 / 被推翻的:某条被新 run 证明不再成立(坑已根治)→ 标记退役 / 移出 active(不物理删,可逆)。
    3. 
    
  3. 消解互相矛盾的:两条打架 → 合并成一条带条件说明的(「A 情况 X,B 情况 Y」),或 flag 给 Lead 定。
    4. 
    
  4. 更新 index:并/退役/合并后同步 index.md(删并走的行、改摘要、修 tag),库和目录一致。
    5. 
  

  
安全:输出可审 diff(哪些并、哪些退役、index 怎么改)+ 理由,Lead review 后才落,绝不自动删。

  
  





  
4范围回顾:图/向量仍不做

  

    
项状态

    
轻量 index / lint / consolidation在 MVP(lint 见第 3 节)

    
图结构(节点/边)仍砍(far-future)

    
向量 / 语义检索仍砍(你确认 not-now)

    
独立后台抽取服务不做(写=Runner ship 前顺手)

    
拆成多个 issue仍一件事(库的四面一体)

  

  
  





  
5MVP = 一个连贯功能(不是 4 个散的)

  
四面服务同一个库、一起做才成立(只写不 lint 会烂、有 index 才查得快),是一个连贯功能 / 一个 build
  issue,不是 4 个散活 —— 跟你「别搞 4 个散的」不冲突。

  
  





  
6差距 + 为什么值得

  
现状:教训靠人记得才写进 MEMORY(已有 约 126 feedback + 一批 qa,已经在烂:重复/只增不并);起活整份
  注入靠运气。这个做的:写固定成 ship 一步、读固定成 onboard 一步、lint 防它重蹈 MEMORY 越攒越烂。
  省重复 debug 的时间 + 一个不会烂的库。诚实:仍是薄的一层流程+约定,不是新系统。

  
  





  
7常规 PRD 段(浓缩)

  
    
    
  • Problem:run 教训靠人记得才留、难被下次读到、只叠不并会越攒越烂 → 同类坑重踩、库不可信。
    • 
    
  • Users:Runner(ship 前写 / onboard 读)、Lead(少踩老坑 + 审 lint diff)。
    • 
    
  • Goals:写成流程一步 / 按 index 读到 / 定期 lint 保库不烂 / 全用 repo markdown。
    • 
    
  • Non-goals:不做图/向量;不做后台服务;不重写 MEMORY;不跨项目;lint 不自动删。
    • 
    
  • Success:有值得记的 run 稳定产 1 教训+更新 index · onboard 按 tag 捞到相关(Bridge/Discord 验收)· lint 按 cadence 合并退役出可审 diff · 库不膨胀失控 · 不拖慢 ship/onboard。
    • 
    
  • Open Q(给 Tadashi):写在 approve 前 vs :cool: 前(建议 approve 前)· tag 从哪取 · index 格式 · lint diff 谁审(建议 Lead)。
