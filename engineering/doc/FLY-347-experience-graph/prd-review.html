1建出来是什么样


  
① 写(ship 前,进同一个 PR)

  
时机(写死):Runner 确认要 ship、请求 approve 之前那一步,用 LLM 给这趟 run 写段
  简短复盘(踩了什么坑 / 根因 / 下次怎么避),提交进当前 PR,跟代码一起 ship。
  没踩到值得记的就跳过,不硬写。

  
写成什么样(一个文件 knowledge/lessons/<ISSUE>-<slug>.md):

  
---
issue: FLY-176
tags: [bridge, restart, process-kill]
---
# 改 Bridge 重启逻辑:PID 变量要加引号

**踩的坑**: restart-services.sh:523 的 multi-line PID 没加引号 → kill 静默失败 → 手动重启。
**避法**: PID 加引号,或 pgrep -f run-bridge | xargs kill -9。

  
frontmatter 只两项:issue(溯源)+ tags(下次按它捞)。正文只要踩的坑 +
  避法。需要就手加 [[别的教训]] 链一下,不强制、不搞索引。存目标 repo 的
  knowledge/lessons/,随 PR 合进 main。


  
② 读(下次 Runner 起活时)

  
起活(onboard)自动扫 knowledge/lessons/*.md,按这单的标签/关键词和文件
  tags 做简单匹配(tag 交集 / 关键词 grep)→ 命中的几个读进来 → 开工前避坑。
  不搞向量、不搞图检索、不建索引 —— 小规模扫目录够。


  
③ 一个真实例子(端到端)

  
    
    
  1. 某 Runner 干 FLY-176 改 Bridge 重启,踩了「PID 没加引号 kill 失败」,修好。
    2. 
    
  2. ship 前写 FLY-176-bridge-pid-quote.md(上面格式),提交进 PR,一起 merge。
    3. 
    
  3. 三周后另一个 Runner 要再动 Bridge restart → 起活按 tag [bridge,restart] 扫到它 →
      读到「PID 要加引号」→ 直接避开。
    4. 
  


  
④ 闭环

  
Runner 干活 ─▶ 修好 ─▶ ship 前用 LLM 写 1 个教训 md ─▶ 提交进同一个 PR ─▶ 随代码 ship
                                                                    │
下一个 Runner 起活 ◀─ 按 tag/关键词扫 knowledge/lessons/ 捞相关教训 ─┘
        └─ 读到相关教训 ─▶ 避坑开工

  
  





  
2砍了什么(直接回答你问的『为什么不是图』)

  
你问得对 —— MVP 不该是图。下面全砍出 MVP,归 far-future(真需要再说):

  

    
砍掉的为什么

    
图结构(节点/边/关系)过度设计;MVP 就是几个 md 文件,需要才手加 [[链接]]

    
正式 index / 目录文件扫目录 + tag 匹配够,不维护索引

    
向量 / 语义检索简单 tag/关键词捞够;规模大了再说

    
独立后台抽取 pipeline / 服务不做后台;ship 前 Runner 顺手写一个文件而已

    
拆成 4 个 issue(EG-1..4)你嫌多易忘 → 收成一件事

  

  
  





  
3MVP = 一件事(不拆)

  
一个功能、一个 PR 做完:『Runner ship 前写一个教训 markdown 进 PR』+『下次 Runner 起活
  按 tag/关键词读相关教训』。写 + 读是一体,不拆子 issue。

  
  





  
4跟现状差距 + 为什么值得

  
现状:教训靠人事后记得才写进 MEMORY,大量蒸发;写了也只能整份 MEMORY.md 注入靠运气。
  这个做的:把「写教训」固定成 ship 流程一步(不靠记得)、把「读教训」固定成起活一步(按需捞、不靠运气)。
  省重复 debug 的真实时间。诚实:这是很薄的一层流程 + 约定,不是新系统 —— 正合你的简化本能。

  
  





  
5常规 PRD 段(浓缩)

  
    
    
  • Problem:run 教训靠人记得才留、留了也难被下次精准读到 → 同类坑反复重踩。
    • 
    
  • Users:Runner(ship 前顺手写 / 起活自动读)、Lead(间接:少踩老坑);人不直接管文件。
    • 
    
  • Goals:ship 前写教训成流程一步 / 起活按 tag 读到 / 全用 repo markdown 零新基建。
    • 
    
  • Non-goals:不做图/索引/向量;不做后台 pipeline;不重写 MEMORY;不跨项目;不自动删。
    • 
    
  • Success:有值得记的 run 稳定产 1 教训文件、没的跳过 · 起活按 tag 捞到相关(Bridge/Discord 两场景验收) · 同类坑重踩降 · 不拖慢 ship/起活。
    • 
    
  • Open Q(给 Tadashi):写在 approve 前还是 :cool: 前(建议 approve 前避 head drift)· tag 从哪取(建议 label+标题)· 起活注入量级 · 文件放 repo 根还是 doc/。
