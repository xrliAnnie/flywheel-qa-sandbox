FLY-2681 · CI 按需矩阵：平时只跑廉价门，全量只在被请求时跑

Issue FLY-2681 · 设计阶段 · 2026-09-17 · 出自 Tadashi 的工程设计节点 · 属于 Epic FLY-2651（CI 成本）· 另一条腿是 FLY-2647（自托管机器）· 外部评审（Codex）三轮后通过：第一轮 7 条、第二轮 3 条，全部采纳 · 本页不等你审完，实现会先往下走；你的意见会作为修订追加
●一句话总结

今天每往 PR 推一次代码，GitHub 就把 16 项检查全跑一遍，约 140 分钟机器时间；一张卡推 4–5 次很常见，所以两天撞了三次账单上限。这一单改成：平时每次推送只跑一道约 7 分钟的「廉价门」，完整的 16 项只在两个时刻跑——交给 QA 验收的那个版本、以及立发布卡之前。发布的门槛一条不松：没跑过完整 16 项的版本，合不进去。

CI（持续集成）= 每次改代码后 GitHub 自动替我们跑的一组检查。PR（pull request）= 往主干交代码的提交单。「头」= PR 当前最新的那个版本，每推一次就换一个头。job = CI 里的一项检查，我们有 16 项。Quick Gate（廉价门）= 其中最便宜的一项：编译、类型检查、代码规范，约 5 分钟。runner-分钟 = GitHub 按「每项检查用了几分钟机器」收费的单位。QA = 专门验收的 AI 工人。立卡 = 给你发那张「可以发布吗」的确认卡。

先说一个和单子不一样的发现

单子原本的想法是「改了哪个包就只跑哪个包的测试」。我拿 2026-09-16 一整天的真实记录重算了一遍：这样只能省 −8% 到 21%，有时还更贵。原因不是规则写得不够细，而是我们的代码长得就不适合这么裁：那天 76 次 PR 检查里有 55 次改了同一个大包 teamlead，46 次改了脚本目录；而脚本类的测试（占一次全量的将近一半）会直接读 teamlead 编译出来的产物，改了 teamlead 就不能不跑它们。

真正能省钱的是「分层」：平时只跑廉价门，全量攒到关键时刻跑一次。Tadashi 已经据此裁定改走这条路。

●核心流程：每个头跑什么
图 1 · 第一项检查（Classify）用约 20 秒决定这个头属于哪种模式；绿色 = 完整 16 项，橙色 = 只跑廉价门，蓝色 = 发布的门怎么看。

安全靠一个很朴素的约定

今天所有发布的门（GitHub 的分支保护、合并前的等待脚本、Bridge 的合并执行器）都只认一项名字叫 CI OK 的汇总检查。新方案让这项汇总检查换名字：完整 16 项全绿时它叫 CI OK；只跑了廉价门时它叫 CI Scope OK。于是没跑过全量的头上根本不存在 CI OK，三个门自动拒绝——它们的代码一行都不用改，也就没有「漏改一处就悄悄放宽」的风险。

分支保护 = GitHub 仓库的一条设置：指定的检查没绿就不让合并。Bridge = Flywheel 一直在跑的中枢程序。

拿不准就跑全量

判定只看这一次事件本身和代码历史的形状，不查 CI 的过往记录。任何读不懂的输入、任何 git 命令失败、开关没打开——统统落到「跑完整 16 项」。判错的方向只会多花钱，不会少测。

●一张卡从头到尾
图 2 · 谁在什么时候请求全量。Runner = Lead 派出去干具体活的 AI 工人。

谁来触发全量、怎么留痕

时刻谁怎么做
交给 QA 的那个头QA Runner，开场第一步运行新命令 flywheel-comm ci-full ensure：这个头上已经有 CI OK 就什么都不做；没有就给 PR 打一个标签 ci:full，GitHub 收到后跑完整 16 项。QA 一边验收一边等，发「通过」之前再确认一次。
立卡之前立卡守卫（程序，不是提示词）发现这个头没有全量绿 ⇒ 自动补一次请求，然后照旧拒绝立卡；等全量绿了再来。
合并前 main 又前进了不需要任何人Bridge 刷新分支会产生一个「合并提交」形状的头，Classify 认得这个形状，直接跑全量。
任何时候你或 Lead在 GitHub 页面上给 PR 打 ci:full 标签即可。

每次请求在 GitHub 上留三处痕迹：PR 时间线里的打标签记录（谁、几点）、那次运行的标题 CI full-request <版本号>、以及运行记录里的触发人。对同一个头，标签最多打一次：命令动手之前先在本机写一张「我要请求了」的回执，之后无论进程崩溃还是网络丢包，再调用都只会观察、不会再打；全量被取消或抖动红了，是在同一次运行上点「重跑」，而不是再开一次新的。

触发得早晚只影响快慢，不影响安全

如果谁都忘了触发，后果是「这个头上没有 CI OK，所有门拒绝」，看得见、卡得住；不会出现「没人触发所以没测就过了」。

Classify 给后面所有检查的四个信号

信号取值谁用
modefull（全量）/ docs_only（纯文档）/ scoped（只跑廉价门）/ reuse（main 上复用）决定汇总检查叫什么名字；写进运行摘要供人查
heavyrun / skip13 项重检查的唯一开关；读不到值时按 run 处理
no_codetrue / false今天就有的「纯文档」判定，原样保留
tested_tree一串 40 位指纹这次运行实际测的那份代码的指纹，用于 main 上的复用

汇总检查在全量模式下会逐项点名：13 项重检查每一项都必须是「成功」，跳过、取消、失败都不算；在跳过模式下则要求 13 项全部是「跳过」，不接受一半跑一半跳。这两条由一份常驻的 CI 结构测试逐字钉住，改了就红。

main 上的「同一份代码不测第二遍」

PR 合进主干后，GitHub 今天会在主干上把 16 项再跑一遍（那天 14 次，其中 6 次跑到一半被下一次合并顶掉）。很多时候主干上的代码和 PR 最后一次全量测的那份逐字节相同（那天 12 次里有 6 次）。新方案：全量全绿时留一张以代码指纹为名的凭证；主干运行时查到同指纹的凭证，再独立核对四件事（那次运行确实是本仓库的 CI、确实全绿、16 项一项没跳、用 git 重新算出来的指纹确实相同），都对上才跳过重检查。凭证本身只当索引用，里面写了什么一概不读、不信。任何一项对不上就照常全量。

●能省多少（按 2026-09-16 重放）

基线：那天 90 次运行，10,936 计费分钟，15 次 QA 验收

那天一共多跑几次全量主干不复用主干复用一半
0 次（每次 QA 验收一次全量，全部一次过）省 59%省 67%
+5 次省 53%省 60%
+10 次（那天每个真出过红的分支各多跑一次）省 46%省 54%
+16 次（每次红都单独多跑一次，不会真发生的悲观上界）省 39%省 46%

「多跑一次全量」= 全量第一次跑红了，修完换了新头再跑一次。今天这些红是分散在各个中间头上一个个发现的；新方案下同一分支的多处红会在第一次全量里一起暴露。偶发抖动的红只重跑红的那几项（每项约 12 分钟），不重跑全量。

一处我自己订正过的数字

我最初报给 Tadashi 的「最坏情形省 49%」用的是「多跑 8 次」，那个 8 是我在查失败记录之前估的，依据不足。查完之后：那天 16 次失败分布在 10 个分支上，有依据的最坏情形是「多跑 10 次」= 省 46%（含主干复用 54%）。订正发给 Tadashi 后已被接受，单子上的验收判据已改为「常规至少省 59%；最坏（多跑 10 次）至少省 46%」，原来的 49% 作废。常规情形的 59% / 67% 不受影响。

怎么复核

合入并打开开关 7 天后，Tadashi 用同一个脚本拉真实记录，主指标是「每次 QA 验收摊到的 CI 分钟」：2026-09-16 是 729 分钟，常规目标 ≤ 299，最坏目标 ≤ 391。

●关键取舍与被否掉的方案

我们接受的代价

  • 测试红会晚一点才看到。平时的头只跑廉价门，单元测试和脚本测试的红要到全量那次才暴露。Tadashi 的裁定：实现 Runner 本来就该在本地跑相关测试；它也可以在交给复审前自己请求一次全量。
  • 平时的 PR 页面上 CI OK 会显示「等待中」。这是设计内的样子，不是故障：它表示「这个头还没跑过全量」。
  • 立卡守卫（程序）要改一小处。旧的廉价门运行会在这个头上留下两条永远盖不掉的旧记录（一条「跳过」、一条可能是「已取消」）。守卫今天见到任何非绿记录就拒绝，所以要开一个很窄的口子：只豁免早于最新 CI OK、而且名字恰好是这两条之一的旧记录；其余一切照旧从严——包括全量绿了之后才出现的任何红、跑着的、取消的记录。守卫还会自己去 GitHub 核对那次全量运行：确实是这个头、确实是我们的 CI、检查名单和仓库里登记的 16 项一项不多一项不少、每一项都成功。纯文档 PR 在这个守卫下照旧过不了（今天也是这样，靠 Lead 直接放行），不借机放宽。（这一条在外部评审 Codex 第一轮后收紧过：原稿会放过「全量绿之后又出现的红」。）

被否掉的方案

方案为什么不要
改哪个包只跑哪个包（单子原文）重放只省 −8%～21%；跨层的毛病恰恰不出在被改的那一层，之前的成本审计（FLY-1987）也明确说过这类测试不能按路径裁。
只看「这一次推送改了什么」要依赖推送的先后记录；被顶掉的那次推送的改动在中间头上永远没测到；你在 FLY-1877 已经否过「看历史」的判定；也只省 13.5%。
平时的头上 CI OK 也显示绿，另加一项新的必过检查三个发布的门都得学会认新名字，漏改一处就是悄悄放宽；还要改仓库设置。
用手动触发（workflow_dispatch）跑全量实测：这种运行的结果盖不掉之前留下的「跳过」记录，立卡守卫会一直拒绝；而且它测的是分支本身，不是「合进主干之后」的样子。
让 Bridge 在 QA 开始时自动触发要在中枢程序里加对外操作、重试和失败处理；而触发只关乎快慢不关乎安全，一条命令加门前补请求已经闭环。
把「任何 .md 文件」都算文档设计节点的产物（engineering/doc、product/doc）今天已经算文档、只跑约 6 分钟；但仓库里另有 259 个 .md 是 Lead 规则、技能说明这类会被测试直接读取的文件，不能一律当文档。
●诚实边界：做什么、不做什么

做

  • 平时的 PR 头只跑 Classify + 廉价门；全量由打标签触发；合并提交形状的头自动全量。
  • 新命令 ci-full ensure；QA 开场步骤、立卡前提示词、立卡守卫的补请求。
  • 主干上同一份代码不测第二遍（带独立核对）。
  • 一个仓库开关 CI_SCOPED_MODE，默认关 = 和今天完全一样。
  • 度量脚本与 7 天复核方法。

不做

  • 不买机器、不上自托管（那是 FLY-2647）。
  • 不改必过检查的名字，不改 GitHub 分支保护，不改合并前等待脚本，不改 Bridge 的合并执行器。
  • 不删、不缩、不跳过任何一项测试本身；全量还是那 16 项。
  • 不做「PR 头上同一份代码不测第二遍」——立卡守卫不接受带跳过的运行，要做就得让守卫自己去核对凭证，那是另一个门的改动，单独立项。
  • 不给 QA 的「通过」加服务端 CI 校验；最后一道硬门仍是立卡守卫和 GitHub 自身。

已知的小毛刺

  • 有人对一个只跑过廉价门的头直接发 :cool:，合并前等待脚本会空等 25 分钟再报超时（安全，但慢）。留作后续改成立刻报错。
  • 合并进主干时若「代码相同但提交信息不同」，极少数依赖提交信息的测试在复用时不会重跑；廉价门每次都跑。
  • GitHub 账单此刻可能仍受限，本单自己的 CI 也可能起不来——如实记录，恢复后重跑，不绕过。
