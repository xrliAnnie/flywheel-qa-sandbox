「某个 Lead 现在在忙什么」只读接口

耳机模式下 Raya 替你问别的 Lead，1 分钟没回时，用它看对方是不是正在一轮活里、这轮是哪张单引起的、已经多久。

① 一句话总结

给 Bridge 加一个只看不碰的接口：问一次，答「忙/闲/不知道」，忙的话再答「从几点开始、已经多久、这轮是哪张单的消息引起的（答不准就明说判断不了）」。Claude 那 14 个 Lead 靠看终端底部那一行；Codex 那 3 个 Lead 靠问它们旁边的 sidecar。

sidecar：每个 Codex Lead 身边跑着的一个小助手进程，负责替它收发消息，所以它知道 Lead 这会儿有没有在一轮对话里。

② 实测推翻了一个前提（要你知道）

上一版设计写的是「看 Claude Lead 终端底部有没有 esc to interrupt」。我在本机 Claude Code 2.1.282 上实测：这句话已经不显示了。现在的样子是：

Lead 的状态终端底部那一行（实测）接口怎么判
一轮活正在进行✽ Bunning… (40s · ↓ 1.5k tokens)忙，已经 40 秒
一轮刚结束✻ Worked for 1m 17s · done 12:17 PM闲（这行长得很像上一行，必须专门认出来，否则会误判成忙）
重启后还没干过活没有这一行，只有输入框和状态栏不知道（状态栏忙的时候也在，证明不了空闲；今天实测 14 个里有 1 个是这样，干完一轮就能正常答）
出现认不出的新格式一行没见过的状态行不知道（不拿更早的旧行来猜）
弹出菜单 / 画面认不出输入框不见了不知道 + 原因

我还专门开了一个一次性的测试会话，让它连续干 3 段活：括号里的计时跨多次动作一直累加，误差约 1 秒。所以「开始时间 = 现在 − 计时」是可靠的，满足你要的「误差 ≤ 30 秒」。

③ 核心流程：问一次，发生了什么

Bridge：Flywheel 的中枢服务，所有 Lead 和 runner 的消息、状态都经过它。只读元数据：只看「谁发的、什么类型、几点送到」，不看消息写了什么。

④ Claude Lead：怎么从终端画面判断

  • 截屏只在内存里解析，不存文件、不写日志、不放进回答；回答里只有「忙/闲/不知道」和一个时长数字。
  • 输入框下方那些行一律不看——那里有后台小助手（subagent）的计时，看了会把「后台在跑」错当成「Lead 本人在忙」。
  • 从输入框往上找，只跳过空行、缩进的正文和「⏺」开头的对话条目（系统提示也是这种），碰到的第一条别的行就是「状态位」；它认不出，就不许再往上拿更早的旧行来作证。今天用这条规则复查 14 个生产 Claude Lead：12 闲、1 忙、1 不知道。认不出就答「不知道」，绝不猜成「闲」。

⑤ 「这轮是哪张单引起的」怎么算

  • Claude Lead 这一版一律答「判断不了」：只能看到「开轮前后几秒到了哪些信」，那只是时间上凑巧，证明不了就是这封信让他开的这轮（比如你在他终端里敲字的同时恰好来了一封信，就会被错算成那张单）。要证明得改 Lead 的启动链路，另开单。
  • 说法是「这轮由 FLY-xxx 的消息引起」，不是「他正在做 FLY-xxx」——Lead 一轮里常常顺手处理好几件事，前者我们能证，后者证不了。
  • 只有唯一一张单且每条投递都能对上时才给单号；否则写「判断不了」+ 原因（多张单 / Discord 聊天对不上单 / founder 自己在终端敲的）。宁可说不知道，也不给错的。Codex 这边目前只有「runner 提问」「Bridge 事件」两类信能可靠对上单。

⑥ 回答长什么样（数据结构）

示例（数字是编的，只为说明形状）：

{
  "state": "busy",
  "leadId": "raya",
  "turn": { "startedAt": "2026-09-25T20:12:34Z", "elapsedMs": 1200000, "precision": "second" },
  "trigger": { "kind": "issue", "issueId": "FLY-2877", "basis": "codex_journal_members" },
  "source": "codex_sidecar",
  "observedAt": "2026-09-25T20:32:34Z"
}

调用入口：Bridge 路由 GET /api/lead-activity（单个 Lead）与 /api/lead-activity/fleet（全部 Lead），命令行 flywheel-comm lead-activity --project … --lead … 或 --all。只接受本机调用，要 Bridge 主令牌。

⑦ 关键取舍与否掉的方案

问题选了否掉了（为什么）
Claude Lead 怎么读看终端底部那一行① 给 Claude 装「开始/结束」钩子：要改启动脚本、重启全部 Lead，而且按 Esc 打断时钩子不触发，会一直卡在「忙」；② 读对话记录文件：里面全是消息原文，违反「不读正文」。
Codex Lead 怎么读给 sidecar 加一个只读问答方法① 扩展它现有的心跳文件：只有部分 Lead 会写、founder 自己在终端敲的那轮不记，文件还会过期；② 截 Codex 的终端窗口：sidecar 已经有结构化的「开始/结束」事件，没必要再认画面。
「在做哪张单」只答「这轮由哪张单的消息引起」，只在因果能证明、且唯一时才给① 按「开轮前后几秒到了哪些信」推断（第一版这么设计过，评审指出会给错单，已删）；② 读 Lead 最近调用的工具标题当摘要：那就是正文的一部分；③ 看他名下哪个 runner 在跑：Lead 忙和 runner 忙是两回事。
读不到时一律「不知道 + 具体原因」当成「闲」：会让 Raya 以为对方有空，去催一个其实在忙的人。

⑧ 诚实边界：做什么、不做什么

做：17 个生产 Lead（14 Claude + 3 Codex）都能问；忙/闲/不知道；开始时间和时长；Codex Lead 能证时给单号。

不做：打断 Lead（另一张单 FLY-2883）；语音侧怎么调用（等核心单）；历史记录、推送、缓存。

要你知道的限制：

  • 3 个 Codex Lead 要重启一次后才有新方法；在那之前接口对它们如实答「不知道：sidecar 版本太旧」。
  • Claude Lead 重启后还没干过活时答「不知道」；Claude Lead 这一版不给单号。
  • Claude Lead 看不出一轮是消息触发的还是你在它终端里直接敲的。
  • Claude 主轮结束、只剩后台小助手在跑时，答「闲」（它能接新消息）。
  • Claude Code 以后改了底部那一行的格式，接口会退化成「不知道」，不会答错；到时要跟着改识别规则。
  • Codex 收到消息但还没开始这轮的那几秒，答「闲」；Codex 自己直接从 Discord 收的消息引起的轮，单号答「判断不了」。
