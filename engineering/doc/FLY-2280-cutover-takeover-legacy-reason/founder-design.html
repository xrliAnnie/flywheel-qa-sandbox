一句话结论

部署脚本在窗口里给刹车贴了一张自己的标签,然后拿着 host 工具那张旧标签去认领,当然认不出来;修法是让它贴的那张标签就是旧标签(逐字一样),并且在动手之前先检查旧标签合不合法。

名词一次讲清:admission pause(下文叫「刹车」:Bridge 暂停接收新任务的开关,是数据库里唯一的一行)· Bridge(Flywheel 的调度中枢进程)· lease(刹车的「所有权凭证」,一个 UUID;只有持有它的人才能续期或松开)· receipt(host 工具写在磁盘上的事务收据,记着刹车是谁、为什么、到期时间)· takeover(新 Bridge 起来后,把旧 Bridge 留下的「无主刹车」变成「有主刹车」的那一步)· phase-1(部署票的第 0 步:停旧 Bridge 之前先拉一次刹车)。

改什么改成什么为什么这就够了
phase-1 的刹车标签cutover 窗口里,标签(reason)逐字取 receipt 里 host 工具写的那一句,并把同一句作为「期望的旧标签」(expectedLegacyReason)一起发出旧 Bridge 忽略「期望」字段、无条件覆盖标签——覆盖成同一句就等于没改;新 Bridge 只在「无主且标签相符」时发所有权凭证,否则 409。两种版本都不会再让后面的认领落空,也不会认领错行
认领前的检查读标签时校验:非空、≤200 字符、首尾无空白、无换行;不合法就在停旧 Bridge 之前停下。第一次贴标签时,只有「连接被拒」(旧 Bridge 已被 bootout,请求根本没到)才继续;被拒绝、超时、断连一律在停 Bridge 之前停下今天这类错误要等新 Bridge 起来、Lead 全被拒之后才暴露;认领用的是同一条谓词,phase-1 被拒就注定 takeover 也被拒;超时/断连则可能是「服务端已经记下了、回包丢了」——两种状态同一个痕迹,唯一诚实的做法是停下让人来看
一道 CI 门用「有状态的假 Bridge」把「旧 Bridge + 新脚本 + 旧 receipt」这段引导过程锁进 CI既有测试只模拟「旧 Bridge 不可达」,从没模拟「旧 Bridge 接受并覆盖」——生产走的恰是后者

不动的:Bridge 代码、host 工具、receipt/handoff 文件格式、普通(非窗口)部署路径、部署主流程与回滚流程。改动净量约 +30/−5 行脚本(全部在 admission/cutover 段)+ 测试。

事故复盘:三段代码各自都对,拼在一起必错

图 1 · 15:25–15:26 PT 的九步。第 2 步的覆盖让第 7 步的匹配永远找不到那一行。

  • phase-1(部署脚本第 0 步)不管在不在窗口里,都用自己的标识 restart-services:updater:pid=… 当刹车标签。
  • 旧 Bridge(当时线上跑的 4e77a39)不认识 lease,收到 pause 就无条件把标签改掉,回复里也没有凭证。
  • takeover(新 Bridge 健康后、Lead 波之前)拿 receipt 里 host 工具写的原标签去认领:「找一行无主且标签等于 X 的」——0 行,返回 409,脚本按设计拒绝 Lead 波。
  • 普通部署没这个问题:它两头用的是同一个变量。窗口路径两头各说各话,从来没相等过。
  • updater 日志证据(逐字):15:25:04 paused without an owner lease id; preserving the cutover brake for post-deploy takeover → 15:26:17 could not take ownership of the legacy cutover pause → refusing the Lead wave → deploy did not converge。
为什么测试没抓到:既有用例让 phase-1 的请求「失败」(模拟旧 Bridge 已被 bootout),从没模拟「旧 Bridge 接受并覆盖」。而窗口脚本里 services-bootstrap 一步把旧 Bridge 又拉了起来,生产走的正是「接受并覆盖」这条。

修复后的核心流程

图 2 · 蓝色是新增的两个动作;红色是 fail-closed 出口;绿色是成功出口。「哪个 Bridge 应答」的四条分支里,三条收敛到同一个认领步骤,一条在停 Bridge 之前就停下。

  • 同一把 helper:phase-1 和 takeover 都通过 cutover_legacy_pause_reason 读同一个 receipt 字段,一处谓词、两处调用——不再有「镜像词汇」。
  • 对旧 Bridge:它忽略「期望的旧标签」字段,覆盖成同一句 = 幂等;顺带把刹车 TTL(到期倒计时)刷成 1800 秒,盖住 15 分钟的健康等待窗。
  • 对新 Bridge(比如第一张票失败后的重试票):它认识 lease,只在「无主且标签相符」时发凭证并写 handoff——既有 adopt 分支,只是加了限定条件;行已有主或标签不符则 409,phase-1 立刻停下,不停 Bridge。
  • 对「连接被拒」(旧 Bridge 已被 bootout,请求没到达):保留既有刹车,健康后再认领——既有分支,不用改。
  • 对其它任何失败(HTTP 拒绝、超时、断连):停下。脚本不猜是 409 还是别的,日志只说「被拒或结果不明」,让操作者按 receipt / handoff / inspect-admission 建立真实状态后再按 runbook §8.3 恢复。
  • 关键洞察:不需要知道「phase-1 那次写入到底落没落」(curl 超时但服务端已提交时,两种状态留下同一个痕迹)。因为无论落没落,数据库里的标签都等于 receipt 的标签。

方案做法裁定

三个小取舍

  • 不加新告警:第一稿想在第 0 步失败时发一条「什么都没动」的具体告警。独立评审指出:在「新 Bridge 已发凭证、随后 handoff 文件写失败」这条路径上,这句话是假的。于是删掉,只留精确的日志行;通用的「异常终止」告警照旧。真话比好看的告警重要。
  • phase-1 被拒或结果不明就停:认领用的是同一条谓词,第 0 步被拒等于预告了 takeover 也会被拒;超时/断连又分不清「没到」和「到了但回包丢了」。只有「连接被拒」能证明请求没到达 Bridge,所以只放行这一种。与其停掉 Bridge 再晚失败,不如在 Bridge 还活着时停下。第一稿只针对 HTTP 错误码停下,独立评审指出那既证明不了 409、又漏掉了超时——改成现在这样。
  • 把合同测试套件提进 CI:它此前被归在「macOS 集成套件」清单里不在 CI 跑,但它本身是全假环境(假 HOME、假 curl)。这条回归花掉了一张部署票,值得一道 CI 门。

诚实边界:这个设计做什么、不做什么

做

  • 让「旧 Bridge → 新 Bridge」这一次跨版本窗口的刹车认领确定性成功。
  • 把标签合法性检查提前到停旧 Bridge 之前,失败时旧 Bridge 仍在跑、什么都没动。
  • 用「有状态假 Bridge」的测试把这段引导过程锁进 CI;修复前必须 RED。
  • 把 runbook 里「旧 Bridge 已 bootout 时 pause 不可达」这一句唯一路径改成事实(旧 Bridge 会被 services-bootstrap 拉回来)。

不做

  • 不能检测窗口内有没有第三方另发过 pause:旧 Bridge 本来就没有所有权语义,同标签只是让覆盖幂等。靠 runbook 的窗口纪律(唯一一张票)保证。
  • 不改 TTL 语义:phase-1 和 takeover 都把倒计时改写成 1800 秒;若旧刹车剩余更多会被缩短(仍盖住 900 秒回滚 + 180 秒启动预算)。这是 FLY-2264 已接受的行为。
  • 不动 Bridge、host 工具、文件格式、普通部署路径、部署主流程与回滚流程。
  • 「没有可用 handoff」只能手工恢复,且不靠固定等待:操作者用裸 curl 发一次「无限定」pause 做原子探测兼获取——成功就拿到新凭证,手写 0600 handoff 再用 host 工具导入;409 说明仍有活跃 owner,用 inspect-admission 盯到 active=false(对方的租约可能被续期,最长 3600 秒一次)再重试,并把这段刹车松开记为连续性缺口。导入成功的判据是「退出码 0 且 receipt 变成 owned 形态」,不是 stdout 里出现凭证(工具刻意不打印它)。恢复步骤逐字写进 runbook §8.3;若想自动化,另开 issue,不在本单。
  • 代码回滚把旧 Bridge 拉回来之后,需要一张「预期失败」的过渡票:旧 Bridge 不认凭证,host 工具导不进 handoff;过渡票让新 Bridge 回到位(认领处按设计拒绝 Lead 波),然后导入 handoff、再发一张 owned 票完成 Lead 波。写进 runbook §8.4。若 founder 觉得两张票不可接受,既有的 FLYWHEEL_RESTART_DISABLE_CODE_ROLLBACK=1 可让窗口票不做代码回滚——那是窗口策略,本单不改默认值。
  • 与 FLY-2271 并行共存(Lead 裁定):FLY-2271 会在同一个部署脚本里加一处最小 hook(部署波次按运行时树哈希重启 quota-monitor daemon,逻辑放独立新 lib)。本单只改脚本里的 admission/cutover 段(helper、phase-1、takeover、Step 0 失败分支),不重构无关段;先合入的一方不动,后合入的一方 rebase。
  • 15:26 到 15:59 之间生产的 lease 与 handoff 是怎么人工取回的,updater 日志里没有,本设计不假装知道;需要可追溯的话另开 issue 让 host 工具记 import-handoff 事件。
  • 非 BMP 字符(emoji)且接近 200 字符的标签在 jq 与 JS 两边长度算法不同——写进 runbook 约束(用 ASCII),不建机制。
