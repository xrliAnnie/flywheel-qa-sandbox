一句话结论

给任何一个 Lead 一条命令,他就能拿到这个 Epic 的一页:上面写着要做的事、先后批次、每件做完算什么样、哪几件要回来找你 —— 而且页上每一格都能说出「我从哪儿来、我是什么时候看到的」,没有一个数只存在于页面里。

这一单只做「静态半边」:定义页面装什么,并生成第一版。让页面自己活起来(做完一件就更新、过期自报)是 FLY-2143 的事;定时回头看还剩什么、空位拉活是 FLY-2141 的事。

你的要求(PRD 原文)本设计怎么落
R1:页面要回答四件事四件事各有唯一来源,全在 Linear 上(下文第 4 节)
R1 验收:Lead 不问「现在该做哪件」能一直推到做完页面上直接列出「现在可以开始的」,并附一条可执行的演练测试:一个只读页面、不知道任何上下文的读者,每一步都能说出下一件
R5:每一格都有出处;过期要说出来每一格 = 值 + 出处 + 看到它的时间;没有这三样的格根本存不进去(有一道守卫)
不写死谁用谁不用代码里零处出现具体 Lead 或具体 Epic;命令只收「项目 + Epic 号」

今天撞到的墙,以及这一单补哪一块

PRD 写得很直白:Epic 定完之后,Lead 手上没有一份东西告诉他先做哪件、后做哪件;想知道做到哪了只能开口问。于是这三件事今天靠你随时说「该做这个了」撑着 —— 正是你说不该由你做的那件事。

一个真实的小证据(2026-09-03 当天发生的):Epic FLY-2108 的五张子单,拆单时「D 依赖 A 和 B」只写在正文里,Linear 上一条连线都没有。页面若从正文去猜依赖,就是在制造「只存在于页面里的事实」。本单向 Lead 提出后,他 02:35 在 Linear 上把连线登记好了 —— 依赖回到了它唯一该在的地方。这件事本身就是本设计最重要的判据:页面不猜,页面如实显示「未登记」,人就会去把它登记到唯一真相里。

核心流程:一条命令之后发生了什么

图 1 · 从 Lead 的一条命令到两种视图。橙色 = 两个事实来源;蓝色 = 生成;绿色 = 权威副本
  1. Lead 跑 epic-page generate(任意项目、任意 Epic 号)。命令打到 Bridge。
  2. Bridge 一次性从 Linear 读下这个 Epic 的快照:子单、子单之间的 blocks 连线、标签。读不到(网络、超时、Epic 不存在、子单多到不正常)⇒ 整次失败,什么都不写。
  3. 再从自己的数据库(StateStore)读每张子单的「账面执行体」:有没有会话在跑、工作流走到哪个节点、门开着没、PR 落地没。某一格读失败 ⇒ 只那一格标「缺」,页面照出。
  4. 生成器是纯函数:两份事实进去,一份文档出来,每格都带出处与时间;不合规矩的文档过不了守卫,不会存。
  5. 存一版(版本号只增不减,保留最近 20 版);同一文档渲染成 Lead 读的 Markdown 和你看的 HTML;要给你看时用现有的 publish-report 发一个托管链接(快照,7 天过期,这是已知边界)。

四件事各从哪来(每一件都只认一个来源)

图 3 · R1 的四问 → 各自唯一的 Linear 来源;红框是页面明确不做的事
必须回答来源(唯一)页面上怎么写
① 要做的事有哪些Linear:这个 Epic 的全部子单(不含已归档)一张表,每张子单一行;被取消的单归到「不做了」—— 这就是 PRD 说的「减法」
② 它们的先后(批次)Linear:子单之间的 blocks 连线(Lead 拆单时本来就在 Linear 上画)「第 1 批 / 第 2 批 / …」:没人挡的是第 1 批,被第 1 批挡的是第 2 批,以此类推;连线成环时不猜顺序,直接点名环上的单
③ 每件做完算什么样Linear:状态到 Done + 子单描述里以「验收」开头的那一段原文逐字引用,不摘要不改写;没有验收段的单显式标「缺」—— 这正是「他不知道什么时候可以往下一件走」的提前告警
④ 要回来找她的那几件Linear:子单上打了 founder-review 标签的一份清单;0 件也明写「0 件」,不隐藏这一格(Lead 的硬约束)
为什么不从正文里抽? 正文是给人读的。页面一旦从正文「理解」出依赖或验收标准,那就是页面自己造的事实 —— 正是你点名的那个坏处。所以页面只认结构化的东西:子单、连线、状态、标签、以及一段被明确标题圈出来的原文。

每一格长什么样:值 + 出处 + 看到它的时间

图 2 · 页面上任何一个值都是一个「格」;格只有三种出处

你说过:「一个说不出自己多旧的页面,和一个错的页面,在她眼里长得一模一样。」所以每一格都带两个时间:来源自己说它上次什么时候变的(比如 Linear 的更新时间),以及我们什么时候去看它的。后者就是「这一格是什么时候的」。

  • 出处只有三种:Linear(哪张单、哪个字段、链接)、StateStore(点名哪张表、哪个键)、规则(编号 + 它读了哪几格)。
  • 「没有」也是值:零阻塞、零执行体、零命中标签都存成空集合,照样带出处和时间;只有「读不到」才叫「缺」,并且必须写明缺的原因。
  • 守卫:没有出处或时间的格、藏在值里的第二套时间、只存在于页面里的字段 —— 都过不了守卫,存不进去。这不是约定,是一道测试。
  • 内容指纹去掉时间再算:这样以后 D 单能分辨「内容真变了」和「只是刷新了时间」。

「现在可以开始的」怎么算 —— 一条默认规则,不是裁定

四件事齐了,Lead 仍要自己拼出「所以现在做哪件」。这一步能确定地推出来,页面就替他推,并标明这是推导、标明规则编号 next.v1:

还没开始(backlog / 未开始) ∧ 挡着它的单全部已完成或已取消(兄弟单和 Epic 外的单都算) ∧ 账面上没有执行体:没有活着的会话、没有在跑的工作流、没有未收尾的落地 ∧ 上面这些事实一格都不「缺」 ← 缺一格就不推荐(宁可少推荐,不冒推错)
诚实标注:PRD §8 里「哪些算还没做、可以往外放」「怎么算一件事做完了」两个问题你还没拍。这条规则是默认值,页面每次显示这一节都带一句「未获 founder 裁定的默认规则」。它说的是「候选」,不是「可以派发」—— 派不派还要看容量,那是 B 单和 E 单的事。

「账面执行体」指的是数据库里登记的记录,不是去探进程活没活着 —— 页面用词也只说「账面上还有执行体」,不说「进程活着 / 死了」。

页面放哪,以及被否决的两条路

方案裁决为什么
放进 Bridge 的数据库,Bridge 出 Markdown / JSON / HTML;给你看的用托管快照采纳Bridge 已经持有全部执行事实和 Linear 的钥匙;新加一张表不动任何旧东西;D 单的「做完就更新」= 再生成一版。Lead 2026-09-03 已裁定。代价:页面是事实的投影副本 —— 正是你点名的坏处,所以用上一节的「每格出处 + 时间」正面回答,而不是绕过去。
放进项目仓库当文件否决仓库铁律是一切改动走 PR;活页面每次更新都要一个 PR,做不成;而且让 Bridge 往项目仓写文件是新一类副作用。(本页这份设计 HTML 仍按流程进仓库,那是另一回事。)
不存,每次现算否决来源不可达时说不出「上次是什么」;没有历史;D 单的「更新」没有对象;给你看的快照还是得物化一份。
用 Linear 标签表示「要回来找她的」采纳结构化、可查、任意 Lead 给任意 Epic 都能打;不解析正文;非 issue 形态的问题(比如 PRD 那三条开放问题)由 Lead 建成带标签的子单。
用 Epic 描述里的某个固定小节表示同一件事否决又要解析正文,而且和标签是两套并存的说法。
加一个开关控制这一切否决不加新 flag 是铁律;这里也没有需要开关的行为:不调用就什么都不发生,回滚 = 撤销 PR。

诚实边界:这个设计做到了什么、没做什么

做到了

  • 四件事都有唯一来源,都是 Linear 上已有的结构,不新造词汇、不解析正文。
  • 每一格有出处和时间,并且是守卫强制的,不是靠自觉。
  • 失败时不装:来源整体读不到就不写版本;某格读不到就标缺;推荐规则在信息缺失时宁可不推荐。
  • 通用主语:任意 Lead、任意 Epic;代码里零处写死谁用。
  • 五轮独立评审 31 条全部处置,最终 APPROVED;没有为了过审新增机制。

没做(有意的)

  • 页面不会自己更新。做完一件要 Lead 再跑一次命令;做完就自动刷新、过期自报归 FLY-2143。
  • 给你看的链接是快照,7 天过期。这是现有托管方式的边界;活页面归 FLY-2143。
  • 不判断「位子空了没」、不管额度和内存。那是 FLY-2141 / FLY-2144;这里的「现在可以开始的」只是候选。
  • 不替你拍 PRD §8 那两个开放问题。规则是默认值,页面上明写。
  • 标签 founder-review 今天还不存在,要 Lead 一次性创建;创建前页面会老实显示「0 件」。
  • 只看一层子单,孙单不展开;已归档的单不读也不计数。
  • 只用真数据跑过 Linear 读取那一段(两种查询形状都返回 200);生成、存储、渲染的真数据演练由实现节点做,验收里写成「同一时刻记证据、按规则手算、再比对」。
