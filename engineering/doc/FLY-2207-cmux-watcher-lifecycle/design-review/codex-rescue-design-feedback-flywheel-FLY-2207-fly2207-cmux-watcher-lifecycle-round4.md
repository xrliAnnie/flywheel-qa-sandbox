# Design Review — design-correction.md FLY-2207 cmux-watcher-lifecycle (Round 4)

Date: 2026-08-31
Author: Codex
Status: CHANGES REQUESTED

## Summary

The appendix correctly identifies all three broken legs: the cleanup snapshot is stale and its write failure is swallowed, strict healing refuses unreceipted workspaces, and watcher alerts run without the token environment. The incremental scope also respects the approved T1–T5 boundary, but T7 does not yet establish the causal path required for closed-tab collection, and T8's proposed evidence proves a live source execution—not ownership of the exact cmux workspace—so the current design could take over a founder-created same-title tab.

## What's Good (Keep)

- Keep the correction as a separate, committed appendix; `plan.md` remains untouched and the approved R3 gate blob is not reopened.
- The repository and sanitized host evidence support the diagnosis: the cleanup snapshot is a valid `complete` snapshot but has been unchanged since 2026-08-25; the watcher log contains repeated freshness-fence deferrals; all 1,059 `cmux_cleanup` dead letters are `no-token`; and the installed watcher plist exposes only `FLYWHEEL_CMUX_SUPERVISED=1`.
- T6 → T7/T8 is the right dependency order, and reusing `cmux_cleanup`, the existing watcher, the existing conservative cleanup path, and the existing view-construction primitives honors the no-new-alert-layer/no-new-daemon constraint.
- Preserve the fail-closed rule for ambiguous identities, duplicate `@flywheel_exec_id` windows, unavailable roster/tmux/cmux truth, and unowned workspaces. FLY-913 remains untouched.
- The proposed hermetic direction is correct: fake roster/tmux/cmux state and isolated persistent paths should prove both convergence and preservation without operating on the production label or tabs.

## Issues & Recommendations

1. **T8's positive identity does not prove ownership of the exact cmux workspace.** The conjunction “node registry row + exactly one tmux window carrying `@flywheel_exec_id`” can prove a live source window, but it does not distinguish a Flywheel-created workspace from a founder-created workspace with the same title. This is exactly why `self_heal_one_workspace` currently requires `ledger_committed_ref` before it can inject an attach command. The existing safe adoption path is materially stronger: `adopt_birth_candidate` binds the exact ref to an immutable workspace UUID and `cmux_workspace_birth_record`, then revalidates that evidence in `_birth_adoption_guard`. Re-minting a receipt from title/source evidence alone would turn an arbitrary same-title workspace into mutation authority and could send commands into a human tab. **Fix:** require exact workspace-side ownership in addition to source identity. Prefer reusing the existing birth-record/UUID adoption path; if the restart wave destroys that evidence, allow only a unique stale committed receipt whose stored workspace UUID still matches the exact current ref/UUID, with no competing current/stale claim. If neither proof exists, retain the current refusal. Revalidate immediately before every tmux/cmux mutation: cmux generation + exact ref + workspace UUID/title, and tmux generation + exact source session/window id + exact exec id + live pane. Add negative tests for a founder same-title workspace, duplicate refs, duplicate exec-id windows, stale registry rows, a replaced window id, and both cmux/tmux generation flips.

2. **T8 does not define a crash-safe recovery transaction or coherent attempt latch.** `create_or_replace_view_session` is a WAL-backed, mutation-time-guarded construction protocol; “use the existing ensure/view primitive, re-mint a receipt, reconnect” does not specify the ordering or which durable evidence owns partial failure. A crash after receipt mint but before a valid viewer exists could leave a false committed claim; a crash after viewer creation but before bookkeeping could cause repeated rebuilds. Also, “at most once per workspace per generation episode” and “second failure alerts” are contradictory unless the design defines what the second attempt is. **Fix:** spell out the state/sequence using existing primitives: recover any construction WAL; prove workspace and source authority; build/verify the exact viewer through the WAL protocol; adopt or prepare the exact UUID-bound receipt; perform the guarded attach; verify the client/surface; then commit/clear episode state. Define whether there is one attempt or one retry, the durable key (at minimum cmux generation + workspace UUID/ref + tmux generation + exec id), crash replay behavior, re-arm condition, and failure alert point. T8 QA must inject crashes/races at each boundary and cover the kill switch. Also add the active flag declaration and its registry/drift tests to the file list; `truth.ts` consumes the active registry rather than being the sole implementation file for a new active kill switch.

3. **T7's stated terminal-roster path does not currently drive workspace cleanup.** `fetch_recent_terminal_runner_roster` is consumed by `reconcile_node_presence`, which converts registry entries into `terminal-summary`/`unresolved-summary` and ensures a node-summary workspace. It does not create a mirror cleanup marker. Mirror cleanup markers currently come from `pane-died`/`window-unlinked` events or the conservative scan, and `process_pending_cleanups` drops a marker when `is_pane_alive` still says the source is live. Therefore “terminal classification drives existing cleanup” does not, by itself, prove the ≤10-minute closed/shipped-tab acceptance—especially for a terminal execution whose stray pane remains alive. **Fix:** choose and document the actual authority boundary. Either prove and test that the close/ship pipeline always kills or unlinks the exact source window, making the existing event/conservative path the causal trigger, or add an explicit exact-execution bridge from a current terminal row to the existing marker path. If terminal status is intended to override a still-live pane, call that out as new teardown authority and add equivalent exact-id, mutation-time, and ambiguity guards. The hermetic acceptance must include the real trigger, not only a fabricated terminal roster response.

4. **T7's freshness and alert invariants are not aligned with the implementation and would create unnecessary alert fan-out.** `node_cleanup_freshness_allows` compares the snapshot header's `snapshot_epoch` and additive round tuple against the marker; it does not use filesystem mtime as cleanup authority. Requiring only “mtime advances” can pass while the authoritative header is stale or fail for valid same-second rounds. Separately, “one alert per marker after 24h” can manufacture a large burst: the host already has hundreds of thousands of repeated fence log lines, while `_alert_cmux_cleanup` locally caps distinct signatures at 64 per cmux generation and resets on watcher restart. Thus the appendix does not define how every marker gets exactly one durable alert. **Fix:** make the invariant an atomically replaced, structurally valid `complete` snapshot whose `(snapshot_epoch, round_epoch, round_sequence)` strictly advances as required by the fence; test the header and cleanup decision, with mtime only diagnostic. Prefer one existing-kind alert per **snapshot-stall episode** (oldest marker age + blocked count), durably re-armed only after a valid snapshot advances, instead of per-marker alerts. This is simpler, avoids flooding, and still makes the broken pipeline visible. If per-marker delivery is retained, specify the durable dedupe owner, restart behavior, and behavior beyond the 64-entry local latch.

5. **T6's env-loading contract is not implementable as written and overexposes secrets if corrected naively.** The shared alert adapter invokes `lead-alert.sh` as `flywheel-eng-lead`; the script's isolated self-load from `.env` applies only to `--lead system`, so the no-token diagnosis is correct. But a plain `source ~/.flywheel/.env` does not export the common bare `KEY=value` assignments to the exec'd watcher or its later `lead-alert.sh` child. The Bridge wrapper explicitly uses `set -a` for this reason. Adding `set -a`, however, would put every `.env` secret into the long-lived watcher and all of its tmux/cmux/curl subprocesses, and direct sourcing also overwrites inherited same-name values—contrary to T6.2's precedence guard. **Fix:** define a minimum projection rather than wholesale inheritance: reuse/generalize `lead-alert.sh`'s isolated trusted-env lookup, or have autostart export only the unified channel, selector, and selected token needed by this alert route while preserving inherited-value precedence. A source/parse failure, missing file, wrong owner/mode, symlink, or non-regular file must log and still exec the watcher. Tests must use bare non-exported assignments, prove successful delivery/no `no-token` dead letter, preserve an inherited override, cover missing/unsafe/symlink inputs, and prove an unrelated secret is absent from the watcher stub's environment.
