roundtable thread「1 小时自动收起」— 根因查明了,这样修

FLY-1435(接替 FLY-802)· 设计阶段报告 · 2026-07-22
一句话:之前测出「自动归档从没触发」,不是机制坏了,而是盯错了信号——Discord 几年前就把这个设置改成了「控制 thread 在侧栏里挂多久」,而我们盯的那个「归档标志」平台本来就几乎不翻(实测 28 天都不动)。你要的「1 小时没动静就从侧栏收起」Discord 原生就能做到,不用巡检员。不过查根因时又挖出两个真窟窿:抢先建 thread 的插件写死了 3 天、Cass 没有改 thread 的权限——这次一起补上。
① 为什么之前会误判「没触发」

Discord 的「自动归档时长」有两套互不相干的行为,之前的验收盯了错的那套:

它实际做什么我们实测
侧栏收起(你要的) thread 超过设定时长没动静,就从左边侧栏列表里收起(消息还在,搜得到) ✓ 真触发:一条闲置 6.4 小时的测试 thread,读掉未读后立刻从你的侧栏消失;旁边设 3 天的对照 thread 还挂着
「归档标志」(之前盯的) 服务器内部另有一个不公开的慢计时器,平时基本不翻这个标志 ✗ 有 thread 闲了 28.3 天标志都没翻——盯它必然误判「没触发」

③ 侧栏到底按什么规则显示(诚实版)

侧栏显示 = 没被归档 且(有未读/被@点名 或 最近 1 小时内有动静)

场景修完之后
你读过的 roundtable thread✓ 没动静 1 小时后自动收起 —— 这就是本单目标
你还没读的(被 @ 了)⚠️ 会一直挂着提醒你,点开看一眼就收 —— 这是 Discord 全平台的未读保护,故意的
#flywheel-alerts 那一大排✗ 不归本单管 —— 那些全是未读钉住的,跟收起时长无关;想连未读一起强收是另一个产品决定,到时你拍
④ 关键取舍(否掉了什么、为什么)
  • 巡检员方案 ✗ —— 你已明确否决(「802 我们不需要巡检员」)。本方案零常驻进程,收起完全交给 Discord;Cass 的权限只是让既有的一次性纠偏动作能成功,不是轮询。
  • 只把 #677 合进去 ✗ —— 不够。插件抢建的 thread 还是 3 天,你实际看到的大多数 thread 恰恰是插件建的。两个窟窿不补,等于又一次「代码看着对、你的侧栏没变化」。
  • 继续拿「归档标志」当验收 ✗ —— 平台就不按这个走,盯它只会永远 Fail。新验收 = 直接看你客户端的侧栏(截图为证):设 1 小时的收了、设 3 天的对照还在,才算过。
  • 换掉 Discord 原生、自己写收起逻辑 ✗ —— 过度工程,还违背零巡检方向。
⑤ 需要你做的两个一次性配置(ship 窗口时找你)
  • 给 Cass 在 #leads-roundtable 加「管理 thread(Manage Threads)」权限 —— 让纠偏和改名真正生效。
  • 把测试频道 #test-leads-roundtable 的默认收起时长设为 1 小时 —— QA 隔离房用,不碰生产。

机器人自己没权限做这两件事,各只需点一次。

⑥ 边界(这个设计不做什么)
  • 未读的 thread 不强收 —— Discord 的未读保护;要强收=新决策,你拍了才另立项。
  • 存量老 thread 不回头处理 —— 只管新建的(FLY-802 就定过的边界)。
  • 侧栏收起是 Discord 客户端的行为 —— 官方文档只有一句话合同,所以验收全部以真机截图为准;将来 Discord 客户端要是改行为,算新问题。
  • issue 讨论 thread(3 天)和告警 thread(1 天)的时长不变 —— 本单只动 roundtable。
