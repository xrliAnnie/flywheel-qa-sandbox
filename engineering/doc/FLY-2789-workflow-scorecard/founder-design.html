02 · 一张单，几层编号

run 是一轮工作流；execution 是一个 Runner 载体；activation 是该载体本次承担的节点工作。原体接返工会有新 activation，换体也保留旧载体账目。

原生 turn 是模型的一轮工作。它开始时固定归属，因此晚到用量不会算到下一节点。

03 · 主要比较什么

每张一次过 QA 单的投入
全组已完成单总 token ÷ 一次过 QA 单数

token 是模型处理文字的计数单位，并非订阅实际账单。跨供应商的统计会标注不可视为等价额度，不据此直接排优劣。失败与返工投入也进入分子；另外展示“一次过单自身平均投入”。

主指标200 token / 首过单
首过单自身均值100 token
平均节点累计 / 端到端耗时1.4 秒 / 约 1.73 秒

这是隔离测试的手算样例，不是生产成绩。三张分组表不能相加。

04 · 成绩怎么算

  • 一次过：整张单最早被系统正式接受的 QA 判决是通过。
  • 先失败再通过仍不算首过；换体前没有判决不算失败。
  • founder 打回只数带真实作者证明的独立决定；重发、转派、验证链不加次数。
  • 打回率以确实受过 founder 审阅的单为分母；未审单单列。
  • 耗时列节点累计与端到端两种墙钟时间，包括当次工作中的等待，不冒充模型推理时间。

05 · 与分流工作的接口

receipt（回执） 是已保存、可追溯的分组记录。B 读取回执，A 决定并写入分组。Lead 已确认这个边界。

接口包含 runId、nodeId、policyVersion、arm、resolvedModel、assignedAt：分别是工作流编号、节点编号、策略版本、组编号、解析后的模型编号、分配时间。

保留旧策略；新策略的设计三组、实现两组与 QA 两组分别比较。实现组由 A 按 Opus 5.5 75% / GPT-6 Sol 25% 分配，B 不改分流。没有回执记“无分流”；来源损坏记“未知”。同一单跨组时列“混组”，不复制成多张单。

额度降级单单列，不进入原组。 只认 A 写入的服务端降级回执，保留原组和实际模型；不靠模型名称变化猜测。分配模型与实际启动模型无理由不一致时，会单列异常，排除原组。整单一旦有降级，三个维度均单独列出。每个原组同时展示被移出的降级单数与比例，避免只看到剩余样本而误判。

06 · 为什么选这条路

  • 选现有账本 + 少量缺失明细 + 只读命令。 复用正式判决，避免再建一套计数器。
  • 不从日汇总反推节点：共享工作目录会混淆不同执行。
  • 不从模型猜组：历史分组不应随当前配置改变。
  • 不做新仪表盘、通用事件平台或账号额度分摊：本单不需要，也无法可靠归因。

07 · 怎么证明数字可信

隔离环境跑基准 4 张模拟单：正常首过、失败返工、founder 打回、换体，再加 1 张额度降级单。降级单要保留全部投入，同时不改变原组的统计。逐条原始记录和手算表核对；再把相同事件重放，数字必须完全不变。

额外验证同一载体接返工、跨节点晚到用量、崩溃补读、缓存 token、缺账与历史缺口。两种模型载体都必须有真实原生日志的脱敏样本证明，不能全填未知就算通过。

dry-run 是只读运行：生产入口只查数据库，不建表、不补账、不改配置、不重启。设计和静态检查不能代替这些实现验收。
