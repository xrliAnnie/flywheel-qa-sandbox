FLY-2405 起房服务 — 设计总览

Issue FLY-2405 · 2026-09-28 · eng_design · Codex 设计评审 6 轮 APPROVED

一句话总结

让沙箱里的 runner（自动干活的 AI 工人）只发一条命令就能起 / 查 / 拆 529 测试房，真正的起房动作由沙箱外的 Bridge（Flywheel 常驻的调度服务进程）代为执行——Codex 和 Claude 一视同仁，Lead 不再手工代起代拆。

  • 529 测试房：一套隔离的 Bridge + Lead + 数据库，用来在真机上端到端验证改动。
  • 沙箱（Seatbelt）：macOS 给 Codex 进程套的"权限笼子"。笼子里起不了系统服务（launchctl bootstrap 报错 5）、看不到笼外进程（拆房拆不干净）、也不能再套一层笼子。
  • founder 2026-09-26 在 A/B/C 里选了 A：Bridge 提供起房服务。

核心流程图

runner 只"发请求、看结果"；抢房位、构建、起房、快照、拆房、清残留都在沙箱外完成。

命令：flywheel-comm room deploy | status | teardown。每个请求带 runner 独有的能力凭据（每次启动时发的一把一次性钥匙，别的 runner 拿不到）和请求号（网络断了重发也不会起两间房）。

房间状态机

每间房的生命周期是一张有限状态图（每一步只能走到规定的下一步）。关键是两条"安全回路"：包装器失联时先隔离，确认起房进程全部停止才放行；拆房失败可以再拆一次直到干净。

数据 / 结构模型

全部状态存在 Bridge 已有的 SQLite 状态库（单文件数据库）里，新增 5 张表；房间号是唯一稳定标识，界面展示用 slot 编号。

  • 审计表只追加：每次起房、拆房、每次被拒都留一行，含原因代码（如 room_not_owned、runner_role_refused）。
  • 快照回执：拆房前把房里的数据库逐个备份并记下校验值，证明数据没丢。

护栏：谁能做什么

请求结果
qa / implement 角色、运行中的 runner 起房允许
generic 节点或没钥匙的 runner 起房拒绝 runner_role_refused / unauthenticated + 审计
拆别人的房拒绝 room_not_owned + 审计
Lead 代拆任意房允许（Lead 不能替 runner 起房）
请求里夹带生产服务标签、路径、配置目录、token拒绝（参数逐项白名单，未知一律拒）
机器负载 ≥ 144排队，负载回落再起

已知 QA 失败一并收掉：最小环境缺 codex（按实际路径自动找工具目录，不写死）；建库前失败的房拆房不再卡快照；残留检查不再按命令行文字匹配（无关的观察进程不会被误判）；拆房失败后能再拆收尾并释放房位。

诚实边界：做什么 / 不做什么

做

  • 沙箱内一条命令起 / 查 / 拆房，Lead 零手工
  • 房位锁、归属、精确版本、负载排队、拆房前快照、全量审计
  • Bridge 崩溃、包装器被杀、网络丢响应都能恢复且不重复起房
  • 拆房零残留，只认"真正属于这间房"的进程

不做

  • 不是让不可信代码变安全的沙箱：被测代码仍以今天 Lead 手工起房的同等权限运行
  • Claude runner 本就不在沙箱里，服务对它只提供结构化和审计，不提供字节隔离
  • 不给 runner 任何生产 launchd / 生产 Bridge 操作权
  • 不做 e2e driver 代跑、codex:rescue（另开单）
  • 本节点只出设计，不写实现、不合并、不部署
