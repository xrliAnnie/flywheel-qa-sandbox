## 2. 建议的后续单（**本单不执行**，交 Tadashi 分诊）

按价值排序。每条都写清「为什么值得做」和「不做的后果」。

### 建议 1（推荐）：新建 `web-research` skill —— 浅研究专用

- **做什么**：把 research.md §5.1 的配方包成 `flywheel-skills` 里的一个 generic skill。无人值守、可并行、纯 CLI。
- **为什么**：现在每次「查个技术现状」都要拉 headed Chrome + 交互配对 + 串行等，成本与风险都远超需要。CLI 路 54 秒出结果且带引用。
- **不做的后果**：继续用重武器打小目标，并持续暴露在那条 8-13 晚刚坏过一次的浏览器链上。
- **关键设计约束**（从本单实测直接来）：
  - 必须 `-c 'web_search="live"'`（`codex exec` 不认 `--search`）
  - 必须 `< /dev/null`（否则非 TTY 挂死）
  - 必须 `--strict-config`（配置键写错要 fail-loud）
  - SKILL.md 里要**明写它的已知失效模式**：本单 n=1 实测出现过枚举漏项。要求调用方对「枚举类问题」自己补核，别把它当 DR 用。
  - 🔴 **不要默认套 `codex-with-fallback`**。本单 §8 就是被它咬的：撞限速/401 时它会**自行轮转全局 codex profile**，副作用落在 `~/.codex/auth.json` 这个**全机共享**的状态上 —— 一个「只读研究」skill 不该有这种半径。三选一，必须在 skill 里明确定下来：(i) 直接用 `codex`，撞限速就失败上报；(ii) 用 wrapper 但把轮转**限定在 skill 自己的 `CODEX_HOME`** 里；(iii) 用 wrapper 但**跑完必须复原并验证** active profile，且把变更写进产出。§5.1 的配方为了跟本单实测逐字一致才写的 wrapper，**不等于**推荐它进 skill。

### 建议 2（低成本，随手）：给 `deep-research` skill 加分流指引

- **做什么**：SKILL.md 顶部加一段「什么时候可以先试别的」：单点事实核查 / 文档核对 / API 现状，**可以先试** web-research，不满意再回来用 DR。
- **为什么**：能让使用者少用那条脆链，而又不需要先有受控数据。
- **注意（重要）**：§6 是 **n=1 的定性判断，不是实验数据**。指引必须写成**可撤回的默认建议**（「先试 A，不行升级到 B」），**不能**写成「某类问题一律走 A」的制度性规则，也不能写成量化承诺。制度化等建议 6 出数据。

### 建议 3（观察项）：订阅 openai/codex#29741

- [openai/codex#29741](https://github.com/openai/codex/issues/29741) 一旦被实现，本单结论立即需要复评。
- **触发复评**（任一条命中就该重跑本单，不需要三条同时成立）：
  1. `~/.codex/models_cache.json` 出现 deep-research 模型（服务端对 ChatGPT auth 下发）；
  2. `codex features list` 出现 deep-research 相关 flag，或 `codex --help` 出现对应子命令/入口；
  3. 建议 5 的 API-key 路径被验证可行（**注意**：这条不需要任何新 flag/子命令就能推翻当前结论 —— 现有 `-m o3-deep-research` 就是入口）。
- **翻案判据**（真正证明「行」的唯一硬标准，不依赖上面任何一条的形态）：
  - 在一次真机运行里，从 CLI 拿到**多步、带逐句引用的长报告**（不是单轮搜索的一段回答），并留下命令 + 原始事件流。
  - 同时必须记录清楚**是哪种 auth、哪个钱包** —— API-key 路径若通，是「行」但**不是订阅内**，与 Annie 的原始诉求只匹配了一半。

### 建议 4（infra-bot 线）：codex profile 快照漂移治理

- **现象**：`profiles/school/auth.json` 里的 refresh token 已被消耗，复原 school 会立刻 401（research.md §8）。
- **本单已做的**：把 live auth 恢复到可用的 `business` 并验证过；切换前按规矩 `save` 过，没丢 token。
- **本单没做的**：`/codex-relogin`（超出 research 单授权）。
- **归因边界**：**无法判定**这个漂移在实验前是否已存在（没有 before baseline）。别把它写成「既有问题」也别写成「本单引入」。

### 建议 5（本单未测的最有希望的一条路）：API-key 登录态下试 DR 模型

- **做什么**：`codex login --with-api-key`（该 flag **确实存在**，证据 `31-apikey-surface.txt`）后，试 `-m o3-deep-research`，看服务端是否放行。
- **为什么值得**：如果放行，就得到一条 **CLI 内、无浏览器、可无人值守**的 DR 路径——正是 Annie 想要的形态，只是换了钱包。
- **为什么本单没做**：会动 Annie 的 API-key 钱包（按 token 计费，DR 模型单次成本不低），且本单红线是不改登录态。**这是授权问题不是技术问题**，需要 Annie 拍板。
- **风险提示（要先跟她说清）**：即使技术上通，它**不是订阅内**，成本模型完全不同；要先估一次 DR 大概多少钱再决定。
- **不做的后果**：本单结论会一直停在「ChatGPT auth 不行」，而没回答「那换个 auth 行不行」。

### 建议 6（把定性升级为数据）：DR vs CLI 受控对比

- **做什么**：挑 3–5 个真实调研问题，**同题、同时**各跑一次浏览器 DR 和 CLI 路，人工评分（准确性 / 完整性 / 引用质量 / 耗时）。
- **为什么**：research.md §6 目前是 **n=1 + 无对照臂**的定性判断。要拿它去做「哪类任务走哪条路」的**制度性**分工，需要真数据。
- **不做的后果**：分流规则建立在一次运行的印象上，可能把 CLI 路低估（或高估）。
- **优先级**：低于建议 1/2。可以先按定性判断分流，跑一段时间后再补这个实验。

## 5. 已知的、本单主动声明的证据弱点
