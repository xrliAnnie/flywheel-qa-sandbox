FLY-1505 设计:ship run 状态追踪 + 假「卡死」拦截

Issue: FLY-1505 · 设计阶段 · 2026-07-27 · 原方案已过 Codex 设计评审(6 轮,APPROVED),本页已纳入 Lead 增量裁决 · 每个板块下方都可以留评论,页底一键汇总复制

① 一句话总结

昨晚的事故是:Runner(替你干活的 AI 工程师会话)发出 :cool:(在 PR 上发的表情评论,是「跑完整测试然后自动合并」的开关)之后只等 10 分钟,而全套测试要跑约 20 分钟——于是它在测试还健康运行时就误报「我被卡住了」,这一误报把你还活着的批准直接作废。本设计做两件事:不再另设第二只倒计时钟,而是盯住本次 GitHub workflow run 直到它给出终态;以及把「ship 没成」和「会话卡死」彻底分开——今后 ship 尝试失败只会「报告 Lead + 原地待命」,你的批准永远不因此失效。

② 出了什么事(事故链)

逐行核实过的完整链条(FLY-1497 当晚实发)。关键在最后两步:「blocked」(会话被标成"卡死等人处理"的状态)一旦写入,合并前的最后一道核验 verify-approval(确认你的批准还有效的检查命令)就永远不放行,而且这个状态没有回头路。

错的不是 Runner——它忠实执行了规则;错的是规则里那个 10 分钟(写死的旧数字,测试预算涨了没人同步它),以及「等不到就自报卡死」这个善后动作本身。

③ 修复后的流程(新规则)

Runner 发出一次 :cool: 后,只认这次评论对应的 started 回执(流水线启动后写回 PR 的机器记录,里面带 GitHub run 编号),拿到 run_id 后每 60 秒查一次真实 run 状态。queued/in_progress 就继续等,由 GitHub 按 workflow 自己的预算决定何时超时;success 才确认合入,failure/cancelled/timed_out 立即报告 Lead。旧一轮回执一律忽略。无论失败还是追踪链失灵,善后都是「报告 Lead + 原地待命」——绝不再自报卡死。

追踪链失灵时的动态兜底

如果 started 回执迟迟不出现,或 GitHub 查询持续报错,Runner 才从当前检出的 .github/workflows/ship-on-comment.yml 现读唯一的 timeout-minutes,再加固定 5 分钟评论传播缓冲。契约测试不再钉另一个等待常数,而是钉住「本次回执 → run_id → run 终态」协议,并确保 workflow 文件只有一处可解析的 timeout——系统里始终只有 GitHub 那一个超时权威。

④ 服务端拦截闸 请你裁决

只改规则文本有个盲区:已经在飞的旧规则 Runner(重启前启动的会话)还带着旧规则,将来文本再被误读也没人拦。所以加一道服务端闸:凡是「已批准待合并」(approved_to_ship(你已批准、只差合并的会话状态))的会话发来「我卡死了」的报告,服务端一律拦下——不翻状态、写一条持久标记(记在会话档案里的一行记录:「这版代码的 ship 尝试失败过」)、第一次提醒 Lead、并暂停系统对同一版代码的自动叫醒(系统每隔几分钟把闲置会话叫醒重试的机制)——否则会话会被反复叫醒、无诊断地反复触发合并,违反你定的「:cool: 点一次就等」。

保护性机制表单(按你的反过度反应规则单列)

防的场景昨晚两次实发(FLY-1497 假报 + 另一单假 blocked 待补账);后续:在飞旧规则 Runner、未来文本再漂移、新接入的其他厂牌 Runner 误用
为何改文本不够文本只对新启动的会话生效,且是软约束(AI 执行);本次事故恰是 Runner 忠实执行了错误文本——没有任何服务端拦截
常驻成本三个入口各一个前置判断 + 一条档案标记 + 一条去重提醒;零新状态、零新定时器、零流程图改动、零新数据库列
误伤面「已批准待合并」阶段的会话唯一剩余任务就是合并,这个阶段的「卡死」必然是 ship 尝试问题;拦下也不静默——提醒 + 标记可查
撤除条件FLY-1498 新一代门模型把「ship 尝试」建模成独立动作后,这道闸随旧路径一起退役

⑤ 数据与结构:改动落在哪里

层改什么不改什么
Runner 规则文本(1 处)只认本次编号的 started 回执,提取 run_id 后盯 GitHub run 终态;追踪链失灵才现读 workflow timeout + 5 分钟传播缓冲;善后改「报 Lead + 待命」「Runner 永不自己合并」红线原样保留;不新增第二个 deadline
服务端入口(3 处)实时接收、进程内、重启补账三个入口统一拦截「批准后的假卡死」;裁决逻辑收敛在一个共享函数里(含「失败属于哪一版代码」的三态判定:当前版→记标记;过期版→归档不污染;版本不明→保守处理,绝不覆盖真记录)普通工作中会话的「卡死」处理一个字节不变
自动叫醒(1 处)对「同一版代码已有失败标记」的会话暂停自动叫醒;Lead 人工唤醒不受任何影响没有标记的正常滞留会话照旧被叫醒
最后核验 verify-approval一行不动(它的状态检查是安全底线;状态不再被翻,检查自然通过)—

配套回归测试 8 组:契约测试、三入口各自的拦截测试、「批准仍可用」的端到端验证(对应 issue 要求的「模拟测试跑 25 分钟不误报」)、版本三态真值表、自动叫醒抑制与不回归。

⑥ 关键取舍与被否方案

方案裁决理由
只把 10 分钟改成另一个固定数字否第二只时钟迟早再次漂移,而「等不到就自报卡死」这个毒药善后也仍在;改为盯 run 终态才消除双 deadline
放宽最后核验,让「卡死」状态也能合并否那道检查是安全底线;「卡死」是个大杂烩状态,放宽等于扩大合并授权面
给「卡死」加一条回到「已批准」的返程路否治标:误报照样发生、提醒照样响、状态照样先错后对;返程路对真卡死的会话反而危险
run 终态追踪 + 善后改向 + 服务端拦截(三层)采纳文本消除第二时钟、拦截兜住在飞旧会话与未来漂移、结构合同防协议退化;Lead 已批准增量裁决

另有两项「想过但不做」:给命令行再加一道拒绝闸(与服务端重复,且在测试房间里容易误拒);给标记加清除命令(Lead 人工唤醒本身就是恢复动作,多余的状态面)。

⑦ 诚实边界:这个设计不解决什么

  • Runner 真崩溃(进程死掉)时批准同样会失效——那是另一个问题,属于 FLY-1448(批准链路重写)的持久恢复范畴,本单不扩。
  • 「拦下后 PR 稍后真合并了」的自动收尾不在本单:近期靠 Lead 收到提醒后人工闭环;结构性方案在 FLY-1448 的外部权威对账。
  • 提醒是尽力送达(投递管道本身不保证必达):可靠性靠持久标记(随时可查证)+ 新规则下 Runner 自己的报告主通道;最坏情况是会话安静地保持「已批准待合并」等 Lead 巡检——仍严格优于现状(现状是批准直接作废)。
  • 窗口是 AI 执行的行为约定,没法用单元测试真跑 25 分钟墙钟;代码级等价验证 = 契约测试(窗口 ≥ 预算+余量)+「误报不能作废批准」的端到端测试。Codex 评审认可此映射诚实且足够。
  • 生效需要一次生产重启(搭 FLY-1507 合入后的统一重启窗,不单独重启);重启前的在飞旧会话正是由拦截闸兜住。落地并观察到首个真 ship 走新规则后,Lead 撤销现行临时硬指令。
