FLY-2169 · 让 Codex 工人在 cmux 里可见

设计方案(已通过 7 轮 Codex 独立设计评审)· 2026-08-29 · engineering/doc/FLY-2169-codex-cmux-visibility/

1 · 一句话总结

给每个 Codex 工人配一个「只读转播窗口」:工人一启动,cmux 里就出现一个实时滚动它工作过程的窗口 —— 不再依赖那个一晚死了 47 次的旧连接方式。

cmux(你平时看所有 AI 工人的那个多窗口界面,它是 tmux 终端窗口的镜像)里,claude 工人一直都有自己的窗口,但 Codex 工人(用 OpenAI Codex 引擎干活的工人)的 implement 段一直是黑的。那晚你连问四次「我怎么什么都看不到」,就是这个病。

重要事实:工人本身没有偷懒,活一直在干 —— 坏掉的只是「让你看到它」的那条通道。这张单修的就是可见性。

2 · 病根 — 旧通道为什么系统性地坏

Codex 工人是一个 socket 直连子进程(Bridge 在后台直接拉起的一个 codex 程序,通过一条本机内部管道对话,天生没有终端画面)。旧方案为了让你能看,会另开一个窗口跑 codex resume —— 相当于「再开一个 Codex 客户端连进同一个会话旁听」。实测这条路有两个治不好的病:

  • 出生依赖时机:旁听客户端要求工人的会话记录文件已经落盘,而落盘时机 Bridge 控制不了 → 经常「文件还没出现」→ 窗口出生 0.2 秒后就死;
  • 旁听本身有副作用:撞上正在写记录的工人时,Codex 会另起一个分叉线程 —— 那晚一个工人家目录里被塞进 3 个 2.5MB 的分叉副本。

窗口一直开不起来,账本(comm.db,记录每个工人在哪个窗口的数据库)里的窗口名就永远停在占位符 pending —— 连锁反应:cmux 找不到它、issue 页面的「跳转到工人」按钮失效、巡逻探活把活着的工人误判成失联(那是 FLY-2155 在修的另一半)。

3 · 新方案 — 只读转播窗口(核心流程)

思路换掉:不再「连进去旁听」,改成 Bridge 自己当转播员。工人对 Bridge 说的每一句话(它本来就全部流经 Bridge),由一个转写器 sink(一段把机器消息翻译成人话并写进文件的程序)实时写进一个转播文件 transcript.log(这个工人专属的文字直播记录);cmux 窗口里只跑一条最朴素的命令 tail -F(持续滚动显示一个文件的最新内容,文件还没出现就安静等待 —— 本机已实测)。

为什么这条路稳

  • 窗口出生和 Codex 完全解耦:开窗只需要 tmux 正常,不依赖 Codex 程序的任何状态 → 「出生即死」从机理上消失;
  • 零副作用:纯只读,不再触发分叉线程、不污染工人家目录;
  • 窗口一建好就把真名写回账本 → cmux / issue 跳转 / 巡逻三面同时受益(占位符 pending 的存续时间从「永远」缩到几秒);
  • 开窗绝不拖慢工人:窗口是并发开的,tmux 再慢再卡,工人照常瞬间启动(评审第 3 轮钉死的规则)。

数据与结构(给想看细节的你)

东西放哪 / 长什么样
窗口命名沿用现有规范 FLY-XX-role-…(和 claude 工人一样,你在 cmux 里按单号找)

4 · 工人结束后,窗口怎么办

规则只有一句:和 claude 工人一模一样。成功的窗口按既有规则关掉;失败的窗口留着当「案发现场」供人查看,24 小时后自动回收;超时的当场关(claude 工人的既有规则 FLY-86);账本登记失败时兜底关窗,防止探活误判。不管窗口关不关,转播文件永远在 —— 你想看「它最后说了什么」,现场永不丢失。

5 · 关键取舍与被否的方案

方案结论为什么
否把旧的「连进去旁听」修好治标死因(记录落盘时机、分叉副作用)都在 Codex 程序内部,Bridge 只能猜和等;上一轮加固(FLY-1239)之后仍然一晚 47 死
否窗口里跑一个自研阅读器直接啃 Codex 的原始记录文件更差的同方向又绕回「等文件出现」的死结,且阅读器自己也是个会崩的长活进程
否两条路都保留,坏了互相降级机制翻倍违反你定的红线「宁删机制,不长机制」
否改成在网页 Dashboard 里看不解本题你的主观察窗是 cmux,这张单的验收就在那扇窗里
选Bridge 转播 + 窗口只跑 tail✔窗口永不难产、零副作用、渲染逻辑可单元测试

评审过程里的一次重要回头

设计中途我一度给「失败后留窗口」加了一套跨账本的保留证明机制,结果独立评审的意见一轮比一轮多(1 条 → 3 条)—— 这正是「机制在生长」的信号。第 5 轮起整套撤销,改成与 claude 工人逐字节同构:7 轮评审,前 4 轮 6→4→3→1 收敛,第 5 轮回头删机制,第 7 轮通过。净结果:新增 1 个模块(转写器),删掉 4 处脆弱机制,跨包新契约 0 个。

6 · 诚实边界 — 这张单做什么、不做什么

做

  • Codex 工人的 implement 段在 cmux 里可见、可读、随时点开(验收 = 你那扇窗);
  • 账本窗口名写真名 → cmux / issue 跳转 / 巡逻同时受益;
  • 终局现场永久留在转播文件里。

不做(以及为什么)

  • 不修探活判定本身 —— 「把活工人误判成失联」的引擎侧修复归 FLY-2155(在飞),两单已写好协作契约:探活以后不该看窗口,该看工人进程本身;
  • 窗口只读,不能在里面打字指挥工人 —— claude 工人的窗口可以,Codex 转播窗口不行(想干预仍需手动连接,自担分叉风险)。这是与 claude 体验的唯一差距,本单不承诺;
  • Bridge 自己崩溃时的残窗交给既有的巡逻回收,不新造机制;
  • 转播美化的完整词表要等实施时对真实消息流采样后定稿 —— 没见过的消息类型会以紧凑单行兜底显示,保证永不黑屏;
  • 评审发现的一个既有小缺口(超时状态的账本行不进某个清理谓词)与本单无关且不因本单变坏,建议另开小单。
