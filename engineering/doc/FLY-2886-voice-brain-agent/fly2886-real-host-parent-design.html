FLY-2886 语音后台：在真机上起得来

FLY-2886 · 增量设计（plan v12 §14）· 2026-09-26 · 仓库文件 engineering/doc/FLY-2886-voice-brain-agent/plan.md

0. 为什么有这一版

第二轮独立测试（QA）第一次在真电脑上打开语音后台，结果一次都没起来。之前实现阶段的证据都是在「替身环境」里拿的，真机上的缺口没暴露出来。这一版只补这个缺口；之前已经通过的设计（防重复写、确认句判断、开场简报等）一个字不改。

真机上撞到的用人话说这一版怎么处理
原生技能基线没装Codex 自带的几份内置技能，要有一份「标准副本」来核对没被篡改；这台机器缺 0.156.1 这一版的副本写进部署前的清单；缺了也只是后台不开，语音照常
记忆库 gbrain 没配置这台机器上没有 gbrain 的配置文件不装这一项，其他照开
Context7 工具表对不上一个查技术文档的外部服务，它现在提供的工具清单和我们登记的不一样不装这一项（对不上的工具绝不给模型用）
node 在沙箱里起不来给后台助手用的工具程序是用 node 跑的；「沙箱」只放行了 node 本身，没放行它运行要用的配套库文件把配套库文件精确地加进放行清单；常驻 Lead 那边同一个毛病一起修
缺 Linear 密钥没有 Linear 的访问密钥不装 Linear，其他照开

「后台 parent」＝ 给后台助手提供工具的那个本机程序；它起不来，后台助手就什么也做不了。
「沙箱」＝ 限制程序只能读写指定文件、不能乱碰电脑其他地方的安全围栏。

1. 一句话

缺什么就少什么，不再一个缺口拖垮整场：少一个工具就只少这一项；后台整个起不来，就退回成「只陪你聊、要查的事转给 Lead」的前台语音，绝不让你进房后听到「语音不可用」。

2. 开场时怎么走

你进房后，程序先试着把后台整套起起来，这一段叫后台准入段（开后台之前的全部检查，最多给 35 秒）。过了就是完整版；任何一步没过，就把已经起的东西关干净，退回前台语音。

Bridge＝ Flywheel 的中枢服务，记录每场语音会话的状态。先让 Bridge 记下「这场降级了」，再去拿开场简报——这样 Bridge 给的就是前台版简报，不会让前台以为自己能查东西。

3. 哪些缺了会降级，哪些缺了只少一项

后台用到的外部服务叫集成（每一个都是一类工具，比如 Linear、GitHub）。我们把它们分成两类：

能力清单（manifest）＝ 这一场后台实际能用的工具名单，开场简报里的「能做什么 / 这场没接上什么」就从它生成。缺了的集成会带着原因写进清单，原因只有下面四种，用固定的中文说，不会把电脑里的报错原文或文件路径念给你听：

原因简报里怎么说例子
credential_missing缺凭据没有 Linear 密钥、没登录 GitHub
host_config_unverified宿主没配置没有 gbrain 配置文件，或它被改过
baseline_drift工具表跟登记的不一致Context7 现在的工具清单变了
provider_start_failed启动失败其他连不上、握手超时之类

安全底线不变：如果是我们的代码漏装了某个工具（不是外部缺东西），照样启动失败、不放行。

4. 沙箱只多放行「node 真正要用的那几个文件」

node 启动时要加载一串配套库文件（dylib，macOS 上的共享库，类似 Windows 的 .dll），还会读一份加密库配置（OpenSSL，负责加密的底层库）。以前沙箱把这些都挡了。

  • 只放行精确的文件，不放行整个目录——比如不会把整个 /opt/homebrew 打开。
  • 加密库配置不去放行系统里那份（不同的 node 读的位置不一样），而是让 node 读一份我们自己写的、内容为空的最小配置。
  • 放行之后还要真跑一遍「隔离探针」（在真沙箱里用真 node 跑一次，证明该挡的仍然挡住、该能跑的能跑）才算过。

5. 上线前要准备的东西（会写进 PR）

项缺了会怎样
Codex 0.156.1 内置技能标准副本（这台机器 QA 已装好，上线前只复核）后台降级，前台照开
Bridge 地址和口令、你的 Codex 订阅登录、部署版本记录一致、系统自带的 otool 工具可用后台降级，前台照开
Linear 密钥只少 Linear
GitHub 登录只少 GitHub 和巡检快照
gbrain 配置（这台机器现在没有）只少记忆库
Context7 登记更新（现在对不上，另开单）只少技术文档查询

语音后台默认仍是关着的，合并后由 QA / Lead 在测试 Lead 上先打开。

6. 怎么证明「真机上起得来」

都在 529 测试房（一套和生产隔开、但用真电脑真程序的测试环境）里做，不装任何替身，用这台电脑真的 node 和 Codex，登录凭据直接指向生产那份（链接过去，不复制）。

测什么过的标准
R1 真机现状下起后台（有 / 没有 Linear 密钥各一场）后台起来、走订阅；清单里「没接上」的正好是这台机器缺的，原因对；隔离探针用真 node 通过；问一张单的 PR 状态，口语里单号和 GitHub 一致；有 Linear 的那场能改一个测试 issue 的状态
R2 后台起不来时这场语音照样开；thread 里出现那句降级提示；要查的事转到 Lead 信箱；后台相关的进程全部退出；全程没有「语音不可用」
R3 常驻 Lead 不受影响常驻那边隔离探针用真 node 通过（修之前同一个测试先失败）；常驻的能力清单和改之前一字不差

R2 里「让后台起不来」是用测试接口人为制造的：真机上能自然制造的核心故障都会连带语音主程序一起坏，没法只坏后台。「真后台能起来」这件事由 R1 在零替身条件下单独证明。

7. 取舍和没选的方案

  • 「缺了只少一项」这次只给语音后台用。常驻 Lead 今天的规矩是「缺一个就整个不起」，改它会改变生产 Lead 的行为，属于另一张单；已经问过 Lead，默认先不动。顺带一提：这台电脑上常驻的 Codex Lead 因为同样缺 gbrain，现在也起不来——这是现状，不是这张单引起的。
  • 没选：放行整个 Homebrew 目录（太宽，会连带别的工具的配置和密钥）；放行系统里的加密库配置（不同 node 位置不同，也查不准）；给缺了的工具放一个「永远拒绝」的假工具（模型会去试，然后又夸口）。
  • 降级的那场还是逐字念 Lead 的回答：因为降级场里查东西的是 Lead 本人，走的是你试过的 FLY-2884 原型那条路。

8. 诚实边界：做什么、不做什么

做：后台在真机上能起来；缺集成只少那一项，简报里如实说「这场没接上什么」；后台整体起不来时退回前台语音、在 thread 里告诉你；沙箱放行 node 真正需要的文件，常驻同修；上线前清单写进 PR。

不做：会话中途不重连缺的集成（要等下一场）；不放宽任何「工具清单必须和登记一致」的检查；不改常驻 Lead 的「缺一个就不起」规矩；不修 Context7 的登记（另开单）；不帮这台电脑配 gbrain。
