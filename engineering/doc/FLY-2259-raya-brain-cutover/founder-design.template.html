FLY-2259 · Raya 的文本脑搬进「有人看着」的体制

设计方案(design 节点交付)· 2026-09-02,09-03 按你的「每个 codex lead 都 generic」要求修订 · Issue FLY-2259 · 分支 flywheel-FLY-2259 · 上游 FLY-2216 / FLY-2131 / FLY-2239
● 1. 一句话总结

把 Raya 的文本脑(Codex 会话)以 com.flywheel.lead.raya-raya 这个身份正式「上岗」——常驻一个窗口、每 3 秒写心跳、假死时 Bridge 自动换体并告警;为此先补齐七样前提、走一次 founder 在场的激活窗口;她现有的语音网关一字不动,不存在「两个脑子抢话」。为此要改的那一点代码不是为 raya 单写的:每个 Codex Lead 的独立凭证目录走同一条规则,raya 只是第一个套用的配置。

名词:文本脑 = 在 #raya 频道用文字跟你对话的那个 Codex 会话。受管常驻体制(FLY-2216)= Flywheel 给每个 Codex Lead 配的一套「常驻窗口 + 心跳 + 假死自愈 + 告警」。launchd = macOS 的系统级进程保姆,进程挂了它会拉起来。激活窗口 = 一段你在场、按手册逐步操作生产机器的时间段。

● 2. 现状实核与两个纠正(Tadashi 已裁)

纠正 1「旧脑」不是脑,是语音网关

issue 里要「退旧脑」的对象 com.xrli.raya.brain,读它的源码确认:它只做三件事——听 /voice、/endvoice 和「进入/退出语音模式」这几句话去拉起语音进程;会议命令(现在没配置,停用);每 60 秒记一次资源占用并在语音掉线时告警。它一句自然语言都不会回。本机现在也没有任何 Raya 文本对话进程在跑——#raya 的文字面目前其实是空的。

后果:把它退掉 = 你失去语音入口。所以裁定为 A:产品网关原样保留;「退旧脑」改成「退应急观察窗」(一个只会 tail 日志的临时脚本)。新脑上线后不存在双脑——一个管语音开关,一个管文字对话,是两层不是两个。

已知边界:你打「进入语音模式」这句文字时,网关会拉起语音,新脑可能同时用文字回你一句。用斜杠命令 /voice 则零重叠(斜杠命令是 Discord 的「交互事件」,新脑的轮询看不到)。

纠正 2新脑要有自己的 Codex 凭证目录

原设计让新脑和语音进程共用同一个 CODEX_HOME(Codex 的凭证 + 配置目录)。实核发现:新脑首次启动会整体重写那里的 config.toml,语音进程的 Codex 线程会跟着继承新的沙箱设置,还会多出一套它用不了的工具。Tadashi 按你的铁律「凭证一体一号」裁定:新脑用独立的 ~/.codex-raya;语音那份原样不动、前后 sha256 必须相同。按你 09-03 的要求,这个目录名不是给 raya 单写的常量,而是「每个 Codex Lead 的凭证目录 = ~/.codex-<名字>」这条通用规则算出来的:mufasa 与 InfraBot 今天用的 ~/.codex-mufasa、~/.codex-infra-bot 也套同一条规则,算出来和现在一字不差。

代价:需要你登录一次 Codex(进那个新目录),用哪个账号由你定。这是前提清单第一条,Tadashi 会在 plan 定稿后向你申请。具体就三步,在生产那台 Mac(MacBook-Pro,跑 Bridge 的那台)你自己的终端里做:

  1. 建目录:install -d -m 700 ~/.codex-raya
  2. 登录(会弹浏览器让你选账号):CODEX_HOME=~/.codex-raya codex login
  3. 验一下:CODEX_HOME=~/.codex-raya codex login status 应打印 Logged in using ChatGPT;stat -f '%Lp %Su' ~/.codex-raya/auth.json 应是 600 xiaorongli。

同一个 ChatGPT 账号可以在多个目录各登一次,每个目录自己一对令牌;绝不复制 auth.json(两处共用同一刷新令牌会互相作废)。登完只记「已登录 + 账号别名 + 时间」进台账,不记令牌。

补两样issue 没列的隐藏前提

  • standalone codex(Codex 的独立安装包,常驻窗口这种「远程控制」模式只能用它)没装在新目录——装配脚本会直接拒启,不会自动装。要在窗口前显式装,版本与 mufasa / InfraBot 对齐(现在是 0.153.0)。
  • summary 名册回执会失配:往名册里加 raya 这一行,会改变一个摘要指纹;每次系统重启前的检查要求指纹与回执一致,不一致就拒绝整舰重启。已在副本上验证:注册后紧接着刷新回执,检查就通过,名册内容一字节不变。

代码改动:一条通用规则,三处接线(不是为 raya 单写)

  • 规则(唯一来源,放在已有的共享库 scripts/lib/lead-address.sh):给一个 Lead 的名字,算出它的凭证目录 ~/.codex-<名字>。纯函数,不读名册、不读环境,名字不合法就拒绝。
  • 三个在跑/将跑的 Codex Lead 启动脚本(mufasa、InfraBot、raya)各自只声明自己的名字,统一调这条规则取默认目录。mufasa/InfraBot 算出来与今天完全一样(有测试盯着这一点),raya 由此得到 ~/.codex-raya。
  • 自愈脚本 resident-codex-lead-recover.sh:核验「这个进程真的是那个 Lead」时的期望目录也用同一条规则算,不再手写三份;并新增一条负例测试——进程若还挂在旧的共享目录,自愈拒绝动手(零 mutation)。
  • 再加一份对「全部 Codex Lead」的结构测试:任何一个启动脚本偷偷写回字面量、或自愈脚本与启动脚本的名字对不上,测试就红。
  • 其余全是文档、手册和物料(名册行 JSON、回执清单、一段通用的持锁原子写脚本)。FLY-2216 的巡视/心跳/告警机制一行不改。

名词:通用规则 = 不针对某一个 Lead 写死路径,而是一条对所有 Codex Lead 都成立的算法;mutation = 对生产机器的任何改写动作;零 mutation = 检查不过就什么都不碰。持锁原子写 = 改名册时先拿系统级的排他锁,写到临时文件再一次性换名,别的进程要么看到旧文件要么看到新文件,不会看到半截。

一处诚实说明:mufasa 与 InfraBot 的目录名(.codex-mufasa、.codex-infra-bot)早于这条规则,与名册里的正式 id(mufasa-lead、codex-infra-bot-lead)不完全一样。规则用的「名字」是每个 Lead 自己声明的一个短名,新 Lead 约定用正式 id(raya 就是);要把两位老 Lead 的目录也改成正式 id,要搬两位正在跑的 Lead 的凭证目录,是另一张单。

● 6. 真机自愈演练:怎么证明「假死有人管」
图 4 · 用 SIGSTOP(把进程「冻住」,可随时解冻)制造 FLY-2216 病案那种活体假死;预计 5–8 分钟走完:心跳停 → 三次判定 → 真告警进 #flywheel-alerts → 自愈脚本二次核验并留回执 → launchd 原地换新进程 → 新一代心跳。

为什么不是直接 kill

被 kill 的进程 launchd 会立刻拉回来,巡视根本看不到「假死」——那验的是 launchd 不是本单的机制。SIGSTOP 才是 8-31 那天的病:进程还在、什么都不干。

时机

巡视名单在 Bridge 启动时定死,所以注册后要等下一班车重启 Bridge 才覆盖 raya(≤12 小时;想立刻覆盖只能你单次批一张 request-restart.sh 票)。这段空窗里进程崩溃仍由 launchd 管,只是假死没人巡视——如实写进台账。

另外两格

  • 关窗重建:把 tmux 窗口杀掉,20 秒内新脑自己把同名窗口建回来,cmux 同名 workspace 复用不开第二个。
  • 语音对照:语音那份凭证目录的 config.toml 前后 sha256 相同 + 你开关一次 /voice 正常——这就是「raya 产品行为零改」的直接证据。
