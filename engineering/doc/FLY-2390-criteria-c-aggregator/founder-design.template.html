FLY-2390 · 判据 c:这个版本稳不稳,机器怎么给出 green / hold / unknown

Issue FLY-2390 · 1143 Epic 的 B3 · 设计节点 · 2026-09-10 · Codex 设计评审 3 轮(R1 6+1、R2 6+1 全部采纳;R3 7 项按 Lead 裁定 1d9ea778 收口)后 effective APPROVED · 文档:engineering/doc/FLY-2390-criteria-c-aggregator/

一句话

给「我们自己机器上跑的这个版本」装一个会说人话的健康表:它把这版跑出来的告警、报上来的 bug、你随手点的 👎 汇成一个结论 —— green 可以发、hold 先别发、unknown 说不清;而且只要它自己不确定,就一律说「说不清」,绝不把「没看见事」当成「没事」。

名词解释:判据 c = PRD 1098 里定的「这版稳不稳」的三个信号(告警数、bug 数、你的手感);B3 = 1143 Epic 里负责算这个结论的那一块,它算出来的结论会喂给将来的 B4(「你不喊停就自动发」的那扇门);sourceCommit = 一个版本对应的那一次代码提交的指纹,是本单里所有账都对得上的唯一身份。

审计发现的三件现场事实(设计前必须知道)

事实 A:issue 标题里写的「FLY-942 原始事件」,它的探测器已经被拆了

FLY-942 当年造的「盯着每个 runner 看它卡没卡」的看门狗,在 FLY-1570 / FLY-1560 被整体拆除(仓库里还有一条守卫测试,专门禁止它复活)。今天真正还在产出「原始事件」的,是告警系统本身:每一条发到 Discord 的告警(崩溃、重启失败、部署失败、死信……)在发出去之前都会先在同一个本地小数据库里「登记领取」。生产库里有 3.4 万条这样的登记,最近 30 天里包括 26 次部署失败、21 次崩溃循环、142 次 Bridge 非正常退出。所以本单消费的是这条告警登记流,不是一个已不存在的看门狗。

事实 B:这些事件今天都不带「哪个版本」

告警登记只有四列(事件 id、哪个 Lead、什么类型、几点),没有版本、没有严重度。部署记录倒是有(更新器每次把新代码部署上来都会记「哪个 commit、几点」),但事件和部署之间只能靠时间硬对,重启窗口里对不准。

事实 C:我们自己机器上跑的 commit,和「beta 版」的 commit 通常不是同一个

更新器每天 00:00 / 12:00 把 main 上最新的代码部署到这台机器;而 beta 版是每 6 小时从 main 上另切一次的。实核当天:机器上跑的是 d964e9f,最新的 beta 1.56.0-beta.4 切自 92532e2。两条线各走各的,这是 PRD 自己写明的设计。

这条事实决定了一个重要取舍:本单只对「这台机器真的跑过的那个 commit」给结论;将来 B4 拿一个机器没跑过的 beta 来问,答案就是「说不清(没有部署证据)」。Tadashi 已裁定接受,并另立一张单去把更新器和 beta 线对齐。

核心流程:在事件发生的那一刻盖章,而不是事后猜

核心动作只有一个:每条告警在被看见的那一刻,记一条「这个事件 + 此刻机器跑的版本 + 有多严重」的观测。Bridge 程序发的告警,在进入告警函数的第一步就直接写进 Bridge 自己的账本(比任何「去重」「没 token」的提前退出都靠前,所以一条都漏不掉);shell 脚本发的告警(部署失败这类最要命的),在它「登记领取」的那笔本地数据库事务里先记观测,事务失败就先落一个本地缺口文件再继续发。同一个事件如果换了版本再出现,是一条新的观测(Codex 评审抓到的一个真坑:事件 id 里不含版本)。之后 Bridge 里一个每 60 秒跑一次的小任务(仓库里叫 rider,就是「搭现有定时器便车、不新开定时器」的意思)把 shell 的观测和缺口搬进账本,并追加一行自己的心跳(「这一刻我活着,告警系统没被关掉,登记库读得到,积压最老的一条有多久」)。

图 1 · 从告警发生到日报与 B4 的完整流向(流程图)
  • 报 bug:走 Bridge 的建单接口时,只要 label 是 Bug,就自动在描述末尾加一行 Reported-on-version: 1.56.0 @ d964e9f…;并且先在本地账本记一条「意图」,再去 Linear 建单,建成后把 issue 号填回去。中间任何一步断了,意图会一直停在「未落定」,结论就一直是「说不清」,直到有人用命令收口 —— 一个真实的 bug 绝不会因为程序崩了一下就从账上消失。「这版 N 个 bug」数的是这本账,不去查 Linear(生产里 Bridge 对 Linear 的绑定是空的,查不到)。
  • 你的 👍/👎:每天的日报会发一条 Discord 消息,Bridge 只看那条消息上你本人点的反应(用现有的「核实是 Annie 本人」的逻辑,翻到最后一页为止)。👎 = 直接 hold;👍 = 不改判(健康由客观信号说了算);不点 = 不阻塞。发消息之后先把「哪一天、哪条消息」写进本地文件再登记,登记失败也不会重发消息;还没成功看过反应的那一天,结论按「说不清」处理,而不是当成「你没点」。
  • 评估是一个纯函数:同样的输入永远给同样的结论,所以能用回放的历史事件做验收,每个结论都带「原因码 + 证据 + 当时用的阈值」落账,随时可查。

三态怎么判:先问「我能不能下结论」,再问「好不好」

顺序是固定的:先把所有「说不清」的情况排掉,再看「该不该拦」,最后剩下的才是 green。这就是 PRD 里 Codex 反复强调的 fail-closed(拿不准就往安全的方向倒)。

图 2 · 判定顺序;所有阈值都是配置项,默认值写在表里(流程图)
结论触发条件(默认阈值,全部可配,并且每次结论都会把当时用的阈值一起记下来)
unknown这个 commit 在本机没有部署记录 / 本机现在跑的不是它 / 问的版本号和它跑时记下的版本号对不上 / 跑够的时间不到 12 小时 / 最新心跳超过 10 分钟没更新 / 期间心跳缺口累计超过 30 分钟(开头结尾都算)/ 期间任何一次心跳说「来源不健康」(Bridge 主循环不新鲜、告警投递被关、登记库读不到、搬运失败、积压太老、缺口目录写不了、有坏行)/ 评估这一刻还有没搬进账本或损坏的本地文件 / 有 severe 告警但观测时不知道版本 / 有任何一条「本该采到却没采到」的缺口 / 有还没落定的 bug 意图 / 「Bug」这个 label 最近一次解析失败 / 期间任何一天的日报消息还没成功看过反应、看的失败了、或看的太久没更新
hold期间任何一天的日报上你点过 👎(后来某天点 👍 不会抵消)/ severe 告警 ≥ 1 / warning 告警 ≥ 5 / 打了这版 tag 的 bug ≥ 1
green以上全都不成立

「期间」= 这个 commit 这一次连续部署的时段,但最多只看最近 14 天(和账本的保留期同一个数字,日报会标明「已截断」)。只算 flywheel 自己(以及整机级)的告警;GeoForge3D、growth 这些项目的告警和 flywheel 的版本无关,不计。info 级别的通知不计。同一个事件重复出现按一件算、严重度取最高。

数据与结构模型:一张盖章表、六张账本

左上角那张 alert_version_observations 是 shell 路径的「观测表」,住在告警登记的同一个小数据库里(现有的四列登记表和它后面的租约语句一个字都不动,只在前面加一条插入,这在仓库里有先例)。其余八张住在 Bridge 的主账本里;deployment_events 是更新器早就在写的部署记录,本单只读。

图 3 · 表与表之间怎么喂给最终的 verdict(实体关系图);心跳每 60 秒追加一行、永不覆盖,失败的那一行不会被后面成功的一行抹掉
  • verdict 同时记两个指纹:被评估的 subject_commit 和评估那一刻机器上的 local_deployed_sha,方便对账「机器到底跑没跑过它」(Tadashi 的附加要求)。
  • 不回填历史:上线之前的告警没有版本章,就不猜;评估窗口自然从第一条心跳开始。
  • 回滚干净:全是新表,老代码不读它们;还原 PR 即可,不需要清数据。
  • 收口有据:把一条「未落定的 bug 意图」标成放弃或补上 issue 号,只能用最高权限的 token,必须写理由,并留一条不可改的收据 —— 因为这是唯一一种能把「说不清」变回「可以发」的人工操作。

关键取舍与否决的方案

问题选了否决了什么、为什么
事件怎么知道自己属于哪个版本选发生那一刻盖章否事后按时间和部署记录硬对 —— 重启窗口里事件和部署交叉,对不准;而且告警的投递日志是「一个收件人一行」,要先去重。
用什么当版本身份选sourceCommit + 基础版本号否用 beta 号(1.56.0-beta.4)—— 这台机器从来不「装」beta 包,跑的是更新器部署的 main 代码;beta 号只是同一个 commit 在版本目录里的名字,而且可能根本没有。
哪些告警算数选按严重度(发出方定)+ 按项目否维护一张「哪些类型算数」的名单 —— 100 种类型,名单必漂(FLY-2386 的教训);要摘掉噪音走配置项,有变更记录。
bug 数从哪来选本地账本(建单时同一处记)否去 Linear 数 —— 生产里 Bridge 的 Linear 绑定全是空的;否每个版本建一个 Linear label —— 你的 /create-issue 规矩是「不建新 label」。
怎么收你的 👍/👎选盯日报那条消息的反应否让你敲命令或点按钮 —— 违背「减少 human-in-loop、只在想拦时出手」。
定时任务怎么跑选搭现有 60 秒定时器的便车否新开定时器 —— FLY-1560 之后的仓库规矩:零新定时器。
新账本留多久选沿用仓库现有的统一 14 天清理;小账本永不删否为本单另造 30/90 天的保留策略 —— 现有清理引擎只有一个 14 天刻度,要跑够的时间才 12 小时,14 天足够;少造一套机制(Codex R1)。
一个版本要看多长的历史选有界窗口 = 这次部署时段与最近 14 天取交集;部署的起止点单独快照进一张不删的表否看「完整部署时段」—— 账本 14 天就清,超过 14 天的部署会因为开头被删而永远「说不清」,或者悄悄忘掉早期的坏事(Codex R3);现在是明说「只看 14 天」。
观察者自己的健康放哪选自己的心跳表否塞进 /health —— 那份契约被测试锁死,不碰。

Tadashi 已裁的三个问题(设计期间非阻塞提问,已折入)

  1. 机器没跑过的 beta 怎么答? → 答「说不清(没有部署证据)」,不放宽;更新器与 beta 线的对齐另开一张 1143 子单;每个结论同时带两个指纹方便对账。
  2. 阈值默认值? → 先按上表(跑 12 小时、severe ≥1、warning ≥5、bug ≥1、心跳 10 分钟、缺口 30 分钟),全部可配并随结论落账。
  3. shell 路径的告警怎么进来? → 盖章必须本地完成、不依赖 Discord token、发送失败也要盖。本设计把盖章放在「登记领取」那一笔事务里,它发生在任何 token / 频道判定之前,满足条件。

怎么验收(issue 原文的验收,一条条对应)

issue 要求本单怎么证明
回放的 FLY-942 事件从生产登记库匿名化导出 30 条真实类型组合(部署失败、崩溃循环、Bridge 非正常退出、死信……)做成回放夹具,评估函数直接吃它
注入的心跳缺失一份完整 14 小时心跳、一份中间挖掉 45 分钟 → 后者必须得 unknown,原因码 heartbeat_gap

上线后第一个非「说不清」的结论最早要等 12 小时(要跑够时间),这是设计,不是故障。

诚实边界:这单做什么、不做什么

做

  • 告警盖版本章(shell + Bridge 两条路径)、Bridge 心跳与搬运、bug 页脚与账本、👍/👎 采集、三态评估与落账、日报渲染 + 每日投递脚本、给 B4 的查询接口。

不做

  • 不做否决窗口、送达回执、决策记录、任何真实发布或撤回(B1 / B4 / B5)。
  • 不读版本目录(manifest)、不持有任何发布凭据、不推算 beta 号。
  • 不做 Beta 分频(B6);日报只展示当前「每 6 小时」这个节奏文字。
  • 不改 /health、不改现有的每日 standup、不复活任何看门狗、不为本单造新的保留期策略。
  • 不自动去 Linear 对账:意图没落定时,由人用最高权限的命令收口(填 issue 号或标放弃,必须写理由,收据上的操作者由服务端固定,不信任请求自报)。
  • Codex 第三轮提的 4 条「把极端故障也完整持久化」的加固(R3 #2–#5),本单只做了每条最便宜的 fail-closed 守卫,完整版留在 plan 的 follow-ups 里,由 Tadashi 裁定。
  • 不回填历史告警的版本。
最重要的三条诚实:① v1 有偏差 —— bug 只算报上来并经过 Bridge 建单接口的那些;你自己用 /create-issue 直接建的单不会自动带版本章(那条命令在仓库外,列为部署前置项)。② 「机器跑过的 commit」和「要发给客户的 beta」今天大概率不是同一个,所以在对齐子单落地前,B4 会经常拿到「说不清」,这是设计如实反映现状,不是 B3 坏了。③ 「说不清」不等于「有问题」,它只表示「我没有足够证据说没问题」。
