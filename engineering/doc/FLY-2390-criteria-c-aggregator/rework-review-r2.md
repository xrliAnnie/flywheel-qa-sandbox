## HIGH shell-cursor-drops-same-second-rows

Shell observation cursor silently and permanently drops rows written in the already-consumed second

`projectShellObservations` seeks with a strict row-value cursor `(observed_at, event_id, source_commit_key, occurrence) > (last projected row)` and advances the cursor to the last row of the batch (ingest-rider.ts:238-241, 281-294). `observed_at` is written by `scripts/lead-alert.sh` with whole-second granularity (`READINESS_UNIX=$(/bin/date +%s)`, lead-alert.sh:254). The rider projects at some instant inside second T; any shell observation that commits later within that same second T and whose `event_id` (a sha1 hex, effectively random ordering) sorts below the cursor's `event_id` is never greater than the cursor and is therefore NEVER projected on any later tick. Concrete failure: at T the rider projects rows with event_ids e1<e2<e3 and sets cursor=(T,e3,...); 200ms later, still in second T, `lead-alert.sh` commits a `severe` observation with event_id a0<e3; every subsequent tick's WHERE clause excludes it, so `release_signal_events` never gets the row. The loss is completely silent: the shell's claim transaction succeeded so `DELIVERY_DB_OK=1` and the preflight intent is moved to `gaps/landed/` (lead-alert.sh:616-620) — no gap row; `rejected_rows` stays 0; and `backlogAgeS` is computed with the SAME `where()` clause (ingest-rider.ts:297-308) so `MIN(observed_at)` also never sees it and the heartbeat reports a healthy backlog. The event is thus invisible to `evaluateReadiness`, and a window whose only severe evidence was that alert evaluates to `green` instead of `hold`. This breaks the plan's central fail-closed invariant ("凡是本该采到却没采到的地方都持久化成缺口或源不健康并让结论变 unknown") in the unsafe direction, under normal operation rather than an exotic failure. `release-readiness-rider.test.ts:307` covers the same-second 500-row paging boundary only for identical `event_id` with ascending `occurrence`, so this case is untested. Suggested fix: hold back the currently open second (project only rows with `observed_at < floor(now)`), or give the claims-side table a monotonic surrogate (AUTOINCREMENT rowid / sub-second timestamp) and seek on that.

## MEDIUM rider-ingests-in-flight-preflight-intent-as-gap

Rider converts a healthy in-flight alert's preflight intent into a permanent capture_gap

`lead-alert.sh` writes `gaps/<...>.intent.json` immediately after argument validation (lead-alert.sh:260-268) and only retires it to `landed/` after the claim transaction commits (lead-alert.sh:616-620). Between those two points the script runs ~6+ subprocess spawns (5× `jq`, `shasum`, a `source` subshell, tool `command -v` checks), i.e. a window of tens to hundreds of milliseconds. The rider's gap-absorption loop (ingest-rider.ts:89-102) has no age/mtime threshold: any `.intent.json` present at `readdirSync` time is inserted as a `release_signal_gaps` row and moved to `landed/`, so a perfectly successful alert that merely happened to be mid-flight during a tick is recorded as `reason='shell_preflight'` forever. `evaluateReadiness` (evaluate.ts:230-246) turns any such gap row into `capture_gap`, pinning the verdict to `unknown` for the remainder of the window (up to 14 days). Per alert the odds are roughly (intent→land duration)/(60 s tick) ≈ 0.2-0.5%, but with hundreds of shell alerts per 14-day window a false permanent `unknown` becomes likely, and it is indistinguishable from a real capture failure. Also note `land()` (ingest-rider.ts:152-158) will move the file out from under the still-running script, after which `[ -f "$READINESS_INTENT" ]` fails silently and the shell never logs the loss. Suggested fix: only absorb intent files older than some grace period (e.g. 2× the expected script runtime), or have the shell write the intent under a `pending/` subdirectory it renames into `gaps/` only on failure paths.

## MEDIUM report-render-exceeds-512kib-on-wide-window

Minute-granularity timeline plus uncapped evidence tables can blow the 512 KiB render guard and kill the daily report permanently

`renderReadinessReport` emits one `<i>` element per minute for the whole window (report.ts:47-58) and renders every row of `input.events`, `input.gaps`, `input.bugs`, `input.publications`, `input.founderVerdicts` with no cap (report.ts:64). A full 14-day window is 20160 minutes; an all-missing timeline is 20160 × 23 B (`<i class="missing"></i>`) ≈ 464 KB plus ~18 KB of hour headers ≈ 482 KB before a single table row. A healthy timeline is ≈ 159 KB, which leaves only ~360 KB for evidence tables — and `input.events` holds every `release_signal_events` row in the window (one per Bridge alert arrival, ~200 B rendered), so ~2000 events is enough to cross the limit. When it does, report.ts:66-67 throws `RangeError`, routes.ts:79-82 answers 413, `scripts/release-readiness-report.sh` dies under `set -e` at line 47 before writing the publication intent, no `release_report_publications` row is ever created for that day, and `evaluateReadiness` adds `founder_signal_unobserved` (evaluate.ts:291-305). Because the script's idempotency guard is per-day, the report is never retried, so the size overflow converts into a permanent `unknown` with no operator-visible cause beyond an exit code. Suggested fix: bucket the timeline (e.g. per 5 or 15 minutes) for wide windows and cap/truncate the evidence tables with an explicit "N more rows omitted" line instead of failing the whole render.

## MEDIUM bug-label-health-is-global-but-resolution-is-team-scoped

Every create-issue makes an extra team-scoped Bug-label lookup and writes a single global health row

plugin.ts:4026-4039 now resolves `bugLabel` unconditionally on EVERY `POST /api/linear/create-issue`, and records the result into `release_bug_source_health`, whose primary key is the literal constant `'bug_label'` (StateStore migration: `key TEXT PRIMARY KEY CHECK(key='bug_label')`). The lookup is team-scoped (`team: { id: { eq: targetTeam.id } }`, plugin.ts:3956-3959) but the health row is global. Concrete failure: a create-issue against a team that has no label named `Bug` (or two matching labels) writes `last_failure_at = now` with no offsetting success; `evaluateReadiness` (evaluate.ts:279-289) then raises `bug_source_unhealthy` and pins the verdict to `unknown` until some later create-issue against a team that DOES have the label writes a newer `last_success_at`. A fleet that routinely creates issues in both FLY and GEO will oscillate the readiness verdict on a signal that has nothing to do with release health. Two secondary costs on the same hot path: (a) the extra `client.issueLabels` round-trip is made on every create-issue, including non-bug ones, doubling label-lookup consumption of the Linear API rate limit and adding a network hop to a widely-used production endpoint; (b) when a caller already passes `Bug` in `labels`, the identical query is issued twice (once at plugin.ts:4001 inside the label loop, once at 4028), and both write a health row. Suggested fix: key `release_bug_source_health` by team (or only record health for the team that owns the readiness subject), and reuse the label id already resolved in the `labels` loop instead of re-querying.

## MEDIUM verdict-endpoint-appends-unbounded-protected-rows

GET /verdict writes a row per request into a never-pruned table

`GET /api/release-readiness/verdict` calls `service.evaluate()` (routes.ts:128), which unconditionally appends a `release_readiness_verdicts` row (service.ts:50-56). `release_readiness_verdicts` is registered as `protected` in `scripts/lib/fly-2006-retention-registry.mjs`, so no retention policy ever deletes it, and each row carries a full `evidence_json` (window, counts, up to 10 unhealthy heartbeat ticks with all their fields, the whole policy object) — on the order of 1-5 KB. Any holder of `config.apiToken` or the scoped gemini token — including the B4 consumer this endpoint exists for, which is expected to poll — grows the Bridge StateStore without bound: a 10 s poll adds ~8600 rows/day. `POST /report/render` has the same effect (routes.ts:62-66). Same-token abuse is not a trust boundary crossing, but an accidental tight poll loop from a legitimate consumer is enough to bloat the DB indefinitely. Suggested fix: make the read-only path reuse a recent verdict (or add an explicit `?persist=true`), and/or give `release_readiness_verdicts` a retention policy or a per-subject row cap.

## MEDIUM alert-version-observations-grows-unbounded

New claims.db companion table has no retention and grows per alert arrival, not per unique event

`alert_version_observations` is created inside `~/.flywheel/alerts/claims.db` (lead-alert.sh:574-587) and inserted with a fresh `occurrence` on EVERY invocation (`COALESCE(MAX(occurrence),0)+1`, lead-alert.sh:589-592) — deliberately not `INSERT OR IGNORE`. Nothing in the repo ever deletes from it: `grep` for DELETE/retention against `alert_claims`/`alert_version_observations` finds no consumer (the PR's own research.md:22 records that `alert_claims` is append-only), and the FLY-2006 retention policies added in this PR only cover the three mirrored StateStore tables, not the claims-side companion. Unlike `alert_claims`, which is `INSERT OR IGNORE` and therefore bounded by the number of distinct `event_id`s, the companion table gains a row for every repeat arrival. Concrete failure: a flapping producer that re-invokes `lead-alert.sh` with the same signature once a minute adds 1440 rows/day forever, so a long-lived machine accumulates hundreds of thousands of rows plus the cursor index in a sqlite file on the alert hot path, with no operator-visible cap and no janitor. Suggested fix: prune `alert_version_observations` to the same 14-day horizon the mirrored tables use (the rider already knows the projected cursor and could delete behind it), or add it to the existing claims.db maintenance path.

## MEDIUM retention-registry-now-requires-built-teamlead-dist

Retention registry re-exports RETENTION_MS from packages/teamlead/dist, inverting the intended dependency direction

`RETENTION_MS` changed from a self-contained literal to `export { READINESS_WINDOW_MS as RETENTION_MS } from "../../packages/teamlead/dist/bridge/release-readiness/evaluate.js"`. That makes `scripts/lib/fly-2006-retention-registry.mjs` — and transitively `fly-2006-retention-engine.mjs`, `fly-1998-database-retention-sweep.mjs`, `fly-2006-retention-rehearsal.mjs`, `fly-2006-retention-consumer-gate.mjs`, `fly-2139-standing-policy.mjs`, and `scripts/flywheel-log-janitor.sh`'s DB sweep — hard-fail with ERR_MODULE_NOT_FOUND whenever `packages/teamlead/dist` is absent. Concrete failure: an operator (or a recovery runbook) running `node scripts/fly-2006-retention-rehearsal.mjs` in a fresh clone, or the launchd log-janitor firing during a window where `update-flywheel.sh` has pulled but not yet rebuilt, now crashes instead of doing retention work; previously these scripts needed nothing but node. Note the plan (§2.3) specified the opposite direction — "evaluator 从同一常量导入" the retention constant — which would have kept the scripts tier self-contained. CI is unaffected because `pnpm build` runs before every consumer here. Suggested fix: keep the literal in the registry (the scripts tier) and have `evaluate.ts` import it, or duplicate the constant with a drift test in both directions.

## LOW soak-blind-to-sub-freshmin-heartbeat-degradation

Interior heartbeat intervals at or below freshMin count as fully covered soak with zero gap

The coverage loop only charges an interior interval to `gapMs`/`interiorGapMs` when it exceeds `policy.heartbeatFreshMin * 60_000` (evaluate.ts:181-186). The rider is expected to append a heartbeat every 60 s, but with the default `heartbeatFreshMin = 10` a stream where 8 of every 9 ticks failed to append (one row every 9 minutes) yields `coveredHours = 12`, `gapMin ≈ 0` and no `source_unhealthy`, so a badly degraded observer reads as perfect 12-hour soak coverage and `green` remains reachable. Nothing else in the pipeline notices a missing tick, since heartbeat health is evaluated per existing row only. Suggested fix: additionally assert a minimum heartbeat density over the window (e.g. observed ticks ≥ some fraction of expected ticks at the rider cadence), or charge interior intervals above a tick-cadence multiple rather than above the freshness allowance.

## LOW founder-channel-unset-reason-undocumented-and-boot-frozen

founder_channel_unset is an undocumented reason code and the channel setting is frozen at Bridge boot

`evaluateReadiness` emits `founder_channel_unset` (evaluate.ts:290), which is not in the plan's stable reason-code table (§2.2) — any consumer written against that contract will see an unknown code. Separately, `policy.founderChannelConfigured` is derived from `FLYWHEEL_READINESS_REPORT_CHANNEL` by `readReadinessPolicy()` called once while assembling the router (plugin.ts:4886), so an operator who sets the channel per the deploy runbook (§8 step 3) keeps getting `unknown` until the Bridge is restarted, with no signal saying so. Suggested fix: add the code to the documented reason table and either re-read the env per evaluation or surface the frozen-at-boot behaviour in the report.
