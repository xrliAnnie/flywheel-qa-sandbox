## HIGH retention-registry-import-escapes-package

`import { RETENTION_MS } from "../../../../../scripts/lib/fly-2006-retention-registry.mjs"` is emitted verbatim into `packages/teamlead/dist/bridge/release-readiness/evaluate.js` (verified: the built file on this branch still carries the specifier). In the monorepo the five `../` land on the repo root and resolve. In a packaged install the file is at `<tree>/node_modules/flywheel-teamlead/dist/bridge/release-readiness/evaluate.js`, so the same specifier resolves to `<tree>/scripts/lib/fly-2006-retention-registry.mjs` — and `package-onboard.sh` PO_SCRIPT_FILES/PO_SCRIPT_DIRS ship neither `lib/fly-2006-retention-registry.mjs` nor any `lib/fly-2006-*`. I reproduced the exact layout in a temp tree and node returned `ERR_MODULE_NOT_FOUND: Cannot find module '<tree>/scripts/lib/fly-2006-retention-registry.mjs' imported from <tree>/node_modules/flywheel-teamlead/dist/bridge/release-readiness/evaluate.js`. Because `plugin.ts` statically imports `release-readiness/{routes,service,ingest-rider,policy,subject,bug-footer}` and all of those reach `evaluate.js`, the whole Bridge module graph fails at load — not a degraded feature, a dead Bridge. Note the repo's own precedent is the opposite direction (`bridge/run-dispatcher.ts` header: "Moved from scripts/lib/retry-dispatcher.ts into the package so that…"); this is the first non-test production import from `scripts/` under `packages/*/src`. Fix: define the 14-day constant inside the package (or in a workspace package both sides import) and have the janitor read it from there, rather than reaching across the package boundary.

## HIGH outbox-ingest-tick-self-poisons-heartbeat

`run()` snapshots `scan = scanReadinessOutbox(outboxRoot)` at line 74, ingests+lands every entry at lines 89-116, then at lines 127-128 writes the heartbeat using the pre-ingest counts. So the very tick that consumes a file records `outboxPending: 1`. `isReadinessHeartbeatHealthy` (evaluate.ts:121) requires `outboxPending === 0`, and `evaluateReadiness` (evaluate.ts:215-222) emits `source_unhealthy` if ANY heartbeat in the window is unhealthy — with the window starting at `anchor.episodeFrom` (evaluate.ts:131-134). There is no way for a file to be landed without at least one tick first counting it as pending, so this is deterministic, not racy. I confirmed it by driving the real `ReleaseReadinessRider` with one `publications/<day>.json`: the single heartbeat row came back `outboxPending: 1` while `landed/<day>.json` already existed after that same tick. `release-readiness-report.sh` writes exactly such a file every day at 08:00 and never removes it (only the rider lands it), so from the first daily report onward every deployment episode is permanently `unknown` until the 14-day truncation rolls `episodeFrom` past it. That makes the feature's positive outcome unreachable in the exact steady state it was built for. (§12 F4 defers 'strict ordering of outbox results into this tick's health'; the deferral's consequence — green never fires — looks unintended.) Fix: compute the heartbeat's outbox counts after ingestion/landing (re-scan, or subtract what this tick successfully landed), or exclude files this tick consumed.

## MEDIUM claims-observation-table-missing-until-first-shell-alert

Only `lead-alert.sh` creates `alert_version_observations` (`CREATE TABLE IF NOT EXISTS` inside CLAIM_SQL). The rider reads it with `.bail on` + `PRAGMA query_only=ON`, so on a Bridge that boots before any shell alert has fired the SELECT fails. I verified against a fresh sqlite file: `Parse error near line 4: no such table: alert_version_observations`, exit 1 → `sqliteRunWithStdin` rejects → `catch { health.claimsDbOk = false }` (line 307-309). Combined with the ANY-unhealthy-tick rule in evaluate.ts:215-222, those bootstrap ticks keep the first deployment episode at `unknown` even after the table appears, because they stay inside `[episodeFrom, now]`. Fix: have the rider create the table (or treat 'table absent' as an empty result rather than a broken claims DB).

## MEDIUM minute-timeline-blows-512kib-cap

`for (let minute = from; minute <= to; minute++)` emits one `<i…>` per minute across the whole verdict window. A truncated 14-day window is 20 160 minutes; missing minutes cost 23 bytes each plus a 53-byte hour header every 60. I rendered the real `renderReadinessReport` with a 14-day window and completely empty evidence (no events, gaps, bugs, publications, one reason): **485 504 bytes against the 524 288 limit** — 38 KB of headroom for every evidence table. A couple hundred event rows, a populated `source_unhealthy` ticks array, or a gaps table pushes it over, `renderReadinessReport` throws RangeError, routes.ts:79-82 returns 413, `release-readiness-report.sh`'s `curl -sf` fails under `set -e`, and the report never publishes. Sparse heartbeats and lots of evidence co-occur precisely when the verdict is `unknown` and the founder most needs the explanation. Fix: bucket the timeline (e.g. 5- or 15-minute cells) or cap its resolution by window length.

## MEDIUM verdict-append-on-every-read-unbounded

`GET /api/release-readiness/verdict` calls `service.evaluate()` (service.ts:50-56), which always `appendReleaseReadinessVerdict`s; `/report/render` does the same at routes.ts:62-66. `release_readiness_verdicts` is registered `protected` in `fly-2006-retention-registry.mjs`, so nothing ever prunes it. Each row stores the full `evidence_json` (window, counts, outbox, policy, founder days) — multiple KB. The plan names this endpoint as B4's polling surface, so a minute-cadence consumer adds ~1 440 rows/day forever to a StateStore that sql.js loads wholly into memory. A read-shaped GET should not be an unbounded durable write. Fix: make GET read-only (return the latest verdict, or dedupe identical consecutive verdicts), or give the table a retention policy.

## MEDIUM rider-loads-full-evidence-to-read-publications

`run()` calls `this.store.getReleaseReadinessEvidence(sourceCommit, now-14d, now).publications` and discards everything else. That helper (StateStore.ts) runs six unbounded queries — events, gaps, heartbeats, bugs, publications, founderVerdicts. Heartbeats alone are one row per minute, so a mature 14-day window means ~20 000 rows built into JS objects and `.map`ped every tick, plus every signal event and gap, to obtain at most a handful of publication rows. Fix: add a narrow `listReleasePublications(commit, from, to)` and call that from the rider.

## MEDIUM no-publication-does-not-block-green

`unobserved` is derived by filtering `publications`; when the window contains no publication rows the filter is empty and no `founder_signal_unobserved` reason is added, and `founderVerdicts` is likewise empty so `founder_thumbs_down` can never fire. `release-readiness-report.sh:27-28` exits 0 when `FLYWHEEL_READINESS_REPORT_CHANNEL` is unset, and `units.manifest` ships the unit with the channel supplied by an operator — so the default, unconfigured state is 'no publications ever', which silently removes the founder 👍/👎 gate instead of failing closed like every other missing-evidence branch in §2.1. This matches the plan text, but the plan's own framing (fail-closed on unobserved founder signal) argues the empty case should also be unknown. Fix: require at least one published+scanned publication covering the soak window before green.

## MEDIUM shell-observation-rejected-when-doc-version-unreadable

`parseReadinessSubject(row.base_version, row.source_commit_key)` returns null whenever `base_version` is NULL, and line 265 then does `if (!valid || (!identity && row.source_commit_key !== "null")) health.rejectedRows++`. `lead-alert.sh` leaves `READINESS_BASE` empty (⇒ `base_version` NULL) whenever `$READINESS_REPO/doc/VERSION` is unreadable, while `READINESS_SHA` still comes from `~/.flywheel/deployed-sha` and is a real 40-hex value. `READINESS_REPO` defaults to `$(dirname "$0")/..`, which is not the repo root when the script is invoked through a bin/symlink path, and packaged trees carry no `doc/` at all (`package-onboard.sh` gate: 'zero .ts / src/ / __tests__/ / doc/ / .git') even though `lead-alert.sh` is in PO_SCRIPT_FILES. Every shell alert then bumps `rejected_rows`, making every heartbeat unhealthy (evaluate.ts:119) and latching the episode at `unknown`. Also, the event is still projected with `sourceCommit: null`, so a severe shell alert additionally trips `unattributed_severe`. Fix: treat 'commit known, base unknown' as attributable (or at minimum don't count it as a rejected row), and/or fail loudly at capture time when the version file is unreadable.

## LOW cursor-page-parse-is-all-or-nothing

`z.array(cursorRow).parse(JSON.parse(output || "[]"))` validates the entire page before the per-row leniency at lines 250-277 ever runs. Any single row that violates `cursorRow` (non-numeric `observed_at`, non-positive `occurrence`, non-string `event_id`) throws out to the outer catch at line 307, sets `claimsDbOk=false`, and — because the cursor is never advanced past it — the same page is re-read and re-fails on every subsequent tick. The plan's contract is the opposite ('坏行:有 event_id ⇒ NULL 归因投影,否则 rejected_rows+1'). Today the shell schema makes such rows impossible, so this is latent, but the per-row degradation path is dead code for exactly the failure it was written for. Fix: `safeParse` each row and count failures into `rejectedRows` while still advancing the cursor.

## LOW post-create-failure-reports-502-after-linear-success

`throw new Error("created bug identifier missing")` and any throw from `store.resolveReleaseBugIntent` land in the handler's outer catch, which responds `502 {error: "Linear API error"}` — after the issue has already been created in Linear. Before this change the handler returned `ok: true` with `identifier: undefined` in that path. Callers (and the `flywheel-comm` / plugin consumers) reasonably retry a 502, producing a duplicate Linear issue. `release_bug_reports.issue_identifier` is UNIQUE, so a finalize colliding with a row already written by `POST /bug-report` for the same identifier is a concrete way to reach this throw. Fix: catch bookkeeping errors separately and still return the created issue (leaving the intent pending, which already routes to `bug_intent_unresolved`).

## LOW bug-report-row-has-no-resolution-receipt

`recordReleaseBugReport` inserts directly with `status='finalized'` and never writes a `release_bug_resolution_receipts` row. `resolveReleaseBugIntent` short-circuits on non-pending rows and then requires the receipt join to succeed, throwing `release bug resolution receipt missing` (line 4656) when it does not — surfacing as an unhandled 500 from `POST /bug-intent/:intentId/resolve` rather than the intended 200-canonical or 404. Fix: write a receipt (`action='finalize'`, `resolved_by='bug-report'`) in `recordReleaseBugReport`, or make the canonical read tolerate a missing receipt.
