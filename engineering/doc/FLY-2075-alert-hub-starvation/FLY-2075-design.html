术语先解释一次:ticket 类告警 = 系统健康类、需要有人动手处理的告警(比如 Bridge 异常退出、僵尸 session 积压、runner 登录过期);claw = claude-infra-bot-lead,Claude 侧的基础设施机器人;alert_threads = 告警工单账本,一条告警一行,记录它开了哪个 Discord thread、谁认领、什么状态;Hub = AlertChannelHub,Bridge 里把一条告警变成「频道根消息 + thread + 账本一行」的那段代码。

2管道长什么样:现在 vs 单车道

所有 ticket 类告警先经过 D1 Router(路由器:按告警种类决定送到哪里的那段代码,FLY-927 建、FLY-1764 改)。现在它把告警必投claw 信箱,频道那条边被关着的开关挡住。裁定后:信箱这条边拆掉,频道那条边成为唯一一条路,开关也不留;Hub 开完 thread 就停手(工单状态 NEW),不再自己 @ 你。

3账本模型:五本账各记什么(为什么容易看错)

PRD §1.3 数「0/497 从未 ACK」用的是 alert_threads;而 claw 实际上在另一本账(信箱)里每天签收几十到几百条。两本账记的是不同的事:信箱的 ACK = 「收到了」,工单账的 ACK = 「我认领来处理」。值守机制要的是后者,所以 Epic 必须落在 alert_threads —— 裁定后它重新每天有新行,而信箱那本账的 ticket 部分停止增长。

#后果说明
C1claw 的信箱工单账停止增长今天 claw 半分钟签收那本账(08-15 起 1,441 行)不再有 Router 来的新行;claw 改为在频道被 🎫 @。claw 的运行时会不会因为频道 @ 醒来、去看整条队列,是 FLY-2076 的事。
C2没有自动读者的窗口在 2076 上线前:频道里的工单既没有信箱唤醒、也没有 @ 你,只有根消息里对 claw 的 @。Tadashi 的默认建议:本单的切换不早于 2076 值守上线那一班部署——除非你明确接受这个窗口。另核过:仓库、脚本、agent/skill、插件缓存里没有任何机器读取 claw 信箱里这类行的代码,唯一读者是 claw 自己(一个 LLM),它改读频道是 2076 的事。
C3你不再被 Hub 自动 @改道前 8-05~8-14 每天 19~34 次(几乎全是「需要人」)的 thread 内 @ 你不会回来;以后只有值守/人判断过才 @ 你。
C4ESCALATED 不再自动出现PRD §1.3 的「425 条 ESCALATED」模式终止;超时、重试耗尽的工单停在 NEW / REPAIRING / MONITORING,挂着可见(R6),没人推它——直到值守接手。
C5「同类升级 3 次自动建单」停止它靠 ESCALATED 触发,随之成为死代码,一并删除。
C6频道日量≈ 改道前水平 + 新类别(cmux_watcher_stalled 8-24/25 各 101/171 条):每天几十到三百条根消息;20/分钟限速,溢出排队回放。
C7issue 绑定的工单不再在 issue thread 里 page 你那是 T2 升级的一种形态,随 T2 一起删。
C8配置出错时的失败形状只在「统一告警频道 / 机器人 token」缺失时出现:频道是唯一车道,fleet 类工单会逐条进死信并弹本机提醒(这是 1764 之前就有的 fail-loud 合同,不会静默丢);启动日志会打红灯行。生产配置是完整的。

被否的两条路A「打开频道副本开关」(我 v1/v2 的推荐):双发 + 留旋钮,两条都撞你的红线(不双发;flag = 最严档写死 + 删旋钮),且开关一开每条新告警会当场 @ 你——Codex 评审抓出我第一版把这条写轻了。C「管道不动,Epic 换账本落在信箱」:信箱的 ACK 只是「收到」,R2 三种去向、R6 终态、thread 归档都没处写 → 要新造一层,踩「不新增告警层」。

时序约束频道车道只能与「删自动 @ 你」同一个 PR、同一次部署上线,永不单独——否则就是把 8-14 之前每天几十次 @ 你的局面原样搬回来。本方案单 PR 满足。

6怎么算修好:一条真实告警走完全链,并且没人被自动 @

不注入假告警(生产 Bridge 没有注入口,也不该为验收加一个)。触发点 = 部署后工单账本里的第一条新行(只有 ticket 类才会开工单;基线每天 83~307 条,但不拿「一小时内必有」当断言——6 小时没新行就记「暂无结论」继续等,不算失败)。取证三件套:同一事件 id 在工单账本有新行且不是 ESCALATED(SQL)+ 在信箱里 0 行(证明车道真拆了)+ 频道截图(根消息带 🎫 @claw,thread 里没有 @ 你的帖)。

部署时点 = PR 合入后的下一班本地 00:00 / 12:00 班车;runner 不投重启票(FLY-1959)。回滚:没有旋钮(这是设计),revert PR 等下一班 → 逐字回到 FLY-1764 的 Flow 2(信箱车道和自动 @ 你一起回来)——不存在「只回滚一半」;回滚会把每天几十次自动 @ 你带回来,要和上线同等级的授权,runner 不能自己 revert。

7诚实边界:这个设计做什么、不做什么

做ticket 类告警回到频道、开 thread、写账本;拆信箱车道与旋钮;删 Hub 全部自动 @ 你 / 自动 ESCALATED 的路径;把路由状态打进启动日志。

  • 不做值守初审、认领、claw 醒来读频道——那是 FLY-2076。本单只保证告警在频道里、工单在账本上、没人被误 @。
  • 不做人或值守 bot 显式把工单标 ESCALATED / @ 你的规则——值守流程的一部分(2076 / Epic)。
  • 不做信箱投递失败(mailbox_dead_letter)那类告警:它走另一条直连路,只发根消息不开 thread(1764 定的「现状即可」);记为 Epic 的已知缺口(PRD §1.4 里它占 22%)。
  • 不做shell 那边取不到 token 的死信(cmux_cleanup 等)= FLY-2062。
  • 不做噪音判定、频道日量控制、限速调参。
  • 不动claw 信箱给 flag 扫描告警、workflow 兜底这三种定向消息的用途——它们不是 ticket 车道。
