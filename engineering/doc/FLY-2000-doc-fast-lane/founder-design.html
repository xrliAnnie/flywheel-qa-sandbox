FLY-2000 文档快车道 — 设计方案

设计已过 4 轮外部评审 实施前有一道实弹硬门 净省上限 ≤ $116/月(不是承诺)

1. 一句话

一条 PR 的代码已经完整测过一次全绿之后,再推的纯文档提交(进度账本、报告、归档)不再重跑整套测试,只跑几分钟的快速检查 —— 每次省约 30–60 计费分钟。

这是你 8/22 在省钱方案页圈的「方案二·文档快车道」。钱的口径:≤ $116/月,这是上限不是承诺 —— 真实能省多少,上线一周后拿真数据对账(方案里已排好这一步)。

2. 现在亏在哪,改完后什么样

场景现在改完后
整条 PR 只有文档已走快车道(现有机制,不动)不变
代码 PR 全绿后,再推文档(进度账本、QA 报告、归档)每笔都重跑全量(30–60 分钟)走快车道(约 3 分钟)
任何含代码的提交、任何拿不准的情况跑全量跑全量(一步都不松)

「快车道」也不是零检查:构建、代码规范、全部治理守卫照跑;跳过的只有重型测试矩阵。

3. 核心流程

「真·全绿」= 那一次运行里 11 个检查任务全部真实跑完且全部成功,一个都没被跳过 —— 快车道自己的绿不算数,防止两笔文档提交互相作保。

4. 凭什么信「曾经全绿」—— 标记与核验模型

难点:CI 平台的历史记录里,「当时是在哪个版本上测的」这个信息事后拿不回来(平台字段会被悄悄改成当前值 —— 上一单 FLY-1987 实测证明过)。所以唯一可靠的做法是:全绿那一刻,自己写下一个存证。

关键原则:标记只是一张「指路条」。它说自己全绿不算数 —— 读取时逐项向 GitHub 官方接口重新核实;11 项核验任何一项对不上,一律退回全量。

5. 关键取舍,和被否掉的路

决定为什么
存证放在 CI 运行的附件里(artifact,平台自带的文件存档)平台自己维护「这文件属于哪次运行」,伪造不了归属;不用给 CI 开任何新权限。否掉的:写数据库/外部存储(新增基础设施)、写评论或状态(要扩权限)。
main 前进了就不走快车道你的代码 + 别人刚合的新代码 = 一个没测过的组合,宁可重测。这会压低命中率 —— 如实接受,一周对账见真章。
不加任何开关沿用你定的「不加新 flag」铁律;要回滚就整个 revert,残留的存证没人读、到期自动清。
先修 FLY-1996 再上线本单已发现 CI 有一条守卫读取文档目录里的文件(那个已立单的安全洞)——快车道扩面会放大它,所以那单不落地,本单不合入。

6. 诚实边界

  • 红线与防线:「动了代码却没测」绝不允许。防线不是一层:标记自述不算数、逐项向官方接口重验、增量逐文件核、任何拿不准一律全跑;合入前必须现场演示一次「掺了代码 → 全量照跑」的反面对照,演示不出来就不许合。
  • 救不了的:PR 第一次推送、全绿之前的提交、全绿之后 main 已经前进的文档提交 —— 这些照旧全跑,是安全边界不是缺陷。
  • $116/月是上限:建模时有两个收窄条件没法预先验证,真实值必然更低,多低只有对账知道。
  • 这机制被删过一次:第一版(FLY-1861)靠「查最新一次运行」当基线,易碎、还信了会漂移的平台字段,你 8/18 下令简化后被整套删掉。这次的三处不同:存证是持久的(不怕运行被打断顶掉)、只记写入那一刻的本地事实(不信活指针)、读取时全部重验。纯文档 PR 的现有简单规则一个字不动。
  • 还有一道实弹硬门(N0):纸面可行已证,但「存证在咱们仓库真的写得进、读得回」只能实弹验。实施第一步就是这个试验,试不过 = 整案放弃、原样撤回 —— 这是方案里明写的合法出口,不是失败。

7. 下一步

  1. N0 实弹试验:只上「写存证」这一半,真实全绿写一次、跨运行读一次、量一次成本 —— 过不了就放弃整案。
  2. N1 实现读取侧(须等 FLY-1996 那个安全洞先修掉)。
  3. N2 合入门:现场演示正、反两个对照(纯文档走快车道 / 掺代码必全跑)。
  4. 上线 7 天后对账:命中率、实际省下的分钟数,按 FLY-1987 同一把尺子记进台账。
