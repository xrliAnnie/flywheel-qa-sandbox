FLY-2508 · 让内部测试版和本机跑的版本对上号

Issue FLY-2508 · 1143 Epic 的 B3a · 设计节点 · 2026-09-13 · __REVIEW_META__ · 文档:engineering/doc/FLY-2508-updater-beta-alignment/

一句话

以后 flywheel 的内部测试版(beta,先给自己人用的试用版)不再从 GitHub 主分支的最新代码铸,而是从你这台机器此刻真正在跑的那个版本铸 —— 这样 B3(那张「这版稳不稳」的健康表)问到的版本,就恰好是它有证据的那一个。

名词解释:更新器 updater = 每天 00:00 / 12:00 自动把这台机器的 Flywheel 更新到主分支最新代码的小程序;deployed-sha = 更新器写在本机的一行记录,内容是「现在跑的是哪个版本」(版本用一串代码指纹标识);B3 = FLY-2390 造的判据,它只对本机真跑过的版本说 green / hold;B4 = 将来「你不喊停就自动对外发布」的那扇门,它要先问 B3。

现场事实:为什么今天永远对不上

  • 两条线各自采样:更新器每天两次把本机推进到主分支最新;内部测试版每 6 小时从主分支最新另切一次。今天(09-13)本机跑的是 4bad8ae,主分支已经到 26ebc49,中间隔了 3 次合并。
  • B3 只认本机跑过的:它的部署证据来自 deployed-sha;拿一个本机没跑过的版本去问,答案固定是「说不清(没有部署证据)」。所以 B4 基本永远拿不到 green —— 这不是 B3 坏了,是两条线没对齐。
  • Bridge 的内部测试版调度器(FLY-2393)还没接管:生产里它的两张账本是空的,GitHub 上也没有那个「谁来调度」的控制开关,现在铸版的仍是 GitHub 上那条旧的 6 小时定时任务;GitHub 读不到你机器上的文件。
顺带发现的故障(已报给 Tadashi;他裁定这是已有主的 FLY-2534,本单不修):FLY-2393 合入主分支之后,那条旧的 6 小时定时任务的配置文件被 GitHub 判为无法解析 —— 09-12 晚上起主分支每次提交都留下一条「0 个步骤、失败」的运行记录,09-13 一整天没有铸出任何内部测试版。根因是配置里一处引用了 GitHub 不允许在那个位置用的变量,FLY-2534 正在修并给所有工作流加一道语法守卫。在它修好之前,没有真实的内部测试版可以拿来验收本单。

核心流程:一份文件,四个读者

deployed-sha 这份文件今天已经有三个读者:更新器(判断要不要更新)、重启脚本(记部署账)、B3(判断有没有证据)。本单只是让第四个读者 —— Bridge 的内部测试版调度器 —— 在 flywheel 这条泳道上也读它:到期时不再去 GitHub 问「主分支最新是谁」,而是读这份文件,把本机正在跑的版本交给 GitHub 的发布流程去铸内部测试版。

图 1 · 对齐之后的完整流向(流程图)
  • 按项目配置,不写死项目名:在项目自己的配置文件里加一行 source_commit: local_deployed_sha(「源版本取本机已部署的」);不写就是老行为(取主分支最新)。GeoForge3D 这类不在本机跑的项目保持老行为。
  • 拿不准就停:文件读不到或内容不像版本指纹 ⇒ 这条泳道标「需要检查」、不发版、不悄悄退回主分支最新;版本不在主分支上(比如误配到别的项目)⇒ 同样停下。这两个守卫都发生在「冻结这一轮」之前,所以修好之后下一次检查自动恢复,不会补发一串历史版本。
  • 接收端不用改:GitHub 那边的发布流程本来就会检查「这个版本在主分支上吗」,并且遇到「已经有更新的内部测试版了」会记为 covered_by_newer(不把指针退回旧代码)、遇到「这个版本已经铸过」会记为 no_change。回滚、紧急部署这些情形都被它现有的逻辑兜住。

数据与结构模型:只加两个字段

图 2 · 配置、本机记录、每一轮铸版、回执、B3 结论之间的关系(实体关系图)
  • 配置里加一个键 beta_release.source_commit,只允许两个值:default_branch_head(主分支最新,默认)/ local_deployed_sha(本机已部署)。放在 FLY-2393 已经定好的唯一位置,不进环境变量、不进名册。
  • 每一轮铸版记一个来源 source_origin,冻结后不变,历史行为空。这样事后能一眼看出「这个内部测试版是从本机版本铸的」,是验收证据链的第一环。
  • 不动的:deployed-sha 文件、部署账本、B3 的判定与结论格式、更新器、GitHub 发布流程。
  • 回滚干净:新字段是惰性的,还原代码即可。唯一注意:老代码不认识新配置键,会把整段配置判为无效并停发(这是安全方向),所以回退代码时要同时删掉那一行配置 —— 已写进运维手册。

关键取舍与否决的方案

图 3 · 三个候选与取舍(流程图);Tadashi 已裁定采纳候选 1
问题选了否决了什么、为什么
谁向谁对齐选内部测试版向本机对齐(从本机版本铸)否B3 按「祖先关系」把没跑过的版本视同跑过 —— 那些代码的字节从没在本机跑过,判 green 就是拿没验证过的东西冒充验证过;还要长期维护一张「哪些改动算运行时改动」的名单,分类错一次就出事。否更新器改去部署内部测试版 —— 你紧急部署一个更新的版本之后,下一次更新器回不到旧的内部测试版,会每 12 小时告警一次;本机能不能更新还会绑死在外部发布服务上。
旧的 6 小时定时任务要不要也对齐选不对齐,等 FLY-2393 接管否让本机把版本号推到 GitHub 的变量里给旧任务读 —— 为一个注定要退出的过渡态多造一条带凭据的出站写通道。
读不到本机版本时怎么办选停下、标「需要检查」否退回主分支最新 —— 那就又对不上了,而且是悄悄的。
怎么防误配选发版前用 GitHub 已有的「比较两个版本」接口确认它在主分支上否在代码里写死「只有 flywheel 能用这个选项」—— 项目名硬编码是另一套要维护的镜像词表。

Tadashi 已裁的两个问题(设计期间非阻塞提问,已折入)

  1. 方案取舍与生效前置? → 采纳候选 1,否决 2 和 3;对齐只在 Bridge 接管之后生效,过渡期不另造写通道。
  2. 对齐之后还有第二道坎:B3 要求一个版本连续跑满 12 小时而且此刻仍在跑才可能 green;可更新器每 12 小时只要主分支有新东西就换版本 —— 所以一个版本的「在跑时段」也就 12 小时左右,green 的窗口几乎为零,只有主分支半天没动才可能 green。→ Tadashi 裁定本单不动「跑满多久」这个参数、也不动更新器节奏;验收改为「B3 的答案离开『没有部署证据』,落到『还没跑够』/ green / hold 之一」。把「跑满多久」降到 12 小时以下是一个产品参数,由 Tadashi 另行向你呈报。

怎么验收

issue 要求本单怎么证明
用一张真实的内部测试版跑一次 B3,答案不再是「没有部署证据」接管后第一轮铸版:账本里这一轮的来源 = 本机已部署;GitHub 回执里发布的版本 = 本机版本;拿它去问 B3,答案落在「还没跑够 / green / hold」之一,原因列表里没有「没有部署证据」「不是当前在跑的」
能看到归因依据证据链三环:账本来源字段 → 回执的发布版本 → B3 结论里「被评估的版本」与「本机当前版本」两个指纹相等
默认行为不变没配这个键的项目,现有全部测试原样通过,GitHub「主分支最新」接口照常被调用,新守卫不被触发
拿不准就停文件缺失 / 内容非法 / 版本不在主分支 / GitHub 接口出错四种情况:不冻结、不发版、标「需要检查」、15 分钟后再试;修好后自动恢复且不补发历史轮次

验收有三个前置:FLY-2390(B3)的代码合入;FLY-2534 把旧定时任务的解析故障修好;按 FLY-2393 的运维手册完成接管。没有真实内部测试版时,不用模拟的来冒充验收。

诚实边界:这单做什么、不做什么

做

  • 配置里一个新键、调度器里一个取源分支和两个守卫、每轮铸版一个来源字段、管理台一行「内部测试版取自:本机已部署版本」、运维手册一小节。

不做

  • 不改 B3 的判定、不改「跑满多久」的默认值;不改更新器的节奏或部署目标。
  • 不改 GitHub 发布流程、不修那条旧定时任务的解析故障(那是 FLY-2534 的事)。
  • 不执行接管、不改生产配置、不铸任何版本、不部署。
  • 不做 B4;不做「祖先关系视同跑过」。
三条要说清的:① 对齐只在 Bridge 接管之后生效,接管前 B4 仍然拿「说不清」。② 对齐之后 B3 的常见答案会从「没有部署证据」变成「还没跑够 12 小时」,要真正拿到 green 还得解决第二道坎(参数或节奏),那是另一个决定。③ FLY-2534 把旧定时任务修好之前,没有任何新的内部测试版,验收做不了。
