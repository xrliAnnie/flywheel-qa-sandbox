01 · 先看结论

这次修好了吗？

8 月 24 日凌晨，一个工作节点的执行体死了，引擎按设计给它换新体。新体在 4 秒内连死两具，然后引擎停手，节点表面还挂着「运行中」，实际没有任何人在干活，静默了 31 分钟没人知道。这次改动做了两件事：一是不再把「助手已经报告成功、只是进程被外力杀掉」误读成失败；二是把真正的死因（Codex 账号的凭据被撤销）一路带出来，写进记录、发进告警，并在连续两具体死于同一个环境原因时直接停手挂起、点名找人，而不是继续盲目换体空转。

原来会怎样

新体 4 秒内夭折，连续两具同一签名；之后引擎不再重试，节点挂 running + 死 exec，静默 31 分钟；记录里的死因永远是同一句「blocked」。

现在会怎样

同样的输入下 ensure 通过、新体活下来；真死因写进记录；连续两具同因时 run 主动挂起并把真因和下一步送到告警频道；退避窗内 Lead 会收到「最早 ~T 再看一眼」的说明。

QA 判断： PASS

02 · 怎么修

病根和修法

换体前要先确认工作用的终端会话还在。负责确认的小助手其实已经确认成功并把结果打了出来，但它自己随后被外部一个信号杀掉了。上层只看「这个助手是正常退出的吗」，看到不是，就把已经到手的成功结论整个丢掉、判成失败。于是每一具新生体都在同一个地方被判死。更糟的是，真正让工作体活不下去的原因——Codex 账号的登录凭据被撤销——从头到尾没有出现在任何记录里，记录上只有一句永远不变的「任务被阻塞」，所以没人知道该去修凭据。

真正的病根

生产日志 539287-539311 的链条是：旧窗 killed → 「kill returned non-ok (non-fatal)」 → 「guarded session ensure attempt 1 held (status=null): {"action":"verified","reachablePid":6234}」 → 「guarded tmux session ensure held — skipping」。ensure 助手的 stdout 已经是成功 action，但进程以 status=null（被信号杀）退出，包装层只按退出态判定 → tuiFailure(retryable-hold, hold_lock_unavailable)。同时 Codex daemon 的 turn 终态错误（codexErrorInfo=unauthorized）被客户端整个丢弃，sessions.last_error 只剩固定文案「goal ended non-complete: blocked」。

修复原则

成功的证据只有被现实复核过才算数；失败的原因必须一路带到人眼前，并且同一个治不好的原因不许反复空转。

具体改了什么

  • 退出异常但助手已报成功时，在共享 deadline 内最多补问一次真 tmux（≤5 秒）；问到会话在才放行，问不到、超预算、或中途被取消一律维持原来的 held。自己发起的取消记成 cancelled，不再冒充故障。
  • 把 Codex 的 turn 终态错误按「只认 turn/start 回应里的 turn id」归属、净化成单行有界文本，产出机器码 codex:unauthorized 与分类 environment，一路落到会话记录与告警正文。
  • 同一节点连续两具执行体死于同一个环境类原因 → 直接挂起 run 并发「需人工」告警（带真因、带恢复入口），不再烧完 3 次盲换；同时每具尸体都告诉 Lead「引擎最早什么时候会再看一眼、届时会做什么」。
