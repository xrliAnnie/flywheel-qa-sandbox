FLY-2018 重生体连环夭折与静默停摆 — 设计方案

Issue: FLY-2018 · 日期: 2026-08-23 · 设计节点交付 · Codex design review 8 轮 APPROVED

1. 一句话总结

取证推翻了 issue 的原始归因:连环秒死的真凶是 Codex 账号的登录凭据(refresh token,自动续期用的令牌)被撤销——每具替换体都从同一份已死凭据复制出生,必死;而 issue 盯上的 tmux 窗口竞速,经证据裁定并不存在。本设计做四件事:把真实死因传上来(A)、给换体治不了的死因装断路器(B)、修掉那条把所有人带偏的误导日志(C)、让退避等待不再看起来像死机(D)。

2. 事故还原 — 死循环长什么样

2026-08-24 00:13–00:44(UTC),FLY-2000 的实现节点连续死了 7 具工人身体(含一次人工恢复铸出的新体),每具都在启动后几秒到几十秒内以同一签名死亡。账本(引擎的只增事件记录)与尸体现场(每具工人自己的会话记录文件)还原出的真实链条:

尸体会话记录里的原始错误(每具都一样):"Your access token could not be refreshed because your refresh token was revoked"(unauthorized)。这个错误只存在于尸体自己的记录文件里——引擎、告警、数据库看到的一律只是一个笼统的「blocked」(被卡住)标签,所以引擎盲换了 7 次、连人工恢复也在治标签而不是治凭据。

插曲:本设计做 review 时,review 用的 Codex 会话自己也撞上了同一个「refresh token revoked」——旁证这条 auth 轴当时确实是坏的。

3. 日志为什么把所有人带偏(issue 修点①的真相)

issue 里那条关键日志「ensure held (status=null)」——看起来像 tmux(终端复用器,工人窗口的宿主)的锁被人占住了。取证还原的真实时序是:

也就是说:那条「held」是拆除过程自己造成的噪声(死亡在前、日志在后),不是死因;所谓「被谁信号杀」的凶手就是拆除流程自己发的 SIGTERM(终止信号)。但这条误导日志是真实缺陷——它把 issue 的作者、运维和引擎全部带去追一个不存在的竞速。修复 C 专治它。

4. 修复设计 — 四个 Fix

Fix做什么治哪层
A把工人回合级错误(如 unauthorized)变成结构化标签 + 净化后的文本,从工人一路传到数据库与告警。以后告警会说「最后死因: 凭据被撤销」而不是「起不来」。诊断信号全链丢失
B环境类失败断路器:同一节点连续两具尸体、同一环境类死因(v1 只认「凭据失效」这一种)→ 引擎立刻收口挂起并发真因告警,不再空转 30 分钟烧完全部盲换配额。分类不确定时行为与现在完全一样(保守缺省)。换体治不了的死因空转
Censure 包装层记录进程被终止的来源与信号名;自家取消打「cancelled」不再冒充「held」;助手已打出成功证据时先复验再裁定。误导性日志
D工人死亡时立刻经既有 Lead 通道告知「引擎最早于 ~T 重新检查替换资格」——退避等待(1/5/15 分钟的重试间隔)不再是零信号黑洞;另把「杀窗落空(窗本来就不在)」和「杀窗真失败」分开记录。退避窗外观像死机

5. 数据 / 结构模型

核心是一条贯穿四个包的 typed 契约(类型化字段,任何一环漏传都会编译失败):

字段/机制说明
failureCode稳定机器码,如 codex:unauthorized。只有已审白名单里的组合才被接受(v1 仅此一个),防止任意文本冒充分类触发断路。
failureClass分类枚举,v1 仅 environment(环境类 = 换身体治不了的死因)。与 code 成对校验,不合法则两个字段一起丢弃。
canonical 分类权威每具尸体的第一条落账分类(含「没有分类」)即永久冻结;之后到达的任何差异只进审计,绝不改判——保证断路器判定与已发通知永不漂移。
turn 归属权威错误必须能证明属于本次目标的回合才被记录(用 daemon 的回合确认,不用会自我注册的旧集合);证明不了就不记,宁缺毋滥。
原子 outbox 通知「死亡 + 通知 Lead」两条记录在同一个数据库事务里落库,崩溃不丢通知;重投用幂等去重,承诺 at-least-once(至少一次,可能重复但内容逐字相同、零副作用)。
事件 environment_failure_escalated断路器收口的账面事件,带真实死因、前后两具尸体 id、盲换计数;复用 retry_limit 的同一段收口代码,行为同构。

6. 关键取舍与被否掉的方案

决策选了什么 / 否了什么为什么
同名窗竞速收敛机制否(issue 修点②原案)证据裁定该竞速不存在:「kill 落空」是因为窗从未建成;既有 FLY-1239 的可证清窗机制已保证 ≤1 窗。为不存在的问题建机制违反简单性纪律。只保留日志区分 + 一条回归测试。
断路器触发门槛连续 2 具同死因,不是 1 具第 1 具死后仍铸一次替换体——万一环境恰好已修好,给它一次探测机会;第 2 具同因死证明环境未愈,再换只是空转。
退避可见性载体否掉「新建退避状态表」与「巡检加一行」,改为死亡瞬间经既有 Lead 通道通知巡检默认 60 分钟一轮,罩不住 1/5/15 分钟的退避窗;新表还要进数据库保留窗治理。死亡瞬间通知 = 退避窗起点即送达,零新表、零新定时器、零新通道。
投递语义如实承诺 at-least-once(可能重复),不为此改共享投递协议重试机制会改写投递身份,接收端绝对去重在现协议下不可达;一条信息性通知不值得动全队共用的投递机器。重复通知内容逐字相同、无任何副作用。
auth 自愈(凭据预检 / 失效自动换号)不在本单做,报 Lead 另立 issue职责边界:引擎的义务是「面对治不了的死因快收口 + 说真话」;凭据管理属账号族(FLY-513 相邻),混进本单会让两边都难 review。
归属证明不了时整链搁置(连「真因文本」也不追加),保持现状并上报证明不了归属的错误可能来自旧目标的迟到消息——写进告警反而制造新的误导,重蹈本次日志骗人的覆辙。

7. 诚实边界 — 这个设计做什么、不做什么

做

  • 真实死因从工人传到告警(A);环境类死因连续 2 具即收口并说真话(B);误导日志改说实话(C);退避等待可见(D)。
  • 全部改动 additive(只增不改)+ 保守缺省:分类缺席/不确定时,引擎行为与现在字节等价。

不做 / 做不到

  • 不修 auth 本身:凭据坏了还是要人(或另一个 issue 的机制)去修;本设计只保证引擎不再对着死凭据空转半小时且告警说得清死因。
  • 断路收口后没有一键恢复:现有机制里 retry_limit 类挂起只能人工按告警处置(terminate 后另起新 run/attempt),本单不扩恢复面——告警文案会如实写这条路径。
  • 通知可能重复(at-least-once):崩溃重投时 Lead 可能收到两条一样的通知,内容逐字相同、带稳定 id 可识别,无副作用。
  • Fix A/B 有一个实测前置:daemon 通知流的回合归属证明要用真 daemon 实测钉死;若两种归属权威都证明不了,A/B 整链搁置并如实上报(计划里写死了这个降级出口)。
  • run 8bfa33b2(FLY-2000)当前仍是 held + 死 exec,等 operator 决策——本单不代做恢复。
