## Summary

The new purge primitive is locally sound. `_prepared_stall_purge_ref` is lease-gated, validates the existing state file, writes a same-directory temporary file, removes the temporary on `awk` failure, and atomically replaces the state file. `_ledger_transaction` releases the ledger inner lock before `_ledger_remove` invokes the purge, so there is no ledger/stall lock inversion. `_ledger_remove` also has the right primary-operation rc semantics: a failed ledger transaction does not purge anything, while a successful ledger removal followed by purge failure logs a warning and still returns the successful ledger rc.

The lifecycle binding is not yet complete, however. Several prepared-to-committed transitions and one direct receipt-deletion primitive bypass the new cleanup, and the sequential ledger/stall writes have an explicit crash window with no restart reconciliation. The new test also does not actually pin two of the new clear sites. The supplied lint and test results, including the negative control, were treated as reported facts and were not re-run.

## Findings

1. **Alternative ledger mutators still bypass stall-evidence retirement — MEDIUM**

   - **File:** `scripts/flywheel-cmux-sync.sh:5115`, `scripts/flywheel-cmux-sync.sh:5306`, `scripts/flywheel-cmux-sync.sh:6905`, `scripts/flywheel-cmux-sync.sh:7255`, `scripts/flywheel-cmux-sync.sh:7271`, `scripts/flywheel-cmux-sync.sh:8479`, `scripts/flywheel-cmux-sync.sh:10830`; `scripts/test-cmux-sync.sh:12896`
   - **Evidence:** [verified by reading code] Cleanup on commit was added only inside `complete_title_migration`, but `_v2_lead_prepare_and_name`, `_v2_lead_adopt_birth`, `adopt_birth_candidate`, restored recovery, stock adoption, and rebind still write `committed` directly. Several of those functions explicitly accept an existing `prepared` row before committing it. In the ordinary view path, `reconcile_workspace_titles` calls `adopt_birth_candidate` for a birth-owned prepared row at lines 8786–8790; that helper commits at line 8479, then the subsequent `complete_title_migration` sees an already-committed receipt and skips both new prepared-only clears. There is also a direct receipt deletion in `_restored_ledger_cas delete` at lines 7255–7274 that never calls `_ledger_remove`. Finally, `_ledger_transaction upsert` removes every existing row with the same ref at line 6905, regardless of generation. In `rebind_adopt_stale_receipt`, the current-generation commit at line 10830 can therefore erase the old-generation receipt before lines 10833–10835 decide whether to call `_ledger_remove`; the old generation's stall rows are left behind.
   - **Failure scenario:** A prepared birth-owned or V2 Lead tuple accumulates migration evidence after a deferred tab rename. On the next pass, its birth-specific convergence path commits it directly. Because committed rows are never re-enumerated by `reconcile_prepared_ledger`, the migration row remains indefinitely. Separately, rebind can replace an old-generation receipt by ref while leaving the old-generation stall evidence, and restored CAS deletion can remove a receipt without retiring any matching evidence. These rows again accumulate toward the 1 MiB validator cap and can carry stale counts into a reused tuple.
   - **Suggested fix:** Bind retirement to every ledger mutation primitive, not selected callers. After any successful committed upsert, purge all prepared-stall evidence made obsolete by that upsert, including prior generations removed by the ref-wide replacement; after `_restored_ledger_cas delete`, perform the same post-success cleanup. Preserve the primary transaction rc and warn on cleanup failure, as `_ledger_remove` now does. Add regression cases for an existing prepared row committed through a non-`complete_title_migration` path and for the rebind/ref-wide replacement or restored-CAS deletion path.

2. **Ledger commit/removal and stall cleanup have an unrecovered crash window — MEDIUM**

   - **File:** `scripts/flywheel-cmux-sync.sh:6933`, `scripts/flywheel-cmux-sync.sh:6936`, `scripts/flywheel-cmux-sync.sh:6966`, `scripts/flywheel-cmux-sync.sh:6969`, `scripts/flywheel-cmux-sync.sh:8256`, `scripts/flywheel-cmux-sync.sh:8260`, `scripts/flywheel-cmux-sync.sh:8314`, `scripts/flywheel-cmux-sync.sh:8315`
   - **Evidence:** [verified by reading code] The ledger replacement happens first. `_ledger_transaction` then executes its existing `after-ledger-mv` crash seam before returning; only after it returns does `_ledger_remove` purge the ref or `complete_title_migration` clear the migration key. A process death at that seam—or the equivalent real crash between the two file operations—leaves the ledger durably committed/removed and the stall row intact. No startup or reconcile sweep removes stall rows whose exact prepared receipt no longer exists.
   - **Failure scenario:** A watcher commits or removes a prepared receipt, is killed immediately after the ledger `mv`, and restarts. For a commit, future prepared reconciliation ignores the now-committed receipt; for a removal, there is no receipt to enumerate or remove again. The orphan evidence therefore survives permanently despite the new lifecycle hooks and has the same cap-exhaustion/stale-count consequences as the Round-2 finding.
   - **Suggested fix:** Add a lease-held, idempotent reconciliation sweep that removes migration/prepared-stall rows lacking an exact matching prepared receipt, and run it on restart/normal reconciliation before the early return for a missing ledger. This provides recovery for every two-file crash point without pretending the operations are atomic. Add a test that seeds the post-crash residue directly (committed or absent receipt plus migration row), runs the recovery entry point, and asserts the row is retired while unrelated live prepared evidence survives.

3. **The lifecycle regression test does not pin two new clear sites or purge-failure rc semantics — LOW**

   - **File:** `scripts/test-cmux-sync.sh:12886`, `scripts/test-cmux-sync.sh:12890`, `scripts/test-cmux-sync.sh:12898`, `scripts/test-cmux-sync.sh:12900`; `scripts/flywheel-cmux-sync.sh:8260`, `scripts/flywheel-cmux-sync.sh:9103`
   - **Evidence:** [verified by reading code] The test labels its middle branch `provisional`, but supplies `~`, which is normalized to `__NULL__`. More importantly, the fixture enables successful workspace and surface mutation. If the branch-local migration clear at line 9103 is deleted, that case still reaches `complete_title_migration`, commits, and clears the same row at line 8315, so the assertion remains green. The direct completion case starts with `Terminal 66`, so it exercises only the post-rename clear at line 8315; deleting the `surface == title` short-circuit clear at line 8260 is not detected. The test also covers only a successful purge, not the explicitly required behavior where purge fails after a successful ledger removal and `_ledger_remove` must still return success.
   - **Failure scenario:** A future edit removes either uncovered clear or accidentally propagates purge failure as ledger-removal failure. The reported lifecycle test remains green, allowing non-consecutive evidence or misleading caller recovery behavior to return.
   - **Suggested fix:** For the combined `__NULL__|__PROVISIONAL__|__DEFAULT__` arm, force the later rename/completion to fail and assert the branch clear alone removed migration evidence. Add a `surface == title` prepared-commit subcase. Add a purge-failure subcase (for example, a validated seam or deliberately invalid stall file) asserting that the receipt is gone, the warning is emitted, and `_ledger_remove` returns the ledger transaction's success rc.

## Verdict

**CHANGES REQUESTED.** The new purge helper, lock ordering, atomic state-file rewrite, and `_ledger_remove` rc handling are correct in isolation. The requested lifecycle invariant is still bypassed by other ledger mutators and is not crash-recoverable across the ledger/stall file boundary; the regression test also leaves two new clear sites unpinned.
