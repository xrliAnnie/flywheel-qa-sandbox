FLY-1628 · pane-loss 结算 reconciler

设计方案 · 2026-08-04 · Codex 设计评审 10 轮 APPROVED · Issue: FLY-1628
① 一句话总结

每个 AI 工人（runner）出生时留下一枚「出生地凭证」；以后无论谁把它的工作窗口整批拆掉，系统都会在下一轮例行对账里拿凭证核对——凭证对不上就自动把账面改成真实状态、在 issue 帖子里说明发生了什么，并且永远不擅自重派工人。

名词解释：runner = 在终端窗口里干活的 AI 工人；tmux = 承载这些终端窗口的「窗口管理器」，它一死所有窗口跟着消失；reconciler（对账器）= 定期把「账面记录」和「真实世界」对齐的程序。

② 出了什么事，为什么 2 小时没人收账

2026-08-03 晚上 7 点 23 分，一次全量重启把全舰 runner 的 tmux 窗口整批带走了。但账本没跟上：有的 runner 账面上还写着「干活中」，有的还挂着「等你审批」。两个多小时没有任何机制来纠正，系统甚至每 5 分钟去「叫醒」一具已经不存在的尸体。

为什么现有的十来个守护机制全都没接住？我们逐个核对了代码，结论是：每一个的「管辖条件」都恰好绕开了这个形态——管终态清扫的要求账面先是终态；管心跳超时的不管「等审批」状态的行；管舰队级死亡的那个（FLY-1082）要求「全员死绝」才动手，而现场恰好残留 6 个空壳窗口，让它整批放弃；专杀尸体窗口的只管「窗口还在、进程死了」，不管「窗口整个没了」。

另外一个关键更正：直接凶手不是重启脚本本身（它对 runner 完全无感知），而是重启流程中被连带杀死的 tmux server——这类死法不可控也不唯一，所以修法必须是「无论谁拆的，账面都能收回来」，而不是去堵某一条产线。

③ 核心流程

设计的核心是一枚「出生地凭证」。runner 出生、创建自己工作窗口的同一条命令会原子地带回三样东西：窗口编号、tmux 的 socket 地址（可以理解为「哪一台窗口管理器」）、以及那台窗口管理器的启动时间。这三样合起来就是「我出生在哪一代 server 上」的凭证，直接存进这个 runner 的既有档案字段——不建新表。

为什么这是可靠的死亡证据：窗口和窗口里的进程都不可能比创造它们的那一代 server 活得久（server 一死，它名下的进程会被系统统一收割）。所以对账时只要发现「当前 server 的启动时间 ≠ 凭证上记的启动时间」，就等于铁证：旧一代已整体消亡，这个 runner 的身体确实没了。用「相等/不相等」比较而不是「早于/晚于」，还天然免疫系统时钟被回拨的干扰。

凭证写不进去，工人就不放行。为了保证「活人绝不可能带着过期凭证」，凭证落档被做成了开工前的硬前提：窗口先以一个「等待壳」创建，凭证写入并回读成功后才放行真正的 AI 进程。中途任何崩溃只会留下一个永远开不了工的空壳，绝不会留下「活人 + 错凭证」。

④ 数据与结构模型

零新表、零新列、零新开关、零新定时器。凭证放进既有的 JSON 档案字段；对账搭在既有的「开机 + 每小时」例行清扫顺风车上；改账只走既有的正规通道（applyTransition，系统里所有状态变更的唯一合法入口，会自动维护终态时间戳等一整套账目规矩）；连紧急停用开关都是复用现成的总开关。

分工也是明确的（见下图）：「server 整个死了」的干净形态仍归现有的舰队级伤亡协调器管（本次只给它补一道门：Codex 型 runner 的身体不一定跟窗口一起死，以后不再被它误埋）；「server 活着但个别窗口没了」的脏残局归本单的新对账 face 管；两者靠调用顺序和「飞行中」互斥标记保证同一时刻只有一个在动手。

⑤ 关键取舍与被否掉的方案

取舍一：等审批的行只「告知」，不自动改账。正在等你审批的 runner 死了体，系统只会在 issue 帖子里说明情况、附上一条 Lead 可以一键执行的收尾命令——绝不自动把状态改成终态，因为那等于替你作废一次还活着的审批。

取舍二：Codex 型 runner 一律只提醒。实测发现（FLY-1634）Codex 的常驻体可以在窗口消失后继续活着，「窗口没了」对它不构成死亡证据，所以宁可多一条人工核实的提醒，也不冒误杀的险。

取舍三：查无实据就不动手。凭证相同（同一代 server）却找不到窗口，按既有安全合同（FLY-1319 事故换来的铁律：「找不到」不等于「死了」）只发提醒。

被否掉的方案为什么否
新建一个常驻巡逻器盯着窗口与刚完成的「拆除追人型看门狗」大方向（FLY-1570，净删 3.2 万行）背道而驰
「找不到窗口」就当死亡处理违反 FLY-1319 事故合同——曾经就是这样误杀过一个活着的 runner
跨数据库的锁/租约/收据事务体系前一位设计者走了这条路，与评审 5 轮未能收敛（始终存在竞态漏洞）后中止；本方案用「出生凭证 + 单同步栅栏」结构性绕开
比较「时间早晚」来判断换代时钟回拨会误判；改用「相等/不相等」+ 指明 socket，两个坑都免疫
等审批的行也自动改终态会作废活着的审批流
⑥ 诚实边界：这个设计做什么、不做什么

做今后每一次「窗口整批消失」事故后，带凭证的 claude 型 runner 在下一轮对账（开机后首轮成功对账，正常约 5 分钟内）自动收账；等审批/Codex/旧存量行收到带证据说明的提醒和收尾建议；对死体的每 5 分钟无效叫醒同步止血。

不做①不自动重派任何工人（重派永远由你或 Lead 拍板）；②部署之前就存在的死账没有凭证，只提醒不自动改（清存量归 FLY-1383）；③重启前「保护正在等审批的 runner」是另一个问题，按 eng-lead 裁定归入重启减法单（FLY-1634）的输出层；④Codex 型的自动结算等有了进程级判活手段再说；⑤Bridge 运行期间新产生的死体最多等一小时到下一轮对账——更快就得加巡逻器，不值。

已知安全假阴性tmux 启动时间精确到秒：同一秒内拆了又重建 server 会漏掉一次自动收账（下次换代自然补上），方向是「漏收不误杀」，可接受。
