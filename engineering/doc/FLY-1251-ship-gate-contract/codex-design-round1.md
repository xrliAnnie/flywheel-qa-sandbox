# Design Review — FLY-1251 plan.md (Round 1)
Date: 2026-07-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

The PR-1 lever is sound: the four founder-facing surfaces really do share `reviewHoldReason`/`isReviewHeld`, and—when PR/head metadata is intact and code review is satisfied—the proposed `qa_evidence_missing` predicate closes the exact 2026-07-14 `qa_required=0` + zero-`auto_qa_record` card-posting incident. The transition-period merge-gate statement is also honest. However, the plan is not yet safe to implement: its card schema cannot perform several promised retries, card `active` state is not part of authorization, and the claimed “R1/R2 full” implementation is still an execution-local QA stopgap rather than the PRD’s run/generation barrier.

## What's Good (Keep)

- The central-lever claim is verified in source: GatePoller, `event-route.ts`, `HeartbeatService`, and `DirectEventSink` all consume the same hold predicate. Adding one fail-closed evidence reason there is the correct low-blast-radius stopgap.
- Main-only scoping is a good incident fix and does not change the current design/implement/qa three-stage phase behavior. Retiring `qa.auto:false`, `skip_labels`, `no-qa`, and the global auto-QA switch as ship exemptions while retaining them as spawn controls matches the ratified policy.
- The plan correctly rejects `ExecutionEvidenceCollector.changedFilePaths` as authority: it is a best-effort snapshot from a runner-writable worktree. A Bridge-owned GitHub view, fail-closed on uncertainty, is the right direction.
- CAS transitions, a partial unique index, durable audit markers, and treating Discord edit/delete as best-effort UX are consistent with the repository’s established patterns.
- PR-1 before PR-2 is sensible, and deferring the `evaluateQaShipGate` truth-table change until FLY-1244 commit B lands is coherent. The plan accurately states that `qa_required=0` still passes the current merge gate during that accepted transition.
- The four explicitly forbidden FLY-1244 files (`ship-eligibility.ts`, `write-gate-response.ts`, `actions.ts`, `qa-result.ts`) are kept out of the proposed FLY-1251 file list.

## Issues & Recommendations

1. **[HIGH] The plan does not implement R1/R2 “fully”; it implements an execution-local QA stopgap.**
   - **Why it matters:** PRD R2 is keyed by `workflow_run_id`/generation and requires every snapshotted obligation for that run, stale-attempt rejection, no active hold, and a frozen subject before activation. The proposed decision is only `(main execution_id, pr_head_sha) -> passed auto_qa_record or docs-only` (`plan.md:75-94`), while the claim source and review-obligation set are explicitly deferred (`plan.md:169-172, 236-237`). `founder_ship_card` also enforces uniqueness per execution, not per workflow run/gate epoch (`plan.md:123-140`). Retry/replacement executions in one run can therefore each own a live card, and no diamond/optional/retry-generation barrier exists.
   - **Suggested fix:** Materialize a run/generation/gate-epoch identity before PR-2 and make both readiness and the live-card unique key use it. Define one `evaluateReadiness(runId, generation, subject)` result that aggregates the snapshotted required obligations, rejects stale attempts, and includes current holds. Either deliver that mechanism here or explicitly relabel the deliverable as an incident stopgap/partial R1-R2 and stop claiming the PRD’s full counters are closed.

2. **[HIGH] The card schema and existing marker/binding semantics make the promised retries impossible, and the send→persist crash window still creates an unobservable clickable card.**
   - **Why it matters:** The row is `UNIQUE(question_id, pr_head_sha)` and `retired` is terminal (`plan.md:123-141`), yet post failure, binding failure, and channel recovery all promise to re-post the same question/head on a later tick (`plan.md:147-150, 165-167`). That insert will conflict forever. The current binding is also immutable per `(question, head)`—the first message ID wins—so a replacement message cannot become authoritative. Finally, current GatePoller writes `founder-thread-notify-<qid>` even after a binding write throws (`gate-poller.ts:2101-2111, 2213-2251`); “keeping” that marker suppresses the promised retry. A crash after Discord accepts the POST but before `message_id` is persisted leaves a visible card whose ID cannot be retired, polled, or answered—the exact half-failure class R1 calls out.
   - **Suggested fix:** Introduce a durable `card_attempt_id`/attempt number and key immutable bindings by card attempt, with a partial unique index only on the run/gate epoch’s live attempt. The current binding pointer must be derived from the active card and must match its exact `message_id`, not merely “a binding exists.” Replace the terminal per-question notify marker with attempt/state-specific markers written only after activation. Add a durable post nonce/idempotency key and a restart reconciliation procedure that can recover the Discord message ID (or find/edit the posted message by nonce) for the POST-success/DB-failure window. Test every crash edge: before POST, after POST before ID persistence, after ID persistence before binding, after binding before activation, and after retirement before replacement.

3. **[HIGH] `founder_ship_card.state='active'` is not an authorization precondition, so posting/retired/no-card states can still approve; the text/deferred behavior contradicts main channel A.**
   - **Why it matters:** The live reaction handler currently checks session status, current question/head, binding, and hold, then writes approval; it never reads a card state (`founder-reaction-approval-handler.ts:80-140`). The text handler similarly writes `{"approved":true}` after its hold recheck (`founder-ship-approval-handler.ts:449-489`). The plan changes posting and stale scanning but does not put `active card + exact card binding` into the shared approval authority. Worse, it classifies `qa_evidence_missing` as deferrable (`plan.md:79`), allowing a founder text sent before readiness to be parked and auto-applied later without clicking the post-readiness active card. `plan.md:161` only redirects text when it is already held/deferred; it does not stop an ordinary text approval from writing while an active card exists or while no active card exists. Until FLY-1244 commit A lands, actions/founder-consent direct writes are also not card-aware.
   - **Suggested fix:** Make current active-card identity and exact message binding a USE-time check in the single approval authority for every approval entry. A reaction may authorize only the exact active card; retired/posting/no-card results must return a typed founder-visible reason. Under the ratified A/B contract, founder approval text with an active card must point to that card, and text with no active card must say why approval is unavailable—not be stored for later authorization. `qa_evidence_missing` must therefore be non-deferrable. Because the shared writer is FLY-1244’s surface, make PR-2 explicitly depend on FLY-1244 commit A (or have FLY-1244 expose the card-authority seam) rather than leaving this to implement-time discovery.

4. **[HIGH] Missing PR/head metadata remains a fail-open card path.**
   - **Why it matters:** The proposed predicate runs only when `pr_number != null` (`plan.md:83`). A real code run whose PR-number ingestion half-failed therefore bypasses `qa_evidence_missing` entirely. Likewise, current `reviewHoldReason` returns early for a missing/malformed head; with the Codex hard gate off or `codex_skip`, that becomes `null`, so appending the new logic after the existing QA check does not recover it. This conflicts with `plan.md:23` (“DB/API read failure → hold”) and recreates the exact “unknown stands in for exempt” failure mode.
   - **Suggested fix:** Add an independent `ship_subject_missing`/`qa_evidence_unknown` hold for a main `approve_to_ship` candidate whenever PR identity or a valid head is absent, unless a trusted server-owned route explicitly proves the workflow is non-mergeable. Do not treat `pr_number == null` as no-code. Specify that snapshot/store read exceptions are caught and converted to a hold plus Lead-visible error. Add adversarial tests for missing PR number, malformed/missing head with both Codex flags, missing/corrupt snapshot table, and a DB read throw. Also make E1 arrange a satisfied Codex gate; otherwise the current reason ordering correctly returns `codex_pending`, not `qa_evidence_missing`.

5. **[HIGH] Manual-QA enrollment does not establish a trusted evidence producer and inherits auto-QA lifecycle side effects without defining ownership.**
   - **Why it matters:** `loopback + same-origin + confirmToken` is CSRF protection, not Lead identity—the sibling FLY-1244 plan says this explicitly. The proposed endpoint accepts an arbitrary `qaExecutionId`, while today’s `qa-result` command lets the caller choose `--exec-id` and sends both `execution_id` and `payload.qaExecutionId` under the shared ingest token (`qa-result.ts:32-58, 107-145`). Matching a self-reported ID to a row is therefore not “stronger binding” and can mint a ship-relevant PASS without proving who ran QA. The reused coordinator also assumes it owns an auto-QA child: PASS closes/archives the reporting runner and FAIL parks/retest-wakes it (`auto-qa-coordinator.ts:1269-1323`), behavior the plan does not define for an independently dispatched main-role session.
   - **Suggested fix:** Do not expose arbitrary evidence enrollment through this local mutation route. Make enrollment a server-owned consequence of a trusted QA dispatch/admission and authenticate the verdict with a per-execution credential/challenge—preferably by consuming FLY-1244’s broker after its commit B, while keeping FLY-1251 out of `qa-result.ts`. If an interim manual path is unavoidable, define its authority and threat model honestly and require a durable server-created parent↔QA binding that the caller cannot choose. Branch cleanup/retest behavior on `enrollment_source`, or explicitly require a dedicated disposable QA execution and validate that fact. Add impersonation, unrelated/terminal execution, PASS cleanup, FAIL/retest, and restart tests.

6. **[HIGH] The docs-only classifier is underspecified in ways that can classify a code change as exempt.**
   - **Why it matters:** Classifying only returned paths against an allowlist misses rename provenance: renaming `src/x.ts` to `docs/x.ts` would look docs-only unless `previous_filename` and operation are checked. `gh pr view --json headRefOid,files` is also not an executable pagination contract as written, and the service input lacks a server-owned repository identity; running `gh` in the wrong cwd/repo can query the wrong PR number. The durable key `(execution, head)` omits PR identity/base and classifier/policy version, so a same-head retarget or future allowlist change can reuse an old exemption forever.
   - **Suggested fix:** Specify an explicit configured `owner/repo` input and a fully paginated PR-files API contract with completeness detection; any cap/truncation/unknown status fails closed. For renames, require both old and new paths to be allowlisted, and validate deletions, modes, binaries, and submodules conservatively. Key or validate the snapshot with repo, PR number, head, base identity, and classifier/policy version; recompute on any mismatch. Add tests for code→docs rename, docs→docs rename, deletion/binary/submodule, >1 page, truncated response, same head under a different PR/base, and classifier-version change.

7. **[HIGH] A seven-day/20-row stale scan cannot satisfy R9’s “every click gets a response” hard invariant.**
   - **Why it matters:** Retired Discord cards remain visible and clickable indefinitely, especially when the best-effort edit fails. `window=7d` silently ignores a click on day eight, and `limit=20/tick` without a defined durable cursor can permanently starve later rows (`plan.md:158-160`). The plan nonetheless claims the hard counter is zero only “within 7d” (`plan.md:215`), which weakens the authoritative PRD rather than implementing it. The static channel-health predicate also omits actual inability to read reactions (missing/invalid bot token, 401/403/404, or persistent fetch failure), leaving an “active” card whose approval channel is unusable.
   - **Suggested fix:** Observe every retired message for as long as it remains actionable, using durable cursor/pagination so the per-tick budget is fair and restart-safe; do not narrow the hard counter to seven days. If observation can legally stop, first establish a durable, externally verified state in which that message can no longer be mistaken for an authorization surface. Model reaction-read failures separately from “no reaction,” retire/block on proven channel unavailability, and alert with a durable recovery path. Test >20 retired cards, old-card clicks, restart cursor recovery, 401/403/404, 429/transient recovery, and channel restoration.

8. **[MED] The “zero file conflict with FLY-1244” and sequencing claims are inaccurate.**
   - **Why it matters:** The four forbidden files are avoided, but both plans modify `StateStore.ts`, `auto-qa-coordinator.ts`, and composition/route wiring. FLY-1244 commit B explicitly changes `auto-qa-coordinator.ts` for enrolled verdicts, exactly where FLY-1251 changes role admission; both also add StateStore migrations and plugin routes. Calling this zero-conflict (`plan.md:25, 244`) gives the implement session no integration order for overlapping semantics. PR-2 additionally needs FLY-1244’s single writer to enforce the active-card USE-time check identified above.
   - **Suggested fix:** Replace “zero file conflict” with a symbol-level integration matrix. Keep PR-1 first, but state the rebase/merge order for `onQaResult`, migrations, and route registration; add a combined test showing manual/legacy auto-QA and FLY-1244 credentialed claims cannot bypass one another. Make PR-2’s authority work explicitly follow FLY-1244 commit A, and keep only the merge-gate truth-table change behind commit B. Preserve the current rule that any need to edit the four forbidden sibling files is escalated rather than improvised.
