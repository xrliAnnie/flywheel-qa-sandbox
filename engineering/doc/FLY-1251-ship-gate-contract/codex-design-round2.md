# Design Review — FLY-1251 plan.md (Round 2)
Date: 2026-07-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 2 materially improves the plan: the delivery boundary is now honest, the exact 2026-07-14 incident is closed by a main-only fail-closed evidence hold, and the attempt-based card model, server-owned manual QA, no-window stale scan, and symbol-level FLY-1244 matrix are all the right directions. The plan is still not implementation-ready, however, because several promised crash recoveries have no converging transition, the active-card authority cannot be installed without violating the stated sibling-file boundary (and still leaves deferred/programmatic bypasses), and the docs-only exemption cannot enforce its stated mode/submodule rule from the selected API data.

## What's Good (Keep)

- The new “交付边界” section accurately distinguishes execution-local incident containment from the PRD’s run/generation readiness barrier. Deferring run-level obligation aggregation and card uniqueness to a named follow-up seam is honest and makes the hard-counter scope reviewable.
- E1 now arranges a satisfied Codex gate and directly exercises the real incident shape: main `awaiting_review`, code diff, `qa_required=0`, and zero `auto_qa_record`. With a valid code snapshot, `qa_evidence_missing` prevents all four shared founder surfaces from reaching card posting.
- `qa_evidence_unknown` for missing PR/head identity closes the prior Codex-off/`codex_skip` fail-open branch. Keeping it main-only preserves the current three-stage role behavior.
- Attempt rows, the partial live-card index, CAS transitions, per-attempt activation markers, and making the active card—not the legacy immutable binding—the read-side authority are consistent with the codebase’s durable-state patterns.
- Replacing caller-selected QA enrollment with a server-spawned real QA session is the correct trust boundary. Keeping the existing `onQaResult` verdict chain untouched is especially important.
- The classifier contract is substantially better: server-resolved repository identity, PR-head preflight, paginated file enumeration with count completeness, conservative unknown statuses, and dual-path rename checks address the largest Round-1 classification holes.
- The stale-card duty now has no time cutoff, uses a durable fairness cursor, and distinguishes Discord authorization/permission/not-found/rate-limit failures from “no reaction.” The channel-unhealthy escalation is the right fail-closed direction.
- The integration matrix correctly acknowledges shared symbols and keeps `onQaResult` out of FLY-1251. PR-1 before PR-2 and merge-gate tightening after FLY-1244 commit B remain coherent.

## Issues & Recommendations

1. **[HIGH] The card state machine still cannot recover three of its own enumerated crash states, and `reconcile_orphan` can create the unobservable clickable card it claims to eliminate.**
   - **Why it matters:** §4.2b only reconciles `posting` rows whose `message_id` is null. A crash after ID persistence but before binding, or after binding but before `posting→active`, leaves a permanent `posting` row. The partial unique index then blocks every replacement attempt. Likewise, a crash after `active→retiring` but before edit/final CAS leaves a `retiring` row that is neither completed by §4.2b nor scanned by §4.4. Finally, “scan recent messages; if not found, retire” is not proof that Discord never accepted the POST: a transient read failure, a truncated recent-message window, or enough intervening thread traffic can miss the nonce. Retiring that row loses the only durable correlation while the visible message may still exist and accept reactions.
   - **Suggested fix:** Define restart/tick convergence for every nonterminal state. For `posting+message_id`, re-read/repair the binding and then CAS active, or retire and visibly neutralize the known message; for `retiring`, retry edit/delete and always converge to a retired row that remains observable. For `posting` without an ID, distinguish fetch failure/incomplete history from an exhaustive scan: paginate back past `created_at` and only declare absence when the scan is complete. On any uncertainty, keep the row live and retry/escalate channel health—do not orphan-retire it. Extend E7 to restart from each persisted substate, including `posting+id`, `posting+id+binding`, and `retiring`.

2. **[HIGH] The USE-time authority plan is internally incompatible with the forbidden-file boundary and still permits the exact non-card authorization paths the plan says are closed.**
   - **Why it matters:** The target form says to insert `assertActiveCardAuthority` into FLY-1244’s `writeFounderApproval`, but that operation lives in `approval-signal/write-gate-response.ts`, one of FLY-1251’s four explicitly forbidden files. No injection/interface seam is specified. The fallback form guards only reaction/text/voice/deferred and §4.3 explicitly leaves `actions` and founder-consent non-card-aware, contradicting §2-8’s “every entry” guarantee. It also says approval-like text/voice is never parked while preserving existing `codex_pending`/`qa_not_green` deferred semantics; an already parked or newly parked approval can later replay with no card target because `targetMessageId` is optional. That is Main-A’s forbidden park-then-auto-apply path.
   - **Suggested fix:** Make FLY-1244 commit A a hard PR-2 merge prerequisite, not an optional unsafe transition. Have commit A expose a card-authority dependency/hook owned outside the forbidden file, or explicitly reassign the file boundary before implementation. Define a source-discriminated authority input and a complete matrix for reaction, text, voice, deferred replay, actions, and founder-consent: reaction must name the exact active message; approval-like text/voice must only redirect/explain; deferred approval replays must be refused or converted to notification-only; every programmatic route must carry its independently verified founder authority and pass the same live-card/hold check. Add mutation tests for all six production routes. Until this is mechanical, do not claim R9 full or execution-domain authority closure.

3. **[HIGH] A successful grey edit does not discharge R9’s per-click response invariant.**
   - **Why it matters:** Editing Discord message content does not make the message or its reactions unclickable; an existing ✅ can still be toggled and a new ✅ can be added. §4.4 removes `grey_edit_done=1` rows from observation, so a later reaction on that retired card receives no click-correlated response. The authoritative PRD explicitly requires continued observation of retired message IDs and a zero stale-click-without-response counter. A visible “expired” label is good UX, but it is not proof that no later click can occur.
   - **Suggested fix:** Treat verified deletion/404 (or another externally verified state that truly removes the reaction surface) as the observation-release condition. Keep successfully grey-edited but still extant messages in a lower-frequency fair scan, and retain the durable response marker/reason. If the product intends the static grey text itself to count as the response to every future click, that is a contract change to the approved PRD and should be ratified there rather than assumed in this implementation plan.

4. **[HIGH] The docs-only classifier cannot enforce its mode/submodule/symlink rule from `pulls/{n}/files`, and the stored base identity is not actually validated.**
   - **Why it matters:** GitHub’s pull-files entries provide path/status/blob metadata but not authoritative Git file modes for ordinary entries. The proposed implementation therefore cannot distinguish a regular docs file from a symlink or gitlink while also granting a docs-only exemption; “mode unavailable → do not guess” would either exempt an unsafe mode change or classify every candidate as ship-relevant. This matters because PRD R4 explicitly treats modes/submodules as subject data. Separately, the table stores `base_ref`, but the read-side validity rule checks only repo, PR number, and classifier version, despite the Round-2 summary promising base validation. A same-head PR retarget can reuse a stale exemption.
   - **Suggested fix:** Add a server-owned base/head Git-tree lookup (or equivalent GitHub tree/content calls) and compare authoritative entry types/modes for both sides; any unavailable or inconsistent tree data remains ship-relevant. Validate `base_ref`—preferably base OID as well—alongside repo, PR number, head, and classifier version before reuse. Add tests for regular-file↔symlink, gitlink/submodule, executable/mode changes, and the same head retargeted to another base.

5. **[MED] “All store read exceptions hold” is stated globally but not made true by the predicate algorithm.**
   - **Why it matters:** §3.2 catches only the snapshot read in step 4. `isCodexGateSatisfied` and `isQaHeld/getAutoQaRecord` run earlier and can throw before the new `qa_evidence_unknown` branch. Some current callers happen to abort safely on an exception, but that does not produce the promised single typed hold reason or durable Lead-visible diagnosis, and behavior can differ across the four surfaces and the future shared writer.
   - **Suggested fix:** Put the complete `reviewHoldReason` read sequence behind one fail-closed exception boundary (while preserving reason priority): any Codex-record, auto-QA-record, or snapshot read failure returns `qa_evidence_unknown` and emits a deduped diagnostic out of band. Add distinct throw tests for each store method, not one generic snapshot throw.

6. **[MED] The manual-spawn route needs a coordinator-owned admission/CAS method; calling the current private spawn path is not enough and can leave no escape hatch.**
   - **Why it matters:** The current private `spawnQa` assumes an already claimed record. The issue-level “one active QA” race guard, foreign-parent ownership check, and claim/reopen logic live earlier in `onMainAwaitingReview`. The proposed endpoint validation only discusses `(execution, head)`, so a direct reuse can double-spawn against another parent execution for the same issue or race auto-spawn. Also, a same-head `stuck`/lost-verdict record is non-superseded and therefore returns 409 forever; current startup reconcile alerts but does not respawn it. That contradicts the plan’s claim that manual spawn is the legitimate escape hatch for a newly strict hold.
   - **Suggested fix:** Add an explicit public `manualSpawnQa` coordinator operation that re-reads the parent, runs the existing issue-owner/foreign-active gates, atomically claims with `enrollment_source='manual'`, and treats claim loss as idempotent. Define a bounded CAS re-drive for a genuinely dead `stuck`/failed same-head QA while never replacing a live runner or a PASS. Test auto-vs-manual concurrency, two parent executions on one issue, crash after claim, and same-head stuck recovery.
