# Design Review — FLY-1251 plan.md (Round 9)
Date: 2026-07-14
Author: Codex
Status: CHANGES REQUESTED

## Summary

Round 9 materially improves restart safety: health is now boot-scoped, configuration drift has a fail-closed transition, and pre-existing reactions are explicitly reconciled before approval authority opens. The design is still not executable under several adversarial startup/runtime outcomes, and two claimed DDL/checklist updates are not actually present on disk; those gaps can still expose a pre-boot reaction or a nonexistent live card to an approval-capable route.

## What's Good (Keep)

- `last_probe_boot_id` is the right cross-restart trust boundary: a durable `healthy` result from an earlier process is no longer sufficient to authorize in a new process.
- The startup reconciliation concept directly addresses the Round-8 quarantine half-failure instead of relying on optimistic recovery from stale database state.
- `channel_config_drift` now has a closed, non-authorizing disposition: retire the old attempt and create a new one under the exact lane actually used.
- Health writes are correctly scoped to project + Lead + channel/thread + non-secret bot identity, and bot-identity resolution failure stays fail-closed.
- The convergent `ensureReactionBlocked` state machine, per-episode CAS discipline, single activation primitive, POST ambiguity handling, and USE-time health check remain strong.
- The incident predicate is still coherent: a main code PR with `qa_required=0`, no three-stage label, and no `auto_qa_record` reaches `qa_evidence_missing`, so PR-1 prevents the 2026-07-14 approve-card shape.
- The FLY-1244 branch still contains commit A but no authority hook/route-source seam. The plan correctly keeps §4.3 blocked on a future pinned seam commit and does not authorize editing the four forbidden sibling files.

## Issues & Recommendations

1. **[HIGH] The startup barrier has no closed convergence rule for failed reads and does not exclude concurrent card production.** §4.5 says to reconcile every persisted live card, but §4.5b leaves 401/403/429/5xx/malformed/network outcomes with the card unchanged and never says that such a card remains boot-unreconciled. If the barrier is released after merely processing that outcome, a later successful health probe can stamp the lane healthy for this boot without first quarantining the reaction that may already be on the old card. The enumeration also covers only cards persisted when the scan runs; it gates approval routes but does not explicitly pause the producer. Current wiring calls `gatePoller.start()` directly in `plugin.ts`, and that poller owns card creation, so a posting/active card can otherwise appear after the startup snapshot and before the barrier opens. **Suggested fix:** define a named boot reconciler with terminal per-card outcomes. A live card is reconciled only after (a) a 200 reaction read whose health result and required quarantine are durably persisted, (b) a 404/config-drift result whose live card is durably retired, or (c) another durable terminal retirement. Every other result remains unresolved and is retried with authority closed. In `plugin.ts`, await this drain before `gatePoller.start()` and before enabling the writer hook, or use an equivalent producer lock/watermark that proves no live card can escape the scan. Add startup tests for 401/403/429/5xx/malformed/network results and a card-creation attempt during reconciliation.

2. **[HIGH] A 404 on a live card still leaves a database-authoritative card that no longer exists.** The closed outcome table maps every 404 to `message_gone=1` only. That is correct for a retiring/retired observation obligation, but not for `posting+ID` or `active`: the row remains live and blocks repost through the partial unique index. More importantly, health is lane-scoped; another execution in the same lane can produce a successful current-boot probe, after which `assertActiveCardAuthority` can accept actions/founder-consent against the missing card because its stated checks do not include `message_gone=0`. **Suggested fix:** make 404 state-sensitive. For `posting+ID` or `active`, CAS to retiring/retired with a specific `message_gone` reason, release the live slot, and repost a new attempt if the gate is still pending; reserve the bare observation-release update for already retiring/retired cards. Also require `message_gone=0` in `assertActiveCardAuthority`. Test two executions sharing one lane where one read returns 200 and the other 404: every route must refuse the dead card and the pending gate must converge to a fresh attempt.

3. **[HIGH] Boot-scoped persistence does not preserve a fail-closed mutation failure within the same process.** Suppose a prior 200 has persisted `healthy` with the current boot id. A later reaction-read failure occurs and the failure-count/latch mutation cannot converge; the current call can return non-authorizing, but the durable row still says current-boot healthy, so the next authority call can pass. The same runtime hole exists when `ensureReactionBlocked` fails and its fallback retirement also cannot persist: the prose says authority stays closed, but names no state consulted by later calls. `last_probe_boot_id` closes the crash/restart version, not this same-boot interval. **Suggested fix:** add an explicit boot-local poison set keyed by lane and, for quarantine/retirement failure, card attempt. Set it before returning any unpersisted/non-convergent mutation outcome; have `tryActivatePostingCard`, `assertActiveCardAuthority`, the reaction path, and the sweep consult it. Clear it only after the exact same lane/card has been safely reconciled with a verified read and durable writes. Restart safety continues to come from the boot-id barrier. Add tests where a current-boot healthy row survives an increment failure and a second actions call occurs before recovery, plus quarantine-failure/retire-failure followed by another reaction poll.

4. **[MED] The authoritative DDL and implementation checklist still do not match the Round-9 claims.** The `approval_channel_health` SQL block does not contain `last_probe_boot_id`; it is mentioned only in prose. §8 still lists `StateStore.ts (founder_ship_card + CAS)` and the integration row still says `snapshot + card + enrollment_source`; neither location lists `ship_card_reaction_quarantine`, `approval_channel_health`, or the named activation/quarantine/health/boot-reconciliation methods. E13 also omits the dual-rearmer and `ensureReactionBlocked`-exhaustion cases even though §4.7 mentions them. **Suggested fix:** put `last_probe_boot_id TEXT` in the normative SQL, update §8 with all three PR-2 tables and named methods, and synchronize E11/E13/§4.7 with the new startup, live-404, same-boot poison, dual-rearmer, and exhaustion tests. This is important because the implement phase is explicitly expected to execute the plan without the designer present.

## Verdict

CHANGES REQUESTED — address items above
