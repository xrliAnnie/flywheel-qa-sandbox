FLY-2452 · Claude 号死了,切号器要自己切

设计节点交付 · 2026-09-09 · Codex 设计评审 4 轮(8→7→5→2 条,全部吸收零拒绝),Lead 裁定 R4 为最后一轮并接受(leadAcceptance) · 文档:engineering/doc/FLY-2452-dead-account-switch/

一句话

Claude 账号池的切号器(自动把 Claude Code 用的账号换成池里下一个的守护程序)今天只认一种「号不能用」:额度用完。9-8 晚 Persona 1 的订阅到期后,号是整个死掉的,切号器把它当成「暂时读不到额度」无限等待,评审任务全部报错、两个 QA 机器人停在提示符上,3 小时 38 分钟后 founder 手动登录才结束。本设计教会三层「识别死号」:守护程序立刻切号并把死号拉黑,Bridge(统一调度中枢)把卡住的评审任务自动重排,并给在跑的 Claude 机器人各发一条「凭据已换,重跑上一轮」。

不改哪里
founder 专属边界(merge / ship / restart)、Codex 侧账号、/review-requests 接口合同、runner 合同

今天再探这个死号(2026-09-09,只读请求):额度接口回 403 permission_error(错误码 oauth_not_allowed_for_organization);账号资料接口回 200,里面写着 subscription_status: canceled、organization_type: claude_free。这两个都是机器可读的「号已死」证据,也都是只读 GET(只查询、不改任何东西的请求)。

注意:事故当晚守护程序记的是 backoff(说明接口当时回的是 429「太频繁」),今天才稳定回 403。所以设计不能只认 403,连续读不到额度也要升级去探活。

核心流程:从第一个 403 到机器人复工

下图是修好之后的完整链路。时序图:竖线是参与者,箭头按时间从上到下。见证文件是 Bridge 写给守护程序的一个小 JSON,意思是「我看见 403 了,你现在就去查一眼」——它不授权切号,切不切仍由守护程序自己探活决定。SIGUSR1 是一种进程间的「叫醒」信号。mailbox 指令是 Flywheel 内部给机器人的信箱消息,Claude Code 自带信箱轮询,收到就开新的一轮。

  1. 识别:守护程序读额度失败 → 立刻(403)或连续两次(429/网络错)后去读账号资料接口 → 订阅状态是 canceled / 组织是 free 档 → 判定 account_dead。判不准(unknown)一律不切,宁可等。
  2. 切号并拉黑:同一把锁里把死号写上 unavailable 标记,切到池里下一个健康号;generation(账号池的版本号,每次切号 +1)前进,并记下 lastSwitch(为什么切、从哪切到哪)。
  3. 告警:切号通知带 account_dead:personal1,另发一条新种类 account_dead 的 severe 告警到 #flywheel-engineer(与额度切号去的 #flywheel-notify 分开)。这条告警的意图与切号结果写在同一次落盘里,守护程序之后崩溃也能补发;新种类要同步登记到告警合同的 8 个文件,否则发送脚本会直接拒收——这是 Codex 第一轮抓到的 blocker。发送时仍以守护程序自己的身份走统一告警模式,只是把目标频道换成工程频道,所以 🎫 工单头与人工处理流程和「没候选号」那类告警完全一样。
  4. Bridge 跟上:Bridge 每 60 秒读一次账号池的 lastSwitch(最近一次切号的记录;光看 generation 会被「刷新凭据」这类不算切号的写入骗到),发现是没处理过的切号 → 把停靠的评审任务用同一个 request-id(任务的唯一编号)重排,仍然要过三道门:总开关、评审 gate 还开着、代码 head 没动。
  5. 叫醒机器人:只在「因为死号切号」时,给每个在跑的 Claude 机器人(CommDB 里 vendor 是 claude-code 的 running session)投一条 mailbox 指令;机器人下一轮自然用新钥匙。每个 (切号代, 机器人) 只发一次,留审计行。

数据 / 结构模型

类图:每个方框是一种持久化的记录,+ 开头的字段是本设计新增。三个新东西:账号池里的 unavailable 标记(单向门,只有人工命令能解除)、评审任务表的 retry_trigger 列(区分「等额度重置」还是「等切号」)、Bridge 的 account_switch_action_receipt 回执表(每次切号的两项动作各自一张回执,做完才盖章,崩溃后把没盖章的重放,重放落在同一主键上不会重复)。

守护程序内部状态

状态图:圆角框是守护程序在某一刻处于的状态,箭头上的字是触发条件。关键是「只读探活」这一站:只有它给出 dead 才会进「死号切号」;alive/unknown 都回到原来的分支,行为与今天一致。

探活触发
额度接口回 403;或连续 2 次读不到(可配 1..10);或读到未消费的见证文件
探活手段
两个只读 GET:额度接口的 403 错误码、账号资料接口的订阅状态。判定真值表在 research §1.3:只有 canceled / 已知 403 错误码判死;past_due 等没实测过的状态一律「不确定」,不切
防抖
额度切号有 15 分钟冷却;死号切号不受冷却限制(死号不是抖动)。只对「已经成功切过」去重;没候选或暂时失败时每个周期重新选号,告警靠现有事件账去重,不会把可恢复的情况封死

三处根因 ↔ 三处修法

#今天的行为本设计验收怎么证明
1守护程序把 403 塌成「网络错」,429 当退避;切号只由额度百分比触发新增 forbidden 错误类 + 只读探活 + account_dead 切号触发 + 拉黑 + 独立告警;见证文件让它不用等周期隔离台架:评审任务 403 → 切号完成 < 1 个 poll 周期(台架里 1 分钟),全程 claude 未被调用
2评审重试只认 429 + 「hit your limit」文案;403 是终态,切号后没人重排,只能 runner 手工重 POST403-disabled 分类为「等切号」停靠(记停靠毫秒);Bridge 每 60 秒看 lastSwitch,有没处理过的切号就把停靠时刻早于切号的行同 request-id 重排(仍过 gate / head / 总开关三道门),停靠多久都会被扫到集成测试:停靠行在切号后 claim 成功;gate 过期走终态;同一次切号不重复;Bridge 崩溃后按回执重放
3切号只换钥匙;机器人停在提示符没人推;Bridge 的 pane 扫描认不出 403 文案Bridge 在死号切号后给在跑的 Claude 机器人各投一条 mailbox 指令(8-29 实证配方);pane 扫描新增 account_disabled 类兼作见证台架复捕 pane:身份行翻到新邮箱 + 出现活动行;不许只报「我发了 send」

为什么叫醒「全部在跑的 Claude 机器人」而不是「已经 403 过的」:死号下每一个机器人的下一次调用都会 403,「已经 403 过」只是「还没轮到」的子集。而额度切号不进这个叫醒路径(那是 FLY-2109 的范围),所以不会有无关的机器人被打扰。

诚实边界:做什么,不做什么

  • 做:识别订阅取消 / 到期 / 组织禁用这类「整个号死了」的情形;切号、拉黑、告警、评审重排、机器人叫醒、两个隔离演练场景、回归测试。
  • 不做:401(钥匙过期)仍走原来的「读不到」告警,不当死号;额度用完后机器人的叫醒(FLY-2109)不在本单,但本单的叫醒机制放开一个过滤条件即可复用。
  • 不改:founder 专属边界(merge / ship / restart);/review-requests 接口;runner 合同;Codex 侧账号;CLAUDE.md。
  • 已知残余:Bridge 的 pane 扫描每 60 分钟一轮,所以「机器人 pane 上的 403」是慢路径;快路径是评审任务的 403(秒级)。如果一段时间内既没有评审任务也没有守护程序的 poll,最长要等一个 poll 周期(20 分钟)。
  • 叫醒的总开关关掉时:那一次切号的叫醒动作记为「已跳过」,之后再打开不会补发(那时机器人的状态已不可知);评审重排的开关关掉则是「等下次再试」,不会丢。
  • 成环防护:切过去的新号也是死号时,评审任务会再停靠一次但不会被同一次切号重排(按时间戳隔开),守护程序下个探活会再切;所有「每次切号一次」都靠主键幂等,不靠先查后写。
  • founder 手动 /login 的情形(9-8 当晚的实际路径):守护程序会承认这次切号并记 lastSwitch,评审任务会自动重排;但机器人叫醒只在「因死号切号」时发,手动切号后的活体仍要 Lead 手工 send(归 FLY-2109)。
  • 回滚:守护程序改动 revert 后走独立 updater 窗口重启;Bridge 侧两个总开关(评审重排复用 FLY-2177 的,叫醒新增一个)可在运行中关掉;新字段对旧代码透明。
  • 本节点只出设计;实现、QA、合入、部署由后续节点与 Lead 执行,merge ≠ 生效。
