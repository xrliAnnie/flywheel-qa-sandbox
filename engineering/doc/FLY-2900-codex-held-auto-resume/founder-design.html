FLY-2900 · 设计说明

Codex 撞墙只换号，不换人。

额度待命 · 同一执行体接回原对话 · 全满才让 Claude 接手 · 每节都能留言

01 / 一句话

Codex 撞额度墙时不再判「死亡」，而是进入额度待命；一旦换到有额度的号、或原号到点回血，系统用同一个执行体起新进程接回原来的对话继续干——不用等人。

执行体（execution）＝某个节点的一次具体运行，有固定编号；对话（thread）＝Codex 这次工作的完整上下文。今天撞墙后系统会「盲换」3 个新执行体继续撞，然后把整单挂起等 Lead 手动放行：近 14 天浪费约 208 单×节点小时，其中约 186 小时是挂着等人。

02 / 为什么 Claude 很少出这事，Codex 却会

Claude 那边的额度监控在撞墙之前就切号，正在跑的会话通过系统钥匙串自动拿到新凭据；卡在「额度用完」提示上的窗口会被自动发一句「continue」唤醒。所以 14 天里 Claude 0 次因额度失败、0 次挂起。

Codex 不一样：正在跑的进程把旧号的登录凭据缓存在内存里，换了凭据文件它也看不到（已实测）。所以 Codex 版的「continue」必须是：新开一个进程（读到新号），用同一个执行体编号接回原对话。这正是本设计的主线，按 Lead 转述的你 9-16 原则「撞额度只切号，不换体」。

另一个关键发现：自动切号机器（FLY-2465）早就写好了，但 14 天里一次都没真正生效——129 次撞墙全被转成「人工处理」。昨晚 FLY-2830 刚修好它能不能启动的问题，本单补上它缺的「放行条件」和「续跑」。

03 / 撞墙之后怎么走

放行证据有两种，任一出现即可续跑：自动切号成功；或撞墙之后发出的额度查询确认当前号有额度——原号到点回血、有人手动切了号，都属于这一种（用只读方式查额度，不消耗额度、不动登录凭据）。判断「续上了」的标准是：新进程在继续回合里真正产出了第一条内容（说明服务端接受了原对话），光是回合开始不算。因非额度原因续跑失败两次，或所有号都满且最早恢复要超过 30 分钟（开关开着），才走「兜底」；拉起时新号也撞墙只回到待命。

04 / 今天撞墙后会卡在哪

盲换耗尽后挂起（31 次）
引擎连续换 3 个新执行体，每个一启动就撞墙，然后整单挂起。只能 Lead 手动放行，而且手动放行这扇门常常不出新执行体。
替身没起来就挂起（40 次）
撞墙时 Codex 正在改文件，工作目录里有未提交的改动；新执行体拒绝接手「脏」目录，于是挂起。
暂停了却永远不解除
原号到点回血不算数（系统只认「换号」）；有人手动换了号也不认账。
正在用的号从来不查额度
撞墙的恰恰是当前在用的号，系统把它标成「占用中」跳过不读，于是既看不到它回血，也判断不出「所有号都满了」。

05 / 一个待命执行体的一生

「放行证据」（permit）是一条记录：某个账号的某一代确实有额度。撞墙和每次查额度都从同一个只增不减的计数器取编号：只有「编号比撞墙晚」的额度读数才能证明回血，放行证据只对它发放之前的撞墙有效，之后这个号若又撞墙，证据立即作废——不靠钟表先后，避免同一毫秒或时钟回拨出错。同一执行体续跑后再撞墙，可以再次待命；24 小时内同一节点最多 6 次，防止「撞墙—续跑—撞墙」死循环。

06 / 数据怎么存

一张表管「谁在待命」，是唯一真源：所有巡检程序只问一个问题「它是不是在额度待命」，都不会把它当成死掉的进程收掉。另有放行证据表、只增不改的审计表，以及兜底时写下的派发要求（Claude 还是 Codex）。

07 / 兜底：什么时候换新执行体、什么时候交给 Claude

换新 Codex 执行体：有额度了，但原对话接不回来（同一放行证据下，因非额度原因失败两次）。如果拉起时新号也撞墙了，不算失败、也不换体，回到待命等下一次放行。交给 Claude：所有 Codex 号都满、最早恢复要超过 30 分钟、开关开着（默认开，Lead 已定）。30 分钟内会恢复就等。

兜底分两步走：先把新执行体安排好、原执行体原样保留；等新执行体真正启动成功，才让原执行体退场。如果新执行体被任何规则拒绝，就退回原样，原会话之后照样可以续跑，不会出现「旧的已退、新的又起不来」的死角。

兜底前，如果工作目录有未提交的改动，系统先把它们打成一个「WIP 提交」（Work In Progress，进行中的工作快照）留在分支上，新执行体在提交历史里直接看到，不丢任何东西；已推送的提交和进度账本照常带上。

改派 Claude 走和平时派单完全同一条路，并留记录：额度页能看到哪些节点因额度改派；模型效果统计把这些节点单独标为「额度兜底」，不混进 Codex 或 Claude 的正常样本。Codex 恢复后，已经在 Claude 上跑的节点跑完为止，不中途切回。若改派会让同一家模型审查自己写的代码（同厂商互评规则），就不改派，继续排队并在额度页标出。

09 / 为什么这样选，没选什么

选：同一执行体接回原对话。保住上下文、不浪费重新读代码的 token；执行体编号不变，原对话里记的身份信息全都对得上。

不选只靠「换新 run 当替身」：丢上下文，还会丢掉同一单前面节点的产出。不选「给正在跑的进程热换凭据」或「给原窗口发 continue」：实测旧进程不认新凭据。不选借用 FLY-2808 的「退下待命」表：它绑定「阶段做完」的语义且默认关，硬套会改变节点完成时的行为。不选用真请求去试探在用号：会让共享的登录凭据互相作废；只读查额度足够，真正的验证就是续跑本身，失败有兜底。

10 / 怎样证明修好了

本机台架（真实路由与数据库、合成的 Codex 协议程序）：6 个任务同时撞墙 → 0 次盲换、0 次挂起 → 切号成功后 3 分钟内全部用原执行体续上；原号回血后 5 分钟内续上；手动切号被认账；全满且开关开 → Claude 接手、开关关 → 排队并在额度页标出；原对话接不回 → 换新 Codex 执行体、不计入盲换次数；人工终止后不再自动动作；Bridge 重启后不重复派。

设计阶段已用真 Codex 做了小实验（隔离目录、不碰共享登录、不切全局号）：在已满的 personal2 号上让对话撞墙，然后换到有额度的 shopping 号新开进程，接回同一对话、重新激活、继续回答——成功，而且模型还记得第一条消息的内容。还没证明的一点：如果 A 号上已经做了大量推理再撞墙，换到 B 号能否无缝接上；这条列为正式演练必证项，不成立就自动换新执行体并记下原因。

11 / 诚实边界

做：Codex 执行节点撞墙后的待命、两种放行证据、同执行体续跑、两种兜底、审计、thread 一句话、额度页。人工一旦介入（关闭、挂起、终止、取消、ship），系统立即停手，不再自动拉起或换体。

不做：OpenAI 服务端宕机（不是额度问题，另开单）；Codex 代码审查进程（已有自己的等待重跑机制）；上线前已经挂起的 2 个历史 run（它们的执行体已判死，自动复活属于另一类事故，交 Lead）；「按模型效果×剩余额度动态派单」的推荐器（FLY-2895，以后接管同一个派发步骤）。

这是设计交付：本轮没有改产品代码、没有部署或合并；实现和独立验证尚未完成。
