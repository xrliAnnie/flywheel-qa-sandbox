FLY-2891 · 设计稿 · 2026-09-25 · 基于 plan.md v4（Codex 评审已通过）

一句话

Claude 写的方案和代码，在本机让 Codex 评审时，每评完一轮就往 Bridge 记一条（第几轮、结论、Codex 自己记下的真实模型）；评审门放行前核对「真实模型 = 要求模型」，用错模型的通过一律拒收；报表用和 Astra 线同一套算法，算出 Claude 线的首轮通过率和平均轮数。评审本身不改、不变慢。

Bridge：Flywheel 的中枢服务，所有「谁在干什么、结果如何」的正式记录都存在它的数据库里。 评审门：设计或代码进入下一步前必须通过的一道自动检查（命令 await-codex-gate）。 runner：在独立工作目录里干活的 AI 执行体。

顺带落地 Lead 追加的两件：④ 分流配置里每个档可以写思考档位（effort）；⑤ 按你 15:15 的决定，删除「Sol 档额度满自动改走 Opus」的保护，额度满就排队等。

为什么 Astra 线有数据、Claude 线没有

你问得对：根子就是「评审在哪儿跑、结果记在哪儿」。

  • Astra 线（Codex 写方案）：评审由 Bridge 亲自拉起，每一轮都在 Bridge 数据库 codex_review_job 里留一行。
  • Claude 线（Claude 写方案）：评审由 runner 在自己的工作目录里调本机 Codex 跑，结论只写进目录里的一个 JSON 文件；Bridge 只在代码评审最终通过时收到一条，设计评审一条都不收。目录一删，轮数就没了。

同一个根上还长出第二个问题：评审门从不看「是哪个模型评的」。FLY-2830 / 2882 / 2883 / 2884 四次，都是 runner 还没收到「请用 gpt-6-astra」的通知就用本机默认的 gpt-5.6-sol 评完了，门照样放行。

manifest（评审请求单）：Bridge 发给 runner 的一张单子，写着审哪份文件、要用哪个模型；以前经信箱送达，常常比 runner 开评晚到。

修好之后怎么走

  1. 先拿单子再开评：runner 登记评审请求时，Bridge 当场把「要用 gpt-6-astra / xhigh」回给它，不再等信箱。
  2. 每轮一条：每评完一轮，runner 跑一条轻命令 review-round，从 Codex 的会话记录里读出这一回合真正用的模型，连同结论一起写给 Bridge。
  3. 送不到不卡人：Bridge 暂时连不上就在本机落一个小文件，Bridge 恢复后自己的巡检来收；runner 早就结束、目录删了也不丢。
  4. 门口核模型：门按回合编号核真实模型；和要求不一致就拒，原因直接写「要求 gpt-6-astra/xhigh，实际 gpt-5.6-sol/xhigh」。
  5. 记一条过门记录：写明「总共评了几轮」，报表用它对账，判断逐轮数据是否齐全。

Codex 会话记录（rollout）：Codex 自己在本机写的流水账，每个回合都记着当时用的模型和思考档位；我们读它，而不是相信 runner 自己报的模型。 effort（思考档位）：同一个模型想得多深，如 high、xhigh。

数据怎么存

  • 逐轮记录（新表）：一轮 = Codex 的一个回合，用「执行体 + 评审类型 + 回合编号」唯一确定；重复上报不会多出行，内容冲突会被拒绝、原记录不被改写。
  • 过门记录（新表）：门接受的是哪个回合、总共几轮、核实过的真实模型。
  • Astra 线沿用已有的每轮一行，只加一列「评完时间」，让两条线都按「评完那一刻」排时间。
  • 报表两条线走同一个计算函数：首轮通过率、平均通过轮数、数据是否齐全。

首轮通过率和轮数怎么算（两条线同一口径）

指标定义
一轮评审者对作者产物给出的一次原始结论（Astra 线不用「按严重度折算后」的结论，保证两边可比）
首轮通过时间上第一轮就是 APPROVED
通过轮数到第一次 APPROVED 为止评了几轮
数据齐全Claude 线：过门记录里的「总轮数」和实际收到的轮数对得上；Astra 线：Bridge 自己跑的，每轮都有结论

关键数据不齐时，这个 issue 的首轮通过和轮数记为「未知」，绝不当成通过；报表会单独列出有多少个「未知」，你一眼能看出样本够不够。

④ 分流档位 + ⑤ 删除额度降级

  • ④ 分流配置每个档可写 effort：写了按它跑、不写继承节点默认、写了模型不支持的档位直接拒绝并说明原因；design-model-split.mjs show 会显示每个档实际生效的档位。「Astra 在设计/实现一律 high」由 Lead 在配置里写，代码不写死。
  • ⑤ 删掉「Sol 档额度满自动改走 Opus」：以后 Codex 额度满就排队等恢复。已经降级过的历史记录和正在跑的已降级任务照常可读、可唤醒，不受影响。按额度动态调比例是另一张单。

分流（model split）：按 issue 把一个节点随机分给不同模型跑，用来比较模型好坏；每个选项叫一个「档（arm）」。

取舍与被否决的方案

方案结论原因
每轮由 runner 调一条轻命令写回采用不动评审本身；单次最多约 2 秒，Bridge 在线时不到 0.3 秒
我们自己包一层去代跑 Codex 评审否决依赖第三方插件的内部格式，插件一升级就坏；也改变了评审方式
只在过门时一次性上传全部历史否决没过门就放弃的评审全丢，而且仍是自报
相信结果文件里自报的模型否决四次事故都是「以为自己用对了」，自报等于没核
送不到就让 runner 下次再补发否决最后一轮送不到时 runner 已结束，没人再补；改为 Bridge 巡检代收
把降级扩到所有 Codex 档撤回你 15:15 决定整个拿掉，改由后续「按额度动态调比例」解决

诚实边界：做什么、不做什么

做到：每轮都有记录（送不到会自动补收）；错模型的通过过不了门；报表能算出两条线可比的首轮通过率和轮数；④⑤ 按 Lead 口径落地。

不做 / 做不到：

  • 不回填历史：2830 / 2882 / 2883 / 2884 等旧单的轮数仍拿不到。
  • 不防有意造假：runner 若故意伪造 Codex 会话记录，仍能骗过门；本设计针对的是「无意用了默认模型」。
  • runner 如果漏报某一轮，这个 issue 在报表里会显示「未知」而不是被猜出来——数据会变少，但不会变假。
  • 中间轮记的「审的是哪一版」是上报那一刻的版本；只有最终通过那一轮的版本由门独立核实。
  • 用户级评审技能文件在仓库外，本次不改；上线后由 Lead 按计划里的补丁手动更新（不更新也能用，Bridge 指令已写明要求）。
  • 上线时正在过门的旧进程会被拒一次并提示升级，重跑即可；建议 Lead 挑没有在飞设计/实现门的时间合并。
