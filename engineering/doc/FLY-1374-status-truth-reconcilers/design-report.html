📡 状态真相双对账器

FLY-1374 · 设计方案(Codex 设计评审 9 轮通过)· 2026-07-24

① 一句话总结

让 Discord 上看到的状态重新可信:给系统加两个「循环核对真相」的对账器 —— 每 3 分钟把进程的真实死活核对进数据库(主因,占七成),数据库一变、Discord 标题自动跟着改(这半套 7 月 6 日已上线,本单补洞)。原则:先当审计员,再当执法者 —— 新机制先只记账不动手,真机跑出「零误判」的证据后才开启自动纠正。

背景:你 7/18 深夜说「Discord 显示的状态经常错/停格,我已经不敢信了」。深诊定位:数据库里死进程还标着"运行中"、活进程被标"失联",显示层只是忠实渲染了这份错误的账本。

② 核心流程:两个对账循环

对账器 1「进程现实 → 数据库」(新建,主活)

每 3 分钟搭现有巡检的车(零新定时器),把全部未完结会话过一遍
直连查证绕开中介层,直接问 tmux:窗口还在吗?进程还活吗?窗口真的是它的吗?(每个会话出生时打上专属身份标记)
身份错位?先找人再定死窗口对不上 ≠ 死了。全局反查:活在别的窗口 → 修映射;确实全网找不到 + 仪器自检正常 → 才算「死亡证明」
↓ 按判定分派
确认死了数据库落终态(完整收尾:两库同步+审计留痕),Discord 标题自动跟上 → ≤5 分钟
其实活着被误标"失联"的 → 恢复认领;数据库行丢了的 → 补回来
拿不准一律不动手,只记录。宁可晚修 3 分钟,绝不误杀活会话

对账器 2「数据库 → Discord 显示」(已在生产,补洞)

已有底子7/6 上线的统一渲染器:每 3 分钟幂等重渲染,标题不对就改、对就跳过(零浪费)
本单补的洞「已否决/已搁置」等终态还挂着进行中标记 → 补全;告警对完结会话反复刷屏 → 每个会话每类事只报一次;重启把活单 thread 锁死 → 修判定 + 自动解锁

附带根治:「复用会话」病族(7/23 晚三案例)

病根停驻的会话被派新活时,系统只发"接力棒",五步开工手续一步都不补 → 领不到任务、写不了进度、收不到信
→
修法唤醒前先把手续补齐(账本行、状态、信箱),全部就绪才交接力棒;中途断电也能从断点续上,绝不出现"拿着棒却开不了工"

④ 关键取舍与被否掉的方案

  • 审计先行,不首发就执法 —— 否掉了「上线即自动纠正」:检测这种东西,误判的代价是杀活会话,必须先用真机证据自证清白(受控杀真会话的正例 + 各种干扰负例都要过)。
  • 补洞不重建 —— 否掉了「重写显示层」:审计发现显示对账器 7/6 就在生产跑着,错在输入(数据库本身是错的)。重建=重复建设。
  • 委托不抢活 —— 否掉了「对账器自己收割一切」:死窗收割仍归现有唯一执法者,对账器只递证据+催它提前跑,结构上杜绝两个执法者打架。
  • worktree 不当身份证 —— 评审抓出:三段式的设计/实现/QA 共用一个工作目录,拿目录认人会把兄弟会话认成本人。改用出生时打的专属标记。
  • 与并行两单划清边界 —— 批准投递断路(FLY-1448)、cmux 层(FLY-1446)一概不碰;等待批准中的会话本单只报不动。
  • 收据双开只降级为检测 —— 评审证实两套收据的证明合同不同,盲目联动会吞掉你的指令,结算方案另开单细做。

Codex 设计评审 9 轮:R1-R8 共 33 项反馈全部采纳(零拒绝),多数是「防误杀」的合同精度 —— 死亡证明怎么才算数、断电各切口怎么续、并发注册谁赢。第 9 轮 APPROVED,留 3 条非阻塞实施注记。

⑤ 诚实边界 — 这个设计不做什么

  • 默认档(audit)不满足「5 分钟内自动纠正」 —— 这是刻意的:自动纠正要等真机 soak 证据达标后才开(PR-3)。验收会在开启后的环境里做。
  • 已完结 thread 被人改名不自愈 —— 关单的 thread 没人看,为它常年烧 API 不值。活跃单的标题改错,下一轮自动纠正。
  • 批准送达链(你批了没生效)不在本单 —— 那是 FLY-1448 的急修,两单并行,边界表已写死防撞车。
  • 老会话(没有身份标记的存量)永远不会被自动判死 —— 只进「身份不明」清单,人工处置;清单不清零,不许宣称「零脱节」。
  • 守卫钝化先取当晚真实被拦样本定位执法点再改 —— 不凭 issue 描述猜着修。
