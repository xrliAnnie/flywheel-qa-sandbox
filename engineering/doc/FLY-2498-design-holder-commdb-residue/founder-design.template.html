FLY-2498 · 设计体死了，它在通信名册里的那一行却永远「活着」

Issue FLY-2498 · 设计节点 · 2026-09-11 · 文档：engineering/doc/FLY-2498-design-holder-commdb-residue/（exploration / research / plan）

1. 一句话

Codex 车道的设计体做完设计交接之后，按合同会继续活着停驻（等 ship 前的设计改动）；等它真的被关掉（Lead 用 close-tmux（Bridge 的「关掉这个 runner 终端窗口」接口）杀窗），没有任何代码给它在 CommDB（各 runner 的通信名册，Lead 巡检靠它知道「谁是我名下的」）里的注册行盖终态戳，于是这一行带着一个已经不存在的窗口一直显示「running」，巡检每一轮都报「MISSING_PANE」（名册里有它、终端里却找不到它的窗口）。再往下挖一层：系统里其实已经有一个专收这种行的每小时清扫（FLY-817），它每小时都扫到了这五具，但全部被「体自称 parked（停驻）」的保护性否决拦住 —— 那个否决只认 Claude 体的证据，对 Codex 体没有任何证据能推翻它。本设计在证明它已死的两处（关窗当场、每小时清扫）用既有的「精确目标封行」原语把这一行删掉：关窗当场直接封；清扫处给 parked 否决补一种「执行缺席」的推翻证据。不动交接、不动巡检、不动适配器、不新增数据库方法。

issue 说的病根「交接只翻 StateStore，不给 CommDB 行写终态」 真库核出来的病根交接时不该写终态 —— 体还活着停驻，CommDB 的 running 是它接收「设计改动唤醒」的门栓。真正没人做的事是：体死了（关窗 + daemon 收掉）没人封账；从不 ship 的 issue（FLY-2107 已 terminated）就永久残留 影响面issue 点名 6 具，今天（09-11 07:24Z）又有 4 具同形体被关窗，正在成为下一批告警；Claude 车道 ~50 具设计体一具都没这个病（它的适配器自己会写终态）

3. 数据 / 结构模型：两本账、一个名册、一个已死的进程

病灶只在 CommDB 的一行；它身上还挂着一个「活进程才该有」的 parked 声明 —— 正是这个声明让每小时清扫不敢删它。清扫的顾虑是合理的：声明 + 窗口名找不到，也可能是「窗口改了名、进程还活着」（FLY-1319 事故）。所以推翻它的证据必须不看窗口名，直接问「这个执行在这台机器上还存在吗」：Codex daemon 在不在、有没有任何窗口带着它的执行标记、宿主上有没有进程引用它。三者都没有，才算死。

为什么交接时不能写终态

消费者CommDB running + keep_alive=1 对它意味着
phase 唤醒（设计改动 / rework）只投给 running 且 keep_alive 的行（assertPhaseKeepAliveSessionRunning）；改了就把活着的持有者踢出路由
Blueprint 给设计体的合同「complete 之后不要退出，park，你是设计上下文持有者直到 ship；Bridge 在 ship 后关你」
Lead 巡检停驻活体出现在 STEP 2 为 STALLED_60M，按合同不催 —— 这是已知噪音，不是本单
FLY-1204 停驻体回收只回收活着的进程（探针说死就跳过）—— 所以它也收不到本案的死行

4. 修法：证明它死了，就用既有的「精确目标封行」删掉这一行

两条入口共用一个既有 CommDB 原语 finalizePaneLossResidue：在一个事务里核「目标窗口没变、它不是 TURN（同一 issue 上「谁有权写共享分支」的令牌）持有者」，然后退掉它未回答的 ask / gate、删掉注册行；任何漂移零写入。CommDB 注册行离场的唯一方式本来就是删除，本设计不发明新的状态。

两条入口各自的「死亡证明」

  • 路径 A · close-tmux 当场：kill-window 成功（窗口本来不在也算成功）且 Codex daemon 收割结果是 absent / reaped（非 Codex 体则不需要）且 StateStore 是可删终态。daemon 残留或无法核实 ⇒ 不删，只记一条 skipped 事件（已有告警路径会报）。
  • 路径 B · FLY-817 每小时 / boot 清扫：它原有的三道门（StateStore 终态、窗口名探针 dead、非 TURN 持有者）不变；到「体自称 parked」这一步，除了原有的 Claude 代际证据，新增一种推翻证据：执行缺席探针说 dead（daemon 缺席 且 没有任何窗口带它的执行标记 且 宿主无进程）。alive / unknown / 探针报错 ⇒ 维持否决。今天残留的 1492b1f6 与 4 具新体都由部署后第一次 boot 清扫收敛。

改动范围（4 个源文件，不新增数据库方法）

  • teamlead/bridge/run-quiescence.ts：新探针 probeExecutionAbsenceBeyondTarget（强制走「不看注册窗口名」的分支，复用引擎判死体的三重缺席证据）。
  • teamlead/bridge/commdb-fsm-reconcile.ts：parked 分支多一个可注入的 executionAbsence 依赖与 parkedOverridden 计数；不注入时逐字节不变（现有 5 条 FLY-1329 否决测试原样绿是门槛）。
  • teamlead/bridge/commdb-session-prune.ts：两个小导出 —— close-tmux 的纯决策函数、finalizePaneLossResidue 的薄包装。
  • teamlead/bridge/plugin.ts：close-tmux 端点接住 daemon 收割结果、杀窗后按决策封行并审计；两处 reconcile 接线注入新探针。
  • 不改：巡检脚本与 owner index、交接路径、Codex / Claude 适配器、close-runner、FLY-1204 回收、FLY-2302 定点封账、FLY-1329 否决本身、表结构。无 flag、无迁移；revert 即回到旧行为，已删的行是既有原语的合法结果。

5. 关键取舍与被否决的方案

方案结论原因
选A. close-tmux 杀窗成功后当场封行采纳（主修）本案与今天 4 具的真实触发面就是它；与 close-runner「杀窗即封账」对齐；复用既有原语
选B. 给 FLY-817 清扫的 parked 否决补「执行缺席」推翻证据采纳日志证明残留就卡在这一行代码；证据不看窗口名，FLY-1319 那种「改名的活体」仍受保护；每小时自动收存量
否B′. 清扫新增「盖戳相」+ 新 CommDB 原语把 running 改成 completed（本单第一稿）否决与 FLY-817 重复一套判定；盖了戳仍被 parked 否决挡在终态清扫外，还要再加清声明 —— 两套机制解一个问题
否C. 交接路径给 CommDB 写 completed（issue 建议之一）否决交接后体按合同活着停驻，running 是唤醒门栓；盖戳会把活体踢出路由
否D. 巡检 owner index 与 StateStore 取交集（issue 建议之二）否决FLY-2302 Lead 裁定的方向守卫：让死体拿到终结，不给巡检加豁免；否则把假阳性换成盲区
不采E. close-tmux 直接走 close-runner 那种无守卫的全量删行不采纳close-tmux 的调用方比 close-runner 杂；少了「目标没变、不是 TURN 持有者」两道守卫会把以前修掉的洞再打开。方案 A 用带守卫的同一原语，效果相同、否决齐全
另开F. 修 close-runner 的「controller 心跳陈旧」拒绝另开 issue那个 fail-closed 有理由（杀活 controller 的窗会孤儿化 daemon）；它是 Lead 退而用 close-tmux 的原因，但不是残留的原因
否G. Bridge 重启时再收养 completed 的停驻体否决「再收养终态」= 复活死者，代码里明确排除

6. 诚实边界：这个设计做什么、不做什么、现在卡在哪

做

  • close-tmux 关掉一个 StateStore 已终态、且执行已证明死亡的体 ⇒ CommDB 行 ≤1 s 内被删；巡检 STEP 1 不再对它报 MISSING_PANE。
  • 存量（1492b1f6 与今天 4 具）由部署后第一次 boot 清扫按新证据删行，日志出现 prune_parked_overridden_execution_absent。
  • 活着停驻的设计体（窗口在、daemon 在）经过任意多轮清扫仍 running、声明仍在、唤醒仍可达 —— 阴性对照，写进验收 A5；FLY-1319 那种「窗口改名的活体」也仍受保护（A6）。
  • 每次封行或跳过都有审计（commdb_ask_disposed / commdb_finalize_skipped），QA 可反证没有静默跳过。

不做 / 不承诺

  • StateStore 非终态但窗口已死的体（如旧车道 design_done 持有者被关窗）不封行，留给 FLY-1204 告警 + close_runner --done（L4）；failed / blocked 的体也不由 close-tmux 封行，交既有的每小时 harvest（L5）。
  • 不修 close-runner 的「controller 心跳陈旧」拒绝（L1）、不修 Codex 孤儿 reaper 每 5 分钟一条的 identity-mismatch 噪音（L2）、不碰两条 2026-08 的 :pending 残留行（L3）。
  • 没被 Lead 主动关窗、自己死掉的体，从死到封行最长 1 小时（清扫节奏，L7）。
  • Linear MCP 401，issue 正文只来自派单；34 次计数未从 Linear 复核。
