FLY-2498 · 设计体死了，它在通信名册里的那一行却永远「活着」

Issue FLY-2498 · 设计节点 · 2026-09-11 · 文档：engineering/doc/FLY-2498-design-holder-commdb-residue/（exploration / research / plan）

1. 一句话

Codex 车道的设计体做完设计交接之后，按合同会继续活着停驻（等 ship 前的设计改动）；等它真的被关掉（Lead 用 close-tmux（Bridge 的「关掉这个 runner 终端窗口」接口）杀窗），没有任何代码给它在 CommDB（各 runner 的通信名册，Lead 巡检靠它知道「谁是我名下的」）里的注册行盖终态戳，于是这一行带着一个已经不存在的窗口一直显示「running」，巡检每一轮都报「MISSING_PANE」（名册里有它、终端里却找不到它的窗口）。本设计在证明它已死的两处（关窗当场、每小时清扫）给这一行盖上终态戳，让它退出名册、再由既有清扫删掉；不动交接、不动巡检、不动适配器。

issue 说的病根「交接只翻 StateStore，不给 CommDB 行写终态」 真库核出来的病根交接时不该写终态 —— 体还活着停驻，CommDB 的 running 是它接收「设计改动唤醒」的门栓。真正没人做的事是：体死了（关窗 + daemon 收掉）没人封账；从不 ship 的 issue（FLY-2107 已 terminated）就永久残留 影响面issue 点名 6 具，今天（09-11 07:24Z）又有 4 具同形体被关窗，正在成为下一批告警；Claude 车道 ~50 具设计体一具都没这个病（它的适配器自己会写终态）

3. 数据 / 结构模型：两本账、一个名册、一个已死的进程

病灶只在 CommDB 的一行；它身上还挂着两样「活进程才该有」的东西：parked 声明与 pending 的 doorbell（Bridge 叫醒 runner 的门铃记录）。盖戳时要一起处理，否则既有清扫会因为「它说自己 parked」而永远不删。

为什么交接时不能写终态

消费者CommDB running + keep_alive=1 对它意味着
phase 唤醒（设计改动 / rework）只投给 running 且 keep_alive 的行（assertPhaseKeepAliveSessionRunning）；改了就把活着的持有者踢出路由
Blueprint 给设计体的合同「complete 之后不要退出，park，你是设计上下文持有者直到 ship；Bridge 在 ship 后关你」
Lead 巡检停驻活体出现在 STEP 2 为 STALLED_60M，按合同不催 —— 这是已知噪音，不是本单
FLY-1204 停驻体回收只回收活着的进程（探针说死就跳过）—— 所以它也收不到本案的死行

4. 修法：证明它死了，就给这一行盖终态戳

两条入口共用一个 CommDB 原语 markDeadSessionTerminal：精确目标 CAS（compare-and-set：只有行还是「running、目标窗口一致、没盖过戳」时才写，任何漂移零写入），同一事务把 doorbell 置 finished、清掉 parked 声明。终态值按 StateStore 状态映射：failed/blocked 同名，其余一律 completed。

两条入口各自的「死亡证明」

  • 路径 A · close-tmux 当场：kill-window 成功（窗口本来不在也算成功）且 Codex daemon 收割结果是 absent / reaped（非 Codex 体则不需要）。daemon 残留或无法核实 ⇒ 不盖，只记一条 skipped 事件（已有告警路径会报）。
  • 路径 B · 每小时 / boot 清扫：对 CommDB 里每条 running 行，先看 StateStore 是否终态（不是就不探进程、不盖），再用引擎回滚死体时用的同一个家族感知探针（Codex 先查 daemon，再查 tmux / 发现 / 宿主）说 dead 才盖。今天残留的 1492b1f6 与 4 具新体都由部署后第一次 boot 清扫收敛，下一轮（≤1h）删行。

改动范围（4 个源文件）

  • flywheel-comm/db.ts：新方法 markDeadSessionTerminal（一个 IMMEDIATE 事务，返回 stamped / no_row / pending_target / target_changed / not_running）。
  • teamlead/bridge/commdb-terminal-stamp.ts（新）：状态映射 + close-tmux 用的纯函数，永不抛，每次恰好记一条审计事件。
  • teamlead/bridge/plugin.ts：close-tmux 端点杀窗后调用上面的纯函数；清扫处注入 StateStore 状态与探针两个依赖。
  • teamlead/bridge/commdb-session-prune.ts：清扫开头加「盖戳相」；两个依赖不注入时逐字节不变（现有 8 组清扫测试原样绿是门槛）。
  • 不改：巡检脚本与 owner index、交接路径、Codex / Claude 适配器、close-runner、FLY-1204 回收、FLY-2302 定点封账、表结构。无 flag、无迁移；revert 即回到旧行为，已盖的行是合法终态行。

5. 关键取舍与被否决的方案

方案结论原因
选A. close-tmux 杀窗成功后当场盖戳采纳（主修）本案与今天 4 具的真实触发面就是它；与 close-runner「杀窗即封账」对齐；最小改动
选B. 清扫加盖戳相做收敛网采纳收存量、Bridge 重启丢适配器、手工杀窗等所有「死了没盖戳」的形状；复用 FLY-2302 的清扫框架与审计
否C. 交接路径给 CommDB 写 completed（issue 建议之一）否决交接后体按合同活着停驻，running 是唤醒门栓；盖戳会把活体踢出路由
否D. 巡检 owner index 与 StateStore 取交集（issue 建议之二）否决FLY-2302 Lead 裁定的方向守卫：让死体拿到终结，不给巡检加豁免；否则把假阳性换成盲区
不采E. close-tmux 直接走 close-runner 的全量删行不采纳close-tmux 是资源清道夫，不是生命周期终结；退 ask / gate 是 close-runner 的语义，ship 收尾还要靠它。盖戳保留身份，让各自完成本职
另开F. 修 close-runner 的「controller 心跳陈旧」拒绝另开 issue那个 fail-closed 有理由（杀活 controller 的窗会孤儿化 daemon）；它是 Lead 退而用 close-tmux 的原因，但不是残留的原因
否G. Bridge 重启时再收养 completed 的停驻体否决「再收养终态」= 复活死者，代码里明确排除

6. 诚实边界：这个设计做什么、不做什么、现在卡在哪

做

  • close-tmux 关掉一个 StateStore 已终态、且执行已证明死亡的体 ⇒ CommDB 行 ≤1 s 内 completed + ended_at，声明清空；巡检 STEP 1 不再对它报 MISSING_PANE。
  • 存量（1492b1f6 与今天 4 具）由部署后第一次 boot 清扫盖戳，下一轮删行。
  • 活着停驻的设计体（窗口在、daemon 在）经过任意多轮清扫仍 running、声明仍在、唤醒仍可达 —— 这是阴性对照，写进验收 A5。
  • 每次盖戳或跳过都有 session_events 审计（commdb_terminal_stamped / commdb_terminal_stamp_skipped），QA 可反证没有静默跳过。

不做 / 不承诺

  • StateStore 非终态但窗口已死的体（如旧车道 design_done 持有者被关窗）不盖戳，留给 FLY-1204 告警 + close_runner --done。
  • 不修 close-runner 的「controller 心跳陈旧」拒绝（L1）、不修 Codex 孤儿 reaper 每 5 分钟一条的 identity-mismatch 噪音（L2）、不碰两条 2026-08 的 :pending 残留行（L3）。
  • 盖戳到删行之间（≤1h）runner_terminal_list 会以 dead-class 显示该行，与 Claude 体现状一致（L5）。
  • Linear MCP 401，issue 正文只来自派单；34 次计数未从 Linear 复核。
