# Design Review — FLY-2190 plan.md (Round 2)

Date: 2026-08-30
Author: Codex
Status: CHANGES REQUESTED

## Summary

R2 is materially better and the S3 downgrade is now honest: it no longer presents the existing helper as a rolling transaction or publishes a rollback sequence that the repository cannot execute. P1–P6 preserve the important R1 findings, but the plan is not yet safe to hand off unchanged because S1's deploy safety is conditional on tmux link state, §1.5 misses a load-bearing transitive overlap, S2's registry/mount contract cannot enforce what it claims, and S3 still lacks one architecture-provenance blocker.

## What's Good (Keep)

- The two R1 overclaims are retracted explicitly. Keeping S3 as an ordering constraint plus unresolved design work is the correct response; an incomplete runbook would be worse than no runbook.
- P1–P6 accurately retain the transaction, non-Lead-server, mixed-fleet rollback, mixed-version command gate, runtime-client convergence, and consumer-matrix problems. In particular, P3 correctly derives rollback direction from the observed bad edge rather than treating `brew unlink` as harmless.
- The compatibility wording is now evidence-sized: 3.7c-client/3.5a-server handshake plus `list-sessions`, not “works normally.” P4 correctly keeps the production command surface unproven.
- The source accounting corrections are sound: 10 production/operator sites plus one QA parity site, `scripts/com.flywheel.log-janitor.plist` in the native-first set, and both stale comments called out.
- The plan now describes the restart guard's actual semantics, reuses `extract_tmux_image`, and requires launch identity/socket/Lead/sidebar receipts rather than a fragile `lsof | head -1` check.
- §2.1 correctly retracts the provisioning claim. `.github/workflows/ci.yml:607` really enumerates `check-global-path-hygiene.test.sh`; `package-onboard.sh:100` is only packaging, while `converge-flywheel-bin.sh:653-658` really invokes the existing global-state scanner.

## Issues & Recommendations

1. **BLOCKER — S1 is independently mergeable, but not independently deployable in both link states.** §1.6 says S1 can land independently while also admitting that, if `/opt/homebrew/bin/tmux` is linked, the next naturally restarted Lead/Bridge/helper enters the unverified 3.7c-client/3.5a-server production-command state. “S1 does not restart anything” does not make that state safe; launchd or an operator can restart a service after deployment. The host is green today (`/opt/homebrew/bin/tmux` is currently absent and `/usr/local/bin/tmux` is 3.5a), but that is driftable host state, not a plan invariant. **Fix:** distinguish merge from deploy and add a fail-closed, time-bound pre-deploy receipt: the ARM tmux link must be absent/unresolvable. If it is present, S1 may not be deployed or allowed to reach a service restart until P4 passes, or until a founder-authorized unlink restores the old-client state. Put this gate in A4/A6. With that condition, S1+S2 can proceed while S3 remains parked.

2. **BLOCKER — §1.5's “only four” consumer inventory is false, and the smoke set does not exercise all four entries it does list.** `scripts/flywheel-voice-bridge-wrapper.sh` is one of the PATH edits; its child reads bare `ffmpeg` at `packages/voice-bridge/src/config.ts:354`, and startup explicitly probes it at `packages/voice-bridge/src/preflight.ts:26-35`. Both prefixes contain different builds: `/usr/local/bin/ffmpeg` is x86_64 8.1.2, while `/opt/homebrew/bin/ffmpeg` is arm64 8.1.1. `packages/voice-core/src/config.ts:84-85` also defaults bare `ffplay` and `ffmpeg`, with the same 8.1.2 → 8.1.1 switch. The wider repo also has bare operational `brew` consumers (the measured resolution changes Homebrew 6.0.18 → 5.1.12) and an `openssl` fallback; those need an explicit in-scope/out-of-scope classification rather than disappearing from the table. **Fix:** replace the hand-selected “only four” claim with a reproducible overlap-to-consumer sweep that follows children of the changed carriers, then classify every hit. At minimum add the voice binaries and run the existing codec/preflight path under the proposed PATH. Exercise `npx` by actually resolving/running the repo-local `tsx` path used to boot Bridge/voice-Bridge; `npm --version` does not test `npx`. For `gh`, inventory the real subcommand families (`auth token/status`, `api`, `repo view`, `pr list/view/checks`) and smoke representative read-only forms, or narrow A4 to the smaller evidence actually collected.

3. **HIGH — the S2 registry cannot prevent a new declaration from escaping, and its stated set omits the QA parity target.** A registry proves only that listed files still exist and obey the rule. A new file containing a mixed-prefix PATH is invisible unless the scanner also discovers candidate declarations and rejects candidates absent from the registry; “注册表缺文件 = 违规” catches a deleted registered file, not a newly added unregistered one. Also §2.2 says “the §1.1 ten sites” plus the already-native batch, which does not explicitly include `scripts/lib/qa-launchd-lead.sh`, despite A1 promising 10+1 parity coverage. **Fix:** add a discovery-versus-registry closure check (with a test that creates an unregistered mixed-prefix declaration), or narrow the guard's promise to the current registered sites. Include the QA parity file explicitly in the guarded registry and positive control.

4. **HIGH — the new source-tree rule is not actually mounted at `converge` as planned.** The current call at `converge-flywheel-bin.sh:653-658` invokes `check-global-path-hygiene.sh` with only optional `--alert`; it supplies no repo root or source-tree mode. The packaged payload contains the checker and `lib/path-hygiene.sh`, but not the full source registry, so a fail-closed source scan cannot silently become the default there. CI does execute the test file, but A3's assertion that the old converge call “exists” still does not prove the new rule ran. **Fix:** specify the exact CLI and call-site change, including how monorepo versus packaged mode is detected and tested. Either make converge invoke the source mode only when a complete validated source tree is present, or explicitly retract converge as an S2 mount and rely on CI/payload assembly. A3 must assert a source-mode receipt/output, not the existence of the legacy global scan.

5. **HIGH — §3.1 generalizes beyond the measured protocol evidence.** The experiment establishes one concrete pair and one command: 3.7c client → 3.5a server succeeds for handshake/`list-sessions`; the reverse fails. It does not establish the semantic-version law “client version >= every server version,” nor even production safety for the permitted mixed edge before P4. **Fix:** state the invariant in exact pair terms: no selected 3.5a client may target a live 3.7c server; before creating any 3.7c server, every relevant client class must be pinned/proven 3.7c; and 3.7c-client/3.5a-server operation is allowed only after P4 passes. Keep inference B, which is valid for this pair.

6. **HIGH — P1–P6 miss launch architecture/preference as an explicit S3 blocker.** The upstream experiment found that starting the ARM tmux binary from an x86-preferred parent still produced translated universal child shells; `arch -arm64` reset the preference transitively. Production is expected to be safe because Lead servers currently have PPID 1 and launchd is native, but that is an inference that must be preserved across every server class and restart path. §3.4 detects a bad result after a batch; P1–P6 do not require the future transaction to prove the launch path before destructive work. **Fix:** add P7 for launch provenance/CPU preference: classify each supervisor/start path, require native launchd or an explicit ARM reset, run a positive-control child `proc_translated=0` probe, and record parent/start identity. Extend/reuse the existing census; its current preflight records image architecture and PPID but not inherited child-slice preference.

7. **MEDIUM — §0.1 overcorrects two facts and the upstream evidence documents still contradict the retraction.** “372 genuinely different binaries” is stronger than the measurement: the evidence shows 372 different resolved paths; it does not prove different content/behavior, and several entries are scripts rather than binaries. The second retraction says the rolling variant lacks three things even though P4–P6 are also blockers; say “at least these three foundational gaps” or point directly to all six/seven. Separately, `exploration.md:9,171` and `research.md:98-110` still conclude that link/S1 are safe and S3 is rollable, while `plan.md:5` says it is based on that research. **Fix:** use the precise “distinct realpaths” wording and add a supersession/correction banner to both upstream documents (or amend the contradicted conclusions) so readers do not recover the withdrawn runbook from the evidence files.

8. **MEDIUM — parking S3 needs a durable completion owner because S1+S2 do not retire the Rosetta deadline.** A7 currently lets this issue accept a “complete” P1–P6 list even though the issue's core tmux replacement remains undone. **Fix:** state whether FLY-2190 remains open after the S1+S2 PR or create a linked blocking follow-up with owner, deadline, and exit criteria for P1–P7, reviewed runbook, and founder-authorized execution. The implementation PR may complete its scoped node; the umbrella risk must not be marked resolved.
