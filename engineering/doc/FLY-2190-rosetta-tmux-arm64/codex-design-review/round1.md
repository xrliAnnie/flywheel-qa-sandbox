# Design Review — FLY-2190 plan.md (Round 1)

Date: 2026-08-30
Author: Codex
Status: CHANGES REQUESTED

## Summary

S1's direction is sound and the plan's named edit sites are accurate, but the safety claim is broader than the evidence: the mixed-version experiment proves one command path, while the PATH change switches hundreds of other duplicated executables. More importantly, §3 is not yet an executable rolling runbook: it omits the shipped transaction's admission/quiescence/budget sequence, does not account for non-Lead tmux servers, and has no valid mixed-fleet rollback.

## What's Good (Keep)

- The implementation order is directionally correct: never allow a 3.5a client to be the selected client for a 3.7c server. The isolated evidence establishes `3.7c client -> 3.5a server` for `list-sessions` and establishes that the reverse direction returns rc=1 without killing the server.
- All 11 sites listed in §1.1 exist at the stated lines and contain the claimed Intel-first literal. All six §1.2 test assertions also exist at the stated lines. A repo-wide literal sweep found no additional Intel-first production declaration under `packages/` or `scripts/` beyond those listed (the other matches are tests, QA fixtures, or historical evidence).
- The plan correctly avoids `/etc/paths`, shell rc files, a second cutover implementation, and an unsupported performance claim. Keeping the two existing canonical PATH copies synchronized without combining them is appropriate scope discipline.
- `scripts/qa-tmux-3.7c-compat.sh` is a real fail-closed exact-version gate, and the restart guard really does detect wrapped Runner-side brew mutations including `arch -x86_64 ... brew`.
- No production runtime check was found that requires the version string to equal 3.5a. The exact 3.5a pins are recovery/test tooling; production code does contain 3.5a-specific behavioral assumptions, which should stay visible in the compatibility gate.

## Issues & Recommendations

1. **BLOCKER — §3 does not actually use, or reproduce the guarantees of, the shipped cutover transaction.** `host-terminal-cutover.sh` is a receipt and bounded-command toolkit; it does not encode a nine-step state machine or a per-Lead rolling operation. Its original FLY-1944 runbook paused admission, proved stable-zero quiescence, stopped all supervisors, took an authoritative census, stopped all old servers, changed the links, bootstrapped services, verified them, and resumed admission. FLY-2190 §3.2 contains only `brew link`, a deployment check, and “restart each Lead”; it never invokes `pause-admission`, `quiescence`, `run-step`, `verify-receipt`, or `resume-admission`, and gives no exact restart commands. A reader following §3 “directly” would bypass the machinery the plan claims to reuse. **Fix:** either retain the whole-host W2 transaction, or define a complete per-batch transaction: pause → two authoritative zero snapshots → inventory/freeze the exact batch → bounded restart → per-Lead verification → receipt → resume. If batches may span windows, specify and test receipt renewal/re-entry between batches. A minimal rolling subcommand/extension is acceptable reuse; a prose assertion that the old script already supports rolling is not.

2. **BLOCKER — restarting 16 Leads cannot satisfy the all-host tmux acceptance criterion.** The upstream evidence reports 20/20 live tmux servers on 3.5a, and the original W2 explicitly covered per-Lead, default, atlas, QA, and loose/unowned servers. The new sequence only restarts Leads, while §3.4 expects every `pgrep -x tmux` image to be the ARM Cellar binary. Default/atlas/runner-base and unowned servers are neither migrated nor dispositioned. **Fix:** take an authoritative pre-window census, classify every server/socket by owner and supervisor, and give each class an explicit migrate/stop/allowlisted-residual action. Re-run the census after every batch and at completion. If scope is intentionally Lead-only, narrow the acceptance criterion and explicitly retain the residual Rosetta deadline risk; that would not meet the current issue framing.

3. **BLOCKER — the post-step-2 rollback is not executable and is unsafe in a mixed fleet.** `build-closure` creates a wrapper and `rehearse-rollback` proves it on an isolated socket; the script does not install that wrapper, restart a Lead with it, or execute a rollback. The 900 seconds are a reserve checked before normal steps, not an implemented 900-second rollback transaction. With `/opt/homebrew/bin/tmux` still linked and first on PATH, merely having the 3.5a closure cannot make a restarted Lead select it. Unlinking ARM first is also unsafe once any 3.7c server exists, because remaining bare clients fall back to 3.5a and cannot control that server. **Fix:** write the exact rollback order and commands: keep an absolute 3.7c client available to stop/inspect every upgraded server, pin the replacement server binary explicitly (or perform a complete batch rollback), then change links/PATH only after no 3.7c server is left, restart under 3.5a, verify tuples and client reachability, and resume admission. Reconcile this with the fact that this variant never upgrades `/usr/local` tmux, so the old W2 closure/bottle requirements may be unnecessary or need a different role.

4. **HIGH — the one-way compatibility evidence is too narrow for “works normally” and “zero interruption.”** The recorded mixed-version positive case exercises `list-sessions`; `qa-tmux-3.7c-compat.sh` exercises a homogeneous 3.7c client/server pair. Neither proves the new-client/old-server intermediate state for the production command surface: attach/control mode, has-session, new-window, display/list formats, send-keys, hook management, and kill operations used across the five packages and cmux scripts. The reverse-direction survival result is similarly one command observation. **Fix:** add a fail-closed mixed-version gate that starts a 3.5a server and drives the representative production operations with the 3.7c client, including the Lead/cmux attach path and the pane-exited cleanup command. Keep the homogeneous 3.7c gate as the final-state gate. Until then, say “handshake and `list-sessions` were verified,” not “works normally.”

5. **HIGH — S1 changes far more than `python3` and `tmux`; the independent-safety claim is unproven.** On this host the two bin directories currently share 373 basenames. Relevant observed switches include `npm`/`npx` 11.16.0 → 11.9.0, `gh` 2.74.2 x86_64 → 2.97.0 arm64, and `brew` 6.0.18 → 5.1.12; `python3` is only one member of that set. The listed regressions test tmux birth environments and two Python hooks, not the other commands invoked by Bridge/Lead/updater wrappers. **Fix:** inventory the overlapping executables actually called from the 11 carriers, record before/after resolution/version/architecture, and add focused smoke tests for load-bearing commands. If an overlap is intentionally allowed to change, document it. The statement that both intermediate states are safe must be narrowed until this sweep is green.

6. **HIGH — a merged/deployed SHA does not prove every client is 3.7c before the first server restart.** Existing Bridge, Runner, helper, pane, and tmux-server environments can retain the old PATH after files change. The plan itself cites 50+ bare clients but checks only one source literal plus `~/.flywheel/deployed-sha`; that is insufficient to conclude “全机 client 已是 3.7c.” Any stale 3.5a client that targets the first upgraded private socket hits the known bad direction. **Fix:** make S1 fully deploy and converge before linking ARM tmux, then add a runtime precondition covering every long-lived client-bearing class (or quiesce/restart those classes) and prove the selected client path/version. The plan's table already puts S1 deployment before the window; make the numbered sequence unambiguous and verify effective runtime state, not just source state.

7. **HIGH — the S2 carrier and provisioning mount claim are not correct as written.** `converge-flywheel-bin.sh:653` really invokes the checker, but `package-onboard.sh:100` only includes the checker in the payload; it does not run it during provisioning. The packaged tree also omits several registry targets (for example TS source, tests, the internal TUI template, and rollback operator script), so a fail-closed source-file registry cannot work there unchanged. Finally, the current checker and `bin_integrity_drift` alert text are specifically about global temp/worktree references; a repository PATH-order violation would produce incorrect remediation text. **Fix:** define an explicit source-tree mode with a validated repo root and registry, run it in CI and during payload assembly, and separately decide whether provisioning should verify materialized artifacts/effective launch configuration. If the existing checker remains the CLI, give the new mode accurate output/alert semantics and test monorepo and packaged shapes. Change A3 to prove an actual invocation, not mere inclusion in a package list.

8. **HIGH — §3.4's verifier contradicts the proven executable-image extraction rule and omits service/view health.** The command `lsof ... | awk '$4=="txt"' | head -1` reintroduces the exact bug FLY-1944 avoided: Rosetta processes can expose multiple `txt` entries, so the first line is not authoritative. `host-terminal-cutover.sh:278-293` filters recognized tmux images and has a positive control. The proposed per-Lead check also does not prove launchd ownership, socket ownership, Lead body health, cmux attach/sidebar recovery, or that a command's output was captured into a receipt. **Fix:** expose/reuse the exact census extractor, write machine-captured per-Lead receipts for shell/Python architecture, and include launchd PID/start identity, socket ownership, Lead health, and cmux/`--verify-sidebar` acceptance after every restart. Final success must be an authoritative all-server census plus all-Lead health/view checks.

9. **MEDIUM — the PATH inventory and acceptance command need small corrections.** Add the production-native declaration `scripts/com.flywheel.log-janitor.plist:17` to the guarded B set; it is installed by `scripts/install-log-janitor.sh`. Update the now-stale `/usr/local` node wording in `scripts/launchd/com.flywheel.updater.plist:12-15`, not only the cmux-autostart comment. Also, §1.1's “11 production sites” includes `scripts/lib/qa-launchd-lead.sh`, which is a QA harness. Finally, A1's raw `grep packages/ scripts/` will still match the three intentionally unchanged test fixtures from §1.2, so it is not an executable zero-match verdict. **Fix:** distinguish 10 production/operator sites plus one QA parity site, include every native-first production declaration in the registry, and make A1 use the registry-aware scanner (or explicit production file list).

10. **MEDIUM — §3.3 describes a guard authorization path that does not exist.** P5 brew mutations are denied only when `FLYWHEEL_EXEC_ID` is present; Lead/founder contexts without it are allowed with an audit row. A Runner can use the generic `FLYWHEEL_RESTART_GUARD_BYPASS=<reason>` prefix only if audit write and strict alert delivery both succeed; that is accountable bypass, not Lead/founder approval. Separately, the per-Lead `launchctl kickstart/bootout` commands needed by rolling cutover match P1 and are also blocked in Claude Bash. **Fix:** name the exact operator context and exact audited bypass contract for both brew and launchctl actions, and require external founder authorization as a runbook precondition rather than claiming the hook provides it.

11. **MEDIUM — there is no exact 3.5a pin, but the consumer sweep is incomplete.** Version-specific behavior remains in `scripts/flywheel-cmux-sync.sh`, `scripts/test-cmux-sync-hooks-integration.sh`, `packages/claude-runner/src/TmuxAdapter.ts`, `packages/teamlead/src/bridge/tmux-lookup.ts`, and the edge-worker real-tmux test. The exact 3.7c gate covers cmux and claude-runner, but not all of the teamlead/edge-worker/flywheel-comm/core consumers named by the research. **Fix:** add a consumer matrix to the plan and either run each version-sensitive family against exact 3.7c or explain, with a test anchor, why it is protocol-agnostic. This is the evidence needed for the plan's “only PATH matters” assumption.

## Verdict

CHANGES REQUESTED — address items above
