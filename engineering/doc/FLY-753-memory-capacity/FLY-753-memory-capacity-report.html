一句话结论

想稳定跑 100 个 session,要么换 256 GB 的机器,要么把每个 session 从 1.4 GB 砍到 ~0.4 GB —— 砍完 96 GB 机器就够,连现在这台 48 GB 都能从 ~18 个提到 ~40–50 个。

换机器
不优化 → Mac Studio 256 GB(~$7–8k)才能跑 100 个。贵且浪费。
砍 footprint
推荐先做 删掉用不到的 MCP + 小 context 默认 → 每 session 1.4→0.4 GB → 96 GB 机器跑 100 个舒适。
当下止痛
不换机器,光删 MCP,当前 48 GB 并发上限 ~18 → ~40,swap 抖动立刻缓解。

最反直觉的发现

吃内存的不是 Claude 的 context,是 MCP 套件。

每个 session 都各自复制一整套 ~15 个 MCP 子进程。小 context session 里,MCP 套件(~1.0 GB)是 Claude 主进程(0.28 GB)的 3.6 倍。20 个 session = 20 份 chrome-devtools、20 份 serena、20 份 context7…… 这才是 48 GB 被 20 个 session 吃满的真因。

MCP 套件 ~1.0 GB(77%) Claude 0.28 GB

↑ 一个小 context session 的内存构成。换 1M→小 context 每 session 只省 ~0.35 GB;砍 MCP 能省 ~0.6–1.0 GB —— 优化 MCP 的杠杆远大于 context。

"~20 吃满 swap"和你的观察一致。基线(OS+Chrome+cmux+Discord 等)约占 10 GB,剩下 ~31 GB / 每 session 1.4 GB ≈ 22 个。

⚠️ CPU 也是硬顶:18 核。多个 session 同时 build/test 时,瓶颈变成 CPU load(历史上 load 冲到 170–450 会把 Mac 卡死 panic)。Flywheel session 多数时间 idle(等 gate/CI),所以内存是主约束;但 active-burst 要限并发。

建议的下一步

1. 先砍 footprint(FLY-751),别急着换机器 —— 删除清单见上,建议你逐项拍。保守首刀今天就能做。

2. 浏览器 MCP(chrome-devtools/playwright)收进 QA-only 路径 —— 正好和 FLY-752(auto-QA 重设计)一起做,QA session 才是唯一真需要浏览器的。

3. 优化落地后,若仍要 100 个,再上 96 GB 机器就够;不必买 256 GB。

本研究不改任何生产代码;删除动作由 FLY-751 执行,要你逐项确认。
