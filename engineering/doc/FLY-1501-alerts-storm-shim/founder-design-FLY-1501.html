先把三个直接问题说死

每次会不会读走全部积压？不会。一次只取一条，处理并销账后才重查下一条。

99 条是全发出来，还是逐条筛满 30 分钟的发？都不是。体检器只发一张“这个收件人堵了多久、堵了多少”的状态卡，绝不把 99 条消息本体倒进 Discord。

进程死了谁处理？独立体检器不依赖被查进程；卡通过专用通道直发 Discord，并沿管理链送到活着的人。

① 消息读取循环：门铃负责快，分钟 tick 负责不丢

  1. 消息先写进 kernel 的权威信箱；入库成功才算存在。
  2. 有新消息时尽量按“门铃”即时叫醒。门铃是 push 信号，允许偶尔丢，因为它只优化延迟。
  3. 另有分钟级 tick兜底。它不是每秒扫库，也不是另一个消息系统；只保证门铃丢了以后，最多等到下一次 tick 仍会继续。
  4. 循环每次只取队头一条：batch=1。处理这一条期间，不预先把后面的积压读走。
  5. 这一条产生的业务结果与“已处理”销账在同一个事务提交；提交成功才重查下一条。
直接答案：不会一次读走全部积压。它是“取 1 条 → 做完并销账 → 再看有没有下一条”。

② 告警怎么触发：每分钟只看两个统计数

  1. 体检器是每分钟跑一次的独立小进程，不住在被检查的 agent 里面。
  2. 对每个收件人，它只查两个数：最老未处理消息等了多久、现在共有多少条未处理。
  3. 精确触发谓词只有一个时间门槛：最老等待超过 30 分钟。没有“至少 N 条才告警”的数量阈值，所以哪怕只有 1 条但真堵了，也会报。
  4. 触发后按“积压种类 + 收件人”打开或更新唯一一张 episode 卡。条数从 1 涨到 99，仍是同一张卡。
  5. 卡里是状态摘要：谁堵了、堵了多久、共有多少条；不是把积压消息本体逐条外发。
直接答案：把 99 条全发出来；把满 30 分钟的消息逐条发。正确行为是：同一收件人只发一张状态卡。
分档通知是 30 分钟、2 小时、8 小时，最多三次。积压清空后，下一分钟体检自动关闭卡。

③ 谁收到卡、怎么恢复：死 / 卡 / 忙三分支

  1. “谁堵了”与“通知谁”分开：卡上固定记堵者 A；发送那一刻查 A 的现任管理者 B。
  2. 卡永不发给堵者本人。Runner 堵了发给现任 Lead；Lead 堵了最终发给 founder。
  3. 管理者判断现场：进程死了就重启/换代；进程活着但卡住就解卡或中止坏任务；确实在忙就观察，不误杀。
  4. 下一分钟体检发现积压已清，自动销账，不需要人回 Discord 手动“摘牌”。
  5. 没有清才在 2 小时和 8 小时升级；到 8 小时后封顶，不无限提醒。

④ Annie 的三个 crux：为什么不会反过来制造更多问题

不多上加多被堵的人不是收卡的人。告警沿管理链上送，堵者无需停下手头工作处理自己的告警。
不越堆越多episode 唯一键保证同一收件人只有一张卡；30m/2h/8h 三档封顶，不卡片风暴。
进程死了仍有人处理体检器独立运行；Bridge 不可用时专用 shell 通道仍可直发 Discord；管理链终点是活人。
父压子：如果 agent 已经死亡，积压只是死亡的后果。死因父卡开着时，子积压卡不重复吵人，只记“通知债”；父卡清掉时按最新档位补一条，然后清债。

⑤ 为什么还要重启刹车：根治已知 crash，不等于保护下一次未知 crash

  1. 这不是 Bridge 特例，而是通用自动重启刹车。全系统唯一会无限自动重试的是 launchd，所以统一守住它管理的五类 supervised 入口。
  2. 每次启动前先在 kernel 外账本记一笔；10 分钟内前 5 次仍允许启动，第 6 次进入 hold，不再执行 child。
  3. hold 同时走独立 meta-alert 与 Discord 通道；人处理根因后显式 resume，再开启新 episode。
  4. 账本在 kernel 外，因为 kernel/Bridge 自己死时仍必须能计数、刹车和告警；文件锁抢不到就 fail closed，避免两个启动器同时穿闸。
实证与工业对标：7 月 6 日真实发生过 Bridge 重启风暴；同类成熟机制是 Kubernetes CrashLoopBackOff 与 systemd StartLimitBurst。窗口与次数可调，默认 10 分钟 / 第 6 次停。

⑥ “垫片”去黑话：就是不同 agent 命令行各自的耳朵转接头

会话窗口不是 UI 窗口；它是正在跑的 agent 进程接收外来消息的“耳朵”。kernel 只认两个动作：可丢的 hint 与可重复的 deliver，没有 ack。

  1. Claude 的耳朵：它原生监听一个信箱文件。小实现用稳定消息号写进去；重复投递由 sidecar 收敛。
  2. Codex 的耳朵：活跃 daemon 的 turn 通路。每次投递临时连接、发一个有界 turn，无论成功、报错或超时都立即关闭，不留长期连接状态。
  3. 以后接的其它 agent 命令行：只写同样大小的一个小实现。kernel、库表、消费循环都不改。
边界：它不是第二套消息系统，也不承诺 vendor 恰一 turn；重复 turn 最终靠同一个 messageUid/attemptUid 在消费端只结算一次。
