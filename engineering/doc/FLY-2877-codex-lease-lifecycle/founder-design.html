Codex 租约与进程同生同灭

FLY-2877 · 设计稿 · 2026-09-25 · 工程设计节点

一句话问题与修法

Codex runner（runner：Flywheel 派出去干活的自动程序）在共享家目录里的租约（lease：一个小文件，写着「这个 runner 正在用这个家目录」）会在 runner 还活着的时候被别人删掉，于是「自动切换 Codex 账号」这件事永远等不到「可以切」的信号。修法是：只要这个 runner 的 Codex 进程还活着，谁都不许删它的租约；被误删了 60 秒内自己放回去；进程退出后才真正释放。

病根生产上到底发生了什么

2026-09-24 晚，两个 Codex runner 同时用同一个共享家目录。其中一个（FLY-2873）的租约在启动后不到 11 分钟就消失了，但它的三个 Codex 进程直到第二天凌晨还活着。

这次不是 issue 猜的那个地方（runner 收尾代码）干的：生产 Bridge（Bridge：Flywheel 的总调度服务）在那 11 分钟里没有重启，日志里也没有任何收尾记录。能在那个时间段里、不看进程、静默删租约的只有一种东西：另一个 worktree 里跑的测试套件。测试启动了一个「假 Bridge」，它用的是真实的家目录，但对照的是测试自己的空账本，于是把生产上所有租约都当成孤儿删掉了。同一晚这件事有两次留下了日志（21:08 删 1 个、21:22 删 2 个，都是刚启动的生产 runner）。

顺带发现另外两个问题：

  • 就算租约都在，现在的判定也会算错：每个 runner 有两个 Codex 进程（后台守护进程和前台窗口），判定代码拿「进程数」和「租约数」硬比，两个 runner 就是 4 比 2，永远不等。FLY-2869 那张单已经把它改成按 runner 去重，本单不重复改。
  • 租约丢了没人会放回去：放回去需要一把只有 runner 自己知道的钥匙（token），Bridge 那边没有。

核心流程修好之后租约怎么活、怎么死

看图的顺序是从上往下：租约在派发时创建；运行中有一个独立的 60 秒定时器自查，被删就用同一把钥匙放回（一次只跑一个，避免和收尾打架）；结束时先停掉定时器并等在途的自查结束，再停守护进程、关窗口、确认退出、等进程真的没了，才走到中间那个菱形「守卫」——只有守卫确认没有任何这个 runner 的 Codex 进程，租约才会被删。Bridge 启动时的清理、派发未交接的回滚、各种失败回滚，也都必须过同一个守卫。

结构模型四个角色、一条规则

租约文件和Codex 进程是一对多（一个 runner 可以有多个进程）。守卫只做一件事：用系统自带的 ps 命令（列出所有进程和它们的环境变量）看看有没有属于这个 runner、用着这个家目录的 Codex 进程；有就保留，没有才删，看不清（命令失败、进程身份对不上）也保留。判「什么算 Codex 进程」的规则逐字复制自 FLY-2869 那张单的进程权威（process authority：三次快照互相印证、只认内核记录的可执行名，防止伪造的命令行参数冒充环境变量），所以守卫和就绪判定看到的是同一个事实。runner 自己是唯一拿着钥匙的人，所以放回租约这件事只能由它做。维护 tick（Bridge 里已有的定期巡检）负责收拾进程已退但租约还在的残留，且不依赖可能已丢失的 session 记录。

三条不变量（不变量：任何时候都必须成立的规则）：

  1. 本仓库的代码删租约 ⇒ 删之前那一次探测确认没有进程、且探测本身成功。（这是严格规则。）
  2. 有这个 runner 的 Codex 进程而租约丢了 ⇒ 60 秒内发起恢复，第一次拿到家目录锁并校验通过就放回。（这是恢复保证，防的是旧代码和外部删除。）
  3. 守卫「数进程」的口径和就绪判定「数进程」的口径是同一份合同，用 FLY-2869 同一组测试向量钉死。

取舍选了什么、放弃了什么

决定为什么放弃的备选
守卫放在删租约的那三个函数内部七个调用方自动受保护，以后新加调用方也不会漏让每个调用方自己判断——漏一处就是下一张单
用 ps 扫环境变量判进程存活就绪判定就是这么数的，两边看同一个事实把进程号写进租约文件——进程号在 runner 起来前还没有，且不止一个进程
runner 每 60 秒自查并放回本机同时有好几个旧版本 worktree 在跑测试，它们的旧代码照样会删；只有 runner 自己有钥匙不做，只靠守卫——防不住旧代码
残留清扫挂在已有的维护 tick 上不新增定时器、同一个总开关新开一个定时器
探测失败时不删删错一个会让活 runner 的家目录十几个小时不可判；此时就绪判定本来也是不可判，不会更坏探测失败时照删
给测试加家目录隔离卫生措施，堵住这次的直接来源——（这是补充，不是防线）

验收怎么证明修好了

  • 每一条会删租约的代码路径，都有一条「进程还活着 → 租约必须还在」的自动化测试；另有一条「进程没了 → 租约被删」。
  • 真机：两个 Codex runner 用同一个家目录，跑的时候租约恒为 2；在另一个 worktree 故意跑那个测试套件，60 秒内租约回到 2；结束一个 runner 后变 1，两个都结束后变 0。
  • 就绪判定对「两个 runner 并行」给出 ready——这一条要在包含 FLY-2869 改动的代码上验（见下节）。
  • FLY-2523 的证据规则代码和测试零改动（用 diff 为空来证）。

诚实边界这个设计做什么、不做什么

钉死了的
删租约的机制、时间窗口、同晚两次同类事件的日志证据。
没钉死的
23:25–23:36 那一次具体是哪个进程干的——测试输出只留在 runner 的终端里，没有落盘。
不修的
正在跑的那个 FLY-2873 runner：它的租约已经丢了，钥匙只在旧代码的内存里，只能等它自然结束。
依赖别人的
「两个 runner 并行判 ready」需要 FLY-2869 的去重改动；本单不碰那份代码，只把它判进程的规则复制一份来用，合并后再收成一份。
两种强度
「新代码不会删活 runner 的租约」是严格规则；「被旧代码或外人删了 60 秒内放回」只是恢复保证，验收时分开算。
留到下一单的
租约被删到零时会顺手把 runner 的 GitHub 推送凭据也擦掉；本单只放回租约，不放回凭据。
