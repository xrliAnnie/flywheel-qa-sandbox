FLY-2211:重启波为什么"杀死"了 codex 工人,怎么修

工程设计说明 · 2026-08-31 · 分支 flywheel-FLY-2211 · Codex 设计评审 5 轮后 APPROVED · 每个卡片下方都可以留意见,页底一键汇总复制

1. 一句话总结

查明:8-31 中午那波重启本身一个工人都没杀;四个 codex 工人是在波结束 11–21 分钟后,被一条不留任何痕迹的杀伤路径成对干掉的——而真正的病根是:Bridge(引擎大脑进程)重启之后,没有任何人重新认领还在干活的 codex 工人,它们成了"无主进程":死了没人发现(实测拖了 9–19 分钟)、被杀没人救。修法就是给 Bridge 加一个启动时的"认领器":活着的看护起来,死了的用同一段对话记忆原地复活,并让系统里每一次"杀进程"都必须先记账。

2. 结构模型:一个 codex 工人其实是三个进程

founder 看到的"工人窗"只是三件套里最薄的一层。daemon(后台常驻进程)才是真正干活的那个:它跑 AI 循环、把每一步写进 rollout(工作日志文件)。TUI(窗里的文字界面)和 Bridge 都只是通过一条本地套接字(同一台机器上进程之间的专用通话线)连到 daemon 上。

所以按设计,重启 Bridge 确实不应该影响工人——daemon 是独立进程组,Bridge 死了它照常干活。你问的"重启不就重启 bridge 吗,跟 worker 有什么关系"在结构上是对的;关系断在下一节。

3. 核心流程:8-31 四杀取证时间线(推翻了工单里的原始推断)

我们把四个工人的 rollout 写盘时刻、codex 自己的运行日志(精确到秒)、Bridge 日志、全部清理巡逻的账本逐一对齐,得到的时间线和工单原来的推断不一样:

三个硬结论

  • 波没杀人。四个 daemon 在波结束后又健康干了 11–21 分钟活,日志写到死亡前 1 秒都毫无异常——然后瞬间静默,是被外部强杀(SIGKILL,操作系统层面"立即处死"信号)的典型死相。
  • 所有"有账本"的清理机制当时都没动手。重启脚本、孤儿收割巡逻、窗口清理、内存不足杀进程……逐一用它们自己的账本排除。也就是说:系统里存在至少一条杀人不记账的路径。在点名它之前,工单原提的"重启波不杀名单"没有可挂靠的对象。
  • 无主才是病根。老 Bridge 一死,四个工人就没了监护:被杀后系统拖了 9–19 分钟才宣告死亡;当天靠 Lead 手工抢救未提交的代码树才做到零丢活。哪怕没有这个杀手,无主的工人干完当前目标也会原地搁浅。

4. 修复设计:re-own 认领器 + 快速死检 + 杀伤记账

核心动作只有一个:Bridge 每次启动,先把机器上所有在飞的 codex 工人重新认领回来。

  • 正常干活的活体:零接触。只登记看护,每 5 分钟确认"套接字还活着 + rollout 还在前进"。不重启、不打扰。两类例外走"有意的、全程记账的换后台"(同一段对话记忆原地续跑):① 停在等待态(parked)的工人——它的"叫醒"通道住在 Bridge 里,必须重建;② 正卡在提问闸口等回答的工人。这是设计评审五轮抠出来的边界,不是含糊话。
  • 死了的:同记忆复活。复活用的是代码里早已备好、只是没人触发的通路:同一个执行体、同一个对话线程(codex 的 thread 会完整带回之前的上下文)、原地拉起新 daemon、自动重开工人窗。以后无论谁再杀工人,都从"损失半天"降级为"两分钟自愈"。
  • 杀伤记账(抓凶手的仪表)。flywheel 里每一处会发"杀进程"信号的代码,今后必须先写一行账(时间、谁、杀谁、为什么)再动手;工人死亡瞬间自动拍"现场快照"。下次再出现无痕死亡,要么账本点名,要么证明凶手在 flywheel 之外。
  • 验收是真机演练:①真实重启波后,正常干活的在场工人 daemon 进程号不变、rollout 持续写 ≥30 分钟(等待态/闸口态工人则断言"恰好一次带账换后台");②"谋杀演练"——手工强杀一个工人,一个巡逻节拍内(≤6 分钟)同记忆复活;后续"无损接管"增强落地后收紧到 ≤2 分钟;③演练窗口内每个信号都有先行账目。

5. 关键取舍与被拒方案

方案判定原因
工单方向 A:重启波"不杀名单"拒波本身没杀人;凶手没点名,名单没有挂靠点。其精神保留为"杀伤记账"。
工单方向 B:TUI 断线后重连而非退出拒实测 TUI 不是超时退出,是和 daemon 同一刻死;且 TUI 行为在上游 codex 二进制里,不是我们的改动面。
工单方向 C:波后重建 broker 并重接采纳并泛化泛化成本设计主体:启动认领器 + 看护 + 同记忆复活。
启动时直接给所有在飞工人换替身拒几乎零新代码,但每次波都杀健康工人、丢在飞上下文和未提交代码——正是这次让你生气的损失形态。仅保留为复活连败后的兜底。
无损接管活工人(不重启 daemon 直接接上事件流)研究门控取决于 codex 的 app-server 是否允许后继连接接管进行中的目标;实现期第一步用半天做真机探针,结论只影响增强层,不阻塞主体。

6. 诚实边界:这个设计做什么、不做什么

  • 做:认领器、复活通路、5 分钟级死亡检测、杀伤记账与死亡快照、真机波演练验收;全部带独立开关,可一键回滚到现状。
  • 不做也做不到:本单不承诺点名 8-31 的凶手——现有证据只够排除所有记账路径;仪表就位后由下一次事件点名(或证明凶手在 flywheel 之外)。
  • 不做:不改 codex 官方二进制的行为;不动 Claude 侧 codex 插件 broker 的生命周期(取证中顺带发现它会继承工人的 CODEX_HOME 并活过任务生命周期——已建议另立卫生工单);不动 claude 工人(它们的窗即进程,天然重启安全)。
  • 已知残余风险:复活会丢掉被杀那一刻正在进行的单个 turn(分钟级工作量),且复活时会把开工指令重发一遍(至多一次重复、逐字节相同——这是 codex 现行已验证的恢复合同,评审确认不装"绝不重发"的假保证);若凶手专杀"有主进程"(8-31 的旁证是替身们全存活,倾向它只碰无主进程),自愈 + 账本也能把损失压到单 turn 并留下归因证据。
