FLY-1788 · tpl_prd 派单卡死修复 — 设计方案

Issue: FLY-1788 · 日期: 2026-08-16 · 阶段: 设计(已过 Codex 设计评审 2 轮 APPROVED)· 后续: 实现 → QA → 上线由流水线后继节点执行

① 一句话总结

tpl_prd(产品需求文档的派单模板)派出去的 runner,出生时没拿到「通行证」(workflow activation,引擎发给 runner 的身份凭证,证明它是当前这单活的合法执行者),于是它干完活想请你审阅时,那扇门永远打不开 —— 修复就是把派单关口的发证条件,从「只发给 design/implement/qa 三种流水线角色」改成「引擎派出的都发」,再补上评审揪出的两个连带缺口。

影响面:tpl_prd / tpl_design / tpl_prototype 三个模板双重卡死(审阅门 + 完工上报都要证);tpl_generic_menu 完工归因也缺证。三节点的 tpl_code 不受影响 —— 这就是为什么别的 runner 一直正常。

② 事故回放:门为什么永远打不开

2026-08-15,FLY-1782 的 runner(执行号 cea85f94)实测:run 建立了、runner 也在干活,但执行 gate founder_review(请求 founder 审阅的命令)时报错 founder_review requires a current workflow activation。查库:通行证表里其他 runner 都有近期记录(仪器正常),唯独它没有 —— 不是它弄丢了,是出生时就没发给它。

关键分岔在图中的菱形判断:发证逻辑写死了「必须是 design / implement / qa 三种角色」。tpl_prd 这类单节点模板编译出来的节点是 generic 类型(通用节点),不在名单里,发证被整个跳过。而门卫(核验逻辑)是刻意从严的:没证就拒,不搞通融 —— 这个从严本身是对的(防冒名顶替),所以修复只能在发证侧。

③ 修复方案:3 个文件、4 个位点

三条真实派单路径最终都汇入同一个发证关口(run-dispatcher)。修复分三刀,后两刀是 Codex 设计评审第 1 轮抓出的连带缺口(我逐条对照源码独立核验后折入):

  1. 修①放宽发证条件:两个发证位点的条件从「三角色专属」改成「引擎派出的(engine-owned)都发证」。发证失败则不启动 runner(fail-closed,宁可不开工,不派一个注定卡死的 runner)。
  2. 修②补齐 retry 路径的发证材料:Lead 手动/网关重试走的是第三条路(actions.ts),它组装的派单包裹里缺了四样引擎材料(含「需要 founder 审阅」的标记)—— 不补的话修①够不着它,重试出来的 runner 还会忘了要请你审阅。
  3. 修③引擎账本投影放宽一格:发证时会同步给引擎账本投一份「发证记录」,账本校验原本只认节点「类型」;generic 节点的记录会被误判成毒信(deadletter,校验不过被永久扣下的消息)。放宽为「类型或节点名字」二选一 —— 伪造值照样拒收。这一格同时治好一个潜伏 bug:返工(rework)和交付载体(carrier)两条既有路径对 generic 节点今天就会踩中它。

无新开关、无数据库结构变更、单 commit 可回滚。TDD:12 条测试先红后绿,其中 4 条锁修①、2 条锁修②、3 条锁修③,3 条锁「原有行为一字不变」。

④ 数据/结构模型:证与权如何互锁

通行证不是一张孤立的纸:它和「轮值权」(TURN,同一单活同一时刻只有一个合法写入者的独占权)锁在一起,门卫要四项字段逐一对上才放行。这就是为什么不能只往表里补一行证 —— 证和权必须同一笔事务一起铸造。

副作用已逐一审计:引擎派的 runner 有自己的生命周期管理,巡检器(TurnBeltReconciler)对它们整体跳过,不会因为多了 TURN 行产生误报;活干完后有统一清理位点收口。

⑤ 关键取舍与被否的方案

方案结论为什么
在发证关口按「引擎派出」放行(选定) ✅ 选定 通行证本来就是引擎概念;单一关口覆盖首发/重试/恢复重派全部路径;发证材料早已备齐,只是被条件挡住。
把单节点也伪装成三角色流水线(共享分支) ❌ 否 会把「共享代码分支」的语义错误附加到单节点活上,连带触发分支探测逻辑,语义污染且改动面大。
门卫对没证的 runner 网开一面(按执行号回退) ❌ 否 方向反了:从严核验正是防冒用的设计,放水等于任何执行都能冒名开审阅门(FLY-1655 刚把这类推断定性为事故源)。
统一三个发证方的字段写法(整型化) ❌ 否 要同步动三处发证方加既有测试面,收益只是「写法唯一」,违背最小改动纪律;修③的一格放宽就够。
给存量卡死 run 写通用补证脚本 ❌ 否 证里的两把提交凭证只在派单瞬间存在,补证要新开凭证轮换运维入口,复杂度和风险远超一次受控重派(见下节)。

⑥ 存量卡死的 run 怎么办(含 FLY-1782)

修复上线后先只读盘点:活跃的单节点 run 里,当前执行没证的就是卡死的。逐张二选一(都由 Lead 决策、走现行权限):

  • 产出还没送到你手上的:关掉卡死的 runner → 引擎自动重派 → 新 runner 走修复后的关口自然拿证 → 它会发现产出已经在分支上,直接进审阅环节,不重做活。
  • 产出已由 Lead 手工转交的(比如 1782 当晚的应急做法):产出闭环后由 Lead 把 run 正常取消收口 —— 不伪造「审阅通过」。

⑦ 诚实边界:这个设计做什么、不做什么

做

  • 让四个单节点模板(prd / design / prototype / generic)派出的 runner 出生即拿证,审阅门和完工上报恢复可用;首发、重试、恢复重派三条路全覆盖。
  • 顺带治好返工/交付载体两条路径对 generic 节点的潜伏毒信 bug(修③)。

不做

  • 不动门卫:核验逻辑一行不改,从严语义保持。
  • 不补存量的证:已卡死的 run 走重派或人工收口(上节),不写补证脚本。
  • 本阶段只是设计:代码实现、529 隔离房的真机复现(修前先复现 1782 报错、修后证明门能开)、独立 QA,都由流水线后继节点执行;本文档没有跑过真机,所有结论来自源码审计 + Codex 交叉评审。
  • 文中行号基于当前 main,实现时若代码移动,以「发证关口的两个条件位点」这类结构描述为准重新定位。
