FLY-2386 值守小版三件收口:给每条告警补一本「去向账」

Issue: FLY-2386 · 上游 Epic FLY-2073(已收口)· PRD FLY-2060 R3/R4/R6/R7 · 设计节点交付 · 2026-09-06 · 工程设计评审:Codex 6 轮,第 6 轮 APPROVED · 数据取自本机生产库(测于 2026-09-06 16:30~17:00 PT)· 详细文档:engineering/doc/FLY-2386-alerts-closure-trio/{exploration,research,plan}.md
0一句话

2073 把「席位、册子骨架、告警管道」都立起来了,但告警到今天只有「投递」没有「去向」—— 这一单补一本去向账,并在账上挂三个出口:处置一次就回填一条册子、每件事都有终态且挂着的看得见、Lead 只在被点名时收信。

名词先说清:值守 = Claw(Claude Infra Bot),负责先看每条告警的机器人;信箱 = Flywheel 里 Bridge 给每个 Lead 投递消息的持久队列(Discord 之外的那条内部通道);去向账 = 记录「这条告警最后怎么了、球在谁手上」的表;册子 = 仓库里的 runbook(解法册)和 contact book(判理册)。

1今天怎么回事:三件「还在咬」的事,根子是同一个

我逐条查了生产机器(不是读文档),三条事实:

事实数字意味着
实测2076 交付的值守写路径(认领 / 转出 / 解决)在生产从未通电近 10 天显式升级账本 170 条,认领 0,解决 0;原因是一条环境变量(值守令牌)没设,门控脚本按合同「不翻」Claw 在看,但一笔账都记不了;而且这件事没有任何地方报警
实测普通告警那条车道根本没有账本近 10 天 Claw 信箱收 671 封,每封各自一个身份,没有 episode(同一问题连响)归并;信箱只有「已送达」态,没有「处理完」态2075 把普通告警改进信箱时明写了这条接缝,2076 没接上
实测Tadashi 的信箱被未点名的告警灌满近 10 天 710 封告警信,其中 657 封是没有 run 编号的工作流升级,由三处代码直投,绕过 Claw 初审;而 19 个 Lead 里没有一个订阅了告警频道,所以 thread 里的 @ 没有任何机器收得到R7「不被 @ 收不到、被 @ 必达」两头都不成立
册子那边:骨架(README、99 类联络表、模板、三页底稿)在;Claw 角色文件承诺「解决后把草稿写到本机一个目录、由 2077 收进仓库」—— 那个目录不存在,2077 里没有收割步骤,仓库里没有读它的代码。回填机制是零。

三件事看似不同,其实都卡在同一处:没有一本「这条告警最后怎么了」的账。没有账,就没法知道哪次处置该回填哪条;没有账,「信已送达」被误当成「事情解决了」;没有账,「被 @」只是 thread 里一段没人订阅的文字。

2核心流程:投递前分档 → 落账 → Claw 三个去向 → 看板

下图是一条告警从产生到「有终点」的路。发射源和转发组件一行不动;变化的是投递前多了一次分档(决定信投给谁)、投出去的同时多记一笔账、Claw 处置时写回这笔账。

图 1 · 核心流程。「车道 A / 车道 B」是 2075 定下的两条路:普通告警进 Claw 信箱(founder 看不到),显式升级才进 Discord thread。本单不改车道,只给车道 A 补账。

分档规则只有四种,写死在一个纯函数里:请求投 Claw 的 → Claw(值守档);合同上已经声明 owner 的 kind(评审失败、旗标扫描)→ 那个 Lead(点名档);其他 kind 却请求投 Lead 的 → 改投 Claw(这就是那 657 封的新去向);值守写路径不可用时 → 保持现状投原 Lead,并在账上标明「fail-open」——fail-open 指系统出问题时宁可多送也不静默丢,这是 Tadashi 对本单的附加条件。

3数据与结构模型:一本新账、一套旧词汇、三个回执目录
图 2 · 四块东西各在哪。实线 = 数据从哪来到哪去;虚线 = 看板只读。
  • 新表只有一张:车道 A 的去向账,和 2076 那张显式升级账用同一套状态词(新 / 已转出 / 已解决,认领时间、转出目标、解决时间)。每个「问题」一行,身份 = 项目 + Lead + 告警类别 + 会话;同一问题没解决又响 → 计数 +1、身份不变(这是既有的身份规则,不是「噪音判定」)。
  • 2076 的旧账加四列:转出理由、转出信编号、转出代数(第几次转)、解决时绑定的草稿编号。新旧两张账在看板上是一个查询。
  • 信箱结构不动:转出信只是一封普通信,只不过编号可预测(含代数),所以看板能逐封查它「排队 / 已读 / 死信」。
  • 回执是文件不是表:③ 兜底时 Bridge 先落一张「欠条」(owed),Tadashi 查明该找谁后补正文(pending),收割命令写进仓库后归档(landed)。三个目录都保留完整头信息,所以「册子欠了几条」直接数文件,不用从账里猜历史。
4册子怎么长:兜底一次 = 一张欠条,解决一次 = 一份草稿
图 3 · ③ 兜底到 contact book 多一行的全过程。顺序是刻意的:先欠条、再记账、再投信 —— 任何一步崩溃都不会「转出了却没人记得要回填」。
出口触发机制为什么这样定
解法册(runbook)Claw ① 自己解决resolve 必须带草稿;命令先把草稿落成回执,Bridge 再核验「回执真实存在、且写的就是这条告警」才允许标解决PRD R4「解决之后立刻写,不是攒着」—— 不带草稿的解决在制度上不成立
判理册(contact book)Claw ③ 册上查不到 → 转 TadashiBridge 先落欠条;转出信里附现成的一行回填命令;Tadashi 查明后执行,欠条变草稿PRD R3「兜底一次就回填一次」—— 欠条在看板上一直可见,直到收割进仓库
写进仓库有仓库写权的人(Tadashi 或他派的 docs runner)一条收割命令把草稿确定性地写进 doc/oncall/(追加一段 + 标记),幂等、不 commit、不开 PR;PR 由跑命令的人开不给 Claw git 写权(2076 D2);Bridge 不自动开 PR(不为小单加凭据面)

通用写法守卫(PRD R4.0「读者是 Infra bot、不写死本机」)机械化成一条拒绝规则:草稿里出现本机路径、账号、Discord 编号、令牌前缀、邮箱 → 命令拒收并列出行号,只拒不改。

⚠️ 这里有一处要 Tadashi 点头:2077 写进 doc/oncall/README.md 的「不为册子加脚本 / 生成器 / 状态探针」「不加新的处理流水」两句,与本单加的三个机械入口(落草稿并拒本机值 / 按回执写页 / 数欠账)冲突。我的判断是 founder 9-6「回填机制没有 → 做」已经推翻了那两句,本单把这个 supersession 明写进 README;不做检测、对账、状态机。

5每件事的终点:四档,没有第五档,挂着的全列
图 4 · 一条告警的生命周期。「已转出」不是终点,是「球在某人手上、且看得见」。

看板(alert-ticket board,也是一个 Bridge 接口)按每个问题一行列出:未初审 / 值守处理中 / 已转出(附转出信送达态)/ 已解决,外加「册子欠账」和「值守写路径是否配置」。三条硬规则:

  1. 没解决的永远全列,不受时间窗和分页截断(时间窗只裁「已解决」的历史);超长就翻页,总数另给。
  2. 没有第五档。「被 fail-open 投给 Lead 的」「合同点名的」都归「已转出」,只是理由列不同。
  3. 不发告警、不 @ 任何人、没有阈值。数字是清单计数,不是指标(founder 直令)。

Claw 的例行 digest 末尾附一行看板摘要(四档数字 + 欠账类别),不 @。founder 想翻「挂着的」时,打开看板最老的在最上。

6被 @ 分档:「被 @」= 你信箱里出现一封转出信,别的都不算
PRD R7本单怎么做怎么验(529 房两个 Lead 身份对照)
不被 @ 收不到非白名单 kind 请求投 Lead 时,投递前改投 Claw;Lead 信箱只可能出现三类告警信:合同点名的、Claw 转出的、fail-open 兜底的。以后新长出的直投代码自动落入同一规则,不需要维护清单注入一条给 B 的无 run 编号升级 → B 信箱 0 封,Claw 1 封,账上一行
被 @ 必达Claw handoff --to X 时,Bridge 在同一步给 X 投一封 [alert_handoff] 信,编号可预测;信的排队 / 已读 / 死信态逐封显示在看板上;再转一次 = 新一封(所以死信可以重投)Claw 转给 A → A 恰 1 封,B 0 封;看板显示「已转出 · 已读」;再转一次 → A 第 2 封

Discord 里的 @ 保留,但它是给人看的留痕,不是送达机制。原因见第 7 节。

那 657 封升级信的新去向:进 Claw 信箱,按身份落账(会话编号各不相同,所以多数各自一行,计数不会把它们并起来 —— 这是身份规则的如实结果);Claw 按 2076 的压力规则处置;Tadashi 只在 Claw 转出时收信。投递量不变(1409 封仍是 1409 封,账本只影响看板行数);它们每 15 分钟重发的源头不在本单,建议另开一张单(R8 根因线)。

7关键取舍与被否掉的方案
决定选了什么否掉了什么 · 为什么
去向账放哪选一张新表,和旧账同一套词汇;旧账不动否把普通告警也塞进旧账:要重建表、且旧账有十几处隐藏读者(自动修复、救援、Discord 同步)都得学会跳过新行,爆炸半径大。否用信箱自己的字段当账:信箱是投递账,每封一行、会被清理,「已送达」已有别的含义。否回到「只发 Discord」:founder 8-26 已裁普通告警不进 Discord
「被 @」是什么选一封走内部信箱的转出信(可查送达态、可在测试房验)否给 19 个 Lead 补 Discord 告警频道订阅 + 服务器层 @ 门控(FLY-898 那套):普通告警没有 thread 可以 @;要动 19 份配置和 bot 入频道;而 2076 自己那个门控翻转在生产都没生效
回填谁开 PR选草稿 + 欠条落本机,一条收割命令写页;PR 由有写权的人开否Claw 直接开 PR(违反不给 git 写权)。否Bridge 自动开 PR(新凭据面,不配小单)
同一问题连响选按既有身份规则(项目+Lead+类别+会话)并入当前一轮,计数 +1否按文本相似度归并:那是「噪音判定」,PRD 明说下一层。否减少投递量:本单不碰投递
值守写路径没配置时选Tadashi 附加条件:改投的告警退回直投原 Lead,账上标明;席位探针、启动日志、Claw 规则三处可见否静默进 Claw 信箱等死:这正是过去 10 天发生的事
设计评审要求的两条「重机制」选不做持久化对账循环、不做自动重投死信理由:Bridge 主库写不进去是 Bridge 级故障,已有元告警通道;死信在看板可见,Claw 再转一次即重投。Codex 第 6 轮接受了这两条 scope cut

  • 前置值守令牌:Tadashi 已裁定由他设进生产环境、随班车重启生效,runner 不碰生产环境。缺这一步,本单的改投告警会退回直投 Lead(不失明),但验收只能记 INCONCLUSIVE。
  • 已批三处直投改投 Claw:Tadashi 原则批准(属 Bridge 内部路由,不算 PRD「不动转发组件」),附加 fail-open 条件已落进设计。
  • 待确认README 两句的 supersession(第 4 节末):我按 founder 9-6 裁定处理,已报 Tadashi;若他不同意,收割命令删掉、入册回人工,其余不变。
  • 建议另开单无 run 编号的工作流升级每 15 分钟重发(10 天 685 封,主要是 FLY-2366 一单)—— 源头修复不在本单。
9诚实边界:这个设计做什么、不做什么
做不做
给普通告警补一本去向账,和旧账同一套词汇;Claw 的认领 / 转出 / 解决扩到两条车道不判噪音、不按相似度归并、不减少投递量
解决必带草稿回执;兜底必落欠条;一条收割命令写进仓库不给 Claw git 写权;Bridge 不自动开 PR;不设计 Infra bot 本身
看板四档、挂着的全列、转出信送达态、册子欠账、写路径配置态不设指标 / 阈值 / hard limit / 全局 QA 门;看板不发告警不 @
非白名单告警投递前改投 Claw;转出信是唯一「被 @」;fail-open 回退不动 Dispatcher、各发射源、D1 分类表;不给 Lead 补 Discord 告警频道订阅;不自动重投死信
2076 三条已知缺口(偶尔多一帖 / 被取代的旧轮次 / 没建成 thread 的工单)原样沿用 founder 裁定不修工作流升级每 15 分钟重发的源头(另开单)

我没证到的一条:Bridge 启动横幅里「值守令牌未设」那一行我没在日志里找到(日志可能已轮转);结论建立在环境文件、门控配置文件、账本三处文件级证据上,横幅留给实现 / QA 节点补。
