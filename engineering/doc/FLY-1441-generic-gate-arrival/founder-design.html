Generic Gate 到达发射

FLY-1441 · 设计方案 v2(重做版,Codex 评审 7 轮 APPROVED)· 2026-07-23

一句话

你的 ship 审批,今后只有一个来源:流程真正走完模板里的所有前置节点、抵达 Gate 的那一刻,由引擎亲手造出审批卡 —— 工程单自然是「QA 完了才到 Gate」,无 QA 的 generic/产品单前置完成即到 Gate,同一条规则,零补丁;任何 runner 都再也造不出一张野审批卡。

你的原话(方向锚点):「通知器不看 QA…只看流程是否走到了 Gate 节点,这个逻辑是对的。我们并不是所有情况都需要看 QA…一定要 generic,一定要简单,不要在上面打补丁。」

真正的 bug 是什么(生产账本铁证)

  • DAG 引擎本身没走错一步:FLY-1364 那单,引擎老老实实走了 implement→QA(fail)→implement→QA(pass),QA 过了才开 Gate。
  • 提前弹给你的 ship gate,是 implement runner 自己造的野审批卡:它的提示词里同时写着两句相反的话 —— 新合同说「流程推进归引擎,不许申请 ship 审批」,旧尾巴(FLY-887 时代)又说「跑 APPROVE GATE 流程」。runner 听了旧的,在 QA 还没开始时就往公共信箱里塞了张审批卡。
  • 光删那句旧话不够:野卡还有 5 个呈现入口 + 2 个投递面能把它送到你眼前;而且写卡的命令是直写数据库,没有任何服务端闸口。
  • 更隐蔽的坑:今天只有 land 类模板有引擎造的真审批卡;普通工程单的「真审批」一直靠 runner 自建的卡 —— 把野卡全拦掉而不补引擎载体,ship 就死锁(评审第一轮就抓过这个)。

结构模型(三个关键机制)

① 审批卡三种「批准后动作」,按模板能力自动推导

  • land 类:批准 → 引擎推进 land 节点(现有链路,一字不动);
  • 工程类(有写代码节点):批准 → 唤醒待命的实现 runner → 核验(卡、代码版本、身份全绑定)→ 合并 → 引擎确认合并后流程收口;
  • 纯产出类(无代码):批准 → 流程直接完成。

推导只看模板声明的能力,不看节点叫什么名字、模板叫什么名字。

② 证据在抵达 Gate 时冻结

QA/评审的通过证据在开 Gate 那一刻由引擎存档进审批卡 —— 你两天后才批准也不会因为「证据过期」卡死(现状:证据凭证只有 1 小时寿命,而你的审批窗口是 48 小时 —— 这个隐雷这次一并拆掉)。

③ 引擎全面去「QA 专名」

  • 发射器删掉模板白名单/schema/QA 条件,只认「抵达 terminal Gate」;
  • current_qa_attempt 等按节点名写死的引擎逻辑,全部改成按模板拓扑/能力推导;
  • 「重跑一轮」操作通用化成「按模板声明的 loop 重入」,不再叫 re-QA;
  • CI 里挂一把守卫尺:引擎代码再出现按节点名写死的行为,直接红。

灰度与回滚

新旧语义按「单」冻结:开关打开后新开的单走新规则,在途旧单原样走完 —— 不混代、不回填历史 Gate、不会因为翻开关把半路的单弄死锁。

关键取舍(和被否掉的方案)

决策取舍(为什么)
审批卡谁造引擎在 Gate 到达事务里原子造(land 已有骨架,泛化到全部)✕ 唤醒 runner 让它造 —— 依赖 runner 活着、提示词对、唤醒不丢,永远证不成不变量
野卡怎么拦7 个呈现面共用一个分类器 + 留痕告警✕ 只删提示词旧话 —— 修得了这次的触发器,挡不住下一个错误命令

QA 要不要进发射条件不进。「QA 完才发」是工程模板拓扑的自然结果✕ 上一版的 QA 谓词方案 —— 你亲自否的:不 generic、是补丁
实现 runner 等批准期间新驻留态「待命」(不显示待批、不触发超时、重启不被回收凭据)✕ 完成即注销 —— 批准时没人可唤醒;✕ 提前标「待批」—— QA 还没跑你就被打扰(这正是这次的体感)

诚实边界 — 做什么、不做什么

做
  • 引擎级 Gate 到达载体,三种批准后模式,全模板一条规则
  • 提示词冲突修复 + 7 面野卡闸 + 留痕
  • 合并后流程收口(现状:工程单合并后永远挂在 Gate 上 —— 顺手治掉)
  • 引擎去 QA 专名 + CI 守卫尺 + 拓扑回归测试(未到 Gate 零呈现 / 到 Gate 恰一张 / 无 QA 模板正向)
  • 按单冻结的灰度,零混代零回填
不做(各归各单)
  • 纯产出类模板这轮不支持「卡上直接打回重做」(卡上不放会失败的按钮;要改意见走 Lead,后续单补)
  • 不改工程模板主拓扑;不动 land 现有链路;旧单(开关前)原样走完
  • 不删旧通知器本体(旧单还要用,删除条件已写明)
  • 审批卡投递承诺「至少一次+以绑定卡为准」,不承诺物理上绝无重复卡
