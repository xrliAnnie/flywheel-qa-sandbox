设计一做完,你就能看见它

FLY-1404 设计说明 · 2026-07-21 · 设计已定稿(评审 5 轮通过),施工即将开始 — 这页不拦施工,看完有意见随时说
1一句话
以后每张走「设计 → 施工 → 验收」流水线的活,设计一做完,你就会在那张 issue 的 thread 里收到一份像这样的设计说明页 — 不用你追问;拿不出这页,设计就交不了差(系统会真的拦住它)。

现在(FLY-1392 踩过的坑)

→

→

施工照常同时开跑,不等你看完 — 你的反馈随到随改,以「设计修正附录」进分支(1392 当天已趟通这条路)
关键:这一步不拦施工。它把「你第一次看见设计」从「做完之后」提前到「做完设计的那一刻」— 返工发生在最便宜的时候。
3怎么立得住:三道门
门在哪里拦什么
① 完成命令自查 设计 runner 喊「我做完了」的那条命令里 检查设计说明页真的存在、真的入了库(在这张 issue 自己的文档文件夹里,防止拿别的文件充数、防止删旧文件也算数);没有 → 当场打回,并告诉它缺什么、怎么补
② 总控台验章 系统总控台(Bridge)收「设计完成」信号时 只认第一道门通过后盖的防伪章(一段只有新版命令在真检查通过后才写得出的凭据)— 老版本命令、崩溃残留的旧信号、绕道进来的信号,一律拒收或隔离,设计状态不会被悄悄推进
③ Lead 投递规则 Lead 的基础守则里 runner 上报「设计页好了」→ Lead 必须用标准投递方式发进对应 issue thread(带截图+链接,绝不发本机路径);发现漏了 → 让还活着的设计 runner 补发,但不回滚、不暂停施工
说明页本身有固定模板(就是你现在看的这页的五段结构),规定图优先、必须有「诚实边界」段 — 那是 1392 当天帮你抓出真问题的功臣。
4关键取舍(以及被否决的做法)
选择为什么
不拦施工选定 你的原话:「这不一定会拦着后续的 implement」。等你看完才开工 = 把你变成流水线瓶颈;反馈异步进来照样能改,还便宜。否决 阻塞式评审门
机器只查「有没有」,你查「对不对」选定 机器门保证这页永远会出现在你面前;内容好坏由你一眼判断 — 空壳页糊弄不过你,暴露本身就是机制。否决 让机器评审内容质量(做不准,还拖慢)
双层把关(命令 + 总控台)选定 评审时发现:只查第一层的话,旧信号重放、版本交错都能绕过去,「缺页就交不了差」就成了空话。否决 只信命令那一层
发 thread 的是 Lead,不是 runner选定 沿用现行铁律:runner 从不直接给你发 Discord。评审时还揪出一个存量 bug:现有发布命令有一种用法会把报告误发到公共频道 — 这次一并修掉。
反馈进来后谁改按 1392 实战 你的反馈 → Lead 转给当前握笔的施工 runner → 写「设计修正附录」(废除什么/保留什么/引用你的原话)→ 增量评审盖住。设计阶段不重开、流水线不回滚。
5诚实边界:这个设计不做什么
  • ✗ 不保证内容质量 — 机器门只验「说明页存在且入库」;一份糊弄的页子能过机器门,但会原样出现在你眼前,由你打回。
  • ✗ 不覆盖非三段式的活 — 只有走「设计→施工→验收」流水线的 issue 受此约束;单人小活、纯文档活不在内。
  • ✗ 没有机器级「已送达」回执 — Lead 漏看上报时,靠它下次接触这张 issue 时的自查兜底(主门在机器层,这种漏网预计很少);真发现兜不住再加。
  • ✗ 留了一个运维逃生开关 — 极端情况下运维可手动关门(关的时候会留下明显日志),但任何自动流程都不会替你关。
  • ✓ 这页本身就是第一份样品 — FLY-1404 自己的设计,就按这个模板交付给你。看完这页,你其实已经验收了这个模板长什么样。
怎么给反馈
直接在这张 issue 的 thread 里说就行。施工不会等你,但你的每条反馈都会以「设计修正附录」的方式进入分支、被增量评审盖住 — 和 1392 那天一样。
