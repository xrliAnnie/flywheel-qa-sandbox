结论

连接层过闸。把第五版那条 WebRTC 订阅会话接进 Discord 语音房，两个方向都是 Opus 原样转交，一个包都没重新编码；听得懂、答得快、10 分钟不断、后台只读回合在 Discord 里也走通了。

要带进「核心」单的三个问题（都不是连接层的问题）：

  • 插话慢、且 4/10 次会「先把刚才那句说完」：服务端要听清你第一个字才判定插话（平均 1.16 秒），判定后有 4 次它先把旧内容说完才回答新问题。
  • 远处有人说话会被当成在跟它说：风扇、键盘各 60 秒零误触发；远处人声 60 秒触发 1 次，它还认真回答了。
  • 它会自己决定把问题交给后台：「今天穿什么颜色」「详细讲讲怎么养绿萝」都被它交给后台去查，于是先说一句「我看看」再答。好处是不瞎编，代价是这些问题慢一拍、还会占后台额度。

founder 真人场（约 2 分钟）：你 6 句话它都听懂并接上了，程序端说完→开口均 1.2 秒；但它先夸口「能控制电脑」、查过才改口道歉，还不知道自己在 Discord 里——这是「大脑」层的事，下一张单要管。

额度：实时语音按音频时长计量（10 分钟场服务端记 585 秒），每场前后周额度读数都没动（<1%，而且账号是所有 Codex Lead 共用的，这是上界）。

1怎么接的

一个 Node 进程同时做三件事：以测试 bot（flywheel-test-3）身份进 Discord 语音房；和 Codex 内核开同一条 WebRTC 实时会话（参数与 CLI /voice 相同）；在两边之间搬运 Opus 包。另一个测试 bot（flywheel-test-1）扮演「说话的人」：播放 macOS 合成的中文语音，同时录下它在房里听到的回答。

「直接转交、不重新编码」成立了

  • 六场共 18,789 个上行语音包、62,197 个下行包，全部是 20ms / 960 样本，没有一个格式不兼容的包（任何一个不兼容就会自动停场，从没触发）。
  • Discord 那边收发都是 DAVE 端到端加密 v1，库在加密层之下给出的就是纯 Opus，直接能当 WebRTC 的负载用；反方向同理。
  • 唯一用到编码器的地方：启动时编码一个 20ms 静音帧，用来在你不说话时填空，保证上行时间轴连续。人声本身一次都没重编码。
  • 先做了一次零额度的回环：不接模型，把收到的包原样放回房里，Discord 往返约 225 毫秒。

第 2 场后改过一次上行缓冲策略（积压时追赶发送、超过 10 包才丢；起步缓冲 60ms），原因是第 2 场丢了 17 个包。之后各场丢包为 0（第 3 场有一次突发，丢 7 个）。

2说完 → 开口：5 次均值 1.58 秒（房里听到）

两个口径，都在各自进程里用同一个时钟算，不跨进程相减：房内 = 「说话的人」最后一个有声帧发出 → 它在房里听到模型第一个有声帧；程序端 = 我们进程收到你最后一个有声帧 → 模型第一个有声帧到达我们进程。

房内比程序端多出来的约 0.5–0.6 秒，是两段 Discord 传输（说话人 → 我们、我们 → 听的人，各约 0.1 秒）加上我们两侧的小缓冲（上行起步 60ms、下行常驻 3–4 包 ≈ 70ms），以及服务端判定「你说完了」的等待。

「说完 → 听到结果」里模型自己「先应一声」的习惯很明显：需要查的问题它会先说「我看看……」，所以你总是在 1.3–2.2 秒内听到声音，即使答案还没好。

3插话：10/10 能打断，但平均要 1.16 秒，且 4/10 会先把旧内容说完

做法：让它长篇回答，确认房里正在连续播放它的回答（≥1 秒、300ms 内仍有声）才开口插话「停一下，换个问题：X 加 X 等于几？」。回答已经自然停了的尝试作废补做。两场共 10 次有效（第 3 场 4 次，第 5 场 6 次）。

* 判定用时 = 插话的声音到达我们进程 → 服务端发来「用户开口」事件（同时截断旧回答）。房里听的人感受到的还要加上两段 Discord 传输和下行缓冲，约 +0.3 秒，也就是 约 1.2–1.7 秒后旧声音才停。

  • 慢在服务端，不在连接层：我们这边的缓冲总共约 140ms。服务端事件里新一轮用户发言总是带着第一个识别出的字（「听」「打」「停」），说明它要等识别出一个字才判定插话——对咳嗽、嗯啊比较稳，但就是慢。
  • 按预先定的判据（房内 1.5 秒内停下 且 直接答新问题），通过 3/10（#1、#2、#8：直接答，且判定用时 + 约 0.3 秒传输 ≤ 1.5 秒）。这是估算：房内纯音频的「停下时刻」被自然停顿和紧跟着开始的新回答干扰，直接量不干净，所以用服务端事件口径 + 内容结果；原始逐帧数据都在证据里。若只问「能不能打断」：10/10。
  • 「先说完旧的」是模型行为：服务端确实截断了（事件里旧回答在你开口约 0.2 秒处被截断），但它下一轮选择把刚才那句接着说完，再回答你。要改只能靠提示词（核心·大脑单）。

权限：原型的后台回合故意开成只读沙盒（和第五版一样），打不开浏览器是预期行为，不算本单缺陷；之后要开哪些权限，Lead 已在 thread 里回答，并记进 FLY-2886。

这一场暴露的都是「大脑」层的问题，连接层没有问题：

  • 它不知道自己能做什么（能力本身受限是预期，问题在它说错了）：先说「能控制电脑」，查过之后才改口道歉。它甚至问你「是通过哪个应用在跟我说话」——它不知道自己在 Discord 语音房里。接 Lead 时必须把「我在哪、能做什么、不能做什么」写进它的开场说明。
  • 语音里给不了链接：它说「你可以直接点这个链接」，你回「我看不到你的链接」。语音场景需要一个把链接 / 文字发到对应 thread 的出口。
  • 它叫你「小蓉」：名字来自 ChatGPT 账号，不是我们给的。

你这场的录音按邀请里说的只存本机（~/.flywheel/artifacts/FLY-2884-founder-s7/），不进代码仓库；仓库里只有日志和指标。

9没做到的、没证明的、下一步

  • 插话「1.5 秒内停下」只部分达到（在哪一步：服务端判定；为什么：要识别出第一个字才判定，均 1.16 秒 + 传输约 0.3 秒）。下一步：核心·连接层可以在我们这边做「本地先压低音量」——检测到人声就先把正在播的声音淡出，不等服务端；这不改变服务端判定，只改变人听到的。
  • 4/10 次先说完旧内容（在哪一步：模型下一轮的选择；为什么：它把被打断的回答当成还没说完）。下一步：核心·大脑单的指令里写明「被打断就放弃刚才的话，直接回应新的话」，再测。
  • 远处人声误触发（1/1）。下一步：核心·大脑单的「只在被叫到 / 明确在跟它说时才回答」规则；连接层可以只转发指定一个人的声音（本原型就是这样），但挡不住同一个麦克风里的背景人声。
  • 它不清楚自己的能力和所在场合（founder 场：先说能控制电脑，又问「你通过哪个应用跟我说话」）。下一步：核心·大脑单给它写明身份、场合、能做与不能做。
  • 语音里没法给链接（founder 场：「我看不到你的链接」）。下一步：连接层 / 大脑单加一个「把文字发到对应 thread」的出口。
  • 多人：原型只转发一个指定的人。多人同时说话要先解码混音再编码，那就不再是「直转」，另议。
  • 单场额度只能给到「<1% 周额度」这个上界；精确到分钟的计量只有服务端的音频时长。
  • Lead 身份、声线、记忆、工具：本单没做（本来就属于后续单）。注意：模型会用 ChatGPT 账号上的名字称呼人（它叫过「小蓉」），接 Lead 时要决定要不要。

function tick() {                     // 每 20ms（performance.now 校正漂移）
  if (idle && queue.length >= 3) idle = false;          // 起步缓冲 60ms
  let pkt = !idle && queue.shift();

③ 读 Opus 包时长（不解码，RFC 6716 TOC 字节）

function opusSamples(p) {
  const c = p[0] >> 3, code = p[0] & 3;
  const ms = c < 12 ? [10,20,40,60][c & 3] : c < 16 ? [10,20][c & 1] : [2.5,5,10,20][c & 3];
  const frames = code === 0 ? 1 : code === 3 ? (p[1] & 0x3f) : 2;
  return Math.round(ms * 48 * frames);
}
