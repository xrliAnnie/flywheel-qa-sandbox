隔离 founder Google Calendar 写凭据

让「AI 助理 Raya 是唯一能自动写你日历的程序」这件事由机器强制，而不再只靠一层会话劝阻。

Issue FLY-2204 ·（为 FLY-2137 补上真正的边界）· 日期 2026-08-31 · 状态：设计已通过独立评审，等你在 A / B 之间拍板

一句话

今天这台机器上，任何一个 AI agent（Claude / Codex / Gemini，或任何拿到命令行的程序）都能绕过 FLY-2137 的护栏，直接写你的 Google 日历——因为写日历的钥匙是「同一个电脑用户下人人可读」的；本设计把这把钥匙真正隔离出去，让只有 Raya 排会程序能用它。

1 · 问题：FLY-2137 自己承认漏掉的那半

FLY-2137 上线了一层会话护栏（在 Claude 会话里敲日历命令时拦一下的钩子），但它自己在文档里写明：拦不住三条路——① agent 把命令写进脚本再运行；② Codex / Gemini 直接连命令行；③ 直接读出机器里的钥匙、自己调 Google。

这三条路有一个共同的根：

写你日历的钥匙，在这台电脑上是「同一个登录用户下人人可读」的。

实测证实：任何拿到你这个电脑账号（xiaorongli）命令行的 agent，今天就能直接 gog calendar create … 写你的主日历，或者读出钥匙串里的令牌自己调 Google。护栏只挡住了最窄的一条，另外三条它结构上够不着。

2 · 一个绕不开的硬事实

在这台单人 Mac 上，「同一个电脑用户」根本不是一条边界。

同一个用户下的两个程序，可以互相读对方的私密文件、可以读对方在钥匙串里的令牌。任何「换个目录 / 换个名字 / 加个密」的做法，对同用户的 agent 都只是障眼法（obscurity——藏起来，但没锁上），不是隔离。这正是 FLY-2137 在护栏那层踩过的同一课，只不过下沉了一层。

所以真正能用的边界只有两类，必须同时上：

  • 权限边界（scope）：把你电脑用户手里那把「到处在用」的 Google 令牌，重新授权成不含写日历的权限。这样就算 agent 把令牌整个偷走，在 Google 那侧也换不出一次日历写。
  • 身份边界（POSIX uid）：能写日历的那把钥匙，放到一个专用系统用户（一个独立的电脑账号 uid，专给这个程序用）名下。你电脑用户下的 agent（没有管理员密码）就读不到它。

3 · 核心机制：把职责拆成三个互不越界的角色

光把钥匙和 agent 分开还不够——因为 Raya 自己会启动一个 Codex（AI）子进程，如果它俩同一个用户，那个 AI 又能读到钥匙。所以最终拆成三个各司其职的系统用户：

图 1 · 三角色隔离：绿色是可信最小程序，红色是被机器挡在四条路之外的 agent 域

  • uid A（agent 域）：Raya 的大脑 / 语音 + Codex，跑各种 AI。它没有日历钥匙，也没有调用写手的权限。
  • uid I（排会入口）：一个不跑任何 AI的最小程序，只认你本人的排会指令，是唯一被允许叫动写手的角色。
  • uid W（日历写手）：一个不跑任何 AI的最小程序，独家持有日历写钥匙，只接受来自 uid I 的请求。

四条红色虚线 = agent 想写你日历的四种办法（偷钥匙、直连写手、伪造排会、自己调 Google），每一条都被一个机器机制挡住。

4 · 数据 / 结构模型：谁拿什么钥匙

关键在于「每把钥匙的权限刚好够用、且注销边界互相独立」。凭据按消费者分开：

谁对日历的权限钥匙身份 / 注销域
你电脑用户下的日常 agent / 生活无日历（读写都去掉）你的 Google 账号 · 主令牌
FLY-2137 每日只读巡检只读你的账号 · 独立 OAuth 应用（独立注销域）
日历写手（方案 A）只能写「指定日历」独立 bot 账号 · 天然独立注销域
日历写手（方案 B）你账号的整域读写你的账号 · 须放独立 OAuth 应用
QA 测试只能写「QA 测试日历」独立 QA 账号 · 对你主日历无权限
为什么在意「注销域」？ 同一个 Google 账号 + 同一个 OAuth 应用，本质只有一份授权；撤销它会把这个应用下所有令牌一起作废。所以只读巡检、以及方案 B 的写手，都必须放到独立的 OAuth 应用里，否则「注销旧的写权限」会把它们一起误杀。（这条是评审第 3、5 轮抓出来的隐藏坑。）

5 · 三个方案（这是要你拍的板）

三个方案共用上面的机制，只在「写手用谁的钥匙」上分叉。A、B 都需要动系统层（建一个专用系统用户），这是只有你能决定的一次性操作。

推荐方案 A · 角色用户 + 独立 bot 账号

写手用一个独立的 bot Google 账号，你把它加成「指定日历」的协作者（writer）。它就算泄露，也只能碰被你授权的那几个日历，碰不到你的 Gmail / Drive / 其他日历；要收回就删一行协作者，不牵动你本人任何登录。这就是 issue 说的「按服务身份隔离」。

防住谁
✅ 所有 agent（无写权限 + 读不到钥匙 + 无管理员密码）· ✅ 写手泄露也只限被授权日历 · ✅ agent 伪造排会 / 直连写手
防不住谁
拿到你交互式管理员密码的人 · 直接攻破那个系统用户的人（但能力被限死在少数日历）· 浏览器 / 人类会话面（见第 8 节）
你要做什么
① 一次管理员密码授权（脚本建系统用户，约 1 次输密码）；② 注册 / 授权一个 bot Google 账号（约 3 步）；③ 给 QA 账号授测试日历协作权（约 2 步）。

备选方案 B · 角色用户 + 你本人的独立令牌

写手用你本人账号的第二把令牌，不用建新账号。但它必须放在一个独立的 OAuth 应用里（否则注销旧写权限会连它一起杀）。达标，但权限更大、更粗：

不达标 · 否决基线方案 C · 完全不动系统层

不建任何系统用户，Raya 还是照旧跑。这看起来最省事，但结构上做不到 issue 的核心要求：凡是 Raya 作为普通程序能读到的钥匙，agent 作为同样的普通程序也能读到（钥匙串的按应用授权绑的是共享的 node 解释器，agent 用同一个 node 就绕过了）；而且 Raya 和它的 Codex 必然同一个用户，前一节的问题无解。

结论：C 不达标，仅作否决基线。若你出于「绝不动系统层」的强约束只能选 C，那这个 issue 的核心目标在本机无法达成，应该重新定范围（例如接受「只有护栏 + 审计、机器强制无解」，或把 Raya 搬到一台独立机器）。

6 · 怎么安全上线、出问题怎么退

上线按「先立后破」：先把新写手搭好、实测能正常建 / 删你的排会，再去收回旧的写权限——中间任何一步不过就有序退回，绝不出现「Raya 突然写不了日历」的窗口。

图 2 · 部署 / 回滚状态机——提交点是「全部安全探针通过」，不是「能写就行」

一个关键顺序细节（评审抓出来的）：撤销旧写权限和重授只读，在同一个 Google 应用下是同一份授权，只能先撤销、证明旧的失效，再重新授权只读——不能反过来，否则会把新令牌一起杀掉。

7 · 认真考虑过、但没选的路

  • 只用钥匙串「按应用授权」，不建系统用户——不行：真正读钥匙的是 gog / node，是 agent 也在用的同一个程序，授权分不清谁是谁。要走通得给 Raya 重写一个签名的原生程序，工作量比建系统用户还大，还堵不住「伪造排会」。
  • 把钥匙搬到云上 / 远程代管——治标不治本：本机总还得留一把能调用云端的钥匙，同样要隔离，绕回原点；且远超本单范围。
  • 限制写手只能连 Google 日历的网络——降级为「加固项」，不作为达标依赖：写手还需要连 Google 的登录服务器等，做一个可靠的按用户网络围栏超出本单，不拿它撑达标声明。

8 · 诚实边界：这个设计做什么、不做什么

✅ 做到
  • agent 上下文里既没有写日历权限、也读不到写钥匙、也无法伪造排会去驱动写手
  • 唯一自动写入方 = Raya 写手，由机器（权限 + 系统用户 + 日历协作名单）强制
  • QA 只能写测试日历；你本人用网页 / App 完全不受影响
🚧 不声称防住
  • 已登录的浏览器会话：如果某个 agent 能操作你已登录 Google 的浏览器，它可以直接在网页上建事件——这属于浏览器 / 人类会话面，本单是「命令行凭据」治理，不声称防住它（如需覆盖另立单）
  • 拿到你交互式管理员密码的本地攻击者
所以「唯一自动写入方」这句话，达标范围限定在「机器命令行凭据 + Raya 的自动排会入口」这一面——这一点会写进要给你的决策包，让你知情后再拍。
