## 5. 与现有各节的一致性核对

改动只有两处,但要确认它们不和 design.md 别处打架。逐条核过:

| 核对项 | 结论 |
| -- | -- |
| 块① 的「前提」 vs §6 规则二 | ⚠️ 不冲突,但**块① 比规则二更强** —— 见下方专条,别当成「只是引用」 |
| 块① vs §3 mailbox 表 `DEAD` 行(「收件人已 terminal,或重投 3 次仍未 ack」) | ✅ 一致,无需改表 |
| 块① 的聚合窗口 vs §8 红线①(投递循环永远不主动发消息) | ✅ 不冲突。死信通知是一封**进 mailbox 的新信**,由正常投递循环送出 = 「有新信要投」;30 分钟窗口反而**削弱**了刷屏风险,强化红线① |
| 块② 的「in-flight 上限 3 批,也按批算」 vs §4 步骤 1(「在途未 ack 的**批**数 >= 3」) | ✅ 原文本来就是批级措辞,块② 是把它说清,不是改它 |

| 块② 的「因为【合批不是折叠】」 vs §4「合批 ≠ 折叠」子节 | ✅ 一致,是对它的回指 |

### ⚠️ 块① 的「前提」是新增规范,不是对规则二的转述(设计评审 Codex R1 抓出,已采纳)

初稿把这条写成了「✅ 一致,块① 是显式引用本节规则二」—— **说满了**。逐字看:

```
§6 规则二(design.md:150)  | 2 | 到期 + **收件人 session 已 terminal** | 🪦 立刻死信,不重试 |
                               ↑ 有「到期 +」这个前置条件

块① 的前提               (前提:收件人已 terminal 之后,新到的信【立刻】进 DEAD ——
                               ↑ 没有「到期」,是入队即判
```

规则二讲的是**租约到期时**发现收件人已 terminal 该怎么办;块① 讲的是收件人 terminal 之后**新到的信压根不用等租约**。§3 mailbox 表的 `DEAD` 行(「收件人已 terminal,或重投 3 次仍未 ack」)支持 terminal 是一个合法触发因,但**没有字面证明「terminal 后新到即刻 DEAD」**。

⇒ **块① 在这里建立了一条新规范。** 这正是「更正」应有的样子,不是矛盾,**但对 D 的实现者是实打实的差别**:

* ❌ 只在 lease expiry 的判断链里查 terminal —— **不够**
* ✅ 还要在 **enqueue / 投递准入**那一侧加一条 recipient-terminal 快速通道

本单**不因此改 design.md 的其他文字**(FLY-1580 明禁),只把这条说清楚记在这里。块① 的正文本身已经把这条规范写进 design.md 了,D 照它实现即可。
