③ 关键取舍(和被否掉的方案)

决定为什么 / 否掉了什么
纯新增一个包,零接线批次 1 对现有生产零行为变化;否掉「边建边接」——地基没验收前不让任何现网流量踩上来
设计 SQL 原文逐字落地索引和查询语句从设计终版逐字复制,测试锁住「每条查询真的命中索引」;否掉「实现自行改写 SQL」——改一个字,性能保证就作废
obligations 走真实表重建迁移老形→新形的搬家路径连同「旧数据一行不丢」一起进测试;否掉「直接建终版形」——那样搬家逻辑永远没被验证过
写通道用「先抢锁再干活」+ 改错行数整单作废否掉乐观锁/事后补偿——账本宁可慢一点,不可错一笔
唯一例外修正案(评审共同裁定)SQLite 有个官方怪癖:文本主键默认允许空值。全部 17 表显式堵死;设计归档原文不改,修正案单独记录、可审计
评审证据:plan 经 Codex 5 轮独立评审收敛(9 → 3 → 3 → 1 → 0 项),抓出并修掉的都是真问题:异步回调的「先提交后报错」窗口、UPDATE 绕过防护触发器、包深层路径绕过唯一入口、锁竞争把写通道永久卡死等。每一版 DDL 都在真数据库端到端跑通过(17 表 / 13 索引 / 全部查询命中索引 / 15 个恶意探针全被拒)。

④ 诚实边界 — 这单做什么 / 不做什么

做(批次 1)不做(留给批次 2-3)
建库(17 表全量,带完整护栏)· 10+3 个索引且逐条验证命中 · kernel 写通道骨架 · 迁移记账 + 热备份钩子 · 全套验收测试(含真双连接并发对抗) 消息消费循环 · dispatcher / 探针 / 告警逻辑 · 各 vendor 注入垫片 · 从 comm.db/JSON 信箱搬家切换(那是批次 3 的 stop-the-world 手册)——批次 1 期间新库不在生产路径上
  • 「短事务」有时长闸兜底,但它是下限保护,不是对所有慢操作的完备证明(诚实记录在案);
  • events 表禁止改历史,但归档时的删除权留给 kernel 纪律(归档协议本身在批次 3 验收)。
