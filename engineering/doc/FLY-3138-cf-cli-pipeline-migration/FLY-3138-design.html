安装包发布流水线：wrangler 换成 cf

FLY-3138 · 工程设计 · 2026-10-02 · 挂起设计评审 3 轮通过

① 一句话

等 cf 出正式版那天，把安装包分发的发布流程里所有 wrangler 命令一次换成 cf，Worker、存储桶、密钥的名字一个都不变；在那之前保持挂起，并且开工前要先过 5 道「闸门」，任何一道不过就停下问你，不硬做。

wrangler 和 cf：都是 Cloudflare 官方的命令行工具（在终端里敲命令操作 Cloudflare 的程序）。wrangler 是老的；cf 是 9/28 新出的，今天（10/2）还是公测版 1.0.0-beta.11，5 天出了 11 个测试版，命令还在变。

Worker：跑在 Cloudflare 上的一个小程序，这里就是给新用户发安装包的那个「门」。存储桶（R2）：Cloudflare 上存文件的地方，安装包放在里面。

② 核心流程：cf 正式版出来那天怎么走

一张挂起的单，最怕的是「到时候硬着头皮迁、迁坏了才发现」。所以设计的核心是 GA 当天先做一轮只读核对，5 道闸门全过才动手。

GA（正式版）：公测结束、官方说「稳定了」的那个版本。

闸门大白话不过怎么办
G1cf 真的出正式版了继续挂起
G2cf 能单独设一个密钥，并且能明确告诉我们「真的设上了」停，问你
G3迁完以后整个仓库不再需要装 wrangler换一种打包方式，还不行就不发
G4重新部署时，没写进配置里的那个「你手设的管理密钥」不会被抹掉停，问你
G5Cloudflare 账号 ID 能安全地填进程序停

③ 迁完后的发布流水线（一次完整演练）

步骤名、顺序、谁能触发（只能在 main 上、只能在 release 环境里、要手打 ACTIVATE 确认）全部不变，只把每一步用的工具换掉，并在每一步后面加「读回核对」。

读回核对：做完一步之后再去 Cloudflare 那边查一遍，确认真的生效了，而不是只看命令说「好了」。原因是 cf 公测版有个坑：在自动化环境里，某些命令会打印「Aborted.」（取消了）却仍然报告成功。

④ 数据 / 结构：什么变，什么不变

  • 配置文件：wrangler.toml（12 行）用 cf migrate 转成 cloudflare.config.ts，人审后提交。cf migrate：cf 自带的「把旧配置翻译成新格式」命令。
  • 设密钥：现在有 4 个地方在设密钥，迁完都走同一个小助手，密钥值只走管道、不写到磁盘、不出现在命令行参数里。
  • CI 演练：每次提 PR 时，CI 会不带任何账号凭据地「假装部署一次」，并检查安装包签名器等 3 样东西确实被打进了包。CI：每次改代码自动跑的检查。
  • 自动检查规则：从「数 wrangler 出现几次」改成「任何地方出现 wrangler 就报错」，并禁止「整包上传密钥文件」这种写法。

⑤ 关键取舍和被否决的方案

方案结论为什么
现在就迁一半（cf + wrangler 并存）否决公测期间命令还在变，等于迁两次；安装包没人用，不急。
现在用 cf 的「部署时附带一份密钥文件」代替单设密钥否决① 密钥要写到磁盘上；② 不知道会不会把你手设、刻意不进 CI 的管理密钥抹掉；③ 要打乱「先设密钥、再部署、再写指纹」的顺序。
命令说成功就算成功否决cf 有「取消了却报成功」的坑，必须每次看到明确回执再写下一个。
在配置里声明「这些密钥必须存在」默认不做有两个密钥是部署之后才写的，声明了反而会让第一次部署卡死。
配置里判断「这次是不是演练」来决定账号 ID否决没有可靠的判断方法；改成配置永远严格，CI 演练只给一个全零的假 ID，真部署前专门拒绝它。

⑥ 诚实边界：这个设计做什么、不做什么

  • 做：一份「cf 正式版那天照着做」的计划 + 5 道闸门 + 每道不过时的退路；保证名字不变、你手设的管理密钥不被抹、每一步都读回核对。
  • 不做：今天不改任何代码、不装 cf、不碰你的 Cloudflare 账号；不碰 npm 发布那半边；不改 Worker 的行为。
  • 不确定：cf 正式版的具体命令名、回执长什么样，今天没法知道——所以计划里写的是「到时候要核对的 11 项」，而不是假装知道。
  • 需要你：迁完后的那次真实演练要动真实账号，由你（或你授权）手动触发；任何闸门不过都会回来问你。
  • 沙箱说明：本次设计跑在测试沙箱里，真正要改的流水线文件只在正式仓库，设计按正式仓库的现状写，实施当天还要再核对一遍。
