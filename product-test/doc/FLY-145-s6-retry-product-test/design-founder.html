FLY-145 · S6 沙箱单：只交付文档，不动代码

Issue FLY-145 · 2026-09-25 · 设计节点 eng_design · 分支 project-slot-1-FLY-145

1. 一句话总结

FLY-145 是一张用来测试「部门范围检查」的假单，本设计决定一行代码都不改，实现节点只交一个纯文档 PR：里面放 S6 的预期结果表和证据模板，让 QA 在 Discord 里对着填。

名词：部门范围检查（dept-scope）——Bridge 服务端按 issue 标签判断哪个 Lead 有资格启动 Runner 的那道关卡。Bridge 是 Flywheel 的调度中枢服务；Lead 是常驻 Discord 的部门主管 bot；Runner 是被 Lead 启动去真正干活的 Claude Code 会话。

2. 核心流程：四个 Lead 看到同一张单会发生什么

QA 把 FLY-145 贴进 cos-test 频道，四个测试 Lead 都会看到。每个 Lead 都不自己猜，直接去问 Bridge「我能不能启动」，由 Bridge 统一裁决。这就是 FLY-127 定下的规则：Lead 信 Bridge，不预先过滤。

名词：spawn——Lead 通过 Bridge 启动一个 Runner 的动作。403 DEPT_SCOPE_REJECT——Bridge 返回的"你不在范围内"错误码，Lead 收到后按规则不重试。

3. 数据与决策模型：Bridge 怎么判、预期表长什么样

Bridge 里负责裁决的模块叫 department-registry（部门注册表：记录每个 Lead 管哪个部门标签、能不能启动 Runner）。它按固定顺序做判断，先命中先返回：

预期矩阵（唯一事实来源，模板 JSON 由它派生）

Lead部门标签预期结论预期 Discord 表现启动 Runner
flywheel-test-2Product-Testok认领 + 启动通知是
flywheel-test-3Ops-Testlabel_mismatch至多一行「这是 test-2 的范围，我不启动」否
flywheel-test-4Finance-Testlabel_mismatch同上否
flywheel-test-1PM-Test（cos）lead_cannot_spawn沉默，或至多一行「我不负责启动」否

为什么 test-1 是 lead_cannot_spawn 而不是 label_mismatch：配置加载器强制要求标签里带 "PM" 的 Lead 显式声明不能启动 Runner，否则整个 Bridge 起不来；而"能不能启动"这一步在"标签对不对"之前判。

证据模板（实现节点新增的 JSON，QA 填空）

字段谁填含义

4. 交付物结构：这个 PR 里到底有什么

名词：docs-only PR——只改文档、不改代码的合并请求；仓库的 CI（自动检查流水线）会识别出这种 PR 并跳过重型测试。

5. 关键取舍与被否决的方案

✅ 选定：零改动，纯文档 PR

忠于 issue 原话「不需要任何代码工作」。

S6 的价值在 Discord 侧的证据，不在仓库代码。

给 QA 一份预填好的对照表，减少人肉推导出错。

❌ 否决：顺手加一个 S6 单元测试

注册表的拒绝路径已有测试覆盖（PR #170 说明），再加是重复。

违反项目规则「不在本 issue 修顺便发现的东西」。

❌ 否决：直接标 blocked 或空转完成

设计节点的完成契约要求探索、调研、计划、设计页齐全并过评审。

跳过会让后继实现节点没有输入。

⚖️ 取舍：证据格式沿用旧例

对齐 FLY-1189 的 QA 证据 JSON 形状，QA 用同一套工具汇总。

代价是模板里有几个 QA 永远不会用到的字段（如 campaign_id 可能为空）。

6. 诚实边界：这个设计做什么、不做什么

做
  • 写清四个 Lead 的预期结论与依据。
  • 给 QA 一份可直接填写的 JSON 模板和填表说明。
  • 把设计文档随 PR 合进 main，留档。
不做
  • 不改 Bridge 注册表、Lead 规则、部署脚本；不加测试。
  • 不去 Discord 贴 issue 号，不代 QA 填证据，不判 PASS / FAIL。
  • 不归档 issue（S6 PASS 后由 QA / Lead 处理）。

两个没法在本会话闭合的事

  • Linear 在本会话无法读取（鉴权失败），issue 当前标签是否仍只有 Product-Test 未能核实。QA 跑之前应再看一眼。
