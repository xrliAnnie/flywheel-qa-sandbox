## 0. 背景与病因

v1 的消息层有四条流,每条流的语义都不一样:

| 流 | 耐久账写在哪 | 有队列层吗 | 怎么送到眼前 | 有租约吗 |
| -- | -- | -- | -- | -- |
| 她(founder) → Lead | `lead_inbox` 一条影子行(`carrier=external`) | ❌ | Discord 适配器**直推**进上下文 | ❌ |
| Lead → Lead | 同上 | ❌ | 同上 | ❌ |
| Runner → Lead | `messages` → `lead_inbox`(**写两遍**) | ✅ claim + owner 围栏 | per-Lead inbox loop → 适配器 → JSON 文件 / unix socket | ⚠️ 字段在,不到期 |
| Lead → Runner | `messages` 一条 | ❌ | `wakeRunnerMailbox()` 直接写 runner 的 inbox.json | ❌ |

**实测数据(**`~/.flywheel/comm/flywheel/comm.db`**,2026-07-31):**

```
lead_inbox 总行数              44,567
  已投递(consumed_at)         44,391   99.6%
  标了 processed_at            38,877   87%
  投了但两样都没标                  30   0.07%   ← 闭环其实是闭上的
  重发过 ≥1 次                 30,020   67%
  重发过 ≥2 次                 14,288   32%
  本身就是重发副本              18,595   42%    ← 表 42% 的重量是它自己的回声
  被升级过(escalated_at)        6,218   14%
  read_at 有值                      0           死字段
  真消息(resend_of 为空)      25,972
```

**病因不是「没有 ack 机制」,而是:**
`ack 慢 → watchdog 催 → 催的时候` **新建一行** `→ 表膨胀 → 更慢` 的自激循环。

**根本设计错误:重投应该是「同一条消息重新变可见」(SQS visibility timeout 的做法),我们做成了「复制一份新的」。**

## 1. 两条铁律

1. **队列只负责「送到没送到」,永远不 track「办没办」。** 队列的 ack 只表示「收件人接下了这个义务」,不表示业务完成。(DR#1:*Never equate queue acknowledgment with proof that an unmodifiable AI agent actually completed the action.*)
2. **永远不替 agent 建一张它看不见、也没法关闭的账。** 那样的表只会堆积,一条也销不掉,而且会导致二次执行。

## 2. 目标架构

```
她 / 其他 Lead / Runner / Lead / cron
                 ↓
      📮 一张 mailbox 表(to_agent 区分收件人)
                 ↓
      🔁 一个投递循环(现有 per-Lead inbox loop 扩容到所有收件人)
                 ↓
   按后端分流(适配器不变,复用现有的)
      Claude → inbox.json + sidecar → 官方 poller
      Codex  → unix socket
                 ↓
            收件人(Lead 或 Runner —— 同一套)
                 ↓ ack
      📋 task 表(仅 Lead;在 ack 的同一个事务里由系统自动建)
```

**关键:四条流其实只有一种流程,**`from_agent` **/** `to_agent` **的值不同而已。最后一公里(适配器 + JSON/socket + 官方 poller)一行不改。**

## 3. 两张表的状态机

### 📮 mailbox —— 只答「送到没送到」

| 状态 | 谁改 | 触发 |
| -- | -- | -- |
| `QUEUED` | 系统 | 有人发信 / 租约到期回来 |
| `LEASED` | 系统 | 投递循环取走并盖 30 分钟租约 |
| `ACKED` | **agent** | 它 ack —— **队列对这封信的职责到此结束,永不再管** |
| `DEAD` | 系统 | 收件人已 terminal,或重投 3 次仍未 ack |

### 📋 task —— 只答「办没办」

| 状态 | 谁改 | 触发 |
| -- | -- | -- |
| `OPEN` | 系统 | **在 ack 的同一个事务里**自动建(仅 Lead) |
| `DONE` | **agent** | 它调 `done` |
| `NO_ACTION` | **agent** | 它调 `no_action` + 原因(**这是它的合法出口**) |

**task 表挂在 agent / issue 上,不挂 session。**(实测:Lead 的会话可跨 45 天、341,252 行、1.47GB;而 agent 自带的 task list 是 session 级,单位错配。)

## 4. 投递循环每 tick 的逻辑

频率沿用现有:**活跃 1 秒 / 空闲 30 秒,不新增任何定时器。**

```
对每一个收件人:
  1. 这人在途未 ack 的批数 >= 3?  → 跳过        (in-flight 上限 = 3 批,可配)
  2. mailbox 里有没有可投的信(从没投过 或 租约已过期)?
     没有 → 什么都不做                          ← 防 watchdog 红线①
  3. 合批:同一个 from_agent + 60 秒时间窗内 + 一批上限 5 条
  4. 盖租约 claim_expires_at = now + 30min
  5. 顺手一句 SQL 查欠账数(仅 Lead):
     select count(*) from task where owner=? and status='OPEN'
  6. 投递。门铃文本写三件事:
     ① 这一批的 id ② 你必须 ack 才有下一批 ③ 你另外还欠 N 件
```

**「有新进来」的精确定义 = mailbox 里有** `to_agent=X` **且未投或租约已过期的信。与 task 表无关。**
**task 表永远不触发投递,它只提供一个数字写进门铃文本。**

### 合批 ≠ 折叠

* **合批** = 一起投递,批里**每条仍然是独立一行、独立建 task**,信息一条不少
* **折叠** = 合成一条,信息会丢 —— DR#2 明确禁止折叠「不同的提问」和「有副作用的命令」

**我们做合批,不做折叠。**

### in-flight 上限为什么是 3 不是 1

DR#1:常见默认是「有序投递 + prefetch 窗口 > 1」,**「必须销账才给下一封」是显式的特殊设置**。窗口=1 会带来**队头阻塞**(它卡住不 ack,后面全堵住)。
让 ack 变刚需的推力来自另外两处:**未 ack 的批租约到期会重投同一批** + **门铃每次都带欠账数**。

## 5. Lead 与 Runner 的职责差异

|  | Lead | Runner(本期范围) |
| -- | -- | -- |
| ack 信 | ✅ 必须 | ✅ 必须(一样) |
| 进 task 表 | ✅ 系统在 ack 时自动建 | ❌ **不建** |
| stop 时 | hook 查 **task 表**有没有 OPEN,有就不许停 | 只要求**发一条「我停了 + 停的原因」**,不查表 |
| 销账动词 | `done` / `no_action` + 原因 | 无 |

**Runner 不建 task 的三条理由:**

1. Runner 一轮活 ≈ 一个 session,**它自带 task list 的生命周期单位刚好匹配**(Lead 才是单位错配的那个)
2. 它的主线任务由 DAG 跟踪(design → implement → QA → ship)
3. 它收到的插入消息多是即时性的(答问、批准)

**⚠️ 明确接受的风险:本期不覆盖 Runner「ack 了但其实没办」的漏。这是有意识的范围决策。**

**Runner stop 通知必须带「停的原因」:** `干完了 / 卡住了 / 等审批 / 撞额度 / 上下文满了` —— 否则 Lead 收到「我停了」还是得去看终端,不知道该派下一个还是去救它。

## 6. 死信闸

判断顺序:

| # | 条件 | 动作 |
| -- | -- | -- |
| 1 | 租约**没**到期 | 什么都不做,继续等它 ack |
| 2 | 到期 + **收件人 session 已 terminal** | 🪦 **立刻死信,不重试** —— 「收件人不存在」≠「收件人没响应」 |
| 3 | 到期 + 收件人活着 + 重投 **< 3 次** | ♻️ **原地重新可见**:state 回 `QUEUED`,`retry_count+1`,**不新建行** |
| 4 | 到期 + 已重投 **3 次** | 🪦 死信 |

**死信 ≠ 删除,死信 = 换一个收件人。** 把该收件人的所有死信**打包成一封新信**,`to_agent` = 它的 Lead,内容为「runner-X 有 N 封信始终没 ack,可能已下线,摘要…请决定:重新派 / 丢弃 / 转给别人」。

Lead 收到就是一封普通的信,走同一套流程。**一个死掉的 runner 最多产生一封死信,不是无限条。**

## 7. 出口把门(替代 watchdog)

|  | Claude Code | Codex |
| -- | -- | -- |
| 机制 | `Stop` 钩子**同步硬拦**(`decision=block` + 理由) | **无主回合 stop 事件** → 用 `config.toml` 的 `notify` + `turn-ended` 回灌唤醒 |
| 现状 | 已配置且已在用(`~/.claude/hooks/discord-reply-enforcer.py`) | 已有 `notify` 配置 |
| 行为 | 根本停不下来 | 停了,然后马上被叫醒 |
| 可靠性 | 强 | 弱一档 → **必须靠租约到期重投兜底** |

## 8. 三条防 watchdog 红线

1. **投递循环永远不主动发消息** —— 只在有新信要投时动作,欠账数是搭便车写在门铃文本里的一行字。没有新信 = 一个字都不发。
2. **欠账数不是一条独立消息** —— 它是门铃里的一行字,不占一封信、不产生新行。杜绝「重发生成新行 → 表膨胀」。
3. **永远给 agent 一个合法出口** —— 被 stop hook 拦下来时可以 `no_action` + 原因把这条关掉。

> **watchdog 为什么会死循环?因为它没有出口。** 它基于「你多久没动」判断,而 agent 无法声明「我不打算动」,所以只能被反复催,催到 page founder。新设计里那个「反复催」的位置,被一个 agent 自己能按的按钮取代了。

## 9. 本期明确不做

* 优先级排序逻辑(只留字段位)
* 折叠 / 去重逻辑(只留 `collapse_key` 字段位)
* 消息分类(引擎不是 LLM,判不了「阻塞性提问 vs 进度汇报」,硬做就是乱填)
* DAG 对接
* 推广 Action List 到 Runner
