## 1. The 18:39 PT incident (2026-05-06)

Simba posted a single mixed routing message in `#geoforge3d-core`:

```
@Peter @Oliver
Product: GEO-346, GEO-348
Operations: GEO-342, GEO-351
起 Runner
```

**Observed prod behavior** (before R3):
- Peter (product-lead) called `/api/chat-threads/create` for **GEO-342 and GEO-351** (Oliver's ops issues)
- Peter's bot then narrated reasoning visible in Discord — long messages explaining label mismatch
- Annie's reaction: "改得越来越坏" (PR #170 was reverted), then "修了个啥" (PR #206 superseded)

**Root cause** (per Codex 3-round design):
- **Layer 1a missing**: Simba allowed multi-Lead spawn directives in one message → ambiguous routing
- **Layer 1b too lenient**: dept Leads spawned on any "run / 起 Runner" keyword without classifying intent
- **Layer 2 missing**: Bridge had no server-side dept-scope check; if a Lead called `/api/runs/start` for a wrong-dept issue it succeeded

---

## 2. R3 fix: 3-layer defence

### Layer 1a — Simba split routing (`cos-lead/identity.md` § "Department Routing Discipline")

A backend routing message **must** mention exactly one dept Lead. Simba splits into separate messages, one per Lead. Discussion (multi-`@`) is still allowed but must use non-spawn verbs.

### Layer 1b — Lead Action Gate (`shared/department-lead-rules.md` § "Action Gate")

Before calling `/api/runs/start`, the Lead semantically classifies the message:

1. **Direct spawn** = single-`@` to me + one Linear ID + assignment intent → spawn
2. **Ambiguous** = single-`@` to me + one Linear ID + unclear intent → confirm-to-spawn (`要起 Runner 吗？起/不用`)
3. **Discussion-only** → reply, no spawn
4. **Bridge reject** → 1-line diagnostic per `reason` code, deduped per `(issue, reason)`

Multi-`@` in a spawn directive triggers the "Multi-Lead Mentions" rule — reply asking Simba to split, no spawn.

### Layer 2 — Bridge dept-check (`bridge/runs-route.ts` + `department-registry.ts`)

`POST /api/runs/start` calls `DepartmentRegistry.isLeadInScope()` after Linear pre-flight. On reject, returns a **machine-only** response (no free-form prose for the Lead to echo):

```json
{
  "success": false,
  "code": "DEPT_SCOPE_REJECT",
  "reason": "label_mismatch | issue_no_department_label | issue_multiple_department_labels | lead_cannot_spawn | lead_unknown | project_unknown",
  "canonicalLeadId": "ops-lead" | null,
  "silent": false
}
```

`canonicalLeadId` is always present (string or `null`) for stable shape across all reject codes. The english `decision.message` from `DepartmentRegistry` is logged server-side for operator debugging but **not** returned in the HTTP response — Leads translate `reason` into the canonical Chinese diagnostic per their Action Gate rule.

Gated by env var `BRIDGE_DEPT_SCOPE_REJECT` (default **on**). Toggle requires Bridge restart — Node `process.env` is a fork-time snapshot; runtime mutation is not picked up by a long-running Bridge process. Runtime no-restart toggle (admin endpoint) is tracked as a follow-up.

## 3. Replay assertions (paper-driven, against the new R3 rule)

Replay of the 18:39 PT message under R3 rules:

### Per-Lead trace

| Lead | Step 1 — `@`-mention check | Step 2 — issue ID count | Step 3 — verdict | Discord action | Bridge action |
|------|----------------------------|--------------------------|--------------------|------|---------------|
| **Peter** | `<@Peter>` AND `<@Oliver>` → **multi-Lead** | 4 IDs | Multi-Lead Mentions rule → spawn directive (`起 Runner`) → **reply asking Simba to split** | 1-line message: `Simba 请 split — one Lead per spawn message` | **NO** `/api/chat-threads/create`, **NO** `/api/runs/start` |
| **Oliver** | `<@Peter>` AND `<@Oliver>` → **multi-Lead** | 4 IDs | Same path | Same 1-line reply | Same — none |
| **Simba** | `geoforge3d-core` channel; Simba is the sender | n/a | identity.md "called someone else not you → don't reply"; Simba doesn't spawn anyway | Silent (its own message) | None |

### Asserted invariants

The R3 rules guarantee, on this exact replay input:

- ✅ **No `ensureChatThread` call from product-lead for GEO-342 / GEO-351** — Layer 1b's Multi-Lead Mentions rule blocks the spawn flow before any Bridge call. (The Bridge call is what creates the chat thread on the Lead's behalf.)
- ✅ **No Bridge call at all from any dept Lead** for this message — Multi-Lead Mentions explicitly says "do not call backend APIs."
- ✅ **No 长 narrate** mentioning "403", "label_mismatch", "Bridge", "只负责", "请找 Operations" — the only allowed reply is the short ask-Simba-to-split line. Bridge's diagnostic codes don't surface because Layer 1b prevents the API call.
- ✅ **Layer 2 still defends** even if Layer 1b is misinterpreted — if a future Lead misclassifies and does call Bridge with a wrong-dept leadId, Bridge returns `DEPT_SCOPE_REJECT label_mismatch` and the Lead replies one short Chinese line per the Action Gate rule (rule 4). Layer 1b's behavior on Multi-Lead spawn directives takes precedence and prevents that path here.

### Why this report does not include a runtime LLM replay

The Lead's classification is a Claude prompt-rule decision. Its behavior is not deterministic and is only observable on a real `setup-discord-lead` run. We rely on:

1. **Bridge-side test fixtures** (`packages/teamlead/src/__tests__/start-e2e.test.ts` § "FLY-127 — department scope reject"): asserts the *exact* response shape that the Action Gate rule's Step 4 reads, and the feature-flag toggle. 7/7 pass.
2. **DepartmentRegistry unit tests** (`__tests__/department-registry.test.ts`): asserts classification correctness across all reject codes. 28/28 pass.
3. **Production canary** (Step 5 below): runs the full prompt-rule path through real Discord with real bots before rollout.

## 5. Production canary plan (post-merge, pre-rollout)

This section is a checklist for the deploy step, not part of code changes.

1. Merge both PRs to `main` in their respective repos.
2. Bridge restart with `BRIDGE_DEPT_SCOPE_REJECT=on` (default). Verify env: `curl /healthz | jq .deptScopeReject` (if exposed) or check `[runs/start] FLY-127 dept-scope reject:` log on a synthetic reject.
3. **Restart Simba first** (cos-lead). Synthetic test: post a single mixed `@Peter @Oliver` spawn directive and verify Simba splits in production (or the GeoForge3D PR's prompt update guides Simba to split).
4. **Restart Peter and Oliver**. Synthetic test for each: post a same-dept spawn (`@Peter run GEO-XXX-product`) — expect successful spawn. Post a cross-dept spawn (`@Peter run GEO-XXX-ops`) — expect 1-line `label_mismatch` diagnostic.
5. Monitor Bridge log for **5 minutes** — no `ensureChatThread` calls from a Lead for an issue outside its scope.
6. **Rollback path** (if needed): `BRIDGE_DEPT_SCOPE_REJECT=off` + Bridge restart (≤30s). Prompt rules can be reverted via `git checkout main` in `~/Dev/GeoForge3D/.lead/` and a Lead restart.
