## Framework gap (root cause + workaround)

**Symptom**: `bash scripts/test-deploy.sh --from-branch <PR-branch> N` runs the Bridge from `${REPO_ROOT}/scripts/run-bridge.ts`, which `import`s `packages/teamlead/dist/bridge/plugin.js` from the same `REPO_ROOT`. `--from-branch` only switches the **sandbox repo / Runner code base**, never the Bridge code base. Until PR #156 lands on `main`, no slot deployed via main's framework loads its Bridge-side product code.

**Reproducible verification**:

```
$ grep "LeadWatchdog" /tmp/flywheel-test-slot-3/bridge.log   # → no match (Round 1A)
$ ls /Users/xiaorongli/Dev/flywheel/packages/teamlead/dist/LeadWatchdog*  # → no match (main has no source)
$ ls /tmp/qa-fly-83-fresh/packages/teamlead/dist/LeadWatchdog.js  # → built (PR branch fresh clone)
```

**Workaround used in Round 1.5**: clone the PR branch into `/tmp/qa-fly-83-fresh`, build, then symlink-equivalent (`cp -r`) the PR's `packages/teamlead/dist`, `packages/teamlead/scripts/claude-lead.sh`, and `scripts/lead-alert.sh` over `main`'s versions. After deploy the swap is reverted with `git checkout HEAD --` + manual restore.

**Permanent fix (recommended for the next sprint)**: extend `test-deploy.sh` with a `--bridge-from-branch` flag (or alias `--from-branch` to also rebuild the Bridge from the PR branch when the branch contains Bridge changes). Until then any standby PR that touches `packages/teamlead/**` will hit the same gap. Tracked as a follow-up note from this round; not blocking PR #156.

The "DUP attempt" message visible in Discord is therefore expected behaviour, not a regression.

PR #156 is solid. Ship.
