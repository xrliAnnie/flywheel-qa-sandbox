## Root cause analysis — Steps 6/7 fail

The v1.24.5 fix in `DirectEventSink.emitCompleted` is correct **at emit time**:

```ts
// FLY-115 v1.24.5 (FLY-120) — packages/teamlead/src/DirectEventSink.ts:267
if (route === "needs_review") {
  status = landingStatus?.status === "merged" ? "completed" : "awaiting_review";
}
```

The fix flips `awaiting_review → completed` **only if** `landingStatus.status === "merged"` is observable at emit time. In Round 6's run, the auto-approve response landed within 2:14 of stage_changed approve, so the Runner shipped, merged, and rewrote `land-status.json` BEFORE Bridge synthesized `session_completed`. In my run, auto-approve landed only after Bridge had already fired `session_completed` (because the first `test-auto-approve.sh` invocation used the default 60 s timeout and exited before the gate opened — operator/timing error, not framework regression).

Once Bridge has emitted `session_completed` with `route=needs_review` + `landing.pending`:

1. The predicate `isPostApproveShipComplete` in `post-ship-finalization.ts` returned **false** (landingStatus was `pending`, not `merged`), so `runPostShipFinalization` was never scheduled.
2. Bridge's `RunDispatcher.entry.promise` resolved at the same moment (Blueprint's `success = gitResult.commitCount > 0 && !result.timedOut` evaluated true the moment the Runner committed); the inflight entry was deleted, and there is no codepath that re-evaluates `landingStatus` and emits a second `session_completed` after the Runner subsequently ships and merges.

So Steps 6/7 are blocked by a **timing race** that's pre-existing and orthogonal to PR #153. The race is well-described by FLY-117/118/119/120 follow-up tickets (FLY-120 in particular: "Post-merge terminal signal contract"). FLY-120 was marked covered by v1.24.5 + ce3800e — but that coverage assumes the canonical Round 6 timing. When `session_completed` fires pre-merge, the post-merge contract is silently broken.

This is not a regression PR #153 introduced; the same race would manifest on `main` without PR #153 if `test-auto-approve.sh` is launched late enough.

## Honest Reflection

The team-lead asked for a Round 6 mirror (full 6/6 PASS S6 chain dogfood). I delivered a 5/7 PASS run because of an operator-side timing error: I launched `test-auto-approve.sh` with the default 60 s timeout instead of the explicit `--timeout 600` Round 6 used. By the time I diagnosed the gate-not-responded-yet state and relaunched auto-approve, Bridge had already synthesized the pre-merge `session_completed` with `awaiting_review`. That synthesizer is single-shot, so there is no recovery path; the Runner ships and merges as expected, but the FSM stays at `awaiting_review` forever.

This exposes a real framework hole — `runPostShipFinalization` only fires if the predicate evaluates true at emit time. In production (where Annie's response timing is unpredictable), this can manifest. Recommend a follow-up FLY ticket. But it does NOT block PR #153, whose product-level fix this round verified end-to-end with the residue scenario explicitly the PR claims to handle.
