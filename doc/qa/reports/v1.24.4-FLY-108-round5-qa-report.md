**Step 6 root cause**: Bridge's `session_completed` synthesizer (in `RunDispatcher` cleanup or its event-route path) emits the default route `needs_review` regardless of `land-status.json.merged === true`. The DB's own `decision_route=needs_review` is the smoking gun — no rule flipped it to a post-merge variant.

## FLY-120 Suggested Fix Directions (team-lead's call)

Two paths reach the same goal — make Bridge's terminal session_completed payload reflect the actual merge state.

1. **Bridge-side fix** (preferred for production correctness): in the session_completed synthesis path (`RunDispatcher` cleanup or wherever it lives in `packages/teamlead/src/bridge/event-route.ts` — needs Codex/worker investigation), read the Runner's `land-status.json` for the execution. If `merged === true`, emit the event with `route="auto_merged"` (or whatever post-ship terminal route the FSM accepts) and let FSM transition `running → completed` (or `approved_to_ship → completed`) directly. No `awaiting_review` detour.

2. **Runner-side fix**: change the Runner Blueprint so that after detecting merge, the Runner calls `flywheel-comm complete --route=auto_merged` (or equivalent) instead of just `flywheel-comm stage set completed`. That gives Bridge an explicit route in the event payload it doesn't have to infer.

Either fix unblocks Step 6 → Step 7 cascade. Production correctness leans toward (1) because the merge fact is observable from the file system; the Runner could already be torn down by the time `merged:true` is true.
