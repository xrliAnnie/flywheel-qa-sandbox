**The deadlock**:

```
Bridge:                "I need session_completed to flip status to awaiting_review."

approve API:           "I need awaiting_review status to accept approve."
test-auto-approve.sh:  "I need awaiting_review status to even check the gate."
```

Production parallel that Codex relied on must include *some* mechanism that flips status to `awaiting_review` purely on gate posting (or fires `session_completed` before the gate blocks). Test-slot Bridge does not have that mechanism — the Runner skipping `flywheel-comm complete` left no event for the Bridge to react to.

## Recommendation — Option 3 (per Annie's call)

Per team-lead's decision, change the **Runner-side** Blueprint to instruct the Runner to call `flywheel-comm complete` (or its equivalent that fires `session_completed`) **before** blocking on `flywheel-comm gate approve_to_ship`. That way:

1. Bridge sees `session_completed` → flips `sessions.status: running → awaiting_review`.
2. `test-auto-approve.sh` outer guard satisfied → SQL detects gate → POST approve → `gateUnblocked=true`.
3. Runner unblocks → `gh pr merge` → Bridge sees PR closed → finalization → tmux close.

Why Option 3 over the others:
- **Not Option 1** (drop the script's status guard): masks the real ordering bug; would also make the script accept any execution that happens to have a stale gate row.
- **Not Option 2** (relax the API): widens an action API's accept window, harder to reason about in production.
- **Not Option 4** (Bridge GatePoller flips status): puts the sequencing decision in the Bridge — invasive product change, easy to introduce subtle race conditions.

Option 3 is the smallest change that matches the production semantic (Runner reports terminal completion → Bridge reacts → Runner blocks for approval). worker-fly-115 picks this up as v1.24.4.
