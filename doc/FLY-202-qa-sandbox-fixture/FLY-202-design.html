FLY-202 DESIGN 节点交付 QA 测试基建 · 2026-08-14 本轮刷新(首版 2026-08-09)· slot-2 沙箱 · 设计者:engineer Runner · run 7c13c0ce
●1 · 一句话总结

给自动化测试系统一张真实存在的任务卡(就是 FLY-202 这张 issue 本身),卡上的活是一个小而稳的 5 步写文档作业——这样每次做端到端测试时,都有一个安全、可重复的"演习任务"可以派给 AI 工程师去跑完整流程。

●2 · 背景:为什么需要这张"演习任务卡"

Flywheel 的 QA 测试环境叫 test slot(测试插槽:一套与生产完全隔离的迷你 Flywheel,专门用来做实验)。测试时我们会往插槽里"注入"一张任务卡,让一个真的 Runner(被派活的 AI 工程师会话)从头到尾把活干完——这叫 E2E 测试(end-to-end,端到端:模拟真实全流程,而不是只测某个零件)。

问题在于:注入用的组件 PreHydrator(调度服务里负责在开工前把任务卡全文从 Linear 拉下来的模块;Linear 是我们的任务看板)要求任务卡必须真实存在。之前文档里引用的演习卡 FLY-SBX-1 实际上并不存在(FLY-197 发现的缺口),FLY-202 就是补上这个缺口的常驻夹具(fixture:一份反复使用的标准测试道具)。

任务内容刻意设计成"多步、慢速、零风险":AI 工程师一步一步写文档,每步之间给测试留出观察mid-work 窗口(任务干到一半的时间窗——很多监控功能,比如"卡死检测",只有在这种窗口里才测得出来)。历史上这张卡已经跑过两轮(沙箱 PR #29、#30),文件被基线重置清掉后每次都能重新来,天然可重复。

●4 · 数据 / 结构模型

整个任务只产出一个文件:doc/qa/sandbox-notes.md,固定四段结构。每一段的内容都从仓库实时取材,不许手工编造——这让每次演习的产出都可以逐段核对:

图 3 · 产出文档的结构与数据来源

分支与提交约定:用插槽预建的分支 project-slot-2-FLY-202,PR 开向沙箱仓库(sandbox:生产代码仓的隔离副本,怎么折腾都不影响真系统)的 main 主干;PR 里只允许这份文档,零生产代码改动。

●5 · 关键取舍与被否方案
决策点选了什么否掉了什么 · 为什么
任务卡形态 用一张真的 Linear issue(本卡) ❌ 伪造一份假任务数据 — 绕开了真实链路,测试框架明确要求"没有合成模式";❌ 复用生产任务卡 — 会污染真实看板
任务类型 纯文档 5 步作业 ❌ 改代码任务 — 有风险且构建检查不稳;❌ 单步任务 — 干完太快,留不出观察中间状态的窗口
文档落点 doc/qa/(与现有 QA 文档同区) ❌ 扔仓库根目录 — 和 QA 文档区割裂;❌ 每次换新文件名 — 反复演习会堆垃圾
重复执行策略 同名文件重建 / 刷新(幂等) ❌ 追加式累积 — 文件无限膨胀;"刷新"模式在历史 PR #30 已验证可行
●6 · 诚实边界:这个设计做什么、不做什么

做到:

  • 给后续实现节点一份完整合同:5 步作业 + 每段内容要点 + 分支/PR 约束。
  • 零生产影响:全程只碰沙箱副本,只产出 Markdown 文档。

不做:

  • 不验证 Discord 通知、不验证合并 — 合并是 founder-gated(只有创始人能放行的关口),属于测试的观察面,不属于这个任务本身。
  • 不保证目录表长期准确 — 内容以每次执行时的仓库快照为准,基线变了表就跟着变。
  • 不供生产环境使用 — 任务卡标题已写明 "do not pick up",只限测试插槽注入。
  • 设计交付不等待创始人审阅(节点合同规定);你之后的意见会由当班执行者以增量修正落地,不回滚。
  • 不承诺修复插槽环境已知缺陷 — 本轮观察到通知/发布链路存在 401 鉴权错误(task#51/#52,属测试环境自身问题);各节点只承诺如实上报失败,不隐藏。
●7 · 本轮实况(2026-08-14):分支基线漂移的发现与修复

本轮设计执行者入场审计时发现:测试插槽预建的工作分支(Git 里一条独立的改动线,活干完后合并回主线)基线是漂移的——它不是从沙箱主线切出来的,而是挂着 2088 个无关提交、涉及 3803 个文件(上一个测试战役遗留的生产仓代码快照)。若带着这种基线直接推送并开 PR,会复刻历史事故 task#55:一个 4863 文件的巨型 PR。

处置:确认远端没有同名分支后,执行者把本地分支重锚到沙箱主线(git switch -C … origin/main)。这不重写任何已发布历史,也不是 force-push(强推:覆盖远端已发布历史的危险操作,规程要求 Lead 明示批准才可用);重锚意图已用非阻塞消息报备 Lead(问题号 9c32493b),留出否决窗口。该处置已沉淀为设计合同的 Task 0:任何节点在第一笔提交之前,必须先核对分支与主线的差距。
