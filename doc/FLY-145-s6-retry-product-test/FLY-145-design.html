● 一句话总结

用一张全新的沙盒工单(只为测试而建、与真实开发隔离的任务单) FLY-145 投进 cos-test 频道,验证 4 个测试 Lead(负责在频道里认领任务并派活的部门主管 AI)中,只有 flywheel-test-2(产品部门)会认领并派发,其余 3 个全程保持沉默——即"按部门标签路由任务"这条规则在生产镜像环境下确实成立。

● 测试背景:这在验证什么

QA-FLY-127 是针对 Flywheel「任务认领路由」的系统性测试战役。其中 S6 场景 = 生产镜像多 Lead 矩阵:让 4 个测试 slot 像生产环境一样同时在线,再投放一张带部门标签的工单,看它们各自的反应是否符合分工。

规则由两层机制保证:一是 prompt 规则(写进每个 Lead 行为说明书里的软规则:标签不属于本部门就别响应);二是 Bridge(Flywheel 的中枢调度服务,负责分发消息和把关规则的后台程序)在 PR #170 引入的 dept-scope check(部门范围检查:放行认领前,用代码硬性核对任务标签与部门是否匹配)。

本轮是 S6 的重试轮:用全新工单 FLY-145 重新执行,保证证据不与上一轮混杂。测试流程:QA agent 在 cos-test 频道发布工单标识 → 各 Lead bot 各自反应 → QA agent 采集证据并判定 PASS / FAIL。本工单是 dummy(空跑)工单,不涉及任何真实代码改动;S6 PASS 后即归档。

● 双层防线:prompt 规则 + Bridge 硬校验

为什么一个越界的 Lead 抢不走任务?第一道防线是 prompt 规则(软约束,让它压根不响应);万一失效,第二道防线 Bridge dept-scope check(硬约束)会在认领 (claim)(Lead 宣布"这个任务归我部门处理"的动作)环节直接拒绝。只有标签匹配的 flywheel-test-2 能通过并 spawn Runner(派发一个自动干活的 AI 工程师会话):

● 关键取舍与被否方案
✓ 采用 生产镜像 4-slot 矩阵
✗ 被否 单 Lead 单元测试 — 单元测试只能证明"该认领的会认领",证明不了"不该认领的不会误抢"。误抢恰恰是路由规则最大的风险点,必须让全部 slot 同时在场才测得出来。
✓ 采用 双层防线一起验证(prompt 规则 + Bridge dept-scope check)
✗ 被否 只测其中一层 — prompt 规则是软约束,AI 有小概率不遵守;Bridge 检查是代码级硬兜底。真实防护是两层叠加后的最终外部行为,拆开单测意义不大。
✓ 采用 全新 dummy 工单(FLY-145)
✗ 被否 复用上一轮旧工单或真实开发工单 — 复用旧工单会让新旧两轮证据混在一起;用真实工单则把"路由是否正确"和"活干得好不好"两个变量搅在一起。dummy 工单零副作用,PASS 后可直接归档。
✓ 采用 由独立的 QA agent 投放工单并采集证据
✗ 被否 由被测的某个 Lead 或本 workflow 节点代发 — 证据采集者必须与被测对象分离,否则测试本身会污染频道行为,证据不可信。
● 诚实边界:这份设计覆盖什么、不覆盖什么

覆盖:

  • Product-Test 标签在 4-slot 矩阵下的一次性认领路由:正向(test-2 认领 + 派发)与负向(test-1/3/4 零反应)。
  • prompt 规则与 Bridge dept-scope check 叠加后的最终外部行为。

不覆盖:

  • test-2 认领之后 Runner 的执行质量(那是另一类测试的事)。
  • 其他部门标签(如工程类标签)的对称场景 — 属于 S6 矩阵的其他条目,另行覆盖。
  • 生产环境的真实 Lead、多工单并发竞争、Discord 平台故障等场景。
特别声明(链路区分):本 HTML 由 slot-4 的 workflow 引擎按 campaign-owner(测试战役归属方)链路派发的 design 节点产出;这与被测的「cos-test 频道认领链路」是两条独立通道。S6 的 PASS / FAIL 判定证据应以频道内各 Lead bot 的反应为准 — 本文档只是测试设计,不是执行记录,slot-4 的 workflow 派发行为不构成频道认领证据。若 QA 判定标准将 slot-4 的任何活动视为违规,请明确豁免 campaign-owner 链路,避免误判。
