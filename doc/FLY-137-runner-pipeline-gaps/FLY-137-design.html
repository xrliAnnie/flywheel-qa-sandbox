Runner Pipeline 四断点收敛设计

FLY-137 design-node handoff 2026-07-23 · 基于 GEO-371 / GEO-372 实测 gap + 本仓代码现状核对
●一句话总结
把 Runner pipeline 的四个断点——agent 文件不随 label 分发、design/code 两道 Codex review 不触发、onboarding 无显式阶段——收敛为一条确定性、配置驱动、fail-closed 的流水线：Bridge 按项目 agents: 声明做 3-step 分发并永远有兜底，review 触发从"祈祷 Runner 记得跑 hook"改为 Bridge 自动触发 + Runner 阻塞等待，onboard 成为一等 stage。
现状核对（诚实基线）：本仓快照中该设计的核心机制已经落地（AgentDispatcher 已接线、await-codex-gate 已存在、onboard 已进 VALID_STAGES）。本文价值 = 把散落在代码注释与两份审计里的设计整合成正式可交接设计（tradeoff + 边界），successor 的起点是验证性收口而非重写。

Step 3b

每次分发都带 matchMethod（override / label / default / shipped-generic / shipped-qa）留审计痕迹 — Lead 事后能看到某个 Runner 为什么拿到某个协议。
② Runner 生命周期（两道 Codex 硬门 + 一等 onboard）
spawn — Blueprint 把选中的 agent file 注入 system prompt（agentContext + Baseline Rules）
↓
onboard（新增一等 stage）— 跑 skill 前先上报（intent 语义）；成功或 skill 缺失 → brainstorm；硬失败 → complete --route blocked
↓
brainstorm → research → plan
↓ stage set design_review --plan <path>
🚧 Design Gate — Bridge 自动写 Codex instruction（或 codex-skip 的 skip.json）→ Runner 跑 /codex-design-review → await-codex-gate 阻塞轮询结果 JSON，超时/坏 schema 一律 fail-closed
↓
implement → test → PR 创建
↓ stage pr_created
🚧 Code Gate — 同一机制的 code review type → /codex-code-review → 阻塞等待 APPROVED
↓
approve / merge 边界 — verify-approval 查 codex_review_record：review 的最终强制点在这里，写文件当下是尽力触发
●数据 / 结构模型
配置（.flywheel/config.yaml）
agents:
  backend:
    agent_file: .flywheel/agents/product/backend-executor.md
    match: { labels: [backend, api] }
    departments: [product, platform]  # 可选 dual-register
  general:
    agent_file: .flywheel/agents/general-executor.md
    match: { labels: [chore] }        # depth 0 = catch-all
default_agent: general
路径合同：必须以 .flywheel/agents/ 开头；depth 0 = 跨部门 catch-all，depth 1 = dept-owned，depth ≥2 或 legacy .claude/agents/ 在配置加载期即拒（不是 spawn 时才炸）。
运行期产物（review gate 的账本）
.flywheel/runs/<execId>/codex/
├── design-review.json   # Runner 写
├── code-review.json     # {status:"APPROVED", rounds, ...}
└── skip.json            # Bridge 写 (codex-skip 治理跳过)
结果同步镜像进 Bridge 的 codex_review_record — 它是 merge 硬门（verify-approval）的输入。
保留名语义
generic永远 = shipped 兜底；项目不可占用
qa项目声明则覆盖，否则 shipped qa-executor.md — 每个项目零配置获得独立 QA runner
两层兜底刻意区分：general-executor.md = 项目级 catch-all（项目自己写、自己声明）；generic-executor.md = Flywheel-shipped 绝对兜底。两层共存、各司其职。
●关键取舍与被否决的替代方案
决策被否决的替代为什么
确定性 label 匹配Haiku 语义分类（早期版本含，后删）分发要可预测、可测试、可审计；LLM 分类带来不确定性 + 延迟 + 成本
显式 agents: 声明 + shipped 兜底Bridge 自动扫 .claude/agents/ 推断自动扫把文件系统变成隐式行为合同（改文件名 = 静默改分发）；显式声明同时保住 zero-config（靠兜底）与可审计
Bridge 触发 + Runner 阻塞 gate继承 user-level PostToolUse hooks（issue 原假设）hooks 是 prompt 层提醒、fail-open——Runner 忘了就静默跳过（GEO-371/372 实证）；gate fail-closed，review 从"约定"变"机制"
onboard = attempted（intent）语义"succeeded" 语义 / 独立 error stage跑 skill 前上报，dashboard 即刻见进度；失败复用 blocked 终态，不膨胀 stage 机
每次 spawn 都报 onboardonce-per-project 持久化标记标记要新状态 + 失效判定；每次报的成本只是 dashboard 一行
flat dept dirs（depth ≤1）任意嵌套子目录嵌套让 dispatch 优先级组合爆炸；一层已覆盖现有组织形态
无匹配兜底到 generic无匹配 → spawn 失败分发职责是"总能给 Runner 合理协议"，不是惩罚没打 label 的 issue
●诚实边界
这个设计做到
  • label/config 驱动的确定性 agent 分发 + Lead 显式 override + 双保留名兜底
  • design/code 两道 Codex review：Bridge 触发 + Runner fail-closed 阻塞 + merge 边界硬校验
  • onboard 一等 stage（intent 语义），失败走既有 blocked 通道
刻意不做 / 已知局限
  • 无语义分类：没 label 且没 default_agent → 一律 generic；分发质量取决于 label 卫生
  • design gate 触发依赖 Runner 上报 stage：不上报就不会在写 plan 当下被拦——最终强制点在 approve/merge 边界
  • onboard ≠ onboarding 质量证明：intent 信号，不校验 skill 内容是否被遵守
  • 不覆盖 Lead 侧 agent 体系、不解决 marketing-lead 缺位、不做任意 user hooks 的通用继承（被 gate 方案刻意替代）
Successor（implement 节点）建议起点：① 按现状核对表逐条 e2e 验证（label → agent 注入 → onboard → 两道 gate → verify-approval）；② 补目标项目的 agents: block + 11 个 executor 文件按路径合同迁移；③ 若要把 design gate 收紧到"写 plan 当下硬拦"，属 three_stage pipeline 层面的顺序强制，另开 issue。
