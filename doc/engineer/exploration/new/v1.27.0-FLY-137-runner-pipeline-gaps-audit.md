### 真实 Gap (实测确认)

#### Gap A — AgentDispatcher 在 production 路径上被 `undefined` skip 掉

**位置**: `packages/teamlead/src/bridge/run-infra.ts:231`

```ts
const blueprint = new Blueprint(
  hydrator,
  // ... 其它依赖
  undefined, // agentDispatcher  ← 这里
  checkpointConfig,
);
```

**影响**: 即使项目 `.claude/agents/{backend,frontend,designer,qa,marketing,operations,product}-executor.md` 都存在，Blueprint 永远走 baseline prompt 路径，从不读 agent file。Runner 拿到的 system prompt 没有 role-specific guidance — 一个 "designer" issue 跟一个 "backend" issue 跑同样的提示词。

**根因**: `AgentDispatcher` 类是 GEO-274 时期搭好的，但 wire-up 没接上 production 路径。test 覆盖了 dispatcher 本体逻辑，但没覆盖 `run-infra → Blueprint` 的注入链。

#### Gap B — Flywheel 没有 shipped 的 `generic-executor.md` fallback

**现状**:
- GeoForge3D 自己写了 `.claude/agents/general-executor.md` (catch-all)
- Flywheel repo 本身没有 shipped 的 generic agent — 新项目 onboard 时拿不到 fallback
- 即使 Gap A 修了，新项目 `.flywheel/config.yaml` 没 `agents:` block 时 `AgentDispatcher` 直接 return `null`，Blueprint 走 baseline prompt

**影响**: 新项目 zero-config 上线时，Runner 没有任何 agent role context。

#### Gap C — GeoForge3D `.flywheel/config.yaml` 没有 `agents:` block

**现状**: 看 `~/Dev/GeoForge3D/.flywheel/config.yaml`，只有 `checkpoints:`，没有 `agents:`。

**影响**: 即使 Gap A 修了，AgentDispatcher 还是拿到空 agents map，dispatch 返回 null。GeoForge3D 自己有 11 个 executor markdown 文件，但配置 block 没 declare 它们。

**值得讨论**: 是不是 Bridge 应该自动扫 `.claude/agents/*-executor.md` 推断 agents map，而不是要求项目手写 `agents:` block? 这样 zero-config 也能 work。

#### Gap D — `VALID_STAGES` 没有 `onboard` / `onboarding` 阶段

**位置**: `packages/teamlead/src/bridge/stage-utils.ts:6-19`

**现状**: 11 个 stage 里没有 onboard。GeoForge3D 有 `onboard` / `onboard-designer` / `onboard-product` 等 skill，executor 协议提到 onboard，但 Runner 跑 `flywheel-comm stage set onboard` 会被 `VALID_STAGES.has()` reject。

**影响**: 新 Runner 启动时 (Lead 不熟悉项目 / 用户) 没法 report onboard stage，Lead 拿不到 progress signal。

#### Gap E — Codex review hooks 没自动触发

**现状**:
- `frontend-executor.md` / `backend-executor.md` 等 executor 的 skills list 里包含 `codex-code-review` / `codex-design-review`
- 但 "skill" 只是 agent 自己记得调用 — **没有 stage 转换或 PR 创建后的自动触发**
- 我搜了 `packages/` 没找到 stage `pr_created` → 自动 Codex review 的 hook 实现

**影响**: agent 忘记跑 codex review 时，Lead 不知道；PR 上 codex review 不一致。

(spawn 信息说 v3 把这条放在 plan 里，需要确认是 Bridge-side hook 还是 prompt-level instruction.)

## Open Questions

(留给 brainstorm 跟 team-lead 决定)

### Product / scope

1. **Zero-config new project**: 新项目不写 `agents:` block，Runner 应该用什么？
   - 选项 A: Flywheel ship 一个 `agents/generic-executor.md`，Bridge 默认 fall back 到它
   - 选项 B: Bridge 自动扫 `.claude/agents/*-executor.md` 推断 agents map
   - 选项 C: Lead manual override 指定 agent

2. **Lead manual override**: Lead 派 Runner 时能否覆盖 dispatcher 选的 agent? (e.g. issue 没 label 但 Lead 知道这是 frontend)
   - spawn 提示 Annie 说 "yes"，但具体 surface 待定 (`/api/runs/start` 的 body 加 `agentName?` 字段?)

3. **Onboarding 触发条件**: `onboard` stage 是 Runner 第一次跑 issue 时永远跑，还是 only-once-per-project?
   - 如果 always 跑，Lead 看每个 Runner 都 onboard 浪费 attention
   - 如果 once-per-project，怎么持久化"已 onboard"标记?

4. **Codex review hook 范围**: 自动触发的话，
   - `pr_created` stage 之后强制 codex-code-review? (会增加 PR latency 但保证一致性)
   - `plan` 写完后强制 codex-design-review? (Annie 已经 push 过几次"plan 必须先 codex")

### Technical (worker 跟 Codex 自决)

5. **agent_file 路径解析**: `.claude/agents/foo.md` vs `agents/foo.md` (Flywheel-shipped) vs `~/.flywheel/agents/foo.md` (用户级) — search precedence?
6. **Dispatcher async/sync wiring**: `loadConfig` 是 per-project (run-infra:331)，AgentDispatcher 需不需要 lazy 创建?
7. **Existing test refactor**: AgentDispatcher 当前 test 不 mock `readAgentFile` (Blueprint 内部用) — Blueprint test 是不是要新加 integration 覆盖?
8. **CheckpointConfig 同步加 agentsConfig**: 不要在 run-infra 多次 load config — 一次 load 拿到两个 block。
