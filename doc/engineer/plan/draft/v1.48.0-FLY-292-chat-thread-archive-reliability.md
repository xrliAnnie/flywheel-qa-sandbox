## Problem

issue 完成时 Discord chat thread 的自动归档(Close Thread,保留消息)**时好时坏**。当它不归档时,Annie 只能手动**删除** thread 来清理侧边栏——而删除会永久丢失对话日志(她视之为"新时代的日志")。目标:让归档**确定性**——每次完成都归档,零手动介入,消息保留。

## Root Cause (已审计)

收尾链 `runPostShipFinalization()`(`packages/teamlead/src/bridge/post-ship-finalization.ts`)结构**已正确**:

- 原子 claim(`post-ship-finalization-${executionId}` UNIQUE)→ 单赢家执行完整流水线。
- 严格顺序:tmux cleanup → notifier(发"🏁 可关闭"消息)→ **archive 最后一步**。
- 所以"消息 un-archive thread"的竞态在编排器内部已被处理。

真正的 flaky 缺口在 `packages/teamlead/src/bridge/chat-thread-utils.ts`:

1. **`archiveChatThread()` 是整条链里唯一没有 timeout、没有 retry 的 Discord 调用**——单发 fire-and-forget `PATCH {archived:true}`,失败只 `console.warn`。Discord 瞬时失败(429 限流 / 5xx / 网络抖动)→静默放弃→**不归档**。这正好解释"有时归档有时不"。
   - 对照:`ChatThreadCreator`(创建)和 `thread-validator`(校验)都有 5s `AbortController` timeout;`runner-ready-to-close-notifier` 也有 timeout + 失败审计。唯独归档没有。
2. **无归档后校验**(issue 明确要求 "verified")。
3. **404 不标 missing**:`archiveChatThread` 遇 404(thread 在 Discord 已删,GEO-200)不调用 `markChatThreadMissing`,陈旧映射残留。
4. **`removeUserFromChatThread()` 同样无 timeout**,且它在 `archiveChatThread` 之前被 `await`——若它挂住会**阻塞下游 archive**(间接缺口)。

## Approach (最小聚焦改动,TDD)

主改文件:`packages/teamlead/src/bridge/chat-thread-utils.ts`,辅以 `post-ship-finalization.ts` 注入 dep + 写 audit。

### 1. `archiveChatThread` 硬化

签名增加可选 deps(向后兼容现有调用):

```ts
interface ArchiveDeps {
  fetchImpl?: typeof fetch;          // 测试缝
  markDiscordMissing?: (threadId: string) => void;  // 404 → StateStore.markChatThreadMissing
  maxAttempts?: number;              // 默认 3
}
interface ArchiveResult {
  archived: boolean;
  attempts: number;
  status?: number;
  error?: string;
  reason?: "ok" | "missing" | "unauthorized" | "exhausted" | "error";
}
```

行为:

- **每次尝试** 加 `AbortController` 5s timeout(对齐 `thread-validator` / `ChatThreadCreator` 既有约定)。
- **有界 retry**(默认 3 次,小退避):
  - 网络错误 / abort 超时 → 可重试。
  - `429` → 尊重 `Retry-After` header(秒;有上限 cap,避免长挂)后重试。
  - `5xx` → 可重试。
- **归档后校验**:Discord `PATCH /channels/{id}` 返回更新后的 channel 对象;确认响应体 `archived === true`。若 2xx 但未归档(防御性)→在配额内当作可重试。
- **不可重试终止**:
  - `404` → `markDiscordMissing(threadId)`,返回 `{archived:false, reason:"missing"}`(GEO-200)。
  - `401/403` → 返回 `{reason:"unauthorized"}`(bad token,重试无益)。
  - 其他 `4xx` → 返回 error,不重试。
- 全程不抛(fire-and-forget 语义保留),返回结构化结果供调用方/测试断言。

### 2. `removeUserFromChatThread` 加 timeout

同样加 5s `AbortController`,避免它挂住阻塞下游 archive。保留现有 404-忽略语义。fire-and-forget 不抛。

### 3. `runPostShipFinalization` 接线 + 可观测性

- 调 `archiveChatThread` 时传 `{ markDiscordMissing: (id) => store.markChatThreadMissing(id) }`。
- 用归档返回的 `ArchiveResult` 写一条 **audit event**(对齐 notifier 的事件审计风格:`chat_thread_archived` / `chat_thread_archive_failed`,带 threadId / attempts / status / reason)→ 事件日志可证明每次完成是否真归档 = 可靠性的验证手段 + 未来 reconcile 的依据。
- 顺序不变(archive 仍最后)。

## Tests (TDD,既有 `fetchImpl` 缝)

新增 `chat-thread-utils.test.ts`:

1. 首次 429(带 `Retry-After`)→ 重试后 200+`archived:true` → `{archived:true, attempts:2}`。
2. 持续 5xx 到配额耗尽 → `{archived:false, reason:"exhausted"}`,调用次数 = maxAttempts。
3. 404 → 调 `markDiscordMissing(threadId)` 恰一次,`reason:"missing"`,不重试。
4. 401 → 不重试,`reason:"unauthorized"`。
5. 2xx 但响应体 `archived:false` → 重试;最终成功 → `archived:true`。
6. 网络错误(fetch reject)→ 重试;`removeUserFromChatThread` 超时不抛。

扩充 `post-ship-finalization.test.ts`:

7. 归档成功 → 写 `chat_thread_archived` audit event(恰一条)。
8. 归档 404 → thread 标记 missing + 写 `chat_thread_archive_failed`。
9. 既有顺序/dedupe/never-throw 断言全部仍通过(回归)。

## Out of Scope (Lead 已同意 follow-up)

- **crash-between-claim-and-archive**:Bridge 在原子 claim 之后、archive 之前崩溃,会因 claim 已消费而永久跳过归档(无跨重启对账)。与观测到的"瞬时失败"主因不同。作为独立 follow-up(轻量 reconcile sweep:扫 completed 但 audit 无 `chat_thread_archived` 的 session 重试归档),不撑大本 PR。
- 人类在完成数分钟后往 thread 发消息合法地 un-archive(她在主动使用)——非 bug,不处理。

## Risk / Compat

- 纯收尾链增强;`verifyApproval` / merge 授权 / 字节兼容路径不受影响。
- `archiveChatThread` / `removeUserFromChatThread` 新增参数均可选,现有调用点零改动即可工作(渐进:`post-ship-finalization` 显式传 dep)。
