# Plan: projectName → Linear team/project auto-mapping

**Version**: v1.52.0 (tentative — re-version at ship if in-flight PRs land first)
**Issue**: FLY-371
**Date**: 2026-06-20
**Source**: FLY-371 issue text (proposal) + brainstorm gate (Lead: scope B confirmed)
**Status**: codex-approved (3 rounds)

---

## 1. Problem

没有任何代码把 Flywheel 的 `projectName`（projects.json 的 roster key）映射到它的 Linear `team` / Linear Project / scope-label。每个 Lead 必须在自己的 identity.md 里**硬编码** "create issues in team X / project Y / label Z"。

实证（现状）:
- `~/.flywheel/projects.json` 的 7 个 project 里 `linear` 字段**全是 null**（绑定不存在）。
- `.lead/flywheel-cos-lead/identity.md` 硬编码:
  - `GET /api/linear/issues?project=Flywheel&labels=Flywheel&...`
  - scope label id `ea47be69-f4d5-4a2c-ab1b-8ccdfe1ca5e9`
  - `save_issue({ team: "Flywheel", project: "Flywheel", labels: ["Flywheel"] })`
- `/api/triage/data` 只能按 `?project=` 过滤,**没有 labels filter** → 只有 label scope（没有 Linear Project）的 COE（如 FLY-351 的 Polaris）无法干净地 scope triage 视图。

新的 first-class Lead（Rafiki/Polaris…）因此每个都要 per-identity wiring。

## 2. Goal / 非目标

**Goal**: 在 projects.json 加一个 per-project 的可选 Linear 绑定,让 `/api/linear/create-issue`、`/api/linear/issues`、`/api/triage/data` 能从 `projectName` 自动解析 team/project/label。Lead 只需带 `projectName=<自己项目>` 调端点,就能 create/list/triage 到正确 Linear scope,identity 去掉硬编码。

**非目标**（明确排除,防 scope creep）:
- 不动 growth runtime 404（brainstorm scope B 已确诊 = growth 仓 config 错误,host-local fix,不在本 PR）。
- 不改 `mcp__linear-api__*` 直连 MCP 路径（只覆盖 Bridge proxy 端点）。
- 不动 `FlywheelConfig.linear`（config.yaml）—— 见 §3 设计取舍。
- 不重写 identity.md（identity 是 host-local `.lead/`，去硬编码是部署侧 follow-up;本 PR 只提供 by-config 能力）。

## 3. 设计取舍:绑定放 projects.json,不放 config.yaml

issue 文字给了两个候选:`.flywheel/config.yaml` 的 `linear:` **和/或** projects.json 字段。**选 projects.json**,理由:

1. **Bridge 已经持有 `ProjectEntry[]`**(`createBridgeApp(store, projects, ...)`),三个端点都在闭包里能直接拿到 —— 零额外磁盘 IO、零 per-request config 缓存/失效问题。config.yaml 在 projectRoot 仓里,Bridge 只在**启动时**经 run-infra 读一次(且只取 checkpoints/agents/skills/roles/doc_flow),热路径不读。
2. **byte-compat / opt-in**:`ProjectEntry.linear` 缺省 = 完全不变(沿用现有显式参数行为)。这正是本仓的既定模式(FLY-231 / FLY-247 "absent = unchanged")。
3. **风险**:config.yaml 的 `linear.team_id` 现状被注释明示为"NOT read at runtime"。一旦让 Bridge 在热路径读它,所有 project 的 config.yaml `linear.team_id` 立刻变 load-bearing —— 对既有 project(geoforge3d/joycon/sub…)可能引入行为变化甚至破坏。projects.json 路径**纯加性**,零既有行为变化。
4. **职责匹配**:Linear 绑定本质是**部署/roster 关切**(这个 Flywheel project 映射到哪个 Linear team/project),正是 projects.json(Annie 控的 host-local roster)的角色,而非 in-repo 的 config.yaml。

## 4. Schema

`packages/teamlead/src/ProjectConfig.ts`:

```ts
/** FLY-371: per-Flywheel-project Linear binding. Absent OR `null` ⇒ endpoints
 *  behave exactly as before (explicit params required). */
export interface ProjectLinearBinding {
  /** Linear team key (e.g. "FLY", "GEO"). REQUIRED when binding present. */
  team: string;
  /** Linear Project name. Optional — label-scoped COEs may have none. */
  project?: string;
  /** Scope label NAME. Optional. Applied on create, defaulted as filter on list/triage. */
  label?: string;
}

export interface ProjectEntry {
  projectName: string;
  projectRoot: string;
  projectRepo?: string;
  leads: LeadConfig[];
  generalChannel?: string;
  memoryAllowedUsers?: string[];
  /** FLY-371: optional Linear binding, resolved from projectName by the
   *  create-issue / issues / triage endpoints. NOT normalized (FLY-231
   *  pattern): absent/null stays as-is so existing in-memory ProjectEntry
   *  objects keep their exact shape. Type allows `| null` to be HONEST about
   *  the deployed shape (Codex R1 HIGH-1: the live roster literally has
   *  `linear: null` for all 7 projects). */
  linear?: ProjectLinearBinding | null;
}
```

### 4.1 Validation（`parseAndValidateProjects`，per-entry，紧跟 memoryAllowedUsers 校验后）

> **Codex R1 HIGH-1（破坏启动的坑）**:部署中的 `~/.flywheel/projects.json` 7 个 project **字面都是 `linear: null`**。因为 `typeof null === "object"`,任何"present 就当 binding 校验 team"的写法会让 `null` 漏过 object 检查、再撞 "team 必填" → throw → **Bridge 启动直接挂**。故 `null` 与 `undefined` **都视作"无绑定"**,在 binding 校验**之前**短路。

- `entry.linear == null`（即 `undefined` 或 `null`）→ **跳过校验、保持原值**（byte-compat;不 normalize）。
- 非 null 但非 object / 是 array → throw。
- `linear.team` 必须是 `trim().length > 0` 的 string,否则 throw（team 是绑定最小必需项）。
- `linear.project` / `linear.label` 若 present 必须是 `trim().length > 0` 的 string,否则 throw（Codex R1 LOW-7:`" "` 这种空白值要在 config 边界 fail,而非后面变成 confusing 的 Linear 404）。
- **不 trim/normalize 存储值**（与本仓既有 optional 字段一致,除非该字段已建立 trim 模式）。
- 多余字段:不强制 reject（与本仓其它 optional block 一致,只校验已知字段类型）。

### 4.2 纯 resolver

```ts
export function resolveProjectLinearBinding(
  projects: ProjectEntry[],
  projectName: string,
): ProjectLinearBinding | undefined {
  // null → undefined（Codex R1 HIGH-1: 消费侧不必到处防 null）
  return projects.find((p) => p.projectName === projectName)?.linear ?? undefined;
}
```

放 ProjectConfig.ts，和 `getProjectRoot` / `resolveLeadForIssue` 并列。

## 5. 端点改动

**统一约定**:新增入参 `projectName`（= Flywheel roster key，区别于既有的 `project` = Linear project name）。**显式请求参数永远覆盖 binding**（precedence: 显式 > binding > 现有缺省行为）。`projectName` 给了但解析不到 → **fail-loud**（不静默 fallback,防误路由 / 静默全量泄漏）。

### 5.0 共享 request-level helper（三端点统一,Codex R1 MEDIUM-5）

不要在三个 handler 各写一份 `projectName` 解析（会在 repeated-param / 空串 / unknown-vs-no-binding / null-binding 上漂移）。新建 `packages/teamlead/src/bridge/linear-scope.ts`,两个工具:

```ts
import type { ProjectEntry } from "../ProjectConfig.js";
import { resolveProjectLinearBinding } from "../ProjectConfig.js";
import type { ProjectLinearBinding } from "../ProjectConfig.js";

/** Framework-agnostic discriminated result（handler 映射到 res.status）。 */
export type ProjectNameResolution =
  | { ok: true; binding: ProjectLinearBinding | undefined }
  | { ok: false; status: number; error: string };

/**
 * 接 `unknown`（Codex R2 MEDIUM-2）—— create 走 JSON body,`projectName: 123`
 * 是真实的 malformed 请求;若签名是 `string | undefined`,非 string 检查在类型层
 * 不可达,实现者会 cast 掉那个 400。这里在一个地方处理 undefined / 数组(取首值,
 * 与 Express repeated-query 既有约定一致)/ 非 string / 空串 / 合法值。
 */
export function resolveProjectNameParam(
  projects: ProjectEntry[],
  rawProjectName: unknown,
): ProjectNameResolution {
  // 数组(repeated query param)→ 取首值,与 plugin.ts 既有 `Array.isArray(...)? [0]` 一致
  const raw = Array.isArray(rawProjectName) ? rawProjectName[0] : rawProjectName;
  if (raw === undefined) return { ok: true, binding: undefined };
  if (typeof raw !== "string" || raw.trim().length === 0)
    return { ok: false, status: 400, error: "projectName must be a non-empty string" };
  const entry = projects.find((p) => p.projectName === raw);
  if (!entry)
    return { ok: false, status: 404, error: `Unknown Flywheel project "${raw}"` };
  const binding = resolveProjectLinearBinding(projects, raw); // null→undefined
  if (!binding)
    return { ok: false, status: 404, error: `Flywheel project "${raw}" has no linear binding` };
  return { ok: true, binding };
}

/** 纯 scope 合并（list/triage 复用）。显式覆盖 binding。 */
export function resolveLinearScope(
  binding: ProjectLinearBinding | undefined,
  explicit: { project?: string; labels?: string[] },
): { project?: string; labels?: string[] } {
  const project = explicit.project ?? binding?.project;
  const labels =
    explicit.labels && explicit.labels.length > 0
      ? explicit.labels
      : binding?.label
        ? [binding.label]
        : undefined;
  return { project, labels };
}
```

> 决策:`projectName` 传了但是 **unknown project** → 404「Unknown…」;**known project 但无 binding** → 404「…has no linear binding」（两条**区分消息**,Codex MEDIUM-5）。两者都 fail-loud（不静默退回全量/无 scope）。不传 `projectName` → `{ok:true, binding:undefined}` = 行为零变化。

### 5.1 POST /api/linear/create-issue（plugin.ts）

body 加可选 `projectName`。先 `resolveProjectNameParam(projects, projectName)`;`!ok` → `res.status(r.status).json({error:r.error})`。拿到 `binding` 后:

- **team**: `effectiveTeam = team ?? binding?.team`，喂给现有 team-by-key 解析块（显式 team 仍优先；都没有则沿用 single-team default / multi-team 400）。**先解析 team** —— label 解析依赖 `targetTeam.id`。
- **Linear project**: `effectiveProject = project ?? binding?.project`。
  - 显式 `project`（caller 传的）→ **行为不变**（现有 `client.projects({filter:{name:{eq}}})` 取 nodes[0]，byte-compat）。
  - binding-derived（`!project && binding?.project`）→ **team-scoped**（Codex R2 HIGH-1:仅 first:2 + 名字去重还不够 —— 一个同名 project 挂在**错的 team** 上仍会被选中,而 create 是写路径,`createIssue` 同时收 teamId+projectId,跨 team 会被 Linear 拒(502)或建到错 scope）。按已解析的 `targetTeam.id` 收窄:
    `client.projects({ first: 2, filter: { name: { eq: binding.project }, accessibleTeams: { some: { id: { eq: targetTeam.id } } } } })`
    （SDK v60 类型已确认 `ProjectFilter.accessibleTeams.some.id.eq` 合法;或等价 `targetTeam.projects({ first: 2, filter: { name: { eq } } })`）。0 → **404**「project not found in team」;≥2 → **400 ambiguous**;1 → 用它。显式 `project=` legacy 路径不动。
- **scope label**（Codex HIGH-2，**team-scoped**）: 若 `binding?.label` 存在 → 在**已解析的 `targetTeam.id`** 内解析 label name→id:
  `client.issueLabels({ first: 2, filter: { name: { eq: binding.label }, team: { id: { eq: targetTeam.id } } } })`。
  - 0 match → **404**「scope label "X" not found in team …」（fail-loud,绝不静默丢 scope）。
  - ≥2 match（team-scope 后仍重名）→ **400 ambiguous**（不 `nodes[0]` 乱挑）。
  - 1 match → 把它的 id **追加**进 `labelIds`(与 caller 显式 label ids 合并去重)。
  - 注:label 解析针对 **effective team**(显式 `team` 覆盖 binding.team 时,label 也按那个 effective team 解析 —— 见测试)。
- 这个 resolver 是 label-name → label-id 的**唯一安全边界**(create 把 `labels` 直接当 `labelIds` 透传给 Linear),故必须 team-scoped + fail-loud。

### 5.2 GET /api/linear/issues（plugin.ts）

query 加可选 `projectName`。`resolveProjectNameParam` → `!ok` 直接 res.status。然后 `resolveLinearScope(binding, { project, labels })`:

- `effectiveProject = 显式 project ?? binding?.project`。
- `effectiveLabels = 显式 labels(**filter 掉空白后非空**) ?? (binding?.label ? [binding.label] : undefined)`。
  - **Codex R2 LOW-3**:现有 list 把 `labelsParam.split(",").map(trim)` 不过滤空串。`?labels=` → `[""]` 会被当"显式非空"从而抑制 binding.label、且产生无用 filter。故在调 `resolveLinearScope` **之前** filter 掉 blank labels(`.filter(Boolean)`),空白 labels 退回 binding。
- binding 同时有 project + label → **两者都作缺省**(project filter AND label filter)—— 正好复刻 cos 现状 `project=Flywheel&labels=Flywheel`。
- 不改 project 在 list 端点的解析方式（`queryLinearIssues` 按 name eq）—— list 是只读、错了不会写坏数据,保持现状。

### 5.3 GET /api/triage/data（triage-data-route.ts）

- **新增 `labels` query 解析**(issue 的 optional 项;镜像 issues 端点),传进 `queryLinearIssues` 的 `filters.labels`(底层已支持)。**此 filter 独立于 projectName 也能用**。
- query 加可选 `projectName` → `resolveProjectNameParam` + `resolveLinearScope`,同 §5.2。
- **sessions 也按 projectName scope（Codex MEDIUM-4）**:triage 当前查**全部** active sessions、只按 `leadId` 过滤。契约补全 —— 传了 `projectName` 时,先把 sessions 过滤到 `session.project_name === projectName`,**再**叠加既有 `leadId` 过滤。否则 label-scoped COE 拿到 scoped 的 Linear issues 却仍看到别项目的 session。
- **capacity 保持 global**（机器级 admission 关切,非 project-scoped）—— 文档 + 测试明确这个选择。

### 5.4 helper 归属

`resolveProjectNameParam` + `resolveLinearScope` 放新 `packages/teamlead/src/bridge/linear-scope.ts`(纯 + framework-agnostic,独立单测)。create-issue 的 team + project + label-name→id 解析需要 Linear 网络调用,自带 inline 逻辑(只复用 `resolveProjectNameParam` 拿 binding,不走 `resolveLinearScope`)。

## 7. Test plan（TDD: RED → GREEN → REFACTOR）

**ProjectConfig**:
- linear 缺省 → 不报错、字段保持 absent（NOT normalized）。
- linear 合法（team only / team+project / team+project+label）→ 通过。
- linear.team 缺失/空/非 string → throw。
- linear.project / linear.label 空/非 string → throw。
- `resolveProjectLinearBinding`: 命中 / project 不存在 / project 无 linear → undefined。

**resolveProjectNameParam（request-level helper，Codex R2 MEDIUM-2）**:
- 不传（undefined）→ `{ok:true, binding:undefined}`（byte-compat）。
- 非 string（如 `123`）/ 空串 / 纯空白 → `{ok:false, status:400}`。
- 数组（repeated param）→ 取首值后照常解析。
- unknown project → `{ok:false, status:404, "Unknown…"}`。
- known project 但 `linear` 缺省 / `null` → `{ok:false, status:404, "…has no linear binding"}`。
- known project + 有 binding → `{ok:true, binding}`。

**resolveLinearScope（纯）**:
- 显式 project 覆盖 binding.project。
- 显式 labels（非空）覆盖 binding.label。
- 显式 labels 空数组 / `[""]`（调用方应先 filter blank）→ 退回 binding.label（Codex R2 LOW-3）。
- binding 仅 label（无 project）→ labels=[label], project=undefined（Polaris 形态）。
- binding undefined + 无显式 → 全 undefined（byte-compat）。

**create-issue**:
- `projectName` → team 从 binding.team；显式 team 覆盖。
- `projectName` → project 从 binding.project（**team-scoped 查询**:正确 team 命中）；显式 project 覆盖（legacy 路径）。
- binding-derived project 名挂在**错 team** → 404「not found in team」；team-scope 后仍重名 → 400 ambiguous。
- `projectName` + binding.label → labelIds 含**按 effective team 解析**出的 label id（与显式 label ids 合并）。
- 显式 team 覆盖 binding.team 时,label 按那个 **effective team** 解析（不是 binding.team）。
- binding.label 在 team 内解析不到 → 404；team-scope 后仍重名 → 400 ambiguous。
- `projectName: 123`（非 string body）→ 400。
- `projectName` 不在 roster → 404「Unknown…」；known 但无 binding / `linear:null` → 404「…has no linear binding」。
- 不传 `projectName` → 行为与现状逐字一致（byte-compat 回归 sentinel；含现有 label-ids 透传 fixture）。

**issues / triage**:
- `projectName` → project+labels 缺省正确；显式覆盖。
- triage 新 `labels` query 直接生效（无 projectName 也能用）。
- 不传 `projectName` 且不配 linear → 现状行为不变。

## 8. 风险 / 边界

- **`linear: null` 启动坑（Codex R1 HIGH-1，最高风险）**:部署 roster 字面 `linear: null`。校验必须把 `null` 与 `undefined` 同等当"无绑定"在 binding 校验**之前**短路,否则 Bridge 启动直接挂。有专门的 `linear: null` sentinel 测试守。
- **label name→id 必须 team-scoped（Codex R1 HIGH-2）**:create 把 `labels` 直接当 `labelIds` 透传,这个 resolver 是 name→id 的唯一安全边界。按 `targetTeam.id` 收窄 + 0→404 + ≥2→400,绝不 workspace-wide `nodes[0]`。多一次 Linear 调用(仅当 binding.label 存在且传了 projectName)。
- **binding-derived project 同名歧义（Codex R1 MEDIUM-3）**:binding 的 team/project 是 pair 权威,binding-derived project 用 first:2 + fail-loud;显式 `project=` 保持现状 nodes[0]。
- **triage session scope（Codex R1 MEDIUM-4）**:传 projectName 时 sessions 也按 `project_name` 过滤;capacity 保持 global(机器级)。
- **byte-compat**:三端点所有现有调用(不传 projectName)行为零变化 —— 显式回归 sentinel 守。
- **两个 "project" 概念**:`projectName`(Flywheel roster key)vs `project`(Linear project name)。命名遵循 issue 原文 + `ProjectEntry.projectName` 字段名,文档/注释里写清。
- **fail-loud vs 静默**:`projectName` 传了但 unknown / 无 binding → 404(区分消息),不退回全量(防 Lead 误以为 scoped 实则全量泄漏)。
