# Plan: Roundtable reply-in-thread — DEFAULT-ON for ALL Claude leads + future Discord agents

**Version**: v1.58.0 (provisional — actual ship version may shift; this is a plugin-fork PR + a tiny Flywheel-side setup helper)
**Issue**: FLY-569
**Date**: 2026-06-25
**Source**: Linear issue FLY-569 (Annie + Cass, post-deploy roundtable 实测), parity with Codex FLY-314 #340
**Status**: draft

---

## 1. Problem

Annie 在真实多人 roundtable 测试中发现:**Claude lead(Belle)被 @ 后回复落在父频道、没回进 thread**,而 Codex lead(Mufasa)回对了 thread。

### Root cause (已查实)

| Lead 类型 | 启动方式 | roundtable env | reply-in-thread |
|-----------|----------|----------------|-----------------|
| Flywheel 部门 lead(Peter/Simba/Tadashi/Oliver/Cass…) | `flywheel-lead-wrapper.sh` → `source ~/.flywheel/.env`(`set -a`)→ `claude-lead.sh` forward | `FLYWHEEL_ROUNDTABLE_REPLY_IN_THREAD=1` + `CHANNEL_ID` 已设 | ✅ ON |
| 独立 companion Claude lead(Belle/atlas/rafiki) | 各自 `start.sh`:`unset` 掉 Flywheel token 变量 + 把 `DISCORD_STATE_DIR` 钉到自己的 bot 状态目录(token 隔离) | 从不设 `FLYWHEEL_ROUNDTABLE_*` | ❌ OFF → 回父频道 |
| Codex lead(Mufasa) | `codex-lead-runtime.ts`(FLY-314 #340) | `=1`(直接读 `~/.flywheel/.env`) | ✅ ON(生产已验) |

机制:Discord 插件(`claude-plugins-official` fork)的 `loadRoundtableConfig(process.env)` 在没有 `FLYWHEEL_ROUNDTABLE_CHANNEL_ID` 时返回 `undefined` → `RT_CFG` 为空 → reply-in-thread 关 → 回复落在父频道。

独立 daemon 故意 `unset` 全部 Flywheel 环境是为了 **token 隔离**(personal-assistant 这类 agent 用自己的 bot token、够不到 Annie 私人数据、不被 Flywheel token 污染)—— 这是一道**安全墙**,不能为了开 reply-in-thread 而把 token 灌回去。

### Annie 的要求(硬)

**不要给单个 lead 打补丁。** 要 **systemic**:reply-in-thread 在 Claude-lead / 插件那条路**默认开**,所有 Claude lead + 以后任何上 Discord 的 agent 起来就自带,无需 per-lead 配置 —— 与 Codex 侧 #340 对齐。

---

## 2. Constraints (硬约束)

1. **绝不破坏 token 隔离** —— 不重新注入任何 token/secret。共享给插件的只能是 **benign 路由配置**(channel id)。
2. **共享源只能有 `channelId`** —— 文件里绝不能出现任何 token/secret(Lead 拍的安全墙红线)。
3. **byte-compat**:
   - env 仍 wins(wrapper lead + QA Room 行为字节不变)。
   - 没有任何可解析的 channel id(vanilla 非-Flywheel 安装)→ `undefined` → OFF,不变。
   - 不碰 Codex 代码 → Mufasa 零回归。
4. **autoContinue 保持 DEFAULT-OFF** —— default-on 只对 **reply-routing(R1)**;no-@ 续聊(R2)是 loop 风险所在,保持 FLY-220 mention-required。
5. setup helper 写 `roundtable.json` 要**幂等、不覆盖已有、不泄露任何 secret**。

## 3. Design

### 3.1 共享非-token 源:`~/.flywheel/roundtable.json`

新建一个**专用 benign 文件**,只放路由配置:

```json
{ "channelId": "1512578695468941333" }
```

- 任何能读到这文件的 agent 进程(包括 token 隔离的 Belle —— 它没 `unset` 这个文件,文件本身零 secret)都能解析出 roundtable channel。
- 文件**绝无 token**,所以即便被 token 隔离的 daemon 读到也不破墙。
- 默认路径 `~/.flywheel/roundtable.json`,可用 `FLYWHEEL_ROUNDTABLE_CONFIG_FILE` 覆盖(QA Room / 测试隔离用)。

**为什么不是别的方案**(brainstorm gate 已确认):
- ❌ 把 channel id 硬编进通用 `claude-plugins-official` fork —— Flywheel 专属 id 进通用插件,不可移植、品味差。
- ❌ allowlist 读 token-laden 的 `~/.flywheel/.env` —— 即便白名单也是「插件打开了装满 bot token 的文件」,攻击面 + review 风险大,违背「共享源本身非-token」。
- ✅ dedicated benign 文件 —— 最干净、零 token-leak 面、可移植(非-Flywheel 安装没这文件 → 自动 OFF)。

### 3.2 共享路由 loader —— 独立 side-effect-free 模块(Codex R1#1)

> **不放 server.ts**:`server.ts` 不是 import-safe —— 顶层有副作用、`server.ts:1422` 会 `client.login(TOKEN)`。把 loader 放它里面 → 单测一 import 就可能启动 Discord client/MCP 进程或撞 live token。所以 loader 放**新的纯模块** `roundtable-shared-routing.ts`,`server.ts` 仅在启动时调用一次。

新建 `external_plugins/discord/roundtable-shared-routing.ts`:

```ts
// PURE, side-effect-free, unit-testable. benign-only. NEVER reads token/secret.
const SNOWFLAKE_RE = /^[0-9]{15,21}$/   // 与 setup helper / Bridge 现有 channel 校验一致

// pure parser: 拿文件文本 → {channelId} | {}. 便于单测,不碰 IO。
export function parseSharedRoundtableRouting(text: string): { channelId?: string } {
  let raw: unknown
  try { raw = JSON.parse(text) } catch { return {} }
  const id = (raw as { channelId?: unknown })?.channelId
  const channelId = typeof id === 'string' ? id.trim() : ''
  return SNOWFLAKE_RE.test(channelId) ? { channelId } : {}   // ONLY a valid snowflake id; 其余全丢
}

export function loadSharedRoundtableRouting(
  env: Record<string, string | undefined> = process.env,
  io: { readFileSync: typeof import('fs').readFileSync } = { readFileSync },
): { channelId?: string } {
  const configured = (env.FLYWHEEL_ROUNDTABLE_CONFIG_FILE ?? '').trim()
  const path = configured || join(homedir(), '.flywheel', 'roundtable.json')
  let text: string
  try { text = io.readFileSync(path, 'utf8') }
  catch { return {} }                              // 缺文件 → 静默 {}(byte-compat,vanilla 不变)
  const out = parseSharedRoundtableRouting(text)
  if (!out.channelId) {
    // 文件存在但解析不出合法 channelId → bounded stderr 警告(R1#6:别让 Belle 静默回父频道、无线索)
    process.stderr.write(`[roundtable] shared config ${path} present but has no valid channelId — reply-in-thread stays OFF\n`)
  }
  return out
}
```

`server.ts` 启动处:
```ts
import { loadSharedRoundtableRouting } from './roundtable-shared-routing'
const RT_CFG = loadRoundtableConfig(process.env, loadSharedRoundtableRouting())
```

### 3.3 pure resolver(roundtable-thread-policy.ts):default-ON

`loadRoundtableConfig(env, routing?)` 改两处,其余不变:

```ts
export function loadRoundtableConfig(
  env: Record<string, string | undefined>,
  routing?: { channelId?: string },   // shared non-token defaults (server.ts 读文件后传入)
): RoundtableConfig | undefined {
  // env wins; shared file is the under-layer (byte-compat for wrapper lead + QA Room).
  const channelId =
    (env.FLYWHEEL_ROUNDTABLE_CHANNEL_ID ?? '').trim()
    || (routing?.channelId ?? '').trim()
  if (!channelId) return undefined                 // OFF / byte-compat (vanilla / 无可解析 channel)
  // FLY-569: reply-routing DEFAULT-ON when a roundtable channel is known.
  // opt-out ONLY via explicit "0". (was: requires "1")
  const replyInThread = env.FLYWHEEL_ROUNDTABLE_REPLY_IN_THREAD !== '0'
  // UNCHANGED — autoContinue stays default-OFF (FLY-220 anti-loop; mention-required).
  const autoContinue = env.FLYWHEEL_ROUNDTABLE_THREAD_AUTOCONTINUE === '1'
  const rawN = Number.parseInt((env.FLYWHEEL_ROUNDTABLE_THREAD_BUDGET ?? '').trim(), 10)
  const budgetN = Number.isFinite(rawN) && rawN > 0 ? rawN : 2
  return { channelId, replyInThread, autoContinue, budgetN }
}
```

**语义变化点(唯一)**:`replyInThread` 从「`=== "1"` 才开」→「有 channel 就开,`=== "0"` 才关」。
- wrapper lead / QA Room:env 里 `=1` → 仍 ON,不变。
- Belle(env 无):env 无 channel → 用文件 channel → `REPLY_IN_THREAD` 未设(`!== "0"` 为真)→ **DEFAULT-ON**。
- 显式关:`FLYWHEEL_ROUNDTABLE_REPLY_IN_THREAD=0` → OFF(逃生口)。
- 无 channel(vanilla)→ 早返 `undefined` → OFF,字节不变。

> guild id 插件 reply-in-thread 路径**不用**(只 Codex 的 active-thread discovery 用),本 PR 不引入 guild,保持最小。

### 3.4 reply 落 thread + 加固 ensureRoundtableThread(Codex R1#2)

`resolveRoundtableInboundChatId` + reply handler 已在 #8 落地。Belle 收到 #leads-roundtable 顶层 @ 后:`channelId === RT_CFG.channelId && !isThread` → chat_id 改写成 `messageId`(thread id == message id 不变量)→ `ensureRoundtableThread`(用 Belle 自己的 token)→ 回复进 thread。多 lead 路由到同一 `messageId` → 同一 thread,幂等。

> Belle 已有 #leads-roundtable 频道访问权(Cass 审计 + `fly-265-roundtable-allowbots-patch.sh` 已把该频道加进 companions 的 `access.json` groups),收得到消息。

**但**(Codex R1#2 高危):现状 `ensureRoundtableThread` **只**尝试 `POST .../messages/{id}/threads` 建 thread,非-2xx/非-160004 一律当「unconfirmed」→ chat_id 回退到父频道。若某 companion bot 有 View/Send 但**没有 `Create Public Threads`**,且 Bridge auto-thread manager 还没建好该 thread → POST 返 403 → **回退父频道 = 修了 config 还是回父频道**(正是要修的 bug 重现)。FLY-314 的 auto-thread manager / host bot 会建 thread,member bot 只需 `Send Messages in Threads`。

**加固**:`ensureRoundtableThread` 在 create 失败(非 2xx 且非 160004)时,**GET `/channels/{messageId}` 确认 thread 是否已被 host/Bridge 建好**(thread channel id == message id),带**有界短重试**(吸收 Bridge-manager race,如 3 次 × ~400ms),确认存在 → 返回 true(路由进 thread);真不存在 → 维持现状回退父频道。

把**状态判定**抽成纯函数(放 `roundtable-shared-routing.ts` 或新 `roundtable-thread-policy.ts` 导出,便于单测,不 import server.ts):
```ts
// create POST 的响应分类(pure)
export function classifyThreadCreate(status: number, bodyCode?: number):
  'created' | 'exists' | 'confirm-via-get' | 'failed' {
  if (status >= 200 && status < 300) return 'created'
  if ((status === 400 || status === 409) && bodyCode === 160004) return 'exists'
  if (status === 403 || status === 404 || status === 429 || status >= 500) return 'confirm-via-get'
  return 'failed'   // 其余 4xx(如 400 非 160004)= 真失败
}
// GET /channels/{threadId} 的响应分类(pure):200 → 确认存在
export function threadGetConfirmsExistence(status: number): boolean { return status === 200 }
```
`ensureRoundtableThread` 编排:`POST` → `classifyThreadCreate` → created/exists ⇒ true;confirm-via-get ⇒ 有界重试 `GET` + `threadGetConfirmsExistence`;failed/超时仍未确认 ⇒ false(父频道回退,现状安全侧)。

> 注:GET 确认到 thread 存在但 bot 无 `Send Messages in Threads` → 真正发送会在 reply send 阶段失败(独立错误路径,属 Discord 角色权限配置,不在本 PR scope —— 本 PR 只负责「thread 存在就路由进去」)。

## 7. Risks

| 风险 | 缓解 |
|------|------|
| default-ON 语义改了影响「channel 有但 reply 未设期望 OFF」的调用方 | 代码库内仅 server.ts 用此函数;生产/QA 都显式 `=1`;无依赖旧默认者。逃生口 `=0`。 |
| 共享文件意外被塞 secret | 插件 `parseSharedRoundtableRouting` **只接受 snowflake `^[0-9]{15,21}$` 的 channelId**、其余字段一律丢弃;setup helper 严格 snowflake 校验 + `jq` 输出 + 非法 fail-loud(白名单 = 结构性 leak guard,secret 写不进去);单测断言 token-ish 字段被丢弃。 |
| companion bot 无 `Create Public Threads` → 仍回父频道 | `ensureRoundtableThread` create 失败 → GET 确认 host/Bridge 已建 thread + 有界重试 → 路由进 thread;真不存在才回退父频道(R1#2)。 |
| stale `roundtable.json`(旧 channel)静默错路由 | setup helper 不同 channelId → fail loud(不静默保留)(R1#4)。 |
| autoContinue 误开导致 loop | 本 PR 不碰 autoContinue 默认(仍 OFF / mention-required)。 |
| Belle 收不到消息 / 无 thread 发送权(非路由问题) | 收消息:已确认有频道访问权(Cass 审计);thread 发送权(`Send Messages in Threads`)属 Discord 角色配置,真发送失败是独立错误路径,不在本 PR scope。 |
