## 2. 设计

### 2.1 数据模型(StateStore)

chat_threads 加 `archived_at TEXT`(幂等 ADD COLUMN 迁移,照 `migrateLeadEventsDeliveryColumns` 模式):
- **为什么要 archived 标记**:① 避免每次 sweep 对已归档 thread 重复 Discord/Linear 调用;② **不与 Annie 重开对抗** —— `archiveChatThread` 注释明确「用户在归档 thread 发消息 → Discord 自动 unarchive(Annie 又在用了),是设计行为」。一旦我们归档过一次就记 `archived_at`,**之后不再 sweep 它**(尊重 Annie 重开),根治「反复归档她重开的 thread」。

新增方法:
- `getArchivableChatThreads(): { thread_id, channel_id, issue_id, lead_id }[]` — `WHERE discord_missing_at IS NULL AND archived_at IS NULL`。**返回 `lead_id`**(Codex R1 #3:thread 创建时记的 lead_id 比「当前 label-based 解析」更可信,labels 会随时间变)。
- `markChatThreadArchived(threadId: string): void` — set `archived_at = datetime('now')`。

> **注**:`post-ship-finalization` 现有的 ship 归档路径**也**改为归档成功后 `markChatThreadArchived`(否则 ship 过的 thread 会被新 reconciler 再扫一遍)。这是必须的一致性改动,不是新行为。

### 2.2 共享 helper(新文件 `bridge/done-thread-archiver.ts`)

```
archiveIssueThread(store, projects, opts, deps): ArchiveOutcome
```
- 入参:`{ issueId, channelId, projectName, leadId?, discordOwnerUserId? }` + `fallbackBotToken`。
- **token 解析(Codex R1 #3)**:优先用 `(projectName, leadId)` 定位 Lead config 取 `botToken`(leadId 来自 chat_threads 记录,thread 创建时绑定);仅当 leadId 缺失(legacy 行)才退回 `resolveLeadForIssue(projects, projectName, session labels)`;再退 `fallbackBotToken`(全局)。
- 步骤:解析 thread(`getChatThreadByIssue`)→ 解析 botToken(见上)→ (可选)`removeUserFromChatThread` → `archiveChatThread`(Bridge 持 token)→ 成功则 `markChatThreadArchived` + 写 audit event(`chat_thread_archived` / `chat_thread_archive_failed`,复用 post-ship 的事件语义)→ 返回结构化结果。
- **never throws**(照 post-ship 风格,call site fire-and-forget)。
- 这是 ① endpoint 与 ②③ reconciler 的**唯一归档收口**(单一 token 收口,满足安全硬约束)。

```
reconcileDoneThreadArchival(store, projects, deps): { scanned, archived, skipped, errors }
```
- 步骤:`getArchivableChatThreads()` → 对每个候选 thread:`getSessionByIssue(thread.issue_id)` 取 `{ issue_identifier, issue_id, project_name, lead_id }` → **逐候选直查 Linear 状态**(`fetchLinearIssueState`,见下)→ `state.type === "completed"`(Done)→ **立即归档** `archiveIssueThread`(用 thread.lead_id 优先解析 token)。
- **Done 即归档(Annie 最终拍板 — 改掉 24h inactivity 等待)**:auto-poll 见 Done 立刻归档,不再查 thread 静默。**安全网 = Discord 自带 auto-unarchive**(有人在已归档 thread 发消息 → 自动重开),配合 **archive-once**(`archived_at` 标记后永不再扫)= 误归档了能恢复、且不与重开对抗。Discord 404(thread 已删)由 `archiveChatThread` 内置 `markChatThreadMissing` 处理,自然移出 sweep 集合。**endpoint 不变**(Lead 按需即时归档)。
- **逐候选直查,不用 bulk 查询(Codex R1 #1,HIGH)**:`queryLinearIssues` 有 `limit` 截断(`truncated` 但无 cursor)→ 一个 project >250 Done issue 时,首页外的候选永远匹配不上、对着不完整集合反复重试 = 永久漏归档,不满足回填/根治目标。改为**逐候选直查**:候选数 = 本地未归档 chat_threads(有界),per-candidate Linear lookup 完全无截断。
- **`fetchLinearIssueState(client, { issueId, issueIdentifier })`(防御式,吸收 Codex R1 #6 + R2 #3,LOW)**:Linear `client.issue()` 主接受 UUID;identifier 走 `searchIssues` 精确匹配。故:① 若 `issue_id` 形如 UUID → `client.issue(issue_id)` 读 `state.type`;② **identifier 候选 = `issueIdentifier ?? issueId` 中首个匹配 `^[A-Z]+-\d+$`(issue-key 正则)的**(legacy 行 issue_identifier 缺失但 issue_id 本身是 PREFIX-N 时不漏)→ `searchIssues(candidate)` 取 `identifier` 精确匹配读 `state.type`。两路都无可用 handle/都 miss → 返回 undefined。(实现时 mock Linear client 做 TDD 锁定契约 + 真 SDK 验证 `client.issue` 是否也吃 identifier;若吃则简化。)
- 无 session 行的孤儿 thread / 两路解析都 miss → **跳过 + log(带 thread_id/issue_id 上下文便于人工回填)**,不误归档。
- LINEAR_API_KEY 缺失 → 整体跳过 + log(不崩)。
- per-candidate 调用串行 + 各自 try/catch(单个候选查询失败不影响其余;失败计入 errors)。

### 2.3 三个触发面(全部走 §2.2 收口)

| # | 触发 | 实现 |
|---|------|------|
| ① endpoint | `POST /api/chat-threads/archive` | `tools.ts` 加路由(挂 `createQueryRouter`,落 `/api`)。入参 `{ issueId?\|issueIdentifier?, channelId, leadId, projectName }`(对齐 `/send`)。**鉴权 fail-closed(Codex R1 #4 / R2 #4)**:`tokenAuthMiddleware` 在 apiToken 未设时 no-op,而 `chatThreadsEnabled` 不像 reply-by-issue 那样 fail-start → 故路由内**显式**校验:新增 opt `apiTokenConfigured`(**默认 `false` = fail-closed**,不改现有 router 测试行为;plugin.ts 传 `Boolean(config.apiToken)`,成功测试才传 true),未配置 token → 503(privileged 写路由绝不裸跑)。gate 在 `chatThreadsEnabled`。用 `validateChatThreadParams({channelId,leadId,projectName}, projects)` 校验(对齐 /create+/send,Codex R1 #3)。**identifier↔UUID canonicalize(Codex R1 #2,HIGH)**:复用 `/send` 解析——给 identifier 则 `store.getSessionByIdentifier(identifier)?.issue_id` 求 canonical key,否则退 identifier;给 UUID 且 Linear 可用则交叉解析再 `getSessionByIdentifier` 映射 → 避免 identifier-only 请求漏掉 UUID-keyed thread。**Lead 按需归档,不查 Linear**(Lead 已判定 Done)。调 `archiveIssueThread`。返回 `ArchiveChatThreadResult`。 |
| ② archive-on-Done(自动) | piggyback **HeartbeatService**(Codex R1 #5)| 在 HeartbeatService **现有 stuck/orphan/stale/review-timeout 检查之后**调 `reconcileDoneThreadArchival`,**独立 try/catch**(Linear 延迟绝不拖累 failure detection)。cadence 默认**每 1 个 heartbeat tick**(`TEAMLEAD_STUCK_INTERVAL` 默认 300000ms=5min,即 ~5min 一次,非「10 tick=50min」),N-tick 经 env 显式可调(`FLYWHEEL_ARCHIVE_SWEEP_EVERY_N_TICKS`,默认 1)。**不新增 timer**(遵循 FLY-169/172/208「零新周期 timer」)。env 逃生口 `FLYWHEEL_ARCHIVE_ON_DONE=0` 关闭(默认 ON)。**不选 GatePoller**(3s runner-question 路径,不该背 Linear 轮询)。 |
| ③ 回填 | boot 一次性(plugin.ts ~2413,FLY-324 reconciler 之后)| 调同一 `reconcileDoneThreadArchival`。非致命 try-catch + log 统计(照 boot reconciler 模式)。受同一 env 开关控制。boot 立刻清存量 backlog,不等 5min tick。 |

### 2.4 byte-compat / 安全

- `archived_at` 迁移:幂等 ADD COLUMN,旧库自动升列,旧行 `archived_at` 为 NULL → 进入 reconciler 视野(预期:旧 Done thread 被回填一次)。
- `FLYWHEEL_ARCHIVE_ON_DONE=0` → ② 与 ③ 全关(逃生口);endpoint ① 不受此开关控制(显式 Lead 调用),受 `chatThreadsEnabled` + `apiTokenConfigured`。
- endpoint 鉴权:走 `/api` 的 `tokenAuthMiddleware`,**但**(Codex R1 #4)该中间件在 `TEAMLEAD_API_TOKEN` 未设时 no-op,且 `chatThreadsEnabled` 不 fail-start 强制 token → 故路由内显式 fail-closed:apiToken 未配置一律 503,绝不让 privileged 归档路由裸跑。
- 归档 100% 走 Bridge 内 `archiveChatThread`,token 不出 Bridge 进程(安全硬约束达成)。reconciler(②③)在 Bridge 进程内,不经路由、不需 apiToken。
