# Plan: Bridge crash-loop 止血 — StateStore sql.js 损坏不再崩 Bridge + best-effort 进程内自愈 + 不可恢复受控重启

**Version**: v1.61.0
**Issue**: FLY-639 ([P1 incident] Bridge crash-loop — StateStore sql.js WASM corruption)
**Date**: 2026-06-28
**Source**: brainstorm (本 issue 描述 + 代码审计实证)
**Status**: codex-approved → inprogress

---

## 1. Problem

2026-06-28 凌晨 Bridge 反复崩溃重启(~每小时一次，pid 51038→84295→62635)。

**实证根因(代码审计确认):**

1. **sql.js 运行时损坏** — bridge log:
   `[HeartbeatService] check error: RuntimeError: null function or function signature mismatch`
   (sql.js WASM 间接函数表损坏)→ 之后 `no such table: sessions`(损坏实例查不到表)。
   典型诱因 = **内存压力**(本次 session 巨大:254 tmux 窗口、几十 runner、codex 进程)。

2. **未捕获 → 整个 Bridge 退出** — stack:
   `Error: no such table: sessions at StateStore.getActiveSessions ← RunnerIdleWatchdog.poll ← Timeout._onTimeout`。

**为什么是崩溃而非 log:**

- `RunnerIdleWatchdog.start()` 用 `setInterval(() => this.poll(), …)`，**没有 `.catch()`**。
- `poll()` 是 `async`；其顶部 `this.config.store.getActiveSessions()`(第 109-110 行)是 `poll` 里**唯一未被 per-session `try/catch` 保护**的 StateStore 调用。
- 它 throw → `poll()` 返回的 promise reject → 无 `.catch()` → **unhandled rejection**。
- Bridge 入口(`scripts/run-bridge.ts` / `packages/teamlead/src/index.ts`)**没有** `process.on('unhandledRejection')` 全局 handler → Node 默认 `--unhandled-rejections=throw` → 进程 **exit 1**。launchd `KeepAlive` 重启 → re-init StateStore 短暂正常 → 内存压力再次损坏 → 再崩 = **crash-loop**。

**对照组(已被保护，不直接崩):**

- `HeartbeatService.start()` 已在 `setInterval` 里 `.catch()` 了 `check()`(第 167-171 行)— 只 log。
- `GatePoller.poll()` 已有 FLY-307 per-lead circuit breaker + 内层 `try/catch`(第 255-340 行)+ founder-reply / health-tick 各自 `try/catch`。但 `setInterval(() => this.poll())` 仍**无 `.catch()`**(defense-in-depth 缺口)。

**注**:FLY-628 只把 idle poll 频率从 30s 改到 3600s = 让崩溃从每 30s 变每 1h，**不是 628 引入**，是预存 robustness 缺陷被高频暴露。

## 2. Goal

- **A(止崩，优先)**:**单个** StateStore sql.js 错误**绝不**让 Bridge 崩溃。三个周期 poller(`RunnerIdleWatchdog`/`GatePoller`/`HeartbeatService`)的 StateStore 调用一律 log + 跳过本轮。(限定为这三个已知周期任务 + 它们触达的 StateStore 路径;不声称「任何地方任何 StateStore 错误都不崩」。)
- **B(best-effort 进程内自愈，非保证根治)**:StateStore 检测到 sql.js 损坏签名时，**进程内从磁盘最近一次 `save()` 镜像重建 DB**(不带病继续)，可恢复的场景下一轮恢复健康、无需进程重启。**这不是对 WASM 函数表/堆级损坏的保证根治**——同一 `initSqlJs()` module 内重建可能修复坏掉的 DB handle / SQLite 堆状态，但**不会**重置已实例化的 WASM module;若 `null function` 反映的是 module 级损坏，同 module 重建可能立即再失败。
- **不可恢复时受控退出(Codex R1 BLOCKER 修复)**:**仅当**识别为损坏签名且**重建尝试连续失败 N 次**(有界窗口内)时，记 FATAL 日志 + 受控 `process.exit(1)`，让 launchd 用全新进程(全新 WASM module)重启。这解决了「永不崩」与「launchd 兜底」的矛盾——避免「活着但 StateStore 永久不可用」的更坏态。**仅**在识别签名 + 重建失败时升级，普通 poller 异常不升级;成功恢复后计数清零。
- 真正根因(内存压力)是运维侧，本 PR 不解决。

非目标:不换 sql.js → better-sqlite3(大改，超 P1 范围);不加全局 `unhandledRejection` handler(过于钝，会掩盖别处真·致命错误;在源头 poller 收口更干净)。

## 3. Design

### 3.1 Fix B — StateStore 自愈(`StateStore.ts`)

1. **保留 sql.js 模块引用**:`create()` 里 `const SQL = await initSqlJs()` 已有；把 `SQL`(`SqlJsStatic`)存到实例(`private sqlModule`)，供同步重建。
2. **损坏识别(纯函数，导出供测试)**:
   ```ts
   export function isSqlJsCorruptionError(err: unknown): boolean
   ```
   匹配(大小写不敏感子串):`null function or function signature mismatch`、`no such table`、`database disk image is malformed`、`out of memory`、`memory access out of bounds`。这些是 sql.js/WASM 不可在同一 DB 实例上继续的致命签名。普通逻辑错误(如约束冲突)**不**匹配 → 不触发 reload。
   - (Codex R1 LOW-6)`no such table` 较宽，可能掩盖真·schema/编程 bug。缓解:每次恢复**都把原始错误消息**带进显眼 `console.error` 恢复日志,真·schema bug 仍刺眼可见,不静默。
3. **重建(同步，guard 住绝不 throw)** `recoverFromCorruption(err: unknown): boolean`(true=已重建恢复):
   - `err` 不匹配损坏签名 → 返回 `false`(不动 DB、不计数、不节流)。
   - **节流语义(Codex R1 LOW-7)**:记 `lastRecoveryAttemptAt`。距上次**实际重建尝试** < `throttleMs`(默认 5s;GatePoller 每 3s 跑、一个 tick 可跨多个 lead 撞同一坏 store)→ 跳过本次重建并返回 `false`。被节流跳过的调用**不**计入升级失败计数(同一 episode)。节流只作用于损坏签名。
   - 否则执行重建(原始消息进 loud log):
     - **先建后换 + 关旧 handle(Codex R1 MEDIUM-5)**:先 `const next`(`:memory:` → `new sqlModule.Database()`;否则 `new sqlModule.Database(readFileSync(dbPath))`,读不到 → 空 DB)+ 在 `next` 上 `migrate()`(幂等)。成功后 `const old = this.db; this.db = next;` **再** best-effort `try { old.close() } catch {}`(释放旧 sql.js handle 内存,内存压力下尤其重要;**绝不**对旧 handle `save()`,关闭失败不算恢复失败)。
     - **关键**:重建前**绝不** `save()` — 损坏实例 `export()` 也会失败/产坏镜像;用上一次良好磁盘镜像。
   - `try/catch`:成功 → 显眼 `console.error` 恢复日志(原始消息 + 「restored from last persisted image」)+ **清零** `recoveryFailures` + 返回 `true`;重建本身 throw(模块级死亡)→ 大声 `console.error` + `recoveryFailures++` + **绝不**抛回调用方 + 返回 `false`。
4. **不可恢复升级(Codex R1 BLOCKER-1)**:`recoveryFailures >= maxRecoveryFailures`(默认 3,有界)→ 记 FATAL + 调用可注入 `onUnrecoverableCorruption(err)`(默认 `console.error` FATAL + 受控 `process.exit(1)`,让 launchd 用全新 WASM module 重启)。**仅**识别签名 + 重建失败累计;普通 poller 异常永不升级;成功重建清零。测试注入 spy(不杀测试进程)。→ 解决「永不崩」与「launchd 兜底」矛盾,杜绝「活着但 StateStore 永久不可用」。
5. **数据取舍(Codex R1 HIGH-3,精确措辞)**:重建**丢弃自上次 `save()`/`flush()` 起的未持久化内存改动**;`appendLeadEvent`/`markLeadEventDelivered` 在 `flush()` 前不 durable,故部分未 flush 的 lead event **可能丢失或重复**(非「一定被 guardrail 补发」)。P1 可接受——带病继续更糟。

### 3.2 Fix A — 三个 poller 止崩

**RunnerIdleWatchdog(`RunnerIdleWatchdog.ts`)** — 主崩溃路径:
- `poll()`:`getActiveSessions()`(+ 顶部 evict/prune 区)包 `try/catch`。catch → `console.warn` log + `store.recoverFromCorruption(err)`(Fix B 钩子)+ `return`(跳过本轮)。保留 `finally { this.polling = false }`。
- `start()`:`setInterval(() => { void this.poll().catch(err => console.error(...)) }, …)` — defense-in-depth，任何意外 throw 都不会成为 unhandled rejection。

**GatePoller(`bridge/gate-poller.ts`)**:
- `start()`:同上给 `setInterval` 加 `.catch()` 兜底。
- per-lead `catch`(第 331-340 行)与 founder-reply `catch`、health-tick `catch` 内**接入** `store.recoverFromCorruption(err)`(损坏时自愈，下一个 lead/cycle 健康)。circuit breaker 逻辑**不动**(互补:circuit 隔离 poisoned heap，recover 修复它)。

**HeartbeatService(`HeartbeatService.ts`)**:
- **(Codex R2 note-2)`check()` body 整体包 `try/catch`**:契约改为「`check()` 自身永不 reject」——catch → `console.error` log + `this.store.recoverFromCorruption(err)` + `return`(跳过本轮)。这让 `check()` 直接可测(`await expect(check()).resolves`),不再只能靠 `start()` 的计时器 catch。
- 保留 `start()` 现有的 `.catch()`(第 167-171 行)作 belt-and-suspenders。

> `recoverFromCorruption` 在 poller 注入的 store 接口上是可选/best-effort 调用 —— 老的 mock store(测试)没有此方法时用 `typeof store.recoverFromCorruption === "function"` 守卫，保持 byte-compat。

## 4. TDD 计划(RED → GREEN)

1. **StateStore.recoverFromCorruption(`StateStore.test.ts`)**
   - `isSqlJsCorruptionError`:匹配两个命名签名 + malformed/oom;不匹配普通错误。

## 6. Risk & Rollback

- **风险**:reload 丢弃自上次 save()/flush() 起的未持久化内存改动 → 部分未 flush 的 lead event 可能丢失或重复(P1 可接受,带病继续更糟);同一 WASM module 内重建可能不治本 → 由「连续失败 N 次 → 受控 `process.exit(1)` 让 launchd 全新重启」兜底,杜绝「活着但 StateStore 不可用」。
- **回滚**:纯 teamlead/Bridge 侧改动 → 单次 Bridge 重启即生效;回滚 = revert PR + 重启。无 schema/迁移变更、无 config 变更，byte-compat(不设任何新 env / 不改默认行为)。
- **部署**:Bridge 侧 → 攒批 Tier-3 重启(遵循「多个 Bridge PR 攒一次重启」纪律)。
