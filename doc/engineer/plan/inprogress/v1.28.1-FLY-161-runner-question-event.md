# Plan: Runner `flywheel-comm ask` → Bridge `runner_question` Event

**Version**: v1.28.1
**Issue**: FLY-161
**Date**: 2026-05-21
**Source**: `doc/engineer/exploration/new/FLY-161-runner-ask-bridge-event.md`
**Status**: draft (Round 6 — Codex R1 + R2 + R3 + R4 + R5 feedback addressed)

> 把 `flywheel-comm ask` 写入 CommDB 的 non-blocking question 接到 Lead inbox。复用 GatePoller 扫 CommDB → `runtime.deliver()` 的现有 infra，新增 `runner_question` event type；与 `gate_question` 在 Bridge 层对称，但 Lead 侧措辞强调 "Runner 主动 surface，不阻塞"。

## 1. Context Recap

Brainstorm 已固化（`doc/engineer/exploration/new/FLY-161-runner-ask-bridge-event.md`，PR #191）。决定采用 **Fix A**：扩 `GatePoller` 把 `checkpoint == NULL` 的 row 也捞出来，分支 build 新 `runner_question` event。

### 1.1 现状（已审计）

| Runner→Lead 通道 | DB 写入 | Bridge 是否 pick up | Lead 怎么知道 |
|---|---|---|---|
| `send` (instruction) | `type='instruction'` | ✅ `inbox-mcp` push (FLY-109) | 自动入 inbox |
| `gate` (blocking question + checkpoint) | `type='question'`, `checkpoint != NULL` | ✅ `GatePoller` (3s tick, `plugin.ts:1883`) → `gate_question` event | 自动入 Lead inbox |
| **`ask`** (non-blocking question) | `type='question'`, **`checkpoint = NULL`** | ❌ `GatePoller.getPendingGateQuestions` line 134 显式 filter 掉 + Runner 可能在下次 poll 前完成 → 双重 drop | **无** |

`packages/flywheel-comm/src/commands/ask.ts:10-19` 只写 DB，不 emit。GatePoller 当前实现（`gate-poller.ts:62-120`）有两个 active-session 假设：

1. `getActiveSessions()` 仅返回 `'running' | 'awaiting_review' | 'approved_to_ship'` 状态的 session（`StateStore.ts:841-844`）
2. 内层 `sessionByExecId.get(question.from_agent)` 不命中就 `continue`（orphan-skip，line 106-107）

对 `gate_question` 这两点都安全：Runner 因 gate 阻塞，session 必然 active。**对 `ask` 都不安全**：Runner ask 后继续干活，可能在下一 poll 前 complete → session 转 `completed` → 下一 poll `getActiveSessions` 跳过 → `runner_question` event 永不入 `lead_events` → 加 `GUARDRAIL_EVENT_TYPES` 也救不回来（FLY-161 主 fix 失败）。

## 2. Brainstorm Q1–Q6 收尾 + Codex Round 1 调整

### 2.1 Q1 — `runner_question` `HookPayload` 字段

**Decision**: **显式 omit `checkpoint`**，不复用为 free-form tag。

- `gate_question` 的 `checkpoint` 字段语义就是 "checkpoint name"。`runner_question` 路径下 `checkpoint == NULL`，强行复用让类型语义糊。
- 实现：GatePoller 在 `runner_question` 分支里 build payload 时**不**赋 `checkpoint`，让它 stay `undefined`。formatter 也不 render checkpoint 段。
- `question_id / from_agent / comm_db_path / summary / session_role / chat_thread_id / execution_id / issue_id / issue_identifier / project_name` 全部复用 — 与 `gate_question` 同形。

### 2.2 Q2 — Guardrail 归类（Codex Round 1 Issue 4 修正）

**Decision (revised)**: **不加入 `GUARDRAIL_EVENT_TYPES`**。

**为什么改**：Codex Issue 4 指出 — `appendLeadEvent` 在 UNIQUE conflict 时返回 existing seq（`StateStore.ts:1394-1420`），`isLeadEventDelivered` 仅在 `delivered_at` 写后返回 true（`StateStore.ts:1504-1513`）。这意味着 **GatePoller poll 自带 retry**：每个 tick 都会重扫，未 delivered 的 question 自动重投。加 GUARDRAIL 等于让 HeartbeatService 也 retry → CommDBLeadRuntime 不 dedup 会插重复 instruction。

**与 brainstorm §6.Q2 的差异**：brainstorm 倾向加 GUARDRAIL"与 gate_question 对等"——但实证 `gate_question` 本身也**不在** GUARDRAIL set（`lead-runtime.ts:18-23` 仅 `session_stuck / session_orphaned / session_stale_completed / runner_idle_detected`）。所以 "对等" 的真正实现就是**也不加** GUARDRAIL，GatePoller poll loop 是 retry source of truth。

**可靠性保证**：CommDB question 是 durable source；Bridge 重启后 GatePoller 重启 → 下次 poll 重扫所有 pending → undelivered 的 `runner_question` 重投。Bootstrap snapshot 在 §2.3 兜底另一条路。

### 2.3 Q3 — Bootstrap snapshot（Codex Round 1 Issue 2 + Round 2 Issue 1+3 + Round 3 Issue 1 修正）

**Decision (revised three times)**: 新增独立字段 `pendingRunnerQuestions`；**只扫当前 leadId 所属 project**（R2 Issue 1）；**`pendingGateQuestions` 保持 active-session + lead-scope 双约束**（R2 Issue 3 + R3 Issue 1）；**加 `chatThreadId` 字段**到 `BootstrapRunnerQuestion`。

- 合并字段 + `kind` 标签会让 type 变 union，prompt 段需分支 render。分开干净。
- 实现：
  - `lead-runtime.ts` 加 `interface BootstrapRunnerQuestion`（无 `checkpoint` 字段；加 `chatThreadId?: string`）；
  - `LeadBootstrap` 加 `pendingRunnerQuestions?: BootstrapRunnerQuestion[]`；
  - `bootstrap-generator.ts:207-251` 改造（详 §4 Phase 2）：
    - **不**迭代所有 lead — 只迭代**含当前 leadId** 的 project：用 `projects.filter(p => p.leads.some(l => l.agentId === leadId))` (or use `findProjectForLead(leadId, projects)` if unique)，per-project 扫一次 CommDB；
    - 调 `db.getPendingQuestions(leadId)` —— 已按 `to_agent=leadId` 过滤（验证：CommDB SQL `WHERE q.to_agent = ?`），不会带其它 Lead 的 question (R2 Issue 1)；
    - per question 用 `store.getSession(q.from_agent)` 补 metadata（**注意 `store.getSession` 不过滤 status**，需要后续手动 check）；缺 session → skip + warn (orphan)；
    - **Partition (R2 Issue 3 + R3 Issue 1 双约束)**：
      - `q.checkpoint != null` → check **(a) `session.status in ['running','awaiting_review','approved_to_ship']` (active) AND (b) `matchesLead(session, leadId, projects)` (lead-scope)** → 都满足才入 `pendingGateQuestions`（与现有行为完全一致：保持 active + lead-scope 双 gate），否则 skip + warn；
      - `q.checkpoint == null` → 入 `pendingRunnerQuestions` regardless of session status / lead-scope（runner_question 设计明确按 `to_agent` 路由）；
    - `chatThreadId` 当 `opts?.chatThreadsEnabled` 时 (R4 Issue 1 修正)：
      - **runner_question** 路径用 **`targetLead.chatChannel`**（`targetLead = project.leads.find(l => l.agentId === leadId)!`） + `getChatThreadByIssue(session.issue_id, targetLead.chatChannel)` —— 跟 `to_agent` 路由一致；
      - **gate_question** 路径保持 label-derived 解析（`resolveLeadForIssue` + `getChatThreadByIssue`）即可 —— partition 时已经过 `matchesLead`，label-derived 跟 target Lead 等价；
  - **`BootstrapGateQuestion` 不动 chatThreadId**（scope discipline；R1 Issue 2 建议 "for symmetry" 作为本 PR 之外 follow-up — 写进 §8 Out of Scope）；
  - `mailbox-lead-runtime.ts` + `commdb-lead-runtime.ts` 各 `formatBootstrap` 加新段 `### Pending Runner Questions`，含 `Chat-Thread: <id>` 行（当 chatThreadId 存在时）。

**Lead-scope 决策依据**: `matchesLead(session, leadId, projects)` 已存在于 `packages/teamlead/src/bridge/lead-scope.ts:51` — 复用，不新建 helper。逻辑：parse session.issue_labels → `resolveLeadForIssue` → compare agentId。失败时 throws —— bootstrap-generator partition 中调用时套 try/catch + warn + skip（保持与现有 `filterSessionsByLead` 一样的 "verify error = exclude" 语义）。

### 2.4 Q4 — Lead prompt 措辞 + 文件位置（Codex Round 1 Issue 3 修正）

## 9. Migration / Rollout

### 9.1 行为变化清单（PR description 必列）

- ✅ Runner `flywheel-comm ask` 现在会**自动**触发 Lead 通知（≤1 poll tick ≈ 3s）→ Lead 转 Annie
- ✅ 新 event type `runner_question`（Bridge state store + Lead inbox 可见）
- ✅ Bootstrap snapshot 新增字段 `pendingRunnerQuestions`（含 chatThreadId）
- ✅ Lead identity rule (dept + cos 两文件) 新增 "Runner Question Handling" 段
- ✅ GatePoller outer iteration 改为 project/lead pairs — completed session 的 pending question 也能被 surface
- ⚠️ 升级后第一次 poll：所有现存未 read non-checkpoint pending question（`ask` 写的）会 burst 给 Lead — 个位数量级
- ✅ 现有 `gate_question` 路径**完全不变**
- ✅ Runner CLI 接口完全不变 — in-flight Runner 不受影响

### 9.2 Rollback strategy

- Squash merge, revert PR + 重启 Bridge + Lead daemon
- 无 schema migration，无 DB 改动
- Rollback 后：(a) GatePoller filter 恢复 → 新 ask 不再 emit；(b) 已写入 `lead_events` 的 `runner_question` row 不被清理（无害，state store 自然过期）；(c) Lead identity rule rollback → Lead 仍可手动 `flywheel-comm pending`
- Rollback 期间 Runner 仍可 `ask`（CLI 不变），只是回到 FLY-161 之前的状态

### 9.3 与 FLY-159 (v1.28.0) 的关系

- 两 PR 都是**纯追加**到 `hook-payload.ts` (FLY-159 加字段，FLY-161 仅注释) 和 `lead-runtime.ts` interface (FLY-161 加 BootstrapRunnerQuestion；FLY-159 加 GUARDRAIL set 成员 + payload 字段)
- Rebase 无 conflict 风险（两 PR 各动不同 line range）
- Ship 顺序：FLY-159 先 → FLY-161 后（已设定 v1.28.1 紧跟 v1.28.0）；若反过来 trivial
- FLY-159 plan 文件目前在 sibling worktree (`worktrees/fly-159-brainstorm/...`)，不在本 worktree
