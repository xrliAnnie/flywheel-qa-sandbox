## 1. 一句话目标

确立钦定心智模型 —— **一个 issue → 一个正确类型的 executor → 端到端做完整个生命周期(brainstorm→research→plan→implement→ship)**,并让 Lead 起 Runner 时按**实际活类型**路由到那个"将端到端拥有该 issue 的 executor",`agentName` 显式传、label 只当提示。把这条规则**从 project layer 提升到 flywheel base layer**,让所有 Lead、所有项目行为一致。

---

## 2. 背景与根因

### 2.1 事件(GEO-380)
GEO-380 标 `Product` label。Lead 起 Runner 时走 FLY-137 label dispatch,label clean match 到 **product-executor**(`match.labels: ["product","pm"]`)。但 GEO-380 的活是造字体功能(FONT_PRIORITY 代码、Docker、部署、PR)—— 是后端工程。结果:**一个 PM 协议的 Runner 在跑后端实现**,全程靠 Lead 喂工程/部署决定。

product-executor 的协议(`.flywheel/agents/product/product-executor.md`)明文「你不写代码、不创建 PR、不做技术实现」,生命周期 `define→research→PRD→建 issue→handoff`;backend-executor 是 `brainstorm→research→plan→implement→ship-pr`(带 codex review)。两者协议根本不同。

### 2.2 审计发现 —— 管道早就绪,缺的是规则与默认
- `POST /api/runs/start` 已接受可选 `agentName`(`runs-route.ts:100-122` 校验 shape;`:355-381` 同步校验,未知名报 `400 INVALID_AGENT_NAME` + `available[]`)。
- `AgentDispatcher.dispatchByName(name)`(`AgentDispatcher.ts:229-244`)按名直接取 config、**完全 bypass label match**。
- ⇒ 实现 #1 **零 Bridge 代码改动**。
- production 的 `product/ops/cos-lead` 规则(源 `GeoForge3D/.lead/shared/department-lead-rules.md:210-237`)**已有** agentName override 一节,但 **flywheel base layer 一处都没有**(`grep agentName lead-rules-base/department-lead-rules.md` = 0),且现框架是 exception-based、明文「Default omit agentName / Do NOT override on a clean label」。

### 2.3 Annie 的根本 reframe(钦定心智模型 —— 规则核心)

> 这一节定义规则的灵魂,优先级高于"label vs work-type"这个机械层面的描述。

1. **正常 = 一个 issue → 一个正确类型的 executor → 从头到尾做完(brainstorm→research→plan→implement→ship)。这是默认。**
2. **工程类 executor(backend/frontend/…)自己会做 brainstorm/research/plan**,**不需要**先派 product-executor 去"预调研"。
3. **GEO-380 的真相不是"调研漂变成实现"**,而是 **它从一开始就该派 backend-executor**:造字体功能本身就是工程活,backend-executor 会先自己调研字体再实现。**Product 的调研 ≠ Backend 的调研** —— backend 的调研是它自身工程流程的一部分,不是另起一个 product 阶段。
4. **product-executor 仅当交付物本身就是调研/PM 产物**(一份调研文档、一份 spec、一份 PRD)时才用,**绝不是工程任务的"第一阶段"**。
5. **两-issue 拆分**(product 调研 issue → backend 实现 issue)是 **建 issue 时的刻意决定**(通常 founder 建,或 Lead 识别出"确实需要一份独立调研交付物先喂给后续实现"),**不是**"活漂成实现"就自动触发的动作。

**因此 FLY-178 #1 的核心 = end-to-end ownership**:Lead 按实际活类型路由到**将端到端拥有该 issue 的那个 executor**。机械手段是 work-type-first 传 `agentName`(label 当提示),但灵魂是"对的单个 agent 把一个 issue 做到底,工程 executor 自研、不被拆出无谓的 product 预调研阶段"。

### 5.3 base 文件 `executor-routing.md`（完整设计,Q2 已填）

> 抽象 voice:`each dept Lead` / `your project's declared executors` / `the founder`,**不写**具体执行器名。

```markdown
# Executor Routing by Work Type (FLY-178)

> Layer: flywheel base. Loaded by every NON-cos dept Lead (the roles that
> spawn Runners) via claude-lead.sh. Generic voice — the project layer
> supplies the concrete executor names, the work-type→executor map, and
> the literal curl to /api/runs/start.

## The default mental model — one issue, one executor, end to end

The normal shape of work is: **one issue → one correctly-typed executor →
that executor owns the whole lifecycle** (brainstorm → research → plan →
implement → ship). Before you spawn a Runner, your job is to pick the
**single executor that will own this issue end to end**, based on the
**actual type of work** the issue requires — then pass `agentName`
explicitly. The issue's Linear label is a **hint**, not the decision.

## Engineering executors do their own research — do NOT pre-stage with PM

This is the rule that prevents the GEO-380 class of error:

- **Engineering executors (backend / frontend / …) run their own
  brainstorm / research / plan** as part of their lifecycle. An
  engineering issue does **NOT** need a product/PM executor to
  "pre-research" it first.
- **Engineering work goes to the engineering executor from the start.**
  If the deliverable is code / a PR / a deployment, route to the
  engineering executor — it will research whatever it needs (the API,
  the library, the data) on its own, then implement and ship.
- **Product/PM research ≠ engineering research.** An engineering
  executor's research is a phase *inside* its own process, not a separate
  product stage handed off to it.

Concretely: an issue whose end-product is a working feature is an
engineering issue **even if it also requires investigation** — give it to
the engineering executor, not to a PM executor "to scope first."

## When the PM/research executor IS the right choice

Use the product/PM/research executor **only when the deliverable itself
is a research or product artifact** — a research write-up, a spec, a PRD,
a competitive analysis, a problem definition. That is: the *output* is
the document, not code. The PM executor is **never** the "phase 1" of an
engineering task.

## How to route

1. **Classify the actual work** by its end-product (a shipped feature/fix
   → engineering executor of the right domain; a research/spec/PRD doc →
   PM executor; a design artifact → designer; etc.).
2. **Map to the executor that will own it end to end** using your
   project's declared executors (`<project>/.flywheel/config.yaml`
   `agents:` block; `flywheel doctor` lists valid names).
3. **Pass `agentName` explicitly** on /api/runs/start (project layer gives
   the curl). This bypasses label dispatch via `dispatchByName`.
4. Unknown name → `400 INVALID_AGENT_NAME` + `available: [...]`; read it
   and retry with a valid name.

The `agentName` value is the **config key** your project declares in its
`agents:` map (the short key, e.g. the one matching your dept's
implementation executor) — **NOT** the executor's markdown file name or
its frontmatter `name`. `available: [...]` lists the valid keys.

You may omit `agentName` and let FLY-137 label dispatch pick — but only
when the label genuinely reflects the end-to-end work. Don't omit it as a
reflex.

## Department scope still applies (FLY-127 — do not weaken it)

"The label is a hint" is about **executor selection**, not department
ownership. `agentName` bypasses label-based *executor* matching; it does
**NOT** bypass FLY-127 department-scope enforcement, which Bridge checks
*before* it ever validates `agentName` (`isLeadInScope()` →
`DEPT_SCOPE_REJECT`). You may only choose an executor for an issue already
in **your** department's scope; passing `agentName` does not authorize
spawning on another department's issue. If Bridge returns
`DEPT_SCOPE_REJECT`, follow your Action Gate rule (fix labels / defer to
the owning dept) — do not try to force it with an explicit `agentName`.

## Trust your judgment (Q3 — no extra friction)

The override deliberately bypasses label match — that is the point. Your
work-type classification is authoritative. You do **not** owe a written
justification when your chosen executor contradicts a clean label;
choosing the right end-to-end executor is exactly your job. The only
guardrail is the name-validity check (`INVALID_AGENT_NAME`).

## Two issues is a deliberate design, not a drift-recovery (Q2)

Splitting work into a research issue (PM executor) **then** an
implementation issue (engineering executor) is a **deliberate decision
made at issue-creation time** — typically by the founder, or by a Lead
who recognizes that a genuinely independent research deliverable must be
produced *and consumed* before implementation can sensibly start (e.g.
"we don't yet know whether to build X or Y; produce a recommendation
first"). It is expressed as **two issues**, each owned end to end by its
correct executor.

It is **NOT** an automatic action triggered by "a research issue's work
turned into implementation." If an issue was mis-typed and the work is
really engineering, the fix is to **route it to the engineering executor
and let that one agent own it end to end** — not to insert a PM
pre-research stage.

## Mis-typed but not yet started → just correct the routing

If you realize an issue is pointed at the wrong executor and the Runner
hasn't meaningfully started, simply correct the routing: fix the label
and/or pass the right `agentName` on the (re)spawn, so the correct single
agent owns it end to end. No handoff ceremony needed.

## Mid-run protocol mismatch (Q4)

If a Runner you own is already executing under the **wrong protocol**
(e.g. a PM-protocol Runner doing implementation work):

- **Do NOT auto-terminate, reject, defer, shelve, or re-dispatch it.**
  Each ends a Runner's life and is **founder-only** in the current window
  (`founder-only-authority.md`, R2). A protocol mismatch is not an
  exception to R2.
- **Instead**: surface the mismatch in the issue's chat thread and
  **propose** the correct re-routing (e.g. "this is engineering work; I
  recommend we re-dispatch <engineering executor> to own it end to end").
  Then **wait for the founder's decision**.

## Relationship to FLY-137 label dispatch

This rule sits on top of FLY-137. When you omit `agentName`, FLY-137's
label dispatch still applies as the fallback. The contract: lead with the
end-to-end work-type judgment; don't *rely* on the fallback for
non-trivial routing.

## Project-layer extension

Your project layer provides the concrete executor names, the
work-type→executor mapping, and the literal curl. It MUST align with this
contract (end-to-end ownership, engineering self-research); it must not
re-assert the old "omit by default / don't override on a clean label"
framing.
```
