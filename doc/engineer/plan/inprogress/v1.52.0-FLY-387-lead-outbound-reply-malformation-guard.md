## Background — 审计推翻 issue 假设

Issue 假设「出站 malformation 从缝里漏、没人修」。审计发现真相不同:

机器上**已经有**一个 Stop hook `~/.claude/hooks/discord-reply-enforcer.py`,且**已注册并在跑**(`~/.claude/settings.json` Stop hook 列表里有 `python3 .../discord-reply-enforcer.py`,Stop summary 实测列出它被执行)。逻辑基本对(写了实质文本却没调 reply 工具 → `block` stop 让 Lead 重发)。它救不了 Belle 是因为两个具体缺陷(**不是「死代码从未跑」,是「ad hoc 装了但对 Lead 无效」**;它只在 block 时写 log,所以缺 log ≠ 没跑过):

1. **cwd 豁免 bug(核心)**: 它顶部
   ```python
   cwd = (data.get("cwd") or "").lower()
   if "flywheel" in cwd: return 0
   ```
   而每个 Lead 的 workspace = `~/.flywheel/lead-workspace/<lead-id>`(claude-lead.sh:378-386),路径含 `flywheel` → **每个 Lead 都被早退豁免**。注释写「Lead daemons intentionally sometimes decide not to reply」—— 作者是为了**避免误判 Lead 刻意沉默**才关掉的,但连真 malformation 也一起放过了。
2. **Discord-触发盲点**: 它要求先找到最后一条 `<channel source="discord">` user turn(`discord-reply-enforcer.py:68-81`),否则 return。但 Lead **主动**发消息(非被入站触发)那轮泄漏时,transcript 里没有 Discord-触发 turn → 漏判。Codex 实测:product-lead 真实泄漏样本(下文)所在 transcript **该泄漏点之前零条 Discord user turn** → 旧 hook 这条也会漏。

**ship 含义**: 本 PR 是**替换**一个已经 ad-hoc 装在 user `~/.claude/settings.json` 里的 Stop hook,不是装进真空。

### 真实泄漏样本(已 Codex 复核,TDD must-block fixture)

`~/.claude/projects/-Users-xiaorongli--flywheel-lead-workspace-product-lead/a90f932f-…jsonl:54775`:cwd=`~/.flywheel/lead-workspace/product-lead`,assistant 消息恰一个 `text` block、**无 tool_use**、含 `<invoke name="mcp__plugin_discord_discord__reply">`、含 `chat_id=1487340532610109520`、用 `<parameter name="message">`(注意:reply 工具真实参数名是 `text`(server.ts:744),模型泄漏时连参数名都幻觉错成 `message` → 回收要兼容 `text`|`message`)。该泄漏点**之前无 Discord user turn**。同形态样本在 cos-lead / rafiki-lead / personal-assistant 都有。

关键事实(决定检测可行性):
- 泄漏体落在**纯 text block**(`type:"text"`),该 assistant 消息**无 tool_use** → `reply_called=False`,且**不在** Markdown 围栏代码块里(裸文本)。
- 签名 `<invoke name="mcp__plugin_discord_discord__reply"` **在剥离围栏代码块后无歧义**(R2#1:诊断/解释这个 bug 的 Lead 会把 XML 引在 ```` ``` ```` 里,那是解释非出站 → 必须先剥围栏)。
- `chat_id` 可从泄漏 XML 的 `<parameter name="chat_id">(\d+)</parameter>` 回收 → 能让 Lead 精准重发。

## Goal

Lead 把 reply 写成文本(没 execute)时 → **立刻拦截 + 纠正让其真发**,Annie 不再收不到回复;**绝不误伤刻意沉默的 Lead**;一轮一纠正、不 wedge。

## Design — 精确 Lead 谓词路由「两个独立 tier」

核心洞察:同一个判断,旧代码用它**早退豁免 Lead**,新代码用它**路由到两个独立检测 routine**(router 选一个,互不交叉 → Tier A 天然字节不变)。

```
main(stdin):
  data = parse(stdin)
  cwd  = data.cwd or ""
  # ── bounded(防 wedge)+ 持续失败遥测 ───────────────
  if data.stop_hook_active:
      # 一个 stop-sequence 只纠正一次(Claude Code 递归保护)。纠正后仍泄漏 →
      # bounded fail-open(放行,绝不 wedge),但落「可用遥测」(非用户可见恢复;
      # founder-visible alert 是 FLY-368 范围,此处显式留缺口)。
      blk = latest_assistant_leak(data.transcript_path)   # 同 Tier B 的泄漏检测
      if blk: loud_log("PERSISTENT_LEAK_AFTER_NUDGE lead=<id> cwd=<cwd> "
                       "transcript=<path> uuid=<msg uuid> chat_id=<id> "
                       "prefix=<redacted 40> hash=<sha1>")
      return 0

  if not transcript_exists: return 0

  # ── 精确 Lead 谓词(Codex #7:别用粗 'flywheel' in cwd)──────────
  is_lead = bool(env FLYWHEEL_LEAD_ID) or ("/.flywheel/lead-workspace/" in cwd)

  if is_lead:  return tier_b(transcript, cwd)   # 新 = FLY-387 核心
  else:        return tier_a(transcript, cwd)   # 旧逻辑逐字保留(byte-compat)
```

### Tier B(新,Lead)—— 不要求 Discord-触发(Codex R1#1)+ 防诊断引用误伤(R2#1)+ 锚 genuine user turn(R2#2)

```
tier_b(transcript, cwd):
  # 窗口 = 「当前 stop sequence」= 最后一条 GENUINE user prompt 之后的 assistant turn(s)。
  # genuine = content 不是「纯 tool_result」的 user 行(R2#2:tool_result 也是 type:user 行,
  # 若用'最后一条 user 行'会漏「泄漏 + 非-reply 工具(如 ScheduleWakeup) → tool_result → 平淡收尾」)。
  # 纯 tool_result 定义(R3 note 2)= list content 且每个 block 都是 {"type":"tool_result"};
  # string content / 混合 text+tool_result / 任何非-tool_result block → 算 genuine。
  start = index after last user row whose content is NOT solely tool_result
  blocks = assistant blocks in rows[start:]
  reply_called = any tool_use(name == "mcp__plugin_discord_discord__reply") in blocks
  if reply_called: return 0                       # 已真发(工具调用在 tool_result 之前也算)
  text_total = concat(text blocks)
  scan = strip_fenced_code(text_total)            # R2#1:剥离 ``` fenced code block 再扫
  m = LEAK_RE.search(scan)
  if not m: return 0                              # ← 无泄漏签名 → 绝不误伤刻意沉默/诊断引用(约束③)
  chat_id = recover_chat_id(scan)                 # 从泄漏 XML <parameter name="chat_id">
  msg     = cap(recover_message(scan), 2KB)       # R2#4:回收 message 截断上限,全长+sha1 进 log
  block(tier_b_reason(chat_id, msg)); return 0
```
- 无 Discord-触发要求 → 抓住 product-lead 那种**主动**泄漏(line 54775 must-block;裸文本不在 fence → 剥离后仍命中)。
- `strip_fenced_code` 关键防误伤(R2#1 真反例):做 FLY-387 / 诊断这个 bug 的 Lead(如 cos-lead line 4750)会把 XML **引在代码块里**解释 —— 那不是出站尝试,剥 fence 后不命中 → 不 block。
- 仅在剥 fence 后 `LEAK_RE` 命中且没真调 reply 时 block → 误判面≈0;Lead 写正常 prose 沉默/后台活 → 不命中 → return 0。

### Tier A(旧,非-Lead/personal-assistant)—— 逐字保留

```
tier_a(transcript, cwd):  # = 旧 discord-reply-enforcer.py cwd 守卫之后那段,原样
  last_discord = last user turn containing '<channel source="discord"'
  if last_discord is None: return 0
  reply_called / text_total = scan assistant after last_discord    # 同旧
  if reply_called: return 0
  if len(text_total) >= SUBSTANTIVE_TEXT_MIN_CHARS(30):

```

### LEAK_RE(锚定精确工具名,Codex #4)

```python
LEAK_RE = re.compile(
    r'<(?:antml:)?invoke\b[^>]*\bname="(?:antml:)?mcp__plugin_discord_discord__reply(?:"|(?=[\s>/]|$))',
    re.IGNORECASE)
```
- 命中真实样本 `<invoke name="mcp__plugin_discord_discord__reply">`,兼容 `<invoke>` 前缀变体、截断(缺收尾引号)。
- 收尾用 `(?:"|(?=[\s>/]|$))`(R2#3:`\b` 会把 `__reply-extra` 的连字符当词边界误匹配)→ **不**命中 `mcp__plugin_notdiscord_reply` / `reply_to_message` / `reply-extra`(锚定全名,非 `discord`+`reply` 子串)。
- `strip_fenced_code(text)`: **balanced-only** 移除完整 ```` ``` ... ``` ````(含语言标记)围栏块再扫,防诊断引用误伤(R2#1);**未闭合/孤立围栏保留在扫描文本里**(R3 note 1:orphan opening fence 不能藏真泄漏)。
- `recover_chat_id`: `<parameter name="chat_id">\s*(\d+)`;`recover_message`: 兼容 `name="message"` 与 `name="text"`,截断到 2KB(R2#4)。

### Tier B reason(带回收上下文,精准重发;纯文本拼接,无反引号包裹命令)

> 如果你本来就不打算回复,显式说 "intentionally not replying" 让我知道这是有意的。

(recovered message 喂回 reason 前截断到 2KB(R2#4),防 context 膨胀;全长 + sha1 落 log。)

### Install 细节(约束② + Codex #3 细粒度)

镜像 `install_post_compact_hook` 的「稳定路径 + jq + 校验」骨架,但**删除粒度收细**(PostCompact 整组删会误伤 Stop 同组 sibling):
- 源 → `~/.flywheel/bin/discord-reply-enforcer.py`。
- jq patch `.hooks.Stop`:对每个 hook group,**只从其 `hooks[]` 里滤掉 command endswith `discord-reply-enforcer.py` 的项**;若该 group 还剩别的 hook → 保留 group;group 变空才删;再 additive 加稳定路径条目(已存在则不加)。**绝不动**别的 Stop hook。
- 同时清掉旧的手工 `~/.claude/hooks/discord-reply-enforcer.py` 条目(command 不同但 basename 同 → endswith 命中)。
- `jq empty` 前后校验;失败 → skip + WARN,**原样保留 settings.json**(fail-open,不破坏)。
- companion(Belle)**也装**(本 hook 与 PostCompact 不同,不 companion-skip)。
