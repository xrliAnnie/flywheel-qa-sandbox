### 1.1 Track A — mailbox 无限增长(已坐实)

调用链:

```
事件源(GatePoller / HeartbeatService / DirectEventSink / plugin event loop / artifact-event / actions ...)
  └─ runtime.deliver(envelope)                       [MailboxLeadRuntime, 硬编码 3000ms timeout]
       └─ MailboxTransport.writeVerified(...)
            ├─ ClaudeCodeAdapter.write(...)
            │    └─ ClaudeMailboxCodec.writeMailboxEntry(...)

            │         ├─ writeMainEntryUnderLock:               [inbox lock]
            │         │    read 整个数组 → push → 整文件 temp+rename 写回
            │         └─ sidecar Phase C: finalize              [sidecar lock]
            └─ ClaudeCodeAdapter.verifyLastWrite(...)            读整个数组(或 sidecar)再验
```

**确认全代码库零 prune/cap/rotate/retention**(grep `prune|maxMessages|rotate|truncate|retention|evict|trim` 干净;命中的都是无关的日志 truncate / HeartbeatService 内存 Set prune / status query evict)。

- inbox = 单个整体 JSON 数组 `~/.claude/teams/<safeLead>/inboxes/<safeAgent>.json`。
- `writeMainEntryUnderLock`(`ClaudeMailboxCodec.ts:505`):读整数组 → `.push()` → 整文件写回。
- `markEntriesAsReadUnderLock`(同文件 :214):读整数组 → `.map()` 翻 `read=true` → 整文件写回。**从不删任何条目。**
- 每次投递 = O(n) 全文件 I/O(读 + 写 + sidecar + verify 再读)。560 条/460KB + ≥2 Runner 并发抢 proper-lockfile → 跨 3000ms → `writeVerified timed out` → `deliver()` 返回 `{delivered:false}` → `StateStore.recordDeliveryFailure` → 事件留 undelivered → 被多个 pump(HeartbeatService:538/gate-poller:249/DirectEventSink:495/plugin:946 ...)反复重试 → 锁竞争加剧 → 更多 timeout = **雪崩**。

## 2. 设计原则

1. **A1 安全第一**:**prune 代码绝不删除 `read:false` 条目**(这是 prune 函数的可证明属性)。⚠️ **注意边界(Codex R1#4)**:这**不是**端到端"消息绝不丢"保证 —— stock `useInboxPoller` 无锁读未读后调 `markMessagesAsRead` 会把**当时文件里所有**消息标 read;若 Bridge 写入恰好落在 stock 读与标记之间,该消息会被标 read 却没真正被 Lead 消费(**stock 既有行为,非本 prune 引入**)。本 prune 的 retention 窗口(最近 50 条 + 24h)给这种"刚标 read 未消费"的消息留足缓冲,不会立刻删;真正闭合该 race 需 stock/native 改成"只标刚消费的 message id"(超出本 issue 范围,§3.5 加 race 文档测试)。未读涨 = bug 信号,要**暴露**不要**吞**。
2. **就地 prune,不加锁循环**:prune 挂在 `writeMainEntryUnderLock` **已持有的 inbox 锁**临界区内,零额外锁、零新增 race。
3. **stock 兼容**:prune 后仍写 stock `TeammateMessage[]` 结构;只删 `read=true`,stock `useInboxPoller` 读 `read=false`,不受影响。
4. **零新增周期性 load**(FLY-129):GC 是**手动脚本** + 可选 boot 一次性 sweep(env 默认关),**不加周期 timer**。Track B 的 self-monitoring 挂在**已存在的 60s drainQueue timer**(`plugin.ts:1929`)上,同样不加新 timer。
5. **根因优先**:prune 让文件恒小 → 3000ms timeout 不再触发 → 雪崩自然消失。timeout 仅作 env 可调兜底,不靠调大它治标。
6. **LeadAlert 绝不静默失败**(Annie 铁律):任何告警发不出 / 队列卡住 / 配置缺口,都必须经一个**不依赖 Discord**的通道暴露给 Annie。宁可吵,不可哑。

### 3.1 mailbox prune(codec 层)

#### 3.1.1 新 `pruneMainEntries()` —— 在 inbox 锁内调用

在 `writeMainEntryUnderLock` 的临界区里,`messages.push(newEntry)` 之后、写回之前插入:

```ts
const pruned = pruneMainEntries(messages, prunePolicy());
// ... 写 pruned 而非 messages
```

`pruneMainEntries(entries, policy)`(纯函数,易测):

- 分区:`unread = entries.filter(e => !e.read)`、`read = entries.filter(e => e.read)`。**`read` 字段缺失/非布尔 → 当 unread**(安全侧,Codex R1#11)。
- **保留全部 unread**(A1:prune 代码绝不删 read:false)。
- read 子集:**丢掉同时满足 (a) 早于 `now - READ_RETENTION_MS` 且 (b) 不在最近 `READ_KEEP` 条之内** 的;即 `keptRead = read 中 (最近 READ_KEEP 条) ∪ (晚于 retention 窗口的)`。保证近期已读可见、丢老已读。
- 返回 `[...keptRead, ...unread]` 重排。**稳定 comparator(Codex R1#11)**:主键 `Date.parse(timestamp)`;**非法/相同 timestamp** 用**原数组 index 作 tie-breaker**(保持稳定序);非法 timestamp(NaN)排到末尾且按 index 稳定。加同毫秒/畸形记录测试。
- **不丢未读** → 若 unread 本身超大(Lead 不消费),文件仍可能大 → 由 §3.1.4 unread-overflow 升级**暴露**(不吞)。

策略默认(env 可调,Codex review):

| env | 默认 | 含义 |
|-----|------|------|
| `FLYWHEEL_MAILBOX_READ_KEEP` | `50` | 无论多旧,保留最近 N 条已读 |
| `FLYWHEEL_MAILBOX_READ_RETENTION_MS` | `86400000`(24h) | 早于此 + 超出 KEEP 的已读丢弃 |
| `FLYWHEEL_MAILBOX_UNREAD_WARN` | `200` | 未读数 ≥ 此 → 触发 overflow 升级(§3.1.4) |

#### 3.1.2 `markEntriesAsReadUnderLock` 也顺带 prune

ack/markRead 时一批条目刚转 `read=true`,正好是 prune 时机。同样在该函数已持有的 inbox 锁内,翻 read 后跑 `pruneMainEntries`,一次写回。

> **澄清(Codex R1#5)**:Lead 的**主消费路径是 stock `markMessagesAsRead`,不是 Flywheel `ClaudeCodeAdapter.ack()`** → stock 路径**不会**调本 `pruneMainEntries`。所以对 **Lead 自己的 inbox**,prune 实际发生在**下一次 Flywheel 写入**(Bridge 投递事件)时 —— 而 Lead inbox 正是 Bridge 高频写的对象,prune-on-write 足以兜住增长(本次事故就是 Bridge 在写、文件在涨)。`markEntriesAsReadUnderLock` 的 prune 主要覆盖 **Flywheel-ack 路径**(Runner inbox 等)。**不宣称** stock-read 的 write-light inbox 会被 ack-prune 兜到 —— 那种纯靠 §3.2 GC 或下次写。

#### 3.1.3 sidecar prune(`.flywheel.jsonl`)

新 `pruneSidecarRecords(records, now)`:丢弃 `status==="finalized"` 且 `finalizedAt < now - SIDECAR_RETENTION_MS`。**保留所有 pending**(可能在途)。挂在 `sidecarFinalize` 已持有的 sidecar 锁内执行(零额外锁),`rewriteJsonLines` 写回。

> **⚠️ 修正(Codex R1#2 HIGH — 1h 会破幂等)**:retention **不能**用 `PENDING_STALE_THRESHOLD_MS`(60s)量级。real race:`MailboxLeadRuntime.withTimeout` 3000ms 超时返回 `{delivered:false}`,但底层 `writeVerified` **仍在跑**并最终写 main + finalize sidecar;StateStore row 因 deliver 已返回 false 而**留 undelivered → 被 pump 重试**,重试用**同一 deterministic `flywheelId`**。若 finalized sidecar 记录已被 1h prune 掉 → `sidecarFindByFlywheelId` miss → **写出重复 main 消息**(`verifyLastWrite` 的 main-scan 只在写后跑,挡不住这条重复)。故 finalized retention **必须 ≥ 最大重试/审计地平线**。
> **定(idempotency-first,Codex R2#1)**:**保留所有 retention 窗口(7天)内的 finalized** —— 这是幂等硬约束,**绝不被 count cap 推翻**。`SIDECAR_KEEP` 只对**早于 retention 的老记录**提供额外保护(再多留最近 N 条老的),**不是**会砍掉窗口内记录的硬上限。即 drop = `finalizedAt < now-RETENTION` **且** 不在"最近 KEEP 条老记录"内。pending 永不按时间 prune。**有意不设会违反 retention 的硬 size cap**(极端高频下宁可 sidecar 大也不破幂等;真遇到再单独治理)。

| env | 默认 | 含义 |
|-----|------|------|
| `FLYWHEEL_MAILBOX_SIDECAR_RETENTION_MS` | `604800000`(**7天**) | finalized 早于此才**可能**丢(硬保留窗口,不被 cap 推翻) |
| `FLYWHEEL_MAILBOX_SIDECAR_KEEP` | `2000` | 对**早于 retention 的**老 finalized 再额外保最近 N 条 |

#### 3.1.4 unread-overflow 升级(A1 "暴露不消费")

`pruneMainEntries` 计算 unread 数;`writeMainEntryUnderLock` 拿到结果后判 `unread` vs `UNREAD_WARN`。

**marker 身份 + 清理契约(Codex R1#6)**:
- `writeMainEntryUnderLock` 当前只收 `inboxPath/recipient/newEntry` → 从 **`inboxPath` 解析 `{team, recipient}`**(`.../teams/<team>/inboxes/<recipient>.json`),不靠猜 leadName(否则 `product-lead/inboxes/team-lead.json` 这类会张冠李戴)。
- marker 文件名 = **inbox-path 的稳定 hash**(`sha1(inboxPath)`),内容含**人读 inbox 路径** + `{team, recipient, unread, oldestUnreadTs, observedAt}`。
- **越界(`unread >= UNREAD_WARN`)**:atomic temp+rename 写/覆盖 marker(幂等,非 append)。
- **回落(`unread < UNREAD_WARN`)**:**删除该 marker**(`unlink`,忽略 ENOENT)→ unread 消化后 PR2 self-monitoring 不再对 stale marker 报警。
- 结构化 `console.warn`(Bridge 日志可见)。
- **告警投递归 Track B**:marker 由 PR2 self-monitoring 读取经告警通道 + meta-alert 送 Annie。PR1 只**检测 + marker 写/删 + log**,接口 ready,delivery 留 PR2。
- 测试:越界写、幂等覆盖、回落删除、{team,recipient} 解析正确。

> 这样 A1 的"高位上限兜底"= 只删已读仍压不住(unread 洪水)时,不悄悄丢未读,而是**越界即升级**暴露"Lead 不消费",回落即自清。安全且不丢数据。

#### 3.1.5 性能 / 去雪崩

- prune 后文件恒在 ~(READ_KEEP + 正常 unread) 量级 → O(n) 的 n 恒小 → 3000ms 不再触发。
- `MailboxLeadRuntime` 的 `writeTimeoutMs` 增加 env 覆盖 `FLYWHEEL_MAILBOX_WRITE_TIMEOUT_MS`(默认仍 3000,保持兼容)。**必须在 factory 接线(Codex R1#10)**:`packages/teamlead/src/bridge/plugin.ts` 的 `createLeadRuntime()` 现在是 `new MailboxLeadRuntime({ leadId, transport })` —— 要 parse + 校验正整数边界 + 传入,否则 env 不生效。仅兜底,不靠调大治标。
- 雪崩自愈:undelivered 事件重试在文件变小后即成功,无需改重试逻辑。

- `ClaudeMailboxCodec` 集成:write/markRead 后文件确实变小且 stock 结构合法;`readUnread` 仍返回全部未读(prune 不误伤)。
- **真 stock-poller 兼容**(per memory 教训:mock 会编码错误假设):用真 inbox 文件跑 `readMailboxEntries` round-trip 验证 prune 后 stock 仍能读未读。
- **stock read/mark race 文档测试(Codex R1#4)**:显式构造"stock read-unread → Bridge write → stock markAllRead"序列,断言**这条 race 是 stock 既有行为、本 prune 不放大**(retention 窗口让刚标 read 的消息至少留 24h)。把 gap 写进测试注释,标"真正闭合需 native 改 mark-by-id"。
- unread-overflow:越界 marker 写 + 幂等覆盖(不 append)+ **回落删除** + {team,recipient} 从 inboxPath 解析正确。
- sidecar:丢"超 7 天 **且** 超 KEEP cap"的 finalized;留所有 pending;留 7 天内 finalized → **超时但写成功的 retry 仍能 dedupe**(回归 Codex R1#2)。
`scripts/__tests__/mailbox-gc.test.*`:
- 活 team(pgrep 命中)/ Lead team(projects.json)/ 近期 team(mtime)**一律不入候选**。
- dry-run 不删;--apply 先备份后删。

### 3.5 兼容性 / 风险

- **stock 兼容**:只删 read=true + 保 stock 结构 → `useInboxPoller` 无感。
- **idempotency**:sidecar finalized retention = **7天 + count cap**(Codex R1#2 修正),覆盖"超时返 false 但底层写成功 → 被 pump 重试"的长地平线;pending 永不按时间 prune → 幂等不破。
- **并发**:prune 在已持锁临界区,与 stock `markMessagesAsRead` 经 proper-lockfile 互斥(同 `${inbox}.lock`)→ 无新 race。
- **数据安全**:GC dry-run 默认 + 备份;mailbox 绝不丢未读。
- **回滚**:prune 是纯增量(env 关掉 KEEP/RETENTION 设极大值即等效旧行为);GC 是独立脚本不影响运行时。

### 4.2 永久 vs 瞬时失败分类

新类型 `type AlertFailureClass = "permanent" | "transient"`:

| 失败 | 分类 | 处理 |
|------|------|------|
| `no-channel`(channel 解析失败) | **permanent**(运行期配置不变) | **不入重试队列**;dead-letter + meta-alert(暴露配置缺口) |
| `no-token` | **permanent** | 同上 |
| `unknown-lead` | **permanent** | log + meta-alert(投递目标本身不存在) |
| Discord 5xx / 网络异常 / fetch throw | **transient** | 入队列,带 cap + 老化,N 次后 dead-letter |
| Discord 429(rate limit) | **transient** | 同上(尊重 retry,不立即 dead-letter) |
| Discord 4xx(401/403/404 —— token/权限/频道错) | **permanent** | dead-letter + meta-alert(配置/权限问题,重试无用) |

> 关键:**永久失败(配置不变)无限重试 = 今天 1667 积压的成因。** 永久的直接 dead-letter,不灌爆队列。

### 4.4 `drainQueue()` 改造(修永久失败空转 + cap/aging)

- 现 bug:`if(!channel||!token) continue` → 永久失败件永远跳过、永不出队 = sent=0 死循环。
- 新逻辑(每条队列件):
  - **件记录的 `queueReason ∈ {no-channel, no-token, unknown-lead}` → 直接 dead-letter + metaAlert**(永久,**无视**当前配置能否解析 —— Codex R1#3,防改配置后历史件批量轰炸 core)。
  - channel/token 仍解析不出 → **dead-letter**(`unlink` + 移 deadletter)+ metaAlert,**不再 continue 占位**。
  - 件龄 > `MAX_AGE`(默认 3 天)→ dead-letter(老化)。
  - 队列总数 > `MAX`(默认 500)→ 最旧的超出部分 dead-letter(cap)。
  - **JSON parse 失败的 malformed 件 → dead-letter(Codex R2#2)**,不再原地 skip。现 `drainQueue` skip malformed 会让 `remaining>0` 永久、反复触发 stuck self-monitoring 却永不出队。移到 `alert-deadletter/`(文件名/旁置元数据带 parse error)+ 去抖 meta-alert 一次。
  - 否则正常 POST;成功 unlink,失败留队列(瞬时重试)。
- 返回值扩展 `{sent, remaining, deadLettered}`,供 §4.5 self-monitoring 判断。

| env | 默认 | 含义 |
|-----|------|------|
| `FLYWHEEL_ALERT_QUEUE_MAX` | `500` | 队列上限,超出最旧 dead-letter |
| `FLYWHEEL_ALERT_QUEUE_MAX_AGE_MS` | `259200000`(3天) | 件龄上限,超时 dead-letter |
| dead-letter dir | `~/.flywheel/alert-deadletter/` | 不再重试,留审计 |
