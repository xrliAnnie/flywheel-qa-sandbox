# Plan: Proactive Discord-outbound tool for full-access Codex Lead

**Version**: v1.53.0 (provisional — Lead/Codex to confirm)
**Issue**: FLY-304
**Date**: 2026-06-21
**Source**: FLY-304 (Linear), Lead 指令 24cd7242 + 816a618c
**Status**: codex-approved (design review Round 1 APPROVED, 6 hardening items folded in — see §9)

## 1. Problem

full-access Codex Lead(Mufasa,FLY-350 v1.51 cutover 后已上线)只能 **reply-on-mention**
(被 @ 才回),**不能主动 initiate** 往频道发消息。这是 Annie 原始困扰(FLY-350 的真正缺口),
FLY-392 live QA 实锤:Mufasa 缺一个 model-callable 的主动发送工具。

**根因(已 verify 代码)**:`buildCodexLeadRuntime`(codex-lead-runtime.ts)只为 (Z)
`write-capable` 档注入 action MCP(the gateway)。`full-access` 落入 else 分支
`buildCodexLeadMcpArgv({ chrome })` —— **不注入任何 action MCP**,所以模型没有 `discord_send`
工具。reply-on-mention 是 runtime 级(`DirectDiscordOutboundSender`,outbound=direct),
不是模型可调用的工具,因此只能被动回复。

## 2. Goal

full-access Codex Lead 能 **主动** 往其被授权的频道(尤其 #leads-roundtable
`1512578695468941333`)发消息,跟 Claude Lead 一样能主动出站 —— 通过一个 model-callable
的 `discord_send` 工具。频道授权 fail-closed、token 不外泄、`founder-only-authority`
(merge/ship)不受影响。

## 3. Design — reuse the existing audited send path (不重新发明)

`content-coordination` 档**已有**一个主动 `discord_send` MCP(`lead-actions-main.ts`),
建立在共享、已审计的 `runDiscordSend`(`discord-send-core.ts`)+ alias-allowlist 之上:
- `target` 只接受 alias(`chat` / `roundtable`),**server-side 解析**为 channel id,
  模型**永远传不了裸 channel id**;
- per-channel rate limit + in-process idempotency(FLY-220 loop-safety);
- metadata-only audit(绝不记消息正文);
- `allowed_mentions:{parse:[]}` + chunking(无 `@everyone`/role ping)。

把**同一个工具**暴露给 full-access,**唯一的不同点 = token 来源**。

### 3.1 Change 1 — lead-actions token 双路径(唯一真正的新逻辑)

`content-coordination` 经 **parent broker** 取 `DISCORD_BOT_TOKEN`(net-off + secretless config)。
`full-access` **没有 broker**,但其 env allowlist 已含 `DISCORD_BOT_TOKEN`(Claude-equal,
`FULL_ACCESS_ENV_ALLOWLIST`)。所以:

- `config.ts`:`brokerSocketPath` 改为 **optional**。
- `lead-actions-main.ts`:
  - broker socket 已配置 → 走 broker(**UNCHANGED**,content-coordination 字节兼容);
  - 否则 → 从自身 env 读 `DISCORD_BOT_TOKEN`(full-access 路径);
  - 两者都没有 → **fail-closed**(一个无 token 的 action server 必须拒启,不能 limp）。

### 3.2 Change 2 — `buildCodexLeadMcpArgv` 增加 `leadActions` 选项

为 headless app-server(full-access 用的 runtime)产出
`-c mcp_servers.lead_actions.{command,args,env,env_vars}` 覆盖:

- **token 经 `env_vars=["DISCORD_BOT_TOKEN"]` 按 NAME 转发**(已在 full-access app-server
  env 内;**绝不以裸值进 argv**)。
- 非密频道坐标(`FLYWHEEL_LEAD_ID` / `FLYWHEEL_PROJECT_NAME` /
  `FLYWHEEL_LEAD_CHAT_CHANNEL_ID` / `FLYWHEEL_LEAD_CROSS_DEPT_CHANNEL_IDS` /
  `FLYWHEEL_LEAD_ACTIONS_STATE_DIR` / 可选 alias pin / rate 旋钮)以 **literal `env.K=value`**
  写入(channel id 是非密)。
- `assertNoRawSecret` 扩展:拒绝任何 secret-shaped(`*TOKEN*`/`*SECRET*`/`*KEY*`)的 literal
  `env` 值(镜像 TUI 路径已有的 secret scan);`env_vars` 仍只接受 bare name。
- `specToArgv` 扩展以支持 `env`(literal)字段。

> 说明:full-access 走 `-c` argv 注入路径(`buildCodexLeadMcpArgv`),**不是** config.toml
> 路径,所以 `assertLeadActionsConfigGate`(禁 `env_vars`、要求 secretless)那条严格门
> **不适用** full-access —— 它服务的是 TUI/confined 的 config.toml 写入。full-access 的
> token-by-name 转发是其 Claude-equal 模型的正常形态。

### 3.3 Change 3 — `buildCodexLeadRuntime` full-access 接线

full-access 分支改为
`buildCodexLeadMcpArgv({ chrome: config.chrome, leadActions: {…} })`;**不起 broker**
(保持 Claude-equal)。`spawnArgv` 已为 full-access 前置 `buildFullAccessArgv`,
lead_actions 的 `-c` 覆盖追加其后。

提供给 `leadActions` 的:lead-actions-main.js 的 trusted dist 路径、node bin
(`process.execPath`)、state dir、上述非密坐标 + `env_vars:["DISCORD_BOT_TOKEN"]`。

## 4. Channel authorization (security)

- alias gate **不变**:模型只能传 `chat` + `roundtable`,server-side 解析为 own chat /
  单一 cross-dept channel;裸 channel id 被拒;ambiguous(0 或多个 cross-dept)fail-closed。
- token **绝不上 argv**(env_vars by name);非密坐标才用 literal env。
- rate-limit + idempotency + metadata-only audit 全部继承自 `runDiscordSend`。
- `founder-only-authority`(merge/ship)不被触碰 —— `discord_send` 不是 merge/ship 动作。

**诚实 caveat(写进 PR + 给 reviewer)**:full-access 本就是 Claude-equal 的全 shell +
network ON + env 里有 `DISCORD_BOT_TOKEN`,所以一个执意的模型理论上能 shell-curl Discord
绕过 alias gate —— 这跟 Claude Lead 完全同构(Claude Lead 也能)。本工具提供的是**干净、
审计、alias-gated 的正路**(护栏 + 顺手),**不是硬沙箱边界**。硬边界仍是 merge/ship 的
founder-gate + branch protection。这是 Annie 明确的 "Codex = Claude-equal" 选择下的对等态。

## 5. Scope / byte-compat

- `content-coordination` + `write-capable` + read-only companion 路径 **不变**
  (broker token 路径未动;env-token 路径仅在无 broker 时触发)。
- full-access 之前注入 0 个 action MCP → 现注入 `lead_actions`(仅此一处行为变化)。
- founder gate / merge-ship 路径 0 改动。

## 9. Codex design review — APPROVED (Round 1) + folded-in hardening

Codex (xhigh) verified claims against source AND verified the Codex CLI side
(`codex app-server -c` 支持 dotted overrides;`codex mcp list --json` 接受一个同时含 literal
`env` + `env_vars` 的 server)。**Verdict: APPROVED**。复用 `lead-actions-main.ts` 是正确
scope(新建 MCP 会重复已审计的 channel/rate/idempotency/audit)。6 项 hardening 全部采纳,
folded into 实现:

1. **`leadActions` 与 gateway 互斥**(item 1):`buildCodexLeadMcpArgv` 若同时收到
   `gateway` + `leadActions` → **throw**(loud)。gateway-only allowlist 是 write-capable
   的安全不变量(MCP child 在 sandbox 外),绝不能旁开第二个 action surface。
   单测:write-capable 仍**恰好** gateway-only、永不含 `lead_actions`。
2. **trusted dist 路径 fail-loud**(item 2):新增 `defaultLeadActionsEntryPath()`
   (类比 `defaultGatewayEntryPath()`,由 import.meta.url 解析),full-access 接线处
   `existsSync` 校验,缺失则 fail-closed + build 提示(不静默起一个坏 MCP command)。
3. **token 来源 pin**(item 3):full-access baseEnv 在 allowlist copy **之后**注入
   `DISCORD_BOT_TOKEN: config.botToken`(或断言 `buildFullAccessEnv(process.env)
   .DISCORD_BOT_TOKEN === config.botToken`)→ token-by-name 在 test/embedded caller
   (config 来自非 process.env)下也稳。token 仍不进 argv。
4. **不弱化 TUI/config.toml gate**(item 4):`brokerSocketPath` 在
   `parseLeadActionsConfig`/`leadActionsMain` 改 optional + **显式 mode**(`broker` vs
   `env-token`),但 config.toml builder + `assertLeadActionsConfigGate` **保持 broker-only**
   (仍拒 `env_vars`)。content-coordination/TUI 的 broker-only 不变量不被触碰。
5. **roundtable alias 部署断言**(item 5):full-access runtime test 带
   `FLYWHEEL_LEAD_CROSS_DEPT_CHANNEL_IDS=1512578695468941333`;dry-run/log 输出
   `roundtable` 是否可用(0 cross-dept → `chat` 可用但 roundtable 不可用,需让 Mufasa
   full-access 部署看得见)。
6. **`-c` 编码形状单测**(item 6):断言
   `mcp_servers.lead_actions.env.FLYWHEEL_LEAD_ID="..."` /
   `...env.FLYWHEEL_LEAD_CROSS_DEPT_CHANNEL_IDS="..."` /
   `...env_vars=["DISCORD_BOT_TOKEN"]` 都被 emit;secret-shaped literal env 键/值被拒,
   bare env var name 仍允许。

**安全边界结论(Codex)**:对一个 full-access = Claude-equal 的 Lead,正路就是暴露已审计的
`discord_send` 并明确它是 preferred/audited 路径、非 sandbox 边界。更严的 channel 边界 =
不把这个 Lead 跑成 full-access(退回 confined write-capable gateway 模型)—— 那是 Annie
已拍板之外的选择,不在本 issue。
