## 1. 背景与根因(审计修正)

cmux 里 product/ops/cos 三列反复变空白(显示空 zsh),长期反复(FLY-98/FLY-169 延伸)。

**原诊断被推翻**:原 issue 写"FLY-169 self-heal 只覆盖 0-client、不覆盖 window-drift"。审计 `scripts/flywheel-cmux-sync.sh` 后确认 **window-drift 自愈早已存在**:
- `refresh_linked_sessions()` 按窗口**名字** `select-window -t "=cmux-<lead>:=<lead-window>"`(`=` 精确匹配,不靠 index)把漂走的 current-window 纠回,幂等、纯 tmux、无 cmux IPC。
- 已接入 `sync_additive`(每 60s)+ `sync_additive_bootstrap`(watcher 启动)。
- 另有 FLY-169 `self_heal_one_workspace` 的 event 路径(Lead 重启 → after-new-window hook → drain,≤15s)。

**真因 = watcher 无守护进程裸死**。`flywheel-cmux-sync --watch` 不是 launchd 托管(bridge/3 Lead/updater/standup 都有 plist,唯独 watcher 没有),靠 `.zshrc` → `cmux-integration.zsh` 在「shell 开在 cmux 内(`CMUX_WORKSPACE_ID` 有值)」时拉起一次 + 单实例锁。主进程一死,不开新 cmux shell 就长期裸死(本次约 16h)。watcher 死 → `sync_additive`/`refresh_linked_sessions`/`self_heal_*` 全停 → 列一直空白。

**结论**:不需要新写 drift 检测。只要 watcher 一直活着,现有自愈就管用。修复 = 给 watcher 上 launchd 守护 + 实测验证现有自愈。

## 2. Scope

**做**:
1. watcher 用 launchd KeepAlive 托管(进程一死自动拉起,launchd 管真正的 watcher PID)。
2. 实测验证现有自愈在 watcher 活着时确实管用 —— **覆盖全部 live 失效模式 ①②③**:② window drift 在 product/ops/cos **三个都验**;① attach 掉线(0-client)、③ linked-session 死了重建 在**一个代表性 prod Lead(product)**上验(代码路径共享、操作更扰动,代表即可)。
3. **顺手收紧 ④**(team-lead 拍板,在 scope 内):`refresh_linked_sessions` 的 `select-window` 同名歧义 → 按 `window_id`(live pane)兜底,不选中残留死窗。

**不做**:
- 不新写 drift 检测器;**不动 `self_heal_*` re-attach 逻辑**。④ 只是对 `refresh_linked_sessions` 里 select-window 选择子的小幅 hardening(name→live window_id),非新检测器。
- 不做结构性重构(每 Lead 独立 session 根治 ② = 单独 follow-up issue)。
- 不给 test-slot 特殊处理(watcher 单进程管所有 session,launchd 守护它 → test-slot 自动受益)。
- ⑤ ghost workspace(症状是无列,非空白列)/ ⑥ cmux IPC 挂 → 标为已知 out-of-scope。

## 4. 设计

> **Codex R1 收紧的核心两点**:(a) launchd 必须管*真正的 watcher* 进程(wrapper 要 `exec`),(b) 不能靠 `KeepAlive` + lock-held `exit 0` 来共存(会变 30s 空转循环,违反 FLY-129 零新增周期 load)。本设计用 **supervised blocking-acquire** 模式根除空转。

### 4.1 新增 launchd plist

`~/Library/LaunchAgents/com.flywheel.cmux-watcher.plist`(部署时由 install 脚本按 `$HOME` 从仓库 tokenized 模板生成,**不在仓库放硬编码用户路径**),参照 `com.flywheel.lead.*.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key><string>com.flywheel.cmux-watcher</string>
    <key>ProgramArguments</key>
    <array>
        <string>/bin/bash</string>
        <string>__HOME__/.flywheel/bin/flywheel-cmux-autostart</string>
    </array>
    <key>EnvironmentVariables</key>
    <dict>
        <key>FLYWHEEL_CMUX_SUPERVISED</key><string>1</string>
    </dict>
    <key>KeepAlive</key><true/>
    <key>ThrottleInterval</key><integer>30</integer>
    <key>RunAtLoad</key><true/>
    <key>StandardOutPath</key><string>/tmp/flywheel-cmux-watcher.log</string>
    <key>StandardErrorPath</key><string>/tmp/flywheel-cmux-watcher.log</string>
</dict>
</plist>
```

- `KeepAlive=true`:进程一死(crash / kill / 健康检查 fatal)launchd 自动拉起。**不**用 `{SuccessfulExit:false}`(否则 `.zshrc` watcher 后来死掉时 launchd 不会接管,守护就漏)。
- `RunAtLoad=true`:登录即起,launchd 通常先于任何 cmux shell 抢到锁、成为长生 owner。
- `ThrottleInterval=30`:与 Lead plist 一致;cmux 未就绪时配合 watcher 自身 health-check backoff(脚本已有,不会死循环)。
- `FLYWHEEL_CMUX_SUPERVISED=1`:仅 launchd 路径设此 env,启用 §4.3 的 blocking-acquire(`.zshrc` 路径不设,保持快速 exit)。
- log 沿用现有 `/tmp/flywheel-cmux-watcher.log`,不另起文件。

### 4.2 wrapper:`flywheel-cmux-autostart.sh` 改为 `exec`(Codex R1 HIGH-2)

现状 wrapper 把 `"$SYNC_SCRIPT" --watch` 当**子进程**起 + wait;FLY-129 当时注释特意"不 exec"理由是留 EXIT trap 给未来副作用。但锁释放早已搬进 sync 脚本自己的 trap,wrapper 的非-exec 此刻**零收益却引入 orphan**:launchd 会管 wrapper 的 PID 而非真正的 watcher → `bootout`/`kickstart -k`/TERM 时子 watcher 可能 orphan、继续持锁 → 空转/回滚歧义。

改法:wrapper 顶部加 PATH 展开后,**`exec` 真正的 watcher**:

```bash
# launchd provides only /usr/bin:/bin:/usr/sbin:/sbin; cmux/tmux live outside it.
export PATH="/opt/homebrew/bin:/usr/local/bin:${PATH}"
...
exec "$SYNC_SCRIPT" --watch >> "$LOG" 2>&1
```

- `.zshrc` 的 `flywheel-cmux-autostart &!` 配合 `exec` 仍正常:后台的就是真正的 watcher(少一层 wrapper shell)。
- launchd 直接管 watcher PID → `bootout`/TERM 正确送到 watcher → sync 脚本现有 TERM/INT trap 释放锁、干净退出,无 orphan。
- 同步更新 FLY-129 那段"不 exec"注释的理由(已过时)。
- `.zshrc` 路径在 cmux shell 里本有完整 PATH,PATH 展开行幂等无副作用。`python3` 用系统 `/usr/bin/python3`(在 launchd 最小 PATH 内)。`CMUX_SOCKET_PATH` 默认 `/tmp/cmux.sock`,无需 source `.env`(若生产改过非默认 socket,再走 plist `EnvironmentVariables` 或 source `~/.flywheel/.env`)。

### 4.3 supervised blocking-acquire 锁模式(Codex R1 HIGH-1 —— 根除空转)

问题:`acquire_watcher_lock` 在锁被占时 `exit 0`。`KeepAlive=true` 下,若 `.zshrc` watcher 先抢到锁,launchd 实例会每 30s "起→锁被占→exit 0→重拉"无限空转,直到那个 watcher 死 —— 既是 FLY-129 禁止的新增周期 load,又意味着这段窗口 launchd 并未真正在守护活 watcher。

改法:给 `acquire_watcher_lock` 加 **supervised 分支**(仅当 `FLYWHEEL_CMUX_SUPERVISED=1`):
- 锁被**活**owner 占用时,**不 `exit 0`**,而是 `sleep`(复用 watch 的 15s 量级)后**重试**,在进程内**阻塞等待**直到能拿到锁(每轮重新校验 owner 是否还活着)。
- 拿到锁后照常进 `watch_main`;TERM/INT trap 现有逻辑不变。等待期间(尚未持锁)收到 launchd 的 TERM/`bootout` → 进程直接退出,**从未持锁 → 无 orphan、无残锁**。
- **unsupervised(`.zshrc`)路径保持现状**:锁被占即快速 `exit 0`,绝不与活的 launchd owner 竞争。

效果:
- 正常登录:launchd RunAtLoad 先抢锁 → 长生 watcher;`.zshrc` 后来快速 exit。**零空转**。
- 逆序(plist 在某 cmux shell 已起 watcher 后才 load):launchd 实例 blocking-wait,**不空转**;那个 `.zshrc` watcher 一死,launchd 实例立刻接管。
- → launchd 始终是稳态唯一 owner;`.zshrc` 退化为真兜底(只在 launchd 没持锁、如 plist 被 unload 时才真正起 watcher)。

### 4.4 `.zshrc` autostart 共存(保留当兜底)

`cmux-integration.zsh` 维持原样(team-lead 拍板:保留兜底,不设 SUPERVISED)。结合 §4.3:launchd 是稳态 owner,`.zshrc` 只在 launchd 未托管/未持锁时真正拉起 watcher。兜底价值:plist 被 unload(dev)或 launchd 失效时仍能起 watcher。

**已知恢复延迟(Codex R1 LOW-6,可接受)**:若 launchd 在 cmux 建 `/tmp/cmux.sock` 之前就起 watcher,watcher 持锁但 health-check backoff 最多 300s;此时 `.zshrc` 兜底也加速不了(它见锁被占即 exit)。符合 FLY-129(不加轮询)。故 AC 措辞为"watcher 处于健康 cmux tick 后 ≤60s 内恢复",而非"绝对 60s"。

### 4.5 install 脚本补 plist provisioning(幂等)

`scripts/flywheel-cmux-install.sh` 增加一步,与现有 socketControlMode / symlink / `.zshrc` 注入并列:
1. 由仓库 tokenized 模板 + `$HOME` 生成 `~/Library/LaunchAgents/com.flywheel.cmux-watcher.plist`(`sed s|__HOME__|$HOME|`)。
2. `plutil -lint` 校验。
3. **`launchctl bootout gui/$(id -u)/com.flywheel.cmux-watcher 2>/dev/null || true` 再 `launchctl bootstrap gui/$(id -u) <plist>`**(幂等重装)。
4. verify:`launchctl print gui/$(id -u)/com.flywheel.cmux-watcher` 拿到 PID,且该 PID == 锁 owner(`cat /tmp/flywheel-cmux-watcher.lock/pid`)。
5. 顺手修正 install 脚本步骤6 那条过时注释("直接 `--watch` 跳过锁"—— 现在 dispatcher 已 gate 锁)。

### 4.6 收紧 ④:`refresh_linked_sessions` select-window 按 live window_id 兜底(team-lead 拍板,在 scope)

问题(④):现状 `refresh_linked_sessions` 用 `tmux select-window -t "=${view_session}:=${wname}"` 按**名字**精确匹配。`claude-lead.sh` 重启时已 `tmux kill-window -t "=flywheel:=${window_name}"` 先杀旧窗,故同名重复**罕见**;但若 kill 失败 / `remain-on-exit on` 留下死窗,同名多窗时 `=name` 会选中**最低 index** 的那个 —— 可能是死窗 → 列显示死 pane/空白。

改法(小幅 hardening,不改检测节奏):`refresh_linked_sessions` 遍历 `get_tmux_agent_windows`(已给 `src_sess|window_id|wname`)时,对每个 window 做 **ID-scoped 判活**(Codex R3 LOW-1:**不要**调 `is_pane_alive "$wname"` —— 它是 name-based,同名另一窗 live 会让死窗误判 alive),而是 `pane_dead=$(tmux display-message -p -t "=${src_sess}:${wid}" "#{pane_dead}")`,**只对 `pane_dead==0` 的窗** `select-window -t "=${view_session}:${wid}"`(按 id;grouped session 共享窗口对象,`@N` 在 view_session 内是合法 target-window)。同名多窗时死窗被跳过,只选活的那个。
- **同名多 live 窗(罕见)的确定性(Codex R3 LOW-2)**:本 hardening 主治"死窗残留 + 新 live 窗"常见态;若同名多窗**都 live**,选 `get_tmux_agent_windows` 快照里 **window index 最高/最新**的那个(确定性 winner),不靠遍历顺序。

- 正常单窗 live Lead:行为与现状等价(选中它,改为按 id)。
- 同名 + 死窗残留:不再选中死窗(④ 修复)。
- 全死(Lead crash 中):不选(那列本就该等 claude-lead.sh 重启出新 live 窗 / reconcile 处理)。
- 纯 tmux、幂等、无 cmux IPC、无新增周期 —— 不碰 FLY-102 高频面。
- **不动** `self_heal_one_workspace`(①re-attach)与 `reconcile_existing_workspaces`(③重建)逻辑,只动 ② 的 select-window 选择子。

> **这是 ship gate,不是可选项**(Annie 拍板):A 写完**必须过这套 QA 真机验证、全部 PASS** 才能提 ship;任一 FAIL/超时 → **不准喊 ship**,回查修。
> **真机验证,不靠 mock**(FLY-169 教训:mock 编码了错误的 cmux 假设 —— cmux/tmux infra 改动只有真机能验)。代码层单测见 §6,但 §6 不替代本节。
> **碰生产**(起 watcher / 造障 ①②③):现有 live Runner GEO-380 在跑,FLY-102 记录 cmux-sync 高频操作曾静默杀 Runner。**执行前:① 把本验证方案发回 team-lead 批 + 给 Annie 过目;② 优先挑无 live Runner 的时间窗;③ 绝不自己擅自重启 watcher。**

**为什么本质安全**:watcher 活着后跑的还是现有 60s additive + event drain,**不新增任何高频操作**(FLY-102 的高频 polling 早被 PR #146 event-signaled 架构取代)。造障手段本身(detach-client / select-window / kill-session)只碰 `cmux-<lead>` grouped **view** session,不碰 `flywheel` 真窗或 `runner-*`。
> **诚实说明(qa-fly-177 中1)**:watcher 启动/重启跑的 `sync_additive_bootstrap` **不是字面"只扫描"** —— 它依次跑 `reconcile_existing_workspaces` + `refresh_linked_sessions` + create + `self_heal_sweep_all`,这些**都遍历 Runner 窗口**。但对**健康** Runner 是 **additive-only / no-op**:`reconcile` 只在 linked-session **已死**时才 `close`(QA 已核实 sync **从不杀源 Runner 窗口**,只 close cmux view workspace);refresh/self-heal 只 select-window / re-attach,不动源窗。所以"不杀 Runner"成立,但**别把 Check G 当零足迹** —— 这正是为什么每个 check 都要前后核对 `runner-geoforge3d` 快照。

**Runner 隔离 guardrail(每个 check 都套)**:全程前后各拍一次 `tmux list-windows -t runner-geoforge3d -F '#{window_name} #{pane_dead}'` 快照,要求 Runner 窗口名/数量/pane-dead/session 全不变;watcher 重启**只做一次 graceful TERM**(不反复重启)。

**自愈触发节奏(决定每个 check 怎么造障 + 等多久)**:
- **②/③** 由 `sync_additive`(每 60s)的 `refresh_linked_sessions`/`reconcile_existing_workspaces` 兜底 → 造障后等 ≤60s(③ 硬超时 ≤120s,见 §11.1)。
- **①** re-attach 是 **event-driven,不在 60s additive**(FLY-169:create/register drain、bootstrap、cmux-recovery 才触发)→ 故 ① 落在 **watcher 重启的 bootstrap sweep**(`sync_additive_bootstrap → self_heal_sweep_all`)这个 event 边界,与守护 check 合并成一次重启,最小化生产触碰。

### QA 验收清单(全部 PASS 才放行 ship)

**前置 P0 — 部署就绪**:`flywheel-cmux-install.sh` 后,`launchctl print gui/$(id -u)/com.flywheel.cmux-watcher` 有运行 PID;`pgrep -fl 'flywheel-cmux-sync.*--watch'` 命中且 PID == 锁 owner(`cat /tmp/flywheel-cmux-watcher.lock/pid`)。**PASS 判定**:launchd 有 PID + 进程命令是 `flywheel-cmux-sync --watch` + PID==锁 owner + `/tmp/flywheel-cmux-watcher.log` 有**本次启动**的 `Watch mode: event-signaled polling` 行(Codex R4 MED:watcher 刻意不 per-tick 打日志,**不要**用"持续有 tick"判定,否则假失败 / 诱导加噪声日志违反零新增 load)。

**Check G — launchd 守护(A 的主交付,必测)** + **Check ①(0-client)合并**(一次 watcher 重启同时验两者):
- **baseline(Codex R4 LOW-3)**:造障前 `tmux list-clients -t "=cmux-geoforge3d-product-lead"` 应 ≥1 行才能证明 detach 真造了障;若起初就是 0(已是现存故障),记录为"从 broken state 起验 bootstrap 修复",不把 detach 当本次成功造障。
- **造障**:(a) 在 product 上 `tmux detach-client -s "=cmux-geoforge3d-product-lead"`,确认 `tmux list-clients -t "=cmux-geoforge3d-product-lead"` 输出 0 行(view 掉到裸 shell;product 的真 claude 在 `flywheel` 不受影响);(b) **记录旧 launchd PID** `OLD=$(launchctl print gui/$(id -u)/com.flywheel.cmux-watcher | awk '/pid =/{print $3; exit}')`(`exit` 防多匹配;qa nit2),**先确认 `$OLD` 非空**再 `kill -TERM "$OLD"`(launchctl 在重启瞬间可能暂无 `pid =` 行 → 空则等 1-2s 重取,绝不 `kill` 空 PID)。
- **预期恢复**:launchd 自动拉起新 watcher;其 bootstrap sweep re-attach product 列。
- **PASS 判定**:~30s(硬超时 60s,bash3.2 sleep+ThrottleInterval 容差)内 ——
  - (G) **PID 取法用 `launchctl print …`(qa-fly-177 中2),不用 pgrep/锁 owner**:`launchctl print gui/$(id -u)/com.flywheel.cmux-watcher` 报的就是 launchd **托管的** PID;恢复后它报一个 **≠ `$OLD`** 的新 PID = PASS。**为什么不用 pgrep**:`.zshrc` 兜底也能拉 watcher(`&!` disown 后 PPID=1,无法靠父子关系区分是 launchd 还是 .zshrc 拉的),pgrep/锁 owner 会**假归因**;launchctl 报的 PID 必然是它自己托管的那个。
  - (①) `tmux list-clients -t "=cmux-geoforge3d-product-lead"` 恢复 ≥1 + 该列显示 product Lead(非裸 shell)。**归因校验(qa-fly-177 低3)**:恢复时刻要与 watcher log(`/tmp/flywheel-cmux-watcher.log`)里这次重启后的 `Self-heal: re-attaching 'geoforge3d-product-lead'` 行**时间戳吻合**,才算 watcher 自愈;否则可能是 cmux 自己重连(detach 后 cmux 可能自动 re-attach)→ 假归因,需重验。
  - **全程不开任何新 shell**(证明不依赖 `.zshrc`)。

**Check ② — window drift(product/ops/cos 三个都验)**:对每个 `geoforge3d-{product,ops,cos}-lead`:
- **造障**:`tmux list-windows -t "=cmux-<lead>" -F '#{window_active}|#{window_id}|#{window_name}'` 记录原 current-window;`tmux select-window` 漂到**任一已存在的非目标窗**即可(qa-fly-177 低4:grouped view 的 `select-window` 只动**这个 view session 自己**的 current-window 指针,不影响其他 session,所以漂到 window 0 zsh **或另一个 Lead 窗**都能验 —— 不必强求"shell 非目标窗")。**仍守红线:绝不现场 `new-window` 造夹具**(grouped session 新窗会污染 `flywheel` 共享窗口集);若该 view **只有目标窗一个**(无任何其它窗可漂)→ 记 blocked 回报。
- **预期恢复**:`refresh_linked_sessions` 下一个 additive tick 把 current-window 选回 `<lead>` 窗。
- **PASS 判定**:≤60s 内 `tmux display-message -p -t "=cmux-<lead>" '#{window_name}'` == `<lead>` 窗名(**精确断言,不只肉眼**)。**超时兜底**:未回 → 手动 `select-window` 还原 + 记 FAIL → 不 ship。

**Check ③ — linked-session 死了重建(代表性 product)**:

- **预期恢复**:`reconcile_existing_workspaces` 关掉 stale workspace → create 阶段重建 linked session + workspace 重新 attach。

## 11. 实施注意(Codex R2 LOW —— coding 时落实,plan 已 APPROVED)

1. **supervised acquire = 真正的 supervisor-only 等待循环**:`FLYWHEEL_CMUX_SUPERVISED=1` 且锁被**活**owner 占用时走 sleep/recheck 等待,**不**落入现有 bounded-3-attempt 退出路径;stale-lock/reap-race 仍走原 bounded 逻辑。顺手校验 owner PID 看起来确实是 `flywheel-cmux-sync --watch`(防 PID 复用导致永久等待)。
2. **install verify 容忍逆序态**:`.zshrc` watcher 已持锁、launchd blocking-wait 时,`launchctl print` 的 PID ≠ 锁 owner —— verify **不应**在此态硬失败。要么强制部署前清残留 watcher(§7 步骤2)再严格判 PID==owner,要么 verify 接受两种合法态(launchd PID==锁 owner,或 launchd 在 supervised wait 且锁 owner 是活的 watcher)。
3. **AC3 重启观测窗用 60s**:macOS bash 3.2 下 TERM trap 在 `sleep` 中可能延迟(健康 tick 通常 ≤15s)+ launchd ThrottleInterval=30 —— 观测窗给 60s(先确认 cmux 健康),记录预期 ThrottleInterval=30 行为。
4. **drift 验证用精确 tmux 断言**(不只肉眼):每个 `cmux-<lead>` 先 `tmux list-windows -t "=cmux-<lead>" -F '#{window_active}|#{window_name}'`,无 shell 窗时 drift 到任一非目标窗,**断言 current-window name 回到 Lead 窗**后再用 Chrome 观察兜底。
5. **`env -i` PATH 测试要带 `HOME`**:wrapper 用 `SYNC_SCRIPT="$HOME/.flywheel/bin/flywheel-cmux-sync"`,故测试用 `env -i HOME="$HOME" PATH=/usr/bin:/bin:/usr/sbin:/sbin /bin/bash <repo>/scripts/flywheel-cmux-autostart.sh`(LaunchAgent 正常有 HOME)。
