## 1. Problem (audited, not assumed)

Three gaps in the runner-lifecycle / terminal-state subsystem — all "stuck at
`awaiting_review` / no clean terminal route" — fixed in one combined PR.

### FLY-228 — abandoned runner stuck at `awaiting_review`

When the founder cancels a runner parked at an `approve_to_ship` gate, the Lead
has **no sanctioned terminal route**:

- `flywheel-comm complete --route` accepts only `{auto_approve, needs_review,
  blocked}`. The runner used `--route blocked` as a proxy, but
  `awaiting_review → blocked` is **not a legal FSM edge**
  (`WORKFLOW_TRANSITIONS.awaiting_review = [approved_to_ship, completed,
  rejected, deferred, shelved, terminated]`), so `applyTransition` silently
  rejected it and status stayed `awaiting_review`.
- `close_runner` (MCP) refuses `awaiting_review` (`status_not_eligible`).
- Lead fell back to raw `tmux kill-window` + `git worktree remove` → leaves a
  zombie `awaiting_review` row (counts against per-issue admission) AND bypasses
  the Bridge audit + founder-consent trail.

**Key finding**: the Bridge already has the full capability. The `terminate`
action (`handleTerminate` in `actions.ts`, `POST /api/actions/terminate`)
accepts `awaiting_review`/`approved_to_ship` and does the complete teardown
(kill tmux + close macOS Terminal viewer + FSM→`terminated` + audit hook), and
is already founder-consent + lead-scope gated. The gap is purely the **Lead
client surfaces** (`close_runner` MCP tool + `complete` CLI).

### FLY-229 — `runner_terminal_list` hides parked-but-alive runners

- `runner_terminal_list` defaults `active_only=true` → CommDB
  `getActiveSessions()` = `status='running'` ONLY. A runner parked after
  `complete` (CommDB `status='completed'`) but still **tmux-alive + agent idle
  at prompt** (re-engageable via `flywheel-comm send`) is filtered out → Lead
  misjudges the runner has exited and reaches for terminate + new-run.
- The count cap (`maxConcurrentRunners`) was **retired in FLY-123**; admission is
  now pure load/memory pressure. The "Max concurrent reached" the Lead saw was
  either stale prod code or the per-issue 409 (`runs-route.ts`: an issue that
  already has a `running`/`awaiting_review` session). The remaining real
  "double-count" is that the per-issue 409 (correctly) treats a parked session
  as occupying the issue while the list (incorrectly) hides it.

> Terminal MCP can only read the per-machine **CommDB** (`status ∈
> {running, completed, timeout}`) + a live tmux probe. It CANNOT see the Bridge
> WorkflowFSM state (`awaiting_review`, etc.). So this fix classifies by
> **(CommDB status, tmux liveness)** only — it never claims FSM `awaiting_review`.

### FLY-222 #1 — no-code Runner completion has no terminal route

FLY-222 adds Flywheel's first **no-code Runner flow** (scheduled "learning"
Runner: read Xiaohongshu collections → analyze → prune gate → create issue drafts
+ write memory → done). It never writes code, opens a PR, or merges. Today
`complete --route auto_approve` WITHOUT `--merged` maps to `awaiting_review`
(`event-route.ts:657-666`, sister `DirectEventSink.ts:263-272`) — NOT terminal.
So the no-code Runner finishes stuck in `awaiting_review`, and because FLY-222
uses one fixed reusable trigger issue per collection, the next cadence spawn is
blocked by the `runs-route.ts:169-185` 409 (same issue+role with status ∈
{running, awaiting_review}). There is no route that maps a no-code/no-merge
success to terminal `completed`. (Same `awaiting_review`-stuck family as FLY-228,
different actor: runner-driven self-completion vs Lead-driven cancel.)

### 1.5 — Unified terminal-state model

| Entry point | Actor | Route / action | Terminal status | Finalize? | Notes |
|---|---|---|---|---|---|
| code, merged | runner | `auto_approve`/`needs_review` + `--merged` | `completed` | yes | unchanged |
| code, needs review | runner | `needs_review` (no merge) | `awaiting_review` (non-terminal) | — | unchanged |
| ship failed/blocked | runner | `blocked` | `blocked` | no | unchanged |
| **no-code success (FLY-222 #1)** | **runner** | **`no_code` (NEW)** | **`completed`** | **no** | no merge, no review, no evidence-gap |
| cancel / abandon (FLY-228) | Lead | `terminate` (via `close_runner --abandon`) | `terminated` | no | founder-consent gated |

Insight: FLY-222 #1 is a **runner-driven** terminal (self-assessed "nothing to
ship → done"); FLY-228 is a **Lead-driven** terminal (external cancel). Same
stuck-`awaiting_review` family, distinct terminal states, one coherent model.

## 2. Approach

### FLY-228 — `close_runner --abandon` → routes to existing `terminate`

Chosen over the other two suggested fixes (terminal route in `complete` is
runner-driven + needs the idle runner to cooperate + more surface; plain-text
gate→terminal conflicts with the established "plain-text = changes-requested"
semantics from FLY-208). `close_runner --abandon` is Lead-driven, reuses the
fully-tested `handleTerminate` teardown, restores the founder-consent + audit
envelope that raw `tmux kill` bypassed, and FSM→`terminated` eliminates the
zombie row.

**Implementation:**

1. `packages/terminal-mcp/src/index.ts` — `close_runner` tool:
   - New optional param `abandon: boolean` (default `false`).
   - `reason` (already required): when `abandon`, validate **trimmed non-empty**,
     max 500 chars (it is written to the terminate audit).
   - When `abandon === true`:
     - Resolve `execution_id`. If only `issue_identifier` given, look it up with a
       **dedicated abandon status set = exactly `awaiting_review,approved_to_ship`**
       (NOT a union with the close-eligible set — Codex R1 MED-1: a union would hit
       the `>1` guard whenever an old `completed` execution coexists with the
       current parked one, i.e. the exact iteration scenario; and could resolve a
       lone `completed` that terminate rejects).
     - **Lead-scope the lookup** (Codex R2 MED-3): pass `leadId` to the
       `mode=by_identifier` endpoint; the endpoint applies
       `filterSessionsByLead(...)` (same `matchesLead` policy as the terminate
       route) BEFORE the `0`/`>1` guards, so an out-of-scope same-identifier
       parked execution can't make an unambiguous in-scope abandon fail with
       `>1` or select an out-of-scope row that fails later. Keep the existing `0`
       ("no parked session to abandon") and `>1` (disambiguation) guards on the
       scoped set. (`by_identifier` gains an OPTIONAL `leadId`; omitted = today's
       behavior, so the existing close_runner lookup is unchanged.)
     - POST to `/api/actions/terminate` with `{ execution_id, leadId, reason }`.
       `leadId` is **always sent** (terminal-mcp requires `FLYWHEEL_LEAD_ID`) so
       the terminate endpoint's lead-scope check is exercised as defense-in-depth
       (Codex R1 LOW-6).
   - For an explicit `execution_id` whose FSM state is not terminable, terminate
     returns a 400 the tool surfaces verbatim (clear error, no silent wrong act).
   - Tool description: abandon cancels a parked (`awaiting_review`/
     `approved_to_ship`) runner; terminate-class reserved action (founder-consent
     gated). Non-abandon path byte-unchanged.

2. `packages/teamlead/src/bridge/actions.ts` — `handleTerminate`:
   - **Optional `reason?: string`**: thread into the transition `last_error` +
     hook `action_reason`. Absent/blank → existing `"Terminated by CEO"`
     (dashboard path unchanged). Trim + cap 500.
   - **Reorder to transition-first** (Codex R1 MED-5 — race): validate
     `fromStates` → `applyTransition`→`terminated` (or `forceStatus`). If the
     transition is rejected (concurrent state change), return failure with the
     FSM **unchanged** and tmux **untouched** — no kill-before-confirm window.
   - **Observable partial-failure cleanup** (Codex R2 MED-1 — do NOT swallow):
     after a successful transition, best-effort gate resolution, then attempt
     tmux kill + Terminal-viewer close.
     - tmux kill **succeeds / already-gone** (`killTmuxWindow` returns
       `{killed:true}`) → `{ success:true, message:"… terminated successfully" }`.
     - tmux kill **fails** (`{killed:false, error}` — real permission/timeout) →
       `{ success:false, cleanupPending:true, message:"… transitioned to
       terminated, but tmux cleanup failed: <err>. FSM row is terminal (no longer
       blocks admission); re-run close_runner to reap the tmux window." }` + a
       `lead_terminate_cleanup_failed` audit event. **Never returns unqualified
       success while the process may be alive.** (`ActionResult` gains optional
       `cleanupPending?: boolean`.) The dashboard re-enables the button on
       `success:false` (its existing behavior) — honest, and the FSM is already
       terminal so the zombie is gone regardless. `close_runner` (terminated ∈
       `AUTO_CLOSE_STATES`) is the sanctioned cleanup retry.
   - **Best-effort gate resolution with ownership validation** (Codex R1 MED-4 +
     R2 LOW-2): ONLY when `priorStatus==="awaiting_review"` OR
     `session.review_question_id` is set (so running/blocked/failed callers skip
     it entirely — no CommDB open). Validate ownership exactly like the approve
     path before acting: resolve the bound `review_question_id` only if
     `getMessageById` is a `question` with `checkpoint==="approve_to_ship"` and
     `from_agent===executionId` (skip `REVIEW_BINDING_UNBOUND`); else the null-
     binding fallback `getPendingGateByRunner(executionId,"approve_to_ship")`.
     Then `CommDB.resolveGate(qid, 0)` (expire now — **no approval-shaped
     response, no wake**). All wrapped best-effort (errors logged, swallowed) so
     an abandoned review gate stops showing pending without risking the transition.
   - The `terminate` route reads `reason` from `req.body` and threads it through.
   - Consent/scope unchanged — terminate already enforces both (`fcMw` +
     `checkLeadScope`). Reuse the shared `commDbPathFor` helper (extract to module
     scope if currently nested) rather than duplicating the path logic.
   - **Decision (push-back on R2 nit "reuse closeRunner"):** keep
     `handleTerminate`'s own kill + viewer-close calls (reordered) rather than
     rerouting cleanup through `closeRunner`. `closeRunner` emits its own
     `lead_close_runner` audit events; routing every terminate through it would
     change the audit-event stream (which founder-consent calibration reads). The
     kill/viewer logic is small; not adding new duplication.

### FLY-229 — parked-alive visibility + accounting hint + guidance

**A. `runner_terminal_list` classifies by (CommDB status, liveness)**
(`terminal-mcp/index.ts` + extracted pure `classifyRunnerRow`/`formatRunnerRow`
helpers for unit-testing):
- Per row emit `status=<commStatus> alive=<true|false> class=<...>`:
  - `running` — CommDB `status='running'` (always shown in active view; alive
    annotated — NOT hidden if tmux died, preserving today's behavior). Running
    rows come from a SEPARATE query and are NEVER consumed by the terminal probe
    cap (pinned by test — Codex R2 nit).
  - `parked-alive` — CommDB `status ∈ {completed,timeout}` AND tmux alive
    (idle, re-engageable).
  - `dead` — CommDB `status ∈ {completed,timeout}` AND tmux not alive.
  - No per-row `unknown` class — `tmuxAlive` already returns `false` on probe
    error, and beyond-cap rows are NOT fetched (Codex R2 LOW-1: a count-only
    summary, not synthetic `unknown` rows).
- Candidate gathering (**Lead-scope inside SQL, before LIMIT/COUNT** — Codex R2
  MED-2):
  - running rows: `getActiveSessions(projectName)` + in-memory scope filter
    (`lead_id IS NULL OR = leadId`), as today (no LIMIT → in-memory is fine).
  - terminal rows: `getRecentTerminalSessions(projectName, leadId, limit=150)` —
    SQL applies `AND (lead_id = ? OR lead_id IS NULL)` and orders by
    `COALESCE(ended_at, started_at) DESC` (right clock — `ended_at` is stamped by
    `updateSessionStatus`; parked-alive are inherently recent so a recency cap
    yields no realistic false-negative) BEFORE `LIMIT`. Scope is applied in SQL so
    an in-scope parked row can't be pushed out by another Lead's newer rows.
  - Probe `tmuxAlive` with **bounded concurrency** (small worker pool, e.g. 8 —
    Codex R2 LOW-1), not 150 subprocesses in one `Promise.all`.
- Truncation: `countTerminalSessions(projectName, leadId)` (same scope predicate).
  If `count > limit`, append ONE summary line:
  `(N older in-scope terminal sessions were not examined; liveness unknown)`.
- `active_only=true` (default): output `running` + `parked-alive` (+ truncation
  summary if any). `active_only=false`: output `running`/`parked-alive`/`dead`
  (+ summary). Same cap both views (probing all history is too slow); the summary
  makes truncation visible.
- `parked-alive` rows append: `→ re-engageable via 'flywheel-comm send' /
  SendMessage (no new run needed)`.
- Param description updated to state the new default semantics; tests pin them.

**B. New-run 409 hint** (`teamlead/src/bridge/runs-route.ts`):
- Extend the `alreadyActive` 409 message with **conditional** language (Codex R2
  nit — Bridge FSM status alone doesn't prove tmux liveness): "...If that session
  is parked and still alive (idle), re-engage via `flywheel-comm send` /
  SendMessage instead of starting a new run; check `runner_terminal_list`."
  Message-only; zero behavior change.

**C. Lead guidance doc** — new
`packages/teamlead/lead-rules-base/runner-reengage-rules.md`:
- Iteration-loop standard op: a runner that `runner_terminal_list` shows as
  `parked-alive` (finished in CommDB but tmux/agent still alive) is re-engageable
  via the normal Runner messaging path; don't terminate + new-run. Worded around
  what the tool actually shows (not FSM state). Loaded for non-cos dept leads
  only, mounted like `stuck-runner-remanage.md` in `claude-lead.sh` (optional
  file = no-op back-compat).

### New CommDB helpers (`packages/flywheel-comm/src/db.ts`)

Both apply the Lead-visibility predicate `(lead_id = ? OR lead_id IS NULL)` in SQL
(Codex R2 MED-2 — scope before LIMIT/COUNT):

- `getRecentTerminalSessions(projectName, leadId, limit)`:
  `SELECT * FROM sessions WHERE project_name = ? AND status IN ('completed','timeout')
  AND (lead_id = ? OR lead_id IS NULL) ORDER BY COALESCE(ended_at, started_at) DESC
  LIMIT ?`.
- `countTerminalSessions(projectName, leadId)`: same `WHERE` (no LIMIT) → COUNT,
  for the truncation summary.

`leadId` is optional in both (omitted → no scope predicate) so non-scoped callers
are unaffected.

### FLY-222 #1 — `no_code` terminal completion route

A FOURTH `complete` route for runner-driven no-code/no-merge clean success →
terminal `completed`. Worker-fly-222 consumes it (`complete --route no_code
--summary "..."`, no `--pr`/`--merged`, no extra flag); it does NOT touch
`event-route.ts`.

1. `packages/flywheel-comm/src/commands/complete.ts`:
   - Add `no_code` to `VALID_ROUTES`.
   - Guard: `--route no_code` with `--merged` → error (contradictory: no_code
     means no merge). `--pr` ignored/forbidden likewise.
2. `packages/teamlead/src/bridge/event-route.ts`:
   - Add `no_code` to the strict-route guard `VALID_ROUTES` (so it isn't rejected
     as an invalid route).
   - New branch: `else if (route === "no_code") { status = "completed"; }` —
     `evidenceGap` stays `false`. (Place BEFORE the `else` undefined-route branch.)
3. `packages/teamlead/src/DirectEventSink.ts`:
   - Mirror the same `no_code → completed` branch (both sinks MUST agree — the
     file's own invariant). `decision_route="no_code"` is already persisted by
     both sinks → dashboard/audit distinguishes no-code completion (FLY-222 req
     #4, no new column).
4. Finalization: **no change needed** — `isPostApproveShipComplete` already
   returns `false` unless `landingStatus.status === "merged"`
   (`post-ship-finalization.ts:75`); `no_code` carries no merge, so
   `runPostShipFinalization` can never fire for it (FLY-222 req #2). And `no_code`
   is not `auto_approve`/`needs_review`, so the evidence-gap path is never taken.
5. FSM: `running → completed` is already a legal edge (`WORKFLOW_TRANSITIONS`);
   no FSM map change.
6. Coexistence: `auto_approve`/`needs_review`(±merged) and `blocked` branches
   are untouched (FLY-222 req #3).

> Interface for worker-fly-222 (sent for sign-off): route name = `no_code`; call
> `flywheel-comm complete --route no_code --summary "..."` with NO `--pr`/`--merged`
> and NO extra flag; lands terminal `completed`; never finalizes; never
> evidence-gap; `decision_route` distinguishes it.
