## 1. Feasibility —— 基于 MCP 真机探测 + 视频实测（事实,非假设）

> **⚠️ §1 整节被 Phase 0 真探校正(见 §7.0):MCP server 已是 v2.0.0,旧 REST `/api/v1/*` 已不通,唯一可靠路径 = curl `/mcp` JSON-RPC 握手(feeds/detail/收藏夹全部经 MCP)。下文字段结构结论仍成立;凡提"REST 路由"以 §7.0 为准。**
>
> 探测法(历史,v2.0.0 前):MCP **客户端调用超时**(~60s < 抓取);用 **curl 直打 `/mcp` 做 JSON-RPC 握手(initialize→initialized→tools/call)绕过客户端超时**取到真实返回。`list_collections`/`get_collection_content` 仅 MCP 协议。

### 1.1 内容来源 = MCP 登录态,不是 summarize 抓 URL

小红书有登录墙,抓裸 URL 撞登录页 → `summarize <url>` 行不通。**内容全部从本地 MCP server 拿**(持登录 cookie)。Claude 直接分析返回文字。

### 1.2 `get_feed_detail`(MCP 协议,真调；v2.0.0 校正见 §7.0)

`{note:{noteId,xsecToken,title,desc,type,time,ipLocation,user,interactInfo,imageList[]}, comments:{list,cursor,hasMore}}`。`desc`=正文/caption(含 hashtag,信息量大);`imageList`=图片直链(rednotecdn,可直接下载);detail **本身无视频字段**(视频见 §1.3 另走 yt-dlp)。

### 1.3 视频 = 可拿本体(实测端到端通,核心能力非兜底)

**Annie 坚持对了。** 路径:**`yt-dlp`(2025.10.22 自带 `XiaoHongShu` extractor)+ 登录 cookie → 真实 mp4 直链 → Gemini 分析。**
- 实测:一条 Suno 教程 video 笔记 → `yt-dlp "https://www.xiaohongshu.com/explore/<id>?xsec_token=<tok>" --cookies <netscape>` → 提取 `sns-video-ak.xhscdn.com/stream/...mp4`(226s,16MB)→ 下载 → `summarize --video-mode understand <file>` → **完整逐字稿**(Suno 改编工作流全过程)。
- cookie 源 = MCP 的 `~/.config/xiaohongshu-mcp/cookies.json`(转 Netscape)。本账号是 **Rednote**(rednote.com),但 yt-dlp 用 `xiaohongshu.com/explore` URL 形式提取成功。
- 备用路:curl 笔记页(带 cookie)→ `__INITIAL_STATE__` 的 `masterUrl`(已确认存在)。
- **凭据/临时文件安全(R2 #5,硬要求)**:skill 创建/派生**任何** cookie 文件必须 `0600` + 全程 `umask 077` + per-run temp dir + 用完 `trap`/stale 清理 + URL/token/cookie **不入日志** + 单文件/单轮下载上限(持续约束)。**MCP 原 cookie `~/.config/xiaohongshu-mcp/cookies.json` 原为 `0644`(全员可读,Annie 真实登录凭据暴露)→ 已修(生产 cookie 已 `chmod 600`,team-lead 2026-06-05,stat 确认 600)。**
- **授权 = `video_opt_in`(default false)唯一开关**(不再"隐含同意"):`false` → **不调 yt-dlp/Gemini**,该笔记退化为 caption+comments(明确退化,不留 pending);`true` → 走视频本体。SKILL.md 透明声明"视频送 Google/Gemini 分析"。

### 1.4 分页 = **无 cursor 暴露**(live 真调,推翻结构推断)

`get_collection_content` 真返 **`{notes:[...], count:N}` —— 不暴露 `hasMore`/`nextCursor`**(binary 内部 struct 有,MCP 工具不透传)。`limit ≤ 200`。
- **够用**:Annie 真实收藏夹 "AI-视频"=13、"妆"=124 → 一次拉全。
- **>200 = 硬上限**:靠 `list_collections` 返回的 `total` 检测;超限 v1 取最新 200 + 显式告警"收藏夹超 200,本工具无法翻页",不静默漏。
- → 增量 = **拉全量(≤200)对已处理 noteId 全窗口差集**,**不需要也拿不到 cursor**(单窗 + gap 策略,Codex R2 #5 的"cursor 不可用"分支已被 live 证实为现实)。

### 1.5 收藏夹访问 = MCP-only;可靠性

**全部经 MCP**(v2.0.0 无 REST,见 §7.0):skill 直打 `/mcp` JSON-RPC 握手取 feeds/detail/收藏夹;视频走 yt-dlp。**MCP 抓取慢(rod 真 Chromium,7 条 60s,并发串行排队)→ 长超时(≥120s)+ 单条串行 + 重试 + fail-soft + 半夜排程(§7.1 实证)。**

## 2. 架构决策（Codex R1 + R2 已回应；HIGH 项落到 Phase 0 决策记录 + 重审）

### 2.2 执行剖面（R1-F3;Phase 0 spike）

普通 Runner 注入 brainstorm/doc-flow/ship gate 且无 no-code 收尾。**Phase 0 验最小"scheduled-learning 剖面":只留 prune gate、关常规 gate、给合法 no-code 终态 + report-back。** 若需 per-run execution profile = 共享编排新能力 → 写回 plan 单独评审。

### 2.3 prune = 阻塞 gate + **FINAL-routing 协议**(R1-F1 + **R2 #1**)

`flywheel-comm ask` 非阻塞 → 用阻塞 `gate`。**但 R2 #1 实证(代码层):`gate` 读到该 question 第一条 response 即 resolve(`gate.ts:145-185`);`respond` 把任意文本直接写 CommDB,只特判 `approve_to_ship`(`respond.ts:104-105`);且 Lead rules 现在指导 Lead 对普通 gate 用 `flywheel-comm respond`。** → **"只有 FINAL 才释放 / malformed 不写入"是代码当前给不了的硬保证,不能在 plan 里假称已有。**
**修 —— 把保证拆两层(产品要害 = "Annie 没 FINAL 时绝不建 issue/写 memory",这条不能依赖 gate 释放语义)**:

- **① 所有路径硬不变量(无论 Path A/B,Runner 端强制)**:Runner 拿到 gate 返回值后**必须严格校验 FINAL schema + 绑定的 run key**;非法 / 非 FINAL / malformed → **fail-close:零 Linear/memory 副作用、state 保持可恢复(不前移)、告警**。**即使 Path A 的 gate 被误释放(Annie 只是追问),Runner 本地校验仍保证零副作用** —— 这是产品安全的真正闸,不靠 gate 脾气。
- **② gate 释放行为 = Phase 0 #4 二选一(诚实,别声称代码给不了的保证)**:
  - **路 A(协议级尽力,v1 默认)**:靠 Lead rules 纪律("`xiaohongshu_prune` 的普通 thread 消息不调 `respond`;只把绑定 run key 的结构化 FINAL `{"final":true,"keep":[...],"edits":{...}}` 当定稿 respond")。**承认 best-effort,gate 仍可能被误释放** —— 但①兜住副作用。
  - **路 B(写入边界硬挡,shared 改动→post-Phase-0 Round-N)**:为 `xiaohongshu_prune` 加 response-write 窄校验:拒绝 generic/malformed、校验 run key + FINAL schema,合法才写 CommDB/释放。**进 Phase 0 决策记录 + post-Phase-0 Round-N 重审后才落。**
- **可选聊 = Lead-mediated**(Annie 与 Lead 在 thread 聊,Lead 攒成一条 FINAL 再 respond);Runner 阻塞等 FINAL,不参与多轮。
- A4 分层验:**①(所有路径)注入 malformed/普通追问误响应 → Runner fail-close、零副作用**(硬);②路 A 验 nominal FINAL 释放 + 纪律提示;路 B 另验 malformed/generic 被拒、非 FINAL 不写 response。

### 2.5 issue 创建 = 分调用面（R1-F6 + **R2 #2**）

**(§7.5 校正:Runner 用官方 Linear MCP `create_issue`,非 `save_issue`;详见 §7.2 #5)** Bridge create-issue 不在仓内 CLI。**R2 #2 关键:scheduler 与 Runner 是不同调用面**:

### 2.6 增量游标 = 全窗口差集 + lease/CAS 状态机（R1-F4/F5 + **R2 #3/#4**)

- **差集(F4)**:拉满窗(≤200)对 processed noteId 集合差集;max_fetch 只限本轮处理数,余 unseen 留 pending;首启 bootstrap;零交集→显式 gap 报告 + **accept-gap/rebootstrap 恢复动作**(绑 run key,R2 #8)不静默推进。
- **crash-safe 幂等(R2 #3)**:逐项 side-effect 记录不够(外部已提交但 state 落盘前 crash 会重建)。**稳定逐输出 operation id = `collection + noteId + outputKind + candidateId/version`**(不是 `run key+noteId` —— 一条 note 可产多个 issue/知识点会撞键;stale 接管复用**同一 logical run identity**,不换键)。每个外部操作**先持久化 operation id 再调外部 + 调前查重**:
  - **Linear(必须 crash-safe,不可重复)**:issue 描述/metadata 写不可变 marker(operation id)→ **建前查该 marker 确认未建**(无需改 Bridge API)。
  - **memory(二选一,Phase 0 #6 定)**:① 扩 source-key 精确去重/幂等写合同(`/api/memory/search` 是语义查询、`/api/memory/add` 无 idempotency key → **算 shared 改动,post-Phase-0 Round-N**);或 ② **明确接受 at-least-once**(学习知识重复低害)→ **同步把 A8 的 memory 项从"不重建"改为"允许重复,issue 不重复"** + 产品承诺如实。
- **lease/CAS(R2 #4)**:原子 rename ≠ 互斥。scheduler(判 due/取 lease)与 Runner(更新 pending/FINAL/副作用)是两个 writer。**单一薄 state helper(归属 flywheel,TS;skill 经其 CLI 调用 —— 不是 skill 与 scheduler 各写 JSON)**,所有 transition 在 collection-scoped mutex 下(复用 skills-sync.sh 的 mkdir-lock precedent)+ 校验 lease owner/run key 再写。明确 lease acquire/handoff/renew/release/stale-takeover、`next_due_at` 在 attempt/timeout/success 的转换、48h gate 与 TTL/heartbeat 关系。
- state 文件 `~/.flywheel/state/xiaohongshu/<project>__<collection_id>.json`。helper 的位置/CLI/schema/lock 语义是 Phase 0 决策记录项。

### 2.7 鉴权矩阵（**R2 #2** — Phase 0 硬交付物）

Runner 当前注入 `FLYWHEEL_INGEST_TOKEN`,**不是** Bridge `/api/*`(memory/linear/runs)用的 `config.apiToken`(`TEAMLEAD_API_TOKEN`)。不能假设 scheduled Runner 天然有这些 HTTP 权限,**也不无评审地给 Runner 全量 API token**。Phase 0 出 **caller/auth matrix** 逐项定 endpoint/token 源/权限范围:① scheduler 建 trigger issue ② scheduler 调 `/runs/start` ③ Runner 建 output issue(优先 Linear MCP,绕开 Bridge token)④ Runner memory 读写(可审计窄路径)。若必须新增 runner-scoped capability/token = 共享架构变更 → 写回 plan 单独评审。

### 2.8 prune 保证 = 协议级,如实声明（R1-F9）

Linear create / memory write 非 founder-only reserved action(无权限冲突),但 prune gate 不受 `FounderConsentEvaluator` 硬约束 → "未 prune 不建 issue"**靠 §2.3 协议保证**(持久化校验绑 run key 的 FINAL 后才建)。v1 不扩 reserved 集合。

## 8. 实现期决策记录（build-time，需 Codex design 复核）

### 8.1 Lease 模型 = option A（Runner 自持 lease + scheduler 纵深防御）

**⚠️ 偏离原 codex-approved plan 的 lease 模型，待 Codex design 复核（team-lead 已批准按 A 推进，不阻塞）。**

- **原 plan(§2.6)字面**:「scheduler(判 due/取 lease)与 Runner(更新…)是两个 writer」—— 即 scheduler 侧取 lease。
- **实现现实推翻它**:trigger issue 是**固定复用**的(§7.2 #2),每轮 `RUN_KEY = Runner 的 exec-id`(用于 lease owner + FINAL 绑定 + operation-id 的 run identity);**scheduler 在 spawn 前根本不知道 exec-id**。要让 scheduler 取 lease,得改 `/api/runs/start` 传一个自定义 run-key 注入 Runner —— 一个 **shared 改动**(更大爆炸半径),还要把 run-key 从固定 trigger issue body 之外的渠道传(issue body 复用 → 每轮同值,破坏 per-run 唯一性)。
- **选定 = option A**:**Runner 自己持 lease**(`xhs-state acquire-lease --owner $RUN_KEY`,acquire/renew/release,SKILL.md step 1/10 已如此)。scheduler **不取 lease**,靠**纵深防御**保证「无重复并发 run」:
  1. **FLY-176 防重入 lockdir**(shell wrapper)→ 同机不重叠 tick;
  2. **`/api/runs/start` 的 409**(同 issueId+role 且 status∈{running,awaiting_review})→ 在飞防重复 spawn;
  3. **Runner 自己的 collection-scoped lease** → 防两个 Runner 同时处理同一收藏夹;
  4. **Runner 完成时 set-next-due** → 下轮按 cadence 不再 due;Runner **死在 set-next-due 前** → collection 仍 due → 下轮 re-spawn = **想要的 fail-soft 重试**。
- **代价/理由**:偏离 plan 字面,但**省一个 shared `/api/runs/start` 改动**、爆炸半径更小、等价安全。若 Codex design 强烈反对再改 B(scheduler 取 lease + runs/start 传 run-key)。

### 8.2 Trigger issue 粒度 = per-collection;并发与串行语义

- **粒度 = 每收藏夹一条固定 trigger issue**(state 按 `<project>__<collection_id>` 键,`triggerIssueId` per collection)。→ **409 闸是 per-(issueId, role) = per-collection**:只挡「同一收藏夹在飞时重复 spawn」,**不**串行化不同收藏夹(不同 issue → 不同 409 域)。
- **不同收藏夹可并发 spawn**(各自 Runner)。但它们都打**同一个本地 MCP server(127.0.0.1:18060,单 rod 浏览器)**→ **MCP 层天然串行**(Phase 0 §7.1 实测:并发请求串行排队;单收藏夹 7 条 60s)。即:**调度层不串行,执行层在 MCP 单浏览器处天然串行**。鉴于 Phase 0 已知 MCP 慢且串行 + Runner 端长超时 + fail-soft,这个**执行层串行是可接受/intended 的现实约束**(不是 bug);A0-A10 须确认并发多收藏夹在单 MCP 浏览器上的争用不致超时失败(若过载,后续可加调度层并发上限,v1 不做)。

### 8.3 A0-A10 必须显式验的承重不变量（team-lead 要求）

A 的去重是承重的 → **A9 扩充为必验**:
- 两个 due collection / 重叠 tick → **同一 trigger issue 不产生重复并发 run**(409 闸 + FLY-176 lockdir 真能拦);
- 不同 collection 的并发 Runner 在单 MCP 浏览器上的争用 = 慢但不失败(长超时兜住),确认是 intended 串行非意外死锁;
- Runner 死在 set-next-due 前 → 下轮 re-spawn(fail-soft 重试)真发生、不产生僵尸并发。

### 8.4 Codex design 复核结果（option A bless,2026-06-06）

**VERDICT: BLESS option A**(额度回来后跑的 plan 级 design review)。Codex 确认纵深防御保住「单收藏夹单活跃 worker」不变量,不需 scheduler 在 spawn 前知道 exec-id;并核到 `RunDispatcher.start()` 的同步 per-issueId+role inflight `has`/`set`(run-dispatcher.ts:437-458)是 409 之外的第二道原子防重复闸。**option A 钉死。**

三条 non-blocking 发现的处置:
1. **(已修)** 竞速越过 route 的 StateStore 检查的重复 spawn 被 RunDispatcher 原子拦下,但可能映射成 500(非干净 409)。→ executor 已改:把 "already in progress" 类消息(任意 status)也当**静默 already_active 跳过**,不误告警(+1 测)。未来 cleanup 可让 dispatcher 重复错误显式返 409(本仓 follow-up,非本 issue)。
2. **(部分修 + 跟踪)** lease 不是 fencing token:mutating xhs-state 命令(mark-processed/op 更新/set-next-due)不校验当前 lease owner → 超 TTL 暂停后恢复的进程可能在他人接管后写。→ **已做**:SKILL.md 明确「lease TTL 要覆盖含 prune-gate 等待的整轮 + download/开 gate 前 renew + 自己 RUN_KEY renew/release」,并说明阻塞 gate 期间 409 才是权威 spawn-dedup(lease 失效不致重复)。→ **跟踪 follow-up(A0-A10 硬化时做)**:给 mutating xhs-state 命令加可选 `--owner` fencing(校验 lease owner 再写)。Codex 注:此风险 scheduler 取 lease 也一样,除非 fence 状态写 —— 故不构成改 B 的理由。
3. **(记录假设)** bless 假设单一权威 Bridge/StateStore/RunDispatcher 进程(本架构如此);active-active Bridge 副本会使 409 + 内存 inflight 失效,需共享唯一性机制 —— 本架构不涉及,记录为前提。
