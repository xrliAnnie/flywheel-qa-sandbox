**Version**: v1.28.0

**Date**: 2026-05-17
**Source**: `doc/engineer/exploration/new/FLY-159-gate-timeout-rethink.md`

> 把 `flywheel-comm gate` 的 default 从"分钟"重构到"天"，并把 timeout 行为从"默默 fail-open 继续"改成"fail-close + 通过 Lead 通知 Annie"。涵盖 brainstorm 里 3 个 open question 的具体方案 + Codex Round 1 反馈中识别出的两层 Runner-side cap race + event payload propagation 修复。

### 1.1 Codex Round 1 关键发现（加入本 plan）

Codex Round 1 (`/tmp/codex-rescue-design-feedback-flywheel-v1.28.0-FLY-159-gate-timeout-48h-round1.md`) 找到 9 个 issue，全部接受。要点：

1. **现有 Runner-side 12h `waitingTimeoutMs` + 48h `BASH_MAX_TIMEOUT_MS` 会在 48h gate timeout 之前 kill Runner** → 加 Phase 0 把这两层 cap 拉到 49h。
2. **`event-route.ts:1206-1226` 重建 `HookPayload` 时**只 copy 已知字段，`checkpoint / waited_ms / original_message / timeout_behavior` 会丢 → 必须扩 `HookPayload` schema + 在 event-route 加 `gate_timed_out` mapping。
3. **`gate.ts` timeout path 不调 `resolveGate(0)`** → CommDB pending question 残留，GatePoller / bootstrap 仍会拿到 → 必须在 fail-close timeout path 调用 cleanup。
4. **Bridge-down 时 HTTP POST `/events` fail** → GUARDRAIL 只覆盖 Bridge→Lead，不覆盖 Runner→Bridge → AC5/AC7 显式说明可靠性边界。
5. **`process.exit(1)` 不是 hard kill** — 它退的是 `flywheel-comm` subprocess，Claude Code Bash tool 收到 failed tool result，不是整个 tmux session 死 → Blueprint instruction 显式 "stop work on non-zero exit"。
6. **Sequencing**：Phase 3（CLI default flip）和 Phase 5（event chain）必须同 PR ship；否则 fail-close 上线但 escalation 没上 → 重排为单 PR + Phase 顺序 cap → event chain → default flip。
7. **`ConfigLoader.test.ts:815-826` 现有测试** expects `1800000` (30 min) 不变 → 必须改成"被自动 raise 到 4h"。
8. **`scripts/test-deploy.sh:489`** yaml 写 `timeout_ms: 3600000 # 1h` → 部署后会被 floor raise 到 4h → comment + QA expectation 同步更新。
9. **Lead rule placement**: `runner-messaging-rules.md` 仅在非-commdb backend 加载（`claude-lead.sh:1159-1165`），rollback 到 commdb 会丢规则 → 放 `department-lead-rules.md`（`claude-lead.sh:1136` 无条件加载）。

### 1.2 Codex Round 2 关键发现（加入本 plan）

Codex Round 2 (`/tmp/codex-rescue-design-feedback-flywheel-v1.28.0-FLY-159-gate-timeout-48h-round2.md`) 找到 3 个 issue，全部接受：

1. **GUARDRAIL_EVENT_TYPES 对 `/events` 路径不生效** — `event-route.ts:1283` 现在 `.then(() => store.markLeadEventDelivered(seq))` **无条件**把行标记 delivered，即使 `runtime.deliver()` 返回 `{delivered: false}`。HeartbeatService 的 `retryUndeliveredGuardrailEvents()` 看不到失败行 → AC7 in practice fail。**必须**在 event-route 加 result.delivered 检查（mirror `HeartbeatService.ts:416` 现有 pattern）。`store.recordDeliveryFailure(seq, error)` 在 `StateStore.ts:1518` 已存在，可直接用。
2. **`gate_timed_out` 不应对 explicit fail-open gate 触发** — fail-open 语义就是"没回也继续"，emit 高优先级 Annie alert 是噪声。**仅 fail-close 路径 emit `gate_timed_out`**。fail-open 路径仅 log stderr，不发 event。
3. **`timeout_behavior_source` 三值过细，无法实现** — CLI 看不到 `--timeout-behavior` 是 Blueprint 注入还是人 hand-type。简化为两值 `"default" | "flag"`（"default" = CLI 没传 flag，"flag" = 传了 flag 不论来源）。够 Lead 给 Annie 写 prompt。

### 2.2 Q4.1 Discord 升级路径 → **新 event type `gate_timed_out`**

**Decision**: 新 event type，不复用 `session_stuck`。

Trade-off：

| 方案 | 优 | 缺 | 选 |
|---|---|---|---|
| (A) 复用 `session_stuck` | 零新 type，复用 FLY-83 LeadWatchdog Discord 通路 | 语义混淆——"agent 进程卡死"和"agent 等用户超时"被 Lead/Annie 看成同一事 | ❌ |
| (B) 新 type `gate_timed_out` | 语义干净，payload 可带 checkpoint name + 原 message + 等待时长，Lead 可专 prompt "retry / kill / approve" | 要走全链路：`HookPayload` schema、`event-route.ts` payload mapping、`EventFilter` 新 rule、`GUARDRAIL_EVENT_TYPES` 加成员、Lead identity.md 教学 | ✅ |

**实现要点（Codex Round 1 + Round 2 修正后）**：
1. Runner 端 `gate.ts` timeout 触发时（fail-close 和 fail-open 都进入这个 branch，但只 fail-close 发 event — Codex R2 Issue 2）：
   1. 调 `db.resolveGate(questionId, 0)`——把 CommDB pending question 标记为 expired（Codex R1 Issue 3）。**fail-open 和 fail-close 都做**——避免 stale question 残留；
   2. 仅当 `args.timeoutBehavior === "fail-close"` 时：调 `reportGateTimedOutBestEffort(args, waitedMs, questionId)`（R3 重命名，避免和 fail-open behavior 混名）——POST `${FLYWHEEL_BRIDGE_URL}/events` (best-effort send, 2s timeout, error swallowed)；
   3. Stderr 打印 `[gate] TIMEOUT (${behavior}) after ${waitedMs}ms checkpoint=${checkpoint}; Runner should stop` 在 fail-close 时；fail-open 时打印 `[gate] TIMEOUT (fail-open) after ${waitedMs}ms; continuing as configured`（Codex R1 Issue 5）；
   4. fail-close → `process.exit(1)`；fail-open → return `{status: "timeout", exitCode: 0}`。
2. Event payload 字段（Codex R2 Issue 3 简化）：`checkpoint`、`exec_id`、`lead_id`、`waited_ms`、`original_message`（truncate to 500 chars 防大 message）、`timeout_behavior`（"fail-close" — Round 2 修后只有这一种值会触发 event）、`timeout_behavior_source`（**两值** `"default"` = CLI 没传 `--timeout-behavior` flag, `"flag"` = 传了 flag 不论来源）、`question_id`。
3. **`HookPayload` schema 扩展**（Codex Issue 2）：在 `packages/teamlead/src/bridge/hook-payload.ts` 加可选字段 `checkpoint?: string`、`waited_ms?: number`、`original_message?: string`、`timeout_behavior?: string`、`timeout_behavior_source?: string`、`question_id?: string`。
4. **`event-route.ts:1206-1226` 加 mapping**（Codex Issue 2）：紧挨着 `event.event_type === "stage_changed"` 的 if 后加：
   ```ts
   if (event.event_type === "gate_timed_out") {
     hookPayload.checkpoint = asString(payload.checkpoint);
     hookPayload.waited_ms = asNumber(payload.waited_ms);
     hookPayload.original_message = asString(payload.original_message);
     hookPayload.timeout_behavior = asString(payload.timeout_behavior);
     hookPayload.timeout_behavior_source = asString(payload.timeout_behavior_source);
     hookPayload.question_id = asString(payload.question_id);
   }
   ```
5. Bridge 侧 `EventFilter.ts:115-148` 加新 rule：`gate_timed_out` → `priority: "high"`, `updateForum: false`。
6. `lead-runtime.ts:18-23` `GUARDRAIL_EVENT_TYPES` Set 加 `"gate_timed_out"`（**仅**保证 Bridge ingest 后的 Bridge→Lead delivery；不保证 Runner→Bridge 这一段，见 AC5/AC7 注脚）。
7. **`event-route.ts:1281-1284` delivery handling 修复（Codex R2 Issue 1，必须）**：当前 `.then(() => store.markLeadEventDelivered(seq))` 无视 `result.delivered` 字段，所有 deliver 都标记 delivered，HeartbeatService retry 永远看不到失败行。修为：

   ```ts
   runtime.deliver(envelope).then((result) => {
     if (result.delivered) {
       store.markLeadEventDelivered(seq);
     } else if (GUARDRAIL_EVENT_TYPES.has(event.event_type)) {
       store.recordDeliveryFailure(seq, result.error ?? "deliver returned false");
     } else {
       store.markLeadEventDelivered(seq);  // non-guardrail: best-effort, no retry
     }
   }).catch((err) => {
     if (GUARDRAIL_EVENT_TYPES.has(event.event_type)) {
       store.recordDeliveryFailure(seq, (err as Error).message);
     } else {
       console.warn(`[event-route] non-guardrail deliver threw: ${(err as Error).message}`);
     }
   });
   ```

   `store.recordDeliveryFailure(seq, error)` 已存在于 `StateStore.ts:1518`，pattern 跟 `HeartbeatService.ts:416` 一致。**影响面**：所有 `/events` route delivery 行为变成"guardrail-aware"，但**仅 GUARDRAIL_EVENT_TYPES 成员**进 retry path，其他 event 行为不变（仍走 markDelivered 兜底）。无 AC7 in practice fail 风险。
8. **Lead rule** 放 `packages/teamlead/lead-rules-base/department-lead-rules.md`（`claude-lead.sh:1136` 无条件加载），**不**放 `runner-messaging-rules.md`（`claude-lead.sh:1159-1165` 在 commdb backend 下 skip）。

### 2.3 Q4.2 ConfigLoader floor → **4h（`14_400_000ms`）**

**Decision**: `MIN_GATE_TIMEOUT_MS = 14_400_000`（4h）。

实现位置：`packages/config/src/ConfigLoader.ts:128-135`。在现有 `timeout_ms <= 0` throw 判断后加：

```ts
if (cp.timeout_ms < MIN_GATE_TIMEOUT_MS) {
  console.warn(
    `[ConfigLoader] checkpoints.${name}.timeout_ms=${cp.timeout_ms}ms is below floor (${MIN_GATE_TIMEOUT_MS}ms = 4h), raising to floor.`,
  );
  cp.timeout_ms = MIN_GATE_TIMEOUT_MS;
}
```

**warn + raise**（不是 throw），保证 boot continuity。

Floor constant 放 `packages/config/src/constants.ts`（新文件）连同 `DEFAULT_GATE_TIMEOUT_MS`、`DEFAULT_TIMEOUT_BEHAVIOR`。

## 3. Implementation Phases（已按 Codex Issue 6 重排）

**关键 sequencing 决定**：本 plan ship 为**单 PR**（不分多个 PR），因为 fail-close default 与 escalation 路径必须同时上线，否则 fail-close 上线但 event chain 没上会导致 Runner 默默退出无人通知。

如果硬要拆 PR，**只允许**这个顺序：
1. PR-A: Phase 0 (Runner caps) + Phase 1 (constants) + Phase 2 (ConfigLoader floor) + Phase 5 (event chain + gate.ts cleanup + HookPayload + event-route mapping + Lead rule) — 全部基础设施
2. PR-B: Phase 3 (CLI default flip) + Phase 4 (Blueprint default + instruction text) — 行为切换

PR-A merged 但 PR-B 未 merge 时，旧的 fail-open default 继续生效，escalation 路径已就绪但暂时不用——安全降级。**绝对不允许** PR-B 先 merge。

### Phase 0 — Raise Runner-side waiting/Bash caps (新增, Codex Issue 1)

**为什么必须先做**：48h gate timeout 需要 Runner 进程能活到 48h。但当前 Blueprint 给 Adapter 的 `waitingTimeoutMs=43_200_000`（12h）会让 TmuxAdapter 在 12h 时 kill Runner pane；`BASH_MAX_TIMEOUT_MS=172_800_000`（48h）会让 Claude Code Bash tool 在 48h precisely 时 kill `flywheel-comm gate` 子进程——race 太紧。

|---|---|
| `packages/edge-worker/src/Blueprint.ts:692` | `waitingTimeoutMs: 43_200_000` → `176_400_000`（49h = 48h gate + 1h buffer） |
| `packages/claude-runner/src/TmuxAdapter.ts:299` | `BASH_MAX_TIMEOUT_MS=172800000` → `BASH_MAX_TIMEOUT_MS=176400000` |
| `packages/claude-runner/src/TmuxAdapter.ts:561` | `ctx.waitingTimeoutMs ?? 43_200_000` → `?? 176_400_000` |

| FLY-102 test 或其他 asserting `BASH_MAX_TIMEOUT_MS=172800000` 的测试 | grep + update assertion |

**Smoke check after Phase 0**: 启动一个 Runner，让它跑 brainstorm gate（不让 Lead respond），grep tmux 进程 `BASH_MAX_TIMEOUT_MS` env var = 176400000。

## 6. Migration / Rollout

### 6.1 行为变化清单（PR description 必列）

- ✅ Default gate timeout: 30 min (Blueprint) / 1h (CLI fallback) → **48h** 两处统一
- ✅ Default timeout behavior: `fail-open` → **`fail-close`**
- ✅ New event type: `gate_timed_out`（Lead 通知 Annie）
- ✅ Config floor: `checkpoints.<name>.timeout_ms < 4h` → auto-raise to 4h + warn
- ✅ Runner waiting cap (Blueprint.waitingTimeoutMs): 12h → 49h
- ✅ Runner Bash cap (BASH_MAX_TIMEOUT_MS): 48h → 49h
- ⚠️ 需保留 fail-open 行为的项目 → 必须显式 `checkpoints.<name>.timeout_behavior: fail-open`
- ⚠️ scripts/test-deploy.sh QA yaml 的 `1h timeout_ms` 部署后变 4h（comment 更新）

### 6.2 可靠性边界（Codex Issue 4 — 明确 AC）

| 故障场景 | 行为 |
|---|---|
| Bridge 在线，event POST 成功 | Lead 在 chat thread 通知 Annie（高优先级，GUARDRAIL 重投递） |
| Bridge 重启 / Bridge ingest 后 → Lead 投递前断 | GUARDRAIL_EVENT_TYPES 保证 HeartbeatService 5min 内 retry → 最终送达 |
| Bridge 完全离线，event POST fail | gate.ts fail-open send 吞掉错误 → Runner 仍 exit 1；**Annie 不会收到 Discord 通知**；Runner sessionTimeoutMs (24h safety net via FLY-92/Blueprint.ts:658) 或下一次 Bridge 上线时的 heartbeat 会发现 Runner 死掉 → 间接通知（延迟可能数小时） |

**本 plan 不引入 Runner-side durable outbox**（Codex Issue 4 建议但 over-engineer 风险高）。可靠性边界写进 AC5/AC7 + PR description。

### 6.3 项目 yaml 兼容性

- Flywheel 自己 `.claude/qa-config.yaml` + `packages/qa-framework/*/qa-config.yaml`：检查 checkpoints 段，看是否需要补 `timeout_behavior: fail-open` 显式（如果想保留旧 fail-open）
- GeoForge3D 项目 yaml：同上
- Designer 项目 yaml：12h timeout_ms 高于 4h floor，保留；但 timeout_behavior 默认变化会让 brainstorm gate 超时后 fail-close → 建议运维通知 Designer 项目 owner

### 6.4 Rollback strategy

PR 是 squash merge，rollback = revert PR + 重启 Bridge + Lead。无 schema migration，无 DB 改动。事件 type `gate_timed_out` rollback 后 EventFilter 走 DEFAULT_RESULT（priority=normal, no Forum update），不 crash。`HookPayload` 新增字段是可选 → revert 后无 TS compile error。
