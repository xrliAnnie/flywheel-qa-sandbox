# Plan: Roundtable thread — surface non-bot (founder) messages to member leads without @

**Version**: v1.60.0
**Issue**: FLY-576 (follow-up to PR #349 — membership + naming already shipped)
**Date**: 2026-06-25
**Source**: `doc/engineer/research/new/FLY-576-roundtable-thread-membership.md`, Lead brainstorm-gate steer (2026-06-25)
**Status**: codex-approved (2 rounds, xhigh)

## Problem

`#349` (v1.59.0) fixed two of FLY-576's three points: roundtable auto-thread **membership**
(founder + @-mentioned leads added as Discord thread members) and **descriptive naming**.

The **third acceptance criterion is still unmet — "回复不 surface"**: inside a roundtable
topic thread, a lead does NOT receive/process a message unless it is explicitly
@-mentioned. So when the founder (Annie) posts in the thread WITHOUT @-ing a lead, none of
the member leads see it in-session → they cannot collaborate without a per-message @.

Annie real-machine confirmed this. Her roundtable is currently **all Claude-backend**
(Belle / Cass / Tadashi) — so the **Claude plugin path is the acceptance-critical fix**;
the Codex path (Mufasa) is fixed in parallel for completeness.

## Root cause (verified, not assumed)

Both lead backends gate inbound roundtable-thread messages through a mention-gate that
requires an explicit @ (or a name regex). The no-@ relaxation (FLY-314 Phase 2b
`autoContinue` + per-thread bot-only anti-loop budget) exists on BOTH sides but is
**default-OFF** (`FLYWHEEL_ROUNDTABLE_THREAD_AUTOCONTINUE` is unset in production). So:

- **Claude plugin** (`roundtable-thread-policy.ts::decideTopicThreadHandling`): with
  `autoContinue` off, branch (1) returns `handle = isExplicitMention`. Founder non-@ →
  `false` → dropped. Membership is only even probed when `autoContinue` is on
  (`server.ts:695`), so the relaxation is unreachable in production.
- **Codex** (`mention-gate.ts::buildMentionGate`): with `autoContinue` off, a dynamic
  (topic-thread) message falls through to `isMentioned(...)`. Founder non-@ → `false` →
  dropped.

`#349` made the founder a Discord thread MEMBER (so Discord surfaces the thread to her
sidebar), but the lead-side inbound gate still drops her non-@ messages — that is the gap.

## Approved policy (Lead brainstorm gate, 2026-06-25)

Inside a roundtable topic thread the lead is a **member** of:

- **NON-BOT author (founder / human)** → handled by **DEFAULT** (no @ needed, no flag) —
  surfaced to the lead, which may reply. Structurally melee-immune (a human cannot form a
  bot-to-bot loop).
- **BOT author (sibling lead)** → **unchanged**: handled only on explicit @-id (and, when
  `autoContinue` is on, budget-gated). Non-@ bot chatter is NOT auto-replied → no melee.
  The founder still sees bot chatter via Discord membership (#349).

Default-ON, no new flag (reply-in-thread is already ON in production; Annie wants it
out-of-box). This is cleaner than flipping `autoContinue` on, which would let bots
multi-turn auto-reply to each other (bounded melee) — not what "回 founder / 被点名" means.

## Membership semantics (both sides == "this lead has joined the thread")

- **Claude plugin**: `isRoundtableThreadMember()` — a Discord `GET
  /channels/{thread}/thread-members/{bot}` probe (200=member, 404=absent, else=unknown →
  fail-closed), positive-cached in `rtMemberThreads` (200 only; absent/unknown uncached).
- **Codex**: `RoundtableThreadRegistry.has()` — a thread is in the registry only via
  `subscribe()` (this lead @-mentioned into the top-level) or `reconcileOnce()` (active
  guild threads whose `members[]` shows the bot has JOINED). So registry membership ==
  "bot has joined" == member.

`#349` adds the @-mentioned leads (and founder) as members, so they are members/subscribed.
A lead that was never pulled into a thread is NOT a member → gets no relaxation (correct —
it is not part of that topic).

## Design — Claude plugin (acceptance-critical)

File: `external_plugins/discord/roundtable-thread-policy.ts`

Restructure `decideTopicThreadHandling` so the NON-BOT human branch runs BEFORE the
`autoContinue` kill-switch:

```
(0) authorIsSelf            → drop
(1) !authorIsBot (HUMAN)    → reset budget; handle = isMember || isExplicitMention   // FLY-576: default-ON
(2) bot && !autoContinue    → handle = isExplicitMention                              // byte-compat (anti-loop default)
(3) bot && isMember!==true  → drop
(4) bot member              → budget-gated (consume; missing entry = exhausted)       // unchanged
```

Only change vs today: the human branch (1) is lifted out from behind `autoContinue`. The
bot branches (2)–(4) are byte-identical to the current (1)/(3)/(4). Resetting the budget on
a human message even when `autoContinue` is off is a no-op for behavior (the budget is
never read while bots go through the mention-only branch (2)).

Add a PURE, unit-testable predicate `shouldProbeTopicThreadMembership` to
`roundtable-thread-policy.ts` (Codex R1#1 — `server.ts` is not importable: it ends with
`client.login(TOKEN)`, and `gate`/`isRoundtableThreadMember` are not exported, so the probe
condition must live in a pure module to be tested):

```ts
export function shouldProbeTopicThreadMembership(input: {
  authorIsBot: boolean; isExplicitMention: boolean; autoContinue: boolean;
}): boolean {
  // bot author: membership only matters on the autoContinue budget path.
  if (input.authorIsBot) return input.autoContinue;
  // non-bot human: membership only matters when there is NO explicit @ (an explicit @ is
  // handled by isExplicitMention regardless of membership — skip the probe + its 5s timeout).
  return !input.isExplicitMention;
}
```

File: `external_plugins/discord/server.ts` (call site ~L695) — pure glue:

```ts
const needsMembership = shouldProbeTopicThreadMembership({
  authorIsBot, isExplicitMention: mentioned, autoContinue: RT_CFG.autoContinue,
})
const isMember = needsMembership
  ? await isRoundtableThreadMember(threadId, botUserId)
  : undefined
```

This makes the FLY-576 human non-@ production path reachable (probe fires for non-bot + no
@), skips the probe on an explicit human @ (already decided) and on bot + `autoContinue` off
(unchanged), and keeps the only non-trivial logic in a pure, tested helper.

## Design — Codex (Mufasa, parallel/completeness)

File: `packages/teamlead/src/lead-backends/codex/mention-gate.ts`

In `buildMentionGate`, inside the `isShared` branch, special-case dynamic (member) threads:

```
if (isShared) {
  if (isDynamicThread) {
    // FLY-576: a NON-BOT human in a member thread is handled WITHOUT @ by default.
    // Reset the bot budget (a human message is a reset event).
    if (!msg.authorBot) {
      if (opts.budgetStore) seedThreadBudget(opts.budgetStore, msg.channelId, budgetN)
      return true
    }
    // bot author → no-@ continuation only under autoContinue (+budget); else @-required.
    if (autoContinue && opts.budgetStore) {
      return decideTopicThreadContinuation(
        { threadId: msg.channelId, authorBot: true }, opts.budgetStore, { budgetN })
    }
    return isMentioned(msg, opts.botUserId, compiled)
  }
  // static shared parent channel → unchanged (mention-required)
  return isMentioned(msg, opts.botUserId, compiled)
}
return true
```

The non-bot relaxation is default-ON for registered (member) threads; bots keep the
existing @-id + budget behavior. (Registry membership already encodes "this lead joined".)

No separate runtime edit is required: both the headless (`codex-lead-runtime.ts`) and TUI
(`codex-lead-tui-runtime.ts:580-594`) runtimes call the SAME shared `buildMentionGate`, so
the change lives wholly in `mention-gate.ts` (+ a `seedThreadBudget` import) and both
runtimes inherit it (Codex R1#3). Tests live at the shared-gate level (`mention-gate*.test`),
not per-runtime.

## Melee safety (the hard constraint)

- A non-bot human cannot drive a bot-to-bot loop. Relaxing for humans only is structurally
  loop-free.
- Bot authors are NOT relaxed by this change: with `autoContinue` off (production default)
  a sibling lead's non-@ message is still dropped → no auto-reply → no melee. With
  `autoContinue` on, the unchanged per-thread bot-only budget bounds any bot continuation
  to `budgetN` steps (FLY-220 / FLY-314 contract, fully preserved).
- "Pile-on" (N member leads all replying to one founder message) is handled at the
  agent/lead-rules layer ("reply only when you have substance"), not the gate — out of
  scope for this gate change.

## Byte-compatibility

- Vanilla / non-roundtable installs: `loadRoundtableConfig`/`RT_CFG` undefined → this path
  is never taken → unchanged.
- Non-roundtable threads & channels: untouched (gate only fires for parent==roundtable).
- Bot-authored behavior: byte-identical (branches (2)–(4) preserved).
- The ONLY intended behavior change: a non-bot human's non-@ message in a member roundtable
  thread is now delivered (was dropped). This is the approved fix.

### Membership-probe cost (Codex R1#2 — corrected)

`isRoundtableThreadMember` caches POSITIVE (200/member) results only; 404/absent and
unknown are intentionally NOT cached (a lead can be added to a thread later — a negative
cache would stale-lock it out). With the `shouldProbeTopicThreadMembership` predicate the
probe fires only for non-bot + no-@ messages (and bot + autoContinue). For the founder — who
IS a member (#349) — the first probe returns 200 and is cached, so subsequent non-@ messages
are one-shot. A non-MEMBER human posting non-@ in a topic thread would re-probe per message
(404 uncached), but `#leads-roundtable` human volume is the founder only → negligible. We do
NOT add a negative cache. An explicit human @ bypasses the probe entirely (predicate returns
false) and is handled by `isExplicitMention`, so it can always recover from a stale-absent
state.

## Test plan (TDD — RED first)

Pure-policy unit tests (no Discord/network) on both sides:

**Claude `decideTopicThreadHandling`:**
- human, member, no @, autoContinue OFF → handle=true (NEW — the fix; was false)
- human, NON-member, no @, autoContinue OFF → handle=false (still needs @)
- human, member, no @ → resets budget (assert store seeded)
- bot, member, no @, autoContinue OFF → handle=false (byte-compat, no melee)
- bot, explicit @, autoContinue OFF → handle=true (byte-compat)
- bot, member, no @, autoContinue ON, budget>0 → handle=true, budget consumed (unchanged)
- bot, member, autoContinue ON, budget exhausted → handle=false (unchanged)
- self → handle=false (unchanged)
- 2-bot adversarial loop terminates in ≤ budget (unchanged invariant re-asserted)

**Claude `shouldProbeTopicThreadMembership` (pure helper — the testable seam for the
acceptance-critical call site):**
- non-bot, no @ → true (must probe — FLY-576 path)
- non-bot, explicit @ → false (skip probe; decided by isExplicitMention)
- bot, autoContinue OFF → false (skip probe)
- bot, autoContinue ON → true (budget path needs membership)

**Codex `buildMentionGate`:**
- non-bot human in dynamic thread, autoContinue OFF → true (NEW)
- non-bot human in dynamic thread → budget seeded
- bot in dynamic thread, autoContinue OFF, no @ → false (byte-compat)
- bot in dynamic thread, explicit @id, autoContinue OFF → true
- bot in dynamic thread, autoContinue ON → budget path (unchanged)
- static shared parent channel, non-bot, no @ → false (parent still mention-required)
- non-shared channel → true (unchanged)

**Server call-site (Claude):** `server.ts` is not unit-importable (ends in
`client.login`, gate/probe unexported), so the probe DECISION is verified via the pure
`shouldProbeTopicThreadMembership` tests above; the call site is thin glue that passes its
result to `isRoundtableThreadMember`. (Real-machine behavior is covered by the independent
Lead-dispatched QA.)
