## 2. 灰度粒度 —— 选项分析(Annie 要点)

| 方案 | 机制 | A/B 能力 | Pros | Cons |
|------|------|---------|------|------|
| **G1 per-project only** | `.flywheel/config.yaml` `ponytail.enabled` | ❌ 同项目无法一开一关 | 最简单;整项目 rollout 清晰 | 不满足 Annie 的 A/B |
| **G2 per-issue label** | Linear 标签 `ponytail` / `ponytail-off` | ✅ 给 issue 打标做 A/B | Linear 里可见、可审计;复用现成 label→dispatch 流;founder/Lead 直接在 issue 上控 | 需打标纪律;label 是 per-issue,re-run/retry 自动继承(对 A/B 反而是好事=条件稳定) |
| **G3 per-run flag** | `/api/runs/start` body `ponytail: on/off`(仿现成 `docTier`) | ✅ Lead/程序化 A/B | 最显式;一次 run 精确控;利于脚本化批量 A/B | Linear 不可见、临时性;要 Lead 主动传 |
| **G4(推荐)解析阶梯** | per-run > per-issue label > per-project > 默认 off | ✅ 三种 A/B 都支持 | 一套优先级覆盖"广 rollout + 精确 A/B + 临时 override";每层用途清晰 | 接线略多(但都在现成 boundary 上;见 §4) |

**推荐 G4**:project 层 = 广灰度;label 层 = 在 Linear 上给指定 issue 做 A/B(最贴 Annie"两个 issue 一开一关");run-param 层 = Lead/程序化精确 override。三层都缺省 = off → byte-compat。

### 2.1 解析阶梯(precedence,高→低)
1. **per-run** `/api/runs/start` body `ponytail`(`"on"|"off"`)——显式,胜过一切。
2. **per-issue** Linear label:`ponytail`→on、`ponytail-off`→off(已 fetch 的 `normalizedIssueLabels`)。
3. **per-project** `.flywheel/config.yaml` `ponytail.enabled`。
4. **默认 off**。
**条件模型(requested vs effective,Codex R3 #2/#3)**——区分"想要什么"和"实际跑成什么":
- `requested`: `{ want: "on"|"off", source: "run"|"label"|"project"|"default" }` —— 解析阶梯产出的**意图**。
- `effective`: `"on"|"off"|"unavailable"` —— 叠加 readiness(§5)后**实际**。
- 持久化串(§6)**同时编码两者**,如 `on:label`(effective on)、`off:default`、`unavailable:readiness:on:label`(requested on via label,但插件不可用 → 没真开,但 retry 能据此恢复)。**不含 mode**(§1)。

**Fail-closed 语义 —— 只在"刻意要 ponytail"时,绝不破坏 default-off byte-compat(Codex R3 #1 HIGH + R2 #3)**:
- **`ponytail`+`ponytail-off` 冲突**:reject / fail-loud,不猜。
- **label fetch 失败**(`issueLabelsFetchFailed`)分两种:
  - **项目 `ponytail.enabled:true`**(rollout 进行中)且无 run-param → 无法判断本 issue 是否被 `ponytail-off` 豁免 → **selector-unavailable**,条件串 `unavailable:selector:label_unreadable`(**未解析**,区别于 readiness 类;§6 retry 须重解析而非冻结)。否则"project:on + issue 有 ponytail-off 但 fetch 挂"会误开。
  - **项目 off/缺省 且无 run-param**(= 纯 default-off,根本没要 ponytail)→ **`off:default`,byte-compatible**(与今天逐字一致),**只 log warning**(不新增持久化 surface;Codex R6 #3 — 诊断需要时再加),**绝不**因 Linear label 读不到就让本就 off 的项目 fail。
- per-run override 存在时,label fetch 失败/冲突都不影响(显式最高)。

**两类 unavailable(retry 行为不同,Codex R6 #1)**:
- `unavailable:readiness:<want>:<source>` —— 请求**已解析**、只是 plugin/node 缺 → retry 走 `frozen_requested`(§6),装好即恢复。
- `unavailable:selector:label_unreadable` —— 请求**没解析成**(label 没读到)→ retry **重解析**(用刷新后的 label + project config),让恢复后的 `ponytail-off` 能生效(不能冻结成 `on:project`)。

## 4. 接入(块 1)—— 强制 installed-but-globally-disabled(Codex R1 #1 HIGH)

`scripts/setup-ponytail.sh`(幂等,**强制最终态**而非只装):
1. 检查 `claude` + `node` 在 PATH(ponytail hooks 依赖 node;缺则 fail-loud)。
2. `claude plugin details ponytail@ponytail` 探测:
   - **不存在** → `claude plugin marketplace add DietrichGebert/ponytail` + `claude plugin install ponytail@ponytail`。
3. **安装后显式** `claude plugin disable ponytail@ponytail`(对 install 用的同一 scope)→ 因为现 CLI 语义下 `install` 可能把它写进 `~/.claude/settings.json::enabledPlugins:true`(Codex 实测本机已装插件都进该字段)→ 不显式 disable 会**全局启用、破坏 default-off**。
4. **验证最终态 = installed 且 globally disabled**;若原本已 installed+enabled → 需 `--force-disable` 或操作员确认,否则 fail-loud 给指引。
5. 打印结果 + per-issue/per-run 怎么开的提示。
- 文档:`doc/engineer/implementation/ponytail-setup.md`。
- 分工:PR 交付脚本+文档+接线;真正全局 install 由操作员跑一次。

## 5. Readiness 兜底(Codex R1 #2 / R2 #4)—— 防"开了却静默没生效"

`--settings` 启用一个**没装**的插件 = 静默 no-op(`plugin list` 不报错)→ 会污染 rollout/eval。

**明确契约(Codex R2 #4 / R3 #2)= requested on 但不可用 → 不 spawn,但仍写 audit row,绝不降级成静默 OFF run**:
- readiness **返回判别式结果**(`ready | unavailable`),**不在 `emitStarted` 之前 throw**(否则 `Blueprint.run()` 的 try 还没起、dispatcher 只 catch+清理预注册,session row / 失败事件都不落,违反 audit 契约,Codex R3 #2)。
- 当 `requested.want === "on"` 时跑 readiness:`claude` + `node` 在 Runner **将继承的同一 `CLAUDE_CONFIG_DIR`** 下可用(`ClaudeCodeAdapter.runtimeEnv()` 仅 env 存在时透传 CLAUDE_CONFIG_DIR → helper 用同一推导)、且 `claude plugin details ponytail@ponytail` exit 0。
- **不可用时的严格时序**:resolve requested → readiness → 若 unavailable:构造 env 带 `ponytail_condition = unavailable:readiness:<want>:<source>`(**readiness 类**,区别于 §2.1 的 selector 类)→ **有序 started 写**(§6,`emitStartedReliable()`)落 audit row → emit **failed 终态**、**不**进 `runInner()` / 不 spawn → fail-loud 通知"ponytail 已要但未装 → 跑 scripts/setup-ponytail.sh"。
- `unavailable:*` 态**不发 `--settings`**;FLY-614/616 须排除 `unavailable:*`。
> 选 fail-before-spawn 而非"降级 OFF 跑":requested on 永远是**刻意**动作,静默吞掉既毁 A/B 数据又藏配置错。但**必须留下 audit row**(含原始 requested,供 §6 retry 恢复)。

## 6. 条件标签持久化(对接 614/616)+ 时序 / retry(Codex R2 #1/#2 HIGH)

**Resolver 输入形状(Codex R4 #1 HIGH)—— 别在 runs-route 提前塌缩**:label fetch 状态只有 `runs-route` 知道(`issueLabelsFetchFailed`),project 默认只有 `Blueprint` 知道(`this.ponytailConfig`)。若 runs-route 先把输入塌缩成 requested,Blueprint 就分不清"label 读不到+project off"(应 byte-compat off)vs"label 读不到+project on"(应 fail-closed)。故传**非塌缩 signal**:
```ts
type PonytailRunSignal = {            // 全新 start 的输入(待解析)
  runOverride?: "on" | "off";        // per-run body 参
  labels?: string[];                 // 已 fetch 的 label(认 ponytail / ponytail-off)
  labelStatus: "readable" | "unreadable";
  labelConflict?: boolean;           // 同时有两个 label
};
type PonytailRequested = { want: "on" | "off"; source: "run" | "label" | "project" | "default" };
// Blueprint 的 ponytail 输入是 union(Codex R5 #1 HIGH:retry ≠ start)
type PonytailInput =
  | { kind: "start_signal";     signal: PonytailRunSignal }      // runs-route 发(待解析)
  | { kind: "frozen_requested"; requested: PonytailRequested };  // actions.ts retry 发(已冻结)
```
- **start**:runs-route 发 `start_signal`;`resolvePonytail` 用 project config + labels 跑 §3 阶梯 + §2.1 fail-closed。
- **retry(R5 #1 / R6 #1)**:`actions.ts` 读 predecessor `ponytail_condition`,**按两类分流**:
  - 已解析条件(`on:label` / `off:run` / `unavailable:readiness:*`)→ 发 `frozen_requested`(原始 requested),`resolvePonytail` **原样返回(不碰 labels/config、不换桶/不改 source)**再跑 readiness → `unavailable:readiness:on:label` 装好后恢复 `on:label`、label/config 变也不挪桶。
  - **`unavailable:selector:label_unreadable` → 发 `start_signal`(用 `actions.ts:728-758` 刷新后的 label + project config)重解析**(等同新 start)→ 让恢复后的 `ponytail-off` 生效,绝不冻结成 `on:project`。**注(Codex R7 #2):retry 时 Linear 刷新若仍失败,start_signal 必须带 `labelStatus:"unreadable"`,绝不回退用 predecessor 的 stored labels**(否则"仍读不到 → 仍 unavailable"在内存里假过、生产语义错)。
- **最终 `resolvePonytail(input, this.ponytailConfig)` 在 `Blueprint.run()` envelope 构造前做**。

**时序(R2 #1):** `Blueprint.run()` 先构造 envelope 再 fire `emitStarted()`(`Blueprint.ts:448-467`),之后才 `runInner()`(`:470`)→ `adapter.execute()`(`:1196`)。所以解析 + readiness 必须在 envelope 构造前。
- 解析出 `requested {want,source}` + readiness 叠加得 `effective`(on/off/unavailable),持久化为 session 列 `ponytail_condition`(紧凑串,同时编码两者:`on:label` / `off:default` / `unavailable:readiness:on:label` / `unavailable:selector:label_unreadable`),仿 `founder_ux_gate_mode`(`StateStore.ts:146/210`、`DirectEventSink.ts:138`)。
- 两条 start 写库路径都带:生产 `DirectEventSink.emitStarted`(快照列)+ HTTP `/events` `session_started`(`event-route.ts`)。
- **unavailable 分支事件排序(Codex R4 #2 / R5 #2 / R6 #2 MED — 收敛单一路径)**:started 事件现是 fire-and-forget,且 **`TeamLeadClient.emitStarted()` 只 `track(p)` 不 await HTTP post**(`ExecutionEventEmitter.ts:61-78`)→ 光 `await emitStarted` **不够**(HTTP `session_started` 可能还没落库,failed 赢竞态丢 `ponytail_condition`)。**选定路径 = 新增 `emitStartedReliable()`,仅 unavailable 分支用**(await 真 HTTP post 落库再 emit failed;不动 happy path、不动终态 payload,blast radius 最小)。测:**delayed `session_started` handler** 下 unavailable 仍收尾为 failed 且带 `unavailable:readiness:<want>:<source>`(不止 happy path)。

**Retry(R2 #2 / R3 #3):** retry **不**重进 `runs-route`;`actions.ts:776-810` 从 **predecessor session + 刷新 label** 造 `RetryRequest`(现只有 `docTier`/`issueUrl`,**无 ponytail**)→ 直接 dispatch(retry context 约 `run-dispatcher.ts:303-355`)。所以 per-run body override 在 retry 会丢,除非持久化 + 显式 rehydrate。
- **锁定语义 = 保留原始 `requested`(A/B 桶稳定)、effective 重算**:retry 读 predecessor 持久化的 **`requested`(want+source)** → 经 `RetryRequest` → `BlueprintContext` → 重跑 readiness 得 effective → patch successor(`actions.ts:836-851`)。
  - 普通 `on:label` / `off:run` → retry 保桶不变。
  - **`unavailable:on:label`(R3 #3)→ retry 保留原始 requested(on via label),重跑 readiness**:操作员跑完 `setup-ponytail.sh` 后 retry 能**恢复成真 on**;装还没好则仍 `unavailable`。**绝不**把基础设施失败当桶钉死、也不静默变 OFF。

**对接(本 issue 只产出标签,不做度量):**
- **FLY-614**:按 run join token 用量到 `ponytail_condition` → "on vs off 省多少"。
- **FLY-616**:按 `ponytail_condition` 分桶 eval → "质量掉没掉"(排除 `unavailable:*`)。
- A/B:同项目,issue A 打 `ponytail`(或 run-param on)、issue B 不打 → 两 run 标签不同 → 614/616 直接对比。

## 10. Rollout / 风险
- 默认全 off。merge 后操作员跑 `setup-ponytail.sh`(强制 installed-but-disabled)。再用任一层开第一个灰度(建议大码项目 flywheel 自己 或 GeoForge3D)。改 per-project config 后**需重启一次 Bridge**(config boot 时读;FLY-205 ship 窗教训);label / run-param 层无需重启(每 run 解析)。
- **Rollout 不变量(Codex R4 #4)**:A/B 期间 **不得**有 project/local/managed 层 settings 强制 enable `ponytail@ponytail`(否则 Flywheel 记 `off:default` 但 Claude 实际加载了 ponytail → 污染 614/616)。OFF run **不**用 `--settings` 强制 disable(那会变成非-byte-compat 改动);改为加一条 QA/preflight:记 OFF 桶时若探到外部已 enable 则报警。
- 风险:① setup 不强制 disable 会全局启用(§4 已修);② enabled 但没装 = 静默 no-op(§5 已兜,fail before spawn);③ retry 丢/钉死 per-run 意图(§6 requested 保留 + 重跑 readiness);④ resolver 输入跨 runs-route/Blueprint 塌缩(§6 `PonytailRunSignal` 非塌缩);⑤ `--settings` JSON 在两条 tmux 路径转义(§9 测 + 真机);⑥ ponytail hooks 需 node(§4/§5 验);⑦ 外部 settings 污染 OFF 测量(本节不变量)。

## 12. Codex 覆盖(Annie 改 scope:Claude + Codex 都要)

**事实(已核 ponytail README + Flywheel Codex Runner)**:
- ponytail **真插件**对 Codex 的官方装法 = `codex plugin marketplace add` + 在 Codex **TUI 里交互式** `/plugins` 装 + `/hooks` **信任两个 lifecycle hook**。**Flywheel 的 Codex Runner 是 headless**(`CodexTmuxAdapter` 经 stdin 喂 prompt,无交互 TUI)→ **真插件 + hook 交互信任在 headless Runner 上跑不了**(且 per-runner 隔离 `CODEX_HOME` 还要每个 runner 重装/重信任)。
- 但 ponytail 核心 = **可移植的 7 级决策梯 ruleset(markdown)**,repo 里有给 Cursor/Windsurf/Cline/Copilot 等的 instruction-only 变体 → **能注入任何 agent 的指令层**。Flywheel Codex Runner 的现成注入缝 = `appendSystemPrompt`(折进 stdin prompt)或一个 Flywheel-managed `AGENTS.md` 层(Codex 原生沿目录树读)。

**选项**:

| Path | 做法 | Pros | Cons |
|------|------|------|------|
| **(a) 统一 flag,Codex 注入等效 ruleset** | 同一 ponytail 条件解析"on"时:Claude→`--settings` 真插件;Codex→把 ponytail ruleset(markdown)注进 Codex Runner 指令层(managed `AGENTS.md` 块 / prompt) | ① **一个 flag/标签覆盖两 backend**(Annie"统一"意图)② A/B 在 Claude+Codex 都能跑、616 两 backend 可比 ③ 复用全部 resolver/条件/标签 plumbing,只 spawn 时按 backend 分支 | Codex 拿的是 **ruleset(等效行为)非真插件**:没 ponytail 的 per-turn hooks / `/ponytail` mode 命令 → Codex 侧效果**可能弱于** Claude(prompt/AGENTS 注入 ≠ 每轮 hook 强化);A/B 时 Codex 收益或被低估(给 616 标注) |
| **(b) 先 Claude、Codex 等效拆 follow-up** | v1 只 Claude ponytail;Codex 等效另开 issue | v1 更小更快、先拿 Claude A/B 数据 | Annie 要的"两 backend 都覆盖"延后;Codex-backed issue 这期做不了 A/B |
| (c) spike:真插件 headless 化 | 预置 install + hook-trust 状态进 per-runner `CODEX_HOME` | 与 Claude **同保真**(真 hooks) | 交互信任 + per-runner 重装 + Codex trust 存储格式未文档化 → **脆弱/不确定**;建议作独立 spike,不阻塞 |

**推荐 = (a)**:统一一个 flag/标签覆盖 Claude+Codex,Codex 经 ruleset 注入(等效 minimalism 行为)。理由:最贴 Annie"两 backend 统一覆盖 + A/B"诉求、复用现成 plumbing、headless-clean。**诚实边界**:Codex 是"等效 ruleset"非真插件 hooks;若要与 Claude 像素级一致,(c) spike 作 follow-up。注入优先 **managed `AGENTS.md` 层**(每轮项目指令、比一次性 prompt prepend 更接近 hook 的持续注入)。

> 选 (a) 则 **v1 范围 = per-issue A/B on Claude + Codex 两 backend**(Codex 走 ruleset 注入);per-project 仍是 v2。选 (b) 则 v1=Claude-only、Codex 拆 issue。**等 Annie 定 (a)/(b) 才 implement。**
