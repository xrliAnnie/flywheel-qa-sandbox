### 2.4 Where it can silently fail

| # | Failure mode | Evidence | Likelihood |
|---|--------------|----------|------------|
| **A** | macOS Terminal.app `do script` concurrency race — 3 Apple Events arrive ≤100ms apart, Terminal coalesces / drops some, or "front window" / tab refs collide | Empirical (Annie's report); known macOS Terminal behavior | **HIGH** |
| **B** | `select-window` 5-retry exhausted (linked-session window propagation slow under tmux server contention) → `return` silently (only console.warn, lost in Bridge stderr) | Possible if Bridge log not tailed; depends on tmux internals | Medium |
| **C** | `new-session -d -s viewer-<exec> -t =baseSession` fails — error logged with `stdio: "ignore"` so stderr text discarded; only generic "Command failed" message; the `/duplicate session/` regex never matches because no stderr captured | Code path exists | Low (different viewerSession per exec) |
| **D** | osascript dedup `tell application "Terminal"` blocks ≥10s on 3 concurrent invocations → exec times out | Possible (Apple Events serial in Terminal) | Low-medium |
| **E** | `cancelOpener(execId)` racing — only triggered by `closeRunnerTerminalView` which fires on close paths, not normal spawn | Code path exists | Very low |

**Primary hypothesis**: A (Terminal.app `do script` concurrency).

**Secondary hypothesis**: B (`select-window` race under tmux server contention when 3 linked sessions propagate base session windows simultaneously).

C/D/E are less likely but worth instrumenting because in production the Bridge log already silently catches the warn, so we have no diagnostic.

### 2.5 Why FLY-116 PR #167 round 1-7 didn't catch this

- All Codex review iterations focused on **single-Runner** correctness (TOCTOU, dedup, escape, retry).
- **No round tested concurrent spawn** — there's no test that fires 3 `openTmuxViewer` calls in <1s and asserts 3 tabs.
- The qa-fly-116 E2E test ran 1 Runner at a time (Annie's testing was sequential).

## 4. Fix Plan (Round 3 — Codex Round 2 feedback folded in)

### 4.1 Serialize `openTmuxViewer` at process level — full opener queue with per-step bounded timeouts

**Why**: Eliminates concurrency from osascript + tmux + Terminal.app interactions. Trades parallelism (which we don't actually need — opening a tab takes <1s) for determinism.

**What goes inside the queue** (Codex R1 critical #4):
- ALL Terminal-interacting work for one opener:
  - Dedup `osascript` (currently line 166)
  - tmux linked-session setup: kill-session / new-session / select-window with retry (currently lines 195-264)
  - Final `do script` `osascript` (currently lines 281-285)
- **Verification** is also enqueued — scheduled "not before 1500ms" then chained onto the queue (Codex R2 critical #1).
- Outside the queue: `which tmux` resolution, customTitle formatting, `openingTitles` same-title guard.

**Timeout strategy** (Codex R2 critical #2): **Per-step bounded timeouts only — NO whole-opener `Promise.race` timeout**. Reasons:
- A `Promise.race` timeout cannot cancel an in-flight `execFile` callback, so the underlying opener could keep touching Terminal/tmux after the queue advances → reintroduces concurrency.
- Per-step timeouts ARE enforceable: `execFile` accepts a `timeout` option (Node will SIGTERM the child); `execFileSync` accepts `timeout` (throws `ETIMEDOUT`).
- Worst-case bounded queue hold per opener:
  - Dedup osascript: ≤5s (timeout)
  - kill-session sync: ≤3s (timeout)
  - new-session sync: ≤5s (timeout)
  - select-window: 10 × max(3s timeout + 500ms delay) ≈ ≤35s in degenerate case, but typical ≤500ms
  - Final do-script osascript: ≤5s (timeout)
  - Verification tail: 1.5s delay + 5s verify osascript timeout = +6.5s
  - **Realistic worst case ≤60s, typical ≤4s.** 60s is acceptable as a worst-case upper bound; production pathological cases will simply log and move on.
- Note: `execFileSync` with `timeout` does block the event loop until SIGTERM clears, but the kill is bounded ≤5s per call, so the queue's overall progression is bounded.
- A simple `aborted` flag is checked between awaits so a future enhancement can cooperatively short-circuit; for the initial fix, the per-step timeouts are the durability gate.

**How**:

```ts
// Module-local queue serializing the full opener pipeline.
// Process-boundary assumption: same as openingTitles — single Bridge Node
// process today. Multi-process Bridge would need a file lock or named pipe.
let openQueue: Promise<void> = Promise.resolve();

const DEDUP_OSASCRIPT_TIMEOUT_MS = 5_000;
const TMUX_KILL_TIMEOUT_MS       = 3_000;
const TMUX_NEW_SESSION_TIMEOUT_MS = 5_000;
const TMUX_SELECT_WINDOW_TIMEOUT_MS = 3_000;
const SELECT_WINDOW_RETRIES = 10;
const SELECT_WINDOW_BACKOFF_MS = 500;
const OPEN_OSASCRIPT_TIMEOUT_MS  = 5_000;
const VERIFY_DELAY_MS            = 1_500;
const VERIFY_OSASCRIPT_TIMEOUT_MS = 5_000;

export function openTmuxViewer(opts: TmuxViewerOpts): void {
  // ... existing path-resolution + customTitle + same-title guard ...
  // ... existing openingTitles.add(customTitle) ...

  openQueue = openQueue
    .catch(() => { /* prior failure must NOT block subsequent runners */ })
    .then(() => doOpen(opts, customTitle))
    .catch((err: unknown) => {
      const msg = err instanceof Error ? err.message : String(err);
      console.warn(`[tmux-viewer] opener finished with error: ${msg}`);
    })
    .finally(() => {
      // Always release the same-title guard regardless of how doOpen ended
      // (success / dedup-hit / select-window abort / per-step timeout / error).
      openingTitles.delete(customTitle);
    });
}

async function doOpen(opts: TmuxViewerOpts, customTitle: string): Promise<void> {
  // 1. dedup osascript (per-step timeout via execFile { timeout })
  const exists = await runDedup(customTitle); // 5s timeout inside
  if (exists) {
    console.log(`[tmux-viewer] viewer already open for ${customTitle}, skip`);
    return;
  }

  // 2. cancellation guard
  if (cancelledExecutions.has(opts.executionId)) {
    console.log(`[tmux-viewer] opener cancelled for ${opts.executionId}, skip spawn`);
    return;
  }

  // 3. tmux setup (sync) with stderr captured + per-call timeouts
  setupViewerSession(opts);                       // kill-session 3s, new-session 5s
  const windowReady = await selectViewerWindow(opts); // 10×(3s timeout + 500ms delay)
  if (!windowReady) {
    console.warn(
      `[tmux-viewer] select-window failed (${SELECT_WINDOW_RETRIES} attempts) for ` +
      `viewer-${opts.executionId}:${opts.windowId}; aborting`,
    );
    killViewerSessionBestEffort(opts.executionId);
    return;
  }

  // 4. final open osascript (per-step timeout)
  await runOpen(opts, customTitle); // 5s timeout inside

  // 5. Verification — IN-QUEUE log-only (Codex R2 critical #1).
  // Scheduling the verify check INSIDE the queue ensures no Terminal Apple
  // Event runs while the next opener is dedup'ing or do-script'ing.
  // We delay 1500ms BEFORE running the verify so Terminal has time to
  // realize the just-fired do-script. `await delay` keeps it inside the queue.
  await delay(VERIFY_DELAY_MS);
  await runVerifyLog(customTitle); // 5s timeout, log-only no-throw
}
```

**Note on verification placement** (Codex R2 critical #1): Verification is now `await`-ed INSIDE `doOpen`, after the 1500ms delay. The next queued opener will not begin its dedup until verification has completed (or hit its own 5s timeout). This eliminates the concurrent-Apple-Event window for verify.

**Note on cancellation** (Codex R2 critical #2): No `Promise.race` whole-opener timeout. Each step's timeout is enforced by Node's child-process timeout option (real cancellation: SIGTERM on the child). Future enhancement could add an `AbortController`-style flag for cooperative cancellation across awaits, but the initial fix relies on per-step timeouts as the durability gate.

**Promise-style wrappers** (Codex R1 non-blocking suggestion):

```ts
function execFilePromise(cmd: string, args: string[], timeoutMs: number): Promise<{stdout: string}> {
  return new Promise((resolve, reject) => {
    execFile(cmd, args, { timeout: timeoutMs }, (err, stdout) => {
      if (err) reject(err);
      else resolve({ stdout });
    });
  });
}

function delay(ms: number): Promise<void> {
  return new Promise((r) => setTimeout(r, ms));
}
```

`select-window` retry loop uses `await delay(500)` instead of shell-out `sleep` (Codex R1 non-blocking suggestion).

**Boundary clarification**: 3 spawns of ~3-4s each (typical: 1s open + 1.5s verify delay + 0.5s verify check) = ~9-12s total under the queue. Acceptable since:
- Annie typically spawns 1-3 Runners at a time.
- Per-step timeouts bound each external operation (`execFile { timeout }` / `execFileSync { timeout }` issue real SIGTERM); cumulative worst case ≤60s per opener (see step-budget breakdown above).
- Failure of one opener does NOT block subsequent (queue's `.catch()` swallows).

### 4.2 Tighten `select-window` failure logging + raise budget

- **Capture stderr** from sync tmux calls: use `execFileSync(cmd, args, { encoding: "utf-8" })` (drops `stdio: "ignore"`) and read `(err as { stderr?: string }).stderr` from `ExecFileSyncException` in catch.
- **Raise retries** from 5 to 10 (5s ceiling instead of 2.5s), keeping 500ms backoff via `await delay(500)`.
- **Log noise discipline** (Codex R1 non-blocking): single info log on the FIRST retry only (so transient propagation isn't chatty); detailed warn log on final abort with last stderr text + attempt count.

### 4.3 Capture stderr on `new-session -t` failure

Replace `stdio: "ignore"` for the `new-session -t` call with `{ encoding: "utf-8" }`. In catch, read `(err as ExecFileSyncException).stderr` (string when encoding set). Log includes stderr text so we can distinguish "duplicate session" / "no current target" / "session not found" / etc.

### 4.4 Verify Terminal tab — IN-QUEUE LOG ONLY (Codex R1 critical #2 + R2 critical #1)

Verification runs INSIDE the same opener queue (not as a free-standing setTimeout) — see §4.1 step 5:

```ts
// inside doOpen():
await delay(VERIFY_DELAY_MS);     // 1500ms
await runVerifyLog(customTitle);  // 5s timeout, never throws
```

`runVerifyLog`:
```ts
async function runVerifyLog(customTitle: string): Promise<void> {
  try {
    const exists = await runTabExistsCheck(customTitle, VERIFY_OSASCRIPT_TIMEOUT_MS);
    if (!exists) {
      console.warn(
        `[tmux-viewer] tab not found ${VERIFY_DELAY_MS}ms after spawn — possible Terminal.app drop (title=${customTitle})`,
      );
    }
  } catch (err) {
    // Verification is diagnostic-only; never fail the opener.
    const msg = err instanceof Error ? err.message : String(err);
    console.warn(`[tmux-viewer] verify check error (non-fatal): ${msg}`);
  }
}
```

**Properties**:
- **In-queue**: subsequent opener does not start its dedup until this `await runVerifyLog` settles (eliminates concurrent Apple Events).
- **Log-only, no auto-retry**: avoids double-tab risk.
- **Bounded**: 1500ms delay + ≤5s osascript timeout = ≤6.5s tail per opener.
- **Diagnostic only**: even if verify fails, the opener is considered done.

describe("openTmuxViewer concurrent serialization (FLY-128)", () => {
  // Use vi.useFakeTimers() and manual osascript callback resolution.

  it("queues opener pipelines so dedup#2 does not start until open#1 settles", async () => {
    // Capture osascript callbacks per call so we can resolve them manually.
    const dedupCbs: Array<(err: Error|null, stdout?: string) => void> = [];
    const openCbs:  Array<(err: Error|null, stdout?: string) => void> = [];

    mockExecFile.mockImplementation((cmd, args, _opts, cb) => {
      const script = args[1];
      if (/return "exists"|return "open"/.test(script) && !/do script/.test(script)) {
        dedupCbs.push(cb!);
      } else if (/do script/.test(script)) {
        openCbs.push(cb!);
      }
    });

    // Fire 3 openers in same tick
    openTmuxViewer({...exec1});
    openTmuxViewer({...exec2});
    openTmuxViewer({...exec3});
    await flushMicrotasks();

    // Only Runner 1's dedup should have started
    expect(dedupCbs).toHaveLength(1);
    expect(openCbs).toHaveLength(0);

    // Resolve Runner 1's dedup as "open" (proceed to actuallyOpen)
    dedupCbs[0](null, "open\n");

    expect(dedupCbs).toHaveLength(1);

    await flushMicrotasks();

    dedupCbs[0](null, "open\n");
    await flushMicrotasks();

      (c) => c[0] === "osascript" && /do script/.test(c[1][1] as string),

  });

  it("queue continues after a per-step timeout/error in opener#1", async () => {

    openTmuxViewer({...exec2});

    await flushMicrotasks();

    await flushMicrotasks();

    vi.advanceTimersByTime(1500);

| Serialization slows down high-volume spawn (10+ concurrent) | Low (Annie typically spawns 1-3 at a time) | Per-step timeouts bound each opener (typical ≤4s incl verify, worst ≤60s); 10 spawns typical = 10×~4s = ~40s |
| One stuck opener (e.g. blocked Apple Event) blocks all subsequent → worse than current intermittent miss | **HIGH if no timeout** | **§4.1 per-step `execFile` / `execFileSync` `timeout` option (real SIGTERM cancellation) + queue `.catch()` to keep going** (Codex R1 critical #1 + R2 critical #2) |
| `openingTitles` Set leaks if `finally` block missing on a path | Medium | Single top-level `.finally()` after `.catch()` ensures cleanup on ALL paths (Codex R1 risk) |
| Verify-after-spawn race with title assignment OR with next opener's dedup | Medium | Verify is enqueued INSIDE doOpen (1500ms delay + 5s osascript timeout); next opener waits (Codex R2 critical #1) |
| Tests order-flaky from real timers | Medium | Use `vi.useFakeTimers()` + manual osascript callback resolution; advanceTimersByTime |
| Stderr capture breaks existing output formatting | Low | Only ADD logging; existing console.log/warn signatures unchanged |
| Per-process queue insufficient if Bridge becomes multi-process | Low (current arch single-process) | Document inline alongside existing `openingTitles` boundary comment (Codex R1 non-blocking) |
| `Promise.race` opener-level timeout cannot cancel in-flight execFile, allowing zombie touch of Terminal/tmux after queue advances | **HIGH if used** | **NOT used.** Only per-step `timeout` options (real SIGTERM). Documented in §4.1 (Codex R2 critical #2) |
| `execFileSync` blocks Bridge event loop during sync tmux ops | Low (each call ≤5s timeout) | Each sync call has bounded `timeout` option; aggregated worst case bounded |

## 9. Resolved Questions (was Open Questions in v1)

1. **Whole-opener timeout vs per-step**: Per-step bounded timeouts only — `execFile` and `execFileSync` accept a `timeout` option which actually cancels the child (SIGTERM); `Promise.race` cannot. Worst-case queue hold per opener ≤60s (5s dedup + 3s kill-session + 5s new-session + 35s select-window + 5s open + 6.5s verify tail), typical ≤4s. (Codex R1 critical #1 + R2 critical #2)
2. **Verify-after-spawn retry**: NO, log-only at 1500ms post-spawn. (Codex R1 critical #2)
3. **Unit test serialization assertion**: Manual osascript callback resolution + observe order across 3 calls. (Codex R1 critical #3)
4. **Queue scope**: Full opener pipeline including dedup, tmux setup, final open, AND verify. (Codex R1 critical #4 + R2 critical #1)
5. **Process-boundary**: Document inline; multi-process is future work, current single-Bridge is sufficient.
6. **Cancellation of in-flight opener**: Not in scope for initial fix. Per-step timeouts give bounded recovery; `AbortController`-style cooperative cancellation can be added later if real production observations show one stuck opener blocking subsequent in unexpected ways.
