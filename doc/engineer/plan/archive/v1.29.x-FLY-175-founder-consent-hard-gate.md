**Version**: v1.29.x (target patch tier; coordinate with Track 1 v1.29.1)
**Issue**: FLY-175
**Date**: 2026-05-28 (Round 3 — Codex Round 1+2 fixes integrated; Codex Round 3 APPROVED with implementation polish)
**Source**: PR #204 (Track 1 rule), GEO-380 governance incident
**Status**: codex-approved (R3) — ready for `git mv` to `plan/new/`

## 1. Problem & motivation

Track 1 (PR #204, commit `3e94936`) ships a **prompt-side** founder-only
authority rule for two reserved action categories (merge to `main` and
ending a Runner's life). The rule is **transitional** — Lead's judgment
is collected as evidence in the chat thread but not act-acted-on for
these specific irreversible operations during the v1.29.x calibration
window.

Track 1 alone has two structural weaknesses:

1. **No server-side enforcement**. A Lead model that drifts on the rule
   (or hallucinates that the founder approved) can still invoke any of
   the reserved paths and Bridge will execute. The rule is the only
   enforcement layer.
2. **No calibration corpus**. The transitional framing of Track 1
   promises future autonomy as Lead judgment proves out, but there is no
   data structure that records the founder's actual allow / deny /
   override pattern over time.

### 1.1 Production "approve" path is NOT `/api/actions/approve`

A second look at production behavior (Codex Round 1 caught this)
confirms an important detail: in shipping production, Lead resolves the
`approve_to_ship` gate **directly via `flywheel-comm respond`**, not via
`POST /api/actions/approve`. The QA suite documents this explicitly
(`packages/qa-framework/suites/fly-60-hard-gate.md:94-115`):

> Runner blocks at `approve_to_ship` gate. Lead's correct response is
> `flywheel-comm respond --db <commdb> --lead <id> <qid> "<reply>"`.
> Runner picks up the response via `flywheel-comm check` and proceeds
> with `:cool:` flow merge. No `/api/actions/approve` call happens in
> the normal production ship path.

The Bridge `/api/actions/approve` endpoint (`approveExecution` in
`actions.ts:152`) exists and also resolves the gate (via `db.insertResponse`
at `actions.ts:290`), but it's a secondary path. **Gating only the
Bridge HTTP endpoint leaves the production ship pathway open**. Track 2
must close BOTH paths or it's not a hard gate at all.

### 1.2 What Track 2 does

A new Bridge component `FounderConsentEvaluator` is the single point of
enforcement. It is reached from two complementary places:

- **HTTP middleware** on every reserved REST endpoint in `plugin.ts`
  (the 14-endpoint set in §4.3 below). Catches Bridge-routed calls.
- **`flywheel-comm respond` instrumentation** for
  `checkpoint=approve_to_ship` (and other founder-authorized gates).
  The CLI is patched so this checkpoint type routes the response
  through a new Bridge endpoint
  `POST /api/founder-consent/runner-gate-response`, which calls the
  evaluator before writing the CommDB row. Direct CommDB writes from
  outside Bridge become a Track 1 rule violation (already enforced by
  the catch-all clause "any other path that resolves the
  `approve_to_ship` gate"); see §13 for the migration story.

Every evaluation — allow, deny, fail-closed, bypass — writes one row to
the `founder_consent_audit` SQLite table. That table is **the
calibration corpus** for Track 3 auto-relaxation, not just a debug log.

## 2. Goals

- **Server-side enforcement** of the Track 1 reserved-action contract,
  closing both the Bridge HTTP path AND the `flywheel-comm respond`
  production approve path.
- **Audit table as corpus**, not just debug log. Schema designed for
  Track 3 to compute per-(action, project, lead_id, label-set)
  agreement rates and drive threshold relaxation.
- **Knob-driven relaxation path**. The evaluator's behavior is fully
  parameterized; the Track 1 roadmap (v1.29.x strict → v1.3x
  per-action / per-issue label / per-Lead trust tier → v1.4x+
  context-aware) is implementable by turning knobs.
- **Fail-closed by default** during the calibration window. Default
  per-action; can be flipped per action type once corpus shows the
  evaluator is reliable.
- **Three-mode operation** via `decisionMode`: `off` (Track 2 disabled),
  `audit_only` (evaluate + write audit but always allow; Phase 0 shadow
  mode), `enforce` (evaluate + write audit + 403 on deny). Default
  `off` so a Bridge boot without explicit opt-in retains pre-Track-2
  behavior byte-for-byte.
- **Zero new periodic timer**. Evaluation is request-driven only.

## 3. Non-goals

- **Auto-calibration / Track 3**. This plan stops at "audit table is
  populated and queryable". The actual ML / heuristic loop that adjusts
  threshold per (action_type, project, Lead) lives in a separate
  future track.
- **Replacing the prompt rule**. Track 1 stays. Track 2 is a backstop
  and a corpus generator.
- **Other gate types**. Track 2 instruments `approve_to_ship`
  specifically as a `flywheel-comm respond` route. Other checkpoints
  (`brainstorm`, project-specific gates) continue to use the existing
  CLI path unchanged. They can be added to the wrapper later.
- **Out-of-band authorization channels**. MVP reads only the issue's
  chat thread. Email / DM / voice / Linear comment / Discord reactions
  as authorization sources are deferred.
- **Multi-founder**. Project assumes one founder during the calibration
  window.
- **Cross-issue batch authorization**. "approve A B C" in one message is
  deferred.
- **Moving the consent check into CommDB itself**. CommDB writes are
  per-process (`flywheel-comm` is a CLI loaded into Runner / Lead /
  Bridge processes). Embedding the check inside CommDB would require
  every process to have an LLM client. Track 2 keeps the check in
  Bridge and patches the CLI to route through Bridge for the gates we
  care about; this preserves CommDB as a transport-only layer.

### 3.1 Residual threat boundary (Codex R2 LOW-8)

Track 2 hard-gates the **sanctioned action paths**: Bridge's REST
endpoints (Surface A) and the patched `flywheel-comm respond` CLI
(Surface B). It does **NOT** protect against an adversary who already
has shell access to the operator machine and can:

- Directly `sqlite3 ~/.flywheel/comm/<project>/comm.db "INSERT INTO
  responses ..."` bypassing both surfaces.
- Run `gh pr merge` against the GitHub API with the operator's PAT.
- Modify the Lead's prompt files on disk.
- Set `FLYWHEEL_COMM_BYPASS_BRIDGE=1` (the emergency env in §11.2).

Mitigations for these adversaries are **out of scope for FLY-175**
and live in different layers:

- OS-level: file permissions on `~/.flywheel/`, separate UIDs per
  Runner, restricted-shell sandbox.
- GitHub-level: branch protection requiring CODEOWNERS approval or
  signed commits.
- Operator hygiene: GitHub PAT rotation, audit-log on the OS shell.

Track 2's threat model is **prompt-drifted Lead processes**, not
malicious shell actors. The Track 1 rule plus Track 2 enforcement
together prevent a Lead model from talking itself into an
unauthorized approve/close; they do not prevent a human with root on
the box from doing the same with `vim` and `sqlite3`. The Phase 0/1
exit criteria (coverage 100% via the audit×CommDB join) will detect
such bypasses after the fact, which is the appropriate level of
defense for this threat boundary.

### 4.2 Data flow (HTTP middleware path, e.g. close-tmux)

```mermaid
sequenceDiagram
    participant L as Lead bot
    participant M as founderConsent<br/>Middleware
    participant E as FounderConsent<br/>Evaluator
    participant D as Discord REST<br/>(bot token)
    participant H as Haiku (via<br/>AnthropicLLMClient)
    participant A as audit.db
    participant B as Bridge handler<br/>(close-tmux)

    L->>M: POST /api/sessions/:execId/close-tmux {leadId}
    M->>M: Path in reserved table? Yes (close_tmux)
    M->>M: Resolve session → issueId, projectName, role, labels, PR
    M->>E: evaluate({action:"close_tmux", issueId, execId, role, leadId})
    E->>E: Cache key = sha((issueId, execId, role, action))<br/>TTL 60s; check
    Note over E: Miss → fetch + LLM
    E->>D: GET /channels/{threadId}/messages?limit=50
    D-->>E: [{author, content, ts, message_id}, …]
    E->>E: Annotate roles (founder / lead / runner / other)<br/>by author_id; full window in prompt;<br/>evidence MUST be a founder message
    E->>H: messages.create(model=haiku-4-5, sys, user)
    H-->>E: {allowed, confidence, evidence_msg_id, reason}
    E->>E: Cache (60s)
    E->>A: INSERT audit row (decision, llm_raw, context...)
    E-->>M: Decision

    alt allow && conf ≥ threshold[action]
        M->>B: next() — existing handler runs
        B-->>L: 200 OK
    else deny
        M-->>L: 403 {code:"FOUNDER_CONSENT_REQUIRED",<br/>reason, evidence_excerpt}
        L->>L: post chat thread asking founder
    end
```

## 6. SQLite schema — `founder_consent_audit`

Lives in a **separate** SQLite file (`~/.flywheel/audit.db`) so the
Track 3 calibration tool can export / replicate / vacuum it without
touching state. Schema designed for both immediate debug (query last N
decisions per issue) AND long-term Track 3 training (group by
action_type / project / lead_id / labels / outcome).

```sql
CREATE TABLE IF NOT EXISTS founder_consent_audit (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL,                    -- ISO 8601 timestamp of decision

  evaluator_version TEXT NOT NULL,     -- e.g. "v1.29.2-prompt-rev-3"
                                       -- bump on any prompt / threshold change
  prompt_content_hash TEXT,            -- SHA-256 of the assembled prompt
                                       -- (system + few-shot + input)
                                       -- — sanity check for missed bumps

  decision_mode TEXT NOT NULL,         -- off | audit_only | enforce
                                       -- (records the *operating mode*,
                                       --  not the per-call branch)

  action TEXT NOT NULL,                -- approve | close_tmux | close_runner
                                       -- | terminate | reject | defer
                                       -- | shelve | retry | approve_to_ship_gate

  -- Issue / session / project context (denormalized for query convenience
  -- AND because sessions mutate after the decision)
  issue_id TEXT NOT NULL,              -- Linear UUID
  issue_identifier TEXT,               -- FLY-XXX
  project_name TEXT,                   -- e.g. "Flywheel", "GeoForge3D"
  execution_id TEXT,                   -- nullable for dashboard-only paths
  session_role TEXT,                   -- main | qa | … (FLY-59)
  session_status_at_decision TEXT,     -- session status at the moment
                                       -- of decision (mutates later)
  issue_labels_json TEXT,              -- JSON array of label names
                                       -- (snapshot at decision time)
  pr_number INTEGER,                   -- when knowable
  pr_head_sha TEXT,                    -- when knowable (used as cache key salt
                                       -- for approve — see §9.6)

  -- Caller context
  actor_source TEXT NOT NULL,          -- http_middleware | gate_response_wrapper
                                       -- | dashboard | unknown
  lead_id TEXT,                        -- nullable: dashboard /actions/* may
                                       -- omit; we record what we know
  requested_by TEXT,                   -- caller identity if not lead_id
                                       -- (e.g. "dashboard-anonymous")
  request_reason TEXT,                 -- optional reason / context the
                                       -- caller passed (Lead may include
                                       -- "founder said 'approve FLY-X' at 14:32")

  -- Decision
  decision TEXT NOT NULL,              -- allow | deny | fail_closed | bypass
  decision_source TEXT NOT NULL,       -- llm | cache | bypass_env
                                       -- | bypass_label | fail_mode
  confidence REAL,                     -- LLM-reported 0.0..1.0
                                       -- null for cache/bypass/fail
  threshold_applied REAL,              -- which threshold was used
                                       -- (depends on action + config)

  -- Evidence
  evidence_message_id TEXT,            -- Discord message_id (null if no
                                       -- evidence)
  evidence_excerpt TEXT,               -- ≤200 chars quote of the cited
                                       -- founder message
  llm_reason TEXT,                     -- short LLM explanation
  llm_raw_response TEXT,               -- full JSON LLM returned (debug)

  -- Telemetry
  prompt_token_count INTEGER,
  completion_token_count INTEGER,
  llm_latency_ms INTEGER,
  fetched_msg_count INTEGER,           -- total fetched (any author)
  founder_msg_count INTEGER,           -- subset that were the founder's
  cache_hit_ts TEXT,                   -- if decision_source = cache,
                                       -- the prior decision's ts

  -- Codex R2 MEDIUM-6: ground-truth / coverage / context-replay
  -- columns. The corpus must capture enough mutable context that
  -- Track 3 can replay decisions without re-querying Discord/Linear
  -- (those services lose history and rate-limit).
  thread_id TEXT,                      -- Discord thread message was in
  discord_channel_id TEXT,             -- parent channel of the thread
  founder_user_id_snapshot TEXT,       -- snapshot of FOUNDER_USER_ID
                                       -- at decision time (env may change)
  message_window_oldest_ts TEXT,       -- ts of oldest msg fed to LLM
  message_window_newest_ts TEXT,       -- ts of newest msg fed to LLM
```

### Schema rationale (key changes from Round 1)

- **`decision_mode` column**: distinguishes Phase 0 (audit-only)
  decisions from Phase 1 (enforce) decisions. Track 3 must filter on
  this when calibrating (audit-only rows reflect the evaluator's
  judgment but not actual enforcement outcomes).
- **`project_name`, `session_role`, `issue_labels_json`, `pr_number`,
  `pr_head_sha`, `session_status_at_decision`**: denormalized
  snapshots. Sessions mutate after the decision (status changes,
  labels get added, branches rebase); the corpus needs the state at
  decision time, not at query time.
- **`actor_source` + nullable `lead_id` + `requested_by`**: today's
  `/actions/*` dashboard alias submits `{execution_id}` only with no
  `leadId` (`packages/teamlead/src/bridge/dashboard-html.ts:205-208`).
  `lead_id NOT NULL` would have broken dashboard calls. New schema
  records who we know about (dashboard caller → `actor_source =
  "dashboard"`, `lead_id` null, `requested_by` populated).
- **`prompt_content_hash`**: SHA-256 of the assembled prompt at
  decision time. Belt-and-suspenders for `evaluator_version` — if a
  prompt change ships without a version bump, the hash diverges and a
  Track 3 sanity-check job flags it.
- **`request_reason`**: optional free-text the caller passed.
  Encourages Lead to cite the founder's message ID / quote inline,
  which gives the LLM a tiebreaker and gives Track 3 a structured
  signal.
- **Track 3 hook columns** (`founder_subsequent_ack*`): populated by
  a future job that watches the chat thread after each `deny`
  decision — out of scope here, but columns reserved now so the
  Track 3 plan ships without schema migration.

## 7. Haiku prompt design

### 7.1 Model + client

- **Model**: `claude-haiku-4-5-20251001`. Matches what
  `packages/teamlead/src/bridge/run-infra.ts:178` already uses
  (`new AnthropicLLMClient()` defaults). Avoids adding a new SDK dep
  to `packages/teamlead/package.json` — we go through
  `flywheel-claude-runner`'s exported `AnthropicLLMClient`.
- **Fallback** when Haiku stalls: bump to Sonnet via
  `FLYWHEEL_FOUNDER_CONSENT_LLM_MODEL` env. Out of scope for default
  config.
- **No Opus**. Latency cost not justified for a binary classification.

### 7.2 Message-window strategy (Round 1 fix)

Previously the plan filtered the prompt to only founder messages —
this loses the context of what the Lead asked and what the Runner
posted. New strategy:

1. Fetch the latest N=50 messages from the chat thread via Discord
   REST (with bot token).
2. **Annotate every message with a role**: `founder` (matches
   `FOUNDER_USER_ID` env), `lead` (matches any of the project's
   Lead bot IDs from BridgeConfig), `runner` (heuristic: posts that
   contain runner-style markers like `[Runner]` prefix or are author
   = a known runner bot — Bridge already tracks this), `other` (human
   teammates), `bot` (catch-all).
3. Pass the full annotated window to Haiku. Instruct in the system
   prompt that **only `founder` messages may serve as evidence
   (`evidence_message_id` MUST point at a `founder` role message)**,
   but Lead/Runner messages are context Haiku may use to disambiguate
   intent ("OK" after Lead's "ship FLY-X?" is approval; "OK" after
   Runner's "PR is up" is acknowledgment).

### 7.3 System prompt skeleton

```
You are FounderConsentEvaluator, a Bridge component that decides
whether a Lead's request to execute a high-risk action is authorized
by the founder for THIS specific issue and session.

INPUT
- action: one of approve | close_tmux | close_runner | terminate |
  reject | defer | shelve | retry | approve_to_ship_gate
- issue_identifier: e.g. "FLY-175"
- execution_id and session_role: identify the specific Runner session
- now_ts: current timestamp (ISO 8601)
- window_hours: time window for valid authorization (default 24)
- messages: list of recent chat thread messages, each annotated with
  role ∈ {founder, lead, runner, other, bot}, most recent first

DECISION RULES
Authorization MUST be:
1. EXPLICIT — not silence, not a status question, not a positive
   acknowledgment ("nice", "good", "看到了") without a directive.
2. ISSUE-BOUND — tied to THIS issue_identifier (mentioned by ID OR
   posted in this issue's thread, which all input messages already
   are). Approval of a different issue does NOT transfer.
3. RECENT — within the window_hours.
4. ACTION-MATCHED — "approve" / "ship" / "merge" authorize the
   approve/approve_to_ship_gate actions; "stop"/"kill"/"关掉"
   authorize close/terminate-class actions; retry needs explicit
   "retry"/"重试"/"重跑".
5. SESSION-SCOPED — if the founder authorized a different execution
   of the same issue earlier, that does NOT transfer to a new
   execution. Use execution_id to verify.
6. SOURCED FROM FOUNDER — evidence_message_id MUST be the id of a
   message whose role == "founder". Lead/Runner messages are context
   only, never evidence.

Reject as non-authorization (allowed=false):
- No founder messages in window
- Status questions from founder ("QA 通过了吗", "怎么样了")
- Acknowledgments without directive ("nice", "noted", "看到了", "good")
- Lead's reasoning quoted/echoed by founder without an action verb
- Stale approval (>window_hours old)
- Cross-issue approval
- Founder explicitly delegating back to Lead's judgment ("你判断好就
  OK") — this is meta-delegation, not consent for THIS action
- Founder explicitly waiting on another gate ("等 codex review")

OUTPUT (strict JSON only, no prose):
{
  "allowed": boolean,
  "confidence": number,  // 0.0..1.0, calibrated certainty
  "evidence_message_id": string | null,
  "evidence_excerpt": string | null,  // ≤200 chars verbatim quote
  "reason": string  // ≤140 chars, same language as the founder
}

CALIBRATION GUIDANCE
- confidence ≥ 0.90: founder used a clear action-specific verb
  recently, no ambiguity, evidence is unambiguous
- 0.75 ≤ confidence < 0.90: clear intent but phrasing indirect or
  context-dependent (e.g. "OK" right after Lead's explicit "ship?")
- 0.50 ≤ confidence < 0.75: probable intent but a careful human
  reviewer would re-ask. Lean DENY in this band.
- < 0.50: insufficient evidence. Always DENY.
```

### 7.4 Few-shot examples (≥ 12 total)

- ALLOW: explicit `approve FLY-X` immediately preceding the action
- ALLOW: `ship 它` / `可以 merge` / `上线` / `拍`
- ALLOW: `停 FLY-X` / `关掉 GEO-X` / `terminate it` for stop actions
- ALLOW: 18h-old `approve FLY-X` within window
- ALLOW: founder "OK" RIGHT AFTER Lead's "ship FLY-X?" (context
  disambiguates — confidence ~0.80)
- DENY: silence (zero founder messages)
- DENY: `QA 通过了吗` (status question)
- DENY: `看到了` (acknowledgment after Runner's PR-created update)
- DENY: founder "OK" after Runner's status update with no prior Lead
  ask (context disambiguates — different intent than above)
- DENY: `nice work` followed by current action = `terminate`
- DENY: `approve FLY-100` when current action is on FLY-101
- DENY: 36h-old `approve FLY-X` (stale)
- DENY: `Lead 你判断好就 OK` (meta-delegation)
- DENY: `等 codex review` (founder explicitly waiting)
- DENY: cross-execution: founder authorized exec=A; request is exec=B
  on same issue

### 7.5 Versioning

Every prompt revision bumps `evaluator_version`. Schema also captures
`prompt_content_hash`; a Track 3 sanity job flags rows whose hash
doesn't match the prompt that the version string implies.

### 8.1 Config parsing tolerance

Critical (Round 1 fix): when `FLYWHEEL_FOUNDER_CONSENT_DECISION_MODE
=== "off"` (the default), the parser MUST NOT require
`FLYWHEEL_FOUNDER_USER_ID`, `FLYWHEEL_FOUNDER_CONSENT_LLM_MODEL`,
etc. The evaluator is not constructed at all in that case — Bridge
boots in pre-Track-2 behavior. Only when `DECISION_MODE !== "off"`
does the parser validate required fields and fail-fast on missing.

This guarantees:
- Existing dev / CI / prod environments without Track 2 env vars
  continue to boot.
- Adding `DECISION_MODE=audit_only` for Phase 0 deploy is the *only*
  required change to start collecting corpus data.

### 8.1.1 Env naming canonical form and precedence (Codex R2 LOW-7)

**Canonical env name throughout this plan and code**:
`FLYWHEEL_FOUNDER_CONSENT_DECISION_MODE`. The plan text occasionally
shortens this to `DECISION_MODE` in inline references for readability;
**that shorthand is plan-prose only — code reads the full env name**.

**Legacy alias precedence** (when both are set):

1. `FLYWHEEL_FOUNDER_CONSENT_DECISION_MODE` present → it wins
   regardless of `FLYWHEEL_FOUNDER_CONSENT_ENABLED`. Bridge boot logs
   a warning if `ENABLED` is also set ("legacy alias ignored").
2. `FLYWHEEL_FOUNDER_CONSENT_DECISION_MODE` absent +
   `FLYWHEEL_FOUNDER_CONSENT_ENABLED=true` → equivalent to
   `DECISION_MODE=enforce` (legacy semantics).
3. `FLYWHEEL_FOUNDER_CONSENT_DECISION_MODE` absent +
   `FLYWHEEL_FOUNDER_CONSENT_ENABLED=false` (or unset) → equivalent
   to `DECISION_MODE=off`.

Tests in `config.test.ts` cover all four conflict cases including
the precedence and the warning log.

### 8.2 Bypass label freshness

Two modes:
- `stored` (default): read `session.issue_labels` (snapshot at session
  start). Cheap; misses labels added after start.
- `linear_live`: fetch fresh from Linear API per evaluation. Catches
  late-added `auto-approve-eligible` labels but adds ~100ms latency
  and consumes Linear API quota.

Operators choose per-project based on workflow. Failure path for
`linear_live`: Linear API unreachable → log warning, fall back to
`stored`, audit row carries `decision_source=bypass_label_stored_fallback`
when applicable.

## 9. Fail modes

### 9.1 LLM unreachable / timeout

- Default: `fail_mode = closed` → deny with HTTP 503,
  `code: "FOUNDER_CONSENT_LLM_UNREACHABLE"`, reason explains LLM
  unreachable, suggests retry or operator bypass env.
- v1.3x: `fail_mode = open` allowable per action via
  `FAIL_MODE_PER_ACTION`. Irreversible actions (approve,
  approve_to_ship_gate, terminate) should stay `closed`.
- Audit row: `decision = fail_closed`, `decision_source = fail_mode`,
  `llm_raw_response = "TIMEOUT after Nms"` or equivalent.

### 9.2 Discord REST fetch fails

- Symmetric: deny with 503,
  `code: "FOUNDER_CONSENT_DISCORD_UNREACHABLE"`.
- Map Discord-specific errors: 401/403 → 503 to caller with audit
  noting "bot token misconfigured"; 404 → 503 with reason "thread
  not found"; 429 → 503 with reason "Discord rate limited, retry
  later"; 5xx → 503 with passthrough.
- Audit row records the exact upstream error class.

### 9.3 LLM malformed JSON

- One retry with stricter "JSON only" reinforcement.
- Second failure → fail-closed deny, audit row carries
  `llm_raw_response = "<full malformed output>"` so operator can spot
  a prompt regression.

### 9.4 Thread does not exist for issue

- Defensive: deny + 404-style reason
  `code: "FOUNDER_CONSENT_NO_THREAD"`. Lead is expected to engage
  the founder via the thread first (Track 1 R1 already requires
  posting to the thread).
- Audit row `fetched_msg_count = 0`.

### 9.5 LLM confidence in the gray zone (0.50–0.74)

- Treat as `deny`. Audit row records confidence and reason so the
  Lead can present a clearer ask to the founder.

### 9.6 Cache hit on a session-bound key (Codex R2 MEDIUM-4 fix)

- Cache key: `sha256(issueId || execId || sessionRole ||
  sessionStatusAtCall || action || prHeadShaIfApprove)`. TTL: 60s
  default. The `sessionStatusAtCall` salt prevents a decision made
  when the session was `running` from being reused after it
  transitioned to `awaiting_review` (the action semantics may
  differ).
- **For `approve` and `approve_to_ship_gate` specifically**: if
  `prHeadSha` is unknown (StateStore doesn't persist it today, plan
  §5.2 adds `pr_head_sha` to Session for this purpose; until then
  it may be `null` for older sessions), **the cache is bypassed
  entirely** (every call re-evaluates). Silently using a SHA-less
  cache key would let a force-push bypass detection. Audit row
  records `cache_hit_ts = null` and `decision_source = llm`.
- A cache hit returns the **same decision** as the prior call (not a
  new "cached_X" value). Audit row records:
  `decision = <original allow|deny>`, `decision_source = cache`,
  `cache_hit_ts = <prior decision ts>`.
- Race: if the founder posts authorization during the 60s cache
  window after a deny, the next call after eviction (or after
  proactive invalidation — see §9.7) picks it up. 60s lag is
  acceptable for non-approve actions; for approve the no-cache rule
  above means no lag.

### 9.7 Optional: proactive cache invalidation on founder message

(Open question — see §14.) If Bridge subscribes to Discord events
(it does, for other reasons), it can invalidate cache entries when a
new founder message arrives in a thread known to a session. v1.29.x
MVP relies on TTL only; the wiring is a v1.3x improvement.

### 9.8 Approve PR head SHA changes mid-decision

(Codex R3 LOW-4: aligned with §9.6 — no silent degradation.)

- Cache key for `approve` and `approve_to_ship_gate` includes
  `pr_head_sha` to prevent a stale approval from carrying across a
  force-push.
- If the action arrives without a known `pr_head_sha`, the
  middleware looks it up from StateStore (§5.2 adds the column). If
  still unknown after lookup, **the cache is bypassed entirely for
  this call** (no SHA-less fallback key — see §9.6). The LLM
  evaluation still runs against fresh founder messages. The audit
  row carries `pr_head_sha = null` so Track 3 can identify cases
  where SHA tracking is missing in StateStore and prioritize
  populating it.

## 10. Performance & cost

- **Per-decision LLM cost** (Haiku 4.5): ~$0.0001 / decision at
  current Anthropic pricing. Cost-negligible at expected volume
  (≤50 reserved-action calls / day).
- **Per-decision latency target** (revised from Round 1):
  - P50 ≤ 500ms (was 250ms — Round 1 caught the optimism)
  - P95 ≤ 1200ms
  - Hard timeout: 3000ms → fail-closed
  - Breakdown:
    - Discord REST `GET /channels/.../messages?limit=50`: ~150-400ms
      (single round trip; existing Bridge already maintains a Discord
      connection so DNS / TLS warm)
    - Haiku call: ~200-500ms
    - DB write (audit row): ~5-10ms (separate audit.db)
    - Middleware overhead / cache miss: ~5-10ms
- **Cache hit ratio**: estimated 30-50% (Lead retries within window
  after a deny → cache hit).
- **Discord rate limits**: ~50 calls/day is well under per-channel
  caps. Bot token already exists and authorizes the calls.
- **DB size**: ~2.5 KB / audit row (denormalized columns + LLM raw).
  ~50 rows/day × 365 = ~46 MB/year. Vacuum monthly.

## 11. Rollout — three phases

### Phase 0 — audit-only mode (v1.29.x, first 1-2 weeks after ship)

- `DECISION_MODE=audit_only`
- Behavior: middleware **evaluates** every reserved-endpoint call,
  writes audit row, but **always returns allow** to the existing
  handler. No 403s, no Lead behavior change.
- Goal: collect a real-traffic corpus + human-labeled review set.

**Exit criteria (falsifiable, Codex R2 MEDIUM-3 fix)**:

1. **Coverage = 100%**: every `approve_to_ship` response in any
   project's CommDB during the Phase 0 window has a matching
   `audit.db` row. Clean join (Codex R3 MEDIUM-1: audit table now
   carries `comm_question_id` as a first-class column, no LIKE on
   request_reason needed):
   ```sql
   -- Attach each project's comm.db, then run per-project:
   -- ATTACH '~/.flywheel/comm/<project>/comm.db' AS comm;
   -- ATTACH '~/.flywheel/audit.db' AS audit;
   SELECT r.question_id, r.checkpoint, r.ts
   FROM comm.responses r
   JOIN comm.questions q ON q.id = r.question_id
   WHERE q.checkpoint = 'approve_to_ship'
     AND r.ts BETWEEN $phase0_start AND $phase0_end
     AND NOT EXISTS (
       SELECT 1 FROM audit.founder_consent_audit a
       WHERE a.action = 'approve_to_ship_gate'
         AND a.comm_question_id = r.question_id
     );
   -- must return zero rows
   ```
   Any gap is a blocker — someone bypassed via env or the wrapper
   failed silently.
2. **Human-labeled review set**: a human (the founder, or someone
   reviewing alongside them) labels each Phase 0 audit row with
   `human_review_label ∈ {founder_authorized, not_authorized,
   unclear}` and `human_review_label_source = "phase0_manual"`. At
   least 30 rows labeled; ≥ 90% agreement between the evaluator's
   `decision` and `human_review_label` (where `decision = allow`
   should match `founder_authorized = true`, etc).
3. **No silent false negatives**: zero retroactive complaints from
   the founder ("I never approved that") about any action that was
   `decision = allow` in Phase 0 audit rows. Track 3 will operationalize
   `retroactive_complaint` capture; for Phase 0, the operator
   manually scans.
4. **Disagreement analysis**: every evaluator-vs-human disagreement
   is triaged into (a) prompt revision (bump `evaluator_version`),
   (b) threshold adjustment, or (c) accepted human judgment override
   (the evaluator was right but the founder accepted Lead's call
   anyway — informational only).

Phase 0 exits when all four criteria are met. If they're not after
2 weeks, extend Phase 0 — do not flip to Phase 1.

### Phase 1 — enforce mode (v1.29.y after Phase 0 passes)

- `DECISION_MODE=enforce`
- Behavior: middleware **enforces** — denies with 403 on deny or
  fail-closed.
- Watch metrics (queried from audit.db):
  - False-positive deny rate (Lead re-asked founder, founder said
    "yes I did approve") — target < 5%.
  - False-negative allow rate (founder later complained) — target
    ≈ 0%. Any incident triggers immediate threshold raise + retro.
- Kill switch: `DECISION_MODE=off` returns to pre-Track-2 behavior
  instantly. Should not be needed if Phase 0 passed.

### Phase 2 — calibrated relaxation (v1.3x onward)

- `THRESHOLD_PER_ACTION` populated based on corpus analysis.
- `auto-approve-eligible` Linear label honored as bypass.
- Audit queried weekly; low-risk action types graduate to lower
  thresholds.
- Eventually feeds into Track 3 auto-calibration (separate plan).

### 11.1 Coordination with Track 1 ship + Lead restart

Track 1 (PR #204) must be merged + Lead-restarted (claude-lead.sh
reads new base file on Lead startup) **before** Track 2 Phase 1
enforce mode. If Lead is still on pre-Track-1 prompts when Track 2
enforce-mode lands, the false-positive rate will spike (no prompt

`/etc/flywheel/lead-rules-version` or similar marker and warn loudly

### 11.2 flywheel-comm CLI rollout (Codex R2 HIGH-1 fix)

The CLI is fail-closed for `approve_to_ship` in Phase 1 — opt-in via
`--bridge-url` is insufficient because a drifted Lead could just skip
the flag. The CLI checks the gate at the SQLite level and refuses to
write directly when the gate is `approve_to_ship`.

**CLI behavior** (in `packages/flywheel-comm/src/commands/respond.ts`):

1. On every `respond` invocation, open the CommDB and look up the
   question by `questionId`. Read its `checkpoint` field. **The CLI
   never trusts a caller-supplied `--checkpoint` value** — it always
   reads from the DB.
2. If `checkpoint` is in `GATED_CHECKPOINTS = ["approve_to_ship"]`:
   - If `BRIDGE_URL` env (or `--bridge-url` flag) is set:
     POST to `${BRIDGE_URL}/api/founder-consent/runner-gate-response`
     with `Authorization: Bearer ${TEAMLEAD_API_TOKEN}` header (the
     same token the rest of `/api/*` already requires — see
     `plugin.ts:534` `tokenAuthMiddleware`). Body:
     `{questionId, leadId, answer, executionId, projectName}`. CLI
     reads `TEAMLEAD_API_TOKEN` from env; if missing, fail-closed
     with stderr `"flywheel-comm: TEAMLEAD_API_TOKEN required when
     routing approve_to_ship via Bridge. Set the env or use
     FLYWHEEL_COMM_BYPASS_BRIDGE=1 for emergency override."`. (Codex
     R3 MEDIUM-2: auth token explicit.)
     Wrapper handles auth + consent + DB write.
   - Else if `FLYWHEEL_COMM_BYPASS_BRIDGE=1` is set (emergency
     operator escape — see below): write directly to CommDB BUT also
     write an audit row to `audit.db` with `decision=bypass`,
     `decision_source=bypass_env_cli`, plus a loud stderr warning
     so the operator notices.
   - Else: **fail-closed** with stderr error
     `"flywheel-comm: refusing to resolve approve_to_ship gate
     directly. Set BRIDGE_URL or --bridge-url so the wrapper
     enforces founder consent. Emergency override:
     FLYWHEEL_COMM_BYPASS_BRIDGE=1."` and exit non-zero. No CommDB
     write happens.
3. For all other checkpoints (`brainstorm`, project-specific, etc.):
   legacy direct CommDB write unchanged.

The emergency env var exists for two cases:
- Local development / CI environments where Bridge isn't running.
- A genuine production Bridge outage where the operator decides to
  manually unblock a Runner. Loud audit + warning ensures this can't
  be silent.

The CLI knows how to write the bypass audit row because `audit.db`
path is well-known (`~/.flywheel/audit.db`, same path Bridge uses).
If `audit.db` is missing (Bridge never booted on this host), the CLI
creates it with the same schema (idempotent `CREATE TABLE IF NOT
EXISTS`).

**Rollout order**:

1. Ship Track 2 Bridge with `DECISION_MODE=off` (no behavior change;
   middleware is wired but evaluator not constructed).
2. Ship `flywheel-comm` patch with the fail-closed gate logic.
   **This is a breaking change for `approve_to_ship` callers** —
   they MUST set `BRIDGE_URL` or `--bridge-url`. Lead deployment in
   step 3 covers production; local-dev callers learn from the error
   message.
3. Update Lead deployment to export `BRIDGE_URL` so Lead's
   `flywheel-comm respond` invocations auto-route.
4. Flip Bridge `DECISION_MODE=audit_only` (Phase 0). Wrapper now
   evaluates + audits + always allows.
5. After Phase 0 exit criteria pass, flip to `enforce` (Phase 1).

Coverage check during Phase 0 / Phase 1: every approve_to_ship
response row in any CommDB MUST have a matching audit.db row (joined
by `questionId`). The Phase 0 exit criterion explicitly requires
this coverage = 100%. A gap means someone bypassed via env or the
wrapper failed silently — both blocking findings.

## Appendix C — `flywheel-comm respond` wrapper design (Codex R2 HIGH-2 fix)

Concrete shape of the new wrapper endpoint. **Bridge derives the
CommDB path server-side — caller-supplied paths are rejected to
prevent SQLite injection** (Codex Round 2 HIGH-2).

```typescript
// packages/teamlead/src/bridge/founder-consent/gate-response-router.ts
import { realpathSync } from "node:fs";
import path, { join, resolve } from "node:path";
import { homedir } from "node:os";

const COMMDB_ROOT = resolve(homedir(), ".flywheel", "comm");

router.post("/", async (req, res) => {
  // Required: questionId, leadId, answer
  // Required (one of): executionId OR projectName — for path derivation
  // FORBIDDEN: dbPath (caller-supplied) — security: prevents pointing
  //            Bridge at an arbitrary writable SQLite file
  const { questionId, leadId, answer, executionId, projectName } = req.body;
  if (!questionId || !leadId || answer === undefined) {
    return res.status(400).json({ error: "missing required fields" });
  }
  if (!executionId && !projectName) {
    return res.status(400).json({
      error: "must provide executionId or projectName for path derivation"
    });
  }
  if ("dbPath" in req.body) {
    return res.status(400).json({
      error: "dbPath is server-derived; do not pass it in the request"
    });
  }

  // 1. Derive canonical CommDB path server-side
  let resolvedProjectName: string;
  if (executionId) {
    const session = stateStore.getSession(executionId);
    if (!session) {
      return res.status(404).json({
        error: "session not found for executionId"
      });
    }
    resolvedProjectName = session.project_name;
  } else {
    // projectName provided directly; validate it's a configured project
    if (!projects.find((p) => p.projectName === projectName)) {
      return res.status(403).json({
        error: "unknown project"
      });
    }
    resolvedProjectName = projectName;
  }

  const candidatePath = join(COMMDB_ROOT, resolvedProjectName, "comm.db");
  let canonicalPath: string;
  try {
    canonicalPath = realpathSync(candidatePath);
  } catch {
    return res.status(404).json({
      error: `CommDB not found at ${candidatePath}`
    });
  }
  // Defense in depth: realpath MUST still be under COMMDB_ROOT
  // (catches symlink attacks where someone symlinked the comm.db
  // to /etc/something). Use path.relative + reject absolute /
  // parent-traversal results to avoid separator/case edge cases
  // (Codex R3 LOW-5).
  const rootReal = realpathSync(COMMDB_ROOT);
  const rel = path.relative(rootReal, canonicalPath);
  if (rel.startsWith("..") || path.isAbsolute(rel)) {
    return res.status(403).json({
      error: "CommDB path escapes the expected root"
    });
  }

  const db = new CommDB(canonicalPath, false);
  try {
    // 2. Look up the question; verify checkpoint is approve_to_ship
    const question = db.getQuestionById(questionId);
    if (!question) {
      return res.status(404).json({ error: "question not found" });
    }
    if (question.checkpoint !== "approve_to_ship") {
      return res.status(400).json({
        error: "wrapper only handles approve_to_ship; other gates use legacy direct CLI path"
      });
    }

    // 3. Resolve session from question's execution_id for evaluator context
    const session = stateStore.getSession(question.from_agent);
    if (!session) {
      return res.status(404).json({
        error: "session not found for question's from_agent"
      });
    }

    // 4. Evaluate consent
    const decision = await evaluator.evaluate({
      action: "approve_to_ship_gate",
      issueId: session.issue_id,
      issueIdentifier: session.issue_identifier,
      executionId: session.execution_id,
      sessionRole: session.session_role,
      sessionStatusAtCall: session.status,
      projectName: session.project_name,
      issueLabels: session.issue_labels,
      prNumber: session.pr_number,
      prHeadSha: session.pr_head_sha,
      leadId,
      actorSource: "gate_response_wrapper",
      requestReason: req.body.reason,
    });

    if (decision.decision !== "allow" && decision.decision !== "bypass") {
      return res.status(403).json({
        code: "FOUNDER_CONSENT_REQUIRED",
        reason: decision.llm_reason,
        evidence: decision.evidence_excerpt,
        auditId: decision.auditId,
      });
    }

    // 5. Allow: write the response (same code path approveExecution uses)
    db.insertResponse(questionId, leadId, answer);
    res.json({ success: true, auditId: decision.auditId });
  } finally {
    db.close();
  }
});
```

The CLI patch in `packages/flywheel-comm/src/commands/respond.ts` is
described in §11.2. Critically: the CLI **opens the CommDB locally
first** to read the question's `checkpoint`, then decides whether to
route through Bridge. It never trusts a `--checkpoint` flag from the
caller. The wrapper POST body carries `{questionId, leadId, answer,
executionId}` — never `dbPath`.
