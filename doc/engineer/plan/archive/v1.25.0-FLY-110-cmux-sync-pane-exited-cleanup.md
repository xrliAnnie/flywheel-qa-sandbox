# Plan: cmux-sync pane-exited cleanup not firing — register `pane-died` hook

**Version**: v1.25.0
**Issue**: FLY-110
**Date**: 2026-05-03
**Source**: Linear FLY-110 issue body (root cause assumptions); revised after Codex Round 1 + Round 2 design reviews; further amended during implementation after isolated tmux integration testing revealed an additional tmux 3.5a hook-scope bug (see Implementation Discoveries section).
**Status**: codex-approved → in progress

## Problem

`scripts/flywheel-cmux-sync.sh --watch` 自 PR #147 起进入 event-signaled polling 模式。注册的 tmux hook 路径 (`pane-exited` → `EVENT_FILE` → `mark_for_cleanup` → 30s delay → `cleanup_workspace_for`) 在生产环境**从未触发过一次**。所有 cmux 侧栏 `~` 残留条目最终都靠 5 分钟 `cleanup_stale_conservative` polling 兜底清理 — 这导致：

1. **侧栏长期保留死 entry** — Annie 截图反馈，体感非常差
2. **Conservative polling 在 watch loop 里每 60s 才跑一次** (`tick % 4 == 0`)，加 5min stale window，**典型 cleanup 延迟 ~5-6 min**
3. **多 Runner 高频生灭场景下** sidebar 长期处于"接近脏"的状态

## Root Cause（minimal repro 已独立验证）

tmux 3.5a `man tmux` 明确区分：

```
pane-died     Run when the program running in a pane exits, but
              remain-on-exit is on so the pane has not closed.

pane-exited   Run when the program running in a pane exits.
```

Runner 的 `TmuxAdapter.ts:105-112` 在 session 创建时显式设置 `remain-on-exit on`（让 dead pane 保留显示 exit code，方便 Lead 排查 — 这是有意 design）。该选项打开后：

- 程序正常退出 / 异常退出 / 被 kill → 触发 **`pane-died`**，**不**触发 `pane-exited`
- pane 真的关闭（kill-pane 强制关闭 live pane，或某些 corner case）→ 触发 `pane-exited`

但 Runner 完成后 Bridge 走 `POST /api/sessions/:id/close-tmux` → `killTmuxWindow` → `tmux kill-window`。program 早就在那之前自然退出过一次（fired `pane-died`），后续 kill-window 在已经 dead 的 pane 上行为是 incidental 的（实测会再 fire 一次 `pane-died`，但不依赖此特性）。

`scripts/flywheel-cmux-sync.sh:256-257` 只注册 `pane-exited`，从不注册 `pane-died` → **事件路径在 `remain-on-exit on` 的所有 Runner / Lead session 上 by design 失效**。

### Minimal Repro（worker 本机 tmux 3.5a 已验证）

```bash
tmux kill-server; rm -f /tmp/test-events
tmux new-session -d -s test-110
tmux set-hook -g 'pane-exited[500]' "run-shell -b 'echo pane-exited >> /tmp/test-events'"
tmux set-hook -g 'pane-died[500]'   "run-shell -b 'echo pane-died   >> /tmp/test-events'"
tmux new-window -t test-110: -n test-die "sleep 2"
tmux set-option -t test-110:test-die remain-on-exit on
sleep 4
cat /tmp/test-events
# → pane-died     ← 只此一行
# pane-exited 从未出现
```

### 为什么 issue body "假设 A" (session grouping) 不是根因

Issue 中怀疑过 "tmux 3.5a + session grouping + remain-on-exit 组合下 pane-exited 失灵"。实际 repro 不需要 session grouping — 单 session 加 remain-on-exit 就足以复现。Session grouping 不是触发条件，**`remain-on-exit on` 才是**。

### Codex Round 1/2/3 是否 regression？

不是。Round 1/2 让 drain 更 robust（two-phase replay 等），Round 3 加 window-granular liveness。这些都没有改变 hook 注册名。`5f22b5a` 修了 `#{hook_*}` empty-var bug 让现存的 `pane-exited` hook **不报错**，但即使变量名修对了，`pane-exited` 在生产场景仍然不会被 tmux 触发。

## End-to-End Cleanup SLA（清理时延实际值）

`watch_loop` 在每个 15s tick **顺序**执行 `drain_events` → `process_pending_cleanups`：

```
scripts/flywheel-cmux-sync.sh:491-494
  sleep 15
  drain_events                    # 写 mark_for_cleanup（用 drain-time ts）
  process_pending_cleanups        # 同一 tick 内立即检查 now - ts ≥ 30s
```

最坏 deterministic loop case：事件刚 fire（错过当前 drain，等下一次 tick）≈ 15s wait → drain（ts = now）→ process 在同 tick 看到 age=0 跳过 → 下个 tick age=15 跳过 → 第二个 tick age=30 触发 cleanup_workspace_for。

```
wait-to-drain 15s + delay 30s = 45s deterministic loop worst case
                              + scheduler / run-shell async / drain work overhead
                              ≈ 60s SLO 缓冲
```

文案：
- **Typical**: 30-45s
- **Deterministic loop worst-case**: ~45s
- **Operational SLO（含 jitter buffer）**: ≤ 60s

明显优于当前 5-6 min 兜底。**不在本 issue 范围内追求严格 30s** — 那需要降低 watch loop tick 间隔（1s）或让 hook 直接持久化 epoch ts（tmux 不展开 `$(date)` 在 set-hook string，需要包装脚本），属于性能优化二期。

## Implementation Discoveries（在实施过程中找到的额外 tmux 3.5a 行为）

集成测试驱动出两个原 plan 没覆盖的 tmux 3.5a 行为：

1. **`pane-died` 必须 GLOBAL 注册（而非 session-scoped）**
   - `tmux set-hook -t <session> 'pane-died[N]' ...` 注册成功（show-hooks 能看到），但 hook **永远不 fire**。
   - `tmux set-hook -g 'pane-died[N]' ...` 正常 fire。
   - `pane-exited`（不带 `-g`）仍然 session-scoped 工作。这是 `pane-died` 特有的 dispatch 限制。
   - 因此 fix 把 `pane-died` 放在 `register_global_hooks()` 而不是 `register_session_hooks()`。

2. **Live forced-close (kill-window/kill-pane on a LIVE pane with remain-on-exit on) 不 fire 任何 hook**
   - tmux 3.5a 在该路径下既不 fire `pane-died` 也不 fire `pane-exited`。
   - 但 production 永远不走该路径 — Bridge `close-tmux` 只在 Runner status 不在 running 时调用，那时 pane 已经自然死亡（pane-died 已 fire）。
   - 因此原 plan 的 scenario C/D（live forced-close）改为：scenario C 测 production cleanup path（natural exit + 后续 kill-window on dead pane → cleanup 已 queued，kill-window 不产生额外噪音），scenario D 删掉。

3. **`#{window_name}` 在 pane-exited 触发后 window 已销毁的情况下会 resolve 到下一个 active window**
   - Scenario B (remain-on-exit off) 触发 pane-exited 时，window 已销毁，`#{window_name}` 落到 `init` 而非 `B-target`。
   - production 不走此路径（remain-on-exit on）；scenario B 的 assertion 改为 "any exited event"。

## Fix（仅本 issue scope，已实施）

### 1. `scripts/flywheel-cmux-sync.sh::register_global_hooks` 加 `pane-died` hook

```bash
# 实际 commit 的代码:
tmux set-hook -g 'pane-died[500]' \
  "run-shell -b 'echo \"exited|#{session_name}|#{window_name}\" >> $EVENT_FILE'" 2>/dev/null || true
```

事件 format 与现有 pane-exited 相同（`exited|<sess>|<wname>`），`_drain_file` 的 case 分支不变。`drain_events` 已对 session 名做 `flywheel|runner-*` 过滤，所以 global scope 不会引入其他 session 的噪音。

### 1b. `register_session_hooks` 注释 update

不再加 `pane-died`（如原 plan 计划），但更新现有 `pane-exited` 的注释 block，解释为什么 `pane-died` 必须 global 注册（在 `register_global_hooks` 里）。注释 cross-reference 两边代码位置。

### 2. Idempotency 已经具备 — 不动 drain 逻辑

`mark_for_cleanup` 早已 guard 重复（`grep -q "^${wname}|" ... || echo ...`）。即使 `pane-died` + `pane-exited` 在某些 edge case 同时触发同一 window，`CLEANUP_PENDING` 不会出现重复条目。`_drain_file` / `process_pending_cleanups` 也已经按 `is_pane_alive` 重新校验，不会误清恢复了的 pane。

### 3. 更新误导性注释（加入 scope，Codex Round 1 反馈）

| 文件 | 现状 | 改为 |
|---|---|---|
| `scripts/flywheel-cmux-sync.sh` 文件头 line 8 | `tmux hooks (after-new-window, pane-exited, session-created)` | `tmux hooks (after-new-window, pane-exited, pane-died, session-created)` |
| `packages/teamlead/src/bridge/tmux-lookup.ts:132-133` | `kill-window ... triggers pane-exited hooks so cmux-sync event-driven cleanup runs.` | `cmux-sync cleanup is signaled by pane-died when a remain-on-exit pane's process exits; kill-window closes the tmux window itself, and for still-live panes tmux may also emit a pane-exited hook.` (避免 over-claim 已死 pane 上 kill-window 的 incidental 行为) |

### 4. 单元测试 (`scripts/test-cmux-sync.sh`)

加两个 case，mock `tmux set-hook` 调用日志：

1. After `register_global_hooks`，日志必须包含 `pane-died[500]` 注册（presence-based，不依赖顺序）。这是 production main path 的核心 regression guard。
2. After `register_session_hooks "flywheel"`，日志**不得**包含 `pane-died[500]`。这条 negative assertion 防止 future reviewer 把 pane-died 错误地"恢复"到 session-scoped — tmux 3.5a 会 silently 接受但不 fire。

Existing tests for `pane-exited[500]` / `after-new-window[500]` 在 `register_session_hooks` 下保持不变。

### 5. 集成测试 (`scripts/test-cmux-sync-hooks-integration.sh` — 新文件)

真 tmux server，自定义 socket name (`tmux -L flywheel-cmux-test`) 隔离运行。**关键**：测试脚本必须 wrap `tmux` 函数让所有 source 出来的函数（包括 `register_session_hooks`）也走隔离 server：

```bash
TMUX_SOCKET="flywheel-cmux-test"
tmux() { command tmux -L "$TMUX_SOCKET" "$@"; }
export -f tmux
# Now `register_session_hooks` (sourced from flywheel-cmux-sync.sh) calls our shim
```

测试矩阵（每个独立 fixture，session 名必须是 `flywheel` 或 `runner-*`，fixture 用 `runner-test-fly110`）：

| Scenario | Setup | Expected event |
|---|---|---|
| A: program exits + remain-on-exit on (production main path) | new-window "sleep 1" + set-option remain-on-exit on | `pane-died` writes `exited|<sess>|<wname>` 且 `<wname>` 等于 target window |
| B: program exits + remain-on-exit off (legacy / off-mode regression guard) | new-window "sleep 1" (default off) | 任意一行 `exited|...` 落到 EVENT_FILE（assertion 放宽：tmux 3.5a 在 pane-exited fire 时 window 已销毁，`#{window_name}` 可能 resolve 到下一个 active window） |
| C: production cleanup path (natural exit then kill-window on dead pane) | new-window "sleep 1" + remain-on-exit on, wait for natural exit, kill-window | (1) Phase 1: 自然退出 fire pane-died，落 1 行；(2) Phase 2: kill-window on dead pane 不 fire 任何额外 hook（tmux 3.5a），事件计数保持 1 |

**Out-of-scope for integration tests**: kill-window / kill-pane on a LIVE pane with remain-on-exit on. Empirically tmux 3.5a fires neither hook for this path. Production never executes it (Bridge close-tmux runs only after Runner status leaves running, by which point the pane has died naturally). The 5-min conservative polling fallback covers this rare corner case, not the integration test.

每个 scenario 独立 EVENT_FILE，wait_for_event 10s budget，失败时 dump 文件用于诊断。

测试脚本框架要求：
- bash strict mode (`set -uo pipefail`)；source flywheel-cmux-sync.sh 后立即 `set +e` 清掉脚本带入的 errexit
- skip cleanly if `command -v tmux` not found
- skip cleanly if isolated tmux server 启动失败 — 三层检测：(1) new-session exit≠0；(2) stderr 含 `Operation not permitted`/`permission denied`（macOS 偶尔在 exit=0 时仍 stderr 报错）；(3) `has-session` probe 失败
- 退出时 `tmux -L "$TMUX_SOCKET" kill-server 2>/dev/null` cleanup（trap）
- 不使用 `sed -i ''`（避开 BSD/GNU 兼容问题）
- session 名必须 match `^flywheel$|^runner-` — fixture 用 `runner-test-fly110`
- tmux shim 在 source flywheel-cmux-sync.sh **之前**定义并 `export -f`，让 register_global_hooks/register_session_hooks 走 isolated socket

### 6. CI 接入（仅新集成测试，不引入 BSD/GNU sed compat scope）

`.github/workflows/ci.yml` 在 "Test" step 后追加：

| Risk | Likelihood | Mitigation |
|---|---|---|
| `pane-died` 重复触发同 window 多次 | low | `mark_for_cleanup` 已 guard `^${wname}|`，重复 noop |
| `pane-died` + `pane-exited` 同时触发（罕见 corner case） | low | 同上，event 同 format，drain 幂等 |
| 旧 tmux < 2.6 没有 `pane-died` | very low | macOS 3.5a + ubuntu 3.x；set-hook 静默失败 (`|| true`) → fallback to 5min conservative，无 regression |
