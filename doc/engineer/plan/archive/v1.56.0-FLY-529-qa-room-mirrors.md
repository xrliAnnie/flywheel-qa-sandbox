## 1. Goal & Scope

让 "重启/上线才显现" 的功能 (FLY-314 roundtable reply-in-thread、FLY-368 alert auto-repair) 能在 **ship 前**于隔离的 QA Testing Room E2E。现有 4-slot QA Room 缺两块: roundtable 镜像、alert 镜像。本 plan 补这两块的 **QA 能力/房间** (channel + 接线 + runs table + smoke + suite 脚手架)。

**In scope**: (1) Round Table 镜像 — 隔离 channel + runs table + 房间能 host ≥2 test lead + bridge-side auto-thread 触发。(2) Alerts 镜像 — 隔离 alert channel (不碰生产 `#flywheel-alerts`) + **完整**隔离 alert queue/claims/deadletter (Bridge **和** shell 两条写路径)。(3) 两处最小字节兼容生产代码改动 (alert dir env-override)。(4) setup helper (含 thread 权限探测) + smoke + suite docs。

**Out of scope** (gate-confirmed Q1/Q4): FLY-314 多-lead reply-in-thread 真 E2E、FLY-368 完整 auto-repair E2E — 留各自下游 QA。529 不真起 Codex test lead 跑完整 reply-in-thread;只证房间能放 2 lead + auto-thread 触发 + 隔离不漏。Runner E2E 在 roundtable 拓扑 = out of scope (同 mirror,多 Bridge 共享 channel 未定义行为)。

## 2. Acceptance Criteria

- **AC1** — Round Table 镜像: 一条命令把 ≥2 test slot 接到隔离 `test-leads-roundtable`,恰 1 个 host Bridge 跑 `RoundtableThreadManager`;在 channel post 一条 topic (**非 host bot 作者**) → host Bridge **auto-create thread** + `roundtable_topic_threads` runs table 出现 row。
- **AC2** — Round Table 隔离: roundtable inbound cursor 落 `${SLOT_DIR}/`,**不**碰生产 cursor;runs table 在 slot teamlead.db。
- **AC3** — Round Table 可用性 (≥2 lead): 2-lead room = host(slot1) 是 thread creator/participant + member(slot2) 被 manager 显式加进 thread。host manager 设 `FLYWHEEL_ROUNDTABLE_MEMBER_USER_IDS=<slot2 bot user id>`;smoke 断言新 thread 由 host bot 创建 **且** member(slot2) bot 被加进 thread (thread 对两 lead 可用,非仅父频道可见) — 满足 314 下游 reply-in-thread 前置。(R2 #2: manager 不把自己 host bot 当 add-member target。)
- **AC4** — Alerts 镜像: test Bridge 把 alert 发到隔离 `test-flywheel-alerts`,**不**碰生产 `#flywheel-alerts`。
- **AC5** — Alerts **完整**隔离 (两条写路径): (a) test Bridge (`LeadAlertNotifier`) **与** test Lead shell-side (`scripts/lead-alert.sh`) 的 alert queue / dead-letter / claims.db **全落 `${SLOT_DIR}/`**;生产 `~/.flywheel/alert-queue|alert-deadletter|alerts/claims.db` **零新增**。(b) shell-side **channel 解析也隔离**: lead-alert.sh 从 `FLYWHEEL_PROJECTS_FILE` 的 per-lead `alertChannel` 解析频道 (不读生产 `~/.flywheel/projects.json`,见 R2 #1),解析到 **test alert channel**。meta-alert 本地通知 (osascript+state file,**非**生产 Bridge drain 的队列) 不在 AC5 范围 (见 Phase 2)。
- **AC6** — 字节兼容: 不设新 env 时 Bridge **和** lead-alert.sh 行为与现状**逐字一致** (reverse-compat sentinel,两侧)。
- **AC7** — setup helper 探测真权限: `setup-roundtable-channel.sh` 验证 host bot 的 **Create Public Threads + Send Messages in Threads** (建临时消息→起 public thread→thread 内发种子→清理),缺则 fail-fast 明确诊断;`setup-alert-channel.sh` 验 repair bot。两者幂等 (重跑 diff 空)。
- **AC8** — 对 QA 环境自身做 QA: roundtable + alert 两 smoke 真机 PASS;teardown 干净。

## 4. Implementation Phases (TDD where unit-testable)

### Phase 0 — test-slots.json schema (config)
`test-slots.example.json` + 文档新增:
```json
"roundtableChannel": { "channelId": "<id>", "channelName": "test-leads-roundtable", "hostSlot": 1, "memberSlots": [2], "triggerMode": "any_top_level" },
"alertChannel": { "channelId": "<id>", "channelName": "test-flywheel-alerts", "repairBotTokenEnv": "TEST_BOT_TOKEN_1" }
```
`triggerMode` 默认 `any_top_level` (smoke 最易触发)。`memberSlots` = **非 host slot** (R2 #2: manager 在 decoration 前过滤掉自己 bot id,`RoundtableThreadManager:366-369` — host bot 是 thread creator/participant,不是 add-member target)。2-lead room = host(slot1,creator) + member(slot2,被 manager 加进 thread)。`memberSlots:[2]` → host manager 的 `FLYWHEEL_ROUNDTABLE_MEMBER_USER_IDS=<slot2 botAppId>`。(314 下游若要证两次显式 add,可用 3 slot + `memberSlots:[2,3]`。)

### Phase 2 — 生产代码 B: shell alert dir env-override (TDD, 字节兼容, Codex code review) — **Codex R1 HIGH-2**
- **问题**: `scripts/lead-alert.sh:256,287` 把 `QUEUE_DIR`/`DEAD_LETTER_DIR` 硬编码到 `~/.flywheel/alert-queue|alert-deadletter` (仅 claims.db 已 env-override)。`claude-lead.sh:324,2048` 在 Lead fail-stop/crash-loop 时调它 → test Lead 失败会写进**生产** queue,被生产 Bridge drainer 捞起 (跨污染)。FLY-368 下游 QA 会**故意**触发 Lead 卡死测 auto-repair → shell 路径必然触发 → 必须隔离。
- **改**: `lead-alert.sh` 读 `FLYWHEEL_ALERT_QUEUE_DIR:-${HOME}/.flywheel/alert-queue` + `FLYWHEEL_ALERT_DEADLETTER_DIR:-${HOME}/.flywheel/alert-deadletter` (与 Bridge 同名 env,default = 现状 = 字节兼容)。
- **meta-alert** (R2 #4): `meta-alert.sh:25-27` **已有** `FLYWHEEL_STATE_DIR` knob (`path-helpers.ts:57-66` 同契约)。但 `FLYWHEEL_STATE_DIR` blast radius 更广 (agent-team-transport 也用它) → **不**在 529 设它 (避免动 test Lead transport)。**显式把 meta-alert state 排除出 AC5**: 它是本地 osascript 桌面通知 + 去抖 state file,**非**生产 Bridge drain 的队列 → 无跨污染;QA 期间最多弹个本地通知 (cosmetic)。文档记 `FLYWHEEL_STATE_DIR` 这个 knob 留作未来更全隔离。
- **TDD**: `scripts/__tests__/lead-alert-dirs.test.sh` — 设 env → 断言写进指定 dir;未设 → 写进 `~/.flywheel/...` (字节兼容)。

### Phase 3 — test-deploy.sh: `--alerts` 加性 flag (shell) — 任意 mode 可用
启用时读 `alertChannel.channelId` (缺则 fail-fast 指回 setup helper) + bot probe。两条 alert 写路径用**不同**的 channel 解析机制,都要指向 test channel:
- **Bridge 路径** (`LeadAlertNotifier`): 走 `FLYWHEEL_UNIFIED_ALERT_CHANNEL_ID` env。
- **Shell 路径** (`lead-alert.sh`): 走 `FLYWHEEL_PROJECTS_FILE` 里 per-lead 的 `alertChannel` (R2 #1,**不**认 unified env)。

注入到 **test Bridge env 与 test Lead env 两块**:
- `FLYWHEEL_UNIFIED_ALERT_CHANNEL_ID="${ALERT_CHANNEL_ID}"` (Bridge)
- `FLYWHEEL_ALERT_REPAIR_BOT_TOKEN_ENV="${repairBotTokenEnv:-$BOT_TOKEN_ENV}"` + 透传 token 值 (Bridge)
- `FLYWHEEL_ALERT_QUEUE_DIR="${SLOT_DIR}/alert-queue"` (Bridge **和** Lead)
- `FLYWHEEL_ALERT_DEADLETTER_DIR="${SLOT_DIR}/alert-deadletter"` (Bridge **和** Lead)
- `FLYWHEEL_CLAIMS_DB="${SLOT_DIR}/alerts/claims.db"` (Bridge **和** Lead)
- **`FLYWHEEL_PROJECTS_FILE="${SLOT_DIR}/flywheel-projects.json"` (Lead)** — 让 shell-side lead-alert.sh 读 slot-local projects (R2 #1)。
- **`"${BOT_TOKEN_ENV}=${TEST_BOT_TOKEN}"` (Lead)** — token 隔离 (R3 #1): lead-alert.sh 用 indirect env expansion 解 `alertBotTokenEnv`/`botTokenEnv` 指向的 env var (`lead-alert.sh:177-187`)。现有 Lead env 只导出 `DISCORD_BOT_TOKEN`,**没**导出命名 env (如 `TEST_BOT_TOKEN_1`),否则强制 shell smoke 解析到 channel 后会 `no-token` dead-letter。Bridge env 已导出此键 (`test-deploy.sh:923-928`),Lead env 须补齐。
- 在 `--alerts` 下,生成 slot-local `flywheel-projects.json` 时给 test lead 加 `"alertChannel":"${ALERT_CHANNEL_ID}"` + `"alertBotTokenEnv":"${BOT_TOKEN_ENV}"` (FLYWHEEL_PROJECTS jq builder 加这两键),shell 路径才解析到 test channel + token (token env 由上一条导出)。
- 可选 `FLYWHEEL_ALERT_THREADS=1` + `FLYWHEEL_AUTO_REPAIR=1` (FLY-368 测试)。

### Phase 4 — test-deploy.sh: `--mode roundtable` (shell)
- `--mode` enum 加 `roundtable`。验 `roundtableChannel.channelId` + host slot probe (含 thread 权限 probe,见 Phase 5)。
- 每 roundtable slot: access.json `groups` 加 roundtable channel + allowBots 加其它 memberSlot botAppId;identity TEST OVERRIDE banner 告知该 channel 为 cross-dept 频道;Lead env `FLYWHEEL_LEAD_CROSS_DEPT_CHANNEL_IDS="${ROUNDTABLE_CHANNEL_ID}"`。
- **host slot (id==hostSlot)**: Bridge env 加 `FLYWHEEL_ROUNDTABLE_ENABLED=1` + `CHANNEL_ID` + `BOT_TOKEN_ENV=$BOT_TOKEN_ENV` + `BOT_USER_ID=$BOT_ID` + `TRIGGER_MODE=<config>` + `MEMBER_USER_IDS=<memberSlots 的 botAppId CSV>` + `INBOUND_CURSOR_PATH="${SLOT_DIR}/roundtable-inbound-cursor.json"`。
- 非 host: 不设 roundtable env (manager OFF),仅订阅。
- mode sidecar = `roundtable`。`--mode roundtable --alerts` 可组合。

### Phase 5 — setup helpers + mode-consumer 更新 (shell) — **Codex R1 HIGH-1 + R1 #5**
- `scripts/setup-roundtable-channel.sh <channel-id>`: **探测 thread 权限** — host bot (a) `GET /channels/<id>` 200,(b) POST 临时消息,(c) `POST .../messages/<msgid>/threads` 起 public thread,(d) thread 内发种子 (验 Send Messages in Threads),(e) 加一个 member bot,(f) 清理 (archive/delete)。任一步失败 → fail-fast "missing CREATE_PUBLIC_THREADS / SEND_MESSAGES_IN_THREADS"。成功 → patch `roundtableChannel`。幂等。无参→打印 Annie 手建步骤 (含**授予 host bot Create Public Threads + Send Messages in Threads**,超出现有 perms 68608)。

## 6. Risks & Mitigations

| `roundtable` mode 破坏 mode 消费者 (R1 #5) | inject-linear-issue.sh 显式拒 roundtable + 逃生口;同步 driver/README。 |
| Discord channel 手建依赖 Annie | setup helper + README;未配时 deploy fail-fast。 |
