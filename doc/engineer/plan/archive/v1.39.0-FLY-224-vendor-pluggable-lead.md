## 1. 背景与目标

FLY-123 把 **Runner** 做成 vendor 可换(`role-adapter-resolver` + `CodexTmuxAdapter`),但 **Lead 仍死绑 Claude Code**。FLY-224 = 执行 FLY-123 预留的 **Phase 3:vendor 可插拔 Lead**。

**驱动(Annie 拍板)**:唯一主因 = **不把 Agent 层锁死在 Claude,能灵活换 Codex / 以后换 Gemini**。**不是**容灾、专属能力、省额度。

**目标**:① 一道**真**可插拔 Lead-backend 缝(只抽真实共享点,不造空壳);② 常驻 Codex Lead 在 **joycon/sub** 跑通核心循环且**行为等同** Claude Lead;③ Gemini 留口子本期不做。

**非目标**:per-Lead 隔离账号(MVP 单账号);迁移 Claude Lead 到新缝;改 `claude-lead.sh` 的 Claude 行为。

## 3. 真实生产启动链(Codex R1#2 纠错 —— 实现前必须吃透)

launchd 实际链(已核源码 + plist):
```
launchd plist
  └─ /bin/bash ~/.flywheel/bin/flywheel-lead-wrapper.sh <manifest.json>
       └─ (wrapper 读 manifest) → exec claude-lead.sh <args>
            └─ claude-lead.sh 不止起 claude,还做:manifest 回写、workspace 隔离、
               identity/rules 注入(~10 base + project shared/dept)、MCP(.mcp.json + inbox-mcp)、
```

**backend source of truth(纠错)**:后端选择来自 **`.flywheel/config.yaml` 的 `roles.lead.backend`**(`role-adapter-resolver` 读 `RoleBackendMap`),**不是** `projects.json` 的 `LeadConfig`(它只有 `agentId/botTokenEnv/botToken`,无 `backend`)。`FLYWHEEL_LEAD_BACKEND` env 为全局兜底。

**缝必须接进这条真链**,不能旁路。**Phase 0A 产出**:project config → resolver → manifest → wrapper → backend launcher → runtime 的完整调用图 + 唯一 backend 解析结果(wrapper/Bridge/watchdog 共用),并划清:

- 哪些 Claude 专属(Discord 插件 channels、PostCompact、`--append-system-prompt-file`)→ Codex 各有等价实现。

## 5. 那道缝:只抽真实共享点(Codex R1#10/D1)

- **shell**:`flywheel-lead-wrapper.sh` 内按解析出的 backend 分流到 `lead-backends/claude` (= 现有 claude-lead.sh 路径,参数/env 字节不变) 或 `lead-backends/codex`(新)。
- **TS 共享面只有**:`ResolvedLeadBackend`(配置 + precedence 解析结果)+ 一份 supervision/health 上报契约。
- **TS 具体类型(Codex 专属,不假装通用)**:`CodexLeadProcess`、`LeadInputRouter`、`LeadHealthProbe`。**避免再用含混的 `LeadRuntime` 名**(已被 mailbox 事件投递占用)。

**`LeadBackendId` ≠ `ExecutorBackend`(Codex R2#1,关键)**:
- 新增 role-aware `LeadBackendId = "claude-code" | "codex-app-server"`(未来 + gemini),**不复用** Runner 的 `ExecutorBackend`(`claude-tmux | codex-tmux`,那是 AdapterRegistry 的 executor key,把 app-server Lead 叫 `codex-tmux` 会再次混淆 executor/transport/runtime)。
- `.flywheel/config.yaml` `roles.lead.backend` 接受 `LeadBackendId`(给旧值兼容别名 + 迁移说明);每项目/Lead **解析一次** → 把 `backendId` + transport vendor + config hash + **project-scoped mailbox identity**(`mailboxTeamName`/`mailboxAgentName`,见下)写进 manifest → 传 Bridge。
- **project-scoped mailbox 身份(Codex R3#1,实修 namespace 非只改 registry)**:现 `CodexAdapter.getInboxPath(leadName,agentName)` 写 `~/.flywheel/codex-teams/<leadName>/...`,且 `MailboxLeadRuntime.buildFlywheelId()` = `${leadId}-${seq}-${executionId}` —— 两个项目都叫 `product-lead` 会写**同一文件 + 同 dedupe key**,Codex Lead 互串事件。修:`mailboxTeamName` 至少含 **project slug + leadId**;`createLeadRuntime`、Codex receiver、`flywheel-comm` env、**所有 dedupe/flywheelId** 用**同一逻辑身份**;`buildFlywheelId()` 必须含 project。加"两项目同 leadId"真实文件路径集成测试(写/听/ack/bootstrap/重启不串)。
- **Bridge mailbox 路由修正**:`createLeadRuntime()` 现调 `AgentTeamTransportFactory.fromEnv()`(全 Bridge 一个 transport,选了 Codex Lead 也不会把 mailbox 写进 Codex mailbox)→ 改 `forBackend(resolved.transportBackend)`;`RuntimeRegistry` 键改 `(projectName, leadId)`(防跨项目同名 Lead)。
- `CodexAdapter.buildLeadSpawnConfig`:**必须有明确调用方**(被 codex backend launcher 消费返回 env/args);否则本期删除,不留无人消费的第二条"启动缝"。**不**承担 gateway/engine 生命周期。

## 6. 组件(逐个:净新/复用 + 文件 + Codex R1 修正)

### 6.1 `CodexLeadProcess`(净新)— app-server 协议客户端 + 会话
- 文件:`packages/teamlead/src/lead-backends/codex/CodexLeadProcess.ts`。
- spawn argv **由 §6.7a 的 canonical `buildCodexLeadMcpArgv` 单一来源生成**(Codex R8#2):`codex app-server --strict-config -c <非 secret MCP overrides…>`,**child env = 显式 allowlist(只 `CODEX_HOME` + 非 Discord app-server 配置;不含 Discord token,Codex R9#1)**,stdio;newline JSON-RPC。**不在此处另编 `-c` 参数。**
- **健壮性(Codex R1#9)**:request timeout、stderr/backpressure、malformed line、CLI version preflight、graceful shutdown + kill timeout。
- **app-server 执行策略 + server-request 逐方法矩阵(Codex R2#5 + R3#4)**:`thread/start` 显式传**固定** `approvalPolicy`/`sandbox`/network policy(不依赖各机 `~/.codex`)。Phase 0A 产出**逐 method 表**(对 0.137.0 实有方法:command/file/permissions approval、user input、MCP elicitation、dynamic `item/tool/call`、`account/chatgptAuthTokens/refresh`、attestation、legacy approval):每行 handler / allowed source / timeout / journal event / response / 拒绝语义 / test;**固定支持的 CLI/protocol 版本范围,preflight 对未知版本 fail-closed**。
  - **human input + MCP elicitation 默认拒绝或转成 durable Discord 新输入**(不自动喂 secrets,不与"问 Annie 后结束 turn"冲突);**未知 method → 有界 JSON-RPC error,绝不静默挂起**。
  - **auth token refresh**:明确是 CLI 自管 / client 应答 / 触发受控退出重登(共享 `CODEX_HOME` 长跑下 token refresh 是可用性边界),长跑测试覆盖。
- 生命周期:`initialize`+`initialized`→`thread/start`/`thread/resume`→`turn/start`,忙时 `turn/steer(expectedTurnId)`。

### 6.2 `LeadInputRouter`(净新,Codex R1#3 核心补漏)— 统一入站
- 文件:`packages/teamlead/src/lead-backends/codex/LeadInputRouter.ts`。
- **同时**收:① Discord gateway 事件 ② Bridge/mailbox 事件(runner_question/gate/stuck/artifact/bootstrap —— 现有 `MailboxLeadRuntime` 已在写,Codex app-server 不会自轮询)。
- 语义:输入先 **durable 持久化接受** → 按 `(project, lead)` **串行**送 thread;幂等键 = Discord message id / mailbox envelope sequence;**仅 durable accept 后才 ack**(修现有 watcher "callback 返回即 ack 可丢消息")。
- **事务型 journal(Codex R2#3 + R3#2,语义诚实化)**:`last-accepted-input` + 原子 JSON **不够**。用 SQLite / append-only store,状态机 **`accepted → dispatching(clientCorrelationId) → dispatched(turnId) → model_completed → output_pending → completed | ambiguous | dead_letter`**。
  - **关键(R3#2):journal 单独无法给 app-server 内部任意 shell/MCP 副作用 exactly-once** —— "exactly-once / 重发 turn / at-most-once" 三者不相容。诚实策略:`dispatching(clientCorrelationId)` 在**发 `turn/start` 前**落盘;恢复**保守**:**仅当能证明旧 turn 未创建且无工具执行**才自动 re-issue;任何无法证明的 dispatched/active/tool-started → **`ambiguous`/`dead_letter` 通知人工**,**绝不自动重跑模型**。
  - **correlation 用 app-server 正式字段(Codex R4#2,非杜撰的 input metadata)**:`UserInput` 无通用 metadata 字段;对账链 = `clientCorrelationId → turn/start|turn/steer 的 `clientUserMessageId` → `thread/read` userMessage item 的 `clientId``(两条路径都验)。某支持版本不回传 `clientId` → preflight/集成测试 **fail-closed** 或降级为正文带 namespaced marker 的兼容方案。
  - **副作用语义按命令逐项声明(Codex R4#1,Option B —— 不改 `flywheel-comm`)**:
    - **merge/ship**(Codex R5,精确化 —— `verify-approval` 是**只读授权**不消费 merge,不能号称 execution at-most-once):**授权 = fail-closed / 绑当前 head**(`verify-approval` 重核 `review_question_id`+structured approval+`approved_to_ship`+`pr_head_sha`,stale/错 head 拒);**执行 = best-effort**,重试前**先查 GitHub PR merged/mergeable postcondition**,provider 已 merged → **收敛成功不再执行**,状态不可证明 → **ambiguous 不盲重试**。**不称 gate 提供 at-most-once**(GitHub 对已 merged PR 的 no-op 是 provider 后置条件,非 gate 保证)。
    - **Runner instruction(`flywheel-comm send`)= best-effort**(`insertInstruction` 无 caller op-key);但协议层 `[lead-instruction <id>]` 幂等(FLY-208)使 Runner 侧重复可吸收。
    - **任意 shell/MCP = best-effort + 逐项记录风险**。
    - 通用 op-key idempotency proxy / 改 `flywheel-comm` = **更大 scope,不进 MVP**。测试**逐命令**标保证等级,不拿"Flywheel-owned"当保证条件。
  - 最终回复进**独立 durable outbox**(canonical sender idempotency key + Discord nonce,见 §6.4)。崩溃恢复先 `thread/read(includeTurns:true)` 对账。

### 6.7a Codex Lead 的 MCP 自注入(净新,独立成立)
- **背景**:Codex Lead **本就不该依赖 Annie 个人 host 的 `~/.codex` 配置**(里面是她的个人 MCP + 一条过期 Linear token —— 正是我 spike 第一次跑 turn 被坏 Linear MCP 拖挂的根因);spike 时 chrome-devtools-mcp 是从那套 host config 读到的,**生产 Codex Lead 必须自带 task-scoped 有效凭证、不取宿主**。(历史注:此设计最初挂在 FLY-230 "strip-host-MCP" 上,但 FLY-230 已关闭(Annie 判定剥宿主对一个小噪音过重,简单解=重登过期 Linear token);本设计**独立成立**,与 FLY-230 是否落地无关 —— 不依赖宿主个人配置这条本身就对。)
- **正解 = task-scoped 注入,经 process-local `-c`**(镜像 Claude 侧 `EdgeWorker.buildMcpConfig` 的"按任务注入有效凭证、不取宿主"原则)。
  - **共享 base `CODEX_HOME`**:Flywheel 托管、干净、**无宿主 MCP**,只承载共享 auth/session + 安全公共 base config;**绝不改宿主 `~/.codex/config.toml`**。
  - **per-Lead 配置经 `-c`(Codex R8 实测纠错:`--profile` 对 `app-server` 不可用,0.137.0 报 "`--profile` only applies to runtime commands and codex mcp")**:**唯一冻结启动形态 = `codex app-server --strict-config -c <非 secret MCP overrides…>`**(process-local,天然不撞共享文件,串身份风险消失)。`-c` 只含 command/args、env-var 名、`env_vars`、`enabled_tools`、timeout;**raw token 不进 argv,也不进 app-server child env**(只在 codex-lead parent/gateway,见下最小权限段)。可另落 per-Lead `0600` audit artifact,但 app-server **不**经它加载。effective config hash 入 manifest `configHash`。
- 注入的 MCP(实测冻结,见 Phase 0A §⑧ 表):
  - **Discord MCP —— 不注入**。候选 `mcp-discord-agent-comm@0.2.0` 只有 `discord_message`(send + expect_reply),**无 read/reaction 安全子集** → 不注入;**read 走 Codex Lead 自己的 gateway**(已收消息)、**reaction 走受控 Bridge endpoint**;关键出站/ask-Annie 全走 §6.4 canonical sender。
  - **chrome-devtools-mcp@1.1.1**(env-gated `FLYWHEEL_LEAD_CHROME_ENABLED`):builder **解析+校验 URL 后写具体 argv**(如 `--browser-url=http://127.0.0.1:9222`),**绝不写字面 `$URL`**(Codex R9#2 实测:stdio MCP 直接 exec command+args 无 shell,`env_vars` 不做 argv 替换 → 字面 `$URL` Chrome 收到无效值);disabled 时**不生成** entry;非关键,init 失败 → 明确 degraded。
  - flywheel-comm 走 CLI 不注入。
- **最小权限分两套 env(Codex R9#1)**:Discord MCP 既不注入,**app-server child env 拿不到 Discord token**(否则模型起的 shell/tool 子进程能碰到 = 扩大暴露面)。
  - **codex-lead parent/gateway** 解析该 Lead 的 Discord token(gateway 用)+ canonical sender 在 Bridge 侧自解 per-Lead token。**未来若某注入 MCP 确需 secret,才按 server-specific env allowlist 转发**(当前无)。
  - **`spawn(app-server)` 用显式 child-env allowlist**;**删 Discord token**。
- **可执行解析 + sanitized child-env 契约(Codex R10#1,实测 `{CODEX_HOME}`-only → `codex`/`npx`/`node` 全 `ENOENT`;launchd PATH 比交互 shell 更窄,FLY-176 雷区)**:
  - Codex 用**已验证绝对路径** = 复用现有 `flywheelCodexBin()`/`FLYWHEEL_CODEX_BIN`(`codex-home.ts`,repo-owned shim),**不在稀疏 PATH 裸 spawn `codex`**。
  - MCP command(`npx`)同样用**绝对路径**或传**显式 allowlist 构造的 `PATH`**(**不硬编码** `/opt/homebrew` 等单机路径);preflight 验 executable + pinned package 可用。
  - app-server child env 完整键集 = `CODEX_HOME` + sanitized `PATH` + 确需的 `HOME`/temp/CA/proxy;**Discord token/env 名显式 deny**;集成测试在 **`env -i`/launchd-like 稀疏环境**真启 app-server + Chrome MCP(证不靠开发者交互 shell)。
  - `configHash` 覆盖 **resolved executable + sanitized PATH policy + MCP command/args**(二进制解析变化触发受控重启)。
- 文件:`packages/teamlead/src/lead-backends/codex/buildCodexLeadMcpArgv.ts`(**canonical argv builder,§6.1/Phase 0A 共用同一个**,Codex R8#2)。测试:真 app-server 启动 + 真 attach、**两个 app-server child env 都不含任何 Discord token**(两 gateway 各用对的 token)、parsed MCP config **无 `$...` 字面**、宿主 MCP 不入、raw token 不落盘/日志。

### 6.8 健康/看门狗 + 重启所有权(Codex R1#5/#6 + R2#2/D4)— 隔离 + 唯一重启者
- 文件:`packages/teamlead/src/lead-backends/codex/LeadHealthProbe.ts` + Bridge 侧 observer 接线。
- **watchdog 隔离**:Bridge startup 注入 canonical resolved backend,**显式过滤掉 Codex leads 再构造现有 `LeadWatchdog`**(现 `plugin.ts` 对所有 `project.leads` 建 pane watchdog);Codex leads 不进 pane watchdog。
- **重启所有权唯一(R2#2,防三方互踢/crash-loop)**:**launchd = 唯一顶层 Codex Lead 进程重启者**(plist `KeepAlive`);Codex Lead 进程内只**监 app-server child**,child hang/不可恢复 → **受控退出整体**,由 launchd 重启;**Bridge 只读 heartbeat/lease/launchd 状态并告警,绝不 kickstart**(进程内 probe 报不了"整进程已死",故顶层归 launchd)。文档补 restart budget / 连续失败阈值 / graceful shutdown 顺序 / crash-loop 告警测试。
- 信号:① child process exit/重启 ② gateway 连接态/重连 age ③ `thread/read(includeTurns:false)` 有界超时 RPC;`turn/completed` age 仅活动 telemetry。状态机:starting/healthy/degraded/down/recovering + 阈值。
- `LeadAlertNotifier` 扩 process/gateway/thread 健康事件类型 + episode 去重 + 恢复通知。
- 反向好处:无 pane → 免疫 FLY-193/218/220 类误报。
- 测试:混合 Claude+Codex fixture 证两套 watchdog 互不观察;app-server hang / gateway flapping / thread-not-found 故障注入;crash-loop(连续退出)告警。

### 6.9 founder 硬门(Codex R1#7/R2#5)— 限定覆盖 + 可验证降级
- Codex Lead 启动 **preflight 强制**:consent `decisionMode=enforce`、Bridge URL/token 可用、`FLYWHEEL_COMM_BYPASS_BRIDGE` **未注入**。
- **失败时选可技术验证的状态**(R2#5):**Lead 启动失败** 或 进入**明确只读 degraded mode**;**不**声称"仍能跑任意 shell 但只禁 ship"(那不可验证)。
- 诚实:硬门只覆盖已接入 Bridge/gate surface,**不**拦 Codex 直接 `gh pr merge` 等旁路 → 文档写明剩余旁路风险;QA 分项验(见 §8)。

### 6.10 crash 恢复 / state(Codex R1#9/R2#3)
- **事务型 journal**(见 §6.2,SQLite/append-only)是恢复正确性的载体,**不是**单个 state JSON。
- state key = **`(projectName, leadId)`**;原子写 + `0600` + schema/version/rule-bundle-hash。
- thread 落盘 → 重启 `thread/read(includeTurns:true)` **对账** journal → `thread/resume` + 按状态机决定重发/续等;**有副作用的命令按 §6.2 逐命令语义**(merge/ship 走 GitHub merged postcondition 收敛、`send`/shell best-effort、不可证明态 ambiguous→人工),**不做"重放=副作用至多一次"的泛化**。
- **MVP 单共享 `CODEX_HOME` 仅 auth/session;per-Lead Flywheel state/journal 独立**(消除"单账号 vs 隔离 home"矛盾);测试才用隔离 temp home。per-Lead 隔离账号 = 留钩子,不进 MVP。

## 10. 决策点结论(Codex R1 D1–D6,已采纳)

- **D1**:shell 分发 + TS 具体类型;删伪双实现契约,共享只留 `ResolvedLeadBackend` + supervision。
- **D2**:每 Lead 进程 co-host gateway+router+engine(否决 Bridge-gateway+独立-engine 无 IPC)。
- **D3**:Flywheel 规则 → `developerInstructions`;`AGENTS.md` 只项目约定;bundle hash → 受控 restart/resume。
- **D4**:`thread/read(includeTurns:false)` RPC 心跳;禁模型 turn 心跳。
- **D5**:关键出站 = Flywheel-owned Bridge REST sender;MCP 仅非关键;问 Annie 后结束 turn。
- **D6**:`turn/start` 返回 turn.id 作 steer 的 expectedTurnId;失配/已完成 → 原输入回队下次 turn/start;不拿 `thread/inject_items` 当常规兜底。
