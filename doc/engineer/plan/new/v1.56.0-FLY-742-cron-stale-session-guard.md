## 0. 目标(一句话)

Bridge `/api/runs/start` 的 409 路径:被 **stale/idle parked blocker** 挡住的 scheduled run-start **要么自愈**(blocker 的 PR 已 merged/closed → fail-closed auto-finalize 释放 slot + 同 tick 继续 start)**要么立即冒泡成 durable Discord 告警**(非-merged blocker → 告警 Lead/founder,绝不自动清)。健康在跑的 `running` in-flight blocker、以及 fresh parked blocker 保持现状(静默 409,零告警,**零 gh 调用**)。默认可一键回退(kill-switch env)。

## 2. `stale-blocker-guard.ts` 设计

### 2.1 两阶段纯 classify(零 I/O,全单测 —— Codex R1 #2:gh 只在 local 判定为 stale 后才调)

```ts
export type LocalClass = "block_silent" | "needs_pr_check";
export type PrState = "merged" | "closed" | "open" | "unknown";
export type BlockerAction = "block_silent" | "alert_block" | "finalize_proceed";

// Phase 1 —— 只看本地 status + 时间戳,绝不 I/O
export interface LocalClassifyInput {
  status: string;
  awaitingReviewEnteredAt?: string;    // 只对 awaiting_review 有意义
  lastActivityAt?: string;
  nowMs: number;
  staleTtlMs: number;
}
export function classifyBlockerLocal(i: LocalClassifyInput): { local: LocalClass; reason: string };

// Phase 2 —— 已知 stale,拿 gh 结果决定 finalize vs alert
export function classifyStaleWithPr(prState: PrState): { action: "finalize_proceed" | "alert_block"; reason: string };
```

**Phase 1 规则(顺序)**:
1. `status ∉ {awaiting_review, approved_to_ship}`(running/其它)→ `block_silent`(in-flight guard 现状;crash-reaper 负责 dead running)。**无 gh 调用**。
2. **status-specific idle anchor**(Codex R1 #3):
   - `awaiting_review` → `awaitingReviewEnteredAt`,缺失才 fallback `lastActivityAt`。
   - `approved_to_ship` → `lastActivityAt`(**不用** `awaitingReviewEnteredAt` —— approve 只更新 last_activity_at,用旧 review 戳会把刚 approve 的 session 误判 stale)。
3. anchor 解析失败/缺失 → `block_silent`(无法证明 stale)。SQLite UTC 戳显式解析(`replace(" ","T")+"Z"`)。
4. `idleMs < staleTtlMs`(太新)→ `block_silent`。**无 gh 调用**。
5. else → `needs_pr_check`。

**Phase 2 规则**:`merged|closed → finalize_proceed`;`open|unknown → alert_block`(**fail-safe**:unknown 绝不自动清)。

### 2.2 编排 `handleActiveBlocker`(注入真 deps)

```ts
export interface StaleBlockerGuardDeps {
  enabled: boolean;                 // 组合注入 seam;生产由 FLY-1807 固化为 true
  staleTtlMs: number;               // FLYWHEEL_CRON_STALE_TTL_MIN,默认 120,正整数 clamp
  now: () => number;
  checkPrState: (projectRoot: string, prNumber: number) => Promise<PrState>;
  finalizeBlocker: (blocker: Session, prState: PrState, anchorIso: string) => Promise<{ proceed: boolean }>;
  alertLead: (blocker: Session, prState: PrState, anchorIso: string) => Promise<void>;
  projectRootFor: (projectName: string) => string | undefined;
  log?: (m: string) => void;
}
export function createStaleBlockerGuard(deps): { handleActiveBlocker(b: Session): Promise<{ proceed: boolean }> };
```

guard 闭包持有一个 **in-memory** `inFlightFinalize = new Set<string>()`(retryable serialization —— Codex R2 #1:**绝不**用永久 session_events 行做 claim,否则首次 transient 失败后永远撞 dup、再不重试 = 复刻 FLY-742 本 bug)。

流程:
1. `!enabled` → `{proceed:false}`(现状 409,零副作用 = 字节兼容)。
2. 算 `anchorIso`(status-specific,§2.1.2)+ `local = classifyBlockerLocal(...)`。
3. `local === block_silent` → `{proceed:false}`(**不调 gh**)。
4. `local === needs_pr_check`:
   - `projectRoot = projectRootFor(project_name)`;`prNumber = pr_number`。
   - `prState = (prNumber && projectRoot) ? await checkPrState(projectRoot, prNumber) : "unknown"`。
   - `d = classifyStaleWithPr(prState)`。
   - `finalize_proceed`:`key = execId+":"+anchorIso`;`inFlightFinalize.has(key)` → `{proceed:false}`(并发 finalize 进行中);否则 `inFlightFinalize.add(key)`;`try { return await finalizeBlocker(blocker, prState, anchorIso); } finally { inFlightFinalize.delete(key); }`(**finally 释放 → transient 失败后下 tick 可重试**)。
   - `alert_block` → `await alertLead(blocker, prState, anchorIso)` → `{proceed:false}`。

### 2.3 `finalizeBlocker`(plugin.ts 实现 —— fail-closed + double re-read;Codex R1 #1/#4/#6, R2 #1)

并发串行化由 §2.2 的 **in-memory `inFlightFinalize` 锁**(finally 释放,retryable)负责,**不**在此用永久 session_events claim。此处 `insertEvent` 只做 **audit**(indeterminate / finalized 结果),不作 retry-gating claim。

1. **Re-read #1(teardown 前)**:`cur = store.getSession(execId)`。
   - 读不到 → `{proceed:false}`。
   - `cur.status` ∈ 终态(completed/terminated/failed/...非-active)→ slot 已释放 → `{proceed:true}`(Codex #4:并发终态别误报 409)。
   - `cur.status` ∉ {awaiting_review, approved_to_ship}(变成别的 active 态)→ `{proceed:false}`(不 teardown)。
2. **tmux tri-state(Codex #1 —— fail-closed)**:`lookup = lookupTmuxTarget(execId, project)`:
   - `error`(无法判断是否活着)→ `insertEvent(cron_stale_finalize_indeterminate)` + `{proceed:false}`。**绝不**当 gone。
   - `gone`(确无 target)→ 无 tmux 要清,进 step 3。
   - `found` → `killCmuxLinkedSession` 失败 → `{proceed:false}`(window 不动,下 tick 重试);→ `killTmuxWindow` 失败 → `{proceed:false}`;→ `closeTerminalView`(best-effort,不 gate)。
3. **Re-read #2(transition 前)**:`cur2 = store.getSession(execId)`;终态 → **若本轮已 teardown 过**则镜像 crash-reaper 的并发-move 分支:`deleteCommDbSession` + `insertEvent("scheduled_run_blocker_finalize_transition_skipped")` 后 `{proceed:true}`(避免罕见 race 下遗留 stale CommDB 行;Codex R3 非阻塞 #2);∈{awaiting_review,approved_to_ship} → `applyTransition(opts, execId, "completed", {trigger:"cron_stale_finalize"}, {last_activity_at, last_error:"Auto-finalized (FLY-742): done+parked, PR "+prState+", idle past TTL — freed cron slot"})`;其它 active → `{proceed:false}`。
   - ⚠️ **文案**(Codex Q3):`prState` 直陈 `merged`/`closed`,**不写 "merged successfully"**(closed-unmerged 也走这条,别暗示 ship 成功)。
4. `deleteCommDbSession(execId, project)`;`archiveIssueThreadIfNoOtherActive(store, ..., {allowStatuses:["completed"]})`(best-effort,中央 helper,Codex #6);`insertEvent("scheduled_run_blocker_finalized" payload: prState/idle/tmux)`。
5. `{proceed: transition.ok}`。
   - **worktree**:completed=终态,由既有 FLY-603 worktree reconciler 处理(同 crash-reaper 的 terminated),此处不重造。

### 2.4 `alertLead`(plugin.ts 实现 —— durable + deduped;Codex R1 #5, R2 #2 顺序修正)

**顺序**(先 resolve 再 claim 再取 seq —— Codex R2 #2:claim 前必须已有 leadId + payload;`tryClaimLeadEvent` 只返 boolean,seq 靠 claim 成功后再 `appendLeadEvent`(同 id)走 UNIQUE-冲突路径拿回既有 seq):
1. `anchorIso` = status-specific(同上);`eventId = "scheduled-run-blocked:"+execId+":"+anchorIso`。
2. `leadId = resolveLeadForIssue(projects, project_name, labels).lead.agentId`;build `payload` + `sessionKey`。payload = `HookPayload{event_type:"scheduled_run_blocked", ...}`:issue id/identifier/title、blocker exec-id/status/idle 小时、PR 号+state、`summary`("scheduled/cron run-start 被 stale session 挡住;上一 run 没 finalize;close_runner 清它 或 ship 它的 PR 来解阻")、`notification_context`("告诉 Annie 某 scheduled job 被 stale session 卡住,需清")。
3. **dedup(持久)**:`claimed = store.tryClaimLeadEvent(leadId, eventId, "scheduled_run_blocked", JSON.stringify(payload), sessionKey)`;`!claimed` → return(此 incident 已告警过 —— 已投递 或 正被 guardrail retry)。
4. `seq = store.appendLeadEvent(leadId, eventId, "scheduled_run_blocked", JSON.stringify(payload), sessionKey)`(claim 已插入该行 → 走 UNIQUE-冲突分支返既有 seq)→ `runtime = registry.getForLead(leadId)`;有则 `runtime.deliver(envelope)` → 成功 `markLeadEventDelivered(seq)`;失败/无 runtime `recordDeliveryFailure(seq, err)`。
5. **durability**:`scheduled_run_blocked ∈ GUARDRAIL_EVENT_TYPES`(§lead-runtime),inline deliver 失败由 `HeartbeatService.retryUndeliveredGuardrailEvents()` 每 heartbeat 重投(bounded MAX_DELIVERY_ATTEMPTS=5;耗尽 → FLY-83 stuck alert 兜底)。in-memory Set **不用**(持久 lead_events unique id 才是 reliability boundary)。

### 5.1 纯两阶段 classify(`stale-blocker-guard.test.ts`)
- running → block_silent(**断言不进 needs_pr_check**)。
- awaiting_review 新(<TTL)→ block_silent。
- awaiting_review 旧 → needs_pr_check → {merged→finalize, closed→finalize, open→alert, unknown→alert}。
- **approved_to_ship anchor**:旧 review 戳 + 刚 approve(fresh last_activity_at)→ block_silent(Codex #3 回归)。
- approved_to_ship 旧(last_activity_at 超 TTL)+ merged → finalize。
- 时间戳缺失/不可解析 → block_silent。TTL 边界确定。

### 5.2 编排 + 集成(注入 fake deps —— Codex #7:覆盖最险 seam)
- **不调 gh**:running / fresh / 无时间戳 时 `checkPrState` 断言未被调用。
- finalize 分支:re-read 终态→proceed=true;still-parked→transition→proceed=true;别的 active→false。
- **tmux tri-state**:`error`→proceed=false(不 transition);`gone`→transition;`found`+cmux 失败→false(window 不动);window kill 失败→false。
- **inFlightFinalize 锁**:同 execId:anchor 的并发 second call → proceed=false;first call `finally` 释放 → transient 失败(如 tmux error)后**下 tick 可重试并最终 proceed**(绝不复用永久 session_events claim)。
- **alert durability/dedup**:`tryClaimLeadEvent` false→不重复 deliver;deliver 失败→recordDeliveryFailure(可被 guardrail retry)。
- runs-route:proceed=true→不返 409 落 start;proceed=false→409(文案不变);guard 未注入→409(字节兼容)。
- `scheduled_run_blocked ∈ GUARDRAIL_EVENT_TYPES/RETRYABLE_LEAD_EVENT_TYPES` 断言。
