# Plan: 完成的 Runner 卡在 status=running — FSM 自动收尾

**Version**: v1.48.1 (cutover 时按实际发布序号终定)
**Issue**: FLY-324
**Date**: 2026-06-19
**Source**: Linear FLY-324 + tidal-echo 工作期间实测 3 例(FLY-284/319/323)
**Status**: codex-approved (code review 3 轮 APPROVED;design review R1 CHANGES REQUESTED 6 项 → 全纳入 → R2 内容 approvable,提交后 R3 终核)

---

## 1. Problem

干完活的 Runner **卡在 `status=running`,FSM 从不 transition 到 `completed`/`awaiting_review`**。后果:
- `close_runner` 拒绝(`status_not_eligible:running`);
- 它的 tmux session + git worktree 一直 linger,只能等下次 Bridge 重启 reconcile 才清掉;
- idle watchdog 误报 `session_stuck`(它只 poll `status=running`)→ 噪音 + 误导(看着像出事,其实早完工);
- running 计数不降 → load 高位 → admission 把新 Runner 挡掉。

自托管下『为清 stuck Runner 而重启 Bridge』blast radius 不划算,所以不能靠重启清。

## 2. Root Cause(从 StateStore 实证,非预设)

对比卡住的 vs 干净的 session:

| issue | status | session_stage | decision_route |
|---|---|---|---|
| FLY-320(干净对照,no_code config fix)| **completed** | completed | **no_code** |
| FLY-319(卡)| **running** | completed | *(null)* |
| FLY-323(卡)| **running** | completed | *(null)* |

差异:FLY-320 调了 `flywheel-comm complete --route no_code` → 发 `session_completed` 事件 → Bridge 走 `applyTransition` 把 FSM `running→completed`。FLY-319/323 **只调了 `flywheel-comm stage set completed`**。

`stage set completed` 发的是 `event_type: "stage_changed"` 事件,它**只更新 `session_stage` 标签列,从不动 FSM `status`**。event-route.ts 的 `stage_changed` handler 原注释明说:

> stage_changed values OTHER than "completed" remain informational only — they do NOT trigger FSM transitions. The FSM status change for non-merged completion still flows through `session_completed`.

而 no-PR / no-code / QA / generic Runner 的收尾协议是 `stage set completed`(它们不创建 PR,从不调 `complete --route`)。于是它们永远卡 `running`。当前 DB 里有 **8 个** `running` + `session_stage=completed` 的僵尸印证此 mode。

**OUT of scope(issue 自标『别预设』):** FLY-284(`stage=implement`)、FLY-286(`stage=pr_created`)卡 running 是**另一种 mode**(完工信号丢失/缺失,非『报了 completed 但 FSM 没转』),本修不处理、也不开 follow-up 单(无新 stuck mode)。

## 3. Fix

一个纯谓词 `isDoneButRunning(s)` = `status==='running' && session_stage==='completed' && !decision_route && !pr_number`,两个 surface 共用:

### 3.1 event-route `stage_changed` handler(治未来)

`stage==='completed'` 且 session 命中 `isDoneButRunning` 时,走 canonical `applyTransition` 把 `running→completed`(合法 FSM 边)。结构上是 FLY-60 W2 merged-ship `if` 之后的 `else if`,守卫:
- `landingStatus?.status !== "merged"` —— 让 W2 merged 路径继续做 merged session 的**唯一** owner(现有 "running + merged + decision_route UNSET" boundary regression 测试不破)。
- `!landingStatus?.prNumber`(design-review #3)—— `stage set completed` 会把 land-status.json(status + prNumber)挂进 payload。一个**已建 PR 但 `complete --route` 丢失且无 marker** 的 session 可能命中 `isDoneButRunning`(pr_number 还没持久化),但**它有 PR、欠 review**,不能在此被强转 completed。incoming landing 带 prNumber → 不命中本分支。
- `!hasPendingCompleteMarker(execId)`(§3.3)。

**契约 scope(design-review #1,重要):** 这条 live 路径把 `stage=completed` 当作 **terminal『我完工了』断言** —— **想 parked 保活的 Runner 绝不能报 `stage=completed`**。§3.4 的 Lead exclude 清单是 **cutover boot-sweep 专用**的、给『修法上线前那批契约还没生效就报了 completed』的存量兜底,**不**保护 live handler(live handler 没有、也不该有 exclude 输入 —— 没人能预测未来哪个 execId 会误报)。

**No-row 竞态(design-review #2):** 若 `stage_changed=completed` 在 `session_started` 之前到(started 是 fire-and-forget 可能丢),`patchSessionMetadata` 是 UPDATE-only、无行则 no-op;随后 `getSession` 返 undefined → `isDoneButRunning({})` = false → **本分支不触发、不伪造 transition**。这与现有所有 stage_changed 的行为一致(stage_changed 不 upsert,只 worktree_ready 才 upsert),FLY-324 不引入新竞态。有测试覆盖。

### 3.2 `reconcileDoneButRunning` boot sweep(清存量)

`startBridge` 里、**FLY-172 marker drain 之后**跑的一次性 sweep:把现存『stage_changed 已发但修法上线前就卡住』的僵尸 `running→completed`。放在 marker drain 之后,让有 pending complete marker 的 session 先被它真实的 `complete --route` 路由,只剩纯 stage-set-completed 僵尸。

### 3.3 Marker guard(Codex code-review R1 LOW)

两个 surface 都 skip『有 pending complete marker(`<markerDir>/<execId>.json`)』的 session —— 那条 marker 的最终 replay 携带真实 route(needs_review→awaiting_review / blocked)。若先强转 `completed`(终态),replay 的 transition 会被拒、route metadata 丢失。这类 session 归 FLY-172 drain / heartbeat reconcile 所有。

### 3.4 Lead 控制的 cutover exclude(parked-needed 安全)

**关键洞察:** 报了 `stage=completed` 的 Runner 不一定是可丢弃的僵尸 —— 可能是 **parked**(刻意保活,如某 QA Runner hold 着 Annie 登录的浏览器 tab、等再 engage 复验)。强转 `completed` 会让它进可 teardown 路径,丢掉复验状态。

**parked vs 真 done 不是可靠的 DB 信号**:这些行**全是 stale heartbeat**(11–37h),comm DB 的 gate question 按 **agent 名**存不是 execId(没有干净 execId→gate 链),『hold 浏览器 tab』Bridge DB 根本不记。任何启发式都会误判。

所以 boot sweep 认一个 **Lead 设的 env exclude 清单** `FLYWHEEL_FLY324_SWEEP_EXCLUDE`(逗号/空格分隔,execId 或 issue identifier 都匹配)。Lead 在 **cutover Bridge restart 前**那一刻指定要跳过的 parked Runner;sweep 只清其余真 done 的。默认不设 = 全扫(字节兼容)。

## 4. Safety Argument

- **Status-only:** 两个 surface + sweep **只翻 FSM `status`,零 tmux/worktree/Discord 操作**。本次改动**没有任何新增 kill 代码**。
- **Teardown 都是 exec-id 范围,但机制不同(design-review #4 修正):** 实际收 tmux/tab 的两条路径都按 execId 定位、**都不是 name-pattern kill**,但用的不是同一个 API:
  - `close_runner` —— 经 `getTmuxTargetFromCommDb(executionId, projectName)` 用 CommDB 按 execId 查窗口(`close-runner.ts:137`),窗口不在则幂等返 `alreadyGone`;kill 成功后再按 `resolveTerminalViewIdentity` 关 `=viewer-${execId}` 的 Terminal tab。
  - boot **tab-reaper** —— 枚举 Terminal custom title、解析出 `executionId/windowId`、**精确 title 相等**匹配,只关 `viewer-${executionId}` 的 tab(`terminal-tab-reaper.ts:54-165`),不碰 Runner 的 tmux window。
  两者都以 execId 为锚 → **零 cross-kill 面**(消除昨晚 @104 stale window-id collision 误杀 —— 关 FLY-275 误杀 FLY-285 window 的事故)。
- **活跃 Runner 不碰:** 在跑的 Runner 处于 `design_review`/`implement` 等非 `stage=completed` 状态,谓词不命中 → sweep / handler 永不碰它们。
- **parked-needed 的保护边界(design-review #1,如实陈述):** **boot sweep** 由 Lead exclude 清单显式跳过(§3.4);**live handler 不在此保护内** —— 它把 `stage=completed` 当 terminal 契约(§3.1)。即:存量 parked(修法前报过 completed)靠 cutover exclude 兜;未来 parked 靠『不报 completed』契约。
- **Misconfig 失败模式良性(Codex code-review 确认):** exclude env 只**抑制** sweep,误配最坏让一个真 done 僵尸继续 running(下次重启 sweep 会清),**绝不授予能力、绝不扩大 teardown**。
- **boot reaper vs sweep 顺序(design-review #5,如实陈述):** `reapTerminalTabs(store)` 在 marker drain + 本 sweep **之前** fire-and-forget 启动(`plugin.ts:1942`),sweep 在后(`plugin.ts:~2391`)。竞态下 reaper 可能读到 sweep 前的 `running`(跳过该 tab)或 sweep 后的 `completed`(同一次 boot 关掉该 viewer tab)。**无论哪种都不 kill Runner 的 tmux window**;被 exclude 的 parked session 停在 `running` → reaper 永不关它;真 done 的被关 viewer tab 本就是期望的清理(完整 teardown 由 Lead `close_runner` 收 tmux+worktree)。故此竞态对 FLY-324 良性,不改启动顺序(避免动高敏的 startBridge 时序)。
- **幂等 / 重启安全:** 转成 `completed` 后不再出现在 `getActiveSessions()`(只返 running/awaiting_review/approved_to_ship)→ 后续重启不重扫。

## 5. Scope

- **IN:** §3 两个 surface + marker guard + exclude 清单;清现存真 done 僵尸(stage=completed:FLY-328/329/330/331 + 其余按 Lead cutover 终核)。
- **OUT:** FLY-284/286(另一 mode,§2);任何 teardown 逻辑改动(复用现成 exec-id 范围路径)。

## 7. Deploy(cutover)

- ship = **Bridge restart(founder-gated,cutover 批次跟 Lead 协调,不自 ship)**。
- boot sweep 在那次 restart 里清存量『顺手』;此后 handler 修法防新僵尸,无需再为清它们重启。
- **cutover 前 Lead 设 `FLYWHEEL_FLY324_SWEEP_EXCLUDE`**(当前判断:排除 FLY-319/323 parked + LEARN-23/56 别项目;清 FLY-328/329/330/331)—— cutover 那刻终核(319/323 复验若已做完则从 exclude 拿掉一起清)。
- **Cutover audit checklist 必查一项(design-review #3,non-blocking):** boot sweep 只看持久化的 DB 行,**看不到 incoming landing payload**。所以『有 PR 但 DB `pr_number` 没持久化(complete --route 丢失且无 marker)』的历史 session 在 sweep 眼里仍像 no-PR 僵尸。`!landingStatus?.prNumber` guard 只护 live handler、护不到 sweep。→ Lead cutover 终核时,除 parked,**也要核一遍目标集里有没有『其实有 PR、只是 pr_number 没落库』的**,有就一并 exclude。当前 8 个目标已逐个核过均无 PR(§FLY-324 audit),但这条要进 cutover SOP。
