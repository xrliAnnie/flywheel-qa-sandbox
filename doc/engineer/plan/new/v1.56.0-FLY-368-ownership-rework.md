## 1. Why a rework (Annie's insight)

#327 shipped (default-OFF, live): unified channel + per-error threading + conservative auto-repair, with **one fixed bot** (`TADASHI_BOT_TOKEN`) posting every alert. Annie's correction:

> **发 alert 不需要那 agent 活着。** bot token 只是凭据 —— **Bridge 直接拿坏掉 agent 自己的 bot token 发**(显示成「那 agent 的 bot 发的」= 归属正确,实为 Bridge 发,agent 进程死了也照发)。

This is correct and we already have the pieces: the Bridge holds **every** lead's `*_BOT_TOKEN` in its env (verified — all 12 present), and the pre-#327 per-lead alert path already resolved `lead.botTokenEnv` from `process.env`. So "post as the stuck agent's own bot" needs no new credential — just route the SEND through the stuck agent's token instead of one fixed token.

## 2. New ownership model

| Concern | Model |
|---------|-------|
| **Channel** | ONE unified channel = **Flywheel Ops** (Tadashi renames + moves to Text Channels via Claude-in-Chrome, gives new channel id). scope = alert + ops/status. (Channel routing unchanged from #327; only the id changes.) |
| **Send (alert attribution)** | post via the **stuck agent's own bot** → 归属正确(「Rafiki 的 bot 报 Rafiki 卡了」,即使 Rafiki 死了). Fallback chain: stuck agent's bot **→ Aunt Cass (`CASS_BOT_TOKEN`) → alphabetically-next lead's bot**. |
| **Repair (auto-repair)** | attributed to **Aunt Cass** (the fleet-recovery CoS): ack / repair-result / resolved / archive thread messages post via `CASS_BOT_TOKEN`; Cass unavailable → alphabetically-next. **Narrative this produces in each per-error thread:** root (channel top-level) = 「谁几点坏了」via the **stuck agent's bot**; thread ack→fix→resolved = 「Bot 几点修好了」via **Cass's bot**. Exactly Annie's "谁坏 / Cass 修" picture.

**Invariants preserved (unchanged from #327):** all default-OFF / byte-compat; conservative auto-repair = only runner `continue` nudge + resume-menu Enter, both audited fail-closed; never restart/kill; `permission_blocked`/compact-prompt → human; restart-safe reconcile as recovery truth.

## 3. Design (delta from #327)

### 3.1 Shared token-chain resolver (new)
`resolveFirstAvailableBotToken(candidateEnvNames: string[]): { tokenEnv, token } | null` — returns the first candidate whose `process.env[name]` is non-empty. Pure + unit-tested. Candidate lists are built per-concern:

- **Send chain** for an alert about lead `L`:
  `[ ...ownBotEnvs(L), CASS_TOKEN_ENV, ...allLeadsAlpha ]`, de-duped preserving priority.
  (runner alert: `L` = owning lead from `payload.leadId`.)
- **Repair chain**: `[ CASS_TOKEN_ENV, ...allLeadsAlpha ]`, de-duped.

**Own-bot contract (Codex R1 LOW-4):** owner attribution means `L.botTokenEnv` FIRST; for byte-compat with legacy-only configs, fall to `L.alertBotTokenEnv` then inline `L.botToken` as compat candidates BEFORE Cass — so a lead configured only the legacy way still attributes to itself, not Cass. Startup WARN when a lead has no `botTokenEnv` (attribution will lean on compat/fallback).

`allLeadsAlpha` = every configured lead's resolvable bot env, sorted by `agentId` (fleet-wide, deterministic). De-duped, preserving the priority prefix; the stuck lead and Cass are not special-cased out (the de-dup handles overlap, e.g. stuck lead == Cass).

### 3.2 Robust "unavailable" = token missing OR POST fails — ONE shared send helper (Codex R1 MEDIUM-2)
"bot 不可用" must cover BOTH (a) token absent from env AND (b) POST rejected (403 no channel perms / 401). Factor a single **`postAlertWithSendChain(payload, channelId): { ok, messageId?, usedTokenEnv?, transient?, status? }`** used by BOTH `alert()` (first send) AND `drainQueue()` (retry), so the retry path is never the old single-token logic:
- iterate the send chain **in order, attempting the Discord POST**; first 2xx wins (return `messageId` + `usedTokenEnv`);
- a permanent rejection (401/403/404) on a candidate → try the NEXT candidate;
- a transient (429/5xx/network) on a candidate → **stop**, report transient (do NOT burn the chain on a transient blip) → `alert()` enqueues, `drainQueue()` leaves the file for the next pass;
- only when **every** candidate permanently fails → dead-letter.
The chain is recomputed at drain time (config/env may have changed); **tokens are NEVER persisted in queue files** (only the payload). The pre-POST claim (claims.db + `tryClaimLeadEvent`) happens once in `alert()` before the chain, so one logical alert = at most one claim regardless of how many candidates the chain tries; `drainQueue()` stays outside the claim path (unchanged) but now routes through the same helper.

### 3.3 `LeadAlertNotifier` changes
- `unifiedAlert` drops the fixed `token`; gains the **lead roster + repair-bot env name** (default `CASS_BOT_TOKEN`, override `FLYWHEEL_ALERT_REPAIR_BOT_TOKEN_ENV`) so it can build send chains. (`projects` already available.)
- `resolveChannel` unchanged (unified channel id).
- Root `alert()` send: build the send chain for `payload.leadId`'s lead → call the shared `postAlertWithSendChain` (§3.2). Return `channelId` + `messageId` + `usedTokenEnv` (informational; **never the token value**).
- **Severe DM (Codex R1 LOW-3):** the winning root token stays PRIVATE inside `alert()` and is reused for the severe-DM fan-out — so the DM is sent by the same bot that visibly posted the root (no independent re-resolve that could pick a different bot).
- `findUnreachableAlertLeads` matrix updated: in unified mode a lead is unreachable only if the WHOLE send chain (own → Cass → alpha) resolves nothing — practically never. No per-lead noise. The threading fail-loud is reframed in §3.5 (resolvable repair CHAIN, not Cass specifically).

### 3.4 `AlertChannelHub` changes
- `createDiscordOps` now takes an **ordered candidate token list** (the repair chain) and, per operation (createThread / postToThread / archive), tries candidates in order, falling through on 401/403/404, returning success on first 2xx (Codex R1 HIGH-1). It resolves env lazily per call so a token that appears later still works; no single fixed token captured.
- Thread is created off the stuck-agent's root message by the **first usable repair bot (Cass, else alpha)** — the repair owner. Root-bot and repair-bot both need Flywheel Ops post perms; if the repair bot can't post, thread creation fails → degrade to root-only (existing best-effort behavior, unchanged).
- Auto-repair audit `actor` = `"aunt-cass"` (was `"auto-repair-bot"`); gate logic unchanged.
- Reconcile / onLeadRecovery / alert_threads schema — unchanged.

### 3.5 plugin.ts wiring
- Read Flywheel Ops channel id (`FLYWHEEL_UNIFIED_ALERT_CHANNEL_ID`), `FLYWHEEL_ALERT_REPAIR_BOT_TOKEN_ENV` (default `CASS_BOT_TOKEN`), `FLYWHEEL_ALERT_THREADS`, `FLYWHEEL_AUTO_REPAIR`.
- Build the lead roster from `projects` → send chains (per-agent) for the notifier, repair chain (Cass → alpha) for the Hub.
- **Hub enable gate (Codex R1 HIGH-1):** enable the Hub when channel id set AND `FLYWHEEL_ALERT_THREADS=1` AND `resolveFirstAvailableBotToken(repairChain)` finds ANY token (NOT "Cass specifically"). Disable threading ONLY when the entire repair chain is empty. Emit a loud log + meta-alert when Cass is NOT the first usable repair bot (degraded attribution), but still run on the alpha fallback.

## 4. Decisions (RESOLVED — Tadashi/Annie confirmed 2026-06-22, instruction-reply 581e890b)

1. **Runner alert attribution** = the **owning lead's** bot (runners have no own bot). ✅
2. **"alphabetically next"** = by `agentId`, **fleet-wide** across all projects. ✅
3. **Thread creation bot** = **Cass's bot** creates the thread off the stuck-agent's root (Cass owns the repair thread). ✅
4. **"unavailable" semantics** = token-missing **OR** POST-rejected (403) both fall through the chain (§3.2, most robust). ✅
5. **Channel perms (operational)**: Tadashi grants all lead bots post access when building Flywheel Ops; if a bot can't post, the fallback chain degrades gracefully (acceptable). Tadashi owns channel setup + the new channel id. ✅
