## 1. 真机研究关键结论(全部真机验证)

1. legacy `sandbox`(read-only)只挡写+网络、**不挡读**。
2. `[permissions]` profile `filesystem deny` Seatbelt 内核层真挡读;`app-server --strict-config` 接受,`thread/start` 回显 `activePermissionProfile:{id,extends}`。
3. **坑 A**:传 legacy `sandbox` 参数 → `activePermissionProfile:null`(profile 禁用)。必须**同时**去三处 legacy 覆盖(thread-param `sandbox` + TUI `-s read-only` + config 顶层 `sandbox_mode`)。
4. **坑 B**:`~/.codex*` 单星不挡;bare `**/.env` 被拒。✅ 生效:`~/.codex**`、`~/**/.env**`(覆盖 `.env`/`.env.local`/`.env.production`/`.envrc`/`.env.example` + 任意深度含单层),精确目录/文件即 deny。
5. **外科手术边界**:不 deny `~/.flywheel` 目录,只 `~/**/.env**` deny 其中密钥文件 → `~/.flywheel/.env` DENIED 而 `comm/teamlead.db/bin/state/deployed-sha` ALLOWED。
6. **env 也是 exfil 面(R2-B1,真机验证)**:`[shell_environment_policy] exclude=["*TOKEN*","*SECRET*","*KEY*"]` → model exec shell `printenv FOO_TOKEN` 返回**空**(隐藏),非 token 名 env 仍可见。沙箱只约束 exec shell;Lead node 运行时 + app-server 进程读 CODEX_HOME 在沙箱外。
7. **daemon 重读 config(R2-B2,真机确认)**:`codex remote-control stop` 存在;长驻 daemon 在 start 时读 config,flag-on 改 config 后必须 stop+start 才生效。
8. `thread/resume` 的 profile 回显在无-auth 测试环境无法确证(turnless thread 报 `no rollout found`);但 `thread/start` 恒回显 → 据此设计 ephemeral-start 强制门(§3.5)摆脱 resume-echo 依赖。

## 3. 改动清单(全部 PR-only)

### 3.1 单一真相:read-deny config 片段(新文件)
`packages/teamlead/scripts/templates/codex-read-deny-profile.toml` —— 含 `default_permissions="flywheel-lead-secret-deny"`、`approval_policy="never"`、`[shell_environment_policy] exclude=[...]`(B1)、`[permissions.flywheel-lead-secret-deny]` extends `:read-only` + §2 filesystem deny + absent 凭据注释。**唯一真相**:shell append,TS 测试断言(防漂移/单星回潮/`~/.flywheel` 一刀切回潮/缺 env 洗白)。

### 3.2 config parse(`codex-lead-runtime.ts`)
- `readDeny = env.FLYWHEEL_CODEX_LEAD_READ_DENY === "1"` → `CodexLeadRuntimeConfig.readDeny`。
- `readDeny && sandboxMode!=="read-only"` → **parse-time fail-loud**(R1-#8 一致化)。

### 3.3 `buildThreadParams`(headless + TUI 共用)
- `readDeny && read-only` → **不写** `params.sandbox`;留 `approvalPolicy:"never"` + `cwd`/`baseInstructions`。否则现状(字节兼容)。

### 3.4 `tui-window.ts buildTuiCommand`
- `TuiWindowSpec` 加 `readDeny?`;true → 省略 `-s read-only`(留 `-c approval_policy=never`)。

### 3.5 boot 强制 enforcement 门(两个 runtime)(R1-#2/#3 + R2-B3,fail-closed 内建)
- 新纯函数 `assertReadDenyProfileActive(descriptor)`:断言 `activePermissionProfile == {id:"flywheel-lead-secret-deny", extends:":read-only"}`(id+extends 双断言);null/错/缺 → throw。
- read-deny 启动序列(`ensureThread`):
  1. **ephemeral 强制门**:`startThreadWithResult`(一次性 throwaway thread,**非 model turn**)→ `assertReadDenyProfileActive`(证明 daemon 的 `default_permissions` profile 已激活 = 实际 enforcement 来源);失败 → fail-closed(**不启动 Discord gateway / 不建 TUI 窗口**);随后丢弃该 throwaway。
  2. **resume 真 thread**:`resumeThreadWithResult` 保记忆;若 resume 结果**含** `activePermissionProfile` 则同样硬断言(额外保险);**不依赖** resume 回显(门已由步 1 把守)。
- 这样把守不依赖未确证的 resume-echo,且不读真 `auth.json`、不靠 model turn。

### 3.6 `codex-lead-tui-home.sh` ensure-home(R1-#1 + R2 非阻塞 1/2)
- flag-on:**原子重写**已知安全 read-deny 形态 —— 仅保留既有 trusted `[projects]`(**TOML 安全引用 key**,路径含特殊字符需转义),append 3.1 片段,**保证无顶层 `sandbox_mode`**;tomllib 校验:`sandbox_mode is None` 且 `default_permissions==` 且 `[shell_environment_policy].exclude` 含三 token 类 且 filesystem **每个 key 的值 == "deny"**(键+值双校验)且 `approval_policy=="never"`;否则 fail-close + 迁移指引。
- flag-off:现状 pin,既有旧 config 不 fail-close(零 live)。

### 3.7 `codex-lead-tui-home.sh` ensure-daemon(R2-B2,daemon 重读 config)
- flag-on:**先 `codex remote-control stop`(幂等容错)再 `start`** → daemon 重读重写后的 config。
- flag-off:**现状幂等 `start`**(不 stop)—— 字节兼容,普通重启不打断 daemon。

### 3.8 dry-run/报告(R2 非阻塞 3)
- dry-run 报告显式打印:`readDeny=on/off`、是否需 daemon 重启、boot 门用 ephemeral-start 断言。

### 3.9 不碰
- `confinement.ts` / write-capable gate / `washActionSecretEnv`(headless,已有)/ 出站 / 任何 live config/launchd/Mufasa 进程(cutover 才动)。

## 4. 测试(TDD)
