## Background

Audit (`exploration/new/v1.27.0-FLY-137-runner-pipeline-gaps-audit.md`) found 5 confirmed gaps in the Runner pipeline. The biggest single defect is that `AgentDispatcher` (which already exists and works) is wired with `undefined` at the only production call site (`run-infra.ts:231`), so every Runner runs with a baseline prompt — GeoForge3D's 11 specialized `*-executor.md` files are dead code from the Runner's POV.

Annie's product decisions (locked via team-lead Round 1):
- **Q1**: zero-config new project gets a Flywheel-shipped `generic-executor.md` fallback (option a)
- **Q2**: Lead may override the dispatcher via an `agentName` field on `/api/runs/start` (yes)
- **Q3**: `onboard` runs every Runner start — always clean (option a)
- **Q4**: Bridge auto-triggers `codex-design-review` on `plan → design_review` and `codex-code-review` on `pr_created` (option c — both)

This plan fixes the wiring, adds the fallback, adds the override surface, adds the onboard stage, and adds the Codex auto-trigger — in that order.

## Solutions per gap

### Gap A + B + C: wire AgentDispatcher with shipped generic fallback

**Type changes** (`packages/edge-worker/src/AgentDispatcher.ts` + `Blueprint.ts`):

```ts
// AgentDispatcher.ts
export interface AgentDispatchResult {
  agentName: string;
  agentConfig: AgentConfig;          // existing — agent_file is RELATIVE
  matchMethod: "label" | "default" | "shipped-generic" | "override";  // v1.27.1: dropped "haiku"
  agentFileRoot: "project" | "flywheel";  // which root to resolve agent_file against
}
```

Critical fix from Codex Round 1: `readAgentFile` rejects absolute paths (Blueprint.ts:745). So we cannot encode shipped-generic as `<flywheelRepoRoot>/agents/generic-executor.md` absolute. Instead carry the root choice on the result, and let Blueprint resolve relative to the matching root.

**v1.27.1 — 3-step deterministic dispatch chain** (Haiku step dropped):

```
1. Override     → if ctx.agentName provided, dispatchByName(name); throws on unknown
2. Label match  → first issue label that matches any agent's match.labels[] (case-insensitive)
3. Shipped     → if agents map empty OR no label match, return shipped-generic
                  (alternatively, project's default_agent if declared)
```

Step ordering matters: Lead override (explicit intent) > label match (declared mapping) > shipped fallback (zero-config). Each step is deterministic — same inputs always yield same agent, no LLM dice rolls.

**`AgentDispatcher` extension**:
- Constructor adds `flywheelRepoRoot: string` (required, validated non-empty).
- **Constructor drops `classifyFn` parameter and `agentKeywords` plumbing** (v1.27.1: no Haiku).
- Label match path: case-insensitive comparison against `agent.match.labels` array; any label in any agent's array wins; **multi-alias support is the existing array semantics** — projects declare `match.labels: ["designer", "design", "ui", "ux"]` and any of those matches. No new code path needed; just ensure `match.labels` array supports multiple entries and add an acceptance test.
- Add **step 3** (shipped-generic fallback): when label match returns no agent AND project has no `default_agent` configured, return synthesized `{ agentName: "generic", agentConfig: { agent_file: "agents/generic-executor.md", match: {labels:[]} }, matchMethod: "shipped-generic", agentFileRoot: "flywheel" }`. If `default_agent` IS configured, use that instead (matchMethod: "default").
- Add new public method `dispatchByName(name: string)`: bypass label match — used by Lead override.
  - If `name === "generic"` → return shipped-generic result (`agentFileRoot: "flywheel"`)
  - If `name` ∈ `agents` map → return that config with `matchMethod: "override"` and `agentFileRoot: "project"`
  - Else → throw `InvalidAgentNameError` with `available: string[]`

### Dispatch + worktree persistence: reuse existing patchSessionMetadata (FIX FROM CODEX ROUND 2 #1 + ROUND 3 #2 + ROUND 4 #4-5)

**Codex Round 4 caught**: `StateStore.patchSessionMetadata(executionId, fields)` ALREADY EXISTS at `packages/teamlead/src/StateStore.ts:683-721`, and `worktree_path` is ALREADY a column in the `sessions` table (`StateStore.ts:180-190`) AND already in the patchSessionMetadata field map (line 698). What's missing is: (a) Blueprint never calls it for agent_name/agent_match_method/worktree_path, (b) the field map doesn't include the new agent fields, (c) the event-route doesn't have a handler that calls patchSessionMetadata for these fields.

**Approach: extend the existing method + add a thin event channel; do NOT migrate worktree_path.**

- `StateStore.SessionUpsert` interface: extend to include `agent_name?: string`, `agent_match_method?: string`, `plan_path?: string`, `codex_skip?: number` (SQLite boolean as 0/1).
- `StateStore.patchSessionMetadata` field map (line 690): extend to map the four new fields. **No new method**, just adds to the existing map.
- Schema migration: ADD COLUMN `agent_name TEXT`, `agent_match_method TEXT`, `plan_path TEXT`, `codex_skip INTEGER DEFAULT 0`. **Do NOT add `worktree_path` — it exists.**
- Add method on the `ExecutionEventEmitter` interface (`packages/edge-worker/src/ExecutionEventEmitter.ts:18-33`):
  ```ts
  patchSessionMetadata?(execId: string, fields: {
    agent_name?: string;
    agent_match_method?: string;
    worktree_path?: string;
    codex_skip?: number;        // 0 or 1 (SQLite INTEGER convention)
    plan_path?: string;
  }): Promise<void>;
  ```
  The `session_metadata_patched` event payload schema in event-route mirrors these fields with the same names.
  **Method is optional** (per Codex Round 3 #4 — avoids compile-break). Blueprint null-checks before calling.
- Implementor updates:
  - `TeamLeadClient` (`ExecutionEventEmitter.ts:35`): adds the method, emits new event type `session_metadata_patched` to `/events`.
  - `NoOpEventEmitter` (`ExecutionEventEmitter.ts:243`): noop implementation.
  - Test stubs in `Blueprint.test.ts:489-499`: rely on the optional null-check (no required change).
- Event handler in `event-route.ts`: handles `session_metadata_patched` → calls `StateStore.patchSessionMetadata(execId, fields)`.
- `DirectEventSink.patchSessionMetadata()`: forwards to StateStore.
- `Blueprint.run()` calls `patchSessionMetadata` at TWO points (per Codex Round 4 #5, **both must be awaited**, NOT fire-and-forget, to avoid races):
  - **After `worktreeInfo` is computed (~line 202)**: `await this.eventEmitter.patchSessionMetadata?.(execId, { worktree_path: worktreeInfo.worktreePath })`. Property is `worktreePath` per `WorktreeManager.WorktreeInfo` (lines 24-30); Blueprint already reads `worktreeInfo.worktreePath` at line 197-202. **Adapter execution does not start until this resolves.** This is the implementation invariant that closes the race.
  - **After `dispatchResult` is computed (~line 254)**: `await this.eventEmitter.patchSessionMetadata?.(execId, { agent_name: dispatchResult.agentName, agent_match_method: dispatchResult.matchMethod })`.
  - Implementation note: both calls go through the same event type; field set differs.

**Why worktree_path matters**: Bridge needs it to write `.flywheel/runs/<execId>/codex/skip.json` (Bridge's only write) inside the Runner's worktree where `await-codex-gate` reads it. Without it, the skip marker lands in Bridge's cwd and the gate fails-closed even on authorized skips.

**Bridge write responsibilities (per Codex Round 4 #2 — Bridge MUST NOT write review JSON)**:
- Bridge writes ONLY `skip.json` (for authorized skips at stage-transition time).
- Runner/Codex writes `design-review.json` and `code-review.json` (these are the **approval results** — if Bridge wrote them, the gate would be self-authorizing).
- Bridge MAY read and validate the review JSON files in defense-in-depth checks, but never creates them.

**Fail-closed on missing worktree_path**: if Bridge handles `stage_changed design_review` and `session.worktree_path` is null (extremely unlikely after this fix): log error, do NOT write skip.json, do NOT insert normal Codex instruction; instead insert an ERROR instruction telling Runner the gate is broken. `await-codex-gate` will then time out → exit 1 → Runner reports via `complete --route blocked`.

**Acceptance**: label-selected (not just override) agent is persisted on session row. Test: spawn Runner without `agentName`, with label-match → session row has `agent_name="frontend"`, `agent_match_method="label"`, `worktree_path` already populated from worktree creation patch.

**Test for await-not-fire-and-forget**: simulate a slow `patchSessionMetadata` (mock delays by 100ms); assert `adapter.execute()` does not begin until the patch resolves. Scoped to Blueprint unit test.

**Onboard stage semantics** (FIX FROM CODEX ROUND 1 #8 + ROUND 2 #2 — failure path uses existing `complete --route blocked`, NOT a non-existent `stage set error`):

- `onboard` means **"Runner attempted onboarding"**, not "onboarding succeeded".
- Runner protocol (in Blueprint system prompt):
  1. Call `flywheel-comm stage set onboard` BEFORE attempting the onboard skill — so the stage indicates intent.
  2. Attempt the `onboard` skill (or role-specific variant `onboard-{designer,product,operations,marketing,qa}` if matching agent role exists).
  3. On **success** → call `flywheel-comm stage set brainstorm`.
  4. On **absent skill** (skill file not present) → call `flywheel-comm stage set brainstorm` directly; legitimate "new project, no onboard skill defined" case.
  5. On **failure** (skill threw, hard error) → report the failure in a Discord message to Lead, then call `flywheel-comm complete --route blocked --summary "onboard_failed: <reason>"`. This is the existing terminal failure channel (`packages/flywheel-comm/src/commands/complete.ts`, VALID_ROUTES includes "blocked"). The Bridge sees `session_completed` with `decision.route="blocked"` and Lead is notified.
  6. On **hang** (no progress after a reasonable time as judged by the agent) → Lead's idle watchdog will surface it via FLY-92 system-level detection; agent itself should set `complete --route blocked` if it detects it's stuck.

**No new `error` stage added** — we reuse the existing fail-route channel. This avoids extending VALID_STAGES + payload schema, and keeps the failure-reporting path consistent with how Runners report any other terminal failure today.

**`Blueprint.ts` prompt change**:
- Inject onboard instructions at the **top** of the system prompt (before agent role injection):
  > "Pipeline preamble: (1) `flywheel-comm stage set onboard`. (2) Attempt the `onboard` skill (or `onboard-<role>` matching your agent role) to load project context. (3) If the skill succeeds, `flywheel-comm stage set brainstorm` and proceed. (4) If the skill is missing in this project (file absent), `flywheel-comm stage set brainstorm` directly. (5) If the skill threw a hard error, do not silently proceed — call `flywheel-comm complete --route blocked --summary 'onboard_failed: <reason>'` and stop."
- Reuses existing `commCliPath` constant; no new dependency.

**`flywheel-comm/commands/stage.ts`**:
- `VALID_STAGES` is the local copy at `packages/flywheel-comm/src/commands/stage.ts:71-86`. Add `onboard`.
- Tests in `packages/flywheel-comm/src/__tests__/stage.test.ts` already cover 10 stages — extend to 11 (add `onboard`).
- Note: stage CLI remains fail-open for normal stages (existing behavior, lines 174-189). See "Codex gate" below for blocking semantics on guarded stages.

**Invocation / distribution (FIX FROM CODEX v1.27.1 #3 — concrete supported paths)**:

The package mirrors `flywheel-comm`'s pattern (`bin: { flywheel-comm: "dist/index.js" }`). Since Flywheel is **not yet npm-published** and projects (like GeoForge3D) sit alongside the Flywheel checkout, v1.27.1 ships THREE supported invocations:

1. **Monorepo-local** (running from anywhere in the Flywheel repo or its worktrees):
   ```bash
   pnpm --filter flywheel-cli exec flywheel <command> [--project-path /path/to/target/project]
   ```
   Uses pnpm workspace symlinks. No install step needed beyond `pnpm install` at the Flywheel root.

2. **Global link** (operator convenience after one-time setup):
   ```bash
   cd <flywheel-repo>/packages/flywheel-cli
   pnpm build
   pnpm link --global
   # then from anywhere:
   flywheel <command> [--project-path .]
   ```

3. **Direct node invocation** (CI / scripts that can't rely on pnpm link):
   ```bash
   node <flywheel-repo>/packages/flywheel-cli/dist/index.js <command> [--project-path .]
   ```

Phase 7 (GeoForge3D companion) uses option 1: `pnpm --filter flywheel-cli exec flywheel migrate-agents-path --project-path ~/Dev/GeoForge3D`. The CLI accepts `--project-path` (defaulting to `process.cwd()`) so the operator doesn't need to `cd` into the target project first.

**Out of scope for v1.27.1**: publishing `flywheel-cli` to npm (would enable `pnpm dlx flywheel-cli init` from any machine without the Flywheel repo). File this as a v1.28 follow-up if Annie wants the smoother UX once Flywheel stabilizes.

**Root `package.json` addition (optional, defensive)**: add a script alias `"flywheel": "pnpm --filter flywheel-cli exec flywheel"` so operators in the Flywheel monorepo root can type `pnpm flywheel init` directly. Minor convenience; not required for correctness.

**`flywheel init` behavior**:
1. Verify `<project-path>` is a git repo (else error: "flywheel init must run inside a git repository").

### Gap E: Codex auto-trigger (revised after Codex Round 1)

Codex Round 1 caught four design holes here. Revised design:

**Where Bridge sees stage transitions**: `event-route.ts` `/events` endpoint (lines 724-840), NOT a new `/api/sessions/:executionId/stage` route. Stage transitions come in as `event_type=stage_changed` payloads.

**Where Bridge writes the instruction**: directly to `CommDB` via `new CommDB(defaultGetCommDbPath(projectName)).insertInstruction("bridge", execId, message)` — NO subprocess shell-out. The CLI signature `flywheel-comm send --from bridge --to <execId>` would also work but adds a fork-per-instruction; direct DB write is cleaner.

**Stage metadata for plan path** (FIX FROM CODEX #5):
- `flywheel-comm stage set design_review --plan <relative-path>` — new flag.
- CLI validates `--plan` is a relative path inside the worktree (similar to ConfigLoader's path-safety check), strips `..` segments, rejects absolute.
- Stage payload extended: `{ stage: "design_review", plan_path: "doc/engineer/plan/draft/v1.27.0-FLY-137-...md" }`.
- Bridge `/events` handler persists `plan_path` to `StateStore` session (new TEXT column `plan_path`).
- When Bridge fires the design_review Codex trigger, it reads `plan_path` from the session and includes it in the instruction.

**Trigger flow (per transition)**:

For `stage_changed` to `design_review`:
1. Bridge handler in `event-route.ts` reads `session.codex_skip` (snapshotted at run start; see "Skip path" below). If `true`, write skip.json marker into `<session.worktree_path>/.flywheel/runs/<execId>/codex/skip.json` (atomic temp+rename) and return ok WITHOUT inserting Codex instruction. **Does NOT call Linear at stage-transition time** — pure session row read.
2. Bridge reads `session.plan_path` from StateStore (must be non-null, else **fail-closed** — see "Missing plan_path" below).
3. Bridge writes instruction to CommDB:
   > "Run `/codex-design-review <plan_path>`. Iterate on findings until Codex returns APPROVED. Write the approved result to `.flywheel/runs/<execId>/codex/design-review.json` with schema `{executionId, reviewType:"design", status:"APPROVED", reviewedTarget:"<plan_path>", timestamp}`. Then call `flywheel-comm await-codex-gate design --exec-id <execId>` (blocks until Bridge confirms result) before `flywheel-comm stage set implement`."
4. Runner inbox picks up instruction, agent runs `/codex-design-review`, iterates, writes JSON result, calls await-codex-gate (which polls the file + Bridge confirmation), then sets stage.

For `stage_changed` to `pr_created`: same pattern with `code-review.json` and `flywheel-comm await-codex-gate code`.

**Blocking gate command** (FIX FROM CODEX #4 — stage CLI is fail-open):

New CLI subcommand `flywheel-comm await-codex-gate <type> --exec-id <execId>`:
- Reads `.flywheel/runs/<execId>/codex/<type>-review.json` from disk.
- If absent → poll every 2s (max 30 min); on timeout exit 1.
- Validates JSON schema: `executionId === execId`, `reviewType === type`, `status === "APPROVED"`, `timestamp` within 24h, `reviewedTarget` non-empty. On mismatch exit 1.
- (Optional) Posts to Bridge `/api/codex-gate/confirm` to cross-check Bridge's view; if Bridge disagrees, exit 1.
- On all checks passing → exit 0 (Runner proceeds).

Failure path is **fail-closed** (non-zero exit) — this is what makes the gate enforceable, unlike fail-open `stage set`.

**Result file format** (FIX FROM CODEX #6 — `/tmp/*.result` too weak):
- Location: `.flywheel/runs/<execId>/codex/{design,code}-review.json` (inside the Runner's worktree, not /tmp).
- Atomic write: write to `*.tmp`, then `rename()` (POSIX atomic).
- Required JSON schema:
  ```json
  {
    "executionId": "<uuid>",
    "reviewType": "design" | "code",
    "status": "APPROVED",
    "reviewedTarget": "<plan-path-or-pr-url>",
    "timestamp": "<ISO-8601>",
    "rounds": <integer>,
    "codexThreadId": "<string>"
  }
  ```
- Validation enforced by `await-codex-gate` command (above).

**Bridge-side enforcement (optional, defense-in-depth)**:
- Bridge `/events` handler can additionally reject `stage_changed` events transitioning to `implement` or `approve` if the corresponding gate JSON doesn't exist. But since `stage set` is fail-open at CLI level, this is **defense-in-depth** — the real gate is the blocking `await-codex-gate` command.
- Bridge does log violations for audit (when Runner skips await-codex-gate and jumps stages directly).

**Skip path (FIX FROM CODEX ROUND 2 #3 + ROUND 3 #3 — start-time snapshot semantics, marker file in Runner worktree)**:

Issue label `codex-skip` makes Bridge skip the Codex trigger. **Semantics: start-time / retry-time snapshot, NOT mid-run emergency.**

- Bridge already loads issue labels at run start in `runs-route.ts:145-166` via Linear SDK. We **snapshot** label presence at that moment.
- On run start: if `codex-skip` is in the snapshotted label list, Bridge stores `codex_skip=true` on the session row (new BOOLEAN column, defaults false). Cheap, deterministic.
- On `stage_changed` to `design_review` / `pr_created`: Bridge reads `session.codex_skip`:
  - If `true`: Bridge writes `<session.worktree_path>/.flywheel/runs/<execId>/codex/skip.json` (atomic temp+rename) with payload `{ executionId, reviewType, reason: "codex-skip-label", timestamp }`. Does NOT insert Codex instruction.
  - If `false`: proceeds with normal Codex trigger.
- `flywheel-comm await-codex-gate <type> --exec-id <id>` first checks for `skip.json` at `.flywheel/runs/<execId>/codex/skip.json` in the Runner's cwd:
  - If exists with matching `executionId` + `reviewType` → exit 0 immediately, log `codex-skip-bypass: <reason>`.
  - Else proceed to poll for `<type>-review.json`.

**Why start-time snapshot, not mid-run refresh**: A mid-run Linear refresh would require event-route to call Linear SDK, adding latency + a new failure surface on every stage transition. The Annie-facing UX is: "label the issue with codex-skip before triggering the Runner; if you forgot, cancel and retry."

**Full `codex_skip` data path (Codex Round 4 #3 — explicit threading)**:

1. **Run start** (`runs-route.ts:145-166`): Bridge fetches issue labels via Linear SDK (already does, for FLY-127 + FLY-80). Snapshot `codexSkip = issueLabelNames.includes("codex-skip")` (boolean).
2. **StartRequest** (`run-dispatcher.ts` + `retry-dispatcher.ts`): add `codexSkip?: boolean` field.
3. **Pass-through**: `run-dispatcher.start()` → `Blueprint.run()` reads `ctx.codexSkip` from `BlueprintContext` (add `codexSkip?: boolean` to context type).
4. **Persistence**: Blueprint calls `patchSessionMetadata({ codex_skip: codexSkip ? 1 : 0 })` alongside the agent_name/worktree_path patches (single patch event or separate, implementation choice).
5. **Event-route read**: `event-route.ts` stage_changed handler reads `session.codex_skip` from StateStore.
6. **`Session` interface + `rowToSession`**: extend with `codex_skip?: boolean` (SQLite INTEGER → JS boolean via `!!row.codex_skip`).

**Retry semantics (Codex Round 4 #3 — choose ONE and wire explicitly)**:

**Choice: re-fetch on retry when LINEAR_API_KEY available; otherwise use stored fallback with warning.**

`actions.ts:587-601` retry path is extended:
- Before reconstructing StartRequest, if `process.env.LINEAR_API_KEY` is set, call `LinearClient.issue(issueId).labels()` and re-snapshot `codexSkip`.
- If Linear call fails OR API key absent: fall back to stored `session.codex_skip` with a `console.warn("[actions.retry] Linear label refresh failed; using stored codex_skip=<value>")`.
- Pass the (refreshed-or-stored) `codexSkip` into the new StartRequest.

Rationale: retry-time labels match Annie's mental model ("I labeled it codex-skip, retry the Runner"), but degrade gracefully if Linear unreachable. Tests cover both branches.

**Risk register update**: `codex-skip` is **pre-run only**, not mid-run emergency. Updated wording below.

This avoids any Linear lookup inside `flywheel-comm` — Bridge owns the label snapshot at start, persists it, then writes the marker file at stage-transition time using `session.worktree_path` (now reliably populated by the patchSessionMetadata fix above).

**Missing `plan_path` (FIX FROM CODEX ROUND 2 #4 — fail-closed, not skip)**:

If Bridge handles `stage_changed` to `design_review` with no `plan_path` in payload AND `session.plan_path` is null:
- Bridge writes an instruction to CommDB: `"ERROR: stage_changed to design_review requires --plan <relative-path>. Re-run: flywheel-comm stage set design_review --plan <path>. Codex design review was NOT triggered. Do not proceed to implement until --plan is provided."`
- Bridge does NOT write a skip marker (this is a Runner protocol violation, not an authorized skip).
- Bridge logs `[codex-trigger] missing plan_path — instruction sent to re-trigger`.
- Runner's `await-codex-gate design` will then time out (no skip, no review file) → exit 1 → Runner reports to Lead.

Also: the Blueprint system prompt is updated to mandate `--plan` for `design_review` so Runners get the requirement upfront, not just at runtime.

**Failure handling**:
- Codex auth expired → `/codex-design-review` slash command fails → Runner does NOT write a result file (or writes with `status: "FAILED"`) → `await-codex-gate` rejects/times out → Runner calls `flywheel-comm complete --route blocked --summary "codex_auth_failed: ..."` (existing fail channel) → FLY-83 watchdog alerts Annie.
- Rate limit → `codex-with-fallback` auto-rotates inside Runner session. Only escalates if all 5 profiles burned.
- Hung Codex → `await-codex-gate` 30-min timeout → exit 1 → Runner calls `flywheel-comm complete --route blocked --summary "codex_hung: <type>"`.
- `codex-skip` label (start-time / retry-time snapshot, NOT mid-run) → Bridge writes skip.json marker, Runner bypass exits 0 immediately. Audit-logged. Lead documents reason in Linear comment.

## Risk register (revised)

| Risk | Mitigation |
|---|---|
| Codex inbox trigger races with Runner's own `flywheel-comm` calls | CommDB `insertInstruction` is sequence-ordered + ack'd (FLY-109 infra). Bridge writes the instruction during the `/events` `stage_changed` handler, before responding 200 to the Runner's `stage set` call — meaning the instruction is durable in CommDB BEFORE the Runner's CLI exits. Runner's next inbox poll sees it. |
| Onboard skill exists but fails (read error / hang) | Runner calls `flywheel-comm complete --route blocked --summary "onboard_failed: <reason>"` and stops. Lead receives Bridge `session_completed` with `status=blocked` and can re-issue / triage. Not silent, no new stage needed. |
| Shipped `generic-executor.md` content goes stale relative to product spec | Out of scope for v1.27. File `FLY-???-shipped-generic-content-review` follow-up — quarterly review with PM. |
| `FLYWHEEL_REPO_ROOT` env var not exported in production cron / launchd | Per Codex Round 2 #5 + Round 3 #5 fix: `setupRunInfrastructure({ flywheelRepoRoot? })` is the single canonical resolver — options arg → env → `import.meta.url` fallback. Covers `scripts/run-bridge.ts`, `packages/teamlead/src/index.ts`, and any future entrypoint uniformly. No fail-fast. |
| `codex-skip` label abused (every PR labeled to dodge review) | Audit log records every skip with issue ID + project + lead ID. Quarterly review surfaces abuse pattern. Note: skip is **start-time only**, not a mid-run emergency lever — adding the label after run start has no effect until retry. |
| Renumbered `STAGE_ORDER` breaks an unknown call site that hardcodes a number | Per Codex Round 1 verification: `DirectEventSink:324-335`, `event-route:470-487`, `event-route:522-539` use relative comparisons only. Will re-verify during implementation with `grep STAGE_ORDER\[` for any numeric literal usage. |
| `await-codex-gate` polling consumes CPU during long Codex sessions | 2-second poll interval × 30-min timeout = 900 polls × ~1ms each = negligible. |
| StateStore migration on live DB | Migration is additive (NULL-able columns), runs at startup. Existing rows have NULL for new fields, treated as "no override / no plan path" → backward compatible. |
| `flywheel-comm await-codex-gate` becomes a synchronization bottleneck if Codex hangs | 30-min timeout exits 1, Runner reports error to Lead → FLY-83 watchdog alerts. Runner stays usable for diagnosis. |
| Plan-path validation in `stage set --plan` lets through symlink escapes | Use the same path-safety check as ConfigLoader (`validateAgentPath` pattern, packages/config/src/ConfigLoader.ts:225-240): reject absolute, reject embedded `..`, resolve against worktree root, confirm prefix match. Symlink check via `realpath`. |
