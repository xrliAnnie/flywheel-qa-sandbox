Kimi Code 那条视频，到底有什么值得抄？

FLY-492 · 来源：你在 #core 发的小红书《Codex要是抄一下这个功能就好了！》· owner Tadashi · informs FLY-494

一句话：这条视频的「眼」是 Kimi Code 把整段原始视频塞进 agent 上下文（不是抽几张帧），所以它能看懂「过程」——运镜、节奏、转场——把一段录屏一比一复刻成可玩游戏 / 重制成有镜头语言的视频。 对 Flywheel 来说：很酷，但当前主线（改代码出 PR）用不到视频；真正的决策是——把 Kimi 接进 Runner，是要便宜地换个模型，还是投工程拿那个独一份的视频能力。这份给你拍。
● 视频里那个「值得抄的功能」
别人（含 Codex）· 抽帧

只看到「状态」

把视频切成几张孤立静态图。能懂界面长什么样，丢了帧与帧之间的变化——动作、速度、节奏、转场时机、因果。复刻视频 → 「硬生生做成了 PPT」。

Kimi Code · video-in-context

看到整个「过程」

把连续帧编码成保留时间维度的「时空块」直接进上下文。所以能复现运镜、动画节奏、转场——复刻视频 → 模拟出了摄像机运镜。

「在视频理解这个场景，很可能你用的 Coding Agent 一直都是残血。抽帧看到的是状态，视频上下文看到的是整个过程。」— 视频作者
● 它现场演示了什么
三个「从视频直接生成」的 demo 实拍
  • 录屏 → 可玩游戏：喂一段 2D 对战游戏录屏，「完整复刻」→ 出一个能玩的 HTML5 游戏（WASD 移动、射击、喷涂占地都实现了）。
  • 网页动画 1:1 复刻：连作者录屏时不小心录进去的播放器进度条都一起复刻了——证明它在「看画面」不是「读源码」。
  • 解说视频重制：用 HyperFrame 框架重做一段 SpaceX 财经解说。Codex 版=丢了镜头语言的 PPT；Kimi 版=还原了叙事 + 运镜。

附带还展示了：Agent Swarm（子 agent 蜂群协同）、终端直接 Used ReadMediaFile、可插本地模型（Qwen）。

● Kimi Code 是什么

TypeScript 写的终端 coding agent（开源 MoonshotAI/kimi-code，MIT），定位跟 Claude Code / Codex 一样。模型 = Kimi K2.7-Code（开源、长程 coding 优化）。 官方 API 同时兼容 OpenAI 和 Anthropic 协议——这点很关键，是「便宜接法」的基础。

● 接进 Flywheel Runner：三条路

底层好消息：Flywheel 的 Runner 后端本来就是可插拔的（已经有 Codex 后端在跑），加一个 Kimi 是「沿已铺的路再走一步」，不是新基建。

一条诚实更正 关于 Path B

我初判「Path B 被 headless 卡死」——不准确。概览文档没提无人值守模式，但 kimi acp 参考页确认它就是个干净的 JSON-RPC/stdio 驱动面（能 spawn、发 prompt、流式收工具调用+完成信号，12 个稳定方法实现了 10 个）。 所以 Path B 不是「做不了」，是「能做，但要写一个适配器（真工程，不是改配置）」。这反而让 A vs B 的取舍更清楚。

● 给你拍的决策 · FLY-494 往哪走

Kimi 集成（FLY-494）第一步，走 A 还是投 B？

我的研究结论：先 A、B 待真实视频用例。但你的 vision 是 agent-agnostic CLI 后端（偏 B），所以这个由你拍——把取舍诚实摆给你：

走 A
便宜，立刻拿到「Kimi 这个模型」
几小时、纯配置、骑现成基建。拿厂商多样性/成本/韧性。但拿不到视频能力——claude 的壳不会把原始视频喂给模型。
投 B
投工程，拿到「视频里那个独一份的能力」
写一个 ACP 适配器（可行、与现有 Codex 后端同构，不是死路）。解锁录屏→UI 复刻 / 视觉 QA 这类工作流。前提：先有一个真实视频用例值得它。
两者
A 先上、B 记 backlog spike（我的默认推荐）
A 立刻拿模型多样性收益；B 等一个具体视频用例出现再投。Tadashi 会把你这个结论带进 FLY-494 scoping。
● 一句元观点（值得记）
「谁最先理解模型厂的技术路线、最先在新能力上跑通整个工作流，谁就能在新一轮迭代里最早拿到红利。」
— 这正是 Flywheel 把 Lead/Runner 做成「换后端只是配置」的同一条逻辑。

诚实分层：① 视频明确展示=视频生成可玩游戏代码、能还原时间相关元素、内置 Agent Swarm。 ② 官方证实=Kimi Code 开源 TS CLI、API 兼容 OpenAI/Anthropic、kimi acp 是 JSON-RPC 驱动面。 ③ 我的推断=「视频入上下文」是作者基于 MoonViT-3D 技术路线的解释（非直接日志）；Path A 用的是 Claude Code 自带的「指向第三方端点」能力，且不会带来视频能力。
