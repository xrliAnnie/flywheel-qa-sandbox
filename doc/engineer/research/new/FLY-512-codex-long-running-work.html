OpenAI 让 Codex 跑 25 小时不间断 —— 哪一招值得 Flywheel 抄?

FLY-512 · 来源:你分享的 openai.com/index/codex-maxxing-long-running-work(同源镜像:developers.openai.com 博客 + openai-cookbook 的 /goal 与 repair-loop 两个 notebook)· owner Tadashi

一句话:OpenAI 这套方法的「眼」不是更聪明的模型,而是 把开放式工作变成一串可验证的检查点 + 把目标/计划/状态写进一份反复回看的文件 + 完成必须靠证据而不是模型自觉。 对 Flywheel(我们本身就是长时 agentic 编排系统)来说:这几条里我们一半已经做得更硬(证据驱动 done 是系统级硬门、不自合并、跨进程崩溃恢复、并行)——验证了核心赌注是对的; 真正值得抄的就一个——让 Runner 维护一份「会话内活文档」,它一举解决防漂移 + 上下文压缩存活 + 断点续跑。这份给你拍方向。

核心转变:不是更聪明,是「持续连贯的时长」

GPT-5.3-Codex「Extra High」跑 ~25h、~13M token、~30k 行从零造了个设计工具。论点:长任务成功「与其说靠一个巨型 prompt,不如说靠模型所在的那个 agent loop」——这句话对 Flywheel 直接成立,我们的价值就在 loop(编排/续跑/验证)。

Agent Loop 结构

有纪律的循环

Plan → Edit → Run tools(test/build/lint) → Observe → Repair → Update docs → Repeat。能撑长程靠三样:真实反馈(跑测试拿客观信号)、外部化状态(状态在磁盘不在上下文)、时间可操纵(人在 milestone steer)。

被点名的「最重要技法」

4 文件项目记忆

Prompt.md(冻结规格/non-goals/done-when)· Plan.md(颗粒 milestone+验收+验证命令+决策记录)· Implement.md(runbook/每 milestone 强制验证)· Documentation.md(滚动状态/审计日志)。一静一动:冻结目标 vs 记录变化,人可异步检查。

/goal 命令:thread-scoped 的持久目标契约 最深的一块

心智模型:普通 prompt = ask→work→result→wait;Goal = work→check→continue or complete。一个强 Goal 定义 6 件事:

  • Outcome / Verification surface / Constraints / Boundaries / Iteration policy / Blocked stop condition
  • 架构:Goal 是持久 thread 状态(不是全局记忆),续跑事件驱动(只在 thread idle 续、无工具调用就抑制下次防空转),完成必须证据驱动(不能靠「模型觉得做完了」),预算 ≠ 完成。
  • 工具契约有界:模型只能「发起 Goal」+「证据支持时标完成」;pause/resume/clear 留给用户。
迭代修复环 Review → Repair → Validate

三相之间用机器可读 JSON 结构化交接:Review(只找问题、不改、返 JSON findings)→ Repair(只改最关键的、不假设成功)→ Validate(端到端执行、按 rubric 打分、返 remaining delta)。

收敛/停止:全过 / 最大 3 轮 / delta 稳定 / 停滞 → 触发人工。每轮写 record.json 审计「为什么继续、为什么停」。核心:判断与证明分离、按证据迭代、保留审计轨迹。

一个值得盯住的反差

我们在小红书引擎里做了教科书级的 checkpoint/resume(checkpoint.py:stage 持久 + skip-done + retry cap + 损坏自愈),却没把同样的纪律用到核心的写代码 Runner 上——写代码 Runner 崩了是从整个 issue 重头跑。这正是下面 P1 的最大机会:不是发明新东西,是把已验证的纪律搬过去。

● 可执行改进点(按杠杆排序)

贯穿主线:把 FLY-349 引擎里验证过的 checkpoint 纪律泛化到写代码 Runner;借 OpenAI 的「活文档 + 证据契约」,但不借它的「自主续跑」(那跟我们人类把关模型冲突)。每条可转一个 Linear issue。

A. 每个 Runner 维护一份「活状态文档」(Living Run Doc)P1 keystone

spawn 时建 .flywheel/runs/<execId>/RUN.md,四块对应 OpenAI 的 Prompt/Plan/Implement/Documentation:①冻结规格(目标+brainstorm 结论+non-goals+done-when)②milestone 计划(每个带验证命令+验收)③执行约束 ④滚动状态/决策日志。每个 milestone 后更新、compaction/resume 后先重读。

为什么是 #1:一举解决三件事——防漂移(冻结规格)、上下文压缩存活(状态外化到文件)、async 可检查(不盯 pane 就能看进度)。这正是 OpenAI 点名的「最重要技法」,也是我们唯一缺的「会话内活文档」层。

成本:中(prompt/Blueprint 注入 + 一个文件约定,无新基建)· 雏形:「Runner Living Run Doc — 会话内活文档 + compaction 重定向」

B. mid-task 续跑:fresh Runner 从 RUN.md 断点恢复,不从头重跑 P1 keystone

基于 A。Runner 崩溃/Bridge 重启后,新 Runner 读 RUN.md 的 milestone 状态、跳过已完成 milestone、从断点继续——把 FLY-349 引擎 checkpoint.py 的 skip-done + 幂等 + retry cap 纪律泛化到代码 Runner。

为什么:审计实锤「Runner 崩溃从整个 issue 重头跑」是当前最大的长任务浪费。25h 跑到 20h 挂掉重来 = 灾难。

成本:中(依赖 A 先落地;复用引擎层已验证的 checkpoint 模式)· 雏形:「Runner mid-task resume — 从 Living Run Doc 断点续跑」

C. 把 Codex review loop 形式化成有界 + 可审计的 Review→Repair→Validate P2

每轮写 codex/round-<n>.json(findings+repair 摘要+validate 结果);跟踪 round 数;设软上限(如 3 轮);停滞(delta 不再缩小)→ 触发人工(走现成 ask/gate 升级)。

为什么:当前 review loop 无 round 计数、无逐轮审计、无停滞升级,理论上能无限循环/静默卡住(已有「codex review death detection」follow-up)。

成本:中(复用现有 codex/*.json 约定 + gate 升级)· 雏形:「Codex review loop 有界化 + record-per-round + 停滞→人工」

D. milestone-based plan:write-plan/implement 强制颗粒化 milestone + per-milestone 验证命令 P2

约定:plan 必须列一个 loop 内可完成的 milestone,每个带验证命令(lint/typecheck/test/build)+验收标准;implement 时每个 milestone 后跑验证、失败先修再前进。落进 A 的「②milestone 计划」块。

为什么:我们有粗粒度阶段门(design_review/code_review),但 implement 内部没有「milestone→验证→修→下一个」的细循环。OpenAI 的 plan.md 正是这个。

成本:低-中(skill/prompt 约定)· 雏形:「write-plan/implement 强制 milestone + per-milestone 验证门」

E. context-compaction 重定向 hook(轻量,配 A) P3

给 Runner 一条指令/hook:任何 compaction 后先重读 RUN.md 的冻结规格 + milestone 状态再继续。Anthropic 自己承认「多次 compact 后意图变弱」——外化状态 + 强制重读是最便宜的兜底。

成本:低(一条 prompt 约定 + 可选 PostCompact hook)

F.(有意不做,记录理由)不在 Runner 层加 /goal 式「自主续跑到 done」循环 记一笔

我们刻意要人在 milestone/merge 处把关(founder-only-authority + approve gate)。一个「无人值守持续续跑」的循环跟这个模型冲突,也跟 pr_handoff/human-gated ship 冲突。要借的是 /goal 的契约结构(A/D 已覆盖),不是它的自主循环。写下来是防止有人误把「抄 /goal」理解成「让 Runner 自己一直跑到合并」。

成本:0(决策记录)

● 给你拍的决策

启动哪些改进?

我的研究结论:先做 P1-A(活文档)+ P1-B(断点续跑),它俩是 OpenAI 这套里唯一对我们真有增量的部分;C/D/E 是顺手的跟进。但这由你拍——把取舍诚实摆给你:

只做 P1
活文档 + 断点续跑(最高杠杆,先验证价值)
一举拿到防漂移 + 压缩存活 + 不再从头重跑。复用引擎层已验证的 checkpoint 纪律,风险低。建议起点。
P1 + P2
再加 review loop 有界化 + milestone 验证门
顺手补齐 QA loop 的可审计性(配合已有的 review-death follow-up)+ implement 细粒度验证。一个 sprint 能装下。
先不动
当作「现状体检报告」存档
结论本身有价值:我们的核心赌注被 OpenAI 实践背书,且在证据驱动/安全上更强。改进点转成 backlog issue,等优先级排到。
「长任务成功,与其说靠一个巨型 prompt,不如说靠模型所在的那个 agent loop。」— OpenAI 长任务博客。这正是 Flywheel 的存在理由:我们就是那个 loop。
