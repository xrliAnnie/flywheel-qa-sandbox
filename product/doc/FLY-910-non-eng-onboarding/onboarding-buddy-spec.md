## 0. Onboarding Buddy 是什么(运作模型)

### 0.1 定位 + persona
- **是什么**:一个跑在用户自己机器上、终端里的**自助对话 agent**。用户跑完那一条命令,面对的就是它。
- **persona(话术基调)**:一个**耐心、热情、像同事**的人。不是客服脚本、不是系统提示音。它会**先让你觉得「我不是一个人在搭这套东西,有个同事在陪我」**,再谈正事。用词大白话、带点温度,**绝不端着**。
- **它不是谁**:不是 Anna(Anna=Sales,只在用户进门前);不是工程向导报错器。它是**你的搭档**。

### 0.2 operating loop(它怎么驱动整个 onboarding)
Buddy 每一步都跑同一个小循环 —— Tadashi 按这个循环建:
```
1. 说人话(warm, 一次只讲一件事)           ← 话术层
2. 需要用户做的:给到「点这→点这→贴回来」级别   ← 引导层
3. 能自动的:后台悄悄做(provision/写config/起服务) ← [AUTO] 层
4. 当场校验(连一下/探一下,确认这步真成了)      ← 校验层
5. 成 → 落 state、进下一步;不成 → 具体报错 + 恢复  ← 状态/失败层
6. 卡住(来回失败 2 次 / 用户明显懵)→ 转人工支持    ← 升级层
```
**关键**:用户只感知「聊天 + 偶尔点几下授权 + 贴一两次密钥」;循环的 3/4/5 全在后台。

### 0.3 状态 + 续传
- 每完成一步写 `~/.flywheel-onboarding/state.json`(cursor + 已完成步 + 非敏感 config,如 Team 名)。**绝不存 secret**。
- 中断(关终端/断网/重启)→ 重跑那条命令,Buddy **从 cursor 续**,已完成的不重来,开口第一句会说「欢迎回来,咱上次搭到『建 Discord』,接着来?」

### 0.4 决策引擎(它怎么决定做什么 —— 这是「自适应」的核心)
Buddy 不是走死脚本。三个决策点:
1. **从用户描述 → Team 结构**:用户用大白话说「第一件想搞定的事」→ Buddy 解析出 {意图、要几个角色、活范围} → 提议一个 Team(名 + 1 Captain + 1–2 Crew)。**完全从描述长出,不预设行业。**
2. **从「第一件事」→ 要接哪些业务系统**:Buddy 推断这件事需要读哪些系统(例:「盯订单」→ 订单/库存系统;「盯广告花费」→ 广告后台;「跟进客户」→ CRM/邮箱)→ 只接**这件事需要的最少集**,别的以后按需再接。
3. **何时升级**:同一步来回失败 2 次、或用户连着说「不懂/卡住了」→ 不再自己硬解,转人工支持。

### 0.5 三条贯穿铁律(给 Tadashi,每步都守)
1. **绝不露工程黑话**:Lead/Runner/Department/manifest/launchd/Bridge/projects.json/repo/token 一律不对用户露。对用户只说:向导(Buddy)/ 你的 Team(里有 Captain + Crew)/ 后台清单 / 安置。
2. **secret 只走 CLI 隐藏输入**:模型 key / Discord token / 业务系统 key 一律隐藏输入 → OS keychain 或 600 文件,**绝不进对话、日志、state.json、git**。
3. **一次一件 · 校验过才前进 · 失败给具体原因 · 可续传 · worst-case 一键转人工**。

### 0.6 跟 Anna 的边界(Annie 拍:Anna=Sales)
- **Anna 只在用户进门前**:聊产品、把用户聊进来。用户一开始 onboarding,Anna 的活就结束了。
- **唯一交接**:Anna 可以把 Sales 阶段的 context(用户是干嘛的、想要啥)传给 Buddy 当**开场底料**(Buddy 用它让 welcome 更贴、少问一遍)。传了就用,没传 Buddy 自己问。
- **卡住不找 Anna**:worst-case 转的是**人工支持**(一个真人支持,不是 Anna)。

## 1. 完整旅程:从「刚拿到 access」→「手里有一个能跑的 system」

> 每步给:**Buddy 说**(真话术)· **Buddy 做**(action)· **用户做** · **这步建出了什么** · **决策/分支** · **卡住怎么办** · **用例自适应**。
> 通篇订单相关只是**一个跑通的例子**,右侧「用例自适应」列说明换个用例怎么变。

### 步骤 1 · Welcome(colleague 感;先不说要做什么)
- **Buddy 说**(第一屏,温暖、像同事、**不马上派活**):
  > 嗨,我是你的搭档 —— 往后帮你把这套东西搭起来、有事招呼我就行 😊
  > 先不急着干活,我就是想说声:**欢迎入伙**。以后这台电脑上就有你自己的一个小团队了,咱一起把它们安顿好。
  > 你先喘口气,准备好了我就带你走,几分钟的事,不难。
  > (三件小事顺带交个底,你心里有数就行 —— 现在**完全免费**随便试;你的东西**全在你自己电脑上**、不往我们这传;因为它们在你电脑上干活,**电脑开着它们才在岗**,像同事上班一样。)
- **Buddy 做**:纯欢迎;若 Anna 传了 context,这里可带一句「Anna 跟我说了你在做 ⟨用户的事⟩,咱就从这儿搭起」——**但仍先 welcome,不立刻派活**。
- **用户做**:读一下 / 回个「好」。
- **这步建出了什么**:**信任/关系的第一印象**(colleague 感)。onboarding 的第一价值不是进度,是「有人陪我」。
- **决策/分支**:有 Anna context → welcome 里带用户的事(更贴);无 → 通用 welcome。
- **卡住**:无(纯欢迎)。
- **用例自适应**:welcome 文案与用例无关,**恒温暖**;要提用户的事就用 Anna 传的 context 或占位「你想搞定的那件事」,**绝不硬塞订单例子**。

> **Annie 改动点(v3)**:第一句 = welcome,不是「接下来做 X」。真正的「要做什么」放到步骤 2 打完招呼之后,那时按对方用例自然引出。

### 步骤 2 · 摸需求(打完招呼后,才问「先搞定哪件事」)
- **Buddy 说**:
  > 那咱开始 ~ 先问你一句:你最想让这个小团队**先帮你搞定哪件事**?就用大白话说,你今天正手动盯着、还挺烦的那种事最好。
- **Buddy 做**:`[AUTO]` 解析描述 → {意图摘要、建议角色、活范围}。
- **用户做**:自由打字描述(例:「盯我 dropship 的订单,哪单卡了直接告诉我为啥」/ 或「帮我把每天的广告花费和成交对上」/ 或「客户来问我价格,帮我先回一下」)。
- **这步建出了什么**:一份**意图理解**(还没落地)。
- **决策/分支**:描述太空(「帮我赚钱」)→ 追问一次:「能说个具体点的场景吗?比如你今天手动在做、还挺烦的一件事。」最多追 2 次仍空 → 给 3 个例子选(按用户行业猜),不硬编死。
- **卡住**:连着说不清 → Buddy 给例子降门槛,不逼。
- **用例自适应**:**这步就是自适应的源头** —— 后面所有步骤(Team 结构、接哪些系统、第一个产出)都从这句长出。

### 步骤 3 · 提议 + 确认 Team
- **Buddy 说**(按步骤 2 变;下例是「盯订单」这个用例):
  > 懂了。那我建议先给你搭个「**订单盯梢**」的小组:
  > · 一个 **Captain** —— 帮你把关、平时你就跟它说话
  > · 一个 **Crew** —— 去你各个系统里查「这单为什么卡了」
  > 名字你随便改。这样成吗?(成 / 改改)
- **Buddy 做**:`[AUTO]` 落一份项目 config(Team 名、要哪个 Captain+Crew、活范围)。**暂不起服务。**
- **用户做**:确认 / 改名 / 加一个 Crew。
- **这步建出了什么**:**Team 的蓝图**(config,还没跑起来)。
- **决策/分支**:用户一上来想要好几个 Team → 「咱先把这一个跑通,回头在 Discord 里跟 Captain 说一声就能再加」(防贪多)。
- **卡住**:用户不确定要不要改 → Buddy 说「先用我这个默认的,回头随时改」。
- **用例自适应**:Team 名 + 角色数 + 活范围**全按步骤 2 变**。内容用例=「上架文案」→ 建「文案助手」组;对账用例→ 建「对账」组。

---

### 步骤 4 · 接大脑(模型 key)[用户亲手 1/3]
- **Buddy 说**:
  > 你这个团队得有个「脑子」才能干活,用的是 Claude。你有 Claude 的订阅或者 API key 吗?
  > 有 → 我带你安全贴进来(不会显示在对话里,也不会存进任何文件被人看到)。
  > 没有 → 这个链接花两分钟注册:https://console.anthropic.com/ ,弄好回来跟我说声。
- **Buddy 做**:CLI 隐藏输入收 key → OS keychain / 600 文件 → 发一个最小 test 调用校验。
- **用户做**:贴 key(隐藏)/ 或去注册。
- **这步建出了什么**:团队**有脑子了**(已验证可用)。
- **决策/分支**:key 无效 → 「这个 key 连不上——看看是不是没复制全,或者额度用完了。再贴一次?」;无额度 → 「key 是对的,但这个账号好像没额度了,去充一下再回来。」
- **卡住**:反复贴不对 2 次 → 「要不我帮你转个人工,让个真人陪你弄这一步?」
- **用例自适应**:与用例无关(所有用例都要脑子)。

### 步骤 5 · 建你自己的 Discord(server + bot)[用户亲手 2/3] —— **详见 §2 深挖**
- **一句话**:Buddy 手把手带用户建**他自己的** Discord(注册→建服务器→建机器人→开权限→邀请进群),我们能自动的都自动(生成邀请链接、建频道),用户只在 Discord 后台点几下 + 贴一次 token。**这是全程唯一略绕的一步**,§2 逐微步写死。

### 步骤 6 · 早聊一句(welcome-first;先打招呼,不马上派活)—— **Annie 改动点**
- **Buddy 说**(Discord + 脑子一接好,先给用户一个「见到活同事」的时刻):
  > 好消息 —— 你的 **Captain 已经上线了**!去你的 Discord 跟它打个招呼吧,就随便说句「在吗」。先认识一下,别的等下再说。
- **用户做**:在 Discord 说「在吗 / 你好」。
- **Captain 说**(**welcome-first:先像同事一样问好,不马上说要干嘛;要提正事就按用户用例、不写死订单**):
  > 在的 👋 我是你的 Captain,以后就是我陪你把活儿盯下来。终于见面了~
  > 你先随便跟我聊两句都行。等你把该接的东西接上,我就能真去帮你干活了 —— 到时候你想让我先看哪件事,直接跟我说就成。
  > （※ 若已知用户用例:把「帮你干活」替换成贴用户那件事的一句,如「帮你盯订单」/「帮你对账」/「帮你回客户」——按用户用例填,**不硬塞订单**。）
- **这步建出了什么**:**第一个「有个活的同事在回我」的时刻**(time-to-first-message 最短化)。信任,不是功能。
- **决策/分支**:用户不想聊 → 直接继续,不阻塞;用户直接问真问题但工具还没接 → Captain 诚实:「这个我得先能看你的 ⟨系统⟩ 才查得了,咱先花一步把它接上?」
- **卡住**:Captain 没上线 → 具体报错 + 自动重试 1 次 → 仍不行转人工。
- **用例自适应**:Captain 的问候恒温暖;提正事那句按用户用例填,订单只是其中一种。

### 步骤 7 · 接后台清单(Linear)[用户亲手 3/3 · 一点授权]
- **Buddy 说**:
  > 还有个**后台小本子**,团队用它记「要做啥、做到哪了」——**你平时根本不用打开**,就给你留个底。点一下授权就行,不用贴任何密钥。
  > [浏览器弹授权 → 用户点同意]
  > ✓ 后台本子接好了,你可以当它不存在 😄
- **Buddy 做**:OAuth device flow → `[AUTO]` 建后台 team + 路由标签(用户无感)→ 存 token 安全存储。
- **用户做**:点一下授权。
- **这步建出了什么**:团队的**记事/追踪底座**(用户无感)。
- **决策/分支**:拒绝授权 → 「不授权的话团队没法记『做到哪了』,重新点一下?」;浏览器没弹 → 给可复制 URL。
- **用例自适应**:与用例无关。

### 步骤 8 · 接第一个真实任务要用的系统 —— **详见 §3 深挖**
- **一句话**:Buddy 从步骤 2 的「第一件事」推断要接哪些业务系统,**只接这件事需要的**,一次一个,能 OAuth 就 OAuth、不能就隐藏输入贴 key,当场探测校验。§3 写死。

### 步骤 9 · 自动安置([AUTO],用户几乎无感)
- **Buddy 说**:
  > 都齐了,我把你的团队正式安顿一下,你喝口水的功夫 ——
  > ✓ 建好工作区　✓ 配好 Captain 和 Crew　✓ 让它们常驻上岗　✓ 上线自检
  > 好啦,搞定 🎉
- **Buddy 做**([AUTO]):脚手架本地工作区(**砍 GitHub、仓留本地**)→ 写 config → 生成+校验 manifest → 装 OS-portable 常驻服务(launchd/systemd/WSL2,FLY-648)→ 起服务 → 健康检查。
- **用户做**:等 30–90s(看逐项打勾)。
- **这步建出了什么**:**一个真能跑、且一直在岗的 system**。
- **决策/分支**:某子步失败 → 具体报错 + 自动重试 1 次 → 仍失败「安置卡在『⟨步骤⟩』了,我帮你转个人工看一下,很快回你」→ 转人工(不甩栈信息)。
- **用例自适应**:与用例无关。

### 步骤 10 · 第一个真产出(它真帮你干成一件事)
- **Buddy 说**:
  > 全搭好了!现在让 Captain 真干件事试试 —— 去 Discord 跟它说你想先看的那件事就行。
- **Captain/Crew 干活**(下例=订单用例,只当样例):
  > 用户:看看我今天有没有卡住的单
  > **Captain**:收到,让 Crew 去查你今天的订单,几十秒。
  > **Crew**(~40s):扫完了。今天 26 单,**1 单要你注意**:#1234 显示 pending,但**不是丢单** —— 供应商已发货,是确认邮件没被读到才没更新状态。其余 25 单正常。要我盯着 #1234、到了自动更新吗?(要 / 不用)
- **这步建出了什么**:**第一个「它真帮到我了」的结果**(≤60s;跨系统还原一件用户平时要当侦探才能查的事)。onboarding 到此**完成**。
- **决策/分支**:第一件事需要一个还没接的系统 → 诚实回到步骤 8 单工具引导,接好再出结果。绝不假装有答案。
- **用例自适应**:产出形态按用例 —— 订单=「为什么卡+要不要盯」;对账=「今天这几笔对不上,差在哪」;文案=「三版标题,你选」。**都是一个可信的结果/答案,不是一个 dashboard。**

## 2. 深挖 A · 带一个非技术新人建他自己的 Discord(server + bot)

> 这是全程**唯一略绕**的一步(Discord 平台不给「替建」的接口,必须用户亲手)。目标:**手把手带到「点错都难」**。配**截图 + 15s 短视频**(见附录)。主线=**用户自建**(Annie 决定);「现成 bot 一键邀请」捷径=理想/大概率做不成,当探索项、不当承诺。

**Buddy 逐微步(每步一句人话 + 一张截图,一步一确认):**

| 微步 | Buddy 说(话术) | 用户做 | Buddy 做([AUTO]/校验) | 卡住分支 |
|---|---|---|---|---|
| A0 判断有没有 Discord | 「你的团队在 **Discord** 里跟你干活。你有 Discord 吗?没有的话咱花 1 分钟弄一个,很简单。」 | 答有/没有 | — | — |
| A1 建账号(没有才走) | 「点这个注册:discord.com,填个邮箱定个密码就行。弄好回来说声。」[截图] | 注册 | 等用户回 | 注册收不到验证邮件 → 「查下垃圾邮件箱,或换个邮箱」 |
| A2 建服务器 | 「现在建一个**你自己的服务器**——就是你团队上班的『办公室』。左边那个大『+』→ 亲自创建 → 起个名(你公司名就行)。[截图] 建好告诉我。」 | 建 server | 等用户回 | 找不到「+」→ 截图红圈指位置 |
| A3 建机器人 app | 「给团队建个专属机器人。打开 discord.com/developers/applications → 右上『New Application』→ 起名 → 勾同意 → Create。[截图] 建好说一声。」 | 建 app | 等 | 页面打不开 → 换浏览器/挂梯子提示 |
| A4 拿 token | 「左边菜单『Bot』→『Reset Token』→ Copy。把那一串**贴进我这里的安全输入**(不会显示出来)。」[截图] | Copy + 贴(隐藏输入) | token→安全存储;连 Discord Gateway 校验 | token 连不上 → 「回 Bot 页面 Reset 一次再贴」 |
| A5 开两个开关 | 「同一页往下滑,打开**两个开关**:Message Content Intent 和 Server Members Intent(截图红圈处)。开好说声。」[截图] | 开 intents | 轮询校验 intents 开了 | 只开一个 → 「还差 Server Members 那个开关」 |
| A6 邀请进服务器 | 「最后一步:点这个链接把机器人请进你刚建的服务器 → [Buddy 自动生成的邀请链接]。选你那个服务器,授权。」 | 点链接授权 | 生成带正确权限的 invite-url;轮询检测 bot 已入 server;[AUTO] 建所需频道 | 没进群 → 「再点一次这个链接,选你刚建的服务器」 |
| A7 完成 | 「✓ 你的机器人在线、进群了,Discord 这步完成!」 | — | 落 state（S5 done） | — |

**我们能帮就帮(降摩擦清单,给 Tadashi)**:自动生成带正确权限 scope 的邀请链接 · 自动建所需频道 · 每微步即时校验给**具体**报错(不是「出错了」)· 每步配截图 + 一段 15s 短视频兜底 · token 全程隐藏输入不进对话。
**worst-case**:任一微步来回失败 2 次、或用户明显懵 → 「这步有点绕,我帮你转个人工,让个真人跟你连屏一起弄,几分钟的事」→ 转人工支持。
**续传**:token 存后中断,重跑从「开 intents / 邀请」续,不重建 app。

## 3. 深挖 B · 接第一个真实任务/自动化(use-case adaptive)

> Team 要真出活,Crew 得能读用户的业务系统。**不前置连全部**——只连**第一件事**需要的那 1–2 个,一次一个。

**Buddy 怎么做:**
1. **[AUTO] 推断要接啥**:从步骤 2 的「第一件事」推断需要的系统(「盯订单」→ 订单/库存;「对广告花费」→ 广告后台;「回客户」→ 邮箱/CRM)→ 列**最少必需集**。
2. **一次接一个,Buddy 说**(下例订单用例):
   > 你那件「订单盯梢」要让团队能看你的订单,得先接上你在用的系统。你今天用哪个?(选一个或告诉我名字)
   > · Shopify　· Veeqo　· Ordoro　· 其它(说名字)
   > [用户选 Shopify]
   > 好,连 Shopify —— 点这个授权就行,**不用你贴任何密钥**。
   > [浏览器 OAuth → 用户点同意]
   > ✓ Shopify 接好了。还要接 Veeqo 吗?(它管你的库存/发货)
3. **按系统类型走两条路**:
   - **有 OAuth 的(Shopify 等)**:浏览器点一下授权,**不贴 key**。
   - **只有 API key 的(Veeqo/Ordoro 等)**:CLI 隐藏输入贴 key + 引导「去哪拿这个 key」(截图),同安全铁律。
4. **每接一个当场校验**:发一个最小**只读**探测(如拉最近 1 单)确认连通 + 权限够。
5. **权限最小化**:onboarding 阶段**只申请只读**;写/改动作留到运行期用户 [GATE] 批准。

**分支/失败**:
- 权限不够 → 「连上了,但还差个权限:得允许我读你的订单。回授权页勾上『读取订单』再点一次。」
- key 错 → 「这个 key 连不上,去 ⟨系统⟩ 设置里重新生成一个**只读**的再贴。」
- 用户的系统没现成连接器 → 诚实:「你的 ⟨系统⟩ 我还没有现成连接器,先记下,我让工程那边看能不能加;这件事咱先用能接的部分做。」**不假装能接。**
- worst-case 接不通 2 次 → 转人工。

**用例自适应表(订单只是一行)**:

| 用户的第一件事 | Buddy 推断要接 | 第一个产出长啥样 |
|---|---|---|
| 盯 dropship 订单 | 订单/库存系统(Shopify/Veeqo…) | 「#1234 卡了,不是丢单,是确认邮件没读到」 |
| 对每天广告花费和成交 | 广告后台 + 支付/订单 | 「今天花 ¥800、成交 12 单,ROI 1.8,比昨天低」 |
| 先回客户询价 | 邮箱/CRM + 价目表 | 「3 个客户在等报价,草稿我拟好了,你看一眼发不发」 |
| 上新品写文案 | 商品库/图床 | 「这款三版标题 + 卖点,你选一个」 |

## 4. 卡住怎么办 + worst-case 转人工支持(升级阶梯)

Buddy 遇阻按这个阶梯走(给 Tadashi 建成状态机):
1. **第 1 次失败** → **具体**报错(精确到哪一步/哪个开关)+ 一句怎么修 → 让用户重试。
2. **第 2 次失败 / 用户明显懵**(连说「不懂/卡住」)→ 不再自己硬解,Buddy 说:
   > 这步有点绕,别耗着 —— 我帮你转个**人工支持**,一个真人跟你连屏、几分钟帮你弄好。要吗?
3. **转人工**:Buddy 生成一份**脱敏**的上下文摘要(走到哪步、卡在哪、报错是啥,**不含任何 secret**)→ 递给人工支持队列 → 告诉用户「转好了,一会有人找你,你先歇着」→ onboarding-state 标 `escalated`,可被人工接手后继续。
4. **绝不**:把栈信息/内部术语甩给用户;不阻死(用户永远有「转人工」这个出口)。
- **注意**:转的是**人工支持**,不是 Anna(Anna=Sales,不在此环)。

## 5. 用例自适应(订单只是一个例子)—— 一句话总纲

同一条流程(步骤 1–10)对**每一种第一件事**都成立,变的只有三处、且都从**步骤 2 用户那句大白话**长出:
1. **Team 名 + 角色**(步骤 3);
2. **接哪些业务系统**(步骤 8);
3. **第一个产出的形态**(步骤 10)。
**welcome(步骤 1)、建 Discord(§2)、接后台清单(步骤 7)、安置(步骤 9)与用例无关,恒定。** —— 所以订单**只是一个跑通的样例**,Tadashi 建的是这套**能按用户用例自适应**的流程,不是订单专用流程。

## 6. 给 Tadashi 的实现要点(落地锚)
- **状态机**:步骤 1–10 各是一个可续传 state;`~/.flywheel-onboarding/state.json` 存 cursor + 已完成 + 非敏感 config;`escalated` 是一个终态可被人工接手。

- **接入实现**:业务系统连接器 = MCP server / 连接器(归 FLY-648 底座);OS-portable 常驻服务(launchd/systemd/WSL2)= FLY-648。
- **安全**:所有 secret → keychain/600,不进 state/git/日志/对话;onboarding 只申请只读 scope;写/改留运行期 [GATE]。
- **persona 实现**:话术层是 Buddy 的 system prompt / 模板,**基调=温暖同事**;每步话术本文已给真样例,可直接当模板起点。
