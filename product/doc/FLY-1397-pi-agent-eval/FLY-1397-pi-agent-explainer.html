Pi Agent — 要不要接进我们自己的系统？

你问的:「值得开个 issue 研究一下,要不要把 Pi Agent 放到我们自己系统里去?」
这份摆事实 + 选项 + 取舍,不替你下「接/不接」的结论 —— 决定权归你。查不到的标 UNKNOWN,来源可追。

一眼看懂(30 秒)

  • Pi 不是一个模型,是一个「执行器」(harness) —— 跟我们现在用的 Claude Code / Codex 是同一层的东西,它自己去驱动模型。
  • 它是我们自己血缘里的近亲:Pi 就是 OpenClaw 里那个极简 agent,而 Flywheel 最早就搭在 OpenClaw 上。这不是「引入一个陌生外部工具」,是「要不要回头用我们出身里那个更省的执行器」。
  • Databricks 一个独立测试的头条:执行器本身能省一大截钱。 同一个模型,换到 Pi 这个执行器上,成本能差 2 倍、质量不变 —— 因为 Pi 每轮喂给模型的内容少约 3 倍。但这是在他们私有代码库上测的,我们这边没验过
  • 第一道门不是省钱,是安全。 Pi 没有内置权限系统。「接进我们系统」要先回答:谁给它兜安全、它认不认我们的 founder 审批。
  • 三条路可选:替换 / 并列(加成第 7 个执行器)/ 借鉴(把 Pi 的省钱手法用到我们现有执行器上) —— 我把取舍摆清楚,你来选。
  • 你后来把这题升级了(见 ⑤):从「要不要用 Pi」→「让 Lead↔Runner 变得跟模型无关:一层统一的执行器抽象,Pi 做新厂商(Kimi/Gemini/…)的通用 wrapper,Claude Code + Codex 留着吃自家模型的深度适配」。
  • 诚实修正(你给的 Codex 反例,见 ⑥):我上一版说「这层已建 80%」是过度声称。准确说:干净的只是「执行器选择层」;一个厂商的完整集成面散在选择层之外的 ~25 个文件里(提示词/派发/数据库/QA 门/报告)——你加 Codex 一层层手补,撞的正是这些。你是对的。

① Pi 到底是什么

一句话:Pi 是一个极简的 coding agent「执行器」(harness),不是模型,MIT 开源。 它自己接 15+ 家模型提供商(Anthropic / OpenAI / Google…),在终端里跑。作者是 Mario Zechner(游戏引擎 libGDX 的作者),挂在 Earendil Inc. 下。

关键理解:它跟我们现在的 Claude Code / Codex 是同一个角色 —— 都是「拿到任务 → 驱动模型 → 读写代码 → 交活」的那层壳。所以「接进 Flywheel」这个问题,天然落在我们已经有的「执行器」槽位上(我们现在有 6 种:Claude、Codex、Gemini、Cursor、以及最近刚加的 antigravity、kimi)。

② Databricks 那个 benchmark 说了什么

Databricks(独立第三方)在自己百万行的私有代码库上,拿真实的、人写的、已合并的 PR 当任务,测各种 coding agent。用真实测试套件判对错(不是让 AI 当裁判),还封存 git 历史防作弊。这套方法论本身对我们「怎么在大代码库上评测 agent」很有借鉴。

方法论金句:「token 单价是端到端真实成本的差指标」 —— 要按「一个任务花多少」测,不是按「一个 token 多少钱」。

执行器层的数字(这单的核心)

「同一个模型、一样的思考力度,换两个不同执行器(Claude Code/Codex vs Pi),每个任务成本能差 2 倍以上,而质量不变。Pi 每轮少发约 3 倍的内容,working set 更紧,用更少轮次完成。极简的 Pi 拿到跟大厂执行器一样的成功率,但成本少 2 倍。」

Databricks CEO 的一句总结:「执行器就是运行时(The harness is the runtime)。同样的模型、同样的代码库,成本/表现天差地别」 —— 因为执行器决定了怎么搜代码、上下文卫生、选哪些文件、工具编排、测试/修复循环、跨轮记忆。

诚实边界

两点必须标清楚,别让「省 2 倍」变成事实:

  • 这个 2 倍是在 Databricks 自己的私有代码库上测的,不可复现、我们这边没验过。它是「他们测出、我们待验」。
  • Databricks 原文里的「Pi」没注明出处 —— 把它等同于 pi.dev 的 Pi,是二手报道 + 业界理解连起来的(可信度高,但不是原文一手确认)。

③ 接进 Flywheel:先过安全门,再谈三条路

接入前提 · 不是脚注

第一道门:安全 —— 谁给 Pi 兜底

「接进我们系统」的第一问不是省不省钱,是它认不认我们的 founder 审批合同、谁来兜安全。Pi 没有内置权限系统,官方答案是「不放心就跑在容器里」,而不是程序化的前置审批闸。

好消息(已核我们代码):最便宜的接法,恰好也是最安全的。 我们最近给系统加 antigravity、kimi 两个执行器时,它们走的是「只 build + 开 PR,然后交回给人,由你手动 ship」的模式 —— 执行器拿不到合并/上线的权限,你的 founder 审批完整保留。Pi 走同一条路的话,安全边界不动。

风险点:一旦想让 Pi「接得更深」(自动 ship),安全这条就会咬回来 —— 谁监督沙箱里的 Pi?这跟我们「自治车队、你不在每个动作旁边」的处境是个开放张力,留给你判。

我方读法

一个反直觉的取舍(值不值的关键不确定性)

Pi 省钱,靠的是它自己那套极简纪律(上下文紧、工具少、提示词短)。而我们的车队会往执行器里塞一大坨自己的流程说明 + 三段式审批。把 Pi 包进我们这套重壳里,很可能把它省钱的本事给抵消掉 —— 那正是它便宜的来源。换句话说:「Pi 裸跑省 2 倍」不自动等于「我们系统里的 Pi 省 2 倍」。 这也是为什么「并列做个 opt-in、在我们自己库上真 A/B 一把」比「直接相信数字」更靠谱。

值得点出 Pi 比我们最近加的 antigravity/kimi 更值得认真接 的一点:那两个只是普通 CLI,只能「build 完交回人」。Pi 有 RPC / JSON / SDK,能接得更深(中途唤醒、甚至自动 ship)—— 天花板更高。当然,接得越深,上面那道安全门就越要认真答。

三条路 + 取舍(不下结论)

路 A · 替换

用 Pi 顶掉 Claude Code / Codex 当主执行器

✓ 若省钱成立,整个车队都受益

✗ 丢掉 Claude/Codex 的成熟度和更强的协作通道;省钱在我们库上未验;高风险,不该轻试

路 B · 并列(加成第 7 个执行器)

Pi 做一个可选执行器,按需逐个任务开(跟 antigravity/kimi 一样)

✓ 便宜、低风险、可逆、默认不影响现状;能在我们自己代码库上真 A/B,验证那个「省 2 倍」到底成不成立;走「只 build+PR」模式,安全边界不动

✗ 若被我们的重壳抵消,A/B 可能测不出优势 —— 要设计公平的对照

路 C · 借鉴

不接 Pi,把它的省钱手法(每轮上下文更紧、工具更少、提示词更短)用到我们现有的 Claude/Codex 执行器上

✓ 省钱是「执行器手法」、可移植;可能最高杠杆 —— 不引第三方,全车队立刻受益

✗ 要先搞清我们执行器的上下文膨胀在哪;动的是核心代码,不像加个可选执行器那么可逆

我方读法 三条路不互斥:比如可以先走 B(做个可选 Pi 执行器,在我们库上实测「省 2 倍」是否成立),同时琢磨 C(把 Pi 的瘦身纪律搬进现有执行器)。用哪条、要不要,归你。

已核代码

发现:执行器「选择层」很干净(但这只是选择层)

我读了真实的派发代码。我们现在已经把三件事分开了:①执行器(壳)②Lead↔Runner 通道 ③模型。派发时按角色选执行器,模型是独立叠上去的。Pi 就是这层上的一个新执行器 —— 跟我们最近加 antigravity、kimi 是完全一样的接法。

杠杆在这: 我们今天是「一个厂商写一个适配器」。你的 reframe = 一个 Pi 适配器顶掉未来 N 个 —— 因为 Pi 自带 15+ 家厂商。但见 ⑥ 「选择层干净」不等于「加一个厂商就零改动」 —— 你加 Codex 撞的那些手补,落在选择层之外。⑥ 把这条边界画清。

三条张力(供你判,不下结论)

问题已知要你判 / UNKNOWN
① 留 CC+Codex 到底真不真值 CC/Codex 确实为自家模型做真事(会话续接、内置工具权限、thinking / reasoning 档)。但 Databricks 的证据显示:在成本上,是「壳的纪律」赢了,不是「自家适配」赢 —— 同模型下 Pi 反而更省。 是真优势,还是我们只是习惯了 CC/Codex 的成熟壳(锁定)?Pi 有没有吃到 prompt 缓存 / thinking = UNKNOWN。要在我们自己库上 A/B(Pi+同模型 vs CC+同模型)才知道。别默认「留着 = 有优势」成立。
② 权限怎么包 Pi 没有内置权限。但我们真正的红线闸(合并/上线/开关 runner)本来就在 runner 外面 —— 任何厂商的 runner 都拿不到这些权限,只能产 PR、你来 ship。所以最便宜的接法(Pi 跑容器里 + 只 build+PR)零新增安全接线。 只有当你想让 Pi「接得更深」(中途自动执行保留动作)时,才需要把 Pi 的确认流接到我们的闸上。我方读法 v1 不必做这步。

一句话 你的 reframe 不是从零造 —— 是在我们已有的执行器层上，把「一厂一适配器」换成「一个 Pi 顶多家」,再决定 CC+Codex 值不值得单独留。三条张力都摆上了,怎么走归你。

Pi 对照 · 诚实判(不 hand-wave)

这些分支是按 harness 能力分叉的(有没有 mailbox、怎么等 gate、要不要环境翻译),不是按模型。所以:

✗ Pi 不解决「加 Codex 很痛」这个具体问题 —— 那是 Codex 那条最贵通道的复杂度,跟 Pi 正交;Pi 一处都不回头清理。

✗ Pi 自己也不是零改动 —— 它落在便宜的 transport=none(像 kimi),复用已铺好的分支,但仍要一个适配器 + 提示词/持久化那一份。

✓ Pi 真正的价值 = 折叠「模型轴」:今天每加一个新模型厂商当独立执行器都要一套;Pi(一个壳驱动 15+ 家)把 N 个新模型集成折成 1 个,且落在便宜那条。

一句话: Pi 让未来加新模型变便宜(N 厂→1 wrapper);它不消除现有的 vendor-fork、不治你现在的 Codex 痛。要不要为「未来模型广度便宜」买单,归你。每处「必改 vs 可选」的精确清单要一次工程 spike 才能定档
