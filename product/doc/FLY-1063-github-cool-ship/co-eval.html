FLY-1063 · 给你拍方向，不是最终 PRD

在 GitHub 上，你亲自发的 🆒
算不算一次审批？

这一页只想让你拍一个方向。别的（怎么装到每个 repo、部署怎么接）都想清了，作推荐给你确认。拍完，我们才拆开发任务。

先说个意外

其实 flywheel 上已经有一个 🆒 了

在 PR 里发 🆒，就会自动跑测试、通过后合并。但它今天的真实样子是——

真正拍板发生在 Discord（你在 thread 里说 ship）；GitHub 上那条 🆒，是机器人在你 Discord 拍板之后、替你补按的一个执行按钮。你本人根本没碰 GitHub。

所以你说的「Discord 和 GitHub 不等价」——你完全说对了。今天的 GitHub 🆒 不是「你看着代码拍板的地方」，只是「机器人替你按的开关」。

你真正想要的，我理解是：你能亲自到 GitHub 看真实代码改动，自己发个 🆒，它就 ship。所以这件事不是「从零造 🆒」，而是把 GitHub 从「机器人的按钮」升级成「你亲自的审批面」，并让每个 repo 都有。

要你拍的那一个问题

两扇门，还是一扇门？

你的话里有两种可能的意思，我都摆出来。两个方案有个共同底座：账本永远只有一本，不会出现「Discord 批了、GitHub 没记」的账目分裂。区别只在下面这点——

方案 A我推荐

GitHub 的 🆒 = 你的正式审批

  • 你亲自到 GitHub，看真 diff / 文件 / 测试状态，自己发 🆒
  • 系统认得出「这是 Annie 本人拍的」，当作一次正式审批记账，然后自动合并 + 部署
  • GitHub 和 Discord = 同一个决定的两扇门，哪扇拍都算数、都记账、都一样安全

为什么推荐：这才真正回应「不等价」——只有把 GitHub 做成你能亲自拍板的一等入口，两个入口才真正等价可选；也最贴你最早说的「想亲自看真 diff 再拍」。

方案 B

GitHub 🆒 只是执行，Discord 才拍板

  • 保持今天的样子：你在 Discord 拍板 → 机器人去 GitHub 发 🆒 → 合并
  • GitHub 的 🆒 不代表你的授权，只是执行
  • 「全 repo 通用」= 把「测试+合并+记账」铺到每个 repo，但拍板永远只在 Discord

代价：你还是不能「亲自在 GitHub 上拍板」，那个「不等价」的痛点没被解决。B 更像把现状铺开，而不是给你新入口。

如果选 A，有个前提要先办

今天机器人和你，用的是同一个 GitHub 账号

机器人和你本人，在 GitHub 上都叫 xrliAnnie。系统看到「一条 🆒 来自 xrliAnnie」，分不清这是你亲自按的（真审批），还是机器人机械补发的（只是执行）。

方案 A 的整个安全性，就靠「能可靠认出这是你本人拍的」。所以前提是：给机器人一个单独的身份去发那些机械 🆒，把 xrliAnnie 还给你本人。这样系统一看是谁发的，就分得清「人拍的」还是「机器按的」。

（方案 B 不强依赖这个前提。具体用「新建机器人账号」还是「GitHub App」是落地细节，等你拍完 A 再定。）

这两点已经想清，给你确认

怎么让每个 repo 都有 + 部署怎么接

① 每个 repo 都有 → 一份中央模板 + 每 repo 挂个瘦接口

中央放一份「🆒 → 认人 → 测试 → 合并 → 记账」的标准流程；每个 repo 只挂一个几行的小接口指向它。以后要改只改中央一份，全体一起升级。

② 部署怎么接 → 合并和部署是分开的两条腿

合并（🆒→测试→合到 main）是通用的；部署每个 repo 不一样（flywheel 本机自更新、GeoForge3D 走 Vercel…）。所以通用只做到「合并 + 记账」，部署由每个 repo 接自己的方式。
