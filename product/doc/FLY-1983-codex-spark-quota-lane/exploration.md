## 1. Annie 真正要解决的问题(不是她说的表面需求)

表面需求是「研究一下 Codex Spark 适合做什么、能不能接进 QA」。

但把她的原话和当夜背景放在一起看,**真问题是一句更硬的话**:

> 「我们在几条模型线上排队(今晚 FLY-1969 的 runner 5h 撞顶两次、7d 曾到 100%),
> 而这里有一条**一次都没用过**的线。我是不是在浪费产能?」

也就是说,这单的落点不是「Spark 是个什么模型」,而是:

**能不能用这条闲置的额度线,换回一些被额度墙挡住的产能 —— 而且不牺牲质量。**

这个提法很重要,因为它决定了「什么算成功的回答」:
- 只答「Spark 是个快模型」= 没回答她。
- 答「它能/不能吸收我们现在被挡住的那部分工作量」= 回答了她。

## 4. 开工前先核前提 —— 结果是 issue 里两条前提要修正

Annie 的 issue 里有两条事实性前提。我核了,**一条修正、一条推翻**,而且两条都改变结论方向:

| issue 里的前提 | 实际 | 影响 |
|---|---|---|
| 「QA 现在硬绑 `models.json` 的 `phases.qa = claude-opus-4-6[1m]`」 | `phases` 这个键**全仓没有任何代码读它**;真正的 QA 绑定在 workflow template manifest 里,是 `claude-opus-5 / high` | 「接进 QA」不是改 models.json,是改模板 manifest + 加模型注册项 |
| 「现状全是 Opus,Spark 尚未接入任何地方」 | 后半句对;但前半句不对 —— `implement` 节点**早就是 `codex / gpt-5.6-sol`**,60 天 414 个 session | Codex 这个**账号**不是闲置的,闲置的只是 Spark 这条**子线** |

第二条尤其关键:它把问题从「我们没在用 Codex」改成「**我们重度在用 Codex,只是没用 Spark**」——
而这恰好接上了 A 里最要命的那个发现(见 research.md §A-4:主线用尽时 Spark 会被一起挡)。
