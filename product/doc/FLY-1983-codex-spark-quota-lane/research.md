# A. 这条线到底是什么

## A-1. 模型本体

| 项 | 值 | 级 |
|---|---|---|
| 全名 | `gpt-5.3-codex-spark` | A(本机 `~/.codex/config.toml` 的 `[tui.model_availability_nux]` 里有它) |
| 定位 | GPT-5.3-Codex 的**小号版本**,为超低延迟交互编码优化 | B |
| 速度 | 1,000+ tokens/秒(跑在 Cerebras WSE-3 专用硬件上) | B |
| 上下文 | **128k** | B |
| 模态 | **纯文本,不吃图**(见下 A-1b —— 这是 Annie 让我核的第一件事) | B |
| 发布 | 2026-02-12,至今(2026-08-21)**仍是 research preview** | B |
| 可用范围 | **仅 ChatGPT Pro**;**API key 拿不到** | B/C |

「小号版本」不是营销词 —— OpenAI 自己就是这么描述的。它不是同一个模型跑得快,是**更小的模型**。
这一句决定了后面所有的取舍。

## A-1b. 🔴 核 Annie 的印象:「它好像不支持多模态」

**她的印象 → 我核了 → 成立。** 而且我拿到的是一手来源(OpenAI 官方开发者账号原话):

> Codex-Spark is **currently text-only** with a 128k context window. We'll introduce more
> capabilities — including larger models, longer context lengths, and **multimodal input** —
> as we learn from our first production deployment of low-latency infrastructure and hardware. (B)

三件事要一起说,少一件都会误导:

1. **今天成立。** 我另外查的 2026-08 各来源仍然说纯文本,**没有任何来源宣称它已经支持图片**。
2. ⭐ **但这条限制有保质期。** 多模态是 OpenAI **明说要加**的三件事之一(另两件是更大的模型、更长的上下文)。
   所以不该把「不吃图」写成 Spark 的**永久属性** —— 它是**当前状态**。
   ⇒ **通则**:**任何来自厂商路线图的限制都要带日期**,否则半年后它会被当成永久属性引用。
   全文凡引用这条,一律写成「**按 2026-08 的状态**」。
3. ⚠️ **墙在模型,不在我们的工具链。****A 级(我实测)**:本机 `codex` CLI **自己是有 `-i/--image <FILE>...` 入口的**
   (`codex --help` 实测)。也就是说,把图递给一个 Spark 会话这条路**在工具层是通的**。

第 3 点带出一个我**没有测、但很要紧**的问题:

> **把一张图递给 Spark,它是报错,还是静默地把图忽略掉?**

在一条流水线里,这两者的差别是决定性的 —— 报错是响的,静默忽略是哑的,而哑的那种会让下游拿到一个
「它看过截图了」的假象。**我没测这一格**(要跑一次真 Spark,会碰共享 codex 状态,而且这不在我被交代的范围里)。
要测的话确切动作是:走 codex-companion 持久会话 `task --model gpt-5.3-codex-spark`,附一张图,看它是否提到图里的内容。
⛔ 在测出来之前,不许假设它会报错。

Spark 撞限时,轮到一个没 Pro 的号上去 = 直接不可用,而不是降速。

## A-3. 「独立额度线」这件事:官方确认它独立,同时官方保留改它的权利

Annie 的截图(Spark 5h limit 100% remaining)是对的,这条线确实存在且我们从没用过。官方口径是:

> 因为它跑在专用低延迟硬件上,**usage is governed by a separate usage limit that may adjust based on demand**。 (B)

请读第二个半句。**OpenAI 是用书面形式保留了随时调整这条线的权利。**
它现在宽,不是因为它被承诺宽,是因为现在没人抢。这是 research preview 的正常形态。

⇒ 对「它会不会哪天并线」的诚实回答:**官方没承诺不会,而且明说了会按需求调整。**
任何依赖这条线容量的设计,必须能在这条线明天变窄时**降级而不是断掉**。

(这条线烧得多快 —— 也就是「空着」到底值多少 —— 单独成节,见 A-5。)

## A-4. 🔴 「空着」到底值多少?—— 这一条打的是本单的立项前提

本单的**立项前提**是那张截图:**一条 5 小时额度线,100% 未用过。** 那是硬事实。
但「未用过」说的是**余量**,不说**这桶能装多久**。而 Annie 给的材料里有用户直接质疑了后者: (C)

> 「这个额度**消耗飞快**不说,还笨得够呛。」(2026-08 评论区,一手用户)

**独立额度线 ≠ 额度耐用。** 它每秒吐 1000+ token —— 同样的墙钟时间,它烧掉的量比慢模型多得多。

⇒ **「这条线 100% 空着」这个观察,不等于「这条线经得起我们用」。**
⇒ **空着的可能不是一桶油,是一杯。**

这不是给结论补一条细节,**它反驳的是「这里有一条闲置产能可以拿来减压」这个前提本身。**

⚠️ **而这一格没人量过 —— 我也没量。** 要回答它得先真跑一段有代表性的负载,见 §H4。
⇒ 在量出来之前,**不该把「有一条空线」当成一项已知的产能**。

## A-5. 🔴 另一条:主线用尽时,Spark 曾被一起挡住

OpenAI 开发者社区有持续的 bug 报告(2026-03 ~ 2026-05,官方支持回过帖但**没有公开的解决声明**): (C)

> 用户看到标准 Codex 周额度 **0% 剩余**、Spark 显示 **55% 剩余**,
> 但 Codex app 直接弹「You're out of Codex messages」并锁死输入框 —— **Spark 也用不了**。

也就是说:**「独立额度线」是一个产品说法,不是一道被强制执行的隔离墙。**
而且它失效的时刻,恰好是你最需要它的那一刻 —— 主线烧完的时候。

**为什么这一条对我们特别致命**:我们的 `implement` 节点**已经在重度烧标准 Codex 线**
(近 60 天 414 个 session 跑 `gpt-5.6-sol`,A 级,见 §D-1)。
所以在 Flywheel 的真实负载下,「标准 Codex 线烧完」不是假想 —— 那是常态。
按这份报告的形态,那正是 Spark 也会一起躺下的时刻。

**诚实边界**:这是 C 级证据。报告说的是 Codex **app**,不确定 CLI 路径是否同样受影响;
时间是 3–5 月,可能已修;**我没有在本机复现过**。
→ 所以 plan.md 把「复现这一条」列为决定性的第一个实验,而且它很便宜。

# B. 它擅长什么

正面清单(B/C):

- **人在场的实时编辑循环** —— 打字级延迟下改一段逻辑、调一个界面、立刻看结果,可以随时打断、改方向。
  这是 OpenAI 造它的**原始用途**,也是 Simon Willison 认可它的点:快到能让人保持在心流里迭代。
- **短、边界清楚、一次就能说完的改动** —— 社区总结的经验法则是:
  「一个人类开发者**一小时内**能把范围讲清楚的活,Spark 大概能做。」
- **探索性写码 / 快速原型** —— 要的是「先出个东西看看」,不是「出个能上线的东西」。

共同点:**人一直在回路里,而且反馈周期以秒计。**

# C. 🔴 它做不好什么(Annie 点名要这一条,所以写具体)

按第三方评测和路由指南整理(C 级,但多个来源互相印证):

| 做不好的形态 | 具体表现 |
|---|---|
| **多文件 / 多步骤的改动** | 推理深度明显弱于完整版 Codex 和 Claude Code |
| **安全敏感代码** | auth 流程、加密实现、输入校验相对 Codex 5.3 有**质量回退** |
| **架构判断** | 划微服务边界、重构有状态系统 —— 超出它的推理容量 |
| **工具编排 / 浏览器交互 / computer-use** | 路由指南直接写:这类活**换 GPT-5.4**,不要用 Spark |
| **长自主流程** | 「它不是设计来开沙箱、跑测试、迭代、自主把 PR 交出去的」 |
| **结构化输出** | 复杂 prompt 下出现 **JSON schema 和 tool-call 格式错误** —— 对 agentic pipeline 是真风险 |
| **需要吃大量上下文** | 128k 窗口,纯文本,不吃图 |

最后两行我要特意点出来,因为它们不是「质量差一点」,是**形态上不兼容**:
- tool-call 格式错 ⇒ 在一个靠工具调用推进的流水线里,失败方式是**卡住或跑偏**,不是「答得差一点」。
- 不吃图 ⇒ 任何要看截图、看渲染结果、看 proofshot 的活,它**物理上做不了**(按 2026-08 状态,见 §A-1b)。

## C-2. 🔴 一条**待核的报告**(不是结论):有人报告它跳过了写给它的规则

这条来自 Annie 指定的材料(一份 7 天重度使用报告,2026-02-25),原话: (C)

> - 「**经常跳过 test:我在 `agents.md` 里写了 TDD,结果它还是爱写完就跑。**」
> - 「复杂多步推理不太稳:给过 detailed spec + plan,但**服从性一般,中途还会停止**。」

**为什么这一条对 Flywheel 比「推理弱」严重得多:**

我们**整个 Runner 架构**,就是靠把一份 markdown 契约**逐字注入 system prompt** 来约束行为的
(`readAgentFile`)。QA 要跑真 E2E、要诚实报没跑的部分、PASS 前要重新 fetch HEAD;实现要 TDD;
每个角色的纪律**全部**写在那份 md 里,**没有任何机制在运行时强制执行它们** —— 全靠模型遵守。

⇒ **如果**一个模型系统性不服从注入的规则,那在我们这儿就不是「做得差一点」,是**那份契约对它整体失效** ——
它会跑完、会报成功,而那些纪律条款一条都没生效,**且从外面看不出来**。

⇒ **而且不止 Runner 契约。** 我们对任何模型的**全部**控制手段都是注入的文字:
agent 契约、rules bundle、doc-flow 指令、founder-only-authority 合同 —— **全是**。
⇒ 所以这件事一旦成立,**不是质量问题,是治理问题**:我们所有的流程和安全保证会对它整体失效。

## 🔴 但这一格的形式是【开工闸】,不是【关于 Spark 的结论】—— 边界守死

这两句话在文档里长得很像,**而只有后者会被下一个人当事实引用**:

| ✅ 现在的证据撑得起 | ⛔ 现在的证据撑不起 |
|---|---|
| 「**有报告说**它跳过注入的规则 ⇒ **在核清楚之前先别建**」 | 「**Spark 不服从规则**」 |

现在的证据是 **C 级、单一用户、2026-02 的版本、我没有复现**。
它撑得起「**先别建**」,撑不起「**它就是这样**」。⛔ 全文任何地方都不许把它写成后者。

⚠️ **成色说清楚**:C 级,单一用户,而且是 **2 月的版本**(可能已改善)。我没有复现。
⛔ **这一条不许单独支撑任何结论。** 而且要让它变硬,需要的是**我们自己的一次实测** ——
**再找第三条同源材料不会让它变硬,只会让它看起来变硬。**(怎么测见 §H1。)
但它和另一份材料评论区**最高赞**的那条独立对上了: (C)

> 「这玩意根本没用,输出的东西一堆 bug,**耗费更多的高级模型去修 bug**。」

—— 也就是 **净负收益**:用 Spark 省下的额度,被修它 bug 的强模型额度吃回去,还倒贴。
(同一条评论下,笔记作者回了个相反的实测:「让 sol 做方案、spark 执行还不错,30 多轮对话没出问题」。
**两边我都摆出来,不替读者选。** 注意作者的用法是**人定方案 + 它执行**,不是让它自己跑 —— 这和我的结论一致。)

# D. 接在哪 —— 检验 Annie 的两个假设(QA / prototype)

## D-1. 先把生产现状摆出来(A 级,读自 `~/.flywheel/teamlead.db` 只读快照)

`models.json` 里的 `phases` 键 **全仓没有任何代码读它**
(`ModelConfigFile` 只声明 `version | bindings | models | tiers`;packages/ 与 scripts/ 全扫无消费者)。
⇒ issue 里写的 `phases.qa = claude-opus-4-6[1m]` 是一个**没有生效的键**,真实绑定是下表。

生产在用的 5 个模板(published revision):

| 模板 | 各节点 vendor / model / effort |
|---|---|
| `tpl_code` | design=**claude**/fable-5/xhigh · implement=**codex**/gpt-5.6-sol/xhigh · qa=**claude**/opus-5/**high** · gate · land |
| `tpl_simple_code` | implement=**codex**/gpt-5.6-sol/xhigh · qa=**claude**/opus-5/high · gate · land |
| `tpl_prd` / `tpl_design` / `tpl_prototype` / `tpl_generic_menu` | 单节点 = **claude**/opus-5/high · gate · land |

模型注册表(`packages/config/src/model-builtins.ts`)里**只有一个 OpenAI 模型**:
`gpt-5.6-sol`,挂在 `runner / workflow / cron` 面,runner 面只允许 `xhigh`。
**Spark 不在注册表里。**

## D-2. QA 节点实际是什么形态(A 级)

近 60 天(2026-06-22 起)Flywheel 生产 session 时长分布:

| 角色 | 模型 | 场次 | 平均时长 | 最长 |
|---|---|---|---|---|
| qa | claude-opus-4-8 | 173 | 8.96 h | 109 h |
| qa | claude-opus-5[1m] | 86 | 5.68 h | 31 h |
| qa | claude-opus-4-8[1m] | 66 | 6.02 h | 205 h |
| qa | claude-opus-5 | 66 | 10.24 h | 178 h |

| design | claude-fable-5 | 439 | 6.47 h | 188 h |

两个读法(以及一个我必须交代的水分):

1. **QA 是长跑,不是短检查。** 约 447 场 QA,平均 **6–10 小时**。
   ⚠️ 水分:这个时长包含 park 等门、等实现方推新 head 的空转,**不是纯模型工作时间**。
   但它准确地反映了**形态** —— QA 是一个要跨小时、跨多轮、会被叫醒再继续的长任务。
2. **QA 是我们唯一大量动用 1M 上下文的地方。** 152/447 ≈ **34%** 的 QA 跑在 `[1m]` 变体上。
   Spark 是 **128k**,约为 1M 的 **1/8**。

## D-3. QA 节点被要求做的事(A 级,读自 `.flywheel/agents/engineering/qa-executor.md`)

合同里逐条写死的硬要求:

- 用 **Claude-in-Chrome** 驱动真实浏览器做 founder 侧动作,截 BEFORE→AFTER→VERDICT 证据
- 用 `test-deploy.sh` 起隔离 529 房、注真 Linear issue、驱动真 Runner、跑真 Discord N-to-N
- 读 PR diff + 产品 spec,判断「谁在用这个、流程对不对」,而不只是技术正确
- PASS 前必须重新 fetch HEAD;PASS 会开 founder ship gate
- 必须产出一页**交互式 ship-report HTML**(founder 语言,不是 markdown 替代品)
- 必须**诚实**:没跑的要点名说没跑 ——「沉默会被读成跳过,不允许」
- 会 park、被唤醒、和实现方多轮 loop,同一个 session 复用

## D-4. 判决:**假设不成立。**

把 §C 的反面清单和 §D-2/D-3 的 QA 画像并排放:

| Spark 明确做不好的 | QA 节点恰好必须做的 |
|---|---|
| 工具编排 / 浏览器交互 / computer-use | Claude-in-Chrome 驱动真浏览器,tmux + Bridge + Discord 编排 |
| 长自主流程(开沙箱、跑测试、迭代) | 起 529 隔离房、注 issue、驱动真 Runner、跨小时多轮 |
| tool-call / JSON 格式在复杂 prompt 下出错 | 整条流水线靠 `flywheel-comm qa-result` 等结构化调用推进 |
| 纯文本,不吃图 | 截图证据、proofshot、渲染面验收 |
| 128k 上下文 | 34% 的 QA 场次显式要 1M |
| 深度上下文分析 | 读 diff + spec + 历史证据后下 PASS/FAIL |
| 安全敏感代码质量回退 | QA 正是最后一道拦安全问题的关 |

**七条,条条对撞。** 这不是「Spark 做 QA 会差一点」,是「Spark 的能力边界和 QA 的任务定义几乎正交」。

**Annie 的直觉里有对的一半,但操作性的那个属性被挑错了。**
她说「QA 比较清楚」—— 她指的是**判据清楚**(PASS/FAIL 有明确标准)。这个观察本身是对的。
但 QA 的**判据**清楚,不代表 QA 的**工作**简单。恰恰相反:判据清楚 + 工作难,正是我们把最强模型放在这里的原因。

而且还有一层:**QA 是我们抓「别的环节做错了」的那道网。**
把网换成一个更小的模型,失败方式不是「QA 变慢」,是**它会漏放东西过去,而且没人会知道它漏了**。
这正好撞上 Annie 自己在 issue 里立的第一条红线(Sonnet 因质量被禁)。


## D-4b. 🔴 核 Annie 的第二个假设:「它好像也适合做 prototype」

Lead 点出我上一版**没有正面判这一格**,而且 §B(说它擅长「探索性地先写点东西看看」)和 §D-5(列位置时没有 prototype)
放在一起会读出矛盾。**他说得对。** 这一格现在正面判。

### 先查我们的 prototype 环节实际长什么样(A 级)

- **绑定**:`tpl_prototype` 只有一个干活节点 `produce` = `claude / claude-opus-5 / high`。
- **契约**(`.flywheel/agents/engineering/prototype-executor.md`)—— 这个环节被要求做的事:

| 步 | 做什么 | 形态 |
|---|---|---|
| 1 | 把模糊的「我们想要 X」变成**一条可证伪的假设 + 一条二值成功判据**,写在动手之前 | 判断 |
| 2 | 爬「最便宜阶梯」:①手跑一次 → ②一次性脚本 → ③静态假 UI → ④一条真通路,**停在最早能回答问题的那一级** | **写扔掉的码** |

### 判决:**不能简单答 yes 或 no —— 要拆开,而且拆开之后两边的答案是相反的**

| prototype 环节内部 | 形态 | Spark |
|---|---|---|
| 步 1 定假设 + 成功判据 | 想清楚要验什么 | ❌ 这是全流程最需要推理的一步 |

| 步 2 阶梯③:静态假 UI | 视觉产物 | ⚠️ 码写得出来,但**它看不见自己做出来什么样** |
| 步 3 给 founder 体验 + 开门等 | 出图 + 工具链 + 长时程阻塞 | ❌ |
| 步 3.5 迭代(她指着说哪不对) | 她若贴截图指 | ❌ 读不了图 |
| 步 4 判 doable / not-doable | 判断 + 建单 | ❌ 见下 |

**⭐ Annie 这次的直觉比 QA 那次准得多,而且准在两个真的地方:**

1. **步 2 确实是它最擅长的形状。** 阶梯①②要的就是「短、快、能试错、写完就扔」——
   我在 §B 写的「探索性地先写点东西看看」和这个是同一件事。她给的材料里,那份路由笔记的
   **优先清单第 3 条就是「小工具和原型」**(C)。她、我、和那份二手材料在这一点上是一致的。
2. **prototype 的失败代价确实低** —— 原型是扔掉的码,判错了最多多试一轮。
   这和 QA 完全不同(QA 判错是漏东西过去)。按我 §E-1 的判据,**这里的判官是 Annie 本人,而且她当场就在看**
   —— 失败是**响**的。

**🔴 但这个环节真正的产出物不是那段码,是一个 doable / not-doable 的判决。**

原型写得对不对,当场看得见;**但「这条路走得通」这个判断错了,不会当场响** —— 它会一路传到工程,
等工程投进去一整轮才发现不行。而做出那个判断,恰恰需要的是它最弱的东西:多步推理、看全局、
知道自己刚才那条「跑通了」的路是真跑通还是绕过去了。

⇒ **拆开之后的诚实答案:**
> **「写那段扔掉的原型码」= 它最合适的形状(全 Flywheel 我找到的唯一一处真正贴合)。**
> **「判这条路走不走得通」= 恰恰是它最不该碰的。**
> **而这两件事在我们今天的基建里,是同一个节点、同一个模型。**

## D-5. 那接在哪?—— 今天一个都接不上,但**原因和我上一版写的不一样**

我逐个过了 Flywheel 现有的模型消费点:

| 位置 | 现状 | 能不能换 Spark |
|---|---|---|
| `design` 节点 | claude/fable-5 | ❌ 长跑 + 要出方案 + 常带视觉 |
| `implement` 节点 | codex/gpt-5.6-sol | ❌ 多文件 agentic,正是 Spark 的短板 |
| `qa` 节点 | claude/opus-5 | ❌ §D-4 |
| `produce`(**prototype**) | claude/opus-5 | ❌ **整个环节**不行(见 D-4b),但**环节里的步 2 是它最合适的形状** |
| `produce` / `execute`(prd / design / generic) | claude/opus-5 | ❌ 长跑 + founder 交付物 |
| Codex code review | gpt-5.6-sol xhigh | ❌ 要的就是深推理 |

| Lead | Claude(Spark 不挂 lead 面) | ❌ |

**⇒ 我们今天所有的模型消费点,Spark 一个都吃不下。**

### 🔴 但「一个都吃不下」这句话,我上一版给的原因找错了一层

上一版我写的是「它什么都做不了」。**第二轮查完,更准的说法是:**

> **它擅长的是「一个环节里的某一步」,而我们绑模型的粒度是「整个环节」。**
> **接不上的真正原因是【粒度错配】,不是「它不行」。**

### ⭐ 压成一句话 —— **但这句话的两半成色不一样,必须分开说**

Lead 从材料完整评论里找出了一条我只摘了负面、没摘正面的一手记录 —— 笔记作者本人的回复: (C)

> 「我实测下来**让 sol 做方案,spark 执行**还不错,**30 多轮对话没出问题**。」

这条**不是**对我结论的反例,它是**同一个形状的正面版**,而且它给了整份研究一句更短的说法:

> ~~它当执行器可以,当决策者不行。~~

🔴 **但这句话我第一版写错了,Lead 抓出来了 —— 它前后两半的成色差了一个量级,而这句话把它们说得一样确定。**

| 半句 | 成色 | 靠什么撑 |
|---|---|---|
| **「当决策者不行」** | ✅ **已立** | 多路证据 + 我们自己的契约拆解(A/C 混合) |
| **「当执行器可以」** | ⚠️ **待定** | 只有**一条 C 级单一用户评论** |

**而且更要命的是**:C-2 那条待核报告的原文是 ——
「给过 detailed spec + plan,但服从性一般,**中途还会停止**」「写了 TDD 结果**还是爱写完就跑**」。
⇒ **这两句描述的失败,全都发生在【执行】那一半,不在决策那一半。**
给了 spec 还不照做、中途停 —— 那正是一个**执行器**该干而没干好的事。

⇒ 所以我原来那句标题,**把唯一直接打脸「当执行器可以」的那条证据,收进了它自己的安全区。**

**⇒ 正确的写法(不砍掉它,它值得留,但要带条件):**

> **「当决策者不行」= 已立。**
> **「当执行器可以」= 待定 —— 它的条件正是那道契约闸(C-2):它服从注入约束,这半句才成立。**

⇒ 也就是说:**那道开工闸和这句结论,是同一个未知的两面。**
**闸没开之前,这句话只有后半句能对外说。**

### ⭐⭐ 方法纪律(Lead 从这次抓的洞里抽出来的,写在这里因为它比结论值钱)

我自己在同一份报告里刚写过:「我先读的是记忆索引那一行,没读原文 ——
**索引行是压缩过的,限定词正是压缩时最先掉的东西。**」

**而那句标题,就是这份研究自己的索引行。** 我把一份成色不齐的结论压成了一句好记的话,
**掉的正是限定词** —— 一模一样的机制,只是这次压缩的人是我、被压掉的是我自己的成色标注。

> **一句好记的结论,是最容易被引用、也最容易在压缩中丢掉成色的那种句子。**
> **⇒ 凡是准备当标题的话,必须【逐半】检查成色,而不是整句盖一个章。**

### 后半句(已立的那半)把前面分散的判断串起来了:

| 场合 | 那里要的是「执行」还是「决策」 | 结果 |
|---|---|---|
| prototype 步 2「写那段扔掉的码」 | 执行 | ⚠️ **待定** —— 卡在同一道闸上 |
| prototype 步 4「判走不走得通」 | **决策** | ❌ |
| **QA 节点** | **纯决策岗** —— 它的产出物就是一个 PASS/FAIL 判决 | ❌ **这就是它最不合适的原因** |
| 材料里的路由建议:强模型定方案 → Spark 执行 → 强模型审关键 diff | 决策在两头,执行在中间 | 与上表一致(但「执行」那段同样待定) |

⇒ 而「粒度错配」是这句话的**基建版**:我们今天买不到「只要执行那一步」,
因为**每个环节都把执行和决策打包在同一个模型上**。

### ⭐ 通则(比 Spark 活得久,以后每次有人想换小模型都先问这一句)

> **判断一个环节能不能换便宜模型,要看那个环节的失败会不会【当场响】。**
> **会响的可以试;不响的,省下来的钱由下游赔。**

这条是从 prototype 那一格抽出来的,而那一格的转折不是「它写得动吗」,是**「它判得准吗」**——
因为这两件事的失败方式完全不同:

| | 失败方式 |
|---|---|
| **写不动** | 当场响 —— Annie 就在看 |
| **判错** | **不响** —— 一路传到工程,投进一整轮才发现 |

⇒ 所以对 Annie 的两个假设,正确的答法不是驳回,是**承认她直觉里对的部分,再说清它为什么现在兑现不了**——
给她一个**带日期的「还不行」**,不是一个「不行」。

三处独立的证据指向同一个形状:

| 来源 | 说的是什么 | 级 |
|---|---|---|
| D-4b 的 prototype 拆解 | 步 2「写扔掉的原型码」贴合;同一个节点里的步 1/3/4 不贴合 | A(我们的契约) |
| Annie 给的路由笔记 | 建议它「**作为 sub-agent 做探索、局部实现和第一轮扫描**」—— 都是**某一步** | C |
| Annie 给的 7 天体验报告 | 128k 窗口小,但快到可以**反复扫**一个陈年目录,1 分钟出结论 —— **用速度换上下文**,而这是「找东西」这一步,不是「做完整件事」 | C |

⭐ 第三条还**部分反驳了我上一版的一个论据**:我把「128k 太小」当成一条硬伤。
但对**检索型**的一步来说,小窗口 + 高速度可以靠多跑几趟补回来。**那条硬伤只在「一次要吃下全部上下文」时才成立。**
—— 我把这条留在这儿,是因为它是**削弱我自己论点**的证据,不该被压掉。

⇒ 所以对 Annie 那个真问题(「能不能用这条闲置的线换回产能」)的完整答案是:

> **不能 —— 但不是因为它没用,是因为我们没有一个能只买「一步」的接口。**
> **我们的额度墙是「活全是长时程 agentic 跑」造成的;而我们绑模型的最小单位,恰好就是那整个跑。**

这个说法比上一版可操作:它点名了要改什么才接得上(**更细的绑定粒度 / 一个 sub-agent 缝**),
而不是笼统地说「不行」。⚠️ 但那是一笔新工程,**不是一次接线**,而且在 C-2(不服从注入规则)被复现或排除之前,
**不该开工** —— 因为 sub-agent 缝正是靠注入规则来约束的。

## D-6. 那 Spark 对我们完全没用吗?—— 有用,但用途不在流水线里

三个我认为真实成立的用法,按今天可行性排序:

1. **Annie 自己的交互式 Codex 会话。** 这是 Spark 的原始设计用途,不需要改 Flywheel 任何东西,
   不需要任何人拍板,今天就能用,而且失败代价 = 她当场看见、当场换模型。**零风险,零工程。**
2. **有机器判官的机械活**(未来,若要接):
   比如「修 lint / 修编译错误直到构建变绿」这类循环 —— 判官是编译器和测试,不是人。
   Spark 错了会被机器立刻打回来,不会静默流到下游。
   ⚠️ 但 Flywheel 现在**没有**这样一个独立节点(build-error 修复是在 implement 节点内部做的),
   所以要用它,得先造出这个节点 —— 那是一笔新工程,不是一次接线。
3. **prototype 环节里「写那段扔掉的原型码」那一步**(未来,若要接):
   全 Flywheel 我找到的**唯一一处真正贴合**的地方(见 D-4b)。
   ⚠️ 同样卡在粒度上:今天绑模型的最小单位是**整个 prototype 环节**,而那个环节还包含
   出图给 founder 看、开门等她、以及判 doable —— 三件它都不该碰的事。

# E. 混用的判据 —— 判据该是什么、谁判、判错的代价

Annie 说「后面可以和 Opus 混着用」。要让混用长期跑得住,得回答三个问题:

## E-1. 判据该是什么

**不该是「这个任务清不清楚」。** 清楚的任务照样可能很长、很多文件、很需要工具。
(§D-4 已经展示了这个判据会怎么误判:QA 判据最清楚,却是最不该给 Spark 的地方。)

**该是「错了会不会被自动抓住」。** 具体成三个都要满足的条件:

1. **下游有机器判官** —— 编译器 / 测试 / schema 校验能判对错,不需要人看。
2. **上下文装得下 128k,且不需要看图。**
3. **失败是响的,不是哑的** —— 错了会红,不会变成一份看起来合理的错答案流到下游。

第 3 条是重点。Spark 的危险不在「它会写错」,在「**它会写出看起来对的错东西**」——
一个更小的模型给出的错误答案,和正确答案在表面上几乎无法区分。
所以判据的核心不是它有多准,是**我们能不能在它错的时候立刻知道**。

## E-2. 谁来判

三种,代价递增:

| 谁判 | 代价 | 评价 |
|---|---|---|
| 每次由人(Annie / Lead)挑 | 每个任务多一次决策 | ❌ 决策成本很快超过省下的额度 |
| 由规则自动判(节点类型固定绑模型) | 一次性工程 | ✅ 唯一可持续的形态 —— 和现在 template manifest 绑模型的做法一致 |
| 让模型自己判要不要升级 | 便宜但不可靠 | ❌ 判断自己能力边界是它最不擅长的事 |

**⇒ 若将来真要混用,形态必须是「按节点类型静态绑定」,不是「按任务临场挑」。**
好消息是我们的基建**已经是这个形态**了(每个 template 节点自带 vendor/model/effort),所以不需要新机制。

## E-3. 判错的代价

| 判错方向 | 代价 |
|---|---|
| 该用 Opus 的给了 Spark,**且下游有机器判官** | 低 —— 多跑一轮,浪费一点时间 |
| 该用 Opus 的给了 Spark,**且下游只有人在判** | **高 —— 错误静默流到下游,可能一路到 ship** |
| 该用 Spark 的给了 Opus | 低 —— 就是现状,只是慢一点、贵一点 |

**不对称。** 保守的默认(继续用 Opus)代价小,激进的默认(试 Spark)代价可能很大。
这本身就是「先不动、只做低风险试用」的理由。

# F. 🔴 Annie 给的三份材料 —— 逐份标明成色

Lead 转达的纪律:**「她给的材料里说 X」和「我核到 X」要分开写,不许合并成「X」。** 这一节就是分开写的地方。

**先说一件事实性的更正,以及它的收尾:**
Lead 通报说这几条小红书链接取不出来(「要在 App 里扫码才看得到」)。**我独立试了一次,三条全部取到完整正文**,
其中一条连评论带子回复。并排报给他之后,**他自己也复现成功,并已向 Annie 撤回 —— 她零动作,没有白花时间。**

⚠️ **我提的成因假设(token 被正则截断)被证伪了**:实测两条 token 只差尾部一个 `=`(46 vs 45 字符),
**两边都成功** —— 接口对尾部 `=` 在与不在都容忍。而他上次失败时用的那个 token,
来自一个**已经不存在的进程**(Lead 于 00:05 重启),**永远取不回来**。

⇒ 所以这一格的正确收尾是:**能用的配方是已知的,失败的成因是未知的,而且这个未知不会再收窄。**
⛔ **不要再为它开分支。**

⭐ **四条从这次撞车里抽出来的通则(比结论本身有用)**:

1. **读错误消息要读「它在陈述什么机制」,不是读「它的语气有多终局」。**
   那句「Scan via rednote」是一句关于**这个页面不为你渲染**的机制陈述,不是一句关于**这条路取不到数据**的判决。

2. **【页面打不开】和【页面里拿不到可用 token】是两件事。**
   把「落地页渲染 / token 来源 / 取内容接口」压成一个自变量的对照,**和一个没做的对照,在文字上长得一样硬**。

3. 🔴 **一个可执行的验证步骤,会让它所检验的那个假设显得已经被检验过了。**
   我当时写的是「我怀疑是 token 被截断了 —— 你把长度打出来就知道」。**后半句的确定性会渗染前半句**,
   而前半句其实**一个前提都没验过**(我从没见过那个失败的 token)。
   ⇒ 一句话:**方法的硬度冒充了结论的硬度。**
   ⇒ 做法:给假设的时候,**把「我没见过的那个东西是什么」一起写出来**。

4. 🔴 **限定词是压缩时最先掉的东西 —— 而掉了之后,剩下的那个数字/那句话看起来比原文更硬。**
   今晚这条出现了**三次**,三次都造成了真实代价:
   ① 我读记忆索引行没读原文,漏掉两个限定词;
   ② 我把成色不齐的两半压成一句好记的标题,掉的正是限定词(见 D-5);
   ③ 一条「≲6000px、真正故障点在 10k/14k」的**带余量参考线**,被压进索引行时掉了后半句,
      到我手上变成了一道悬崖 —— 我为它砍了四轮散文,而那四轮**不产生任何效果**。
   ⇒ 配套纪律见 D-5:**凡是准备当标题的话,必须【逐半】检查成色,而不是整句盖一个章。**

5. 🔴 **成色纪律有两个方向,而我们整晚只在防其中一个。**
   我在这份研究里说过「重发新卡会把她的批注**孤立掉**」——**这话说重了**。
   准确说法是:那一轮可能**被忽略**,不是**被销毁**(旧 URL 一直活着)。
   **我在没核实的情况下,把一个可恢复的后果说成了不可恢复的。**

   | 方向 | 形态 |
   |---|---|
   | **过度声称** | 把不确定的说成确定的 |
   | **过度保守** | 把可恢复的说成不可恢复的 |

   **两个都是「说得比证据硬」,只是符号相反。** 而**过度保守那一侧更阴**:
   > **一个被过度谨慎压下去的决定,不留任何痕迹,没有人会去审计它。**
   过度声称至少会被现实打脸;过度保守不会。
   ⇒ 所以这不是「注意措辞」,**这是成色纪律缺的那一半**。

6. 🔴 **「我察觉了并且报告了」会产生一种【我已经处理了它】的感觉,而实际上什么都没变。**
   本单实例:我砍散文砍到第三轮时,**自己已经察觉不对**,并在报告里如实写了
   「砍到后面已经在动铺陈句而不是重复内容了」—— **然后继续砍了第四轮。**
   ⇒ 一份如实写着「我知道这样不对」的报告,**读起来非常负责,产出却和沉默完全一样**。
   ⇒ 这和我们今晚追的那一族是同一个病:**看起来在运作、其实是空转。**
   ⇒ **可执行版**:察觉到自己在**为一个约束伤害目标**时 —— **当场停手并质疑那个约束。**
   **「报告了但继续做」不算处置。**

7. 🔴 **更正要出现在【那句错话会被读到的地方】,不是【我记录错误的地方】。**
   本单的实例:那句没带条件的标题本来要给 Annie 当结论用,她是最可能引用它的人 ——
   所以更正进了**她页面的首卡**,而不是只留在 research.md 里。
   只在记录处更正,等于**把更正投给了不会读到错话的那批人**。

# G. 结论(第二轮修订)

## 一句话 —— **两半成色不同,必须分开说**

> **「当决策者不行」= 已立。**
> **「当执行器可以」= 待定** —— 它的条件正是下面那道开工闸;闸没开之前,**只有前一句能对外说**。
>
> 而**即便**后半句将来立住,我们今天也**买不到「只要执行那一步」**(粒度错配)。

⚠️ 我第一版把这句写成了不带条件的「执行器可以,决策者不行」,**是错的** ——
两半成色差一个量级,而且 C-2 那条待核报告描述的失败(不照 spec 做、中途停、跳过测试)
**全都落在【执行】那一半**。详见 D-5。

## 三层展开

**① 真正的产出:粒度错配。**
「它什么都不行」不可操作。准确的说法是:**它擅长的是「一个环节里的某一步」,而我们绑模型的粒度是「整个环节」**,
每个环节都把**执行**和**决策**打包在同一个模型上。所以接不上不是因为它不行,是因为**没有一个能只买一步的接口**。
这条点名了要改什么才接得上(D-5)。

**② 立项前提本身要打折:「空着」不等于「经得起用」。**
那条 100% 未用的 5 小时线是硬事实,但它说的是**余量**,不说**能撑多久**。
有一手用户说它「额度消耗飞快」,而它每秒 1000+ token —— **空着的可能不是一桶油,是一杯。**
这一格**没人量过,我也没量**(A-4)。此外官方保留随时收窄这条线的权利(B),
还有报告说主线烧完时它会被一起挡(C)—— 而我们的 `implement` 正在重度烧主线(A)。

**③ 她的两个假设:一个不成立,一个对了一半。**
- **QA — 不成立。** 六条能力边界正面对撞;而且 QA 是**纯决策岗**(产出物就是一个 PASS/FAIL 判决),
  正是「决策者」那一栏。它还是我们抓别人出错的网,换小了是**哑的失败**(D-4)。
- **prototype — 对了一半,对的那半很实。** 「写那段扔掉的原型码」是全 Flywheel **唯一一处真正贴合**;
  但这个环节真正的产出物是**「走不走得通」的判决** —— 又是决策。而两者今天同属一个节点(D-4b)。

## ⚠️ 一条压过以上全部的【开工闸】

**在「它遵不遵守注入给它的规则」(C-2)被复现或排除之前,不该为 Spark 开任何工程** ——
包括那个能只买一步的接口,因为那种接口**恰恰也是靠注入规则来约束的**。

**为什么这条闸这么硬**:我们对任何模型的**全部**控制手段都是**注入的文字** ——
agent 契约、rules bundle、doc-flow 指令、founder-only-authority 合同,**全是**。
⇒ 这件事一旦成立,**不是质量问题,是治理问题**:我们所有的流程和安全保证会对它整体失效。

🔴 **但这一格的形式是【开工闸】,不是【关于 Spark 的结论】**:
证据(C 级、单一用户、2026-02 版本、我没复现)撑得起「**先别建**」,撑不起「**它就是这样**」。
⛔ 全文任何地方都不许写成「Spark 不服从规则」—— 这两句长得很像,**而只有后者会被下一个人当事实引用**。
要它变硬需要**我们自己的一次实测**(协议已冻结在 §H1)—— **再找第三条同源材料不会让它变硬,只会让它看起来变硬。**

## ⭐ 两条比这份研究活得久的通则

1. **判断一个环节能不能换便宜模型,看那个环节的失败会不会【当场响】。**
   **会响的可以试;不响的,省下来的钱由下游赔。**
2. **任何来自厂商路线图的限制都要带日期** —— 否则半年后它会被当成永久属性引用。

## H1 的实验协议(**先写死,再跑** —— 判据跑前冻结,免得跑完再挑一个好看的判据)

| 项 | 冻结值 |
|---|---|
| **假设** | 「如果给它一份含一条**机械可判**约束的注入契约 + 一个真任务,那么它会遵守那条约束」 |
| **约束** | 「**任何情况下先写测试**」—— 选它是因为**服从与否是机械可判的**:看提交顺序,不需要人来评价 |
| **成功判据(二值)** | 该约束在**真任务**里被遵守 = 服从;写完才补测试 / 完全不写 = 不服从 |
| ⛔ **不算核的做法** | **问它「你知道要先写测试吗」** —— 知道 X 和按 X 行动是**两次不同的测量**;必须造一个**它想违反的处境** |
| **样本** | 不少于 3 个真任务(单次服从可能是运气) |
| **能把这一格从 C 抬到 A** | 是 —— 因为它是**我们自己的数据**,不是第三条同源材料 |

⛔ **现在不跑**(与 FLY-1911 共用 codex 状态冲突)。协议冻结在这里,时机到了照着跑。
