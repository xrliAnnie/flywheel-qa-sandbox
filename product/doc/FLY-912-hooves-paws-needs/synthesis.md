## 0. 一句话结论

第一个真实客户的痛,底层不是「缺某个 dashboard」,而是**「我这套多系统的生意,到底在发生什么、哪里在悄悄漏钱/漏单,我理不清、也没想清自己下一步该干嘛」**。他们已经**能自己造工具**(而且造了),缺的不是能力,是**「理清思路、把散落的东西 organize 起来、判断该做对哪一半」**。→ 对定位的最大启发(Annie review 收紧后):Flywheel 的楔子是**「帮这类操盘手把事情理清、organize 起来、知道自己该做什么 → 帮公司成长」**,而且是**给他工具让他自己找到答案** —— **不是替他建 dashboard/根因视图**(我们对他系统理解没那么深),**也不是把完整答案端给他**。而这个「第一个客户」比「非工程」框架假设的**更技术**——这是定位要正视的信号,不是缺陷。

## 1. 怎么读这份梳理(定位纪律,先说清)

> **客户反馈 = 方向,不是照单全收的 spec。**(Annie 2026-07-06 硬原则)
> 客户(djw / Daniel)提得**过于具体**——统一 dropship dashboard、invoice↔order 关联、CheckDS 根因视图、修 stale-alert、两套数据模型——**都只当「方向信号」读,不是我们的 build 计划,也不承诺照做**,更**不是**要替 Hooves & Paws 定制开发。
> Flywheel 的定位是**提供系统给客户自己用**去解决自己的问题。所以本文抽的是 **problem 层 / 底层 job**,排优先级,并**逐条标「方向 vs 太具体先不做」**。面向客户的能力表述以 `product-intro/` 为准。

**样本诚实(说人话)**:目前**只有 Hooves & Paws 一个客户**的数据点(就一家,业内叫 n=1),而且只聊了 1 次、数字多是**某一瞬间的快照**(57 单一瞬间 / 125 单 30 天)。所以以下是**喂定位的方向信号**,不是被验证的市场规律——现在的定位是**建在一个样本上**的,要更多客户采访才能一般化。

## 2. 方法

用 `problem-definition` / `analyzing-user-feedback` / `synthesize-research` 的做法:
把客户说的**具体解法**先剥掉 → 追问「这解法是想解决什么 job / 底层想达成什么结果」→ 归纳成少数 problem 主题 → 每个主题标证据 + 优先级 + 对定位的启发。**这一步是本 issue 的核心**,因为照抄客户的 solution 会被带偏(他们自己都说「务必分开 scope / 只是方向」)。

本文是**在 Anna summary 第 5 节「产品设计启发」之上再进一层**:加 ①solution→problem 的显式分离 ②JTBD 化 ③排序 ④收敛成定位输入。不重复她已写的原始记录与结论。

## 3. 客户是谁 —— 一个被低估的定位信号

Hooves & Paws:1994 年创立的多渠道宠物+马术用品电商(Shopify 主店 + Amazon + eBay + Target),~2,800 SKU,今由 **Daniel** 精简+**高度自动化**运营。对接人 **djw** 是 Daniel 的 AI 助手,**直接接进店铺所有系统**。

关键观察:**这不是一个「完全非技术」的小白**。他们有——
- 自建 dropship 自动化栈(Cloudflare Workers 路由供应商、Veeqo/Ordoro 同步、处理发票、KV logs);
- 自建统一层 `hp-order-dashboard`(D1 数据库、登录/角色/admin、1,344+ 单、当天新鲜);
- 一个「ops/marketing hybrid」AI 助手,需求短而具体(「order X 卡没卡」「重写这条 listing」)。

→ **定位含义(重要)**:父 EPIC FLY-908 的框架是「**非工程**小企业也能用」,但我们的**第一个真实客户坐在『技术娴熟』这一端**——他们缺的是**时间/注意力 + 造对方向**,不是编码能力。这直接呼应 FLY-909 竞品扫描里悬着的开放问题:**目标客户到底是「有技术直觉、缺时间的操盘手」还是「完全非技术」?** 第一个客户的证据指向**前者**。这不是要改 EPIC,而是提醒定位别把「非工程」等同于「不会技术」——更准的可能是「**不想/没空当技术侦探的经营者**」。

> **✅ 已定(Annie 2026-07-06)**:beachhead = **甲**(时间紧、有技术直觉的经营者)。Annie 认这画像,并接受**现阶段只有一个客户、先为它定位**。与 FLY-909/FLY-910 同一发现合并后拍板。

## 5. Problem 主题(排序 · 证据 · 定位启发)

排序说明:客户**按压力**把 T1 排第一(未知成本);**按频率/耗时** T2 最重(每天 26 单 dropship、每个 exception 都是真诊断)。T3 是 Daniel 亲口点的**底层价值锚**。三者高度关联,是同一个「可信可见性」母 job 的三个面。

### 🥇 T1 · 未知风险的可见性(silent-failure)—— 客户排第一
- **Job**:「我不要求它永不出错,我要求**它出错时我知道**」——把「我不知道这到底有没有事」的焦虑,变成可见状态。
- **证据**:30 天 125 单发供应商,只 25% 有匹配确认;94 单挂 pending;内置 stale-alert **30 天一次没触发**。Daniel 补充:主要是**检测/解析失效**(货其实发了、bot 没读到确认邮件),不是丢单——但**真风险是「万一真卡一单,会藏在同一个盲区里没人发现」,直到客户来问**。
- **为什么排第一**:这是**未知成本 > 已知成本**。压力**不成比例于频率**——焦虑不是「这活烦」,是「我不知道是不是 fine」。
- **定位启发**:诊断类产品的核心价值之一 = **如实反映真实状态**,别让静默失败伪装成正常。「把未知风险变成可见」的价值感,**远超**「把已知琐事做快一点」。

### 🥈 T2 · 跨系统根因诊断劳动(the multi-system detective task)—— 最高频/最耗时 · 🟢 被 founder 验证的方向
- **Job**:「信号已经散在各系统里了,别让我手动串起来——给我**一个『这单为什么卡』的答案**」。
- **证据**:happy path 一切正常;一旦出问题,「**没有任何单一视图告诉你为什么**」,得手动串 Veeqo notes + Ordoro 库存 + Cloudflare KV logs(有时翻发票)才能还原一单。**每个 case 都不一样,无法固化成 checklist——每次都是真诊断。**客户原话:「that's not a quick lookup, that's the multi-system-detective task.」次痛点 Shopping feed hygiene 同形状(先查是哪一个才能修)。
- **🟢 Annie 的判断(review,2026-07-06)**:她觉得这个方向**有意思、理论上可做**,标为**被 founder 验证的方向**。她的**心智模型**:一个 Lead 本就了解系统里的各种信号,**只需要一个类 cron job 每天把信息整合一下 + 给个判断**;而且是**给工具让客户自己清晰简单地找到方案**,不是我们把一切都告诉他。**具体怎么做她还没想清** —— 记为方向,不是 spec。
- **定位启发**:痛不在**单个工具**,在**信号散落多系统、没被整合成一个『发生了什么 + 该怎么办』**。「帮用户**自己把多源信号整合起来、看清并自己找到方案**」是这类电商客户会真用起来的能力——注意是**给他能力/工具**,不是替他建一个死 dashboard、也不是我们替他把答案都算好。

### 🥉 T3 · 成本/利润可见性(clean P&L)—— 底层价值锚
- **Job**:「诊断的尽头是**钱**——让我把成本接回订单,看清真实 P&L」。
- **证据**:Daniel 原话「the real value add would be able to tie invoices of dropships to order so we can get clear PL」。排障是「nag(持续累积的烦)」不是「fire(救火)」——所以真正想要的**不是分钟数**,是**成本清晰度**。(呼应他们已有的 ordering-hub P&L 工具——dropship 侧没接上。)
- **定位启发**:**痛点的底层货币往往是钱/风险的可见性,不是任务本身**。产品设计/价值主张要**往下追一层**:用户要的常不是「这个视图」,是「这个视图让我看清的**钱/风险**」。→ 价值主张说**结果**(干净 P&L、不漏单),别列**功能**。

### T4 · 诊断类需求天然要分领域建模(问题形状即洞察)
- **Job / 洞察**:CheckDS(仓内自履约,**排除** dropship)与 confirmation gap(**仅** dropship-routed)是**两个不重叠的订单集 / 两套独立系统**,只是都长着「Daniel 要做人工判断」的形状。客户明确警告:**别一把梭进一个 dashboard**。
- **定位启发**:这类「诊断类」需求**天然要按领域分开建模**,别把用户不同的问题硬塞进一个视图——即使最后共用一个 UI。这是**产品该怎么想**的洞察,**不是**承诺给这家客户的交付。

### T5 · happy-path 已经 fine(反向信号,防过度投资)
- **观察**:product copy、campaign edits、analytics pulls「comparatively quick,usually one clean tool call」——**已经不痛**。
- **定位启发**:**别把投资砸在已经顺的单次 tool-call 上**。价值集中在「跨系统调查」这类高摩擦场景。区分「one clean tool call」vs「multi-system investigation」本身就是一条产品优先级判据。

## 6. 方向 vs 太具体先不做(逐条 tag)

> 硬原则落地:客户的每个具体方案都标清「当方向 / 太具体不做」,防止被 solution 带偏。

| 客户具体项 | 判定 | 理由 |
|---|---|---|
| 统一 dropship 根因 dashboard | 🧭 **方向**(能力级)/ ❌ 具体形态不做 | 底层 job(跨系统诊断可见性)是方向;「一个我们替他建的 dashboard」是太具体的交付形态,且违背「给客户自己用的系统」定位 |
| invoice ↔ order 关联 | 🧭 **方向**(价值锚)/ ❌ 具体实现不做 | 指向 T3 成本可见性 job,极有定位价值;具体怎么 join 是他们系统的实现细节 |
| CheckDS 根因视图 | ❌ **太具体先不做** | 单客户单系统的具体功能;只作 T2/T4 的证据 |
| 修 stale-alert / confirmation 解析 | ❌ **太具体先不做**(且是**他们自己系统的 bug**) | 我们不碰客户系统;但它暴露的 T1「静默失败可见性」是强方向 |
| 拆两套数据模型 | ❌ 实现不做 / 🧭 **问题形状是方向** | 「分领域建模」作为产品设计原则(T4)保留;具体两个 model 不做 |
| 先查清 pending 75% 到底发没发货 | ❌ 不做(客户侧行动) | 这是给**客户自己**的第一步建议,不是我方交付 |

## 7. 收敛 · 对 FLY-908 / FLY-911 定位的输入

把上面收敛成**可以直接喂定位**的 5 条:

1. **楔子(Annie review 收紧)= 帮客户「理清 + organize + 知道该做什么」→ 帮公司成长;给工具让他自己找到答案。** 不是「替你建 dashboard/根因视图」——我们对客户系统理解没那么深、**不能替建**;也不是**把完整答案端给他**。即便一个能自己造工具的操盘手,真缺的是「有人帮我把散落的东西理清、organize 起来、判断该做对哪一半」。诊断/可见性只是这个能力的**一个表现**,不是我们要交付的制品。→ 这是**给能力**(给他自建、自己找到答案的工具),不是**给成品**。
2. **目标客户 beachhead 已定 = 甲**(Annie 2026-07-06):**「时间紧、有技术直觉的经营者」**(更准是「没空当技术侦探的经营者」),不是「完全非技术小白」。第一个真实客户就在这端。Annie 认这画像,接受现阶段一个客户先为它定位。别让「非工程」被读成「不会技术」。(与 FLY-909/FLY-910 同一发现合并后拍板。)
3. **「给客户自己用的系统」被行为验证**:他们**已经自建**(hp-order-dashboard)。缺口不是能力,是 ①造对那一半 ②时间/注意力。→ Flywheel「**先对齐要做什么、再动手,一支持续养 codebase 的 AI 团队**」正好补这个:他们「built the wrong half」正因为注意力在别处;一个**先对齐**的团队本可以早点抓到更痛的那一半。
4. **价值主张说结果,不说功能。** 底层货币是**钱/风险可见性**(干净 P&L、不静默漏单),不是 dashboard 数量。定位文案往下追一层到「看清钱/风险」。
5. **「如实反映真实状态」是可与现有差异化对齐的产品美德。** T1 静默失败 + FLY-909 里我们的「工程级可信交付 / 独立质检」是同一种诚实——诊断类产品不让静默失败伪装成正常,和 Flywheel「独立验收、不自证」的 ethos congruent。可作定位的「可信度」轴的一个具体例证。
