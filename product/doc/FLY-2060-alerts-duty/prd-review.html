每一段下面都有一个意见框,写完到最下面点「一键汇总复制」,贴回 issue 里我才收得到 —— 页面不会自动同步。

① 真正的缺口是什么先看这个

告警频道已经是一条像模像样的工单队列 —— 有格式、有「该谁修」这一栏、有「新建 / 已认领 / 修复中 / 已解决」的流转。缺的不是这些。

缺的是:没有任何一个角色对「这条队列今天有没有被清空」负责。

现在的模式是逐条点名:被点到名 → 有人管。
没被点名的、点了名但那个 bot 没起来的、以及根本没成功发出去的 —— 这三类全部落地为零,而且没有任何人在看这条队列本身。

你当天的三件事(切号器喊了一天没人应 / FLY-1969 的卡被埋掉 / 提了一嘴没人管),指向的是同一个洞,不是三个 bug。

所以本 PRD 只补一件事:在「逐条点名」上面,加一个「整条队列有人负责」。现有的东西不推翻、不重建。

② 我去数了一下,数字比想象的难看影响验收口径

测量时间 2026-08-25 下午,数据来自本机的告警记账库和「发不出去」的存档目录。
口径提醒:我数的是「系统认为发生了一件该报的事」的条数,不是频道里贴出来的消息条数 —— 我没有读频道历史的通路。这个差别下面很关键。

55%近 7 天的告警里,超过一半只是同一个东西(工作区清理)在反复喊
77%再加上第二名(信箱投递失败),两个来源吃掉了近八成
77%近 7 天的告警压根没发进频道——416 条卡在「发不出去」,只有 126 条真的到了
第三个数字是这次最要命的发现。
有一整类问题是「系统想告诉你,但你根本没收到」。抽样看原因写着发送身份取不到钥匙,全部集中在那个刷屏最凶的来源上。
⇒ 如果「签收率」的分母用「频道里贴出来的条数」来算,这 77% 会从分母里凭空消失,签收率反而更好看。这一整类问题会被指标结构性地藏起来。

还有一个数要记住:近 14 天的每日量在 22 到 1735 条之间,差一个数量级还多。所以任何「日均多少条」的验收都不靠谱,必须拿同样长度的前后两段做对照。

③ 谁来值守,以及「这次为什么不会重演」你已认可候选

席位 = claude-infra-bot。三条理由是实测的:24 小时在线(挂了会被自动拉起)、已经有自己动手修的权限、本职活少。

但我要把上次的成因写清楚:Cass 做不灵,不是因为她不行,是因为处境 —— 她同时是分派、协调、汇报口,值守对她永远是第 N 优先级。而值守的本质是「优先级低、但必须 100% 覆盖」,这两个属性天生打架。

Cass 当时的处境值守席位必须换成的处境
值守排第 N,主职是分派协调值守是排第一的日常职责,写进它的角色文件
主职有人催,值守没人催每日结算是硬动作,悬案数直接进指标
只有一条条帖子,没有「整条队列」的概念明确对整条队列负责,清零是它的验收
我必须诚实说一句:换个 bot 本身不是解法。我没法证明 infra-bot 不会重蹈覆辙。真正起作用的是上面这三条处境的改动 —— 任何一条被砍掉,风险就回到原点。
顺带发现一个洞:「值守自己挂了」这条告警,现在的负责人写的就是值守自己。它挂的时候,它是自己的负责人 —— 这条永远不会有人签收。需要你拍板交给谁(见 ⑫ Q1)。

④ 值守合同:只有三种反应,没有第四种你已认可

档什么时候做什么禁止
A 自愈职权内、会修直接修,修完安静收工,不打扰你—
B 转办不归它管 / 不会修按 ⑥ 的表转给对应的人,两处都发(⑦),每天追到闭环禁止装懂
C 宁转勿吞判不清是哪一类按默认转办,并写下「我判不清的是哪一点」禁止「看不懂就放着」

「禁止装懂」具体是什么意思:对一条没有现成处置手册的告警,它可以看、可以查(读日志、看状态),但不许动手改系统状态去试。因为装懂的修复会把一个还能诊断的问题,变成一个被搅乱的现场。

⑤「签收」到底算什么 —— 这是我本版加的要你评

签收率 100% 是一个极其容易被盖章刷满的指标。如果不把「签收」定义死,一周后我们会拿到一个漂亮的 100%,和一条一模一样烂的队列。

算签收的:落到下面四种之一并留下记录 ——

  • 我来修 + 修了什么
  • 转给 X + 转到哪儿
  • 判不清,默认转 X + 我判不清的是哪一点
  • 这条不是真问题 + 掐源头的动作(改阈值 / 降级成通知 / 关掉发射点 / 提一张单)

明令不算签收的:

  • 只回一个表情 / 「收到」/「已看」
  • 把状态点成「已认领」但后面什么都没有
  • 对一堆同类的批量甩同一句话,没有一条真的落到上面四种

特别注意第四种:判成噪音不是免费的 —— 必须同时给出掐源头的动作,否则不算签收,算悬案。不然「判噪音」会变成新的盖章方式。

⑥「该谁修」的表首版,要 Tadashi 校

每一类告警都必须在表上有主人。「表上没有」这件事本身要能被发现 —— 新加一类告警,上线前必须先落表。

域主人大致是哪些
基建自愈值守自己工作区/会话/窗口清理、卡死、账号额度与登录过期、重启风暴、Bridge 异常退出(「谁都不救自己」的交叉规则不变)
引擎 · 通信Tadashi工作流引擎、三阶段卡住、自动 QA 卡住、发布失败、信箱/投递失败、部署降级
产品 · 交付对应项目 Lead(默认 Honey Lemon)给你的卡没送到、里程碑没送达、Runner 等 Lead 没人接
人的决定你权限类(这条是既有判例,不改)
判不清默认 → Tadashi必须附判据(见 ⑧),否则不算签收
代价点名:默认边指向 Tadashi,等于把「判不清」的成本压在工程侧。⑧ 那条规矩就是这条默认边的对冲 —— 没有 ⑧,一周后这条默认边一定退化成「看不懂就丢过去」。

⑦ 转办 = 两处都要发你已认可

一次转办必须同时发生两件事:① 在告警频道原帖上 @ 对方 + 一行去向(留痕,队列自己能读);② 正文进对方自己的场子(那张 issue 的讨论串,或对方的部门频道),带完整上下文。

为什么两条都要:只留痕 → 对方在频道里看不见(⑨ 之后更看不见);只发正文 → 队列上这条永远显示没人认领,悬案账算不清。

⑧「判不清」必须留下判据你的补充②

转办时必须写下「我判不清的是哪一点」,而且要能被指认、能被反驳:

  • ✅「我分不清这是 Runner 自己卡住,还是唤醒根本没投过去 —— 我看得到它不动,看不到投递记录」
  • ✅「这类告警我没有处置手册,历史上也没见过」
  • ❌「情况比较复杂」「不太确定」「需要工程判断」—— 套话,不算

两个用途:① 让「判不清」有成本,不能变成甩锅;② Tadashi 追加的 —— 这些「说不清的点」攒起来,三个月后就是值守手册的「怎么判」那一章。它是资产,不只是防御。

要求:判据要归集到一处能读的清单,不能散在各个帖子里。每周结算时产出「本周说不清的点」。

⑨ 所有 Lead 都进告警频道,但不被 @ 就收不到你的原话要求

照搬核心房那套(FLY-898)、并且是服务器层强制,不靠嘴上自律:

  • 不被 @ → 根本收不到(不是「收到了请忽略」)
  • 被 @ → 必达必看
  • 光打名字不算,必须真 @(核心房已有的收口,防止一堆人误触)

值守是这个频道的「大管家位」 —— 它收得到所有消息,包括没 @ 任何人的。这正是「整条队列有人负责」在投递层的前提。

⑩ 降噪 = 掐源头 + 留账你已认可

噪音不是靠值守忍,是掐掉发射源。每掐一次记一笔账:掐的是哪一类 / 掐前多少条 / 怎么处置 / 为什么这不是真问题(一句能被反驳的人话) / 什么时候生效。

这本账不是形式主义 —— ⑪ 的分母守卫直接依赖它:告警总量的每一次下降,都要在账上找得到对应条目。账上解释不了的下降 = 指标造假信号。

已经看得见的头两笔候选(判定权在域主人,不在我):

  • 工作区清理拒绝(7 天 416 条,55%):这是日常状态,还是真要人管的问题?
  • 信箱投递失败(7 天 169 条,22%):是真在失败,还是判定过宽?

⑪ 怎么算成功(含你的补充①)口径是本版重点

基线两个数(你认可的口径):试运行一周 —— 签收率 100%、悬案清零(每天 24:00 结算)。转办中且当天有追办动作不算悬案;转办后连续 2 天没人动 = 悬案,必须升级。

分母守卫(你的补充①,我把它做实了):
「签收率 100% + 悬案清零」是结果指标,可以靠少发告警刷出来。所以第三个数必须一起看:
③ 告警发射总量 —— 试运行期总量相对基线不下降;若下降,下降部分必须 100% 能被降噪账逐条解释。

分母怎么取(本页最重要的一条):

  • 分母 = 去重后的发射事件数,包含发不出去的那些。
  • 绝不能用「频道里贴出来的条数」当分母 —— 理由是 ② 里实测的 77%:那一整类「系统想说但你没收到」会从分母消失,分数反而更漂亮。
  • 推论:发不出去的那些也必须被签收。「没送到」本身就是一条要人判理的告警。

基线怎么取:用试运行开始前同样长度的窗口做同期对照。因为日量波动超过一个数量级,不许用日均阈值;还要逐类分解 —— 总量持平但结构性地丢了某一类,同样是失效。

再加四条防盖章的验收:

指标目标
判据完整率(转办条目里判据非空、非套话)100%(抽查)
转办闭环率(转出去的最终有结果)100%
值守自身噪音(它自己在频道里的发言量)不构成新的刷屏
难例覆盖:一周内至少真出现过一次「判不清」并留下判据≥ 1;一次都没有,必须显式记「找过,没出现」
最后一条为什么必要:只验「它做了没有」,一个系统性回避难题的实现照样全绿通过。一周内一条「判不清」都没有,更可能说明这一档形同虚设,而不是值守全知全能。
