## 1. 问题

现在的早报是**我手动跑出来的**。v1–v7 每一版都是我(或我的 runner)坐在那儿,
一步步驱动浏览器、把数据搬出来、拼页面、再投递。她看到的东西是真的,
**但产生它的过程不是产品,是我在演。**

三个具体缺口:

| 缺口 | 现状 | 后果 |
|---|---|---|
| **agent 当传声筒** | 数据要一段一段**过 agent 的对话上下文**:页面里读一段 → 回到自己的对话 → 再写进文件 | 100 条要 20–25 次往返,上下文被搬运占满,agent 没余量做判断 |
| **没有排程** | 每次都要人手动起 | 她要早报就得先找我;我不在就没有 |
| **反馈无处可去** | 页面上的笔记存 `localStorage`(页面自己写着「换机器看不到」) | 她读完的判断**没有出口** —— 系统不知道她觉得哪条有用 |

第三条最容易被低估:**早报现在是单向的。** 她每晚花 10 分钟读,产生的判断全部蒸发。

> **🔴 口径更正(Annie 2026-08-12 当场指出):** 第一栏我原先写的是「采集靠人驱动」,她问
> 「采集不是 Runner 去做的吗?」——**她是对的,是我词用错了。**
> 干活的当然是 Runner。真正卡住的是**数据要过 agent 的对话上下文**,即 agent 当传声筒;
> 而「要人手动起」是**第二条**(没排程)。我把两件事塞进同一句话,读出来就成了「人在采集」。

## 4. 先把一个词说清楚:「采集器」是什么

Annie 问了两次「采集器是什么东西?」。**问两次说明我一直没说清楚,这是我的问题。**
所以这里用最笨的方式讲一遍。

### 4.1 它是什么

**「采集器」就是把网页上的东西读下来、存成一个文件的那一小段程序。** 就这么简单。

具体到 X 的 For-you 流,它做四件事:

```
① 打开她已经登录的 Chrome,进 X 首页
② 往下滚(X 的内容不滚不加载)
③ 把滚出来的每条推文的 作者 / 正文 / 链接 / 时间 抠出来
④ 存成一个 JSON 文件
```

**这四步加起来 = 采集器。**

它**不做判断**、**不写早报**、**不筛选**。它只负责「把原料搬进文件」。
判断和写早报是后面另一段(agent)的事,读的就是这个文件。

我之前把这个词当成一个已知部件在用 —— 它不是,它是个还不存在的东西,
而且名字听起来比它本身气派得多。

### 4.2 她的第二个问题:「是不是也不需要 prototype 去做?」

**这个 prototype 已经做完了**(2026-08-12,`pilot/supply-probe/`)。
而且它推翻了我们原本以为的瓶颈。

原本以为要验的是「feed 到底给不给得出 100 条」。
**实测结果是这个问题不成立** —— 滚到 30 条时产量**完全没有衰减**(每轮 +9 左右,曲线 3/9/10/8 是平的),
上一轮记录的「第三轮零新增」没有复现。

⇒ **供给不是瓶颈。真正的瓶颈是第 ④ 步:怎么把数据从浏览器弄进文件。**

### 4.3 「无人值守」是什么意思(她的第三个问题)

**定义:整晚没有任何人需要坐在电脑前点任何东西。**

拆成两半回答,因为两半的答案不一样:

| | 状态 |
|---|---|
| **采集的动作**(滚动、抠数据、导出) | ✅ **全部可以自动做**。合成点击算「可信输入」,浏览器认它,实测跑通了 |
| **浏览器配对**(让 agent 能操作 Chrome) | ⚠️ **目前是人的动作** —— claude-in-chrome 要人点一次 Connect,而且必须只有一个浏览器连着 |

**所以「无人值守」目前唯一的真缺口不在采集器里,在浏览器基建里。**

> 口径:配对这条约束来自 chrome 技能文档 + FLY-1116 事故记录,**不是我这轮实测的**。

**缓解方案(已有现成做法):** 一个常驻的、已配对的、headed 的专用 Chrome profile
(chrome-repair 技能里的 "portable setup" 就是这个)。配好并保持运行后,后续每晚不需要人。
**但机器重启 / Claude 账号切换会打断它** —— 这是本方案已知的脆弱点,不假装它不存在。

⇒ **验收里必须包含:机器重启后早报能不能自己恢复。**(见 §8)

## 5. 需求

### 5.1 【核心】采集器怎么绕开「agent 当传声筒」

**这是整单唯一真正的工程未知数。** 其他部分都有现成东西可复用。

#### 问题的准确形状

原本的做法是 **agent 自己当搬运工**:它在页面里读一段,回到自己的对话里,再写进文件。

四条路已经**实测否定**(前三条是旧账,第四条是本轮新增):

| 路径 | 结论 |
|---|---|
| 页面 `fetch()` POST 到本机端点 | ❌ 混合内容策略挡(https → http://127.0.0.1) |
| 数据塞 DOM + `read_page` 读回 | ❌ 文本节点截断(塞 6,684 字节,读回约 150) |
| `javascript_tool` 返回值 | ❌ 约 1,200 字符上限 |
| JS 合成 `WheelEvent` 驱动加载 | ❌ 不触发懒加载 ⇒ 采集**必须**走真输入 |

还有一条**主动排除、没实测**的:把数据编码进 URL 打到本机端口。
技术上可能通,但那等于**把她 For-you 流的内容放进 URL 查询串** ——
违反「绝不把个人数据放进 URL」。**不试,不推荐。**

#### ✅ 已实测通过的解法:剪贴板

```
页面内把 100 条拼成一个 JSON
  → 注入一个按钮 → 真点一下(合成点击,浏览器认)
  → navigator.clipboard.writeText()
  → 宿主侧 LC_CTYPE=UTF-8 pbpaste > collected-x.json
```

**为什么这条成立而前四条不成立:它根本不走对话通道。**
剪贴板是操作系统级通路,容量以 MB 计。

**成本特性(这是关键):一次点击 = 一次导出,与条数无关。**
对比旧路径「100 条要 20–25 次分块往返」,这是从 **O(条数) 降到 O(1)**。

**真机验证(2026-08-12,生产 Chrome,不是替身):**

| | |
|---|---|
| 载荷 | 100 条中文 + emoji + 弯引号,**28,649 字节,63.9% 非 ASCII**(与真早报同形态) |
| 真值来源 | **页面内**生成 —— `TextEncoder` 算长度、`crypto.subtle` 算 SHA-256 |
| 防残留 | 写之前先给剪贴板下毒(sentinel)并回读确认;测完 sentinel 消失 ⇒ 确实是这次写进去的 |
| 结果 | **长度 ✅ / SHA-256 逐字节相符 ✅ / 严格 UTF-8 ✅ / JSON 解析出 100 条 ✅** |

#### 🔴 硬性前置:编码修法必须先落地

**默认 `pbpaste` 会毁掉数据,而且专挑中文。**

根因:本机 `LANG` / `LC_CTYPE` / `LC_ALL` **全部未设**,
`pbpaste` 于是把剪贴板里的 Unicode 转成旧的 Mac OS Roman 再输出。

同一份 100 条中文载荷,两种取法:

| 取法 | 落盘字节 | 严格 UTF-8 | 逐字节等于真值 | JSON |
|---|---|---|---|---|
| `pbpaste`(默认) | 16,747(**丢 42%**) | ❌ | ❌ | **解析不出来** |
| **`LC_CTYPE=UTF-8 pbpaste`** | **28,649** | ✅ | ✅ | ✅ 100 条 |

> **关于「30 条里坏 4 条」:** Annie 说得对 ——「就算 30 条里面坏 4 条,也是需要修的呀」。
> 补充一个她当时还不知道的数:那 30 条样本**恰好以英文为主**,所以只坏了 4 条。
> 早报正文是中文,**中文一上量就是全毁**(上表:整个文件解析不动)。
> 她要修的判断成立,而且比看上去更紧急。

**⇒ 需求 R1:所有从剪贴板落盘的读取必须带 `LC_CTYPE=UTF-8`。这是验收前置,不是优化项。**

#### ⚠️ 还剩的那个真未知数:驱动成本

供给不是瓶颈,取回不是瓶颈了。**剩下唯一线性增长的是「驱动浏览器滚动」的开销。**

实测速率 **~9 条 / 6000px**(= 6 次真滚轮)。推到 100 条:

```
100 条 ≈ 47,000px ≈ 72 次真滚轮
```

**而 runner 这轮在 30 条就停手了,停的原因是上下文预算,不是产量归零** ——
因为**每次真滚动都会回一张全屏截图**,这是这条路径的固定成本。

⇒ **100 条需要的滚动量,是已经耗尽预算那次的约 4 倍。**

**⇒ 需求 R2:滚动循环必须在不把每帧截图灌进 agent 上下文的前提下跑完 ~72 次滚动。**

**候选机制:`browser_batch`** —— 它把 N 个浏览器动作打成**一次往返**。
**但它的说明里写着「Screenshots and other images are returned interleaved with outputs」,
所以它到底省不省上下文,取决于 batch 里的 `scroll` 动作会不会各自回一张图。我不知道,没测过。**

**⇒ 建单后的第一个动作是这个实验,不是写代码:**

> **两臂对照(必须两臂,不能只跑一臂看着像省了就下结论):**
> - A 臂:12 次单独 `computer scroll`
> - B 臂:1 次 `browser_batch` 装 12 个 `scroll`
> - 测同一个量:**agent 上下文增长的 token 数**(不是墙钟时间,不是「感觉快了」)
> - 判据:B/A ≤ 1/4 才算这条路成立
>
> **如果 B 臂不省** —— 那 100 条这个目标就和「一晚跑完」冲突,必须回来找 Annie 重新拍,
> **而不是偷偷降到 50 条然后报「做到了」。**

### 5.2 三个数必须分开写(现配置把它们混成了一个)

`supply-probe` 顺带核出当前配置**没有单一真相**,三个数互相打架:

| 出处 | 数 |
|---|---|
| Annie 原话 | 起码 100 条 |
| `x-harvest/MANIFEST.md` | 按 100 记 |
| `sources.config.json` → `x-for-you.max_items` | **50** |
| `sources.config.json` → `x-for-you.stop_after_scrolls` | **6**(≈6000px,实测该位置 = **12 条**) |

而且这不是「写错一个数」:`max_items: 50` 的注释自己写着「上限是成本闸,不是产量预测」——
**它本来就不是目标值。** 真正会先咬住的是 `stop_after_scrolls: 6`,它比 50 和 100 都紧得多。

> **补一句这个 `50` 的来历(我查了 git,不是转述):**
> 它是 `justinsuntron 25 + sunyuchentron 25` 两个账号源的和。
> 08-11 10:04 那次提交把 `x-for-you` 从 `enabled:false` 翻成 `true`,**数字原封没动。**
> ⇒ **这个 50 没有主人,是个被继承下来的占位符。**

**⇒ 需求 R3:配置里把三件事拆成三个字段,各自有名字。Annie 2026-08-12 的取值:**

| | 取值 | 出处 |
|---|---|---|
| **① 目标 target** | **100 条 / 晚** | Annie:「我希望这个 Agent 每晚起码看 100 条 feed」 |
| **② 成本闸 cost_brake** | **不设** | Annie:「暂时不需要给它加成本闸」 |
| **③ 停止条件 stop** | **扫满 100 条即停** | Annie:「它看满 100 条 feed 就可以停止了」 |

**③ 需要一个补充条款(我加的,请她过目):** 万一 feed 真的先见底,只有「满 100 停」会永远滚下去。
所以停止条件写成:

```
停止 = 扫满 100 条  OR  连续 3 轮零新增
```

「连续 3 轮零新增」是 runner 自己定的归零判据(单轮零可能只是加载卡顿,不是没货),
**这轮一次都没触发过**。它是「确实扫完了」,不是「预算用光了」—— 和她「不设成本闸」不冲突。

**⇒ 同时删掉 `max_items: 50` 和 `stop_after_scrolls: 6`。** 保留它们 = 保留两个会先咬住的隐形刹车。

### 5.3 模型

**Opus。** Annie 2026-08-12 直接指定:「那个 Agent 你用 Opus 去跑就可以。」

不需要 1M 上下文 —— **恰恰相反,R2 的整个目的就是让上下文不被截图撑爆;**
用 1M 去装截图是拿内存换一个本该修掉的浪费(而且每 runner +0.35GB)。

### 5.4 筛选:扫 100,不是给 100

**这是她说得最明确的一条,不能做歪:**

> 「不是说需要把 100 条全部都给我,它需要在那 100 条里面筛选出觉得比较值得我们看的,再放在早报里面。」

- **扫 100 条** = 采集器的目标(§5.2 ①)
- **上早报的条数** = 闸门决定,当前 `gate_pass_max: 8`
  (Annie 2026-08-11 从 3 调到 8,理由是「早报是**发现工具**不是核实报告 ——
  宁可多给几条浅的,不要少给几条深的」)

**⇒ 需求 R4:早报必须在最上面写清楚底数。** 「扫了 100,选了 N」这个比例本身就是信息 ——
它让她知道今晚是「货多我挑」还是「货少我硬凑」。v7 已经这么做了(GitHub 扫 18 全列 18,X 扫 13 选 5),
**保持。**

**⇒ 需求 R5:被淘汰的不能静默消失。** 已有的 `check_states` 三态(`verified` / `scanned` / `mismatch`)
必须保留 —— 条目变多、深度变浅之后「扫到但没核」会成为多数,
**不能让没核的看起来像核过的。**

### 5.6 可配置的多源扩展(Annie 2026-08-12 加的目标)

她的话:「以后如果想要加新的 Feed(比如 Hacker News、Trending 等),其实只要再加一个新的
Type 进来……我希望它还是 configurable 的,比如最近只需要看 X,就可以暂时把小红书 disable 掉。」

**结论先说:这个不复杂,因为结构已经在配置文件里了。** 分三档,成本差很远:

| 档 | 例子 | 成本 |
|---|---|---|
| **① 开关已有的源** | 这阵子只看 X,把别的关掉 | **改 `enabled` 一个字段,零代码** |
| **② 加同 kind 的新实例** | 再加一个 X 账号源 | **config 里加几行,零代码** |
| **③ 加一个新 kind** | HN、小红书 | **要为这个 kind 写一段采集逻辑** |

**③ 贵不贵,只取决于一件事:这个源有没有现成 API。**

- **有 API(HN)→ 便宜。** Algolia 接口已实测(200 / 20 条 / 免 key),配置已躺在文件里。
- **要开浏览器(X)→ 最贵。** 得驱动真滚动,还受 §5.1 那个上下文成本约束。
- **小红书 → 未知,不承诺。** 走 MCP 大概率不抢浏览器,**但一次都没实测过**。

**⇒ 需求 R8:配置是唯一的加源/减源入口。** 开关一个源、加一个已有 kind 的实例,**不允许要求改代码**。
新增一个 kind 才允许写代码,且那段代码只做「把这个源的原料变成统一格式的条目」,不碰漏斗、不碰早报。

#### 并行:能力留在配置里,本轮按串行跑

她问:「有必要把这个做成并行的吗?……两个 runner,一个看小红书一个看 X,并行去做出东西快一点。」

**这个我们其实已经设计进去了 —— `needs_browser` 字段的契约原文就是:**

> `true` = 抢浏览器,必须与其他 `needs_browser` 源串行;`false` = 纯 HTTP,可并行

所以按当前配置:**GitHub 和 X 今天就能并行**(GitHub 是 `false`)。X 之间必须串行 —— Chrome 单客户端,这是硬的。小红书走 MCP 大概率能与 X 并行,**但没实测,不写死**。

**⇒ 需求 R9:本轮按串行跑,但配置必须保留并行能力(字段已在),等机器稳了直接开、不改结构。**

**理由不是架构,是负载。** 今晚机器就出过 OOM。并行省下的十几分钟,不值得拿一次 crash 换。
这是**我的选择,不是被逼的** —— 技术上纯 HTTP 源随时可以并行。

### 5.7 轻量偏好记录(Annie 2026-08-12 加的目标)

她的话:「我希望它多多少少可以学习一下我更喜欢看什么样的内容,哪怕只是用一个 markdown file
稍微记录一下……不需要搞个 machine learning model 去 train,那有点太夸张了。」

**巧的地方:她已经在产生这个信号了,不需要额外做任何动作。**

§7 里她的真实流程是「把值得跟进的 copy 出去贴到 core」。**她亲手挑出来复制的那几条,就是最强的
偏好信号** —— 比任何打分都强,因为那是她真的要拿去用的。

**⇒ 需求 R10:维护一个 `preferences.md`,输入只有两样:**

1. **她 copy 走了哪几条**(强信号 —— 她主动挑的)
2. **她写的评论 / 回到 core 里的话**(带理由的信号)

**输出**:下一晚闸门打分时,agent 先读这个文件当上下文。

**不做的**:不打分、不训练、不算权重、不做推荐模型。**这是一份笔记,不是一个模型。**
它出错的后果也只是「今晚选题偏一点」,不会静默地把某类内容永久埋掉 —— 这正是不做 ML 的理由。

#### 🔴 谁来写这个文件 —— 这一条必须写死,否则 R10 会变成一个没人执行的空需求

上面说「她 copy 走的那几条就是信号」是对的,**但系统看不见这个动作** ——
她是在浏览器里复制、粘到 Discord 的,采集器那边根本观察不到。
**§7 又明确不建机制**,所以没有任何代码能自动捕获它。

**如果不指定人,`preferences.md` 就永远是空文件,而 R10 会「实现了」却从不生效。**

**⇒ 需求 R10 补全:第一版由我(Honey Lemon)手写。**

- **触发**:她把某几条贴进 `#flywheel-core` 之后。
- **动作**:我把「她挑了什么 / 她说了什么理由」追加进 `preferences.md`,一次一两行。
- **频率**:有就写,没有就不写。**不定期、不补齐、不追溯。**
- **成本**:每次一分钟量级;这是 Lead 的活,不是 Runner 的活,也不是代码的活。

**为什么第一版故意是人工的:** 我们还不知道该自动捕获什么
——是「她复制了哪条」?「她说了什么理由」?还是「她后来真的开了单的那条」?
**先手写几周,让这份笔记自己长出形状,再决定要把哪一段变成代码。**
过早自动化 = 把一个我们还没理解的信号固化成机制。

> **口径提醒(这条是 Codex 审出来的,我原稿漏了):** 原稿写「她已经在产生这个信号了,
> 不需要额外做任何动作」——**对她成立,对系统不成立**。她确实不用多做动作,
> 但**得有人把这个动作记下来**,而那个人现在是我。

## 7. 反馈回流 v1 —— 明确不建机制

**Annie 2026-08-12 的原话口径:「我设想的初始版本可以做得简单一些。」**

### v1 就是这样(Annie 2026-08-12 亲口描述的真实流程)

我原先写的是「她看到值得跟进的,就开一个 issue」。**她把这条掰正了,而且方向不一样:**

> 「我的这个初始反馈,**并不是说日报一定要怎么改**。……比如我们今天看了 10 条内容,
> 也许其中某几条**还需要 deep dive,或者需要应用到我们的系统中去**。那我应该会
> **直接在那个日报上 copy paste,然后回复到 flywheel Core 的那个 channel 里**,
> 到时候就会**分流给不同的人**再去做接下来的东西。**这样子的反馈是一开始就会有的。**」

**⇒ 所以「反馈」不是「评价早报」,是「从早报里挑活出来」。** 这两件事的产品含义完全不同:
前者要评分控件,后者**只要好复制**。

真实链路:

```
她读早报 → 挑出值得 deep dive / 值得用进系统的那几条
        → 在早报上 copy → 贴进 #flywheel-core
        → 那边分流给不同的人 → 变成后续的活
```

- **没有反馈按钮。没有打分。没有「一键转 issue」。**
- 分流由 #flywheel-core 那边现有的人做 —— **不新建任何机制。**
- **这是第一天就有的行为,不是以后的功能。**

### 🔴 但它带出一条我原来没有的硬要求:每一条都必须好 copy

既然她的动作是「复制一条 → 贴出去」,那早报的每一条就必须是一个**自足的块**:

> **一条 = 是什么(一句)+ 链接 + 为什么值得看(一句)**,复制出去**直接可贴**,不用她手工拼。

**⇒ 需求 R12:早报每条支持整块复制,复制出来自带标题 + 链接 + 一句理由。**

**这跟「不建机制」不冲突:不建的是自动化,要建的是这个复制手感。**
(同一个形态我已经在 PRD 评审页上做过一次 —— 每节留言 + 一键复制带章节标签 —— 跑通了,可直接照搬。)

### 顺带:这个动作同时就是偏好信号

她 copy 走了哪几条,是她**亲手挑的**,比任何打分都强。§5.7 的 `preferences.md` 输入就是它,
**所以偏好记录不需要她多做任何动作。**

### 为什么这是对的(不是偷懒)

现在页面上那个 `localStorage` 笔记功能,是**比没有更糟**的形态:
它看起来像个回流入口,实际上换台机器就没了(**页面自己写着「换机器看不到」**)。
**一个会静默丢数据的入口,不如没有入口。**

⇒ **需求 R7:把 `localStorage` 笔记功能摘掉**,不要留一个假的回流口。

### 什么时候才该建机制

**等到「她连续几周都在把同一类东西贴进 core」** —— 那时候我们才知道要自动化的是什么形状
(是自动建 issue?是自动 @ 到某个人?是自动进某个待办?)。**现在建,是在猜。**

而且现在**有地方可以看出来了**:`preferences.md` 会记录她挑走了什么。
几周之后那份笔记本身就会告诉我们该自动化哪一段 —— **让证据先长出来,再动手。**

## 8. 成功判据

**⚠️ 全表遵守一条元规则:任何「修好了」的结论都必须有两臂对照** ——
只跑修好的那一臂看着通过,证明不了是修法起的作用。
(这条不是形式主义:本轮的 supply-probe 里,**同一个形状的仪器错误出现了五次**,
其中一次是用 `pbcopy` 造数据,写入端和读出端犯同一个错误、互相抵消,round-trip 看起来完美 ——
**对称的错误会互相掩盖。**)

| # | 判据 | 怎么量 | 为什么是这个数 |
|---|---|---|---|
| S1 | **每晚真的扫满 100 条** | 落盘 JSON 的条目数 ≥ 100,**去重后** | Annie 定的目标 |
| S2 | **数据无损** | 落盘文件严格 UTF-8 解码通过 + SHA-256 与页面内真值相符 | 中文不能坏(§5.1) |
| S3 | **上下文不被截图撑爆** | R2 两臂对照,B/A ≤ 1/4 | 这是 100 条能不能一晚跑完的前提 |
| S4 | **无人值守** | **连续 3 晚**没有人碰过任何东西,早报**在她起床前已经投到位** | 一晚成功可能是运气 |
| S5 | **重启能恢复** | 机器重启后的第一晚,早报仍然到位 | 浏览器配对是已知脆弱点(§4.3) |
| S6 | **筛选比例可见** | 早报最上面写明「扫 N 选 M」 | 她要知道今晚是货多还是货少 |
| S7 | **开关一个源不用改代码** | 把某个源 `enabled` 翻成 false,**只改配置**,当晚少扫那个源且状态栏写明它被关掉了 | R8;「可配置」必须被**执行过**才算数,不能只是声称 |
| S8 | **偏好记录真的被读了** | `preferences.md` 里写一条明确偏好 → 下一晚闸门的排序**可解释地**受它影响 | R10;否则就是写了个没人读的文件 |
| S9 | **每条能整块复制** | 复制任意一条 → 粘出来自带 标题+链接+一句理由,**不用手工拼** | R12;这是她真实动作(copy→贴 core)的唯一硬需求 |

**S7 特别说明:验收动作是「真的去开关一次」,不是「看配置文件里有这个字段」。**
字段存在 ≠ 翻了它系统会照做 —— 今天已经栽过一次(`stop_after_scrolls` 存在,但会先咬住)。

**S4 的 3 晚不是拍脑袋:** 它要覆盖的失败模式是「配对断了但当晚恰好没断」。
一晚过不了这一关。
