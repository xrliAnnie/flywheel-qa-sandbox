## 1. 我理解的真实意图(law 4:先摸清,再拆)

Annie 的原话是「每晚扫一批我配的源,早上给一份可互动日报」。但把 2026-08-10 HL 补的
「本周真实用法」放进来看,**这句话的字面意思不是她真正要的东西**。

本周实际发生了至少五轮(Kimi /swarm、block/buzz、Agent swarm 18 页、Prime Agent、
Cloudflare computer)。这五轮里,**价值全部不在「摘要」那一层**:

| 轮次 | 摘要值多少 | 真正的价值在哪 |
| -- | -- | -- |
| Kimi /swarm | 低(读了就知道) | 画出机制图 + 同步给 Tadashi |
| block/buzz | 低 | 读源码后的三问对照 |
| Agent swarm 18 页 | 中(图文本身有料) | **口径**:指出作者利益相关 + 题型偏向 |
| Prime Agent | 低 | **核实**:小红书那篇低估了它自己;读源码对照我们 |
| Cloudflare computer | 负(帖子本身是错的) | **核实**:抓出帖子三处错 → 收敛出 FLY-1688 |

**⇒ 我的判断:她要的不是「资讯摘要机」,是三样东西合起来的一个东西。**

1. **过滤器** —— 替她挡噪音,只留下值得她花 30 秒的。反向价值同样重要:
   结论是「不用看 / 跟我们无关」也是合格产出,而且很可能是多数产出。
2. **核实器** —— 原帖不可信。必须落到**原物**(GitHub repo / 官方文档 / 论文 / 源码),
   并明确标出「帖子说 X,实际 Y」。本周五轮里至少两轮的**全部**价值来自这一步。
3. **接线器** —— 「跟我们什么关系」。对照我们已知的事实(拓扑、67% 等待、
   校验器锁死出度…)。**没有这一段的条目应该被砍掉,不是照登。**

再加上她原单就有的第四件:**闭环** —— 她拍一下就变成 follow-up issue 草稿。

### 一句话复述

> 我要一个**每晚替我先审一遍外部信息的人**:他不只是读,他会去核原物、会告诉我帖子哪里
> 说错了、会说清楚这跟我们已经知道的东西什么关系,还会诚实地说「这条你不用看」。
> 早上给我一页我能 30 秒扫完、每条能拍一下就开单的东西。

## 2. ⚠️ 我必须先摆到桌上的一个张力(不点出来这单会做歪)

**本周五轮的价值密度极高,是因为每一轮都是一个 Lead 烧了大量 context 去深读 + 核实 + 对照。**
这和「每晚自动扫 4 个源、每源 N 条」是**完全不同的成本结构**。

- 本周真实节奏 ≈ **一天 1–2 条深的**。
- 「每晚扫 X feed + GitHub Trending + HN」的自然产出 ≈ **一晚几十上百条**。

如果每条都要做「核实 + 对照我们」,那是几十个深读任务/晚。这不是排程问题,**这是预算问题**。

**⇒ 所以这单最关键的产品判断不是「怎么扫」,而是「怎么砍」。**
我的强推(可被否决):**双漏斗**——

```
夜间:
  [扫读层]  广、便宜、每晚全跑  ──→ 打分排序 ──→ 只放行 top-N
                                                    │
  [深读层]  窄、贵、有硬额度      ←────────────────┘
     └─ 核实原物 + 「跟我们什么关系」+ 口径栏
早上:
  [日报]   N 条(个位数),每条可留 feedback ──→ follow-up issue 草稿
```

不设这个闸,日报会退化回「摘要机」——也就是本周证明了**没有价值**的那种东西。

## 3.5 边界:本条 vs「语音总管 / 统一 CoS」(HL 2026-08-10 Round-1 回复后补)

### 为什么现在要划这条线

Annie 刚提了一个新的组织构想:**取消各项目分散的 CoS,改设一个统一 CoS,常驻语音**,
统筹所有项目状态、汇总各 Lead 需要她决策的事再向她汇报;她明确的一个能力是
「平时我对着电脑时,他接收定期的进度汇报(比如每半小时一次)」。

⇒ **「定期把该看的东西汇总给 Annie」现在有两个候选载体**:本条(夜间扫外部信源 → 早报)
和统一 CoS(常驻汇总内部状态 → 语音)。**各写各的,最后一定打架。**

### 线在哪

| | **FLY-1410(本条)** | **语音总管 / 统一 CoS** |
| -- | -- | -- |
| 信源 | **外部**:X / GitHub Trending / HN / 小红书 | **内部**:各项目状态、各 Lead 待她决策的事 |
| 节奏 | 每晚扫一次,早上交付一次 | 常驻,约每半小时 |
| 交付形态 | 可互动 HTML(每条留 feedback) | 语音 |
| 本条**不碰** | — | ✋ **内部系统状态汇报** 全归那条线 |

### 为什么必须分开(是产品理由,不是行政划线)

1. **信源的可信度根本不同。** 外部信息**不可信** —— 本单 70% 的价值就在「核实」
   (帖子说 X,实际 Y)。内部状态是**我们自己的账本**,不需要核实,需要的是**去重和聚合**。
   这是两种完全不同的加工。
2. **节奏会互相污染。** 半小时一次的内部播报和一天一次的外部日报塞进一个载体,
   **高频的会把低频的冲掉** —— 早报会消失在噪音里。
3. **形态由使用场景决定。** 她对着电脑时不想读页面(→ 语音);
   而外部条目需要她**逐条做决定**(→ 可互动 HTML + feedback 框)。
4. **可靠性预算不同。** 本条整晚白跑(浏览器掉线)= 少一天日报,可容忍;
   那条漏报 = 她错过一件该拍的事,**不可容忍**。不该被同一套 SLA 绑一起。

### 将来要合,合在哪一层

HL 的初判是「共用**够格才出声**的打分/过滤层」。**我同意方向,但要说得更准** ——
「共用打分层」这句话可以指两种完全不同的东西:

- 🚫 **不能共用:打分的判据。**
  外部条目的分 = 「核实后还站得住 + 跟我们已知事实有关系」;
  内部条目的分 = 「卡了多久 + 是不是只有她能拍」。**两套判据没有共同特征,硬合就是空抽象。**
- ✅ **能共用:打分之后的那个闸 + 注意力预算合同。**
  即一个统一的「注意力预算」概念 —— 各自打各自的分,但**都必须申报「我这次要占她多少注意力」**,
  并服从一个总额。这才是 HL 说的「够格才出声」真正可复用的那一层。
- ✅ **最该共用、但最容易被忽略的第三件:她拍完之后怎么落地。**
  两条最后都收在同一个动作上 —— 她拍一下 → 变成一个 issue / 一个被记下来的决定。
  **这一层如果各写各的,会长出两套 follow-up 机制,那才是真打架。**

> **结论:合在「输出闸 + 落地动作」,不要合在「怎么打分」。**
> 各自的信源、加工方式、交付形态保持分开。

### 现在做什么:什么都不做

1410 **不引入任何跨线的抽象层** —— 两条都还没有活实例,现在抽象就是过早耦合。
这一段只负责把边界写下来,让将来要合的时候不用重来。

### 一条要挂起的 open question(不是这轮解)

统一 CoS 每半小时播一次、1410 每天早上给一份 —— **她的注意力总预算是同一个**。
所以 A 块里「每晚深读几条」这个数,**将来必须和 CoS 的播报频率一起看,不能各自最优**。
等两条都有形状了再一起定;现在先记下,别在 1410 里单方面锁死。

### ② 跑多少时间 —— 一条时间线 + 每段预算

| 时刻 | 阶段 | 预算 | 超了怎么办 |
| -- | -- | -- | -- |
| 00:30 | **浅层 A:HN + GitHub Trending**(纯 HTTP,不碰浏览器) | 10 min | **砍源不砍时间**:按固定优先级,超时丢掉未抓完的源,报告状态栏写明 |
| 00:40 | **浅层 B:X via claude-in-chrome**(抢浏览器,单客户端) | **15 min 硬超时** | 超时即停,**已抓到多少算多少**,状态栏标「⚠️ 超时,只抓到 N 条」。**绝不重试**(重试会顶到打分窗) |

| 02:30 | 写报告 + 发布 | 10 min | — |
| **02:40** | **生成完成** | — | 仍然完全避开 03:00 晨会窗 |
| **08:00** | **投递到 thread**(与生成解耦) | — | 推荐值,可调 |

#### ⚠️ 关于「X 不能和别的并行」—— 我要精确化一下

HL 给的约束是「Chrome 单客户端,所以 X 那段不能跟别的抓取并行」。
**真正的约束比这个窄:X 只跟「其他要用 Chrome 的活」互斥。**
HN 和 GitHub Trending 是**纯 HTTP**(curl / gh API),**根本不碰浏览器** ——
技术上它们可以和 X 同时跑。

**但我仍然推荐串行,理由不是资源冲突,是负载:**
我在上一版自己写过「夜里跑重活会把机器跑挂,每晚 crash 的主因是 load 过载」。
并排跑省下的那 10 分钟,不值得拿 crash 风险换。**所以串行是我的选择,不是被逼的。**

**真正不可协商的互斥是这条**:X 抓取期间,**任何其他要用 Chrome 的活都得让路**
(比如 deep-research)。这条要写进调度约束,不是靠自觉。

### ②-bis X 的失败降级(HL 硬性要求 + 我的加强)

**X 是整条链路里唯一一个「会在夜里静默失败、而且自己修不好」的部分** ——
claude-in-chrome 的配对是**交互式**的,要有人在扩展里点一次 Connect;
一个 00:30 无人值守的任务,配对掉了它没有任何办法把自己接回来。

#### 三条硬性规则(HL 定的)

1. **X 拿不到 ≠ 今晚白跑。** HN + GitHub Trending 照常走完、照常出报告。
   **X 是可降级源,不是阻塞源。**
2. 🔴 **报告必须明说「X 今晚没拿到,原因是 ___」**,而不是只让条目安静地少一截。
3. **失败要可区分**:配对掉了 / 抓取超时 / 抓到了但 0 条 —— 三种不同情况,报告里要分开。

#### 我的加强:不要「失败时才说」,要**每晚都说**

HL 第 2 条的写法是「X 挂了要说」。**我建议改成:报告顶部固定一行「今晚源状态」,
每个源每晚都报,不管成没成。**

| 写法 | 问题 |
| -- | -- |
| 只在失败时说 | **要求失败被正确检测到**。检测器自己漏了,就又变成静默 —— 这正是我们在治的病 |
| **每晚固定报**(我推荐) | **状态行缺失本身就是信号**。不依赖任何一个检测器判断对不对 |

```
今晚源状态
  HN               ✅ 抓到 12 条
  GitHub Trending  ✅ 抓到 41 条(去重后)
  X · 我的 feed     ❌ 浏览器没连上 —— 需要你在扩展里点一次 Connect
  X · 指定账户      ❌ 同上
```

#### 三种 X 失败怎么区分(可执行判据)

| 情况 | 怎么判 | 状态栏怎么写 | 要她动手吗 |
| -- | -- | -- | -- |
| **配对掉了** | 列连接的浏览器返回空 / 工具报未连接 | ❌ 浏览器没连上 —— **需要你在扩展里点一次 Connect** | ✅ **要** |
| **抓取超时** | 15 min 硬超时触发 | ⚠️ 超时,只抓到 N 条 | ❌ 不用 |
| **抓到但 0 条** | 连接正常、流程走完、结果为空 | ✅ 连上了,但 24h 内 0 条符合条件 | ❌ 不用 |

> **第三种必须和前两种分开,这不是文字游戏。**
> 「0 条」**不是故障** —— 把它混进失败里,会让她去修一个没坏的东西。
> 反过来,把「配对掉了」写成「今天没什么可看的」,她就永远不知道要去点那一下。
> **这一栏里唯一需要她动手的只有第一种,所以它必须长得跟另外两种不一样。**

**两个设计约束,我主动点出来:**

1. **必须避开 03:00。** 那是 daily-standup 的历史窗口(FLY-1045 记录过 03:00 standup-service 冲突)。
   虽然 standup 现在没在跑,**设计上不该占用它的窗**。所以窗口定在 00:30–02:30。
2. **夜间跑重活会伤机器。** 已有记录:每晚 crash 的主因是 load 过载。
   所以 90 min 的深层预算是**保守值**,不是能力上限 —— **宁可少报一条,不要把机器跑挂**。

**「生成」和「投递」解耦**:报告 02:30 就生成好了,但**不半夜推送她**。
投递时间是独立参数(推荐 08:00,由 Lead 投到 thread)。

### ③ 什么样的漏斗 —— 带真实数字

```
浅层扫描      上限 ~160 条       HN 8–15 + GitHub Trending 去重后 45–55
                                 + X 上限 90(feed 50 + 指定账户 40)
      │
      │  硬性否决(不进打分,直接丢弃)
      │  ⚠️ X 的否决率显著更高:转推 / 闲聊 / 纯观点
      ▼
初筛保留       ~45–60 条
      │
      │  打分排序(三维 0–9 分)
      ▼
闸门放行         3 条            ← 没变。入口变宽不改变出口
      │
      │  深层核实 + 「跟我们什么关系」
      ▼
报告条目        1–3 条           ← 可以少于 3,不能多于 3
```

> **加了 X 之后最重要的一件事:闸门数字没变,还是 3。**
> 浅层从 ~65 涨到上限 ~160(约 2.5 倍),初筛只从 30–40 涨到 45–60(不到 1.6 倍,
> 因为 X 的硬性否决率高得多),而**出口一条没多**。
> **这正是双漏斗的意义** —— 加源提高的是「不漏掉」的概率,**不是她早上要读的量**。
> 如果加一个源就要多给她读一条,这个设计就失败了。

> ⚠️ 口径:X 那 90 条是**我们设的上限**,不是预测。真实产出量要等
> Annie 说的「先手动跑一遍」才知道 —— 初筛后的 45–60 因此比另外两个源的数字更不可靠。

> **关键设计:报告条目允许少于闸门放行数。**
> 深层核实后如果发现「这条其实没料」,报告就该说「今晚只有 1 条值得看」,
> **而不是硬凑 3 条**。这直接对应 Annie 的要求:日报要能承载否定结论。

#### 闸门判据 v0(粗版 —— 她要「哪怕粗也要给一版」)

三维各 0–3 分,总分 0–9,取 top-3:

| 维度 | 3 分 | 2 分 | 1 分 | 0 分 |
| -- | -- | -- | -- | -- |
| **① 跟我们有没有接口** ⭐权重最高 | 直接碰我们已知的一个具体问题(编排 / runner 生命周期 / founder 注意力 / 多 agent 通信) | 同领域不同问题 | 只是相关技术栈 | 无关 |
| **② 可核实性** | 有公开 repo / 论文 / 官方文档 | 有官方博客但无代码 | 只有二手转述 | 纯观点,无可核实主张 |
| **③ 新颖度** | 我们从没见过的做法 | 见过但有新数据 | — | 已知 |

**硬性否决(不进打分,直接丢弃)**:纯营销 / 招聘 / 融资新闻 / 过去 30 天已报过的同一项目。

**为什么这样加权 —— 两条都是从本周真实用法反推的:**
- **①权重最高**,因为 Annie 明说「跟我们什么关系比这是什么重要」,没这一段的条目该被砍掉。
- **②必须进闸门,不能留到深层才发现** —— 「核实」是本单的主环节,
  **没有原物可核的条目,核实环节根本无法执行**。等到深层才发现核不了 = 浪费一个 20 min 名额。

> **我对这版打分的诚实评价:这是拍脑袋的 v0。**
> 真正该做的是跑两周、把她的 feedback 当标注数据、回头调权重。
> **第一版不准是预期内的,不是失败。**

#### 淘汰掉的东西去哪(她点名要的)

| 被淘汰在哪一层 | 去哪 | 为什么 |
| -- | -- | -- |
| 硬性否决 | **丢弃,不留档** | 纯噪音,留档本身就是负担 |
| 打分了但没进闸门 | 报告底部一个**折叠的「没选上」清单**(只有标题 + 链接 + 分数,不做核实) | ① 她能扫一眼确认闸门没漏掉重要的;② **这份清单就是调打分的标注数据** —— 她说「这条你应该给我」时,我们才知道判据错在哪 |
| 进了闸门、深层核实后判定没料 | **进报告正文**,写明「核过了,结论是不用看」+ 为什么 | 这是她要的**反向价值**,不能悄悄丢掉 —— 「核过确认无关」和「没核过」对她是完全不同的信息 |

### ⑤ 下一步 = 「先手动跑一遍」,不是建 Skill

Annie 的原话顺序:**方案定下来 → 先跑一遍看效果 → 可以的话再去建相应的 Skill。**
⇒ **这一轮不建 Skill、不做自动化封装。** 到「能手动跑一遍」为止。

那一遍要回答的,恰恰是这份方案里唯一编不出来的三个数:

1. **X 真能抓到多少条?**(现在写的 90 是上限,不是预测)
2. **X 的硬性否决率有多高?**(初筛后 45–60 这个区间全靠它)
3. **15 分钟够不够?**(超时值现在是拍的)

跑完这三个数落地,方案才从「设计」变成「可以建」。

**为什么推荐 3**:贴近本周人肉版的真实节奏(1–2 条/天),留一格余量。
不是算出来的,是对齐已被验证有效的节奏。
