# X For you 抓取 — 底数如实记录(2026-08-11 第二次会话,登录恢复后)

**目标:100 条。实际:23 条。** 下面是为什么,以及每一块的去向。

## 实际数字

| | |
| -- | -- |
| 目标(Annie 原话) | 起码看一小时 Feed、起码 100 条 |
| 浏览器里实际采到 | **23 条** |
| 完整取回并落盘 | **19 条**(batch-001=10 / 002=4 / 003=5,无重复) |
| 差额 | **4 条**留在浏览器内存里没取回(采到 23,取回 19) |

## 为什么停在 23 而不是 100

**不是抓不到,是取不回来 + 上下文预算到顶。**

1. **传输是硬瓶颈(本轮再次实测)** —— 单次工具输出约 1,200 字符,一次只能安全取回
   **4 条**。100 条需要约 25 次「滚动 → 采集 → 取回 → 落盘」往返。
2. **滚动收益递减** —— 前两轮滚动把 10 条推到 23 条,第三轮 20 格滚动**没有带来任何新条目**。
   算法流不是滚多少出多少。
3. **上下文预算** —— 本 runner 的会话已接近上限。继续磨 100 条的风险是:
   **抓到一半、页面没建、报告没交**。

## 这次做对的一件事(以及一次自我纠正)

按「一边抓一边落盘」执行:每取回一块**立刻写文件**,不攒到最后。
⚠️ **但我第一版把文件写到了 /tmp** —— 那不持久,正好违反 Lead 刚给的「只有推到 origin 的才铁定还在」。
发现后立刻改成写进仓库并 push。**批次文件本身就是证据:即使会话现在死掉,这 19 条也还在。**

## 要真做到 100 条,需要的不是更多轮次

需要一条**正经的落盘通路**:采集端直接写文件,不经过对话通道。
三条绕过路径已实测全部不通(混合内容 / DOM 文本节点截断 / 工具输出上限)——
详见 RUN-NOTES 里「采集数据的取回是个独立问题」那一节。


## ⚠️ 一处我自己写错又自己抓出来的数

第一版 manifest 写「完整取回 22 条」,而三个批次文件加起来是 **19** 条。
落盘脚本按 id 去重后打印的是 19,**我的正文写的是 22 —— 报告里的数字跟数据对不上。**

改法不是把 19 写成 22,是把正文改成 19,并把这一段留着。
**一份自己的数都对不上的底数表,比没有底数表更糟** —— 这正是这份原型一直在治的病。
