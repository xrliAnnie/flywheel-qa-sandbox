# 「100 条到底能不能做到」— 两个子问题的实测结论

日期:2026-08-12 · Issue: FLY-1410
方法数据:`clipboard-raw.invalid-utf8.bin`(本次实测的原始落盘产物,30 条)

> **📌 关于这个文件的扩展名:** 它原名 `clipboard-raw.json`,后来改成 `.invalid-utf8.bin`。
> 原因:**它本来就不是合法 UTF-8**(这正是它要证明的东西),linter 连读都读不了,
> 会让整条 CI 挂掉。改扩展名是为了**保住这份取证原件的每一个字节** ——
> 绝不能让任何格式化工具「修好」它,修好了这份证据就没了。
> 字节指纹未变:`d8f1e801…`,12,208 字节。

## 先说三句话

1. **B 的前提被推翻了。** 不是「feed 给不到 100」——我滚到 30 条时**产量完全没有衰减**
   (每轮 +9 左右)。上一轮记录的「第三轮滚动零新增」**没有复现**。
2. **A 有解。** 第四条路(剪贴板)实测通了:12,208 字节 / 30 条一次性完整落盘,
   **数据全程不经过对话上下文**。
3. **所以真正的约束不是供给,也不再是取回,是「驱动浏览器」本身的成本。**

## B · 供给上限 —— 没找到上限

### 怎么测的(先说仪器,因为上一版的数就是被仪器坑的)

- **只用真滚轮**。两条更省的滚法都被我自己否掉了,而且是**实测**否掉的:
  - `window.scrollBy()` —— scrollY 到 3000,新增 0,页面高度不变 ⇒ 不触发懒加载
  - JS 派发合成 `WheelEvent` —— 同样 0 新增、高度不变
  ⇒ **X 把无限滚动闸在了「可信用户输入」上。** 这条本身是 A 的一个约束(见下)。
- **不用「JS 跳位 + 一小段真滚动」这种混合加速法。** 它跑得快 5 倍,但跳过去的区间
  从来没被渲染过 ⇒ 那些条目**永远不会被采到** ⇒ 会系统性低估供给。
  这正是本轮最不能犯的错,所以宁可慢。
- 采集用 **MutationObserver 持续捕获**,不是滚动间隔采样 —— 时间线是虚拟化的,
  滚过去的条目会被摘出 DOM,只在间隔采样必然漏。
- 每轮 = 6 次真滚轮 × 10 格 ≈ **6000px**,轮间等 2s。

### 数

| 轮 | scrollY | 本轮新增 | 累计 | 页面高度 |
|---|---|---|---|---|
| 0(进页面) | 0 | 3 | 3 | — |
| 1 | 6,000 | **+9** | 12 | 15,550 |
| 2 | 12,000 | **+10** | 22 | 21,263 |
| 3 | 18,000 | **+8** | 30 | 22,939 |

**曲线 3 / 9 / 10 / 8 —— 平的,不是递减的。**

### 「收益归零」的判据,以及我没用上它

判据本来定的是:**连续 3 轮零新增**才算归零(单轮零可能只是加载卡顿,不是没货)。

**我没有触发这个判据。** 我在第 3 轮停手,原因是**上下文预算**,不是产量归零 ——
每次真滚动都会回一张全屏截图,这是这条路径的固定成本。
按 Lead 的边界(别为了凑数硬滚到上下文见底),我停下如实报,而不是硬撑。

⇒ **能说的:到 30 条为止没有上限。**
⇒ **不能说的:上限是多少。** 我没测到。

### 一条外推(明标为外推,不是实测)

按 ~9 条 / 6000px 的实测速率,100 条约需 **47,000px**,即再约 12 轮同样大小的滚动。
**这是成本问题,不是供给问题。**

### 跟上一轮记录的冲突,如实摆出来

MANIFEST 记的是「第三轮 20 格滚动没有带来任何新条目」⇒ 推出「算法流可能吐不出 100 条」。
本轮**没有复现**这个现象。两种可能我都不排除:
- (a) 那次的零是加载卡顿 / 单轮偶然,被当成了上限;
- (b) For-you 是个性化流,不同时刻供给确实不同。

我能证明的只有一件:**「供给上限 ≈ 23」这个数不成立**,至少今天不成立。

### ⚠️ 一个可能自己制造了那个「上限」的配置

`sources.config.json` 里 `x-for-you.stop_after_scrolls: 6`。
如果它数的是**单次滚动动作**,那采集在约 6000px 就会停 —— 本轮实测那个位置正好是
**12 条**。**那不是 feed 的上限,是我们自己设的刹车。**
这条要跟下面的口径不一致一起看。

## A · 直写落盘 —— 有路,已实测

### 先确认旧账(读记录,不重试)

| 路径 | 结论 |
|---|---|
| 页面 `fetch()` POST 到本机端点 | ❌ 混合内容策略挡(https → http://127.0.0.1) |
| 数据塞 DOM + `read_page` 读回 | ❌ 文本节点截断(塞 6,684 字节,读回约 150) |
| `javascript_tool` 返回值 | ❌ 约 1,200 字符上限 |

**本轮新增第四条否定**(我自己实测的,不在旧账里):

| 路径 | 结论 |
|---|---|
| JS 合成 `WheelEvent` 驱动加载 | ❌ 不触发 ⇒ 采集**必须**走真输入,绕不开浏览器扩展这条窄门 |

**还有一条我主动排除、没有实测的**:把数据编码进 URL 打到本机端口。
顶层导航不受混合内容限制,技术上可能通 —— 但那等于**把她 For-you 流的内容放进
URL 查询串**,违反「绝不把个人/敏感数据放进 URL」。不试,不推荐。

### ✅ 通了的那条:剪贴板

**形态:** 页面内把采集结果拼成 JSON → 注入一个按钮 → **真点一下** →
`navigator.clipboard.writeText()` 写进系统剪贴板 → 宿主侧 `pbpaste > 文件`。

**实测证据(本次真跑,产物就是同目录的 `clipboard-raw.invalid-utf8.bin`):**

| | |
|---|---|
| 载荷 | **12,208 字节 / 30 条** |
| `pbpaste` 取到 | **12,222 字节**(多的是重定向的换行) |
| 解析 | ✅ 完整合法 JSON |
| 条目 | 30 条,**去重后仍是 30**,29 条带正文 |
| 数据是否经过我的上下文 | **否** —— 我只看见「OK 12208」这 11 个字符 |

**为什么这条成立而前三条不成立:** 它根本不走对话通道。
剪贴板是操作系统级的通路,容量以 MB 计,**12KB 是那条 1,200 字符上限的 10 倍**,
一次过。

**它的成本:** 每次导出需要**一次真点击**(剪贴板 API 要用户手势 ——
这点我上一轮踩过:用 JS 调 `click()` 必然被拒)。
⇒ **一次点击 = 一次导出,跟载荷大小无关。**
对比旧路径的「100 条要 20-25 次分块往返」,这是从 O(条数) 降到 O(1)。

**没验过的边界,不假装验过:** 更大载荷(比如 100 条约 40KB)我没测;
剪贴板会不会被其它进程覆盖、并发跑多个采集会不会互相踩,都没测。

现在的配置把 ②③ 当成了 ①。具体取值请 Annie 拍。

## 给产品口径的一句话

原来的判断是「先证伪最贵的假设:如果 feed 给不到 100,A 做到极致也没用」。
**实测结果是反过来的** —— feed 到 30 条还没露底,而 A 也有了 O(1) 的解。
所以现在真正该拍的不是「能不能做到 100」,而是:

> **每晚愿意为「多扫一条」花多少驱动成本?**

因为供给不稀缺、取回不再是瓶颈,唯一线性增长的是**驱动浏览器滚动的开销**。
「有多少收多少、封顶 N」仍然可能是对的产品口径 —— 但理由不是「feed 只有这么多」,
而是「N 之后每条的边际成本不值」。**这两个理由会导出完全不同的工程方案。**

# 🔴 更正:A 的「完整合法 JSON」是我用一把宽容的尺子量出来的

Honey Lemon 用严格解码复核,推翻了上面 A 那节的结论。**他是对的,我复核过了。**

## 我错在哪

我的判据是 `JSON.parse(fs.readFileSync(f,"utf8"))` 过了就算合法。
**`readFileSync(...,"utf8")` 遇到非法字节会静默替换成 U+FFFD,不抛错** ——
所以那把尺子会先把坏数据修好,再告诉我「没问题」。

严格复核(`TextDecoder(fatal:true)`):**7 处非法字节**,首个在偏移 906,
字节 `0xd5`,上下文 `anthropic<0xd5>s rule` —— 本该是弯引号 U+2019(`e2 80 99`)。
`0xd5` 正是 **Mac OS Roman 的右单引号**。

⇒ 他那句「弯引号 3 字节、中文也 3 字节,换成中文会大面积毁字」成立。**早报正文就是中文。**

## 坏在三段里的哪一段:第三段,取回

用原生 Unicode 写剪贴板(`osascript` 设值,跟 Chrome 同类的写法),再比三种取法:

| 取法 | 字节 | 严格 UTF-8 | 逐字节等于真值 |
|---|---|---|---|
| `pbpaste`(locale 未设) | 45 | ❌ 非法 | ❌ |
| **`LC_CTYPE=UTF-8 pbpaste`** | **57** | **✅** | **✅ 相等** |
| `osascript «class utf8»` | 58 | ✅ | ❌(尾部多一个换行) |

默认 `pbpaste` 的**首个非 ASCII 字节就是 `0xd5`** —— 跟真实产物同一个签名,现象复现。

**根因:** 本机 `LANG` / `LC_CTYPE` / `LC_ALL` **全部未设**。
`pbpaste` 于是把剪贴板里的 Unicode 文本转成旧的 Mac OS Roman 再输出。
**页面拼 JSON 和 `writeText` 都没问题,坏的是落盘那一步的编码。**

**修法:`LC_CTYPE=UTF-8 pbpaste`**,实测逐字节等于真值。

## ⚠️ 我在定位过程中先得出过一个相反的错误结论,记下来

第一次我用 `pbcopy` 造测试数据,得到「默认 `pbpaste` 逐字节完好、
加 `LC_CTYPE=UTF-8` 反而搞坏」—— **正好相反。**

原因:`pbcopy` 在 locale 未设时也把输入当 Mac Roman 读。写入端和读出端
**用同一个错误编码,两个错误互相抵消**,round-trip 看起来完美,
而剪贴板里存的其实是乱码(`clipboard info` 显示 `«class utf8»` 是 186 字节,
而我的输入是 118 —— 这个数露的馅)。

**教训:round-trip 相等不能证明中间那一步是对的 —— 对称的错误会互相掩盖。**
必须拿一个**独立于被测管线**的真值去比,我第二次才这么做。

## 还欠一步,不假装做完了

上面的定位用 `osascript` 写剪贴板**替代**了 Chrome 写剪贴板。
理由是 Chrome 扩展中途断连,拿不到浏览器。

**所以「Chrome 写 + `LC_CTYPE=UTF-8 pbpaste` 读 = 逐字节相等」这一条我没有实测。**
被替换掉的正是他要求的那个判据里的「页面里那个字符串」那一端。
扩展恢复后必须补:含中文 + emoji + 弯引号的载荷,页面内用 `TextEncoder` 算真值长度与校验和,
落盘后比长度 + 校验和 + 严格解码。**通了 A 才算成立。**

## A 的结论,改成这样

**机制成立**(O(1)、绕开对话上下文、真机跑通 12KB / 30 条),
**但当前实现的落盘编码是有损的**,而且损的正好是中文那一类字节。
**修法已定位并在代理条件下验证;在补完 Chrome 端实测之前,不能作为方案基础。**

## 补测:真早报量级 + 中文为主(他那个预测,现在有数了)

他说「换成中文内容,这条通路会大面积毁字」。**量化验证,而且比他说的更严重。**

载荷 = 100 条、**34,599 字节**、**66.5% 是非 ASCII 字节**(跟真早报同形态:中文正文 + emoji + 弯引号)。

| 取法 | 落盘字节 | 严格 UTF-8 | 逐字节等于真值 | JSON |
|---|---|---|---|---|
| `pbpaste`(默认) | **19,399** | ❌ | ❌ | **解析失败** |
| **`LC_CTYPE=UTF-8 pbpaste`** | **34,599** | ✅ | **✅ 相等** | **100 条** |

**默认路径丢掉 44% 的字节,整个文件解析不动。**
不是「30 条里坏 4 条」那种局部损伤 —— 那只是因为昨晚样本恰好以英文为主。
**中文一上量就是全毁。**

这同时补掉了我自己在上面列的两个「没验过的边界」:
更大载荷(34.6KB > 之前的 12KB)、以及中文大面积的情况。**修法在这两种条件下都成立。**

**仍然没变的那一条:写入端还是 `osascript` 代替 Chrome。** 见上一节。

## 用生产产物本身回答「Chrome 那一端」—— 不需要重开浏览器

Playwright 起不来(具体报错:`Socket directory path is too long (109 chars); set PWTEST_SOCKETS_DIR`
—— 那是 MCP 服务进程的环境变量,我改不了)。但这一端有个更好的证法:**拿真实生产产物直接反解。**

**推理:** 如果 Chrome 写进剪贴板的是**正确 Unicode**、只是 `pbpaste` 转成 Mac OS Roman 才丢的,
那么把产物**按 Mac Roman 反解**应该能**无损还原**。反之如果 Chrome 写的就是乱码,反解只会得到垃圾。

**实测(`iconv -f MAC -t UTF-8` 作用于 `clipboard-raw.invalid-utf8.bin`):**

| | |
|---|---|
| 反解后 | 12,222 字节,**严格 UTF-8 通过**,JSON **解析出 30 条** |
| 损坏点 | 原始 `nthropicÕs rule` → 反解 **`anthropic’s rule`** ✅ 弯引号逐字还原 |
| U+2019 还原 | **5 处** |
| U+FFFD 替换符 | **0 个** |

⇒ **生产剪贴板里存的是正确 Unicode。`writeText` 是干净的,全部损失发生在取回那一步,而且对这个样本是可逆的。**

### 顺带解开那个「12208 vs 12222 差 14 字节」

**那 14 字节不是多出来的数据,是我自己量错。**
我当时用 `Buffer.byteLength(readFileSync(f,"utf8"))` —— 先按宽容模式读成字符串(7 个非法字节
各被替换成 3 字节的 U+FFFD),再量这个**已被修好的字符串**的长度:
`12,208 + 7×(3−1) = 12,222`。**文件本身一直是 12,208 字节。**
同一把坏尺子,既给了我「合法 JSON」的假绿,也给了这个假差值。

### 这证明了什么、没证明什么

**证明了:** Chrome 的写入端干净,损坏 100% 在取回端 —— 用的是**真实生产管线的真实产物**,
比任何重跑都硬。
**没证明:** 这个样本以英文为主,弯引号在 Mac Roman 里**恰好有对应字符**才可逆。
**中文和 emoji 在 Mac Roman 里没有对应**,那种情况下取回是**不可逆**的丢失 —— 所以
「中文 + emoji 走真 Chrome」这条仍然没测,判据(长度+校验和+严格解码)也仍然没在真 Chrome 上跑过。

**⇒ A 的状态:从「完全未知」收窄到「只差一个已知形状的补验」,但仍未立住。**

最后一截由 Honey Lemon 在他的座位上跑(我这个客户端绑不到浏览器,交互配对是人的动作,
不该由 runner 补;也不该让 founder 去点 Connect 只为了让测试跑起来)。

`example.com` 空页注入判据脚本:页面内造 **100 条中文 + emoji + 弯引号**载荷,

| | |
|---|---|

## 🔴 第五次「仪器坏了但报告很漂亮」—— 这次差点把结论判反

他第一版校验和是手写 FNV,**JS 端算错、Python 端算对**,于是长度对、字节和对,
**只有校验和不符** —— 差一点据此报「B 也失败」。换成 `crypto.subtle` 的 SHA-256 就一致了。

**根因写准一点(免得下一个人以为 FNV 本身不能用):**
JS 里 `h * 0x01000193` 会超过 2^53,浮点乘法丢精度;`Math.imul(h, 0x01000193)` 是
32 位安全的、不丢。**坏的是乘法写法,不是 FNV。**
但既然 SHA-256 一行就能消掉整类陷阱,**判据里的「校验和」一律指定 SHA-256,不用手写哈希** ——
已同步改进 `chrome-leg-probe.md`。

**今天同一形状的第五次**(前四次:`readFileSync` 宽容模式静默修好坏字节 / `npx` 抓到同名野包冒充 linter /
