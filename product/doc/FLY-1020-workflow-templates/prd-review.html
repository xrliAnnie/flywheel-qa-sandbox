1 · 要解决的问题 + 北极星

结论 —— 痛点:今天 Flywheel 只有一个写死的 eng 三段式(Design→Implement→QA,静态直线),对所有 issue 一刀切。两个具体后果:① 一个「写 PRD」的 product issue 被自动 spawn 一个 QA runner 去「验」文档 —— Auto-QA 误触发,浪费 runner + 干扰你;② 现实里「验不过要回去重做」「一件事拆成 4 个 PR 逐个做」这类动态,静态直线表达不了。

结论 —— 北极星:每类任务一套轻的、默认的、可覆盖的模板;动态由 loop+skip 给;模板只钉粗脚手架,不钉模型怎么想。

一句话验收:eng issue 走三段式(QA 不过自动回去重做);product issue 走短模板(不再被误 spawn QA);没挂模板的活 = 裸单 session(agent 自己发挥);不配置 = 今天行为一个字不变。

2 · ⭐ 需要你拍的一条:MVP 收敛(动了你 v6 看到的验收面)

⚠️ 请拍板 —— 这条跟你 v6 看到的不一样 MVP 先只做内建的三个节点(Design / Implement / QA)。 你 v6 里看到的「创作视频 = Research / 生成视频(新节点类型)」挪到阶段 2。

为什么(工程实情): design|implement|qa 这三个名字硬编码在系统好几个生产面里 —— 数据库存的角色枚举、Discord 线程展示、ship 收尾清理、retry 恢复、重启对账。要支持「任意新节点类型」,得先把这五处全部泛化 + 做数据迁移。把它和「抽象化现有三段式」塞进同一刀,会漏掉整片生产生命周期面。(这是 Codex 评审第一条,我核过码属实。)

关键:这不是砍功能,是排期。三层设计 + 注册表这个「可扩展的口子」原样保留 —— 新节点类型将来就是「往注册表里加一条」。只是本轮不验收它。阶段 2 会专门做那五处泛化,然后开放新节点类型。
你要拍的:同意「MVP = 内建三节点,新节点类型排阶段 2」吗?若你要视频那类节点现在就能用,请说 —— 那 MVP 会显著变大、上线更晚。

3 · 三层架构:YAML 结构 + 注册表 + Markdown(最底层不变)

结论(打消那个误解):不是用 YAML 重写 brainstorm/research。 上两层只是加在现有 Markdown 之上的编排层:design 节点说「用这些技能」,每个技能具体怎么做仍由它自己的 Markdown 决定。新增只在上两层,第三层零改动。
分工一句话:YAML 管「节点怎么连」· 注册表管「每节点用哪些技能 + 哪个模型 + 有什么能力」· Markdown 管「每个技能怎么做」。

4 · 动态 = loop + skip(跑在固定节点上,不加新节点)

算子做什么你的两个铁例
loop某段重复到条件满足(串行)① QA↔Implement 来回,直到 QA 过 ② Design→4 个 PR:重复 (Implement→QA) 四次
skip条件跳过某节点(同套节点、不同任务走不同路)product 跳 QA(治 §1 的 Auto-QA 误触发)· 简单任务跳 Design
结论(有硬证据):「QA 不过回去重做」这个 loop 今天已经存在,只是焊死在 eng 三段式里(FLY-939)。升级 = 把它变成一行可声明的回边 + 加上「最多重复几次」的上限。—— 说明 loop 不是理论需求,是我们已经在用的东西。
安全细节:每条 loop 边必须写死最大重复次数,到上限就停下来升级给人,绝不无限打转;崩溃重启能接着跑;唤醒失败也停下报人,不静默跳过。

5 · 怎么配(轻 YAML)+ 不配就等于今天

配置项作用默认
pipeline.workflow_templates.enabled总开关:是否启用模板层false(不配 = 今天行为逐字不变)
pipeline.workflow_templates.default没匹配到类别时用哪套null = 裸单 session
pipeline.workflow_templates.files模板 YAML 文件(eng / product …)—
pipeline.node_type_registry.file节点类型注册表文件—
结论 —— 三种状态,都安全:不配 → 关,今天行为一个字不变;配错(格式坏) → 该项目失败关闭 + 大声报错(绝不「猜着跑」,也不拖垮整个 Bridge);配对 → 开。另有一个紧急 kill-switch 环境变量可一键回退。
安全约束:模板只从项目的主干(canonical)读,绝不从某个实现 PR 的工作区读 —— 否则一个 runner 能改自己的模板来跳过 QA。这条沿用现有纪律。

YAML 是给我们和 Tadashi 写模板的轻格式,不是给你碰的 —— 你永远只在 Discord 指挥。想「看有哪些 DAG / 注册到哪台 instance」的管理界面 = FLY-1038。

6 · 评审救回的一个大坑(值得你知道)

结论:我第一版 PRD 里,想让「模板内部的 QA」复用系统现有的 QA 放行开关。Codex 核码发现这会让 ship 永久卡死 —— 那个开关要求存在一份「独立 QA runner 写的通过记录」,而模板内部的 QA 从不写那份记录。真按第一版建出来,eng 的 PR 会永远合不进去。

已修:给 ship 放行加一条「模板专用」通道:模板内部 QA 通过时写自己的证据(绑定当时的代码 head,代码一变证据作废);product 跳过 QA 的,入口就标「本次免测」。没挂模板的老路径一个字不动。
另外两处也已收紧:① QA 通过的证据里,「代码 head 是谁」由服务端自己抓/校验,不信 runner 自报(不然 runner 能自证通过);② 三个开关互不串味 —— 关「独立 QA」不会偷偷改掉模板的形状。

Codex 三轮共 15 条 findings,我逐条核过源码、全部采纳,第三轮 APPROVED。评审报告一起存进仓库了。

7 · 节点类型:定义时可扩展,跑中不加节点

结论:「固定节点」= ① 模板内固定(YAML 定义时就定死,跑之前已知)② 跑中不临时长新节点。不是「全世界只有三种节点」—— 新类别将来在注册表里加自己的节点类型(定义时加,不是跑中插)。

对照:eng = Design/Implement/QA · product = 同套节点但 skip QA · 将来创作视频 = Research/生成视频(阶段 2,见 §2)。

8 · inject / fork = roadmap(不是不做)

能力什么时候想要(用例)状态
node-inject
(跑中加新节点)		跑到一半发现要一个模板里没有、又不是 loop/skip 能覆盖的新步骤 —— 如 implement 中途要插一个「安全审计」节点roadmap · post-MVP 跑中改图要更强的追踪与治理,值得单独一版 PRD
fork
(并行分支)		同时试多个方案比较 —— 两种实现策略并行、或 A/B 两版设计并行,择优roadmap · post-MVP 成本翻倍,要专门治理
结论:MVP 的动态 = loop + skip(已够解你举的两个铁例)。inject / fork 有价值、排 roadmap、进后续 PRD,用例记在案,不是砍掉。

9 · ⚠️ 红线守卫(可验收,防「轻模板」滑成「重 DSL」)

  1. MVP 只提供 我们内置的模板;项目只能选择 / 覆盖 / 关掉,不能随便自定义。
  2. 阶段 2 前不开放任意自定义节点类型。
  3. 节点内部怎么推理,模板一个字都不管 —— 由第三层 Markdown + 模型决定。
  4. 不挂模板 = 裸单 session,永远留着「不套流程」的出口。
  5. loop / skip 的条件只认有限的几个枚举值,不引入自由表达式(那就成 DSL 了)。
呼应你的红线:我们不绑模型的脑子,只挂治理和编排的钩子(成本、独立 QA 位置、gate 落点、context 隔离、可观测)—— 这些东西模型变强也不会过时。

10 · 分阶段 · Non-goal · 关联 issue

阶段 1(本轮验收):YAML 结构 + 节点类型注册表(含能力)+ 内建三节点 + skip + 每节点换模型 + 现有 QA loop 配置化 + 物化快照 + ship 放行的模板通道 + 内置模板(eng / product / 裸 default)+ 可覆盖。Markdown 不动、默认关、字节兼容。

阶段 2:任意节点类型(先做那五处泛化)+ 任意 loop 边。roadmap:node-inject · fork。

Non-goal(明确不做):可视化模板编辑器 · 让用户随便自定义模板 · 系统学历史自动调模板。

关联:FLY-1038 = 你要的管理 UI(有哪些 DAG / 注册到哪台 instance)—— 本 PRD 不含 · FLY-353 = 第二层编排引擎,是本层模板的消费方 · FLY-1022 = scale。
