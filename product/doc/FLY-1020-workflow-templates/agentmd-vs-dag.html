1 · 一句话

结论:agent.md 是「谁来干」,DAG 是「分几步、每步谁干、每步用哪个模型」。 简单活只用 agent.md;只有当你要「不同步骤不同模型」或「写的人和验的人必须隔离」时,才在上面加一层 DAG。而且 DAG 只在引擎里,Claude 每一步只收到一个 agent.md 的角色,从不知道有图。

agent.mdDAG(工作流模板)

4 · 你要 DAG 的两个理由 —— 都成立,而且 agent.md 物理上做不到

① 多 model

我们今天就在做:设计/实现用 Fable、QA 用 Opus。这句「哪一步用哪个模型」没地方放进 agent.md —— 就算你在里面写 model:,系统一个字都不读(§6 实据 1)。所以必须由 agent.md 之外的一层来说。

② 防 bias 隔离

你可以在 agent.md 里写「请客观地验一遍自己的代码」—— 那只是叮嘱。真正的独立验证需要 QA 是另一个 fresh session、另一个模型、看不到写代码时的思路。一个 agent.md = 一个 session,它无法把自己劈成两个互相看不见的 session。 只有编排层能做「切成两个节点」。

所以:你要的这两件事恰好在 agent.md 的能力边界之外。这不是偏好问题,是缺了这层就做不到。

6 · ⭐ 三条代码实据(不是我说说,配出处)

实据 1 —— agent.md 只能表达「我是谁」,表达不了模型/技能/权限

系统读 agent.md 时,当纯文本读、截断到 4 万字符、直接塞进提示词;全仓没有任何地方解析它的 frontmatter。所以你在里面写的 model: / skills: / permissionMode: 全是死字。

Blueprint.ts:1602(读)· Blueprint.ts:1967(readAgentFile,纯文本 + slice 40_000)· 全仓 grep 无 frontmatter 解析 · Blueprint.ts:1682(permissionMode 是硬编码的)

推论:「agent.md 管角色 / 另一层管模型和能力」不是一个提案 —— 代码今天就是这样。 DAG + 节点注册表只是把「另一层」这件事说清楚。

实据 2 —— 通用节点天然安全:用户写的 agent.md 无法给自己授权

正因为 frontmatter 是死字,非工程师写的 agent.md 物理上无法给自己授予「能 ship」「能合并」「能开 PR」,也无法自选模型。这些能力永远只在我们内置的注册表里。

意思是:扩展性给出去了,权限没给出去。 非工程师随便写 agent.md,最坏也只是「角色说得不好」,动不了流程和权限。

实据 3 —— 「为什么不开任意节点类型」的真答案:成本形状不同

做法成本
开放任意新节点类型每加一种就要动 5 处硬编码生产面 → per-type 付账
three-stage-phases.ts:35(角色联合类型)· StateStore.ts:258/2576(存的角色枚举 + 查询)· issue-display.ts:16/214(展示)· post-ship-finalization.ts:205(ship 收尾)· actions.ts:852(retry)
通用节点(跑某个 agent.md 角色)只加这一个类型、只付一次账;之后任何人写自己的 agent.md 就能用,零代码改动
复用现成的 readAgentFile 注入通路,不是新造机制
所以:不是「不能扩展」。通用节点是比「开放任意节点类型」更便宜、更安全的扩展。

7 · ⭐ homerail 怎么做的(我 clone 了它的码亲手读)

⚠️ 结论跟我们原本的猜测相反 —— 它处理了,而且就是分层。 我们本来猜「homerail 可能没处理 agent 定义 vs DAG」。我把 repo clone 下来读了真码:它处理得很明确。 如实报告。

它一个 DAG 模板文件 = 三块(下面是它仓库里 public-two-node.yaml.template 的真实内容):

# ① 绑模型:哪个 agent 用哪个模型 / 哪个 harness
runtime_profiles: { offline-deterministic: { agents: { "*": { agent_type: deterministic } } } }

# ② agent 定义:每个 agent 就是一段 system 角色提示词
agents:
  drafter:   { system: "You are the drafting node ..." }
  reviewer:  { system: "You are the review node ..." }

# ③ 图:每个节点【按名字引用】一个 agent
nodes:
  draft:   { agent: drafter,  after: [],      outputs: { drafted: {to: "review.in:draft"} } }
  review:  { agent: reviewer, after: [draft], outputs: { approved: {to: ""} } }

它独立的 profile 文件里,不同 agent 绑不同模型 + 不同 harness:

default: { model_alias: local-qwen,  agent_type: claude-sdk }
agents:
  reviewer: { model_alias: kimi-main, agent_type: kimi_code }   # 审稿的换个模型
三条硬证据(我读码得出): ① 节点 ≠ agent,节点引用 agent —— 跟分层框架一模一样。
② worker 只拿到「自己那个 agent 的 system」,拿不到整张 DAG(worker/src/index.ts:systemPrompt = agentConfig.system)→ 实锤「DAG 永不甩给模型」。
③ 一个节点一个容器(createWorkerContainer)→ 防 bias 是结构隔离。
另外它 profile 里 reviewer 用 kimi、其余用 qwen → 实锤你的「多 model」理由。
⚠️ 但有一处我们不该抄(正是 §5 🅑 的实证):它把 agent 定义内嵌进每个 DAG 文件。我数了它三个 shipped 模板:agents 数 == nodes 数(1/1、5/5、2/2) —— 每个 DAG 都要重写一遍自己的 agent,零复用;全 repo 没有任何独立可复用的 agent.md 等价物。
我们的做法更好:agent.md 独立、可复用,一个角色写一次,任何 DAG 都能引用。

8 · 什么时候该上 DAG(可直接用的判据)

这件活…用什么
一个角色 · 一个模型 · 不需要独立验证只用 agent.md(裸单 session)—— 不碰 DAG
不同步骤要不同模型(设计 Fable / QA Opus)上 DAG
写的人和验的人必须隔离上 DAG
「不过就回去重做直到过」/「同一段重复 N 次」上 DAG(loop)
某类任务要跳过某一步(纯 doc 不测)上 DAG(skip)
非工程师想加自己的角色(如「小红书选题官」)写一个 agent.md + 挂通用节点(零代码)
一句话:DAG 是「例外时才拿出来的工具」,不是默认。默认永远是一个 agent.md 跑一个 session。
