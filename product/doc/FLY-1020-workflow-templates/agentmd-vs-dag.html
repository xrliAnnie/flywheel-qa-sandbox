1 · 先给结论(一句话)

一句话:agent.md 是「谁来干」(角色/人格),DAG 是「分几步、每步谁干、每步用哪个模型」(工作流)。两者不是竞争关系,是上下层。 简单活只要 agent.md;只有当你需要「不同步骤用不同模型」或「写的人和验的人必须隔离」时,才在上面加一层 DAG。
而且:DAG 永远不交给 Claude —— 是我们的引擎读 DAG、按图调度,每个节点只把「一个 agent.md 的角色」交给 Claude。Claude 从头到尾不知道有张图。

2 · 本质区别:一个是「演员」,一个是「剧本 + 排班表」

agent.mdDAG(工作流模板)
回答什么谁来干(WHO):你是什么角色、什么风格、什么职责边界怎么跑(HOW):分几步、什么顺序、哪步可跳、哪步要重复
内容一段角色提示词节点 + 顺序 + loop + skip
谁读它Claude 读(塞进它的提示词)引擎读(Claude 永远看不到)
粒度一个角色 = 一个 session一条 issue = 多个 session,每个 session 一个角色
管模型吗不管(见 §7:它的 model 字段根本没人读)管:每个节点绑一个模型
类比:agent.md = 一个演员的人设;DAG = 剧本(几场戏、什么顺序)+ 排班表(哪场戏谁演、用哪台机器)。你不会因为有了人设就不需要剧本,也不会因为有了剧本就不需要人设。

3 · 为什么非要 DAG?——你给的两个理由,我逐个验证

你的两个理由:① 不同步骤要用不同模型 ② 写代码的和验代码的要隔离,防 bias(不能自己判自己)。

理由 ①:多 model —— 成立,而且 agent.md 物理上做不到

我们今天就在做:设计/实现用 Fable、QA 用 Opus。这个「哪一步用哪个模型」的信息,没地方放进 agent.md —— 我核过码:agent.md 里就算写了 model:,系统根本不读(§7)。它只被当成一段提示词文本塞给 Claude。所以「每步换模型」这件事,必须由 agent.md 之外的一层来说。那一层就是 DAG + 节点注册表。

理由 ②:防 bias 隔离 —— 成立,而且这是「结构」不是「叮嘱」

你可以在 agent.md 里写「请客观地验一遍自己的代码」—— 但那只是叮嘱。真正的独立验证需要:QA 是另一个 fresh session、另一个模型、看不到写代码时的思路。一个 agent.md = 一个 session,它无法把自己劈成两个互相隔离的 session。只有编排层能做「切成两个节点」这件事。

所以:你要的这两件事,恰恰是 agent.md 这一层的能力边界之外。这不是「要不要多一层」的偏好问题,是缺了这层就做不到。
反过来也成立:如果一件活只有一个角色、一个模型、不需要独立验证 —— 那 DAG 一点用没有,只用 agent.md 就够(= 我们 PRD 里的「裸单 session 默认」)。

4 · 三个选项:取代 / 共存 / 分层

选项是什么评价
🅐 取代
(DAG 取代 agent.md)		把角色人格也写进 DAG,不要 agent.md否 ① DAG 不含人格,写进去就是把 agent.md 塞进 YAML(更难读、不可复用)② 简单活被迫画图,违反你的红线
🅑 共存
(两套并行,各管各)		agent.md 一套、DAG 一套,谁都能定模型/技能危险 职责重叠 → 「模型到底听谁的」会打架;非工程师改 agent.md 可能悄悄改掉流程
🅒 分层
(HL 的框架)		agent.md = 通用原子/默认;DAG = 可选编排层,只在多 model / 防 bias 时上对 职责不重叠、简单活零负担、能力边界清楚 —— 而且 homerail 独立走到了同一个答案(§6)

5 · 分层框架长什么样(HL 抛的,我核过工程可行)

  1. agent.md = 通用原子 / 默认(Claude 原生的东西)。不挂 DAG 的活,就是「一个 agent.md 跑一个 session」—— 今天就这样。
  2. DAG = 我们引擎内的可选编排层。只在需要「多 model」或「防 bias 隔离」时才上。
  3. ⭐ DAG 永不甩给 Claude。 引擎读 DAG → 决定「现在跑哪个节点」→ 把那个节点对应的一个 agent.md 角色交给 Claude 跑。Claude 只看到自己的角色,不知道有图。
  4. 简单活不需要 DAG —— 永远留着「不套流程」的出口。
这层框架的好处:DAG 的复杂度被关在引擎里,不外溢给模型、也不外溢给你。你和非工程师面对的永远是「写一个 agent.md 角色」这件简单事。

6 · ⭐ homerail 怎么处理的(我 clone 了它的码,亲手读的)

⚠️ 结论跟我们原本的猜测相反 —— 它处理了,而且就是分层。 HL 原本猜「homerail 可能没处理这件事」。我把 repo clone 下来读了真码:它处理得很明确。 如实报告。

homerail 的一个 DAG 模板文件里,是三块:(下面是它仓库里 public-two-node.yaml.template 的真实内容,我删了注释)

# ① 绑模型:哪个 agent 用哪个模型 / 哪个 harness
runtime_profiles:
  offline-deterministic:
    agents: { "*": { agent_type: deterministic } }

# ② agent 定义:每个 agent 就是一段 system 角色提示词
agents:
  drafter:   { system: "You are the drafting node ..." }
  reviewer:  { system: "You are the review node ..." }

# ③ 图:每个节点【按名字引用】一个 agent
nodes:
  draft:   { name: Draft,  agent: drafter,  after: [],      outputs: { drafted: {to: "review.in:draft"} } }
  review:  { name: Review, agent: reviewer, after: [draft], outputs: { approved: {to: ""} } }

它独立的 profile 文件里(example-runtime.profile.yaml),不同 agent 绑不同模型 + 不同 harness:

default: { model_alias: local-qwen,  agent_type: claude-sdk }
agents:
  reviewer: { model_alias: kimi-main, agent_type: kimi_code }   # 审稿的用 kimi,其他用 qwen
三条硬证据(我读码得出,非二手): ① 节点 ≠ agent,节点引用 agent(agent: drafter)—— 跟分层框架一模一样。
② worker 只拿到「自己那个 agent 的 system 提示词」,拿不到整张 DAG(worker/src/index.ts:systemPrompt = agentConfig.system)—— 实锤了「DAG 永不甩给模型」。
③ 一个节点一个容器(createWorkerContainer)—— 节点之间物理隔离,这就是防 bias 的结构做法,不是靠叮嘱。
它也验证了你的「多 model」理由:它的 profile 里 reviewer 用 kimi、其余用 qwen,连 harness 都不同。「审稿的换个模型」是它明确支持的一等能力 —— 跟我们 QA 用 Opus 是同一个动机。
⚠️ 但它有一个我们不该抄的地方:它把 agent 定义内嵌进每个 DAG 文件,而且我数了它三个模板:agents 的数量 == nodes 的数量(1/1、5/5、2/2)—— 也就是每个 DAG 都要重写一遍自己的 agent,零复用。它没有任何独立可复用的「agent.md」。
我们的做法更好:agent.md 是独立、可复用的文件,一个角色写一次,任何 DAG 都能引用。

7 · 我们自己的代码事实:「分层」不是我们发明的,是现状

我核了我们自己的码,三条:

  1. 系统读 agent.md 时,是当纯文本读,截断到 4 万字符,直接塞进提示词(Blueprint.ts 的 readAgentFile)。
  2. 全仓没有任何地方解析 agent.md 的 frontmatter —— 你在里面写 model: / skills: / permissionMode:,系统一个都不读,它们只是提示词里的字。
  3. 所以今天:agent.md 只能表达「我是谁」;模型、技能、能力(能不能开 PR、能不能 ship)只能来自 agent.md 之外。
推论:「agent.md 管 WHO / 别的层管模型和能力」不是一个设计提案 —— 代码今天就是这样。 DAG + 节点注册表只是把「别的层」这件事说清楚、变成一等公民。

8 · 「通用节点」给非工程师 —— 顺便回答「为什么不开任意节点类型」

通用节点 = 一个节点,它跑「某个 agent.md 角色」。 非工程师写一个自己的 agent.md(比如「小红书选题官」),挂到通用节点上,就能进 DAG 跑。

为什么它比「开放任意节点类型」更好(这是你 §2 那个问题的真正答案): 不是「不能扩展」,是成本形状不同。
· 开放任意新节点类型:每加一种,就要动 5 处硬编码的生产面(存的角色枚举 / Discord 展示 / ship 收尾 / retry / 重启对账)= 每加一种付一次账。
· 通用节点:只加这一个类型、只付一次账;之后任何人写自己的 agent.md 就能用,零代码改动。
而且它天然安全(不是妥协):因为 agent.md 的 frontmatter 系统不读(§7),非工程师写的 agent.md 物理上无法给自己授予「能 ship」「能合并」「能开 PR」,也无法自选模型 —— 这些能力永远只在我们内置的注册表里。扩展性给出去了,权限没给出去。

9 · 那到底什么时候该上 DAG?(可直接用的判据)

这件活…用什么
一个角色 · 一个模型 · 不需要独立验证只用 agent.md(裸单 session)—— 不碰 DAG
不同步骤要不同模型(如设计 Fable / QA Opus)上 DAG
写的人和验的人必须隔离(防自己判自己)上 DAG
要「不过就回去重做,直到过」/「同一段重复 N 次」上 DAG(loop)
某类任务要跳过某一步(如纯 doc 不测)上 DAG(skip)
一句话:DAG 是「例外时才拿出来的工具」,不是默认。默认永远是一个 agent.md 跑一个 session。
