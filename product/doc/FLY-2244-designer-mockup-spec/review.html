为什么会有这张单

同一个纠正,你说了两遍

2026-08-27 一次,2026-09-01 一次,内容一样:mockup 交上来是脱离实际的假 HTML。

查下来原因不在那个 runner 身上 —— 规范本身就是这么教它的:

  • Step 0 把「一次性静态高保真 HTML」列成一个可以随便选的类型,一句"什么时候不该选"都没有
  • Step 4 对"要落到真产品上"的那一类,只要求交「mockup + 一张说明落在哪里的纸条」,从没说过要是真代码
  • 技能表把「发一张托管卡片给 founder 看」写成通用做法,没有任何限定

⇒ 每次纠正的是人,没纠正规范,所以下一个 runner 又会犯一遍。这次改的是规范。

改后的规范 · 核心四条

下面每一条都能指回你的原话

① 静态 HTML 没错 —— 它是【选方向】那一步的正确形态

「Step 0 做一个静态高保真 HTML 是可以的。比如你用 Codex 或者 Gemini 做了几个 mockup image,然后放在 HTML 里给我展示 Option 1、Option 2、Option 3,这完全没问题。最初的 mockup 阶段用 HTML 是 OK 的。」

所以规范没有把静态 HTML 一棍子打死。它被明确定位成:概念图拼成 Option 1/2/3,给你挑方向用。

② 高保真 = 真代码,挂在 localhost,你能直接打开

「到了要落实到真正产品改动、做高保真 mockup 的时候,我希望它能用代码(JavaScript / TypeScript 这些)写出来,方便我直接看。」

规范里写死:交付物是跑着的东西,不是它的照片。数据可以是假的、代码可以糙,长得像才是重点。服务挂了 runner 自己重启,不许让你去弄。

③ 界面已经存在时,从现有代码改起 —— 是【强默认】,不是铁律

「它不一定非要真的跑在产品自己的前端上。我之前提到跑在前端,主要是因为这个东西大概率不需要完全重写:我们是在现有的 dashboard 上做 polish,现有的 code 已经定义了它现在的样子,直接在现有代码的基础上去改会简单很多。这才是我的初衷。」

规范把这条的理由(省事)写在了规则旁边,并明说:确有理由要独立写,是允许的,但要说明理由。

⚠️ 这里我上一轮翻过车:你给的是理由,我把它硬化成了教条("必须跑在产品自己的前端上"),被你当场纠正。第二次提交改回来了。这一版我全程按"强默认 + 可给理由破例"写,请重点看这条有没有又写硬。

④ 顺序不许跳,两个方向都不许

概念图(便宜,给你挑方向) ↓ 你确认方向 真代码 + 假数据,挂 localhost

不许为了"省一轮"跳过概念图 —— 跳过你那一步只会多花轮次。也不许停在概念图就交差:方向定了,还欠你真代码那一版。

第二遍扫描查出来的 · 这条最重

同一个洞,从另一扇门原样走了回来

把假 HTML 从 Step 4 赶出去之后,我把全文的每一条禁令重新过了一遍,问同一个问题:这条禁令,是不是把规范自己要求的下一步唯一的路堵死了?查到这个:

那就是你退回两次的那个东西。我们把它从 Step 4 赶出去,它从 CRITICAL rules 那扇门原样走了回来。(文件里本来有一条豁免,但它只覆盖 implement / QA 阶段,够不到 design 阶段。)

今晚先把危险出口焊死(这条不需要你拍,已经加进去了)

⛔ 手搭一个跟产品源码毫无关系的独立仿制页,在这份文件的任何读法下,都不是合法的 Type (b) 交付物。如果你把 Step 4 和 CRITICAL rules 一起读完,结论是「我唯一能做的就是搭一个」——那你找到的是这份规范的一个矛盾,不是一个任务。停手,报给你的 Lead,不要搭。

✅ 这条不预设下面那道选择题谁赢 —— 无论你选甲还是乙,「手搭仿制页」都是错的。所以它今晚就能上,不用等你。

顺手修掉一个坏范例:规范里当范例引的那个 prototype/server.mjs,仓里根本没有,下一个体照着找会扑空。查了历史 —— 它提交过、后来被特意删掉,理由是它 import 了一个永远不会进 main 的文件,到了 main 上就指向一条不存在的路径:死的、不报错、只有下一个想跑它的人才会发现。规范里已标明它没了,并留下当年那条判据:「这东西到了 main 上还立得住吗?」

本来要问你一道选择题 · 推导下来它自己解开了

两条路,各有各的归宿 —— 不用你二选一

Type (b) 的真代码住哪儿、能不能进 main,本来是我准备让你二选一的题。后来发现它不是二选一 —— 是两条路,各走各的。

默认:从现有代码改起(= 改了产品的真源码) → 这一半碰了产品前端代码,【不进 main】 留在自己的 PR 里刻意不合,下一个人能读到 确切改了什么、能把分支 checkout 出来跑 → 粗代码 + 假数据在这条路上是【预期的】 ——正因如此,它更不能待在能合并的路上 → 这条 PR 合进 main = 违规,不是抄近道 例外:独立写(要说明理由) → 它【没碰】产品前端代码,所以不受上面那条约束 → 它要过另一条测试:【这东西到了 main 上还立得住吗?】 立得住就能合 —— 所以能拷就拷,别 import 一个 永远不进 main 的路径(FLY-2071 就是这么烂掉的)

⇒ 两条路的归宿都明确了:能进 main、能活得久的是例外那条;默认那条用「贴着真源码、最省事」换来的代价,就是它的产物活在一个永远不会合的分支上。

顺带交代一个我自己犯的错,免得你以为这段一直是对的

我第一次写这条约束时,把它挂错了地方 —— 挂在了「例外(独立写)」那条路上。可那条路根本不碰产品前端代码,约束挂在那儿等于没挂;而真正会去改产品源码的默认那条,反而一条合并限制都没有。

⚠️ 照那一版执行,一个体会:默认去改产品源码 → 然后把它合进 main。正是你 FLY-2071 里明确否掉的事。我们花一晚上堵洞,那一版会亲手开一个。已经改到正确的那条路上了。

⚠️ 归属说清楚,免得我们替你说话 —— 你实际定过的只有一句(记在 commit fb3ca7b):文档和 mockup 材料可以进 main,碰了产品前端代码的那一半不许进。

而且那一句也不是你当面对我说的原话,是我们从那条 commit message 里读来的转述。
至于「两条路各自的归宿」这个结论,是我们从那一句推导出来的,不是你定的。我们按推导结果写进规范了,没有再问你一遍。
如果哪一步读错或推错了 —— 你一句话就能推翻。

顺手改的一处小措辞

Step 0 现在读起来像"二选一的菜单"

原文把两种 mockup 并排列出来,像点菜:选 (a) 静态,或者选 (b) 落到真产品。

但按上面第 ① 条,对一张"要落到真产品"的单子来说,静态那一版不是另一个选项,是它必经的第一步。照旧措辞,runner 很容易理解成"我选了 (a),就不用做 (b) 了"。

所以 Step 0 真正在问的只有一句:这次改动落不落到真产品上?规范里补了一句明说:这两个不是"挑一个然后就完事"的菜单。

并且补了一句硬话 —— 原来最缺的就是它:

如果答案是 (b),那么独立的托管静态页在这张单的任何阶段都不构成合法的终态交付。它只在 Step 2 当选项卡、只用来挑方向;方向一旦定了,它就再也交不了差。拿它当 (b) 类单子的答复,是交付失败,不是"部分完成" —— 那张页正是你 2026-08-27 和 2026-09-01 两次退回的东西。

只有在你确认「这是纯探索、不会落到产品上」时,静态页才是合法的终态形式。没拿到这个确认,就默认走 (b) 这条路。

✅ 「交付失败,不是部分完成」这个区分是 Lead 特意要留的 —— 「部分完成」是这类活最常见的自我安慰。
