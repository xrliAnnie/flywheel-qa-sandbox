先把分层说清楚

一套 flow，两件不同的事

你在跟我收敛「整套 CI/CD」，其实是两件独立的事：

  • 上线（ship）= 每个 commit 怎么合并、内部部署。已经拍完了（FLY-1063，你选了「Discord 授权、GitHub 执行」）。这页不动它，只画进来当左边一条道。
  • 发布（release）= 把一个版本打包好、发给别的项目/客户。你说得对：它自己还分两层 —— beta（我们 Flywheel 自己一直用、先在自己身上跑）和 正式版（beta 跑稳了才提升、才给别人）。这是这页的重点。
一条硬规矩（Tadashi 的 REQ-0，不能违反）： 上线和发布是两扇独立的门。不是每次上线（每个 commit）都要发布 —— 上线是每个 commit，发布是每 ~6h 打一个新版本。也能从已经上线的代码单独打个版本发出去。两件事绝不焊在一起。

决策块 ①

渠道 + 你说的「免费版 / 付费高级版」怎么顺过去

你在 FLY-1062 里已经拍了渠道 B（来源：FLY-1062 §5 决策记录，2026-07-09，经 Tadashi 转达；当时设计其实推荐 A 全公开，你选了 B 要护话术/IP）。这一版不重开这个，重点回答你新提的：以后要免费版 + 付费高级版，现在该做什么形态才顺得过去？

好消息：你选的 B 天生就是「免费 / 付费」的分界机制。 B = 公开发一个薄壳（安装器，没 IP）+ 客户输 license key 才换到真正的 payload（话术/构建产物）。这个「有没有 key、key 是什么等级」本身就是免费 vs 付费的开关 —— 不用以后重构。

顺到「免费 + 付费高级版」的路径

  • 免费版 = 装了就能用的基础档（薄壳 + 一个基础 payload，或一个免费档 key）。
  • 付费高级版 = 用付费 license key 换高级 payload（更强的能力 / 更多话术）。
  • 现在做什么 = 就把 B 建起来（薄壳 + key + gated payload）。现在不用做计费、账号、席位那套 —— 那是以后。现在选 B，等于把「免费/付费」这道门提前留好了，以后加档只是「多一个 key 等级 + 多一个 payload 档」。

诚实提醒：今天 FLY-1062 的 B 是「没 key 就啥也没有」（全靠 key）。要做「免费也能用一点」，就是在 B 上加一个免费 payload 档 —— 是自然延伸，不是推翻重来。

还没定的：付费 payload 放哪、key 谁来管

薄壳去公开 npm 没争议。凭 key 才能下载的 payload 要挂哪、key 怎么发/吊销 —— 两条路（你往「免费+付费」走，这个选择更关键了）：

  • 自己搭一个薄端点：复用我们验证过的托管（FLY-203 那套私有存储 + 薄函数）。验 key → 给包。全在自己手里、便宜；但免费/付费分档、key 等级要我们自己写一点。
  • 用现成的商用「license + 分发」平台（如 Keygen 这类）：免费/付费分档、key 等级、按客户吊销都是现成的 —— 正好贴你要的产品形态；代价 = 一个外部依赖 + 订阅费。UNKNOWN：定价/数据放哪我还没细查，你要倾向这条我再深挖。

决策块 ②（你上轮留空，我摆个方案）

版本号 + 谁装哪个、怎么升级

按你说的 beta / 正式版两层，落成这样（版本怎么命名见 ③）：

  • 我们 Flywheel 自己：一直跟 beta 通道，自动更新到最新 beta（先在自己身上跑、先撞问题）。
  • 别的项目 / 客户：跟 正式版通道，装的永远是提升过、跑稳的正式版，不会碰到半生不熟的 beta。
  • 升级怎么做：重跑安装命令（或包内一条 flywheel update）→ 装进新版本目录 → 原子切换指针 → 重启服务。旧版本留一个当回滚位，切换失败自动翻回去。
  • 坏版本怎么撤：npm 规则是「发出去 72 小时后不能彻底撤」，所以坏版本用标记「弃用」+ 从下载清单摘掉 + 发个修复版，不硬撤。

决策块 ③

上线↔发布的节奏 + 不同版本怎么命名

节奏（三个不同频率，别混）

  • 上线（ship）= 每个 commit。内部的事。
  • beta 发布= 每 ~6h 一个。自动。我们自己跟。
  • 正式版发布= 某个 beta 跑稳、你点头才提升（比 6h 少得多）。给别人。

关键：不是每个 commit 都发版，也不是每个 beta 都变正式版 —— 三个频率各自独立（这正是 REQ-0「两扇独立门」的意思）。

你问的：不同版本怎么命名（我的建议）

是什么版本号长啥样发到哪个通道谁装
beta 版（每 ~6h） v1.56.0-beta.3 ← 带 -beta.N，一眼知道是 beta，N 往上加 beta 通道（next） 我们自己
对外正式版（提升后） v1.56.0 ← 干净、没后缀 = 正式版 正式版通道（latest） 别的项目 / 客户
  • 一眼区分：版本号带 -beta.N = 还在 beta；干净的 v1.56.0 = 对外正式版。
  • 提升 = 把某个 beta 的代码，出成对应的干净正式版号发到正式版通道。
  • 机器断言（Tadashi 硬 REQ）：版本号必须和仓库里记的一致，CI 每次核对，对不上 = 构建失败、绝不发错版本。
  • 可重现打包 + 打包接 CI 每次验（另两条 Tadashi REQ）：已经落地（FLY-1062 PR1 已把「打包 + 真装一遍 + 起得来」接进 CI 每次跑）。
