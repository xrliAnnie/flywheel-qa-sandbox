新开放点 ① · 怎么算 beta「跑稳了」判据产品定 · 信号工程定

你每天点「发」之前，凭啥判断这个 beta 稳？

你选了 Option 3（每天日报一键）。那日报得给你看几个信号，你才好判断「今天这个 beta 能不能发」。日报大概长这样：

📮 今日发布候选 · beta v1.56.0-beta.7

跑了多久在我们机器上跑了 2 天，没被回滚、没崩
测试✓ 全绿
错误告警无（这 2 天没触发报警）
改了啥距上个正式版：3 个改动（…摘要…）
发正式版
今天先不发

「跑稳了」= 这几个信号。要多严由你定，给 3 档：

A · 纯给你信息，你凭感觉点

日报只摆信号，发不发完全你判断，系统不拦。

B · 系统给个「建议」，你可以覆盖推荐

系统按「跑够 N 天 + 测试绿 + 没报警」标「建议发 / 建议再等」，但最终你说了算，你想发照样能发。

C · 硬门槛，不满足不让发

必须满足条件（比如跑满 1 天 + 测试绿）「发」按钮才亮，否则灰掉。最安全但最死板。

新开放点 ② · 「自动推给客户装」长啥样 给不给自动产品定 · 机制工程定

客户升级：手动跑命令 vs 自动装

你懂「客户自己跑 flywheel update」那种。你要我讲清「我们推、客户自动装」到底咋做 —— 就是给客户机器装一个小的自动更新器，像 Chrome / VS Code 那样自己更新：

客户机器上的
自动更新器
定时任务，每天醒一次
──每天查──▶
对外正式版通道
(npm)
▼ 有新正式版
自动下载 → 装进新目录 → 切过去 → 重启
（装失败自动翻回旧版）

给你 3 个 option：

A · 手动 CLI（默认，推荐起步）推荐

客户想升级就自己跑 flywheel update。客户完全控制时机，最安全，我们也不用管他们机器。

B · 自动更新器（上面那张图）

客户机器装个定时任务，每天自动查、有新正式版就自动装、失败自动回滚。客户不用管，但等于我们能动他们机器（要他们信任）。

C · 混合：自动查 + 问一声

自动发现有新版 → 通知客户「有新版，要装吗」→ 客户点一下才装。又省心又不擅自动手。

我的建议：起步用 A（手动，安全、简单），把 B 的自动更新器留作「想省心的客户可选」（FLY-1062 里已经把它列为后续件了）。给不给自动 = 你定；具体怎么做 = Tadashi。

②
客户升级给哪种？ A 手动 CLI（起步推荐）/ B 自动更新器 / C 混合（自动查+问一声）？可以「起步 A、以后加 B/C」。
① payload 托管 · 收你的保留期

R2 + 自动删（beta 2 周 / 正式版 4 周）实现工程定

你定的保留期已写进设计：payload 存 Cloudflare R2（10GB 永久免费 + 客户下载零流量费），在 R2 后台建两条自动删规则 ——
  • beta 的包：14 天后自动删（你定的 2 周）；
  • 正式版的包：28 天后自动删（你定的 4 周）。
到期 R2 自己删、不用人管。我们 payload 一个几十 MB，这点量 10GB 免费额度远用不完。

为什么 R2 不是 S3（上轮查的，复习）：R2 客户下载零流量费、10GB 永久免费；S3 旧的永久免费档已取消、下载还按 GB 收（0.09 美元/GB）。同样能自动删，R2 更省。
