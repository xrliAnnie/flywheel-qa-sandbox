答你「release 到哪」：分两处 —— 薄壳发到 npm（公开包，客户 npm install 就这个）；真 payload 传到 R2（私有，凭 license key 才能下）。不用 GitHub release（那个绑仓库访问，跟我们「零仓库访问」相反）。每 6h/定时的 beta 就在 GitHub 的定时 CI 里跑。

要不要「每个 commit 都打 beta」？频率产品定 · 技术工程定

你的质疑对 —— 不用每个 commit。 查了别人：几乎没人真的「每 commit 发版」，都是定时发一班（Next.js 每次合并、Expo 每晚、Docusaurus 每提交但那是极小项目）。每 commit 会堆一大堆几乎一样的版本、很吵。建议：定时（比如每 6h 或每晚）醒一次，有新代码就打一个 beta，取当时最新那条 commit；没新代码就跳过。

release 频率 + 挑哪个 commit（「release train / 发车」模型）节奏产品定

别人的通行做法叫「release train（班车）」：不是每个改动都单独发，而是定点发车，那一刻准备好的改动一起上车，没赶上的等下一班。

  • beta 班车（给我们自己）：定时（如每 6h/每晚）发一班，取当时的 main 最新 commit（= 你说的「golden commit」，就是发车那一刻的代码）。
  • 正式版班车（给客户）：每 ~1-2 周发一班，从近期一个跑稳的 beta 提升。频率可配置（你要的）—— 想快想慢改个数字就行。

别人怎么做：release train 是 iOS/安卓/大项目的标准做法（每周/双周定点发，ready 的上车）；StackStorm 把「过了 e2e 的 master」定时提升成候选版再发布。

promote 审批流程 —— 不天天烦你，给你 3 个 option

你原话：「你只说需要我点头，但流程到底咋样？每天来找我点？」—— 不会天天来。设计成低打扰，给你 3 个 option：

Option 1 · 每周「发车日」一键 promote推荐

每周固定一天（比如周一），系统在一条消息/日报里列出「本周的 beta 候选 + 有啥变化」，你看一眼、点一下「发车」→ 提升成对外正式版。一周一次，不烦，正好贴你说的「对外 ~1-2 周」。

Option 2 · 你随时手动发

没有固定节奏。你什么时候觉得某个 beta 稳了，在 Discord 说一句「把这个提成正式版」→ 就发。你完全主导，但要你自己记着什么时候发。

Option 3 · 每天日报带一个「今天发不发」

每天的日报里带一个一键按钮。更勤，但可能太频繁（你说过不想天天点）。

为什么推荐 Option 1：既是「你点头」（founder 授权，符合 REQ-0），又不天天打扰；跟「对外 ~1-2 周」的节奏天然对齐。发车那条消息可以顺带告诉你这周改了啥，你有依据地点。

Cloudflare R2 vs S3 —— 查清了 选型工程定 · 存多久产品定

你点名 R2、问「是不是最简单 + 免费额度最大」。查了真数字：

Cloudflare R2AWS S3
免费存储10 GB 永久免费旧的「5GB 永久」已取消；新账号只有 $200 额度用 6 个月
客户下载流量（egress）全免费（零 egress 费）前 100GB/月免费，超了 $0.09/GB
自动过期删除✓ lifecycle 规则✓ lifecycle 规则
复杂度单一存储档，最简单多档/多概念，更复杂
结论：R2 更适合我们。 关键是零 egress —— 客户下载 payload 不管多少次都不额外花钱（S3 下载要按 GB 收）；加上 10GB 永久免费（我们 payload 一个几十 MB、只留 2 周，远用不到 10GB），R2 基本白嫖。

自动过期（beta 留 ~2 周、超期自动删）实现工程定 · 留多久产品定

明确答你：能自动做到。 R2 有「object lifecycle 规则」：在 R2 后台给存 beta 的 bucket 建一条规则「N 天后自动删」（比如 14 天），到期它自己删、24 小时内执行，不用人管。所以「每次传新 beta、只留近 2 周、旧的自动清掉」= 一条规则搞定。留几天由你定（2 周？1 周？），怎么配是 Tadashi 的事。
