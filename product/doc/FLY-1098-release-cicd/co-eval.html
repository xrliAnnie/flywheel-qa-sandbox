⭐ 你的真痛点 · 怎么判断「今天这版稳不稳」

把散落的报错，汇总成一个发布参考信号

你说的问题我听到了：新版本老把系统搞崩，你每天『有感觉』哪版好坏，但 bug 反馈散在各 thread、口头告诉 Tadashi、他开 issue —— 没有一个地方告诉你「今天这版收到几个问题、崩没崩」。 解法 = 每天那份日报里，自动把散落信号聚到一起：

📮 今日发布候选 · beta v1.56.0-beta.7

崩溃/卡死这版 0 次← 看门狗自动测
报警数2 天内 1 个← 看门狗
bug 报告这版收到 2 个← 报 bug 时自动按当前版本归类
你的手感👍 今天顺👎 不顺
建议🟡 再观察（收到 2 个 bug、你还没标顺）
发对外正式版
今天先不发
关键：不另造评分系统，复用现成的。
  • 崩溃/卡死/报警 = 直接接 FLY-942 看门狗（已上线，本来就在测崩溃/卡死/rate-limit/报警）—— 它的信号喂进这份日报就行。
  • bug 报告归类 = 跟 FLY-1045（反馈机制那条线）一路 —— 报 bug 时打上「当前运行的是哪版」，散落报错就自动汇成「这版 N 个」。

三个信号源，给你 3 种组合 用哪些+多严=产品定 · 接线=工程定

(a) 只看 bug 数

报 bug 自动打当前版本 tag → 日报显示「这版收到 N 个 bug」。抓到散落报错，但只有报了的才算。

(b) 只看系统健康（看门狗）

复用 FLY-942：这版崩没崩、几个报警。客观、已现成，但只反映「崩没崩」，不反映「难用/别扭」。

(c) 三个都要，凑成一个参考推荐

看门狗健康(b) + 版本化 bug 数(a) + 你每天一个 👍/👎(c) 一起摆在日报，系统给个「🟢发/🟡等」建议，你最终拍。兼顾客观 + 你的手感。

诚实说：v1 会有 bias。 你的 👍/👎 是主观的、bug 数只算报上来的 —— 不是完美的「稳定度」。但比现在「散在各 thread、全靠你脑子记」强太多：至少一个地方、一眼看到「这版几个问题、崩没崩、我什么感觉」。你也认「先傻着来、以后再精」。

容易，而且你定的保留期正好支持。 因为老版本在 R2 留着（正式版留 28 天），客户降级 = 拉回一个旧版本装上、切过去。给客户一条命令：
flywheel rollback

▼
切回上一个版本目录（本地还留着）→ 重启

或指定装某个旧版本
──▶
从 R2 拉那个旧版
(28 天内都在)

两种降级：① flywheel rollback = 秒回上一个版本（本地目录还留着，翻个指针就行）；② flywheel install <旧版本号> = 想回更早的某版，从 R2 拉下来装（28 天保留期内都拿得到）。这套复用我们已经设计的「版本目录 + 切指针 + 留回滚位」机制，不新造。
