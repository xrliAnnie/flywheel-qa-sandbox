先把分层说清楚

一套 flow，两件不同的事

「整套 CI/CD」其实是两件独立的事，共用你在 GitHub 上发的那个 🆒 当入口：

  • 上线（ship）= 一次改动怎么合并、内部部署上线。这层已经拍完了（FLY-1063，你选了「Discord 授权、GitHub 执行」）。这页不动它，只把它画进来当左边一条道。
  • 发布（release）= 把一个版本切成带版本号、可重现、打包好、零源码暴露的安装包，发布给客户。这层是这页要你拍的重点。
一条硬规矩（Tadashi 定的 REQ-0，任何设计都不能违反）： 上线和发布是两扇独立的门。不是每次上线都要发布（大量内部改动上线了，客户不该收到新包）；也不是每次发布都要重新上线（可以从已经上线的代码打个版本发出去）。你的 🆒 可以只开上线、只开发布、或两个都开——但它俩绝不焊在一起。

决策块 ①

发布渠道：客户怎么拿到包，源码露多少

你在 FLY-1062 里已经拍过一次渠道（选了 B）。这里把当时那张对比表原样摆出来当背景，你确认发布这层沿用它就行——真正还没定的是下面那个「payload 放哪」。

渠道客户装包体验源码暴露面我们的成本
A · npm 公开 scoped 包 npx @flywheel/onboard，零账号零 token 最大：任何人可下载（安装器 + 编译后 JS + 话术/prompts 可读） 最低（npm org + CI publish）
B · 公开薄壳 + license key 换 gated payload ✓ 你已拍 npx 同上，但要输入我们发的 license key 最小：薄壳零 IP；真 payload（话术/prompts/构建产物）只有持 key 客户拿得到 中（payload 托管 + key 签发/吊销）
C · 私有 registry（npm private / GitHub Packages） 客户要先配 registry token 才能装 最小 低托管 + 高（每客户 token 分发/轮换）
D · 自托管 tarball + curl curl <带 token URL> | sh，零 Node 前置 同 B 可控 中（托管 + URL 管理）
你已拍 B（2026-07-09）：公开 npm 只发薄壳（安装器，零话术零产物）；客户输 license key 才换到真 payload。你的红线「客户绝不接触源码」由此守住——薄壳没 IP，payload 只给持 key 客户。诚实边界：Node/bash 产品没有真·源码保护（bash 与编译后 JS 天然可读），B 真正保证的是——客户拿不到 TS 源码、git 历史、内部文档，且话术/prompts 只有持 key 客户可得。

还没定的：payload（真正的包）放哪儿？

薄壳去 npm 公开，这没争议。但那个「凭 key 才能下载的真 payload」要挂在哪个托管上——FLY-1062 把这块明确留到了发布这层来定。两条路：

  • 自己搭一个薄的 gated 端点：复用我们已经验证过的托管模式（FLY-203 那套私有存储 + 薄函数层）。验 key → 返回包。成本可控、全在自己手里。
  • 用现成的商用分发平台（如 Keygen 这类「license + 分发」服务）：per-customer 授权 token、即时吊销都是现成的，少写基建，但引入一个外部依赖 + 订阅成本。UNKNOWN：具体定价/数据驻留我还没细查，你要是倾向这条我再深挖。

决策块 ②

版本号 + 客户怎么升级

发布这层要能机器断言版本（Tadashi 的硬 REQ：版本号对不上就停，绝不发错版本），客户还要有条清楚的升级路。现在的设计是这样——

版本号（单一真相）

  • 版本号只有一个来源 = 包里的 version，和仓库里的 doc/VERSION 保持一致；CI 每次断言它俩相等，对不上 = 构建失败。
  • 发布通道 latest（客户默认）/ next（内测）。客户永远 npx …@latest 拿最新稳定版。

客户怎么升级

  • MVP 升级路：客户重跑安装命令（或包内 flywheel update 子命令，同一套代码）→ 用已存的 key 拉新版本清单 + 新包 → 装进新版本目录 → 原子切换指针 → 重启已装的服务。旧版本保留一个当回滚位，切换失败自动翻回去。
  • 坏版本怎么撤：npm 有「发出去 72 小时后不能彻底撤回」的规则，所以坏版本用 npm deprecate 标记 + 从下载清单里摘掉 + 发个修复版，不硬撤。
  • 全自动后台更新（客户机自己静默升级）= 留作后续，MVP 先手动 / 半手动。
2
版本 + 升级这套，够吗？ 尤其：客户升级你希望是「客户自己点一下命令」，还是「我们推、客户机自动装」？MVP 我倾向前者。
决策块 ③

🆒 → 打包发布，这条链怎么串

你在某个 PR 上发 🆒（想发布这个版本时）→ 开的是发布门（独立于上线门）→ 打包 → 版本断言 → 发布。三条 Tadashi 的工程硬 REQ 已经在链里：

  • 打包命令接进 CI、每次都验 —— 这条已经落地了（FLY-1062 PR1 已把「打包 + 真 npm 装一遍 + 起得来」接进 CI 每次跑，验收线是「装得上≠起得来」）。发布门复用同一条打包链，不另造。
  • 可重现打包 —— 同一次改动重跑打包，产出的树逐字一致（幂等，diff 为空）。
  • 版本机器断言 —— 见 ②，包版本 == doc/VERSION，CI 断言。
和上线门的关系（REQ-0 再强调）：发布门自己有一次 founder 授权，不蹭上线门的授权。就算这段代码早就上线了，要发布给客户仍然要你在发布门这里点一次头。这样才做到「已上线的代码，能单独打个版本发出去」。

触发链 + 授权，这样串对吗？ 关键：发布要不要你单独点一次头（哪怕代码已经上线过）？我按「要」设计的——这正是「两扇独立门」的意义。
决策块 ④

先做首片，还是一上来就 fleet 级？

你说想要「fleet 级的发布 CI/CD」——目标形态确实是它（每个要发布给客户的 repo 都能走这套发布门）。但落地我建议先做首片、设计上留好推广口子：

  • 首片（第一个落地实例）= FLY-1062 的 PR4：客户 npm install 拿到打包产物、零仓库访问、零源码暴露。就是上面 ①②③ 那套，先在 flywheel 自己身上跑通。
  • 目标形态 = fleet 级：把「发布门」做成可复用的一块，将来别的 release-bearing repo 接同一套（同一个 🆒 → 发布门 → 打包 → 版本断言 → 发布）。
  • 我的建议：PRD 写成「首片先落，但每块设计都能推广到 fleet」——不是一上来铺满，也不是只做一次性的。
