## 1. 先把问题问准

旧 E1 有**两件**安全装置,不是一件:

| 装置 | 它回答的问题 |
| --- | --- |
| 「Lead 点头才派」(逐条闸) | **这一条派发决定对不对?** |
| 「空跑 / 只报不派」(首批) | **这个决策者本身够不够好?** |

我原来把它们当成了同一件事的强弱两档 —— **不是**。它们回答的是不同问题,所以「有了逐条闸就不需要空跑」这个推论**不能直接成立**,得看第二个问题有没有别的答法。

## 2. 空跑真正独有的价值(先诚实地说它好在哪)

一旦有人在回路里点头,你就**测不到机器提案的原始质量**了,因为人污染了样本:

- **点头偏置**:人对着一列建议点批准,大概率大部分都批。批准率因此不含信息量。
- **选择效应**:只有被批准的决定才会产生结果。被拒的那些永远没有结果,你无法知道拒得对不对(经典的「被拒贷款人」问题)。
- **吞吐上限**:人闸把量压到人能处理的程度;空跑可以按全频率跑完整个 backlog,每天多出一个数量级的样本。

⇒ 所以空跑不是「弱版的人闸」,它是**唯一能无偏地读出「这个派发器好不好、能不能放松闸门」的东西**。

## 3. 但这里有一条决定性的反证 —— 而且是**实测**出来的,不是推理

这个组织**已经把「加一张审计表当校准语料」这个模式原样建过一次了**:FLY-175 Track 2 的 `founder_consent_audit`(`~/.flywheel/audit.db`),CLAUDE.md 里逐字写着它是「**the calibration corpus for Track 3, not a debug log**」。

它的 schema **设计得非常好**,该有的字段一个不少:

```
llm_reason / llm_raw_response / confidence / threshold_applied
founder_subsequent_ack / _ts / _message_id      ← founder 后来确认了吗
human_review_label / _source / _ts              ← 人工打分标签
```

**六周后它的实际状态(2026-08-21 只读实测):**

| 观测 | 值 |
| --- | --- |
| `human_review_label` | **我能读到的每一行都是 null** |
| `founder_subsequent_ack` | **我能读到的每一行都是 null** |
| `PRAGMA integrity_check` | ❌ `database disk image is malformed` |
| 同一张表三次扫描的行数 | `SELECT id` → 215 · `SELECT ts` → 215 · `SELECT action` → **252** · 打分列 → **110** |
| `MAX(id)` vs `COUNT(*)` | 514 vs 215 |
| 磁盘上的历史残骸 | `audit.db.corrupt-20260714-2213.bak`、`audit.db.malformed`(均 2026-07-14) |

⚠️ **成色**:因为库是坏的,**上面每一个数字我都不敢当事实用** —— 真正的发现不是任何单个数字,而是**三次扫同一张表得出互相矛盾的行数**。「打分列全 null」这条也要限定:是在我能读到的 110 行里全 null,不是在全部 ≥215 行里。
⚠️ 我**不知道**损坏是什么时候开始的、也**不知道**成因。可读行显示 `decision_mode = audit_only`(这个闸没在强制执行),所以我**没有**证据说它造成了运行影响。
⚠️ 我只读,没写,也**没有**尝试修复。

**这个模式失败的地方不是设计 —— 设计是好的。它失败在:没有任何东西强迫有人去读它。** 于是它安静地攒了六周、攒进一个坏掉的文件里,而且这是**第二次**坏(七月中旬已经坏过一次并被轮转过),没人发现。

## 4. 结论

**空跑是多余的 —— 但不是因为人闸替代了它,而是因为空跑和那张审计表犯的是同一个病:**

> **它产出的语料,需要「另外有人专门去读」这个动作才能变成价值。而这个动作在这里已经被实证会消失。**

正确的替代不是「保留空跑」也不是「什么都不留」,而是:

> ### 记录点头时的 **diff**(提案 vs 实际派出去的),而不是记录一个 yes/no。
>
> Lead 的**改动本身就是打分**。不需要任何人事后回来评。它是一个**别人本来就要做的动作的副产品**。

这一条比空跑和审计表都便宜:一次派发多存一份提案原文,对比现有的 workflow 台账是加法,不是新机制。

**为什么 diff 是必须的、yes/no 不够:**
如果只记「批准了吗」,你分不清「机器判对了」和「机器差一点、Lead 顺手改对了」。而**恰恰是后者的分布**告诉你哪些决定以后可以不用再问 —— 那就是毕业曲线,免费拿到。

**代价(我不藏):**
- 被拒的提案仍然没有结果,反事实问题**依然存在**。diff 解决不了它。空跑也解决不了。谁都解决不了,除非有人手工补「这条其实该派」—— 而那正是已经被实证会消失的那个动作。
- 样本量仍受 Lead 吞吐限制。

⇒ 所以我的建议是**接受**这个局限,而不是为了消除它去建一个没人读的空跑通道。

## 5. 落成一条不变量

> **每一条派发路径,要么有人点头(留 diff),要么有空跑(留提案)。
> 不许有第三种:既没人点头、也没留提案。**

这条现在写下来很便宜,以后补很贵。它也自动覆盖了「以后开出一条自动直派的快车道」那个情况 —— 那条路径没有人点头,所以它**必须**留提案。

## 6. 这对 B 块(改动两类分法)的影响 —— HL 问的就是这个

**一条派发决定本身就是一个「改动」**,所以它落进她的两类里:

| 类 | 例子 | 怎么处理 |
| --- | --- | --- |
| ②「具体怎么做」 | 这个 issue 派给谁、用哪套流程、现在派还是等会儿派 | Lead 点头(留 diff),进**汇总**,不打断她 |
| ①「最终做完是什么样」 | **批次怎么切** —— 她自己举的例子就是「把这个 batch 再拆一下」 | 必须到她那儿,**阻塞** |

⇒ 两类分法**正好就是**「Lead 能自己拍板 vs 必须给她」的那条线。这不是巧合 —— 她给的分类本来就是按「谁有权决定」切的。

**而 diff 记录是这条线唯一可审计的证据。** 没有 diff,你说「这些都是第二类」时拿不出依据。

**还有一个白拿的好处:**累积的 diff 会告诉你**哪些决定 Lead 从来没改过** —— 那些正是以后可以停止询问的。B 块的「汇总」于是不只是一份通知,它是**放松闸门的依据来源**。

**我不确定的(留给下一轮问她):**
「批次怎么切」到底算①还是②。她 8/21 的原话是「我只是告诉你们把这个 batch 再拆分一下而已」,语气像是②(她认为我们能判);但按内容它离「最终做完是什么样」很近。**这一条我不自己定** —— 它正好是分类边界上最有信息量的一个例子,值得单独问她。
