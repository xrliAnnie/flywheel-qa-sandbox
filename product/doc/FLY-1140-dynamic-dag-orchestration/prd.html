1背景与问题

现状(准确基线):Flywheel 现在对符合条件的 engineering main 任务启用一条硬编码的 Design → Implement → QA 链(three-stage,项目 opt-in、默认关,仅 fresh main 进入);其他任务走单 session。现状已经有一条固定回退(QA 失败 → Implement → 再 QA)。

真正缺的:没有一个通用机制,能按任务选任意角色、长度、顺序、回退,并把「怎么配合」物化成一次可执行、可恢复、可审计的 workflow。固定三段链 ≠「按任务现画一张图」。

目标:从「几条写死的链」→「一堆职能积木(角色 markdown = IC 职能)+ 一张按任务现组的可执行图」。

2目标 / 非目标

目标:① 核心编排机制 + 最小执行契约;② 决策权按任务/scope 定 + 编排唯一 owner;③ 记录+复盘+call-eval 的权威与本轮边界;④ 进化阶梯 + 每级毕业条件。

押后 / 下一轮:C(swarm)/D(成本感知派活)押后;E(好组合固化成模板)+ 两维评估打分规则 → 下一轮(本轮 call-eval 只记 outcome、不打分);Annie 另欠一个宏观综合 round;拓扑上 parallel / 跑中插节点 / 任意 loop → v1 deferred。

只有一个核心机制:「Lead 讨论一个任务、当场组一张 DAG」。一次讨论顺手定完这 4 样 —— 不是 4 个独立仪式:

关键澄清(消除 r2 重叠错觉):③ 决策权 和 ④ 记录,是 ① 那次讨论的两个产出面,不是另外要做的两件事。

3.1 最小执行契约(vision 层,不写低层 schema)

  • 拓扑边界(v1):只支持可变长度顺序 workflow + allowlisted/预声明/带 max_iterations 的有界回退边(至少保留现有 qa_fail / founder_feedback_kickback,维持与现有 QA fix loop 的兼容)。任意新 loop / 自由条件 / parallel / 跑中插节点 —— deferred。
  • 产出 snapshot:讨论结束产出一个 per-run workflow snapshot,复用 FLY-1020 的 node/edge/role-version/output 语义;可从静态模板起步再覆盖,但绝不改 canonical 模板。
  • node 完整性:每个 node 至少有 role+version、依赖、预期产出/验收、handoff、D 与 A;缺一项不 dispatch。
  • 跑中改图:由同一个 orchestrating Lead 发起,形成新 revision;明确保留/失效/runner 去留;旧事件不得推进新 revision。
  • fail closed:无法形成有效 snapshot / 修订失败 → 回退静态模板或人工接管,不「猜着跑」(启动条件严格遵守 §5.2)。
