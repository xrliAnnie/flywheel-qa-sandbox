## 1. 现在是什么样（实读，2026-09-22）

机器里有**两个**判断，各判各的：

| | A · 三点判断 | B · 自动批那道闸 |
|---|---|---|
| 判什么 | alignment / conflict / coverage | 只改文档 + Lead 的 pure_docs 声明 + 强度二证据 |
| 什么时候跑 | `dry_run` 和 `auto` 都跑 | 决定动不动手时 |
| 产出 | 可 / 不可 / 建议拒 / 不可判定 | 能不能自动批 |
| 会不会驱动动作 | ⛔ 不会 —— 源码注释：仅供审计，永不得被当作批准指令 | ✅ 会 |
| 读不读对方 | — | **从不读 A 的结论** |

⇒ **founder 看到的「意见」来自 A，真正决定批不批的是 B。** 这就是她说的「两套东西」。

---

## 2. 改完是什么样

```
judge(这张 ship 卡) → 结论        ← 就是现在的 A，一个字不改

flag 只决定【拿这个结论干什么】：
  off       不调用 judge，什么都不记
  dry_run   调用 judge，记账 + 写卡面，不做任何动作
  enabled   调用 judge，结论 = 可 → 真批；结论 ≠ 可 → 等 founder
```

**三个值的区别只有最后一列。判据一个字都不变。**

### 要动的三处

1. **闸改成消费 A 的结论**；B 自己那套（只改文档 + pure_docs + 强度二）**整套退役**，不再是判据。
2. **「只改文档」降级**：它不再是一道闸，改成判据内部的一个输入（纯文档的单没有测试要求，这是 coverage 那一点的事实，不是判据本身）。
3. **「仅供审计、永不得当作批准指令」这条约束不删，改写成由 flag 决定**：
   - `dry_run`：原样保留 —— 结论只许记账和显示，不得驱动任何状态变更；
   - `enabled`：允许驱动批准，且每次写审计。

   ⇒ 约束还在，只是从「**永远**不许」变成「**在 founder 打开的那个模式下**才许」。

## 3. 那套判据具体是什么（照抄现有实现，不是重新定义）

| 判据点 | 现有实现 | 怎么产出 | 对应 founder 2026-09-10 的三条件 |
|---|---|---|---|
| `alignment` | 语义点 | 模型判，必须引用 issue / plan / prd / revision 类证据 | **符合设计** |
| `coverage` | 语义点 | 模型判，必须引用 qa 证据，按 use case 逐条对结果 | **测试证据充分** |
| `conflict` | 机器算 | 扫其它 open PR 的文件清单，看有没有改同一个文件 | （三条件里没有，是现有实现自带的） |

聚合规则（现成的，不改）：

```
任一点 = 待补证                    → 整体「不可判定」
alignment 或 coverage = 未通过      → 「建议拒」
conflict = 未通过                  → 「不可」
否则                               → 「可」
```

### 「改动合理」这一条：证据已经在，只是没被聚合成一个点

founder 三条件里的**「改动合理」**（复审 APPROVED 且零 HIGH）在现有实现里的位置是：
**证据账本里已经有 `code_review` / `design_review` 这两类证据**，但它们**没有被聚合成一个独立的判据点**。

⇒ **是否把「改动合理」提升为第四个点，是一个独立的增量决定，本单不做。**
本单只做「一套判据服务三个 flag 值」。把它写在这里，是为了让它**不被忘记**，而不是为了在本单里做。

## 4. flag 三态行为表

| | 判据 | 跑判断 | 写卡面 | 记账 | 动作 |
|---|---|---|---|---|---|
| `off` | 同一套 | ✗ | ✗ | ✗ | 无 |
| `dry_run` | 同一套 | ✓ | ✓ | ✓ | 无 |
| `enabled` | 同一套 | ✓ | ✓ | ✓ | 可 → 批；其余 → 等 founder |

**「判据」那一列永远是同一套** —— 这是本单的全部主张。

---

## 5. 验收

**主验收（一条，可机械判）**：

> 同一张 ship 卡，在 `dry_run` 和 `enabled` 下，judge 的结论必须**逐字相同**。不同即为又分叉。

配套：

- 阴性对照：改动前，`enabled` 模式下 B 那套仍在决定动作（即结论与 A 无关）。
- `off` 下：零判断记录、零卡面意见、零动作。
- 每一次 `enabled` 下的自动批准，都写审计，且能查到它基于哪一次 judge 的结论。

---

## 6. ⛔ 本单不做

- ⛔ 不新造判据、不重写评估器、不改三点的语义
- ⛔ 不把「改动合理」提升为第四个点（见 §3 末，单独的增量）
- ⛔ 不改 founder 批准的权威边界：`enabled` 只是让**已经存在的判据**去驱动**已经存在的批准动作**，不新增任何人的权限
- ⛔ 不碰 Jev / 概率模型 —— 那是另一条线，且红线是「出意见可以，真批准那一下永远不给概率模型」
