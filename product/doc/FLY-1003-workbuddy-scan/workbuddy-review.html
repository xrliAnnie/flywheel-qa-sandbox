A. 跑在谁的机器上? · 双模式,你选 官方

  • 本机模式:跑你自己电脑(Docker/Podman 本地容器),直读本地文件,适合敏感数据。代价:电脑要开着、不能关机/休眠。
  • 云端沙箱模式:跑腾讯给的机器(指向 E2B 托管云沙箱),不依赖你电脑开机,适合出差/只有手机时。
  • 手机 / IM 端 = 遥控器 UI,不是干活的地方:微信/企微/QQ/飞书/钉钉 发指令(语音/拍照/传文件)→ 后台跑(云沙箱 或 远程控制你本机)→ 回报。
  • 「后台常驻跑哪几个渠道?」(你的原问)—— 精确答:常驻的不是「某几个渠道」,而是一个后端(云沙箱 或 你的本机)。9 个 IM 渠道都只是往这一个后端派活+收结果的入口,本身不各自常驻。准确说 =「一个常驻后端 + 9 个发起/接收渠道」,不是「9 个渠道各跑一个常驻 agent」。

→ 它「云沙箱替你托管、不用开机」是我们也想做的;它「本机模式不能关机」的运维负担甩回用户,是反面教材。

这个回答清楚吗?

B. 多模型切换 · 怎么切 / 收费 / BYOK 官方

  • 怎么切:对话界面底部有「模型切换入口」 → 点「+配置自定义模型」。有 UI、在对话框底部。
  • 收费:走腾讯云 TokenHub —— token 配额套餐,内置模型收费(输入/输出分别计价、分阶越高越便宜)。免费档能上车但有限制(用户吐槽免费版被限速逼付费)。
  • BYOK:支持。带自己第三方 API key 调任何模型(「内置=招牌菜收费,自定义=自带食材免费」)。

→ 它把「供应商中立/多模型」做成了产品里一个下拉+BYOK 的现成功能 —— 我们那条候选差异塌得更实。

这个回答清楚吗?

C. 三剑客 clarify · CodeBuddy / WorkBuddy / 腾讯云 官方

E. ⭐ 最关键一问 · 能不能长期拥有并演进一套真系统? 决定差异

诚实结论:不是纯一次性(它也能建软件),但也不是「长期拥有并演进一套系统」的 owner —— 它是一个『你得自己搭台、每天重新 brief 的 per-session 执行器』。我们那条差异站得住,而且更精准。

它「不止一次性」:跨会话记忆 + Checkpoints + 多 agent(前/后端/测试)+ 自动化基础设施 + 真有大型案例(600+ 轮、15000+ 行、10+ 次部署)。

但「不是长期 codebase steward」(逐条):①无自主 repo/项目 ownership;②项目连续性靠人肉日志、每天重新 brief(否则失忆);③无 git/PR/CI/review 工程纪律,部署手动;④真实翻车 = 系统级失忆、日志造假(写了但没做)、宕机。

→ 差异不是「软件 vs 办公」,是「人力搭台的 per-session 执行器(你当架构师/PM)」vs「替你拥有并养一套系统、带工程纪律的组织」。WorkBuddy 把「攒成一个持续系统」留给用户;Flywheel 替你做了。⚠️ 但我们这套 done-for-you 也还没做实,是要争的。

R3-② ⭐ 记忆模型:跟用户走还是跟项目走?(你最想知道) 评测⚠️

  • 两者都有,分开存(两级):用户级(跟你走、跨项目)= ~/.workbuddy/(偏好:时区/代码风格/报告格式);项目级(跟项目走、隔离)= {workspace}/.workbuddy/(项目技能+上下文)。
  • 三层时间维度(评测口径⚠️):L1 范式(永久行为原则)/ L2 归档(项目+决策摘要)/ L3 会话(31 天滚动日志)。
  • 做完 A 明天开 B 记不记得 A? 机制上记得(同一工作空间:用户偏好+项目记忆+L2+L3)。但不牢靠:会「系统级失忆、日志造假」,要你自建日志兜底。
  • 有没有像我们的常驻 leader? ❌ 没有。 它的「leader」是 Expert Teams 里 per-task 临时组的 lead agent(干完就散);记忆是文件/分层存储跟用户或项目走,不是一个跨时间常驻、持有全局、主动盯 backlog 的人格化 Lead。

→ 对我们差异有利:我们卖的「常驻 named Lead = 记忆+掌控+主动 Push」它结构上没有,它是「记忆文件 + 临时 lead agent」。

R3-③ 云沙箱生命周期(核实你的假设) E2B机制⚠️

  • 创建:按需(开工/发指令起沙箱)。销毁:idle 超时自动销毁(评测约 30 分钟;官方默认值 ⚠️UNKNOWN)+ 主动销毁。
  • 持久化:E2B 用 CRIU 秒级快照(只传文件系统变更)→ pause/resume + 快照恢复;企业版每人独立沙箱、对话+文件持久保存。
  • 接回:支持 pause/resume 接回同一环境。

→ 你的假设「开工开沙箱→干完关→数据进冷存储→下次接回」大致对(按需起+超时关+CRIU 快照持久化+resume 接回);⚠️「冷存储」实际是 CRIU 快照+文件 diff,默认 timeout/保留时长官方值 UNKNOWN。

R3-④ ⭐ 帮不帮长期拥有并演进同一 codebase vs 一次性?(钉死) 决定差异

诚实结论:它 CAN 在同一个项目工作空间上持续迭代(机制齐),所以不是「只做一次性」;但它不是「替你 own 并演进一个 codebase 的自主组织」—— owner/项目经理/工程治理 三顶帽子都还戴在你头上。我们差异站得住,且钉到机制层。

能持续迭代的机制:项目级记忆 {workspace}/.workbuddy + 沙箱 CRIU resume + 分层记忆 + 大项目案例(同一项目 600+ 轮/15k 行)。→ 纠正二轮「per-session 执行器」的过简说法。

但它不是 codebase owner(逐条):① 在「工作空间目录」迭代 ≠ own 一个 git repo(无 git/PR/CI/review/版本治理,部署手动);② owner 是你(靠你维护记忆/日志、每次发起、re-brief,记忆漏了你兜);③ 没有常驻组织盯这 codebase 的 backlog 主动推进(你当 PM)。

→ 差异不是「能不能在同一 codebase 迭代」(它能),是「谁 own + 谁盯 backlog + 有没有工程纪律 + 记忆牢不牢」。WorkBuddy 给你工具+记忆,但把 owner/PM/工程治理留给你;Flywheel(常驻组织 own repo+自推 backlog+PR/CI/review+常驻 Lead)替你做了。⚠️ 但我们这套 done-for-you 也还没做实。
