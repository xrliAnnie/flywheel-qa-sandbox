AIO Sandbox 值不值得我们做？

字节开源的「一体化 agent 沙箱」到底能不能帮到我们的系统 —— 一页讲清 + 你在每节直接回。

FLY-346 · 2026-07-08 · research（不写代码）· 结论已过 Codex 审两轮

一句话

现在这套系统在 Mac 上跑 —— 整个搬进 AIO Sandbox 这种容器，不划算。但你说的对：真要上云 / Windows / Linux，很可能就得容器化，那时才是真问题 ——「用它，还是自研一套」。这页就把这两件事分开讲。

1AIO Sandbox 是什么？怎么用？

它是字节开源的一个「啥都齐了的 agent 工作台」—— 把 浏览器、命令行终端、VSCode、Jupyter、文件系统、还有 MCP 工具 全塞进 一个 Docker 容器里，大家共用一套文件系统。开源（Apache 2.0，5.4k 星）。

怎么起：一条命令，然后浏览器打开就能用（VNC 桌面 / VSCode / Jupyter / 终端都在一个网址下）。

docker run --rm -p 127.0.0.1:8080:8080 ghcr.io/agent-infra/sandbox:latest # 然后浏览器开 localhost:8080 —— 浏览器/终端/VSCode/Jupyter 都在这一个口

它想解决的痛点：过去每个能力（浏览器、终端…）是分开的小沙箱，互相传文件很麻烦。它把这些合一，agent 在浏览器里下载的文件，终端里立刻能用。还自带 MCP（让 AI 直接调浏览器/文件/命令的高层接口），有 Python / TS / Go 三种 SDK。

对我们的系统有没有帮助？

看你要它帮什么：

  • 有用的点子 一条命令拉起一致环境（可复现）、自带 MCP、多个界面能看 —— 这些「思路」是好的。
  • 但直接搬进来没用 它是给「一个 agent 配一个大工作台」设计的（一个容器 = 一个 agent）。我们是「一台机器上同时跑好几个 runner」，两者形态对不上（详见第 2 节）。
  • MCP 大部分我们已有 我们的 runner 现在已经有终端 MCP + 浏览器（Claude-in-Chrome）默认可用，它的 MCP 对我们增量不大。

2为什么我觉得「现在」不值得做

不是它不好，是放到我们现在这套（Mac + tmux + 你能在 cmux 里实时看 runner）里，代价 > 收益。四条理由讲透：

① 你就看不到 runner 在干嘛了

我们有条硬规矩（FLY-398）：每个 runner 都得是你能在 cmux 里实时盯着的窗口。AIO Sandbox 这类容器里的 agent 是「无界面（headless）」跑的 —— 要保留「你能实时看」，就得把整套观测重写（改成看录像 / VNC / VSCode）。这是伤筋动骨。

② Runner 和 Lead 说话，被迫要走网络

现在 Lead 和 runner 沟通是「同一台机器上、走文件 + tmux」，零网络、简单。一旦 runner 关进容器，它俩说话就得跨容器走网络协议（要重做唤醒、审批、心跳这一整套）。这是动整个「沟通 + 生命周期」层。

③ 在你的 Mac 上，Docker 本身就有性能税 你点名的点

你的 Mac 是 Apple 芯片。这类容器是 Linux 的东西 —— 虽然它最新版本已经补了 arm64 镜像，但它仍然不是原生 mac 程序，在 mac 上跑要靠 Docker Desktop 里的一层 Linux 虚拟机：吃内存（每个容器 ~2GB）、吃 CPU、性能打折。我们之前评估同类沙箱（阿里 OpenSandbox）时就记下过这个「mac 上 Docker 性能差」的坑。

另外一个相关的点：这类沙箱的「管住 agent 能连哪些网站（egress 控制）」这类安全能力，基本只在 Linux 上才有效 —— 在 mac 上享受不到。所以在 mac 上，我们既付了 Docker 的性能税，又拿不到它最值钱的隔离/管控好处。

④ 要重做启动 runner 的一整套代码

现在启动一个 runner 是「开一个 tmux 窗口」。换成容器后，四种 runner（claude / codex / antigravity / kimi）的启动、看门狗、心跳、cmux 同步全都要重写一遍。

一句话算账：收益 = 安全隔离 + 环境可复现；代价 = 同时动「启动 / 观测 / 沟通」三层 + mac 上的 Docker 性能税。在单机 mac 上，收益够不着代价。
⚠️ 但有一件事要诚实说：我们现在的 runner（默认那种）其实没有真正的安全隔离 —— 它以你电脑用户的身份跑，理论上能读到机器上的密钥、别的项目。想补这个洞，光加个「路径白名单」是不够的（挡不住 runner 里的脚本自己去读），得靠容器 / mac 的 Seatbelt / 独立用户这类真机制。这是一个独立的安全话题，值不值得单独立项，你定。

3⭐ 你点的关键问题：上云 / Windows / Linux 之后呢？

这才是真问题。你说得对 —— 现在在 mac 上不划算，但如果要把整套系统搬到云上、或 Windows / Linux 机器上跑，很可能就需要容器化了。原因：

  • 云 / Linux 机器上，容器是原生的 —— 上面第 2 节 ③ 说的「mac Docker 性能税」和「egress 只在 Linux 有效」这两个坑，在 Linux 上直接消失。
  • 多台机器 / 多用户跑时，「一个 runner 关一个笼子」的安全隔离就从「可有可无」变成「真需要」。

那时的真问题：用它，还是自研一套？

我诚实的看法（不预设答案，等你和实际需求定）：

维度直接用 AIO Sandbox自研一套
上手速度快 开源、一条命令、现成 MCP + 多界面慢 从零搭
贴合我们一般 它为「单 agent 大工作台」设计，非「多 runner + 你实时看」量身 能保留 FLY-398 实时看 + 我们的沟通模型
维护依赖别人 跟它的版本走自己扛
更该抄谁其实还有个更贴切的参考 homerail（见第 4 节）—— 它已经在做「容器化的 runner 隔离」，比 AIO 更像我们的场景
我的倾向：真到那一步，大概率不是「整套照搬 AIO」，而是「参考 AIO / homerail 的做法，搭一套贴合我们（保留你实时看 + 我们沟通模型）的容器化」。但这要等「上云 / 多机」真立项时再定，跟 FLY-1005（多机部署） 一起想 —— 我已经跟那条对齐了。
重要区分：「上多机」和「用不用沙箱」是两件事，不绑在一起。多机技术上不一定要沙箱（可以先简单地 SSH + 远程跑）。所以别因为「以后要多机」就现在急着上 AIO 沙箱。
↪ 你在批注里问的：「既然 1005 说要容器化，那我们该容器化吗？用 AIO 还是别的 service？」

要不要容器化：1005 真走到「上云 / Linux / 多机」时要；现在还在 Mac 上不要。这个决定归 1005 拍，346 给你「用哪个」的素材。

用哪个 —— 三条路，结合 1005 的一个关键需求一起看：1005 要的是一个「预热节点池（warm pool）」——每个节点得预装浏览器、预登录好 Cloud / Chrome / Suno 这些账号，随时能上手干活。这个需求会直接改变「用哪个」的答案：
路是什么对 1005「预登录富节点池」贴不贴
① 直接用 AIO Sandbox现成一体、重、自带浏览器 + 桌面 + 终端 + IDE意外地贴 它「胖、自带浏览器桌面」正好能塞进「预登录 Chrome/Suno 的富节点」——之前嫌它太胖，在这个场景反而是优点，起步最快
② 轻执行隔离（HomeRail 式，一 node 一容器）轻、只有 node + agent CLI一般 纯执行隔离最干净，但没浏览器/桌面层，warm pool 要的「预登录浏览器」得自己再加
③ 自写完全定制最贴但最慢 能保住「你实时看 + 我们的沟通」，但从零搭
⭐ 跟 1005 对齐（重要，别打架）：1005 的最新版（v5）已经写进去了——「节点的 provisioning 可以站在 346 的 AIO Sandbox 上」。所以 346 这套 AIO Sandbox 的真正位置，不是「346 独立要不要采用」，而是「它当不当 1005 预热节点池的容器化基座」。在云/Linux 上，前面说的 Mac Docker 性能税消失了，而它自带浏览器桌面正好用来放 profile——这时它是个很合理的候选基座。
我的诚实倾向：短期要快 → 拿 AIO 当富节点基座起步最省事；长期要保「你实时看 + 我们的沟通」→ 往 ②/③ 收。这个选择归 1005 定，346 提供素材 + 结论：AIO 最合适的角色是「1005 节点基座候选」，不是「现在拿来整套换 runner」。

4你问的：AIO Sandbox 和 HomeRail 到底啥区别？（附图）

先分清：「沙箱」和「容器」不是对立的两个东西

你问「一个是 Sandbox 一个是 Container，这俩不一样对吧？」—— 其实它俩是两个层次，不是二选一：

  • 容器（Container）= 底层砖头。就是 Docker 那套「把一个程序连同它的环境打包、关进一个隔离盒子里跑」的技术。它是机制。
  • 沙箱（Sandbox）= 用途。指「给 AI agent 安全跑活的封闭环境」。它通常就是用容器实现的。
所以：AIO Sandbox 和 homerail 的 worker，都是「沙箱」，底下都用「容器」。它俩的区别不在「沙箱 vs 容器」，而在下面这张图里的形状——一个是「一个大盒子」，一个是「一个工厂管很多小盒子」。

你追问的几点

Q：能把不需要的（比如 IDE / 桌面）拆掉吗？
能。它开源，浏览器/终端/VSCode/Jupyter/MCP 是可拆模块，可以 fork 砍层、build 一个只留终端+浏览器+MCP 的精简镜像，更轻更省内存。但这里有个关键 trade-off，诚实说清：你砍得越多，最后得到的东西就越接近「自己拼一个瘦容器」。AIO 的价值就是「一整套还预集成好」；一旦砍到只剩终端+浏览器，那份「预集成」的价值也基本没了。
所以我的诚实结论：与其「用 AIO 再砍」，不如「拿它当参考（它的组件清单 / 镜像分层）自己搭一个瘦镜像」——这样每一层都是我们自己要的、可控、可保留「你实时看 + 我们的沟通」。（小注：它的官方 repo 其实没有提交现成的 Dockerfile，镜像是在别处 build 的，所以「参考」= 参考它的组件构成/镜像分层，不是照抄一个文件。）判断点不变：要「带浏览器的富节点」（配合 1005 预登录 Chrome/Suno）→ 精简版或自搭都行；连浏览器都不要 → 直接自搭瘦容器 / homerail 式最省。

Q：这 Sandbox 跑什么系统？macOS / Linux / Windows？
容器里永远是 Linux。不管你机器是 Mac / Windows / Linux，AIO 跑起来里面都是一个 Linux 环境。区别只在怎么跑这个 Linux 容器：Mac 上→靠 Docker Desktop 的一层 Linux 虚拟机（就是「性能税」）；Linux 机器上→原生跑、没税；Windows→也是 Docker Desktop（WSL2）。这正是「你 Mac 上有 Docker 税、云/Linux 上没有」的根因。
具体发行版：外部资料指向 Ubuntu 系（约 Ubuntu 25.10）。诚实标注：它官方 repo 没提交现成 Dockerfile（我翻了整个 repo，0 个 Dockerfile，镜像在别处 build），所以确切 base image 我没能从官方源逐字核到 → 标「Ubuntu 系，确切版本 UNKNOWN / 待核」。但「容器=Linux、Mac 上走 Linux VM」这个关键事实是确定的。

Q：我理解 AIO 当 hub、homerail 一人一容器，对吗？
基本对，各补一句：
① AIO 当 hub（一个 lead + 整个 team 跑在一个 AIO 里）= ✅ 合理用法，一个胖盒子放 lead + 几个 runner 共用同一套环境。代价：他们挤在同一个盒子里、彼此没有隔离（共享 fs，一个出事影响别人）。hub = 省事+共享，牺牲互隔。
② homerail 每个 worker 独立容器 = ✅ 对。小订正「shared」：同一次 run 的几个 worker 共享一个 workspace（数据层），但它们是各自独立的容器（执行层隔离）。
你抓的对比本质很准：AIO-hub = 大家挤一个共享盒子（在一起、无互隔）；homerail = 一人一个隔离盒子（分开）。就是「共享 vs 隔离」这条轴的两端。想「一个 lead+team 共享富环境+预登录浏览器」→ AIO-hub（拆掉 IDE）很贴；想「每个 runner 严格互隔」→ homerail 式。

⭐ 关键洞察：这俩不是二选一 —— 可以「分层用」

你上面把 AIO-hub 和 homerail-一人一容器 当成两条路。其实更聪明的用法是把它俩叠起来：上面一层共享的 hub，下面一层每个 runner 一个瘦容器。而这正好对上 1005 想要的架构（「共享 hub + 每个 runner 一个节点」）：

🧠 Hub 层：一个普通 container / 一台机器
Lead + Bridge —— 协调、排活、你在这层实时看（普通容器就够，不用 AIO）
每个 runner 各自一个 container ↓（互相隔离；要浏览器就把浏览器装进它）
📦 worker
runner A
📦 worker
runner B
📦 worker
runner C
= hub（普通 container）+ 每 runner 一个隔离 container（homerail 式）。AIO 不是这里的默认 —— 见下方
把名词理清（别被绕）：
· Hub 层 = 一个普通 container（Lead + Bridge）—— 不需要 AIO 那套胖环境，普通容器就够。
· Worker = 一个 container（每 runner 一个、互相隔离）—— 要浏览器就把浏览器装进这个 container。
· AIO = 可选的「胖节点」方案 —— 只在某个 worker 节点要「自带浏览器 + 桌面一整套」时才考虑（多半还用精简版）；它不是 hub 层的东西。
所以答案不是「AIO 还是 homerail 二选一」：hub 用普通容器、worker 一人一容器（像 homerail），AIO 只是「要富节点时」的一个可选基座。正好落在 1005 的「共享 hub + 每 runner 一节点」上：1005 只要决定 worker 节点要不要富（要富→AIO 精简版或自搭；不要→瘦容器装该装的），346 已把参照物摆清。
