## 1. 先把基线量出来（v8 实测，不是感觉）

在 v8 线上页（`fw-reports-a53de2.vercel.app/r/093314a4…`）跑 DOM 测量得到：

| 量 | v8 实测 | 参考物典型值 | 判断 |
|---|---|---|---|
| 内容栏宽度 | **820px**（卡片满宽） | TLDR ≈ 430px · Import AI ≈ 355px · Linear ≈ 435px | 太宽 |
| 正文行宽 | **665px = 46 汉字/行** | 中文舒适区约 30–40 字/行 | 超出 |
| 单卡带框/底色的容器 | **10 个**（9 个后代 + 卡片自己） | TLDR 0 个 · NextDraft 0 个 · Import AI 0 个 | 严重超出 |
| **被「围成一张卡」的条目** | **24 / 24 条** | 参考物 **全部为 0** | ⚠️ |
| 整页字段名单元格 | **74 个** | 参考物 **全部为 0** | ⚠️ 最大差异 |
| 常驻空输入框 | **25 个** | — | 视觉重量浪费 |
| 页面总高 | **9,790px ≈ 11 屏** | TLDR 当日刊 ≈ 3 屏 | 太长 |

复跑方法：打开 v8 页，控制台跑 `assets/measure.js`（本文件夹内）。上表就是它的输出。

> 🔎 **量的时候发现的一件事，值得单独记**：截图上那个把每条围起来的「卡片框」
> **其实不是边框，是一条 `box-shadow`**（v8 的 `.card` 只有 4px 左侧色条 + `0 1px 3px rgba(0,0,0,.06)` 投影 + 12px 圆角）。
> 意思是 —— **「卡片感」不需要边框也能造出来**，所以验收「零卡片边框」时
> 只查 border 会漏掉投影这条路。尺子里已经把投影一并算作「围起来」（`measure.js` 的 `enclosed()`）。

**这张表就是结论的一半**：v8 和四个参考物**唯一的量级差异不在颜色、不在字体，在「容器数」和「字段名数」。**
参考物在这两项上都是 **0**。

## 2. 四个真实参考 —— 它们各自做对了什么

### ① Import AI — <https://jack-clark.net> 📷 `assets/ref-import-ai.jpg`

**为什么它最相关**：这是**结构上跟我们最像的东西** —— 一个人、每天一次、每条 = 外部链接 + 他自己的判断 + 「这为什么重要」。
跟我们的四段（这是什么 / 为什么值得你看 / 跟我们什么关系 / 哪里能借鉴）几乎一一对应。

**它做对了什么 —— 一句话：它把「字段」写成了「句子」。**

```
Want to be able to deal with RSI? Here are 23 actionable policy ideas:   ← 加粗的「论断」当标题
…IFP serves up some "low-regret" policy recommendations…                 ← 斜体一行 tagline
Policy experts with think tank IFP have published…                       ← 正文，无标签
Why this matters – the fewer options we have, the worse…: Right now…     ← 加粗引导句，嵌在段落里
Read more: How Should the US Prepare…(IFP).                              ← 链接在最后
***                                                                       ← 三个星号做分隔
```

关键点：
- **「Why this matters」不是表格行，是句首的加粗引导句。** 它同时是标签**和**内容 ——
  `Why this matters – the fewer options for dealing with RSI we have, the worse the outcomes will be:`
  这一句读完就已经拿到了结论，后面的段落是展开。**我们的「为什么值得你看」是纯标签，读完等于零信息。**
- **标题是一句有内容的论断**，不是 repo 名。
- **分隔用 `***`，不用卡片边框。**
- 行宽极窄（约 355px）。

> 这一条如果只能借一件事：**把左侧的 4 个字段名删掉，改写成句首加粗引导句。**
> 内容一个字不用改，`judgments.json` 现有的 `why` / `relation` / `borrow` 直接就能这么排。

### ② TLDR 当日刊 — <https://tldr.tech/tech/2026-08-11> 📷 `assets/ref-tldr-issue.jpg`

**为什么相关**：极限可扫性的教科书。它一天也是十几条，也全是外链。

做对的：
- **标题即链接**（粗体 + 下划线），一眼知道能点。下面**只有一段**纯文本。**零容器。**
- 每个标题带 **`(6 minute read)`** —— 明码标价的阅读成本。
- 分组只用一个 emoji + 一行小标题（`🚀 Science & Futuristic Technology`），**没有 tab、没有边框**。
- 内容栏 ≈ 430px。整刊约 3 屏。

> 借：**标题即链接**、**阅读成本前置**（我们可以换成「今日 +1,148 星 · 深读」）、**一条只有一段**。

### ③ NextDraft — <https://nextdraft.com> 📷 `assets/ref-nextdraft.jpg`

**为什么相关**：Dave Pell 一个人做的每日精选，每条 = 大编号 + 大写标题 + 他的评论散文，链接内嵌在句子里。
**它证明了「编号」和「好看」不冲突** —— 这正是 Annie v7 要的编号。

做对的：
- **编号是一个大号轻质的排版符号**（衬线体、大字号、低对比色），不是深色小方块 chip。
  它给眼睛一个节奏锚点，但不抢戏。**我们 v8 的编号是黑底白字方块 —— 反了。**
- **完全没有卡片边框**。分隔靠留白 + 一条细线。
- 链接**长在句子里**（`NYT (Gift Article): America Is Atomizing`），不是单独一行。
- 标题是**一句人话**，不是对象名。

> 借：**编号的排版做法**（大、轻、不抢戏）、**零边框靠留白分隔**。

### ④ Linear Changelog — <https://linear.app/changelog> 📷 `assets/ref-linear-changelog.jpg`

**为什么相关**：它解决的正是我们最难的那件事 —— **元数据往哪放**。
我们每条有一堆非正文信息：星数、语言、`✅核过原物` / `⚪只扫了没核`、备注入口。塞进正文就是 v8 现在的样子。

做对的：
- **左边一条固定的元数据栏**（日期 + 一个小圆点），**右边一条窄的内容栏**。
  元数据永远在视线外侧，**读的时候眼睛只走一条直线**。
- 内容栏 ≈ 435px，段落之间大留白，**没有一个框**。

> 借：**把星数/语言/核验状态/编号全部移到左栏**，正文栏一个字段名都不留。

## 3. 四个参考物的共同点（这才是「好看」的实际定义）

把四个放在一起，**它们互相之间风格差很远**（Import AI 是等宽极客风、NextDraft 是粗黑报纸风、
TLDR 是极简、Linear 是暗色高级感），但**有五件事它们全都做了**：

1. **没有字段名。** 四个参考物加起来 **0 个**。标签要么删掉、要么写成句子的一部分。
2. **没有卡片边框。** 分隔靠留白、细线、或一个 `***`。
3. **内容栏 355–435px。** 全都比我们的 665px 窄得多。
4. **每条有且只有一个视觉入口** —— 那个加粗的标题 / 论断。眼睛知道从哪开始。
5. **元数据要么删掉、要么移到正文之外**（Linear 的左栏 / TLDR 的括号阅读时长）。

**⇒ 所以「好看」在这个品类里不是风格问题，是四条可执行的约束。**
它们和风格无关 —— 你可以用它们做出报纸风、极客风、极简风，这正是下面四个方向要试的事。

## 4. 从研究到方向：四个方向各赌什么

四条约束都遵守的前提下，仍然有一个**没被研究回答的问题**：
**当一天有 18 条、每条有 4 段深度内容时，该先给她什么？** 四个参考物给了四个不同答案：

| 方向 | 学谁 | 赌的是 | 代价（诚实写出来） |
|---|---|---|---|
| **A 电报** | TLDR | **扫得快** —— 18 条 3 分钟扫完，深读内容折叠起来 | 深读要多点一下才看得到 |
| **B 简报** | Linear + Import AI | **读的时候不被打断** —— 信息一条不少，但元数据全在左栏 | 需要宽屏；手机上要塌成单栏 |
| **C 杂志** | NextDraft | **替她做减法** —— 头条大版面，其余收进紧凑清单 | 需要「谁是头条」的排序判断 |
| **D 工作台** | （反向：密集表） | **先给全局再钻细节** —— 一屏看完 18 条，点开才展开 | 那一句话结论必须真的够好 |

**D 是故意的对照组**：它是唯一一个**不**追求「像读物」的方向，而是承认
「这是一个每天要过一遍的工作清单」。研究里说的「卡片被滥用了，重复标签的结构化数据用表格更合适」
正好支持这一条 —— 如果她的真实心智是「过一遍」而不是「读一读」，D 才是对的。
**把这个反向假设也做出来，比四个都做成读物更有信息量。**

## 5. 我没做的 / 不确定的

- **没有做用户测试**，也没法做（用户只有一个人，就是 Annie，她本人就是评审）。
  所以上面所有"好看"的判断都是**从参考物身上归纳的**，不是验证过的。四个方向就是四个待证伪的假设。
- **只看了西文参考物。** 中文排版（行宽字数、标点、加粗的可见度）跟西文不同，
  §3 的「355–435px」不能直接照搬 —— mockup 里我按中文实测取值（见 plan.md §2）。
- **没看小红书 / X 的信息流本身**（派单里提到的方向之一）。原因：那两个是
  **无限流 + 图片驱动 + 陌生人内容**，跟「一天一次、十几条、给一个人、每条要留备注」的场景差得远，
  借过来大概率是错的。**如果 Annie 认为该看，这是一个明确的下一轮输入。**
