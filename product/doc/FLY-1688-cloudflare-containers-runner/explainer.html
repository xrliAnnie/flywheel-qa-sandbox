问题 ① 凭据安全

你明确说这条最关心。所以先审我们自己:一个 Runner 今天到底带着什么。

先审自己:Runner 现在手上有什么

凭据存在哪能干什么 / 多久过期
Claude 登录态你 Mac 的钥匙串整个 Claude 账号;长期有效
GitHub~/.config/gh/hosts.yml账号级(除非换成受限令牌)

Discord 机器人令牌.env —— Runner 读不到—

今天有一个很好的性质:Runner 并没有被塞进这些令牌。它是隐式继承你这台机器上已经登录好的 gh 和钥匙串。所以一个 Runner 出事,炸的是「这台机的 GitHub + 你的 Claude 账号」,不是整个 .env。

上云会把这个隐式继承变成显式投递 —— 云上的容器里没有你的钥匙串,凭据必须被主动塞进去。这既是机会(可以趁机收窄),也是新的暴露面(它们变成容器里的明文环境变量)。

审计 Bridge 只把 FLYWHEEL_INGEST_TOKEN 注入 Runner(TmuxAdapter.ts:468);Linear key 由 Bridge 持有(teamlead/config.ts:154)。 实测 各凭据文件位置与权限位。

Cloudflare 那边提供什么

  • 可以做到「每个容器实例拿一份不一样的凭据」 —— 官方文档明确支持 per-instance 环境变量:「Each instance gets a different set of environment variables」。这让「每个 issue 一份专属令牌」在架构上成立。
  • 官方也自己警告:不要用明文环境变量装敏感信息,要用 secrets 或 Secrets Store。
  • 但 Secrets Store 目前是 公开测试(open beta),还不是正式版;而且谁能读、怎么轮换、有没有审计日志 —— 文档里查不到查不到。真要拿它当凭据面,这三条得先问清楚。
  • 容器之间是 各自独立的虚拟机,隔离级别高(「strong isolation」)。
  • 出网默认是开的,但可以整个关掉,或者只放行白名单里的域名。

关键落点:Cloudflare 这条路是「把凭据安全地送到容器门口」,不是「让容器永远看不到凭据」。送进去之后,它就是容器进程里的普通环境变量。

厂商自报 Cloudflare Containers 文档:env-vars-and-secrets / platform-details / outbound-traffic;Secrets Store overview。

爆炸半径:一个容器被攻破会怎样

三件事叠起来:

  • 我们的 Runner 是跳过权限确认跑的 审计(Blueprint.ts:2682)。
  • Anthropic 自己的文档对这个组合写得很直白:
「When executed with --dangerously-skip-permissions, dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials. … prefer repository-scoped or short-lived tokens.」
—— Claude Code 官方文档,dev container 页 厂商自报
  • 容器里的凭据就是普通环境变量。

⇒ 一个被攻破的 Runner 容器,等于它手上那份 Claude 令牌 + 那份 GitHub 令牌全部外泄。容器之间不会互相波及(虚拟机隔离),但单个容器内部没有第二道墙。

还有一条容易漏掉的:解决问题 ③ 的那条 SSH 命令,同时是一条新的凭据通路 —— 任何对该容器有写权限的 Cloudflare 账号身份,都能 shell 进一个正在跑的 Runner,而它此刻正拿着上面两份凭据。也就是说,Cloudflare 账号本身会变成一个必须按最高等级来守的新东西。

能不能做到「一次性、最小权限」?—— 分两半,答案不一样

哪一半能不能为什么
GitHub 能 GitHub App 令牌约 1 小时过期、可锁到单个仓库。我们内部已经有两个现成模式:FLY-350/245 的受限令牌经 broker 投递(不进模型环境),以及 Anna 那套 scoped 令牌 + 隔离验证脚本。配上 Cloudflare 的 per-instance 环境变量,「每个 issue 一个只能碰那个仓、一小时过期的令牌」是成立的。
Claude 不能 容器里没有钥匙串。无人值守容器要跑 Claude Code,官方给的路是生成一个长期令牌 —— 有效期一年、认证整个订阅账号。它只能发模型请求(开不了远程控制、拉不了 connectors),算收窄了一点点,但不是按 issue、按仓、按小时的最小权限。

唯一真正能收窄 Claude 那半的替代是换成 API key(可撤销、可设支出上限)。但那等于从订阅制换成按用量计费 —— 那是一个独立的、量级很大的成本决定,不能当凭据方案顺手做掉。

⚠️ 这条跟 Cloudflare 无关。换成 AWS、Google、或者自己在别处放一台 Linux 机器,结论一样:只要 Claude Code 跑在你不物理控制的机器上,它就带着一份一年期的全账号订阅凭据。

🔴 一条独立的安全约束 —— 比「要不要上 Cloudflare」更重要

这条不是关于 Cloudflare,也不是事故记录。它是审计过程中暴露出来的、当下就成立的设计约束。

约束:Runner 跑「跳过权限确认」模式 ⇒ 它执行的任何命令都没有人工拦截层。因此:

  • 任何能读到凭据的命令 —— 读钥匙串、打开凭据文件、打印环境变量 —— 一旦被执行,凭据就落进那次会话的记录里(本机日志 + 发往模型的上下文)。没有任何机制会拦下它或告警。
  • 这跟「谁在跑那条命令」无关。agent 出于正当目的审计时会这么做(这次就发生了);一个被注入的恶意仓库也会这么做。在这个模式下,系统分不出这两者,也不试图分。
  • 它是靠执行者自报才被发现的。没有自报,这次就不会有人知道 —— 「靠 agent 自觉」不是控制措施。
  • 上云不改善这一条,只放大它。同一条命令在自己机器上是打进自己的日志;在云上是打进别人家的日志和别人家的上下文,而且上面那条 SSH 还多开了一条进入活体 Runner 的通路。

⇒ 推论(对任何底座都成立):只要 Runner 保持这个模式,「把凭据本身收窄」就是唯一还剩的那道墙 —— 因为「不让它执行到凭据」这道墙根本不存在。所以凭据收窄(单仓、短期、可撤销)不是可选的加固项,是这个架构下的唯一防线。

本单不对此提方案 —— 那是独立的工程/产品决定,应另开单。这里只把约束陈述清楚。

⚠️ 一个必须报告的事:本次审计我自己泄了一次

为了搞清楚「Claude 登录态到底存在哪」,我跑了一条读钥匙串的命令,它把你的 Claude 令牌明文打进了本次会话记录 —— 因此进了本机的会话日志文件,以及发往模型 API 的上下文。

  • 范围:是你自己的 Claude 账号令牌,收方是签发方本身,泄漏面小 —— 但不为零。
  • 我没有把它写进任何文档、这张页面或任何提交,也没有再跑第二次。
  • 要不要轮换(重新登录一次 Claude)由你决定 —— 我不擅自动生产登录态。

它同时是上面那段分析的实证:这份凭据距离「任何以你的身份运行的进程」只有一条命令。这不是抽象风险。

跟自己买机器比:盈亏平衡点在哪

机器的成本是固定的(用不用都在),云是按用量的。所以平衡点可以写成一个公式,你代入自己真实的机器价就行:

盈亏平衡(Runner·小时/月) = (机器价 ÷ 摊销月数 + 每月电费) ÷ 云上每 Runner·小时单价

代入一组假设参数(不是报价):机器 $2,000、摊 36 个月、电费约 $13/月 → 固定成本约 $68.6/月。对 standard-2($0.079/时):

盈亏平衡点
1.2 个并发
只要你持续跑得动 约 1.2 个以上的并发 Runner,一台自己的机器就已经比云便宜了。我们实测平均并发是 6.5–16.6。
单位成本差距
约 17 倍
一台 64 GB 机器若能装约 20 个 Runner 槽位 → 每槽位约 $3.4/月;Cloudflare 每槽位约 $57.4/月。

内存装得下吗:12 并发约 17 GB,峰值 27 约 38 GB —— 一台 64 GB 的机器基本覆盖当前峰值。(FLY-517 那次装不下,是因为机器只有 16 GB,不是「必须上云」。)⚠️ 这只算了内存装不装得下,没算 CPU、IO 和下面那条拥塞成本 —— 「装得下」不等于「跑得动 27 个还不降级」。

⚠️ 这个「17 倍」里藏着一个假设 —— 必须说出来

它默认那台物理机能「免费吸收」全部并发。

注意上面两个数的口径其实不同:平衡点写的是 1.2 并发,而 17 倍用的是「一台机器装 20 个槽位」。如果一台机器真的只能扛 1.2 个并发,那 27 并发就需要二十几台 —— 物理侧成本会跟着涨上去,17 倍就不成立了。

而且我们有反例,说明那台机器并不是免费吸收的:

  • 1M context 的 runner 曾经把内存吃爆(swap 耗尽),所以 1M 被改成显式手动开启;
  • 高 load 时段是 chrome 断连等故障的复发温床。

这两条都说明:物理机的并发是有拥塞成本的,不是免费的。

⇒ 所以 17 倍是「忽略物理机拥塞成本」前提下的上界比值。把机器的拥塞/降级成本算进去之后,真实倍数会低于 17 倍,但方向不变 —— 云仍然更贵。精确倍数需要「单台机器真实能扛多少并发」的数据,这一单没有,也没有去测。

这两条反例由 Honey Lemon 提供(2026-08-10),本单未独立核实。

一个结构性的计费错配 —— 精准命中我们的形态

内存是按「已分配」计费的,不看 CPU 忙不忙。而我们的 Runner 有一大段时间是停在门口等你回复 —— 那段时间几乎不用 CPU,但内存一直被占着、一直在计费。一个 Runner 在门口等 10 小时,光内存就是约 $0.54,而它什么都没干。

这不是一般性缺点,是精准命中我们形态的一条。

等待占比约 24%(Honey Lemon 实测,本单未独立复核)。

口径:完成单中 founder_gate 处于打开状态的时长 ÷ 整单跨度;仅统计 gate 已正常关闭的单,n=5(span 603 分钟 / 节点工作 459 分钟 / founder gate 144 分钟)。

⚠️ 此数早前有一版「67% 在等」是错的,已公开撤回。错因:原查询对未关闭的 gate 用了「算到现在」,而 9 个完成单里有 5 个 gate 从未关闭 —— 等待时长被虚高约 3 倍。现值为修正后的版本。

⚠️ n=5 样本很小,只能作方向性判断,不要当精确值使用。真实占比可能在此上下浮动;本单未重新测量。

这段等待时间在自己的机器上是免费的,在容器上按内存计费 —— 这是我们这种「要等人拍板」的形态特有的成本放大,一个纯自动化的 CI 负载不会有这一条。

能不能让它先睡过去省钱?不改架构的话不能。因为 Cloudflare 明确写着:磁盘是临时的,睡醒之后拿到的是一块全新的、按镜像重建的磁盘。

⇒ 睡一觉 = 工作区和终端会话全没了。一个做到一半的 issue 不能靠睡觉省钱。要绕开只能改形态(等门之前先提交推送、等完之后重建容器重进会话)—— 那是一个真实的产品/工程决定,不是一个配置开关。这也是为什么上面那个月成本估算,是下不去的。

厂商自报 Containers FAQ:「All disk is ephemeral」/「when it goes to sleep, the next time it is started, it will have a fresh disk」。
问题 ③ 出问题时能不能马上点进去看

你的要求很具体:不需要一直显示,只要出问题时有一条成熟、随时可用的命令点进去看它在跑什么。

Cloudflare 有,而且是官方一等公民

已解决自 2026-05-12 起默认开启,不需要额外配置。

wrangler containers instances          # 列出正在跑的容器,拿到实例 ID
wrangler containers ssh <实例ID>       # 开一个交互终端
wrangler containers ssh <实例ID> -- tmux attach -t <会话名>   # ← 你要的那一条

也可以当成标准 SSH 的跳板用,直接接进你惯用的 SSH 客户端。

这跟 FLY-624 当初设计的那条命令是同一个形状 —— 只是寻址从「哪台机器」换成「哪个容器实例」。所以 FLY-624 的设计不需要推翻,只要在「位置标识」那一栏留一个既能装机器名、也能装容器 ID 的抽象。Tailscale 那层在纯 Cloudflare 路径上不需要;混合形态(自有机器 + 云节点)则两种寻址都要支持。

厂商自报 Cloudflare Containers SSH 文档 + wrangler 命令参考 + 三条 changelog(2026-03-12 支持 / 2026-05-12 默认开启 / 2026-05-28 支持 ProxyCommand)。

限制(得知道)

  • 好的一面:不开公网端口 —— 唯一入口是经 Cloudflare 账号鉴权的官方命令行工具。这比裸开 SSH 端口安全。
  • 容器必须还活着才能点进去。官方明说 SSH 不会把停掉的容器叫醒,而且「光有一个 SSH 连接不足以让容器保持存活」。⇒ 已经睡掉的 Runner,你点不进去看。
  • 只支持一种密钥类型(ed25519),公钥要提前写进容器配置。
  • 谁能进:任何对该容器有写权限的 Cloudflare 账号身份 —— 见上面「爆炸半径」那段。
  • 日志侧比 SSH 弱不少:容器的输出自动汇进 Cloudflare 日志目前还是一个待做的功能请求,不是已发布能力;wrangler containers 也还没有 logs / stop / start 这些子命令(同样是 open issue)。日志保留期:付费版 7 天。

顺带核实了你在 issue 里已经写的三条 —— 全部为真

无硬性运行时长上限
✅ 官方原话:不会在跑到某个时长后主动关掉你的容器。但宿主机重启是不定期的,不承诺任何在线时长。
关闭序列
✅ 先 SIGTERM,15 分钟后 SIGKILL。
冷启动
⚠️ 官方说「通常 1–3 秒,取决于镜像大小」。但我们的镜像要装一整套工具链,而且磁盘是临时的 —— 每次还得重新 clone 仓库、装依赖。那不是秒级。这条没验证过。
边界 这一单没覆盖什么

写清楚,免得被当成已验证。

  • 零动手验证。没有 Cloudflare 账号、没部署过、没真跑过一个 Runner 容器。所有 Cloudflare 结论都是读文档推出来的。要往前走,第一件事应该是一个小实验:真起一个容器,跑通命令行工具 + 终端 + 那条 SSH。
  • 冷启动真实数字没测 —— 加上 clone 仓库和装依赖之后到底多久,未知。
  • Claude 命令行工具在 Cloudflare 的容器运行时下能不能正常跑,没验证 —— 尤其是交互式终端界面这一块。
  • 三张官网价目表已抄录,但月成本只算了容器那一张。Workers 请求、Durable Objects(尤其是「醒着但闲着」的时长)、日志都另计费,没有按我们的形态建模 —— 所以上面那个月成本是下界,不是全额账单。入网算不算钱查不到。
  • 物理机对照用的是假设参数,不是报价 —— 给的是公式,数字要代入真实机器价重算。
  • CPU 忙的比例是假设,不是实测 —— 这是月成本估算里最大的不确定项之一。
  • Secrets Store 的权限模型 / 轮换 / 审计日志查不到。
  • 没有横向比其它云(AWS、Fly.io、Google 等)。本单只回答「Cloudflare 容器这一个具体底座」,不回答「云里哪家最好」。
  • 没重做 FLY-1005 的多机架构(Bridge 怎么暴露和鉴权、跨机唤醒、温池、按用途分池)。那些在云上一条不少,成本和复杂度都不在上面的数字里。
  • 没评估 Lead 上云 —— FLY-555 已定不上,本单不重开。
  • 并发数据没重查生产库,直接用了你在 issue 里给的三个数和你自己标的高估口径。
  • 顺带记一笔:Cloudflare 另有一个 Sandbox SDK(建在容器之上、专门给 AI agent 跑代码用,带 WebSocket 终端),目前是 preview,本单没深入评估 —— 列在这里免得漏掉。
