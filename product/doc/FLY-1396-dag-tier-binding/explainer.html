● 核心机制:一件活怎么在派发那刻被判成某部门

这才是 PRD 的核心(不是那张表)。下面是扒完代码的真实情况。

派发一件活  →  看它的标签 / 派发它的 Lead  →  已算出「归哪个部门」✓
✗ 断在这里 → 部门这个结果没被拿去选模板  →  模板还是默认 eng-heavy
  1. 已建好:「活 → 部门」的判定。 系统在派发那刻已经算出这件活归哪个部门(依据 = 它的标签,或派发它的 Lead 本身就带部门;flywheel-product-lead = 产品部)。这套判定已经在跑(用来决定归谁管)。
  2. 缺的一根线: 这个「部门」结果没有被接到「选哪套模板」那一步。选模板时系统只看一个没人填的字段,填空 → 默认落 eng-heavy。这就是为什么讲过很多遍、系统还是全走 eng-heavy —— 不是判部门没建,是判出来的部门没接上模板。
  3. 要做的: 把已算出的部门接到选模板那一步 + 一张小小的「部门 → 模板」对照 + 允许 Lead 每单手动指定覆盖。难度远小于「从头造一个分类器」—— 分类器已经在跑。
● 那张小对照:部门 → 模板

这是简单的 30%。看「活的部门」,不看项目。

活的部门模板说明
工程eng(1 套 + 旋钮)+ generic真建代码走 eng(重/中/轻合并成 1 套 + model 旋钮);其余走 generic
产品PRD + designer + prototype-engineer + generic= 三个产品角色各一套 + generic 兜底
其余 / 判不出generic单 session、最轻,不套重型流水线
generic = 一个 session、agent 直接做、不塞一堆阶段 prompt。大多数活的默认 + 所有部门的兜底 + 判不出部门时的落点。绝不再默认落 eng-heavy。 砍掉了 research-light / ops-light / qa-only / doc 那些专门轻模板 —— 能 generic 就 generic。
● 三条 framing
  1. 临时默认,不是永久硬规则。 这套「部门 → 模板」是起步默认;Lead 派单可以每单覆盖(能力已有)。不是「这个部门永远只能这套」。
  2. 终态是动态 DAG。 agent file 都备好,Lead 按任务当场组图;静态模板 = 动态 DAG 的默认层 / 积木。现在建 = 铺底、非弯路。(动态 DAG 形态另开方向,这里只点一句。)
  3. 为什么现在做: 立刻止住「全走 eng-heavy」的浪费,不等动态 DAG。
