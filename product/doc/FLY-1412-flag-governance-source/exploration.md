## 2. 代码事实:今天「创建一个新 flag」那一刻,已经发生了什么

**关键发现:创建时的拦截点 _已经存在_,而且已经在挡住一部分事。**

新 flag 的注册中心 = `packages/config/src/feature-flags/registry.ts`(FLY-709,3551 行,单一真相)。
今天开一个新 flag,要通过**三道已存在的门**:

| # | 门 | 在哪 | 现在拦什么 |
|---|---|---|---|
| 1 | **TypeScript 类型** `FeatureFlagSpec` | `registry.ts:58-94` | 少写 name/category/source/scope/polarity/valueKind/default/description/readSites/toggleable 任一个 → **编译不过** |
| 2 | **双向漂移守卫**(CI) | `packages/config/src/__tests__/feature-flags-drift.test.ts` | **正向**:生产代码里出现没注册的 `FLYWHEEL_*` 布尔开关 → **CI 挂**。**反向**:注册了但 readSite 文件里没有这个 env → **CI 挂** |
| 3 | **注册表不变量**(CI) | `packages/config/src/__tests__/feature-flags-registry.test.ts`(647 行,**29 条** —— 初版误写 30,实跑 vitest 为 29) | governance gate 必须 readonly、direct toggle 必须有实证、enum 默认值必须合法…… |

> ⚠️ **门 2 的覆盖范围没有初版说的那么宽**(见 prd.md §1.3 的完整边界):
> forward 只扫 4 个目录(全仓 21 个 package 带 `src/`),只认几种读法,不查 `project_config` 键;
> reverse 用 `.some()` + 字符串 `includes`,声明多个 readSite 只要一个命中就通过。
> **对已写进 registry 的行是硬门;对完全绕开 registry 的野 gate 有洞。**

**推论(对本单最重要的一条)**:
> issue 问的「是并进 FLY-872 的钩子,还是独立拦截层」—— 答案可能是**两个都不是**。
> 拦截点**今天就有**,而且是最便宜的那个:一个 TS 必填字段 + 一条 CI 断言。
> 加一个必填的「退役条件」字段,等于**零新基建**就把 Annie 要的第 1 件事做成硬门。

**FLY-872 的现实**:状态 = **Backlog,还没开工**。它要的是「机器本地 override 层 + Dashboard 自动渲染」。
所以「并进 872」在近期**不可用**,而且 872 的钩子是**读**侧(把 flag 渲染进 dashboard),
本单要的是**写**侧(创建那一刻卡住)。两者本来就不是同一个点。

两周半从 0 涨到 148,没有任何一周是持平的。

### 3.2 删除率 — ⚠️ 本节初版数字有误,已重算(见 prd.md §1.1)

**初版写的**:「`RETIRED_FLAGS` 总共 10 条 → 17 天只删过 10 个 → 自然退休速 = 0」。
**这是错的,而且错法很典型:拿标签当事实。**
`RETIRED_FLAGS`(`truth.ts:292`)是「生产 env 里还残留旧变量就 fail-loud」的 **tombstone 表**,
**不是删除账本** —— registry 行的删除根本不经过它。

**重算方法**(逐 commit 集合差,`names(C)` vs `names(C^)`):

| 指标 | 实测 |
|---|---|
| 累计新增 | **167** |
| 累计删除 | **19** |
| 净值 | **148** ✅(= 今天 registry 实际行数,自洽) |

**19 个删除的来源**:14 个来自一次性人肉审计(FLY-1136 → FLY-1240/1241/1242/1243,**全部集中在 7/14 一天**),
5 个是做别的活时顺手删的(FLY-1251/1373/1385/1392),**0 个来自任何常规 / 自动机制**。

→ 修正后的结论:**出口不是 0,是 19;但 19 个里 0 个来自常规出口 —— 每一次出口都要人亲自发起一场审计。**
方向不变,而且这个版本更准、更有说服力。

### 3.3 flag 长什么样:她说的「bug fixing 也做成 flag」是**可测量的**

148 个的构成:

| 维度 | 分布 |
|---|---|
| category | **kill_switch 64** · feature 77 · governance_gate 7 |
| polarity | **default_on 105** · opt_in 43 |
| toggleable | readonly 62 · conversational 60 · direct 26 |
| source | env 141 · project_config 7 |

**`default_on` + `kill_switch` = 「我修好了一个 bug,顺手留了个开关能把修复关回去」** ——
这正是 Annie 抱怨的那一类。105 个 default_on 里,绝大多数是这个形状。

→ ⚠️ **本段推论已被推翻,见 prd.md §5.2.1**(registry 里有确凿反例:`watchdog_blocked` 等长期安全门)。保留原文只为留痕。原推论:这给了一个**可执行的判据**:如果一个新 flag 是 `default_on kill_switch`,
它按定义就是**临时的**(修复稳定后就该固化成默认行为、把开关删掉),
它**必须**有退役条件。这不需要人来判断意图,类型自己就说了。

## 4. 「退役」在今天有多贵(为什么第 2 件事——自动建清理单——有价值)

FLY-1243 的探索文档(`engineering/doc/FLY-1243-flag-cleanup-batch12/exploration.md`)记了一条硬约束:

> 退休一个 flag = **代码 gate 和注册表定义必须同步删**。
> 只删注册表 → 正向漂移守卫失败(生产还有裸 gate);只删代码 → 反向失败(readSite 找不到 envVar)。

而且 12 个 flag 的退休被迫分成 4 类变换(A 干净删守卫 / B 有同伴 gate 兜底 / C flag 是唯一主 gate、裸删会 throw / D 生产从没通电过、需人确认)。

→ **退休不是「删一行」,是一次真实的工程改造。** 所以「到期自动建一张单」不是官僚主义,
它对应的是一份真实的、需要排期的工作。这一条支持 issue 的第 2 个诉求。

### 已有的可复用基建

- Bridge 侧**已经会自动建 Linear issue**:`auto-qa-effects.ts:304` / `plugin.ts:9947` 都在跑 `client.createIssue`。
  → 「自动建清理单」有现成先例,不用新建轮子。
- registry 里已有一个 `retiring?: string` 字段 —— 但它是**可选**的,语义是「这个 flag 正在退役中」
  (148 个里只有 9 个填了),**不是**出生时声明的死期。语义不同,不能直接复用,但可以合并进新设计。
