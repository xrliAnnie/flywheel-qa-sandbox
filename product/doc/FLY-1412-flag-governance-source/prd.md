## 0. 一句话

**每周扫描一次**:一个开关**在同一个状态待满【一周】**(值一直没变),就**摆出来问 Annie**「这个还要留着吗」——

> ⚠️ **这是 Annie 2026-07-23 裁决后的骨架**。她砍掉了原设计的「创建时必须填退役条件 + CI 挡」——

### 5.2 `longTermKeep` 的语义(Annie 裁决后:状态位,不是必答格)

**旧设计**(已删):每个新 flag 建的时候**必须**显式答 `longTermKeep`,不答 CI 挡、建不出来。
**新设计**(Annie 裁决):

```
longTermKeep 是一个【状态位】,由【扫描问她、她答『留』】时系统写入:
  · 她答「留」 → 写 longTermKeep = true + 一句 keepReason,之后扫描不再问它
  · 她答「清」 → 进清理单(§5.4)
  · 从没被问过 / 还没定 → 字段缺失,合法
```

**没有创建时的【退役申报】强制。**(登记强制那道 CI 与本字段无关,照旧,§1.3。)`longTermKeep` 的意图不再「预先申报」,而是「事到临头由她的回答记录下来」。

> ⛔ **原 §5.2「自动推断 flag 生命周期」的那整场辩论,在没有创建时申报之后已无意义** ——
> 但它挖出来的那个洞仍然是对的、值得记:**`category` / `polarity` 说的是「这开关是什么、谁能翻」,不是「它该活多久」**
> (反例:`watchdog_blocked` 注释写着 Annie 裁定长期保留;merge/ship/QA killswitch 都是长期安全门;
> `founder_ux_gate_killswitch` 归类 governance_gate 却正在 RETIRE 一道 gate)。
> **所以扫描也绝不会拿类型替她判「该不该清」—— 只按『值多久没变』摆出来问她,判断权永远在她。**

| **`value_last_changed`** | **不手写;来自「有效值变迁」记录** | ⭐ **每周扫描的判据就是它**。⚠️ **1150 当前 DDL 里没有这一列**;产出方 = **OQ-9 未定**。本单不实现。见 §5.3 |
| 行来源(**git 派生**,不加字段) | **不手写、也不填** | **责任链**用(清理单链回来源单)。**OQ-4 已决:git 派生,不引入 `sinceIssue` 字段** —— 靠人填会填错且无人发现;git 派生可重算、可审计、错了能重跑 |

#### ⭐⭐ 两个时间戳量的不是同一件事,必须拆开(v15 修正 —— 这是个概念错)

**曾经共用 `last_updated_at` 一个词,那是错的**,照那个写法实现 B3,做出来的**不是 Annie 要的那条规则**:

| 名字 | 量的是什么 | 谁用 | 住哪 |
|---|---|---|---|
| **`value_last_changed`** | **这个开关的【值】上次什么时候变的**(开↔关) | **每周扫描的判据**(§5.4) | **FLY-1150 的表**;本单不实现 |
| **git 派生的行来源** | **registry 那一行**的来源 / 最后编辑 | **责任链** —— 清理单链回来源单、有人认领 | git 历史(**不加字段**) |

**为什么不能混用**(两个真实会发生的错法):
- 有人改了那一行的**注释** → 行的时间戳变了,**值一点没动** → 把一个该问的 flag 重置成「刚动过」→ **漏问**;
- 有人在生产里把值从开翻成关 → **值变了,registry 那一行一个字没改** → 行的时间戳纹丝不动 → **该重新计时却没重新计时**。

Annie 的原话量的明确是**值**:「一个 flag 在**同一个状态**保持了两周」,并举例「**比如说打开、关闭**」。

**推论:「值上次什么时候变的」这个事实今天哪儿都没有。** 我逐条核过:
- 生产 `.env` **不在仓里**(`git ls-files` 无此文件)→ 没有任何 git 历史记录值的变化;
- 代码里**没有任何** value-change 账本(`changed_at` / `feature_flag_changelog` 只存在于 FLY-1091 的设计里,未实现);
- `registry.ts` 自己的头注就写着它是 **CATALOG + declaration**,**effective value 由 `resolve.ts` 从 process.env + per-project config 算**。

→ **所以 B3 硬依赖 FLY-1150** —— 但依赖的是**它建起来的那套值存储与解析边界**,
**不是**「它已经提供了 `value_last_changed` 这一列」(它没有)。**产出方未定 = OQ-9**(甲:写进 FLY-1150 的产出契约 / 乙:本单下游自己在解析边界记)。⚠️ **别写成「1150 已经提供了它」—— 1150 当前 DDL 里没有这一列。**

#### ⚠️ 「依赖是真的」≠「1150 已经承诺产出它」(Codex code review R1 HIGH-1)

**我核过 FLY-1150 当前的权威 scope(= 已合库的 FLY-1091 动态 store PRD,PR #533),它没有承诺这个字段**:
- `feature_flags` 表主键是 **`(scope_kind, project, flag_name)`** 组合键,列里只有 **`updated_at`** ——
  **没有稳定 UUID `id`、没有 `created_at`、也没有 `value_last_changed`**;
- 所以「1150 会给我 `value_last_changed`」这句**当前不成立** ——
  1150 完全可以**照它现在的验收做完**,而 B3 仍然没有那口时钟。

**但原料是有的**:`feature_flag_changelog` 表有 **`changed_at` / `action` / `from_raw` / `to_raw`**。
所以正确的写法不是「1150 提供这个字段」,而是**把产出合同写死**(见下方「在解析边界记录有效值变迁」):

**⚠️ 结论先说:这口时钟【不能】靠回放 changelog 重建。必须由「值被解析出来的那一层」直接记录。**

#### 为什么回放 changelog 不行(Codex R2+R3 逐层挖出来的,我逐条复核属实)

**1150 权威合同里的有效值链,比我先前写的多一层**:

```
project DB override  →  允许的 global DB override  →  【legacy project config / env】  →  registry code default
```

四条**可观测**的漏洞,只要少任何一条,时钟就会算错:

| # | 漏洞 | 后果 |
|---|---|---|
| 1 | **tombstone / 没有 DB 行时会刻意回落到 legacy config / env** | 那一层的变化**根本不产生 changelog 行** |
| 2 | **`shadow` epoch 里 DB 写会产生 changelog 行,但 reader 仍然返回 legacy 值** | 「写进了 changelog」**不等于**「有效值变了」→ 会被一个**从未影响过运行时**的事件推迟提问 |
| 3 | **1150 是 per-flag 走 `shadow → global-compatible → project-capable`** | **同一行 changelog,在不同 epoch 下权威性不同** —— 回放时无法只看行本身判断它当时算不算数 |
| 4 | **registry code default 的变更根本不是 changelog 事件** | 本仓就有实例:commit **`740c90ee`** 把 `founder_ux_gate.mode` 的 default 从 `"off"` 改成 `"enforce"` —— 对任何没有更高层 override 的 project,**这是一次真实的有效值变更**,而事件回放**看不见它** |

→ **所以「写路径已进 changelog」这个 readiness 判据是不够的**(那是我上一版写的,不成立):
一个 flag 可以**有** changelog 行而有效读仍走 legacy;一个已迁移的 flag 在 CLEAR 之后
**仍会暴露一个没被记账的 legacy / default 值**。

#### 正确的形态:在解析边界记录「有效值变迁」

不要试图从 override 行**重建**有效值。要求**产出方在值被解析出来的那一层(reader / cutover 边界)
直接记录一条「有效值变迁」**:

```
effective_transition(flag, project) 记录:
    when   = 变迁发生时刻
    from   = 变迁前的【类型化有效值】
    to     = 变迁后的【类型化有效值】
  —— 只要 from ≠ to 就记一条,不管这次变化来自 project override / global override /
     legacy config / env / registry default / cutover epoch 切换。

value_last_changed(flag, project) := 最后一条 effective_transition 的 when
```

**这样四个漏洞一次性全堵**:它记的是**被观测到的值**,而不是**某一层的意图**。

#### ⛔ readiness:凑不齐就判「无时钟」,不许估

> **只有当一个 flag 的【全部】有效值来源都被记账(或可证明不可变)时,它才有可信的时钟。**
> **否则一律判「无时钟」** —— **不进候选**,但**必须在报告里单列一节「无时钟(来源未全覆盖)」**。

**绝不允许**「大部分来源有记账,那就先按这个算」—— 那正是会让 B3 **过早去问**
或**该问却不问**的那种「差不多」。宁可显式说「这个我算不出来」。

#### 候选的单位(⚠️ 这条在 v19 重写时被我误删,现补回)

时钟天然是 `(flag, project)` 粒度的,而 1150 明确允许**每个 project 有不同的有效值**。

> **本单定:候选单位 = flag。一个 flag 够资格被问,当且仅当它在【所有活跃 project 上】
> 的最近一次有效值变更都已满 **1 周**(出厂 7 天,可配)**(即取各 project 的 `value_last_changed` 里**最新**的那个来比)。

理由:任何一个 project 上刚动过,就说明这个开关**还在被用**,这时候去问她是打扰。

##### ⚠️ 「无主」不是 fail-closed 的理由(Codex R1 HIGH-3,单值化)

早先版本同时写了两条相反的话:一边说无主 flag 要**显式列出来**,一边说「来源未知 → **fail-closed 不建单**」。
**照后者做,恰恰会把最该清的那批永久饿死。** 现在单值化:

| 情形 | 行为 |
|---|---|
| **合法地查不到来源**(无标记直提 / 应急 wip —— 实测 7/40) | ✅ **照常进本周批量单**,放在「**无主 flag(来源不可考)**」一节;**不指派、但绝不隐藏** |
| **查询动作本身失败**(git 跑不了 / Linear 拿不到 / 解析器崩) | ⛔ **fail-closed**:不产出一份可能残缺的报告,**告警**并保留上周状态 |

**区别是**:前者是**一个确定的结果**(「确实没有来源」),后者是**没有结果**(「我没查成」)。
fail-closed 只用于后者。

→ Piranha 那条「必须有人认领否则机制空转」的教训,用
**「能归户的自动归户 + 归不了户的显式暴露」**满足:**责任链没断**,
只是断链的责任归到「**清理它**」,而不是「猜个人名」。

### 5.4 出口:每周扫描 → 一张批量清理单

**参考系 = Uber Piranha**(research §2):周跑 → 查陈旧 flag → 自动生成删除 diff → 指派给作者 → 外加提醒机器人;清掉约 2000 个 flag。

> **摆出来按数量收敛成一张批量单;执行时按【动作性质】拆,不按数量拆。**

| 决定 | 取值 | 理由 |
|---|---|---|
| 触发 | **每周扫描**(不是 per-flag 到期日) | Annie 砍掉了枚举和日期 |
| **摆出来**的粒度 | **一张批量单** | 一 flag 一单会淹掉 Linear(实测 ~37.5 个/周),Annie 对噪音有红线 |
| **执行**的粒度 | **按风险拆**(见下) | 我们自己的先例本来就是按风险分的,不是按数量分的 |

#### ⭐ 明文规则:执行单按【动作性质】拆(OQ-8 定论,别只写「批量」)

| 动作性质 | 怎么拆 | 先例 |

| **机械、可逆** —— bake in 成默认 / 退休 flag,**逻辑仍留在代码里** | **继续批量**,一张单处理一批 | **FLY-1243**(一张单批量处理 11 个) |
