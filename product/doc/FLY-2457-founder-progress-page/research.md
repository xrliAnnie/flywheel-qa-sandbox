## 2. 「一句人话」到底是不是机器算不出来的(✅ 逐格核过)

把手写页里 14 条「↳ 现在到哪了」拆开,看每一条的成分:

| 成分 | 例子 | 机器有没有 | 出处 |
|---|---|---|---|
| 工作流走到哪一步 | 「设计中」「实现完」 | ✅ 有 | `run.current_node_label`,唯一来源 `workflow-display-labels.ts` ✅ |
| 卡在什么上 | 「等 CI」「等 #1126 合入」 | 半 —— 有 `run_held` / `question_pending` / `land.current_step`,**没有「等哪个 PR」** | `stuck_items` + `land` ✅ |
| PR / commit 指针 | 「终审 APPROVED @ ec9d75e72」 | ✅ 有 PR 号与落地状态;❌ 没有评审结论 | `land` ✅ |
| 依赖谁 | 「等 2445 定下接口」 | ✅ 有 `blocked_by`(读 Linear `inverseRelations`) | `model.ts` BlockedByValue ✅ |
| **给她的指示** | 「卡先别按」「旧卡别按」「新卡我 @ 你」 | ❌ **完全没有** | 只在 Lead 脑子里 |

⇒ **一句人话 ≈ 70% 机器已有 + 30% 只有人有**。这 30% 正是 issue 正文点名要 PRD 列的「要新增的字段」。

| 信号 | 机器来源 | 够不够直接印到页面上 |

| 有一道门开着等她 | `workflow_gate_holder` / `founder_review` 未决 → `waiting_founder` 信号 | 够 —— 但要翻成「你去 thread 里回一句 approve」 |

| ship 卡在她手里 | `land_operation` 状态 + `approve_to_ship` 门 | 够 |

⇒ 🔶 「等我」应当分两类:**机器测得到的门**(自动上榜,自动下榜)与 **Lead 手挂的一句话**(人写、人撤)。两类同区显示但**标记来源不同** —— 她要能一眼看出「这条是系统在等我」还是「这是 Lead 在问我」。

| 候选 | 可行性 | 代价 |

🔶 **本单倾向第三条**,理由三点:① 已有同构先例(依赖账本),不是新机制;② 判断天然带「谁写的、什么时候写的」,满足「不许有只存在于页面里的事实」;③ 她的分组决定(现在做/以后/不要)也能进同一张表 —— 见 §4.1,**她的决定今天正在丢**,这是比页面更早的漏。

### 4.1 她的 14 个决定 vs Linear 现状(✅ 本单亲手查 Linear API,as-of 2026-09-09T04:40:12Z)

| 她拍的 | 个数 | 现在 Linear 的状态 | 对得上? |
|---|---|---|---|
| 现在做 | 2 | FLY-2441 / FLY-2355 均 In Progress | ✅ |
| 以后 | 6 | 1954 / 1451 Backlog · 2072 / 648 Done · **2309 / 1143 In Progress** | ❌ |
| 不要 | 5 | 32 / 542 Canceled · 1251 / 908 Done · **555 Backlog** | ❌ |

📌 **本单最硬的一条证据**:机制页今天列的 5 个 active 父单 = 2441 / 2369 / 2355 / **2309 / 1143**,其中后两个正是她说过「以后」的。
⇒ 她的决定与 Linear 的 `state` 是**两条轴**,今天被硬塞进同一个字段:
- 「以后」与「从没拍过」在库里同形(都 Backlog),**不可区分**;
- 「不要」的 FLY-555 至今 Backlog,**没人去关**;
- 「以后」的 2072 / 648 是 Done 状态 —— Epic 关了但仍有剩活,`scope.v1` 反而**整个看不见**。

⇒ 修正一条更早的表述:并非「她的决定完全没落地」——「不要」有 3/5 落成了 Canceled/Done,「现在做」2/2 落成了 In Progress。**准确的说法是:决定与状态被压进一个字段,压不下的部分在静默丢失。** 排序与判断理由则是完全没有落点。

⇒ 这把 O3 需要的新字段收窄了:不是「重造一套决定系统」,而是补 **① 决定(尤其区分「以后」与「没拍过」)② 排序 ③ 判断/要她做什么** 三格,并让页面能自己报「你的决定和库里对不上」。
