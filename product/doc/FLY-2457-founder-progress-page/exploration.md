## 2. 今天并存的两页,各自是什么(✅ 逐个核过)

### 2.1 机制自动页(引擎生成)

- 入口:`flywheel-comm epic-page status|generate|show|render`(`packages/flywheel-comm/src/commands/epic-page.ts` ✅),生成器在 `packages/teamlead/src/epic-page/`(11 个文件 4170 行 ✅)。
- 地址:**固定的**。`StateStore.reserveEpicPageToken()`(`StateStore.ts:10055-10079` ✅)对同一 project 复用同一 token ⇒ `https://fw-reports-a53de2.vercel.app/r/839a63…/` 每次刷新原地重传,**不换链接**。
  📌 这条推翻了「托管报告只能是一次性快照」的直觉 —— 一页固定地址在机制侧**已经成立**。
- 活性:事件 + 巡检双路刷新(FLY-2143),每格带 `observed_at`,页头带 `generated_at` + 「你打开时它已 N 分钟旧」。
- 范围规则 `scope.v1`:`root_state_type=started` + 排除 `日常` 筐 + 排除 `backlog` 子单。今天实测 = **5 个 active 父单 / 17 张子单**(✅ 2026-09-09T04:28Z 抓的页面字节)。
- 机器已经知道的东西(`epic-page/model.ts` ✅):`ready_items`(现在就能开工的)、`stuck_items`(卡住的,带 `declared_blocked / runner_stopped / question_pending / run_held`)、`waiting_founder` 信号、`founder_items`(靠 Linear `founder-review` 标签 —— `rules.ts:3` ✅)、`dependency_review`(依赖减法/环/全堵)、`land`(PR 号 + 落地状态)、`run.current_node_label`(设计/实现/QA 的中文标签)、`gaps`(哪格缺了、为什么缺)。
- **它今天为什么不能给她看**(✅ 抓页面实读):
  1. **没有层级** —— `items[]` 是**平铺**的 17 张卡,Epic 只在页头 `header.roots` 出现一次。正是她否掉的第 3 版的病。
  2. **说机器话** —— 页面上直接印 `{"root_state_type":"started",...}` 原始 JSON、`scope.v1` / `ready.v1` 规则号、`observed_at` RFC3339 时间戳。
  3. **只读** —— 没有留言框,没有「复制给 Lead」。
  4. **没有判断** —— 它能说「2444 在 In Progress、卡在 question_pending」,说不出「2444 在返工,卡先别按」。

### 2.2 Lead 手写计划页(Tadashi 维护)

- 地址 `https://triage-flywheel-plan.vercel.app`,固定;内容手写,一次一版。
- 它比机制页多的东西(✅ 读 `artifacts/flywheel-epic-plan-20260909.html` 与 `epic-review.html` 的正文):
  1. **她的决定分组**:现在做 2 / 以后 6 / 不要 5 / 容器 1 —— 这是**她拍的**,Linear 里没有这个字段。
  2. **排序 + 为什么排第 N**:「所有别的都建在它上面,它不收,2447/2448 都没落点」。
  3. **每张子单一句「↳ 现在到哪了」**:「两轮返工落地、合 main、终审 APPROVED @ ec9d75e72;等 QA 复验打包形态 → 新卡我 @ 你(旧卡别按)」。机器给得出 `run_held`,给不出这句。
  4. **「还等你一个字」**:今天手写的是「2107 返工体『换体』」。
  5. **Epic 外的散单**:529 房台架线四张、2452 切号器 —— 它们没有 Epic parent,机制页的 `scope.v1` 直接看不见。
- 代价:**手写 = 会过期、会和 Linear 不一致、只有 Tadashi 在时才有**。她今晚看到的「In Progress」有一批是旧读数(页面自己写了「昨晚 12:5x PT 拉取 + 今晚变化叠加」)。

## 3. 本单真正要判的东西(主题树)

```
一页 founder 进度页
├── T1 层级与默认视图     —— Epic 卡 / 子单折叠 / 分组与排序 / 手机可读
├── T2 「到哪了」怎么写   —— 机器算的状态 vs 人写的一句话,谁盖谁
├── T3 「等我」怎么呈现   —— 从 waiting_founder 信号 → 一条「你按一下」的动作
├── T4 反馈怎么回来       —— 留言框 + 一键复制(现有做法) vs 更省事的路
├── T5 数据源与新增字段   —— 生成器 / Lead 手写 / 两者合流;新字段落在哪个唯一真相里
└── T6 范围与替换         —— 一页替两页怎么落地;Epic 外散单、以后/不要的 Epic 放哪
```

**T5 是本单唯一的硬问题**,也是 issue 正文点名要 PRD 回答的那条。它的形状是:

> 「Lead 判断 / 优先级 / 等 founder 的动作」这三样,**今天只存在于 Tadashi 的脑子和手写 HTML 里**。要么给它们一个机器能读的家,要么这一页永远只能半自动。

三个候选(PRD 里展开):
- **O1 全机器**:只显示机器算得出的,放弃「一句人话」。→ 退回她已经否掉的第 3 版观感。
- **O2 全手写**:Lead 每次重写整页。→ 就是今天,会过期、依赖人在。
- **O3 合流** 🔶(本单倾向):**骨架和状态归机器,判断归 Lead**;Lead 用一条 CLI 把「判断 / 排序 / 等你什么」写进一个账本,生成器把它渲染到对应的 Epic 卡上,每格照旧带出处和时间(判断格的出处 = 「Tadashi 于 X 时写」)。她一眼能分清哪句是机器测的、哪句是人说的。

## 4. 我此刻的假设(要她确认或推翻)

1. 🔶 她要的「一页」= **一个固定链接**,想看就打开,不是每次等人发。(机制页已具备固定链接 ✅)
2. 🔶 「哪些 Epic 在做」的默认范围 = 她拍过「现在做」的那些,不是 Linear 的 `In Progress` 全集。⇒ 需要一个存她决定的地方(T5)。
3. 🔶 「以后 / 不要」的 Epic 不进这一页的默认视图,但要能一键看到 —— 且页面要能报「你的决定和库里对不上」(research §4.1 ✅ 实测:她说「以后」的 2309/1143 今天正被机制页当成「在做」印出来;她说「不要」的 555 还活着)。
4. 🔶 手机上默认只渲染 Epic 卡 + 状态点 + 「等你」计数,子单一律折叠。
5. ⬜ 她愿不愿意在这一页上**直接改决定**(像 epic-review 页那样点「改成:以后」),还是这一页只读、决定另开评审页。
