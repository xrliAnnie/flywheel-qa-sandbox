⭐ 你的疑问(原样)
「我们做这么多 DAG / multi-agent 编排,会不会是过度设计 —— 到时候一个足够强的单 agent 就把活全干完了,根本不需要?」
本页收集业界(研究 + 头部实践者 + 产品)对「multi-agent 编排会不会被单 agent 取代」的多方视角,拿来验证/挑战我们已有的「拐杖 vs 地基」判断,决定权还是你 + HL 的。

① 业界不是「二选一」,是三种声音在吵(摆事实,不调和)

DR 的结论(Bottom line,逐字全文):「The strongest public evidence from 2024 to July 13, 2026 points to a hybrid outcome, not a winner-take-all one. As frontier models improved, a lot of orchestration that used to exist mainly to make weaker models usable started getting absorbed into stronger single-agent runtimes: larger context windows, better native tool use, better planning, longer autonomous loops, compaction, notes/memory, and built-in subagents-as-tools all reduce the need for brittle, hand-authored step-by-step DAGs. At the same time, the orchestration that remains important is increasingly about control, not cognition: independent review, security boundaries, approval gates, parallel throughput, model routing, persistence, observability, and organizational interoperability. Anthropic, OpenAI, Google, Microsoft, LangChain, and Cognition all now publish systems that reflect some version of that split, even when their rhetoric differs.」

派一:编排/多-agent 是持久架构

Anthropic(多-agent research 系统):lead agent 并行 spawn 3-5 个 subagent、各自干净上下文当「智能过滤器」,复杂研究省时最多 90%。anthropic.com/engineering/multi-agent-research-system

论据:模型再强,单线程也快不过 N 个并行;subagent 各自隔离上下文能隔噪声。—— 但注意:这是把编排用在并行广度 + 上下文隔离,不是给弱模型切步。

派二:别搭多-agent,一个精干 agent 自己扛

Cognition(Walden Yan《Don't Build Multi-Agents》):默认单线程线性 agent,多-agent 要过很高的门才用。cognition.ai/blog/dont-build-multi-agents

论据(逐字):「Actions carry implicit decisions, and conflicting decisions carry bad results.」把上下文拆给不共享全貌的子 agent,各自局部决策 → 冲突 → 坏结果。「Context Engineering」= 工程师第一要务。⚠️ 它反的是拆认知线程,不是反所有编排。Pi Agent(pi.dev,§4.5)是这派的活样本。

派三:用能过 eval 的最简形态,编排按需加(官方 playbook)

Anthropic《Building Effective Agents》:分 workflow(走预定义代码路径 = DAG)vs agent(模型自主导流程)。anthropic.com/engineering/building-effective-agents · LangChain / Harrison Chase:难点是「每步给 LLM 对的 context」,单 agent 扛不住复杂指令时才多 agent。langchain.com/blog/how-to-think-about-agent-frameworks

论据:「用能过 eval 的最简模式 —— 常常是一个 workflow 甚至一个配好工具的 LLM 调用」;能 hardcode 路径就别上 agent。→ 编排是按任务复杂度加的工具,不是默认。

同一个 Anthropic、两篇看似打架:《Building Effective Agents》劝你用最简、《multi-agent research system》又秀并行 subagent 大赢 —— 不矛盾,因为用途不同:前者反「无脑加编排」,后者是「并行广度」这类编排的正例。这正是我们要分辨的:为什么加编排比「加不加」更重要。

② 哪些编排正在被强单-agent「吸收」掉(验证「拐杖」侧)

DR 与官方博客一致:随模型变强,下面这些能力让「把整块活切成一步步喂」的手写死步骤 DAG 变多余 ——

  • 更长 context window —— 不必再把活切碎来塞进小窗口。
  • 原生 tool use + 更好的 planning —— 模型自己会规划、调工具,不用外部脚手架一步步替它导。
  • 更长的自主循环(autonomous loops) —— 一个 agent 能连续跑很多步不掉线。
  • compaction + notes/memory —— 上下文自己压缩、记笔记,不用外部编排管记忆。
  • subagents-as-tools —— 连「子 agent」都退化成一个工具调用,编排从架构降级成一个 function call。
对照我们的尺子(开放问题,不替你判):DR 的原话是更强 runtime「reduce the need for brittle, hand-authored step-by-step DAGs」。那我们的三段式(design→implement→QA)死步骤,有多少属于这半、模型变强就该按需化?判据(供你用):「就算 agent 聪明 10 倍,这步还需要吗?不需要 = 拐杖。」—— 这道题留给你,下面留言。

③ 哪些编排「agent 越强越重要」(验证「地基」侧)

DR 的原话把它总结成一句:留下的编排越来越是关于 control, not cognition(控制,不是思考)。清单几乎和你的「地基」定义逐字重合 ——

  • 独立评审 / 交叉检查(reviewer ≠ doer) —— 自己审自己 = 假审,再聪明也有盲区。
  • 安全边界(security boundaries) —— 谁能碰什么。(审计/留痕是我们自己的关切词;DR 清单里对得上的是 security boundaries / observability / persistence。)
  • 对不可逆动作的批准闸(approval gates) —— 人对 ship / merge / 删数据的最终控制。
  • 并行吞吐(parallel throughput) —— 多个一起跑,快。
  • 模型路由 / 持久化 / 可观测(model routing / persistence / observability)。
  • 组织 / 信任边界 + 互操作(organizational interoperability,跨 agent / 跨组织)。
对照我们的尺子(开放问题,不替你判):业界的说法是这些「control」类不因模型变强而消失,反而 agent 越强越自治越快、越需要独立一层来约束/验证/留人对不可逆动作的控制 —— 这正对上你说的「信任地基」(ship 闸 / founder 批准 FLY-1211 是活例子)。按你的判据「聪明 10 倍也依然需要 = 护城河」,你读这份清单算不算护城河?有没有例外?下面留言。

④ 你的「拐杖 vs 地基」框架:业界证据说它对不对?

文字上高度重合(这是事实;要不要读成「印证」由你判):DR 独立得出的分界线 =「control not cognition」,和你的「拐杖(为弱模型切步→会消)vs 地基(为独立/安全/人控→会长)」在措辞上高度重合;DR 的落点也是 hybrid(非「单 agent 取代一切」、也非「编排永恒」)。—— 但这是「业界的线碰巧和你的线对齐」,不等于「你的框架被盖章正确」。要不要把它当印证,是你的判断。

可能过简的地方(业界还有二分没覆盖的第三类):

  • 并行吞吐 / 规模 —— Anthropic 多-agent research 省 90% 时间。这既不是「给弱模型打拐杖」,也不纯是「信任/控制」,是scale。模型再强,单线程也快不过 N 个并行。
  • 上下文完整性 / 认知不分裂 —— Cognition 的反面论:拆认知线程会坏事,所以「留一个不分裂的 doer」本身是设计约束。
  • 专业化 / 上下文隔离 —— subagent 各自干净上下文隔噪声,不是因为模型弱。
一个更锋利的角度(我们从 Pi 案例提出的推断,见 §4.5;当工具用,不替你定):决定「拐杖 vs 地基」的,也许往往不是功能本身,而是「人还在不在回路里」。同一个「批准闸」,在有人在旁的本地工具里也许能砍,在人稀缺的自治 fleet 里可能更像地基 —— 这个角度你认不认?
✍️ 「拐杖 vs 地基」两分,你想不想加第三类(并行/规模、上下文完整性)?还是保持两分、把它们塞进「地基」里就行?

④.5 现实测试:Pi Agent 主动砍编排,留下什么、丢了什么、代价是什么

Pi Agent(pi.dev,作者 Mario Zechner / libGDX 之父),就是 OpenClaw 里那个 minimal agent。起因:Claude Code 功能越堆越多、行为变得不可预测 → 决定「尽量少加功能」。mariozechner.at/posts/2025-11-30-pi-coding-agent · lucumr.pocoo.org/2026/1/31/pi

它砍了什么(赌是拐杖):sub-agents(「a black box within a black box」)、plan mode、MCP、内置 todos、后台 bash、大 system prompt(它的 prompt+工具定义合计 <1000 token)。核心就 4 个工具:read / write / edit / bash。理由(原话):「All the frontier models have been RL-trained up the wazoo, so they inherently understand what a coding agent is. There does not appear to be a need for 10,000 tokens of system prompt.」

它也砍了一项「地基」——批准闸:「full YOLO mode」,无权限检查;理由:他把前置权限检查看成 security theater(安全剧场) —— 一旦 read/execute/network 共存,前置闸挡不住 exfiltration(此处为转述,非逐字引用)。他在这段只明确建议「不放心就跑在容器里(run inside a container)」;此外还有全透明可观测、可读 session 文件事后审(出现在别的语境)。——把这几项合起来当「前置闸的替代」是我们的读法,不是 Pi 明说的(『人实时盯』更是我们对本地结对语境的推断)。

它保留 / 承认的代价:保留全上下文透明、自我扩展、session。承认「models are still poor at finding all the context needed」(砍掉脚手架后模型漏读上下文的问题裸露)。而且 review(/review)和多-agent(/control)它做成按需 opt-in 扩展,不内建。

一种读法(我们的,供你判、不替你定):Pi 是本地结对工具(人就在旁边)——这可能是它敢砍闸的语境之一;我们更像「人注意力稀缺的自治 fleet」。如果把「人还在不在回路里」当判据,那同一个批准闸在 Pi 可砍、在我们这儿会更像地基 —— 这道分辨题留给你。另一个可讨论的共通做法:「不内建、按需 opt-in、且可见」(把 review/orchestration 做成显式扩展而非黑箱),你觉得值不值得借?
一道更锋利的测试(当工具用,不替你下结论):别问「这个编排需不需要」,问 「如果砍掉它,得靠什么替代 —— 而我们有没有那个替代品?」
套到批准闸:Pi 砍它后,相关做法是容器隔离 + 全透明 + 可读文件事后审(把这几项合起来当「替代」是我们的读法;它是本地结对、人在旁,『实时盯』也是我们的推断)。那我们呢?—— 我们是自治 fleet,这类「有人在看 / 能事后审」的替代品我们有没有、够不够?这正是要你判的。关键 nuance:Pi 砍它对不对,取决于它有没有替代;所以就算 Pi 砍得对,也不自动等于我们该砍 —— 别读成「看 Pi 都砍了、我们也该砍」。Pi 不是「反例证明我们过度设计」,而是「同一批控制在不同语境命运不同」的活证。这道测试,下面 §5 逐块量四个程序时都好使。
