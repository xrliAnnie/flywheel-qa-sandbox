2核心:为什么这不是 RAG

  
他一开篇就把它和 RAG 对立(引号=原文):

  
    
    
  • RAG(NotebookLM / ChatGPT 传文件):查的时候取相关片段拼答案 —— "the LLM is
      rediscovering knowledge from scratch on every question. There's no accumulation."
    • 
    
  • 他的做法:LLM "incrementally builds and maintains a persistent wiki" ——
      一堆结构化、互相链接的 markdown,夹在你和原始资料之间。新来一个源,LLM 不是只索引待查,
      而是读它、抽要点、整合进现有 wiki(更新实体页、修订综述、标出和旧结论矛盾的地方)。
    • 
    
  • 关键:"the wiki is a persistent, compounding artifact." 交叉引用已经在了、
      矛盾已经标了、综述已反映你读过的一切。每加一个源都让库更富,而不是每次从头重来。
    • 
  

  
他的类比"Obsidian is the IDE; the LLM is the
  programmer; the wiki is the codebase." —— 你选源、问问题;LLM 干所有 bookkeeping。

  
  





  
3三层架构

  

    
层是什么谁负责

    
Raw sources你精选的源(文章/论文/图/数据)。不可变,source of truth你选,LLM 只读

    
The wiki一堆 LLM 生成的 markdown:摘要页/实体页/概念页/对比/综述"The LLM owns this layer entirely."

    
The schema一份 CLAUDE.md 或 AGENTS.md,写清 wiki 怎么组织、各操作走什么流程你和 LLM 共同演化

  

  
schema 是关键:"it's what makes the LLM a disciplined wiki maintainer rather than a
  generic chatbot." 一手已核

  
  





  
4三个操作 + 两个特殊文件

  
    
    
  • Ingest(喂源):丢进 raw → LLM 读 → 和你讨论要点 → 写摘要页 → 更新 index →
      更新相关实体/概念页 → 追加 log。"A single source might touch 10-15 wiki pages."
    • 
    
  • Query(问):LLM 搜相关页 → 综合 + 引用。答案可是页/对比表/幻灯/图表。关键:
      "good answers can be filed back into the wiki as new pages." —— 你的探索也 compound 进库。
    • 
    
  • Lint(体检):定期让 LLM 找矛盾、过时断言、孤儿页、缺失交叉引用、可补的数据缺口。
    • 
  

  
    
    
  • index.md:全库目录(每页一链+一行摘要),答问题先读它再钻。他说这在 ~100 源、
      数百页的规模「surprisingly well」,不需要向量 RAG 基建。
    • 
    
  • log.md:append-only 时间线,前缀统一就能 grep "^## \[" log.md | tail -5。
    • 
  

  
  





  
5工具与技巧(他 gist 里点名的)

  
    
    
  • Obsidian Web Clipper:浏览器扩展,把网页转 markdown 进 raw。
    • 
    
  • 图片本地化:Obsidian 里设固定附件目录 + 绑热键一键下图。诚实局限:LLM 一次
      读不了内联图,得先读文字再单独看图 —— 他原话 "a bit clunky but works well enough."
    • 
    
  • Obsidian graph view 看库形状;Marp 出幻灯;Dataview 按 frontmatter 生成动态表。
    • 
    
  • wiki 就是个 git repo —— 白拿版本历史/分支/协作。
    • 
    
  • 规模大了要真搜索:推荐 qmd(本地 markdown 搜索,BM25+向量+LLM 重排,有 CLI 也有 MCP)。
    • 
  

  
  





  
6为什么这套行得通

  
"The tedious part of maintaining a knowledge base is not the reading or the thinking —
  it's the bookkeeping." 人放弃 wiki 是因为维护负担涨得比价值快;LLM 不会腻、不会
  忘更新交叉引用、一次能改 15 个文件 —— 维护成本≈0,库就一直活着。

  
思想血缘:Vannevar Bush 的 Memex(1945) —— 私人、主动策展、文档间关联和文档本身一样
  值钱。Bush 没解决"谁来维护";"The LLM handles that."

  
  





  
7通用做法全景(不只 Karpathy)

  

    
路线代表检索特点 / 局限

    
RAG / 传即查NotebookLM、ChatGPT 传文件、向量库查时取 chunk上手快;不累积,每次从头拼

    
传统 PKM(人维护)Obsidian、Roam、Logseq、Zettelkasten、Second Brain/PARA人建互链+全文搜结构好;维护靠人,常烂尾

    
Agentic wiki(LLM 维护)Karpathy 的 LLM Wikiindex 优先,大了加语义搜累积+LLM 维护;新,吃 token,规模/新鲜度是开放问题

  

  
诚实的开放问题:①规模上限 UNKNOWN(~100 源够,再大要语义搜,
  成本曲线无公开定论);②token 成本明显(一次 ingest 触 10-15 页);③图片处理 clunky;④新鲜度靠
  定期 lint 兜,不是自动强一致。

  
  





  
8对照:我们已有 vs Karpathy 差距(理解用,不是 close 理由)

  

    
Karpathy 的环节Flywheel 最接近的东西差距/关系

    
raw → 持续编译成互链 wiki/compound→docs/solutions、文件式 MEMORY我们是离散手动沉淀,无 backlinks/lint/index/log 纪律

    
LLM 把零散输入结构化xiaohongshu-learning 闭环(它生成了 FLY-347)已在做,但产物是 Linear 草稿,不是 compounding wiki

    
个人研究主题库你的 Notion 第二大脑(FLY-510)另一种 substrate(Notion vs markdown+Obsidian+agent)

  

  
一句话:同向、精神相近,但我们没有那套「持续编译+互链+lint+index/log」的知识库形态;
  你个人层已有 Notion。要不要把它变成能力,你理解后再定。
