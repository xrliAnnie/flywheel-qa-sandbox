Flywheel 给 Agent 用的 compounding wiki


FLY-347 提案 v2 · 给 agent 参考,不是给人看 · 诚实评估值不值得(现有 memory 已经不错)




  
结论先给,不埋:Flywheel 不需要从头建 Karpathy 的 wiki —— 我们已经有它
  ~70% 的骨架(页 + 索引 + 互链)。真正缺的是他那条核心洞见:LLM 自己跑的『维护回路』。
  且这个缺口有真痛证据(~190 个记忆文件、~126 个
  feedback、索引只增不并 —— 库在慢慢『烂』)。所以提案 = 不建大 wiki,只补最有杠杆的一小块
  小 MVP:一个 agent 自跑的记忆 consolidation/Lint pass。Ingest/Query/语义搜索都留后。

  
  





  
1你的 reframe:给 agent 用,不是给人看

  
Karpathy 原版是人在环里(Obsidian 浏览、人策展)。你要的是去掉人这一环 ——
  读者是 agent,产物是 agent ingest/query 时参考的层。所以:

  
    
    
  • ❌ 不做任何人类 UI(不 Obsidian、不 Notion、不 graph、不幻灯)。
    • 
    
  • 存储 = 就是我们已有的 markdown 树 + agent 约定,给 agent 读写。
    • 
    
  • 成功标准 = agent recall 更准 / 更少重复,不是「人看着爽」。
    • 
  

  
  





  
2诚实的起点:我们已经有多少

  
我审计了本项目的 MEMORY,把它和 Karpathy 的要件逐条对:

  

    
Karpathy 的要件Flywheel 现状有没有

结论:我们不是从零,骨架在了。这也是为什么你说现有系统「用起来也还不错」—— 你是对的。

  
事实校正(会有人问『我们不是有 mem0 吗』):我们确实有 mem0 式的

  真缺,不是重复造 mem0 的轮子。

  
  





  
3缺的那层 + 回路具体怎么做

  
我们有「离散的页 + 索引 + 零散互链」。要补的,是在现有 markdown 记忆之上加一个
  agent 维护的『编译层』 —— 不建新存储,就是现有 markdown 树 + 一个维护 skill +
  index/schema 约定。这个编译层靠一个三段回路活着:

  

    
回路agent 具体做什么现状

    
Ingest(喂)读到新东西 → 写成互链的 wiki 页 + 补 [[链接]] + 更新 index;不仅新增,还修订相关页 + 标矛盾只「新增」,少「整合」

    
Query(查)答难题时先读编译好的 wiki / index,不翻 raw;综合结果可回填成新页索引注入✅;综合不回填

    
Lint(体检)定期 pass:去重、并重叠、消解矛盾、清过时、找孤儿链、瘦身索引 → 出可审 diff完全缺(=本 MVP)

  

  
三段是完整回路的描述(讲清整体长什么样);但 MVP 只做其中 Lint 那一段(见第 6 节 —
  因为 Ingest+index+互链我们已有 ~70%,先补最痛的 Lint)。

  
  





  
4为什么必须有 Lint(这段是你要我讲清的)

  
知识库越攒越大,会『烂』。攒到几百页时,自然长出三种病:

  
    
    
  • 重复:同一件事被写进好几页(我们现在 约 190 文件里,约 126 个 feedback_* + 一批 qa 明显有可并项)。
    • 
    
  • 矛盾:新证据推翻了旧断言,但旧页还在,两页打架,agent 读到哪页看运气。
    • 
    
  • 过时 & 孤儿:陈旧的页没人清、没有入链的页查不到 —— 占 context、拖准确率。
    • 
  

  
就像 lint 代码:代码不 lint 会烂(死代码、重复、不一致),所以我们跑 linter
  定期体检。知识库同理 —— Lint = 给记忆库跑的 linter:定期一个 pass 去重 / 消解矛盾 /
  清过时 / 标缺口,让库一直健康。Karpathy 的原话就是:维护(bookkeeping)才是人放弃 wiki 的
  真正原因,而 LLM 不会腻、不会忘 —— 所以这件事正好该交给 agent 定期做。

  
这也是为什么 MVP 选它:我们的库已经在『烂』的边缘(只增不并),Lint 是当下最痛、最该先补的一段。

  
  





  
5诚实评估:值不值得?(不硬吹)

  
反方(别做/现有够用):现有 recall 对 Lead/Runner 的活「够用」,你自己
  也这么说。全套 wiki(整合式 ingest + 综述页 + 语义搜索)是明显的 over-engineering 风险,
  正是 FLY-212「做完 PR+QA 才发现没戳心坎」的坑。token 成本也真。

  
正方(值得做的那一小块):唯一有真痛证据的缺口是 Lint/consolidation:
  约 190 文件、约 126 feedback、索引 20KB「只增不并」—— 正是他说的「维护是人放弃 wiki 的原因,而
  LLM 不会腻」。让 agent 定期并一次,低成本、对准已观测的痛、纯 agent-facing。

  
净判断:不建大 wiki,只做 Lint MVP。综述页 / query 回填 / 语义搜索 =
  明确「以后再说,MVP 证明价值后」,不塞进这版。

  
  





  
6小 MVP:Memory Consolidation/Lint pass

  
一个 agent 自跑、输出可审 diff、绝不自动删的维护 pass:

  
    
    
  • 输入:一个项目的 memory/(约 190 文件 + MEMORY.md)。
    • 
    
  • 去重/并项:找主题重叠的文件(多个 qa_*/feedback_* 讲同一事),提议 merge 成一页(留全来源要点)。
    • 
    
  • 标矛盾/陈旧:找互相打架或被新事件推翻的断言。
    • 
    
  • 孤儿 & 断链:找无入链的页 + 指向不存在页的 [[链接]]。
    • 
    
  • 索引瘦身:提议精简 MEMORY.md(它每次注入,越小越省 context)。
    • 
    
  • 输出:一份 consolidation 提案 diff + 理由 → 你/Lead review 后才落。可逆、不自动删。
    • 
  

  
成功 = 什么为真:跑一遍能 约 190→更少且不丢信息、索引更小、矛盾被标;用一阵后 recall 不降(最好升)。

  
不是什么:不是新数据库/向量 RAG/人类 UI/重写记忆系统 —— 就是跑在现有 markdown 记忆上的一个 pass。

  
  





  
7Scope 边界 / 非目标

  
    
    
  • ❌ 不做人类 UI(Obsidian/Notion/graph)。
    • 
    
  • ❌ 不重写 / 不替换现有 MEMORY —— 在它之上加一个维护 pass。
    • 
    
  • ❌ 不自动删记忆 —— 只出可审 diff。
    • 
    
  • ❌ 不上向量库/语义搜索(MVP index-first 够,他亲述 ~100 页 index 就够)。
    • 
  

  
留后(不在 MVP):完整 Ingest 整合(触多页)· 维护式综述页 · query 结果自动回填 · 大规模上 qmd 语义搜索。
