经验图谱 —— 我们具体怎么用、用在哪


FLY-347 单拎一片 · 灵感来自竞品 homerail · 聚焦『怎么应用』· 我不下结论,你 co-decide




  
这页只讲一件事:「经验图谱」这东西我们具体怎么用、用在哪 —— 每个 Runner 跑完
  自动抽出教训 → 存进我们的知识层 → 下次谁起活能查到相关的坑。我不下『要不要做』的结论,
  给你 2 个真实场景 + 跟现状的差距,你看完 co-decide 要不要真出 PRD 给 Tadashi。

  
  





  
1这东西是什么

  
来自 Annie 找到的竞品 homerail 的一个点子:自动从每次 run 抽出结构化教训 → 存成
  一张图 → 让 agent 查。翻译到我们:每个 Runner/Lead 干完一单活,系统自动把这单里
  「失败根因 / 教训 / 信号」抽出来,结构化存起来、互相链起来,下次有人干相关的活能查到。

  
它接得上我之前那份 agent-facing wiki 提案:那份讲的是「知识层长什么样(页+索引+互链
  +维护)」;经验图谱是往里灌『run 教训』这一类内容的自动管道 —— 具体、聚焦在 run 上。

  
  





  
2怎么用(3 步应用回路)

  

    ① 抽 run 跑完自动→
    ② 存 进知识层(结构化+互链)→
    ③ 查 下次起活时
  

  
    
    
  1. 抽(Runner 跑完自动触发):从这单 run 的 transcript / CI 结果 / code-review verdict /
      QA 结果 / retro 里,抽出结构化的 失败根因、教训、避坑信号(不靠人事后记得去写)。
    2. 
    
  2. 存(进我们的知识层):存成结构化条目,链到 这单 issue / 碰的子系统(如 Bridge、
      Discord、cmux) / 失败类型 / 相关的旧教训 —— 这就是「图」:教训之间、教训和子系统之间有边。
    3. 
    
  3. 查(下次 Runner/Lead 起活时):一上来先按这单要碰的子系统/任务类型查图,把相关
      历史教训注入 context,让它不用把老坑重踩一遍。
    4. 
  

  
  





  
3场景 A:Runner 要改 Bridge 重启逻辑 真实教训

  

    
没有经验图谱:新 Runner 起活改 Bridge restart,不知道历史上这块埋了哪些雷,很可能
    重踩 —— 杀错 PID、改配置顺序反了、和别的 agent 同时重启撞车。

    
有经验图谱:起活时按「子系统=Bridge/restart」查图,一上来就 surface:

    
query: 起活 · 子系统=Bridge restart → 相关教训· FLY-176: restart-services.sh:523 multi-line PID 没加引号 → kill 失败,得手动重启
· FLY-193 教训: 改 config 要在 kill Bridge 之前(launchd KeepAlive 会自动 respawn,先杀就用了旧 config)
· bridge_bootout_wrong_pid: launchd job PID ≠ 真 Bridge PID,bootout 会杀错进程
· coordinate_bridge_restarts: QA hot-deploy 时别让别的 agent 同时重启

    
这些全是我们自己踩过、已经写在记忆里的真教训 —— 经验图谱做的是让它们在对的时刻
    自动冒出来,而不是靠 Runner 恰好记得去翻。

  

  
  





  
4场景 B:QA Runner 起一个 Discord E2E 测试 真实教训

  

    
有经验图谱:QA Runner 起活时按「任务类型=Discord E2E」查图,surface:

    
query: 起活 · 任务=Discord E2E → 相关陷阱· thread_rename_ratelimit: Discord thread 改名硬限 2 次/10min/线程 → 每个场景用新线程
· 529_runner_injection_gotchas: chat-threads 要设 TEST_REPLY_BY_ISSUE=1 等 4 个坑
· urllib_user_agent_cloudflare_ban: 手写 urllib 直发不带 User-Agent → 被 Cloudflare 403

    
这些坑每一个都真的坑过我们、花过真调试时间。让新 QA Runner 一上来就拿到,而不是
    重新踩一遍 —— 这就是「经验图谱」最直接的价值。

  

  
  





  
5跟我们现状的差距(诚实)

  
诚实说:上面这些教训很多我们其实已经存了(记忆里有 约 126 个 feedback_* + 一批 qa 文件)。
  所以差距不在「有没有教训」,在怎么进、怎么出:

  

    
环节现状经验图谱加什么

    
进(抽+存)靠人事后记得手写进 MEMORY;很多 run 的教训蒸发了run 跑完自动抽,不靠人记得

    
结构零散 markdown 文件 + 手动 [[链接]]图:教训 ↔ 子系统 ↔ 失败类型,能按维度查

    
出(查)整份 MEMORY.md(20KB)每次注入,靠运气命中相关那条起活时按这单子系统/任务 targeted 查,只给相关的

    
底层mem0 MemoryService 代码在,但 pgvector 基本没接、主力人工 markdown—(可先不上向量,图+targeted 查已经是提升)
