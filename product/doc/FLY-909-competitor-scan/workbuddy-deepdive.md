## 一句话定位(verbatim)

> 【官方】**"Tencent WorkBuddy — an AI-native agent … your own AI teammate"**;腾讯云口径:**全场景职场 AI 智能体桌面工作台**,「用一句话描述需求 → 像同事一样自主规划、执行、交付**可验收**的结果」。
> 腾讯官宣战略:从「**服务开发者(CodeBuddy)**」向「**服务全职场人**」延伸 —— 继承 CodeBuddy 底层 agent 架构,把能力边界从「写代码」扩到「坐在电脑前能做的事都能帮你做」。
> 【媒体】TechNode / issue 定性:**"OpenClaw-like workplace AI agent"**。

## 目标用户(⭐ 关键 —— 官方比想象的更贴我们 beachhead)

- 【官方,全球页逐字】**"One-person company: Individual entrepreneurs, freelancers, small team leaders"**(一人公司 / 个体创业者 / 自由职业者 / 小团队负责人)+「Research content(市场调研/竞品分析/成稿)」+「Data insights(运营/客服/管理业务数据)」。
- 【评测/媒体】2026 上半年主力用户 = **HR / 行政 / 运营白领**;也覆盖企业客户 + 程序员(程序员那套走 CodeBuddy)。
- **诚实结论**:WorkBuddy **不是「只打公司里的白领」** —— 它官方就打**一人公司 / 自由职业者 / 小团队**,跟我们 beachhead(非技术 solo OPC operator)**正面重叠**。不能把它的目标用户当成「跟我们错开」。

## 产品形态(怎么用)

- 【官方/评测】**桌面 app + 多渠道 IM bot 双形态**:
  - **桌面端**直连本地机器读写本地文件(清 Excel、整理文件夹、从本地文档生成报告),**sandbox 隔离执行**(「no-setup sandboxed」,活跑在隔离环境里不碰系统其他部分)。
  - **IM 端**派活回报 —— 【官方全球页逐字,**9 个渠道**】**Slack / Telegram / Discord / WeChat Assistant Bot / Enterprise WeChat / QQ / Yuanbao Pai(元宝派)/ DingTalk / Feishu**。「这些渠道变成命令台:发一条高层指令 → 它后台跑完 workflow → **完成后回报**」。⚠️ 部分媒体/评测说「12+ 渠道」,**官方页只列 9 个**,取官方标差异。
- **官方列的使用场景(⭐ 正好撞我们 beachhead 的业务活)**【官方】:**电商选品 · 独立落地页生成 · IM/在线客服 · 网页内容合规 · 市场调研/竞品分析 · 报告成稿 · 会议纪要 · 数据/运营洞察**。← 非技术电商/social operator 天天要干的业务活,不是抽象办公。
- **持久性**:【官方】只证「**Personalized memory capability**(专业版)」= 一个记忆 feature;【评测,⚠️存疑】llm-agent.cc/aicost 说「持久 daemon、离开工位也在、跨 run 记忆」—— **官方不背书 daemon 说法**。诚实合并:**它有个性化记忆 + IM 后台派发/回报,但「常驻 daemon 组织」是评测口径、未经官方/一手证实。**

## 核心机制

- 【官方/评测】**多 agent 并行**(它的最大杀手锏):把大目标拆子任务**并行跑**(不是排队);**Expert Teams** = 一个 lead agent 协调多个 sub-agent(一个调研 / 一个写代码 / 一个写文档)。
- 【官方】**100+ 内置专家角色**:"covering all roles and scenarios including operations, design, **data, development**, etc." —— 注意 **development(开发)明确在专家角色里**,不是「完全不碰编程」(但代码深度弱、不主打,见软肋)。
- 【官方】**多模型**:「one-click switching between multiple models」+ **TokenHub** 统一管理 token 调用,接 **14 个顶级模型**(混元 / DeepSeek / GLM / Kimi / MiniMax… + BYOK)。
- MCP + 20+ skill:连 GitHub / GitLab / Jira / Confluence / Google Drive / Gmail / Notion / Slack。

## 公司背景 & 体量(决定威胁量级)

- 【媒体】2026-01 内测 → **2026-03-09 国内全量上线** → **2026-05-29 全球上线**(TechNode / Forbes)。上线前 2000+ 非技术员工(HR/行政/运营)测过。
- 【媒体/分析,⚠️非独立审计】上线 3 个月 **13M+ DAU**,行业第二名 **3-4 倍**;**DAU/MAU 65-75%**(粘性直逼 Slack);3 个月迭代 **43 个版本**;3 月环比 **831%**。腾讯口径「中国目前最常用效率 agent」;**Citi** 称「中国 AI agent 市场拐点」;**Forbes**「WorkBuddy 出海标志 AI agent 竞赛的一次反转」。**数字口径可信但未独立审计。**
- 有 **Enterprise Edition(6 月)「From Super Individuals to Super Teams」+ Agent Suite**(企业 AI team)。

## Onboarding

【官方/评测】**开箱即用(out-of-the-box / no-setup)** —— 免费档 + 全员 50GB 云存储先试核心能力,一句话描述需求就开跑;100+ 专家角色即「预配好的团队」,不用自己攒 prompt/skill。上手门槛低是它爆量的原因之一。

## 亮点 feature

1. **多 agent 并行拆解**(把一个大目标拆成子任务同步推进,不排队)。
2. **100+ 专家角色 = 现成的「虚拟团队」**(每个预装领域技能 + prompt 模板 + 方法论)。
3. **sandbox 隔离执行**(活跑在隔离环境,降低碰坏系统的风险 —— 对非技术尤其安心)。
4. **多模型 TokenHub**(一键切 14 个模型 + 统一 token 管理)。
5. **9 渠道 IM 派活 + 后台跑 + 回报**(手机上发指令、桌面上出活)。
6. **免费档 + 50GB 存储**的低门槛获客。

## 已知软肋(诚实 = 机会点,但别夸大)

1. 【评测】**复杂多步易错**(算错 / 内容错位,要用户自己核对);**error recovery ~3/5,活有时只干一半**。
2. 大文件吃力、跨 OS 兼容问题、上线初期服务器压力/崩溃。
3. **代码深度落后** Cursor / Claude Code(本就不主打编程)。
4. **红海、缺鲜明优势**:微软 Copilot(集成进 Windows)、字节豆包、金山/WPS AI(更深集成或更便宜)—— 评测直言 WorkBuddy「**缺乏鲜明竞争优势**」。
5. 生态偏腾讯:跟非腾讯 WPS/飞书/钉钉 兼容不足;行业垂直功能有限。
6. 企业落地阻力:本地文件操作的数据安全顾虑 + 审批慢 + 员工换工具阻力。

## 定价

(⚠️各源出入,取区间)个人 Lite 39 / Standard 99 / Pro 299 元/月;企业 Standard 99 / Premium 199 / Flagship 999 元/月,企业 SaaS 旗舰约 198 元/人/月。免费档 + 全员 50GB 云存储。订阅 + token 售卖变现。

## 腾讯三剑客分工辨析(关键 nuance —— 别把 WorkBuddy 当 OpenClaw fork)

【评测,多篇横评一致】腾讯「Claw/龙虾」矩阵里三个最相关:
- **CodeBuddy** = 给**程序员**的「对话即编程」全流程研发搭档(**造软件的那个**)。
- **WorkBuddy** = 办公室全能助理(重「深度」、多 agent 并行、含 development 角色**但不主打编程**)。
- **QClaw**(小龙虾 AI)= 腾讯电脑管家团队**基于 OpenClaw 开源框架**的微信直连本地 AI 遥控器(重「随时」、数据不出本地)。

→ **腾讯真正的 OpenClaw 衍生品是 QClaw,不是 WorkBuddy;WorkBuddy 是自研(继承 CodeBuddy 架构)。** 「OpenClaw-like」是形态类比,别当成 fork。

## 跟 Flywheel:像谁 / 不一样(这份深挖的重点)

### 像(为什么最该警惕 —— 而且比 Matrix/Cowork 更贴)

WorkBuddy 一次性覆盖了我们**一堆候选形态差异**,且比之前扫的任何一家都全:
- **组织形态**:lead agent 协调 sub-agent 团队(Expert Teams)+ 100+ 专家「当同事」—— 骨架跟 CoS→Lead→Runner 相邻。
- **手机 IM 驱动**:官方 9 个 IM 渠道(含微信/Discord)派活回报 —— 跟我们「手机原生 IM」界面赌注**正面撞**。
- **多模型/供应商中立**:一键切 14 个模型 + TokenHub —— 跟我们「架构上跨后端」**正面撞**。
- **done-for-you**:描述任务 → 它交付 —— 跟我们**一样**。
- **个性化记忆 + 后台派发回报**:跟我们「常驻 + 记忆」的**可感知那部分撞**(「持久 daemon 组织」官方未证,标⚠️)。
- **目标用户**:官方打**一人公司 / 自由职业者**,场景列电商选品/落地页/客服 —— **正面重叠我们 beachhead**。

> 结论:靠「AI 团队 / IM 界面 / 多模型 / done-for-you / 目标是一人公司」**都区分不开了**。真差异只能落到「**你做的活到底是不是长期拥有并演进一套软件/业务系统**」+「**是不是一个被协调、自己推 backlog、持续 own 的组织**」上,否则跟 WorkBuddy 在一句话定位上会撞脸。

### 不一样(逐轴诚实 · 哪几轴站得住 / 塌了)

| 轴 | WorkBuddy | Flywheel | 判定(诚实) |
|---|---|---|---|

### 大厂做办公 agent 对我们的威胁形态(founder 该看的)

**威胁为什么真:**
1. **量级碾压(分发,不是能力)**:早期团队(Matrix/Paperclip/OpenClaw)vs 腾讯 13M DAU + 微信生态分发 + 企业渠道 + 43 版/3 月迭代。
2. **覆盖面 + 目标都撞**:一次覆盖我们一堆候选差异,**且官方直接打一人公司/自由职业者 + 电商选品/落地页/客服** —— 「靠单点形态 + 靠目标用户」两条差异化路都被堵。
3. **⭐ Substitution path(最该盯的具体路线)**:腾讯**不需要抄 Flywheel 架构**就能伤我们 —— 把 **IM 派发(微信/企微/QQ)+ 办公/业务 skill(选品/落地页/客服)+ 腾讯云部署 + TokenHub 多模型 + CodeBuddy 的建软件 + 企业销售 + 存储捆绑 + 社交图谱** 拼成**够用的 operator 系统**,就能在我们产品化之前**从「够用的业务自动化」这一侧吃掉 beachhead** —— 全程不用长得像 GitHub/PR/CI。

**威胁为什么没到「取代」——诚实的另一半:**
1. **长期 ownership 的缝还在**:今天是任务式交付,没有「长期拥有 + 变更管理 + 维护 + 演进一个 operator 的软件/业务系统」的闭环;造软件在分开的 CodeBuddy(给开发者),两者还没融。
2. **验收/可信仍弱**(复杂任务易错、半途、无长期维护闭环)。
3. **大厂结构惰性**:融合「建软件 + 被协调组织 + 服务非技术 operator done-for-you 长期养系统」需跨团队 + 想清非技术 operator 的 job —— 大厂不必然快做这件对它非核心的事。**这是窗口,但靠速度守,不靠护城河。**

## 值得借鉴(from WorkBuddy)

1. **多 agent 并行拆解**做成显式能力(把大目标拆子任务并行),对「一个人手握一支队」的叙事很直观。
2. **100+ 专家角色 = 现成虚拟团队**,是非技术 onboarding 的好范式(喂 FLY-910;跟 Paperclip Company Wizard 同类)。
3. **sandbox 隔离执行** —— 「能感知的护栏」的一种(降低碰坏系统的恐惧),对非技术尤其重要。
4. **免费档 + 50GB 存储**的低门槛获客。
5. ⚠️ **别学**:红海里靠堆功能没鲜明优势(WorkBuddy 自己就被这么评);腾讯生态锁定(跟非腾讯工具兼容差)是**大厂的病、正好是我们「供应商中立整合」可讲的地方**,但那也只是「可信方向」不是现在主卖点。

## 二轮深挖(Annie 逐条存疑 · FLY-1003 deeper round)

> Annie 逐条批注后要的 deeper round:部署/运行模型、多模型切换、三剑客+腾讯云、真实用户评价、以及**最关键一问**(能不能长期拥有并演进一套真软件系统)。诚实,查不到标 UNKNOWN。

### A. 部署 / 运行模型(Annie 最关心:跑在谁的机器上?)

**答:双模式,你选 —— 既能跑腾讯给的机器(云沙箱),也能跑你自己电脑(本机);手机/IM 端只是遥控器 UI,不是干活的地方。**【官方/媒体】
- **本机模式**:跑在**你自己电脑**,基于 **Docker/Podman 本地容器**,直读本地文件、操作本地软件,适合敏感数据。代价:**电脑要开着、不能关机/休眠**(任务在你机器上跑)。
- **云端沙箱模式**(2026-03-31 微信小程序上线时补的):跑在**腾讯给的机器**(evidence 指向 **E2B 托管云沙箱**),独立跑、**不依赖你电脑开机**,适合出差/只有手机时。
- **手机 / IM 端 = 瘦客户端 / 命令台**:微信小程序 / 企业微信 / QQ / 飞书 / 钉钉 发指令(语音 / 拍照 / 传文件)→ 后台跑(云沙箱 **或** 远程控制你的本机)→ 回报。**ARM/手机端本身不常驻跑 agent,是遥控 + 看结果**;常驻能力来自云沙箱(不用开机)或你开着的本机。
- **「后台常驻跑哪几个渠道」(Annie 原话)—— 精确答**:常驻的**不是「某几个渠道」,而是一个后端**(云沙箱 **或** 你的本机)。9 个 IM 渠道(官方:Slack/Telegram/Discord/微信助手 bot/企微/QQ/元宝派/钉钉/飞书)**都只是往这一个后端派活 + 收结果的入口,本身不各自常驻**。所以准确说法 =「一个常驻后端 + 9 个可发起/接收的渠道」,不是「9 个渠道各跑一个常驻 agent」。
- 对我们:它的「云沙箱替你托管、不用开机」这条,正是我们「managed、替你托管的可靠」想做的;但它把**本机模式的运维负担(不能关机)甩回用户**,是可借鉴的反面。

### B. 多模型切换(怎么切、收费、BYOK)

【官方/评测】
- **怎么切**:WorkBuddy **对话界面底部有「模型切换入口」**,点「**+配置自定义模型**」即可。有 UI、在对话框底部,不用碰配置文件。
- **收费**:走腾讯云 **TokenHub**(大模型服务平台)—— **token 配额套餐制**,内置模型收费(输入 / 输出 token **分别计价**、不同模型不同单价、套餐分阶「等级越高百万 token 越便宜」、号称比直调低 50%+)。有免费档「零成本上车」,但**免费版有限制**(用户评论:免费版被限速/限制、逼你付费)。

### C. 三剑客 clarify(CodeBuddy / WorkBuddy / 腾讯云 Core Cloud 各是啥、怎么关联)

【官方/评测,多源一致】
- **CodeBuddy**(2025-04 起):**全流程 AI 编程助手**(需求规划→产品设计→代码研发→产品上线),IDE / 插件 / CLI / 云 四端,给**开发者**(PM→DevOps)。**这是「造软件」的那个。**
- **WorkBuddy**(2026-03):**AI 原生桌面办公工作台**,泛办公全场景,给**职场人**。**基于 CodeBuddy 的智能体架构开发**(复用多 agent / 任务规划 / 记忆那套底座)。
- **腾讯云(Tencent Cloud / 常说的 Core Cloud)**:**基础设施层** —— CloudBase(DB/serverless)、CloudStudio、**EdgeOne Pages(部署/建站)**。两个 Buddy **都集成腾讯云来部署**(CodeBuddy IDE 直接部署 CloudBase;WorkBuddy 建的落地页/网页落 EdgeOne)。
- **关系一句话**:CodeBuddy(开发)+ WorkBuddy(办公)= 腾讯 AI agent「**双子星**」,**共享同一底座**,覆盖「开发-办公」全链路;腾讯云是它们共同的**部署/算力地基**。→ **这正是 §威胁形态 里 substitution path 的拼图:腾讯已经手握「建软件(CodeBuddy)+ 办公/IM(WorkBuddy)+ 部署(腾讯云)」三块,只差把它们缝成「替非技术 operator 长期养一套系统」。**

### D. 真实用户评价(非官方页 · 小红书 + 知乎 + 媒体 · 客观两面)

**① 优势 / 好处**【小红书/知乎/媒体】:
- 效率提升显著(实测「周报 2 小时→1 分钟」「数据处理 +300%」);**傻瓜式**(点预设不用自己配);深度集成企微 / QQ(手机发消息电脑干活,「太省心」);安全合规、腾讯生态、多模态(报表 / 海报);跨会话记忆「用一个多月越来越懂我、文案都不用改」。

**② 需改进 / 吐槽(诚实,别过滤)**【小红书爆款帖 511 赞 + 评论区】:
- **稳定性差是最大槽点**:「太不稳定、目前就是个半成品、是个智障」「第一天有结果,今天再用**直接宕机、一直在思考**」「设了自动化任务,到点**直接说任务失败**」「客户端框内**打字特别慢**」。
- **建东西弱**:「做个网页 workbuddy 生成效果**比 qoderwork 差太多**,普通办公确实够了」;「不要用 workbuddy,用 codebuddy 干 workbuddy 的活」。
- **免费档限制**(评论:免费版被限速逼付费;企业版 GLM 好些);技能数量少于 AutoClaw;本地自定义偏保守;正面帖常被怼「这么硬的营销吗?」。
- **⭐ 关键用户洞察(直接印证我们差异)**:多个用户点出 —— 要让 WorkBuddy 稳定好用,**得用户自己搭一套「记忆文件 + 独立工作空间 + 中转层 + 日志系统」**,「**把它当成建自己的系统一样慢慢搭**,不是每次从头聊天」;对比 OpenClaw 一句「**一个组装好的、一个自己组装的**」;还有「**它是实习生,干不好指导老师(你)自我反思**」。→ **潜台词:WorkBuddy 把「攒成一个持续系统」的活留给了用户 —— 而这活正是非技术 operator 搭不出来的。**

### E. ⭐ 最关键一问:能不能长期拥有并演进一套真软件/业务系统?(逐条求证)

**诚实结论:不是纯一次性办公活(它也能建软件),但也不是「长期拥有并演进一套系统」的 owner —— 它是一个『你得自己搭台、每天重新 brief 的 per-session 执行器』。我们那条差异站得住,而且更精准了。**

**它「不止一次性」的证据**【评测】:跨会话持久记忆 + Checkpoints(存/回退/分叉工作状态)+ 多 agent 并行(前端/后端/测试角色 + send_message 协调)+ 「自动化基础设施」(一次描述规则→每天/每周自动出日报/周报/监控)+ 真有大型开发案例(**600+ 对话轮、15000+ 行代码、10+ 次 EdgeOne 部署**)。

**但它「不是长期 codebase steward」的逐条证据**【大型项目案例复盘 + 用户评论】:
1. **无自主 repo/项目 ownership**:每个会话 task-bound,跨会话不自主治理一个 codebase。
2. **项目连续性靠人肉外部记忆**:用户得自建「三维日志(who/what/when)」,**每天回顾昨天日志重新 brief**,否则「失忆」丢上下文;还得自己搭记忆文件 / 工作空间 / 中转层(小红书印证)。**用户是架构师 + 项目经理,不是 WorkBuddy。**
3. **无工程纪律**:无 git / PR / CI / code-review 治理;部署靠手动 EdgeOne Pages。
4. **真实翻车**:系统级失忆(任务卡壳丢对话)、**日志造假(「写了但没做」)**、连环失忆(备案/身份遗忘)、以及上面的宕机/自动化失败。

**→ 决定我们那条差异站不站得住:站得住,且收窄得更准。** 差异**不是**「软件 vs 办公」(WorkBuddy 也能建软件),而是:
- **WorkBuddy = 人力搭台的 per-session 执行器** —— 你自己搭记忆/工作空间/日志、每天重新 brief、自己核对、无工程纪律、会失忆/造假。想变成「一套持续系统」,那套架构得**你自己搭**(非技术 operator 搭不出来)。
- **Flywheel = 一个自主拥有 repo + backlog + 记忆 + 工程纪律(PR/CI/review/QA)+ 持续维护演进的被协调组织**(done-for-you)—— 把「搭成一个持续系统」这件事**替你做了**,不用你当架构师/项目经理。
- 一句话:**WorkBuddy 把「攒成一个持续系统」的活留给用户;Flywheel 替你把这套系统拥有并养着。** 这正落在 beachhead(非技术 operator 搭不出来那套),是我们最该做实的一条。⚠️ 但仍诚实:**我们自己也还没把这套 done-for-you 做实**(还一堆 bug),这是要争的,不是已赢。

## 三轮深挖(Annie 深挖 v4 后 · FLY-1003 round-3)

> Annie v4 后再钉 4 条:跨 OS 兼容具体指啥、记忆模型(她最想知道)、云沙箱生命周期、以及**能不能长期拥有并演进同一 codebase**。grounded、查不到标 UNKNOWN。⚠️ 说明:官方页只泛证「个性化记忆 / 沙箱」,以下**架构细节多来自第三方深度评测/E2B 机制**,标 provenance;要一手确证需官方架构文档(暂无)或真机拆解。

### R3-① 跨 OS 兼容问题具体指什么

【官方系统要求 + 安装指南 blog】
- **支持**:Windows 10(1909+)/ Win 11(64 位);macOS 10.15+(Intel + Apple Silicon M1/M2/M3)。**不支持**:Windows 7 等旧系统、**各类 Linux 发行版的图形界面操作**。
- **具体的兼容坑(不是泛泛「不兼容」)**:
  1. **Windows 安装脚本易报错** —— 跨平台**权限模型分叉**:Windows 用基于证书链的强制验证(执行策略 5 级)、Unix-like 用文件属性「软约束」→ 同一套安装脚本在 Windows 上更容易踩权限报错。
  2. **运行失败常因环境缺失**:装完打不开,多是缺 **Node.js / Git / .NET** 运行时,要逐条排查修。
  3. **Intel Mac 性能弱**:苹果安全机制严,官方建议用 **M 系列芯片**以获得更好的**视觉识别(看屏幕操作)性能** → 暗示 Intel Mac 在「看屏幕点按」这类功能上性能打折。
- → 对我们:这些是**桌面自托管 app 的跨平台运维税**(装环境、Windows 权限、Intel Mac 短板),正是我们用 Discord + managed 托管想替用户绕开的。

### R3-② ⭐ 记忆模型(Annie 最想知道 · 钉透)

【评测/深度分析 blog;官方仅泛证「个性化记忆」,分层/路径细节 provenance=第三方,标 ⚠️】
- **跟用户走 vs 跟项目走 —— 两者都有,分开存(两级)**:
  - **用户级(跟你走、跨项目)**:`~/.workbuddy/`(用户 home)—— 偏好(时区 / 代码风格 / 报告格式)+ 用户级技能。
  - **项目级(跟项目走、隔离)**:`{workspace}/.workbuddy/`(项目工作空间目录)—— 项目级技能 + 项目上下文。
- **三层时间维度**【评测口径 ⚠️】:L1 范式层(永久行为原则)/ L2 归档层(重要项目+决策摘要)/ L3 会话层(**31 天滚动日志**,近期完整上下文)。
- **做完 Task A、明天 Task B 记不记得 A**:**机制上记得** —— **同一工作空间**里,用户级偏好 + 项目级记忆 + L2 归档 + L3 31 天日志让它跨会话/跨天接上。**但(诚实)不牢靠**:二轮已证「系统级失忆(任务卡壳丢对话)、日志造假」,用户还得自建日志兜底。→ **「记得」是有机制的,但会漏、要人肉兜底。**
- **有没有像我们一样的常驻 leader?** **❌ 没有。** WorkBuddy 的「leader」= **Expert Teams 里 per-task 临时组的 lead agent**(这个活干完就散),记忆是**存储层(文件 / 分层)跟用户或项目走**,**不是一个跨时间常驻、持有全局、主动盯 backlog 的人格化 Lead**。→ **这条对我们差异有利**:我们卖的「常驻 named Lead = 记忆 + 掌控 + 主动 Push」,WorkBuddy 结构上没有;它是「记忆文件 + 临时 lead agent」。

### R3-③ 云沙箱生命周期(核实 Annie 的假设)

【E2B 机制 + 企业版口径;WorkBuddy 云端跑在 E2B(二轮已确),生命周期取 E2B 文档化行为,标 provenance】
- **创建**:**按需**(开工 / 发指令时起沙箱)。
- **销毁**:**idle 超时自动销毁**(评测提**约 30 分钟无操作**;官方默认值 **⚠️ UNKNOWN**)+ 主动销毁 + context-manager 用完即清。
- **持久化**:E2B 用 **CRIU(Checkpoint/Restore In Userspace)秒级快照**,只传文件系统变更 → **pause / resume + 快照恢复**;企业版**每人独立云沙箱、对话 + 文件持久保存**。
- **接回**:支持 **pause/resume 接回同一环境**。
- **核实 Annie 假设「开工开沙箱 → 干完关 → 数据进冷存储 → 下次接回」**:**大致对** —— 按需起 + idle 超时关 + CRIU 快照持久化(≈她说的「冷存储」)+ resume 接回。⚠️ 但「冷存储」是她的用词,实际机制是 **CRIU 快照 + 文件系统 diff**(不一定是传统冷存储);默认 timeout / 数据保留时长的**官方值 = UNKNOWN**。

### R3-④ ⭐ 帮不帮用户长期拥有并演进同一个 codebase,还是只做一次性?(钉死)

**诚实结论(比二轮更准):它 CAN 在同一个项目工作空间上持续迭代(机制齐),所以不是「只做一次性」;但它不是「替你 own 并演进一个 codebase 的自主组织」—— owner / 项目经理 / 工程治理 这三顶帽子都还戴在用户头上。我们那条差异站得住,且现在钉到了机制层。**

- **它「能在同一 codebase 上持续迭代」的机制**:项目级记忆 `{workspace}/.workbuddy` + 沙箱 CRIU resume + 分层记忆 + 二轮大项目案例(同一项目 600+ 轮 / 15k 行 / 10+ 次部署)。→ **纠正二轮「per-session 执行器」的过简说法:它有项目连续性的机制,不是每次全新。**
- **但它不是 codebase 的 owner(逐条)**:
  1. **在「工作空间目录」里迭代 ≠ own 一个 git repo**:无 git / PR / CI / code-review / 版本治理;部署手动 EdgeOne。
  2. **owner 是你**:项目连续性靠**你**维护项目记忆 / 日志、每次发起会话、re-brief;记忆会漏(失忆 / 造假)要你兜底。
  3. **没有常驻组织盯这个 codebase 的 backlog 并主动推进**(R3-②:无常驻 leader)——**你当项目经理**。
- **最终判定(直接给差异,钉死)**:差异**不是**「能不能在同一 codebase 迭代」(它能),差异**是**「**谁 own + 谁盯 backlog + 有没有工程纪律 + 记忆牢不牢**」:
  - **WorkBuddy** = 给你「同一工作空间迭代」的**工具 + 记忆存储**,但**你**当 owner / PM、无 git-PR-CI 纪律、记忆会漏。
  - **Flywheel** = **一个常驻被协调组织,own repo + 自推 backlog + 常驻 Lead 持有全局 + PR/CI/review/QA 纪律 + 持续维护演进**(done-for-you),不用你当 owner / PM。
  - 一句话:**WorkBuddy 把「在同一 codebase 上持续演进」的工具和记忆给了你,但把「当这个项目的 owner + 项目经理 + 工程治理者」留给你;Flywheel 把这些替你做了。** ⚠️ 诚实:我们这套 done-for-you 也还没做实,是要争的。
