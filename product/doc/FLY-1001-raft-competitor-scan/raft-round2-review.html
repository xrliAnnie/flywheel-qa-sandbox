Raft vs Flywheel —— 更深一层

新竞品 Raft(raft.build,前身 slock)到底威胁到哪、我们的差异还站不站得住
FLY-1001 · competitor-scan round-3 · 2026-07-08 · 诚实结论不美化 · 查不到的一律标 UNKNOWN 绝不编 · 证据链 research.md · raft.build
一句话:Raft 是目前找到最贴、最该警惕的一家 —— 它把「人+agent 频道协作」产品化了、引擎层比我们强、还供应商中立。

它没吃掉我们的唯一原因 = 它瞄的是 技术 leader / 工程师(它自己 trust 博客原话:"technical leaders and senior engineers... architects, not line-by-line code readers"),不是我们那个「自己建不了的非技术 operator」。

round-2 净影响:三轴结论不变,但轴 3(给非技术 operator)反而更硬了 —— 是 Raft 自己的话 佐证的;并挖出一条新差异(非技术 trust 模型)。融资 / 团队规模 / 声量 = 诚实 UNKNOWN(被同名公司数据污染,不硬凑)。

④ 产品具体长啥样(讲透)

怎么用(onboarding 四步 · 官方原话)

① 见到 Onboarding Agent(建 server、连一台电脑、见团队第一个 agent)→ ② 交第一个任务(给真活、看它做完带回来)→ ③ 把队友拉进房间(人和 agent 并肩)→ ④ 养一支 agent 队(加 agent、定职责、越用越会)。

形态 = web workspace(channels / threads / tasks / @提及)+ agent 跑你自己硬件上的 lightweight daemon;agent = 一等公民,"one agent is one session:跨天跨任务的连续身份",自己维护 inbox/tasks/reminders,能被点名后主动加进频道开干。

⭐ 核心工程机制 —— Cass 说的『报数/staged-draft/version-check』的真身

(官方叫 Inbox surface + Held Draft surface + version marker;『报数/Dmail』是 Cass 的转述简称。)

问题:"the gap between an agent's reasoning and the room moving on" —— agent 回合制读快照→推理→提交,写的时候看不到新消息进来;房间在推理和提交之间动了,它可能还在对着一个已不存在的状态说话。← 这正是我们的 crossed-wires(Lead 读旧频道快照)。
  • Inbox surface:把「消息硬推进上下文」反转成「agent 有余力时主动拉」—— @提及/thread 更新变成可查询项,agent 自己决定啥值得进上下文,不被房间噪声挤掉任务状态。
  • Held Draft + version marker:每条出站消息带版本标记(标它对着哪个房间状态写的)。发送时房间没变→提交;房间动了→扣住、连同「你写时进来了啥」还给 agent("draft 是一等状态,不是发送失败")。agent 四选一:Revise 重写Send as-isStay silentSend anyway

= 我们 FLY-574(draft-not-sent)+ crossed-wires 的正解,已被 Raft 产品化。这是「引擎层他们更精」最硬的证据。

Raft 的产品哲学(博客暴露的,对我们有战略含义)

  • "Agents Need Names" —— named agent 做信任/路由。→ 我们「named Lead」这条信任点,Raft 也做,不独有。
  • "Trust Doesn't Live in Code Review"(⭐ 战略金矿)—— trust = "能预测它";验证靠持续读系统信号(bug 簇 / mutation testing / agent 间碰撞检测);人从看门人变成「读系统、收紧输入」的人。目标用户原话 = technical leaders / senior engineers / architects,明确不是非技术。
  • "You Don't Need a Company Brain" —— 主张多专才视角 > 一个统一大脑。⚠️ 和我们「共享记忆/第二大脑」是分叉哲学,值得盯。
三轴差异化 —— 逐轴标 vs Raft(round-2 更新)
轴vs Raft一句话(round-2)
① 领域
替非技术 operator 建养真软件产品		 部分成立 站得住 = done-for-you + 给建不了的人 + 养;塌 = 「跑在真实软件上」(Raft 主场,它 agent 本就跑你真 repo);且待兑现,done-for-you 还没 ship。
② 被协调常驻组织 + 复利
always-on + 记忆 + 管理 + Push		 大部分不成立 复利 / 记忆 / 常驻被 Raft 匹配甚至更精(Held Draft/version marker 就是证据);只剩「管理 + Push(不用你当 PM)」一薄条,还可被 Raft 加个 manager agent 补。
③ done-for-you 给非技术 + founder 判断 成立(最硬) round-2 更硬:Raft 自己 trust 博客把用户定义成 technical leaders/architects → 非技术 operator 确是它盲区(它自己的话佐证)。Annie operator-taste vs Raft engine-taste 真方向差。但非结构、靠速度+聚焦守、done-for-you 未 ship。

净结论:三轴里 ②(大部分)+ ①(一半)被 Raft 匹配或塌,只有 ③(客户切入点 + taste)真站得住,且非结构、靠速度守、还没兑现。

🆕 round-2 新挖出的一条差异(建议补进 911 信任章):非技术 trust 模型 —— Raft 服务 architect、trust 靠「读系统信号」(要技术素养);我们服务非技术 operator、trust 靠 4 件可亲验(named Lead / 可读审批 / 结果证明 / 护栏)。「非技术怎么信任」是两套人的两套答案 —— 这条对 Raft 成立。

Cass 三压测点 —— 证据结论

① 停在 调度引擎 层 = 被吃 → 完全成立、更扎心。Raft 本身就是被产品化的 调度引擎 层、更成熟。护城河是待兑现的赌注、不是现有资产;按我们自认的诚实边界(done-for-you 没到),此刻我们离「停在引擎层」比离「已 ship 复利产品」更近。

② 融资 + 专注 + 前 Kimi → 引擎更精 → 成立,认输这层。硬证据 = Held Draft/version marker 他们已 ship、我们还在 backlog。别在引擎精巧度上跟它掰(必输战场),引擎够用就行。

③ 唯一真差异(自用 + 真实产品闭环 + Annie 判断) → 真实但薄。dogfooding 不是护城河(Raft 也自用、还同主场);「跑真实产品上」= Raft 主场;复利被匹配;最能守的 = 指向非技术 operator 的 founder taste,但要转成 ship 出的产品才算数、且还在建(Anna)拿真客户声音磨。是先发 + 聚焦 + taste 优势,不是结构护城河。

对 FLY-911 定位的建议(弹药 + 推荐 · Annie 拍)

动摇了「可防御性」,没动摇「打谁」。always-on / 记得一切 / 复利被 Raft 匹配、从差异变 人人都有的基础能力;但我们最先要专攻的那群客户(= 非技术、自己不会写代码、自己做电商/社媒的一人公司老板)是 Raft 盲区、站得住。
