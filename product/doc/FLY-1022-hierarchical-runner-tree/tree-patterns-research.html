1 · 部分聚合上汇 MVP

机制 叶子(runner)自报 → 中间层 sub-lead 先做部分聚合、只送聚合值 → 对数轮到顶。抄 Spark treeAggregate / MapReduce combiner。
权衡 代价 只对 associative+commutative 聚合成立(count/max)→ 顶层拿到的必然是有损摘要,细节留下层。
映射 sub-lead 把 N 个 runner 压成可结合聚合:计数 + 冒泡的少数异常。→ 直接约束 PRD §9 的摘要 schema(不能把原始明细往上堆)。
来源:Spark treeAggregate · MapReduce combiner

2 · 两级调度委派 MVP(一层)

机制 拆开「资源分配」与「任务放置」:上层把活 offer/派给下层独立调度器,下层自己安排。抄 Mesos 两级。
权衡 代价 下层看不到全局放置选项 → root 失去全局细粒度视图、跨组抢占难。委派 = 用全局视图换可扩展。
映射 Lead = 资源管理器,派给 sub-lead。这条代价正是「为什么 MVP 只一层、跨组协调仍回 root/founder」 —— 是取舍不是缺陷。
来源:Mesos / Omega / Borg: a survey

3 · 子树故障隔离(bulkhead / cell + circuit breaker)MVP

机制 隔舱:资源分独立池,一处失败不耗尽全局、限制爆炸半径。cell:blast radius=1/N。熔断:反复失败→跳闸停打、防级联。
权衡 代价 隔离降利用率(空闲 slack 不共享)—— 对我们可接受,注意力隔离本就是目的。
映射 每个 sub-lead 子树 = 一个隔舱/cell,一组卡住不级联到兄弟组/root。sub-lead 自己冻住 → root 跳闸它、重路由或升级 founder,不干等。= 你说的「检测+隔离卡住子树」。
来源:Azure Bulkhead pattern · Cell-based / blast radius

4 · ⭐ 背压 = 353 的容量信号 MVP · 接 353

机制 下游处理不过来 → 向上游发信号减速(不让队列无界膨胀)。抄 Reactive Streams / 有界队列削峰。DR 补强:带显式 credit 的有界队列(sub-lead 声明「我还能收 n 个」)。
权衡 代价 故意压过载吞吐换不崩;待办必须有界(无界缓冲会 OOM/级联)。
映射 sub-lead 饱和 → 向上发背压 → root/353 停止往这个子树派新活。sub-lead 的饱和信号,就是 353 capacity-aware 派发要消费的容量信号。 1022 的树和 353 的流控用「背压」一个机制接上,不是两套东西。
来源:Reactive Streams backpressure · Back pressure in distributed systems

5 · ⭐ SWIM「先疑再判死」MVP · 喂回 942

机制 SWIM(2002)= outsourced heartbeat + gossip。检测时延/误报率/每进程负载与组大小无关(传统 heartbeat 是 O(N²));传播随成员数对数增长。
关键 suspect-before-declare:先「怀疑」再「宣告」→ 降误报。
权衡 代价 弱一致(几轮才传到顶)—— 异步+人在环可接受。
映射 逐层上报 = 分层故障检测。sub-lead 先 suspect 再升级,直接治 FLY-218/220 误报病;O(N²)→分层 = 树观测能 scale 的理论依据。
来源:SWIM 协议 · SWIM paper (Das/Gupta/Motivala)

6 · 何时加/合并 sub-lead(B-tree 分裂/合并)later 留位

机制 节点满 → 中位数分裂成两个;占用跌破阈值 → 合并/借兄弟。大 fan-out 保持树浅而快。
权衡 代价 分裂/合并 churn;频繁增删会 thrash → 用滞回阈值(高水位分裂、低水位合并、中间留 gap)。
映射 sub-lead 超容量(≈5-6)→ 分裂新 sub-lead 挪一半;两个都低 → 合并。MVP 手动/配置、不自动(防 thrash + 复杂度)。
来源:B-tree · B+tree underflow: merge or borrow

7 · runner 分到哪个 sub-lead(一致性哈希 + vnode)later 留位

机制 加/删节点只重映射 ~K/N 的 key(朴素取模要 ~99%);虚拟节点(128/节点)→ 负载均匀、加节点从多处各拿一小片。
权衡 代价 环/vnode 元数据复杂;我们只有一小把 sub-lead 时是过度设计。
映射 动态增删 sub-lead 又不想全体重洗时的成熟机制;MVP 用简单静态/轮询分配就够、留位 later。
来源:Consistent hashing + virtual nodes (Dynamo)

8 · 每个 sub-lead 带多宽(fan-out 权衡,LSM 视角)

机制 fan-out 越大 → 树越浅、升级跳数少、查任意 runner 状态快,但每层聚合越重;越小 → 树越深、跳数多(LSM leveled 的写/读放大权衡)。
映射 每 sub-lead 带多少 runner = fan-out。上界由「一个脑扛得住」定 ≈5-6(认知瓶颈,不是磁盘)→ 我们的 fan-out 被认知容量天然钉在 ~5-6,不用调到 128。
来源:RocksDB compaction (leveled/tiered) · Leveled compaction overview

8b · ⭐ 进程监督树(Erlang/OTP supervision tree)MVP 策略语言 · DR 新增

机制 supervisor 监督一组 children,按 restart strategy(one_for_one 只重启挂的 / one_for_all 全组重启 / rest_for_one)恢复;restart intensity 限流(超 max-restarts/period → supervisor 自己放弃、上报它的父级);let-it-crash(不修坏状态,重启到干净态)。
权衡 代价 重启丢进程内存态(靠 progress.md / FLY-353 重建,不在本 issue);restart intensity 防「重启风暴」。
映射 sub-lead = 它那摊 runner 的 supervisor;runner 反复失败超 restart intensity → sub-lead 停止重试、上报父级(逐层),呼应 942「失败 3 次问 founder」+ 现有 retry。let-it-crash ≈ 我们「坏 worktree 清掉重派」。给「子失败该怎么办」一套成熟词汇。
来源:Erlang/OTP supervisor 官方文档(ChatGPT DR 引)
