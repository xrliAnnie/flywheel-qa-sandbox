2 · 核心:树 = 压缩层 + 树聚合(DDIA)

Lead(root) ├── sub-lead A ── runner · runner · runner ├── sub-lead B ── runner · runner · runner └── ... ▲ Lead 只看「组摘要」,不看每个 runner 细节
  • 压缩层:Lead 只跟直属 sub-lead 谈、只看组摘要(「A 组:3 正常 / 1 卡在 X 要你拍」)。注意力 = O(直属子节点数),不是 O(runner 总数)。
  • 树聚合(DDIA):叶子 runner 自报健康 → 每层 sub-lead 聚合压缩上报 = 经典 roll-up。记 DDIA《Designing Data-Intensive Applications》当 eng 参考(聚合树 / 扇出扇入 / 背压)。
  • 容量算术(说明上限,非 MVP 目标):1 → 5 → 25 → 125…… 每加一层 ×~5。MVP 只一层:1 Lead → 5 sub-lead → ~25-30 runner(已远超今天 5-6)。

3 · ⭐ 942 变 tree-aware(你点名的:报最底 → 层层上 → 不直顶)

不是新观测系统,是给 942 加一条「沿树上报」的落点(喂回 942)。

  • 检测不变:仍是 942/878/927 的系统看门狗,零 token 纯文本比对,一行检测逻辑不重写。
  • ⭐ 落点变:看门狗判某 runner 卡住 → 报给它的直属 sub-lead(最底层),不直接顶到 root Lead。
  • 层层升级:sub-lead 是第一响应人(942 契约);先自愈/relay。只有它解决不了 / 应答超时,才逐层向上冒泡,最后才到 root Lead / founder。
  • 喂回 942:这条「树-aware 落点 + 层层升级 + sub-lead 应答时效」作为 942/878/927 的一个增强记回去。

4 · ⭐ 节点粒度:一个节点 = 一整条三段式 session(不拆)

  • 树上一个叶子 = 一个 runner 跑的一整条 workflow(设计→实现→QA)当一个整体,不拆成三个树节点。
  • 为什么不拆:拆散 = 每个子阶段都独立上报/被指挥 = 通信爆炸,正是 1022 要治的病。
  • 跟 1020 对齐:1020 定「节点内部怎么编排(哪套模板)」;1022 把「跑这条模板的整条 session」当树上一个被指挥的单元。两层解耦、互不侵入。

5 · ⭐ per-issue thread 保留(硬约束):压注意力 ≠ 藏 thread

你的硬约束: 树压缩的是 Lead 的注意力,绝不是隐藏 founder 的可见性。每件事照样有自己的 thread 直接给你看。

两条正交的路:

  • 注意力路(压缩):runner 健康/进展 → sub-lead 聚合成组摘要 → 上到 root Lead。Lead 看摘要,不被 N 个细节淹。
  • 可见性路(不压缩):每件事照进它自己的 [ISSUE-ID] thread(更新/决策卡),直达你。树不藏、不合并、不吞 thread。
  • thread 所有权下放:每条 thread 由该 runner 的直属 sub-lead owned(负责写),但 thread 本身照常一件一条、直达 founder。

6 · 多机放置(合成 1005)+ Lead-as-child 通信

  • 放置:lead + sub-lead 在 hub 机(它们是「脑」,要 hub 的本地 StateStore/CommDB/mailbox);runner 在节点池/卫星机(1005)。
  • Lead-as-child(核心新增):一个 Lead 能当另一个 Lead 的孩子 —— 向上报组摘要、向下带 runner。复用同一套 Lead→Runner 机制、只调 schema:LeadConfig 加 parentLeadId(default-off)+ dispatch 多一跳。Tadashi 初判「中等改动」。
  • 字节兼容:parentLeadId 不设 = 今天的扁平行为,零变化。
