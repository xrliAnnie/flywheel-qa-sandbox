1 · 要解决的问题 + 北极星

结论 —— 痛点:issue 一多,「派活」本身成 founder 的重复劳动。今天「谁下一步做什么」这层始终人肉:要一个个开 issue、再一个个跟 Lead 说「你做 1、你做 2」。issue 一多就成瓶颈。你只想列大方向,不想当人肉调度员。

结论 —— 北极星:founder 只列大方向,系统自动挑 / 派 / 推进到底,人不再逐个 assign,判断没丢、不失控。

一句话验收:你开一批 issue 后不用逐个 assign;CoS 自动分诊 → 每 6h 按负荷/依赖自动派;复杂的 runner 跑中拉你定;ship 仍你点头;Discord 看得见、随时叫停。

2 · 全景架构:353 = 第二层治理引擎

结论:浅紫 = 353 要建的第二层治理引擎(分诊 + 自动派发 + 监管);虚线灰 = 第一层轻模板(= FLY-1020,另开 issue,此处只示意)。353 不建第一层,只调用它。

3 · 三形态对照 + 两层 DAG(353 只做第二层)

结论:把「issue 级编排」的三种形态摆平,353 选第三种 —— 自动派发 + LLM 分诊 + 判断在 run 里,拿到「自动省心」又不丢「判断不机械」,且有护栏。

形态怎么做适用 / 软肋
🅐 静态 DAG(旧 dormant resolver)整批 issue+依赖预先排图 → Executor 机械照图走依赖预先清楚才行;软肋:机械判断易错(旧 issue 还照跑)
🅑 现状(动态、人在环)Lead 现场判断派谁(人肉,一个个)判断靠人不机械;痛:派活人肉、逐个 assign 累
🅒 353 提议(自动派发+LLM 分诊+跑中判断)CoS(LLM)分诊 → 自动派 → runner 跑中判断 → 护栏两全:自动省心 + 判断不机械 + 有护栏

结论 —— 两层拆分:

  • 第一层 · 轻模板层(= FLY-1020,另开 issue) —— 一个 issue 内部怎么跑;每类任务一套轻/可覆盖模板;353 只调用不建。
  • 第二层 · 353 治理引擎(本 issue) —— 做哪些 issue + 派谁 + 何时 + 护栏 = CoS 分诊 + 自动派发 + 监管。
范围边界:353 不碰 lead-tree / fleet-scaling = FLY-1022。两者互补:353 = offload 让单 Lead 拿更多;1022 = 分 sub-lead 每个拿更少。

4 · 核心结论:轻模板 + 强治理

结论(回应「会不会过度复杂化 / 限制越来越强的模型」):不束缚模型「怎么想」,提供的是治理 + 编排。

  • 模板 = 轻的、可覆盖的默认起手式,不是死模板/紧身衣 —— 模型可偏离(简单一步跑完、复杂多绕几步);模型越强越能在模板之上自由发挥,不锁每一步。
  • DAG 真正价值 = 治理(分诊 / founder gate / 接管 / 成本控制:贵模型只用在难步骤)—— 控制、信任、成本需求,模型再强都还要;管的是「派什么、谁批、花多少」,不是「怎么推理」。
一句话:轻模板(不锁模型)+ 强治理(可控可信可省钱)。复杂度只加在治理层(有持久价值),不加在束缚模型思考。

5 · CoS = 分诊节点 —— 产决策 ≠ spawn 权

结论:CoS 是 LLM 分诊节点,每轮逐条判 —— 还相关吗?派给谁?用哪套模板?何时?更 proactive?置信度(低置信 → escalate 不派)。

关键边界(grounded):CoS 产决策 ≠ 有 spawn 权。CoS 是 canSpawnRunners:false(triage 角色);正确做法 = CoS 只产 typed DispatchDecision{issue, targetLead, targetDept, template, confidence, rationale, dependencies},底下 dept Lead 执行 spawn,仍经 DepartmentRegistry 校验 label/dept/lead。机器真相 = 决策 + ledger,不是语言指令;decision ≠ authority。

6 · 依赖层:轻、可选、多靠 Lead/PM

结论:大多数 issue 不标依赖;founder 偶尔给一个大方向 A→B;其余靠 Lead/PM 临时判。依赖层一开始可基本没有 —— 有标就尊重,没标就并行 / 按到达序 + 负荷。

结论 —— 精确语义(fail-closed):v1 以 Linear relation 为权威;自然语言 note 只作 proposed edge、需确认;unknown / cross-project blocker 不越过、升级;cycle escalate;Linear fetch 失败不派;无依赖 ≠ 无并发上限。

7 · 频次(周期扫为主·每 6h)+ CoS 输出 + 面板

结论 —— 频次 = 周期扫为主,不是事件驱动(新建 issue 不代表马上执行;任务有 priority,靠分诊决定谁先谁后)。初期每 6 小时扫一次,每轮:

  1. 读每个 Lead 当前负荷(上限如 N=5:各手里几件)。
  2. 谁不满 → 用 backlog top-priority 补齐到上限(Lead1 有 0 → +5、Lead2 有 2 → +3)。
  3. = 读负荷 → 抓 top-priority → 按各 Lead 余量分发。

结论 —— 动态负载触发 = 北极星(后续):按系统水位(内存 / token)自动决定何时扫。诚实 现在监控不了内存/token,先做每 6h 固定 + capacity 补齐;capacity 关联 FLY-1022。

结论 —— CoS 每轮出两样:① 给各 Lead 的语言指令(dept Lead 执行 spawn 的载体)+ ② 一张 HTML(给你瞟)。机器真相仍是 typed decision + ledger,语言指令是人可读的渲染 + 审计件,不是唯一机器触发。

结论 —— 面板 = Discord(不另做 dashboard,复用 FLY-203 publish-report;每轮 summary + dedupe / noise budget);cron = 引擎里定时节点。

8 · ⚠️ 4 监管护栏(自动但不失控)+ 工程硬护栏

结论 —— 判断在 run 里:默认全自动派发;简单 runner 自己跑完;复杂的用现有 brainstorm gate 跑中拉你,再继续。四条监管护栏:

  • ① ship 仍 founder-gated(复用 verify-approval,合入 main 永远你点头)。
  • ② 随时接管 / 叫停(暂停自动流、抽某条转人工)。
  • ③ 失败 → escalated 升级给人,不静默(卡住 / 报错 / 跑偏 → 上面板告诉你,不 shelve-继续)。
  • ④ 看得见(Discord 面板)。
工程硬护栏(启动前置 / 验收):默认 off + kill switch(FLYWHEEL_AUTO_DISPATCH=0)· 首批 dry-run 只出决策不真派 · per-issue opt-out · per-dept 最大并发上限 · 低置信 escalate · 启动前写 durable dispatch ledger。

9 · 渐进自治:早会学偏好 → 全自动(依赖 FLY-1034)

结论:全自动不是一步到位,是一条毕业曲线 —— 近期靠早会让 CoS 学你偏好(节奏 / 依赖 / 优先级),学够了越来越自主,早会越来越短,终点全自动。

回路:CoS 每轮决定 → 早会上你确认/纠正 → CoS 学到偏好 → 下轮更准 → 早会需要你的地方变少。你随时能介入,越到后面越少需要。

范围边界:「怎么学」= 单独 issue FLY-1034(autonomy learning),353 不 build。两处学:① 早会 CoS 学派发;② Lead 学替你决策。353 只用「早会 + 渐进自治」运行模型,依赖 FLY-1034。voice 化早会 = FLY-906 context,非硬依赖。

10 · 引擎:删没用的旧 dag-resolver + 重搭

结论:现有 dag-resolver = v0.1.0 基础货(Kahn + getReady/markDone/shelve),没接生产、无 LLM 分诊、无护栏、出错 shelve-继续 → 删掉,按新模型重搭。

迁移 note:edge-worker 仍 import DagNode type、tests 还实例化 DagDispatcher → 先 move shared types、移依赖、更新 tests,别机械删导致 breakage。

11 · Non-goal + session-log backlog + build 拆分

结论 —— Non-goal(353 不碰,防越界):lead-tree / fleet-scaling = FLY-1022 · 学习引擎 = FLY-1034 · 第一层轻模板 = FLY-1020 · voice 早会 = FLY-906 · dashboard(用 Discord)· ship 授权(仍 founder-gated)。

结论 —— session-log 解耦 = backlog:我们用 Claude Code,brain/hands/session 原生就有,单机不痛;只在 3 场景才值(Codex/kimi · 跨 agent slice · 多机),等实测真痛再做。

结论 —— 给 Tadashi 的 build 拆分(schema/护栏先行): E1 决策 schema + ledger + 默认 off + dry-run(含删旧引擎)· E2 CoS 只产决策 · E3 引擎校验 + 派发(每 6h + capacity)· E4 护栏 + 面板 · E5 动态负载(后续)· E6 模板泛化 inject/fork(后续)。eng issue 由 Lead 按 910 建 1 个 umbrella + PRD,不在此建。
