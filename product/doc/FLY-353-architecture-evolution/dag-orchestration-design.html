1 · 要解决的痛(你说的)

你现在的烦躁:手动开一堆 Linear issue 1-10,再一个个跟 Lead 说「你做 1、你做 2、你做 3」。issue 一多,派活本身就累。

主动 DAG 编排要给你的: 你只列大方向(开 issue + 标清依赖)→ 后台自动按依赖挑出「能做的」→ 派 runner 去做 → 做完自动标完成 → 自动推进下一个。你不用再一个个 assign。

这正是 353「架构进化 → 精进 Flywheel 架构」的答案:把「谁下一步做什么」这层从人肉搬成自动(在有护栏的前提下 —— 见第 3 节)。

2 · 三种形态对照(静态 DAG / 我们现在 / 提议的主动派发)

🅐 静态 DAG(dormant resolver / homerail-ish)

你把整批 issue + 依赖预先排成一张图
↓
Executor 照图自动走:挑没被 block 的开跑
↓
做完自动标 done → 解锁下游 → 继续
适用:任务 + 依赖预先清楚、说得明白、确定性强。不适合:边做边变、需判断的。
UNKNOWN homerail 确切实现没查到;这是静态 DAG 的通用 pattern(= 我们 dormant 的 resolver 也是这套)。

🅑 我们现在(动态、人在环)

issue 进来 → CoS 分诊 → 部门 Lead
↓
Lead 现场判断派谁、何时派(人肉)
↓
三段式(设计/实现/QA)→ founder gate ship
适用:开放式、需产品判断的活。代价:issue 一多,人肉派活累(= 你的痛)。

🅒 提议:主动派发 + 护栏

你开 issue + 依赖;标「可自动」的进自动流
↓
后台自动挑 ready → 派 runner → 标 done → 推进
↓
护栏:ship 仍你点头 · 可随时接管/叫停 · 出错升级给人
适用:两全 —— 依赖清晰的自动跑、探索性的留人判断;省掉一个个 assign,但不失控。

🅒 = 把 🅐 的「自动照图跑」和 🅑 的「人在环判断」合起来:能自动的自动、该人管的人管。下面第 3 节就是这条线怎么切。

3 · 主轴:哪些 issue 能自动派发 vs 哪些必须留人判断

这是整个设计的脊梁(也直接回应你说的「要好好设计 + 监管,不然容易出问题」):不是所有 issue 都该自动跑。

类型特征怎么处理
可自动依赖清晰 + 说明白 + 确定性(如「按这份 spec 实现 X」「修这个明确的 bug」「加个已定义的字段」)进自动流:后台按依赖挑着跑,不用人 assign
留人判断探索性 / 需产品决策 / 方向没定 / 架构 / 要先 brainstorm(如「产品化怎么做」「这个方向值不值」)不进自动流:走现在的 Lead 派 + 人判断

怎么标一个 issue 是「可自动」还是「留人判断」?几个选项(想听你偏好):

  • 选项 A(保守默认):默认全是「留人判断」,只有显式标记(如打个 label / 你或 Lead 点一下)才进自动流。—— 最安全,不会误自动跑该判断的。
  • 选项 B(Lead 分诊时定):CoS/Lead 分诊时判断这条属哪类、打标。—— 借现有分诊动作,不加你负担。
  • 选项 C(你成批圈定):你一次圈一批「这几个自动跑」(如 issue 3-8 是明确的实现活)。—— 贴你「列大方向」的习惯。

我倾向 A + C 合起来:默认留人判断(安全),你能成批圈「这批自动」(省心)。B 作为 Lead 辅助。—— 但这是你的产品判断,想听你的。

4 · ⚠️ 监管护栏(你最在意的:别失控)

自动派发不等于放手不管。四道护栏:

  • ① ship 仍 founder-gated(不变):自动流只管「把活跑出来 / 出 PR」,合入 main 永远你点头 —— 和现在一样。自动的是「派活」,不是「发布」。
  • ② 随时接管 / 叫停:你或 Lead 能暂停整个自动流、把某个 issue 抽出来转人工、或改依赖重排。自动流是「默认帮你跑」,不是「锁死不能插手」。
  • ③ 出错 → 升级给人,不硬跑:自动流里一个 runner 卡住 / 报错 / 跑偏 → 停下 + 告诉你/Lead,绝不「静默 shelve 了继续跑别的」当没事。(现在 dormant 的 resolver 是「shelve 掉 + 跑别的分支」,护栏要把它改成「该升级的升级」。)
  • ④ 看得见:一个面板/视图 —— 哪些在自动跑、哪些排队、哪些被 block、哪些升级了等你。你随时知道自动流在干嘛(呼应可观测)。

一句话:自动的是「省掉你一个个 assign」;没动的是「你对 ship 和方向的控制」。出问题第一反应是「叫人」,不是「自己硬扛」。

5 · 取舍:复活 dormant resolver vs 做个更轻的新派发

🅐 复活 dormant resolver🅑 做个更轻的新派发
现状引擎已经写好且能用:dag-resolver(Kahn 拓扑排序、getReady/markDone/shelve、并行、错误隔离)+ LinearGraphBuilder(直接从 Linear 的 blockedBy 关系建图)+ DagDispatcher。只是没接进生产、没在跑。从零写一个更贴护栏模型的简单派发循环。
优点核心引擎省了 —— 你那套「列 issue+依赖 → 自动挑/跑/标完成」它本来就实现了。干净贴合新护栏 + 现在这套 Lead/三段式/founder-gate 栈。
代价是 v0.1.0 老代码,要:接 live 派活 + 加整层监管护栏(第 4 节)+ 加「自动 vs 人判断」分类 + 跟现在演进过的栈(RunDispatcher/三段式/founder-gate)整合。老引擎的「出错 shelve 掉继续」还跟护栏③冲突,要改。引擎要重写一遍(拓扑排序/ready/并行/错误隔离都得再做)。

我倾向 混合:复用 resolver 的图逻辑(拓扑排序 + 从 Linear blockedBy 建图,这块最成熟、白扔可惜),但外面套一层新的「护栏 + 派发」(founder-gate/接管/升级/分类),而不是原样接旧的 DagDispatcher。这样既不白写引擎、又能把护栏做进去。—— 具体归 Tadashi 定,PRD 阶段细化。

6 · 分阶段(先小后大)

  • 阶段 1(MVP,验证省心 + 护栏):只让你成批圈定的「可自动」issue进自动流;后台按依赖自动挑/派/标完成;护栏①②③④ 全在(ship 仍你点头、可叫停、出错升级、有个看得见的面板)。范围小、可灰度、可关。
  • 阶段 2:更聪明的分类(Lead 分诊辅助定「可自动/留人」)、更强的失败自愈、并行度调优。
  • 默认关 + 可回退:整套默认 off,先在自托管/一批明确 issue 上试,验证「真省心 + 没失控」再放开。
