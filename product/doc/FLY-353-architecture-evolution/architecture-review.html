1 · 他们的架构怎么做的

A · Anthropic「Managed Agents」工程博客,细节最实

把一个 agent 拆成三个能各自独立替换的部件(它叫「cattle not pets」):

  • brain(大脑) = Claude + harness,只做决策。无状态 —— 记忆不攒进程里,每次从 session 日志按需读回,所以大脑随时可杀可重建不丢。
  • hands(手) = 沙箱 + 工具,统一接口 execute(name, input) → string;它「不知道沙箱是容器、手机、还是宝可梦模拟器」= 跟执行环境完全解耦。
  • session = 「发生过的一切的 append-only 日志」,在 context 之外。emitEvent 写 / getEvents 取位置切片 / rewind 回退 / wake(sessionId) 崩溃后重启读。

换来: 推理立即开始不等容器 → p50 首字延迟降约 60%、p95 降超 90%;多个大脑可互传手;崩溃能 wake 续。

对我们: 我们已经是大脑/手解耦(runner 跨 4 引擎、工具已 execute 式),差的只是「自己 own 的 session 日志」—— 而这只在收窄的 3 场景才需要。

来源:anthropic.com/engineering/managed-agents(已逐条核实)。事件确切字段结构博客没给全 UNKNOWN。

B · openclaw 开源,已被 OpenAI 收购(2026-02)

24/7 无人值守个人 agent 框架(一周 10 万 star)。查到的真实配置键:

  • Gateway 常驻 daemon(systemd / LaunchAgent):管渠道、路由消息到 session、调度;写锁 session.writeLock。
  • session 持久化:~/.openclaw/agents/{id}/sessions/sessions.json;pruneAfter:30d / maxEntries:500。
  • 记忆 / context 饱和(和我们最相关):compaction(有损摘要)+ memoryFlush:压缩前先把记忆写进 memory/*.md 再压;+ startupContext 注入每日记忆。
  • 队列:messages.queue.mode=steer/followup/collect/interrupt;debounce 2s;cap 20 + drop。
  • failover:model:{primary, fallbacks} 按序退;utilityModel/imageModel 各自 fallback。

对我们: 编排能力我们几乎逐条都有(见对照表)。不该照抄它的架构;值得学的只是它处理 context 饱和的手法(memoryFlush = 压缩前先落记忆)。注意:它是有损压缩 + md 记忆兜底,和 A 的全事件日志不丢是两条路。

来源:docs.openclaw.ai/gateway/*(已核实配置键)。transcript 格式、OAuth 刷新、多实例选主 UNKNOWN。

2b · DAG:动态 vs 静态 / 跟 homerail 差在哪

结论(已 grounded 核代码):我们是动态编排,不是静态预编排 DAG。

  • 有 dag-resolver 包(Kahn 拓扑排序 Linear blockedBy),但整图自动执行的 DagDispatcher 在生产路径 0 处实例化 = dormant。
  • 真实派活 = Lead 逐 issue 动态派(RunDispatcher / AgentDispatcher),issue 内三段式;谁跑/何时跑 = Lead/founder 现场决定;blockedBy 是给人读的。

你上轮那句说到根子上了,完全对:静态 DAG 要你预先把整张任务图规划好 → Executor 照图走;但开放式、边做边推进的活没法预先规划成静态图。我们的活正是探索性/需求边做边清/要产品判断 —— 所以不是我们不会做静态 DAG,是我们的活本来就不该用静态 DAG,故弃 DAG、转「Lead 动态派 + 人在环」。

「是不是已很像 homerail?」:表面像(有 dag-resolver 包 + Linear blockedBy),实质不像 —— 静态 DAG 预先/自动,我们现场/Lead 动态人在环。UNKNOWN homerail 确切架构没查到官方文档。

2c · 你问的 4 个问题(grounded 核代码答)

① DAG:当初为啥建、优势、为啥现在 dormant?

为啥建: v0.1.0 第一个 Core Loop 的编排原语 —— 设想「Linear issues → DAG resolver → sessions → PR」,自动按依赖排序往下跑。

优势: Kahn 拓扑排序自动挑出「谁没被 block、可开跑」、做完标 done、卡住 shelve 挡下游、独立分支并行 = 图排好不用人盯自动跑完。

为啥 dormant: 产品方向变了(见 2b)—— 我们的活开放式、要产品判断,转成「Lead 逐 issue 动态派、人在环」;v0.2 把 DAG 标「Preserved 代码不变」但没接进 live 派活。

② respawn / tmux 保活具体怎么实现?多机怎么变?

你问「crash 了 tmux 还在、记住名字就行?」—— 精确一点:不完全是。 真正保住 context 的不是 tmux,是「我们不让那个 claude 进程退出」:它 parked/idle 但一直活着,所以内存里完整 context 还在(代码原话 parked session「woken, not respawned, keep full context」);要它继续就唤醒(mailbox + tmux send-keys)。tmux 只是托住这个活进程的壳。

如果进程真的挂了(crash / terminate / reboot):tmux 窗口还在,但死进程内存里的 context 没了 —— tmux 救不回死进程的记忆;只能重启 + 从 progress.md 粗粒度重建(丢细节)。

多机(你说的对): tmux send-keys 是本机操作,跨不了主机 → 多机时保活/唤醒直接失效 → 要 host-independent 的 log(= 场景③)。多机目前是 future(有 008-multi-machine-consensus 研究)。

→ 所以:真机制 = 「别让进程退出」;单机+进程没真死时好用,真 crash 会丢、多机也不行 —— 这两道缝正是自己 own log 的动机。

③「编排层」大白话(= 谁决定下一步派谁干啥)

  • Linear issue 进来 → CoS(Aunt Cass)分诊、打标签、路由给对应部门 Lead(如 Tadashi);
  • Lead 决定派一个 Runner去干(何时派、派哪种,现场定);
  • issue内部走三段式:设计→实现→QA;
  • ship(合入)永远 founder 点头。

所以「编排 = 一串人/Lead 的现场决定」。那个 dormant 的 DAG,当年就是想把这层自动化掉;现在交回给了人 + Lead。
