1 · 他们的架构怎么做的

A · Anthropic「Managed Agents」工程博客,细节最实

核心是把一个 agent 拆成三个能各自独立替换的部件(它管这叫「cattle not pets」——牲口,不是宠物):

  • brain(大脑) = Claude + harness,只负责做决策。它无状态 —— 记忆不攒在进程里,而是每次用的时候从 session 日志里按需读回来。所以大脑随时可以被杀掉重建,不丢东西。
  • hands(手) = 沙箱和工具,负责执行动作。统一接口 execute(name, input) → string;harness 对任何工具/MCP/自己的工具一视同仁,它「不知道沙箱是一个容器、一部手机、还是一个宝可梦模拟器」= 完全跟执行环境解耦。
  • session(会话日志) = 「发生过的一切的 append-only 日志」,存在模型 context 之外。这是最关键的一层。支持:emitEvent(id,event) 写、getEvents() 取某段位置切片、rewind 回退到某一刻之前几条事件重读、wake(sessionId) 在 harness 崩溃后重新拉起、getSession(id) 取回。

它换来什么: 因为大脑无状态、手不绑大脑,推理可以立刻开始不用等容器 provision → 它报的数是 p50 首字延迟降约 60%、p95 降超 90%;而且多个大脑可以互相传手(工具不绑任何一个大脑),session 在崩溃后能 wake 续上。

对我们的意义: 我们其实已经是「大脑/手解耦」的形态(runner 已跨 4 种引擎、工具已是 execute 式)。三层里我们唯独缺 session 这层 —— 一条自己拥有、可 replay 的日志。

来源:anthropic.com/engineering/managed-agents(2026,已逐条核实)。事件的确切字段结构博客没给全 UNKNOWN。

B · openclaw 开源,已被 OpenAI 收购(2026-02)

一个 24/7 无人值守的个人 agent 框架,一周拿了 10 万 GitHub star。它的实现文档很细,值得逐条对照(下面是查到的真实配置键):

  • Gateway 常驻 daemon(Linux systemd / macOS LaunchAgent):管消息渠道连接、把消息路由到 agent session、调度。路由用 bindings[] 按确定顺序匹配(peer→guild→team→account→默认)。写锁 session.writeLock(60s 拿锁、1800s 抢回僵锁)。
  • session 持久化:~/.openclaw/agents/{id}/sessions/sessions.json per-agent;维护策略 pruneAfter:30d / maxEntries:500 + transcript 归档保留。
  • 记忆 / 长跑 context(和我们最相关):workspace 里 AGENTS.md/SOUL.md/HEARTBEAT.md 注入系统提示;关键是它处理 context 饱和的手法 —— compaction(default/safeguard 两档,chunked LLM 摘要、可用专用小模型);memoryFlush:在自动 compaction 之前先跑一个静默 agent 轮,把该记的东西写进 workspace 的 memory/*.md,再压缩,减少信息损失;还有 contextInjection:continuation-skip(安全续跑不重复注入)、startupContext(重置后注入最近的每日记忆)、contextPruning:cache-ttl。
  • 消息队列:messages.queue.mode = steer(插进正跑的轮)/ followup(跑完再跑)/ collect(批)/ interrupt(打断);debounce 2000ms;队列 cap 20 + drop 策略(summarize/old/new)。
  • failover:model:{primary, fallbacks:[...]} 失败按序退;utilityModel/imageModel 各自 fallback;OpenAI 模型默认走 codex harness。

对我们的意义: 这些编排能力我们几乎逐条都有对应(下节对照表)。openclaw 不是一个我们该照抄的新架构;真正值得学的是它处理 context 饱和的具体手法(尤其 memoryFlush = 压缩前先把记忆落到文件)—— 注意这跟 A 的「全事件日志」是两条不同的路:openclaw 还是有损压缩 + 一层 markdown 记忆兜底,A 是根本不丢的 append-only 日志。这个分叉正是你要评估的点。

来源:docs.openclaw.ai/gateway/{config-agents,heartbeat}(2026,已核实配置键)。JSONL transcript 确切格式、OAuth 刷新、多实例 leader-election 文档没给 UNKNOWN。

2b · 你问的:我们到底用不用 DAG?动态还是静态?跟 homerail 差在哪

先给结论(已 grounded 核代码,不是猜):我们是动态编排,不是静态预编排 DAG。

  • 我们有 DAG 代码,但它 dormant(没在跑)。 仓里确实有个 dag-resolver 包(用 Kahn 拓扑排序处理 Linear 的 blockedBy 依赖)—— 这是 v0.2 老架构留下的(老图「Linear issues → DAG resolver → sessions」)。但核代码事实:整图自动执行的 DagDispatcher 在当前生产 Bridge 路径里没有任何实例化点(全仓 grep new DagDispatcher = 生产路径 0 处)→ 这套「预排好一张图、自动照图走」的机制事实上没在跑。
  • 当前真实派活 = Lead 逐 issue 动态派。 生产入口是 RunDispatcher(FLY-22)按 /api/runs/start 一个 issue 一次触发;AgentDispatcher.dispatch({issueLabels, owningDept}) 按 label/部门动态选哪个 agent role;一个 issue 内部的编排 = 三段式(设计→实现→QA)。谁跑、什么时候跑,是 Lead(Cass 分诊 / Tadashi 派)或 founder 现场决定的,不是一张预先规划好的图在自动走。
  • 唯一起作用的「依赖」= Linear 自己的 blockedBy —— 由人/Lead 读了判断先做哪个,不是一个自动 DAG 执行器在 gate。

跟 homerail 的「静态 DAG」差在哪:

  • 静态 DAG 的形态(general pattern,已核实):一个 Planner 预先把整张任务图规划好 → Executor 照图走 → 依赖预声明、执行顺序固定(需要时有 Replanner 调整)。「先规划、后自动执行」。
  • 我们相反:没有「先把整图规划好再自动执行」这一步。每次派活是 Lead/founder 现场动态决定的,人在环。那张「图」(Linear blockedBy)是给人看的 advisory,不是自动执行的。

「我们是不是已经跟 homerail 很像了?」诚实答:表面像、实质不像。 表面像 —— 我们确实有个 dag-resolver 包、Linear 也有 blockedBy 依赖;但那只停在「都有依赖这个概念」。实质不像 —— 真正的分水岭是「谁决定执行、何时决定」:静态 DAG 是预先 / 自动照图执行;我们是现场 / Lead 动态派、人驱动。所以我们不该被归成「静态 DAG 那一类」。

2c · 你问的 4 个问题(grounded 核代码答)

① DAG:当初为啥建、优势是啥、为啥现在 dormant?

为啥建: DAG 是最初版(v0.1.0,第一个 Core Loop)的编排原语 —— 那会儿的设想就是「Linear issues → DAG resolver → Claude Code sessions → PR」,让系统自动把一堆 issue 按 blockedBy 依赖排好序、自己往下跑。

优势(它擅长的): 用 Kahn 拓扑排序自动算出「现在哪些没被 block、可以开跑」(getReady)、 做完标 markDone、卡住 shelve 并自动挡住下游;独立分支能并行。= 一张图排好、不用人 盯着就自动按依赖跑完。

为啥现在 dormant(不跑了): 产品方向变了。我们从「自动跑整张图」转成「Lead 逐 issue 动态派、人在环」 (v0.2 起、多 Lead 之后)。v0.2 架构文档把 DAG resolver 标成「Preserved 代码不变」 —— 留着,但没接进 live 派活。根本原因:我们赌的是「人的注意力才是瓶颈」+ 每次派活要过 founder/Lead 的产品判断,而不是让 一个自动 planner 把整张图跑完。所以那张自动执行器被「人/Lead 现场决定」取代了,blockedBy 现在是给人看的。

② respawn / tmux 保活具体怎么实现?多机时怎么变?

单机怎么实现(现状): 每个 runner 跑在一个 tmux 会话里。为了不丢状态,我们不 respawn、而是保活 + 唤醒 (FLY-887 保活 + FLY-939 wake-not-respawn):那个 phase session 一直挂着(parked);要重跑/复验时,Bridge 给它发一个 mailbox 唤醒 + 用 tmux send-keys 把消息打进那个终端,让原来那个进程接着干,而不是新起一个。

⚠️ 精确一点(回应你的问题「crash 了 tmux 还在、记住名字就行?」):不完全是。 真正保住 context 的不是 tmux,是 「我们不让那个 claude 进程退出」 —— 它 parked/idle 但一直活着,所以它内存里的完整 context 还在(代码原话: parked session「woken, not respawned, keep full context」)。tmux 只是托住这个活进程的壳。如果进程真的挂了 (crash / 显式 terminate / reboot),tmux 窗口还在,但那个死进程内存里的 context 就没了 —— tmux 救不回死进程的记忆; 这时只能重启 + 从 progress.md 粗粒度重建(丢细节)。所以真机制 = 「别让进程退出」;它在单机、进程没真死时好用, 真 crash 会丢、多机也不行 —— 这两道缝正是「自己 own 一条 log」能补的(= 场景②③ 的动机)。

为什么这套只在单机成立: tmux send-keys 是本机操作 —— Bridge 得和那个 tmux 会话在同一台机器、 用同一个 tmux socket 才能戳进去。我们现在正是单机(Lead + 所有 runner 都在同一台 Mac)。

多机就不是这样了(你点的那点,对): 一旦 runner 分散到多台机器,machine A 的 Bridge没法 tmux send-keys 到 machine B 上的会话 → 「保活 + 唤醒」直接失效。这时候要么状态得做成 host-independent(= 场景③ 那条自己 own 的 log,fresh runner 在任意机器上从 log 重建),要么得有跨机的协调层。多机目前是 future(有份 008-multi-machine-consensus 研究在评 Raft/BFT/中心 Coordinator),还没做。

③「编排层」大白话是啥?(= 谁决定下一步派谁干啥)

「编排层」就是「决定下一步该干嘛、该让谁去干」的那层。我们现在这层是人/Lead 在现场做的,不是一个自动程序:

  • 一个 Linear issue 进来 → CoS(Aunt Cass)先分诊:打标签、判断归哪个部门 → 路由给对应的部门 Lead(比如 Tadashi);
  • Lead 决定派一个 Runner去干这个 issue(什么时候派、派哪种 agent,Lead 现场定);
  • 一个 issue内部,走三段式:设计 → 实现 → QA,一段做完进下一段;
  • ship(合入)永远是 founder 点头。

所以「编排 = 一串人/Lead 的现场决定」。那个 dormant 的 DAG,当年就是想把这层自动化掉(机器照图决定下一步),现在这层交回给了人 + Lead。
